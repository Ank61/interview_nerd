Why Eventual Consistency is WRONG Here</h3>\n<div class=\"code\"><div class=\"code-head\"><span>javascript</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c>// Eventual consistency = &quot;the system will become consistent... eventually.&quot;</i>\n<i class=c>// This is fine for many systems. It is CATASTROPHICALLY WRONG for ticket booking.</i>\n<i class=c>// ================================================================================</i>\n<i class=c>//</i>\n<i class=c>// Eventual consistency means:</i>\n<i class=c>// - Read and write to any node immediately</i>\n<i class=c>// - Nodes sync with each other asynchronously</i>\n<i class=c>// - For a brief window, different nodes have different views of the data</i>\n<i class=c>//</i>\n<i class=c>// Example of eventual consistency working fine:</i>\n<i class=c>// User A updates their profile bio. User B&#x27;s feed shows old bio for 500ms.</i>\n<i class=c>// Then replication catches up. Both see new bio. No harm done.</i>\n<i class=c>//</i>\n<i class=c>// Example of eventual consistency for tickets (DISASTER):</i>\n<i class=c>// User A books seat 42 on Node 1. Node 1 accepts.</i>\n<i class=c>// User B books seat 42 on Node 2. Node 2 also accepts (hasn&#x27;t received A&#x27;s write yet).</i>\n<i class=c>// Replication runs. Conflict detected. System must pick a winner.</i>\n<i class=c>// Under &quot;last write wins&quot; (LWW): A&#x27;s booking is silently deleted.</i>\n<i class=c>// A received a confirmation. A shows up. No seat. A sues the venue.</i>\n\n<i class=c>// Why &quot;last write wins&quot; CAN&#x27;T fix double booking:</i>\n<i class=c>// =================================================</i>\n<i class=k>class</i> <i class=f>LastWriteWins</i> {\n  <i class=c>// In distributed databases like Cassandra, DynamoDB (without transactions):</i>\n  <i class=c>// Each write has a timestamp.</i>\n  <i class=c>// On conflict, the write with the LATER timestamp wins.</i>\n  <i class=c>// The EARLIER write is overwritten without error.</i>\n  <i class=c>// Both users received &#x27;booking confirmed&#x27;. One booking is silently deleted.</i>\n  <i class=c>//</i>\n  <i class=c>// Cassandra: seat 42 → written at t=100 (User A) and t=101 (User B)</i>\n  <i class=c>// Cassandra resolves: User B wins (later timestamp)</i>\n  <i class=c>// User A has a confirmation email for a booking that no longer exists.</i>\n}\n\n<i class=c>// Why &quot;read your own writes&quot; consistency isn&#x27;t enough:</i>\n<i class=c>// ======================================================</i>\n<i class=c>// Even if each user can read their own writes:</i>\n<i class=c>// User A writes booking, reads it back → sees confirmed (correct)</i>\n<i class=c>// User B writes booking, reads it back → sees confirmed (correct)</i>\n<i class=c>// But BOTH EXIST. Seat is still double booked.</i>\n<i class=c>// Read-your-own-writes doesn&#x27;t detect cross-user conflicts.</i>\n\n<i class=c>// Why you need STRONG (linearizable) consistency for booking:</i>\n<i class=c>// ============================================================</i>\n<i class=c>// Strong consistency: every read sees the most recent write.</i>\n<i class=c>// All nodes agree on the current state of every row.</i>\n<i class=c>// When User B tries to book seat 42, the system KNOWS User A already booked it.</i>\n<i class=c>// User B&#x27;s booking fails. Zero double bookings.</i>\n\n<i class=c>// Systems that provide strong consistency for OLTP:</i>\n<i class=c>// ==================================================</i>\n<i class=c>// ✅ PostgreSQL, MySQL — single-node, ACID, serializable</i>\n<i class=c>// ✅ CockroachDB, YugabyteDB — distributed, but ACID with serializable isolation</i>\n<i class=c>// ✅ Google Spanner — global distributed, external consistency (even stronger than serializable)</i>\n<i class=c>// ❌ Cassandra — tunable, but &quot;eventual&quot; by default. No row-level transactions across partitions.</i>\n<i class=c>// ❌ DynamoDB — EVENTUALLY consistent reads by default. Strongly consistent reads available</i>\n<i class=c>//               but no cross-partition transactions (unless using Transactions API at cost)</i>\n<i class=c>// ❌ MongoDB (without transactions) — document-level atomicity only</i>\n\n<i class=c>// The CAP theorem and tickets:</i>\n<i class=c>// ============================</i>\n<i class=c>// CAP: In a distributed system, choose 2 of: Consistency, Availability, Partition Tolerance</i>\n<i class=c>// Network partitions WILL happen. So you choose: Consistency OR Availability.</i>\n<i class=c>//</i>\n<i class=c>// CP (Consistency + Partition Tolerance): System refuses to serve if it can&#x27;t guarantee consistency.</i>\n<i class=c>//   → Correct for tickets. User gets an error during partition, not a wrong answer.</i>\n<i class=c>//</i>\n<i class=c>// AP (Availability + Partition Tolerance): System serves requests even during partition.</i>\n<i class=c>//   → Might show seat as available when it isn&#x27;t. Double booking risk.</i>\n<i class=c>//</i>\n<i class=c>// For ticket booking: choose CP. It is BETTER to show &quot;System temporarily unavailable&quot;</i>\n<i class=c>// than to sell the same seat to two people.</i>\n<i class=c>// Users tolerate outages. Users do NOT tolerate showing up to a concert without a seat.</i>\n\n<i class=c>// The bottom line:</i>\n<i class=c>// ================</i>\n<i class=c>// Eventual consistency is a performance/availability optimization.</i>\n<i class=c>// It trades correctness for speed.</i>\n<i class=c>// Ticket booking cannot trade correctness. Choose strong consistency.</i>\n<i class=c>// Use PostgreSQL or a distributed SQL database. Not Cassandra. Not DynamoDB.</i></code></pre></div>\n<h3>7.
