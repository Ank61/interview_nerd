When a step throws, Secrets Manager leaves <code>AWSCURRENT</code> where it was, so the application keeps working with the old credential and there is no user-visible symptom. The failure only becomes an incident when something else expires — a vendor key with a hard 90-day life, a certificate, a compliance audit, or a database policy that disables passwords older than N days. By then the rotation has been failing for weeks. Build four independent layers of detection, because each catches things the others miss.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>EventBridge on rotation events.</strong> Secrets Manager emits events to the default event bus, including <code>RotationFailed</code>, <code>RotationSucceeded</code> and <code>RotationStarted</code>. Secrets Manager retries the rotation automatically for a period, and will re-enter the state machine at the failed step; if a subsequent scheduled rotation arrives it issues a new <code>ClientRequestToken</code>, which is why you can accumulate multiple stale pending versions if nobody is looking.</p>\n<p style=\"line-height: 1.75\">The recovery procedure has a hard rule at the front of it: <strong>verify the target system's actual state, do not trust the secret's state</strong>. The secret cannot tell you whether the ALTER USER committed, whether the vendor minted the key, or whether the new user got its grants. So: (1) read the pending version and try to authenticate to the target with it manually. (2) If the pending credential works, the target was already mutated — the safest move is to let rotation retry, or to complete it deliberately by moving <code>AWSCURRENT</code> onto that version. (3) If the pending credential does not work, the target was never mutated or was mutated to something else — remove the <code>AWSPENDING</code> staging label from the orphaned version with <code>update-secret-version-stage --remove-from-version-id</code>, which leaves it unstaged and eligible for eventual deletion, then fix the underlying cause and re-run <code>rotate-secret --rotate-immediately</code> from a clean state. (4) Only as a last resort, and only when you have confirmed the target's real password out of band, use <code>put-secret-value</code> to write the truth back into <code>AWSCURRENT</code>. And note the recovery you do <em>not</em> reach for: rolling back by re-staging <code>AWSPREVIOUS</code> as current is only valid if the target still accepts that old value, which after a completed single-user rotation it does not.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Blast-Radius Control</h4>\n<p style=\"line-height: 1.75\">A change to a rotation function is a change to something that mutates production credentials, so it deserves deployment discipline stronger than normal application code. <strong>Canary</strong> it: point the new version at a handful of low-risk secrets — staging, internal tools, a scratch database — let them rotate on an accelerated schedule, and only then promote. <strong>Version and alias</strong> the function: publish an immutable Lambda version on each deploy and attach secrets to an alias such as <code>live</code>, so promoting is an alias update and rollback is an alias update back, without touching a thousand secret configurations. Note that the <code>RotationLambdaARN</code> on each secret should then be the <em>alias</em> ARN, and the alias must carry the <code>lambda:InvokeFunction</code> resource permission for <code>secretsmanager.amazonaws.com</code>.</p>\n<p style=\"line-height: 1.75\">On function topology, the strong default at scale is <strong>one well-tested shared function per credential class</strong>, configured per secret through fields in the secret JSON, tags, or environment lookups — not a function per secret. A function per secret means a thousand Lambdas to patch when the runtime is deprecated, a thousand copies of a bug, and a thousand IAM roles. The shared function's downsides are real and manageable: its IAM role must be able to read every secret it serves, which is a concentration of privilege you mitigate with tag-based or path-based conditions; and its <code>Errors</code> metric is fleet-wide, which you mitigate with EventBridge for per-secret attribution.
