{"title":"VPC Endpoints and Private Connectivity for Secrets Manager","tags":["vpc-endpoint","privatelink","networking","data-perimeter"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Secrets Manager is a regional public API. By default, an application calling <code>GetSecretValue</code> resolves <code>secretsmanager.us-east-1.amazonaws.com</code> to a public IP address and reaches it over the internet — from a private subnet that means a NAT gateway and an internet gateway, and from a public subnet it means straight out. The traffic is TLS-protected the whole way, so confidentiality is not the objection. The objections security teams actually raise are different and worth stating precisely, because \"it's encrypted anyway\" is the answer that loses the interview.</p>\n<p style=\"line-height: 1.75\">First, the traffic leaves the private network path, so network-layer controls, flow logs and egress inspection see an anonymous TLS flow to an AWS IP range rather than a governed path. Second, every secret fetch now depends on NAT gateways, which cost per hour and per gigabyte, have their own failure and throttling characteristics, and put a shared, cross-service component on the critical path of application startup. Third, and most important, there is <strong>no network-level constraint at all</strong>: a credential that leaks — a set of long-lived access keys in a log, an exfiltrated instance profile token — can be used from anywhere on the internet to read the same secrets. The network gives you nothing to hold on to.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interface endpoints and PrivateLink</h4>\n<p style=\"line-height: 1.75\">An interface VPC endpoint for Secrets Manager is the service <code>com.amazonaws.us-east-1.secretsmanager</code>. Creating it provisions an <strong>elastic network interface in each subnet you select</strong>, each with a private IP from that subnet's range, fronting a PrivateLink connection to the service. API calls then travel over the AWS network and never touch an internet gateway or NAT.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Private DNS.</strong> When you enable the private DNS option, AWS associates a managed private hosted zone with your VPC for the service's regional hostname, so the standard SDK endpoint resolves to the endpoint ENI's private address. Applications and SDK configuration need no change whatsoever — this is the single most valuable property of interface endpoints. Endpoint-specific DNS names (regional and zonal) are also provided for cases where you want to target the endpoint explicitly.</li>\n<li><strong>Security groups.</strong> The endpoint ENIs carry security groups, and they are the access control for the endpoint at the network layer. The requirement is inbound TCP 443 from your workload sources. The default security group allowing all traffic from itself is a common cause of a mystifying timeout, because application instances are not in that group.</li>\n<li><strong>Availability.</strong> Create the endpoint in <strong>every Availability Zone your workloads run in</strong>. An endpoint with one ENI in one AZ makes secret retrieval — a startup-path dependency for everything — fail when that AZ has a problem, which converts a single-AZ event into an estate-wide outage.</li>\n<li><strong>Cost.</strong> Interface endpoints bill per ENI per hour (roughly a cent per hour per AZ, so single digits of dollars per month per AZ) plus a small per-gigabyte data processing charge. Secret payloads are tiny, so the data charge is negligible, and for a workload that was paying NAT gateway hourly and per-gigabyte charges for this traffic the endpoint is frequently cheaper as well as safer.</li>\n<li><strong>You almost certainly need a KMS endpoint too.</strong> If secrets use a customer managed key, every read triggers a <code>kms:Decrypt</code> call, and that call has the same public-endpoint problem. Add <code>com.amazonaws.us-east-1.kms</code>, or the private-path story has a hole in it. The same applies to any other service on the startup path, such as STS.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Two controls that look similar and are not</h4>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">A) ENDPOINT POLICY <i class=o>-</i> attached <i class=k>to</i> the endpoint, filters what can pass THROUGH it\n<i class=c>------------------------------------------------------------------------------</i>\n   app <i class=k>in</i> VPC <i class=c>--&gt; [ VPCE (endpoint policy) ] --&gt; Secrets Manager</i>\n                        <i class=o>^</i>\n                        <i class=o>|</i> &quot;only prod/* secrets, only read actions&quot;\n   Effect: traffic through THIS endpoint <i class=k>is</i> limited.\n   Does <i class=k>NOT</i> stop the same credential being used <i class=k>from</i> the internet.\n\nB) aws:SourceVpce <i class=k>CONDITION</i> <i class=o>-</i> <i class=k>in</i> the <i class=k>identity</i> <i class=k>or</i> resource policy\n<i class=c>------------------------------------------------------------------------------</i>\n   app <i class=k>in</i> VPC <i class=c>--&gt; [ VPCE ] --&gt; Secrets Manager   ALLOW (SourceVpce matches)</i>\n\n   laptop <i class=k>on</i> internet <i class=k>with</i> stolen creds <i class=c>--&gt; Secrets Manager   DENY</i>\n                                            (<i class=k>no</i> aws:SourceVpce <i class=k>in</i> request)\n   Effect: the CREDENTIAL <i class=k>is</i> useless outside your network.\n\nYou need BOTH. Its default is full access, which means creating an endpoint changes nothing about authorization until you write one. It cannot grant permissions a principal does not already have; it only filters. Typical uses are restricting the endpoint to Secrets Manager read actions, to secrets in specific account IDs (a data-perimeter control preventing a compromised instance from reaching a secret in an attacker's account), or to a specific ARN prefix. Endpoint policies have a size limit and no visibility into which principal is \"supposed\" to be calling, so keep them coarse: perimeter shape, not per-team detail.</p>\n<p style=\"line-height: 1.75\">The <strong>aws:SourceVpce condition key</strong> is the control that actually changes an attacker's economics. Placed in an identity policy, a resource policy on the secret, or an SCP, it asserts that the request must have arrived through a named VPC endpoint. A credential exfiltrated to an attacker's machine produces requests with no <code>aws:SourceVpce</code> key present, so a deny-unless-matching statement denies them. Its siblings are <code>aws:SourceVpc</code>, which names the VPC rather than a specific endpoint and therefore survives an endpoint being replaced, and <code>aws:VpcSourceIp</code> for the private source address. The VPC's managed private hosted zone is not visible to an on-premises resolver, so the pattern is a <strong>Route 53 Resolver inbound endpoint</strong> in the VPC: on-premises resolvers forward queries for the AWS service domain to the inbound endpoint's IP addresses, which resolve against the VPC's view and return the private addresses. The alternative, hard-coding the endpoint-specific DNS name or its IPs on-premises, works but is brittle and breaks certificate hostname matching if you use raw IPs, so the resolver approach is the one to name in an interview.</p>\n<p style=\"line-height: 1.75\">The failure mode to know cold is <strong>private DNS disabled</strong>. If the endpoint exists but private DNS is off, the standard hostname still resolves publicly, the SDK still works, and traffic goes out over NAT exactly as before. Nothing breaks, no error appears, and the team believes the traffic is private when it is not — until a flow log review or an audit discovers otherwise, or until the NAT gateway is removed as a cost saving and everything fails at once. The related trap is that private DNS requires both <code>enableDnsSupport</code> and <code>enableDnsHostnames</code> on the VPC; without them the option cannot be enabled. Verify with a DNS lookup from inside the subnet: the answer must be an address inside your subnet CIDR, not a public AWS address.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Lambda in a VPC</h4>\n<p style=\"line-height: 1.75\">A Lambda function attached to a VPC loses default internet access entirely. Without a NAT gateway or an interface endpoint it cannot reach any AWS API, so a function that fetched a secret happily before being VPC-attached will start timing out — and because the SDK retries, the symptom is the function hitting its timeout rather than a clean error, which sends people hunting in the wrong place. The fix is an interface endpoint in the same subnets the function is attached to, with a security group permitting 443 from the function's security group. Note the ordering consequence: functions that fetch secrets at module initialization will fail during init, so also cache the secret in a module-level variable to reuse it across warm invocations, which reduces both latency and endpoint traffic.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Troubleshooting, in order</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>1. An <code>UnknownHostException</code> or resolution failure is DNS. This single distinction saves most of the debugging time.</li>\n<li><strong>2. DNS.</strong> From an instance in the subnet, resolve the service hostname. A public address means private DNS is off, or the VPC lacks DNS support or DNS hostnames, or your workload uses a custom resolver that bypasses the VPC resolver.</li>\n<li><strong>3. Security groups.</strong> The endpoint's security group must allow inbound 443 from the client's security group or CIDR. This is the most common cause of timeouts and is frequently missed because the default group only allows itself.</li>\n<li><strong>4. Subnets and routing.</strong> The endpoint must have an ENI in the subnet or at least the AZ where the client runs; cross-AZ works but is a resilience risk. Interface endpoints do not require route table entries — that is a gateway endpoint concern, and confusing the two is a classic error.</li>\n<li><strong>5. Endpoint policy.</strong> If the connection succeeds and you get AccessDenied, check the endpoint policy before anything else, because it is the layer people forget exists and its denials look identical to IAM denials in the client.</li>\n<li><strong>6. Identity, resource and key policies.</strong> Then the usual chain, including the KMS key policy — and check whether a <code>aws:SourceVpce</code> condition somewhere names an endpoint that has since been recreated with a new ID, which is a self-inflicted outage that appears after an infrastructure change.</li>\n<li><strong>7. CloudTrail.</strong> The event record includes <code>vpcEndpointId</code> when the call came through an endpoint. Its absence proves the call went out the public path, which is the definitive test of whether your private path is actually in use.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Production scenario: secrets readable only from inside the VPC</h4>\n<p style=\"line-height: 1.75\">A regulated payments workload must guarantee that production secrets cannot be read from outside the VPC, even with valid credentials, and must prove it to an auditor.
