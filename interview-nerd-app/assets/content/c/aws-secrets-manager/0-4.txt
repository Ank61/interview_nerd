Understanding this one mechanism explains how zero-downtime rotation works.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why Versions Exist at All</h4>\n<p style=\"line-height: 1.75\">Think about what actually has to happen when a database password changes. You have twelve application servers holding the old password in memory. You change the password in the database. For some period — seconds, or minutes if instances cache — some servers are still using the old value. If the old value stopped working the instant the new one was created, every one of those servers would fail.</p>\n<p style=\"line-height: 1.75\">So the core insight is this: during a change, <strong>both the old and the new value may briefly need to be valid at the same time</strong>. Versions give you a place to keep both. They also give you two other practical wins: <strong>rollback</strong>, because if a new value turns out to be wrong you can go back to the exact previous one rather than reconstructing it from memory, and <strong>auditability</strong>, because you can see that the value changed and when.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Version Id</h4>\n<p style=\"line-height: 1.75\">Each version has a <strong>version id</strong> — a unique identifier, in practice a 32-character UUID such as <code>b21f0e9c-3d47-4a12-9f88-1c0e5a7d2b31</code>. It is generated for you (or you may supply one as the <code>ClientRequestToken</code>, which doubles as an idempotency key so a retried call does not create a duplicate version). The version id is permanent and immutable: a version's <em>value</em> never changes once written. What changes is which labels point at it.</p>\n<p style=\"line-height: 1.75\">That immutability is the key mental model. <strong>Versions are immutable; labels move.</strong> Nothing is edited in place — a new value means a new version, and going live means moving a pointer.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Staging Labels as Movable Pointers</h4>\n<p style=\"line-height: 1.75\">A <strong>staging label</strong> is a short text tag attached to a version that describes the role that version is currently playing. The three built-in labels are:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>AWSCURRENT.</strong> The live value. When you call GetSecretValue without specifying a version or a stage, this is what you get. Your applications should always use this default, which is what makes rotation transparent to them.</li>\n<li><strong>AWSPREVIOUS.</strong> The version that used to be AWSCURRENT. It is kept deliberately so that you can fall back — either by reading it during an incident to compare values, or by moving AWSCURRENT back onto it to roll the change back. During a rotation it also means the old credential is still discoverable while stragglers finish using it.</li>\n<li><strong>AWSPENDING.</strong> A newly created value that is <strong>not yet in use</strong>. Rotation creates it, tests it against the real target system, and only then promotes it. If the test fails, AWSPENDING is simply abandoned and nothing in production is affected. This is the label that makes rotation safe rather than a leap of faith.</li>\n</ul>\n<p style=\"line-height: 1.75\">The single most important rule: <strong>a given staging label points to exactly one version at a time</strong>. A label is not a list. If you attach AWSCURRENT to version B while it is on version A, it is automatically removed from A — and, as a special behaviour of this particular label, Secrets Manager automatically puts AWSPREVIOUS onto A. <strong>Moving the AWSCURRENT label is the act that makes a new value live.</strong> Creating the version did not; moving the pointer did.</p>\n<p style=\"line-height: 1.75\">Note the relationship is one-directional, though: one label points to one version, but one version can carry several labels. A version that has <strong>no staging label at all</strong> is considered <strong>deprecated</strong>, and Secrets Manager cleans deprecated versions up in the background. Two guardrails apply: a deprecated version is retained for at least <strong>24 hours</strong> before it can be removed, and the service keeps a bounded number of versions — <strong>at most about 100 deprecated versions</strong> are preserved per secret, with the oldest removed first. Anything still carrying a label, including a custom one, is exempt from cleanup entirely.</p>\n<p style=\"line-height: 1.75\">Two practical consequences. First, you cannot rely on Secrets Manager as a long-term archive of every password you have ever used — if you need that for compliance, capture it deliberately elsewhere. Second, if you want a particular version to survive, put a custom staging label on it. You can list what exists at any time with <code>list-secret-version-ids</code>, which optionally includes deprecated versions.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">How This Makes Zero-Downtime Rotation Possible</h4>\n<p style=\"line-height: 1.75\">Put the pieces together and the guarantee becomes clear. The new value is created and tested while wearing AWSPENDING, so applications are entirely unaffected if it is wrong. Promotion is a <strong>single atomic label move</strong>, so there is never a moment when AWSCURRENT is undefined or when two values are both \"the\" live one. The old value survives as AWSPREVIOUS, so an application that retries after an authentication failure has a defined fallback and an operator has a one-command rollback.</p>\n<p style=\"line-height: 1.75\">The remaining gap — the seconds or minutes during which cached copies of the old password are still in use — is closed in one of two ways.
