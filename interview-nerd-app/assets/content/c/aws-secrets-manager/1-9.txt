{"title":"Secrets in CI/CD — OIDC Federation and Pipeline Security","tags":["cicd","oidc","github-actions","supply-chain"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">The CI/CD system is the highest-value target in most engineering organisations, because it holds credentials for everything and is the one system that is allowed to change production. The dominant anti-pattern is depressingly simple: someone generates an IAM user, creates an access key pair, pastes it into the CI provider's secret store as <code>AWS_ACCESS_KEY_ID</code> and <code>AWS_SECRET_ACCESS_KEY</code>, and it stays there for years. That key is long-lived, usually over-permissioned because nobody wants the pipeline to fail on a missing permission, shared across dozens of workflows, and copied to laptops for local debugging. It is exfiltratable by any code that runs in the pipeline — including a compromised transitive npm or PyPI dependency executing in a build step, which is precisely how several high-profile supply-chain incidents have played out. And it is invisible to your detection: the credential is valid, so CloudTrail shows a normal API call from a normal principal, just from an unexpected IP.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">OIDC federation: the modern answer</h4>\n<p style=\"line-height: 1.75\">The fix is to remove the static key entirely using <strong>OIDC federation</strong>. The mechanics are the same as IRSA in EKS, which makes this a nice interview thread to pull. The CI provider — GitHub Actions, GitLab CI, Bitbucket, CircleCI, Buildkite — acts as an <strong>OpenID Connect identity provider</strong>: at job start it mints a short-lived, cryptographically signed JWT describing that specific job. The token's claims say which repository, which branch or tag, which workflow file, which environment, and which event triggered it. You create an <strong>IAM OIDC identity provider</strong> in the AWS account pointing at the CI provider's issuer URL, and a role whose trust policy accepts <code>sts:AssumeRoleWithWebIdentity</code> from that provider <em>with conditions on the claims</em>. The job calls STS with the token and receives temporary credentials that expire in an hour.</p>\n<p style=\"line-height: 1.75\">Three properties follow. There is <strong>no stored credential</strong> to leak, rotate, or audit. The credential is <strong>scoped to one job</strong> and dies with it. And the <strong>trust policy is expressive</strong> — you can say \"only the main branch of the acme/payments repository, running in the production environment, may assume the production deploy role.\" That last property is where all the security lives, and where all the mistakes are.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Subject conditions: the place people get breached</h4>\n<p style=\"line-height: 1.75\">GitHub's <code>sub</code> claim takes forms like <code>repo:acme/payments:ref:refs/heads/main</code>, <code>repo:acme/payments:environment:production</code>, and <code>repo:acme/payments:pull_request</code>. The dangerous patterns:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>No sub condition at all.</strong> If the trust policy only checks the <code>aud</code> claim, then <em>any GitHub repository on the internet</em> can assume your role. This is not hypothetical; it has happened repeatedly to real companies. Always condition on sub.</li>\n<li><strong>A trailing wildcard on the org.</strong> <code>repo:acme/*</code> means any repo in the org — including a new, unreviewed one, or one a contractor can push to.</li>\n<li><strong>A wildcard on the ref.</strong> <code>repo:acme/payments:*</code> means any branch, any tag, any pull request from any fork. Anyone who can open a PR can then run arbitrary code with your production role. This is the single most common real-world OIDC misconfiguration.</li>\n<li><strong>Forgetting the aud condition.</strong> Always pin <code>token.actions.githubusercontent.com:aud</code> to <code>sts.amazonaws.com</code>, so a token minted for a different audience cannot be replayed at STS.</li>\n<li><strong>StringLike where StringEquals would do.</strong> If the value has no wildcard, use StringEquals — it removes the whole class of accidental-wildcard bugs. Use <code>ForAllValues</code>/<code>StringLike</code> carefully if you must match a set.</li>\n</ul>\n<p style=\"line-height: 1.75\">The strongest pattern for production is to condition on <strong>environment</strong> rather than branch: <code>repo:acme/payments:environment:production</code>. GitHub Environments support required reviewers and branch protections, so the token for that environment is only minted after a human approval gate, and the enforcement is on GitHub's side of the boundary rather than depending on your branch-name discipline. Pair it with separate roles per environment — a read-only plan role for PRs, an apply role for main, a production role behind an environment gate — so the blast radius of each is bounded.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Build-time versus runtime secrets — most secrets shouldn't enter the pipeline</h4>\n<p style=\"line-height: 1.75\">This is the reframing that separates a senior answer from a junior one. Ask what the pipeline actually needs. In the overwhelming majority of cases, the pipeline needs to <strong>deploy infrastructure that grants the running workload access to a secret</strong> — it does not need to read the secret's value. A deployment that sets an ECS task definition's <code>secrets</code> block to a secret ARN, or a Lambda environment variable to a secret ARN, or an IRSA role annotation, hands the credential problem to the runtime, where the value is fetched by the workload's own identity at start. Best handled by never exposing the key at all: use KMS asymmetric signing or AWS Signer, so the pipeline calls an API and the private key never leaves the HSM.</li>\n<li><strong>Third-party registry or package credentials</strong> — pulling from a private registry, publishing to npm or PyPI. Scope to a publish-only token for one package, with a short expiry, and prefer the registry's own OIDC trusted-publishing support where it exists, which removes the token entirely.</li>\n<li><strong>Integration-test database or service credentials</strong> — needed by tests that talk to a real dependency. Use a dedicated non-production secret with a disposable, throwaway target (an ephemeral test database created and destroyed per run), never the production credential.</li>\n<li><strong>Deploy-time bootstrap</strong> — seeding a brand-new secret. Generate the value in-place with <code>--generate-secret-string</code> so nothing is ever transported.</li>\n</ul>\n<p style=\"line-height: 1.75\">For each exception, the discipline is: separate secret per pipeline, scoped IAM so the pipeline role can read only that ARN, short-lived where possible, and an explicit owner. \"Does this pipeline need the value, or just a reference?\" is a question worth asking of every secret in the store.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Leak prevention — and why masking is not a control</h4>\n<p style=\"line-height: 1.75\">Every CI provider masks registered secrets in log output, replacing them with asterisks. Treat it as a typo-catcher, not a security boundary, because it is defeated trivially:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Transformation.</strong> Base64-encode, URL-encode, reverse, gzip, or JSON-escape the value and the masker no longer matches. Any tool that re-encodes a credential into a connection string or a header breaks the match.</li>\n<li><strong>Multi-line values.</strong> Masking is typically line-oriented; a PEM private key printed in full often emerges with only some lines masked.</li>\n<li><strong>Substrings and splitting.</strong> Printing the value one character at a time, or a script echoing a partial value, slips through.</li>\n<li><strong>Non-log egress.</strong> Masking only touches the log stream. A value written to an uploaded artifact, a test report, a core dump, or an outbound HTTP request is untouched.</li>\n</ul>\n<p style=\"line-height: 1.75\">The structural controls that actually work:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Never use container build arguments for secrets.</strong> A Docker <code>ARG</code> is recorded in the image history and readable by anyone who pulls the image, even if the file is deleted in a later layer — layers are additive, deletion does not remove data. Use BuildKit secret mounts, which expose the value to one RUN step via a tmpfs mount and leave nothing in the layer.</li>\n<li><strong>Ephemeral runners.</strong> A fresh VM or container per job means no credential, cache, or clone survives to the next job, and a compromised job cannot pivot to another team's build. Self-hosted persistent runners on public repositories are a well-known path to compromise because fork PRs can execute on them.</li>\n<li><strong>Restrict who can run workflows with secrets.</strong> Fork pull requests must not receive secrets or an OIDC token for privileged roles; use the separate PR-triggered event types deliberately and keep privileged work on post-merge triggers or environment-gated jobs.</li>\n<li><strong>Scan artifacts and images.</strong> Run a secret scanner over built images and published artifacts, not just source, because credentials leak via config files baked at build time.</li>\n<li><strong>Pin third-party actions/orbs by commit SHA</strong>, not by a mutable tag. A tag can be repointed at malicious code that reads your environment.</li>\n<li><strong>Least privilege on the job token itself</strong> — set default permissions to read-only and grant per-job, so a compromised step cannot push code or create releases.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Scanning and remediation: the rotation rule</h4>\n<p style=\"line-height: 1.75\">Layer detection: <strong>pre-commit hooks</strong> (gitleaks, detect-secrets, trufflehog) catch the mistake before it leaves the laptop but are bypassable with <code>--no-verify</code>, so they are a convenience not a control; <strong>server-side push protection and repository scanning</strong> (GitHub secret scanning with push protection, or a scanner in CI on every PR) is the enforcement point because it cannot be skipped; and <strong>provider-side detection</strong>, where AWS itself flags exposed access keys found in public repos and applies a quarantine policy.</p>\n<p style=\"line-height: 1.75\">The remediation rule is the part interviewers listen for: <strong>a leaked secret must be rotated, not merely deleted.</strong> Rewriting git history with filter-repo or BFG does not help, because the commit was already cloned, mirrored, cached by the forge, indexed by crawlers, and possibly picked up by an automated scanner within seconds of the push. Public-repo credentials are typically exercised by bots in under five minutes. So the order is: (1) revoke or rotate the credential immediately — for AWS, deactivate the key and rotate the secret; (2) search CloudTrail for any use of it outside expected sources; (3) only then clean history, mostly to stop the scanner from re-alerting; (4) file the incident and fix the mechanism that allowed the value into the repo in the first place. Rotating first and investigating second is deliberate — the value of the credential to an attacker decays to zero the instant you rotate.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Deployment-time injection patterns</h4>\n<p style=\"line-height: 1.75\">The mechanisms that let a pipeline deploy without reading values:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>ECS/Fargate task definitions.</strong> The <code>secrets</code> container property takes a name and a <code>valueFrom</code> ARN (optionally with a JSON key suffix). The ECS agent, using the <strong>task execution role</strong>, fetches the value at container start and injects it as an environment variable. The pipeline only ever writes an ARN into JSON.</li>\n<li><strong>Lambda.</strong> Put the secret ARN in an environment variable and fetch in the init phase, ideally through the <strong>Parameters and Secrets Lambda Extension</strong>, which provides a local HTTP cache so warm invocations avoid an API call. Never put the value itself in a Lambda environment variable — it is visible in the console, in <code>GetFunctionConfiguration</code>, and in the CloudFormation template.</li>\n<li><strong>EKS.</strong> Deploy the SecretProviderClass or ExternalSecret; the workload's IRSA role resolves it at runtime.</li>\n<li><strong>App Runner, CodeBuild, Batch</strong> all accept secret ARNs in their environment configuration with the same fetch-at-start semantics.</li>\n<li><strong>CloudFormation dynamic references</strong> resolve a secret at deploy time — useful, but note the resolved value can end up materialised in the deployed resource's configuration, so an ARN reference plus a runtime fetch is usually stronger.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario: hardening a pipeline that stores a production DB password</h4>\n<p style=\"line-height: 1.75\">Finding: a GitHub Actions workflow has <code>PROD_DB_PASSWORD</code> and a static <code>AWS_SECRET_ACCESS_KEY</code> as repository secrets, and a deploy step substitutes the password into a rendered ECS task definition.
