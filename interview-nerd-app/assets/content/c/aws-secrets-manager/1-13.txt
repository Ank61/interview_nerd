{"title":"Auditing, Detection Engineering, and Compliance","tags":["aws","secrets manager","cloudtrail","detection"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Almost every organisation has CloudTrail enabled. Almost none of them <em>detect</em> anything with it. Enabling a trail and setting a retention policy is <strong>evidence collection</strong>; it answers questions after someone already knows to ask. <strong>Detection engineering</strong> is the discipline of converting that evidence into hypotheses that fire on their own — specific, tuned, owned, tested queries that say \"this pattern of secret access is abnormal and someone should look at it now.\" The gap between the two is where breaches live for months. A senior candidate should be able to say what Secrets Manager writes to CloudTrail, how to query it at fleet scale, which specific detections are worth the maintenance burden and why, and how the same pipeline produces audit evidence.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What CloudTrail Actually Records for Secrets Manager</h4>\n<p style=\"line-height: 1.75\">The critical and slightly unusual fact: for Secrets Manager, <strong><code>GetSecretValue</code> is recorded as a management event</strong>. In most services the data plane is a separate, opt-in, chargeable data-event category — S3 object reads being the classic example. Here the read path is in the management event stream, which means it is captured by an ordinary organisation trail with no extra configuration and no per-event data-event charge. That is why a Secrets Manager audit story is so much easier to build than an S3 one, and saying so demonstrates real familiarity.</p>\n<p style=\"line-height: 1.75\">Each event record carries the fields that make detection possible:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>userIdentity.</strong> The principal: an assumed role with its session name, an IAM user, or an AWS service. The <code>sessionContext</code> sub-structure includes the role ARN, when the session was issued, and — importantly — whether MFA was present. For a role assumed by EC2 or ECS, the session name often encodes the instance or task, which is how you get from \"a role did this\" to \"this host did this.\"</li>\n<li><strong>sourceIPAddress.</strong> The caller's IP. For calls from inside a VPC through a VPC endpoint this is a private address; calls traversing the internet show a public one. A production-only role suddenly calling from a residential or hosting-provider IP is one of the strongest single signals available.</li>\n<li><strong>userAgent.</strong> The SDK, language, version, or CLI that made the call. Your application fleet has a stable, narrow user-agent distribution. A sudden appearance of a bare CLI user agent, an unfamiliar SDK language, or an enumeration tool's fingerprint against a production secret is a high-quality signal precisely because the baseline is so tight.</li>\n<li><strong>requestParameters.secretId.</strong> Which secret was requested. Note that this reflects what the caller passed — a friendly name or an ARN — so normalise it before grouping, or your counts will split across spellings of the same secret.</li>\n<li><strong>eventName, errorCode and errorMessage.</strong> Whether the call succeeded, and if not, why: <code>AccessDeniedException</code> for an authorisation failure, <code>ResourceNotFoundException</code> for a secret that does not exist, <code>ThrottlingException</code> for rate limiting. <strong>Denied calls are logged</strong>, which is what makes enumeration detection possible at all.</li>\n<li><strong>vpcEndpointId, eventTime, awsRegion, recipientAccountId, requestID.</strong> The endpoint used (proving in-VPC access), the timing, and the identifiers that let you correlate across services and accounts.</li>\n</ul>\n<p style=\"line-height: 1.75\">One thing CloudTrail emphatically does <strong>not</strong> record is the secret value itself, or any plaintext derived from it. The log proves that a retrieval happened; it never leaks what was retrieved. Do not alert on an absolute threshold — alert on a <strong>ratio against that principal's own recent baseline, normalised by fleet size</strong>. A service that triples its task count legitimately triples its retrievals; a service whose per-task retrieval rate jumps a hundredfold has a broken cache or an attacker.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">EventBridge for Near-Real-Time Response</h4>\n<p style=\"line-height: 1.75\">CloudTrail-plus-Athena is minutes-to-hours. Some events deserve seconds. <strong>EventBridge</strong> receives CloudTrail management events as they occur and can match them with a pattern, delivering to SNS, Lambda, Step Functions, or Systems Manager Automation. This is where automated containment lives.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Notify on high-signal, low-volume events.</strong> Resource-policy changes, force-deletes, rotation cancellations, and replication to new Regions are rare enough to page on directly with almost no tuning.</li>\n<li><strong>Trigger containment automation.</strong> On a strong exfiltration signal, a Lambda can call <code>RotateSecret</code> immediately, attach a deny statement to the secret's resource policy, tag the secret as under investigation, and open an incident ticket — turning a detection into a contained event before a human reads the page.</li>\n<li><strong>Consume Secrets Manager's own rotation events.</strong> The service emits events for rotation outcomes, which lets you alert on <em>rotation failed</em> rather than discovering it in a monthly compliance report.</li>\n<li><strong>Automate carefully.</strong> Automatic rotation as a containment action can itself cause an outage if alternating-users rotation is not configured and clients do not retry. Gate aggressive automation on tags that assert the secret is safe to rotate unattended; otherwise notify and let a human pull the trigger.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">AWS Config, Security Hub, GuardDuty and Access Analyzer</h4>\n<p style=\"line-height: 1.75\">Detection tells you what <em>happened</em>. Posture management tells you what is <em>true right now</em>. You need both, and interviewers like candidates who separate them cleanly.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>AWS Config managed rules</strong> evaluate configuration continuously. The relevant ones are <code>secretsmanager-rotation-enabled-check</code> (rotation is turned on), <code>secretsmanager-scheduled-rotation-success-check</code> (rotation actually succeeded within its schedule — the one that catches silent failure), <code>secretsmanager-secret-periodic-rotation</code> (the value has changed within N days), <code>secretsmanager-secret-unused</code> (not accessed within N days, which is your dead-secret finder), and <code>secretsmanager-using-cmk</code> (encrypted with a customer managed key rather than the AWS managed key). Deploy them organisation-wide through a <strong>conformance pack</strong> so posture is uniform and drift is visible in one dashboard.</li>\n<li><strong>AWS Security Hub</strong> aggregates those findings across accounts and Regions and maps them to standards. The AWS Foundational Security Best Practices standard includes Secrets Manager controls covering automatic rotation being enabled, rotation succeeding, unused secrets being removed, and secrets being rotated within a specified number of days. Security Hub is the right place to answer \"what is our posture across 200 accounts\" in one view rather than per account.</li>\n<li><strong>Amazon GuardDuty</strong> is behavioural rather than configurational. Its IAM finding types cover anomalous credential behaviour and, notably, <strong>instance credentials being used from outside AWS</strong> — the finding that most directly indicates a stolen role credential which could then be used to read secrets. Treat GuardDuty as a complement to your own rules: it has a baseline you do not have to build, and you have context it does not have.</li>\n<li><strong>IAM Access Analyzer</strong> analyses resource-based policies to find resources — including <strong>Secrets Manager secrets</strong> — that grant access to a principal <em>outside your defined zone of trust</em>, which you set to the account or the organisation. This is the tool that answers \"is any production secret readable by an external account?\" without manually reading every resource policy. Run it continuously, treat every new external-access finding on a secret as an incident until proven intentional, and archive the intentional ones with a documented reason so the signal stays clean.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Compliance Mapping and Log Immutability</h4>\n<p style=\"line-height: 1.75\">Frameworks differ in wording, but auditors substantively ask for the same four things about secrets.
