Cross-account rotation additionally supplies a <code>RotationToken</code>. That is it — no connection details, no configuration. Everything else must come from the secret itself, from Lambda environment variables, or from tags on the secret.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">Secrets Manager rotation state machine (<i class=k>one</i> Lambda, four invocations)\n\n  RotateSecret <i class=o>/</i> scheduled <i class=k>trigger</i>\n        <i class=o>|</i>\n        v\n  [<i class=n>1</i>] Step<i class=o>=</i>&quot;createSecret&quot;   <i class=o>-</i><i class=o>&gt;</i> <i class=k>new</i> <i class=k>value</i> <i class=k>exists</i> <i class=k>as</i> version <i class=o>&lt;</i>token<i class=o>&gt;</i> labelled AWSPENDING\n        <i class=o>|</i>                        (secret now has AWSCURRENT <i class=o>+</i> AWSPENDING)\n        v\n  [<i class=n>2</i>] Step<i class=o>=</i>&quot;setSecret&quot;      <i class=o>-</i><i class=o>&gt;</i> target <i class=k>system</i> now accepts the pending credential\n        <i class=o>|</i>\n        v\n  [<i class=n>3</i>] Step<i class=o>=</i>&quot;testSecret&quot;     <i class=o>-</i><i class=o>&gt;</i> pending credential proven <i class=k>to</i> work <i class=k>with</i> <i class=t>real</i> privileges\n        <i class=o>|</i>\n        v\n  [<i class=n>4</i>] Step<i class=o>=</i>&quot;finishSecret&quot;   <i class=o>-</i><i class=o>&gt;</i> AWSCURRENT moves <i class=k>to</i> <i class=o>&lt;</i>token<i class=o>&gt;</i>; <i class=k>old</i> version auto<i class=o>-</i>labelled AWSPREVIOUS\n\n  Same <i class=k>function</i> ARN <i class=k>for</i> <i class=k>all</i> four. Secrets Manager retries a failed step, and asynchronous Lambda invocation itself can deliver duplicates, so <strong>every step must be safe to run twice</strong>. This is the single most important design constraint in the whole topic.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Step 1 — createSecret: Generate, but Only Once</h4>\n<p style=\"line-height: 1.75\">The job is to produce the new credential value and store it as the <code>AWSPENDING</code> version. The trap is that people write \"generate a password, put it\" with no check. If <code>setSecret</code> then fails and Secrets Manager retries from <code>createSecret</code>, a naive implementation generates a <em>second</em> password and overwrites the pending version — while the target system may already have been set to the first one. You now have a secret whose pending value does not match the target, and the rotation can never converge.</p>\n<p style=\"line-height: 1.75\">The correct implementation first calls <code>GetSecretValue</code> with <code>VersionId</code> set to the <code>ClientRequestToken</code> and <code>VersionStage</code> <code>AWSPENDING</code>. If that succeeds, a pending value already exists for this token — log it and return without doing anything. Only on <code>ResourceNotFoundException</code> do you generate. Generation should use <code>GetRandomPassword</code> rather than a hand-rolled RNG, and it must honor the target system's character rules via <code>ExcludeCharacters</code>, <code>ExcludePunctuation</code>, <code>PasswordLength</code> and <code>RequireEachIncludedType</code>. This matters more than it sounds: a MySQL password containing a quote character, or an Oracle password starting with a digit, produces a rotation that \"works\" in <code>createSecret</code> and blows up in <code>setSecret</code> with an opaque syntax error. Store the new value with <code>PutSecretValue</code>, passing <code>ClientRequestToken</code> as the version id and <code>VersionStages=['AWSPENDING']</code>. Preserve the rest of the JSON structure — username, host, port, engine, dbname — and change only the password field.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Step 2 — setSecret: The Only Step That Mutates the World</h4>\n<p style=\"line-height: 1.75\">This is where the external system actually changes, and therefore the only step whose failure leaves real damage. Two authentication approaches exist. The first is to connect with the <strong>current</strong> credential (the <code>AWSCURRENT</code> version) and change its own password — simple, no extra secret, but it means the credential must have permission to alter itself, and if the current credential is already broken you cannot bootstrap. The second, used by the AWS alternating-users templates, is to store a separate <strong>admin or superuser secret</strong> and reference it from the rotated secret's <code>masterarn</code> field; the function fetches the admin credential and uses it to manage the target user. This is more robust and is required for alternating-users, but it creates a high-privilege secret you must protect at least as carefully as the one you are rotating.</p>\n<p style=\"line-height: 1.75\">Idempotency here means: setting the password to the pending value when it is <em>already</em> the pending value must succeed, not error. For a database, <code>ALTER USER ... WITH PASSWORD</code> is naturally idempotent. For a vendor API where \"create key\" mints a new key each call, it is not — there you must first list existing keys and look for one you already created for this rotation (tag or name it with the <code>ClientRequestToken</code> prefix so you can recognise your own work), and only mint if absent. Also handle the ordering rule that many vendors impose: create the new key first, and do not revoke the old one in this step at all. Revocation, if the vendor requires it, belongs in <code>finishSecret</code> or in a separate cleanup — never before the new credential is proven.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Step 3 — testSecret: Test Privilege, Not Connectivity</h4>\n<p style=\"line-height: 1.75\">The failure mode this step exists to catch is a credential that authenticates but cannot do the application's work. If <code>setSecret</code> created a brand-new user and forgot a <code>GRANT</code>, a bare connect succeeds and rotation completes; the outage arrives the moment <code>AWSCURRENT</code> flips and every query returns permission denied. So <code>testSecret</code> must connect with the <strong>pending</strong> value and execute a real operation representative of production use — a <code>SELECT</code> against an application table, a read of the specific S3 prefix, a vendor API call on the endpoint your service actually uses. Throwing an exception here is the cheap failure: rotation stops, <code>AWSCURRENT</code> never moves, and clients keep using the old credential that still works. That is exactly the behaviour you want. Resist the temptation to catch and swallow errors in this step.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Step 4 — finishSecret: The Atomic Switch</h4>\n<p style=\"line-height: 1.75\">Finish is one API call: <code>UpdateSecretVersionStage</code> with <code>VersionStage='AWSCURRENT'</code>, <code>MoveToVersionId</code> set to the <code>ClientRequestToken</code>, and <code>RemoveFromVersionId</code> set to the version that currently holds <code>AWSCURRENT</code>. You find that current version id by calling <code>DescribeSecret</code> and scanning <code>VersionIdsToStages</code>. Supplying <code>RemoveFromVersionId</code> is what makes the move atomic — it is effectively a compare-and-swap, so a stale retry cannot clobber a newer state. Secrets Manager then applies <code>AWSPREVIOUS</code> to the demoted version automatically; you never set <code>AWSPREVIOUS</code> yourself. If <code>DescribeSecret</code> shows the token already carries <code>AWSCURRENT</code>, the step already ran: log and return successfully.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Guardrails at the Top of the Handler</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Rotation must be enabled.</strong> Call <code>DescribeSecret</code> and reject if <code>RotationEnabled</code> is not true. This stops a stray or spoofed invocation from mutating a production credential.</li>\n<li><strong>The token must be staged AWSPENDING.</strong> If <code>ClientRequestToken</code> is not a key in <code>VersionIdsToStages</code>, refuse. If it already holds <code>AWSCURRENT</code>, exit cleanly (a duplicate delivery after finish). If it holds neither <code>AWSCURRENT</code> nor <code>AWSPENDING</code>, refuse loudly.</li>\n<li><strong>Timeout sized to the target.</strong> Lambda default is 3 seconds and rotation work is not. Set the timeout above the worst-case target latency — a DNS lookup plus TLS handshake plus <code>ALTER USER</code> on a loaded database, or a slow vendor API. Rotation function timeouts must also stay under 20 minutes; the practical answer for most targets is 30 to 120 seconds with a connect timeout set inside the client so a hung socket fails fast rather than burning the whole budget.</li>\n<li><strong>Network placement.</strong> A private RDS instance means the function must be attached to the VPC, in subnets with a route to the database, with a security group the database's security group allows inbound on the engine port. The moment you attach a Lambda to a VPC it loses default internet egress, so it also needs an <strong>interface VPC endpoint for <code>com.amazonaws.&lt;region&gt;.secretsmanager</code></strong> (plus KMS if your CMK is not reachable) or a NAT gateway — otherwise the function hangs calling the Secrets Manager API and times out, which looks exactly like a database problem.</li>\n<li><strong>Execution role.</strong> <code>secretsmanager:DescribeSecret</code>, <code>GetSecretValue</code>, <code>PutSecretValue</code>, <code>UpdateSecretVersionStage</code> and <code>GetRandomPassword</code> (the last one cannot be resource-scoped), plus <code>kms:Decrypt</code> and <code>kms:GenerateDataKey</code> on the CMK if the secret uses a customer managed key, plus <code>ec2:CreateNetworkInterface</code>-style permissions via the VPC access managed policy. Separately, the function needs a <strong>resource policy</strong> allowing <code>secretsmanager.amazonaws.com</code> to invoke it, scoped with <code>SourceArn</code> to the secret.</li>\n<li><strong>Logging that leaks nothing.</strong> Log the step, the secret ARN, the token, elapsed time and the outcome. Never log the secret value, never log the parsed dict, never log a connection string, and never let an exception traceback carry the password — many database drivers put the DSN in the exception message, so catch and re-raise with a sanitised message.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Testing a Rotation Function Safely</h4>\n<p style=\"line-height: 1.75\">Never debug rotation against a production secret. Create a non-production copy — a throwaway secret pointing at a scratch database or the vendor's sandbox — attach the function, and drive it with <code>rotate-secret --rotate-immediately</code>. Watch the function's CloudWatch Logs; the AWS templates emit one log line per step, so you can see exactly which step failed and how far the state machine got. Between attempts, inspect <code>describe-secret</code> and confirm the staging labels look how you expect. Unit-test the four steps locally by invoking the handler with hand-built events against a local container of the target, and add a negative test where <code>testSecret</code> is given a credential without the required grant, asserting that it raises. A rotation function whose failure path has never been exercised is not a tested rotation function.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Production Scenario: Rotation Half-Completes</h4>\n<p style=\"line-height: 1.75\">A rotation for a self-managed Postgres cluster runs at 02:00. <code>createSecret</code> writes pending version <code>v-77</code>. <code>setSecret</code> connects and issues <code>ALTER USER app_user WITH PASSWORD</code>, the statement commits, and then the function times out waiting for the connection to close because a network ACL change is dropping the FIN. Secrets Manager records the step as failed and retries. Now consider what each design does.</p>\n<p style=\"line-height: 1.75\">A naive function regenerates the password in <code>createSecret</code> on retry — pending is now <code>P2</code>, the database has <code>P1</code>, and the state can only be fixed by hand. The correct function sees the existing <code>AWSPENDING</code> version for the same token, returns immediately, and <code>setSecret</code> re-issues <code>ALTER USER</code> with the same <code>P1</code> — a harmless no-op that converges. <code>testSecret</code> then proves <code>P1</code> works, and <code>finishSecret</code> flips <code>AWSCURRENT</code>. The whole incident becomes a delayed rotation instead of an outage. Note what the design buys you at every intermediate moment: until <code>finishSecret</code> runs, <code>AWSCURRENT</code> still points at the old version, so <strong>applications are reading a password the database no longer accepts</strong> — this is the single-user rotation risk window, and it is why the retry must converge fast and why alerting on rotation failure matters. The recovery rule is to <strong>verify the target system's state, not the secret's state</strong>: the secret says nothing about whether <code>ALTER USER</code> committed. Connect manually with the pending value; if it works, let rotation retry finish the job.
