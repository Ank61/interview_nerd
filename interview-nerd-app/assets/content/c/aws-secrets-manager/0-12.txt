Parameter Store can act as a front door to Secrets Manager. If you call GetParameter with a name of the form <code>/aws/reference/secretsmanager/my-secret-name</code>, Systems Manager retrieves the value from Secrets Manager on your behalf and returns it.</p>\n<p style=\"line-height: 1.75\">The practical use is uniformity: tools and services that only know how to read Parameter Store — some EC2 bootstrapping flows, older automation, anything that already standardized on the SSM API — can consume real Secrets Manager secrets, rotation and all, without being rewritten. Permissions still apply on both sides: the caller needs <code>secretsmanager:GetSecretValue</code> on the underlying secret.</p>\n<p style=\"line-height: 1.75\">Which leads to the split most mature teams actually run: <strong>configuration in Parameter Store, credentials in Secrets Manager.</strong> The database host, port, feature flags and timeouts are free Standard parameters; the password is a rotating Secrets Manager secret. This is the answer to give when an interviewer asks \"which one do you use?\" — the honest answer is both, with a clear rule for which goes where.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Briefly: the other options</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>HashiCorp Vault.</strong> A mature, cloud-agnostic secrets platform with capabilities AWS does not match — dynamic secrets generated per-request with a short lease, a full PKI engine, encryption-as-a-service, and fine-grained templated policies. The trade-off is that you run and secure it yourself (or pay for HCP Vault), and you take on its availability, its unseal procedure, and its upgrades. Choose it for genuinely multi-cloud or on-premises estates, or when you need dynamic short-lived credentials. For an AWS-only shop, Secrets Manager is far less operational burden.</li>\n<li><strong>Plain environment variables.</strong> The baseline everyone starts with, and weaker than it looks. In an ECS task definition's <code>environment</code> block the value is stored <strong>in plaintext in the task definition</strong>, visible to anyone with <code>ecs:DescribeTaskDefinition</code>, retained in every revision forever, and echoed into CloudTrail and Infrastructure-as-Code repositories. There is no audit of who read it, no rotation, and no per-secret access control — access to the task definition is access to the credential. The same applies to Lambda environment variables, readable with <code>lambda:GetFunctionConfiguration</code>. Environment variables are fine for non-sensitive configuration; the secure alternative is the <code>secrets</code> block with a <code>valueFrom</code> ARN, or SDK retrieval in the application.</li>\n<li><strong>Encrypted files in Git</strong> (SOPS, git-crypt, sealed secrets). Workable and popular, but the ciphertext is distributed to everyone who clones the repo, so rotation means a new commit and a redeploy, and revoking a person's access does not un-distribute what they already have.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Best practices — the consolidated checklist</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Never commit secrets to source control.</strong> Enforce it mechanically, not by policy: pre-commit hooks (git-secrets, gitleaks, detect-secrets), GitHub push protection, and Amazon CodeGuru Security or similar in CI.</li>\n<li><strong>If you already committed one: rotate it immediately.</strong> This is the point people get wrong. Deleting the commit is <em>not enough</em>. The value exists in every clone, in every fork, in the reflog, in CI caches, in any mirror, and in whatever scraper found it — public GitHub secrets are harvested within minutes. Git history rewriting is cleanup, not remediation. The order is: rotate the credential first so the leaked value is worthless, then revoke sessions issued with it, then check logs for use during the exposure window, then clean history.</li>\n<li><strong>One secret per application per environment, with a naming convention.</strong> A path-style scheme like <code>environment/service/purpose</code> — <code>prod/orders-api/db-credentials</code> — makes IAM wildcards natural (<code>prod/orders-api/*</code>), makes the console navigable, and makes ownership obvious. Never share one secret across environments: that couples staging's blast radius to production's.</li>\n<li><strong>Least-privilege IAM, scoped to specific secret ARNs.</strong> Never <code>\"Resource\": \"*\"</code> on <code>secretsmanager:GetSecretValue</code>. Scope to the exact ARN or a prefix wildcard, remembering that Secrets Manager appends six random characters so the ARN pattern needs a trailing <code>-*</code>. Add <code>kms:Decrypt</code> scoped to the key with a <code>kms:ViaService</code> condition. Consider an explicit <strong>Deny</strong> for human roles on production credentials so the \"no human sees it\" property is enforced rather than assumed.</li>\n<li><strong>Enable rotation wherever the target supports it.</strong> Managed rotation for RDS, Aurora, Redshift and DocumentDB is close to free to turn on. Use the <strong>alternating users</strong> strategy for zero-downtime rotation on production databases, and always monitor for rotation failure — a broken rotation is invisible until it is a finding.</li>\n<li><strong>Cache in the application, and handle rotation with retry-on-auth-failure.</strong> Fetch at startup or module scope, keep the value for minutes not milliseconds, and on an authentication error invalidate the cache, re-fetch, and retry once. This single pattern gives you low latency, low cost, and rotation-tolerance simultaneously. Use the AWS secrets caching libraries or the Parameters and Secrets Lambda Extension rather than writing it yourself.</li>\n<li><strong>Use IAM roles, never static access keys.</strong> An IAM role delivers temporary, automatically-rotated credentials — via the EC2 instance profile, the ECS task role, the Lambda execution role, or IRSA on EKS. A long-lived access key pair stored to reach a secrets manager is a secret protecting a secret, and it is the one that leaks.</li>\n<li><strong>Audit with CloudTrail and alert on deletions.</strong> Plus resource policy changes, unexpected principals, and retrieval-volume anomalies. Retain beyond CloudTrail's free 90 days with a trail to S3 if you need longer evidence.</li>\n<li><strong>Use VPC endpoints for private access.</strong> An interface VPC endpoint (AWS PrivateLink) for Secrets Manager keeps retrieval traffic on the AWS network, lets private subnets fetch secrets without a NAT gateway, and — via an endpoint policy — lets you restrict which secrets can be read from that VPC at all.</li>\n<li><strong>Tag for ownership and cost.</strong> Tags like <code>team</code>, <code>service</code>, <code>environment</code> and <code>data-classification</code> become cost-allocation dimensions in Cost Explorer, drive attribute-based access control, and answer \"whose is this?\" during cleanup.</li>\n<li><strong>Clean up unused secrets.</strong> Sweep <strong>LastAccessedDate</strong> periodically, confirm ownership by tag, and delete with a recovery window. Every orphaned live credential is a standing risk, not just a line item.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"Parameter Store isn't secure.\"</strong> A SecureString is KMS-encrypted at rest with the same cryptography Secrets Manager uses. The real differences are rotation, resource policies, replication and size — not encryption strength.</li>\n<li><strong>\"Secrets Manager is always the right answer.\"</strong> For thousands of non-rotating configuration values, free Standard parameters are correct and Secrets Manager would be expensive for no benefit.</li>\n<li><strong>\"Parameter Store is completely free.\"</strong> Standard tier storage is free at standard throughput; the advanced tier, higher throughput, and per-API-call charges beyond the free tier are not.</li>\n<li><strong>\"Deleting the commit fixes a leaked secret.\"</strong> It does not.
