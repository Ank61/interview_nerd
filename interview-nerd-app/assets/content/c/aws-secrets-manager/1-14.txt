{"title":"Incident Response — Handling a Leaked or Compromised Secret","tags":["aws","secrets manager","incident response","security"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">This is the single most common senior interview scenario for Secrets Manager, and it is asked because it separates people who have read documentation from people who have been paged at 2am. The prompt is usually one line — <em>\"a production database password just appeared in a public GitHub repository, what do you do?\"</em> — and the interviewer is listening for a runbook: an ordered set of decisions with explicit trade-offs, not a list of security nouns. The structure below is the runbook: detect, contain, scope, eradicate, recover, learn.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Detection Sources — How You Find Out</h4>\n<p style=\"line-height: 1.75\">Where the report comes from shapes your confidence, your urgency, and your first move. Say this explicitly; it demonstrates that you triage rather than react uniformly.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>A secret scanner fires on a repository.</strong> GitHub secret scanning, GitLab, or an internal scanner in CI. High confidence that a credential-shaped string exists; you still must verify it is live and current, because scanners fire on test fixtures and long-dead values constantly. The crucial sub-question is <em>public or private repository</em>. Public means assume compromised, full stop — automated harvesters find public credentials within seconds to minutes. Private still means a large and untracked internal audience.</li>\n<li><strong>A vendor notification.</strong> Cloud providers and SaaS vendors run their own scanners against public code hosts and paste sites. AWS itself will notify an account and may apply a quarantine policy when it detects exposed AWS keys. A vendor notification is high confidence and implies the value was <em>publicly reachable</em>, which removes any debate about urgency.</li>\n<li><strong>Anomalous CloudTrail or GuardDuty activity.</strong> This is the worst case, because it means the credential is not merely exposed but <strong>actively being used</strong>. A GuardDuty finding for instance credentials used outside AWS, an unexpected principal reading a production secret, or a retrieval volume spike from a single session all put you past \"exposed\" and into \"in progress.\"</li>\n<li><strong>A security researcher or bug bounty report.</strong> Often accurate and often accompanied by proof. Treat it as credible immediately; the reputational and disclosure-timeline pressure is real, and arguing about validity while the clock runs is the wrong instinct.</li>\n<li><strong>Internal discovery.</strong> An engineer notices a credential in a Slack message, a Confluence page, a log file, a CI build log, or a container image layer. Lower urgency than a public leak, but the audience is still wider than intended and the value must be treated as compromised.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The First Decision: Rotate Now, or Assess First?</h4>\n<p style=\"line-height: 1.75\">Everything hinges on this, and the interviewer wants a <em>position</em> with reasoning, not a shrug. <strong>The default for a production credential is rotate immediately.</strong> The reason is asymmetric cost: if you rotate and the leak turns out to be stale, you have spent a rotation and possibly a brief blip. If you assess for forty minutes and the credential was live and public, an attacker has had forty minutes of authenticated access to production data. Exposure time is the only variable you fully control, and it starts running the moment you learn.</p>\n<p style=\"line-height: 1.75\">But \"rotate immediately\" is only a safe default if you know the answers to three questions <em>in advance</em> — and knowing them in advance is precisely what a runbook is for:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Is alternating-users rotation configured?</strong> With the alternating-users strategy the previous credential stays valid while the new one is created, so clients holding a cached value keep working until their TTL expires. With single-user rotation the password changes in place, and every client still holding the old value fails <em>immediately</em>. Rotating a single-user secret on a large fleet mid-incident can convert a security event into a full outage — which is how incidents become two incidents.</li>\n<li><strong>Do clients retry and refresh on authentication failure?</strong> If clients invalidate their cache on an auth error and refetch, rotation is nearly transparent. If they cache for an hour with no refresh path, you have chosen an outage window equal to the TTL, and you should plan a rolling restart to accompany the rotation.</li>\n<li><strong>Do you know every consumer?</strong> A rotation breaks any consumer you did not know about. This is where a shadow consumer — a cron job, a reporting tool, a partner integration, a laptop — surfaces painfully.</li>\n</ul>\n<p style=\"line-height: 1.75\">The honest senior answer is therefore: <strong>rotate immediately by default, and let the pre-existing runbook tell you whether rotation is safe or whether you must take a revocation path instead.</strong> If you genuinely cannot answer those three questions, the correct move is not to delay — it is to <em>contain by another route</em> while you find out, which is the next section. Delay is never the containment strategy.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Revocation Paths When Rotation Is Slow or Impossible</h4>\n<p style=\"line-height: 1.75\">You have four independent levers, at different layers, with very different blast radii and speeds. Candidates who lead with \"disable the KMS key\" for a leaked database password have solved the wrong problem impressively.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Scoping the Blast Radius</h4>\n<p style=\"line-height: 1.75\">Containment buys you time; scoping tells you how much trouble you are in and what else must be rotated. Three questions, answered with evidence:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Who consumes this secret?</strong> Do not rely on documentation or memory. Query CloudTrail for every distinct principal that called <code>GetSecretValue</code> on this secret over a long window — 90 days catches monthly and quarterly jobs that a 7-day window misses entirely. Cross-check with <code>DescribeSecret</code>, whose <code>LastAccessedDate</code> gives a coarse but useful signal. This list <em>is</em> your rotation impact assessment, and building it takes minutes.</li>\n<li><strong>How long was the value exposed?</strong> Not when you found out — when it became reachable. For a Git leak that is the <strong>commit timestamp</strong>, which may be far earlier than the push, and earlier still than the repository being made public. For a log leak, when the log line was first written and who could read the log group. This window is what the forensic search must cover, and it is what determines whether this is a notifiable event.</li>\n<li><strong>What could the credential reach?</strong> Enumerate the actual authorisation, not the intent. For a database user: which schemas, which tables, read or write, and does it have permission to create users or read other credentials? For an API key: which vendor endpoints, can it move money, can it read customer PII, can it mint further keys? <strong>Assume lateral movement</strong> — if the exposed credential could read other secrets, or the compromised host held other credentials, those must be rotated as well. Scope expansion is the norm, not the exception.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Forensics — Was It Used?</h4>\n<p style=\"line-height: 1.75\">\"Exposed\" and \"exploited\" are different incidents with different disclosure obligations. Establish which one you have, using two independent evidence streams, and <strong>preserve evidence before you change anything you do not have to change</strong>.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>The Secrets Manager side.</strong> CloudTrail for <code>GetSecretValue</code> on this secret across the exposure window: which principals, which source IPs, which user agents, and whether any fall outside your known egress and known SDK fingerprints. This tells you whether the <em>secret</em> was harvested from AWS.</li>\n<li><strong>The target system side — the one people forget.</strong> The leaked value is a database password or a vendor API key; the authoritative record of its use is in <strong>that system's logs</strong>, not in CloudTrail. Pull database authentication logs for that user, the vendor's API access logs for that key, VPC Flow Logs for connections to the database from unexpected addresses, and RDS or Aurora audit logs where enabled. An attacker using a leaked database password never touches Secrets Manager at all, so a CloudTrail-only investigation will conclude \"no evidence of use\" while the breach is happening.</li>\n<li><strong>Preserve evidence.</strong> Snapshot the relevant logs to immutable storage in the log-archive account before retention expires; capture the repository state, commit hash, author and timestamps; record the exact secret version identifier involved; and keep a timestamped incident log of every action taken and by whom. If this becomes a legal or regulatory matter, the contemporaneous record is what you will be judged on. Notably, <strong>do not force-delete the secret</strong> — that destroys version history that is evidence.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Deleting the Commit Does Not Remediate the Leak</h4>\n<p style=\"line-height: 1.75\">This is the point most worth stating emphatically, because it is where less experienced responders genuinely stop. Once a value has been committed and pushed, it must be treated as <strong>permanently compromised</strong>, and the only remediation is invalidating the value. Removing it from the repository is hygiene, not containment. The reasons are concrete:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Git history is append-only.</strong> A later commit that deletes the line leaves the earlier commit object intact. Anyone who clones gets the whole history.</li>\n<li><strong>Clones and forks are already out of your control.</strong> Every developer laptop, every CI cache, every fork holds a copy. History rewriting with <code>git filter-repo</code> or BFG changes <em>your</em> repository; it cannot reach into theirs.</li>\n<li><strong>Automated scrapers index public repositories continuously.</strong> For a public leak, assume harvesting happened within seconds to minutes. Credential-stuffing infrastructure is fully automated and does not sleep.</li>\n<li><strong>Platform caches persist.</strong> Deleted commits can remain reachable through the code host's own caches, pull-request views and event APIs for some time after deletion, and third-party mirrors have their own retention.</li>\n<li><strong>The corollary for rotation.</strong> Because you can never prove the value was not copied, \"we made the repo private\" and \"we rewrote history\" are never sufficient. They are worth doing to stop <em>further</em> spread — and they are worth doing <em>after</em> you have rotated, not instead of it.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Worked Scenario: Production Database Password in a Public Repository</h4>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">T<i class=o>+</i><i class=n>00</i>:<i class=n>00</i>  GitHub secret scanning alerts: a production Aurora password\n         appears <i class=k>in</i> a PUBLIC repo. <i class=k>Commit</i> <i class=t>timestamp</i> <i class=k>is</i> <i class=n>6</i> DAYS OLD.\n         <i class=o>=</i><i class=o>&gt;</i> Public <i class=o>+</i> <i class=n>6</i> days <i class=o>=</i><i class=o>&gt;</i> assume compromised. <i class=k>No</i> debate.\n         <i class=k>Declare</i> an incident, <i class=k>open</i> a channel, <i class=k>start</i> a timestamped log,\n         assign an incident commander separate <i class=k>from</i> the responders.\n\nT<i class=o>+</i><i class=n>00</i>:<i class=n>03</i>  CONTAIN. <i class=k>Check</i> the runbook: <i class=k>is</i> alternating<i class=o>-</i>users rotation\n         configured <i class=k>on</i> prod<i class=o>/</i>orders<i class=o>/</i>aurora?
