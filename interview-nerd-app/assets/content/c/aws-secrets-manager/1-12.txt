{"title":"Performance, Quotas, Throttling, and Caching Architecture","tags":["aws","secrets manager","performance","caching"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">The moment you move credentials out of a config file and into Secrets Manager, you have added a <strong>network dependency to your application's request path</strong>. That is a genuinely good trade — but it is a trade, and senior interviews probe whether you understand what you signed up for. A config file has no rate limit, no throttling, and no cross-service failure mode. An API call has all three. The engineering job is to keep Secrets Manager on the <em>startup</em> path and off the <em>request</em> path, and to make the startup path resilient to the one failure mode that reliably takes down fleets: the stampede.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Secrets Manager as a Request-Path Dependency</h4>\n<p style=\"line-height: 1.75\">Classify the dependency honestly. If your code calls <code>GetSecretValue</code> once per process at boot and caches the result, Secrets Manager is a <strong>startup-time dependency</strong>: an outage or throttle prevents new capacity from coming online but leaves running capacity healthy. If your code calls it per request, per database connection, or inside a retry loop, it is a <strong>runtime dependency</strong>: every Secrets Manager hiccup is now your hiccup, your p99 inherits its latency, and your availability is the product of yours and theirs.</p>\n<p style=\"line-height: 1.75\">The second classification is almost always an accident rather than a design. It happens when a connection-pool factory fetches credentials on every new connection, when a Lambda handler fetches inside the handler body instead of at module scope, or when a framework's \"config provider\" is wired to resolve lazily on every lookup. Reviewing for this is a five-minute exercise with an enormous payoff, and it is the single highest-value thing to say in an interview on this topic.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Availability multiplies.</strong> A runtime dependency means your service cannot be more available than the dependency times your own reliability. A startup dependency means a Secrets Manager blip costs you elasticity, not traffic.</li>\n<li><strong>Latency adds.</strong> An uncached retrieval is an HTTPS round trip plus a KMS decrypt — realistically tens of milliseconds. A cache hit is an in-memory map lookup, microseconds. Putting the former in a hot loop is a self-inflicted latency regression that no amount of database tuning will explain.</li>\n<li><strong>Cost tracks call volume.</strong> Secrets Manager charges per 10,000 API calls. Per-request retrieval on a service doing a few thousand requests per second turns a rounding-error line item into a visible one, and the KMS request charges ride alongside it.</li>\n<li><strong>Quota consumption is shared.</strong> The rate quota is per account and Region, not per application. A badly behaved service burns the budget that every other service in the account depends on. This is why the noisy-neighbour conversation is an <em>organisational</em> one, not just a code-review one.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Quota Model: What Is Actually Limited</h4>\n<p style=\"line-height: 1.75\">Secrets Manager enforces <strong>request-rate quotas per AWS account per Region</strong>, defined separately for each API operation. <code>GetSecretValue</code> carries by far the highest allowance because it is the read path; the mutating operations (<code>CreateSecret</code>, <code>PutSecretValue</code>, <code>UpdateSecret</code>, <code>RotateSecret</code>, <code>DescribeSecret</code>, <code>ListSecrets</code>) carry substantially lower ones. There are also resource quotas — a maximum number of secrets per account and a maximum secret value size. The exact figures are published in the Secrets Manager quotas page and differ between operations; the important interview points are the <em>shape</em> of the model, not a memorised number:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Per-operation, per-account, per-Region.</strong> Every principal and every application in the account shares one budget. Two accounts, or two Regions, are independent budgets — which is itself an isolation strategy.</li>\n<li><strong>Read quota is generous; write quota is not.</strong> The read path is designed for fleets. The management operations are not, which is why control-plane tooling that lists and describes thousands of secrets in a tight loop throttles long before an application reading one secret per host would.</li>\n<li><strong>Most are adjustable.</strong> They appear in the <strong>Service Quotas</strong> console under the Secrets Manager service, and adjustable ones can be raised by request. Treat a quota increase as a capacity-planning action with lead time, not an emergency lever — approvals are not instantaneous.</li>\n<li><strong>Quotas are not the only limiter.</strong> KMS has its own independent request-rate quota, discussed below, and it is frequently the one you hit first on decrypt-heavy patterns.</li>\n</ul>\n<p style=\"line-height: 1.75\">Because the figures change and vary, the defensible senior answer is: \"the rate limits are documented per operation in the Secrets Manager quotas page, they are per account per Region, most are adjustable through Service Quotas, and I design so that steady-state consumption sits well under whatever the current value is — typically by caching so that call volume scales with <em>host count and TTL</em>, not with request rate.\"</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What Throttling Looks Like to a Caller</h4>\n<p style=\"line-height: 1.75\">When you exceed the rate quota, Secrets Manager returns <strong>ThrottlingException</strong> — an HTTP 400-class error with a retryable error code. The AWS SDKs classify it as retryable and, in their default <em>standard</em> retry mode, will retry it automatically with <strong>exponential backoff and jitter</strong>, up to a small maximum number of attempts (three total attempts by default in current SDKs). The SDKs also support an <em>adaptive</em> retry mode that adds client-side rate limiting, slowing the caller when it observes throttling.</p>\n<p style=\"line-height: 1.75\">Two things routinely defeat this protection, and naming them is the mark of someone who has actually operated this:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>The default attempt count is small.</strong> Three attempts over a few hundred milliseconds is designed for transient blips, not for a sustained, self-inflicted overload lasting a minute. Once every caller exhausts its attempts simultaneously, they all fail simultaneously.</li>\n<li><strong>Jitter does not help when the population is synchronised and the load is self-generated.</strong> Backoff spreads retries within a client, but if five hundred tasks all started within the same two seconds, the aggregate arrival rate is still far above quota, and the retries themselves become the sustaining load. This is congestion collapse, and it is exactly the startup stampede.</li>\n<li><strong>Code that catches and re-fetches defeats it entirely.</strong> An application-level <code>try/catch</code> that loops on failure sits <em>outside</em> the SDK's backoff and turns a well-behaved client into an unbounded one. If you write retry logic around an SDK call, you must implement backoff and a cap yourself, or simply let the SDK do it and configure <code>max_attempts</code> upward.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Startup Stampede</h4>\n<p style=\"line-height: 1.75\">This is the canonical Secrets Manager outage, and it is worth being able to draw. The preconditions are ordinary: every task fetches its secret synchronously at startup, before it reports healthy, with no cache and no jitter. The trigger is also ordinary: a scale-out event, a rolling deploy, an Availability Zone recovery, or a crash-loop restart. Suddenly the arrival rate at <code>GetSecretValue</code> is not \"steady-state fleet size divided by TTL\" — it is \"entire fleet, all at once.\"</p>\n<div class=\"code\"><div that sustains the overload. The fleet cannot converge because every attempt to converge generates more load. This is why the incident does not self-heal and why simply waiting is not a strategy.</p>\n<p style=\"line-height: 1.75\">The mitigations, in the order you should reach for them:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Cache, so the steady state is not fetch-per-process.</strong> The single biggest lever. With a TTL-based cache, fleet-wide call rate becomes roughly <em>number of cache instances divided by TTL</em>. Four hundred hosts with a one-hour TTL is about one call every nine seconds — nowhere near any limit.</li>\n<li><strong>Fetch once per host, not once per process.</strong> If a host runs eight worker processes, a per-process fetch multiplies load by eight for no benefit. A sidecar, a node-level agent, or a shared init container collapses that back to one.</li>\n<li><strong>Jitter the startup fetch.</strong> A random delay of up to a few seconds before the first retrieval flattens the arrival spike dramatically at essentially zero cost. It is three lines of code and it is the cheapest insurance in this entire topic.</li>\n<li><strong>Raise SDK retry attempts and use adaptive mode for startup clients.</strong> A startup path can afford to spend thirty seconds retrying politely; a request path cannot. Configure them differently.</li>\n<li><strong>Decouple health from secret availability where you safely can.</strong> If a task can start, report healthy, and fetch its secret lazily before first use with a bounded retry, the orchestrator stops killing it and the loop breaks. This is not always appropriate — a task that cannot serve without the secret should not claim to be healthy — but a distinction between <em>liveness</em> and <em>readiness</em> often lets you keep the container alive while it retries.</li>\n<li><strong>Inject at deploy time for truly static cases.</strong> ECS task definitions and EKS with the Secrets Store CSI Driver can resolve a secret into the environment or a mounted file at task start, handled by the platform rather than your code. This does not eliminate the API call, but it moves it into a system with its own retry behaviour and removes per-process duplication.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Caching Architecture: The Four Real Options</h4>\n<div style=\"overflow-x: auto; You attach it as a layer; it starts a small local HTTP server inside the execution environment, and your function retrieves a secret with an ordinary HTTP GET to <code>http://localhost:2773/secretsmanager/get?secretId=NAME</code>, passing the function's session token in a request header. Its behaviour is tuned with environment variables covering the listening port, whether caching is enabled, the cache size, the secrets TTL in seconds, and log level. The default TTL is a small number of minutes, which you should raise deliberately rather than leave at the default. Crucially, the cache lives in the <em>execution environment</em>, so a function scaling from 10 to 1,000 concurrent executions creates roughly 990 cold caches and 990 API calls in a short window — the extension reduces steady-state load beautifully but does not eliminate burst load.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">TTL Versus Rotation Interval Versus Cost</h4>\n<p style=\"line-height: 1.75\">Cache TTL is the dial that trades three things against each other: <strong>API call volume and cost</strong>, <strong>how long a stale credential can be served after rotation</strong>, and <strong>how quickly an emergency rotation propagates</strong>. Longer TTL means fewer calls, lower cost, more stampede protection — and a longer window during which clients hold a value that has just been rotated away.</p>\n<p style=\"line-height: 1.75\">The correct way to resolve that tension is not to shorten TTL until it feels safe. It is to make staleness <em>harmless</em>, which is exactly what the <strong>alternating-users rotation strategy</strong> does: the previous credential remains valid while the new one is created, so a client holding a stale value keeps working until its TTL expires. Combine that with a <strong>refresh-on-authentication-failure</strong> path — on an auth error, invalidate the cache entry, fetch once, retry once, and only then fail — and you get the best of both: long TTL in the normal case, immediate correction in the exceptional one. Without that fallback path, TTL becomes a guaranteed outage window on every rotation, and teams respond by shortening it, which is how they end up back at high call volume.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>TTL must be shorter than the rotation interval</strong> — dramatically so — or clients may never observe a rotation at all.</li>\n<li><strong>TTL should be long enough that steady-state call rate is trivial.</strong> Compute it: fleet size divided by TTL is your average calls per second. If that number is not comfortably small, the TTL is wrong.</li>\n<li><strong>Emergency rotation needs a faster path than TTL expiry.</strong> Either accept the TTL as your worst-case propagation delay and size it accordingly, or build an explicit invalidation signal — an EventBridge rule on the rotation event driving a fleet-wide cache flush, or simply a rolling restart, which is often the pragmatic answer.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">KMS: The Second, Independent Throttle</h4>\n<p style=\"line-height: 1.75\">Every retrieval of an encrypted secret involves a <strong>KMS decrypt operation</strong>, and KMS enforces its own request-rate quota on cryptographic operations, shared across all KMS usage in the account and Region and varying by Region. This is a genuinely separate limit: you can be comfortably inside your Secrets Manager quota and still see failures because something else in the account — S3 with SSE-KMS on a large object workload, EBS volume attachments, a DynamoDB table with a customer managed key, an Athena scan over encrypted data — is consuming the shared KMS budget.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>The symptom differs.</strong> You may see a KMS throttling error surfaced through the Secrets Manager call rather than a Secrets Manager ThrottlingException. Read the error body, not just the status code — this is the detail that separates a five-minute diagnosis from a two-hour one.</li>\n<li><strong>Blast-radius separation has a performance dimension.</strong> Using a dedicated customer managed key for secrets, rather than sharing one key across many services, does not raise the account-level KMS quota, but it does make attribution possible in CloudTrail and lets you reason about which workload is consuming what.</li>\n<li><strong>Caching fixes this too.</strong> Every cache hit is a KMS call that never happens. The same lever solves both limits, which is why caching is the answer to roughly every question in this topic.</li>\n<li><strong>The quota is documented per Region and is adjustable.</strong> As with Secrets Manager, treat the number as something to look up and raise ahead of a known launch, not memorise.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Latency Characteristics and Capacity Planning</h4>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">LATENCY BUDGET (orders <i class=k>of</i> magnitude, <i class=k>not</i> guarantees)\n\n  <i class=k>in</i><i class=o>-</i>process cache hit         <i class=o>~</i> microseconds       (a hash map lookup)\n  sidecar <i class=o>/</i> extension hit      <i class=o>~</i> sub<i class=o>-</i>millisecond    (loopback HTTP)\n  GetSecretValue <i class=o>+</i> KMS decrypt <i class=o>~</i> tens <i class=k>of</i> ms         (TLS round trip <i class=o>+</i> crypto)\n  same <i class=k>call</i>, throttled<i class=o>+</i>retried <i class=o>~</i> hundreds <i class=k>of</i> ms     (backoff before success)\n  same <i class=k>call</i>, cold TLS handshake  <i class=k>add</i> more           (<i class=k>new</i> connection setup)\n\n  <i class=o>=</i><i class=o>&gt;</i> a <i class=k>per</i><i class=o>-</i>request <i class=k>fetch</i> adds tens <i class=k>of</i> ms <i class=k>to</i> <i class=k>EVERY</i> request<i class=s>&#x27;s p50\n  =&gt; and adds hundreds of ms to p99 whenever the account is near quota</i></code></pre></div>\n<p style=\"line-height: 1.75\">For capacity planning on a large fleet, do the arithmetic explicitly rather than hoping. Alarm on any sustained non-zero value. This is authoritative — it is the service's own record — but it is delayed by CloudTrail's delivery latency, so it is a detection mechanism, not a real-time control.</li>\n<li><strong>Client-side SDK metrics.</strong> Emit your own counters for retrieval attempts, retries, throttles, cache hits and cache misses, and the latency of the fetch. A rising <strong>cache miss rate</strong> is the earliest and most actionable signal you will get — it precedes throttling rather than following it, and it immediately localises the problem to a specific service.</li>\n<li><strong>Service Quotas utilisation.</strong> Track consumption against the quota for the operations you care about so you can see the trend before it becomes an incident, and so a quota-increase request can be filed with lead time rather than during an outage.</li>\n</ul>\n<p style=\"line-height: 1.75\">The alarm that matters most is not \"throttling is happening\" — by then you are already in the incident. It is \"<strong>calls per host per hour has increased</strong>\", which catches a deployment that accidentally removed caching on the day it ships rather than on the day of the next scale-out event.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Production Scenario: The Outage That Starts During Scale-Out</h4>\n<p style=\"line-height: 1.75\">A checkout service on ECS Fargate runs 120 tasks at baseline.
