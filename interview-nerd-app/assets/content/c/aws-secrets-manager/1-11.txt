{"title":"Multi-Region Architecture, Replication Internals, and DR Runbooks","tags":["multi-region","disaster-recovery","replication","resilience"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Secrets Manager is a <strong>Regional service</strong>. A secret created in us-east-1 does not exist in eu-west-1, and an application in eu-west-1 calling <code>GetSecretValue</code> against the us-east-1 endpoint has just made its availability a function of another Region's health and added cross-Region latency to every cold start. Multi-Region secret architecture is about removing that dependency, and the interesting parts are the consistency semantics, what actually breaks during a Regional outage, and the operational runbook — not the API call, which is one flag.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Replication mechanics</h4>\n<p style=\"line-height: 1.75\">A replicated secret has one <strong>primary</strong> and one or more <strong>read-only replicas</strong>. The precise semantics:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Writes go only to the primary.</strong> <code>PutSecretValue</code>, <code>UpdateSecret</code>, <code>RotateSecret</code>, tag changes and policy changes are all primary-only operations. A replica rejects writes.</li>\n<li><strong>Every change propagates,</strong> including new versions created by rotation, staging label movements (so <code>AWSCURRENT</code> and <code>AWSPREVIOUS</code> track), metadata, tags, and the resource policy. Replication is continuous, not a one-time copy.</li>\n<li><strong>Each replica is encrypted with a key in its own Region.</strong> KMS keys are Regional, so the plaintext is decrypted in the primary and re-encrypted under the replica Region's key. You specify the replica's <code>KmsKeyId</code> per Region; if you omit it, the AWS managed key <code>aws/secretsmanager</code> in <em>that</em> Region is used. A replica <strong>cannot</strong> use another Region's AWS managed key, and if you use customer-managed keys you must create one per Region and grant the consuming principals <code>kms:Decrypt</code> on the local key — a forgotten replica-Region KMS grant is one of the most common failure modes, and it surfaces as an <code>AccessDeniedException</code> only in the failover Region, i.e. exactly when you can least afford to debug it.</li>\n<li><strong>The replica has its own ARN</strong> — same name, different Region and a different random suffix is not the case (the suffix is preserved), but the Region component differs, so any IAM policy or config that hardcodes a full ARN must account for both. Using the secret <em>name</em> with a Regional client is usually cleaner.</li>\n<li><strong>Replication is eventually consistent.</strong> There is a propagation window — normally sub-second to a few seconds, but not contractually bounded and observably longer during Regional stress.</li>\n</ul>\n<p style=\"line-height: 1.75\">That last point has a concrete application-level consequence. If a process writes a new value to the primary in us-east-1 and a process in eu-west-1 immediately reads the replica, it may get the <em>previous</em> value. Any workflow that writes-then-reads-elsewhere must not assume read-after-write across Regions. The correct designs are: poll the replica until the expected version appears; drive the cross-Region step off the <code>RotationSucceeded</code> / secret-version EventBridge event rather than a timer; or — the reason this is usually a non-issue in practice — use the <strong>multi-user rotation strategy</strong> so both the old and new credentials are valid simultaneously and the propagation window simply does not matter. Designing rotation so that staleness is survivable is strictly better than trying to make replication synchronous, which you cannot do.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What breaks in a Regional outage</h4>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">NORMAL                                <i class=k>PRIMARY</i> REGION IMPAIRED\n<i class=c>------                                -----------------------</i>\nus<i class=o>-</i>east<i class=n>-1</i> (<i class=k>primary</i>)                   us<i class=o>-</i>east<i class=n>-1</i>  X  unreachable\n  <i class=o>|</i>  writes, rotation                   <i class=o>|</i>  <i class=k>no</i> writes\n  <i class=o>|</i>  <i class=k>local</i> <i class=k>reads</i>                        <i class=o>|</i>  <i class=k>no</i> rotation\n  v                                     v\neu<i class=o>-</i>west<i class=n>-1</i> (replica)  <i class=o>&lt;</i><i class=c>-- replicate    eu-west-1 (replica)</i>\n  <i class=o>|</i>  <i class=k>local</i> <i class=k>reads</i> OK                     <i class=o>|</i>  <i class=k>local</i> <i class=k>reads</i> STILL OK\n  <i class=s>&#x27;-&gt; app reads locally                 &#x27;</i><i class=o>-</i><i class=o>&gt;</i> app <i class=k>reads</i> locally, unaffected\n                                        <i class=o>|</i>\n                                        <i class=s>&#x27;-&gt; but: value is FROZEN\n                                            rotation is HALTED\n                                            any write path is BROKEN</i></code></pre></div>\n<p style=\"line-height: 1.75\">The good news is the part people expect: <strong>replicas remain readable</strong>. An application in the surviving Region that only calls <code>GetSecretValue</code> against its local endpoint keeps working, which is exactly why you replicate rather than making cross-Region calls. The bad news is everything that writes: <strong>no new versions can be created, no rotation can run, and no new secrets can be created</strong> in the replicated set. The value is frozen at whatever it was when the primary became unreachable. For a short outage this is fine — a secret that does not change is not a problem. It becomes a problem if the outage is long enough that a scheduled rotation is missed (usually harmless, rotation just runs late), or if your incident response requires rotating a credential — for example, a compromise during a Regional outage, where you need to change a credential and cannot.</p>\n<p style=\"line-height: 1.75\">Be specific about what does <em>not</em> break so you do not over-engineer: existing applications reading the local replica, cached values in running processes, and the target systems themselves are all unaffected. Most services survive a primary-Region Secrets Manager outage without noticing, provided they were already reading locally.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Promotion: a one-way door</h4>\n<p style=\"line-height: 1.75\"><code>StopReplicationToReplica</code> — surfaced in the CLI as <code>aws secretsmanager stop-replication-to-replica</code>, run <strong>in the replica Region</strong> — severs the replication link and promotes the replica to a standalone, writable primary secret. Two things to internalise:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>It is not reversible.</strong> There is no \"demote\" API. After promotion you have two independent secrets with the same name in two Regions and no relationship between them. Re-establishing the original topology means choosing a survivor, calling <code>ReplicateSecretToRegions</code> from it, and deleting the other — and you cannot replicate into a Region that already holds a secret of that name, so the reconciliation involves a delete with a recovery window (or <code>--force-overwrite-replica-secret</code>), which is a real operational step, not a formality.</li>\n<li><strong>It is run from the replica side</strong> and therefore works when the primary Region is unreachable. That is the whole point — it is the break-glass action available during an outage.</li>\n</ul>\n<p style=\"line-height: 1.75\">So when do you promote? The decision hinges entirely on <strong>whether you need to write</strong>. If the surviving Region only needs to read, do not promote: reads already work, and promotion buys you nothing while costing you a painful reconciliation. Promote when you must create a new version — an active incident requiring credential rotation, a new service that must be deployed during the outage, or an outage long enough that you have lost confidence in a return within your rotation tolerance. In practice the answer is \"wait\" far more often than teams expect, and a runbook that says \"promote immediately on any Regional impairment\" causes more damage than the outage. State the decision criterion explicitly: <em>promote only if a write is required and the primary's recovery is not imminent.</em></p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Writing a DR runbook that is actually trustworthy</h4>\n<p style=\"line-height: 1.75\">A runbook that only lists commands is not a runbook. The parts that matter:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Detection criteria.</strong> Concrete signals, not \"the Region is down\": error rate on <code>GetSecretValue</code> in the primary Region, replication status via <code>DescribeSecret</code>'s <code>ReplicationStatus</code> field (which reports <code>InSync</code>, <code>InProgress</code> or <code>Failed</code> with a message), failed rotation CloudWatch alarms, and the AWS Health Dashboard. Alarm on replication status <em>continuously</em>, not just during incidents — a replica that silently went <code>Failed</code> six weeks ago because someone changed a KMS key policy is the real disaster.</li>\n<li><strong>A decision, with an owner.</strong> Name the role (incident commander, not a person) who decides to promote, the criteria they apply (the write-requirement test above), and the explicit authority to <em>not</em> promote. Ambiguous ownership is why promotion happens reflexively.</li>\n<li><strong>The promotion steps</strong>, verbatim and tested: run <code>stop-replication-to-replica</code> in the surviving Region, verify writability with a no-op tag change, confirm the KMS key in that Region permits the consuming roles to decrypt, and check the secret's resource policy came across correctly.</li>\n<li><strong>Repointing automation.</strong> Rotation schedules do <em>not</em> follow a promotion — the rotation Lambda lives in the old primary Region, and the new primary has no rotation configured. You must deploy or attach a rotation function in the new Region, which means the DR stack that contains it should already exist (deployed and dormant), because writing a rotation Lambda during an incident is not a plan. The same applies to the EventBridge rules, CloudWatch alarms, and any automation keyed to the old ARN.</li>\n<li><strong>Reconciliation afterwards.</strong> The original primary comes back holding a stale, divergent secret with the same name. Decide which survives, replicate from it, and delete the other — noting the deletion recovery window and the <code>--force-overwrite-replica-secret</code> flag. Write down who owns this, because it is the step teams skip, leaving two live secrets with the same name and no replication, which is worse than where they started.</li>\n<li><strong>Game days.</strong> A runbook nobody has executed is fiction. Test it quarterly in a non-production account by promoting a real replica, repointing a real consumer, and reconciling — and time it, because the measured duration is your actual RTO regardless of what the SLA document claims. Game days routinely surface the missing KMS grant, the hardcoded ARN, and the rotation Lambda that only exists in one Region.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Rotation in a multi-Region world</h4>\n<p style=\"line-height: 1.75\">Rotation runs against the <strong>primary</strong> and the new version replicates outward, which is the easy half. The hard half is the <em>target system</em>, and this is where senior candidates separate themselves. Rotation must target the global writer, which means the function lives in (or has connectivity to) the primary Region and its security group and subnet routing must be correct there. After a database failover to a secondary Region, the writer moves — and your rotation function's endpoint configuration must follow, which is another item for the runbook and another reason the cluster endpoint, not an instance endpoint, belongs in the secret.</p>\n<p style=\"line-height: 1.75\">And in every case, <strong>multi-user rotation is what makes multi-Region safe</strong>. With two alternating users, the previous credential remains valid after a rotation, so any application anywhere in the world that is still holding a cached or not-yet-propagated value continues to authenticate. Single-user rotation plus cross-Region propagation delay plus client-side caching is a recipe for a brief authentication storm on every rotation.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The alternative: rolling your own sync</h4>\n<p style=\"line-height: 1.75\">Teams sometimes build a Lambda triggered by EventBridge on secret-change events that copies values into another Region or account, usually because they want cross-<em>account</em> distribution (which native replication does not do — replication is cross-Region within one account) or because they want to transform the value. It works, and it is almost always worse: you now own <strong>code in the critical path of credential availability</strong>, a second IAM identity with read access to every secret it syncs, a divergence problem when the sync fails silently, no native <code>ReplicationStatus</code> to alarm on, decrypt-and-re-encrypt operations that materialise plaintext in your Lambda's memory and potentially its logs, and an ordering problem where rapid successive updates can land out of order. Use native replication for cross-Region. For cross-account, prefer a <strong>resource policy on the secret plus a role in the consuming account</strong> so the consumer reads the single source of truth directly — no copy, no drift, and CloudTrail attributes the read to the actual consumer. Copying a secret is duplicating a liability.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cost and hygiene</h4>\n<p style=\"line-height: 1.75\"><strong>Each replica is billed as a secret</strong> at the standard per-secret monthly rate, plus API call charges in the replica Region. A secret replicated to three Regions costs four times the base. That is trivial for fifty secrets and material for five thousand, so replicate deliberately: only secrets that a workload in another Region actually reads. Two housekeeping notes. First, <strong>you cannot delete a primary secret while replicas exist</strong> — you must call <code>remove-regions-from-replication</code> first, which is a frequent source of \"why won't this delete\" confusion in teardown scripts. Second, audit for <strong>orphaned replicas</strong>: Regions you exited, experiments nobody cleaned up, and secrets replicated by a since-deleted module. A scheduled job that reports every secret's <code>ReplicationStatus</code> and flags replicas in Regions with no running workload pays for itself.</p>\n<p style=\"line-height: 1.75\">One more consistency point that is easy to miss: <strong>the secret and the resource it authenticates to must fail over together</strong>. If your application fails over to eu-west-1 but the secret there contains a <code>host</code> field pointing at the us-east-1 database endpoint, the replicated secret is perfectly healthy and completely useless. Options: store only the credential in the secret and resolve the endpoint from Regional configuration or a Route 53 record that follows failover; use a global endpoint (an Aurora Global Database writer endpoint, a Global Accelerator address) that is valid from anywhere; or keep separate per-Region secrets when the targets are genuinely independent. Deciding which fields are global and which are Regional is the actual design work.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Production scenario: active-active in two Regions with a tight RTO</h4>\n<p style=\"line-height: 1.75\">A payments API runs active-active in us-east-1 and eu-west-1 behind latency-based Route 53, on Aurora Global Database with the writer in us-east-1, with an RTO of 15 minutes. Design:</p>\n<p style=\"line-height: 1.75\"><strong>Layout.</strong> Database credentials in one secret, primary us-east-1, replicated to eu-west-1, with a customer-managed KMS key in <em>each</em> Region and the task roles in each Region granted <code>kms:Decrypt</code> on their local key with a <code>kms:ViaService</code> condition. Every application calls <code>GetSecretValue</code> against its <strong>local Regional endpoint</strong> — via an interface VPC endpoint so the call never leaves the VPC — with a client-side cache (the AWS caching library, or the Lambda extension) with a TTL of a few minutes and a refetch-on-auth-failure path. The secret stores the credential plus the <strong>cluster writer endpoint</strong>, not an instance endpoint, so a database failover does not invalidate it. Region-specific values (a local read endpoint, a Regional queue URL) live in Regional SSM parameters, not in the replicated secret.</p>\n<p style=\"line-height: 1.75\"><strong>Rotation.</strong> Multi-user alternating strategy, 30 days, function in us-east-1 with VPC connectivity to the global writer — chosen specifically so that during the propagation window and cache TTL, both credentials authenticate and eu-west-1 never sees a failure. Rotation and database failover are both exercised on the same game day, because the interaction is where the bugs live.</p>\n<p style=\"line-height: 1.75\"><strong>Failover.</strong> Because both Regions already read locally, a us-east-1 Secrets Manager impairment requires <em>no action</em> — eu-west-1 keeps reading its replica, and the 15-minute RTO is met by doing nothing, which is the strongest possible answer. The runbook's promotion branch is reserved for the case where a write is required: an active credential compromise, or an impairment lasting long enough that a missed rotation matters. In that branch: <code>stop-replication-to-replica</code> in eu-west-1, attach the pre-deployed dormant rotation stack there, verify decrypt permissions, then reconcile when us-east-1 returns by choosing eu-west-1 as the survivor, force-overwriting the us-east-1 copy, and re-establishing replication.</p>\n<p style=\"line-height: 1.75\"><strong>Monitoring.</strong> A CloudWatch alarm on <code>ReplicationStatus != InSync</code> checked continuously, an alarm on rotation failure, an alarm on <code>GetSecretValue</code> error rate per Region, and a quarterly game day that measures actual promotion time.
