{"title":"Secrets in Kubernetes and EKS — CSI Driver, External Secrets Operator, and IRSA","tags":["kubernetes","eks","irsa","csi-driver"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Kubernetes ships with a <strong>Secret</strong> object, and the single most important fact about it is that it is not encrypted — it is <strong>base64-encoded</strong>, which is an encoding, not a cipher. By default the value sits in plaintext in etcd, it is readable by anyone who can <code>get secrets</code> in that namespace, it is readable by anyone who can read an etcd snapshot or a Velero backup, and it is never rotated. A Secret created on day one is still there, with the same value, two years later. Every serious EKS platform therefore treats the native Secret as at best a delivery mechanism and never as the system of record — the system of record is AWS Secrets Manager, and the interesting engineering question is how the value gets from Secrets Manager into a running pod.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">IRSA and EKS Pod Identity: the foundation</h4>\n<p style=\"line-height: 1.75\">Nothing else works until a pod can prove who it is to AWS without a static key. The naive answer — bake an access key into the container or into a Secret — recreates the exact problem you were trying to solve, one layer down. <strong>IAM Roles for Service Accounts (IRSA)</strong> solves it with OIDC federation. Every EKS cluster exposes an OIDC discovery endpoint; you register that endpoint as an <strong>IAM OIDC identity provider</strong> in the account, and then an IAM role's trust policy says \"I trust tokens from this cluster's issuer whose <code>sub</code> claim is <code>system:serviceaccount:my-namespace:my-sa</code>\". You annotate the Kubernetes ServiceAccount with <code>eks.amazonaws.com/role-arn</code>, and a mutating webhook injects a projected service account token plus the <code>AWS_ROLE_ARN</code> and <code>AWS_WEB_IDENTITY_TOKEN_FILE</code> environment variables into the pod. The AWS SDK's default credential chain picks those up and calls <code>AssumeRoleWithWebIdentity</code>, receiving temporary credentials that auto-refresh. No long-lived key exists anywhere.</p>\n<p style=\"line-height: 1.75\"><strong>EKS Pod Identity</strong> is the newer, simpler alternative. Instead of an OIDC provider per cluster, you install the Pod Identity Agent as a DaemonSet and create a <strong>pod identity association</strong> mapping (cluster, namespace, service account) to a role. The role's trust policy just trusts <code>pods.eks.amazonaws.com</code> — one trust policy shape, reusable across clusters, no per-cluster OIDC provider to create and no role trust policy edit when you add a cluster. The trade-offs: Pod Identity is EKS-only and does not work for cross-account role chaining in quite the same way IRSA did historically (it supports it via target role configuration), and IRSA works for self-managed Kubernetes and for EKS Anywhere because it only requires a reachable OIDC issuer. Interviewers like the follow-up \"which would you pick for a new cluster?\" — the honest answer is Pod Identity for greenfield EKS because the operational model is simpler, IRSA when you need portability or already have hundreds of roles wired to an OIDC issuer.</p>\n<p style=\"line-height: 1.75\">Either way, the granularity is the <strong>service account</strong>, which is the real security control: the IAM policy on that role should name specific secret ARNs and, if a customer-managed KMS key is used, grant <code>kms:Decrypt</code> scoped with a <code>kms:ViaService</code> condition. A role that grants <code>secretsmanager:GetSecretValue</code> on <code>*</code> makes every other control in this topic cosmetic.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Secrets Store CSI Driver with the AWS provider</h4>\n<p style=\"line-height: 1.75\">The <strong>Secrets Store CSI Driver</strong> is a CSI volume plugin: when a pod starts, the kubelet asks the driver to mount a volume, and the driver asks a provider to fetch the content. The <strong>AWS Secrets Manager and Config Provider (ASCP)</strong> is the provider that talks to Secrets Manager and Parameter Store, authenticating as the pod's service account via IRSA or Pod Identity. The value never becomes a Kubernetes API object — it is written into a <code>tmpfs</code> volume mounted into the container's filesystem.</p>\n<p style=\"line-height: 1.75\">The configuration object is a <strong>SecretProviderClass</strong>, a namespaced CRD. Its <code>spec.provider</code> is <code>aws</code> and its <code>spec.parameters.objects</code> is a YAML string listing each object to fetch: <code>objectName</code> (a secret name or full ARN), <code>objectType</code> (<code>secretsmanager</code> or <code>ssmparameter</code>), optionally <code>objectAlias</code> to control the filename, <code>objectVersionLabel</code> to pin a staging label, and <code>jmesPath</code> to extract individual fields out of a JSON secret into separate files — which is how you turn one <code>{\"username\":...,\"password\":...}</code> secret into <code>db-user</code> and <code>db-pass</code> files. The pod then declares a volume of type <code>csi</code> with driver <code>secrets-store.csi.k8s.io</code>, <code>readOnly: true</code>, and <code>volumeAttributes.secretProviderClass</code> naming the class.</p>\n<p style=\"line-height: 1.75\">Two behaviours matter enormously in interviews. First, the mount is <strong>blocking</strong>: if the pod's role cannot read the secret, or the secret does not exist, the volume mount fails and the pod stays in <code>ContainerCreating</code> with the real AWS error surfaced in <code>kubectl describe pod</code> events. That is a feature — you fail closed, loudly, at startup, rather than starting with an empty credential. Second, the CSI driver's <strong>rotation reconciler</strong> is opt-in: you install the driver with <code>enableSecretRotation=true</code> and a <code>rotationPollInterval</code> (default 2 minutes). The reconciler periodically re-fetches from AWS and, if the value changed, rewrites the file in the tmpfs volume.</p>\n<p style=\"line-height: 1.75\"><strong>And here is the detail that trips up most candidates: updating the file does not restart the pod and does not reload the application.</strong> If your process read the file once at startup and cached the string in memory, rotation propagates to the filesystem and changes nothing about the running process. You must either (a) write the app to watch the file — re-read on every use, or use an fsnotify-style watcher, or re-read on an auth failure — or (b) restart the workload, which means something has to trigger a rolling restart. Common approaches for (b) are Reloader-style controllers that watch a synced Kubernetes Secret and patch a pod template annotation, or an EventBridge rule on the rotation event driving a deployment restart. A design that pairs rotation with a long-lived process that reads once at boot is a latent outage.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">secretObjects: the sync feature and what it costs you</h4>\n<p style=\"line-height: 1.75\">The CSI driver also supports <code>spec.secretObjects</code>, which mirrors mounted content into a native Kubernetes Secret so that a container can consume it as an environment variable via <code>envFrom</code> or <code>valueFrom.secretKeyRef</code>. This is enormously convenient — most off-the-shelf images expect <code>DATABASE_URL</code> in the environment — and it is a genuine security regression, which you should say out loud in an interview. The moment you sync, the plaintext value is an object in the Kubernetes API and a row in etcd. Anyone with <code>get secrets</code> in that namespace can read it, it lands in etcd backups, and the \"never touches etcd\" property that motivated the CSI driver is gone. A second subtlety: the synced Secret's lifecycle is tied to a pod actually mounting the volume — the sync happens as part of the mount, so the Secret appears when the first pod mounts and is garbage-collected (via owner references) when the last one goes away. People are surprised when a Secret referenced by a CronJob does not exist because no long-running pod is holding the mount.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">External Secrets Operator</h4>\n<p style=\"line-height: 1.75\">The <strong>External Secrets Operator (ESO)</strong> takes the opposite design stance: it is a plain controller, not a CSI plugin, and its entire job is to reconcile a Kubernetes Secret to match an external store. You define a <strong>SecretStore</strong> (namespaced) or <strong>ClusterSecretStore</strong> (cluster-wide) describing the backend — <code>provider.aws</code> with <code>service: SecretsManager</code>, a region, and auth via <code>jwt.serviceAccountRef</code> (IRSA) or the node/controller role. Then an <strong>ExternalSecret</strong> names the target Secret, a <code>refreshInterval</code>, and either a list of <code>data</code> entries mapping a target key to a <code>remoteRef.key</code> (with optional <code>property</code> to pull one JSON field) or a <code>dataFrom.extract</code> that explodes an entire JSON secret into keys. There is also a <strong>PushSecret</strong> resource for the reverse direction, and <strong>ClusterExternalSecret</strong> to fan an ExternalSecret out across namespaces by label selector.</p>\n<p style=\"line-height: 1.75\">ESO's <code>target.template</code> is its killer feature: you can render the secret into whatever shape the app wants — a full connection string, a <code>.pgpass</code> file, a Java properties blob, a dockerconfigjson for an image pull secret — using Go templating over the fetched values, with helper functions for base64 and JSON. This is why teams with heterogeneous off-the-shelf software often land on ESO: they can adapt any secret to any config format without touching the application.</p>\n<p style=\"line-height: 1.75\">The cost is structural and unavoidable: <strong>ESO always writes a native Kubernetes Secret</strong>. The value is in etcd, full stop. There is no ESO mode that keeps it out. Its rotation story is simpler than the CSI driver's — the controller polls on <code>refreshInterval</code> and updates the Secret — but the same reload problem exists: a pod with an <code>envFrom</code> reference will not see a changed Secret, because environment variables are fixed at process start. A pod with the Secret mounted as a volume does see the updated file (the kubelet syncs projected Secret volumes, with its own sync-period lag of up to about a minute plus cache TTL), and again the app must re-read it.</p>\n<h4 style=\"margin-top: 1.5rem; If you control the code, having the application call <code>GetSecretValue</code> itself with a caching client gives you the smallest exposure surface, per-call CloudTrail attribution, and a natural place to handle rotation (refetch on authentication failure). The CSI driver and ESO exist mostly to serve software you cannot modify.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Environment variables versus mounted files</h4>\n<p style=\"line-height: 1.75\">Environment variables feel harmless and are the weakest of the delivery mechanisms:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>They are inherited by every child process.</strong> A shell-out to a helper binary, a debugging tool, or a crash handler gets the full environment.</li>\n<li><strong>They land in crash dumps and error reporters.</strong> Many APM and exception libraries serialize the environment into the crash payload and ship it to a third party.</li>\n<li><strong>They are readable through the API.</strong> <code>kubectl describe pod</code> shows literal <code>env</code> values; <code>kubectl get pod -o yaml</code> shows the secretKeyRef names; and anyone with pod exec can read <code>/proc/1/environ</code>.</li>\n<li><strong>They are frozen at process start.</strong> There is no mechanism for an env var to change in a running process, so env-var delivery is fundamentally incompatible with rotation without a restart.</li>\n<li><strong>They get logged.</strong> \"Dump config on startup\" is a near-universal debugging habit.</li>\n</ul>\n<p style=\"line-height: 1.75\">A file on a tmpfs volume with mode 0400 avoids all five: it is not inherited, not in the environment, not visible in the pod spec, re-readable after rotation, and permissioned. The one place env vars remain defensible is the pointer, not the value — put the <em>secret ARN</em> in an env var and let the app fetch it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Namespace isolation, RBAC, and etcd encryption</h4>\n<p style=\"line-height: 1.75\">Kubernetes Secrets are namespaced, so the namespace is your primary blast-radius boundary — one team or tenant per namespace, and <code>get/list/watch secrets</code> granted only to the workload's service account and to a tightly held platform role. Two traps: a ClusterRole with <code>secrets</code> in its resources applies to every namespace, and <code>list</code> on secrets returns the values, so \"read-only list access\" is full disclosure. Audit with a periodic check for subjects that can list secrets cluster-wide. Beyond RBAC, use a policy engine (Kyverno, OPA Gatekeeper, or Pod Security Admission plus admission policies) to block pods that mount another tenant's SecretProviderClass, to require <code>readOnly: true</code> on CSI volumes, and to forbid <code>hostPath</code> mounts which would let a pod read another pod's tmpfs through the kubelet directory.</p>\n<p style=\"line-height: 1.75\">Finally, <strong>EKS secrets encryption with KMS</strong> is defense in depth for anything that does land in etcd. EKS supports envelope encryption of Secret resources with a customer-managed KMS key, so an etcd snapshot without KMS access is useless, and every decrypt is a CloudTrail event. It does not solve the RBAC problem — a user with <code>get secrets</code> still sees plaintext because the API server decrypts for them — but it closes the backup and disk-image exposure. It is a two-line answer that reliably impresses: \"KMS envelope encryption protects etcd at rest; it does nothing about who can call the API, which is what RBAC is for.\"</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Production scenario: secret delivery for a multi-tenant cluster</h4>\n<p style=\"line-height: 1.75\">Forty teams share one EKS cluster, namespace-per-service, and the platform team owns the delivery mechanism.
