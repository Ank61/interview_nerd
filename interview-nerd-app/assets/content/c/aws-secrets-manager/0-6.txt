{"title":"Encryption — How Secrets Manager Protects Values with AWS KMS","tags":["kms","encryption","envelope-encryption","customer-managed-key"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">When you store a database password in Secrets Manager, that value ends up written to disk on AWS hardware somewhere. The obvious question a security reviewer will ask is: what stops someone with access to that storage from reading it? The answer is encryption, and Secrets Manager does not do it alone — it delegates the key handling to another AWS service called KMS. Understanding this pairing explains a whole category of confusing errors, so it is worth getting precise.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Encryption at rest and encryption in transit</h4>\n<p style=\"line-height: 1.75\">Two different moments need protecting, and they are handled by two different mechanisms.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Encryption at rest.</strong> The secret value sitting in storage is scrambled with a key. If someone somehow obtained the raw bytes from the underlying disk or a backup, they would get unreadable ciphertext, not your password. This is always on in Secrets Manager — there is no option to store a value in plaintext.</li>\n<li><strong>Encryption in transit.</strong> When your application calls <code>GetSecretValue</code>, the value travels across a network. Secrets Manager API endpoints only accept <strong>TLS</strong> (the same protocol behind HTTPS), so the traffic is encrypted between your client and the service. There is no unencrypted endpoint to accidentally use.</li>\n</ul>\n<p style=\"line-height: 1.75\">Both matter. Encrypting at rest but sending in plaintext would be pointless, and vice versa. The piece you configure and get asked about is at-rest encryption, because that is where key choice lives.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What AWS KMS actually is</h4>\n<p style=\"line-height: 1.75\"><strong>AWS KMS</strong> — Key Management Service — is a managed service whose job is to hold encryption keys and control who may use them. In plain words: it is a vault for keys, and every use of a key is a permission-checked, logged API call.</p>\n<p style=\"line-height: 1.75\">The important property is that a <strong>KMS key</strong> never leaves KMS in plaintext form. You cannot download it. You do not handle it. Instead you ask KMS to perform operations on your behalf: encrypt this, decrypt that, generate a data key for me. Every one of those calls is authorised against policy and recorded in <strong>AWS CloudTrail</strong> (the AWS service that logs API activity), which is how you can later prove who decrypted what and when.</p>\n<p style=\"line-height: 1.75\">This matters because it moves the hardest problem — protecting the key that protects everything else — into a service backed by hardware security modules and audited access, instead of a config file on a server.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Envelope encryption, explained simply</h4>\n<p style=\"line-height: 1.75\">KMS keys are designed for small payloads and every use is a network call, so encrypting large or frequent data directly with them would be slow and expensive. It appears in your account the first time you create a secret without specifying a key, costs nothing, and requires zero setup. For a straightforward single-account application it is a perfectly respectable choice, and saying so in an interview shows judgement rather than cargo-culting.</p>\n<p style=\"line-height: 1.75\">A <strong>customer managed key</strong> is one you create yourself. It shows up in the KMS console under Customer managed keys, has its own ARN, its own alias such as <code>alias/prod-secrets</code>, and — crucially — its own <strong>key policy</strong>, which is a document attached to the key saying who may use it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Concrete reasons to choose a customer managed key</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Cross-account access requires it.</strong> If a role in account B must read a secret owned by account A, the AWS managed key cannot be shared. You must use a customer managed key whose key policy grants decrypt permission to the principal in account B. This is the single most common forcing reason.</li>\n<li><strong>The key policy is a second, independent permission layer.</strong> Even if someone accidentally grants overly broad <code>secretsmanager:GetSecretValue</code>, they still cannot read the value without decrypt permission on the key. Two locks controlled by two different policies — often by two different teams — is a real separation-of-duties control.</li>\n<li><strong>You can revoke instantly.</strong> Disabling the key makes every secret encrypted under it immediately unreadable, with no policy edits, no deployment and no waiting. That is a genuine break-glass control during an incident, and it is impossible with the AWS managed key.</li>\n<li><strong>Rotation and auditing are yours.</strong> You choose whether the key material rotates automatically each year, and you own the CloudTrail record of every Decrypt call against it, which is what auditors ask to see.</li>\n<li><strong>Grouping and blast radius.</strong> Using separate keys for production and non-production, or per business unit, means a mistake or compromise in one scope cannot read the other's secrets.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The two-permission rule — the number one beginner AccessDenied</h4>\n<p style=\"line-height: 1.75\">This is the most valuable practical fact in this topic. To read a secret encrypted with a customer managed key, a caller needs <strong>both</strong> permissions:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>secretsmanager:GetSecretValue</strong> on the secret — permission to ask for the secret at all.</li>\n<li><strong>kms:Decrypt</strong> on the KMS key — permission to unwrap the encrypted data key so the value can be decrypted.</li>\n</ul>\n<p style=\"line-height: 1.75\">Because envelope encryption requires unwrapping the data key, having the first without the second fails. The error message mentions KMS, but beginners read \"AccessDenied\" and go back to editing their Secrets Manager policy, which is already correct. If you take one thing from this topic into an interview, take this: a working <code>secretsmanager:GetSecretValue</code> policy plus a failing read usually means the missing permission is <code>kms:Decrypt</code>.</p>\n<p style=\"line-height: 1.75\">There is a subtlety worth knowing. With a customer managed key, permission can come from the caller's IAM policy <em>or</em> from the KMS key policy, and for cross-account it must be granted in both the key policy and the external account's IAM policy. Rotation functions and writers also need <code>kms:GenerateDataKey</code>, because storing a new value means creating a new data key, not just decrypting an old one. With the AWS managed key, Secrets Manager handles the permission plumbing for same-account callers, which is exactly why beginners hit this wall only after switching to a customer managed key.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What happens if the key is disabled or deleted</h4>\n<p style=\"line-height: 1.75\">Keys have a lifecycle, and it has sharp edges.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Disabled key.</strong> Every attempt to read a secret encrypted under it fails immediately. The data is intact — nothing is lost — and re-enabling the key restores access at once. Rotation for those secrets also fails while the key is disabled. This is reversible, which is what makes it useful as an emergency switch.</li>\n<li><strong>Scheduled for deletion.</strong> KMS never deletes a key instantly; you schedule deletion with a waiting period of 7 to 30 days. During that period the key is effectively disabled, so reads already fail, but you can cancel the deletion and recover. This waiting period exists precisely because deleting a key is unrecoverable.</li>\n<li><strong>Actually deleted.</strong> Once the waiting period elapses and the key material is gone, every secret encrypted under it is permanently unreadable. AWS cannot recover it and neither can you. The ciphertext still sits there; it is simply meaningless forever.</li>\n</ul>\n<p style=\"line-height: 1.75\">The operational lesson: before scheduling a KMS key for deletion, find everything encrypted under it. CloudTrail data on recent Decrypt calls against the key is the practical way to check whether it is still in use.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">You can change the key later</h4>\n<p style=\"line-height: 1.75\">A secret's encryption key is not permanent. You can call <code>update-secret</code> with a new <code>--kms-key-id</code> to point the secret at a different key — for example migrating from <code>aws/secretsmanager</code> to a customer managed key when a workload moves into scope for compliance.</p>\n<p style=\"line-height: 1.75\">The important nuance is that this applies to <strong>future versions</strong>. Existing stored versions remain encrypted under the old key, so you must keep the old key available (not disabled, not deleted) until those versions no longer matter. The clean migration is: change the key, then store a new value or trigger a rotation so that the current version is encrypted under the new key, and only then retire the old key. Also remember to grant callers <code>kms:Decrypt</code> on the new key before the switch, or you will manufacture the exact AccessDenied described above.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What is NOT encrypted</h4>\n<p style=\"line-height: 1.75\">Only the secret value is encrypted. The secret's <strong>metadata</strong> is not:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>The name.</strong> Anyone with <code>ListSecrets</code> or <code>DescribeSecret</code> sees it. So never encode sensitive information in the name — <code>prod/acme-corp-merger/db</code> leaks a fact even though the password stays safe.</li>\n<li><strong>The description.</strong> Same exposure. Write \"connection string for the orders database\", not the connection string itself.</li>\n<li><strong>Tags.</strong> Tag keys and values are plaintext and visible to anyone who can describe the secret. Never put a token or an account number in a tag. Tags are also used in IAM conditions, which makes who-can-write-tags a security question in its own right.</li>\n<li><strong>ARNs, timestamps, rotation configuration and version labels.</strong> All plaintext operational metadata.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"I have to enable encryption.\"</strong> You do not; it is always on. The only decision is <em>which key</em>.</li>\n<li><strong>\"GetSecretValue permission is enough.\"</strong> Not with a customer managed key. You also need <code>kms:Decrypt</code>, and writers need <code>kms:GenerateDataKey</code>. This is the classic confusing AccessDenied.</li>\n<li><strong>\"KMS stores my secret.\"</strong> It does not. KMS holds keys; Secrets Manager holds the encrypted value. Under envelope encryption the secret value never travels to KMS at all.</li>\n<li><strong>\"A customer managed key is always the better choice.\"</strong> It costs money and adds operational responsibility. If you are in one account with no separation-of-duties requirement, <code>aws/secretsmanager</code> is a defensible choice.</li>\n<li><strong>\"Tags and names are private.\"</strong> They are plaintext metadata, readable by anyone who can list or describe secrets.</li>\n<li><strong>\"Deleting a KMS key just cleans up.\"</strong> It permanently destroys the ability to read everything encrypted under it. That is why KMS forces a 7-to-30-day waiting period.</li>\n<li><strong>\"Changing the key re-encrypts everything.\"</strong> It only affects future versions; old versions still need the old key.</li>\n</ul>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"Secrets Manager always encrypts values at rest using AWS KMS, and all API traffic is TLS-protected in transit.
