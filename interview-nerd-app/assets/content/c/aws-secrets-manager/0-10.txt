{"title":"Integrations — Databases, Lambda, ECS, and Infrastructure as Code","tags":["aws","secrets manager","integrations","ecs"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Storing a secret safely is only half the job. The other half is getting it into your running code without ever writing it into a config file, a container image, or a Git repository. <strong>AWS Secrets Manager</strong> — the AWS service that stores and hands out credentials — integrates with most of the places your code actually runs, and each integration has its own mechanics and its own gotcha. This topic walks through them one at a time.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Databases: Amazon RDS, Aurora, Redshift and DocumentDB</h4>\n<p style=\"line-height: 1.75\"><strong>Amazon RDS</strong> is AWS's managed relational database service, and <strong>Amazon Aurora</strong> is its high-performance MySQL/PostgreSQL-compatible engine. This is the deepest integration Secrets Manager has, because AWS ships ready-made rotation code for these engines.</p>\n<p style=\"line-height: 1.75\">When you create an RDS or Aurora database in the console, the \"Credentials management\" option lets you choose <strong>Managed in AWS Secrets Manager</strong>. Choosing it means AWS generates the master password, creates the secret for you, and wires up rotation — you never see or type the password at all. For an existing database you can instead create a secret of type \"credentials for an RDS database\" and point it at the DB instance.</p>\n<p style=\"line-height: 1.75\">Either way, the secret value is JSON with a specific, expected shape. The AWS-provided rotation functions read these exact field names, so getting them right is what makes one-click rotation possible:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>username</strong> — the database login name.</li>\n<li><strong>password</strong> — the credential itself.</li>\n<li><strong>engine</strong> — which database this is: <code>mysql</code>, <code>postgres</code>, <code>oracle</code>, <code>sqlserver</code>, <code>mariadb</code>, <code>mongo</code> or <code>redshift</code>. The rotation function uses this to pick the right SQL dialect for changing a password.</li>\n<li><strong>host</strong> — the endpoint hostname, so the rotation function knows where to connect.</li>\n<li><strong>port</strong> — the port number.</li>\n<li><strong>dbname</strong> — the database to connect to.</li>\n<li><strong>dbClusterIdentifier</strong> — present instead of a plain instance identifier for Aurora clusters.</li>\n</ul>\n<p style=\"line-height: 1.75\">If you hand-roll a secret with a field called <code>user</code> instead of <code>username</code>, the managed rotation function will fail — and it will fail at rotation time, weeks later, not at creation time. That is why the console's structured \"credentials\" secret type is worth using: it fills the shape in for you.</p>\n<p style=\"line-height: 1.75\">Two other database-adjacent integrations are worth naming. <strong>Amazon RDS Proxy</strong> — a connection pooler that sits in front of your database — authenticates to the database by reading credentials directly from a Secrets Manager secret, so your application authenticates to the proxy and never holds the database password at all. And the <strong>RDS Data API</strong> for Aurora Serverless takes a secret ARN as a parameter instead of a connection string.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">AWS Lambda: where you fetch matters enormously</h4>\n<p style=\"line-height: 1.75\"><strong>AWS Lambda</strong> runs your function code without you managing servers. A Lambda execution environment is reused across invocations when traffic is steady — a \"warm\" container — and code at <strong>module scope</strong> (outside the handler, at the top of the file) runs once per environment, while code <strong>inside the handler</strong> runs on every single invocation.</p>\n<p style=\"line-height: 1.75\">That distinction is the entire Lambda story for secrets:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Fetching inside the handler</strong> means an API call to Secrets Manager on every invocation. At 10 million invocations a month that is 10 million billed API calls, plus 20–100 ms of added latency on each one, plus exposure to throttling.</li>\n<li><strong>Fetching at module scope</strong> (or lazily into a module-level variable) means one call per execution environment, reused across every warm invocation. This is the single highest-value optimization here.</li>\n</ul>\n<p style=\"line-height: 1.75\">The catch with caching forever is rotation: a long-lived warm container can hold a password that has since been rotated. The standard pattern is a <strong>cache with a short time-to-live plus retry-on-auth-failure</strong>: keep the value for a few minutes, and if the database rejects the credentials, clear the cache, re-fetch, and retry once.</p>\n<p style=\"line-height: 1.75\">AWS packages all of this for you as the <strong>AWS Parameters and Secrets Lambda Extension</strong>. A Lambda extension is a companion process that runs alongside your function in the same execution environment. You attach it as a <strong>layer</strong> (a versioned bundle of code added to a function), and it starts a tiny local HTTP server on port 2773. Your code makes a plain local HTTP GET to <code>localhost:2773/secretsmanager/get?secretId=my-secret</code> instead of calling the AWS SDK, and the extension handles the API call and caches the result in memory.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>SECRETS_MANAGER_TTL</strong> — how long a cached secret stays valid, in seconds. Default is 300; set it to 0 to disable caching.</li>\n<li><strong>SECRETS_MANAGER_CACHE_SIZE</strong> — how many distinct secrets to hold; default 1000.</li>\n<li><strong>PARAMETERS_SECRETS_EXTENSION_HTTP_PORT</strong> — change the port if 2773 conflicts.</li>\n<li><strong>Authentication.</strong> Requests must include the function's <code>AWS_SESSION_TOKEN</code> in the <code>X-Aws-Parameters-Secrets-Token</code> header, so other processes cannot trivially read secrets through it.</li>\n</ul>\n<p style=\"line-height: 1.75\">The function's <strong>execution role</strong> — the IAM role Lambda assumes to run your code — still needs <code>secretsmanager:GetSecretValue</code> on the specific secret. The extension does not grant permission; it only caches.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Amazon ECS and AWS Fargate</h4>\n<p style=\"line-height: 1.75\"><strong>Amazon ECS (Elastic Container Service)</strong> runs Docker containers for you, and <strong>AWS Fargate</strong> is the mode where AWS runs them without you managing servers. A <strong>task definition</strong> is the JSON blueprint describing your container: image, CPU, memory, ports and environment.</p>\n<p style=\"line-height: 1.75\">A task definition has two similar-looking blocks and the difference is the whole point:</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Block</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">What you put in it</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Visibility</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><code>environment</code></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Literal name/value pairs</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Plainly visible to anyone who can describe the task definition, and stored in CloudTrail and version history forever</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><code>secrets</code></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">A name plus a <code>valueFrom</code> ARN pointing at a secret</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Only the ARN is stored; the value is fetched at task start and injected as an environment variable inside the container</td></tr>\n</tbody>\n</table>\n</div>\n<p style=\"line-height: 1.75\">In the <code>secrets</code> block, <code>valueFrom</code> takes the secret's ARN, and you can append a JSON key to pull one field out of a JSON secret — the format is the ARN followed by a colon, the JSON key, a colon, an optional version stage, a colon, and an optional version id. So <code>...:secret:prod/db-AbCdEf:password::</code> injects just the password field.</p>\n<p style=\"line-height: 1.75\">The permission lives on the <strong>task execution role</strong>, not the task role. The execution role is what the ECS agent itself uses to pull images and fetch secrets <em>before</em> your container starts; the task role is what your application code uses <em>while</em> running. Secret injection needs <code>secretsmanager:GetSecretValue</code> (and <code>kms:Decrypt</code> if a customer managed key is used) on the <strong>execution role</strong>. Putting it on the task role by mistake produces a task that fails to start with a ResourceInitializationError — a classic interview troubleshooting question.</p>\n<p style=\"line-height: 1.75\"><strong>The critical caveat:</strong> injected secrets are resolved exactly <strong>once, at container start</strong>. They become ordinary environment variables in the container's process. When the secret rotates, running tasks keep the old value forever — an environment variable cannot change underneath a running process. To pick up a rotated secret you must <strong>start new tasks</strong>: force a new deployment, which ECS rolls out with your usual deployment strategy. If your workload cannot tolerate that, fetch the secret with the SDK inside the application instead, where you control caching and refresh.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Amazon EKS and Kubernetes</h4>\n<p style=\"line-height: 1.75\"><strong>Amazon EKS (Elastic Kubernetes Service)</strong> is managed Kubernetes. The standard approach is the <strong>Kubernetes Secrets Store CSI Driver</strong> with the <strong>AWS Secrets and Configuration Provider (ASCP)</strong>. CSI stands for Container Storage Interface — the plugin system Kubernetes uses to mount storage into pods.</p>\n<p style=\"line-height: 1.75\">You install the driver and the AWS provider, then create a <code>SecretProviderClass</code> resource naming which Secrets Manager secrets to fetch. Pods reference it as a volume, and the secret values appear as files on a mounted in-memory filesystem inside the pod. Two orientation-level details matter: authentication uses <strong>IAM Roles for Service Accounts (IRSA)</strong> or EKS Pod Identity, which maps a Kubernetes service account to an IAM role so pods get scoped AWS permissions without static keys; and the driver can optionally <strong>sync to native Kubernetes Secret objects</strong> and can rotate mounted values on a polling interval if rotation reconciliation is enabled. Mounted files can update in place — unlike ECS environment variables — but your application still has to re-read the file to notice.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">CloudFormation and the AWS CDK</h4>\n<p style=\"line-height: 1.75\"><strong>AWS CloudFormation</strong> creates AWS resources from a template file, and the <strong>AWS CDK (Cloud Development Kit)</strong> lets you write those templates in a real programming language. Both support a genuinely excellent pattern: <strong>nobody ever sees the password</strong>.</p>\n<p style=\"line-height: 1.75\">A secret resource can carry a <code>GenerateSecretString</code> property. At deploy time CloudFormation asks Secrets Manager to generate a random password, optionally embedding it into a JSON template so you get a complete credentials document. You control length, which character classes to exclude, and which JSON key receives the generated value. The password is created inside AWS and stored encrypted — it never appears in the template, in your repository, in a pipeline log, or on anyone's screen.</p>\n<p style=\"line-height: 1.75\">To then <em>use</em> that value elsewhere in the template, you use a <strong>dynamic reference</strong> — a special placeholder string that CloudFormation resolves by calling Secrets Manager at deployment time. Written out, it is two open-brace characters, then the word <code>resolve</code>, a colon, <code>secretsmanager</code>, a colon, the secret id, then optional colon-separated parts for <code>SecretString</code>, the JSON key, the version stage and the version id — closed by two close-brace characters. So the inner text is <code>resolve:secretsmanager:prod/app/db:SecretString:password</code>, wrapped in that double-brace pair.</p>\n<p style=\"line-height: 1.75\">There is an important nuance about what a dynamic reference protects. It keeps the secret out of the <em>template</em> and out of CloudFormation's stored parameters and events. It does <strong>not</strong> keep the value out of the resource it is passed to. If you resolve a secret into a Lambda environment variable, the resolved plaintext sits in that function's configuration where anyone with <code>lambda:GetFunctionConfiguration</code> can read it. Dynamic references are for properties that consume the value securely — an RDS master password, for instance — not a laundering mechanism.</p>\n<p style=\"line-height: 1.75\">CloudFormation also offers a <strong>SecretTargetAttachment</strong> resource, which stitches the database's host, port and identifier into an existing secret after the database is created — solving the chicken-and-egg problem where the secret must exist before the database but needs the database's endpoint. In the CDK, the equivalents are <code>Secret</code> with <code>generateSecretString</code>, the <code>attach</code> method, and <code>secret.grantRead(role)</code>, which writes the correctly-scoped IAM policy for you.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">CodeBuild and CodePipeline</h4>\n<p style=\"line-height: 1.75\"><strong>AWS CodeBuild</strong> runs your build and test commands; <strong>AWS CodePipeline</strong> chains stages together. Builds routinely need credentials — a private package registry token, a Docker Hub login, a code-signing key.</p>\n<p style=\"line-height: 1.75\">In a <code>buildspec.yml</code> file, the <code>env</code> section has a <code>secrets-manager</code> block that maps an environment variable name to a secret id and optionally a JSON key. CodeBuild fetches the value at build start and injects it. The build project's <strong>service role</strong> needs read permission on the secret. CodeBuild also masks these values in build logs, though you should still avoid echoing them. For Docker Hub and GitHub credentials specifically, CodeBuild and CodePipeline have first-class fields that accept a Secrets Manager ARN directly.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"ECS injected secrets update automatically when the secret rotates.\"</strong> They do not. The value is resolved once at container start and becomes a plain environment variable. Running tasks keep the old value until you deploy new ones.</li>\n<li><strong>\"A dynamic reference keeps the value out of the deployed resource.\"</strong> It only keeps it out of the template and CloudFormation's own records. The resolved plaintext lands in whatever property you put it in — including a Lambda environment variable, where it is readable.</li>\n<li><strong>\"Lambda caches secrets for me by default.\"</strong> It does not. Every SDK call is a real API call unless you cache at module scope yourself or attach the Parameters and Secrets Lambda Extension.</li>\n<li><strong>\"Permissions for ECS secret injection go on the task role.\"</strong> They go on the <strong>task execution role</strong> — the ECS agent fetches the secret before your container exists. Getting this wrong yields a task that never starts.</li>\n<li><strong>\"Any JSON shape works for RDS rotation.\"</strong> The AWS-provided rotation functions expect specific field names — <code>username</code>, <code>password</code>, <code>engine</code>, <code>host</code>, <code>port</code>, <code>dbname</code>. A near-miss like <code>user</code> fails silently until the first rotation.</li>\n<li><strong>\"The Lambda extension replaces IAM permissions.\"</strong> It only caches. The execution role still needs <code>GetSecretValue</code> on the secret.</li>\n<li><strong>\"Putting a secret in the task definition's environment block is fine if the repo is private.\"</strong> It is not — anyone with describe permissions on the task definition sees it in plaintext, and every revision is retained.</li>\n</ul>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"RDS and Aurora integrate deepest — a structured JSON secret with username, password, engine, host, port and dbname unlocks AWS's managed rotation functions.
