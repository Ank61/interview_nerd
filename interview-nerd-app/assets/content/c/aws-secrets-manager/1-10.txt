{"title":"Infrastructure as Code Patterns — and the Terraform State Problem","tags":["terraform","cloudformation","cdk","iac-security"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Infrastructure as code creates a structural tension with secrets. IaC wants everything declared in a file that is version-controlled, reviewed, and diffable — and a secret is precisely the thing that must not be in a version-controlled, reviewed, diffable file. Every mature pattern here is a way of describing a secret's <em>existence and lifecycle</em> in code while keeping its <em>value</em> out of the repository, out of the state file, and out of the plan output. The mature answer to \"how do I put a password in Terraform?\" is usually \"you don't — you make Terraform create a secret whose value it generates or never sees.\"</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">CloudFormation: generate the value at deploy time</h4>\n<p style=\"line-height: 1.75\">The cleanest CloudFormation pattern is that <strong>no human ever sees the value</strong>. <code>AWS::SecretsManager::Secret</code> has a <code>GenerateSecretString</code> property: instead of supplying <code>SecretString</code>, you describe the shape you want and Secrets Manager generates the value server-side during stack creation. The useful sub-properties are <code>PasswordLength</code>, <code>ExcludeCharacters</code>, <code>ExcludePunctuation</code>, <code>ExcludeUppercase</code>/<code>ExcludeLowercase</code>/<code>ExcludeNumbers</code>, <code>RequireEachIncludedType</code>, and the JSON pair, <code>SecretStringTemplate</code> with <code>GenerateStringKey</code>, which lets you emit <code>{\"username\":\"app\",\"password\":\"&lt;generated&gt;\"}</code> in one shot.</p>\n<p style=\"line-height: 1.75\"><strong>ExcludeCharacters matters more than it looks.</strong> Target systems have real restrictions: RDS forbids <code>/</code>, <code>@</code>, <code>\"</code> and space in the master password; a password that ends up in a URI breaks on <code>/</code>, <code>:</code>, <code>@</code>, <code>?</code> and <code>#</code> unless everything percent-encodes correctly; a value passed through a shell breaks on quotes, backslashes and dollar signs. A generated password that works for six weeks and then fails on the one rotation that happens to produce an <code>@</code> is a genuinely nasty intermittent outage, so pick the exclusion set for the strictest consumer and compensate with length rather than character diversity.</p>\n<p style=\"line-height: 1.75\">From there you wire the rest declaratively: <code>AWS::SecretsManager::SecretTargetAttachment</code> links the secret to the RDS instance or cluster, which populates the connection fields (<code>host</code>, <code>port</code>, <code>dbname</code>, <code>engine</code>) into the secret JSON — and crucially it breaks the circular dependency where the database needs the password and the secret needs the database identity. Then <code>AWS::SecretsManager::RotationSchedule</code> attaches rotation, either with a <code>HostedRotationLambda</code> (AWS builds and manages the function) or a <code>RotationLambdaARN</code> you own, plus a <code>RotationRules</code> block. For RDS you can also skip the secret entirely with <code>ManageMasterUserPassword</code>, where RDS itself creates and rotates a managed secret.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Dynamic references and their limits</h4>\n<p style=\"line-height: 1.75\">CloudFormation <strong>dynamic references</strong> let a template resolve a value at deploy time using the syntax <code>&lbrace;&lbrace;resolve:secretsmanager:secret-id:SecretString:json-key:version-stage:version-id&rbrace;&rbrace;</code> — so a template can carry a pointer while CloudFormation substitutes the real value during the stack operation. There is also <code>ssm-secure</code> for SecureString parameters. Three nuances a senior candidate should volunteer:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Not every property supports them.</strong> The <code>ssm-secure</code> form in particular is supported only on a documented subset of resource properties (it was designed for things like an RDS master password), and <code>secretsmanager</code> references are not permitted everywhere either — notably they are not resolved in all custom-resource or nested-stack paths, and using one where it is unsupported silently ships the literal string, which then appears as a nonsensical password.</li>\n<li><strong>The resolved value can persist in the deployed resource.</strong> This is the big one. If you use a dynamic reference for a Lambda environment variable or an ECS container <code>environment</code> entry, CloudFormation resolves it and the <em>plaintext is now stored in that resource's configuration</em> — visible in <code>GetFunctionConfiguration</code>, in the console, to anyone with describe permissions, and in drift detection output. It is masked in the template, not in the deployed artifact.</li>\n<li><strong>It is a deploy-time snapshot.</strong> When the secret rotates, the deployed value does not change until the next stack update, so a dynamic reference and automatic rotation are in direct conflict.</li>\n</ul>\n<p style=\"line-height: 1.75\">Therefore the rule: use a dynamic reference where the consuming service performs the resolution securely and refetches (an RDS master password at create time, an ECS <code>secrets</code> block) and otherwise <strong>pass the ARN and let the workload fetch at runtime</strong>. \"Reference the ARN, not the value\" is the sentence to say.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">CDK ergonomics and the classic mistake</h4>\n<p style=\"line-height: 1.75\">CDK makes the good pattern easy and the bad pattern easier. <code>new secretsmanager.Secret(this, 'Db', &lbrace; generateSecretString: &lbrace;...&rbrace; &rbrace;)</code> synthesises exactly the GenerateSecretString template above; <code>secret.grantRead(taskRole)</code> writes the least-privilege policy including the KMS grant; and passing a Secret into an RDS <code>Credentials.fromSecret()</code> or an ECS <code>ecs.Secret.fromSecretsManager(secret, 'password')</code> produces ARN references rather than values.</p>\n<p style=\"line-height: 1.75\">The classic mistake is <code>SecretValue.unsafePlainText()</code> or, subtly, calling <code>.toString()</code> / <code>unsafeUnwrap()</code> on a <code>SecretValue</code> and interpolating it into a construct property. CDK deliberately makes <code>SecretValue</code> awkward to convert to a string precisely to stop this. When you force it, the value — or a resolvable that renders to it — is <strong>baked into the synthesized CloudFormation template</strong>, which is then committed to the repo, uploaded to the CDK assets S3 bucket, stored in the stack's template history, and visible to anyone with <code>cloudformation:GetTemplate</code>. The same applies to reading a secret in synthesis code (an SDK call at synth time and then embedding the result): the value ends up in the artifact. A safe rule — <strong>anything you can see in <code>cdk synth</code> output is public within your organisation</strong>. Run <code>cdk synth | grep</code> for known markers as a CI check.</p>\n<p style=\"line-height: 1.75\">Also watch context and parameters. CloudFormation <code>NoEcho: true</code> on a parameter hides it in the console and in <code>DescribeStacks</code>, but it does not encrypt anything, it does not hide it from someone who can read your CI logs or your parameter source, and the value still moves through the deploy path. <code>NoEcho</code> is an obfuscation, not a control.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Terraform state problem</h4>\n<p style=\"line-height: 1.75\">This is the canonical IaC secrets interview question, so be precise. <strong>Terraform stores every attribute of every managed resource in state, in plaintext JSON.</strong> There is no per-attribute encryption in the classic state file. Concretely:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li>A <code>random_password</code> resource stores the generated password in state.</li>\n<li>An <code>aws_secretsmanager_secret_version</code> stores the <code>secret_string</code> in state.</li>\n<li>An <code>aws_db_instance</code> stores <code>password</code> in state.</li>\n<li>A <code>data \"aws_secretsmanager_secret_version\"</code> block — merely <em>reading</em> a secret — writes the value into state.</li>\n<li><code>sensitive = true</code> on a variable or output only redacts <strong>CLI output</strong>. It does nothing to state. This is the single most common misconception, and stating it clearly scores points.</li>\n</ul>\n<p style=\"line-height: 1.75\">The consequence: <strong>your state backend is a secrets store, whether you designed it to be one or not</strong>, and must be treated as the most sensitive artifact in the repo's blast radius. That means: S3 with SSE-KMS using a customer-managed key (not just SSE-S3), bucket policy denying unencrypted transport, <strong>versioning on</strong> (because old versions contain old secrets — and also means a rotation does not erase the previous value from history), state locking (S3 native lockfile or DynamoDB), a bucket policy and IAM policies that grant state read to a very small set of principals, and <strong>never a local state file</strong> or a state file committed to git. Also remember that <code>terraform plan</code> output and Terraform Cloud/Enterprise run logs can contain values, and that <code>terraform show -json</code> and <code>terraform state pull</code> expose everything to anyone who can run them.</p>\n<p style=\"line-height: 1.75\">Design patterns that limit the damage:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Let Terraform create the container, not the value.</strong> Manage <code>aws_secretsmanager_secret</code> (name, KMS key, policy, tags, rotation schedule) in Terraform and set the value out of band — via a rotation Lambda's first run, via <code>aws secretsmanager put-secret-value</code>, or via the console for a truly manual third-party key. Terraform then never holds the value.</li>\n<li><strong>Generate in the provider, not in Terraform.</strong> Use RDS's <code>manage_master_user_password</code> so RDS creates and rotates the secret, and Terraform only records an ARN.</li>\n<li><strong>Ephemeral resources and write-only arguments.</strong> Terraform 1.10 introduced <strong>ephemeral values</strong> (ephemeral resources and ephemeral variables/outputs) that exist only during a run and are never persisted to state or plan; 1.11 added <strong>write-only arguments</strong>, where a provider accepts a value that is used in the API call but never stored — the AWS provider exposes these for secret version values and for database passwords, paired with a version-nonce argument so you can trigger an update. This is the modern answer and is worth naming explicitly, along with the caveat that it requires recent Terraform and provider versions and that not every argument has a write-only counterpart.</li>\n<li><strong>Don't read secrets with data sources</strong> just to pass them somewhere. Pass the ARN and resolve at runtime.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Drift: the apply that reverts your rotated password</h4>\n<p style=\"line-height: 1.75\">This failure is common enough to be worth memorising. Terraform creates <code>aws_secretsmanager_secret_version</code> with a generated password and also sets that password on the RDS instance. Rotation runs sixty days later and Secrets Manager changes the value. Terraform's next plan compares the API's current value to state, sees a difference, and proposes to <strong>put the old value back</strong>. Someone approves the plan without reading it, the secret reverts to a password the database no longer accepts, and every application fails authentication at once — usually during an unrelated deploy, which makes the diagnosis confusing.</p>\n<p style=\"line-height: 1.75\">Remedies, in order of preference: don't have Terraform manage the version at all (manage the container, let rotation own the value); use write-only arguments so there is nothing to compare; or, if you must, add <code>lifecycle &lbrace; ignore_changes = [secret_string] &rbrace;</code> on the version resource and the equivalent on <code>password</code> for <code>aws_db_instance</code>. The same pattern applies to any externally mutated attribute. And the organisational control matters as much as the code: plans should be reviewed by a human who will notice a secret-value diff, and CI should fail a plan that proposes to change a secret version outside an explicitly flagged change.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Bootstrapping, stack separation, and cross-stack references</h4>\n<p style=\"line-height: 1.75\">The <strong>first credential problem</strong> is unavoidable: something must be trusted before anything else can be. You cannot store the credential that gets the first credential. The answer is to shrink it to an identity rather than a secret — the pipeline authenticates by OIDC federation, EC2 and ECS and Lambda use instance/task/execution roles, EKS uses IRSA — so the only bootstrap artifact is an IAM trust relationship configured once, by a human, in the console or by an organisation-level account factory. Truly unavoidable seeds (a third-party API key that only exists in a vendor's portal) are entered once, manually, by a named owner, into a secret whose value Terraform never reads.</p>\n<p style=\"line-height: 1.75\"><strong>Separate creation from consumption.</strong> Secrets live in a long-lived, slowly changing \"platform\" or \"data\" stack, while applications live in fast-moving stacks that reference them. Two reasons: lifecycle mismatch (you do not want a routine app deploy to be able to delete or recreate a secret, and a secret deletion has a recovery window that will block a recreate), and permission separation (the app stack's deploy role can be denied <code>secretsmanager:DeleteSecret</code> and <code>PutSecretValue</code> entirely). Cross-stack wiring should be <strong>by ARN</strong> — a CloudFormation Export/ImportValue or an SSM Parameter Store lookup, a Terraform remote state data source or a data source resolving by name — never by passing the value between stacks. Prefer an SSM parameter holding the ARN over a hard CloudFormation export, since exports cannot be changed while another stack imports them and that rigidity bites during refactors.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario: reviewing an IaC repo for secret handling</h4>\n<p style=\"line-height: 1.75\">You are handed a Terraform repo and asked what is wrong.
