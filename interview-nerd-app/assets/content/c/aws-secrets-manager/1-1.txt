Single-user is simpler and almost always the right default; alternating-users is what you reach for when the workload cannot tolerate even a brief authentication failure.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Single-User: Where Exactly the Gap Is</h4>\n<p style=\"line-height: 1.75\">In single-user rotation there is one database user, say <code>app_user</code>. <code>createSecret</code> generates a new password into <code>AWSPENDING</code>, <code>setSecret</code> issues <code>ALTER USER app_user WITH PASSWORD</code>, <code>testSecret</code> proves the new password works, and <code>finishSecret</code> moves <code>AWSCURRENT</code>. The critical detail is that <strong>the target starts rejecting the old password the instant setSecret commits</strong>, but <code>AWSCURRENT</code> — what every client reads — does not change until finishSecret. Window B is the bigger one and is entirely the application's fault: a client that cached the secret for fifteen minutes will keep presenting a dead password for up to fifteen minutes unless it invalidates on authentication failure. This is why single-user rotation is perfectly acceptable for any workload that <strong>retries on authentication error and refreshes its cache</strong>, and genuinely unacceptable for a latency-critical synchronous path with no retry logic, where those seconds become user-visible 500s.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Alternating-Users: Trading Complexity for a Full Interval of Slack</h4>\n<p style=\"line-height: 1.75\">Alternating-users keeps two users — conventionally <code>app_user</code> and a clone the AWS templates create by appending a suffix, commonly written as <code>app_user_a</code> and <code>app_user_b</code>. Each rotation operates on the user that is <strong>not</strong> currently referenced by <code>AWSCURRENT</code>: <code>createSecret</code> writes a pending value naming the other user, <code>setSecret</code> creates or updates that user (using an admin credential, since you cannot alter a user you are not authenticated as), <code>testSecret</code> logs in as it, and <code>finishSecret</code> switches <code>AWSCURRENT</code> to the version naming that user. The credential the clients were using is never touched — it stays valid until the <em>next</em> rotation, an entire interval later.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">ALTERNATING<i class=o>-</i>USERS rotation timeline\n\n rotation N      setSecret updates app_user_b   (clients <i class=k>are</i> <i class=k>on</i> app_user_a)\n                 finishSecret <i class=o>-</i><i class=o>&gt;</i> AWSCURRENT <i class=o>=</i> app_user_b\n                 app_user_a STILL VALID  <i class=c>-------------------------+</i>\n                                                                  <i class=o>|</i>\n clients drift onto app_user_b <i class=k>over</i> the next minutes<i class=o>/</i>hours        <i class=o>|</i> <i class=k>full</i>\n                                                                  <i class=o>|</i> <i class=t>interval</i>\n rotation N<i class=o>+</i><i class=n>1</i>    setSecret updates app_user_a   <i class=o>&lt;</i><i class=c>-- only now is a | of slack</i>\n                 the <i class=k>old</i> credential invalidated                   <i class=o>|</i>\n                 finishSecret <i class=o>-</i><i class=o>&gt;</i> AWSCURRENT <i class=o>=</i> app_user_a  <i class=c>--------+</i>\n\n Risk <i class=k>window</i> <i class=k>for</i> a client: <i class=k>none</i>, provided it refreshes <i class=k>within</i> <i class=k>one</i> interval.</code></pre></div>\n<p style=\"line-height: 1.75\">That slack is not free. Alternating-users imposes three real prerequisites. First, a <strong>superuser or admin credential in a separate secret</strong>, referenced from the rotated secret's <code>masterarn</code> field — the rotation function needs privileges to create and alter both users. That admin secret is now the most sensitive object in the system and must be tightly scoped, rotated itself, and never shared with applications. Second, the two users must have <strong>identical privileges forever</strong>. This is the failure mode that bites in practice: months later someone adds a table and runs <code>GRANT SELECT ON new_table TO app_user_a</code>, everything works because clients are on A, and then the next rotation flips to B and half the application starts throwing permission errors. The defence is to grant to a <strong>role</strong> and make both users members of it, so a single grant covers both, plus a privilege-diff check in CI or in <code>testSecret</code>.</p>\n<p style=\"line-height: 1.75\">Third, and specific to PostgreSQL, is <strong>object ownership</strong>. font-size: 1.25rem; font-weight: 600\">Special Cases That Break the Model</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Credentials that cannot be duplicated.</strong> Many third-party APIs allow exactly one active key per integration, so alternating-users is impossible by construction and you are forced into single-user semantics no matter what strategy label you put on it. Where the vendor supports a short overlap — two live keys, or a grace period during which the revoked key still works — design the rotation to exploit it: mint the new key, switch AWSCURRENT, wait out a deliberate soak period, and revoke the old key on the <em>next</em> rotation. That turns a hard cutover into an alternating-users-shaped flow without vendor support for two permanent identities.</li>\n<li><strong>Certificates.</strong> A certificate is not a password: issuance involves a CA round trip and possibly approval, the material has an independent expiry the rotation schedule must respect, and clients often load it from disk at process start rather than from an API. Rotating one usually means overlapping validity periods, distributing the new pair before the old expires, and triggering a reload. For TLS on AWS-integrated endpoints, ACM's own managed renewal is a better fit than Secrets Manager rotation; keep Secrets Manager for private keys that must be delivered to code.</li>\n<li><strong>Multi-consumer secrets.</strong> When thirty services share one database credential, rotation blast radius is thirty services, and the probability that <em>all</em> of them implement cache invalidation correctly approaches zero. The structural fix is not a cleverer rotation strategy — it is to stop sharing: issue a credential per consumer so each rotation risks one service, or move to <strong>IAM database authentication</strong> where the token is short-lived by design and there is nothing to rotate. If you cannot split, alternating-users is the minimum bar, because it converts a synchronous cutover into an interval-long migration.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Choosing a Rotation Interval</h4>\n<p style=\"line-height: 1.75\">Interval is a genuine trade-off, not a compliance checkbox. Shorter intervals reduce the useful lifetime of a leaked credential, which is the whole security argument. But each rotation event carries operational risk — a chance that a step fails, that a client with a broken cache falls over, that a privilege drift surfaces. So the expected number of incidents scales with rotation frequency, while the expected damage from a leak scales with interval length. The counterintuitive conclusion interviewers like is that <strong>an untested rotation configured at a long interval is more dangerous than one at a short interval</strong>. With a 365-day rotation, the machinery runs once a year: the Lambda's network path may have been broken by a subnet change eight months ago, the privileges may have drifted, nobody remembers the design, and the one execution happens at 2am against a system nobody has rehearsed. With a 7-day rotation, breakage surfaces within a week, in daylight, while the change that caused it is still fresh — and the path is exercised often enough that it stays working. Rotate frequently enough that rotation is boring; that is the real goal. Practically: pick an interval your compliance regime allows, set a rotation <code>Duration</code> window inside a low-traffic period, and never enable rotation on a schedule you have not first exercised with <code>--rotate-immediately</code> on a copy.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Design Scenario: Zero-Downtime Requirement</h4>\n<p style=\"line-height: 1.75\">A payments API with a 50ms p99 budget and a strict no-failed-requests SLO reads an Aurora PostgreSQL credential from Secrets Manager. Compliance mandates 30-day rotation. The team's first proposal is single-user rotation at 03:00; the objection is that the service is synchronous and a failed authentication on a payment is not a retryable inconvenience.</p>\n<p style=\"line-height: 1.75\">The design that satisfies both: use the AWS-provided <strong>alternating-users</strong> rotation function with a dedicated admin secret, so the outgoing credential stays valid for the full 30 days and no client ever holds a dead password. Grant all application privileges to a single <code>app_role</code> and make both users members, so privilege parity cannot drift; forbid runtime DDL from the application credential so PostgreSQL ownership never bites. On the client side, cache the secret with a <strong>TTL well under the rotation interval</strong> — an hour, not a day — so the switch is picked up long before the next rotation invalidates the old user, and still implement auth-error-triggered cache invalidation with a single bounded retry as a safety net. Configure the connection pool with a maximum connection lifetime shorter than the TTL so pooled connections actually recycle onto the new identity rather than lingering for days. Finally, set the rotation <code>Duration</code> to a two-hour low-traffic window, alarm on rotation failure, and rehearse the whole thing monthly in staging.
