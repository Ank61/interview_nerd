{"title":"Attribute-Based Access Control and Advanced Condition Keys","tags":["abac","condition-keys","tagging","multi-tenant"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Role-based access control to secrets works beautifully until about the two-hundredth secret. Then you notice the pattern: every new team produces a new policy, every new application produces a new statement, and the IAM policy for the platform role has grown past the character limit and nobody can say with confidence what it permits. Attribute-based access control is the structural fix. Instead of enumerating which principals may touch which resources, you write one policy that says \"a principal may access a secret when the principal's attributes match the secret's attributes,\" and then access is granted by tagging rather than by editing policy. Done properly, onboarding a new team becomes a tagging operation with no IAM change at all.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The mechanics</h4>\n<p style=\"line-height: 1.75\">ABAC has three moving parts. First, <strong>resources carry attributes</strong>: every secret is tagged with a small, mandatory set such as environment, team, application, and data classification. Second, <strong>principals carry attributes</strong>: an IAM role can have tags attached directly, or a session can carry <strong>session tags</strong> passed at <code>AssumeRole</code> time, or an identity provider can pass attributes into the session through the SAML or OIDC principal-tag attribute during federation. Session tags are the powerful form, because the attribute comes from the identity system rather than from IAM, so a user's team membership in the corporate directory drives access without any AWS-side provisioning. Session tags can be marked <strong>transitive</strong>, meaning they survive a subsequent role chain, which matters when a pipeline assumes one role and then another.</p>\n<p style=\"line-height: 1.75\">Third, the policy compares the two using <strong>policy variables</strong>. A policy variable is written as a dollar sign followed by an opening brace, the key name, and a closing brace, and it is substituted at evaluation time with the value from the request. For ABAC on secrets the canonical comparison puts <code>aws:ResourceTag/team</code> on the left of a <code>StringEquals</code> condition and the policy variable form of <code>aws:PrincipalTag/team</code> on the right, so the policy reads \"allow when the secret's team tag equals the caller's team tag.\" In the JSON you would write the right-hand side as a dollar sign, then a brace, then <code>aws:PrincipalTag/team</code>, then a closing brace; in this study file that literal sequence is shown with the HTML entity <code>&#36;</code> standing in for the dollar sign to keep the file parseable.</p>\n<p style=\"line-height: 1.75\">The four condition keys you must be able to distinguish:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>aws:ResourceTag/key.</strong> The tag on the resource being acted upon. Only meaningful for actions that operate on a specific resource; it is unavailable for list-style or create-style calls where no tagged resource exists yet.</li>\n<li><strong>aws:PrincipalTag/key.</strong> The tag on the caller, whether attached to the role or supplied as a session tag. This is the left-hand side of identity in ABAC.</li>\n<li><strong>aws:RequestTag/key.</strong> The tag value being supplied <em>in</em> the request, used on create and tag operations. This is how you force a correct tag at creation time.</li>\n<li><strong>aws:TagKeys.</strong> The set of tag keys present in the request, used with <code>ForAllValues</code> or <code>ForAnyValue</code> set operators to control <em>which</em> keys may be written or removed, independent of their values.</li>\n</ul>\n<p style=\"line-height: 1.75\">Secrets Manager also exposes a service-specific mirror, <code>secretsmanager:ResourceTag/key</code>, which behaves like the global key but is scoped to this service and is useful when you want a policy statement that cannot accidentally match another service's resources.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Tag integrity is the whole security model</h4>\n<p style=\"line-height: 1.75\">This is the point that separates a candidate who has read about ABAC from one who has operated it. If access is decided by tags, then <strong>the ability to write a tag is the ability to grant yourself access</strong>. A developer tagged with team equals payments who can call <code>TagResource</code> on a secret owned by the treasury team can simply retag that secret to team equals payments and read it. The ABAC policy will work exactly as designed and hand over the credential.</p>\n<p style=\"line-height: 1.75\">So an ABAC rollout is really a tag-governance rollout, with three mandatory controls:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Deny untagged creation.</strong> Use a <code>Null</code> condition on <code>aws:RequestTag/team</code> (and the other mandatory keys) to deny <code>CreateSecret</code> when the tag is absent, and a <code>StringEquals</code> condition tying the supplied value to the creator's own principal tag so a developer cannot create a secret already tagged for another team. Without this, an untagged secret exists in a limbo state that no ABAC statement matches — which fails closed for reads but leaves an orphan nobody can manage.</li>\n<li><strong>Deny tag modification of governance keys.</strong> An explicit <code>Deny</code> on <code>secretsmanager:TagResource</code> and <code>secretsmanager:UntagResource</code> when <code>aws:TagKeys</code> includes any of the governance keys, with an exception only for the security administration role. Use the <code>ForAnyValue</code> set operator so the deny fires if <em>any</em> protected key appears in the request. Explicit deny beats every allow, which is exactly the property you want.</li>\n<li><strong>Enforce with a permissions boundary.</strong> Both controls above can be undone by anyone who can edit IAM policies. A <strong>permissions boundary</strong> attached to every developer-creatable role caps the maximum permissions of anything they create, so a developer with IAM privileges cannot mint a role that escapes the tag rules. In a multi-account estate the same guarantees are reinforced with service control policies, which no account-level policy can override.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; It scales to any number of tenants with no provisioning, but its correctness rests entirely on the handler never setting the wrong tenant tag, so that tag-derivation code is security-critical and must be reviewed as such. <strong>Session policies</strong> tighten it further: when assuming the role, pass an inline session policy that intersects with the role's policy and names only the tenant's secret prefix, so even a bug in a downstream code path cannot reach another tenant. <strong>Separate roles per tenant</strong> is stronger but reintroduces provisioning per tenant and hits role-count limits in the thousands. <strong>Separate accounts per tenant</strong> is the strongest, closes the <code>ListSecrets</code> metadata leak entirely, and is what regulated or high-value tenants will ask for; it costs an account-vending pipeline. A common tiering is session-tag ABAC plus session policies for the long tail, dedicated accounts for enterprise tenants.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario: access control for 40 teams without 40 policies</h4>\n<p style=\"line-height: 1.75\">A platform account holds around 3,000 secrets for 40 teams across three environments, and the security team is drowning in policy review. Design: mandate four tags on every secret — environment, team, application, data-classification — enforced at creation by a deny statement using <code>Null</code> on <code>aws:RequestTag</code> for each key, plus a <code>StringEquals</code> tying the team value to the creator's own principal tag. Names follow environment slash team slash application slash purpose, so ARNs remain self-describing and a prefix-based backstop policy exists. Federated users arrive through the identity provider with team and environment passed as session tags sourced from directory group membership, so nobody provisions AWS-side attributes. One managed policy, attached to every application and human role, grants read actions on all secrets in the account subject to a condition requiring the secret's team tag to equal the principal's team tag and the secret's environment tag to equal the principal's environment tag; a second statement additionally requires access through the approved VPC endpoint via <code>aws:SourceVpce</code> for anything tagged confidential. Tag integrity is protected by an explicit deny on tag and untag operations whose <code>aws:TagKeys</code> include any governance key, exempting only the security administration role, and by a permissions boundary attached to every role a developer can create so they cannot mint a role that escapes the rules. Write access to production is not ABAC at all: it is a small named set of deployment roles, because ABAC is excellent for read scoping and dangerous as the only control on mutation. Rotation is locked down by restricting <code>secretsmanager:RotationLambdaARN</code> to the platform's approved rotation functions, closing the exfiltration-via-rotator path.
