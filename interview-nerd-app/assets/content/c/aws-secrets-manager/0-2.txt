Everything else — description, tags, rotation — can be added later. You can do this in the web console, from the command line, from code with the SDK, or from infrastructure-as-code.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Creating in the Console</h4>\n<p style=\"line-height: 1.75\">In the AWS Console you go to Secrets Manager, choose <em>Store a new secret</em>, and walk through four pages: pick the secret type and enter the value, give it a name and description and tags, configure rotation (or skip it), and review. The console shows the key-value pairs in a friendly editor and a <em>Plaintext</em> tab where you can see and paste the raw JSON — useful when you want to be certain of the exact structure.</p>\n<p style=\"line-height: 1.75\">The console is the right tool for learning and for genuine one-offs. For anything that has to exist in more than one environment, use the CLI or infrastructure-as-code, because a secret created by hand in the console exists nowhere in your change history and nobody will remember how it was configured six months from now.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Three Secret \"Types\" the Console Offers</h4>\n<p style=\"line-height: 1.75\">The first console page asks you to choose a type. This choice is not stored as some special field — it just changes which form fields you see and, importantly, which rotation options become available later.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Credentials for an Amazon RDS database (and similar supported databases).</strong> You type a username and password and then <em>pick your actual database instance from a dropdown</em>. The console fills in <code>engine</code>, <code>host</code>, <code>port</code>, and <code>dbname</code> for you from the real resource. This is the type to choose whenever it applies, because it produces exactly the JSON shape the AWS-managed rotation functions expect. The same treatment is offered for Amazon Redshift, Amazon DocumentDB, and Amazon Aurora.</li>\n<li><strong>Credentials for another database.</strong> For a database engine Secrets Manager understands the shape of but does not host — a MySQL, PostgreSQL, Oracle, SQL Server, or MongoDB server you run yourself on EC2 or on-premises. You type the host, port, and database name by hand. You can still use rotation, but you provide the connectivity details and the rotation function must be able to reach the host over the network.</li>\n<li><strong>Other type of secret.</strong> The catch-all: an API key, an OAuth client secret, an SSH key, a license key, or anything else. You enter either a set of arbitrary key-value pairs or a single plaintext blob. Rotation for these requires a <strong>custom rotation Lambda function</strong> that you write, because only you know how to change that credential on the other side.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Choosing the Encryption Key</h4>\n<p style=\"line-height: 1.75\">Every secret is encrypted with a key from <strong>AWS KMS</strong>, the Key Management Service. At creation you choose between two options, and the default is chosen for you if you say nothing:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>The AWS managed key</strong> (shown as <code>aws/secretsmanager</code>). Created automatically the first time you need it, free, and requires no setup. The downside is that you cannot attach your own key policy to it, which means you cannot use the key as a second, independent lock — and you cannot share the secret with another AWS account, because AWS managed keys cannot be used cross-account.</li>\n<li><strong>A customer managed key (CMK)</strong> that you create in KMS. Costs about 1 USD per month plus per-request charges, but you control its key policy, you can rotate the key itself, you can see KMS-level CloudTrail entries, and you can grant another account use of it. Required for cross-account secret sharing.</li>\n</ul>\n<p style=\"line-height: 1.75\">The practical consequence for beginners: when a customer managed key is used, a caller needs <strong>both</strong> <code>secretsmanager:GetSecretValue</code> <strong>and</strong> <code>kms:Decrypt</code> on that key. Forgetting the second one is the classic mystery AccessDenied. The full treatment of encryption is a separate topic; for creation, just know that the choice is made at create time via the <code>--kms-key-id</code> flag and can be changed later.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Creating with the CLI: create-secret</h4>\n<p style=\"line-height: 1.75\">The core command is <code>aws secretsmanager create-secret</code>. The flags you will actually use are <code>--name</code>, one of <code>--secret-string</code> or <code>--secret-binary</code>, and optionally <code>--description</code>, <code>--tags</code>, <code>--kms-key-id</code>, and <code>--client-request-token</code> (an idempotency token that prevents a retried call from creating a duplicate). The call returns the ARN, the name, and the <strong>version id</strong> of the first version, which is automatically labelled AWSCURRENT.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Never Pass a Secret as a Plain Command-Line Argument</h4>\n<p style=\"line-height: 1.75\">This is the most important operational habit in this topic. Typing <code>--secret-string '{\"password\":\"hunter2\"}'</code> directly into a shell leaks the value in at least three ways:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Shell history.</strong> The whole command lands in <code>~/.bash_history</code> or <code>~/.zsh_history</code> in plaintext, often synced to a dotfiles repo or a backup.</li>\n<li><strong>Process listings.</strong> While the command runs, anyone on the machine who runs <code>ps aux</code> sees the full argument list, password included. On a shared bastion host or a CI runner, that is a real exposure.</li>\n<li><strong>CI/CD logs.</strong> Build systems commonly echo the command they are about to run, so the value ends up in a build log that is retained and broadly readable.</li>\n</ul>\n<p style=\"line-height: 1.75\">The fix is to use a <strong>file reference</strong>: write the JSON to a file with restrictive permissions and pass <code>--secret-string file://creds.json</code>. The AWS CLI reads the file itself, so the value never appears as an argument. Delete the file afterwards. A related habit: prefixing a command with a space stops most shells recording it in history, but that does nothing about the process listing, so the file approach is the real answer.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Let AWS Generate the Password: get-random-password</h4>\n<p style=\"line-height: 1.75\">Do not invent passwords yourself, and do not paste one from a blog post. Secrets Manager exposes <code>get-random-password</code>, which generates a cryptographically strong random string server-side. Useful flags: <code>--password-length</code>, <code>--exclude-punctuation</code>, <code>--exclude-characters</code> (important, because many database engines reject certain symbols — Amazon RDS disallows <code>/</code>, <code>@</code>, <code>\"</code>, and spaces in master passwords), <code>--require-each-included-type</code>, and switches to exclude numbers, uppercase, or lowercase. The AWS-managed rotation functions call this same API internally, so using it keeps your manually-created secrets consistent with rotated ones.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Storing Multi-Field JSON Correctly</h4>\n<p style=\"line-height: 1.75\">Because SecretString is a single string that happens to contain JSON, escaping bites people constantly. Two rules keep you out of trouble. First, <strong>put the JSON in a file</strong> and reference it — no shell escaping involved at all, and the file is valid JSON you can lint. Second, if you must inline it, <strong>wrap it in single quotes</strong> in bash/zsh so the shell does not interpret the double quotes, and remember that a password containing a single quote will still break the line. On Windows PowerShell the quoting rules differ again, which is another argument for the file approach everywhere.</p>\n<p style=\"line-height: 1.75\">Validate before you store.
