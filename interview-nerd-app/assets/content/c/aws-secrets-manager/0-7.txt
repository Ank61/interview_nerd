{"title":"Access Control — IAM Policies, Resource Policies, and Cross-Account Access","tags":["iam","resource-policy","least-privilege","cross-account"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Putting a password into Secrets Manager only helps if fewer people and systems can read it than could read the config file it replaced. That is entirely a question of access control. AWS answers it with <strong>IAM</strong> — Identity and Access Management, the service that decides who is allowed to call which API on which resource. Everything below is IAM applied to secrets, and it is the area where beginners generate the most support tickets, so it is worth being methodical.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Two directions of permission</h4>\n<p style=\"line-height: 1.75\">A <strong>principal</strong> is whoever is making the call — an IAM user, or much more commonly an IAM <strong>role</strong>, which is a set of permissions that a service like EC2 or Lambda temporarily assumes. Permission for a principal to read a secret can be written from either end.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>An identity-based policy</strong> is attached to the principal. It says, from the identity's side, \"this role may call GetSecretValue on that secret ARN.\" This is the normal, everyday way to grant access within one account.</li>\n<li><strong>A resource-based policy</strong> — for Secrets Manager, called a <strong>secret policy</strong> — is attached to the secret itself. It says, from the resource's side, \"these principals may read me.\" You attach it with <code>put-resource-policy</code>.</li>\n</ul>\n<p style=\"line-height: 1.75\">An <strong>ARN</strong> (Amazon Resource Name) is the globally unique identifier of an AWS resource, like <code>arn:aws:secretsmanager:us-east-1:111122223333:secret:prod/myapp/db-a1b2c3</code>. Policies use ARNs to name exactly what they are talking about.</p>\n<p style=\"line-height: 1.75\">When do you use which? Identity-based policies are the default: they are easier to manage centrally and they answer \"what can this role do?\" in one place. Reach for a resource policy in three situations — <strong>cross-account access</strong> (the other account's principals cannot be named in your identity policies), <strong>attaching a guardrail to the secret itself</strong> so it travels with the resource regardless of who writes identity policies, and <strong>explicitly denying</strong> everyone except an allowed set, which is a strong protection for a high-value secret.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">How the two combine</h4>\n<p style=\"line-height: 1.75\">The evaluation rule is simpler than it sounds. Within a single account, access is allowed if it is permitted by <em>either</em> the identity policy or the resource policy, and is not <strong>explicitly denied</strong> anywhere. An explicit <code>Deny</code> always wins over any Allow, in any policy, always. Anything not allowed at all is denied by default — IAM starts from \"no\".</p>\n<p style=\"line-height: 1.75\">Cross-account is the exception worth memorising: when the principal lives in a different account from the secret, you need an Allow in <strong>both</strong> — the secret's resource policy must allow the external principal, and that principal's own account must grant it permission too. Either side alone is not enough. Other layers can also deny: a <strong>service control policy</strong> (an organisation-wide guardrail) and a <strong>permissions boundary</strong> can each cap what is possible, no matter what your policies say.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The actions you should know</h4>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Action</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Read or write</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">What it does</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">GetSecretValue</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Read (sensitive)</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Returns the actual secret value. A monitoring tool that checks rotation freshness needs Describe, not Get. And note that <code>TagResource</code> is a security permission, not a housekeeping one: if a policy says \"allow access to secrets tagged Environment=dev\", then anyone who can retag a production secret can grant themselves access to it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Least privilege and the ARN suffix trick</h4>\n<p style=\"line-height: 1.75\"><strong>Least privilege</strong> means giving a principal exactly the permissions it needs and nothing more — this role, this action, this secret. The opposite, which you will see in a lot of real accounts, is <code>\"Action\": \"secretsmanager:*\", \"Resource\": \"*\"</code>, which lets a single compromised workload read every secret in the account.</p>\n<p style=\"line-height: 1.75\">Scoping to a specific secret has one practical wrinkle. Secrets Manager appends a random six-character suffix to every secret ARN, so a secret named <code>prod/myapp/db</code> gets an ARN ending <code>...:secret:prod/myapp/db-a1b2c3</code>. You usually do not want to hardcode that suffix — it changes if the secret is recreated, and it is a nuisance in infrastructure-as-code. The convention is to end the resource pattern with a wildcard:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>One specific secret.</strong> <code>arn:aws:secretsmanager:us-east-1:111122223333:secret:prod/myapp/db-*</code> — the trailing <code>-*</code> absorbs the random suffix.</li>\n<li><strong>A group of secrets by name prefix.</strong> <code>arn:aws:secretsmanager:us-east-1:111122223333:secret:prod/myapp/*</code> grants access to every secret whose name starts with that path. This is why naming secrets hierarchically, like <code>environment/application/purpose</code>, pays off — the naming convention becomes your permission boundary.</li>\n</ul>\n<p style=\"line-height: 1.75\">Be aware of the small risk in <code>db-*</code>: it would also match a secret literally named <code>db-something</code>. In high-stakes cases, pin the full ARN including the suffix and let your IaC read it from the created resource.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Condition keys worth knowing early</h4>\n<p style=\"line-height: 1.75\">A <strong>condition</strong> is an extra test that must pass before an Allow applies. A few are genuinely useful at beginner level.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Restrict by tag.</strong> <code>secretsmanager:ResourceTag/Environment</code> lets you write one policy such as \"this role may read any secret tagged Environment=prod\", which scales better than listing ARNs. Pair it with tight control over <code>TagResource</code>.</li>\n<li><strong>Restrict by VPC or VPC endpoint.</strong> <code>aws:SourceVpce</code> or <code>aws:SourceVpc</code> means the call must arrive through your private endpoint. Even a leaked credential is then useless from the public internet — a strong, simple control.</li>\n<li><strong>Require encryption in transit.</strong> <code>aws:SecureTransport</code> set to true, usually written as a Deny when it is false, makes the intent explicit for auditors.</li>\n<li><strong>Restrict which principals.</strong> <code>aws:PrincipalOrgID</code> limits access to accounts inside your AWS Organization, which is a neat guardrail on a resource policy that would otherwise be broad.</li>\n<li><strong>Restrict version stage.</strong> <code>secretsmanager:VersionStage</code> can limit a caller to AWSCURRENT, so it cannot fish for pending or previous values.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cross-account access, step by step</h4>\n<p style=\"line-height: 1.75\">A very common architecture keeps shared secrets in one account and lets workloads in other accounts read them. Those are long-lived credentials: they do not expire, they get copied into config files and CI variables, and if one leaks it stays valid until a human notices and revokes it. That is the exact problem Secrets Manager exists to solve, so solving it by introducing another permanent credential is self-defeating.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>EC2:</strong> attach an instance profile; the SDK picks up temporary credentials automatically (use IMDSv2).</li>\n<li><strong>Lambda:</strong> the function's execution role is already there — just add the secret permissions.</li>\n<li><strong>ECS:</strong> use a task role, which scopes permission to the task rather than the whole host.</li>\n<li><strong>EKS:</strong> use IAM roles for service accounts (IRSA) or EKS Pod Identity so each pod gets its own scoped role.</li>\n<li><strong>Outside AWS:</strong> use IAM Roles Anywhere or an OIDC federation (for example GitHub Actions) rather than storing a static key.</li>\n</ul>\n<p style=\"line-height: 1.75\">In every case the SDK receives short-lived, automatically rotated credentials, and there is nothing durable for an attacker to steal from disk.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Troubleshooting AccessDenied, in order</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>1.
