If it lives in <strong>AWS Secrets Manager</strong>, it has a precise one, with a timestamp and an identity. This topic covers how to get that audit trail, how to alert on it, and what the whole thing costs.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">AWS CloudTrail: the record of every API call</h4>\n<p style=\"line-height: 1.75\"><strong>AWS CloudTrail</strong> is the AWS service that records every API call made in your account — who made it, what they called, on which resource, from which IP address, at what time, and whether it succeeded. Effectively everything in AWS happens through an API call, including clicks in the console, so CloudTrail is a near-complete activity log.</p>\n<p style=\"line-height: 1.75\">CloudTrail keeps the last 90 days of <strong>management events</strong> in Event history at no charge, and you create a <strong>trail</strong> to deliver events to an Amazon S3 bucket for longer retention, or to <strong>CloudWatch Logs</strong> so you can query and alarm on them.</p>\n<p style=\"line-height: 1.75\">For Secrets Manager, CloudTrail records events including:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>GetSecretValue</strong> — someone retrieved a secret. The single most security-relevant event: which identity read which secret, and when.</li>\n<li><strong>CreateSecret, UpdateSecret, PutSecretValue</strong> — a secret was created or its value changed.</li>\n<li><strong>RotateSecret</strong> — a rotation was started, whether by schedule or by hand.</li>\n<li><strong>DeleteSecret, RestoreSecret</strong> — a secret was scheduled for deletion or recovered.</li>\n<li><strong>PutResourcePolicy, DeleteResourcePolicy</strong> — the resource-based policy attached to the secret changed, which is how cross-account access is granted. A change here can silently widen who can read a secret.</li>\n<li><strong>TagResource, ReplicateSecretToRegions, StopReplicationToReplica</strong> — metadata and replication changes.</li>\n</ul>\n<p style=\"line-height: 1.75\">Two details worth knowing precisely. First, the event record contains the secret's ARN and the caller identity, but <strong>never the secret value</strong> — CloudTrail does not leak what it audits. Second, Secrets Manager API calls are recorded as <strong>management events</strong>, which means GetSecretValue is captured by default without you enabling data events (unlike, say, S3 object reads).</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Alerting on the events that actually matter</h4>\n<p style=\"line-height: 1.75\">A log nobody reads is not a control. The point of the audit trail is to notice the handful of events that indicate something is wrong. The usual list:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Deletion.</strong> A DeleteSecret on a production secret should page someone. It is both a common mistake and a step in a destructive attack.</li>\n<li><strong>Resource policy changes.</strong> PutResourcePolicy is how a secret becomes readable from another AWS account. An unexpected one is a serious signal.</li>\n<li><strong>Unusual retrieval volume.</strong> A service that normally reads a secret twice an hour suddenly reading it ten thousand times suggests either a broken cache (expensive) or credential harvesting (worse).</li>\n<li><strong>Retrieval by an unexpected principal.</strong> A <strong>principal</strong> is the identity making the call — an IAM role, user or service. If the payments database secret is only ever read by the payments task role, a read by a developer's role or a CI role deserves a look.</li>\n<li><strong>Access denied bursts.</strong> Repeated AccessDenied on GetSecretValue is either a misconfigured deployment or someone probing what they can reach.</li>\n</ul>\n<p style=\"line-height: 1.75\">The mechanism is usually a <strong>metric filter</strong> on a CloudWatch log group receiving CloudTrail events — a pattern that increments a custom metric whenever a matching event appears — plus a CloudWatch alarm on that metric publishing to an <strong>Amazon SNS</strong> topic (SNS is the AWS pub/sub notification service that fans a message out to email, Slack webhooks, or PagerDuty).</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">CloudWatch metrics and alarms — especially rotation failures</h4>\n<p style=\"line-height: 1.75\"><strong>Amazon CloudWatch</strong> collects numeric metrics and lets you alarm when one crosses a threshold. Rotation runs in the background on a schedule. Your application keeps working, because the old password is still valid. The secret simply stops getting newer.
