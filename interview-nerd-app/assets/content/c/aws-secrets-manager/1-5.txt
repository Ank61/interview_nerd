style=\"line-height: 1.75\">Two details make this exact. First, in a Secrets Manager resource policy the <code>Resource</code> element is written as <code>\"*\"</code>, meaning \"this secret,\" because the policy is already attached to the secret. Second, the consuming principal calls the producer account's API directly using its own credentials and the full secret ARN; there is no copy of the secret in the consumer account, and the SDK must be pointed at the producer's Region. The consumer can also assume a role in the producer account instead, which changes the model entirely: then the call is same-account from Secrets Manager's point of view, no resource policy is needed, and the trust policy of the assumed role becomes the control point.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Debugging order when it fails</h4>\n<p style=\"line-height: 1.75\">The error messages are deliberately vague, so work the layers in a fixed order rather than guessing:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>1. Is the identity policy right in the consumer account?</strong> Check with the IAM policy simulator or by attempting the call with a temporarily broad policy. A missing allow here fails before any cross-account evaluation happens.</li>\n<li><strong>2. Does the resource policy name the exact principal?</strong> Role ARNs, not assumed-role session ARNs. If the policy names a role and the caller is a session of that role, it matches; if the policy names a session ARN, it will not match reliably. Use <code>ValidateResourcePolicy</code> and <code>GetResourcePolicy</code> to read back what is actually attached.</li>\n<li><strong>3. Is the secret encrypted with a customer managed key?</strong> If <code>DescribeSecret</code> shows the AWS managed key, stop: cross-account is impossible. Re-encrypt under a CMK first.</li>\n<li><strong>4. Does the key policy allow the external principal <code>kms:Decrypt</code>?</strong> This is the most common remaining failure and it produces an AccessDenied that mentions KMS only sometimes.</li>\n<li><strong>5. Do conditions exclude the caller?</strong> An organization ID condition, a source VPC endpoint condition, or an encryption context condition will silently deny a caller that satisfies everything else.</li>\n<li><strong>6. Is there an SCP in either account denying the action?</strong> SCPs deny before any policy is consulted and are invisible from inside the account without organization access.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; Secrets that are <strong>intrinsically shared</strong> — a single database credential consumed by many workloads, a third-party API key the company holds one of, a signing key — belong in a hub owned by the team accountable for them, because there is genuinely one source of truth and a scattered copy is worse. Secrets that are <strong>intrinsically local</strong> — a service's own database password, a per-workload token — belong in the workload account, because centralizing them adds a cross-account dependency and a bottleneck with no isolation benefit. A mature platform runs both: a small, heavily governed hub for shared credentials, and per-account secrets for everything else, with the same Terraform module and tagging standard applied in both places so auditability does not depend on location.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Organizations-aware patterns</h4>\n<p style=\"line-height: 1.75\">Enumerating twelve account IDs in a resource policy is workable; enumerating two hundred is not, and every new account means a policy change in the hub. The <code>aws:PrincipalOrgID</code> condition key solves this by matching any principal whose account belongs to your organization, so one statement covers the whole estate and new accounts are covered automatically. Its sibling <code>aws:PrincipalOrgPaths</code> lets you scope to a specific organizational unit, which is how you say \"any account in the Production OU\" without listing them. The important caveat is that an organization-wide grant is broad: combine it with a second condition narrowing the principal, such as a role-name pattern via <code>aws:PrincipalArn</code> with a wildcard, or a tag condition, otherwise every role in every account in the organization can read the secret.</p>\n<p style=\"line-height: 1.75\">Service control policies work the other direction, as guardrails that no account-level policy can override. Two are worth naming. First, deny <code>secretsmanager:PutResourcePolicy</code> and <code>secretsmanager:DeleteResourcePolicy</code> for everyone except a designated platform role, so a team cannot unilaterally expose a secret outside the organization. Secrets Manager also supports a <code>BlockPublicPolicy</code> parameter on <code>PutResourcePolicy</code> that refuses a policy granting broad public access, and an SCP can require it. Second, a data-perimeter SCP that denies <code>secretsmanager:GetSecretValue</code> when <code>aws:ResourceOrgID</code> does not match your organization, which stops a compromised workload from reading a secret in an attacker-controlled account — a real exfiltration-channel and command-and-control vector. On delegated administration: Secrets Manager itself has no delegated administrator concept, so the equivalent pattern is a dedicated security or shared-services account that owns the hub, combined with delegated administration of IAM Access Analyzer, which will flag any secret or KMS key whose policy grants access outside the organization. That analyzer finding is the control that catches a mistaken resource policy before an auditor does.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Confused deputy risk</h4>\n<p style=\"line-height: 1.75\">The confused-deputy problem is a trusted intermediary being tricked into using its privileges for someone else. In Secrets Manager it appears in two forms. When an AWS service accesses a secret on someone's behalf, the mitigations are <code>aws:SourceAccount</code> and <code>aws:SourceArn</code> conditions in the resource or key policy, so the service principal is only trusted when it is acting for a resource you actually own. When you grant a third-party vendor a role in your account, the mitigation is <code>sts:ExternalId</code> in the role's trust policy: a value you generate and share privately, so a vendor who holds many customers' role ARNs cannot be induced by another customer to assume yours. For internal multi-account work, <code>aws:PrincipalOrgID</code> serves the same purpose by ensuring the caller is inside your trust boundary at all, and <code>aws:PrincipalArn</code> pins it to a specific expected role.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cross-account rotation and auditing</h4>\n<p style=\"line-height: 1.75\">Rotation is configured on the secret, so the rotation function belongs to the account that owns the secret and must be in the same Region as the secret. That has a consequence people miss: if the hub account owns a credential for a database running in a workload account, the hub's rotation Lambda must reach that database and change the password there. Typically the Lambda assumes a role in the workload account to perform the credential change, or reaches the database over a peered network path, and its execution role needs <code>secretsmanager:GetSecretValue</code>, <code>PutSecretValue</code>, <code>UpdateSecretVersionStage</code> and <code>DescribeSecret</code> on the secret, plus <code>kms:Decrypt</code> and <code>kms:GenerateDataKey</code> on the key, plus <code>sts:AssumeRole</code> on the target role. Consumers in other accounts do nothing during rotation except tolerate the change, which is exactly why the alternating-users strategy and client-side retry-on-auth-failure matter more in a shared-secret design than in a single-owner one: a rotation now affects twelve teams at once.</p>\n<p style=\"line-height: 1.75\">For auditing, cross-account API calls produce CloudTrail events in <strong>both</strong> accounts. The consumer account's trail records that its role called <code>GetSecretValue</code> against a resource in another account; the producer account's trail records the same call arriving from an external principal, and that is the authoritative record of who read the secret. The KMS <code>Decrypt</code> event lands in the account that owns the key, with the secret ARN visible in the encryption context. So a complete \"who read this secret\" answer requires the producer trail for Secrets Manager plus the key owner's trail for KMS, which is another argument for an organization trail aggregating into a security account rather than per-account trails.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The copy-the-value anti-pattern</h4>\n<p style=\"line-height: 1.75\">A frequent shortcut is a pipeline that reads the secret in the hub and writes a copy into each consumer account. It is appealing because it removes the cross-account permission puzzle. It is wrong for four reasons: rotation now has to fan out to N copies and any failure leaves accounts on a stale credential with no signal; the plaintext transits a build system, which becomes the most privileged and least monitored component in the architecture; revocation no longer works, because deleting the hub secret does nothing to the copies; and the audit trail is destroyed, since reads now appear as local reads in each account with no link back to the owner. Native cross-account access with a resource policy and a shared CMK preserves one source of truth, one rotation event, one revocation point, and a complete trail. Replication (the built-in multi-Region feature) is a different thing and is fine, because it stays within one account's control plane and is driven by Secrets Manager itself.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario: one database credential, twelve workload accounts</h4>\n<p style=\"line-height: 1.75\">The platform team owns an Aurora cluster used by twelve product teams in twelve accounts, and must expose one read-only application credential with least privilege and clean revocation. Design: the secret lives once in the platform account, encrypted with a customer managed key created for shared credentials. Rather than enumerate twelve account IDs, the resource policy uses a single statement with <code>aws:PrincipalOrgID</code> equal to the organization ID, narrowed by a <code>aws:PrincipalArn</code> wildcard matching the standardized role name each account provisions, for example any role path ending in the agreed consumer role name. That way onboarding account thirteen requires zero change in the platform account: the team creates the standard role, and access works. The same pair of conditions goes on the KMS key policy for <code>kms:Decrypt</code>, because the key is the layer that actually enforces confidentiality. Each consumer account attaches an identity policy allowing <code>GetSecretValue</code> on the exact secret ARN and <code>kms:Decrypt</code> on the key ARN with a <code>kms:ViaService</code> condition. Guardrails: an SCP denies <code>PutResourcePolicy</code> outside the platform role, IAM Access Analyzer with delegated administration alerts on any external grant, and an organization CloudTrail aggregates both sides. Rotation runs in the platform account on a thirty-day schedule using the alternating-users strategy so there is never a window with no valid credential, and the onboarding contract requires consumers to use the caching client with refresh-on-auth-failure. Revocation of a single team is a one-line change: tighten the <code>aws:PrincipalArn</code> condition or add a deny statement naming that account, and the access stops at the next uncached read, with the KMS key policy as a second, independent kill switch if you need it to stop immediately and estate-wide.</p>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"Cross-account sharing needs three things, not one: a resource policy on the secret naming the external principal, an identity policy in the consuming account, and — the piece people forget — a customer managed KMS key whose key policy lets that principal decrypt, because the AWS managed key can't be shared at all.
