The other half lives in the application, and it is where rotation actually breaks. The tension is unavoidable: applications <strong>must</strong> cache secrets, because calling <code>GetSecretValue</code> on every request adds a network round trip to a hot path, costs money per call, and will hit the Secrets Manager API rate limit under load. But a cache is <em>by definition</em> a copy of a value that can become wrong — and rotation is the event that makes it wrong. Every resilient design is therefore about <strong>bounding how long a stale credential can persist and detecting staleness the moment it matters</strong>.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why You Cannot Simply Fetch Every Time</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Latency.</strong> A <code>GetSecretValue</code> call is tens of milliseconds including TLS and a KMS decrypt on the service side. On a p99-sensitive path that is a material fraction of the budget, added to every single request.</li>\n<li><strong>Cost.</strong> Secrets Manager charges per 10,000 API calls. A service at 1,000 requests per second fetching per request is on the order of 2.6 billion calls a month — an absurd bill for a value that changes once a month.</li>\n<li><strong>Throttling.</strong> <code>GetSecretValue</code> has an account-and-region request-rate quota. A fleet that fetches per request will hit it, and the failure mode is <code>ThrottlingException</code> across every service at once — you have coupled your entire estate's availability to one API's rate limit.</li>\n<li><strong>Blast radius.</strong> If Secrets Manager or its regional endpoint has a bad minute and you fetch per request, your service is down for that minute. With a cache, you ride through it.</li>\n</ul>\n<p style=\"line-height: 1.75\">So caching is correct. The design question is not <em>whether</em> to cache but <strong>how staleness is bounded and how it is detected</strong>.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Canonical Resilient Pattern</h4>\n<p style=\"line-height: 1.75\">There are two independent mechanisms, and a correct implementation has <strong>both</strong>. The first is a <strong>TTL</strong>, which bounds staleness proactively: after N minutes the cached value is discarded and re-fetched regardless of whether anything has gone wrong. The second is <strong>failure-triggered invalidation</strong>, which reacts: when an operation fails with an <em>authentication</em> error specifically, the cache is invalidated, the secret is re-fetched, and the operation is retried exactly once. TTL alone means up to a full TTL of hard failures after rotation. Invalidation alone means a credential that rotated while the service was idle is only discovered by a user-facing error. Together, the TTL keeps normal operation correct and the invalidation path handles the rotation moment.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">request\n   <i class=o>|</i>\n   v\nsecret <i class=o>=</i> cache.get()            <i class=c>-- TTL expired? fetch, store, continue</i>\n   <i class=o>|</i>\n   v\ndo_work(secret) <i class=c>---- success ---&gt; done</i>\n   <i class=o>|</i>\n   <i class=o>|</i> AuthenticationError  (<i class=k>NOT</i>: timeout, DNS, connection refused, <i class=n>5</i>xx)\n   v\ncache.invalidate()              <i class=c>-- force a real GetSecretValue</i>\nsecret <i class=o>=</i> cache.get()\n   <i class=o>|</i>\n   v\ndo_work(secret) <i class=c>---- success ---&gt; done</i>\n   <i class=o>|</i>\n   <i class=o>|</i> still AuthenticationError\n   v\nFAIL LOUD <i class=o>+</i> alarm               <i class=c>-- do NOT loop: the credential is genuinely wrong</i>\n\nRetry budget: exactly <i class=k>one</i> refresh<i class=o>-</i><i class=k>and</i><i class=o>-</i>retry <i class=k>per</i> operation, <i class=k>with</i> jitter, plus a\ncircuit breaker so N consecutive auth failures stop calling GetSecretValue <i class=k>at</i> all.</code></pre></div>\n<p style=\"line-height: 1.75\">Three details make or break this. <strong>Distinguish the error class.</strong> Invalidating the cache on any failure turns a database outage into a Secrets Manager stampede: every request in a 5,000-request-per-second service fails, invalidates, and calls <code>GetSecretValue</code>, and now you are throttled on top of being down. Under alternating-users the old credential survives one full interval, so a TTL of an hour against a 30-day rotation gives an enormous margin. Under single-user the TTL bounds the length of the outage window, so shorter is better and the failure-triggered invalidation path is doing most of the real work. Add <strong>jitter</strong> to expiry so a fleet that started together does not re-fetch in lockstep, and refresh <em>proactively</em> just before expiry rather than lazily on the first request after it, so no user request ever pays the fetch latency.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Connection Pools: Why Rotation Bugs Surface Hours Later</h4>\n<p style=\"line-height: 1.75\">This is the detail that separates a senior answer from a junior one. In virtually every database protocol, <strong>authentication happens once, at connect time</strong>. Once a connection is established and authenticated, changing the user's password in the database does <em>not</em> terminate it or invalidate it — the existing session keeps working indefinitely. A connection pool therefore <strong>masks rotation completely</strong>: after a rotation, a service with a warm pool of 20 connections continues serving traffic with zero errors, because it never needs to authenticate again.</p>\n<p style=\"line-height: 1.75\">The failure appears only when the pool opens a <strong>new</strong> connection, and that happens at unpredictable times: when an idle connection is reaped by the pool's idle timeout, when the database closes one server-side, when traffic spikes and the pool grows toward its maximum, when a network blip kills some connections, or when a new task is scheduled during scale-out. This is why rotation problems are so maddening — the symptom lands minutes or hours after the rotation, often on <strong>only some hosts</strong> (the ones that happened to open a connection), often only under load, and it is essentially impossible to reproduce on demand. Engineers correlate it with the traffic spike rather than the rotation, and chase the wrong cause for hours.</p>\n<p style=\"line-height: 1.75\">The mitigations are all about making connection turnover <strong>fast and predictable</strong> rather than rare and random. Set a <strong>maximum connection lifetime</strong> (HikariCP <code>maxLifetime</code>, SQLAlchemy <code>pool_recycle</code>, pgBouncer <code>server_lifetime</code>, node-postgres <code>maxLifetimeSeconds</code>) shorter than the secret cache TTL, so connections are deliberately recycled and re-authenticate with fresh credentials on a known cadence instead of living for days. Make sure the pool's <strong>connection factory reads the credential from the cache at connect time</strong>, not from a value captured once when the pool object was constructed — this is an extremely common bug, where the pool was handed a password string at startup and will use that same string forever no matter how good your caching layer is. Use the pool's connection-validation hook so broken connections are detected and replaced rather than handed to application code. And treat a pool-level authentication failure as the trigger for cache invalidation plus a pool reset, so the whole pool re-authenticates rather than failing one connection at a time.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Ready-Made Options</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>AWS Secrets Manager caching libraries.</strong> Available for Java, Python, .NET, Go and JavaScript. They implement in-memory caching with a configurable TTL and maximum cache size, handle version-stage-aware lookups, and give you a <code>refresh_now</code>-style method to force invalidation from your auth-error handler. Use them rather than writing your own — the subtle parts (single-flight, thread safety, stage handling) are already done.</li>\n<li><strong>AWS Parameters and Secrets Lambda Extension.</strong> A Lambda layer that runs a local HTTP server on <code>localhost:2773</code> inside the execution environment. Your function makes a plain HTTP GET to <code>/secretsmanager/get?secretId=...</code> with the <code>X-Aws-Parameters-Secrets-Token</code> header set to the function's session token, and the extension serves from its cache or calls the API. It is configured with environment variables such as <code>SECRETS_MANAGER_TTL</code> (seconds, with 300 the default and 0 disabling caching), <code>PARAMETERS_SECRETS_EXTENSION_CACHE_SIZE</code> and <code>PARAMETERS_SECRETS_EXTENSION_HTTP_PORT</code>. The critical property to understand: <strong>each execution environment has its own cache</strong>. Caching is per-sandbox, not global, so a function with 200 concurrent environments makes up to 200 independent fetches, and a cold start always pays the full call. It removes SDK boilerplate and reduces calls dramatically for warm, low-concurrency functions; it does not give you a shared fleet-wide cache.</li>\n<li><strong>Sidecar and agent patterns in containers.</strong> In ECS or EKS, a sidecar container or a node-level agent fetches and refreshes secrets and exposes them to the app over a shared volume, a loopback endpoint, or projected files — the <strong>Secrets Store CSI Driver with the AWS provider</strong> mounts secrets as files and, with rotation reconciliation enabled, updates them in place on a poll interval. The trap is that a file being updated is useless if the application read it once at startup; the app must either re-read the file per use or watch it for changes (inotify) and reload. ECS task definition <code>secrets</code> injection has the same issue in a stronger form: it resolves the secret into an environment variable at <strong>task start only</strong>, so a rotated secret is never picked up until the task is replaced.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Boot-Time-Only Anti-Pattern</h4>\n<p style=\"line-height: 1.75\">The worst pattern is a long-lived process that reads the secret once at startup — into a module-level constant, an environment variable, or a config object — and never again. It is extremely common because it is the simplest thing that works, and because in testing it works perfectly. Its failure mode is that the process holds a credential that becomes wrong at a time nobody controls, and the only remedy is a restart. With alternating-users rotation it survives one interval and then breaks; with single-user it breaks at the first rotation. Environment variables are the worst version, because they are captured at exec time and are literally immutable for the process's life, and because they are visible to anything that can read <code>/proc</code> or inspect the container. If a process genuinely cannot re-read a secret, then it must at minimum be <strong>restarted more frequently than the rotation interval</strong> — and you should recognise that as a workaround, not a design.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Debugging Scenario: Errors Hours After a Successful Rotation, on Some Hosts</h4>\n<p style=\"line-height: 1.75\">A rotation completes cleanly at 02:00 — <code>RotationSucceeded</code>, <code>AWSCURRENT</code> moved, no Lambda errors. At 09:40 a service begins throwing <code>password authentication failed for user app_user</code>. It is intermittent, affects roughly a third of the hosts, and the error rate climbs with traffic.</p>\n<p style=\"line-height: 1.75\"><strong>Read the shape of the evidence first.</strong> The seven-hour delay and the partial host coverage are the diagnosis, not a distraction. They mean the credential was already wrong at 02:00 and the pool was hiding it: hosts with warm, long-lived connections never re-authenticated, so they were fine. At 09:40 traffic rose, pools grew past their warm size and opened new connections, and those new connections authenticated with whatever the application believed the password to be. Only the hosts that scaled or reaped connections are affected, and the error rate tracks traffic because it tracks new-connection rate.</p>\n<p style=\"line-height: 1.75\"><strong>Confirm, then localise.</strong> Fetch <code>AWSCURRENT</code> and authenticate manually — it works, so Secrets Manager and the database are correct and the bug is entirely client-side. Now the question is why the application is presenting an old value. Check the three usual causes in order: (1) the secret was injected as an <strong>environment variable</strong> at task start, so the process is structurally incapable of picking up a new value; (2) the cache <strong>TTL is longer than you think</strong> or a bug means expiry is never evaluated for a long-lived singleton; (3) most likely, the <strong>connection pool captured the password string once at construction</strong> and its connection factory never consults the cache, so even a perfectly working cache layer changes nothing. A quick discriminator: restart one affected host. If it recovers permanently, the value was captured at boot (cause 1 or 3); if it recovers and then fails again after the next rotation, the invalidation path is missing.</p>\n<p style=\"line-height: 1.75\"><strong>Fix and prevent.</strong> Immediate mitigation is a rolling restart to pick up the current value. The real fix is to make the pool's connection factory call the cache on every new connection, add a <code>maxLifetime</code> shorter than the cache TTL so connections recycle on a known cadence, and implement auth-error-triggered invalidation with a single bounded retry and a pool reset. To prevent recurrence, make rotation a <strong>tested path</strong>: run a rotation in staging under synthetic load and assert the error count is what you expect, add a metric for cache refreshes and for auth-failure-triggered invalidations so you can see the mechanism working, and alarm on authentication errors specifically rather than burying them in a generic 5xx rate.
