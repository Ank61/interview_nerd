{"title":"Automatic Rotation — How Secrets Manager Changes Credentials For You","tags":["rotation","lambda","rds","alternating-users"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Think about the database password you set when you created the database. If nobody ever changes it, that one string is a permanent key to your data. If it ever leaks — pasted into a Slack message, committed to Git, printed in a log file, copied by someone who left the company — it stays valid forever. <strong>Rotation</strong> simply means changing a credential to a new value on a regular schedule, so that an old leaked value stops working. AWS Secrets Manager is unusual among secret stores because it does not just hold the value; it can go change it for you in the system that owns it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why rotation matters</h4>\n<p style=\"line-height: 1.75\">There are three separate reasons teams care about rotation, and interviewers like to hear all three rather than just the first one.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>A leaked credential that never changes is valid forever.</strong> Rotation puts a clock on the damage. If you rotate every 30 days, a password stolen today is useless within a month, even if you never discover the leak.</li>\n<li><strong>Compliance regimes require it.</strong> Standards such as PCI DSS, HIPAA-aligned controls, SOC 2 and most internal security policies ask for periodic credential rotation and for evidence that it happens. Automated rotation with a timestamped history is that evidence.</li>\n<li><strong>Manual rotation is error-prone, so teams simply do not do it.</strong> Doing it by hand means changing the password on the database, then updating every application config, every CI variable, every container image — and if you miss one, you cause an outage. Because the manual process is painful and risky, in practice passwords sit unchanged for years. Automation removes the excuse.</li>\n</ul>\n<p style=\"line-height: 1.75\">The honest framing for an interview is: rotation is not about making a password stronger. It is about shrinking the window of time during which a stolen password is useful.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The rotation schedule</h4>\n<p style=\"line-height: 1.75\">When you turn rotation on for a secret, you tell Secrets Manager how often to do it. There are two ways to express that.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>A fixed interval in days.</strong> The simplest form: rotate every 30 days, every 7 days, every 90 days. In the CLI this is the <code>AutomaticallyAfterDays</code> field of the rotation rules. Secrets Manager picks a time inside a rotation window and runs it.</li>\n<li><strong>A cron-style or rate schedule expression.</strong> For more control you supply a <code>ScheduleExpression</code> such as <code>cron(0 8 1 * ? *)</code> (08:00 UTC on the first of every month) or <code>rate(15 days)</code>. Cron expressions let you land rotation on a quiet maintenance window instead of the middle of your busiest hour. You can also set a <code>Duration</code> such as <code>2h</code> to bound the window in which the rotation may start.</li>\n<li><strong>Rotate immediately or wait.</strong> When you first enable rotation, Secrets Manager by default performs one rotation right away so it can prove the whole pipeline works. You can suppress that with <code>--no-rotate-immediately-on-set</code> (the API field is <code>RotateImmediatelyOnSet</code> set to false), which is what you want if the very first rotation would disrupt something mid-day.</li>\n</ul>\n<p style=\"line-height: 1.75\">You can also trigger a rotation on demand at any time with <code>aws secretsmanager rotate-secret</code>, which is how you respond to a suspected leak: do not wait for the schedule, rotate now.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Managed rotation versus a custom rotation Lambda</h4>\n<p style=\"line-height: 1.75\">Something has to actually go and change the password in the target system. That something is a small program. Who writes it depends on what the secret is for.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Managed rotation for supported AWS databases.</strong> For Amazon RDS (MySQL, PostgreSQL, Oracle, SQL Server, MariaDB), Amazon Aurora, Amazon Redshift and Amazon DocumentDB, AWS supplies the rotation logic. In the console you pick the database, pick single-user or alternating-users, and you are done — you write no code. For several of these, AWS now runs the rotation entirely inside the service, so there is not even a Lambda function in your account to maintain. For the rest, AWS generates the function for you from a published template.</li>\n<li><strong>A custom rotation Lambda function you write.</strong> For anything else — a third-party API key such as Stripe or Datadog, a self-managed PostgreSQL on EC2, an SFTP password, a service account in an on-premises system — you write a small <strong>AWS Lambda function</strong> (a piece of code AWS runs for you on demand, with no server to manage). Secrets Manager invokes it and passes it the secret ID, a request token, and which step to perform.</li>\n</ul>\n<p style=\"line-height: 1.75\">AWS publishes rotation function templates on GitHub for the common database engines, so even a custom function usually starts as a copy of a template rather than a blank file.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The four steps of a rotation function</h4>\n<p style=\"line-height: 1.75\">This is the single most commonly asked detail in a Secrets Manager interview. The catch is that applications cache secrets, and connection pools hold connections opened with the old password. The moment <code>setSecret</code> runs, the old password is dead. Any process that still has it cached and tries to open a new connection gets an authentication error. The fix is application-side: catch an authentication failure, call <code>GetSecretValue</code> again to fetch the fresh value, and retry once. That retry-on-auth-failure pattern is a genuinely expected answer in interviews.</p>\n<p style=\"line-height: 1.75\"><strong>Alternating-users rotation</strong> removes that window. Secrets Manager maintains two database users that are clones of each other in terms of permissions. If the secret currently holds credentials for <code>app_a</code>, the rotation creates or updates <code>app_b</code> with a fresh password, verifies it, and flips the label so the secret now hands out <code>app_b</code>. Crucially, <code>app_a</code> still exists and still works — it is only rotated at the following cycle. So any application still holding the previous credential keeps functioning until then. The price is real: you need the second user kept permission-identical, and you need a separate <strong>superuser</strong> (admin) secret, because changing another user's password requires elevated privilege. That admin secret is referenced by the rotation function and should itself be tightly locked down.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The networking requirement people forget</h4>\n<p style=\"line-height: 1.75\">The rotation function has to be able to open a TCP connection to the database. If your database lives in a private subnet of a <strong>VPC</strong> (a Virtual Private Cloud, your own isolated network inside AWS), then a Lambda function running outside that VPC cannot reach it. This causes far more failed rotations than any coding mistake.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Put the Lambda in the VPC.</strong> Configure the rotation function with subnets in the same VPC as the database (private subnets, usually in at least two Availability Zones).</li>\n<li><strong>Open the security group path.</strong> A <strong>security group</strong> is a virtual firewall around a resource. The database security group must allow inbound traffic on the database port from the Lambda security group.</li>\n<li><strong>Give the Lambda a way back to the Secrets Manager API.</strong> A Lambda inside a private subnet has no internet route by default, so it cannot call the Secrets Manager endpoint. Either add a NAT gateway, or — cleaner and cheaper — create a <strong>VPC endpoint</strong> for Secrets Manager, which is a private door into the AWS service that never leaves the AWS network. A rotation that hangs and then times out after several minutes is almost always this.</li>\n<li><strong>Permissions both ways.</strong> The Lambda execution role needs Secrets Manager permissions on the secret, plus <code>kms:Decrypt</code> if a customer managed key is used, and the secret must have a resource policy or the function must be granted invoke permission from <code>secretsmanager.amazonaws.com</code>.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Did rotation actually work?</h4>\n<p style=\"line-height: 1.75\">Rotation failing silently is worse than not rotating, because you believe you are protected. Three places tell you the truth.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>The secret metadata.</strong> <code>aws secretsmanager describe-secret</code> returns <code>RotationEnabled</code>, <code>LastRotatedDate</code>, <code>NextRotationDate</code> and, when something went wrong, <code>LastRotationStatus</code> and a human-readable <code>LastRotationStatusMessage</code>. The console shows a banner on the secret when the last rotation failed.</li>\n<li><strong>CloudWatch Logs.</strong> The rotation Lambda writes to a log group named after the function. This is where you find the actual exception — a connection timeout, an access-denied, a SQL syntax error in the ALTER USER statement.</li>\n<li><strong>EventBridge and CloudWatch alarms.</strong> Secrets Manager emits events for rotation failures, and Lambda publishes an Errors metric. Create an alarm or an EventBridge rule that notifies a team channel when rotation fails, and a second alarm on secrets whose <code>LastRotatedDate</code> has gone stale.</li>\n</ul>\n<p style=\"line-height: 1.75\">The usual causes, roughly in order of frequency: the Lambda cannot reach the database (VPC or security group), the Lambda cannot reach the Secrets Manager endpoint (no NAT or VPC endpoint), the rotation user lacks privilege to alter passwords, the KMS key does not allow the Lambda role to decrypt, the new password violates the database password policy, or the secret is not in the expected JSON shape (the managed rotation functions expect fields such as <code>username</code>, <code>password</code>, <code>engine</code>, <code>host</code>, <code>port</code>, <code>dbname</code>).</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"Rotation updates my application config automatically.\"</strong> It does not. Rotation changes the value stored in Secrets Manager and in the target system. Your application only sees the new value when it next calls <code>GetSecretValue</code>. If you copied the secret into an environment variable at deploy time, rotation will break you. Fetch at runtime and cache with a short lifetime.</li>\n<li><strong>\"Rotation can never cause an outage.\"</strong> Single-user rotation genuinely has a brief window where a cached old password fails.
