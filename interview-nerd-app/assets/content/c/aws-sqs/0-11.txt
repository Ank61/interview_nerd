{"title":"Monitoring, Alarms, and SQS Pricing","tags":["SQS","CloudWatch","Alarms","Pricing"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">A queue is the one place in your architecture where \"things are broken\" shows up as a number before anyone complains. If consumers stall, the backlog grows. If a message is poisonous, it accumulates receive counts and lands in a dead-letter queue. Nothing crashes, no HTTP 500 appears — the work simply piles up silently until messages start expiring. Good monitoring turns that silence into a page at 2 a.m. instead of an angry customer at 9 a.m.</p>\n<p style=\"line-height: 1.75\"><strong>CloudWatch</strong> is AWS's monitoring service. SQS publishes metrics there automatically at one-minute intervals, for free, with no configuration. Your job is knowing which numbers mean what, and which ones deserve an alarm.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The metrics that matter</h4>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Metric</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">What it actually tells you</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><strong>ApproximateNumberOfMessagesVisible</strong></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">The <strong>backlog</strong> — messages sitting in the queue waiting for someone to pick them up.</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><strong>ApproximateNumberOfMessagesNotVisible</strong></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Messages <strong>in flight</strong> — received by a consumer and currently hidden by the visibility timeout. And <strong>ApproximateAgeOfOldestMessage</strong> deserves its reputation because it directly encodes the failure you care about. A growing age means consumers are not keeping up, and every second it grows pushes the oldest message closer to the <strong>retention period</strong> (up to 14 days), after which SQS deletes it permanently. Age is latency, and eventually it is data loss.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Queue depth versus age: how to reason</h4>\n<p style=\"line-height: 1.75\">Beginners alarm on depth and get paged constantly. Anything arriving there is, by definition, work your system could not do. If nobody watches it, messages silently expire after the retention period and the work is gone forever. Alarm on <code>ApproximateNumberOfMessagesVisible &gt; 0</code> on the DLQ, evaluated over one period.</li>\n<li><strong>Age of oldest message above a threshold.</strong> Set the threshold from your business promise: if orders must be processed within five minutes, alarm at 300 seconds. This catches stalls, poison messages and under-capacity all at once.</li>\n<li><strong>Queue depth growing.</strong> Alarm when <code>ApproximateNumberOfMessagesVisible</code> stays above a level well beyond normal for several consecutive periods, so bursts do not page you.</li>\n<li><strong>Stalled consumer.</strong> Alarm when <code>NumberOfMessagesReceived</code> is 0 while <code>ApproximateNumberOfMessagesVisible</code> is greater than 0 — messages are waiting and nobody is reading. Express this as a CloudWatch <strong>composite alarm</strong> (an alarm over other alarms) or a metric math expression. This catches crashed workers, a disabled event source mapping and a broken IAM permission.</li>\n<li><strong>Optional: high NumberOfEmptyReceives</strong>, which flags short polling and wasted spend rather than an outage.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Beyond metrics: CloudTrail and X-Ray</h4>\n<p style=\"line-height: 1.75\"><strong>AWS CloudTrail</strong> records API calls made in your account — the \"who did what, when, from where\" log. CloudWatch tells you the queue depth doubled; CloudTrail tells you that someone called <code>SetQueueAttributes</code> to change the visibility timeout, or <code>PurgeQueue</code> at 14:02, or edited the queue policy. For a queue that suddenly misbehaves after being fine for months, CloudTrail is where you look first. Management events are recorded by default; you can also enable data events for message-level API activity.</p>\n<p style=\"line-height: 1.75\"><strong>AWS X-Ray</strong> is distributed tracing: it follows a single request across services and shows where the time went. SQS propagates the trace context, so a trace can span the producer, the queue wait, and the consumer — which is how you answer \"the checkout is slow, is it the API, the queue, or the worker?\" without guessing.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Pricing in plain terms</h4>\n<p style=\"line-height: 1.75\">SQS pricing is refreshingly simple: <strong>you pay per API request.</strong> Not per message stored, not per hour, not per queue.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>A request is one API call</strong> — <code>SendMessage</code>, <code>ReceiveMessage</code>, <code>DeleteMessage</code>, and their batch variants — and each call can carry <strong>up to 10 messages</strong>. This is why batching is a direct cost lever: ten messages in one batch call cost the same as one message in one call.</li>\n<li><strong>Payload size counts.</strong> Each 64 KB chunk of payload is billed as a request, so a 256 KB message counts as four requests.</li>\n<li><strong>Free tier:</strong> the first 1 million requests per month are free, and this does not expire.</li>\n<li><strong>Standard queues</strong> cost roughly &#36;0.40 per million requests beyond the free tier; <strong>FIFO queues</strong> cost roughly &#36;0.50 per million. Prices vary by Region and there are volume tiers at very high scale.</li>\n<li><strong>No charge for storage duration.</strong> Keeping a message for 14 days costs nothing extra beyond the requests that put it there and took it out.</li>\n<li><strong>Extras:</strong> data transfer out of the Region is charged normally, and <strong>SSE-KMS</strong> adds KMS request charges (mitigated by raising the data key reuse period).</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">A worked monthly estimate</h4>\n<p style=\"line-height: 1.75\">Take a realistic This is usually the single biggest saving.</li>\n<li><strong>Avoid tight polling loops in idle workers.</strong> Twenty workers polling an empty queue every 100 ms generate millions of empty receives a day. Long polling plus a small backoff when the queue is empty fixes it.</li>\n<li><strong>Consolidate chatty small messages.</strong> If a producer emits 50 tiny events per user action, consider one message containing all 50 (staying under the 256 KB limit, with the extended client library for larger payloads). Fewer, fuller messages cost less and often process faster.</li>\n<li><strong>Raise the KMS data key reuse period</strong> if you use SSE-KMS, to cut billable KMS calls.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"SQS charges for storage.\"</strong> It does not.
