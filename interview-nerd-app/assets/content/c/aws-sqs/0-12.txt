{"title":"SQS vs SNS vs EventBridge vs Kinesis — Choosing the Right AWS Messaging Service","tags":["aws","sqs","sns","eventbridge"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">\nIf you have only ever built a web application where one service calls another directly over HTTP, AWS's messaging menu looks confusing: SQS, SNS, EventBridge, Kinesis Data Streams, Amazon MQ. They all \"move messages around\", so why five? The answer is that they solve four genuinely different problems, and once you can name the problem you can pick the service in about ten seconds. This topic gives you that vocabulary, then the decision framework interviewers are actually testing for.\n</p>\n<p style=\"line-height: 1.75\">\nA <strong>message</strong> here just means a small piece of data — usually JSON — that one part of your system hands to another part instead of calling it directly. The reason to do that at all is <strong>decoupling</strong>: the sender does not have to wait for the receiver, does not have to know where the receiver lives, and does not break when the receiver is down. Everything below is a different answer to \"and then what happens to that message?\"\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The one distinction everything else hangs off: queue vs topic</h4>\n<p style=\"line-height: 1.75\">\nA <strong>queue</strong> is a line of work. Each message in it is meant to be done <em>once</em>, by <em>one</em> worker. If you have ten workers reading the same queue, they share the work between them — each message goes to exactly one of them. This is called <strong>work distribution</strong>, or \"competing consumers\" (the workers compete to grab the next item).\n</p>\n<p style=\"line-height: 1.75\">\nA <strong>topic</strong> — the pattern is called <strong>publish/subscribe</strong>, usually shortened to <strong>pub/sub</strong>, meaning \"one sender publishes, many interested parties subscribe\" — is a broadcast. Each message is delivered to <em>every</em> subscriber. Sending one message to many independent recipients like this is called <strong>fan-out</strong>. This is <strong>notification</strong>, not work distribution.\n</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">QUEUE  (SQS)  <i class=o>-</i> <i class=k>one</i> message, <i class=k>ONE</i> consumer      TOPIC  (SNS)  <i class=o>-</i> <i class=k>one</i> message, <i class=k>EVERY</i> subscriber\n\n                <i class=o>+</i><i class=c>-----------+  Worker A                        +-----------+ --&gt; Billing</i>\n  Producer <i class=c>--&gt;  |  M3 M2 M1 | --&gt; Worker B       Producer --&gt;   |  Topic    | --&gt; Search index</i>\n                <i class=o>+</i><i class=c>-----------+  Worker C                         +-----------+ --&gt; Email service</i>\n\n  M1 goes <i class=k>to</i> A. Use a queue where you needed a topic and only one of your three downstream systems reacts to each order — the other two silently miss two thirds of your traffic. Use a topic where you needed a queue and every worker does the same job three times, so you charge the customer three times.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Amazon SQS — the pull-based queue</h4>\n<p style=\"line-height: 1.75\">\n<strong>SQS (Simple Queue Service)</strong> is a fully managed queue. A producer calls <code>SendMessage</code>; the message sits durably in the queue until a consumer calls <code>ReceiveMessage</code> to pull it, does the work, and calls <code>DeleteMessage</code> to confirm. <strong>Pull-based</strong> (also called \"polling\") means SQS never pushes anything at you — your consumer asks for work when it is ready for work. That is why SQS naturally protects a slow consumer: it can simply ask more slowly.\n</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Retries built in.</strong> If a consumer crashes without deleting the message, the message becomes visible again after the <strong>visibility timeout</strong> (a hold period during which other consumers cannot see it) and someone else retries it.</li>\n<li><strong>Dead-letter queue (DLQ).</strong> A separate queue where messages land after failing N times, so one poison message cannot loop forever. You inspect it, fix the bug, and replay.</li>\n<li><strong>Buffering.</strong> The queue absorbs a traffic spike so your database is not hit by it. Retention is up to 14 days.</li>\n<li><strong>No routing, no broadcast.</strong> A message goes in one end and out the other. Anything cleverer than that is not SQS's job.</li>\n</ul>\n<p style=\"line-height: 1.75\">\nReach for SQS for background jobs: resize this image, send this email, generate this PDF, sync this record. Anything where the answer to \"who should handle this?\" is \"whichever worker is free\".\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Amazon SNS — the push-based pub/sub topic</h4>\n<p style=\"line-height: 1.75\">\n<strong>SNS (Simple Notification Service)</strong> is the broadcast side. You create a <strong>topic</strong> (a named channel), other things <strong>subscribe</strong> to it, and every message you publish is delivered to every subscriber. <strong>Push-based</strong> means SNS calls <em>them</em> — subscribers do not poll.\n</p>\n<p style=\"line-height: 1.75\">\nSubscribers can be: an SQS queue, a Lambda function, an HTTP/HTTPS endpoint (a webhook to your own or a partner's server), email, SMS, a mobile push notification, a Kinesis Data Firehose delivery stream, or AWS Event Fork pipelines. SNS also has <strong>FIFO topics</strong>, which deliver in order to FIFO SQS queues, and <strong>message filtering</strong>: a <strong>filter policy</strong> is a small JSON rule attached to a subscription so that subscriber receives only the messages it cares about — for example only events where <code>eventType</code> is <code>order_cancelled</code>. Without filter policies you would either send everything to everyone and filter in code, or create a topic per event type.\n</p>\n<p style=\"line-height: 1.75\">\nThe important caveat: SNS does not store messages for you. If a Lambda subscriber is broken, SNS retries on a delivery policy and then gives up (to an SNS-level DLQ if you configured one). There is no queue to sit in until you fix things. That limitation is exactly what the next pattern fixes.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The canonical pattern: SNS-to-SQS fan-out</h4>\n<p style=\"line-height: 1.75\">\nThis is the single most-asked AWS messaging design in interviews. You publish once to an SNS topic, and each subscriber is <em>its own SQS queue</em> rather than a Lambda or a webhook. Each consuming team then reads from the queue that belongs to it.\n</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">                                <i class=o>+</i><i class=c>---------------+   +--------------------+</i>\n                          <i class=o>+</i><i class=c>---&gt; | queue-billing | -&gt;| Billing workers    | -&gt; DLQ-billing</i>\n                          <i class=o>|</i>     <i class=o>+</i><i class=c>---------------+   +--------------------+</i>\n<i class=k>Order</i>   <i class=c>--&gt; [ SNS topic   |     +---------------+   +--------------------+</i>\nService     <i class=k>order</i><i class=o>-</i>events ]<i class=o>+</i><i class=c>---&gt; | queue-search  | -&gt;| Search indexer     | -&gt; DLQ-search</i>\n                          <i class=o>|</i>     <i class=o>+</i><i class=c>---------------+   +--------------------+</i>\n                          <i class=o>|</i>     <i class=o>+</i><i class=c>---------------+   +--------------------+</i>\n                          <i class=o>+</i><i class=c>---&gt; | queue-email   | -&gt;| Email sender       | -&gt; DLQ-email</i>\n                                <i class=o>+</i><i class=c>---------------+   +--------------------+</i></code></pre></div>\n<p style=\"line-height: 1.75\">\nWhy this beats either service alone:\n</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Isolation.</strong> If the email sender is down for two hours, its messages pile up in <em>its</em> queue. Billing and search never notice. With SNS pushing straight to three Lambdas, a broken subscriber just drops traffic after retries.</li>\n<li><strong>Independent retry and DLQ per consumer.</strong> Each queue has its own visibility timeout, its own redrive policy, its own DLQ and alarm.</li>\n<li><strong>Independent speed.</strong> Billing can run 50 workers; email can run 2 because of a provider rate limit. Neither constrains the other.</li>\n<li><strong>Add consumers without touching the producer.</strong> A fourth team subscribes a new queue; the order service does not change or redeploy.</li>\n</ul>\n<p style=\"line-height: 1.75\">\nTwo practical requirements: the SQS queue needs a <strong>resource policy</strong> allowing the SNS topic to send to it, and you almost always want <strong>raw message delivery</strong> enabled so the consumer receives your JSON directly instead of your JSON wrapped inside an SNS envelope. The modern variant is <strong>EventBridge to SQS</strong>, which gives you the same isolation plus much richer routing rules.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Amazon EventBridge — the event bus with routing rules</h4>\n<p style=\"line-height: 1.75\">\nAn <strong>event bus</strong> is a shared channel where producers publish events and the <em>bus</em> decides who gets what, based on rules you write. EventBridge's distinguishing feature is <strong>content-based routing</strong>: a rule matches on the actual content of the event, with a pattern like \"source is <code>com.shop.orders</code> AND detail.amount is greater than 500 AND detail.country is CA or US\". SNS filter policies can do simple attribute matching; EventBridge rule patterns are considerably richer and live centrally on the bus rather than on each subscription.\n</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>AWS service events.</strong> Most AWS services emit events to the default bus — an EC2 instance changed state, a CodePipeline stage failed, an S3 object was created. You can react without writing any glue.</li>\n<li><strong>SaaS partner events.</strong> Third parties such as Datadog, Zendesk, Stripe (via partner integrations) can deliver events directly onto a partner event bus in your account.</li>\n<li><strong>Schema registry.</strong> EventBridge can discover the structure of events flowing through and generate typed code bindings, so consuming teams are not guessing at field names.</li>\n<li><strong>Archive and replay.</strong> You can archive matching events for a retention period and later replay them onto the bus — useful after fixing a consumer bug.</li>\n<li><strong>Scheduling.</strong> EventBridge Scheduler runs one-off or recurring (cron/rate) invocations — the modern replacement for cron-on-a-server.</li>\n<li><strong>Many targets.</strong> Lambda, SQS, SNS, Step Functions, Kinesis, ECS tasks, API destinations (outbound HTTP with auth), and more.</li>\n</ul>\n<p style=\"line-height: 1.75\">\nChoose EventBridge when the <em>routing logic itself</em> is part of the design, when you want producers to publish domain events without knowing their consumers, or when you are integrating AWS or SaaS events. Its per-event latency is typically higher than SNS and its throughput limits are lower, so it is not the right layer for millions of events per second.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Amazon Kinesis Data Streams — the ordered, replayable stream</h4>\n<p style=\"line-height: 1.75\">\nA <strong>stream</strong> is different from both a queue and a topic. Think of it as an append-only notebook: records are written in order and stay there for a retention period (24 hours by default, configurable up to 365 days). Consumers are not <em>given</em> records — they read from a <strong>position</strong> they keep track of themselves, and they can move that position backwards to read the same records again. Re-reading past records like this is called <strong>replay</strong>.\n</p>\n<p style=\"line-height: 1.75\">\nA stream is divided into <strong>shards</strong> — independent slices that let you process in parallel. Order is guaranteed <em>within a shard</em>, and records with the same <strong>partition key</strong> (a value you choose, like <code>customerId</code>) always land on the same shard, so all events for one customer stay in order relative to each other. Several independent applications can read the same stream at the same time, each at its own position, and a fan-out consumer with <strong>enhanced fan-out</strong> gets its own dedicated read throughput.\n</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">STREAM (Kinesis <i class=o>/</i> Kafka) <i class=o>-</i> records kept <i class=k>for</i> days, <i class=k>each</i> reader has its own position\n\nshard<i class=n>-0</i> : [r1][r2][r3][r4][r5][r6][r7][r8][r9] ...\n                    <i class=o>^</i>                <i class=o>^</i>\n                    <i class=o>|</i>                <i class=o>|</i>\n            Analytics app      Fraud detector\n            (position <i class=n>3</i>)       (position <i class=n>7</i>)      <i class=o>&lt;</i><i class=o>-</i> <i class=k>both</i> read the SAME records,\n                                                    independently, <i class=k>and</i> can rewind</code></pre></div>\n<p style=\"line-height: 1.75\">\nUse Kinesis for clickstreams, IoT telemetry, application logs, metrics pipelines, change-data capture (the stream of row changes coming out of a database), and anything where multiple analytics consumers need the same data or where you may need to reprocess history after fixing a bug. Do <em>not</em> use it as a plain job queue: there is no per-message delete, no visibility timeout, no per-message retry and no built-in DLQ — a stuck record blocks its shard until your code handles it.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Amazon MQ — the managed traditional broker</h4>\n<p style=\"line-height: 1.75\">\n<strong>Amazon MQ</strong> is managed <strong>RabbitMQ</strong> or <strong>ActiveMQ</strong> — established open-source message brokers with decades of enterprise use. You choose it when you need <em>protocol compatibility</em>: AMQP 0-9-1, MQTT, STOMP, OpenWire or JMS. SQS speaks only its own HTTPS API, so an existing application written against JMS or AMQP would have to be rewritten to use it. Amazon MQ lets that application keep its code and move to AWS. It is a lift-and-shift and protocol-compatibility choice, not usually the right pick for a brand-new AWS-native system, and unlike SQS you pick broker instance sizes rather than getting elastic scale for free.\n</p>\n<h4 style=\"margin-top: 1.5rem;
