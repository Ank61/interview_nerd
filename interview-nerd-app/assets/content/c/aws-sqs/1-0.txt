It writes copies of the message to multiple servers spread across multiple Availability Zones in the region, and only then returns a <code>MessageId</code> and an MD5 of the body. That redundancy is what makes the queue durable: an AZ can fail and your message survives. If the queue holds a handful of messages scattered over many servers, the sampled subset may legitimately contain none of them, and you get an empty response while <code>ApproximateNumberOfMessages</code> says five. Nothing is broken. The effect is most visible on low-volume queues, where the messages-to-servers ratio is worst; on a busy queue almost every server holds something, so sampling almost always hits.</p>\n<p style=\"line-height: 1.75\">Long polling (<code>WaitTimeSeconds</code> up to 20) fixes this by having the front end keep sampling for the duration of the wait, returning as soon as it finds anything. That is why long polling is not merely a cost optimization — it is the correction for a sampling artifact. On a long-polled queue, an empty response after the full wait is a much stronger signal that the queue is genuinely empty, though still not a proof.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Consequence 2: Duplicate Delivery</h4>\n<p style=\"line-height: 1.75\">Deleting a message is also a distributed operation. <code>DeleteMessage</code> with a receipt handle instructs the servers holding that message to drop their copies. In the overwhelming majority of cases every copy is removed before anyone could receive it again. But if one server is briefly unreachable — a network partition, a host restart, a transient hiccup — it may not have processed the delete when a later <code>ReceiveMessage</code> samples it. That server still believes the message is available and past its visibility timeout, so it hands it out again. Your consumer sees the same body a second time, with a <strong>different receipt handle</strong> but the <strong>same MessageId</strong>.</p>\n<p style=\"line-height: 1.75\">Note that this is a distinct source of duplicates from the far more common operational one: a consumer whose processing exceeds the visibility timeout, so SQS makes the message visible again and a second consumer picks it up while the first is still working. Consensus means a quorum, a quorum means that a partition can leave you unable to make progress, and it means every operation pays a cross-AZ round trip even when the network is healthy.</p>\n<p style=\"line-height: 1.75\">In CAP terms SQS is an <strong>AP</strong> system for the delivery path: under partition it keeps accepting sends and serving receives rather than refusing service to preserve a strict single-copy view. Two messages sent a millisecond apart may live on disjoint sets of servers; a receive that samples server 3 before server 7 returns them in the opposite order from the send. SQS makes a best effort to deliver roughly in order, but there is no global sequence number, so there is nothing to enforce.</p>\n<p style=\"line-height: 1.75\">FIFO queues provide strict ordering by narrowing the problem: ordering is guaranteed only <strong>within a message group</strong>. Each <code>MessageGroupId</code> gets its own sequenced stream, and SQS will not hand out message N+1 of a group until message N has been deleted (or has become visible again). That per-group serialization is exactly why FIFO throughput is bounded while standard is effectively unlimited: sequencing requires coordination, coordination costs, and the cost is charged as a transactions-per-second limit. Ordering is not free; on a FIFO queue you are buying it with throughput, and the number of distinct active message groups is the knob that buys parallelism back.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The In-Flight Message Limit</h4>\n<p style=\"line-height: 1.75\">A message that has been received but not yet deleted or returned to visibility is <strong>in flight</strong>. SQS caps how many messages can be in flight per queue at once. For standard queues the documented cap is approximately 120,000; for FIFO queues it is approximately 20,000. Exceeding it does not silently drop anything — further <code>ReceiveMessage</code> calls fail with an <code>OverLimit</code> error while the existing in-flight set drains. Quotas are documented per queue type and some quotas are adjustable via support, so treat the exact figure as something to look up rather than recite.</p>\n<p style=\"line-height: 1.75\">The design implication is a hard ceiling on <em>fleet size times batch size times concurrency</em> when processing is slow. A thousand workers each holding a batch of ten messages for four minutes is 10,000 in flight — comfortable. Ten thousand Lambda concurrency each holding ten messages is 100,000 — close enough to the standard ceiling to start failing under a burst. The usual fixes are reducing batch size, shortening processing time (offload the long tail to Step Functions or a state machine and delete the message early), or sharding across multiple queues so the limit applies per queue rather than to the whole workload.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Durability, Retention, and the Absence of a Browse API</h4>\n<p style=\"line-height: 1.75\">Retention (<code>MessageRetentionPeriod</code>) ranges from 60 seconds to 14 days, with a 4-day default; a message older than the retention period is deleted whether or not anyone consumed it. Maximum message size is 256 KB, with the Extended Client Library pattern for larger payloads: store the body in S3 and put a pointer in the message. The service keeps your messages redundantly and encrypts them at rest when SSE is enabled, but it deliberately offers no way to <strong>look</strong> at them.</p>\n<p style=\"line-height: 1.75\">There is no peek, no browse, no \"get message by id\", and no query. The console's \"Poll for messages\" is an ordinary <code>ReceiveMessage</code> — it makes messages invisible while you look at them, which is why casually polling a production queue in the console can starve your real consumers. The architectural consequence is blunt: <strong>you cannot ask a queue whether your message is in there.</strong> A queue is a transport, not a datastore.
