Send <code>{\"orderId\": \"ord_123\"}</code>, not the entire order with its line items, customer record and PDF invoice embedded.</p>\n<p style=\"line-height: 1.75\">Why? Small messages are cheaper (SQS bills in 64 KB chunks, so a 256 KB message costs as much as four requests), faster to move, less likely to hit the limit as your data grows, and — importantly — they cannot go stale. If the consumer re-reads the order from the database using the id, it always sees the current state; a fat message carries a snapshot from whenever it was sent.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The large payload problem and its two standard solutions</h4>\n<p style=\"line-height: 1.75\">Sometimes the payload genuinely is large — a 40 MB video to transcode, a 10 MB CSV to import. SQS will reject it: the maximum message size is <strong>256 KB</strong> and a send over that fails outright. The consumer reads the ticket and fetches the object. It is a handful of lines of code, completely explicit, and works in any language. You own the cleanup (an S3 lifecycle rule to expire old objects) and the failure handling (what if the object is missing when the consumer looks).</li>\n<li><strong>The Amazon SQS Extended Client Library.</strong> An AWS-provided library (Java, and a Python equivalent) that wraps the SQS client and performs the claim check <em>transparently</em>. The consumer side, using the same library, retrieves and reassembles it so your code sees the full body.
