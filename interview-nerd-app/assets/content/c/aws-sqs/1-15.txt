{"title":"Queue-Based System Design — Reference Architectures","tags":["system-design","reference-architecture","saga","event-driven"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">This is the capstone. Individual SQS features only matter insofar as they assemble into systems that survive production, and a staff-level interview is largely a test of whether you can lay out a complete architecture, justify every component, name what breaks when each one fails, and say what you would remove first under time pressure. What follows is five reference architectures you should be able to draw from memory, the cross-cutting concerns a strong candidate raises without being asked, a decision framework for choosing between AWS messaging services, and the anti-patterns that end interviews badly. The discipline throughout is the same: <strong>state the requirement, name the component, explain what it contains, and explain what breaks if it is removed.</strong></p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">(a) Asynchronous Job Processing at Scale</h4>\n<p style=\"line-height: 1.75\">The canonical pattern and the one most likely to open a design round. A client submits work that takes longer than an HTTP request should, so the API accepts it, returns a job id immediately, and the work happens elsewhere.</p>\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">client                API (ALB + ECS/Lambda)              DynamoDB <i class=s>&quot;jobs&quot;</i>\n  |  POST /jobs            |                                   |\n  |-----------------------&gt;| 1. jobId = uuid                   |\n  |                        | 2. PutItem status=QUEUED ---------&gt;|\n  |                        | 3. SendMessage {jobId}             |\n  |  202 + {jobId, href}   |          |                        |\n  |&lt;-----------------------|          v                        |\n  |                            [ SQS work-queue ]              |\n  |                                   |  (long poll, batch 10) |\n  |                            +------+------+                 |\n  |                            | worker pool  |  (ECS/Lambda)   |\n  |                            | idempotent   |                 |\n  |                            +------+------+                 |\n  |                                   | 4. conditional write    |\n  |                                   |    RUNNING -&gt; SUCCEEDED&gt;|\n  |  GET /jobs/{<i class=b>id</i>}  (poll)           | 5. DeleteMessage        |\n  |&lt;----------------------------------+                         |\n  |  or  webhook / WebSocket / EventBridge on completion        |\n                                      |\n                       after maxReceiveCount -&gt; [ DLQ ] -&gt; alarm</code></pre></div>\n<p style=\"line-height: 1.75\"><strong>Why each piece exists.</strong> The <strong>202 Accepted with a job id</strong> decouples client latency from work duration and is what makes the whole thing possible; without it you are holding an HTTP connection for minutes and your load balancer will kill it. <strong>DynamoDB as the status store</strong> exists because the queue is not queryable — a client asking \"is my job done?\" cannot ask SQS, so status must live somewhere addressable by job id. Writing the status row <strong>before</strong> sending the message matters: if you send first and crash, a worker can process a job whose status row does not exist. The <strong>queue</strong> absorbs the difference between arrival rate and processing rate; the <strong>worker pool</strong> scales on queue depth. <strong>Idempotency</strong> is mandatory because SQS is at-least-once — the worker conditionally transitions the job row from QUEUED to RUNNING, and a second delivery whose row is already SUCCEEDED simply deletes the message and returns.</p>\n<p style=\"line-height: 1.75\"><strong>Retry and DLQ.</strong> Transient failures are handled by not deleting the message: visibility expires, it is redelivered, <code>ApproximateReceiveCount</code> increments, and at <code>maxReceiveCount</code> the redrive policy moves it to the DLQ. Set <code>maxReceiveCount</code> to about 5 and alarm on DLQ depth greater than zero. On the final failure the worker should also write <code>status=FAILED</code> with a reason, or clients poll forever against a job that will never complete — a subtle bug that is very common in real systems.</p>\n<p style=\"line-height: 1.75\"><strong>Backpressure.</strong> The queue itself is the buffer, but it is not infinite in usefulness: if arrival rate exceeds maximum processing rate indefinitely, depth grows without bound and the oldest jobs breach their SLA. The controls are scaling workers on <code>ApproximateNumberOfMessagesVisible</code> (or better, on backlog-per-worker), capping concurrency where a downstream dependency is the real bottleneck, and — the part candidates forget — <strong>rejecting work at the API</strong> with a 429 when depth or <code>ApproximateAgeOfOldestMessage</code> exceeds a threshold. Accepting work you cannot perform is worse than refusing it.</p>\n<p style=\"line-height: 1.75\"><strong>How the client learns about completion.</strong> Three options with different trade-offs. <strong>Polling</strong> <code>GET /jobs/{id}</code> is simplest and works everywhere; guide clients with a <code>Retry-After</code> header and exponential backoff or you will serve enormous volumes of pointless reads. <strong>Webhooks</strong> push to a client-supplied URL, which is efficient but makes you a client of an unreliable endpoint — so the webhook delivery itself needs its own queue, retries and DLQ, and the receiver must verify a signature. <strong>WebSocket or SSE</strong> via API Gateway gives the best user experience for interactive UIs at the cost of connection state. In all three cases keep polling available as the fallback, because push mechanisms fail and the client needs a way to recover.</p>\n<p style=\"line-height: 1.75\"><strong>What breaks if you remove a piece:</strong> no DynamoDB status store and clients have no way to learn the outcome; no idempotency and a redelivery duplicates the side effect; no DLQ and a poison message retries forever, consuming capacity and hiding the failure; no 429 backpressure and overload becomes an unbounded backlog rather than a clear signal.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">(b) Media / Video Processing Pipeline</h4>\n<p style=\"line-height: 1.75\">Large payloads, long-running work, and a fan-out to multiple derivatives. The defining constraints are that the data never goes through the queue and the work outlives Lambda's limits.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">client <i class=c>--(1) POST /uploads--&gt; API --&gt; presigned S3 PUT URL</i>\n  <i class=o>|</i>\n  <i class=o>+</i><i class=c>--(2) PUT bytes directly to S3 (never through your API or the queue)</i>\n                     <i class=o>|</i>\n            S3 ObjectCreated event\n                     <i class=o>|</i>\n                EventBridge  (content filtering, archive<i class=o>+</i>replay, many targets)\n                     <i class=o>|</i>\n                SNS topic &quot;media-ingested&quot;\n            <i class=o>+</i><i class=c>--------+--------+---------------+</i>\n            v                 v               v\n      SQS transcode      SQS thumbnail    SQS captions\n            <i class=o>|</i>                 <i class=o>|</i>               <i class=o>|</i>\n      ECS<i class=o>/</i>Fargate        ECS<i class=o>/</i>Fargate      ECS<i class=o>/</i>Fargate\n      (<i class=n>30</i><i class=n>-90</i> min job)    (<i class=n>2</i> min)          (<i class=n>10</i> min)\n            <i class=o>|</i>                 <i class=o>|</i>               <i class=o>|</i>\n            <i class=o>+</i><i class=c>---- write derivative to S3 ----+</i>\n            <i class=o>+</i><i class=c>---- update DynamoDB &quot;asset&quot; progress/status ----+</i>\n            <i class=o>|</i>\n      heartbeat: ChangeMessageVisibility <i class=k>every</i> <i class=n>60</i>s while working\n            <i class=o>|</i>\n      failures <i class=o>-</i><i class=o>&gt;</i> <i class=k>per</i><i class=o>-</i>queue DLQ <i class=o>-</i><i class=o>&gt;</i> alarm (isolated <i class=k>per</i> derivative)</code></pre></div>\n<p style=\"line-height: 1.75\"><strong>Presigned URLs</strong> keep gigabytes out of your API and out of SQS entirely — the message carries only a bucket and key, which is the <strong>claim-check pattern</strong>. Without this you are constrained by the SQS payload limit and paying to move bytes through compute you control. <strong>S3 event notification</strong> makes the pipeline trigger on the fact of the upload rather than on a client call that may never come; going through <strong>EventBridge</strong> rather than wiring S3 directly to SQS buys content-based filtering (only process objects under a prefix, or above a size), multiple targets, and archive-and-replay for reprocessing. <strong>SNS fan-out to per-derivative queues</strong> is the critical structural choice: each derivative gets its own queue, its own scaling, its own retry policy and its own DLQ, so a broken caption generator cannot block transcoding.</p>\n<p style=\"line-height: 1.75\"><strong>ECS/Fargate rather than Lambda</strong> because transcoding runs for tens of minutes and exceeds Lambda's 15-minute maximum, needs more than Lambda's memory and ephemeral storage for large files, and benefits from a long-lived container that can stream from S3 to local disk. Lambda remains correct for the thumbnail job. This asymmetry — different derivatives on different compute — is a sign of a mature design, not an inconsistency.</p>\n<p style=\"line-height: 1.75\"><strong>Visibility timeout and heartbeating</strong> is the technical heart of this architecture. The maximum SQS visibility timeout is <strong>12 hours</strong>, but setting it to 12 hours is wrong: if a worker dies one minute into a job, that message is invisible for 12 hours and the user's video sits unprocessed. Instead set a modest visibility timeout (say 5 minutes) and have the worker call <code>ChangeMessageVisibility</code> on a timer — typically every third of the timeout — extending it while it is genuinely alive. A crashed worker stops heartbeating and the message becomes available within minutes. Two rules: bound the total extension so a hung worker cannot heartbeat forever, and stop the heartbeat thread in a <code>finally</code> block or you will extend the visibility of a message you already deleted.</p>\n<p style=\"line-height: 1.75\"><strong>Progress tracking</strong> lives in DynamoDB — one item per asset with a map of derivative states, updated as each completes, so the UI can show \"transcode 60%, thumbnail done, captions queued\". Workers write percentage updates during long jobs, which also serves as a liveness signal independent of the heartbeat. <strong>Remove the heartbeat</strong> and long jobs get duplicated by redelivery mid-flight; <strong>remove the per-derivative queues</strong> and one failing derivative retries the whole fan-out; <strong>remove the presigned upload</strong> and your API becomes a bandwidth bottleneck.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">(c) Order Processing with a Saga</h4>\n<p style=\"line-height: 1.75\">A multi-step distributed transaction across services that do not share a database. The saga executes each step locally and, on failure, runs <strong>compensating actions</strong> to undo the completed steps in reverse.</p>\n<div class=\"code\"><div class=\"code-head\"><span>java</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=t>FORWARD</i> <i class=f>PATH</i> <i class=p>(each hop is a queue; each step is idempotent)</i>\n\norder-created.fifo      payment-requested.fifo    inventory-requested.fifo\n(group = orderId)       (group = orderId)         (group = orderId)\n     |                        |                          |\n[Order svc] --ok--&gt; [Payment svc] --ok--&gt; [Inventory svc] --ok--&gt; [Shipping svc]\n     ^                   |                      |                       |\n     |                 FAIL                   FAIL                    FAIL\n     |                   |                      |                       |\n<i class=t>COMPENSATION</i> <i class=f>PATH</i> <i class=p>(reverse order, each compensation also idempotent)</i>\n     |                   v                      v                       v\ncancel-order &lt;---- refund-payment &lt;---- release-inventory &lt;---- cancel-shipment\n                        .fifo                 .fifo                 .fifo\n\n<i class=t>Saga</i> <i class=f>state</i> <i class=p>(DynamoDB)</i>: orderId -&gt; {step, status, completedSteps[], version}</code></pre></div>\n<p style=\"line-height: 1.75\"><strong>Why a queue-based saga beats two-phase commit.</strong> 2PC requires a coordinator holding locks across all participants for the duration of the transaction. That means: every participant must support a prepare/commit protocol (most HTTP services and SaaS APIs simply do not — you cannot ask Stripe to prepare a charge); locks are held across network calls, so throughput collapses and a slow participant stalls everyone; and the coordinator is a single point of failure whose crash after prepare but before commit leaves participants <strong>blocked indefinitely holding locks</strong>. A saga holds no distributed locks, requires nothing special of participants, and each step commits locally and immediately. The price is honest and you should state it: <strong>you give up isolation</strong>. Intermediate states are visible — money can be captured while inventory is still being reserved — so the business must accept eventual consistency and you may need semantic locks (an order status of PENDING that hides it from other flows).</p>\n<p style=\"line-height: 1.75\"><strong>Ordering per order id</strong> matters because a compensation must not overtake the action it compensates — a refund arriving before the charge is recorded is a support ticket. FIFO queues with <code>MessageGroupId = orderId</code> give exactly that: strict ordering within one order, full parallelism across orders, and millions of distinct orders need no capacity planning. Alternatively, a version guard per saga step achieves the same with standard queues if FIFO throughput is a concern.</p>\n<p style=\"line-height: 1.75\"><strong>Idempotency at every step</strong> is non-negotiable, both forward and compensating. Each service records <code>(orderId, step)</code> as a processed marker with a conditional write before acting, and external calls carry a provider idempotency key (Stripe's <code>Idempotency-Key</code>, for example). <strong>Compensations must be idempotent too</strong> — refunding twice is worse than charging twice — and they must be able to run against a step that never actually completed, which means \"release inventory that was never reserved\" has to be a safe no-op rather than a negative adjustment.</p>\n<p style=\"line-height: 1.75\"><strong>Choreography versus orchestration here:</strong> the diagram above is choreography — each service listens and emits. It is loosely coupled but the saga's overall state exists nowhere, which makes \"why is order 123 stuck?\" genuinely hard. For sagas of more than three or four steps, <strong>Step Functions</strong> as an orchestrator is usually the better answer: the state machine is the explicit, visualisable definition of both the forward path and the catch handlers that invoke compensations, it gives you per-execution history for debugging, and it removes the hand-rolled saga state table. Use <strong>Standard</strong> workflows for long-running order sagas (Express workflows are for high-volume short-lived executions with at-least-once semantics).</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">(d) Rate-Limited Third-Party Integration</h4>\n<p style=\"line-height: 1.75\">A partner API allows 100 requests per second and returns 429 beyond that. Your traffic is bursty and you must never drop a request.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">producers (spiky: <i class=n>0</i> <i class=o>-</i><i class=o>&gt;</i> <i class=n>5000</i><i class=o>/</i>s)\n     <i class=o>|</i>\n[ SQS partner<i class=o>-</i>requests ]   <i class=o>&lt;</i><i class=c>-- the buffer that converts a spike into a backlog</i>\n     <i class=o>|</i>\nconsumer fleet <i class=k>with</i> BOUNDED concurrency (e.g. reserved concurrency <i class=o>=</i> <i class=n>20</i>,\n<i class=k>or</i> a fixed ECS task count) <i class=c>-- unbounded autoscaling here would DDoS the partner</i>\n     <i class=o>|</i>\ntoken bucket <i class=k>in</i> Redis<i class=o>/</i>DynamoDB (shared across <i class=k>ALL</i> consumers)\n     <i class=o>|</i>  acquire() <i class=o>-</i><i class=o>&gt;</i> if <i class=k>no</i> token: ChangeMessageVisibility(backoff) <i class=k>and</i> <i class=k>return</i>\n     v\npartner API  <i class=c>--200--&gt; DeleteMessage</i>\n             <i class=c>--429--&gt; read Retry-After; ChangeMessageVisibility(retry_after)</i>\n                      <i class=k>and</i> do <i class=k>NOT</i> <i class=k>delete</i>  (<i class=k>no</i> wasted retry attempt)\n             <i class=c>--5xx--&gt; exponential backoff + full jitter, let redelivery handle it</i>\n             <i class=c>--4xx--&gt; permanent: send to DLQ immediately, do not retry</i>\n     <i class=o>|</i>\n[ DLQ ] <i class=o>-</i><i class=o>&gt;</i> alarm <i class=o>-</i><i class=o>&gt;</i> manual review <i class=o>/</i> redrive after the partner <i class=k>is</i> fixed</code></pre></div>\n<p style=\"line-height: 1.75\"><strong>The queue converts a spike into a backlog</strong>, which is the entire point: the partner sees a smooth 100 requests per second while your producers burst to 5,000, and nothing is dropped. <strong>Bounded consumer concurrency</strong> is the primary control — with Lambda that is <em>reserved</em> concurrency (a cap), and the subtlety is that Lambda's SQS poller scales up in increments, so a low reserved concurrency plus a large backlog produces throttling that consumes receive attempts; with ECS it is simply a fixed task count, which is often easier to reason about. <strong>Do not autoscale on queue depth here</strong> — that is the natural instinct and it is exactly wrong, because scaling out increases the rate at which you hit a partner who is already refusing you.</p>\n<p style=\"line-height: 1.75\"><strong>The token bucket</strong> gives precise, shared rate limiting across a fleet: a bucket refilling at 100 tokens per second with a small burst allowance, implemented atomically in Redis (a Lua script) or DynamoDB (a conditional update). Concurrency limits alone are a poor proxy for a rate limit — 20 concurrent workers at 50 ms per call is 400 requests per second, four times the budget — so you need both: concurrency bounds resource usage, the token bucket bounds request rate.</p>\n<p style=\"line-height: 1.75\"><strong>Handling 429 well</strong> is the detail interviewers listen for. On a 429, read the <code>Retry-After</code> header and call <code>ChangeMessageVisibility</code> with that value, then return <strong>without deleting the message</strong>. This is better than sleeping in the worker (which burns a worker slot) and better than letting the default visibility timeout apply (which retries too soon). Note that a 429 handled this way still increments <code>ApproximateReceiveCount</code>, so set <code>maxReceiveCount</code> high enough that sustained partner throttling does not dump legitimate messages into the DLQ. Distinguish error classes rigorously: <strong>429 and 5xx are retryable</strong> (backoff with full jitter), <strong>4xx other than 429 is permanent</strong> and should go straight to the DLQ rather than consuming five retries. Add a <strong>circuit breaker</strong> so that when the partner is down you stop consuming entirely rather than draining your retry budget — and when the circuit is open the queue keeps the work safely, which is precisely why the queue is there. Finally, if some requests matter more than others, use two queues (high and low priority) polled with weighted attention, since SQS has no priority concept.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">(e) Event-Driven Microservices Backbone</h4>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">services publish domain events\n     <i class=o>|</i>\nEventBridge custom bus &quot;domain-events&quot;    (schema registry, archive <i class=o>+</i> replay)\n     <i class=o>|</i>   rules <i class=k>with</i> CONTENT<i class=o>-</i>BASED filtering <i class=k>on</i> the event body\n     <i class=o>+</i><i class=c>-----------------+------------------+-------------------+</i>\n     v                 v                  v                   v\nSQS billing<i class=o>-</i>q     SQS <i class=k>search</i><i class=o>-</i>q       SQS notify<i class=o>-</i>q      Step Functions\n     <i class=o>|</i>                 <i class=o>|</i>                  <i class=o>|</i>            (orchestrated flows)\nbilling svc       indexer svc        notifier svc\n     <i class=o>|</i>                 <i class=o>|</i>                  <i class=o>|</i>\n    DLQ               DLQ                DLQ      <i class=o>&lt;</i><i class=o>-</i> <i class=k>each</i> consumer owns its own\n\nWhy a QUEUE <i class=k>per</i> consumer rather than a direct target:\n  <i class=o>-</i> buffering: a slow consumer does <i class=k>not</i> lose events during a deploy <i class=k>or</i> outage\n  <i class=o>-</i> independent retry policy <i class=k>and</i> DLQ <i class=k>per</i> consumer\n  <i class=o>-</i> independent scaling; <i class=k>one</i> slow consumer cannot affect another\n  <i class=o>-</i> replay <i class=k>of</i> <i class=k>one</i> consumer<i class=s>&#x27;s backlog without re-delivering to everyone</i></code></pre></div>\n<p style=\"line-height: 1.75\"><strong>EventBridge or SNS?</strong> SNS is simpler, cheaper at very high volume and lower latency, with filtering on <em>message attributes</em>. EventBridge filters on <strong>message content</strong>, supports many target types, has a <strong>schema registry</strong>, and offers <strong>archive and replay</strong> — which is the closest thing to Kafka replay in the serverless stack and frequently the deciding feature. Use SNS for high-volume simple fan-out; EventBridge for a genuine domain-event backbone with evolving consumers.</p>\n<p style=\"line-height: 1.75\"><strong>Schema versioning</strong> is what keeps this from becoming a distributed monolith. Every event carries an explicit <code>schemaVersion</code>. Changes must be <strong>backward compatible</strong>: add optional fields, never remove or rename or retype a field, and never change a field's meaning. When a breaking change is unavoidable, publish a new event type (<code>OrderPlaced.v2</code>) in parallel, migrate consumers one at a time, and retire v1 only after telemetry shows no consumers remain — consumers must ignore unknown fields for this to work. Keep the event payload to <strong>facts about what happened</strong> plus enough identifying data for consumers to fetch the rest; fat events that embed another service's entire model create coupling you cannot remove later.</p>\n<p style=\"line-height: 1.75\"><strong>Choreography versus orchestration.</strong> Choreography (services react to events) is loosely coupled, easy to extend, and has no central bottleneck — but the overall business process exists in no single place, so debugging a stuck flow means correlating logs across five services, and cyclic event dependencies are easy to create by accident. Orchestration (a <strong>Step Functions</strong> state machine calls services in order) makes the process explicit and visual, gives per-execution history, and handles retries, timeouts, parallel branches and compensation declaratively — at the cost of a central component that must know about every participant. The practical rule: <strong>choreography for notification-style fan-out where nobody owns the outcome; orchestration for business processes with a defined outcome, more than three or four steps, or compensation logic.</strong> Most mature systems use both.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cross-Cutting Concerns</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Idempotency everywhere.</strong> Every queue in AWS is at-least-once, so every consumer must tolerate redelivery. Use a producer-generated business event id, a conditional write or unique constraint before the side effect, and provider idempotency keys for external calls. Set a TTL on the idempotency store longer than your maximum retention plus retry window.</li>\n<li><strong>Poison-message handling.</strong> Every queue gets a DLQ with a <code>maxReceiveCount</code> around 5. Distinguish <strong>permanent</strong> failures (malformed payload, 4xx) which should go to the DLQ immediately, from <strong>transient</strong> ones which should retry. Add a DLQ redrive runbook so an operator knows how to replay after a fix.</li>\n<li><strong>Backpressure.</strong> Queues absorb bursts, not sustained overload. Scale on backlog-per-worker, cap concurrency where a downstream dependency is the bottleneck, and shed load at the edge with 429s when depth or oldest-message age crosses a threshold.</li>\n<li><strong>Observability and correlation ids.</strong> Generate a correlation id at the edge and propagate it through every message attribute, log line and trace. Without it, debugging an async flow is guesswork. Use X-Ray or OpenTelemetry for distributed traces, and log the message id and receive count on every failure.</li>\n<li><strong>DLQ alarming.</strong> Alarm on <code>ApproximateNumberOfMessagesVisible &gt; 0</code> on every DLQ — a DLQ nobody watches is just slower data loss. Also alarm on <code>ApproximateAgeOfOldestMessage</code> on the main queue, which is the single best SLA proxy, and on <code>NumberOfEmptyReceives</code> if cost matters.</li>\n<li><strong>Retention versus recovery time.</strong> SQS retention maxes at <strong>14 days</strong>. That is your hard deadline to fix a broken consumer before messages are silently deleted. Set retention to the maximum on DLQs, and if you need longer than 14 days, archive to S3.</li>\n<li><strong>Cost.</strong> Batch sends and receives up to 10 messages, always use long polling, and watch for chatty status polling. SQS charges per request, so an idle consumer short-polling in a tight loop can cost more than the real work.</li>\n<li><strong>Failure domains.</strong> Name what each component contains. The queue contains producer-consumer failure (a dead consumer costs latency, not data). The DLQ contains poison messages. Per-consumer queues contain a slow consumer. Bounded concurrency contains a downstream overload. A circuit breaker contains a dependency outage. Articulating the blast radius of each component is the difference between a good answer and a great one.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Decision Framework</h4>\n<div style=\"overflow-x: auto;
