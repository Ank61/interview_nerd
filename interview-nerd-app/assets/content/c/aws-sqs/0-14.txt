Scaling is trivial — add workers to go faster, remove them to save money — and because the queue holds the work, a worker crashing loses nothing: its in-flight messages reappear after the <strong>visibility timeout</strong> (the period during which a received message is hidden from other consumers) and someone else picks them up.\n</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">API <i class=c>---&gt; [ jobs queue: m7 m6 m5 m4 m3 ] ---&gt; worker-1  (has m1, invisible)</i>\n                                        <i class=c>---&gt; worker-2  (has m2, invisible)</i>\n                                        <i class=c>---&gt; worker-3  (crashed holding m3</i>\n                                                        <i class=o>-</i><i class=o>&gt;</i> m3 reappears after\n                                                           the visibility timeout)</code></pre></div>\n<p style=\"line-height: 1.75\">\nUse this for image processing, report generation, webhook delivery, email sending — anything where jobs are independent and order does not matter. Traffic spikes hit the queue, which absorbs them; the downstream system sees a flat, predictable rate. This is <strong>load levelling</strong>: converting a spiky arrival pattern into a steady processing pattern, trading latency for survival.\n</p>\n<p style=\"line-height: 1.75\">\nThe point beginners miss: <strong>the queue alone does not protect anything</strong>. If you leave autoscaling to add 200 workers when the backlog grows, those 200 workers will hammer the fragile system exactly as the spike would have. What actually protects it is <strong>limiting consumer concurrency</strong> — a fixed small number of workers, or for Lambda the event source mapping's <code>MaximumConcurrency</code> setting (or a reserved concurrency limit on the function). The queue supplies the buffer; the concurrency cap supplies the rate limit. You need both.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Pattern 3: Fan-out to multiple queues</h4>\n<p style=\"line-height: 1.75\">\nWhen one event must reach several independent consumers, publish once to an <strong>SNS topic</strong> or an <strong>EventBridge</strong> bus and give each consumer <em>its own</em> SQS queue. Each consumer then has its own backlog, its own visibility timeout, its own retry count and its own DLQ, so a broken consumer cannot affect the others. Putting three different consumers on one shared queue does <em>not</em> achieve this — they would split the messages between them rather than each receiving all of them.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Pattern 4: Priority queues (SQS has none natively)</h4>\n<p style=\"line-height: 1.75\">\nSQS has no concept of message priority; a queue is first-in-roughly-first-out and nothing jumps the line. The standard workaround is <strong>two queues</strong>, <code>jobs-high</code> and <code>jobs-low</code>, and a consumer loop that always drains high first:\n</p>\n<div class=\"code\"><div class=\"code-head\"><span>yaml</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=a>loop:</i>\n  <i class=s>msgs</i> <i class=s>=</i> <i class=s>receive(jobs-high,</i> <i class=s>wait=1s)</i>        <i class=c># short wait so we do not block</i>\n  <i class=a>if msgs is empty:</i>\n      <i class=s>msgs</i> <i class=s>=</i> <i class=s>receive(jobs-low,</i> <i class=s>wait=20s)</i>    <i class=c># long poll the low queue</i>\n  <i class=s>process(msgs)</i></code></pre></div>\n<p style=\"line-height: 1.75\">\nTwo cautions. Low-priority work can be <strong>starved</strong> indefinitely if high-priority traffic never stops, so many teams reserve a few workers exclusively for the low queue. And keep it to two or three tiers — a five-tier priority scheme built from queues becomes very hard to reason about. If you truly need rich priorities, that is one of the genuine reasons to consider RabbitMQ instead.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Pattern 5: Request-response over queues (usually a mistake)</h4>\n<p style=\"line-height: 1.75\">\nSometimes you need an answer back. The mechanism: the requester creates or owns a <strong>reply queue</strong>, sends the request with a <strong>correlation ID</strong> (a unique value identifying this request) and the reply queue's URL in the message attributes, then waits on the reply queue and matches incoming responses by correlation ID.\n</p>\n<div class=\"code\"><div class=\"code-head\"><span>css</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">Client --<i class=selector-attr>[ req: correlationId=abc, replyTo=reply-q-17 ]</i>--&gt; <i class=selector-attr>[ work-queue ]</i> --&gt; Worker\nClient &lt;---------<i class=selector-attr>[ resp: correlationId=abc ]</i>------------- <i class=selector-attr>[ reply-q-17 ]</i> &lt;-- Worker</code></pre></div>\n<p style=\"line-height: 1.75\">\nThe honest note: if the caller is a user waiting on an HTTP request, this is usually the <strong>wrong choice</strong>. You have added queue latency, a timeout you must handle, orphaned replies when the client goes away, and a reply-queue lifecycle to manage — all to simulate the synchronous call you could have made directly. Prefer a direct HTTP or gRPC call for synchronous needs; use a queue with a webhook, a polled status endpoint, or WebSocket push for long-running work.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Pattern 6: Pipelines and choreography</h4>\n<p style=\"line-height: 1.75\">\nChain stages so each one's output is the next one's input: <code>uploads-q -> virus-scan -> thumbnails-q -> thumbnail-worker -> index-q -> indexer</code>. Each stage scales, retries and fails independently, and each has its own DLQ. This style — where each service reacts to the previous one's output without a central controller — is called <strong>choreography</strong>, as opposed to <strong>orchestration</strong> where something like AWS Step Functions directs the whole flow.\n</p>\n<p style=\"line-height: 1.75\">\nChoreography is loosely coupled and easy to extend, but hard to observe: no single place tells you where a given job is. Once the flow has branching, compensation on failure, or a business person asking \"where is order 1042 right now?\", Step Functions usually pays for itself.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Pattern 7: Claim-check for large payloads</h4>\n<p style=\"line-height: 1.75\">\nSQS messages are capped at 256 KB. Never put a 40 MB video or a large PDF in the body. Instead, store the payload in S3 and send only a pointer — the bucket, key and version, plus a checksum. The consumer fetches it. This is the <strong>claim-check</strong> pattern, named after a coat check: you hand over the coat and carry only the ticket. The <strong>Amazon SQS Extended Client Library</strong> (available for Java and Python) implements this for you transparently, supporting payloads up to 2 GB. Beyond size limits it is also cheaper (SQS bills in 64 KB chunks) and keeps sensitive data out of the message body.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Pattern 8: Batching</h4>\n<p style=\"line-height: 1.75\">\n<code>SendMessageBatch</code>, <code>ReceiveMessage</code> with <code>MaxNumberOfMessages=10</code> and <code>DeleteMessageBatch</code> each move up to 10 messages per API call. Since SQS bills per request, batching can cut request costs by up to 90% and dramatically raises throughput per worker. Combine it with <strong>long polling</strong> (<code>WaitTimeSeconds=20</code>), which waits for messages to arrive instead of returning empty immediately, reducing both cost and latency. The trade-off is a little added latency while a batch fills, and the need to handle partial failures — a batch call can succeed for 8 messages and fail for 2, and the response tells you which.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Idempotency — the practical crux of using SQS correctly</h4>\n<p style=\"line-height: 1.75\">\n<strong>Idempotent</strong> means running the operation twice with the same input has the same effect as running it once. SQS standard queues guarantee <strong>at-least-once delivery</strong>, which means duplicates are not a rare bug but an expected, normal event — a network hiccup between your successful processing and your <code>DeleteMessage</code> call is enough. Add upstream retries and the duplicates multiply. So idempotency is not optional hardening; it is a requirement of using the service correctly. Even FIFO queues only deduplicate within a 5-minute window, so they do not remove the need.\n</p>\n<h5 style=\"margin-top: 1rem; font-weight: 600\">Choosing the idempotency key — get this right</h5>\n<p style=\"line-height: 1.75\">\nThe key must identify <em>the business operation</em>, not the delivery. This distinction trips up almost everyone:\n</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>SQS MessageId — wrong.</strong> It identifies a message, not an operation. It does catch SQS redelivering the same message (the ID stays the same). But if your upstream service retried a failed <code>SendMessage</code>, you now have <em>two distinct messages with two different MessageIds carrying the same business intent</em> — and a MessageId-based check will happily process the payment twice.</li>\n<li><strong>A business identifier — right.</strong> The order ID, the payment reference, the invoice number: <code>payment-ord-1042</code>. Two different messages describing the same payment share it, so both duplicate paths are caught.</li>\n<li><strong>An event ID generated by the producer — also right</strong>, provided the producer generates it <em>once</em> when the event happens and reuses it across its own retries. This is the cleanest general answer: it survives SQS redelivery, producer retry, and even a fan-out where the same event arrives from two paths.</li>\n<li><strong>Composite keys for multi-step work.</strong> If several consumers act on the same event, scope the key per action: <code>send-receipt:evt-8891</code> and <code>update-ledger:evt-8891</code>, so one consumer's record does not suppress another's work.</li>\n</ul>\n<h5 style=\"margin-top: 1rem; font-weight: 600\">Recording processed keys in DynamoDB</h5>\n<p style=\"line-height: 1.75\">\nThe standard implementation is a DynamoDB table keyed on the idempotency key, written with a <strong>conditional write</strong> — <code>attribute_not_exists(pk)</code> — so that only one writer can ever claim a key, atomically. If the condition fails, this operation has already been handled (or is being handled) and you skip it. Add a <strong>TTL</strong> attribute so rows expire automatically after a window comfortably longer than your maximum retry horizon (24 hours to 7 days is typical), because you do not want to store these forever. AWS also ships <strong>Powertools for AWS Lambda</strong>, whose idempotency utility implements exactly this pattern with a decorator.\n</p>\n<h5 style=\"margin-top: 1rem; font-weight: 600\">Make operations naturally idempotent where you can</h5>\n<p style=\"line-height: 1.75\">\nThe best deduplication is not needing any. Prefer operations that are safe to repeat by construction:\n</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Upsert, not insert.</strong> <code>PutItem</code> with a deterministic key, or SQL <code>INSERT ... ON CONFLICT DO UPDATE</code>, produces the same row whether run once or five times.</li>\n<li><strong>Set, not increment.</strong> <code>status = 'SHIPPED'</code> is idempotent; <code>ADD attempts 1</code> is not. Absolute values beat relative ones.</li>\n<li><strong>Deterministic destinations.</strong> Writing to S3 key <code>thumbs/ord-1042.jpg</code> is idempotent; appending to a log file is not.</li>\n<li><strong>Pass an idempotency key downstream.</strong> Stripe, and many payment and messaging APIs, accept an <code>Idempotency-Key</code> header. Forward your key and let them do the deduplication authoritatively.</li>\n</ul>\n<h5 style=\"margin-top: 1rem; font-weight: 600\">The in-flight race, handled honestly</h5>\n<p style=\"line-height: 1.75\">\nWhat if two workers get the same message simultaneously — for example because the visibility timeout expired while worker A was still running? A naive \"check then act\" has a window: both read 'not processed', both proceed. The conditional write closes it, because exactly one <code>PutItem</code> succeeds. But then worker B must decide what to do about a key that exists in an <code>IN_PROGRESS</code> state:\n</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Write IN_PROGRESS first, COMPLETED after.</strong> Store the state and a timestamp, not just the key's existence.</li>\n<li><strong>If the state is COMPLETED</strong>, worker B skips the work, deletes its copy of the message, and — ideally — returns the stored result.</li>\n<li><strong>If the state is IN_PROGRESS and recent</strong>, worker B should <em>not</em> delete the message. It should back off and let the message become visible again, so the work is not silently lost if worker A dies.</li>\n<li><strong>If the state is IN_PROGRESS but stale</strong> (older than your maximum processing time), treat it as an abandoned attempt and take over, overwriting the lock.</li>\n<li><strong>Always set a visibility timeout longer than your worst-case processing time</strong>, and extend it with <code>ChangeMessageVisibility</code> (a heartbeat) for long jobs. This makes the race rare rather than routine.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner mistakes, with the fix for each</h4>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\">\n<th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Mistake</th>\n<th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">What actually goes wrong</th>\n<th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Fix</th>\n</tr></thead>\n<tbody>\n<tr>\n<td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Deleting the message before processing succeeds</td>\n<td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Silent permanent data loss.
