{"title":"Ordered Processing Without FIFO — Sequencing Patterns","tags":["ordering","sequencing","idempotency","fifo-alternatives"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Junior engineers reach for a FIFO queue the moment ordering is mentioned. Senior engineers ask a sharper question first: <strong>do you need ordered processing, or do you need a correct final state?</strong> Those are different requirements, and the second one is usually what the business actually cares about. If a customer changes their shipping address three times in two seconds, nobody needs those updates applied in order — they need the last one to win. If a bank account receives a deposit and a withdrawal, order does not matter at all because addition is commutative; what matters is that both are applied exactly once. Once you separate \"ordered processing\" from \"correct outcome\", a whole family of application-level techniques opens up that are cheaper, faster and more scalable than FIFO, and knowing them is a reliable senior signal.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why Teams Avoid FIFO</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Throughput limits.</strong> Standard SQS is effectively unlimited; FIFO is not. The long-standing default is 300 API calls per second per action (3,000 messages per second with batches of 10), and <strong>high throughput mode for FIFO</strong> raises that substantially — check the current service quotas page for your region rather than quoting a number from memory. FIFO also has a much lower in-flight message limit than standard queues, which constrains how much concurrent work you can have outstanding.</li>\n<li><strong>Head-of-line blocking.</strong> This is the real killer and the one candidates underweight. Within a message group, SQS will not release the next message until the current one is deleted or its visibility timeout expires. One poison message in a group stalls that entire group for <code>maxReceiveCount</code> multiplied by the visibility timeout — with five retries and a 5-minute timeout that is roughly 25 minutes of frozen processing for that customer while every other group runs fine. If your group id is coarse (per tenant, per region) you have just built an outage for a large population out of one bad payload.</li>\n<li><strong>The group-ID design burden.</strong> Choosing the group id is a permanent architectural decision that fixes your parallelism. Too coarse (<code>MessageGroupId = \"orders\"</code>) and you have a single serial pipeline. Too fine and you may not actually get the ordering you needed, because two related entities land in different groups. Getting it right requires understanding exactly which pairs of messages have a real causal dependency, which is harder than it sounds.</li>\n<li><strong>Higher cost.</strong> FIFO requests cost more per million than standard, and the throughput ceiling often forces more queues and more complexity around them.</li>\n<li><strong>It does not solve the whole problem anyway.</strong> FIFO gives ordered <em>delivery</em>; it does not give ordered <em>completion</em> if your consumer does anything asynchronous, and it does not protect you across systems or across a migration. You will still want idempotency.</li>\n</ul>\n<p style=\"line-height: 1.75\">So the first question in a design review should be: <strong>what breaks if these two messages are processed out of order?</strong> Very often the answer is \"nothing, as long as we do not apply stale data\", and that converts an ordering problem into a much cheaper versioning problem.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Pattern 1 — Version Numbers with a Conditional Write (Last-Write-Wins with a Guard)</h4>\n<p style=\"line-height: 1.75\">This is the most broadly useful technique in the entire topic, and if you remember one thing, remember this one. The producer stamps every message with a <strong>monotonically increasing version or sequence number scoped to the entity</strong>. The consumer applies the update only if the incoming version is greater than the version already stored; otherwise it discards the message as stale. Crucially, the comparison and the write must be <strong>atomic</strong>, which means a DynamoDB <code>ConditionExpression</code> (<code>attribute_not_exists(version) OR version &lt; :v</code>), or in SQL an <code>UPDATE ... WHERE version &lt; :v</code> that you check affected rows on. A read-then-write in application code is a race and will silently corrupt state under concurrency.</p>\n<div class=\"code\"><div class=\"code-head\"><span>css</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">Producer emits, in <i class=a>order</i>:   v1 {addr:A}   v2 {addr:B}   v3 {addr:C}\nStandard queue delivers:    v2 ... v3 ... v1 (delayed retry)\n\nConsumer with version guard:\n   v2 arrives -&gt; stored=none -&gt; apply   -&gt; stored version = <i class=n>2</i>, addr = B\n   v3 arrives -&gt; <i class=n>3</i> &gt; <i class=n>2</i>       -&gt; apply   -&gt; stored version = <i class=n>3</i>, addr = C\n   v1 arrives -&gt; <i class=n>1</i> &lt; <i class=n>3</i>       -&gt; DISCARD -&gt; state unchanged  (correct!)\n\nFinal state = C, the true last write. Order of DELIVERY was wrong;\n<i class=a>order</i> of OUTCOME is <i class=a>right</i>. No FIFO queue, no head-of-<i class=e>line</i> blocking,\nunlimited throughput, and duplicates are handled by the same guard.</code></pre></div>\n<p style=\"line-height: 1.75\">The properties are excellent: it is idempotent for free (a duplicate of v2 fails the condition and is discarded), it works across queues, across systems and across a migration cutover, it imposes no throughput ceiling, and a poison message affects nothing else. The cost is that the producer must be able to generate a monotonic per-entity version — trivial if the entity lives in a database with an update counter or an optimistic-locking version column, harder if events originate from many independent producers for the same entity. The other limitation is that <strong>it only works for state replacement, not for accumulation</strong>: you cannot version-guard \"add 5 to the balance\", because discarding a stale increment loses money. For accumulation you need Pattern 4 or exactly-once idempotency keyed per event.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Pattern 2 — Timestamp-Based Ordering (and Its Pitfalls)</h4>\n<p style=\"line-height: 1.75\">The same idea using <code>occurredAt</code> instead of a counter. It is attractive because every event already has a timestamp and no coordination is needed. It is also the pattern most likely to produce a subtle production bug, and interviewers like to probe it:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Clock skew.</strong> Two application servers with clocks 200 ms apart will order events wrongly whenever updates are closer together than the skew. NTP typically keeps machines within tens of milliseconds, but a drifting VM or a container on a busy host can be much worse. If your update frequency is comparable to your skew, timestamps are unsafe.</li>\n<li><strong>Ties.</strong> Millisecond timestamps collide constantly at scale, and a strict <code>&gt;</code> comparison silently drops the second event while <code>&gt;=</code> lets stale events overwrite. Break ties deterministically with a secondary key (producer id, a random suffix, or a UUIDv7-style value) so the outcome is at least consistent.</li>\n<li><strong>Which clock?</strong> The producer's wall clock, the broker's enqueue time, or the consumer's receive time are three different orderings. Use the <strong>producer's occurredAt</strong> — it is the only one that reflects when the fact actually happened — and record the others for debugging, never for ordering.</li>\n<li><strong>Clock moving backwards.</strong> NTP corrections and leap-second handling can move a wall clock backwards, making a later event look older. Use a monotonic source where possible, or reject timestamps more than a bounded interval in the past or future.</li>\n</ul>\n<p style=\"line-height: 1.75\">Use timestamps when events genuinely come from independent producers that cannot share a counter, when your update frequency per entity is far lower than your clock skew, and when losing a tie is acceptable. Otherwise prefer Pattern 1. A good hybrid: a database-generated sequence for events originating in your own system, timestamps only for externally sourced events.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Pattern 3 — State-Machine Guards</h4>\n<p style=\"line-height: 1.75\">Rather than comparing versions, encode the <strong>legal transitions</strong> and reject anything that arrives from an impossible prior state. An order can go <code>CREATED -&gt; PAID -&gt; SHIPPED -&gt; DELIVERED</code>, plus <code>CANCELLED</code> from <code>CREATED</code> or <code>PAID</code>. If a <code>SHIPPED</code> event arrives while the stored state is still <code>CREATED</code>, that transition is invalid — the <code>PAID</code> event has not been processed yet — and the consumer refuses it rather than corrupting the record.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"> bugs (a service emitting a transition it should not) as well as ordering artefacts, and it makes illegal states unrepresentable. The weakness is that response (a) — throw and let redelivery retry — depends on the missing message actually arriving soon, so you must bound it: after N retries the message goes to a DLQ and a human looks, because waiting forever for a message that was lost is an outage that pages nobody. Combine this with Pattern 1: the state machine validates the transition, the version guard makes the write atomic and idempotent.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Pattern 4 — Idempotent Convergent Operations</h4>\n<p style=\"line-height: 1.75\">The most elegant solution is to design the operation so that <strong>order stops mattering</strong>. Two properties do this. <strong>Idempotence</strong>: applying the same message twice equals applying it once. <strong>Commutativity</strong>: applying A then B equals applying B then A. If both hold, the queue can deliver in any order any number of times and the final state is identical.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Set-to-value, not delta.</strong> <code>setStatus(\"SHIPPED\")</code> is idempotent; <code>incrementShipCount()</code> is not. Emitting the resulting absolute state rather than the change is the single highest-leverage design choice available, and it is usually possible because the producer knows the new value.</li>\n<li><strong>Set union instead of append.</strong> Adding an element to a set is idempotent and commutative; appending to a list is neither. Modelling \"tags applied to this document\" as a set makes duplicate and out-of-order events harmless.</li>\n<li><strong>Max / min instead of assignment.</strong> <code>highWaterMark = max(stored, incoming)</code> converges regardless of arrival order — this is exactly what the version guard in Pattern 1 is doing, generalised.</li>\n<li><strong>Per-event ledgers for accumulation.</strong> When you genuinely need a sum, do not increment. Write one immutable row per event keyed by its unique event id (so a duplicate is a no-op via a primary-key conflict) and compute the balance as an aggregate, or maintain a running total updated in the same transaction as the ledger insert. Addition is commutative, so out-of-order arrival is fine; the only hazard is duplication, and the unique key kills it.</li>\n<li><strong>CRDT-style merges.</strong> For genuinely concurrent multi-writer scenarios, structures that merge deterministically (grow-only counters, last-write-wins registers with a tiebreaker) remove ordering requirements entirely, at the cost of a more complex data model.</li>\n</ul>\n<p style=\"line-height: 1.75\">In an interview, proposing this reframing before reaching for infrastructure is a strong move: \"before I choose a queue type, I would try to make these operations commutative, because then the ordering requirement disappears and I can use a standard queue with unlimited throughput.\"</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Pattern 5 — Buffering and Reordering</h4>\n<p style=\"line-height: 1.75\">Sometimes you truly need to <em>process</em> in sequence — applying a CDC stream to a replica, rendering video segments, or running a stateful pipeline where step N's output feeds step N+1. Then buffer: hold arriving messages in a small window keyed by entity, ordered by sequence number, and release them only when the next expected sequence is available or a timeout expires.</p>\n<div class=\"code\"><div class=\"code-head\"><span>typescript</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">expected = <i class=n>5</i>      <i class=f>buffer</i> (sorted): {<i class=n>7</i>, <i class=n>8</i>, <i class=n>9</i>}     <i class=v>window</i> = 2s\n\n  arrive <i class=n>7</i> -&gt; buffer, start/extend timer\n  arrive <i class=n>9</i> -&gt; buffer\n  arrive <i class=n>5</i> -&gt; emit <i class=n>5</i>; expected=<i class=n>6</i>; <i class=n>6</i> missing -&gt; wait\n  arrive <i class=n>6</i> -&gt; emit <i class=n>6</i>,<i class=n>7</i> ; expected=<i class=n>8</i> ; <i class=n>8</i> missing -&gt; wait\n  arrive <i class=n>8</i> -&gt; emit <i class=n>8</i>,<i class=n>9</i> ; expected=<i class=n>10</i>; buffer empty\n\n  timer fires <i class=k>with</i> {<i class=n>7</i>,<i class=n>8</i>,<i class=n>9</i>} and <i class=n>5</i>,<i class=n>6</i> <i class=b>never</i> <i class=a>arrived</i>:\n      -&gt; <i class=v>GAP</i> <i class=f>DECISION</i> (see below): skip and proceed, or alert and halt</code></pre></div>\n<p style=\"line-height: 1.75\">Buffering has real costs you must name: <strong>added latency</strong> (every message waits for the window in the worst case), <strong>state in the consumer</strong> (so the buffer must live somewhere durable, or a crash loses it and you must re-derive from redelivery), and <strong>an unbounded-growth failure mode</strong> if the missing message never arrives. Keep the window small (hundreds of milliseconds to a few seconds), cap the buffer size, and make sure buffered messages have their visibility extended or they will be redelivered while you are still holding them. This is the pattern of last resort, not first.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Partitioned Processing — The DIY Message Group</h4>\n<p style=\"line-height: 1.75\">Rather than sequencing at the data layer, you can sequence at the routing layer: hash the entity id to one of N queues or N workers so that every event for one entity is handled serially by one consumer, while different entities run in parallel. This is exactly what Kafka partitions and FIFO message groups do internally, built by hand.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" <strong>Rebalancing</strong>: when a worker dies, something must reassign its shard, and if two workers ever believe they own shard 7 you have lost your ordering guarantee — so you need leases or a coordinator (DynamoDB conditional-write leases with heartbeats, ZooKeeper, or a consumer group protocol), and a lease must expire before reassignment, which means downtime for that shard. <strong>Hot partitions</strong>: one enormous customer can saturate a single shard while fifteen sit idle, and the fix (a compound key, or splitting that tenant across sub-shards) sacrifices strict ordering for that tenant. <strong>Resharding</strong>: changing N rehashes everything, so in-flight events for a customer can be split across the old and new shard and processed out of order — mitigate with consistent hashing, a drain-per-shard cutover, or by choosing N generously up front. <strong>Operational weight</strong>: sixteen queues means sixteen sets of alarms, DLQs and dashboards. The honest conclusion: if you find yourself building this, first check whether SQS FIFO with a fine-grained group id already gives you it for free — because it does, without any of the rebalancing or resharding problems.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Outbox Pattern with Monotonic Sequence Numbers</h4>\n<p style=\"line-height: 1.75\">All of the above depends on the producer emitting a reliable sequence, which is exactly what a naive \"update the database, then publish\" cannot do: it can lose events on a crash between the two steps, and it can publish out of order when two concurrent transactions interleave. The <strong>transactional outbox</strong> fixes both. In the same database transaction as the business change, insert a row into an outbox table carrying an entity-scoped, monotonically increasing sequence number. A separate relay reads the outbox in sequence order and publishes.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=k>BEGIN</i>;\n  <i class=k>UPDATE</i> customers <i class=k>SET</i> address <i class=o>=</i> <i class=s>&#x27;C&#x27;</i>, version <i class=o>=</i> version <i class=o>+</i> <i class=n>1</i>\n    <i class=k>WHERE</i> id <i class=o>=</i> <i class=n>42</i> <i class=k>AND</i> version <i class=o>=</i> <i class=n>2</i>;            <i class=c>-- optimistic lock: serialises writers</i>\n  <i class=c>-- affected rows = 0 =&gt; someone else won, abort and retry</i>\n\n  <i class=k>INSERT INTO</i> outbox (aggregate_id, seq, type, payload, published)\n    <i class=k>VALUES</i> (<i class=n>42</i>, <i class=n>3</i>, <i class=s>&#x27;AddressChanged&#x27;</i>, <i class=s>&#x27;{&quot;address&quot;:&quot;C&quot;}&#x27;</i>, <i class=l>false</i>);\n                       <i class=o>^</i><i class=o>^</i><i class=o>^</i> <i class=o>=</i> the customer<i class=s>&#x27;s NEW version: monotonic BY CONSTRUCTION\nCOMMIT;\n\nrelay: SELECT * FROM outbox WHERE published = false\n       ORDER BY aggregate_id, seq LIMIT 500;   -- publish in order, mark published\n       (or read the DB change stream / CDC instead of polling)</i></code></pre></div>\n<p style=\"line-height: 1.75\">Three things make this work. The sequence is the entity's own <strong>optimistic-locking version</strong>, so concurrent writers cannot both produce version 3 — one transaction fails and retries. The event and the state change commit atomically, so there is no lost-event window. And the relay is <strong>at-least-once</strong>, which is fine precisely because every downstream consumer has the version guard from Pattern 1. Note the ordering subtlety in the relay: it must order by <code>(aggregate_id, seq)</code>, and if it publishes concurrently across aggregates that is fine, but publishing two rows for the <em>same</em> aggregate concurrently can invert them on the wire — which again only matters if consumers lack a version guard. Modern implementations often replace polling with CDC (DynamoDB Streams, Postgres logical replication, Debezium), which preserves commit order for free.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Detecting and Handling Gaps</h4>\n<p style=\"line-height: 1.75\">Once messages carry sequence numbers you get a free integrity check: the consumer knows it processed version 5 and then sees version 7, so version 6 is missing. What to do next depends entirely on the semantics:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Proceed immediately</strong> when updates are full-state replacements. If version 7 contains the complete current state, version 6 is irrelevant — it was superseded. Record a metric and move on. This is the common case and the reason full-state events are preferable to deltas.</li>\n<li><strong>Wait, briefly and boundedly</strong>, when events are deltas or the state machine needs the intermediate step. Hold in the reorder buffer for a short window; if it arrives, proceed; if not, escalate. Never wait unbounded — that converts a lost message into a stalled pipeline.</li>\n<li><strong>Reconcile from source</strong> after the window expires: fetch the authoritative current state for that entity directly from the owning service or database and reset the local version to match. This is the most robust answer for critical data because it does not depend on the missing message ever arriving, and it is why entity-level reconciliation jobs are worth building.</li>\n<li><strong>Alert and halt</strong> for financial or compliance data where proceeding with a known gap is unacceptable. Park the entity, emit a high-severity alarm, and let a human decide.</li>\n</ul>\n<p style=\"line-height: 1.75\">And remember that a gap is not always loss: it can mean the message is still in flight, was filtered out upstream by a routing rule, was consumed by a different consumer group, or that a sequence number was allocated by a transaction that then rolled back. That last one is a classic — if your sequence comes from a database sequence rather than a committed version column, rolled-back transactions leave permanent holes, so your gap alarm must tolerate them.</p>\n<h4 style=\"margin-top: 1.5rem;
