This topic gives you a decision you can defend in an interview and in a design review.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The choice is permanent</h4>\n<p style=\"line-height: 1.75\">The queue type is fixed at creation time and <strong>cannot be changed afterwards</strong>. There is no \"convert to FIFO\" button, no API call, no support ticket. If you picked wrong, you create a new queue of the correct type, point producers at it, drain the old one, and delete it. FIFO queues also have a naming rule enforced by the API: the name must end in <code>.fifo</code>, for example <code>payments.fifo</code>. That suffix counts toward the 80-character name limit.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Standard queues: fast, and honest about it</h4>\n<p style=\"line-height: 1.75\">A standard queue gives you nearly unlimited throughput — you do not provision capacity, you simply send, and SQS scales behind the scenes. In exchange, it makes two deliberately modest promises.</p>\n<p style=\"line-height: 1.75\"><strong>At-least-once delivery</strong> means every message is delivered at least once, and occasionally more than once. Here is the honest reason, and it is worth being able to explain: for durability, SQS stores each message redundantly on multiple servers across multiple Availability Zones. When a consumer receives and deletes a message, the delete has to reach all of those copies. In rare cases — a server being unreachable at exactly the wrong moment — one copy does not learn about the delete in time and hands the message out again. The same durability that stops you losing messages is what occasionally produces a duplicate. It is uncommon, but it is guaranteed to happen eventually at volume.</p>\n<p style=\"line-height: 1.75\"><strong>Best-effort ordering</strong> means messages usually arrive in roughly the order they were sent, but this is not guaranteed. Because messages are spread across many servers, a message sent second can reasonably be handed out first. A FIFO queue guarantees ordering — but crucially, <em>within a message group</em>, not across the whole queue. It also offers <strong>exactly-once processing</strong>: within a five-minute <strong>deduplication window</strong>, if the same message is sent twice, SQS accepts the first and silently discards the second, and a message that has been received is not delivered again while it is in flight.</p>\n<p style=\"line-height: 1.75\">Two FIFO-only concepts make this work. You meet them here and study them in depth later:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Message group ID</strong> — the ordering key. Every message sent to a FIFO queue must carry one. SQS guarantees that messages sharing a group ID are delivered in order and that only one message from a group is in flight at a time. Different groups are processed independently and in parallel, so the group ID is also your parallelism knob: one group means strictly serial processing, ten thousand groups (say, one per user ID) means heavy parallelism with per-user ordering.</li>\n<li><strong>Message deduplication ID</strong> — the duplicate key. If two messages with the same deduplication ID arrive within the 5-minute window, the second is accepted by the API but never delivered. You can supply it yourself (ideally a natural business key like the order ID) or enable <strong>content-based deduplication</strong>, which makes SQS hash the message body and use that as the ID.</li>\n</ul>\n<p style=\"line-height: 1.75\">The price is throughput. font-size: 1.25rem; font-weight: 600\">Standard is the right default</h4>\n<p style=\"line-height: 1.75\">This is the honest guidance, and it surprises people who assume the stricter option is the safer one. For the overwhelming majority of background work — sending emails, processing images, generating reports, firing webhooks, re-indexing search documents — order genuinely does not matter and duplicates are cheap to defend against. Standard gives you unlimited throughput, lower cost, no head-of-line blocking, and simpler producer code.</p>\n<p style=\"line-height: 1.75\">Choose FIFO only when order or strict deduplication genuinely changes the outcome. Good reasons include: financial transactions that must be applied in sequence (a deposit then a withdrawal is not the same as a withdrawal then a deposit); a command stream for one user or one IoT device where \"turn on\" then \"turn off\" reversed is a real bug; and inventory adjustments where a reserve-then-release ordering matters. Notice that all three examples have a natural grouping key — account ID, user ID, device ID, SKU — which is exactly what the message group ID is for.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The engineering consequence: you must be idempotent</h4>\n<p style=\"line-height: 1.75\"><strong>Idempotent</strong> means processing the same message twice produces the same result as processing it once. This is not optional advice for standard queues — at-least-once delivery makes duplicates a certainty over time, and a duplicate that is not handled is a real, customer-visible bug.</p>\n<p style=\"line-height: 1.75\">Take the concrete disaster. A message says \"charge customer 42 nineteen dollars for order 8821\". Your worker calls the payment provider, the charge succeeds, and then the worker crashes before deleting the message. The message reappears, another worker picks it up, and the customer is charged twice. Alternatively, SQS simply delivers the message twice all on its own. Either way, a naive handler double-charges.</p>\n<p style=\"line-height: 1.75\">The fix is an <strong>idempotency key</strong>: a stable identifier derived from the business fact, not from the message delivery. For a charge, use the order ID. Before doing the work, record the key in a store with a uniqueness constraint — a DynamoDB conditional write on the key as the partition key, or a UNIQUE column in a relational table. If the write succeeds, you are the first to process this fact, so do the work. If it fails because the key already exists, this is a duplicate, so skip the work and delete the message. Good payment providers also accept an idempotency key of their own, so you can pass the order ID straight through and let them collapse the duplicate.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=k>NOT</i> IDEMPOTENT                    IDEMPOTENT\n\nreceive &quot;charge 8821&quot;             receive &quot;charge 8821&quot;\n  charge_card(<i class=n>19.00</i>)                try: claim key &quot;charge:8821&quot;\n  <i class=k>delete</i> message                    <i class=o>|</i><i class=c>-- claimed  -&gt; charge_card(19.00)</i>\n                                    <i class=o>|</i><i class=c>-- already claimed -&gt; skip silently</i>\nduplicate arrives                   <i class=k>delete</i> message\n  charge_card(<i class=n>19.00</i>)  <i class=o>&lt;</i><i class=c>-- BUG!</i>\n                                  duplicate arrives\n                                    claim fails <i class=o>-</i><i class=o>&gt;</i> <i class=k>skip</i> <i class=o>-</i><i class=o>&gt;</i> delete.
