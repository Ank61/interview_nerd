{"title":"Consuming Messages — Lambda, Containers, and EC2 Workers","tags":["SQS","Lambda","Auto Scaling","Consumers"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Putting messages into a queue is the easy half. The interesting engineering is on the consumer side: something has to take messages out, do the work, and delete them — reliably, at the right speed, without melting the database behind it. There are two mainstream ways to build that, and knowing when to pick each is a standard interview question.</p>\n<p style=\"line-height: 1.75\">Option one is <strong>AWS Lambda</strong>, where AWS polls the queue for you and calls your function with a handful of messages. Option two is a <strong>long-running worker</strong> — a container on ECS or Kubernetes, or a process on an EC2 virtual machine — that runs its own loop. We will build up both, then compare.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Model 1: Lambda with an event source mapping</h4>\n<p style=\"line-height: 1.75\">An <strong>event source mapping</strong> is a small piece of configuration that connects a queue to a Lambda function. Behind the scenes AWS runs a fleet of pollers that call <code>ReceiveMessage</code> on your queue and invoke your function with a <strong>batch</strong> — a group of messages delivered in one invocation, up to 10 by default and up to 10,000 for standard queues when a batch window is configured. Larger batches mean fewer invocations, fewer API requests and lower cost, but one bad message affects more work.</li>\n<li><strong>Batch window</strong> (<code>MaximumBatchingWindowInSeconds</code>): how long Lambda waits, up to 300 seconds, to accumulate a fuller batch before invoking. Zero means invoke as soon as messages are available.</li>\n</ul>\n<p style=\"line-height: 1.75\">This is a straight <strong>latency versus efficiency</strong> trade-off. A batch window of 0 with a batch size of 1 gives the lowest latency and the highest cost per message. A window of 20 seconds with a batch size of 100 batches aggressively and costs far less per message, but a message can wait 20 seconds before anyone looks at it. Choose by asking what the message is: a user-visible notification wants a small window; a nightly analytics ingest wants a large one.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The visibility timeout rule</h4>\n<p style=\"line-height: 1.75\">The <strong>visibility timeout</strong> is how long a message stays hidden from other consumers after being received. If your function is still working when it expires, the message becomes visible again and gets processed <em>a second time in parallel</em> — duplicate charges, duplicate emails.</p>\n<p style=\"line-height: 1.75\">The rule: <strong>the queue's visibility timeout must be meaningfully larger than the function timeout</strong>, and AWS recommends at least <strong>six times</strong> it. The multiplier exists because a batch may be retried by the same poller, and because Lambda may need extra time around the invocation. If your function times out at 30 seconds, set the visibility timeout to 180 seconds. This one mismatch is probably the single most common cause of \"why is my Lambda processing everything twice?\"</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Success, failure, and the partial batch failure trap</h4>\n<p style=\"line-height: 1.75\">If your function <strong>returns normally</strong>, Lambda deletes every message in the batch for you. If your function <strong>throws or times out</strong>, Lambda deletes nothing — the entire batch becomes visible again and is retried, each message's receive count increments, and messages that exceed <code>maxReceiveCount</code> go to the dead-letter queue.</p>\n<p style=\"line-height: 1.75\">That default is dangerous with batches. Suppose a batch of 10 messages arrives, nine succeed and the tenth throws. Because your function threw, <strong>all ten</strong> come back — including the nine that already ran. If those nine sent emails, nine customers get a second email on every retry.</p>\n<p style=\"line-height: 1.75\">The fix is <strong>partial batch failure reporting</strong>. Set the event source mapping's <code>FunctionResponseTypes</code> to <code>[\"ReportBatchItemFailures\"]</code>, then have your handler catch errors per message and return an object listing only the failed message IDs: <code>{ batchItemFailures: [ { itemIdentifier: \"&lt;messageId&gt;\" } ] }</code>. Lambda deletes everything not listed and returns only the listed messages to the queue. Two gotchas: returning an empty list means \"all succeeded\", and if you enable the feature but return nothing at all, Lambda treats the batch as fully successful and may delete messages you failed to process. For FIFO queues, report the failed message and every message after it in that group so ordering survives.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Scaling behaviour and protecting the downstream</h4>\n<p style=\"line-height: 1.75\"><strong>Concurrency</strong> means how many copies of your function run at the same time. With an SQS trigger, Lambda starts with a small number of concurrent pollers and, while the backlog keeps growing, adds more — increasing concurrency in steps each minute up to your account limit. This is wonderful for absorbing a spike and terrifying if there is a small relational database behind the function, because hundreds of concurrent executions will open hundreds of connections and take it down.</p>\n<p style=\"line-height: 1.75\">Two controls exist:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Reserved concurrency</strong> — a function-level cap on how many copies may run. It protects the downstream, but it is a blunt instrument: once the cap is reached, Lambda's pollers can still receive messages and get <strong>throttled</strong> (rejected for exceeding the limit), which increments receive counts and can push perfectly good messages into the dead-letter queue.</li>\n<li><strong>Maximum concurrency on the event source mapping</strong> (<code>ScalingConfig.MaximumConcurrency</code>, from 2 to 1,000) — the better modern control. It caps how many concurrent invocations this <em>mapping</em> creates, so Lambda simply polls less instead of over-reading and throttling. No spurious DLQ traffic, and other triggers on the same function are unaffected.</li>\n</ul>\n<p style=\"line-height: 1.75\">Rule of thumb: use maximum concurrency on the event source mapping to pace an SQS consumer; use reserved concurrency when you need an account-wide guarantee about a function's share of capacity.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Model 2: container or EC2 workers</h4>\n<p style=\"line-height: 1.75\">A long-running worker owns its loop.
