Set between 2 and 1,000; the pollers themselves stop pulling, so messages remain visible with untouched receive counts. No throttles, no spurious dead letters. It is a single API call, so it is also the right emergency lever mid-incident.</li>\n<li><strong>Reserved concurrency on the function.</strong> A blunter instrument. It caps executions and carves a guaranteed share out of the account pool — useful for isolating a critical function — but the pollers do not respect it, so they keep invoking and Lambda throttles them. Each throttle increments <code>ApproximateReceiveCount</code> and pushes healthy messages toward the DLQ. Use it for isolation, not for pull-rate control.</li>\n<li><strong>Worker fleet size and per-worker thread counts.</strong> For ECS or EC2 consumers, effective concurrency is tasks multiplied by threads per task. Both must be bounded, and the second one is the one teams forget: scaling from 10 to 40 tasks while each task runs 25 worker threads takes you from 250 to 1,000 concurrent downstream calls. Always compute the product, and set autoscaling <code>MaxCapacity</code> from the downstream's capacity, not from the backlog you wish would disappear.</li>\n<li><strong>Explicit client-side rate limiting.</strong> Concurrency limits bound simultaneous work; they do not bound the request rate if calls are fast. If the downstream limit is expressed in requests per second — a third-party API allowing 100 rps, a database you have measured at 500 writes per second — you need an actual rate limiter, not just a concurrency cap.</li>\n</ul>\n<p style=\"line-height: 1.75\">Also worth naming as a coarse control: <strong>connection pooling</strong> (RDS Proxy in front of a relational database converts unbounded Lambda connections into a bounded pool), and <strong>batching</strong>, which raises throughput per unit of downstream load — one 500-row bulk insert instead of 500 single inserts — and is the only lever that improves both sides of the trade at once.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Rate limiting: token buckets and where to put them</h4>\n<p style=\"line-height: 1.75\">A <strong>token bucket</strong> is the standard implementation: tokens refill at a steady rate (the sustained limit), the bucket has a maximum size (the allowed burst), and each call consumes a token, blocking or shedding when empty. It is preferred over a fixed-window counter because fixed windows permit double the limit across a window boundary.</p>\n<p style=\"line-height: 1.75\">Placement is the real question. An <strong>in-process limiter</strong> is simple, adds zero latency, and works when the fleet is fixed and you can divide the global limit by the instance count — but it breaks the instant the fleet autoscales, because ten instances each allowed 10 rps become forty instances allowed 400 rps. A <strong>distributed limiter</strong> in ElastiCache for Redis (atomic <code>INCR</code> with an expiry, or a Lua script for a true token bucket) or DynamoDB (a conditional update on a counter item) enforces a genuine global limit at the cost of a network round trip per message and a new dependency in the hot path — one that must fail open or closed by explicit decision, because a Redis outage that fails closed stops all processing while failing open removes all protection.</p>\n<p style=\"line-height: 1.75\">The pragmatic hierarchy: prefer <strong>bounding concurrency</strong> where the downstream constraint is connections or parallelism (almost all databases); use a <strong>distributed rate limiter</strong> where the constraint is genuinely a published requests-per-second quota; and for Lambda specifically, remember that <code>MaximumConcurrency</code> divided by average handler duration is already an approximate rate limit — 50 concurrency at 100 ms per message is roughly 500 messages per second, and tuning that is usually cheaper than adding Redis to the critical path.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Queue-depth-driven autoscaling, done properly</h4>\n<p style=\"line-height: 1.75\">Scaling on <code>ApproximateNumberOfMessagesVisible</code> alone is a poor signal, and this is a favourite interview probe. Scaling harder is not available (the downstream is the constraint), so the remaining choice is <em>which</em> work to do. Doing nothing is also a choice, and usually the worst one.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Shed by value.</strong> Separate queues by priority and starve or pause the low-value one during overload. Recommendation refreshes and analytics events can wait; payment captures and password resets cannot. This requires the separation to exist <em>before</em> the incident — you cannot split a queue during an outage.</li>\n<li><strong>Discard stale work using message age.</strong> Compute age from <code>SentTimestamp</code> in the message attributes and drop or divert messages older than their useful lifetime. A push notification about a flash sale that ended is negative value — delivering it costs money and annoys the user. Rejecting early — with the message returned to the queue or quarantined — is strictly better than a timeout, because a timeout costs the full timeout duration on both sides.</li>\n<li><strong>Degrade instead of dropping.</strong> Often there is a cheaper path: skip the enrichment call, write a minimal record, emit a follow-up event for later reconciliation. Shedding does not have to mean losing.</li>\n</ul>\n<p style=\"line-height: 1.75\">Whatever you shed must be <strong>counted and alarmed</strong>. Silent shedding is indistinguishable from a bug, and the first person to notice will be a customer.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Latency versus throughput</h4>\n<p style=\"line-height: 1.75\">Nearly every flow-control knob trades one for the other, and being explicit about which you are optimizing is the mark of a considered design. Long polling (<code>ReceiveMessageWaitTimeSeconds</code> of 20) costs up to 20 seconds of latency on an empty queue but eliminates empty-receive charges and is essentially free on a busy one. A <strong>batching window</strong> of 30 seconds adds up to 30 seconds of latency per message and can cut invocation counts by orders of magnitude while enabling bulk downstream writes. Larger batches amortise cold starts and connection setup but widen the blast radius of a failure and increase the memory footprint. Lower concurrency protects the downstream and lengthens drain time.</p>\n<p style=\"line-height: 1.75\">The useful framing is that <strong>latency is what you spend and stability is what you buy</strong>, and the exchange rate depends on the workload. For an analytics pipeline with an hourly SLO, a 5-minute batching window costs nothing anyone can perceive and saves a great deal. For a password-reset email, 30 seconds of batching is a support ticket. Without backoff and jitter the retries also synchronize into waves.
