When the call returns successfully, the message is <strong>durably stored</strong> — written to disk on multiple servers across multiple Availability Zones. If your process dies one millisecond later, the message is still there.</p>\n<p style=\"line-height: 1.75\">SQS returns two things worth knowing. A <strong>MessageId</strong>, a unique identifier SQS assigns to this message that stays with it for its whole life and is useful for logging and tracing. And an <strong>MD5OfMessageBody</strong>, a checksum of the body you sent — you can compute the MD5 of your own string and compare, verifying that SQS received exactly the bytes you sent and nothing was corrupted in transit. (Most SDKs check this for you automatically.)</p>\n<p style=\"line-height: 1.75\"><strong>SendMessageBatch</strong> sends up to <strong>10 messages in a single API call</strong>, subject to a combined payload limit of 256 KB. This is both faster (one network round trip instead of ten) and cheaper (SQS bills per API request, so batching ten messages costs one request instead of ten). Each entry needs its own <code>Id</code> that is unique within the batch — this is just a label so the response can tell you which entries succeeded and which failed. Batch calls can <strong>partially succeed</strong>: the response has a <code>Successful</code> list and a <code>Failed</code> list, and it is a classic bug to ignore the failed list and assume everything went through.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Step 2: ReceiveMessage — and the critical insight</h4>\n<p style=\"line-height: 1.75\">Here is the thing to internalise: <strong>receiving a message does not remove it from the queue.</strong> ReceiveMessage returns a copy of the message to your consumer and, at the same instant, makes the message <strong>invisible</strong> — hidden from every other consumer — for a period called the <strong>visibility timeout</strong> (30 seconds by default). The message is still sitting in the queue the whole time. It is just temporarily hidden so two workers do not do the same job simultaneously. Messages in this state are called <strong>in flight</strong>.</p>\n<p style=\"line-height: 1.75\">Along with the body, each received copy comes with a <strong>ReceiptHandle</strong> — a long, opaque, temporary token that identifies <em>this particular receive of this particular message</em>. It is not an identifier of the message itself; it is your ticket proving you are the consumer currently holding it. You need it for DeleteMessage and ChangeMessageVisibility.</p>\n<p style=\"line-height: 1.75\">Crucially, the receipt handle is <strong>different every time the message is received</strong>. If your worker holds a message, the visibility timeout expires, another worker receives it and gets a brand-new receipt handle, and then your slow worker finally tries to delete with its old handle — the delete either fails or is ignored. This is a safety feature: an old receipt handle cannot delete a message you no longer own. It is also why a delete that \"silently did nothing\" is usually a sign your visibility timeout is too short.</p>\n<p style=\"line-height: 1.75\">Two parameters shape the receive call:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>MaxNumberOfMessages</strong> (1 to 10, default 1). How many messages you are willing to accept in this call. Asking for 10 reduces your API calls tenfold.</li>\n<li><strong>WaitTimeSeconds</strong> (0 to 20). Zero is <strong>short polling</strong>; anything above zero is <strong>long polling</strong>, where SQS holds the request open until a message appears or the wait expires. Set it to 20 on essentially every queue.</li>\n</ul>\n<p style=\"line-height: 1.75\">Now the surprise that catches everyone: <strong>SQS may return fewer messages than you asked for — even zero — while the queue is not empty.</strong> This is not a bug. SQS stores messages across a large fleet of servers, and a receive request samples a subset of them. With short polling it samples only some servers, so it may genuinely miss messages that exist. Even with long polling, a call may return fewer than MaxNumberOfMessages. The correct mental model is: an empty response means \"nothing was found on this attempt\", never \"the queue is empty\". Your loop must simply poll again rather than deciding it is done. If you truly need to know how many messages are waiting, read the <code>ApproximateNumberOfMessages</code> attribute — and note the word \"approximate\", which is honest for the same reason.</p>\n<p style=\"line-height: 1.75\">You can also ask for system attributes on a receive. Think of it not as cleanup but as an explicit statement: <em>\"I have successfully finished this work; nobody needs to do it again.\"</em></p>\n<p style=\"line-height: 1.75\">From that follows the fundamental design principle of SQS consumers: <strong>delete only after successfully processing</strong>. If the worker crashes mid-work — the process is killed, the instance is terminated, the container is redeployed — no delete happens, the visibility timeout expires, the message becomes visible again, and another worker retries it. That is not an accident or a fallback; it is precisely the mechanism by which SQS guarantees work is not lost. Deleting early converts every crash into silent data loss.</p>\n<p style=\"line-height: 1.75\"><strong>DeleteMessageBatch</strong> deletes up to 10 messages in one call using their receipt handles, with the same partial-success semantics as SendMessageBatch.
