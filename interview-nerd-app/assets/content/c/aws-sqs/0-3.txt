It is the setting that decides whether a crashed worker's job gets retried, whether your customers get one confirmation email or three, and whether a Lambda function processes the same message forever. It is also the setting most often left at its default without anybody thinking about it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What it is, in plain words</h4>\n<p style=\"line-height: 1.75\">When a consumer receives a message, SQS does not delete it. Instead it <strong>hides the message from every other consumer for a fixed period</strong>. That period is the <strong>visibility timeout</strong>. During it, the receiving consumer has exclusive time to do the work and call <code>DeleteMessage</code>. The message is said to be <strong>in flight</strong>.</p>\n<p style=\"line-height: 1.75\">The point is to stop two workers doing the same job at the same time, without SQS having to know anything about whether your work succeeded. SQS's rule is beautifully simple: <em>if you do not delete the message before the clock runs out, I assume you failed, and I give it to somebody else.</em></p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Default:</strong> 30 seconds.</li>\n<li><strong>Range:</strong> 0 seconds to 12 hours (43,200 seconds), which is also the maximum total time a single message can stay invisible.</li>\n<li><strong>Where it is set:</strong> on the queue (the <code>VisibilityTimeout</code> attribute, applying to every message by default), or overridden <strong>per receive call</strong> with the <code>VisibilityTimeout</code> parameter of ReceiveMessage, or adjusted for an in-flight message with <code>ChangeMessageVisibility</code>.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The happy path and the two failure paths</h4>\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">HAPPY PATH  (visibility <i class=b>timeout</i> = 30s, work takes 12s)\n\n  t=0   ReceiveMessage  -&gt; message hidden <i class=k>until</i> t=30\n        |&lt;------------- invisible -------------&gt;|\n  t=0   <i class=c>##### work #####</i>\n  t=12  DeleteMessage   -&gt; message gone. If a job takes 5 seconds on average but the p99 is 50 seconds because some images are enormous and a downstream API occasionally takes 30 seconds to respond, a 30-second timeout will produce duplicates for 1% of your traffic, and 1% at scale is a lot of angry customers.</p>\n<p style=\"line-height: 1.75\">Measure your p99 (or p99.9) processing duration, add headroom for retries and network slowness inside your handler, and set the timeout from that. For a job whose p99 is 50 seconds, something like 180 seconds is a sensible starting point.</p>\n<p style=\"line-height: 1.75\">But do not simply set it to 12 hours and forget it, because the trade-off runs in both directions. The timeout is also your <strong>failure detection time</strong>. If a worker dies one second after receiving a message and the timeout is two hours, that message sits invisible — untouched, unprocessed, invisible to every other worker — for the remaining one hour and fifty-nine minutes before anyone can retry it. Your recovery from a crash is exactly as slow as your timeout is long. Setting the queue timeout to the worst imaginable case penalises every fast job with slow crash recovery.</p>\n<p style=\"line-height: 1.75\">The right pattern is <strong>heartbeating</strong>: keep the queue timeout modest, and while the worker is genuinely busy, call <code>ChangeMessageVisibility</code> periodically to push the deadline out in increments. Every 30 seconds, extend to 90 seconds from now. The worker is effectively saying \"still alive, still working.\" The moment the worker dies, the heartbeats stop, the remaining window lapses, and the message is retried within about 90 seconds rather than hours later. You get both long jobs and fast failure detection — which one enormous timeout can never give you.</p>\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">HEARTBEATING (queue <i class=b>timeout</i> 60s, job takes 5 minutes)\n\n  t=0    receive            hidden <i class=k>until</i> t=60\n  t=30   heartbeat: <i class=b>set</i> 90  hidden <i class=k>until</i> t=120\n  t=60   heartbeat: <i class=b>set</i> 90  hidden <i class=k>until</i> t=150\n  t=90   heartbeat: <i class=b>set</i> 90  hidden <i class=k>until</i> t=180\n  ...\n  t=300  work <i class=k>done</i> -&gt; DeleteMessage\n\n  If the worker dies at t=95, the last heartbeat expires at t=180\n  and the message is retried ~85 seconds later -- not 5 hours later.\n\n  (Total invisibility <i class=k>for</i> one message still caps at 12 hours.)</code></pre></div>\n<p style=\"line-height: 1.75\">The mirror image is equally useful: <strong>set the visibility timeout to 0</strong> to release a message immediately when the worker knows it cannot process it — a dependency is down, a feature flag is off, the payload version is unsupported. Instead of the message sitting hidden for the full timeout, it becomes available instantly for another worker or a later retry. Doing nothing and waiting for the timeout is a slower, worse version of the same outcome.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Lambda interaction (a very common exam and interview point)</h4>\n<p style=\"line-height: 1.75\">When SQS triggers Lambda, you create an <strong>event source mapping</strong> — an AWS-managed poller that calls ReceiveMessage on your behalf, invokes your function with a batch of messages, and deletes them automatically if the function returns successfully. You do not write the receive/delete loop.</p>\n<p style=\"line-height: 1.75\">The mapping expects the <strong>queue's visibility timeout to be meaningfully larger than the function timeout</strong>. AWS's own guidance is to set the queue visibility timeout to at least <strong>six times</strong> the function timeout. The multiplier exists because a single invocation is not the whole story: the poller may retry an invocation after a throttle or an error, and the batch needs to stay hidden across those attempts plus the poller's own processing overhead. With a batch window configured, add that window to the calculation too.</p>\n<p style=\"line-height: 1.75\">If the visibility timeout is too short, the failure mode is nasty and self-inflicted. Suppose the function timeout is 60 seconds and the queue visibility timeout is left at the 30-second default. At t=30 the message becomes visible again while the function is still running; the poller receives it again and invokes a second concurrent execution on the same message; at t=60 that one reappears too. You get the same message processed repeatedly, rising concurrency, duplicate side effects, and a bill to match. With a 60-second function, a 360-second visibility timeout is the safe configuration. You wire it up with a <strong>redrive policy</strong> on the source queue containing the DLQ's ARN and a <strong>maxReceiveCount</strong>.</p>\n<p style=\"line-height: 1.75\">Here is the connection people miss: <strong>every time the visibility timeout expires and the message reappears, its ApproximateReceiveCount increases by one.</strong> The counter measures receives, not failures — SQS has no idea whether your code succeeded, only whether the message was deleted. So a visibility timeout that is too short burns through maxReceiveCount on messages that were being processed perfectly well, and perfectly healthy messages end up in the DLQ. Meanwhile a very long timeout means a truly broken message takes maxReceiveCount multiplied by the timeout to reach the DLQ — with maxReceiveCount of 5 and a 2-hour timeout, that is over ten hours before anyone sees it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Diagnosing \"my messages are being processed multiple times\"</h4>\n<p style=\"line-height: 1.75\">Work through these causes in order — this is the sequence an interviewer wants to hear.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>1. Is processing time exceeding the visibility timeout?</strong> By far the most common cause. Log your processing duration and the <code>ApproximateReceiveCount</code>. If durations approach or exceed the timeout and the receive count is climbing, this is it. Fix by raising the timeout to above p99, or by heartbeating.</li>\n<li><strong>2. Are you actually deleting the message?</strong> Check that DeleteMessage is called on every successful path, that you use the <strong>receipt handle</strong> and not the message ID, and — for batch deletes — that you inspect the <code>Failed</code> list. A delete that quietly failed looks exactly like a duplicate.</li>\n<li><strong>3. Is the delete happening but with a stale receipt handle?</strong> If the timeout already expired, your handle is no longer valid and the delete does not remove the message somebody else now holds. This is really symptom 1 wearing a disguise.</li>\n<li><strong>4. Is the worker crashing after the side effect but before the delete?</strong> The email really was sent and then the process died. The retry is correct SQS behaviour; the fix is <strong>idempotency</strong>, not a queue setting.</li>\n<li><strong>5. Lambda specifically: is the visibility timeout at least 6x the function timeout?</strong> If not, the poller is re-invoking on messages still in progress.</li>\n<li><strong>6. Is it simply at-least-once delivery?</strong> Standard queues occasionally deliver a message twice on their own. If the receive count is 1 on both copies and durations are healthy, this is SQS working as documented.</li>\n<li><strong>7. Is the producer sending twice?</strong> A retried HTTP request, a client-side retry, or two code paths publishing the same event. Check the MessageIds — two different MessageIds with the same business payload means a producer problem, not a consumer one.</li>\n</ul>\n<p style=\"line-height: 1.75\">Underlying all seven: no visibility-timeout setting makes duplicates impossible. Sizing it correctly makes them rare; <strong>idempotency</strong> — processing the same message twice producing the same result as once — makes them harmless. You need both.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"The visibility timeout is how long the message lives.\"</strong> No — that is the <strong>message retention period</strong> (60 seconds to 14 days, default 4 days), which controls when SQS deletes an unprocessed message. The visibility timeout (0 to 12 hours, default 30 seconds) only controls how long a message stays hidden after being received. They are unrelated settings with unrelated ranges.</li>\n<li><strong>\"A longer timeout is always safer.\"</strong> It reduces duplicates but directly slows recovery: a worker that dies immediately leaves its message invisible and untouched for the entire remaining window, and a broken message takes far longer to reach the dead-letter queue where you would notice it.</li>\n<li><strong>\"The timeout guarantees only one consumer ever sees the message.\"</strong> It guarantees no <em>other</em> consumer sees it <em>while the timer is running</em>. Once it expires, or if SQS's at-least-once delivery produces a duplicate, a second consumer absolutely can see it. It is a best-effort lock, not a mutual-exclusion guarantee.</li>\n<li><strong>\"Visibility timeout and message retention are the same thing.\"</strong> They are commonly confused precisely because both are durations on the queue. Retention decides when SQS gives up on a message; visibility decides when SQS gives up on the consumer currently holding it.</li>\n<li><strong>\"Setting a long timeout removes the need for idempotency.\"</strong> It does not. Crashes after a side effect, at-least-once delivery, and producer retries all still produce duplicates. Idempotency is the only real defence.</li>\n<li><strong>\"ApproximateReceiveCount counts failures.\"</strong> It counts <em>receives</em>.
