A good answer starts by noticing that these products are not three versions of the same thing. Deliberately small feature surface.</li>\n<li><strong>Traditional message broker (RabbitMQ, ActiveMQ).</strong> A server program you run (or pay someone to run). There are no brokers, no partitions to plan, no version upgrades, no capacity to provision. Standard queues scale to effectively unlimited throughput, and you pay per request with nothing at idle.\n</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>At-least-once delivery.</strong> A standard queue guarantees a message is delivered at least once; occasional duplicates are normal, so consumers must be <strong>idempotent</strong> (safe to run twice with the same result). FIFO queues add ordering per <strong>message group</strong> and exactly-once processing within a 5-minute deduplication window.</li>\n<li><strong>Per-message deletion.</strong> Each message is acknowledged individually by deleting it, so one slow or failing message does not block the others — a genuinely useful property Kafka does not have.</li>\n<li><strong>DLQs and redrive.</strong> After a configured number of failed receives, a message moves to a dead-letter queue; the redrive API moves them back after you fix the bug.</li>\n<li><strong>Limits to know.</strong> 256 KB maximum message size (up to 2 GB via the Extended Client Library, which stores the payload in S3), 14-day maximum retention, no replay once deleted, no routing logic, no priorities, and it exists only on AWS.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">RabbitMQ — routing and protocol breadth</h4>\n<p style=\"line-height: 1.75\">\nRabbitMQ's defining idea is that producers do not send to queues; they send to an <strong>exchange</strong> along with a <strong>routing key</strong> (a short string label such as <code>eu.order.created</code>). The exchange decides which queues receive a copy, and its type determines how:\n</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Direct.</strong> Deliver to queues bound with an exactly matching routing key.</li>\n<li><strong>Topic.</strong> Wildcard matching — a queue bound to <code>eu.order.*</code> receives <code>eu.order.created</code> and <code>eu.order.cancelled</code> but not <code>us.order.created</code>.</li>\n<li><strong>Fanout.</strong> Copy to every bound queue, ignoring the routing key — pub/sub broadcast.</li>\n<li><strong>Headers.</strong> Match on message header values rather than the routing key.</li>\n</ul>\n<p style=\"line-height: 1.75\">\nBeyond routing, RabbitMQ offers <strong>message priorities</strong> (a genuinely higher-priority message jumps the line — SQS has no equivalent), <strong>per-message TTL</strong> and expiry, dead-letter exchanges, built-in <strong>request-reply</strong> support, and <strong>acknowledgements with prefetch</strong>: a consumer says \"send me at most 20 unacknowledged messages\", which is a clean form of <strong>backpressure</strong> — the mechanism by which a slow consumer tells the system to send less rather than being overwhelmed. It speaks <strong>AMQP 0-9-1</strong> natively and supports <strong>MQTT</strong>, <strong>STOMP</strong> and others through plugins, which matters enormously if you have IoT devices or existing enterprise clients.\n</p>\n<p style=\"line-height: 1.75\">\nTwo updates to dated claims. First, RabbitMQ has had <strong>streams</strong> since version 3.9 — an append-only, replayable log-like structure with non-destructive reads, so \"RabbitMQ cannot do replay\" is no longer accurate, though its streams are less mature and less ecosystem-rich than Kafka's. Second, RabbitMQ's clustering has improved substantially with <strong>quorum queues</strong> (Raft-based replication). Still, the honest statement is that RabbitMQ is <em>not horizontally elastic in the way SQS is</em>: you size nodes, deep queues hurt performance, and very high throughput or cross-region setups take real engineering. Amazon MQ for RabbitMQ removes the install-and-patch work but not the sizing and capacity thinking.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Apache Kafka and Amazon MSK — the distributed log</h4>\n<p style=\"line-height: 1.75\">\nKafka organises data into <strong>topics</strong>, and each topic is split into <strong>partitions</strong> — independent ordered sequences that allow parallel processing. A record's key decides its partition, so all records for one key land in one partition and stay in order relative to each other. <strong>Ordering is guaranteed per partition, never across the whole topic</strong>; that is the single most important Kafka fact.\n</p>\n<p style=\"line-height: 1.75\">\nEach record in a partition has an <strong>offset</strong> — its position number. A <strong>consumer group</strong> is a set of consumers cooperating to read a topic; the group tracks its own committed offsets, and partitions are divided among its members so each partition is read by exactly one member of that group. Crucially, <strong>different consumer groups are completely independent</strong>: the analytics group and the fraud group both read every record, each at its own position. Because records are retained by time or size rather than deleted on read, a group can reset its offsets and <strong>replay</strong> history — reprocess yesterday's data after fixing a bug, or bootstrap a brand-new service from the beginning of time.\n</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Throughput.</strong> Sequential disk writes and batching give Kafka very high sustained throughput — hundreds of MB/s per broker is routine. This is its strongest technical claim.</li>\n<li><strong>Log compaction.</strong> A retention mode that keeps at least the latest record per key forever, so a topic can act as a durable snapshot of current state — the backbone of event sourcing and CDC.</li>\n<li><strong>Exactly-once semantics.</strong> Via the idempotent producer and transactions, Kafka provides exactly-once processing <em>within the Kafka ecosystem</em> (read-process-write between Kafka topics). It does not magically make an external HTTP call or database write exactly-once; you still need idempotency at the boundary.</li>\n<li><strong>Ecosystem.</strong> <strong>Kafka Connect</strong> for source and sink integrations without writing code, <strong>Kafka Streams</strong> and ksqlDB for stream processing, plus Flink and Spark integrations and a schema registry.</li>\n<li><strong>The cost.</strong> Partition-count planning (too few limits parallelism; too many hurts latency and recovery), <strong>rebalancing</strong> pauses when consumers join or leave, <strong>consumer lag</strong> monitoring as a first-class operational concern, replication and retention sizing, and a head-of-line problem: a record your code cannot process blocks its partition unless you deliberately route it aside.</li>\n<li><strong>Modern Kafka uses KRaft, not ZooKeeper.</strong> Kafka's own Raft-based metadata mode became production-ready in 3.3, the default for new clusters in 3.x, and ZooKeeper support was removed in Kafka 4.0. Saying \"Kafka needs ZooKeeper\" in 2026 dates you.</li>\n<li><strong>Amazon MSK</strong> runs Kafka for you — provisioning, patching, multi-AZ replication — while you still design partitions and consumers. <strong>MSK Serverless</strong> removes capacity planning too, at a different price point. Either way you get real Kafka APIs, so clients and tooling are portable.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The rest of the field, briefly and accurately</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Apache ActiveMQ.</strong> A mature <strong>JMS</strong>-centric broker, very common in Java enterprises. font-size: 1.25rem; font-weight: 600\">Decision guidance — choose X when</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Choose SQS when</strong> you are on AWS and the job is background work: sending emails, generating reports, processing uploads, syncing with a third party. Each message is done once and then gone, you want retries and a DLQ for free, and you want nobody on the team paged for broker health. A team of four shipping a SaaS product on AWS should reach for SQS by default.</li>\n<li><strong>Choose Kafka or MSK when</strong> several independent teams need to read the <em>same</em> data at their own pace, when you need <strong>replay</strong> because consumers will change and need to reprocess history, when you are doing event sourcing or change-data capture, or when sustained throughput is in the hundreds of thousands of events per second. The application keeps its client library and semantics; you change an endpoint and a credential. Plan a later migration to AWS-native services if it makes sense, but do not couple that to the lift.</li>\n<li><strong>Choose RabbitMQ when</strong> the routing itself is the requirement: a message that must reach the EU audit queue and the order queue but not the US queue, or genuine <strong>priorities</strong> where an urgent job must jump ahead of a backlog of bulk jobs. It has no per-message acknowledgement, no visibility timeout and no built-in per-message DLQ — a record your code cannot process blocks its partition until you handle it deliberately. For a queue of independent jobs, SQS's per-message delete is genuinely the better model.</li>\n<li><strong>\"SQS cannot scale.\"</strong> Standard SQS has effectively unlimited throughput and is used at enormous scale inside Amazon. The FIFO variant has published limits (raised substantially by high-throughput mode), but \"SQS does not scale\" is simply false.</li>\n<li><strong>\"RabbitMQ is obsolete.\"</strong> It is actively developed, and quorum queues and streams have modernised it considerably. Its routing model and protocol breadth remain best in class, and for many workloads it is the better fit than either alternative.</li>\n<li><strong>\"Pick Kafka because big companies use it.\"</strong> Big companies use it because they have the scale <em>and</em> the platform team to run it. Adopting Kafka for a 1,000-message-per-day job queue means partition planning, lag dashboards and rebalancing incidents in exchange for nothing.</li>\n<li><strong>\"A queue and a log are interchangeable.\"</strong> A queue's message disappears once handled; a log's record stays for everyone. If you need \"replay last Tuesday for a new consumer\", a queue cannot do it. If you need \"one worker, retried individually, with a DLQ\", a log makes you build that yourself.</li>\n<li><strong>\"Kafka needs ZooKeeper.\"</strong> Outdated. Kafka's own KRaft metadata mode is production-ready since 3.3, the default for new clusters, and ZooKeeper support was removed in Kafka 4.0.</li>\n<li><strong>\"Kafka gives exactly-once end to end.\"</strong> Only within the Kafka ecosystem, via the idempotent producer and transactions.
