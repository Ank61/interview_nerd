{"title":"Exactly-Once Processing — Idempotency Architecture","tags":["idempotency","exactly-once","dynamodb-conditional-write","transactional-outbox"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">\"How do you get exactly-once with SQS?\" is one of the most common senior-level questions, and the strongest answer starts by rejecting the premise. Exactly-once <em>delivery</em> is not achievable over an unreliable network — but exactly-once <em>effect</em> is achievable, and it is achievable entirely on the consumer side. The whole engineering problem is making the effect of processing a message independent of how many times that message arrives. Everything else in this topic is technique in service of that one idea.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why Exactly-Once Delivery Is Impossible</h4>\n<p style=\"line-height: 1.75\">Consider the simplest possible exchange: a sender delivers a message, the receiver processes it, the receiver acknowledges. If the acknowledgement is lost, the sender cannot distinguish \"the receiver never got it\" from \"the receiver got it and the ack died\". It has exactly two choices: resend (risking a duplicate — at-least-once) or not resend (risking loss — at-most-once). There is no third option, because no finite exchange of messages over a lossy channel lets both parties reach certainty about the other's state. This is the Two Generals Problem, and it is not an implementation gap that a better queue could close.</p>\n<p style=\"line-height: 1.75\">So \"exactly-once\" systems are always doing one of two things: they are running an expensive coordination protocol to shrink the window (FIFO's 5-minute dedup, Kafka's transactional producer with an epoch-fenced producer id), or they are pushing the problem to the consumer as an idempotency requirement. SQS chooses the second, honestly and explicitly.</p>\n<div class=\"code\"><div class=\"code-head\"><span>java</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">exactly-<i class=t>once</i> <i class=v>DELIVERY</i>   <i class=o>=</i> impossible over a <i class=t>lossy</i> <i class=f>channel</i>  <i class=p>(Two Generals)</i>\nexactly-<i class=t>once</i> <i class=v>EFFECT</i>     <i class=o>=</i> achievable, and entirely your job\neffectively-once        = at-least-once delivery + idempotent processing, end to end\n\n  duplicate arrives --&gt; idempotency check --&gt; already done? <i class=k>return</i> stored result\n                                          --&gt; not done?     <i class=k>do</i> work, <i class=k>record</i> <i class=f>result</i></code></pre></div>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Choosing the Idempotency Key — and Why MessageId Is Wrong</h4>\n<p style=\"line-height: 1.75\">Everything hinges on the key, and the single most common mistake is using the SQS <code>MessageId</code>. It fails in the case you most need it to cover:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Redelivery of the same message</strong> (visibility timeout expiry, replica-level duplicate) reuses the <em>same</em> MessageId. Deduping on it works here — which is exactly why it looks correct in testing.</li>\n<li><strong>Producer retry</strong> — the upstream called <code>SendMessage</code>, the response was lost, it retried — creates a <strong>second, distinct message with a different MessageId</strong> carrying the same logical work. Deduping on MessageId processes both. This is the case that double-charges customers.</li>\n<li><strong>Replays and reprocessing.</strong> Re-driving a DLQ or replaying an event log produces new MessageIds for work that may already have been done.</li>\n</ul>\n<p style=\"line-height: 1.75\">The key must come from the <strong>domain</strong>: a business identifier that is stable across every path by which the same logical work can reach you. Good choices, in order of preference: an <strong>upstream-generated event id</strong> (a UUID the producer stamps <em>once</em>, before any retry, and reuses on every retry of that event); a <strong>natural business key</strong> such as <code>payment_intent_id</code>, <code>order_id + state_transition</code>, or <code>invoice_id</code>; or, as a last resort, a <strong>deterministic hash</strong> of the semantically meaningful fields of the payload. The hash approach is fragile — a timestamp or a trace id in the payload breaks it — so use it only when you control the schema and can exclude volatile fields.</p>\n<p style=\"line-height: 1.75\">The discipline point: the producer must generate the id <em>before</em> its first attempt and reuse it across retries. An id generated inside the retry loop is a new id per attempt and provides no protection at all.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The DynamoDB Conditional-Write Pattern</h4>\n<p style=\"line-height: 1.75\">The workhorse implementation. style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Two states, not one.</strong> A single \"seen\" marker cannot distinguish \"someone is working on it right now\" from \"it You need <code>IN_PROGRESS</code> and <code>COMPLETED</code>, because the correct reaction differs: for COMPLETED you return the stored result and delete the message; for IN_PROGRESS you must <em>not</em> delete it — if the other worker crashes, that message is your only remaining copy of the work.</li>\n<li><strong>Lock expiry is mandatory.</strong> Without it, a worker that crashes mid-work leaves a permanent <code>IN_PROGRESS</code> record and the work can never be retried — a self-inflicted deadlock. Set <code>lock_expires</code> comfortably above your p99.9 processing time and allow the claim to be taken over once it passes.</li>\n<li><strong>Store the response.</strong> For request/response paths (an API-backed idempotency key), returning the <em>original</em> stored response on a duplicate is what makes the operation genuinely idempotent from the caller's perspective, rather than returning a confusing 409.</li>\n<li><strong>TTL for cleanup.</strong> Set <code>expires_at</code> and enable DynamoDB TTL so the table does not grow forever. Choose the window deliberately: it must exceed the longest realistic duplicate delay — message retention (up to 14 days), a DLQ redrive, a manual replay. A 24-hour TTL with a 14-day retention is a latent bug.</li>\n<li><strong>The simultaneous-claim race.</strong> Two workers receiving the same message (or two messages with the same domain key) call PutItem at the same instant. DynamoDB serializes single-item conditional writes, so exactly one wins and the other gets <code>ConditionalCheckFailedException</code>. That is the whole race, handled — the atomicity is provided by the database, not by your code, which is why this pattern is preferred over read-then-write (a read-then-write has a window between the read and the write in which both workers see \"not present\").</li>\n<li><strong>Consider making it part of the transaction.</strong> If the work itself writes to DynamoDB, put the idempotency record and the business write in a single <code>TransactWriteItems</code>. Then there is no window at all between doing the work and recording it — the strongest version of the pattern.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Naturally Idempotent Operations Beat Dedup Tables</h4>\n<p style=\"line-height: 1.75\">A dedup table is infrastructure you must operate, pay for, and reason about. That is idempotency with no extra table, no TTL and no lock — which is why designing for it beats bolting on deduplication.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Hard Case: Non-Idempotent Side Effects</h4>\n<p style=\"line-height: 1.75\">Charging a card, sending an email, calling a partner API, publishing to a third party. You do not control the remote system's state, so no local conditional write can undo a second execution. The standard answers, and their honest limits:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Provider-side idempotency keys.</strong> Payment providers and most modern APIs accept an idempotency key header; the provider guarantees that two requests with the same key produce one effect and return the same response. Derive the key from your <em>domain</em> key, not from a random value generated at call time. This is by far the strongest mechanism, and the first thing to look for in any third-party API.</li>\n<li><strong>Local record written transactionally before the call.</strong> Write an <code>ATTEMPTED</code> record (with the exact key you will send) <em>before</em> making the call, so that after a crash you know a call may have been made and can query the provider for its status rather than blindly retrying.</li>\n<li><strong>Query-before-retry.</strong> Many providers let you look up by your idempotency key or client reference. On recovery, ask \"did this already happen?\" instead of assuming.</li>\n<li><strong>The honest limit.</strong> If you crash <em>after</em> the provider processed the request and <em>before</em> you recorded the outcome, no protocol closes that window — it is the Two Generals Problem again, now with a third party. You are choosing between a possible double effect and a possible missed effect. The professional answer is to make the choice explicit per operation (double-charge is unacceptable, so retry only after a successful status query; a duplicate marketing email is tolerable, so retry freely), keep a reconciliation job that compares your records against the provider's, and expose the discrepancy rather than hiding it.</li>\n</ul>\n<p style=\"line-height: 1.75\">For emails specifically: a suppression record keyed by (template, recipient, business_event_id) checked before send turns \"send an email\" into something close to idempotent, and is the standard mitigation when the provider offers no key.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Dual-Write Problem and the Transactional Outbox</h4>\n<p style=\"line-height: 1.75\">A subtler correctness bug sits upstream of all of this. No guarantee is required of it.</li>\n<li><strong>Consumer</strong> claims the <code>event_id</code> with a conditional write, does work that is naturally idempotent wherever possible, passes the key through to any third party that accepts idempotency keys, records completion (ideally in the same transaction as the work), then deletes the message.</li>\n<li><strong>Observability</strong>: emit a metric on duplicate-suppressed events. A sudden rise means a producer bug or a visibility-timeout problem; zero forever probably means your key is wrong and you are not detecting duplicates at all.</li>\n<li><strong>Reconciliation</strong> compares your records against downstream systems on a schedule, so the irreducible windows are measured rather than assumed.</li>\n</ul>\n<p style=\"line-height: 1.75\">Note the ordering discipline: <strong>delete the message only after the effect is durably recorded.</strong> Deleting first gives you at-most-once and silent data loss — always the worse trade.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Production Scenario: The System That Double-Charges</h4>\n<p style=\"line-height: 1.75\">Customers are occasionally charged twice. The consumer reads <code>payment.requested</code> from SQS, calls the payment provider, then writes a payment row. Deduplication exists: the consumer keeps a Redis set of processed <code>MessageId</code>s with a one-hour TTL. Diagnose and fix.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Bug 1 — wrong key.</strong> <code>MessageId</code> catches SQS redeliveries but not producer retries, which produce a <em>different</em> MessageId for the same logical payment. Replace with the domain key: <code>payment_intent_id</code> (or an upstream <code>event_id</code> stamped once before the first send).</li>\n<li><strong>Bug 2 — wrong TTL.</strong> One hour against a 4-day message retention and manual DLQ redrives. A redrive on day three sails straight past the dedup window. TTL must exceed the longest plausible duplicate delay — set it to at least retention plus a margin, e.g. 7 days.</li>\n<li><strong>Bug 3 — wrong store semantics.</strong> A Redis set with read-then-write has a race between the check and the add, and Redis is not the durability tier you want guarding money. Move to a <strong>DynamoDB conditional write</strong> (<code>attribute_not_exists</code>), which is atomic, strongly consistent and durable. (A single <code>SET NX</code> would at least be atomic, but the durability argument stands.)</li>\n<li><strong>Bug 4 — wrong ordering.</strong> Charge first, record second, means a crash in between loses all knowledge of the charge and the retry charges again. Claim the key <em>before</em> calling the provider, storing the exact idempotency key you will use.</li>\n<li><strong>Bug 5 — not using the provider's key.</strong> Every serious payment API supports an idempotency key header. Send <code>payment_intent_id</code> as that key and the provider itself collapses duplicates, returning the original charge. This is the fix that actually makes double-charging impossible rather than unlikely.</li>\n<li><strong>Residual window.</strong> Crash after the provider charged and before you recorded the result. On retry, the provider's idempotency key makes the second call return the <em>original</em> charge rather than creating a new one — so the window is closed for the charge itself, and the remaining work is just recording it. Where a provider offers no key, replace that with query-before-retry plus a daily reconciliation against provider settlements.</li>\n<li><strong>Also fix the producer.</strong> If the upstream writes the payment request to its database and then sends to SQS as two separate steps, add a <strong>transactional outbox</strong> so a crash cannot produce a charged-but-unrecorded request or a phantom event.</li>\n</ul>\n<p style=\"line-height: 1.75\">The finished design has no exactly-once delivery anywhere in it and still never double-charges, which is precisely the point to land in an interview.</p>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"Exactly-once delivery is impossible — that is the Two Generals Problem, not a gap in SQS.
