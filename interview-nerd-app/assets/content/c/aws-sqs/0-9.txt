{"title":"SQS Security — IAM, Queue Policies, and Encryption","tags":["SQS","IAM","Encryption","Queue Policy"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">A queue is a pipe between parts of your system, and anything that can write to that pipe can inject work, while anything that can read from it can steal or destroy work. Securing SQS comes down to four questions: who may call the queue, from where, is the data encrypted while it sits there, and is it encrypted on the wire. This topic walks through each in plain language, starting with the piece beginners find most confusing — the fact that permissions in AWS can be written from two different directions.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">First, three words you need</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>IAM</strong> (Identity and Access Management) is the AWS service that decides who is allowed to do what. Nothing in AWS is permitted by default — every call is denied unless a policy allows it.</li>\n<li><strong>A principal</strong> is simply \"who is making the call\": an IAM user, an IAM role (a set of permissions a service or application temporarily assumes), an AWS account, or an AWS service itself such as S3.</li>\n<li><strong>A policy</strong> is a JSON document listing allowed or denied actions on specific resources, optionally with conditions.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The two permission directions</h4>\n<p style=\"line-height: 1.75\">You can grant access to a queue by writing a policy on the <em>caller</em> or a policy on the <em>queue</em>. Both exist because they answer different questions.</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Kind</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Attached to</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Reads as</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Use it when</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><strong>IAM identity policy</strong></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">A user or role in your account</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">\"This service may send to that queue\"</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">The caller is an identity you control, in the same account</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><strong>Queue policy</strong> (resource-based)</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">The queue itself</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">\"These principals may use me\"</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">The caller is in another AWS account, or is an AWS service like S3 or SNS</td></tr>\n</tbody>\n</table>\n</div>\n<p style=\"line-height: 1.75\">Within a single account, an identity policy alone is enough. For <strong>cross-account</strong> access, you need <em>both</em>: the queue policy must allow the other account, and that account must also grant its own role permission to call your queue. For AWS <strong>services</strong> such as S3 event notifications, there is no IAM role you can edit on the service's side, so the queue policy is the only place the grant can live.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The SQS actions worth knowing</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>sqs:SendMessage.</strong> Put a message on the queue. Producers need this and nothing else.</li>\n<li><strong>sqs:ReceiveMessage.</strong> Read messages (which also starts their visibility timeout).</li>\n<li><strong>sqs:DeleteMessage.</strong> Remove a message after successful processing. Without it a consumer processes the same message over and over forever.</li>\n<li><strong>sqs:ChangeMessageVisibility.</strong> Extend or shorten the time a message stays hidden — used by long-running consumers that need more time (a \"heartbeat\").</li>\n<li><strong>sqs:GetQueueAttributes.</strong> Read settings and approximate counts. Lambda's event source mapping and most monitoring tooling need this.</li>\n<li><strong>sqs:GetQueueUrl.</strong> Look up a queue's URL from its name, so code does not hardcode URLs.</li>\n<li><strong>sqs:PurgeQueue.</strong> Delete every message in the queue instantly and irreversibly. Treat it as a break-glass admin action; never grant it to application roles.</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>Split them by role.</strong> Give producers send-only and consumers receive/delete/change-visibility. This is not bureaucracy — it is a blast-radius control. If a buggy deploy in your reporting service accidentally calls <code>ReceiveMessage</code> and <code>DeleteMessage</code> on the orders queue, it will quietly drain another team's work and the messages are gone. With send-only credentials the call simply fails with AccessDenied, and you get an error instead of an incident.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Queue URL versus queue ARN, and scoping to one queue</h4>\n<p style=\"line-height: 1.75\">These two identifiers look similar and are used in different places, which trips people up constantly.</p>\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">Queue URL  (used by the API / SDK calls)\n  https://sqs.us-east-1.amazonaws.com/111122223333/orders\n\nQueue ARN  (used <i class=k>in</i> POLICIES, event <i class=b>source</i> mappings, alarms)\n  arn:aws:sqs:us-east-1:111122223333:orders\n\nRule of thumb: code talks <i class=k>in</i> URLs, policies talk <i class=k>in</i> ARNs.</code></pre></div>\n<p style=\"line-height: 1.75\">Always scope the <code>Resource</code> field to the specific queue ARN. On the queue, you add a statement whose <code>Principal</code> is the role in account B and whose <code>Action</code> is <code>sqs:SendMessage</code> on your queue ARN. In account B, the team attaches an IAM policy to that role allowing <code>sqs:SendMessage</code> on the same ARN. Both sides must agree; either one missing produces AccessDenied.</p>\n<p style=\"line-height: 1.75\">One subtlety worth mentioning in an interview: when account B's consumer reads a message from account A's queue, and the queue is encrypted with a customer managed KMS key, account B also needs permission on that <strong>key</strong>, granted in the key's own policy. Cross-account plus encryption is a two-part grant.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Letting an AWS service send to your queue (and the confused deputy)</h4>\n<p style=\"line-height: 1.75\">The most common queue policy you will ever write allows another AWS service to deliver messages: S3 object-created notifications, an SNS topic fanning out to the queue, or an EventBridge rule routing events. In each case the <code>Principal</code> is a <strong>service principal</strong> — an identifier like <code>s3.amazonaws.com</code>, <code>sns.amazonaws.com</code> or <code>events.amazonaws.com</code> that represents the service acting on your behalf.</p>\n<p style=\"line-height: 1.75\">If you stop there, you have a problem. A service principal is shared by every customer of that service. A policy that says \"S3 may send to my queue\" literally means \"any S3 bucket anywhere may send to my queue\" — a stranger could configure their bucket to publish notifications into your queue and flood it with junk. This is the <strong>confused deputy problem</strong>: a trusted intermediary (the service) is tricked by a third party into acting against you.</p>\n<p style=\"line-height: 1.75\">The fix is a <strong>condition</strong> on the statement. Add <code>aws:SourceArn</code> restricting it to your specific bucket, topic, or rule, and ideally <code>aws:SourceAccount</code> restricting it to your account ID. Choose SSE-KMS when compliance requires a key you own, when you need an audit trail of every decrypt, when you need the ability to revoke access by disabling a key, or when a partner account must be granted or denied decryption independently of queue permissions.</p>\n<p style=\"line-height: 1.75\"><strong>The classic confusing AccessDenied:</strong> a team switches a queue to SSE-KMS and producers immediately start failing, even though their SQS permissions were never touched. The reason is that with SSE-KMS the caller needs KMS permissions <em>in addition to</em> SQS permissions — senders need <code>kms:GenerateDataKey</code>, receivers need <code>kms:Decrypt</code> — granted either in their IAM policy or in the key policy. The error mentions KMS, so read it carefully rather than adding more SQS actions.</p>\n<p style=\"line-height: 1.75\">Because each KMS call costs money, SQS has a cost control called the <strong>data key reuse period</strong> (<code>KmsDataKeyReusePeriodSeconds</code>). SQS fetches a data key from KMS and reuses it for this window instead of calling KMS for every message. It ranges from 60 seconds to 86,400 seconds (24 hours), defaulting to 300 seconds. Longer reuse means far fewer KMS requests and a smaller bill; shorter reuse means tighter key rotation. On a high-volume queue this single setting can be the difference between pennies and hundreds of dollars a month.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Encryption in transit</h4>\n<p style=\"line-height: 1.75\">All SQS API endpoints are HTTPS, so traffic is encrypted on the wire by default. To <em>prove</em> it and prevent a misconfigured client from using plain HTTP, add a queue policy statement that denies any request where the condition <code>aws:SecureTransport</code> is false. Auditors ask for this, and it costs nothing.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">VPC endpoints (AWS PrivateLink)</h4>\n<p style=\"line-height: 1.75\">A <strong>VPC</strong> (Virtual Private Cloud) is your own private network inside AWS. A server in a private subnet has no public internet route, so by default it cannot reach the public SQS endpoint at all — teams usually solve this with a NAT gateway, which costs money per hour and per gigabyte and sends traffic out over the internet backbone.</p>\n<p style=\"line-height: 1.75\">A <strong>VPC endpoint</strong> (powered by AWS PrivateLink) is a private door into an AWS service from inside your VPC. With an interface endpoint for SQS, your private instances get a private IP address that resolves to SQS, so traffic never leaves the AWS network — no internet gateway, no NAT gateway. The benefits are security (traffic stays private), cost (no NAT data processing charges), and often latency.</p>\n<p style=\"line-height: 1.75\">You can attach an <strong>endpoint policy</strong> — a policy on the door itself — restricting which queues can be reached through it, for example only queues in your own account. Combine that with a queue policy condition on <code>aws:SourceVpce</code> to require that requests arrive through your endpoint and nowhere else. That is about as locked down as an SQS queue gets.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"The queue is private, so anyone in my account is fine.\"</strong> Account boundaries are not a security model.
