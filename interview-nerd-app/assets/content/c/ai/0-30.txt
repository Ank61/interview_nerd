Every production system that handles real enterprise queries ends up hybrid, usually after a painful discovery.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nPart 1: What Pure Vector Search Cannot Do\n</h4>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>code</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">THE FAILURE THAT STARTS EVERY HYBRID SEARCH PROJECT\n\n  User: &quot;I&#x27;m getting error ERR-4471B on invoice INV-2024-88213&quot;\n\n  Vector search embeds the MEANING of that sentence, which is\n  roughly &quot;an error occurred relating to an invoice&quot;.\n\n  It returns: five documents about invoice errors in general.\n  It MISSES: the one page in the knowledge base that contains\n             the literal string ERR-4471B and explains the fix.\n\nWHY: the embedding is a summary of MEANING. BM25 scores this near zero.\n\n  Vector search finds it instantly, because the MEANING matches.\n\nKEYWORD SEARCH FAILS ON:\n  Synonyms          &quot;car&quot; vs &quot;automobile&quot; vs &quot;vehicle&quot;\n  Paraphrase        the user&#x27;s words are not the document&#x27;s words\n  Concepts          &quot;how do I get my money back&quot; vs &quot;refund policy&quot;\n  Morphology        partially handled by stemming, imperfectly\n  Cross-lingual     completely\n\nSO THE TWO METHODS FAIL ON DISJOINT SETS OF QUERIES. That is\nprecisely why combining them works so well - they are not\nredundant, they are COMPLEMENTARY.</code></pre></div>\n</div>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nPart 3: What BM25 Actually Is\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nBM25 (\"Best Match 25\") is the standard keyword ranking function — the evolution of TF-IDF, and still the strong baseline in information retrieval after decades. You should be able to describe it in plain terms.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>code</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">BM25 scores a document for a query by summing, over each query\nterm, three ideas:\n\n1. TERM FREQUENCY (TF) - how often does the term appear here?\n   More occurrences means more relevant... but with SATURATION.\n   A document mentioning &quot;refund&quot; 50 times is not 5x more\n   relevant than one mentioning it 10 times. BM25 dampens this\n   with a parameter k1 (typically ~1.2 to 1.5).\n   This is a key improvement over naive TF-IDF.\n\n2. INVERSE DOCUMENT FREQUENCY (IDF) - how RARE is the term\n   across the whole corpus?\n   &quot;the&quot; appears everywhere and carries no signal -&gt; near-zero\n   weight. &quot;ERR-4471B&quot; appears in one document -&gt; ENORMOUS\n   weight. THIS is exactly why BM25 nails identifiers: rarity\n   is the signal, and rarity is what embeddings throw away.\n\n3. DOCUMENT LENGTH NORMALISATION - a long document naturally\n   contains more of every word, so it should not win by being\n   long. Parameter b (typically 0.75) controls how strongly\n   length is penalised.\n\nTHE ONE-LINE VERSION FOR AN INTERVIEW:\n  &quot;BM25 rewards rare terms, dampens repeated terms, and\n   normalises for document length.&quot;\n\nIT IS ALSO SPARSE: the representation is a vocabulary-sized\nvector that is almost all zeros. Dense embeddings are the\nopposite - a few hundred or thousand non-zero floats capturing\nmeaning. Sparse = literal form. Dense = meaning.</code></pre></div>\n</div>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nPart 4: Fusion — How You Actually Combine Them\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nYou now have two ranked lists that disagree. Combining them is the interesting engineering problem, and there is a clear default.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>code</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">THE PROBLEM WITH ADDING SCORES:\n  Cosine similarity is bounded, roughly 0.6 to 0.95 in practice.\n  BM25 is UNBOUNDED and corpus-dependent - it might be 3.2 or\n  47.8 depending on term rarity and corpus size.\n  There is no principled way to add two numbers on completely\n  different scales. Any weighting you choose is arbitrary and\n  will break when your corpus changes.\n\nRECIPROCAL RANK FUSION (RRF) - the default answer\n\n    score(doc) = sum over lists of  1 / (k + rank_in_that_list)\n\n    k is a constant, conventionally 60.\n\n  IT USES ONLY RANK, NOT SCORE. So the incompatible scales\n  problem disappears entirely. That single property is why RRF\n  is the standard choice.\n\n  WORKED EXAMPLE (k=60):\n    Doc A: rank 1 in vector, rank 30 in BM25\n           1/61 + 1/90  = 0.0275\n    Doc B: rank 5 in vector, rank 2 in BM25\n           1/65 + 1/62  = 0.0315   &lt;- WINS\n    Doc C: rank 2 in vector, absent from BM25\n           1/62         = 0.0161\n\n  Doc B wins because BOTH methods liked it. That is exactly the\n  behaviour you want - agreement across independent methods is\n  strong evidence.\n\n  WHAT k DOES: a larger k flattens the difference between top\n  ranks, so being ranked 1 versus 3 matters less and appearing\n  in both lists matters more. 60 is a reasonable default; it is\n  worth sweeping on your own data.\n\n  THE TRADE-OFF TO NAME: because RRF discards scores, it cannot\n  express &quot;this result was OVERWHELMINGLY better than the rest&quot;.\n  For that you need a reranker - which is the next stage anyway.\n\nALTERNATIVES WORTH KNOWING:\n  Weighted score fusion - normalise both scores (min-max or\n    z-score) then blend with a weight. More expressive, but the\n    normalisation is fragile and needs recalibrating whenever\n    the corpus or the model changes.\n  Relative score fusion - normalise against the top score in\n    each list. A middle ground.\n  Learned fusion - train a model on click or relevance data.\n    Best if you have the data; most teams do not.</code></pre></div>\n</div>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nPart 5: The Middle Ground — Learned Sparse Retrieval\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nWorth naming, because it shows depth. <strong>SPLADE</strong> and similar learned-sparse models produce a sparse vocabulary-sized vector like BM25, but the weights are <em>learned</em> by a transformer, and the model performs <strong>term expansion</strong> — a document about \"automobile\" gets non-zero weight on \"car\" too. So you get exact-match behaviour <em>and</em> some semantic matching in one index, searchable with standard inverted-index infrastructure. The costs are a heavier indexing step and larger index size than BM25. It is a genuine alternative to running two systems, though hybrid BM25-plus-dense remains the more common production choice.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nPart 6: Implementation Details That Matter\n</h4>\n<ul style=\"margin-top: 1.0rem; margin-left: 1.5rem; list-style-type: disc\">\n<li style=\"margin-top: 0.5rem\"><strong>Run both searches in parallel.</strong> They are independent, so latency is the slower of the two rather than the sum. Doing them sequentially is a free performance loss that appears in a surprising number of implementations.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Both indexes must be written, updated and deleted together.</strong> A document removed from the vector store but left in the keyword index is still retrievable — a correctness bug, and a compliance one if the removal was a deletion request.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Apply the same access filter to both.</strong> An easy and serious mistake is filtering the vector path and forgetting the keyword path, which leaks documents through the side door.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Retrieve deep from both.</strong> Take the top 50 from each rather than the top 5, because RRF needs enough of each list to find agreement, and the reranker downstream wants candidates.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Tokenisation and stemming matter for BM25</strong> in a way they do not for vectors. Language-specific analysers, stemming, stop-word handling and how you tokenise identifiers all affect results. Make sure \"ERR-4471B\" is not split into \"err\" and \"4471b\" in a way that destroys its rarity.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Consider query routing.</strong> If a query obviously contains an identifier — a regex match for a code pattern, a quoted phrase — you can weight the keyword side higher for that request. Cheap, deterministic, and effective.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nPart 7: Where To Run It\n</h4>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>code</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">TWO SYSTEMS (a vector DB + a search engine)\n  + Best-in-class on each side.\n  - Two systems to keep in sync, two sets of deletes, two\n    failure modes, fusion in application code.\n\nONE SYSTEM WITH BOTH (Elasticsearch/OpenSearch, and increasingly\nthe vector databases themselves)\n  + One write path, so no sync bug.
