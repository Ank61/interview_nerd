That is mostly wrong. Two agents running the same model with different system prompts are not meaningfully different experts; they are two prompts.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\n<strong>The actual win is that each worker gets a fresh context window.</strong> One agent researching five subtopics accumulates five subtopics' worth of tool output and degrades. Five workers each researching one subtopic each stay clean, and the supervisor only ever sees five short summaries. That is a structural fix for context bloat, and it is why the pattern genuinely works when it works. The second real win is <strong>parallelism</strong> — wall-clock time becomes the slowest worker rather than the sum.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nThe Other Patterns, Briefly\n</h4>\n<ul style=\"margin-top: 1.0rem; margin-left: 1.5rem; list-style-type: disc\">\n<li style=\"margin-top: 0.5rem\"><strong>Pipeline</strong> — agents in a fixed order, each transforming the last one's output. This is a workflow whose steps happen to be agents; predictable and easy to test.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Parallel fan-out and aggregate</strong> — the same task attempted several ways, then merged. Useful when coverage matters more than cost.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Generator and critic</strong> — one produces, another critiques with a genuinely different brief. Often worth it, because a fresh context critiquing an artefact catches things the author's context will not.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Peer network</strong> — agents hand off to each other freely. Almost always a mistake: no single owner of termination, easy to loop, and very hard to debug. If you cannot draw the delegation as a tree, reconsider.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nWhen Multiple Agents Genuinely Beat One\n</h4>\n<ol style=\"margin-top: 1.0rem; margin-left: 1.5rem; list-style-type: decimal\">\n<li style=\"margin-top: 0.5rem\"><strong>The task decomposes into genuinely independent subtasks.</strong> Independent is the operative word — if B needs A's output, that is a loop, not a fan-out.</li>\n<li style=\"margin-top: 0.5rem\"><strong>The context volume exceeds one window.</strong> The clearest case. Isolation is the only real fix.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Subtasks need different tools or permissions.</strong> A worker that can write to production and one that only reads should genuinely be separate, because the permission boundary is real.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Cost asymmetry.</strong> A cheap model does the bulk gathering; an expensive one synthesises.
