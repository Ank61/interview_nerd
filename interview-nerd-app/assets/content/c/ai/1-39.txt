{"title":"IoC Container Internals","tags":["ioc","container","bootstrap","dependency-graph"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">\nThe container is the part of Nest that creates your objects and hands them to each other. You never call it directly, but almost every confusing error message comes from it, so knowing roughly how it works turns those errors from mysterious into obvious.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThe simplest mental model: <span style=\"font-weight: 600\">the container is a big map from a token to an instance</span>. You give it a token, it gives you the object. Everything else is how that map gets filled in.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nWhat Happens When You Call NestFactory.create()\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nFour phases, in order:\n</p>\n<ol style=\"margin-top: 1.0rem; margin-left: 1.5rem; list-style-type: number\">\n<li style=\"margin-top: 0.5rem\"><span style=\"font-weight: 600\">Scan</span> &mdash; walk the module tree and write down everything that exists.</li>\n<li style=\"margin-top: 0.5rem\"><span style=\"font-weight: 600\">Instantiate</span> &mdash; work out the order and create every object.</li>\n<li style=\"margin-top: 0.5rem\"><span style=\"font-weight: 600\">Lifecycle</span> &mdash; run the startup hooks.</li>\n<li style=\"margin-top: 0.5rem\"><span style=\"font-weight: 600\">Register routes</span> &mdash; read the routing metadata and hand routes to Express or Fastify.</li>\n</ol>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nOnly after all four does <code>listen()</code> open the port. That ordering is why misconfiguration crashes at boot rather than surfacing as a 500 three weeks later.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nPhase 1: Scanning\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nNest starts at <code>AppModule</code> and follows every <code>imports</code> array, recursively. For each module it finds, it reads the four arrays &mdash; <code>imports</code>, <code>controllers</code>, <code>providers</code>, <code>exports</code> &mdash; and records them.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThree things happen here that are worth knowing.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\n<span style=\"font-weight: 600\">Dynamic modules are evaluated.</span> A <code>forRoot()</code> or <code>forRootAsync()</code> call runs now, producing an ordinary module description that gets scanned like any other.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\n<span style=\"font-weight: 600\">Nothing is created yet.</span> This phase only builds a catalogue. No constructor has run.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\n<span style=\"font-weight: 600\">Modules that nobody imports do not exist.</span> If a module is not reachable from the root, it is never scanned, so its providers are never created and its controllers' routes are never registered. This is the single most common cause of a 404 on an endpoint that clearly exists in the code.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nWhat the Container Stores\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThe container holds one entry per module, and each of those holds several maps:\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>code</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">NestContainer\n  └── Module: OrdersModule\n        providers    Map&lt;token, wrapper&gt;    everything declared here\n        controllers  Map&lt;token, wrapper&gt;\n        injectables  Map&lt;token, wrapper&gt;    guards, pipes, interceptors, filters\n        imports      Set&lt;Module&gt;            modules this one can reach\n        exports      Set&lt;token&gt;             what others may take</code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nNotice that <code>exports</code> is a set of <span style=\"font-weight: 600\">tokens</span>, not instances. Exporting does not copy anything &mdash; it grants permission to look a token up. That is why exporting a provider gives every consumer the <span style=\"font-weight: 600\">same</span> instance.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nEach entry is wrapped in an object that holds the token, how to build it, its scope, and once it exists, the instance itself. Before instantiation, that instance slot is empty.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nPhase 2: Instantiating\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nNow Nest actually builds things. For each provider it needs to answer one question: <span style=\"font-weight: 600\">what arguments does this constructor need?</span>\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nIt reads that from metadata the TypeScript compiler emitted &mdash; a plain array of constructor functions saved under <code>design:paramtypes</code>. That array only exists because the class has a decorator on it, which is the real reason <code>@Injectable()</code> is required.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>typescript</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=m>@Injectable</i>()\n<i class=k>export</i> <i class=k>class</i> <i class=f>OrderService</i> {\n  <i class=f>constructor</i>(<i class=p><i class=k>private</i> <i class=a>repo</i>: <i class=f>OrderRepository</i>, <i class=k>private</i> <i class=a>mail</i>: <i class=f>MailService</i></i>) {}\n}\n<i class=c>// The compiler saved: [OrderRepository, MailService]</i>\n<i class=c>// Nest reads that array and resolves each entry as a token.</i></code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nFor each position it picks a token using a clear order of preference:\n</p>\n<ol style=\"margin-top: 1.0rem; margin-left: 1.5rem; list-style-type: number\">\n<li style=\"margin-top: 0.4rem\">If <code>@Inject(TOKEN)</code> was used on that parameter, use that token.</li>\n<li style=\"margin-top: 0.4rem\">Otherwise use the class from the paramtypes array.</li>\n</ol>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThen it looks the token up, in this order:\n</p>\n<ol style=\"margin-top: 1.0rem; margin-left: 1.5rem; list-style-type: number\">\n<li style=\"margin-top: 0.4rem\">This module's own providers.</li>\n<li style=\"margin-top: 0.4rem\">The <span style=\"font-weight: 600\">exports</span> of every module this one imports.</li>\n<li style=\"margin-top: 0.4rem\">Global modules.</li>\n</ol>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nIf none of those match, you get the familiar error naming the class, the index and the module it searched. That message is a direct readout of these three steps, which is why reading it carefully usually tells you the fix.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nDepth First, Not Top Down\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nCreating a provider means first creating everything it depends on. So the container works <span style=\"font-weight: 600\">downwards through the dependency chain</span> and builds from the bottom up.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>code</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">OrdersController needs OrderService\nOrderService     needs OrderRepository and MailService\nOrderRepository  needs DataSource\nDataSource       needs nothing\nBuilt in this order:\n  DataSource -&gt; OrderRepository -&gt; MailService -&gt; OrderService -&gt; OrdersController</code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nOnce created, an instance is stored and reused. Ask for <code>OrderService</code> from three places and all three get the same object &mdash; that is what \"singleton\" means here.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nA Singleton Per Module, Not Per App\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nAn important detail people get wrong. The map of instances belongs to a <span style=\"font-weight: 600\">module</span>, not to the whole application.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nSo if you list the same class in the <code>providers</code> array of two different modules, you get <span style=\"font-weight: 600\">two separate instances</span> &mdash; two caches that never agree, two connection pools, two counters.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>typescript</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c>// WRONG - two CacheService objects</i>\n<i class=m>@Module</i>({ <i class=a>providers</i>: [<i class=f>CacheService</i>] }) <i class=k>export</i> <i class=k>class</i> <i class=f>OrdersModule</i> {}\n<i class=m>@Module</i>({ <i class=a>providers</i>: [<i class=f>CacheService</i>] }) <i class=k>export</i> <i class=k>class</i> <i class=f>UsersModule</i> {}\n<i class=c>// RIGHT - one instance, shared through exports</i>\n<i class=m>@Module</i>({ <i class=a>providers</i>: [<i class=f>CacheService</i>], <i class=a>exports</i>: [<i class=f>CacheService</i>] })\n<i class=k>export</i> <i class=k>class</i> <i class=f>CacheModule</i> {}</code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThis usually happens by accident. Someone hits a resolution error, and the fastest way to silence it is to add the class to their own <code>providers</code>. The error goes away and a duplicate instance quietly appears.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nAsync Providers Are Awaited\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nIf a <code>useFactory</code> returns a Promise, the container waits for it before continuing.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>typescript</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">{\n  <i class=a>provide</i>: <i class=s>&#x27;REDIS&#x27;</i>,\n  <i class=a>useFactory</i>: <i class=f>async</i> (<i class=a>config</i>: <i class=f>ConfigService</i>) =&gt; {\n    <i class=k>const</i> client = <i class=f>createClient</i>({ <i class=a>url</i>: config.<i class=f>getOrThrow</i>(<i class=s>&#x27;REDIS_URL&#x27;</i>) });\n    <i class=k>await</i> client.<i class=f>connect</i>();       <i class=c>// startup pauses here</i>\n    <i class=k>return</i> client;\n  },\n  <i class=a>inject</i>: [<i class=f>ConfigService</i>],\n}</code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThis is genuinely useful: a bad connection string crashes the app on boot rather than failing on the first request in production. The trade-off is that slow connections directly extend startup time, which matters for rolling deployments and readiness probes.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nWhy Circular Imports Break Things\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThe paramtypes array is written by the compiler when the class is defined. If two files import each other, one of them is still part-way through loading when the other runs, so the class it needs has not been assigned yet.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThe array ends up containing <code>undefined</code>. Nest reports an error at that index with a <span style=\"font-weight: 600\">blank name</span> &mdash; blank because there is no class to name.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\n<code>forwardRef(() =&gt; Other)</code> fixes it by wrapping the reference in a function. Nest does not call that function until resolution time, by which point both files have finished loading.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nIt is a workaround, not a fix. A cycle usually means a missing third module, a dependency that should be inverted onto an abstract class, or a call that should be an event. And barrel <code>index.ts</code> files make cycles far more likely, because importing one thing loads everything the barrel re-exports.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nRequest-Scoped Providers Work Differently\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nEverything above describes singletons, which are built once at boot. A request-scoped provider cannot be, because it needs the request.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nSo Nest creates a small identifier for each incoming request and keeps a separate instance map per identifier. Anything request-scoped is built fresh, on demand, and thrown away when the request finishes.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThe consequence people underestimate: <span style=\"font-weight: 600\">scope spreads upwards</span>. If a provider is request-scoped, anything that injects it must also be rebuilt per request, and so on up to the controller. Then <code>onApplicationBootstrap</code> fires once everything is initialised.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nShutdown reverses it, and only runs at all if you called <code>app.enableShutdownHooks()</code>.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThe practical rule: use <code>onModuleInit</code> for work needing only your own module's providers, and <code>onApplicationBootstrap</code> when you need the whole application ready first.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nPhase 4: Routes\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nFinally Nest walks the controllers, reads the path and method recorded by each decorator, joins the pieces into a full URL, builds a wrapper function that runs the whole enhancer pipeline, and registers that wrapper with Express or Fastify as an ordinary route.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThis is also when Nest logs one line per route, which is the fastest way to check whether a missing endpoint was never registered or is being shadowed by something else.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nWhat This Costs\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nAll of it is real work: reading metadata for every class, resolving a graph, constructing every singleton, awaiting async factories.
