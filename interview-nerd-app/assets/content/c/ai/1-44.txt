If it can only retrieve what this user could already open, a hijacked answer shows them their own data. This is the biggest single control and it is not clever — it is just scoping.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Separate reading from acting.</strong> The strongest structural fix, and the one worth naming: one component reads the untrusted content and may only return <em>structured data</em> — no free text, no instructions. A separate component holds the tools and never sees the raw document. Injected text cannot reach the part of the system that can do anything.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Reduce privilege after touching untrusted content.</strong> Once a request has read external material, take the dangerous tools away for the rest of that run.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Approval gates on anything irreversible</strong>, especially after external content has been processed. A human sees \"send email to external@attacker.example\" and stops it.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Control the output channel.</strong> Escape everything, allow images and links only from hosts you control, and set a content security policy. That closes the no-click exfiltration route.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Clean content on the way in.</strong> Strip HTML comments, invisible text, zero-width characters, metadata and alt text at ingest. Cheap, and it removes the lazy version entirely.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Track where every chunk came from.</strong> Then you can treat a curated internal policy document differently from a crawled web page — and when something goes wrong, you can find and delete it.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Mark content as data in the prompt.</strong> Delimit it and say it is information, never instructions. Worth doing.
