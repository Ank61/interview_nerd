You do this because human grading does not scale and a rule cannot check \"is this explanation clear\".\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">\nThe second half is the actual question, and it is where the interview is won. <strong>A judge is a model in your measurement pipeline, so every problem a model has is now a problem with your numbers.</strong>\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nThe Six Biases Worth Naming\n</h4>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>code</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">1. POSITION BIAS\n   Comparing two answers, it favours whichever it saw\n   first. Same two answers, swapped order, different\n   winner. This one is large and very well documented.\n   FIX: run both orders. Only count it if both agree.\n\n2. LENGTH BIAS\n   Prefers longer answers, even when longer is worse. This\n   is the one that quietly ruins products: every prompt\n   change that adds a bit more padding scores better, so\n   your system slowly gets more verbose and nobody notices\n   because the number keeps going up.\n   FIX: tell it to ignore length, AND check whether score\n   correlates with length. If it does, the instruction did\n   not work.\n\n3. SELF-PREFERENCE\n   Models rate text from their own family more highly.\n   Awkward if you generate and grade with the same model,\n   which is the default setup.\n   FIX: judge with a different family where you can, and\n   at minimum do not compare two models using one of them\n   as the judge.\n\n4. CONFIDENCE AND FORMATTING BIAS\n   Sways towards answers that sound sure, use headings and\n   bullets, and cite things - even when the citations are\n   wrong. It is grading POLISH.\n   FIX: name the criteria explicitly, and verify citations\n   with code rather than trusting the judge to notice.\n\n5. SCORE CLUSTERING\n   Ask for 1 to 10 and almost everything is 7 or 8. The\n   scale is really three values wide, and the same answer\n   scored twice gives different numbers.\n   FIX: yes/no per criterion. Never a numeric scale.\n\n6. DRIFT\n   The judge model updates, or someone edits the judge\n   prompt, and your scores shift with no change to the\n   product. You will spend a day chasing a regression that\n   is in the ruler, not the thing being measured.\n   FIX: pin the judge version. Re-validate on any change.</code></pre></div>\n</div>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nWhat Actually Makes A Judge Reliable\n</h4>\n<ul style=\"margin-top: 1.0rem; margin-left: 1.5rem; list-style-type: disc\">\n<li style=\"margin-top: 0.5rem\"><strong>Ask narrow questions.</strong> \"Does the answer state the notice period?\" is answerable. \"Is this a good answer?\" is an opinion. Narrow questions are where judges are genuinely reliable — it is the same reason claim-level faithfulness checking works.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Yes or no, not a score.</strong> Several yes-or-no checks that add up beat one number out of ten, because every point is defined and repeatable.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Reason first, verdict second.</strong> Ask for the reasoning before the answer in your schema. It measurably improves reliability, and it gives you something to read when you disagree with a grade.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Comparing beats scoring.</strong> \"Which of these two is better?\" is a much easier task than \"rate this\", and it is the most trustworthy way to choose between two prompt versions.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Show it a few graded examples</strong> — especially borderline ones, which is where judges are least consistent.</li>\n<li style=\"margin-top: 0.5rem\"><strong>Use rules first.</strong> Anything a string match or a schema check can decide should never reach the judge. A misunderstanding that made the answer wrong will make the grading wrong in the same direction, and the score will look fine. It is worse in a comparison: judging model A against model B <em>using model A</em> is not a fair test, and any result from it is close to meaningless.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nWhere it matters, use a different model family to judge, and keep a human-labelled set as the thing that anchors both.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nCost, Which People Forget\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nA judge call per case, times a few runs per case for stability, times every pull request that touches a prompt. A two hundred case set at three runs is six hundred judge calls per CI run, and if each case has five criteria checked separately it is three thousand. That is enough to make people stop running the eval, which is much worse than a slightly less precise grader. So: rules first, judge only what is left, a cheaper model for the mechanical checks, and cache results for cases that did not change.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nHow This Comes Up In Interviews\n</h4>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>code</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">THE QUESTION\n  &quot;How does LLM-as-a-judge work, and what are its failure\n   modes and biases?&quot;\n\nWHAT THE INTERVIEWER IS TESTING\n  Whether you trust your own numbers too much.
