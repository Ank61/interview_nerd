{"title":"AWS PrivateLink and VPC Endpoint Services with NLB","tags":["privatelink","vpc-endpoint-service","nlb","saas-architecture"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">AWS PrivateLink answers a question that peering and Transit Gateway answer badly: how does one party expose a single service to many other VPCs and accounts, privately, without giving them network reachability to anything else and without either side caring about the other's IP addressing? The mechanism is a <strong>VPC endpoint service</strong> — a provider publishes a service backed by a Network Load Balancer (or a Gateway Load Balancer for appliance services), and consumers create <strong>interface VPC endpoints</strong> in their own VPCs. Traffic flows over the AWS private network with no internet gateway, no NAT gateway, no VPC peering, no route table changes, and — crucially — no consequences at all if both VPCs use overlapping CIDR blocks. It is the backbone of essentially every SaaS-on-AWS private integration and of most mature internal platform teams.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The model, end to end</h4>\n<p style=\"line-height: 1.75\">The provider side has three objects: an NLB fronting the actual service targets, a VPC endpoint service configuration referencing that NLB, and a permissions list naming which AWS principals may create endpoints. The consumer side has one object: an interface VPC endpoint, which materializes as an <strong>elastic network interface with a private IP in each subnet the consumer chooses</strong>, plus DNS names that resolve to those interfaces. exposure</strong>. If a consumer needs to reach forty of your services and you need to reach theirs, PrivateLink is the wrong tool and you want a TGW. If you are publishing one API to strangers, or to teams whose networks you refuse to couple yourself to, PrivateLink is exactly right — and the security property is strong, because there is no path back: a compromised provider cannot scan the consumer's VPC, and a compromised consumer reaches only the port the NLB listener exposes.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The provider side in detail</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Acceptance settings.</strong> An endpoint service either requires manual acceptance or auto-accepts connection requests. Manual acceptance gives you a gate — useful for a commercial SaaS where a connection should correspond to a paying account — but it is a human step in the consumer's onboarding path, so at scale it is usually automated with an EventBridge rule reacting to the connection notification and a Lambda that validates and accepts. Auto-accept plus a tight principal allow list is the common internal-platform choice.</li>\n<li><strong>Allowed principals.</strong> Permissions are a list of IAM principal ARNs — an account root, a specific role or user, or an <strong>organization ARN</strong> which covers every account in an AWS Organization at once. Nothing outside the list can even discover the service by name. This is the primary authorization boundary and should be treated as such; acceptance is a second gate, not a replacement.</li>\n<li><strong>Availability Zone mapping.</strong> An endpoint service is only reachable in the zones the provider enabled on the backing NLB. A consumer cannot create an endpoint ENI in a zone the provider did not enable, and a consumer whose workload lives only in an unsupported zone simply cannot use the service. Worse, <strong>zone names are per-account aliases</strong>: the provider's <code>us-east-1a</code> is not necessarily the consumer's <code>us-east-1a</code>. Always publish and reason about <strong>AZ IDs</strong> (values like <code>use1-az1</code>), which are stable across accounts, and enable at least three zones so consumers are not boxed in.</li>\n<li><strong>Private DNS name.</strong> You can attach your real service hostname to the endpoint service so consumers connect to, say, <code>api.example.com</code> rather than an opaque endpoint DNS name. AWS requires <strong>domain ownership verification</strong>: it issues a TXT record name and value that you publish in the public DNS zone for the domain, and it periodically re-verifies — if the record disappears, verification can fail and private DNS stops working. Consumers must also enable private DNS on their endpoint and have DNS hostnames and DNS support turned on in their VPC, at which point a private hosted zone is associated automatically and the name resolves to the endpoint ENIs inside their VPC while resolving normally everywhere else.</li>\n<li><strong>Consumer-facing endpoint DNS.</strong> Independently of private DNS, every endpoint gets AWS-generated names: a regional name that resolves to the ENI in the caller's own zone where possible, and per-zone names for deliberate zonal pinning. Clients that want zonal affinity — to avoid cross-zone data charges or to implement zonal shuffle sharding — should use the zonal names explicitly rather than hoping the regional name resolves locally.</li>\n<li><strong>Supported listeners.</strong> The backing NLB can expose TCP, TLS, UDP and TCP_UDP listeners, and the endpoint service exposes the listener ports. An ALB can be registered as an NLB target, which is the standard trick when you need HTTP-aware, per-request routing behind a PrivateLink-compatible front door.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The network details that actually bite</h4>\n<p style=\"line-height: 1.75\">Three things surprise almost everyone the first time.</p>\n<p style=\"line-height: 1.75\"><strong>1. The target does not see the consumer's client IP.</strong> Traffic entering through a VPC endpoint is source-NAT'd by the PrivateLink data plane, so however you set <code>preserve_client_ip.enabled</code>, the target sees an address associated with the provider-side path rather than the consumer application's real address. Client IP preservation is not supported for endpoint traffic. This matters for source-based access control, for logging and abuse attribution, and for multi-tenant rate limiting. The correct answer is <strong>proxy protocol v2</strong>: enable <code>proxy_protocol_v2.enabled</code> on the target group and the NLB prepends a binary header whose AWS type-length-value extensions include the <strong>VPC endpoint ID</strong>. Map that endpoint ID to the consumer account using the endpoint service connections API, and you have reliable per-consumer attribution. The target application must be built to parse and strip the header — including on the health check listener, which also receives it.</p>\n<p style=\"line-height: 1.75\"><strong>2. Security groups behave asymmetrically.</strong> The consumer attaches a security group to the endpoint ENIs controlling which of their own resources may reach the service — that is the consumer's lever and it works as expected. On the provider side, inbound traffic arriving through the endpoint service is by default <strong>not evaluated against the NLB's inbound security group rules</strong>, on the reasoning that PrivateLink access is already governed by the allow-listed principals and the acceptance workflow. If you want defense in depth, enable the option to <strong>enforce inbound security group rules on PrivateLink traffic</strong> when setting the load balancer's security groups. Do this carefully on a live service: the source addresses of endpoint traffic will not match rules you wrote for ordinary clients, so switching it on without first adding matching rules disconnects every consumer simultaneously.</p>\n<p style=\"line-height: 1.75\"><strong>3. Source NAT means ephemeral port budgets.</strong> Because the path source-NATs, the number of simultaneous connections between the PrivateLink infrastructure and a <strong>single target</strong> in a <strong>single zone</strong> is bounded by the ephemeral port range — on the order of tens of thousands per unique target per NLB node. A busy endpoint service with few targets will hit this before it hits any documented service quota, and the symptom is connection failures and resets under load while the targets themselves look idle. The fixes are to register more targets (more destinations means more port tuples), to expose more listener ports, and to avoid single-target target groups for high-connection services. Long-lived connections make this dramatically worse, so connection pooling with sensible reuse is part of the design, not an optimization.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Scaling, quotas, and cross-Region</h4>\n<p style=\"line-height: 1.75\">An endpoint service supports a large number of consumer endpoint connections — thousands — and the quotas that usually matter first are endpoints per VPC and endpoint services per account rather than connections per service; both are adjustable on request. The NLB behind it scales as any NLB does, with no pre-warming required, but remember that its own behavior still applies: cross-zone load balancing is off by default, so keep target counts balanced per zone or enable it, and the flow-hashing caveats about long-lived connections are unchanged.</p>\n<p style=\"line-height: 1.75\">PrivateLink is fundamentally a <strong>Regional</strong> construct in its classic form — an endpoint and the endpoint service it connects to live in the same Region. AWS has since added <strong>cross-Region</strong> interface endpoints, which let a consumer in one Region create an endpoint to a service published in another, with the traffic riding the AWS backbone; the provider opts in by enabling the supported Regions on the service configuration. Even so, a multi-Region service is usually published as one endpoint service per Region, with consumers creating local endpoints and choosing between Regions with DNS or Global Accelerator, because that keeps latency low and the failure domains independent. Cross-Region endpoints are best thought of as a convenience for consumers who cannot deploy in your Region, and they carry inter-Region data transfer charges on top of endpoint processing.</p>\n<h4 style=\"margin-top: 1.5rem; For a SaaS provider this is attractive. For an internal platform team it means a service consumed by two hundred accounts creates two hundred sets of endpoint-hour charges, which is a real number and a common reason platform teams reach for a shared-VPC or TGW model for very chatty internal traffic while keeping PrivateLink for cross-boundary and third-party access.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Monitoring both sides</h4>\n<p style=\"line-height: 1.75\">PrivateLink publishes CloudWatch metrics in two namespaces, one for endpoints (the consumer's view) and one for endpoint services (the provider's view). The useful ones are active and new connection counts, bytes processed in each direction, <strong>packets dropped</strong> broken down by reason, and <strong>reset packets sent</strong>. Two diagnostic patterns matter: a rise in packets dropped because no healthy targets exist in a zone points at provider-side health or zone imbalance, and a rise in resets usually points at either the ephemeral-port exhaustion described above or a target refusing connections. On the provider side, the endpoint service connections API is your inventory — it lists each connected endpoint with its ID, owner and state — and pairing it with proxy-protocol-derived endpoint IDs in application logs gives per-consumer traffic and error rates, which is what you need for quota enforcement and for telling a customer their integration is broken before they tell you. VPC Flow Logs capture endpoint ENI traffic on the consumer side, and DNS Resolver query logs are the fastest way to prove whether private DNS is resolving to the endpoint or leaking to the public name.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The two canonical patterns</h4>\n<p style=\"line-height: 1.75\"><strong>SaaS on AWS.</strong> A vendor runs the service in its own accounts, publishes one endpoint service per Region behind an internal NLB, requires manual or automated acceptance, allow-lists each customer's account as part of contract onboarding, registers a verified private DNS name so customers use the vendor's real hostname, and enables proxy protocol v2 to attribute connections to endpoint IDs and therefore to customers. Customers get a private path with no internet exposure, no firewall changes and no IP allow-list maintenance, which removes the single largest security objection to adopting a SaaS product. The vendor gets a clean tenancy boundary and a per-consumer identity handle it did not have to invent.</p>\n<p style=\"line-height: 1.75\"><strong>Internal platform team.</strong> A central team publishes shared services — an authentication API, a feature-flag service, an internal artifact proxy, a Kafka gateway — as endpoint services with the organization ARN as the allowed principal and auto-accept on. Application accounts create endpoints from a standard module. No central route tables, no CIDR planning across the estate, overlapping addresses in acquired accounts are a non-issue, and the blast radius of a misconfiguration is one endpoint rather than the whole network. The trade-off is per-endpoint cost and the fact that PrivateLink is one-directional, so a service that needs to call back into consumer VPCs (webhooks, callbacks) needs a second, reverse endpoint service published by the consumer — a design detail people frequently miss.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario: exposing an internal API to fifty consumer accounts</h4>\n<p style=\"line-height: 1.75\">Requirement: a platform team's HTTPS API, currently behind an internal ALB, must be consumed by fifty accounts across an Organization plus three external partner accounts, with per-consumer attribution, no CIDR coordination, and minimal onboarding friction.</p>\n<p style=\"line-height: 1.75\">Design. Keep the ALB for its per-request balancing, path routing and HTTP features, and place an internal <strong>NLB in front of it by registering the ALB as a target</strong> — this is the standard composition, giving PrivateLink compatibility without losing layer 7 behavior. Enable the NLB in three Availability Zones chosen by <strong>AZ ID</strong> and publish those IDs in the onboarding documentation. Create the endpoint service with <strong>auto-accept off</strong> and drive acceptance from an EventBridge rule plus a Lambda that checks the requesting principal against a registry — Organization accounts are approved automatically, partner accounts require a ticket reference. Set allowed principals to the <strong>organization ARN</strong> plus the three partner account ARNs. Register the team's real hostname as the private DNS name and publish the TXT verification record in the public zone, with monitoring on that record because losing it silently breaks resolution for everyone.</p>\n<p style=\"line-height: 1.75\">Attribution and security. Enable <strong>proxy protocol v2</strong> on the NLB target group so each connection carries the consumer's VPC endpoint ID, have the ALB-fronted application log that ID, and join it against the endpoint service connections inventory to get per-account request and error rates for quota enforcement. Keep application-level authentication regardless — PrivateLink authenticates the network path, not the caller, so SigV4 or mutual TLS or OIDC still does the identity work. Leave PrivateLink security group enforcement off initially, then enable it deliberately after adding rules that match endpoint-sourced traffic, in a staged change with a rollback.</p>\n<p style=\"line-height: 1.75\">Scale, cost and failure modes. Fifty endpoints times three zones is a hundred and fifty endpoint ENIs, all billed hourly to the consumers — publish that number so teams place endpoints only in the zones they actually use, and note that consumers can trade availability for cost by using fewer zones. Watch for ephemeral-port pressure on the provider side and keep enough ALB nodes and targets registered; keep cross-zone load balancing off to avoid inter-AZ charges and keep ALB capacity symmetric per zone. Document the onboarding as a three-line Terraform module for consumers, because the whole point of this design is that a consumer team can self-serve in minutes without the platform team touching a route table. Finally, be explicit about what PrivateLink does not solve: it is unidirectional, so callbacks need a reverse endpoint service; it does not replace authentication; it does not protect against a malicious authorized consumer; and a provider-side outage is still a provider-side outage — the private path adds no resilience by itself.</p>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"PrivateLink exposes one service, in one direction, over the AWS private network.
