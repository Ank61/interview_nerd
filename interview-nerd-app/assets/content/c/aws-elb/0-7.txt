{"title":"Network Load Balancer Basics — Layer 4, Static IPs, and Extreme Performance","tags":["elb","nlb","layer4","static-ip"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">The Application Load Balancer reads your HTTP requests and routes on their contents. The <strong>Network Load Balancer (NLB)</strong> takes the opposite approach: it forwards connections without looking inside them at all. That one design decision explains everything else about it — its speed, the protocols it supports, its fixed IP addresses, and the things it simply cannot do.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What &quot;layer 4&quot; actually means here</h4>\n<p style=\"line-height: 1.75\">Networking is often described as a stack of layers. <strong>Layer 4 is the transport layer</strong>, where <strong>TCP</strong> (a reliable, ordered connection — the basis of HTTP, databases and SSH) and <strong>UDP</strong> (fast, connectionless, fire-and-forget packets — used by DNS, video streaming and game traffic) live. <strong>Layer 7 is the application layer</strong>, where HTTP and its URLs and headers live.</p>\n<p style=\"line-height: 1.75\">An NLB operates at layer 4. In plain words: it sees &quot;a TCP connection arriving on port 443 from this client address&quot;, picks a target, and shovels bytes between the two. It <strong>does not parse the contents</strong>. The consequences follow directly:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Extremely fast, with very low latency.</strong> There is no HTTP parsing, no header rewriting, no buffering of a full request before forwarding. AWS reports single-digit millisecond latencies added by the NLB, noticeably lower than an ALB.</li>\n<li><strong>Absorbs sudden enormous spikes.</strong> The NLB is engineered to handle millions of requests per second and volatile traffic patterns without any pre-warming. An ALB scales up too, but it scales — for a genuinely instantaneous flash of traffic (a ticket sale opening, a broadcast mention) the NLB's capacity model is more forgiving.</li>\n<li><strong>It cannot route on a URL path or a host name.</strong> Those live in the encrypted-or-not HTTP payload the NLB never reads. There are no path-pattern rules, no host-header rules, no header rules, no redirects, no fixed responses. An NLB listener maps a port to a target group and that is all.</li>\n<li><strong>No HTTP-level features at all.</strong> No cookie-based sticky sessions (stickiness on an NLB is per-connection flow), no <code>X-Forwarded-For</code> header injection, no integration with AWS WAF (the web application firewall, which inspects HTTP requests).</li>\n</ul>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">WHAT <i class=k>EACH</i> <i class=k>ONE</i> SEES\n\n ALB  (layer <i class=n>7</i>)                       NLB  (layer <i class=n>4</i>)\n <i class=c>---------------------                -----------------------</i>\n <i class=k>GET</i> <i class=o>/</i>api<i class=o>/</i>v2<i class=o>/</i>orders?x<i class=o>=</i><i class=n>1</i>               TCP connection\n Host: api.example.com                   <i class=k>from</i> <i class=n>203.0</i><i class=n>.113</i><i class=n>.9</i>:<i class=n>51234</i>\n <i class=k>User</i><i class=o>-</i>Agent: curl<i class=o>/</i><i class=n>8.4</i>                    <i class=k>to</i>   port <i class=n>443</i>\n Cookie: session<i class=o>=</i>abc                  ...bytes...\n                                      (contents never parsed)\n <i class=o>-</i><i class=o>&gt;</i> can route <i class=k>on</i> <i class=k>any</i> <i class=k>of</i> this          <i class=o>-</i><i class=o>&gt;</i> can <i class=k>only</i> choose a target</code></pre></div>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Static IP addresses — the headline feature</h4>\n<p style=\"line-height: 1.75\">An ALB gives you a <strong>DNS name</strong> only, and the IP addresses behind that name change over time as AWS scales the load balancer. You are expected to always resolve the name. Its listeners support <strong>TCP</strong>, <strong>UDP</strong>, <strong>TCP_UDP</strong> (both on the same port), and <strong>TLS</strong>. This unlocks a whole category of workloads an ALB cannot touch:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Game servers.</strong> Real-time multiplayer traffic is usually UDP for latency reasons. An ALB speaks only HTTP; an NLB forwards the UDP packets happily.</li>\n<li><strong>DNS services.</strong> DNS runs on UDP port 53 (with TCP as a fallback), which is exactly what TCP_UDP on one port is for.</li>\n<li><strong>MQTT brokers.</strong> The lightweight publish/subscribe protocol used by IoT devices runs over long-lived TCP connections.</li>\n<li><strong>Mail servers.</strong> SMTP on port 25 or 587, IMAP on 993 — plain TCP protocols.</li>\n<li><strong>Database proxies.</strong> PostgreSQL on 5432, MySQL on 3306, Redis on 6379: none of these are HTTP, so only a layer 4 load balancer can distribute them.</li>\n<li><strong>gRPC and WebSockets over raw TCP</strong>, or any custom binary protocol your own application invents.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">TLS listeners on an NLB</h4>\n<p style=\"line-height: 1.75\">A <strong>TLS listener</strong> on an NLB lets it terminate encryption at layer 4. It holds an <strong>ACM certificate</strong> (AWS Certificate Manager issues these free and renews them automatically), completes the TLS handshake with the client, decrypts the byte stream, and forwards the plain bytes to a TCP target group — all without ever interpreting those bytes as HTTP. You still get certificate management in one place, automatic renewal, a configurable <strong>security policy</strong> (which TLS versions and ciphers are allowed), and multiple certificates with <strong>SNI</strong> so the client can name the host it wants during the handshake.</p>\n<p style=\"line-height: 1.75\">The distinction from an ALB's HTTPS listener is what happens after decryption. An ALB parses the HTTP request and can route on it. An NLB TLS listener just hands the decrypted stream onward. So a TLS listener is the right tool when you want centrally managed certificates for a <em>non-HTTP</em> protocol — encrypted MQTT for IoT devices, or a TLS-wrapped custom protocol — or when you want HTTPS with static IPs and no layer 7 processing. If you do not need termination, a plain <strong>TCP</strong> listener passes the encrypted traffic straight through untouched, letting your own servers terminate TLS and see the client certificates themselves.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Source IP preservation — and the security group trap</h4>\n<p style=\"line-height: 1.75\">This is the NLB behaviour that confuses beginners most, and it is worth getting completely straight.</p>\n<p style=\"line-height: 1.75\">With an <strong>ALB</strong>, the load balancer terminates the client's connection and opens its own new connection to the target. Your server therefore sees the <em>load balancer's</em> private IP as the source of every request. To find the real client, your application reads the <strong>X-Forwarded-For</strong> header, which the ALB adds.</p>\n<p style=\"line-height: 1.75\">With an <strong>NLB</strong> using <code>instance</code> or <code>ip</code> targets, <strong>client IP preservation</strong> is on by default: the packets arrive at your server still carrying the <em>original client's</em> IP address as the source. Your server sees <code>203.0.113.9</code>, the actual visitor, with no header needed. This is genuinely useful — logging, geolocation, rate limiting and IP-based access control all just work with no application changes.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">SOURCE ADDRESS <i class=k>AS</i> THE TARGET SEES IT\n\n Client <i class=n>203.0</i><i class=n>.113</i><i class=n>.9</i>\n     <i class=o>|</i>\n     v\n [ ALB <i class=n>10.0</i><i class=n>.1</i><i class=n>.50</i> ]  <i class=c>--new connection--&gt;  target sees src = 10.0.1.50</i>\n                                         <i class=t>real</i> client <i class=k>only</i> <i class=k>in</i> X<i class=o>-</i>Forwarded<i class=o>-</i><i class=k>For</i>\n\n Client <i class=n>203.0</i><i class=n>.113</i><i class=n>.9</i>\n     <i class=o>|</i>\n     v\n [ NLB ]  <i class=c>--preserved--&gt;                 target sees src = 203.0.113.9</i>\n                                         <i class=k>no</i> header needed</code></pre></div>\n<p style=\"line-height: 1.75\"><strong>The security group consequence.</strong> A <strong>security group</strong> is a virtual firewall around a resource, allowing traffic based on source. With an ALB you write a neat rule on your instances: &quot;allow port 80 from the load balancer's security group&quot;. That is tidy, self-maintaining and specific.</p>\n<p style=\"line-height: 1.75\">With an NLB preserving client IPs, <strong>that rule breaks</strong> — the traffic no longer appears to come from the load balancer, so a rule referencing the load balancer matches nothing and every request is silently dropped. Health checks may still pass (they originate from the NLB's own address range within your VPC), which makes the symptom maddening: targets show as healthy while real client traffic times out. The instance security group must instead allow traffic from <strong>the actual client addresses</strong>, which for a public service means <code>0.0.0.0/0</code> on the service port. Your instances are still in private subnets and unreachable from the internet directly, but the rule is much broader than the ALB equivalent.</p>\n<p style=\"line-height: 1.75\">Two things soften this. Since 2023 an NLB can itself have <strong>security groups</strong> attached, so you can filter at the load balancer and additionally control whether traffic that bypasses the NLB is allowed to reach targets. And for <code>ip</code>-type target groups you can <strong>disable client IP preservation</strong>, restoring ALB-like behaviour where the NLB's address is the source — at the cost of losing the real client IP. Note that preservation cannot be turned off for <code>instance</code>-type targets, and that it is off by default for <code>ip</code> targets behind a TLS listener.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Health checks on an NLB</h4>\n<p style=\"line-height: 1.75\">A <strong>health check</strong> is a periodic probe the load balancer sends to each target to decide whether to keep sending it traffic. NLB supports <strong>TCP</strong>, <strong>HTTP</strong> and <strong>HTTPS</strong> checks, and the choice matters more than beginners expect:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>TCP checks</strong> only confirm that something accepts a connection on the port. They are the default for TCP listeners and they are <em>shallow</em>: a web server that has accepted the socket but whose database connection pool is exhausted, or which returns 500 to every request, passes a TCP check perfectly. Treat a passing TCP check as &quot;the process is running&quot;, not &quot;the application works&quot;.</li>\n<li><strong>HTTP or HTTPS checks</strong> request a path such as <code>/health</code> and require a success status code. Use these whenever the target is actually a web server, even behind an NLB, because they test the application rather than the socket.</li>\n</ul>\n<p style=\"line-height: 1.75\">Two NLB-specific behaviours to know. First, NLB health checks come from addresses within your VPC's own range, not from the client, which is why a misconfigured security group can leave targets healthy while real traffic fails. Second, and important operationally: if <strong>all</strong> targets in a target group are marked unhealthy, the NLB <strong>fails open</strong> and routes requests to all targets anyway, on the reasoning that a possibly-broken target beats a guaranteed total outage. This can be confusing during an incident — traffic is flowing to targets the console says are unhealthy — so if your health check is itself misconfigured, an NLB will keep serving traffic while an ALB would return 503.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cross-zone load balancing: off by default on NLB</h4>\n<p style=\"line-height: 1.75\">AWS places a load balancer <strong>node</strong> in each Availability Zone you enable. <strong>Cross-zone load balancing</strong> controls whether a node may send traffic to targets in <em>other</em> zones or only to targets in its own.</p>\n<p style=\"line-height: 1.75\">The commonly tested fact: <strong>cross-zone load balancing is enabled by default for the Application Load Balancer and disabled by default for the Network Load Balancer.</strong> Know that sentence verbatim.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">NLB <i class=k>DEFAULT</i> (<i class=k>cross</i><i class=o>-</i>zone OFF) <i class=c>-- unbalanced zones hurt</i>\n\n  zone A node: <i class=n>50</i><i class=o>%</i> <i class=k>of</i> traffic <i class=c>--&gt; 1 target   =&gt; that target gets 50%</i>\n  zone B node: <i class=n>50</i><i class=o>%</i> <i class=k>of</i> traffic <i class=c>--&gt; 9 targets  =&gt; each gets ~5.6%</i>\n\n  The single zone<i class=o>-</i>A target carries nine times the load <i class=k>of</i> <i class=k>each</i>\n  zone<i class=o>-</i>B target, <i class=k>and</i> will fall <i class=k>over</i> first.\n\n<i class=k>CROSS</i><i class=o>-</i>ZONE <i class=k>ON</i> <i class=c>-- every node reaches every target</i>\n\n  <i class=k>all</i> traffic <i class=c>--&gt; 10 targets =&gt; each gets 10%</i></code></pre></div>\n<p style=\"line-height: 1.75\">Turning it on evens out uneven target counts and makes the fleet behave as one pool. font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>&quot;The NLB is just a faster ALB, so I should always pick it.&quot;</strong> It is faster because it does less. Choosing it for a web app throws away path and host routing, cookie stickiness, redirects, <code>X-Forwarded-For</code> and WAF support. Pick by required features first, performance second.</li>\n<li><strong>&quot;An NLB can route /api to a different service.&quot;</strong> It cannot. Paths live in the HTTP payload it never reads. Different ports can go to different target groups, but URLs cannot.</li>\n<li><strong>&quot;Cross-zone load balancing is always on.&quot;</strong> On for ALB, <strong>off by default for NLB</strong>. This is one of the most frequently tested facts about ELB.</li>\n<li><strong>&quot;My instance security group can allow traffic from the load balancer's security group.&quot;</strong> That works for an ALB. Behind an NLB preserving client IPs, the source is the <em>client</em>, so such a rule drops everything — while health checks still pass, so targets look healthy and traffic times out.</li>\n<li><strong>&quot;I can add Elastic IPs to my ALB.&quot;</strong> ALBs do not support Elastic IPs and their addresses change. If you need fixed addresses, use an NLB — optionally with an ALB registered behind it.</li>\n<li><strong>&quot;A passing TCP health check means my app is working.&quot;</strong> It means a process accepted a connection.
