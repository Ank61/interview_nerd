Say a banking partner insists on allow-listing a fixed IP address, but you also need path-based routing. You register the ALB as a target of an NLB: clients hit the NLB's static IP, and the NLB forwards to the ALB, which does the HTTP routing. You pay for two load balancers and add a small amount of latency, and in exchange you get both properties.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">How ELB relates to neighbouring services</h4>\n<p style=\"line-height: 1.75\">Beginners often frame these as competitors — \"should I use CloudFront or an ALB?\" — when in practice they stack.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Amazon CloudFront (a CDN) in front of an ALB.</strong> A <strong>CDN (content delivery network)</strong> is a global network of edge locations that cache copies of your content near users. CloudFront terminates TLS at the edge, serves cached assets without touching your servers at all, and keeps a warm connection back to your ALB for the requests it must forward — which also makes dynamic responses faster because the slow first-hop handshake happens close to the user. It is <em>in front of</em>, never <em>instead of</em>: CloudFront still needs an origin, and that origin is your load balancer.</li>\n<li><strong>Amazon Route 53 (DNS) above everything.</strong> <strong>DNS</strong> is the system that turns a hostname into an address. Route 53 is AWS's DNS service, and you use an <strong>alias record</strong> to point <code>www.example.com</code> at your load balancer's DNS name — an alias is free to query and follows the load balancer's changing addresses automatically. Beyond that, Route 53 offers <strong>health-checked failover</strong> (if the primary Region's endpoint fails its check, DNS answers with the secondary) and <strong>latency-based routing</strong> (each user is sent to the Region that is fastest for them). The crucial point: <strong>ELB balances within one Region; Route 53 is what spans Regions.</strong> No amount of ELB configuration will fail over to another Region. If you need sub-minute, TCP-level global failover instead of DNS-level, <strong>AWS Global Accelerator</strong> gives you two static anycast IPs that route to the nearest healthy Regional endpoint.</li>\n<li><strong>API Gateway versus ALB for an API.</strong> Choose <strong>API Gateway</strong> when you need per-client <strong>API keys and usage plans</strong>, request/response validation against a schema, throttling per consumer, a developer portal, request/response transformation, or tight Lambda and WebSocket integration — and note it is billed per request, which is excellent at low volume and expensive at high volume. Choose an <strong>ALB</strong> when you have containers or EC2 behind a straightforward HTTP API, want predictable hourly-plus-LCU pricing at scale, and do not need per-consumer quotas. Many teams run both: API Gateway for the public partner-facing API, an internal ALB for service-to-service calls.</li>\n<li><strong>Kubernetes and service meshes use ELB underneath.</strong> On Amazon EKS, the <strong>AWS Load Balancer Controller</strong> turns a Kubernetes <code>Ingress</code> resource into an ALB and a <code>Service</code> of type LoadBalancer into an NLB. ECS services register tasks into target groups directly. So \"we use Kubernetes ingress\" is not an alternative to ELB — it is ELB, created for you by a controller. Understanding target groups and health checks is exactly what lets you debug an ingress that will not come up.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The <strong>Route 53</strong> gives users a memorable name and is the only layer that can move traffic between Regions. <strong>CloudFront</strong> serves cached content from the edge so most requests Always use its <strong>DNS name</strong>, and point your domain at it with a Route 53 <strong>alias record</strong>. If you genuinely need a fixed address, that is the reason to use an NLB, not a reason to look up an ALB's current IPs.</li>\n<li><strong>Enabling only one Availability Zone.</strong> An ALB requires at least two subnets in different <strong>AZs</strong> (independent data centres in a Region) for exactly this reason. One zone means one power or network event takes your whole site offline, and the load balancer cannot help.</li>\n<li><strong>Security groups open to the world on app servers.</strong> The app tier's security group should allow its port only from the <strong>load balancer's security group</strong>. Opening <code>0.0.0.0/0</code> there discards the isolation the load balancer was giving you.</li>\n<li><strong>Forgetting the health check port rule.</strong> If health checks use a different port from traffic, that port needs its own inbound rule. This is the single most common cause of \"all targets unhealthy while the app works fine\".</li>\n<li><strong>A health check path that returns 404.</strong> Health checks expect a <strong>2xx</strong> status. Pointing at <code>/</code> on an API that has no root route, or at a path removed during a refactor, marks every target unhealthy. Use a dedicated endpoint such as <code>/healthz</code> and include it in your deployment tests.</li>\n<li><strong>A health check that also checks the database.</strong> Tempting, but if the shared database hiccups, <em>every</em> target fails at once, the load balancer has nowhere to send traffic, and a recoverable database blip becomes a total outage. Keep the load balancer health check <strong>shallow</strong> — is this process alive and serving? — and put dependency checks on a separate <code>/ready</code> endpoint used by deployment tooling and dashboards.</li>\n<li><strong>Relying on sticky sessions instead of externalising state.</strong> Stickiness causes uneven load, loses sessions when a target dies, and makes every rolling deploy log users out. Move sessions to <strong>Redis/ElastiCache</strong>, DynamoDB, or a signed token.</li>\n<li><strong>App keep-alive shorter than the ALB idle timeout.</strong> The ALB reuses pooled connections; if your app closes one first, the next request lands in a closed socket and the ALB returns <strong>502</strong>. The app's keep-alive must be <em>longer</em> than the idle timeout (65-75 s against the 60 s default).</li>\n<li><strong>Not enabling access logs before an incident.</strong> They are off by default and need an S3 bucket policy. You cannot retroactively log something that already happened, so turn them on when you create the load balancer.</li>\n<li><strong>No alarm on UnHealthyHostCount.</strong> Alarm on <code>UnHealthyHostCount &gt; 0</code> as early warning and on <code>HealthyHostCount</code> below your minimum as the page-someone alarm, with <code>--treat-missing-data breaching</code> so an empty target group actually fires.</li>\n<li><strong>Unbalanced target counts across zones with cross-zone disabled.</strong> With <strong>cross-zone load balancing</strong> off, each load balancer node only sends to targets in its own zone, and traffic is split evenly <em>per zone</em>. Two targets in AZ-A and eight in AZ-B means each AZ-A target gets 25% of traffic and each AZ-B target gets 6.25%. Either enable cross-zone (on by default for ALB, off by default for NLB target groups) or keep target counts balanced.</li>\n<li><strong>Running many load balancers where one would do.</strong> Ten services with ten ALBs means ten hourly charges. Consolidate with <strong>host-based</strong> or <strong>path-based routing</strong> on one ALB; the LCU usage follows real traffic and barely changes, so the saving is close to pure.</li>\n<li><strong>Forgetting deregistration delay during deployments.</strong> Set it just above your slowest normal request (30-60 s is typical) so in-flight requests finish. Leaving the 300-second default makes every rolling deploy crawl; setting it to 0 severs live requests.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"A load balancer makes my app highly available on its own.\"</strong> It only routes around targets it knows are unhealthy. You still need multiple AZs, an Auto Scaling group, a Multi-AZ database and no other single point of failure.</li>\n<li><strong>\"ELB can fail over between Regions.\"</strong> It cannot. An ELB is Regional. <strong>Route 53</strong> health-checked failover or <strong>Global Accelerator</strong> is what spans Regions.</li>\n<li><strong>\"CloudFront replaces my load balancer.\"</strong> CloudFront is a CDN and needs an <strong>origin</strong>; the ALB is that origin. They stack.</li>\n<li><strong>\"API Gateway and ALB do the same job.\"</strong> Overlapping, not identical. API keys, usage plans, per-consumer throttling and schema validation are API Gateway features; predictable hourly-plus-LCU pricing at high volume favours the ALB.</li>\n<li><strong>\"Kubernetes ingress is an alternative to ELB.\"</strong> On EKS the AWS Load Balancer Controller creates an actual ALB or NLB for you — it <em>is</em> ELB with a Kubernetes-shaped front end.</li>\n<li><strong>\"The Classic Load Balancer is fine for new projects.\"</strong> It is legacy. Use an ALB for HTTP and an NLB for TCP/UDP; new features land only on the newer types.</li>\n<li><strong>\"A deeper health check is a better health check.\"</strong> A health check that tests shared dependencies takes every target down simultaneously when a dependency wobbles. Shallow for the load balancer, deep for a separate readiness endpoint.</li>\n<li><strong>\"More load balancers means better isolation.\"</strong> Sometimes, but usually it just means more hourly charges and more things to monitor. Host- and path-based routing on one ALB gives logical separation at a fraction of the cost.</li>\n</ul>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"I default to an ALB for HTTP because only it routes on path, host and header.
