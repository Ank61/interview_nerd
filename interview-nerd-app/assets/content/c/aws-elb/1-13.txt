{"title":"Troubleshooting Production Load Balancers — A Symptom-Driven Playbook","tags":["troubleshooting","502-503-504","health-checks","incident-response"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Load balancer incidents are unusually tractable because the load balancer tells you almost everything if you know which field to read. The difference between a twenty-minute incident and a three-hour one is almost never cleverness — it is having a <strong>symptom-to-signal mapping</strong> memorized so you stop guessing. This playbook is organized the way a page arrives: by symptom. For each symptom there is a short list of candidate causes, and for each cause a specific metric, access log field or CLI command that confirms or eliminates it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">General Triage Ordering</h4>\n<p style=\"line-height: 1.75\">Before any symptom-specific work, run the same four steps every time. Three distinguishable causes:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>No healthy targets.</strong> Targets are registered but all failing health checks. Confirm with <code>HealthyHostCount = 0</code> per target group per AZ and <code>describe-target-health</code> showing <code>unhealthy</code> with a reason. Then the question becomes why the health check fails — see Symptom 4.</li>\n<li><strong>No targets registered at all.</strong> <code>HealthyHostCount</code> and <code>UnHealthyHostCount</code> are both zero and <code>describe-target-health</code> returns an empty list. This is a deployment or automation failure: an Auto Scaling group detached from the target group, a Terraform apply that replaced the target group, an ECS service with zero desired tasks, or a Kubernetes target group controller that lost permissions. Nothing is wrong with your application — the plumbing is disconnected.</li>\n<li><strong>Load balancer or listener problems.</strong> A rule with no target group, a default action pointing at an empty group, or — the rarer case — the load balancer itself unable to scale into a near-instant traffic spike. ALB scales by adding capacity, which takes minutes; a flash spike of tens of times normal traffic can produce 503s and <code>RejectedConnectionCount</code> during scale-out. Correlate the 503s with <code>ConsumedLCUs</code> and <code>NewConnectionCount</code> slope: if the 503 window aligns exactly with a near-vertical traffic ramp and targets stayed healthy throughout, it is a scaling event, and the fix is architectural (CloudFront absorbing the spike, or an arrangement with AWS to pre-scale for a known event) not a health check change.</li>\n</ul>\n<p style=\"line-height: 1.75\">One subtlety: a 503 can also come from <em>your application</em>, in which case it appears in <code>HTTPCode_Target_5XX_Count</code> with <code>target_status_code = 503</code>. People chase load balancer configuration for hours on an application-generated 503. Always check the attribution first.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 2: 502 Bad Gateway</h4>\n<p style=\"line-height: 1.75\">A 502 means the load balancer got a connection to the target but the response was unusable: the target closed the connection before responding, or sent something the load balancer could not parse as valid HTTP. historical default keep-alive timeout was 5 seconds against a 60-second ALB idle timeout, producing a steady background rate of 502s that looks random and correlates with nothing. Other causes worth eliminating: the <strong>application crashed or was OOM-killed</strong> mid-request (check the target's process logs and dmesg for the exact timestamps from the access log); a <strong>TLS mismatch to the target</strong> when the target group protocol is HTTPS but the target speaks plain HTTP, or the target's certificate is malformed; <strong>header size violations</strong> where the target's response headers exceed what the load balancer accepts; and a target returning <strong>malformed HTTP</strong> — duplicate Content-Length, invalid chunked encoding, or headers with invalid characters, which is also where desync mitigation mode can convert an ambiguous response into a rejected one. The access log <code>error_reason</code> and <code>classification_reason</code> fields name the specific violation, which is why guessing is unnecessary.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 3: 504 Gateway Timeout</h4>\n<p style=\"line-height: 1.75\">A 504 means the target did not respond within the load balancer's idle timeout. The load balancer is correct and the timeout is doing its job; the question is <em>what</em> is slow. This is where the three processing-time fields are decisive.</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; Take a trace id from a 504 row, find it in the application logs, and look at X-Ray or your own span timings. The correct fix is almost never raising the ALB idle timeout — that converts fast failures into slow ones and holds connections open, consuming LCUs and client patience. The correct fixes are a <strong>shorter timeout on the dependency call</strong> than the request budget, a circuit breaker, bulkheads so one slow dependency cannot consume the whole worker pool, and an explicit request budget that returns a fast error. Raise the idle timeout only for genuinely long-lived request semantics such as streaming responses or large uploads, and when you do, remember to raise the target keep-alive above it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 4: Targets Flapping Between Healthy and Unhealthy</h4>\n<p style=\"line-height: 1.75\">Flapping is worse than a stable failure because it produces intermittent errors, churns connections, and can trigger Auto Scaling replacement loops. Four causes, in order of frequency:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Thresholds too tight.</strong> A 5-second interval with a 2-second timeout and an unhealthy threshold of 2 means <em>two</em> slightly slow responses take a target out. Under normal p99 variance that happens regularly. Widen the timeout above your health endpoint's p99 with real headroom, and use an unhealthy threshold of 3 or more so a single blip cannot evict. Health checks should be decisive, not twitchy.</li>\n<li><strong>The health check competes with real traffic.</strong> On a saturated application the health endpoint queues behind real requests and times out — so the load balancer removes the target, sending its traffic to the remaining targets, which saturate further and also fail. This is a <strong>cascading failure driven by the health check itself</strong>, and it is why the health endpoint should be cheap and ideally served with reserved capacity or a separate listener port, and why <strong>target group health</strong> settings (minimum healthy count or percentage, with DNS or routing failover behavior) matter: below the configured minimum, ALB can fail open and route to all targets rather than hammering the survivors.</li>\n<li><strong>A deep health check failing on a dependency blip.</strong> If <code>/health</code> checks the database, a two-second database hiccup marks <em>every</em> target in <em>every</em> zone unhealthy simultaneously and turns a minor dependency event into a full outage. The rule: the load balancer health check answers &quot;can this process serve traffic?&quot; (shallow, cheap, no dependencies), while deep dependency checks belong in a separate monitoring endpoint that pages humans but does not control routing.</li>\n<li><strong>Garbage collection or runtime pauses.</strong> A multi-second stop-the-world pause fails health checks on an otherwise fine JVM. Correlate flap timestamps with GC logs. The fix is heap and collector tuning, plus a timeout that tolerates your p99.9 pause — not a looser threshold that hides real failures.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 5: Uneven Load Distribution</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Cross-zone disabled with unbalanced target counts.</strong> The canonical case: traffic arrives roughly evenly across zonal nodes, but if one zone has 2 targets and another has 8, each target in the small zone gets four times the load. Confirm with <code>RequestCountPerTarget</code> per AZ. Fix by balancing target counts across zones (Auto Scaling with all zones and balanced capacity) or by enabling cross-zone.</li>\n<li><strong>NLB flow hashing with long-lived connections.</strong> NLB assigns a flow to a target by hash and keeps it there for the life of the connection. With a handful of long-lived connections — a message broker, a gRPC client pool, a database proxy — the hash distribution is statistically lumpy and stays lumpy for hours. This is not a bug; it is what flow-level load balancing means. Fixes: more connections, periodic client-side connection recycling, or layer-7 load balancing where request-level distribution is what you actually need.</li>\n<li><strong>Sticky sessions.</strong> Duration-based or application-based stickiness pins clients to a target, so distribution follows session lifetime, not request rate. Combined with an autoscaling event, new targets receive almost nothing while old ones stay loaded. Slow start helps new targets ramp, but the honest fix is externalizing session state so stickiness is unnecessary.</li>\n<li><strong>Client DNS caching.</strong> A client (or a JVM with a long DNS TTL, or an SDK caching resolution) that resolves the load balancer name once and reuses one node address forever sends all its traffic through that zonal node. With cross-zone off, that pins traffic to one zone's targets. This is also why load tests from a single host produce misleading distribution results.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 6: Intermittent Connection Resets or Hangs</h4>\n<p style=\"line-height: 1.75\">These are the hardest because they are usually not the load balancer. Work through: <strong>idle timeout mismatches</strong> at every hop (client, load balancer, target, and any NAT or firewall in between — a NAT gateway idles connections out at its own timeout and drops them silently, so a connection the client believes is open is gone, producing a hang until the client's own timeout); <strong>MTU and path MTU discovery</strong> problems, where large packets are dropped because ICMP &quot;fragmentation needed&quot; is blocked by a security group or on-premises firewall, so small requests work and large ones hang — the fingerprint is size-dependent failure; <strong>security group asymmetry</strong>, where the target allows inbound from the load balancer but egress rules or NACLs block the return path, or health checks pass on one port while traffic uses another; and <strong>client IP preservation on NLB</strong>, which changes the source address arriving at the target from the NLB's private address to the real client address, so target security groups must allow the client ranges, not the VPC CIDR. Enabling client IP preservation has also historically produced connection failures in specific topologies — for example when a target connects back through NAT, or when the client and target are the same instance, or with certain instance-behind-NLB-behind-NAT arrangements — and it interacts with the <code>preserve_client_ip</code> and hairpinning rules. For NLB, use <code>TCP_ELB_Reset_Count</code> versus <code>TCP_Target_Reset_Count</code> to establish <em>who</em> sent the reset before theorizing, and VPC Flow Logs to confirm whether packets arrived at all.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 7: TLS Handshake Failures</h4>\n<p style=\"line-height: 1.75\">Signal: rising <code>ClientTLSNegotiationErrorCount</code>, and individual events in connection logs. Causes: <strong>security policy incompatibility</strong> after tightening minimum TLS version or cipher suites — the client and load balancer share no mutually acceptable version or cipher; <strong>missing SNI</strong> on old clients, which matters because a multi-certificate listener needs SNI to choose a certificate and falls back to the default certificate, which may be the wrong one for that hostname (check <code>domain_name</code> and <code>chosen_cert_arn</code> in the access log); <strong>certificate chain or expiry problems</strong>, including a chain missing intermediates that some clients tolerate and others reject, and an ACM certificate that failed renewal because its DNS validation record was deleted; and <strong>mTLS trust store issues</strong>, where the client certificate is not signed by a CA in the configured trust store, has expired, or the revocation list rejects it. Reproduce precisely with <code>openssl s_client</code> against the load balancer, specifying the protocol version and the SNI servername, which converts a vague report into a one-line confirmation.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 8: Latency Spike With No Application Change</h4>\n<p style=\"line-height: 1.75\">Candidates, each with a distinguishing signal: <strong>load balancer scale-out during a spike</strong> (correlate with a near-vertical <code>NewConnectionCount</code> ramp and any <code>RejectedConnectionCount</code>; latency recovers on its own within minutes); <strong>a single unhealthy or degraded zone</strong> (per-AZ <code>TargetResponseTime</code> split — flat p50 with a spiking p99 in one zone); <strong>target saturation</strong> (elevated <code>request_processing_time</code> and <code>TargetConnectionErrorCount</code> with rising CPU or thread-pool utilization, meaning queueing in front of the app); <strong>one bad host</strong> (group latency by <code>target:port</code>); and <strong>a dependency</strong> (elevated <code>target_processing_time</code> with normal target CPU — the app is waiting, which X-Ray attributes to a specific call). A useful sanity check is the gap between load-balancer-observed latency and application-self-reported latency: when that gap widens, the delay is in accept queues and connection handling, not in your handlers.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 9: Requests Not Reaching the Expected Target Group</h4>\n<p style=\"line-height: 1.75\">Listener rules are evaluated in <strong>priority order, lowest number first, and the first match wins</strong> — there is no most-specific-match logic. A broad rule at priority 10 matching <code>/api/*</code> shadows a specific rule at priority 20 matching <code>/api/v2/reports</code>, and the specific rule is dead code. Diagnose from the access log: <code>matched_rule_priority</code> tells you exactly which rule fired and <code>actions_executed</code> tells you what it did, which turns an argument into a fact in one query. Two other traps: path patterns are <strong>case-sensitive</strong> while host header matching is <strong>case-insensitive</strong>, so <code>/API/v2</code> does not match a <code>/api/*</code> pattern; and wildcards behave as you would expect only if you write them — <code>/api</code> matches exactly that path, not its children, which needs <code>/api/*</code> (usually both). Also remember that query strings are not part of path-pattern matching — use a query-string condition for those — and that a default action applies only when no rule matches.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Incident Walkthrough: Page to Root Cause</h4>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=n>03</i>:<i class=n>14</i>  PAGE: api <i class=n>5</i>xx ratio <i class=n>4.2</i><i class=o>%</i> (threshold <i class=n>1</i><i class=o>%</i>).\n<i class=n>03</i>:<i class=n>15</i>  ATTRIBUTE: HTTPCode_ELB_502 <i class=o>=</i> <i class=n>1</i>,<i class=n>900</i><i class=o>/</i>min.
