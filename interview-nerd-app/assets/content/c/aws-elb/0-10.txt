Where does a logged-in user's data live? What happens to a request that is half-finished when you deploy? How long may a quiet connection stay open? This topic covers the five settings that answer those questions — stickiness, deregistration delay, idle timeout, slow start and the health check grace period — and why the wrong values produce the mysterious intermittent errors that eat whole afternoons.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The state problem, concretely</h4>\n<p style=\"line-height: 1.75\">A <strong>session</strong> is the server's memory of who you are between requests. HTTP itself has no memory — each request arrives on its own with no knowledge of the last one — so when you log in, the server typically creates a session record holding \"this is user 4127\", gives your browser a <strong>cookie</strong> (a small piece of text the browser stores and sends back with every later request to that site) containing a session ID, and looks the record up next time.</p>\n<p style=\"line-height: 1.75\">On one server that works perfectly. Now add a second server behind a load balancer and imagine session records live in each server's own memory:</p>\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">Request 1  POST /login       -&gt; ALB -&gt; Server A   creates session abc123 <i class=k>in</i> RAM\n                                        Server A knows: abc123 = user 4127\nRequest 2  GET  /dashboard   -&gt; ALB -&gt; Server B   looks up abc123 ... not found\n                                        Server B redirects to /login\n\n  User<i class=s>&#x27;s experience: &quot;I keep getting logged out at random.&quot;</i></code></pre></div>\n<p style=\"line-height: 1.75\">Roughly half the requests land on the server that has no idea who you are, so you appear to be randomly logged out. That is the problem stickiness solves — and it is also why experienced engineers prefer to avoid needing stickiness at all.</p>\n<p style=\"line-height: 1.75\">A <strong>stateless</strong> application is one where any server can handle any request because no per-user data is kept in a server's local memory. Every server can serve every user identically, which means you can add, remove and replace servers freely. Statelessness is the property that makes horizontal scaling and zero-downtime deployments easy, and losing it is the real cost of leaning on sticky sessions.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Sticky sessions (session affinity)</h4>\n<p style=\"line-height: 1.75\"><strong>Sticky sessions</strong>, also called <strong>session affinity</strong>, tell the load balancer to keep sending the same client back to the same target. It is enabled per <em>target group</em>, not per load balancer. On an ALB there are two flavours.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Load balancer generated cookie (duration-based).</strong> The ALB issues its own cookie named <strong>AWSALB</strong> (plus <code>AWSALBCORS</code> for cross-site requests, which carries the SameSite attribute browsers need). The cookie encodes which target to use, and you set how long it lasts with <code>stickiness.lb_cookie.duration_seconds</code> — anywhere from 1 second to 7 days, default 1 day (86400). Your application needs no changes at all. On a Classic Load Balancer the equivalent cookie is <code>AWSELB</code>.</li>\n<li><strong>Application-based stickiness.</strong> Your application sets its own cookie — you name it, for example <code>MYSESSION</code> — and the ALB wraps it in a cookie called <strong>AWSALBAPP</strong> that maps it to a target. The attribute is <code>stickiness.app_cookie.cookie_name</code>, with <code>stickiness.app_cookie.duration_seconds</code> controlling lifetime. The advantage is that <em>your app</em> decides when affinity ends: if the app stops sending the cookie, stickiness stops too, so a logout can genuinely release the user. The names <code>AWSALB</code>, <code>AWSALBCORS</code>, <code>AWSALBAPP</code> and <code>AWSALBTG</code> are reserved — do not use them for your own cookies.</li>\n</ul>\n<p style=\"line-height: 1.75\">On a <strong>Network Load Balancer</strong> there are no cookies, because there is no HTTP. Affinity there is based on the client's IP address, via <code>stickiness.enabled</code> with type <code>source_ip</code>.</p>\n<p style=\"line-height: 1.75\">Now the downsides, which are the part interviews probe:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Uneven load.</strong> Requests are pinned to targets, not balanced. A few heavy users can pile onto one instance while another idles. Load balancing stops being load balancing.</li>\n<li><strong>A failure loses those users' sessions.</strong> If the target a user is stuck to dies, their session dies with it. They are logged out, their shopping cart is gone, and only <em>they</em> are affected, which makes the bug reports maddeningly hard to reproduce.</li>\n<li><strong>Scaling in gets worse.</strong> A newly launched instance receives only new clients, so it stays under-used while existing instances remain hot. Scale-in is equally awkward because every removal is a small outage for somebody.</li>\n<li><strong>Deployments become disruptive.</strong> Replacing instances means breaking affinity for everyone on them, so a routine rolling deploy logs users out.</li>\n</ul>\n<p style=\"line-height: 1.75\">The better long-term answer is to <strong>externalise session state</strong> so no server owns it:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Redis via Amazon ElastiCache.</strong> An in-memory data store outside your instances. Every server reads and writes sessions there, so any server can serve any request. Fast, and the standard choice.</li>\n<li><strong>Amazon DynamoDB.</strong> A managed key-value database with a time-to-live feature that expires old sessions automatically. Slightly higher latency than Redis, but nothing to manage.</li>\n<li><strong>A signed token.</strong> Put the user's identity in a cryptographically signed token (such as a JWT) held by the client. The server verifies the signature and needs no lookup at all — truly stateless. The trade-off is that you cannot instantly revoke a token before it expires, so keep lifetimes short and pair them with refresh tokens.</li>\n</ul>\n<p style=\"line-height: 1.75\">Legitimate uses of stickiness remain: a legacy application you cannot modify, a long-lived WebSocket where the connection itself is the affinity, or a server-side cache so expensive to rebuild that hitting the warm one matters. Use it knowingly, not by default.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Deregistration delay (connection draining)</h4>\n<p style=\"line-height: 1.75\">When you remove a target — during a deploy, a scale-in event, or an instance replacement — what should happen to the requests it is already in the middle of serving? Two consequences: the delay will expire and cut those connections anyway, so the client must be able to reconnect gracefully; and a very long delay to accommodate them makes deployments crawl. The usual compromise is a moderate delay plus client-side reconnect logic. Note also that for an NLB, deregistration delay applies to TCP connections, and the NLB additionally waits a fixed period for unfinished flows.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Idle timeout — and the 502 race every team hits</h4>\n<p style=\"line-height: 1.75\">The ALB's <strong>idle timeout</strong> is how long a connection may sit with <em>no data flowing</em> before the load balancer closes it. The default is <strong>60 seconds</strong> and the range is 1 to 4000 seconds, set with the attribute <code>idle_timeout.timeout_seconds</code>. It applies to both the client-side connection and the target-side connection.</p>\n<p style=\"line-height: 1.75\">It is <strong>not</strong> a request timeout. A request that is streaming data for ten minutes is never idle and is never cut. The timer only counts periods of silence. Raise it when you have <strong>long polling</strong> (the client opens a request and the server deliberately holds it open until something happens), a slow report or export endpoint that thinks for a while before responding, or WebSockets that go quiet between messages.</p>\n<p style=\"line-height: 1.75\">Now the genuinely valuable detail. To avoid the cost of a new TCP handshake for every request, the ALB uses <strong>keep-alive</strong> connections — it holds the connection to your target open and reuses it. For an application with caches to fill, a connection pool to establish, or a just-in-time compiler that needs to warm up, that full share arrives before the target is really ready — so its first requests are slow, or it falls over and gets marked unhealthy, and you get a flapping loop where each replacement dies the same way.</p>\n<p style=\"line-height: 1.75\"><strong>Slow start</strong> fixes this. Set <code>slow_start.duration_seconds</code> on the target group (30 to 900 seconds; <code>0</code>, the default, means disabled) and a newly healthy target receives a <strong>linearly increasing</strong> share of requests over that window instead of everything at once.
