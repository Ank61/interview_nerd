style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Target types — what you are allowed to register</h4>\n<p style=\"line-height: 1.75\">You choose a <strong>target type</strong> when you create the target group, and it cannot be changed afterwards. There are four.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>instance.</strong> Register <strong>EC2 instances by instance ID</strong> (<code>i-0abc123</code>). This is the common case and the one you will use first. The load balancer resolves the instance's private IP itself, so if the instance is replaced you register the new ID. Only instances in the target group's VPC are eligible.</li>\n<li><strong>ip.</strong> Register <strong>arbitrary IP addresses</strong>. Two good reasons to use this. First, servers that are not EC2 instances at all — a machine in your own data centre reachable over a <strong>VPN</strong> (an encrypted tunnel between your office network and your VPC) or <strong>AWS Direct Connect</strong> (a dedicated private line to AWS). Second, containers, where many tasks share a host and each gets its own IP — this is what Amazon ECS with the <code>awsvpc</code> network mode and EKS pods use. Note that the IPs must be in a private range (the VPC's own range or RFC 1918 space); you cannot register public internet IPs.</li>\n<li><strong>lambda.</strong> Register a single <strong>AWS Lambda function</strong>. Lambda is AWS's serverless compute service — you upload a function and AWS runs it on demand with no server to manage. An ALB can invoke a Lambda function directly as a target, converting the HTTP request into a JSON event and the function's JSON response back into an HTTP response. The practical payoff: a serverless endpoint can sit behind the <em>same</em> load balancer and the <em>same</em> host name as your EC2 fleet, so you can migrate one path at a time from servers to serverless with a rule change. This target type is ALB-only, and the target group holds exactly one function.</li>\n<li><strong>alb.</strong> Register an <strong>Application Load Balancer as a target of a Network Load Balancer</strong>. The reason is almost always <strong>static IP addresses</strong>: the NLB out front gives you fixed Elastic IPs that a partner's firewall can allow-list, while the ALB behind it still provides layer 7 path and host rules. The registered target is the ALB's ARN.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Protocol and port — and why they need not match the listener</h4>\n<p style=\"line-height: 1.75\">A target group has its own <strong>protocol</strong> (for an ALB: HTTP or HTTPS) and its own <strong>port</strong>. These describe how the load balancer talks to the <em>targets</em>, and they are completely independent of the listener the client talked to.</p>\n<p style=\"line-height: 1.75\">This is one of the most useful things to understand early. A very normal setup is: clients connect to the <strong>HTTPS listener on port 443</strong>, and the target group forwards to <strong>HTTP on port 8080</strong> because that is where your Node.js or Spring Boot application happens to listen. The TLS is terminated at the load balancer, the traffic inside your private network is plain HTTP on a high port, and nothing about that is wrong. Beginners often waste an afternoon making their app listen on 443 because they assumed the ports must match. They do not.</p>\n<p style=\"line-height: 1.75\">There is also a <strong>port override per target</strong>: when you register a target you may specify a different port for that specific entry, overriding the target group's default port. This is how several containers on one EC2 host, each with a randomly assigned port, can all be registered from the same host.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Registering and deregistering targets</h4>\n<p style=\"line-height: 1.75\">You can add a target with <code>aws elbv2 register-targets</code> and remove it with <code>deregister-targets</code>. Doing this by hand is fine for learning and for a fixed pair of servers you rarely touch, but it is not how production works, for a simple reason: servers get replaced, and a human will forget.</p>\n<p style=\"line-height: 1.75\">The normal practice — and the answer you should give if asked — is to attach an <strong>Auto Scaling group</strong> to the target group. An Auto Scaling group is an AWS feature that maintains a desired number of EC2 instances, launching replacements when one dies and adding or removing instances according to a scaling policy. Once it is attached to a target group, it <strong>registers each new instance automatically as it launches and deregisters it as it terminates</strong>. Two settings make this work properly:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><code>--health-check-type ELB</code> tells Auto Scaling to trust the load balancer's health verdict, so an instance the load balancer marks unhealthy gets replaced rather than lingering.</li>\n<li><code>--health-check-grace-period</code> gives a newly launched instance a number of seconds to boot and start its application before that verdict counts. Set too low, you get a loop of instances being killed while still starting up.</li>\n</ul>\n<p style=\"line-height: 1.75\">Deregistration is not instant, and that is deliberate. When a target is removed, it enters the <strong>draining</strong> state: the load balancer stops sending it <em>new</em> requests but lets in-flight requests finish, for up to the <strong>deregistration delay</strong> (default 300 seconds, configurable from 0 to 3600). This is what lets you deploy without dropping a single user's request. For <code>instance</code> and <code>ip</code> target types you must supply <code>--vpc-id</code>, and every target must be reachable within that VPC (an <code>ip</code> target can be an address in a peered network or on-premises range reachable from the VPC, but the target group itself still belongs to one VPC). This is how small teams run a whole system on a single ALB:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><code>/api/*</code> to <strong>api-tg</strong> (the API service on port 8080)</li>\n<li><code>/images/*</code> to <strong>media-tg</strong> (a media service on port 9000)</li>\n<li><code>admin.example.com</code> to <strong>admin-tg</strong> (a separate admin app on port 3000)</li>\n<li>everything else to <strong>web-tg</strong> via the default rule</li>\n</ul>\n<p style=\"line-height: 1.75\">One hourly load balancer charge, one certificate, one set of access logs, four independently scaled and independently health-checked fleets. Set <code>blue</code> to 100 and <code>green</code> to 0 and all traffic goes to blue; change it to 95 and 5 and one request in twenty reaches the new version.</p>\n<p style=\"line-height: 1.75\">That is the mechanism behind two deployment patterns you will hear constantly. A <strong>canary release</strong> sends a small percentage to the new version, watches error rates and latency, then increases the weight if all is well. A <strong>blue/green deployment</strong> runs the old (blue) and new (green) fleets side by side and flips the weights from 100/0 to 0/100 in one step, with instant rollback by flipping them back. Both are just weight changes on one forward action — no DNS change, no waiting for TTLs.
