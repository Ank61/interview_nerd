{"title":"ALB Internals, Scaling, and Capacity","tags":["alb-internals","lcu","pre-warming","capacity-planning"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">An Application Load Balancer is not a box. It is a regional, AWS-managed fleet of <strong>load balancer nodes</strong> placed in each subnet you enable, fronted by a DNS name. Almost every surprising ALB behaviour in production — 503s during a flash sale, one Availability Zone taking all the traffic, a bill that jumps without a traffic jump, a client that keeps talking to an address AWS retired — falls out of three facts: the data plane is a scaling fleet discovered through DNS, capacity is metered in Load Balancer Capacity Units across four independent dimensions, and the ALB is a full proxy that owns two separate sets of TCP connections. A senior candidate should be able to reason from those three facts to the observable symptom and back.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Node architecture and the DNS data plane</h4>\n<p style=\"line-height: 1.75\">When you create an ALB and enable subnets in, say, three AZs, AWS provisions load balancer nodes in each of those AZs. The ALB's DNS name (for example <code>my-alb-1234567890.us-east-1.elb.amazonaws.com</code>) is an A record — or an A and AAAA record for dualstack — that resolves to one or more IP addresses per enabled AZ. Those addresses belong to the nodes. As AWS scales the fleet up, new nodes appear in DNS; as it scales down or replaces unhealthy hardware, old addresses are withdrawn. The record is published with a <strong>short TTL of 60 seconds</strong>, and that TTL is a contract: clients are expected to re-resolve roughly every minute so that the set of nodes they use tracks the set of nodes that exist.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Per-AZ addressing.</strong> Each node has an address in its own AZ's subnet. A client that resolves the name and gets several addresses will typically pick one, and where it lands determines which AZ's node proxies the request. With cross-zone load balancing on (the ALB default) that node can still forward to targets in any AZ, so per-AZ client skew does not become per-AZ target skew — but it does become per-AZ <em>node</em> skew, and node capacity is per-node.</li>\n<li><strong>Subnet capacity is node capacity.</strong> Each enabled subnet needs at least a /27 and at least eight free addresses, because the fleet consumes ENIs as it scales. A nearly-full subnet is a silent scaling ceiling: AWS cannot add nodes if there are no free IPs, and you will see elevated latency or 503s without any obvious cause in your own metrics.</li>\n<li><strong>Static addressing is not a feature of ALB.</strong> ALB node addresses change; only NLB offers per-AZ static and Elastic IPs. Firewall rules and allowlists written against resolved ALB IPs will break. The correct answers are DNS-based allowlisting, an NLB in front of the ALB when a partner truly requires a fixed IP, or Global Accelerator for anycast static addresses.</li>\n<li><strong>Names, not addresses, in your own infrastructure.</strong> Route 53 alias records to the ALB (or CNAMEs) are re-resolved by Route 53 itself, which is why alias records are free and always current.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The DNS-caching failure mode worth knowing by heart</h4>\n<p style=\"line-height: 1.75\">The classic production incident: a long-lived client caches the ALB's DNS resolution forever. The textbook offender is a JVM. The JVM's <code>InetAddress</code> cache is governed by <code>networkaddress.cache.ttl</code>; in some historical configurations, notably when a security manager was installed, the default was to cache successful lookups <strong>indefinitely</strong>. Connection-pooling HTTP clients compound it: they resolve once at pool creation and keep those sockets, or keep re-dialing the same cached address for the process lifetime. Custom clients written against a resolver that ignores TTL, sidecars with aggressive caching, and containers with a local DNS cache set to hours all do the same thing.</p>\n<p style=\"line-height: 1.75\">The symptom arrives when AWS scales the ALB fleet <em>down</em> after a peak, or replaces a node. Suppose peak traffic pushed the fleet to twelve nodes and your fleet of five hundred JVMs each pinned one of those twelve addresses. Traffic falls, AWS retires eight nodes, and DNS now advertises four. Well-behaved clients move to the four survivors. Your JVMs do not: they keep hammering whichever of the twelve they cached. Two things happen. The clients that cached a retired address see connection timeouts or connection resets — because the address is simply gone — which surfaces to you as sporadic, unexplained failures on a small percentage of requests with no corresponding ALB 5XX metric, since the request never reached a load balancer. The clients that cached a surviving address concentrate all their load onto a shrinking set of nodes, producing latency and, if it is bad enough, rejected connections. The tell is asymmetry: a subset of client hosts fail or slow down while the ALB's own metrics look healthy, and restarting the client process fixes it instantly. That last detail — restart fixes it — is the fingerprint of a cached resolution.</p>\n<p style=\"line-height: 1.75\">The fixes are client-side, because the ALB is behaving correctly. Set the JVM DNS TTL explicitly (the AWS SDKs ship guidance to set <code>networkaddress.cache.ttl</code> to 60 or less, and the SDK for Java can be told to use its own TTL). Bound connection lifetime in your HTTP client so sockets are recycled and re-resolved: a max-connection-age or idle-eviction policy of a minute or two forces re-resolution. Do not set a local DNS cache TTL longer than the record's. And in the reverse direction, remember that DNS-based client behaviour is why you must never hardcode ALB IPs into anything.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Scaling of the load balancer itself, and pre-warming</h4>\n<p style=\"line-height: 1.75\">The ALB scales itself based on observed traffic, and that scaling is not instantaneous. It reacts over a period of minutes, which is fine for organic growth and diurnal curves and actively bad for <strong>step changes</strong>. The three canonical step-change events are a flash sale or ticket drop that goes from near-zero to peak in seconds, a marketing or product launch timed to a broadcast, and — most commonly, and most self-inflicted — a load test that starts at full rate. In each case demand outruns the fleet's scale-out and you see, in roughly this order: rising <code>TargetResponseTime</code> that is not explained by target-side latency, then <code>HTTPCode_ELB_5XX_Count</code> with 503s generated by the load balancer, then possibly <code>RejectedConnectionCount</code> as nodes hit their connection ceiling.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Ramp instead of stepping.</strong> The oldest and still the most broadly applicable technique. Build the ramp into your load generator and into your launch: increase load by something like 50 percent every few minutes rather than opening the gate. This is also the only technique that validates your own auto scaling, not just the ALB's.</li>\n<li><strong>Engage AWS Support for known step changes.</strong> For a genuine, scheduled step change — a televised launch, a registration window — open a case with the expected traffic shape (requests per second, new connections per second, payload sizes, ramp profile, start time and duration). Historically this was called <strong>pre-warming</strong> and it was the only option; AWS would raise the fleet ahead of your event. It remains sound practice for large events, and Support may also raise quotas you are about to bump into.</li>\n<li><strong>Capacity unit reservation.</strong> AWS later shipped a self-service replacement: <strong>Application Load Balancer capacity unit reservation</strong>, which lets you reserve a minimum number of LCUs on a specific load balancer so the capacity is there before the spike arrives, without a support case. You set a minimum capacity, AWS provisions to it within minutes and holds it until you change or remove the reservation; the load balancer still scales <em>above</em> the reservation on its own. You are billed for the reserved capacity for as long as it is held, which makes it a scheduled, event-shaped tool: reserve before the drop, release after. The API surface is <code>modify-capacity-reservation</code> and <code>describe-capacity-reservation</code> in the <code>elbv2</code> namespace. Sizing it is a modelling exercise in LCUs, which is the next section — this is precisely why the LCU model matters as a capacity model and not merely as a line item.</li>\n<li><strong>Architectural escape hatches.</strong> An NLB scales to sudden spikes far more gracefully than an ALB and needs no pre-warming, so genuinely spiky L4 workloads sometimes belong behind one. CloudFront in front absorbs cacheable spikes and terminates connections at the edge, converting a million client connections into a much smaller number of origin connections. And if your event is a fixed-time drop, a queue or waiting room in front of checkout is more robust than any amount of load balancer capacity.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The LCU model as a capacity model</h4>\n<p style=\"line-height: 1.75\">An ALB is metered in <strong>Load Balancer Capacity Units</strong>. One LCU is defined as a bundle of allowances across four dimensions, and — this is the part candidates get wrong — you are charged for the <strong>maximum</strong> across the four dimensions, not their sum. For each hour, AWS computes your consumption in each dimension, divides by that dimension's allowance, and bills the largest quotient. A service whose LCU bill is driven by new connections has a client-behaviour problem, and the fix is keep-alive and connection pooling, not more capacity. A service driven by active connections is a WebSocket service and should be modelled on concurrency, with the knowledge that the ALB's idle timeout is what releases those sockets. A service driven by processed bytes should be asking whether CloudFront or S3 pre-signed URLs should be carrying those bytes instead of a load balancer. A service driven by rule evaluations has an architecture question: that is usually a single shared ALB with dozens of path rules for dozens of teams, and the honest fix is to split the listener rules across more load balancers or move host-based fan-out to separate ALBs — both because of cost and because rules per listener is a hard quota you are approaching.</p>\n<p style=\"line-height: 1.75\">Because rule evaluations depend on <em>rules processed</em>, ordering matters. The ALB evaluates rules in priority order and stops at the first match, so putting your highest-volume path first genuinely reduces evaluations, and burying the hot path behind fifty rare rules genuinely inflates them. That is a real, measurable optimisation that almost nobody makes.</p>\n<p style=\"line-height: 1.75\">Operationally, the metric to look at is <code>ConsumedLCUs</code> in the <code>AWS/ApplicationELB</code> namespace — but <code>ConsumedLCUs</code> alone only tells you <em>how much</em>, never <em>which dimension</em>. To find the dominant dimension you pull the four raw metrics for the same window — <code>NewConnectionCount</code>, <code>ActiveConnectionCount</code>, <code>ProcessedBytes</code> and <code>RuleEvaluations</code> — normalise each by its per-LCU allowance, and compare. Whichever normalised series tracks <code>ConsumedLCUs</code> is your binding constraint, and it is the only dimension worth optimising. Metric math in a CloudWatch dashboard does this nicely: four expressions producing \"LCUs implied by this dimension\", plotted against actual consumption.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Connection handling: two independent connection pools</h4>\n<p style=\"line-height: 1.75\">The ALB is a full application-layer proxy, not a packet forwarder. It terminates the client's TCP and TLS connection, parses the HTTP request, and then sends that request over a <strong>separate connection to the target</strong>, drawn from a pool of keep-alive connections that the ALB maintains itself. Client-side and target-side connection counts are therefore decoupled, and that decoupling explains a lot.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">clients                     ALB nodes (<i class=k>per</i> AZ, autoscaling)              targets\n<i class=c>--------                    -------------------------------              -------</i>\nC1 <i class=o>=</i>HTTP<i class=o>/</i><i class=n>2</i><i class=o>=</i>  C2 <i class=o>=</i>HTTP<i class=o>/</i><i class=n>2</i><i class=o>=</i>    many client conns,        pooled keep<i class=o>-</i>alive conns,   <i class=o>/</i><i class=o>=</i> T1 (az<i class=o>-</i>a)\nC3 <i class=o>=</i>HTTP<i class=o>/</i><i class=n>1.1</i><i class=o>=</i><i class=o>&gt;</i><i class=c>--- multiplexed streams ---&gt; reused across clients ---&lt;--= T2 (az-b)</i>\nC4 <i class=o>=</i>HTTP<i class=o>/</i><i class=n>1.1</i><i class=o>=</i><i class=o>/</i>   (TLS terminated here)     (HTTP<i class=o>/</i><i class=n>1.1</i> <i class=k>by</i> <i class=k>default</i>)     <i class=o>=</i> T3 (az<i class=o>-</i>c)\n\nclient idle timeout: <i class=n>60</i>s <i class=k>default</i>        target keep<i class=o>-</i>alive reuse\nclient keepalive duration: <i class=o>~</i><i class=n>1</i>h <i class=k>default</i>  (ALB decides <i class=k>when</i> <i class=k>to</i> <i class=k>close</i>)\nHTTP<i class=o>/</i><i class=n>2</i> stream <i class=o>-</i><i class=o>&gt;</i> <i class=k>one</i> HTTP<i class=o>/</i><i class=n>1.1</i> request <i class=k>on</i> the target side</code></pre></div>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>HTTP/2 multiplexing from clients.</strong> ALB supports HTTP/2 for clients on HTTPS listeners (negotiated by ALPN, and enabled by the <code>routing.http2.enabled</code> attribute, on by default). Treat these as defaults to verify in Service Quotas for your account and region, since AWS adjusts them and many are increasable on request:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Rules per load balancer (excluding defaults): 100.</strong> The single most commonly hit ALB quota, and the reason the \"one shared ALB for the whole platform\" pattern collapses at scale. It is also an LCU driver. When you approach it, split by domain onto separate ALBs, or push routing decisions down into a service mesh or into the application.</li>\n<li><strong>Target groups per load balancer: 100, and target groups per action: 5.</strong> The second number is what caps weighted deployments: a single forward action can reference at most five target groups, which is ample for blue/green and canary but rules out using weights as a general-purpose sharding mechanism.</li>\n<li><strong>Targets per load balancer: 1,000, and targets per target group per AZ: 1,000 for instance and IP targets.</strong> Large ECS or EKS fleets with IP-mode targets reach these faster than people expect, especially when every task is its own target. Note also that a target can be registered a limited number of times per load balancer, which matters when you register the same instance on many ports.</li>\n<li><strong>Certificates per load balancer (excluding the default): 25.</strong> This is the constraint behind wildcard-versus-SAN strategy for multi-tenant SaaS. If you are terminating hundreds of customer domains, you need wildcards, SANs, multiple load balancers, or CloudFront in front.</li>\n<li><strong>Listeners per load balancer: 50; condition values and wildcards per rule: 5 each.</strong> The per-rule condition limits push you toward host-header wildcards and fewer, broader rules.</li>\n<li><strong>Subnet and IP requirements.</strong> At least two AZs for an ALB, a /27 minimum per subnet with at least eight free addresses. Not a quota, but the same class of constraint: it silently caps scale-out.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Production scenario: 503s during a traffic spike</h4>\n<p style=\"line-height: 1.75\">A retail team runs a 10:00 flash sale. At 10:00:04 the on-call dashboard shows client-reported error rates at 8 percent, and <code>HTTPCode_ELB_5XX_Count</code> spikes while <code>HTTPCode_Target_5XX_Count</code> stays near zero. Walk the diagnosis.</p>\n<p style=\"line-height: 1.75\"><strong>Step 1 — establish who generated the 503.</strong> <code>HTTPCode_ELB_5XX_Count</code> counts responses the load balancer produced itself; <code>HTTPCode_Target_5XX_Count</code> counts responses from targets. The target metric being flat proves the application is not the source — the request never got a target response. In access logs, the same distinction appears as <code>elb_status_code</code> of 503 with a <code>target_status_code</code> of <code>-</code>, and a <code>target_processing_time</code> of <code>-1</code>. Confirm that first; it eliminates half of the hypothesis space.</p>\n<p style=\"line-height: 1.75\"><strong>Step 2 — rule out the boring cause: no healthy targets.</strong> An ALB returns 503 when the matched target group has zero healthy targets. Check <code>HealthyHostCount</code> and <code>UnHealthyHostCount</code> per target group over the incident window. In a spike, the common shape is that healthy count <em>fell</em> as targets became overloaded and started failing health checks, which then concentrated traffic on the survivors and knocked them over too — a classic health-check-driven cascade. If healthy count dropped, your problem is target capacity and health check tuning (a health check that is stricter than your real SLO will amputate capacity exactly when you need it), not load balancer capacity.</p>\n<p style=\"line-height: 1.75\"><strong>Step 3 — test the load balancer capacity hypothesis.</strong> If healthy counts held steady and targets were not saturated, look at <code>RejectedConnectionCount</code>, which is non-zero when a node refuses connections because it reached its connection limit, and at <code>ConsumedLCUs</code> versus the four raw dimension metrics. Plot <code>NewConnectionCount</code> per second: a flash sale is the canonical new-connections spike, because every waiting customer's browser opens fresh connections at the same instant. If new connections per second went from 400 to 20,000 in four seconds and <code>ConsumedLCUs</code> tracks the new-connection dimension, you have out-run the ALB's scale-out. Corroborate with latency: <code>TargetResponseTime</code> flat while client-observed latency spikes means the delay is in front of the targets.</p>\n<p style=\"line-height: 1.75\"><strong>Step 4 — check the things that masquerade as capacity.</strong> Was the ALB's subnet out of free IPs (scale-out blocked)? Did the spike route through a rule whose target group was mid-deployment and briefly empty? Were there 460 or 463 codes (client disconnected, or malformed <code>X-Forwarded-For</code>) confusing the picture? Did WAF in front return 503-equivalents? Rule these out explicitly rather than assuming.</p>\n<p style=\"line-height: 1.75\"><strong>Step 5 — remediate now, then fix properly.</strong> Immediate: if targets are the constraint, scale out and relax health check thresholds; if the ALB is the constraint, there is no instant fix mid-incident beyond shedding load — put a queue, waiting room, or CloudFront cache in the path, or throttle at the edge. Properly, for the next sale: reserve ALB capacity ahead of the event using capacity unit reservation sized from the new-connections dimension of the last sale's metrics, pre-scale the target fleet on a schedule rather than reactively, fix client connection reuse so the new-connection dimension stops being the binding constraint, front static and cacheable content with CloudFront, and rehearse with a <em>ramped</em> load test that reaches the same peak — a stepped load test would merely reproduce the incident and teach you nothing new. Finally, add an alarm on the specific signature: <code>HTTPCode_ELB_5XX_Count</code> rising while <code>HTTPCode_Target_5XX_Count</code> is flat, which is a much sharper signal than a generic 5XX alarm.</p>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"An ALB is a fleet of nodes per AZ behind a 60-second-TTL DNS name, so clients must honour TTL — JVMs that cache DNS forever keep hitting retired nodes and fail in ways the ALB's own metrics never show.
