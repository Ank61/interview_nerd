{"title":"NLB Deep Dive — Flow Hashing, Client IP Preservation, and Connection Behavior","tags":["nlb","flow-hashing","client-ip-preservation","proxy-protocol"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">A Network Load Balancer is not a proxy in the way an ALB is. An ALB terminates the client TCP connection, parses HTTP, and opens a separate connection to the target, so it can make a fresh balancing decision for every single request. An NLB, for TCP and UDP listeners, behaves much more like a distributed flow router built on AWS Hyperplane: it picks a target once, at the moment the flow is first observed, records that decision in a distributed flow table, and then forwards every subsequent packet of that flow to the same target. The client's TCP handshake is completed by the target, not by the load balancer. Understanding that single sentence explains almost every surprising NLB behavior a senior engineer will be asked about: why load can be badly skewed, why security groups have to allow client CIDRs, why a connection can go silent after roughly six minutes, and why a passing health check can coexist with a completely broken application.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What the NLB actually is: Hyperplane, not a proxy</h4>\n<p style=\"line-height: 1.75\">The NLB is implemented as a set of per-Availability-Zone network interfaces (one ENI per enabled subnet) backed by AWS Hyperplane, a shared, horizontally scaled, flow-aware packet processing layer. Each NLB node has a private IP in its subnet, and the DNS name resolves to the node addresses (public Elastic IPs for internet-facing NLBs, private IPs for internal ones). A packet arriving at a node is matched against a distributed flow table. If the flow is new, the node runs the flow hash, chooses a target, and installs state. If the flow is known, the node reuses the stored target. Because the state is in Hyperplane rather than in a single instance, the NLB scales to millions of flows per second with single-digit-millisecond added latency and no pre-warming.</p>\n<p style=\"line-height: 1.75\">Two consequences follow immediately. First, there is no request concept at all for a TCP listener — the NLB never sees HTTP methods, paths, or headers, so it cannot do host or path routing, cannot inject <code>X-Forwarded-For</code>, and cannot retry a request on a different target. Second, the unit of load balancing is the flow, not the request. A TLS listener is the exception: there the NLB does terminate TLS and open a back-end connection, so it is a proxy for that listener type, but the target selection is still done once per front-end connection.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Flow hashing: how a target is chosen</h4>\n<p style=\"line-height: 1.75\">For each new flow the NLB computes a hash over the connection's identifying tuple and maps it onto the set of healthy registered targets that are eligible for that node. style=\"line-height: 1.75\">This is the single most important NLB design trade-off and a very common senior interview probe. Because the NLB balances flows, the fairness of the distribution depends entirely on how many flows exist and how similar they are. With tens of thousands of short-lived, roughly equal connections, hashing is statistically excellent. With a small number of long-lived, heavy connections — gRPC channels, HTTP/2 or HTTP/3 connections that multiplex thousands of requests, Kafka or database connections, WebSockets, persistent MQTT sessions — the hash is effectively a random assignment of a handful of balls into a handful of bins, and the variance is brutal.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">Scenario: <i class=n>6</i> gRPC clients, <i class=k>each</i> holding <i class=k>ONE</i> long<i class=o>-</i>lived HTTP<i class=o>/</i><i class=n>2</i> channel,\n          <i class=n>3</i> targets, <i class=n>10</i>k requests<i class=o>/</i>sec <i class=k>per</i> client.\n\nNLB (<i class=k>per</i><i class=o>-</i>flow)                         ALB (<i class=k>per</i><i class=o>-</i>request)\n t1: [c1][c3][c4]  <i class=o>-</i><i class=o>&gt;</i> <i class=n>30</i>k rps           t1: <i class=o>~</i><i class=n>20</i>k rps\n t2: [c2]          <i class=o>-</i><i class=o>&gt;</i> <i class=n>10</i>k rps           t2: <i class=o>~</i><i class=n>20</i>k rps\n t3: [c5][c6]      <i class=o>-</i><i class=o>&gt;</i> <i class=n>20</i>k rps           t3: <i class=o>~</i><i class=n>20</i>k rps\n     <i class=o>^</i> <i class=n>3</i>x skew; t1 saturates <i class=k>first</i>          <i class=o>^</i> even, because <i class=k>each</i>\n       <i class=k>and</i> scaling <i class=k>out</i> does <i class=k>NOT</i> move          HTTP<i class=o>/</i><i class=n>2</i> request <i class=k>is</i> routed\n       existing channels                      independently</code></pre></div>\n<p style=\"line-height: 1.75\">Worse, scaling out does not fix it: adding a target only changes where <em>new</em> flows go, because existing flows are pinned. The remedies are architectural, not configuration flags. Use an ALB when the protocol is HTTP-family and you want per-request balancing. If you must keep the NLB, force connection churn — have clients open a pool of several connections rather than one, cap connection lifetime with a maximum-age setting so channels are recycled and re-hashed, or put a client-side or sidecar load balancer (Envoy, gRPC client-side round robin over resolved target IPs, or a service mesh) in front so the balancing decision is made per request by something that understands the protocol. A useful middle ground is registering an ALB as a target of the NLB, which gives static IPs and PrivateLink compatibility while retaining per-request balancing behind them.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Client IP preservation</h4>\n<p style=\"line-height: 1.75\">By default, in most configurations, the target sees the original client's address as the packet source — the NLB does not source-NAT. The target group attribute that controls this is <code>preserve_client_ip.enabled</code>. The defaults are protocol- and target-type-dependent, which is exactly the kind of detail interviewers like:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Instance targets.</strong> Preservation is on by default for all protocols, and cannot be turned off for UDP and TCP_UDP target groups.</li>\n<li><strong>IP targets with TCP or TLS.</strong> Preservation is off by default — the target sees the NLB node's private IP — and can be switched on with the attribute. This is the setting people most often need to find.</li>\n<li><strong>IP targets with UDP or TCP_UDP.</strong> Preservation is on and cannot be disabled.</li>\n<li><strong>ALB targets.</strong> The concept does not apply; the ALB behind the NLB sees the NLB node address and records the NLB's view in <code>X-Forwarded-For</code>.</li>\n<li><strong>PrivateLink traffic.</strong> Traffic that reaches the NLB through a VPC endpoint is source-NAT'd by the endpoint infrastructure, so preservation does not deliver the consumer's real client IP; targets see an address from the provider-side NLB path.</li>\n</ul>\n<p style=\"line-height: 1.75\">Preservation changes the security model. The NLB has no implicit path to the target, so the target's <strong>security group must allow the client CIDRs on the target port</strong>, not the load balancer. For an internet-facing NLB with instance targets, that frequently means the instance security group has to allow <code>0.0.0.0/0</code> on the application port — which is why security-group support on the NLB itself (discussed below) was such a welcome addition. Health check traffic is different: it always originates from the NLB nodes' subnet addresses, so the target group must also allow the VPC CIDR or the node IPs on the health check port. Getting this wrong produces the classic symptom of healthy targets that refuse real traffic, or unhealthy targets that would serve traffic perfectly.</p>\n<p style=\"line-height: 1.75\">Preservation also breaks in one specific topology: <strong>hairpinning</strong>, where the client and the selected target are the same instance, or where a request loops back through the NLB to the host that originated it. With the source address preserved, the target receives a packet whose source is its own address and whose destination is its own address, which the network stack and the VPC data plane will not correctly return, and the connection hangs. The same class of problem appears with NAT devices and with targets registered by IP behind a NAT gateway. The fix is to disable client IP preservation for that target group (so the NLB SNATs and the loop resolves), to keep callers and callees on disjoint host sets, or to bypass the load balancer for same-host calls.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Proxy protocol v2 — metadata without preservation</h4>\n<p style=\"line-height: 1.75\">When preservation is unavailable or undesirable, enable the target group attribute <code>proxy_protocol_v2.enabled</code>. The NLB then prepends a binary PROXY protocol version 2 header to the first bytes of the TCP connection carrying the original source and destination addresses and ports, plus AWS-specific type-length-value fields — notably the VPC endpoint ID for PrivateLink traffic, which is the only reliable way a service provider can attribute a connection to a specific consumer endpoint. There is a hard requirement: the target application must understand the header and strip it, because the bytes arrive inside the application stream. NGINX, HAProxy, Envoy, and most modern servers support it behind an explicit flag; a naive application will see the binary preamble as corrupt protocol data and fail the connection. For TCP flows the default is 350 seconds of no data in either direction, now adjustable through the load balancer attribute <code>tcp.idle_timeout.seconds</code> within a documented range; UDP pseudo-flows age out far faster, after roughly two minutes of silence. The dangerous part is the failure mode: when the flow entry is evicted, the NLB does not send a TCP RST or FIN to either side. Both peers still believe the connection is ESTABLISHED. Application-level heartbeats work equally well, and connection pools should be configured with a maximum idle time shorter than the NLB's window so stale connections are discarded rather than used. Raising the NLB idle timeout helps but does not remove the class of bug; keep-alive does. Note that the NLB also behaves this way for connections idled by a slow back end, which is why long-running synchronous jobs behind an NLB should stream progress bytes rather than going silent.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Sticky flows and source-IP stickiness</h4>\n<p style=\"line-height: 1.75\">Every NLB flow is inherently sticky for its lifetime — that is what flow hashing means. Target group stickiness is a stronger, cross-connection guarantee: with <code>stickiness.enabled=true</code> and <code>stickiness.type=source_ip</code>, all connections from the same source address go to the same target, not just all packets of one connection. It is useful for stateful protocols where a client must land on the host holding its session, but it inherits the weaknesses of source-IP affinity: clients behind a large corporate NAT or a mobile carrier gateway collapse into a single hash bucket and can hot-spot one target, and a client whose address changes loses its affinity. Combined with UDP target groups it is the standard configuration for stateful game or VoIP servers. If the flow's target becomes unhealthy, the stickiness is broken and the flow is rehashed to a healthy target.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Health checks: TCP versus HTTP, and the check that lies</h4>\n<p style=\"line-height: 1.75\">NLB target groups support TCP, HTTP, and HTTPS health checks. A TCP check establishes a connection and tears it down; it proves that something is listening on the port and that the network path and security groups are correct. It proves nothing about the application. A process that has deadlocked its worker pool, lost its database connection, exhausted its heap, or is serving 500s on every route will still accept TCP connections, so the check passes while every real request fails — the NLB happily keeps sending flows to a broken target. For anything HTTP-based, always use an HTTP or HTTPS health check against a path that exercises the critical dependencies shallowly. Keep the check cheap and bounded: a deep health check that queries a shared database can turn a slow dependency into a fleet-wide outage when every target fails its check simultaneously. NLB health checks are configured with interval, timeout, and healthy/unhealthy thresholds, and the effective time to eject a bad target is interval multiplied by unhealthy threshold, which is what you quote when asked about detection latency.</p>\n<p style=\"line-height: 1.75\">There is one more behavior worth knowing: if every target in every enabled zone fails its health check, the NLB <strong>fails open</strong> and forwards to all targets rather than blackholing traffic, on the theory that a broken health check is more likely than a totally dead fleet. Additional target group attributes govern how aggressively unhealthy targets are handled — whether existing connections to a newly unhealthy target are terminated immediately or allowed to drain for a configured interval, and DNS or routing failover thresholds that take a whole zone out of the NLB's DNS answer when too few targets in it are healthy.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cross-zone load balancing, zonal DNS, and zonal isolation</h4>\n<p style=\"line-height: 1.75\">Cross-zone load balancing is <strong>off by default on the NLB</strong> (the opposite of the ALB, where it is always on and free). With it off, a node in <code>us-east-1a</code> only forwards to targets registered in <code>us-east-1a</code>. That has three effects. It keeps traffic in-zone, avoiding cross-AZ data transfer charges and shaving latency. It makes the zone a true failure boundary, so a bad deploy or a poisoned dependency in one zone cannot be spread by the load balancer. And it makes the distribution sensitive to imbalance: if one zone has two targets and another has ten, and DNS hands out node addresses roughly evenly, the two targets absorb roughly the same share of traffic as the ten. The rule of thumb is to keep target counts balanced per zone, or to enable cross-zone (now settable per target group with <code>load_balancing.cross_zone.enabled</code>) and accept the inter-AZ data processing cost.</p>\n<p style=\"line-height: 1.75\">For advanced failure containment, the NLB publishes <strong>zonal DNS names</strong> — a per-AZ hostname alongside the regional one — that resolve only to that zone's node. Clients or an internal service discovery layer can target a specific zone deliberately, which is the foundation of zonal shuffle-sharding and of evacuating a single zone during a partial impairment by simply stopping resolution of its zonal name. AWS Application Recovery Controller's zonal shift and autoshift automate exactly this for supported load balancers, pulling one zone out of the regional DNS answer. Note that when a zone has no healthy targets, the NLB removes that zone's node address from the regional DNS answer, but clients that have cached the address will keep using it until they re-resolve — one more reason to bound DNS caching in clients.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Security groups on the NLB and PrivateLink enforcement</h4>\n<p style=\"line-height: 1.75\">NLBs now support security groups, which finally lets you filter traffic at the load balancer rather than relying on every target's own rules. Two details matter. First, security groups can only be associated at creation time — an NLB created without them cannot have them added later, so you rebuild the load balancer; the rules inside an associated group can be changed freely. Second, because client IP preservation means the target sees client addresses, the NLB's security group and the target's security group are evaluated independently, and with preservation on, the target group still needs rules for client CIDRs. AWS provides a setting to relax that: you can configure the target security groups to reference the NLB's security group instead of client ranges when the load balancer's own group is doing the filtering.</p>\n<p style=\"line-height: 1.75\">The PrivateLink interaction is a favorite interview detail. Inbound traffic arriving at the NLB through a VPC endpoint service is, by default, <strong>not</strong> evaluated against the NLB's inbound security group rules — the reasoning being that PrivateLink access is already governed by the endpoint service's allow-listed principals and acceptance workflow. If you want defense in depth and want endpoint traffic subjected to the security group as well, turn on the enforcement flag (exposed on the security group API for the load balancer as an option to enforce inbound rules on PrivateLink traffic). Turn it on carelessly on a live service and every consumer breaks at once, because the source addresses of endpoint traffic will not match the rules you wrote for clients.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Deregistration and in-flight flows</h4>\n<p style=\"line-height: 1.75\">When a target is deregistered it enters <code>draining</code>. New flows stop being hashed to it immediately; existing flows continue, and the NLB waits for <code>deregistration_delay.timeout_seconds</code> (default 300) before considering the target fully removed. Two behaviors differ from the ALB. First, because the NLB has no request boundary, it cannot tell when an in-flight unit of work finishes — a long-lived connection will simply keep running for the whole drain window. Second, when the window expires, the NLB by default just forgets the flow, producing the same silent-drop symptom described earlier. The attribute <code>deregistration_delay.connection_termination.enabled</code> changes that to send TCP RSTs at the end of the window, which is usually what you want: an immediate, loud error the client can retry beats a hang. The properly graceful pattern is to have the application close its own connections during drain — stop accepting, send GOAWAY for HTTP/2, finish in-flight work, exit — so the client reconnects and is rehashed rather than being cut off by the load balancer.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Production scenario: skewed CPU and mysterious timeouts</h4>\n<p style=\"line-height: 1.75\">A team runs a gRPC service on twelve instances behind an internal NLB, cross-zone disabled. Two symptoms arrive together. First, CPU on three instances sits near 85 percent while others idle at 20 percent, and adding four more instances changes nothing. Second, a batch job that talks to the service reports sporadic deadline-exceeded errors, always on its first call after a quiet period, never under sustained load.</p>\n<p style=\"line-height: 1.75\">The diagnosis for the skew starts with counting flows, not requests. <code>NewFlowCount</code> and <code>ActiveFlowCount</code> on the load balancer, compared with request rate from the application, show a tiny number of flows carrying an enormous number of requests — the signature of long-lived HTTP/2 channels being balanced per connection. Confirming it is easy: the hot instances each hold several client channels, the cold ones hold one or none, and new capacity receives nothing because existing flows are pinned. Cross-zone being off compounds it if the callers are concentrated in one zone. The fixes are to have clients hold a pool of connections and recycle them on a maximum-age policy so rehashing happens continuously, to move to an ALB or an ALB-as-NLB-target so balancing is per request, or to adopt client-side balancing over the resolved target set. Enabling cross-zone widens the candidate pool and reduces but does not remove the variance.</p>\n<p style=\"line-height: 1.75\">The timeout symptom is the idle-timeout eviction. The batch job holds pooled connections across long gaps, the NLB drops the flow state after its idle window without notifying anyone, and the next write disappears until the client's own deadline fires. The give-away is that the failures cluster at idle durations just above the NLB idle timeout, and that packet captures on the target show the request never arriving. The fix is TCP keep-alive on both ends at well under the idle window, a pool maximum-idle-time shorter than the window, and enabling connection termination on deregistration so drain-time closures are explicit resets rather than silent holes.
