It is not a universal win — many application servers handle HTTP/1.1 keep-alive perfectly well, and switching the target group protocol version means the target must actually speak HTTP/2 or every request fails. Note that with the default HTTP/1.1 backend, the ALB <em>already</em> gives clients the benefits of HTTP/2 (single connection, header compression, multiplexing) by de-multiplexing on the way through, so the client-side win is available without touching targets.</p>\n<p style=\"line-height: 1.75\"><strong>gRPC</strong> support means the ALB understands gRPC framing rather than merely tunnelling it, so it can route by service and method path (<code>/package.Service/Method</code> in listener rules), report per-target gRPC metrics, and health check properly. Three specifics interviewers probe: the listener must be <strong>HTTPS</strong> and the target group protocol version <code>GRPC</code>, because gRPC requires HTTP/2 end to end; the health check can use <strong>protocol version GRPC</strong> with a path like <code>/grpc.health.v1.Health/Check</code>; and the success matcher is a <strong><code>GrpcCode</code></strong> rather than an HTTP status code, where the default accepted code is <strong>12</strong> (UNIMPLEMENTED) so that a service <em>without</em> a health service still passes — if you implement the standard health service you should change the matcher to <strong>0</strong> (OK), otherwise a genuinely unhealthy service that answers OK would be misclassified. Also remember that gRPC's long-lived HTTP/2 connections mean the ALB balances <em>connections</em>, not RPCs, so a few clients can pin load to a few targets; the mitigations are client-side round-robin with a resolver that sees all targets, periodic connection recycling via <code>GOAWAY</code>, or a service mesh for true per-RPC balancing.</p>\n<p style=\"line-height: 1.75\"><strong>WebSocket</strong> upgrades are transparent, but the governing timer changes: once upgraded, the connection is subject to the <strong>idle timeout</strong> (default 60&nbsp;s, configurable 1-4000&nbsp;s), which measures <em>inactivity</em>, not connection age. A chat application with sparse traffic must send application-level pings more often than the idle timeout or connections will be reaped, and the symptom — reconnects every 60 seconds — is one of the most common ALB support questions. Do not simply raise the idle timeout to hours: that pins draining behaviour and hides the fact that the client needs keep-alive pings anyway.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Connection Efficiency and Its Cost Signature</h4>\n<p style=\"line-height: 1.75\">The ALB maintains a pool of persistent connections to targets and reuses them across client requests. Whether the client side reuses connections is up to the client, and this is where money and latency are lost. A client that sends <code>Connection: close</code>, or an SDK configured without connection pooling, or a serverless caller that creates a new HTTP client per invocation, forces a full TCP handshake and TLS negotiation <strong>per request</strong>. The latency cost is two to three round trips before a single byte of application data moves. The cost signature is visible in billing: ALB pricing is driven by <strong>LCUs</strong>, and the <em>new connections</em> dimension bills at only <strong>25 new connections per second per LCU</strong> whereas <em>active connections</em> bills at <strong>3,000 active connections per minute per LCU</strong>. Those numbers differ by more than two orders of magnitude in effect — so a workload doing one request per connection can be billed 100&times; more LCUs than the same request volume over reused connections. When someone reports an inexplicable ALB bill, connection churn is the first hypothesis.</p>\n<p style=\"line-height: 1.75\">Other connection-level levers: <strong>TLS session resumption</strong> reduces handshake cost for returning clients, and is another argument for terminating at CloudFront where resumption tickets are cached close to the user; choosing a modern <strong>security policy</strong> enables TLS 1.3, which completes the handshake in one round trip instead of two; and enabling <strong>HTTP/2 to clients</strong> (the default) means a browser needs one connection rather than six. On the target leg, ensure the application's keep-alive timeout exceeds the ALB idle timeout, both to avoid the 502 race and so the pool actually stays warm.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Routing Algorithm Selection</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Round robin</strong> (<code>load_balancing.algorithm.type=round_robin</code>, the default). Distributes requests evenly by count. Correct when requests are homogeneous in cost and targets are homogeneous in capacity. Its weakness is that it is blind to what a target is currently doing: a target stuck on ten slow requests still receives its share.</li>\n<li><strong>Least outstanding requests</strong> (<code>least_outstanding_requests</code>). The ALB sends the next request to the target with the fewest in-flight requests. This is the right answer in two specific situations, and saying <em>which</em> is what distinguishes a senior candidate. First, <strong>heterogeneous request cost</strong>: an endpoint mix where some requests take 5&nbsp;ms and others 5&nbsp;s, so round robin piles new fast requests onto a target already saturated by slow ones. Second, <strong>heterogeneous target capacity</strong>: a mixed-instance-type fleet, or a fleet mid-deploy where warming targets are temporarily slower, or Graviton and x86 targets side by side. It also self-corrects for a degraded target that is still passing health checks — a target with a failing disk or a GC pause naturally accumulates outstanding requests and stops being chosen. LOR is not free: it is less useful when all requests are identical, it can concentrate traffic on a fast-but-buggy target that returns errors quickly, and long-lived connections (WebSocket, gRPC streams) count as perpetually outstanding, which distorts the metric.</li>\n<li><strong>Weighted random</strong> (<code>weighted_random</code>) distributes requests randomly with respect to target weights and is the algorithm that supports <strong>automatic target weights / anomaly mitigation</strong> (<code>load_balancing.algorithm.anomaly_mitigation</code>). When enabled, the ALB detects targets whose behaviour deviates from their peers and reduces their share of traffic without removing them, which is a gentler response than a health check failure and catches gray failures that binary health checks miss. It is the strongest choice for large fleets where one bad host in fifty is a routine occurrence, with the caveat that it is only available with weighted random and cannot be combined with everything.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Attributes, Limits, and Desync Mitigation</h4>\n<p style=\"line-height: 1.75\">Performance-relevant attributes worth knowing by name: <code>idle_timeout.timeout_seconds</code> (client-side idle), <code>routing.http2.enabled</code>, <code>routing.http.preserve_host_header.enabled</code>, <code>routing.http.drop_invalid_header_fields.enabled</code>, <code>routing.http.xff_header_processing.mode</code> (append, preserve or remove), <code>routing.http.x_amzn_tls_version_and_cipher_suite.headers.enabled</code>, <code>routing.http.compression.enabled</code>, and on target groups <code>deregistration_delay.timeout_seconds</code>, <code>slow_start.duration_seconds</code>, <code>stickiness.*</code> and <code>target_group_health.*</code> (minimum healthy target count, which prevents the ALB from concentrating traffic on a handful of survivors). On the NLB side, configurable <strong>TCP idle timeout</strong> and <code>preserve_client_ip.enabled</code> matter.</p>\n<p style=\"line-height: 1.75\"><strong>Size limits</strong> are hard boundaries that appear as mysterious 4xx: the ALB caps the request line at roughly <strong>16&nbsp;KB</strong>, a single header at roughly <strong>16&nbsp;KB</strong>, and the whole header block at roughly <strong>64&nbsp;KB</strong>. Applications that stuff a large JWT or a fat cookie jar into headers hit these and receive a 400 from the load balancer, with no target log entry — a classic debugging dead end. The answer is architectural (reference tokens, session IDs instead of embedded claims), not a quota increase.</p>\n<p style=\"line-height: 1.75\"><strong>Desync mitigation mode</strong> (<code>routing.http.desync_mitigation_mode</code>) controls how strictly the ALB enforces RFC compliance to prevent <strong>HTTP request smuggling</strong>, where ambiguity between <code>Content-Length</code> and <code>Transfer-Encoding</code> lets an attacker desynchronise a proxy and a backend and inject a request into another user's connection. The three modes are <strong>monitor</strong> (classify and log, forward everything — for discovery only), <strong>defensive</strong> (the default: forward safe requests, mitigate risky ones by closing the client and target connections, block the worst), and <strong>strictest</strong> (reject anything non-compliant with a 400). The trade-off is security against compatibility: strictest is unambiguously safer but will break legacy clients, hand-rolled HTTP libraries and devices that send slightly malformed requests. The disciplined path is to run in <strong>monitor</strong> mode first, use the <code>DesyncMitigationMode_NonCompliant_Request_Count</code> metric and access logs to find offenders, fix or exempt them, then move to strictest — never flip to strictest on a Friday afternoon for a public API.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Capacity Planning for the Load Balancing Tier</h4>\n<p style=\"line-height: 1.75\">ALB capacity and cost are expressed in <strong>Load Balancer Capacity Units</strong>, and you are billed on the <strong>highest</strong> of four dimensions, not their sum:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>New connections:</strong> 25 per second per LCU.</li>\n<li><strong>Active connections:</strong> 3,000 per minute per LCU.</li>\n<li><strong>Processed bytes:</strong> 1&nbsp;GB per hour per LCU for instance, IP and container targets (0.4&nbsp;GB per hour for Lambda targets).</li>\n<li><strong>Rule evaluations:</strong> 1,000 per second per LCU, computed as request rate multiplied by the rules processed beyond the first 10, which are free.</li>\n</ul>\n<p style=\"line-height: 1.75\">Planning is therefore an exercise in working out which dimension binds. Take 10,000 requests per second, 5&nbsp;KB average response, 20 requests per connection, and 40 listener rules. New connections: 10,000/20 = 500/s &rarr; 20 LCU. Active connections: if 30,000 are concurrently open, 30,000/3,000 = 10 LCU. Processed bytes: 10,000 &times; 5&nbsp;KB = 50&nbsp;MB/s = 180&nbsp;GB/h &rarr; 180 LCU. Rule evaluations: 10,000 &times; 30 = 300,000/s &rarr; 300 LCU. The binding dimension is <strong>rule evaluations</strong>, and the cheapest optimisation is not more capacity but <strong>fewer or better-ordered rules</strong> — putting the hottest paths at low priority numbers and collapsing rules that could be one condition. That kind of reasoning, rather than reciting the four dimensions, is what the question is really testing. Note the same calculation with 1 request per connection would have made new connections 10,000/25 = 400 LCU, which is why connection reuse dominates cost conversations.</p>\n<p style=\"line-height: 1.75\">For <strong>known step changes</strong> — a ticket sale, a broadcast, a Black Friday open — the ALB does scale automatically, but not instantly; scaling is reactive and takes minutes. Two mitigations: <strong>capacity unit reservation</strong>, where you pre-provision a minimum ALB capacity so the first burst is absorbed without waiting for scale-out; and, where reservation does not apply or for other ELB types, engaging <strong>AWS Support</strong> ahead of time to pre-warm, giving them the expected request rate, connection rate and payload sizes. Either way you must also plan the tier <em>behind</em> the load balancer, because a pre-warmed ALB pointed at an un-scaled fleet just delivers the flood faster.</p>\n<p style=\"line-height: 1.75\"><strong>Load testing methodology</strong> is where most teams get the wrong answer. A <strong>step load</strong> that jumps from zero to peak measures <em>the load balancer's scale-out rate</em>, not your application: you will see elevated latency and possibly 503s for the first minutes purely because the ALB is adding capacity, then everything settles — and if you report the step-load numbers you have measured AWS, not yourself. Always <strong>ramp</strong>: increase load in stages over 10-20 minutes with a plateau at each stage, record steady-state latency per plateau, and identify the knee of the curve. Additional discipline: generate load from enough distinct source IPs that you are not distorted by per-source behaviour, drive it through the load balancer's DNS name and re-resolve DNS periodically so you spread across all load balancer nodes rather than pinning one, enable keep-alive to match real clients (and run a separate no-keep-alive scenario to quantify the connection-churn penalty), and hold each plateau long enough for autoscaling on both the ALB and the fleet to settle. Finally, test the failure shapes you care about: one AZ removed, half the targets unhealthy, a dependency slowed.</p>\n<p style=\"line-height: 1.75\"><strong>Quotas that become design constraints</strong> at scale: load balancers per Region, target groups per Region, <strong>rules per ALB (default 100)</strong>, certificates per ALB, targets per target group and per ALB, listeners per load balancer, and security group rules referencing prefix lists. These drive architecture — the rules-per-ALB limit is exactly why EKS ingress groups and consolidated host-based routing matter, and the target-groups-per-Region limit is what bites platforms that create a target group per microservice per environment. Current p99 is 140&nbsp;ms behind an ALB. Method:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Attribute first.</strong> Access logs show <code>target_processing_time</code> p99 of 18&nbsp;ms, <code>request_processing_time</code> p99 of 95&nbsp;ms, <code>response_processing_time</code> near zero. The application is already within budget; the time is being spent before the request reaches a target. That single observation redirects the whole investigation away from the code.</li>\n<li><strong>Diagnose the 95&nbsp;ms.</strong> Correlate with <code>NewConnectionCount</code> versus <code>ActiveConnectionCount</code>: the ratio is near 1, meaning roughly one request per connection. Every request is paying a TCP handshake plus a TLS handshake. Fix the <em>clients</em>: enable connection pooling and keep-alive in the SDK, stop sending <code>Connection: close</code>, and raise the pool size to cover peak concurrency. Confirm the application keep-alive exceeds the ALB idle timeout so the pool stays warm.</li>\n<li><strong>Shorten the remaining handshakes.</strong> Move the listener to a TLS 1.3-capable security policy so new handshakes take one round trip instead of two, and consider a CloudFront or Global Accelerator front door if callers are geographically distant — for an internal API, prefer keeping caller and ALB in the same Region and AZ-local routing.</li>\n<li><strong>Tune target selection.</strong> The endpoint mix is heterogeneous (a few heavy aggregation calls among many cheap reads), so switch <code>load_balancing.algorithm.type</code> to <strong><code>least_outstanding_requests</code></strong> so cheap requests stop queueing behind heavy ones on the same target. Consider <code>weighted_random</code> with anomaly mitigation if the fleet is large and gray failures are common.</li>\n<li><strong>Remove per-request overhead.</strong> Cut the listener rule count and order the hot path first, since rule evaluations both add latency and drive LCUs. Disable stickiness if it is not needed — it constrains target selection and defeats LOR. Check whether compression is adding time for already-small JSON payloads.</li>\n<li><strong>Re-test properly.</strong> Ramp load in stages with keep-alive on, holding plateaus, measuring p99 and p99.9 per plateau; compare against a deliberately non-keep-alive run to quantify what connection reuse bought. Re-check <code>TargetResponseTime</code> per AZ to make sure one zone is not dragging the tail.</li>\n<li><strong>If the tail is still wrong,</strong> question the ALB itself: for a pure-TCP, ultra-low-latency internal path, an <strong>NLB</strong> avoids HTTP parsing and generally adds less latency than an ALB, at the cost of losing path routing, WAF and per-request features.
