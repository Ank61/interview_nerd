Once you can name all three and say what each one decides, the console stops looking intimidating and the whole service makes sense.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The three building blocks</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>The load balancer itself.</strong> This is the thing with the DNS name. It lives inside your <strong>VPC</strong> — a Virtual Private Cloud, which is your own private network inside AWS — and you place it in specific <strong>subnets</strong>. A subnet is a slice of that private network, and each subnet belongs to exactly one <strong>Availability Zone</strong>, which is a physically separate data centre in the same AWS region. You must give the load balancer at least two subnets in two different Availability Zones; AWS then runs redundant load balancer nodes in each. The load balancer also has a <strong>security group</strong> attached, which is a virtual firewall controlling what traffic may reach it.</li>\n<li><strong>Listeners.</strong> A <strong>listener</strong> is a process on the load balancer that watches one specific protocol and port for incoming connections — for example HTTP on port 80, or HTTPS on port 443. No listener means nothing is accepting connections, so a load balancer with no listener does nothing at all. An HTTPS listener is also where you attach your <strong>TLS certificate</strong>.</li>\n<li><strong>Rules.</strong> Each listener has an ordered list of <strong>rules</strong>. 1.25rem; font-weight: 600\">Walking one request end to end</h4>\n<ol style=\"margin-left: 1.5rem; list-style: decimal; line-height: 2\">\n<li>A browser wants <code>https://shop.example.com/api/orders</code>. It asks <strong>DNS</strong> for <code>shop.example.com</code>, which is an alias to the load balancer, and gets back the current IP address of one of the load balancer's nodes.</li>\n<li>The browser opens a TCP connection to port 443 on that address. The <strong>HTTPS listener</strong> accepts it and completes the TLS handshake using the certificate attached to that listener. The load balancer now has the decrypted request in front of it.</li>\n<li>The listener evaluates its rules <strong>in priority order</strong> — lowest number first — and stops at the <strong>first</strong> rule whose conditions all match. Here <code>/api/orders</code> matches the <code>path = /api/*</code> rule at priority 10, so evaluation stops there and the <code>host = admin...</code> rule at priority 20 is never considered.</li>\n<li>That rule's action is <strong>forward to api-tg</strong>. The load balancer looks at the healthy targets in that target group, picks one using the target group's routing algorithm (round robin by default), and — this is the important part — opens a <strong>brand-new connection of its own</strong> to that target, on the target's port.</li>\n<li>The target processes the request and responds to the load balancer. The load balancer sends the response back down the original encrypted connection to the browser. The browser never learns which server answered.</li>\n</ol>\n<p style=\"line-height: 1.75\">Two connections, not one. The client talks to the load balancer; the load balancer talks to the target. That single fact explains several things that otherwise look like bugs, which we come back to below.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The default rule, and rule priority</h4>\n<p style=\"line-height: 1.75\">Every listener has exactly one <strong>default rule</strong>, created with the listener and impossible to delete. It has no conditions, so it always matches, and it always sits last. It is the catch-all: any request that matched none of your other rules lands here. In the console it is shown as the rule with priority <code>default</code>; in the CLI, <code>describe-rules</code> returns it with <code>\"IsDefault\": true</code> and <code>\"Priority\": \"default\"</code>. You set its action with <code>--default-actions</code> when you create the listener, or later with <code>modify-listener</code>.</p>\n<p style=\"line-height: 1.75\">Your own rules carry a numeric <strong>priority</strong> from 1 to 50000, and they are evaluated from lowest number to highest. Priority, not creation time, decides order — a rule you add later with priority 5 will be evaluated before one you created first with priority 100. This is worth internalising, because ordering bugs are the most common ALB mistake: a broad rule like <code>path = /*</code> at priority 1 will match everything and shadow every rule behind it. Put the most specific rules at the lowest numbers and leave gaps (10, 20, 30) so you can insert rules later without renumbering.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Rule actions you will actually use</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>forward.</strong> Send the request to a target group. This is the workhorse action and the one the default rule normally uses. A forward action can name more than one target group with weights, which is how canary and blue/green releases are done.</li>\n<li><strong>redirect.</strong> Tell the client to go somewhere else with an HTTP 301 (permanent) or 302 (temporary) response, without involving any server. The overwhelmingly common use is the <strong>HTTP-to-HTTPS redirect</strong>: a listener on port 80 whose default action redirects to <code>HTTPS</code> on port <code>443</code>, keeping the host, path and query intact. Doing this on the load balancer is free, instant and means your application never has to think about it.</li>\n<li><strong>fixed-response.</strong> Answer directly with a status code and a short body — no target involved. Useful for a maintenance page on a specific path, for returning <code>404</code> or <code>403</code> on paths you want to block outright (for example <code>/.env</code> or <code>/wp-admin</code> probes on a non-WordPress site), or for a cheap health endpoint on the load balancer itself.</li>\n<li><strong>authenticate-oidc / authenticate-cognito.</strong> Make the user log in before the request reaches your app. Worth knowing exists; you will not need it on day one.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Internet-facing versus internal</h4>\n<p style=\"line-height: 1.75\">When you create a load balancer you choose a <strong>scheme</strong>, and you cannot change it afterwards.</p>\n<div style=\"overflow-x: auto; An internet-facing load balancer in public subnets forwarding to servers in private subnets is the standard secure pattern: the internet can reach the load balancer, and nothing else.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why your server logs show the load balancer's IP, and what to do about it</h4>\n<p style=\"line-height: 1.75\">Because the ALB terminates the client connection and opens a new one to the target, from the target's point of view the client <em>is</em> the load balancer. Your access logs fill up with the load balancer node's private IP, and any code doing per-IP rate limiting or geolocation sees the wrong address. Nothing is broken — this is how a layer 7 proxy works — but you need the real address, and the ALB hands it to you in HTTP headers it adds to every forwarded request:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>X-Forwarded-For.</strong> The original client's IP address. If the request already passed through other proxies (a CDN, for example), the header is a comma-separated list and the <em>rightmost</em> entry added by the ALB is the address the ALB itself saw. Never blindly trust the leftmost value on an internet-facing path, because a client can send a forged header — with an ALB in front, take the entry the ALB appended.</li>\n<li><strong>X-Forwarded-Proto.</strong> The protocol the client used, <code>http</code> or <code>https</code>. Essential when the ALB terminates TLS and speaks plain HTTP to your server: without it your framework thinks the request was insecure and may build <code>http://</code> links or refuse to set secure cookies. Most frameworks have a \"trust proxy\" setting that reads this header.</li>\n<li><strong>X-Forwarded-Port.</strong> The port the client connected to on the load balancer (for example 443), which again differs from the port your server saw.</li>\n</ul>\n<p style=\"line-height: 1.75\">Practically: turn on the \"trust proxy / forwarded headers\" option in your web framework, configure your web server's log format to record <code>X-Forwarded-For</code>, and if you need a full picture enable <strong>ALB access logs</strong>, which the load balancer writes to an S3 bucket with the client IP, target IP, processing times, status codes and the matched rule.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">HTTP/2, WebSocket and keep-alive</h4>\n<p style=\"line-height: 1.75\"><strong>HTTP/2</strong> is a newer version of HTTP that lets a browser send many requests over one connection at once. The ALB supports it on the client side by default on HTTPS listeners (it is negotiated during the TLS handshake) and translates those requests into HTTP/1.1 towards your targets, so your application needs no changes to benefit. If your backend is gRPC, you can also use HTTP/2 or gRPC all the way to the target by setting the target group's protocol version.</p>\n<p style=\"line-height: 1.75\"><strong>WebSocket</strong> connections — the long-lived two-way connections used by chat, live dashboards and multiplayer features — are supported natively. A WebSocket starts life as an ordinary HTTP request with an <code>Upgrade</code> header; the ALB recognises the upgrade and then keeps the connection open, relaying frames in both directions. The one setting to know is the <strong>idle timeout</strong>, 60 seconds by default: if no data crosses the connection for that long, the ALB closes it. For WebSocket or long-polling workloads, either raise the idle timeout or have the application send periodic keep-alive pings.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"My server logs show the load balancer's IP, so I have lost the client IP.\"</strong> You have not. The ALB adds <code>X-Forwarded-For</code> to every request; read the client IP from there and tell your framework to trust forwarded headers. If you truly need the raw source IP on the socket, that is an NLB behaviour, not an ALB one.</li>\n<li><strong>\"Rules are evaluated in the order I created them.\"</strong> They are evaluated by <strong>numeric priority</strong>, lowest first, regardless of when you created them. A later rule with a lower number wins.</li>\n<li><strong>\"An ALB passes requests through unchanged.\"</strong> It is a proxy, not a wire. It terminates the client connection, opens a new one to the target, adds the <code>X-Forwarded-*</code> headers, can downgrade HTTP/2 to HTTP/1.1, normalises some headers and enforces its own limits on header size and URL length.</li>\n<li><strong>\"One listener per target group.\"</strong> No — one listener can fan out to many target groups through its rules, and that is the point of an ALB. Conversely one target group can be used by several rules or listeners.</li>\n<li><strong>\"I can switch a load balancer from internal to internet-facing later.\"</strong> You cannot; the <strong>scheme</strong> is fixed at creation. You create a new load balancer and move DNS.</li>\n<li><strong>\"My app redirects HTTP to HTTPS, so I do not need a redirect rule.\"</strong> If the ALB terminates TLS and your app only sees plain HTTP, your app cannot tell secure requests from insecure ones without <code>X-Forwarded-Proto</code>, and naive app-level redirects turn into infinite loops. Do the redirect on the port 80 listener instead — it is one action, costs nothing and never loops.</li>\n<li><strong>\"A request with no matching rule gets rejected.\"</strong> It matches the <strong>default rule</strong>, which always exists and always matches.
