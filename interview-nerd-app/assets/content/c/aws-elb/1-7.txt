{"title":"Global and Multi-Region Architecture — Global Accelerator and Route 53 Patterns","tags":["global-accelerator","route53","multi-region","failover"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Every Elastic Load Balancer is a <strong>Regional</strong> resource. Its DNS name resolves to node addresses in one Region's Availability Zones, its target groups can only hold targets in that Region's VPCs, and it has no awareness whatsoever that another Region exists. This is the single most important framing for a senior multi-Region discussion: a load balancer is a zonal-to-Regional construct, and everything global must be built <em>above</em> it. The two tools that do that are <strong>AWS Global Accelerator</strong>, which changes where clients enter the AWS network and moves failover into the data plane, and <strong>Route 53</strong>, which changes what answer clients get when they resolve a name. They optimize genuinely different things, they are frequently combined, and the honest comparison between them is the heart of this topic.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">AWS Global Accelerator: anycast at the edge</h4>\n<p style=\"line-height: 1.75\">A standard accelerator gives you <strong>two static anycast IP addresses</strong>, one from each of two separate network zones for redundancy (you can also bring your own address range). Those addresses are advertised by BGP from a large number of AWS edge locations worldwide. A client packet destined for one of them is routed by the internet to the <em>topologically nearest</em> edge location that advertises it — usually within a few network hops of the client — and from that point the traffic travels over the <strong>AWS global backbone</strong> to the Region hosting your endpoint, rather than traversing an unpredictable chain of transit providers and peering points.</p>\n<p style=\"line-height: 1.75\">That is the core value proposition, and it is a network-path optimization, not a caching or DNS optimization. Public internet paths are chosen by BGP policy and money, not latency; they suffer from congested peering points, asymmetric routes, and packet loss that causes TCP to back off. The AWS backbone is congestion-managed and well provisioned, so entering it early typically reduces both <strong>median latency</strong> and, more importantly, <strong>jitter and tail latency</strong>, and it improves throughput because TCP congestion control performs better on a low-loss path. The effect is largest for clients that are far from the serving Region and on poor networks, and smallest for clients already sitting next to the Region on a good transit path.</p>\n<div weights</h4>\n<p style=\"line-height: 1.75\">The object model has three levels and interview questions almost always probe the middle one.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Accelerator.</strong> Owns the two static IPs and the overall enabled state. It also gets a DNS name, and a dual-stack accelerator additionally gets IPv6 addresses.</li>\n<li><strong>Listener.</strong> A protocol (TCP or UDP) and a port range, plus the <strong>client affinity</strong> setting. A single accelerator can have several listeners for different ports.</li>\n<li><strong>Endpoint group.</strong> One per Region. It holds the endpoints in that Region and carries the <strong>traffic dial</strong>, a value from 0 to 100 that caps the percentage of traffic that would otherwise go to this Region. It also owns the health check configuration used for non-load-balancer endpoints and optional port overrides.</li>\n<li><strong>Endpoint.</strong> An ALB, NLB, EC2 instance, or Elastic IP within that group, each with a <strong>weight</strong> from 0 to 255 controlling its share of that group's traffic.</li>\n</ul>\n<p style=\"line-height: 1.75\">Routing works in two stages. First, Global Accelerator sends a client's traffic to the endpoint group in the Region that is <strong>nearest to the client's edge location</strong> — this is proximity-based by default, not latency-measured, and it is not configurable per client. Then, within that group, traffic is distributed across endpoints by weight. The traffic dial modifies stage one: setting the dial on a Region to 40 means only 40 percent of the traffic that proximity would have sent there actually goes there, and the rest spills to the next-nearest healthy group. For <strong>ALB and NLB endpoints, Global Accelerator uses the load balancer's own health state</strong> rather than probing independently — the ELB already knows whether it has healthy targets, so the signal is inherited and the health check settings on the endpoint group are ignored for those endpoint types. For EC2 instance and Elastic IP endpoints, Global Accelerator performs its own TCP or HTTP health checks with a configurable port, path, interval and threshold.</p>\n<p style=\"line-height: 1.75\">When a Region's endpoints become unhealthy, the accelerator stops sending new connections there and shifts them to the next-nearest healthy endpoint group. Because the anycast addresses never change, this happens <strong>entirely in the data plane, in seconds, with no DNS involvement</strong>. Clients keep using the same IP addresses; they simply find their packets arriving at a different Region. That is the precise gap Global Accelerator closes and the single best reason to choose it over DNS failover. Note that existing TCP connections to the failed Region are not magically moved — they break and must be re-established — so clients still need retry logic; what you gain is that the retry succeeds immediately instead of waiting for a cache to expire.</p>\n<p style=\"line-height: 1.75\"><strong>Client affinity</strong> controls whether a given client always reaches the same endpoint. The default is <code>NONE</code>, which uses the full 5-tuple, so each new connection is hashed independently and distribution is best. Setting it to <code>SOURCE_IP</code> uses a 2-tuple (source and destination address) so all connections from one client address reach the same endpoint, which stateful applications sometimes require — with the usual source-IP affinity caveats about large NATs collapsing into one bucket. There is also <strong>client IP preservation</strong> for endpoints, which is supported for ALB and EC2 endpoints (the original client address is presented to the endpoint, and appears in ALB access logs and <code>X-Forwarded-For</code>) but not for NLB endpoints — with an NLB endpoint the target sees an accelerator-side address, so security groups and logging must account for it. When preservation is on for an ALB endpoint, the ALB's security group must permit the Global Accelerator managed prefix list rather than arbitrary client ranges.</p>\n<p style=\"line-height: 1.75\">Global Accelerator also absorbs a class of attack: because traffic enters at the edge, AWS Shield protection applies at the edge, and the accelerator's static IPs give you a stable, allow-listable entry point — a genuine benefit for enterprise customers whose partners maintain IP allow lists and who cannot accept a load balancer's changing addresses. A second flavor, the <strong>custom routing accelerator</strong>, maps deterministic port ranges to specific instances and private ports, which is the standard pattern for real-time multiplayer game session placement where a matchmaker must direct a player to one exact process.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cost, and when Global Accelerator is not worth it</h4>\n<p style=\"line-height: 1.75\">Global Accelerator charges a <strong>fixed hourly fee per accelerator</strong> regardless of traffic, plus a <strong>per-gigabyte data transfer premium</strong> that varies by the edge Region the traffic entered and the direction — and the premium for traffic entering in some Regions is substantially higher than in others. Two consequences. First, for a low-traffic service the fixed hourly fee dominates and can be hard to justify if all you wanted was a nicer DNS story. Second, for a very high-traffic service the per-gigabyte premium is the number to model carefully, especially for egress-heavy workloads.</p>\n<p style=\"line-height: 1.75\">Cases where it is genuinely not worth it: clients are concentrated in the same Region as the service, so there is little path to optimize; the workload is cacheable HTTP, in which case <strong>CloudFront</strong> gives you both the edge entry and the cache and is the better answer; the service is internal and not internet-facing; or the failover requirement is loose enough that Route 53 health checks meet it at near-zero cost. Cases where it clearly is worth it: a globally distributed client base hitting a small number of Regions, non-HTTP protocols such as gaming UDP, VoIP, MQTT or bespoke TCP where CloudFront does not apply, a hard requirement for static IPs, or a failover objective measured in seconds rather than minutes.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Route 53 patterns as the alternative and the complement</h4>\n<p style=\"line-height: 1.75\">Route 53 solves the global problem at the naming layer. A useful way to say it in an interview: CloudFront answers the request at the edge, Global Accelerator shortens the trip to the Region, and Route 53 decides which of them a client is pointed at.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Multi-Region topologies, and the parts that are never the load balancer</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Active-active.</strong> Both Regions serve production traffic continuously. Failover is capacity loss rather than a switch, which is the most reliable posture because the standby path is exercised every second. The cost is the hardest data problem: either you accept eventual consistency with a globally replicated store such as DynamoDB global tables or Aurora Global Database with a designated writer, or you <strong>partition by key</strong> so each Region owns a subset of users or tenants and is authoritative for them — the pattern that actually scales.
