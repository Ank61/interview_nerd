The Application Load Balancer does something more interesting: it <em>reads</em> each HTTP request and decides where to send it based on what is inside. One important caveat on source-ip: it matches the <strong>actual source address of the connection</strong> and deliberately ignores the <code>X-Forwarded-For</code> header. If your users arrive through CloudFront or another proxy, the source IP the rule sees is the proxy's, not the user's — so do not rely on source-ip conditions behind another proxy layer.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Combining conditions, and how priority resolves overlaps</h4>\n<p style=\"line-height: 1.75\">Putting several conditions in one rule creates an <strong>AND</strong>: the request must satisfy every one of them. So a rule with host-header <code>api.example.com</code> plus path-pattern <code>/v2/*</code> plus method <code>POST</code> fires only for POST requests to the v2 paths on the API host. Within a single condition you may list several values, and those are an <strong>OR</strong> — a path-pattern condition listing <code>/img/*</code> and <code>/images/*</code> matches either.</p>\n<p style=\"line-height: 1.75\">Now the classic mistake, which will bite you in real life and is asked about constantly in interviews. Because nothing warns you when a rule is shadowed, leave gaps between priority numbers — 10, 20, 30 rather than 1, 2, 3 — so you can insert a more specific rule ahead of a broad one later without renumbering everything.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Wildcards, and case sensitivity</h4>\n<p style=\"line-height: 1.75\">Path and host patterns support two wildcards: <code>*</code> matches zero or more characters, and <code>?</code> matches exactly one character. Some details that catch people out:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Path patterns are case-sensitive.</strong> A pattern of <code>/API/*</code> will not match a request for <code>/api/users</code>. This produces mysterious 404s that people chase in their application code for hours. If clients might use either casing, list both values in the condition.</li>\n<li><strong>Host headers are case-insensitive</strong>, which matches how DNS works. Host patterns also allow a wildcard for one label, so <code>*.example.com</code> matches <code>api.example.com</code> but not the bare <code>example.com</code> and not <code>a.b.example.com</code> — the same rule as wildcard certificates.</li>\n<li><strong>The pattern must match the whole path, not a prefix.</strong> A pattern of <code>/api</code> matches only the exact path <code>/api</code>. To catch everything underneath you need <code>/api/*</code>, and to catch both you list both values.</li>\n<li><strong>The path pattern excludes the query string.</strong> For <code>/search?q=shoes</code> the path is <code>/search</code>; use a query-string condition for the rest.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The three actions a beginner uses</h4>\n<p style=\"line-height: 1.75\"><strong>1. The interesting version is forwarding to <strong>several target groups with weights</strong>, where the load balancer splits traffic by ratio. Redirect.</strong> The load balancer answers the client itself with a 301 (permanent) or 302 (temporary) and a new location, without ever touching a target group. You can rewrite the <strong>protocol, host, port, path and query string</strong> independently, and placeholders such as the host, path and query of the original request let you carry parts through unchanged. The canonical example is the <strong>HTTP to HTTPS redirect</strong> on the port 80 listener. It is equally useful for consolidating a domain (send <code>www.example.com</code> to <code>example.com</code> so you have one canonical URL for search engines) or retiring an old URL structure after a site rebuild.</p>\n<p style=\"line-height: 1.75\"><strong>3. Fixed response.</strong> The load balancer returns a hard-coded status code, content type and short body — again without contacting any target. Two very practical uses: a <strong>maintenance page</strong> during a deployment, where you point the default rule at a fixed 503 with a friendly message so visitors see something sensible instead of a raw error; and <strong>blocking a path</strong>, such as returning 403 for <code>/admin/*</code> unless the source IP is your office range. Note that a fixed response body is limited to about 1 KB of text, so it is a short message, not a designed HTML page — for something richer, redirect to a static page on S3 or CloudFront.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Authentication actions, at orientation level</h4>\n<p style=\"line-height: 1.75\">You should know these exist even before you use them, because they change how you think about building login. The ALB offers two more actions:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>authenticate-cognito.</strong> Requires the user to sign in through an <strong>Amazon Cognito</strong> user pool (Cognito is AWS's managed user-directory and sign-in service) before the request is allowed through to your application.</li>\n<li><strong>authenticate-oidc.</strong> The same idea against any identity provider that speaks <strong>OIDC (OpenID Connect)</strong> — a standard sign-in protocol built on OAuth 2.0 — so Google, Okta, Microsoft Entra ID, Auth0 and similar.</li>\n</ul>\n<p style=\"line-height: 1.75\">The significance is that <strong>the load balancer enforces login before traffic reaches your app at all</strong>. An unauthenticated visitor is redirected to the identity provider and never touches your code. After a successful sign-in, the ALB passes the user's identity to your application in request headers, so your app can read who the user is without implementing OAuth flows, session cookies, or token validation itself. These actions must be used on an <strong>HTTPS listener</strong> (the session cookie has to be protected), and they are typically applied to a specific rule — protecting <code>/admin/*</code> or an internal dashboard — rather than to the whole site.
