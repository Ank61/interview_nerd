{"title":"CloudFront in Front of a Load Balancer — Edge Architecture","tags":["cloudfront","edge","caching","security"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">For any public-facing web workload, the modern default front door is not the Application Load Balancer — it is CloudFront <em>in front of</em> the ALB. The ALB remains the regional entry point that does host and path routing, target selection and health checking; CloudFront becomes the global layer that terminates TLS close to the user, serves what it can from cache, and forwards only the irreducible remainder to your Region over AWS-managed network paths. Understanding this as a <strong>layered front door</strong> rather than as two interchangeable products is what separates a senior answer from a beginner one: each layer has its own TLS session, its own timeouts, its own logs, its own error codes, and its own WAF attachment point, and almost every production incident in this architecture comes from a mismatch between the two.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What CloudFront Adds Above an ALB</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Caching at the edge.</strong> Static assets are the obvious win, but cacheable dynamic content matters more: product pages, search result pages, API responses with a few seconds of TTL, personalised-but-bucketed fragments. A 10-second TTL on a hot endpoint can remove 90% of origin load during a traffic spike.</li>\n<li><strong>TLS termination near the user.</strong> The TCP and TLS handshake costs one to three round trips. Terminating at an edge location 10&nbsp;ms away instead of an ALB 150&nbsp;ms away removes hundreds of milliseconds from first-byte time on new connections, even for content that is a full cache miss.</li>\n<li><strong>Connection reuse to the origin.</strong> CloudFront keeps warm, already-negotiated connections to the ALB and multiplexes many viewer requests over them across the AWS backbone, so a cache miss pays neither a fresh TLS handshake nor cold TCP congestion windows to your Region.</li>\n<li><strong>HTTP/3 (QUIC) to viewers.</strong> The ALB speaks HTTP/1.1 and HTTP/2; HTTP/3 is available only at CloudFront. Enabling it at the edge gives lossy mobile networks faster recovery and zero-round-trip resumption while the origin leg stays HTTP/1.1 or HTTP/2.</li>\n<li><strong>Absorbing load before your Region.</strong> AWS Shield Standard, request and header validation, and the edge cache all act before traffic consumes an LCU on your ALB or a thread on your application. Layer 3 and 4 floods are absorbed at the edge network; you never see them.</li>\n<li><strong>Request manipulation without an application deploy.</strong> CloudFront Functions and Lambda@Edge handle redirects, header rewriting, A/B bucketing, auth token checks and normalisation at the edge, keeping that logic out of the ALB rule set and out of your service.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Origin Configuration in Depth</h4>\n<p style=\"line-height: 1.75\">An ALB is a <strong>custom origin</strong> to CloudFront: you give CloudFront the ALB DNS name (or, better, a stable Route&nbsp;53 alias you control such as <code>origin.example.com</code>) and CloudFront connects to it like any HTTP server. Without it, each of the many edge locations (and each regional edge cache) can independently miss and hit your origin for the same object, so a globally distributed audience multiplies origin fetches for the same URL. With Origin Shield placed in or near your origin Region, all misses converge on one cache that collapses concurrent requests for the same object, which both raises effective hit ratio and dramatically reduces origin request rate for long-tail content. It costs per request, so it pays for itself on large libraries of moderately popular objects and on origins that are expensive to hit, not on tiny, uniformly hot catalogues.</p>\n<p style=\"line-height: 1.75\"><strong>Origin failover groups</strong> pair a primary and a secondary origin with failover criteria (connection errors plus a chosen set of status codes such as 500, 502, 503, 504). CloudFront retries the secondary on the same viewer request, which makes it a genuine availability improvement rather than just a DNS trick. Two caveats a senior candidate should volunteer: failover applies only to GET, HEAD and OPTIONS requests, so write traffic is not protected; and the retry consumes the viewer's patience, so the failover budget must fit inside the client timeout. A typical design pairs an ALB in the primary Region with an ALB in a standby Region, or an ALB with a static S3 maintenance page.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Locking the ALB So Only CloudFront Can Reach It</h4>\n<p style=\"line-height: 1.75\">This is the single most common real misconfiguration in this architecture. If the ALB keeps <code>0.0.0.0/0</code> on port 443 and its DNS name or IP is discoverable — and it is, via certificate transparency logs, DNS history, subdomain enumeration or an old CNAME — then an attacker simply sends traffic to the ALB directly and <strong>bypasses the edge entirely</strong>: no WAF, no Shield-backed rate limiting, no bot rules, no caching, and your origin absorbs the full flood. Everything you bought at the edge evaporates. Defence is two independent layers:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Network layer: the CloudFront managed prefix list.</strong> AWS publishes a managed prefix list, <code>com.amazonaws.global.cloudfront.origin-facing</code>, containing the CloudFront origin-facing address ranges. Reference that prefix list ID as the source in the ALB security group instead of a CIDR, and AWS keeps it current as edge ranges change. Note the prefix list counts against the security group rule limit by its weight, so raise the referenced-entry quota if needed.</li>\n<li><strong>Application layer: a shared secret header.</strong> The prefix list only proves the request came from <em>some</em> CloudFront distribution — including one an attacker creates pointing at your origin. So CloudFront must also add a custom origin header (for example <code>X-Origin-Verify: &lt;random-value&gt;</code>) that the origin checks. Enforce it either with an ALB listener rule whose default action returns 403 unless the header matches, or with a WAF rule on the ALB. Store the value in Secrets Manager and rotate it by adding the new value as accepted, updating the distribution, then dropping the old one.</li>\n</ul>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">Viewer ──TLS──<i class=o>&gt;</i> CloudFront edge ──TLS──<i class=o>&gt;</i> [Origin Shield] ──TLS──<i class=o>&gt;</i> ALB ──<i class=o>&gt;</i> targets\n                 │  WAF (CLOUDFRONT <i class=k>scope</i>)                          │  SG source <i class=o>=</i> CloudFront\n                 │  CF Functions <i class=o>/</i> Lambda<i class=v>@Edge</i>                      │    managed prefix list\n                 │  adds X<i class=o>-</i>Origin<i class=o>-</i>Verify: secret                    │  listener rule <i class=o>/</i> WAF\n                 │                                                  │    verifies secret header\nAttacker ────────┴─ direct <i class=k>to</i> alb<i class=n>-1234.</i>elb.amazonaws.com ──────────<i class=o>&gt;</i> blocked <i class=k>at</i> SG, <i class=k>then</i> <i class=n>403</i></code></pre></div>\n<p style=\"line-height: 1.75\">Two stronger variants exist. You can make the ALB <strong>internal</strong> and reach it from CloudFront through VPC origins, which removes public reachability altogether — the cleanest answer when it fits your account and routing design. Or you can accept the public ALB but put the secret-header check in WAF so that rejected requests never reach a listener rule evaluation. Either way, verify the control by curling the ALB directly from outside and confirming you get a connection timeout or a 403, and make that curl a continuous compliance check rather than a one-off.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cache Behaviour Design: the Cache Key Is the Whole Game</h4>\n<p style=\"line-height: 1.75\">CloudFront separates two concepts that beginners conflate. A <strong>cache policy</strong> defines the cache key — which headers, cookies and query strings distinguish one cached object from another — plus the TTL bounds and compression settings. An <strong>origin request policy</strong> defines what CloudFront <em>forwards</em> to the origin, which can be strictly more than the cache key. That split is the key insight: you can send the origin everything it needs (Host handling, <code>Authorization</code>, a locale cookie, the viewer's country) while keeping the cache key tiny.</p>\n<p style=\"line-height: 1.75\">Every value you add to the cache key <strong>multiplies</strong> the number of distinct cached objects for the same URL. Adding <code>Accept-Language</code> alone can produce dozens of variants because browsers send long, idiosyncratic values; adding an unnormalised <code>User-Agent</code> effectively disables caching, since nearly every request becomes unique. Adding a session cookie guarantees a 0% hit rate. The disciplined pattern is: forward what the origin needs via the origin request policy, include in the cache key only values that genuinely change the response body, and normalise them first — use <code>CloudFront-Viewer-Country</code> rather than raw geo headers, and use a CloudFront Function to collapse a messy header into a small enum (say, <code>x-device: mobile|desktop</code>) before it reaches the cache key.</p>\n<p style=\"line-height: 1.75\">On TTLs, the origin's <code>Cache-Control</code> should be the source of truth. CloudFront honours origin directives between the behaviour's minimum and maximum TTL, and falls back to the default TTL only when the origin sends no caching headers. A common failure is setting a large default TTL as a performance hack, then being surprised when an endpoint the origin marked <code>no-store</code> still caches — because someone also set a minimum TTL above zero. Prefer <code>Cache-Control: public, max-age=60, stale-while-revalidate=300</code> from the application, plus <code>s-maxage</code> when you want the shared cache to hold content longer than browsers do. Also mind the <code>Vary</code> header: CloudFront respects only a limited set of <code>Vary</code> values, so never rely on <code>Vary</code> to protect correctness — encode the variation in the cache key instead.</p>\n<p style=\"line-height: 1.75\">For <strong>invalidation versus versioned URLs</strong>: invalidation is an eventually-consistent, rate-limited, chargeable control plane operation that takes tens of seconds to minutes to propagate and is billed beyond a free monthly allowance of paths. It is the right tool for an emergency correction or for HTML. It is the wrong tool for routine deploys. For assets, emit <strong>content-hashed filenames</strong> (<code>app.9f2c1e.js</code>) with a one-year immutable TTL: the new deploy references new URLs, so there is nothing to invalidate, rollback is instant because old URLs still resolve, and you never race a partially propagated invalidation. When you must invalidate broadly, invalidate <code>/*</code> once rather than thousands of individual paths — it counts as a single path against the allowance.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">WAF Placement, Edge Compute and Client IP</h4>\n<p style=\"line-height: 1.75\"><strong>WAF belongs at the edge</strong> in this architecture, for four reasons: malicious requests are dropped before they consume origin bandwidth or LCUs; rate-based rules count per edge-aware client rather than per ALB, which reacts faster to distributed abuse; Web ACLs with CloudFront scope are created in <code>us-east-1</code> and cover every distribution behaviour globally; and Shield Advanced's automatic application-layer mitigation hooks into the CloudFront-scoped Web ACL. Keep a thin Web ACL on the ALB too, but give it a different job: enforce the secret header, and act as defence in depth for traffic that somehow arrives directly. Do not duplicate a full managed rule set on both layers — you pay twice and double your false-positive surface.</p>\n<p style=\"line-height: 1.75\"><strong>CloudFront Functions</strong> run on viewer request and viewer response only, in a lightweight JavaScript runtime with sub-millisecond execution, no network access and no request body access. Use them for URL rewrites, header normalisation, cache-key shaping, simple redirects and cheap token checks — they run at every edge location and are effectively free at scale. <strong>Lambda@Edge</strong> runs at viewer request/response and origin request/response, in regional edge caches, with full network access, larger memory and the ability to inspect the request body. Use it for origin selection logic, signed-cookie generation, calls to an auth service, or response assembly — accepting higher latency, real cost and a replication model that makes deploys slower. The decision rule: if it can be done with string manipulation on headers and the URL, it is a CloudFront Function.</p>\n<p style=\"line-height: 1.75\"><strong>Client IP through two layers</strong> trips up almost every team. CloudFront sets <code>X-Forwarded-For</code> to the viewer's IP; the ALB then <em>appends</em> the CloudFront edge address, so your application receives <code>X-Forwarded-For: 203.0.113.9, 130.176.x.x</code>. The real client is therefore the <em>left-most</em> entry after CloudFront, not the right-most, which is the opposite of the rule for a bare ALB. Because an attacker can inject arbitrary XFF values at the viewer, trusting the left-most entry blindly is a spoofing vector — the robust approach is to take the value CloudFront provides authoritatively: attach an origin request policy that forwards <code>CloudFront-Viewer-Address</code> and read the client IP from that header, treating XFF as advisory. Never use raw XFF for rate limiting or authorisation decisions; use WAF at the edge, which sees the true connection source.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Monitoring: Know Which Layer Returned the Error</h4>\n<p style=\"line-height: 1.75\">The diagnostic habit that makes engineers fast in this architecture is answering one question first: <em>did CloudFront generate this error, or did it relay one from the ALB, or did the ALB generate it, or did the target?</em> Four independent telemetry sources answer it.</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Source</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Field to read</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Tells you</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">CloudFront metrics</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">4xxErrorRate, 5xxErrorRate, OriginLatency, CacheHitRate (additional metrics)</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Edge-wide error rate and whether latency is origin-side. Also add a synthetic canary that hits the CloudFront domain and a second that hits the origin hostname with the secret header — when both are green and users complain, the problem is between the viewer and the edge; when only the origin canary is green, the problem is at the edge or in the cache configuration.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Production Scenario: Adding CloudFront in Front of a Live ALB Without Breaking It</h4>\n<p style=\"line-height: 1.75\">You own <code>www.example.com</code>, an A-alias to a public ALB, serving a mix of static assets and dynamic pages with session cookies. Requirement: introduce CloudFront with zero customer impact and no big-bang cutover.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Step 1 — give the origin its own name.</strong> Create <code>origin.example.com</code> as an alias to the ALB and issue or extend the ALB certificate to cover it. CloudFront will use this name, which decouples the distribution from the ALB's generated DNS name and lets you swap the ALB later.</li>\n<li><strong>Step 2 — build the distribution in shadow.</strong> Alternate domain name <code>www.example.com</code>, an ACM certificate in <code>us-east-1</code>, origin protocol https-only, minimum TLS 1.2. Start with a single default behaviour using the managed <strong>CachingDisabled</strong> cache policy and the managed <strong>AllViewerExceptHostHeader</strong> origin request policy, with all methods allowed. That combination makes CloudFront a transparent proxy: everything is forwarded, nothing is cached, session cookies and <code>Authorization</code> reach the origin unchanged. Behaviour equals today's behaviour.</li>\n<li><strong>Step 3 — validate on a test hostname.</strong> Point <code>cf-test.example.com</code> at the distribution and run your integration suite plus a login, checkout and file-upload path against it. Watch for the classic breakages: absolute redirects that leak the origin hostname (fix by having the app honour <code>X-Forwarded-Host</code> or by preserving the Host header), code that reads the right-most XFF entry (switch it to <code>CloudFront-Viewer-Address</code>), and anything relying on the raw client IP for rate limiting (move it to WAF).</li>\n<li><strong>Step 4 — shift traffic gradually.</strong> Use a Route&nbsp;53 weighted record set: 1% to the distribution, then 10%, 50%, 100%, watching CloudFront 5xxErrorRate, ALB HTTPCode_Target_5XX_Count and your application's own error rate at each step. Rollback is a weight change, which propagates in seconds because you kept the TTL low before starting.</li>\n<li><strong>Step 5 — only now add caching.</strong> Carve out a <code>/static/*</code> behaviour with CachingOptimized and long TTLs on hash-named assets, then add narrow behaviours for specific cacheable API paths with short TTLs and a minimal cache key. Measure hit ratio per behaviour; never turn on a broad cache policy across the default behaviour.</li>\n<li><strong>Step 6 — lock the origin last.</strong> Once all traffic is on the edge, attach the secret header in the distribution, add the listener rule (initially a 403 only for requests missing the header, monitored in WAF count mode first), then tighten the ALB security group to the CloudFront managed prefix list. Doing this before the traffic shift would have blocked live direct traffic; doing it last makes it safe.</li>\n</ul>\n<p style=\"line-height: 1.75\">The reason this sequence works is that each step is independently reversible and only one variable changes at a time — proxy first, caching second, lockdown third.
