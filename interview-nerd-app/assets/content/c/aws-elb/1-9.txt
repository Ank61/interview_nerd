{"title":"Load Balancing for Containers — ECS, EKS, and the AWS Load Balancer Controller","tags":["ecs","eks","kubernetes","containers"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Load balancing to EC2 instances is a slow-moving problem: targets change when you scale or deploy, a few times a day. Load balancing to containers is a fast-moving one: targets appear and disappear continuously, a single host may run several replicas of the same service on different ports, and a rolling deploy can churn every target in the group within a minute. The load balancer itself did not change — what changed is that <strong>something must continuously reconcile the desired set of targets with the target group</strong>, and that reconciliation loop is where correctness lives. On ECS that reconciler is the ECS service scheduler; on EKS it is the <strong>AWS Load Balancer Controller</strong>. Nearly every \"we drop requests during deploys\" incident in containerised environments is a timing bug between that reconciler, the target group's health checking and draining, and the container's own shutdown behaviour.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">ECS: the Service Scheduler as Target Registrar</h4>\n<p style=\"line-height: 1.75\">An ECS service is declared with a <code>loadBalancers</code> block naming a target group, a container name and a container port. From then on the ECS scheduler owns registration: when it starts a task it registers the task's address with the target group and waits for it to pass health checks before counting it toward the deployment; when it stops a task it deregisters first and waits out the draining period. You never call <code>register-targets</code> yourself, and manually editing the target group fights the scheduler. The service also needs an IAM <strong>service-linked role</strong> (or a legacy ECS service role) that grants the ELB registration calls.</p>\n<p style=\"line-height: 1.75\">The <strong>network mode</strong> determines what kind of target gets registered, and this is the most consequential choice:</p>\n<div style=\"overflow-x: auto; This is how several replicas of the same service share one EC2 host without port conflicts, and it is why the ALB security group rule must open the ephemeral range to the instances rather than a single port. Health checks likewise hit the mapped port, so a health check port of <code>traffic-port</code> is essentially mandatory. The costs are a NAT hop, per-instance security-group granularity (all containers on the host share it), and less useful flow logs. <strong>awsvpc with IP targets</strong> is the modern default: first-class per-task security groups, a direct path from the ALB to the task ENI, clean VPC flow logs, and compatibility with Fargate — at the price of consuming a subnet IP and an ENI slot per task, which you must plan subnet sizing around.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">ECS Timing Controls That Prevent Dropped Requests</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Health check grace period</strong> (<code>healthCheckGracePeriodSeconds</code>, up to 2,147,483,647 but practically 60-600). For a service behind a load balancer, ECS ignores ELB health check failures for this long after a task starts. Without it, a JVM or Rails app that needs 90 seconds to boot is killed by the scheduler before it ever becomes healthy, producing an infinite crash-restart loop that looks like an application bug. Set it to the p99 boot time plus margin, and pair it with the target group's own healthy threshold.</li>\n<li><strong>Deployment circuit breaker</strong> (<code>deploymentConfiguration.deploymentCircuitBreaker</code> with <code>enable</code> and <code>rollback</code>). ECS watches how many consecutive task launches fail to reach a steady state and, past a threshold, fails the deployment and optionally rolls back to the last successful task definition. Without it a bad image can sit retrying for hours while the old tasks are already gone. Combined with <code>minimumHealthyPercent</code> it is the cheapest safety net in ECS.</li>\n<li><strong>minimumHealthyPercent / maximumPercent</strong> control the rolling replacement shape. 100/200 means \"start all the new tasks before stopping any old ones\" — safest, needs double capacity. 50/100 means \"stop half first\" — cheap, halves capacity mid-deploy. For a latency-sensitive service, 100/150 or 100/200 is the right answer.</li>\n<li><strong>Deregistration delay interaction.</strong> When ECS replaces a task it deregisters the target and the ALB marks it <em>draining</em>; ECS waits for draining to complete before sending <code>SIGTERM</code>, subject to <code>stopTimeout</code> (default 30&nbsp;s on EC2, and the ECS agent's <code>ECS_CONTAINER_STOP_TIMEOUT</code>) before <code>SIGKILL</code>. The trap: if the target group's deregistration delay is 300&nbsp;s (the default) but <code>stopTimeout</code> is 30&nbsp;s, the container is killed long before draining finishes and in-flight requests die. Align them: deregistration delay slightly above the longest normal request, and <code>stopTimeout</code> at least deregistration delay plus shutdown time.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">EKS and the AWS Load Balancer Controller</h4>\n<p style=\"line-height: 1.75\">The controller is a Kubernetes deployment that watches the API server and materialises AWS resources. It owns two main flows plus a CRD:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Ingress &rarr; Application Load Balancer.</strong> An <code>Ingress</code> with <code>ingressClassName: alb</code> produces an ALB, listeners, listener rules derived from the host and path rules, and a target group per backend service, continuously reconciled as Endpoints change.</li>\n<li><strong>Service of type LoadBalancer &rarr; Network Load Balancer.</strong> With <code>service.beta.kubernetes.io/aws-load-balancer-type: external</code> (or the <code>service.k8s.aws/nlb</code> load balancer class on modern versions) the controller provisions an NLB. Without that annotation, the legacy in-tree cloud provider creates a Classic Load Balancer, which is a common surprise on older clusters.</li>\n<li><strong>TargetGroupBinding</strong> is the lower-level primitive both flows compile down to, and you can also author it yourself.</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>Ingress groups</strong> are the feature that matters most at organisational scale. Setting <code>alb.ingress.kubernetes.io/group.name: shared-public</code> on many Ingress resources — across different namespaces and owned by different teams — makes them all share a single ALB, with <code>group.order</code> deciding listener rule priority. Instead of thirty ALBs each with its own hourly charge, idle LCU floor, subnet IP consumption and certificate attachment, you run one. That matters because ALBs per Region, rules per ALB (default 100), certificates per ALB and target groups per Region are all quotas that bite at scale. The trade-offs are real and worth volunteering in an interview: a shared ALB is a shared blast radius, one team's broken rule or oversized certificate list affects everyone, WAF and access logging are ALB-wide rather than per-team, and the rules-per-ALB quota now becomes a shared budget. The usual compromise is one group per trust tier or per environment — public, internal, admin — rather than one per team or one global group.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">IP Mode Versus Instance Mode</h4>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">instance mode (target<i class=o>-</i>type: instance)\n  ALB <i class=c>--&gt; NodePort on node-A --&gt; kube-proxy / iptables --&gt; maybe pod on node-B</i>\n          (extra hop, source NAT <i class=k>or</i> lost affinity, node counted healthy <i class=k>not</i> pod)\n\nip mode (target<i class=o>-</i>type: ip)   [VPC CNI gives <i class=k>every</i> pod a routable VPC IP]\n  ALB <i class=c>--&gt; pod IP directly</i>\n          (<i class=k>one</i> hop, <i class=k>per</i><i class=o>-</i>pod health checks, <i class=t>real</i> client connection <i class=k>to</i> the pod)</code></pre></div>\n<p style=\"line-height: 1.75\">In <strong>instance mode</strong> the controller registers <em>nodes</em> on the Service's NodePort. The ALB has no idea which nodes actually run pods, so a request can land on a node with no local replica and be forwarded by kube-proxy to a pod on another node — an extra network hop, extra latency, and (with <code>externalTrafficPolicy: Cluster</code>) source rewriting that obscures the origin. Health checks test the NodePort, so they report \"some pod somewhere is reachable\" rather than the health of a specific pod. Setting <code>externalTrafficPolicy: Local</code> removes the second hop but makes nodes without a local pod fail health checks, which causes uneven traffic distribution across nodes.</p>\n<p style=\"line-height: 1.75\">In <strong>IP mode</strong> — the default and correct choice on EKS with the VPC CNI, and mandatory for Fargate — the controller registers <strong>pod IPs directly</strong>. Traffic bypasses kube-proxy and iptables/IPVS entirely: one hop from the ALB to the pod, the client connection terminates on the pod so the ALB sees per-pod health and per-pod metrics, and load balancing decisions are actually per-replica rather than per-node. It also unlocks <strong>pod readiness gates</strong>, which instance mode cannot provide meaningfully. The costs: every pod consumes a VPC IP (plan subnet CIDRs and CNI prefix delegation accordingly), the pod security group or node security group must permit the ALB security group on the container port — the controller manages this automatically when it owns the backend security group — and target churn is per-pod, so the registration API rate matters on very large, fast-churning deployments.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">TargetGroupBinding, Readiness Gates and Graceful Shutdown</h4>\n<p style=\"line-height: 1.75\"><strong>TargetGroupBinding</strong> is a CRD (<code>elbv2.k8s.aws/v1beta1</code>) that says \"keep this target group's members in sync with the endpoints of this Service\". It is what Ingress and Service reconciliation generate internally, and authoring it directly is the right answer whenever the load balancer is owned outside Kubernetes: a Terraform-managed ALB, a shared ALB provisioned by a platform team, a weighted blue/green setup where CodeDeploy or your pipeline controls listener weights, or a migration where you want to shift traffic gradually from EC2 targets to pods in the same target group. It also lets you attach pods to an NLB target group that fronts a non-HTTP protocol.</p>\n<p style=\"line-height: 1.75\"><strong>Pod readiness gates</strong> are the single strongest senior answer about container load balancing. Kubernetes by default considers a pod Ready as soon as its readiness probe passes — but the pod is not yet <em>registered and healthy in the ALB target group</em>, which takes several seconds (registration call, then <code>healthy_threshold</code> &times; <code>interval</code> of successful checks). A Deployment rollout with <code>maxUnavailable: 0</code> will therefore terminate an old pod as soon as the new pod is locally Ready, even though the ALB has not yet begun sending traffic to it — and if the rollout is fast enough you can transiently have zero registered healthy targets, which the ALB answers with 503s. The readiness gate closes this gap: label the namespace with <code>elbv2.k8s.aws/pod-readiness-gate-inject: enabled</code> and the controller injects a readiness gate condition (<code>target-health.elbv2.k8s.aws/&lt;binding&gt;</code>) into new pods, which it sets to True only once the target is <em>healthy in the target group</em>. Until then the pod is not Ready, so the Deployment controller will not proceed, and the rollout advances at exactly the rate the load balancer can absorb. Requirements: IP mode targets and a Deployment (not a bare pod).</p>\n<p style=\"line-height: 1.75\">The mirror image is <strong>graceful shutdown</strong>. When a pod is deleted, Kubernetes sends <code>SIGTERM</code> and removes it from Endpoints <em>concurrently</em>, and the controller's deregistration is asynchronous — so for a few seconds the ALB may still send requests to a pod that has already begun shutting down. The fix is a <code>preStop</code> hook that simply sleeps long enough for deregistration and draining to complete before the application is signalled, with <code>terminationGracePeriodSeconds</code> greater than preStop sleep plus in-flight completion time, and the target group's <code>deregistration_delay.timeout_seconds</code> set just above the longest normal request. A coherent set looks like: deregistration delay 30&nbsp;s, preStop sleep 35&nbsp;s, termination grace period 75&nbsp;s, application closing its listener on SIGTERM and finishing in-flight work. Get any one of these wrong and you see connection resets during every deploy.</p>\n<p style=\"line-height: 1.75\"><strong>IRSA permissions.</strong> The controller runs as a service account annotated with <code>eks.amazonaws.com/role-arn</code>, and the trust policy federates the cluster's OIDC provider scoped to that exact service account. The role needs elasticloadbalancing create/modify/delete on load balancers, listeners, rules and target groups plus register/deregister targets; EC2 describe calls for subnets, security groups and VPCs, plus create/authorize/revoke/delete on the security groups it manages; ACM and IAM read for certificates; WAF and Shield associate calls if you use those; and tagging permissions since the controller identifies the resources it owns by tags. Public tasks and pods must also be in subnets tagged <code>kubernetes.io/role/elb=1</code> (public) or <code>kubernetes.io/role/internal-elb=1</code> (private), or the controller cannot discover where to place the load balancer — a very common first-deploy failure whose symptom is a stuck Ingress with a subnet-discovery event.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">How This Compares to a Mesh and to Native Ingress Controllers</h4>\n<p style=\"line-height: 1.75\">The AWS Load Balancer Controller handles <strong>north-south</strong> traffic: the edge into the cluster. A <strong>service mesh</strong> (App Mesh, Istio, Linkerd) handles <strong>east-west</strong> traffic between services, adding mTLS, retries, circuit breaking, fine-grained traffic splitting and per-hop telemetry that an ALB cannot provide between pods. They are complementary, not alternatives: the common pattern is an ALB at the edge terminating TLS and doing coarse host/path routing into the mesh's ingress gateway, with the mesh owning everything inside. Choosing a mesh <em>instead</em> of the controller means you still need something to get traffic from the internet to the gateway — usually an NLB — so you rarely avoid an AWS load balancer entirely.</p>\n<p style=\"line-height: 1.75\">Against <strong>in-cluster ingress controllers</strong> (NGINX, Traefik, Envoy Gateway): those run as pods, so you get richer routing (regex rewrites, complex header logic, custom Lua or WASM filters), portability across clouds, faster config reloads, and no AWS API rate limits or quotas. But you own their capacity, availability, upgrades and scaling, traffic takes an extra in-cluster hop, and you still need an NLB in front. The ALB path gives you a managed data plane, native WAF/Shield/ACM integration, per-target health visibility in CloudWatch, and no pods to babysit — at the cost of AWS-specific manifests, listener rule quotas, and less expressive routing. A pragmatic hybrid is common: ALB for the public edge and coarse routing, an in-cluster controller or gateway behind it for the fancy rewriting.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Production Scenario: Eliminating 502s and 503s During EKS Rolling Deploys</h4>\n<p style=\"line-height: 1.75\">Symptom: every deploy of a payments API on EKS produces a 20-40 second window with a few hundred 502s and a burst of 503s. Rollouts use <code>maxSurge: 25%, maxUnavailable: 25%</code>, targets are in instance mode, deregistration delay is the default 300&nbsp;s, <code>terminationGracePeriodSeconds</code> is the default 30, and there is no preStop hook. Diagnosis and fix, in order:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Attribute the errors first.</strong> <code>HTTPCode_ELB_5XX_Count</code> with no matching <code>HTTPCode_Target_5XX_Count</code> means the ALB generated them. In the access log, 503 with an empty <code>target_status_code</code> means <em>no healthy targets</em>; 502 with an empty target status means the target closed or reset the connection mid-request. That split tells you there are two distinct bugs, not one.</li>\n<li><strong>Fix the 503s with readiness gates.</strong> The 503s come from the rollout outrunning target registration: <code>maxUnavailable: 25%</code> lets old pods die as soon as new pods are locally Ready, before the ALB has completed health checks on them. Switch to IP mode (<code>alb.ingress.kubernetes.io/target-type: ip</code>), label the namespace <code>elbv2.k8s.aws/pod-readiness-gate-inject: enabled</code>, and set <code>maxUnavailable: 0</code> with <code>maxSurge: 25%</code>. Now a new pod counts as Ready only when it is healthy in the target group, so the rollout is paced by the load balancer.</li>\n<li><strong>Fix the 502s with shutdown choreography.</strong> The 502s come from the pod being SIGTERMed while the ALB still has it registered. Add <code>preStop: exec: [sleep, 35]</code>, set <code>terminationGracePeriodSeconds: 75</code>, and set the target group attribute <code>deregistration_delay.timeout_seconds=30</code> via <code>alb.ingress.kubernetes.io/target-group-attributes</code>. Make the application handle SIGTERM by stopping the listener and draining rather than exiting.</li>\n<li><strong>Close the keep-alive race.</strong> Ensure the application's HTTP keep-alive/idle timeout exceeds the ALB's idle timeout (default 60&nbsp;s) — a Node.js service with a 5-second keepAliveTimeout will periodically close a connection the ALB is about to reuse, yielding sporadic 502s that are easy to blame on deploys.</li>\n<li><strong>Tighten health checking.</strong> A 30-second interval with a healthy threshold of 5 means 150&nbsp;s before a pod receives traffic, which readiness gates will now correctly wait for and which makes deploys glacial. Use interval 10&nbsp;s, healthy threshold 2, unhealthy threshold 2, on a cheap <code>/healthz</code> that checks only local liveness — not downstream dependencies, or one slow database will fail every pod at once.</li>\n<li><strong>Prove it.</strong> Run a steady load generator at production-like concurrency through the ALB for the duration of a deploy and assert zero non-2xx, while watching <code>HTTPCode_ELB_5XX_Count</code>, <code>TargetConnectionErrorCount</code> and <code>HealthyHostCount</code>. Make this an automated pre-production gate; otherwise the configuration will silently regress the next time someone edits the chart.</li>\n</ul>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"With containers the targets churn constantly, so something has to reconcile the target group continuously — the ECS scheduler, or the AWS Load Balancer Controller on EKS.
