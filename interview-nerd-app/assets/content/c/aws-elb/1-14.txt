{"title":"Security Architecture for Internet-Facing Load Balancers","tags":["aws-waf","shield-advanced","request-smuggling","tls-posture"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">An internet-facing load balancer is your attack surface. Everything hostile that reaches your application arrives through it, which makes it the single best place to stop things cheaply — and the place where a weak configuration silently undoes good application security. A senior answer to &quot;secure this ALB&quot; is not &quot;turn on WAF.&quot; It is a layered story: something at the edge absorbing volume, a request-inspection layer with rules you have actually tuned, a load balancer whose HTTP parsing and TLS posture are deliberately chosen, a network posture where the origin cannot be reached except through the intended path, an application that never trusts client-controlled headers, and logging good enough to reconstruct an attack afterwards.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">AWS WAF: Rule Design and the Placement Decision</h4>\n<p style=\"line-height: 1.75\">AWS WAF attaches to an ALB, a CloudFront distribution, API Gateway, AppSync, Cognito user pools, App Runner and Verified Access — but notably <strong>not to an NLB</strong>, which is one of the strongest practical arguments for terminating HTTP at an ALB even when you also need static IPs. A web ACL is an ordered list of rules with a default action; each rule either terminates evaluation (block, allow) or does not (count, captcha and challenge sit in between), and rules are evaluated in priority order with <strong>WCU</strong> capacity limits per web ACL.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Managed rule groups.</strong> AWS and Marketplace vendors publish maintained rule sets. The core ones: <em>Core rule set (CRS)</em> for broad OWASP-style coverage, <em>Known bad inputs</em>, <em>SQL database</em> and <em>Linux/Windows/POSIX</em> operating-system groups, <em>Amazon IP reputation list</em> and <em>Anonymous IP list</em> for source-based signals, and <em>Bot Control</em> (with a targeted tier that adds behavioral detection and challenges) and <em>Account takeover / account creation fraud prevention</em> for credential-focused abuse. These are the highest value per hour of effort you will spend — but they are also where false positives come from, so never deploy them straight to block.</li>\n<li><strong>Custom rules.</strong> Statements match on the URI, query string, headers, body (with a size limit — oversized bodies can be matched partially or handled explicitly), method, IP set, regex pattern set, label from an earlier rule, or geographic origin, combined with AND/OR/NOT and with <strong>text transformations</strong> (URL-decode, HTML-decode, lowercase, compress whitespace) applied before matching so trivial obfuscation does not bypass you. Scope-down statements let you apply an expensive rule group only to the paths that need it.</li>\n<li><strong>Rate-based rules.</strong> The most operationally valuable rule type. WAF counts requests per aggregation key over a sliding window and blocks keys that exceed the limit. The key is what matters: aggregating by <strong>IP</strong> is the default, by <strong>forwarded IP</strong> when you are behind CloudFront or another proxy, and by a <strong>custom key</strong> — a header, cookie, query argument, URI path, or a combination — which is how you rate-limit per API key or per account rather than per IP. Combine with a scope-down statement so the limit applies only to <code>/login</code> or <code>/password-reset</code>: a global limit high enough not to hurt legitimate users is useless against credential stuffing, while a limit of a few attempts per minute against the login path alone is devastating to it and invisible to everyone else. Distributed credential stuffing from thousands of IPs defeats IP aggregation entirely, which is exactly when custom keys plus Bot Control and account-takeover rules earn their cost.</li>\n<li><strong>Count mode and safe rollout.</strong> Deploy every new rule or managed group in <strong>count</strong> mode first, enable WAF logging, and analyze for days or weeks: which rules would have matched, on which paths, from which clients, and how many of those were legitimate. Then add rule-level exceptions (override specific rules within a managed group to count, or scope the group away from paths that legitimately carry SQL-looking payloads or large HTML) and only then flip to block. Skipping this step is the single most common cause of a WAF rollback, and &quot;we turned it on in count mode for two weeks and tuned with the logs&quot; is the sentence interviewers listen for.</li>\n<li><strong>Logging.</strong> WAF logs to CloudWatch Logs, S3 (directly or via Firehose) or Kinesis Data Firehose, with redaction of sensitive fields and optional filtering to log only blocked requests. Query them in Athena or Logs Insights. Logs are how you tune, how you prove an attack was blocked, and how you build a rate-limit threshold from evidence rather than intuition.</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>Edge versus ALB placement.</strong> WAF at CloudFront inspects and blocks at the edge location nearest the client, so malicious traffic never crosses into your Region and never consumes origin capacity or data transfer; it also gives you a single web ACL for a global footprint. WAF on the ALB inspects after traffic has arrived in-Region, but it sees the request in its final form after any CloudFront behavior rewriting, it can use regional rules and IP sets, and it protects paths that bypass CloudFront. The mature pattern is <strong>both</strong>: coarse volumetric and geo rules plus Bot Control at CloudFront, finer application-specific rules at the ALB, and — critically — the ALB locked so it only accepts traffic from CloudFront, otherwise an attacker who learns the ALB name simply skips your edge WAF entirely.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Shield Standard, Shield Advanced and DDoS Resilience</h4>\n<p style=\"line-height: 1.75\"><strong>Shield Standard</strong> is always on at no additional cost for all AWS customers and defends against common network and transport layer attacks — SYN floods, reflection attacks, UDP amplification — at the edge of the AWS network. For most workloads it is genuinely sufficient at layers 3 and 4. <strong>Shield Advanced</strong> is a paid subscription with a substantial monthly commitment and adds: enhanced detection tuned to your specific traffic baseline, the <strong>Shield Response Team</strong> for assisted mitigation during an event, <strong>cost protection</strong> that credits scaling charges caused by an attack (ALB LCUs, CloudFront data transfer, Route 53 queries, EC2 scaling), health-based detection using a Route 53 health check so mitigations understand application impact, application-layer automatic mitigation on protected CloudFront and ALB resources, and centralized management through AWS Firewall Manager across an organization. The honest decision rule: subscribe when downtime is expensive enough, or when you are a likely target — payments, gaming, gambling, political and media sites — or when the cost protection and the response team are worth more than the fee. It is not a substitute for architecture.</p>\n<p style=\"line-height: 1.75\">The architecture matters more than the subscription. <strong>CloudFront</strong> puts hundreds of edge locations between attackers and your origin, absorbs volumetric traffic in a globally distributed fashion, serves cached content without touching your Region, and terminates TLS at the edge so slow-loris style connection abuse hits AWS capacity rather than your load balancer. <strong>Global Accelerator</strong> similarly moves the attack surface to the AWS edge for non-HTTP workloads and is protected by Shield Standard. The strongest single move is <strong>keeping origin addresses private</strong>: an internal ALB reachable only through PrivateLink or a VPC origin, or a public ALB whose security group allows only the CloudFront managed prefix list. Anything else means the origin's address is discoverable and directly attackable. Finally, be honest about <strong>scaling assumptions under attack</strong>: autoscaling turns a volumetric attack into a bill and eventually into a quota wall, so explicit maximums, rate limiting at the edge, and shedding load with a cheap fixed response beat scaling into an attack. Practice this: know which knob you pull first, and have a pre-built web ACL rule you can flip from count to block.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Request-Level Threats the Load Balancer Participates In</h4>\n<p style=\"line-height: 1.75\"><strong>HTTP request smuggling and desync.</strong> When two HTTP implementations in a chain disagree about where one request ends and the next begins — typically because of conflicting <code>Content-Length</code> and <code>Transfer-Encoding</code> headers, or obfuscated header values — an attacker can smuggle a second request that the front end does not see but the back end processes, poisoning the connection for the next victim, bypassing front-end authorization, or capturing other users' requests. ALB exposes <strong>desync mitigation mode</strong> with three settings:</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; Query for ambiguous requests grouped by client and user agent; if they are all one legacy partner, fix that integration and then tighten. Related: <code>routing.http.drop_invalid_header_fields.enabled</code> drops headers with invalid characters rather than forwarding them, and the corresponding metrics tell you the blast radius before you enable it.</p>\n<p style=\"line-height: 1.75\"><strong>Header injection and the X-Forwarded-For trap.</strong> ALB <em>appends</em> the immediate peer's address to <code>X-Forwarded-For</code> rather than replacing the header, so a client that sends <code>X-Forwarded-For: 1.2.3.4</code> produces <code>1.2.3.4, &lt;real client IP&gt;</code> at your application. An application that reads the <strong>first</strong> value — the common naive implementation, and the default in several frameworks — is trivially spoofable, which breaks rate limiting, IP allow-listing, geo restrictions, audit logs and fraud signals all at once. The correct derivation is to count from the <strong>right</strong>: if you have exactly <em>n</em> trusted proxies between the client and your application (an ALB alone is one; CloudFront plus ALB is two), the client IP is the <em>n</em>th value from the end. Everything to the left of that is attacker-controlled data and must be treated as such. Configure this explicitly in your framework — a trusted-proxy count or trusted-proxy list — rather than accepting a default, and be aware that ALB also supports an <code>xff_header_processing.mode</code> attribute (append, preserve or remove) plus <code>xff_client_port</code>, which changes the arithmetic, so the setting and the application code must be decided together. For traffic that must come only via CloudFront, the correct client IP comes from CloudFront's headers, which you can trust precisely <em>because</em> the origin lock makes CloudFront the only possible path.</p>\n<p style=\"line-height: 1.75\"><strong>Oversized headers and slow-loris behavior.</strong> The load balancer enforces its own limits on header count and size and rejects requests that exceed them, which protects targets from a class of resource exhaustion for free. Slow-loris style attacks — opening many connections and sending bytes very slowly to exhaust the server's connection capacity — are largely absorbed by the load balancer because the connection is terminated at managed capacity that scales rather than at your fixed-size worker pool; ALB also has its own request timeout for clients that never complete a request. CloudFront in front improves this further, and WAF rate-based rules aggregating on IP add a ceiling on connection-establishing behavior. The residual risk to watch is <code>RejectedConnectionCount</code> and <code>ConsumedLCUs</code> — a connection-exhaustion attack shows up as cost and rejected connections before it shows up as errors.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Network Posture: Make the Origin Unreachable</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Private-only architectures.</strong> Internal ALBs in private subnets, targets in private subnets with no public IPs, egress via NAT gateway or VPC endpoints only. The load balancer is the only ingress and it is not on the internet. This is the default for service-to-service traffic and for anything fronted exclusively by CloudFront with a VPC origin or by PrivateLink.</li>\n<li><strong>The CloudFront-only origin lock.</strong> Two controls together, because each alone is insufficient. First, restrict the ALB security group to the AWS-managed prefix list for CloudFront origin-facing servers (<code>com.amazonaws.global.cloudfront.origin-facing</code>), which keeps itself updated as CloudFront's ranges change — do not hand-maintain CIDR lists. That stops arbitrary internet clients but not <em>another</em> CloudFront distribution, including an attacker's. So second, have CloudFront add a <strong>custom secret header</strong> (stored in Secrets Manager, rotated) and have the ALB reject requests lacking it, ideally with a listener rule returning a fixed 403 so the request never reaches a target, or via a WAF rule. Newer alternatives — CloudFront VPC origins, or an origin access pattern that removes public reachability entirely — are stronger where available because there is no public IP to find.</li>\n<li><strong>Security group hygiene.</strong> Target security groups should allow traffic only from the load balancer's security group (a security-group reference, not a CIDR), on exactly the traffic and health check ports. No <code>0.0.0.0/0</code> on anything but the public listener ports of the internet-facing load balancer, and no leftover administrative rules. ALB has always had security groups; <strong>NLB now supports them too</strong>, which closed a long-standing gap — historically an NLB had no security group, so the target's own security group was the only enforcement point and, with client IP preservation on, it had to allow the client ranges directly, which meant &quot;allow the internet&quot; on the target. With NLB security groups you can enforce at the load balancer, and the <code>SecurityGroupBlockedFlowCount</code> metrics tell you what is being dropped. Note the related setting controlling whether security group rules are evaluated for traffic that NLB routes to targets — understand it before assuming your target rules are being applied.</li>\n<li><strong>Client IP preservation nuances.</strong> With preservation on, the target sees the client address, so target security groups must permit client ranges and your flow logs show real clients; with it off, the target sees the NLB's address and rules are simple but you lose client identity unless you use Proxy Protocol v2. This is a genuine security-versus-observability trade-off to state explicitly.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">TLS Posture, Authorization Offload and Logging as a Control</h4>\n<p style=\"line-height: 1.75\"><strong>TLS.</strong> Choose a security policy deliberately: a modern policy that requires TLS 1.2 as a minimum, prefers TLS 1.3, and offers only forward-secret cipher suites (ECDHE), so that compromise of the private key does not retroactively decrypt captured sessions. AWS also publishes FIPS-compliant policies for regulated workloads. Use ACM certificates with automatic renewal and alarm on approaching expiry, since a certificate whose DNS validation record was deleted will silently fail to renew. Add <strong>HSTS</strong> as a response header so browsers refuse plaintext, and redirect HTTP to HTTPS with a listener rule rather than in application code, so the redirect happens before your compute is involved. ALB can also inject security response headers at the listener level in newer configurations, but the safe assumption in an interview is that HSTS, CSP and frame options come from the application or CloudFront functions unless you have verified otherwise. For traffic from the load balancer to targets, encrypt in transit where your threat model includes the VPC — end-to-end HTTPS target groups, remembering that ALB does not validate the target certificate, so this is protection against passive observation rather than a target authentication mechanism. <strong>Mutual TLS</strong> on the listener authenticates clients with certificates against a trust store, with verify or passthrough modes, which is the right control for partner and device APIs.</p>\n<p style=\"line-height: 1.75\"><strong>Authorization offload.</strong> ALB can authenticate users with <strong>OIDC</strong> or <strong>Cognito</strong> before a request ever reaches your targets: the listener rule performs the authorization-code flow, sets a session cookie, and forwards the request with signed <code>x-amzn-oidc-data</code>, <code>x-amzn-oidc-identity</code> and <code>x-amzn-oidc-accesstoken</code> headers. This is a real security boundary — unauthenticated requests never touch application code, which shrinks the attack surface dramatically for internal tools and admin consoles, and centralizes session handling where it is hard to get wrong. Two obligations: the application must <strong>verify the signature</strong> of the OIDC data header (and be reachable only through the load balancer, or an attacker sets the header themselves), and you must plan for the session cookie size and for the fact that this pattern fits browser flows better than machine-to-machine APIs, where a JWT authorizer at API Gateway or in-application validation is usually the better fit.</p>\n<p style=\"line-height: 1.75\"><strong>Logging as a security control.</strong> Access logs, connection logs and WAF logs are not just diagnostics: they are the evidence base for incident response, and they are frequently a compliance requirement. Send them to an S3 bucket with encryption, versioning, restricted access and a lifecycle policy, ideally in a separate logging account so that compromise of the application account does not let an attacker erase the record. Connection logs are particularly valuable for security because they record connection attempts that never became requests — scanning, failed handshakes, and mTLS rejections. Complete the picture with CloudTrail on <code>elasticloadbalancing</code> and <code>wafv2</code> API calls so that a change to a listener rule, a security group or a web ACL is attributable, and Config rules or Firewall Manager policies so that an ALB created without a web ACL is detected automatically rather than discovered during an incident.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Security Review Scenario: A Public ALB</h4>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">FINDINGS <i class=k>on</i> &quot;prod-web&quot; (internet<i class=o>-</i>facing ALB, <i class=n>3</i> AZs, EC2 targets)\n\n<i class=n>1</i>  <i class=k>No</i> WAF web ACL associated.
