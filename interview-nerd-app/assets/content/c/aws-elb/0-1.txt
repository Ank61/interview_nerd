{"title":"The Load Balancer Types — ALB, NLB, GWLB, and the Classic Load Balancer","tags":["aws","elb","alb","nlb"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">AWS does not offer one load balancer; it offers a small family of them. Choosing the right one is the first real decision you make, and the choice comes down to a single question: <em>how much of the traffic does the load balancer need to understand?</em> Before any AWS specifics, that question is worth unpacking, because it explains the whole family.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">First, the idea of \"layers\" in plain words</h4>\n<p style=\"line-height: 1.75\">Network people describe communication as a stack of <strong>layers</strong>, each building on the one below — a model called the <strong>OSI model</strong>. You only need two of its seven layers to understand load balancing.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Layer 4, the transport layer.</strong> This is the level of <strong>TCP</strong> and <strong>UDP</strong> connections. All you can see here is: which IP address and port is talking to which IP address and port, and a stream of bytes flowing between them. You cannot see what those bytes <em>mean</em>. A layer 4 load balancer picks a server for the connection and then shovels bytes back and forth without inspecting them. Because it does almost no thinking, it is extremely fast and works with any protocol.</li>\n<li><strong>Layer 7, the application layer.</strong> This is the level of <strong>HTTP</strong> — the protocol browsers and APIs speak. Here the traffic has structure: a method (<code>GET</code>, <code>POST</code>), a <strong>host name</strong> (<code>api.example.com</code>), a <strong>URL path</strong> (<code>/images/logo.png</code>), <strong>headers</strong> (extra key-value metadata sent with each request), <strong>query strings</strong>, and <strong>cookies</strong> (small values the server asks the browser to send back on later requests). A layer 7 load balancer reads all of that and can make decisions based on it — send <code>/api/*</code> to one group of servers and everything else to another.</li>\n</ul>\n<p style=\"line-height: 1.75\">That is the whole trade-off: layer 7 gives you intelligence about web traffic, layer 4 gives you raw speed and protocol freedom. Now the AWS types make sense.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Application Load Balancer (ALB) — the default for web traffic</h4>\n<p style=\"line-height: 1.75\">The <strong>Application Load Balancer</strong> operates at layer 7 and handles <strong>HTTP and HTTPS</strong> (including HTTP/2 and gRPC). Because it parses each request, it can do <strong>content-based routing</strong>: route on the URL path, the host name, HTTP headers, the request method, query-string parameters, or the client's source IP range. One ALB can therefore serve <code>shop.example.com</code> and <code>api.example.com</code> and send <code>/checkout</code> somewhere different again — all with one certificate store, one set of access logs, and one hourly charge.</p>\n<p style=\"line-height: 1.75\">It also does the web-specific work you would otherwise write yourself: terminating TLS with a certificate from <strong>AWS Certificate Manager</strong>, redirecting HTTP to HTTPS, returning a fixed response such as a maintenance page, <strong>sticky sessions</strong> via a cookie so a user keeps landing on the same server, and integration with <strong>AWS WAF</strong> (a web application firewall that filters malicious requests) and with <strong>Amazon Cognito</strong> or any OIDC provider for authentication at the edge. Its addresses are always dynamic, so you reference it only by DNS name. For a normal web application or REST API, the ALB is the right answer and should be your default.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Network Load Balancer (NLB) — layer 4 speed and static IPs</h4>\n<p style=\"line-height: 1.75\">The <strong>Network Load Balancer</strong> operates at layer 4 and handles <strong>TCP, UDP</strong> and <strong>TLS</strong> (TLS here meaning it can terminate encryption for a raw TCP stream, not that it understands HTTP). It forwards connections without reading their contents, which makes it capable of millions of requests per second at very low, very consistent latency, and lets it carry protocols an ALB cannot touch at all.</p>\n<p style=\"line-height: 1.75\">Two features drive most NLB decisions:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Static IP addresses.</strong> An NLB gets one IP address per enabled Availability Zone, and you may supply your own <strong>Elastic IP</strong> (a fixed public IP you own in your account) for each zone. This is what you need when a bank, a hospital or a partner will only allow traffic from a hardcoded list of addresses in their firewall.</li>\n<li><strong>Non-HTTP workloads.</strong> A multiplayer game server exchanging UDP packets, a database proxy speaking the PostgreSQL wire protocol, an <strong>MQTT</strong> broker for IoT devices, an SMTP mail relay, or a custom binary protocol — none of these are HTTP, so an ALB simply cannot load balance them. An NLB can.</li>\n</ul>\n<p style=\"line-height: 1.75\">Two behavioural details matter early. First, an NLB can <strong>preserve the client's source IP address</strong> when targets are registered by instance ID, so your application sees the real client IP with no extra headers — but the flip side is that your instance <strong>security group</strong> rules must allow the client's IP range rather than the load balancer. Second, because it is not HTTP-aware, an NLB has no path rules, no host rules, no HTTP-to-HTTPS redirect and no fixed-response action.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Gateway Load Balancer (GWLB) — for network appliances, not for your app</h4>\n<p style=\"line-height: 1.75\">The <strong>Gateway Load Balancer</strong> is the odd one out, and beginners rarely configure one — but you should recognise what it is for so the name does not confuse you. It exists to insert <strong>third-party network appliances</strong> — firewalls, intrusion detection and prevention systems, deep packet inspection, traffic analysis tools from vendors such as Palo Alto, Fortinet or Check Point — transparently into your traffic path.</p>\n<p style=\"line-height: 1.75\">It works at layer 3 (the IP layer) as a \"bump in the wire\": traffic is routed to it, it distributes flows across a fleet of appliances while keeping each flow pinned to the same appliance, the appliance inspects the packets and hands them back, and the traffic continues to its real destination. It uses the <strong>GENEVE</strong> encapsulation protocol on port 6081 and is paired with a <strong>Gateway Load Balancer endpoint</strong> that you point a route table at. The key mental note: a GWLB is a security-inspection building block for the network team, not something you put in front of a web application.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Classic Load Balancer (CLB) — the legacy original</h4>\n<p style=\"line-height: 1.75\">The <strong>Classic Load Balancer</strong> was the first ELB, launched in 2009, and it predates the split into layer 4 and layer 7 products — it does a bit of both (HTTP/HTTPS plus raw TCP/SSL) but does neither as well as the modern types. It has no target groups, no path or host rules, no support for containers on dynamic ports, and no HTTP/2. AWS calls it the <strong>previous-generation</strong> load balancer.</p>\n<p style=\"line-height: 1.75\">You will still meet it in three places: old accounts that were built before 2016, older blog posts and tutorials, and certification exam material that tests whether you know it is legacy. Treat it as read-only knowledge — <strong>all new work should use an ALB or an NLB</strong>, and AWS provides migration tooling for moving off it. One historical artefact worth knowing: the CLB's routing algorithm for TCP listeners was least-connections, and for HTTP listeners round robin, and it used the <code>AWSELB</code> cookie for stickiness.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">ELB v1 versus ELB v2, and the elbv2 CLI namespace</h4>\n<p style=\"line-height: 1.75\">This trips people up the first time they touch the CLI. AWS splits the service into two API generations:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>ELB v1</strong> is the Classic Load Balancer only. Its CLI namespace is <code>aws elb</code> (commands like <code>aws elb describe-load-balancers</code>, <code>aws elb register-instances-with-load-balancer</code>).</li>\n<li><strong>ELB v2</strong> covers ALB, NLB and GWLB — everything modern. Its CLI namespace is <code>aws elbv2</code> (<code>aws elbv2 create-load-balancer</code>, <code>aws elbv2 create-target-group</code>, <code>aws elbv2 describe-target-health</code>). The concepts of listeners, rules and target groups only exist in v2.</li>\n</ul>\n<p style=\"line-height: 1.75\">So if a command you copied uses <code>aws elb</code> and you are working with an ALB, that is your bug: you need <code>aws elbv2</code>. In CloudFormation the same split appears as <code>AWS::ElasticLoadBalancing::LoadBalancer</code> (classic) versus <code>AWS::ElasticLoadBalancingV2::LoadBalancer</code> (modern).</p>\n<h4 style=\"margin-top: 1.5rem;
