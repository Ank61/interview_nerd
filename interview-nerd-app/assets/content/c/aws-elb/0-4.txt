{"title":"Health Checks — How the Load Balancer Knows a Target Is Broken","tags":["aws","elb","health-checks","troubleshooting"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">A load balancer is only useful if it knows which servers are actually working. A <strong>health check</strong> is how it finds out: the load balancer repeatedly calls a chosen path (or simply opens a connection to a chosen port) on every registered target, looks at the answer, and decides whether to keep sending that target real user traffic. Nothing else in ELB causes beginners as much pain as this, so it is worth understanding properly rather than copying a config and hoping.</p>\n<p style=\"line-height: 1.75\">The checks come from the <strong>load balancer nodes</strong>, and there is a node in every Availability Zone you enabled — so each target is being probed by several sources at once, from the load balancer's private IP addresses. That has two consequences you will meet later: your firewall rules must allow the load balancer, and your health endpoint must be cheap, because it is being called constantly.</p>\n<h4 style=\"margin-top: 1.5rem; Requiring <em>two or more consecutive</em> failures means one bad moment does not eject a perfectly good server, which would reduce your capacity for no reason and could cascade. The cost is detection time: with the defaults, unhealthy threshold 2 and interval 30 seconds, a dead target takes up to about 60 seconds to be pulled out. If you need faster failover, lower the interval (to 10 seconds, say) rather than dropping the threshold to 1 — which is not even allowed, the minimum is 2. Conversely the healthy threshold of 5 is deliberately cautious about letting a flapping server back in.</p>\n<p style=\"line-height: 1.75\"><strong>Why timeout must be shorter than interval.</strong> The timeout is a deadline inside each attempt; the interval is the gap between attempts. If the timeout were longer than the interval, a slow target would still be waiting on attempt one when attempt two was due, and the checks would overlap and confuse each other. AWS enforces the relationship, so a timeout of 5 with an interval of 30 is normal, and a timeout of 10 with an interval of 5 will be rejected.</p>\n<p style=\"line-height: 1.75\"><strong>Why success codes are so often wrong.</strong> The default matcher is exactly <code>200</code>. Plenty of real endpoints answer something else: an API gateway path may return <code>204 No Content</code>, a root path may issue a <code>301</code> redirect to HTTPS or to a locale, and some frameworks answer <code>404</code> for a path you did not define. All of those are marked unhealthy by default. You can widen the matcher to <code>200,204</code> or a range like <code>200-299</code>, but the better instinct is usually to fix the endpoint so it genuinely returns 200 — a matcher of <code>200-499</code> \"fixes\" the alarm by making the health check meaningless.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The target lifecycle states</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>initial.</strong> The target has just been registered and the load balancer has not yet completed enough checks to judge it. Perfectly normal for the first minute or two — do not panic and start changing settings.</li>\n<li><strong>healthy.</strong> Passing checks and receiving traffic. This is the goal.</li>\n<li><strong>unhealthy.</strong> Failed the unhealthy threshold number of consecutive checks. It receives <strong>no new requests</strong>, but the load balancer keeps checking it, so it will return to <code>healthy</code> on its own once it recovers. <code>describe-target-health</code> also gives a <code>Reason</code> code such as <code>Target.Timeout</code>, <code>Target.ResponseCodeMismatch</code> or <code>Target.FailedHealthChecks</code>, which is your single most useful diagnostic.</li>\n<li><strong>draining.</strong> You (or Auto Scaling) deregistered it. New requests stop immediately, in-flight requests are allowed to finish, up to the <strong>deregistration delay</strong> (default 300 seconds). Then it disappears from the group.</li>\n<li><strong>unused.</strong> The target is registered and may even be fine, but it cannot receive traffic for a structural reason: its target group is not attached to any listener rule, or the target is in an Availability Zone that is not enabled on the load balancer, or the target group's load balancer does not exist. A classic <code>unused</code> sighting is registering an instance in <code>eu-west-1c</code> when the ALB only has subnets in <code>1a</code> and <code>1b</code>.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What actually happens when a target fails</h4>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">t<i class=o>=</i><i class=n>0</i>s    <i class=k>GET</i> <i class=o>/</i>health <i class=o>-</i><i class=o>&gt;</i> <i class=n>200</i>   i<i class=o>-</i>AAA healthy   i<i class=o>-</i>BBB healthy   (<i class=n>50</i><i class=o>%</i> <i class=o>/</i> <i class=n>50</i><i class=o>%</i> <i class=k>of</i> traffic)\nt<i class=o>=</i><i class=n>30</i>s   i<i class=o>-</i>AAA app crashes. The important planning consequence is <strong>capacity</strong>: if two servers were each at 60% CPU and one fails, the survivor is asked to do 120% of a server's work and will also fall over. Size your fleet so the remaining targets can absorb the loss — commonly phrased as N+1, and across Availability Zones so the loss of a whole data centre is survivable.</p>\n<p style=\"line-height: 1.75\"><strong>The all-unhealthy case is special.</strong> If every target in a target group is unhealthy, the load balancer does not have a healthy target to pick, and it answers clients itself with <strong>HTTP 503 Service Unavailable</strong>. For an ALB there is a deliberate safety behaviour to know: if <em>all</em> targets in a target group are unhealthy, the ALB will route requests to <em>all</em> of them anyway (\"fail open\"), on the theory that a broken health check is more likely than a simultaneously broken fleet, and a half-working server beats a guaranteed 503. This is why you sometimes see traffic still reaching targets the console paints red — and it is a strong hint to look at your health check configuration, not at your servers.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Designing a good health check endpoint</h4>\n<p style=\"line-height: 1.75\">Do not point the health check at <code>/</code> and move on. Add a dedicated path such as <code>/health</code> that answers the real question: <em>can this process serve a request right now?</em> A good one is:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Inside the application, not the web server.</strong> If the check is served by nginx alone, it will return 200 while the application behind nginx is dead. The point of a layer 7 check over a simple port check is that it proves the app is alive, not just that something is listening.</li>\n<li><strong>Lightweight.</strong> No database queries, no external API calls, no heavy computation. Return a tiny body and a 200.</li>\n<li><strong>Unauthenticated and un-redirected.</strong> The load balancer sends no cookies and no credentials and does not follow redirects, so a check path behind a login wall or issuing a 302 will fail.</li>\n<li><strong>Not logged at full volume.</strong> With an interval of 30 seconds, two Availability Zones and multiple nodes, you can easily receive thousands of health probes a day per target; many teams exclude the path from access logs to keep them readable.</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>The deep health check trap.</strong> It is tempting to make <code>/health</code> also verify the database, the cache and three downstream services — \"then the check really means the app works\". Resist it, and understand why: every target shares those dependencies. If the database hiccups for 20 seconds, <em>every</em> target fails its health check simultaneously, the entire fleet is marked unhealthy, and if Auto Scaling is set to <code>ELB</code> health checks it starts <strong>terminating and replacing your whole fleet</strong> — turning a brief database blip into a long, self-inflicted outage. The replacements then fail their checks too, because the database is still unhappy.</p>\n<p style=\"line-height: 1.75\">The standard resolution is two endpoints with different audiences. A <strong>shallow</strong> check (<code>/health</code> or a liveness check) that only proves this process can serve, used by the load balancer and Auto Scaling. A <strong>deep</strong> check (<code>/health/deep</code> or a readiness/diagnostics endpoint) that tests dependencies, used by your monitoring and alerting system — where a failure pages a human instead of destroying servers. Many teams also add a small in-app circuit breaker so the app returns fast errors during a dependency outage while still reporting itself alive.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Troubleshooting checklist: \"my targets are unhealthy\"</h4>\n<p style=\"line-height: 1.75\">Start by reading the reason code from <code>aws elbv2 describe-target-health</code> — it points at the right branch immediately. Then work down this list.</p>\n<ol style=\"margin-left: 1.5rem; list-style: decimal; line-height: 2\">\n<li><strong>Security group not allowing the load balancer.</strong> The most common cause by far, and it usually shows as <code>Target.Timeout</code>. A <strong>security group</strong> is a virtual firewall attached to your instance. The instance's security group must allow <strong>inbound traffic on the health check port from the load balancer's security group</strong> (reference the load balancer's security group ID as the source — cleaner and safer than an IP range). Remember to allow the health check port even when it differs from the traffic port.</li>\n<li><strong>Wrong path returning 404.</strong> Reason code <code>Target.ResponseCodeMismatch</code> with a 404. Either the path does not exist, or it exists but with a different prefix (<code>/api/health</code>, not <code>/health</code>). Test from a machine inside the VPC with curl before you change anything else.</li>\n<li><strong>The app binds only to localhost.</strong> Also <code>Target.Timeout</code>, and maddening because the app works when you SSH in and curl it. If the process listens on <code>127.0.0.1:8080</code> it is unreachable from any other machine, load balancer included. It must bind to <code>0.0.0.0:8080</code> (all interfaces). Confirm with <code>ss -tlnp</code> on the instance and look for <code>0.0.0.0:8080</code> rather than <code>127.0.0.1:8080</code>.</li>\n<li><strong>The app is slow to start; the health check is not.</strong> Checks begin as soon as the target is registered. A JVM that takes 90 seconds to warm up will fail its first several checks. The fix is not a longer timeout — it is an Auto Scaling <code>--health-check-grace-period</code> long enough to cover startup, and, if needed, a larger healthy threshold or a slightly longer interval.</li>\n<li><strong>Wrong success codes.</strong> Reason <code>Target.ResponseCodeMismatch</code> with something like 204, 301 or 302. Either widen <code>--matcher</code> (for example <code>200,204</code>) or, better, make the endpoint return a plain 200 with no redirect.</li>\n<li><strong>The app requires a Host header.</strong> Health check requests arrive with the target's IP address as the Host, not your domain. A virtual-host configuration in nginx or Apache with only <code>server_name shop.example.com</code> and no default server will answer with a 404 or 403 — so add a default server block that answers the health path regardless of Host, or use the ALB's health check <code>--health-check-path</code> against a server that does not care.</li>\n<li><strong>HTTPS and certificate issues.</strong> If the health check protocol is HTTPS, the target must actually serve TLS on that port. Note that ELB health checks <strong>do not validate the certificate</strong>, so a self-signed certificate is acceptable — but a target serving plain HTTP on a port being checked with HTTPS (or the reverse) fails every time. Unless you have a specific reason, check with plain <strong>HTTP</strong> on the private network and keep TLS termination at the load balancer.</li>\n<li><strong>Structural problems.</strong> A state of <code>unused</code> rather than <code>unhealthy</code> means the target group is not attached to a listener rule, or the target sits in an Availability Zone the load balancer does not have a subnet in. Also check the instance is genuinely <code>running</code> and in the target group's VPC.</li>\n</ol>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"Unhealthy means the instance is broken.\"</strong> Far more often the <em>health check configuration</em> is broken — a security group rule, a 404 path, a wrong matcher. Prove the app works by curling the health path from another machine in the VPC before you touch the server.</li>\n<li><strong>\"An unhealthy target is terminated.\"</strong> Not by the load balancer. It only stops sending traffic and keeps probing, so the target can recover by itself. Termination happens only if an <strong>Auto Scaling group</strong> with <code>--health-check-type ELB</code> decides to replace it.</li>\n<li><strong>\"I should set the unhealthy threshold to 1 to fail over faster.\"</strong> The minimum is 2, and for good reason: a single lost packet or garbage-collection pause would eject a healthy server. To detect failure faster, shorten the <strong>interval</strong> instead.</li>\n<li><strong>\"A deeper health check is a better health check.\"</strong> A check that tests the database can take your whole fleet out during a brief database blip — and with ELB-type Auto Scaling health checks, replace it. Keep the load balancer's check shallow; put the deep check behind monitoring.</li>\n<li><strong>\"A port check is enough.\"</strong> An open TCP port only proves something is listening. An HTTP check on a real path proves the application can serve — which is why an ALB uses HTTP checks by default.</li>\n<li><strong>\"If all targets are unhealthy, nobody gets anything.\"</strong> Clients generally get an <strong>HTTP 503</strong> from the load balancer, but an ALB deliberately <strong>fails open</strong> when every target in a group is unhealthy and sends requests to all of them anyway — so seeing traffic reach red targets is a hint that your health check, not your fleet, is misconfigured.</li>\n<li><strong>\"The health check uses my domain name.\"</strong> It requests the target's IP address directly, with the IP as the Host header. Virtual-host configurations that only recognise your domain will fail.</li>\n<li><strong>\"Health check settings live on the load balancer.\"</strong> They live on the <strong>target group</strong>, so every target group can have its own path, interval and matcher — which is exactly what you want when one ALB serves several different applications.</li>\n</ul>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"A health check is the load balancer repeatedly calling a path on each target from every enabled Availability Zone and deciding whether to keep sending it traffic.
