{"title":"What Is Elastic Load Balancing — Why You Need a Load Balancer","tags":["aws","elb","load-balancing","high-availability"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Imagine you have deployed your web application to a single server. It works. People visit your domain, the request lands on that one machine, and the machine answers. That setup has two problems, and both of them will bite you eventually.</p>\n<p style=\"line-height: 1.75\">The first problem is <strong>one point of failure</strong>. If that server crashes, runs out of memory, or the underlying hardware dies, your site is simply down. There is nowhere else for traffic to go. The second problem is a <strong>hard ceiling on traffic</strong>. A single machine has a fixed amount of CPU and memory. Once you saturate it, requests queue up, pages get slow, and then they start timing out. You can buy a bigger machine (this is called scaling <em>up</em>), but there is always a biggest machine, and it is expensive.</p>\n<p style=\"line-height: 1.75\">The obvious fix is to run two servers instead of one. But that immediately raises a new question: when a visitor types your domain into a browser, <em>something</em> has to decide which of the two servers that visitor reaches. And that something must notice when one of the servers has died, so it stops sending people there. That \"something\" is a load balancer.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What a load balancer is, in one sentence</h4>\n<p style=\"line-height: 1.75\">A <strong>load balancer</strong> is a traffic cop that sits in front of your servers: it receives every incoming request and forwards it to one of the healthy servers behind it. Your users only ever talk to the load balancer. They never know, and never need to know, how many servers are behind it or which one answered.</p>\n<p style=\"line-height: 1.75\">In AWS, the service that provides this is called <strong>Elastic Load Balancing (ELB)</strong>. \"Elastic\" is AWS's word for \"grows and shrinks automatically\" — the load balancer itself scales with your traffic without you doing anything. ELB is a <strong>managed service</strong>, which means AWS runs the software and the machines it runs on; you configure behaviour through the console, CLI or an infrastructure-as-code template, and you never patch or log into the load balancer itself.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The four things a load balancer actually buys you</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Distributing load.</strong> Instead of every request hammering one machine, requests are spread across several. Two servers each handling half the traffic are each half as busy, so response times stay low and you have headroom for a spike. This is scaling <em>out</em> (more machines) rather than <em>up</em> (a bigger machine), and it is how essentially every large site works.</li>\n<li><strong>High availability.</strong> The load balancer constantly tests each server behind it with a small repeated request — AWS calls this a <strong>health check</strong>, and it is simply the load balancer asking \"are you still able to answer?\" on a path you choose. A server that stops answering correctly is taken out of rotation, and traffic silently goes to the remaining ones. Because you can place servers in more than one <strong>Availability Zone</strong> — a physically separate data centre in the same AWS region, with its own power and networking — the load balancer can also route around the loss of an entire data centre. A single-server setup has no equivalent: its failure is your outage.</li>\n<li><strong>Scalability.</strong> Adding capacity becomes trivial: launch another server, register it with the load balancer, and it starts receiving traffic within seconds. Removing one is equally easy. This pairs naturally with an <strong>Auto Scaling group</strong> — an AWS feature that watches a metric such as average CPU and automatically launches or terminates servers to match demand. An Auto Scaling group can be attached to a load balancer, and from then on new servers are registered and dying servers are deregistered for you, with no human involved. A shop during a flash sale can go from 2 servers to 20 and back again overnight.</li>\n<li><strong>A single, stable entry point.</strong> Without a load balancer, the address your users reach is the address of a specific server, and that address changes every time you replace the server. With one, there is exactly one name to point <strong>DNS</strong> at — DNS, the Domain Name System, is the internet's phone book that turns a name like <code>shop.example.com</code> into an address a computer can connect to. Your DNS record points at the load balancer once and never changes again, no matter how often the servers behind it are replaced.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why AWS gives you a DNS name, not an IP address</h4>\n<p style=\"line-height: 1.75\">When you create an Application Load Balancer, AWS hands you a hostname such as <code>my-app-1234567890.eu-west-1.elb.amazonaws.com</code>. It does not hand you an IP address. That surprises beginners, but the reason is important: AWS scales the load balancer itself behind the scenes. Under heavy traffic it adds more load balancer nodes, and those nodes have new IP addresses; under light traffic it removes nodes and those addresses go away. The DNS name always resolves to whichever addresses are currently in service.</p>\n<p style=\"line-height: 1.75\">So the classic beginner mistake is to look up the load balancer's IP address today and hardcode it — in a DNS A record, a firewall rule, or a config file. It will work for a while and then break at the worst possible moment when AWS changes the addresses. Always reference the DNS name. If you are using Amazon's own DNS service, <strong>Route 53</strong>, you point your domain at the load balancer with an <strong>alias record</strong>, which is a special record type that tracks the load balancer's addresses automatically and costs nothing to query. If you use another DNS provider, use a <strong>CNAME</strong> record pointing at the load balancer's hostname.</p>\n<p style=\"line-height: 1.75\">One exception worth knowing early: a <strong>Network Load Balancer</strong> can be given fixed, static IP addresses, which is exactly why people use it when a partner's firewall needs a stable IP to allow. An Application Load Balancer cannot; its addresses are always dynamic.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Isn't the load balancer itself a single point of failure?</h4>\n<p style=\"line-height: 1.75\">This is the best question a beginner can ask, and the answer is no. An AWS load balancer is not one box. When you create one, you choose which Availability Zones it should operate in, and AWS places redundant <strong>load balancer nodes</strong> in each of those zones. If a node fails, DNS stops handing out its address and the remaining nodes carry the traffic. If a whole Availability Zone goes dark, the nodes in the other zones keep serving. AWS also scales those nodes up and down for you.</p>\n<p style=\"line-height: 1.75\">The practical rule that follows: always enable at least <strong>two Availability Zones</strong> on a load balancer, and put servers in both. Enabling one zone gives you a load balancer whose fate is tied to a single data centre, which quietly throws away most of the availability you were trying to buy. The load balancer can handle <strong>TLS/HTTPS termination</strong>: it holds your certificate, accepts the encrypted HTTPS connection from the browser, decrypts it, and forwards a plain HTTP request to your servers inside your private network. TLS (Transport Layer Security, the modern name for SSL) is the encryption that puts the padlock in the browser's address bar.</p>\n<p style=\"line-height: 1.75\">Centralising this is a real operational win. Instead of installing and renewing a certificate on every server, you attach one certificate to the load balancer. With <strong>AWS Certificate Manager (ACM)</strong> that certificate is free for use with ELB and renews itself automatically, so the \"our site went down because the certificate expired\" outage largely disappears. Your application servers get simpler too, because they only speak plain HTTP on a private network.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"A load balancer makes my app faster.\"</strong> Not by itself. It adds one extra network hop, so a single request is marginally slower. What it does is stop your app getting slow <em>under load</em>, by spreading work across machines and keeping each one comfortable. Latency for one idle request is not the point; throughput and resilience are.</li>\n<li><strong>\"The load balancer is a new single point of failure.\"</strong> No — it is a managed, redundant service with nodes spread across the Availability Zones you enable.
