{"title":"ALB Built-In Authentication — OIDC and Cognito","tags":["authenticate-oidc","cognito","oidc-flow","zero-trust"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">An Application Load Balancer can require a user to log in before a request ever reaches your application. The listener rule performs a complete <strong>OIDC authorization code flow</strong> on the client's behalf, maintains the session in a cookie, and hands the target a signed set of identity claims. Done well this removes an entire class of authentication bugs from every service behind the load balancer; done carelessly it produces a system that looks authenticated and can be bypassed with a single crafted header. The interesting engineering is in the second half — the trust boundary, the header-spoofing question, and the honest limits of what the ALB will and will not do for you.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The authenticate-oidc action</h4>\n<p style=\"line-height: 1.75\">Authentication is a listener <strong>action</strong>, not a load balancer setting. A rule's action list is ordered, and <code>authenticate-oidc</code> must come before the <code>forward</code> action it protects — the ALB runs authentication first and only forwards once a session exists. It is available only on <strong>HTTPS listeners</strong>, for the obvious reason that the session cookie and the authorization code must not travel in the clear. Configuration fields:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Issuer.</strong> The OIDC issuer identifier, used to identify the provider.</li>\n<li><strong>AuthorizationEndpoint, TokenEndpoint, UserInfoEndpoint.</strong> The three provider URLs. The ALB does not perform discovery for you — you supply these explicitly, which you normally copy from the provider's <code>/.well-known/openid-configuration</code> document.</li>\n<li><strong>ClientId and ClientSecret.</strong> The confidential client registered with your IdP. Because the ALB is a confidential client, it can perform the code-for-token exchange securely. On updates you can pass <code>UseExistingClientSecret</code> so you do not have to resupply the secret.</li>\n<li><strong>Scope.</strong> Defaults to <code>openid</code>; add scopes such as <code>email</code>, <code>profile</code> or <code>groups</code> when you need those claims. What the IdP will actually release depends on its own configuration.</li>\n<li><strong>SessionCookieName.</strong> Defaults to <code>AWSELBAuthSessionCookie</code>.</li>\n<li><strong>SessionTimeout.</strong> Session lifetime in seconds, default seven days (604800), which is also the maximum. When it expires the ALB re-runs the flow.</li>\n<li><strong>OnUnauthenticatedRequest.</strong> <code>authenticate</code> (default), <code>deny</code>, or <code>allow</code> — discussed below.</li>\n<li><strong>AuthenticationRequestExtraParams.</strong> Additional query parameters appended to the authorization request, for provider-specific behaviour such as <code>prompt</code>, <code>login_hint</code>, or a tenant or connection selector.</li>\n</ul>\n<p style=\"line-height: 1.75\">Two prerequisites trip people up. First, the IdP must have <code>https://your-dns-name/oauth2/idpresponse</code> registered as an allowed <strong>redirect URI</strong> — that path is reserved by the ALB and is where the authorization code is delivered. If you serve the application on a custom domain, register that domain's URI, not the load balancer's generated name. Second, the load balancer nodes must be able to <strong>reach the IdP's token and user-info endpoints outbound</strong>. An internet-facing ALB does this through the internet gateway; an <em>internal</em> ALB talking to a public IdP needs a route to the internet, typically a NAT gateway, or an IdP reachable inside the VPC. A rule that silently returns 500s on the callback is very often this.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The flow the ALB performs</h4>\n<div Step 13 is every subsequent request: the ALB decrypts and validates its own session cookie, refreshes the token with the IdP if needed, and forwards. That is why the <strong>first</strong> request of a session carries several extra round trips of latency — a browser redirect to the IdP, the login interaction, the callback, plus two server-to-server calls from the ALB to the token and user-info endpoints — while subsequent requests add only cookie processing. Budget accordingly: the auth handshake is user-perceptible and depends on your IdP's latency and availability, which means <strong>your IdP becomes a hard dependency of your front door</strong>. If the IdP is down, new sessions cannot be established; existing sessions continue until they need a refresh.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The session cookie, and its size limit</h4>\n<p style=\"line-height: 1.75\">The ALB sets a cookie (default <code>AWSELBAuthSessionCookie</code>) whose contents it encrypts and can read back; your application cannot and should not parse it. Because a browser cookie is limited to roughly 4KB, the ALB <strong>shards</strong> the session across numbered cookies — <code>AWSELBAuthSessionCookie-0</code>, <code>-1</code> and so on — when the payload exceeds that. This is the origin of a very common production failure: an enterprise IdP that releases a large claim set, most often a long list of group memberships, blows the budget. AWS documents a hard limit on the size of user claims the load balancer can pass; when the claims returned by the IdP exceed it, the load balancer returns an <strong>HTTP 500</strong> rather than a partial session. The symptom is memorable: authentication works perfectly for ordinary users and fails with a 500 for exactly those users who belong to many groups — often the administrators doing the testing.</p>\n<p style=\"line-height: 1.75\">The fixes are all on the IdP side: trim the claims released to this client, replace a full group list with a small number of application-specific roles, use a scope that omits the heavy claim, or move authorization data out of the token entirely and have the application look up entitlements by subject. Shrinking claims is also good hygiene — a token is a poor place to carry a large, frequently changing authorization model.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What the target receives</h4>\n<p style=\"line-height: 1.75\">On every authenticated request the ALB injects three headers:</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Header</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Contents</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">How to use it</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><code>x-amzn-oidc-data</code></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">A JWT containing the user claims, signed by the ALB with <strong>ES256</strong></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">This is the one to trust, after verifying the signature. It is <em>not</em> a verified assertion on its own; derive identity from the verified <code>x-amzn-oidc-data</code> JWT.</td></tr>\n</tbody>\n</table>\n</div>\n<p style=\"line-height: 1.75\">The whole point is that your application never implements OIDC: no redirect handling, no code exchange, no client secret in your code, no token refresh logic, no per-service session store. It reads a signed JWT out of a header. That is a genuine and large reduction in the amount of security-critical code you own, and it is uniform across every service behind the listener regardless of language or framework.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">authenticate-cognito</h4>\n<p style=\"line-height: 1.75\">The managed variant. Instead of three endpoint URLs you supply <code>UserPoolArn</code>, <code>UserPoolClientId</code> and <code>UserPoolDomain</code>; the rest of the configuration — scope, session cookie name, session timeout, on-unauthenticated-request, extra params — is the same. Cognito provides the <strong>hosted UI</strong>, so you get a working login, sign-up, forgot-password and MFA experience without building one, and the user pool acts as an <strong>identity broker</strong>: it federates to social providers (Google, Facebook, Apple, Amazon) and to enterprise providers over SAML 2.0 or OIDC, presenting one consistent interface to the ALB. That brokering is the main reason to choose Cognito over direct <code>authenticate-oidc</code> — you configure the ALB once and add or change identity providers in the user pool. The claim set the target receives is analogous, with Cognito's claims in the signed JWT and <code>cognito:groups</code> available when you have configured groups. The trade-offs are the usual managed-service ones: hosted UI customisation is limited, Cognito behaviour and quotas are its own to learn, and you are coupling to an AWS-specific identity layer. If your organisation already has an IdP that everyone authenticates against, <code>authenticate-oidc</code> straight to it is simpler; if you are serving external consumers and want federation plus a user directory without running one, Cognito earns its place.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">OnUnauthenticatedRequest: authenticate, deny, allow</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>authenticate</strong> (default). Begin the flow — issue the 302 to the IdP. Correct for browser-facing pages, where a redirect to login is exactly the desired user experience.</li>\n<li><strong>deny</strong>. Return HTTP 401 immediately. Correct for API endpoints consumed programmatically, where a 302 to an HTML login page is useless and actively confusing: an XHR or a CLI client receives a redirect it cannot follow meaningfully, and you get mystifying CORS failures because the browser attempts a cross-origin navigation to the IdP. A crisp 401 lets the client do something sensible.</li>\n<li><strong>allow</strong>. Forward the request without authenticating, and <em>without</em> the identity headers. This is the right choice for endpoints that must stay public on an otherwise protected listener: health check paths (a health check cannot complete an OIDC flow, so a protected health path will mark every target unhealthy), webhook receivers that authenticate by signature rather than by session, unauthenticated marketing or status pages, and well-known paths such as ACME challenges. The crucial engineering consequence: with <code>allow</code>, the absence of identity headers is a legitimate state, so your application must treat the presence of a verified <code>x-amzn-oidc-data</code> as the signal of authentication and must not assume every request it sees has been authenticated. Structure it as separate rules — a high-priority rule with <code>allow</code> for the public paths, and a lower-priority catch-all with <code>authenticate</code> — rather than one rule doing double duty.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The trust boundary: why headers alone are not enough</h4>\n<p style=\"line-height: 1.75\">This is the question that separates candidates. The identity headers are injected by the load balancer, so their trustworthiness is exactly as strong as the guarantee that <strong>every</strong> request reaching the target came through that load balancer, on a rule that authenticated it. Two independent controls are required.</p>\n<p style=\"line-height: 1.75\"><strong>Network control.</strong> The target's security group must accept traffic only from the load balancer's security group, on the target port — never <code>0.0.0.0/0</code>, never the VPC CIDR. If anything else in the VPC can open a socket to the target port, a compromised neighbour, a misdeployed debug container, or an SSRF vulnerability elsewhere can send a request with a hand-written <code>x-amzn-oidc-identity: ceo@example.com</code> and your application will believe it. This is the single most important configuration in the whole feature, and it is why \"the load balancer authenticates\" is never a complete answer. For IP-mode targets in ECS or EKS, the same rule applies to the task or pod security group. Private subnets with no inbound internet path are a sensible additional layer.</p>\n<p style=\"line-height: 1.75\"><strong>Cryptographic control.</strong> The application should <strong>verify the ES256 signature</strong> on <code>x-amzn-oidc-data</code> against the ALB's public key for its region, check the expiry, and derive identity only from the verified payload — never from <code>x-amzn-oidc-identity</code>, which is a bare string. Signature verification is what makes the network control a defence in depth rather than the sole defence: even if someone reaches the target directly, they cannot forge a signature they do not have the key for. Cache the public key by <code>kid</code> so you are not fetching it per request, and fail closed when verification fails. As a further layer, some teams strip any client-supplied <code>x-amzn-oidc-*</code> headers at the edge and enable the ALB attribute that drops invalid header fields; but the durable answer is the two controls above, applied together.</p>\n<p style=\"line-height: 1.75\"><strong>Sessions and logout.</strong> Session lifetime is <code>SessionTimeout</code>, up to seven days; shorten it substantially for anything sensitive, because a long-lived session cookie is a long-lived credential and there is no server-side session revocation list. Logout requires cooperation: the ALB has no logout action, so your application must expire the session cookie (setting <code>AWSELBAuthSessionCookie</code> and its shards to an empty value with a past expiry) <em>and</em> redirect the user to the IdP's logout endpoint — Cognito exposes <code>/logout</code> on the user pool domain — otherwise the IdP session immediately re-establishes the ALB session and the user appears never to have logged out. Understand also that disabling a user at the IdP does not terminate an existing ALB session until the session or token needs refreshing, which is the strongest argument for short session timeouts.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Honest limits, and the comparison</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Authentication, not authorization.</strong> The ALB answers \"who is this?\" and nothing else. There is no per-path role check, no scope enforcement, no policy engine. All authorization stays in your application (or in a policy service such as Verified Permissions). You can approximate coarse separation with different rules for different paths, but you cannot express \"editors may PUT here\".</li>\n<li><strong>Claims size.</strong> Large claim sets exceed the documented limit and produce HTTP 500. Trim claims at the IdP.</li>\n<li><strong>First-request latency.</strong> Multiple redirects plus two ALB-to-IdP calls. Unavoidable, and it makes the IdP a front-door dependency.</li>\n<li><strong>Browser-shaped by design.</strong> The flow is a redirect flow, so it fits browsers and breaks non-browser clients. There is no client-credentials or machine-to-machine support: a service calling your API cannot authenticate this way. Mixed browser-and-API surfaces need <code>deny</code> on API rules plus token validation in the application, or a separate listener or load balancer for machine traffic.</li>\n<li><strong>HTTPS only, one action per rule.</strong> No authentication on HTTP listeners, and a rule has a single authenticate action, so you cannot offer a choice of providers within one rule — use separate rules, or federate through Cognito.</li>\n<li><strong>Operational coupling.</strong> Rotating the client secret is a listener modification; the reserved <code>/oauth2/idpresponse</code> path must be registered per domain; and troubleshooting spans the ALB, the IdP and the application.</li>\n</ul>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; It is the wrong call for public APIs, machine-to-machine traffic, and anything needing fine-grained or step-up authorization.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Production scenario: protecting an internal admin tool</h4>\n<p style=\"line-height: 1.75\">A five-year-old Django admin console runs on two EC2 instances. It has its own username-and-password login, no MFA, and shared accounts. Security wants corporate SSO with MFA within the week, and nobody wants to touch the Django code.</p>\n<p style=\"line-height: 1.75\"><strong>Design.</strong> An internal ALB in private subnets, reachable over the corporate VPN or through a Client VPN endpoint, with an HTTPS listener carrying an ACM certificate for <code>admin.corp.example.com</code>. Register <code>https://admin.corp.example.com/oauth2/idpresponse</code> as a redirect URI with the corporate IdP and create a confidential client. Because the ALB is internal and the IdP is on the public internet, ensure the ALB subnets route outbound through a <strong>NAT gateway</strong> so the token and user-info calls succeed — the classic cause of a 500 on the callback here.</p>\n<p style=\"line-height: 1.75\"><strong>Rules.</strong> Priority 10: path <code>/health</code>, action <code>authenticate-oidc</code> with <code>OnUnauthenticatedRequest = allow</code>, then forward — because a target health check cannot complete a login flow, and protecting the health path would mark both instances unhealthy and take the tool down.
