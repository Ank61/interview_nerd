A <strong>WebSocket</strong> or <strong>server-sent events</strong> stream is one HTTP request that never completes, so it will simply be cut at the end of the draining window no matter how long that window is — setting the delay to 3600&nbsp;s just delays the pain and pins old capacity for an hour. The correct design is application-level: the server watches for a shutdown signal and sends a <em>close/reconnect</em> frame or an SSE retry directive, letting clients reconnect through the load balancer onto new capacity, with jitter so the whole fleet does not reconnect simultaneously. <strong>Long polling</strong> should use a poll timeout meaningfully shorter than the deregistration delay so a poll naturally completes inside the window. <strong>Large uploads</strong> are the opposite problem: they are genuinely one long request, so either allow a deregistration delay long enough for the p99.9 upload, or move uploads to <strong>S3 presigned URLs</strong> so they never traverse the load balancer and deploys stop being coupled to upload duration — the better architectural answer.</p>\n<p style=\"line-height: 1.75\"><strong>ALB versus NLB draining.</strong> The ALB is request-aware: it knows where one HTTP request ends and can stop at a clean boundary, so draining is genuinely graceful. The NLB operates on flows; historically a deregistered NLB target kept receiving packets for existing flows until the deregistration delay elapsed and then the flow was simply dropped. The NLB target group attribute <code>deregistration_delay.connection_termination.enabled</code> controls whether connections are forcibly terminated at the end of the delay (when disabled, established flows can persist). The practical implication is that with an NLB you carry <strong>more of the graceful-shutdown burden in the application</strong>: it must notice the drain and actively close its own connections at a safe point, because the NLB cannot pick a protocol-safe boundary for you.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Application's Obligations</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Handle SIGTERM as \"stop accepting, finish what you have\".</strong> The default behaviour of most runtimes is to exit immediately, which kills in-flight requests. Correct handling: stop the listener (or call the framework's graceful close), let in-flight handlers complete, drain background queues that hold user-visible work, flush metrics and logs, close database and cache pools, then exit 0. Never call a hard exit on the first signal; keep a hard-exit timer as a last resort so a wedged handler cannot hold the process forever.</li>\n<li><strong>Fail the health check <em>before</em> shutdown begins.</strong> This is the highest-leverage trick and it is widely skipped. Have the process flip an internal flag on SIGTERM (or on a pre-drain signal) that makes <code>/healthz</code> return 503 while normal traffic is still served correctly. After <code>unhealthy_threshold</code> &times; <code>interval</code> — say 2 &times; 10&nbsp;s — the ALB stops choosing this target on its own, which means new requests stop arriving <strong>before</strong> the deregistration call and long before the process dies. This costs one flag and one code path and eliminates the entire class of \"request arrived just as we started shutting down\" errors. In Kubernetes the same effect is achieved by the <code>preStop</code> sleep, because Endpoints removal happens at the same moment.</li>\n<li><strong>Keep the keep-alive relationship right.</strong> The ALB maintains persistent connections to targets and reuses them. If the target's idle/keep-alive timeout is <em>shorter</em> than the ALB's idle timeout, the target will sometimes close a connection at the exact instant the ALB is writing a new request onto it; the ALB sees a reset on a request it cannot safely retry and returns a <strong>502</strong>. These are the classic sporadic, unexplained 502s at a low steady rate. Node.js is the canonical offender (<code>server.keepAliveTimeout</code> defaults to 5&nbsp;s, and <code>headersTimeout</code> must exceed it); nginx <code>keepalive_timeout</code> and Go's <code>ReadTimeout</code>/<code>IdleTimeout</code> need the same treatment. Rule: application keep-alive &gt; ALB idle timeout, always.</li>\n<li><strong>Be idempotent where you can.</strong> Deploys inevitably interrupt something. Idempotency keys on mutating endpoints turn an interrupted request from a correctness incident into a client retry.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Auto Scaling: Lifecycle Hooks, Instance Refresh, Topologies</h4>\n<p style=\"line-height: 1.75\"><strong>Lifecycle hooks</strong> pause an instance in <code>Terminating:Wait</code> so you can do pre-termination work: verify the ALB has finished draining, upload final logs, deregister from service discovery, hand off leadership or in-memory state, snapshot a cache. The hook has a heartbeat timeout (default 3600&nbsp;s, maximum 7200&nbsp;s) which you extend with <code>record-lifecycle-action-heartbeat</code> and end early with <code>complete-lifecycle-action</code>. A common pattern is an EventBridge rule on the lifecycle notification invoking a Lambda, or a systemd unit on the instance that polls its own lifecycle state. The <code>Pending:Wait</code> hook is the symmetric tool for warming an instance — fetching a cache snapshot or pre-compiling — before it is registered as healthy. The controls that matter: <code>MinHealthyPercentage</code> (use 100 with extra capacity headroom for a latency-sensitive service, or 90 for cost), <code>MaxHealthyPercentage</code> to allow surging above desired capacity, <code>InstanceWarmup</code> so the refresh waits for a real warm-up rather than just for the health check, <code>CheckpointPercentages</code> with <code>CheckpointDelay</code> to bake at 10% then 50% then 100% while you watch alarms, and <code>SkipMatching</code> so instances already on the desired configuration are left alone. Cheapest, no extra infrastructure, but the fleet is mixed-version during the deploy — so the change must be backward compatible in both directions (schema, cache keys, message formats). Rollback means another roll, so it is slow.</li>\n<li><strong>Blue/green with weighted target groups.</strong> Two target groups behind one listener rule using a weighted forward action. Shift 1% &rarr; 10% &rarr; 50% &rarr; 100%, watching metrics; rollback is a single weight change that takes effect in seconds. This is the strongest general answer and is what CodeDeploy's ECS blue/green and canary configurations automate.</li>\n<li><strong>Immutable.</strong> Build an entirely new ASG or service, register it to a new target group, shift traffic, then delete the old.
