{"title":"Listeners, HTTPS, and TLS Termination","tags":["elb","https","tls","acm"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">You have deployed an app on a single server before, so you already know the shape of the problem: something has to be listening on a port before a browser can talk to it. A load balancer is no different. The piece of a load balancer that does the listening is called a <strong>listener</strong>, and until you create one, your load balancer has a DNS name but answers nothing at all.</p>\n<p style=\"line-height: 1.75\">This topic covers what a listener is, how HTTPS works in plain words, what it means to let the load balancer handle the encryption for you (the phrase you will hear is <strong>TLS termination</strong>), where the certificates come from, and how one load balancer can serve many different domain names at once.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What a listener actually is</h4>\n<p style=\"line-height: 1.75\">A <strong>listener</strong> is a process on the load balancer that watches exactly one <em>port</em> and one <em>protocol</em>, and holds the rules that decide what to do with whatever arrives there. A port is just a numbered door on a machine (port 80 is the traditional door for plain web traffic, port 443 the traditional door for encrypted web traffic). A protocol is the language spoken through that door — HTTP for plain web requests, HTTPS for encrypted ones.</p>\n<p style=\"line-height: 1.75\">So a listener is best read as a sentence: <em>&quot;on port 443, speaking HTTPS, using this certificate, apply these rules.&quot;</em> Three things always travel together:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Protocol and port.</strong> What door to watch and what language to expect. One listener per port — you cannot have two listeners both on 443.</li>\n<li><strong>A default action.</strong> What to do with a request that matches none of your rules. Every listener must have one; without it there is no answer to give.</li>\n<li><strong>Rules (optional, Application Load Balancer only).</strong> Extra conditions like &quot;paths starting with /api go to the API servers&quot;. These are covered in depth in the routing topic.</li>\n</ul>\n<p style=\"line-height: 1.75\">The near-universal beginner setup is <strong>two listeners</strong>: one on port 80 for plain HTTP and one on port 443 for HTTPS. The reason for keeping port 80 at all is that people type <code>example.com</code> into a browser without typing <code>https://</code> first, and the browser tries port 80. If nothing is listening there they get a connection error rather than your site. AWS itself mixes them (the API field is called <code>SslPolicy</code> even though it configures TLS versions). Treat them as synonyms in conversation, but know that real SSL versions are long dead and insecure.</p>\n<p style=\"line-height: 1.75\">TLS gives you three things at once, and it is worth naming them separately because beginners usually only think of the first:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Confidentiality.</strong> Nobody sitting between the browser and your server — the coffee shop Wi-Fi, the internet provider, anyone tapping a cable — can read the request or the response. Without it, a login form posts a password in plain readable text across the internet.</li>\n<li><strong>Integrity.</strong> Nobody in the middle can quietly change the bytes. Without it, an intermediary could inject advertisements or malicious JavaScript into your pages.</li>\n<li><strong>Authenticity.</strong> The browser can verify it is really talking to <code>example.com</code> and not an impostor. This is what the certificate is for.</li>\n</ul>\n<p style=\"line-height: 1.75\">A <strong>TLS certificate</strong> is a small signed file that says &quot;the holder of this file is the legitimate operator of example.com&quot;, signed by a <strong>certificate authority (CA)</strong> — an organisation that browsers already trust, whose job is to verify that claim before signing. Your browser ships with a built-in list of trusted CAs. When the padlock appears in the address bar, it means the certificate the server presented was signed by a CA on that list, covers the host name that was typed, and has not expired. When any of those fail, you get the full-page red warning instead.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">TLS termination at the load balancer</h4>\n<p style=\"line-height: 1.75\"><strong>TLS termination</strong> means the encrypted connection <em>ends</em> at the load balancer. The load balancer holds the certificate and the matching private key, performs the handshake with the browser, decrypts the request, reads it, decides where it should go, and then usually forwards it to your server over <strong>plain HTTP</strong> inside your private network. It never leaves AWS and never crosses the public internet — it travels inside your <strong>VPC (Virtual Private Cloud)</strong>, which is your own private, isolated network inside AWS. For the great majority of applications that is an accepted and normal risk posture. The load balancer still terminates the browser's TLS connection (it must, in order to route), but it then opens a <em>second</em> TLS connection to your target and re-encrypts the request. You configure this by setting the <strong>target group</strong> protocol to HTTPS instead of HTTP. AWS documents this explicitly. The practical upshot is that you can put a cheap self-signed certificate on your instances purely to get encryption on the wire, without paying for or managing trusted certificates internally. The honest trade-off is that this gets you confidentiality but not authenticity on that inner hop — the load balancer is not checking who it is talking to, it is relying on the fact that the target is one you registered inside your own private network.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">AWS Certificate Manager (ACM)</h4>\n<p style=\"line-height: 1.75\"><strong>AWS Certificate Manager (ACM)</strong> is an AWS service that issues and automatically renews TLS certificates, and public certificates used with AWS services like Elastic Load Balancing, CloudFront and API Gateway are <strong>free</strong>. You request a certificate for your domain, ACM validates that you control the domain, and from then on ACM renews it for you before it expires.</p>\n<p style=\"line-height: 1.75\">Compare that to the traditional path. You buy a certificate from a vendor, generate a private key and a signing request, complete a validation process, download files, install them on each server, and then put a reminder in a calendar for eleven months' time. Public certificates now typically last around a year or less, and the industry is moving to much shorter lifetimes, so this becomes a recurring chore. Expired certificates are one of the most common and most embarrassing production outages there is: the site is running perfectly and every visitor sees a security warning. ACM removes that entire failure mode for load-balancer certificates, because renewal is automatic and the listener picks up the renewed certificate with no action from you.</p>\n<p style=\"line-height: 1.75\"><strong>Domain validation</strong> at a high level: ACM has to confirm you really control the domain before it will issue a certificate for it. You choose one of two methods.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>DNS validation (recommended).</strong> ACM gives you a special CNAME record to add to your domain's DNS. Being able to publish DNS records for a domain proves control of it. Crucially, if you leave that record in place, ACM can re-validate silently at renewal time, so renewal is fully hands-off. If your domain is in Route 53 in the same account, the console can create the record for you in one click.</li>\n<li><strong>Email validation.</strong> ACM emails the addresses registered for the domain and you click a link. This works, but every renewal needs a human to click again, which defeats the main benefit.</li>\n</ul>\n<p style=\"line-height: 1.75\">Two operational details worth remembering. First, ACM certificates are <strong>regional</strong>: a certificate must live in the same AWS region as the load balancer that uses it (the exception is CloudFront, which requires the certificate in the us-east-1 region). Second, you can request a certificate covering several names at once, including a <strong>wildcard</strong> like <code>*.example.com</code>, which matches any single label in that position — so it covers <code>api.example.com</code> and <code>app.example.com</code>, but not the bare <code>example.com</code> and not <code>a.b.example.com</code>. Request both <code>example.com</code> and <code>*.example.com</code> on one certificate to cover the usual case.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Many certificates on one listener, and SNI</h4>\n<p style=\"line-height: 1.75\">One HTTPS listener can hold <strong>many certificates</strong> — one designated as the default, plus a list of additional ones. This is what lets a single load balancer serve <code>shop.example.com</code>, <code>blog.example.com</code> and an entirely unrelated <code>partner-brand.net</code>, each with its own certificate.</p>\n<p style=\"line-height: 1.75\">The mechanism is <strong>SNI (Server Name Indication)</strong>. So without help, the server faces a chicken-and-egg problem: it must pick a certificate before it knows which site is being asked for. SNI fixes it by having the client announce the host name it wants, in plain text, in the opening handshake message.
