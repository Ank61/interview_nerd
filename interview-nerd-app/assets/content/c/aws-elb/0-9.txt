{"title":"Security Groups and Network Access for Load Balancers","tags":["elb","security-groups","network-acl","waf"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">When you put a load balancer in front of your application, you suddenly have two things that need firewall rules instead of one: the load balancer itself, and the servers behind it. Getting those two sets of rules right is the single most common place beginners get stuck, and it produces two very recognisable symptoms — either the site does not load at all, or the load balancer reports every server as <strong>unhealthy</strong>. This topic walks through the exact pattern AWS expects, and why it is designed that way.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What a security group actually is</h4>\n<p style=\"line-height: 1.75\">A <strong>security group</strong> is a virtual firewall that you attach to an AWS resource — an EC2 virtual server, a load balancer, a database. It is a list of rules describing what network traffic is allowed <em>in</em> (inbound rules) and what is allowed <em>out</em> (outbound rules). Everything not explicitly allowed is denied. There is no \"deny\" rule type at all; a security group is a pure allow-list.</p>\n<p style=\"line-height: 1.75\">Two properties make security groups easier than traditional firewalls once you see them:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>They are stateful.</strong> If you allow a request in, the reply is automatically allowed back out. You never write a matching outbound rule for the response. (\"Stateful\" just means the firewall remembers connections it has already approved.)</li>\n<li><strong>The source of a rule can be another security group.</strong> Instead of writing an IP address in the \"source\" field, you can write the ID of another security group, which means \"any resource that has that security group attached\". This is the feature the whole load balancer pattern is built on.</li>\n</ul>\n<p style=\"line-height: 1.75\">A rule has four parts: protocol (usually TCP), port (or port range), source (for inbound) or destination (for outbound), and an optional description. A source is written either as a <strong>CIDR block</strong> — an IP range in slash notation, like <code>203.0.113.0/24</code> — or as a security group ID like <code>sg-0ab12cd34ef56</code>. The special CIDR <code>0.0.0.0/0</code> means \"every IPv4 address on the internet\", and <code>::/0</code> is its IPv6 equivalent.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The two-security-group pattern</h4>\n<p style=\"line-height: 1.75\">The pattern AWS documentation assumes, and the one you should default to, uses exactly two security groups: one for the load balancer, one for the application servers. Inbound: allow TCP port 80 (plain <strong>HTTP</strong>, the unencrypted web protocol) and TCP port 443 (<strong>HTTPS</strong>, the encrypted one) from <code>0.0.0.0/0</code>. This one <em>is</em> supposed to be open to the world, because the whole point of a public load balancer is that anyone on the internet can reach it.</li>\n<li><strong>Step 2 — create the application servers' security group.</strong> Call it <code>sg-app</code>. Inbound: allow TCP on your application port (say 8080) with the <strong>source set to <code>sg-alb</code></strong>, not an IP range. Add no other inbound rules.</li>\n<li><strong>Step 3 — attach them.</strong> <code>sg-alb</code> goes on the load balancer, <code>sg-app</code> goes on every instance (usually via the launch template your Auto Scaling group uses, so new instances get it automatically).</li>\n<li><strong>Step 4 — outbound.</strong> Make sure <code>sg-alb</code> is allowed <em>out</em> to <code>sg-app</code> on the application port. The default outbound rule on a new security group is \"allow everything out\", which already covers this, but if you have tightened outbound rules you must add it back or health checks silently fail.</li>\n</ul>\n<p style=\"line-height: 1.75\">The payoff is real isolation. Because <code>sg-app</code> has no rule allowing the internet, an attacker who somehow learns your instance's private or even public address still cannot open a connection to it. Traffic physically cannot arrive except through the load balancer. Put the instances in <strong>private subnets</strong> too — subnets whose route table has no path to the internet gateway — and they have no public address at all.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why you reference the security group, not IP addresses</h4>\n<p style=\"line-height: 1.75\">This is the detail worth internalising. An Application Load Balancer is not one machine. AWS runs a fleet of nodes for it, one or more in each Availability Zone you enabled, and that fleet <strong>scales up and down and gets replaced</strong> as traffic changes. The private IP addresses those nodes use come and go without warning and without notifying you.</p>\n<p style=\"line-height: 1.75\">So if you write today's node addresses into <code>sg-app</code> as a CIDR range, your application keeps working until the day AWS replaces a node — and then a portion of requests start timing out and targets start failing health checks, with no configuration change on your side to blame. Referencing <code>sg-alb</code> as the source sidesteps this entirely: the rule means \"whoever currently has that security group attached\", so it follows the fleet automatically. There is no maintenance and no race.</p>\n<p style=\"line-height: 1.75\">The same logic is why you never hardcode the load balancer's public IP addresses in DNS or client configuration. You always use its <strong>DNS name</strong> — the hostname AWS gives you, which resolves to whatever addresses are current.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The health check port rule — the classic gotcha</h4>\n<p style=\"line-height: 1.75\">A <strong>health check</strong> is a small request the load balancer sends to each target on a schedule to decide whether that target is fit to receive traffic. By default it uses the same port the traffic uses, but a target group has a <code>HealthCheckPort</code> setting, and plenty of applications expose health on a separate admin port — Spring Boot Actuator on 8081, a metrics sidecar on 9090, and so on.</p>\n<p style=\"line-height: 1.75\">If your health check port differs from your traffic port, <code>sg-app</code> needs <strong>two</strong> inbound rules from <code>sg-alb</code>: one for the traffic port and one for the health check port. Miss the second and you get the most confusing failure mode in ELB: every target shows as unhealthy with the reason \"Health checks failed with these codes: Request timed out\", the load balancer returns HTTP 503 to users, and yet you can curl the health endpoint perfectly from inside the instance. The application is fine — the packet is simply being dropped at the firewall.</p>\n<p style=\"line-height: 1.75\">Diagnostic habit: when targets are unhealthy, check in this order — (1) is there an inbound rule from <code>sg-alb</code> covering the health check port, (2) does the health check path return a 2xx status code, (3) is the application actually listening on that port and bound to all interfaces rather than just <code>127.0.0.1</code>.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Network Load Balancer difference</h4>\n<p style=\"line-height: 1.75\">A <strong>Network Load Balancer (NLB)</strong> works at the connection level rather than the HTTP level, and it behaves differently here in two ways that catch people out.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Client IP preservation.</strong> When targets are registered by instance ID, an NLB by default forwards the connection with the <em>original client's</em> source IP address intact, rather than replacing it with its own. That is useful — your application logs see real client addresses — but it means the target's security group must allow the <strong>client IP ranges</strong>, not the load balancer. For an internet-facing NLB that often means allowing <code>0.0.0.0/0</code> on the traffic port, which feels wrong after learning the ALB pattern but is simply what preserved client IPs require. You can turn the behaviour off with the target group attribute <code>preserve_client_ip.enabled=false</code>, after which the source becomes the NLB node's private address and you allow the subnet CIDRs instead. Health checks always come from the NLB node addresses, so allow the VPC CIDR (or the subnet ranges) for the health check port.</li>\n<li><strong>Security groups on the NLB are newer and optional.</strong> For years NLBs could not have a security group at all — that is precisely why this trips people up. Today you <em>can</em> attach one, but only <strong>when you create the load balancer</strong>; you cannot add a security group to an NLB that was created without one. So decide up front. There is also a setting for whether the NLB's security group is evaluated for traffic that arrives via PrivateLink or is routed to the NLB, exposed as <code>enforce_security_group_inbound_rules_on_private_link_traffic</code>.</li>\n</ul>\n<p style=\"line-height: 1.75\">Practical takeaway: with an ALB, the target security group references the load balancer. With an NLB preserving client IPs, it references the clients. Knowing which one you are running tells you which rule to write.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Network ACLs — the subnet-level layer</h4>\n<p style=\"line-height: 1.75\">A <strong>network ACL (NACL)</strong> is a second, coarser firewall that sits on a <em>subnet</em> rather than on an individual resource. Every resource in that subnet is subject to it. Two differences matter: NACLs support explicit <strong>deny</strong> rules, and they are <strong>stateless</strong> — the reply traffic is not automatically allowed, so you must permit the ephemeral return port range (typically 1024-65535) outbound as well as the request inbound.</p>\n<p style=\"line-height: 1.75\">The default NACL that comes with a VPC allows all traffic in both directions, so most people never touch it, and that is fine. Use security groups as your primary control. Reach for a NACL only when you need a blanket subnet-wide block — for example denying one abusive IP range at the edge of a subnet. If your security groups look correct and traffic still does not flow, a customised NACL missing its return-traffic rule is the usual culprit.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">AWS WAF on an ALB</h4>\n<p style=\"line-height: 1.75\"><strong>AWS WAF (Web Application Firewall)</strong> is a service that inspects the <em>content</em> of HTTP requests — the URL path, headers, query string, body, the source country — and allows, blocks, counts or rate-limits them based on rules you choose. Security groups only see addresses and ports; WAF reads the request itself. That is the difference in one sentence.</p>\n<p style=\"line-height: 1.75\">You use it by creating a <strong>web ACL</strong> (a rule set) and associating it with your load balancer. Typical contents: an AWS-managed rule group for common exploits such as SQL injection and cross-site scripting, a managed list of known-bad IP reputation ranges, a rate-based rule that blocks any single IP sending more than N requests in five minutes, and perhaps a geographic restriction. A good habit is to deploy new rules in <strong>Count</strong> mode first so you can see what they <em>would</em> block before you let them block real users.</p>\n<p style=\"line-height: 1.75\"><strong>WAF attaches to an Application Load Balancer, not to a Network Load Balancer.</strong> This follows directly from what each device understands: WAF rules are about HTTP, and an NLB does not parse HTTP. WAF can also attach to CloudFront, API Gateway, AppSync, Cognito user pools and App Runner. If you need HTTP inspection in front of an NLB, the usual answer is to put CloudFront (with WAF) in front, or use an ALB instead.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">AWS Shield — DDoS protection, at orientation level</h4>\n<p style=\"line-height: 1.75\">A <strong>DDoS (distributed denial of service)</strong> attack tries to take you offline by flooding you with traffic from many machines at once. <strong>AWS Shield Standard</strong> is on for every AWS customer at no extra cost and automatically absorbs common network-layer floods (SYN floods, UDP reflection) against load balancers, CloudFront and Route 53. You do not configure it.</p>\n<p style=\"line-height: 1.75\"><strong>AWS Shield Advanced</strong> is a paid subscription adding attack visibility and reporting, 24/7 access to the AWS Shield Response Team, automatic application-layer mitigations, and billing protection that credits scaling charges caused by an attack. For a beginner the right mental model is: Shield Standard is your free baseline against volumetric floods, WAF is your tool against application-layer abuse, and Shield Advanced is what large or high-profile workloads add on top.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Internal load balancers and private-only architectures</h4>\n<p style=\"line-height: 1.75\">Setting a load balancer's <strong>scheme</strong> to <code>internal</code> instead of <code>internet-facing</code> means its DNS name resolves only to private addresses inside your VPC. Nothing on the internet can reach it, regardless of security groups. This is what you use for service-to-service traffic — an internal ALB in front of your orders service, called by your checkout service — and for internal tools like an admin dashboard.</p>\n<p style=\"line-height: 1.75\">The security group pattern stays the same, only the source changes. For an internal tool, <code>sg-alb-internal</code> allows inbound 443 from your office or VPN CIDR range (for example <code>198.51.100.0/24</code>) rather than <code>0.0.0.0/0</code>. For a service-to-service call, it allows inbound from the calling service's own security group — the same group-referencing trick, one layer up. To share an internal load balancer with another VPC or another AWS account without any internet path, you front an NLB with <strong>AWS PrivateLink</strong> (an endpoint service), which gives consumers a private endpoint in their own VPC.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"I should allow 0.0.0.0/0 on my app servers so the load balancer can reach them.\"</strong> No. The load balancer's nodes sit inside your VPC and carry <code>sg-alb</code>, so referencing that group is sufficient and far safer. Opening the app port to the world defeats the entire point of hiding your servers behind a load balancer.</li>\n<li><strong>\"The load balancer bypasses security groups.\"</strong> It does not. Traffic from the load balancer to a target is evaluated against the target's security group like any other traffic. The reason the group-reference rule is needed at all is that the rules genuinely are enforced.</li>\n<li><strong>\"Health checks use the same port as traffic, so I do not need an extra rule.\"</strong> Only true if you left the health check port at the default. The moment you point health checks at a different port, that port needs its own inbound rule, and forgetting it is the number one cause of \"all targets unhealthy\".</li>\n<li><strong>\"WAF works with any load balancer type.\"</strong> WAF attaches to an ALB (and CloudFront, API Gateway, AppSync, Cognito, App Runner) but not to an NLB, because an NLB does not inspect HTTP.</li>\n<li><strong>\"An internal load balancer does not need security groups.\"</strong> It does. Internal only removes the internet path; anything inside your VPC or connected networks can still reach it unless the security group says otherwise.</li>\n<li><strong>\"A network ACL and a security group are the same thing.\"</strong> A NACL is per-subnet, supports deny rules, and is stateless, so it needs explicit return-traffic rules. A security group is per-resource, allow-only, and stateful.</li>\n<li><strong>\"Shield Standard needs to be enabled.\"</strong> It is already on for every account and every load balancer, free of charge.
