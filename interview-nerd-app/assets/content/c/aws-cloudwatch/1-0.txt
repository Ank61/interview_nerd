A metric is a pre-aggregated counter you alarm on and group by; a log line is a high-cardinality record you search after the fact. If an attribute is something you would put on the X axis of a dashboard or in an alarm's dimension filter, it is a dimension. If it is something you would only ever use to find a specific failing request during an investigation, it is a log field.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Belongs as a dimension.</strong> Environment, service name, Region, Availability Zone, instance type, API operation, coarse status class (2xx/4xx/5xx), queue name, table name, deployment stage. All bounded, all stable, all things you page on or group by.</li>\n<li><strong>Belongs in logs.</strong> Request id, trace id, user id, account id, session id, full URL path with embedded identifiers, SQL statement, error message string, IP address, user agent. Unbounded or effectively unbounded.</li>\n<li><strong>The grey zone.</strong> Customer tier, feature flag variant, and shard id are bounded today but can grow. Treat them as dimensions only if someone will alarm on them per-value; otherwise they are log fields with an optional aggregate metric.</li>\n<li><strong>Status codes.</strong> Prefer a small class dimension over the exact numeric code. You almost never page on 418 specifically; you page on the 5xx rate.</li>\n<li><strong>Guardrails.</strong> Never build a dimension value by string-concatenating a user-supplied value. Put an allowlist in the metrics wrapper library so a new dimension value must be a compile-time constant or come from a fixed enum.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Aggregation Strategy: Three Levers</h4>\n<p style=\"line-height: 1.75\"><strong>Pre-aggregate in the application.</strong> Do not call PutMetricData once per request. Accumulate in-process for a flush interval and publish a rolled-up value. This cuts API calls (and PutMetricData request charges) by orders of magnitude and is the difference between a metrics client that costs nothing and one that becomes a latency source in the request path.</p>\n<p style=\"line-height: 1.75\"><strong>Statistic sets.</strong> PutMetricData accepts <code>StatisticValues</code> — a SampleCount, Sum, Minimum and Maximum for a whole window — instead of individual values. One API payload then represents thousands of observations, and CloudWatch computes Average, Sum, Min, Max and SampleCount correctly from it. The trade-off is that percentiles are effectively unavailable for statistic-set data unless SampleCount is 1 or Minimum equals Maximum, because the distribution shape was discarded. The middle ground is the <code>Values</code> and <code>Counts</code> arrays, which publish a compressed histogram (each value with a repeat count) and preserve percentile accuracy while still collapsing many observations into one payload.</p>\n<p style=\"line-height: 1.75\"><strong>Embedded Metric Format (EMF).</strong> This is the answer to \"I need high-cardinality detail and low-cardinality metrics from the same event\". CloudWatch extracts metrics asynchronously from the log line at no PutMetricData cost, and the full record stays in Logs where you query it with Logs Insights. So <code>requestId</code>, <code>customerId</code> and <code>path</code> stay as searchable log fields while only <code>{Service, Operation}</code> becomes a billable metric. A service with a 40 ms average can still time out 1% of requests at 10 seconds, and that 1% is a real cohort of real users — often the ones with the most data, which correlates with your largest customers. The mean of five hosts' p99 values is not the fleet p99, and the mean of sixty one-minute p99 values is not the hourly p99. Percentiles are not linear functionals of the distribution, so combining them requires the underlying distribution, not the summary. Practically this means: request the percentile at the period and dimension granularity you actually want (CloudWatch computes it from the raw values it stored for that series), never build metric math that averages percentile series, and be aware that a dashboard which \"zooms out\" to a coarser period is recomputing the percentile from stored data rather than averaging your one-minute values.
