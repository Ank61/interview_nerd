{"title":"What Is Amazon CloudWatch — The Observability Service","tags":["cloudwatch","observability","monitoring","aws-basics"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">When your application runs on your laptop, you can see everything. You watch the terminal scroll by, you add a print statement, you restart it when it misbehaves. When that same application runs on a server in an AWS data centre you will never physically touch, all of that goes away. You cannot SSH into a Lambda function mid-request. You cannot watch the console output of a machine that autoscaled into existence at 3am and disappeared at 3:04am. \"It works on my laptop\" is a statement about your laptop, not about production. <strong>Observability</strong> — the ability to understand what a system is doing from the outside, using the data it emits — is the gap that has to be filled, and on AWS the service that fills it is Amazon CloudWatch.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">CloudWatch in one plain sentence</h4>\n<p style=\"line-height: 1.75\">Amazon CloudWatch is AWS's built-in service for collecting numbers about your systems over time, storing the text your applications write out, raising alerts when something crosses a line you defined, and drawing all of it on graphs and dashboards. It is turned on for your account the moment you start using AWS — there is nothing to install to get started, and a surprising amount of data is already flowing into it right now.</p>\n<p style=\"line-height: 1.75\">The word people use for this category of tool is <strong>telemetry</strong>: data a system emits about itself, so that someone (or something) elsewhere can judge its health. CloudWatch is AWS's telemetry warehouse plus the alerting and graphing built on top of it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The three things CloudWatch handles (and the fourth that lives elsewhere)</h4>\n<p style=\"line-height: 1.75\">People talk about the \"pillars of observability\". You do not need the jargon, but you do need the three shapes of data, because CloudWatch treats each one completely differently and beginners routinely reach for the wrong one.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Metrics — numbers over time.</strong> A <strong>metric</strong> is a named measurement recorded repeatedly with a timestamp: CPU was 34% at 10:00, 41% at 10:01, 88% at 10:02. Metrics are cheap to store, fast to graph, and perfect for spotting trends and for triggering alerts. They tell you <em>that</em> something is wrong.</li>\n<li><strong>Logs — text records of what happened.</strong> A <strong>log</strong> is a line of text your application or an AWS service wrote out, with a timestamp: \"OrderService: payment declined for order 8812, gateway timeout\". CloudWatch Logs stores these, lets you search them, and can even turn patterns in them into metrics. Logs tell you <em>why</em> something is wrong, because they carry detail a number never could.</li>\n<li><strong>Alarms and events — reacting when something crosses a line.</strong> A <strong>CloudWatch alarm</strong> watches one metric and changes state when it crosses a threshold you set, then takes an action such as emailing you or scaling out your fleet. <strong>Amazon EventBridge</strong> (which grew out of what was once called CloudWatch Events) reacts to things happening in your account — an instance changing state, a scheduled time arriving — and routes them to a target. Together these are the part that wakes a human up, or fixes the problem without one.</li>\n</ul>\n<p style=\"line-height: 1.75\">The fourth piece is <strong>traces</strong> — a record following one single request as it hops through several services, so you can see that the checkout call spent 40 milliseconds in your API and 2.1 seconds waiting on the payments service. That lives in a separate service, <strong>AWS X-Ray</strong> (now surfaced inside the CloudWatch console under Application Signals). That splits into two groups.</p>\n<p style=\"line-height: 1.75\">First, <strong>things inside your operating system</strong>. AWS runs your EC2 instance on a hypervisor — the layer that carves a physical machine into virtual ones. From there AWS can see how much CPU time your instance consumed and how many bytes crossed its network card, because the hypervisor mediates those. It genuinely cannot see how much RAM your Linux kernel considers free, or how full <code>/var</code> is, because those are facts inside a guest operating system AWS does not look into. That is why <strong>EC2 memory usage and disk space usage are not in CloudWatch by default</strong>. To get them you install the <strong>CloudWatch agent</strong>, a small program that runs on the instance, reads local system statistics, and pushes them up as custom metrics. Almost every beginner is surprised by this, and almost every real production setup installs the agent.</p>\n<p style=\"line-height: 1.75\">Second, <strong>things only your application knows</strong>: orders placed per minute, how long your checkout handler took, cache hit rate, how many users hit a validation error.
