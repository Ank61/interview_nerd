{"title":"Advanced CloudTrail Analysis — Athena Performance and Least-Privilege Engineering","tags":["athena","partition-projection","least-privilege","access-analyzer"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Two skills separate engineers who <em>have</em> CloudTrail from engineers who <em>use</em> it. The first is querying terabytes of it without accidentally spending a week's budget on a single <code>SELECT</code>. The second is the highest-value application of that data: deriving <strong>least-privilege policies</strong> from what principals actually did, rather than from what someone guessed they might need. The second skill is where most of the engineering judgement lives, because the naive version — delete every permission not seen in the last 90 days — breaks production in ways that surface a quarter later.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The table, and why the default is slow</h4>\n<p style=\"line-height: 1.75\">CloudTrail writes gzipped JSON into a deeply nested key structure: <code>AWSLogs/&lt;org-id&gt;/&lt;account&gt;/CloudTrail/&lt;region&gt;/YYYY/MM/DD/</code>, one small object every few minutes per account per Region. Athena reads that through a CloudTrail-specific SerDe, and the resulting table works immediately — which is the trap. Athena bills by <strong>bytes scanned</strong> (on the order of five dollars per terabyte in most Regions), and without partitions every query reads <strong>every object in the prefix</strong>, across every account, Region and day you have ever archived. A single unbounded query over a large organization's multi-year archive can scan many terabytes. That is not a performance problem, it is a billing incident.</p>\n<p style=\"line-height: 1.75\">Compounding it, gzipped JSON is a bad format for analytics: gzip is not splittable, so one file is one reader task, and JSON means every column is parsed even when you select one field. The fix is two-layered — <strong>partitioning</strong> to read fewer files, and <strong>columnar conversion</strong> to read less of each file.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Partition projection: partitions without a partition catalog</h4>\n<p style=\"line-height: 1.75\">The traditional approach adds partitions to the Glue catalog with <code>MSCK REPAIR TABLE</code> or explicit <code>ALTER TABLE ADD PARTITION</code> statements. For CloudTrail this is miserable: partition count is accounts times Regions times days, which reaches hundreds of thousands quickly, repair scans are slow, and new days need a scheduled job that will eventually fail unnoticed.</p>\n<p style=\"line-height: 1.75\"><strong>Partition projection</strong> solves it by telling Athena the <em>rule</em> for partition values instead of storing them. You declare that the <code>region</code> partition is an enum of your Regions, that the <code>timestamp</code> partition is a date ranging from a start date to <code>NOW</code> with a day interval and a <code>yyyy/MM/dd</code> format, and you give a <code>storage.location.template</code> that maps partition values to S3 prefixes. Athena then computes which prefixes a query needs from the <code>WHERE</code> clause and reads only those — no catalog, no repair job, no drift. Query a single day across one Region and you scan a handful of megabytes instead of terabytes.</p>\n<p style=\"line-height: 1.75\">Two operational cautions. Because projection is purely computed, a query <strong>without</strong> a predicate on the projected columns expands to the full projected range, so keep the range start realistic and make time predicates a team habit. And the projected range must actually cover your data — a range starting later than your archive silently hides older events, which is a genuinely dangerous failure mode for audit queries, because the query returns successfully with incomplete results.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Columnar conversion for repeated heavy analysis</h4>\n<p style=\"line-height: 1.75\">If you run the same analysis repeatedly — a monthly access review, a quarterly least-privilege sweep, an ongoing usage study — convert the window you care about to <strong>Parquet</strong> with a <code>CREATE TABLE AS SELECT</code>, partitioned by date and account, with Snappy compression. Parquet is columnar and splittable: selecting five fields reads five columns rather than every byte of every record, and predicate pushdown skips row groups. Ten-to-one reductions in bytes scanned are typical, sometimes far more, and queries go from minutes to seconds.</p>\n<p style=\"line-height: 1.75\">The cost calculus is simple and worth stating explicitly in an interview: the conversion itself scans the source data once and costs storage for the copy. It pays for itself the moment you run more than a few analyses over the same window, and it is wasted effort for a one-off investigation. So: <strong>projection for ad hoc investigation, Parquet for repeated analysis.</strong></p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Query economics in practice</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Always constrain the partition columns.</strong> A predicate on <code>eventtime</code> alone does not prune files — Athena cannot know that <code>eventtime</code> correlates with the <code>timestamp</code> partition. Filter on the partition column, then refine with <code>eventtime</code>.</li>\n<li><strong>Select columns, never <code>SELECT *</code>.</strong> On Parquet this directly reduces bytes scanned; on JSON it at least reduces the work and the result size.</li>\n<li><strong>Aggregate server-side.</strong> Return counts and groupings rather than raw rows; a query that returns fifty rows is cheaper to run, read and share than one returning fifty thousand.</li>\n<li><strong>Use a workgroup with a per-query data-scanned limit.</strong> This is the guardrail that turns a costly mistake into a failed query. It is the single control most teams wish they had set before their first surprise bill.</li>\n<li><strong>Lifecycle the query-results bucket.</strong> Athena writes every result to S3 forever unless you expire it, and those results often contain sensitive audit data, so this is a cost <em>and</em> a security control.</li>\n<li><strong>Read the scan figure every time.</strong> Athena reports bytes scanned per query. Making the team look at it is the cheapest cost discipline available.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Least-privilege derivation: the high-value application</h4>\n<p style=\"line-height: 1.75\">The typical production role was written under deadline, granted <code>s3:*</code> and <code>dynamodb:*</code> because the precise actions were unknown, and has never been revisited. CloudTrail turns that guess into evidence: it records what the role <strong>actually called</strong>. There are three tools, and a senior answer sequences them by cost and precision.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>IAM last-accessed data — the quick first pass.</strong> IAM reports, per principal, which <strong>services</strong> were last accessed and when, and for a subset of services (IAM, S3, EC2 and others) it reports <strong>action-level</strong> last-accessed data. It is free, instant, and needs no queries. It is perfect for the coarse cut: a role granted access to thirty services that has touched four in a year has twenty-six services' worth of permissions to remove, and you did not need Athena to learn that. Its limits: it is service-level for most services, its tracking period is bounded (a rolling window measured in months, not years), and it is per-Region-aware in ways that surprise people.</li>\n<li><strong>IAM Access Analyzer policy generation — the precise pass.</strong> Point Access Analyzer at a role and a CloudTrail trail and it reads the role's recorded activity over a lookback window and <strong>generates an IAM policy</strong> containing the actions it observed, with resource-level ARNs for the services that support them and action-level statements elsewhere. It is far more precise than last-accessed data and produces something you can review as a diff. Its limits are important: it depends on what the trail captured, so activity in a Region or account the trail did not cover is invisible, S3 object-level actions only appear if <strong>data events</strong> were enabled, and the lookback window is bounded (up to roughly 90 days), so it cannot see a quarterly job.</li>\n<li><strong>Direct CloudTrail analysis — the judgement pass.</strong> Athena or Lake over a longer history than Access Analyzer's window, which is what lets you see the rare-but-real. This is where you ask not just \"what actions?\" but \"when, how often, by which invocation path, and with what error rate?\" — the questions that determine whether a permission is dead or merely infrequent.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The nuance that separates a senior answer</h4>\n<p style=\"line-height: 1.75\">\"Not used in 90 days, therefore remove\" is the answer of someone who has never caused an outage this way. The permissions most likely to be missing from a 90-day window are precisely the ones whose absence hurts most:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Periodic jobs.</strong> Quarterly reconciliation, annual archival, year-end reporting, certificate rotation on a yearly cadence. A 90-day window sees none of a quarterly job that ran on day 95.</li>\n<li><strong>Disaster-recovery and failover paths.</strong> Promoting a replica, restoring from a snapshot, failing over a Route 53 record, switching an active-passive stack. By definition these are unexercised — that is the whole point — and removing them means the recovery path fails during the one event where it must not.</li>\n<li><strong>Error and rollback paths.</strong> Permissions used only when something fails: writing to a dead-letter queue, publishing a failure notification, rolling back a deployment, deleting a partially created resource.</li>\n<li><strong>Scale-out and burst paths.</strong> Actions only taken under load the environment has not seen recently — attaching volumes, creating capacity, requesting quota.</li>\n<li><strong>Seasonal business logic.</strong> Retail peak, tax season, enrolment periods.</li>\n</ul>\n<p style=\"line-height: 1.75\">So the method is: use CloudTrail to produce a <strong>candidate</strong> list, then apply human review that asks, for each permission, \"is there a code path that uses this which simply has not run?\" Read the code and the infrastructure definitions, not just the logs. Then de-risk the change: look back over the <strong>longest window you have</strong> rather than 90 days, remove in stages starting with entire unused services, and — the technique that makes this safe — use a <strong>Deny with a time condition or a staged rollout</strong>, or better, deploy the tightened policy to a non-production copy of the role first and run the full test suite including DR drills. Crucially, <strong>monitor AccessDenied for the role after the change</strong> with an alarm wired to a fast rollback, because the feedback loop is what converts an irreversible guess into a reversible experiment. And never tighten a role the day before a known peak.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Unused roles and credentials</h4>\n<p style=\"line-height: 1.75\">The same evidence cleans up principals, not just permissions. IAM records a <strong>role last-used</strong> timestamp and Region, and credential reports give per-user password and access-key last-used dates. <strong>IAM Access Analyzer unused access findings</strong> package this at organization scale: roles, users, permissions and credentials unused beyond a threshold you set, as findings you can triage like any other.</p>\n<p style=\"line-height: 1.75\">The cautions mirror the permissions case. Role last-used tracking began at a specific point in IAM's history and does not cover activity before it, so a very old role showing no usage may simply predate tracking. Break-glass and DR roles are <strong>supposed</strong> to be unused, and deleting them is exactly the wrong move — tag them explicitly (for example <code>Purpose=BreakGlass</code>) so they are excluded by rule rather than by memory. Roles assumed only by other services, or only during incidents, look idle. The safe sequence is: detach permissions or attach a deny-all first, wait a full business cycle, then delete — because a deleted role cannot be restored, and any policy or trust relationship referencing it by ARN breaks in ways that are awkward to diagnose.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Validating a change before applying it</h4>\n<p style=\"line-height: 1.75\">Before applying a tightened policy, test it against evidence rather than intuition. <strong>Replay history:</strong> extract every distinct action and resource the role called over the longest available window from CloudTrail, then evaluate the proposed policy against that list — the IAM <strong>policy simulator</strong> (<code>SimulatePrincipalPolicy</code>) does this programmatically and can be scripted over the extracted call list, which is the closest thing to a regression test for permissions. <strong>Use Access Analyzer policy validation</strong> to catch structural problems and security warnings, and its <strong>custom policy checks</strong> — <code>CheckNoNewAccess</code> proves the new policy grants nothing the old one did not, and <code>CheckAccessNotGranted</code> proves a specific dangerous action is not permitted. Those checks belong in CI on every policy change, not just on cleanup work. Finally, deploy behind a monitored rollback: alarm on AccessDenied for the role, and make reverting a one-command operation.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Operational realities that make analysis honest</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Delivery latency.</strong> CloudTrail typically delivers events within a handful of minutes, but it is a best-effort target, not a guarantee. Never treat \"no events in the last ten minutes\" as evidence of anything, and never build a synchronous control that blocks on a CloudTrail event arriving.</li>\n<li><strong>Eventual completeness.</strong> A file for a given hour can arrive after you queried that hour. Rerunning yesterday's query can legitimately return more rows today, which matters for anything that snapshots results.</li>\n<li><strong>Duplicates.</strong> Delivery is at-least-once; the same event can appear more than once. Deduplicate on <code>eventID</code> whenever you count anything, or your \"number of times this action ran\" is wrong.</li>\n<li><strong>Unexpected event sources.</strong> Console sign-in is <code>signin.amazonaws.com</code>, not the service you were in. Actions a service takes on your behalf appear with <code>userIdentity.invokedBy</code> set to that service and the event may be recorded in a different account than you expect. Cross-account role assumption produces events in both the calling and the trusting account. Some features log under a source that does not match the console's branding. If a search returns nothing, question the event source before concluding the action never happened.</li>\n<li><strong>Absence is weak evidence.</strong> This is the most important point and the one to say out loud. A missing event may mean the action did not happen — or that data events were not enabled, or the Region was not covered by the trail, or the action is one of the small set that is not logged, or it happened in a service that records it elsewhere. Before concluding \"nobody read that object\", verify that you would have seen it if they had. That verification, not the query, is what makes the conclusion defensible.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario: tightening an over-permissive production role</h4>\n<p style=\"line-height: 1.75\"><strong>Situation.</strong> <code>payments-service-role</code> carries a policy granting <code>s3:*</code>, <code>dynamodb:*</code>, <code>sqs:*</code>, <code>kms:*</code> and <code>iam:PassRole</code> on <code>*</code>. It runs the payment path. An audit flagged it, and the mandate is to tighten it without an incident.</p>\n<p style=\"line-height: 1.75\"><strong>Step 1 — free evidence first.</strong> Pull IAM last-accessed data for the role. It immediately shows which of the granted services have never been touched; that is the coarse, low-risk cut and it costs nothing.</p>\n<p style=\"line-height: 1.75\"><strong>Step 2 — precise evidence.</strong> Run Access Analyzer policy generation against the role over its full lookback, giving action-level and, where supported, resource-level detail. In parallel run an Athena query over <strong>12 months</strong> of archive, not 90 days, grouping by <code>eventname</code> with counts, first-seen and last-seen — the long window is specifically to catch quarterly and annual paths, and first-seen/last-seen is what reveals \"this ran four times, each about 90 days apart\".</p>\n<p style=\"line-height: 1.75\"><strong>Step 3 — human review of the candidate removals.</strong> For every permission on the removal list, ask whether a code path exists that has not run. Read the service code and the infrastructure-as-code. Talk to the team about DR runbooks, month-end and quarter-end jobs, and the rollback path. Expect this to rescue several permissions the data said were dead — that outcome is the point of the step, not a failure of the analysis.</p>\n<p style=\"line-height: 1.75\"><strong>Step 4 — validate before applying.</strong> Extract the distinct action-plus-resource pairs from the 12-month history and run them through <code>SimulatePrincipalPolicy</code> against the proposed policy; every historical call must still be allowed. Run Access Analyzer policy validation and a <code>CheckNoNewAccess</code> custom check to prove the new policy grants nothing extra. Deploy the tightened policy to a staging copy of the role and run the full test suite including a DR drill.</p>\n<p style=\"line-height: 1.75\"><strong>Step 5 — staged rollout with a fast rollback.</strong> Apply in stages: entire unused services first, then unused actions within used services, then resource scoping last (resource scoping is the highest-risk step because a new bucket or table ARN silently breaks it). Between stages, give it a full business cycle. Before the first stage, put a CloudWatch alarm on AccessDenied events for this role wired to the on-call channel, and keep reverting to a single command. Do not do any of this in the week before a peak.</p>\n<p style=\"line-height: 1.75\"><strong>Step 6 — make it stick.</strong> The role will drift again unless the tightened policy lives in version control with <code>CheckNoNewAccess</code> in CI, and unless the unused-access findings from Access Analyzer are reviewed on a schedule with an owner.
