The scenario repeats endlessly: a security incident happens, someone asks \"which files did the attacker download from that bucket?\", the team opens CloudTrail confidently — and finds nothing. Not because CloudTrail failed, but because the thing they needed was a category of event that is <strong>off by default</strong>, and it cannot be turned on retroactively.</p>\n<p style=\"line-height: 1.75\">CloudTrail records four kinds of event: <strong>management events</strong>, <strong>data events</strong>, <strong>Insights events</strong>, and <strong>network activity events</strong>. Understanding which is on by default, which costs money, and which answers which question is the whole topic.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Control plane versus data plane</h4>\n<p style=\"line-height: 1.75\">Everything here rests on one idea borrowed from networking. The <strong>control plane</strong> is the set of operations that <em>manage</em> resources — creating, configuring, listing and deleting them. The <strong>data plane</strong> is the set of operations performed <em>on</em> the contents of a resource, once it exists.</p>\n<p style=\"line-height: 1.75\">Creating an S3 bucket is control plane; reading an object out of it is data plane. Creating a Lambda function is control plane; invoking it is data plane. Creating a DynamoDB table is control plane; putting an item in it is data plane.</p>\n<p style=\"line-height: 1.75\">The difference that drives every design decision here is <strong>volume</strong>. You might create a bucket once and never touch its configuration again, but your application could read a million objects from it every hour. Examples: <code>CreateBucket</code>, <code>RunInstances</code>, <code>TerminateInstances</code>, <code>AttachRolePolicy</code>, <code>CreateUser</code>, <code>AssumeRole</code>, <code>ConsoleLogin</code>, <code>AuthorizeSecurityGroupIngress</code>, <code>CreateFunction</code>.</p>\n<p style=\"line-height: 1.75\">These are <strong>logged by default</strong> — they are what appears in the free 90-day Event history, and what a trail captures unless you change anything. Crucially, the <strong>first copy of management events delivered to S3 by a trail is free</strong>. That phrase matters: it means one trail capturing management events costs you only S3 storage. Create a second trail capturing the same management events and the second copy is charged per event.</p>\n<p style=\"line-height: 1.75\">Management events cover the vast majority of security and governance questions, because almost everything an attacker or a careless engineer does to <em>change</em> your environment is a management event.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Data events</h4>\n<p style=\"line-height: 1.75\"><strong>Data events</strong> record data-plane operations performed <em>on</em> resources. The ones you must know:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>S3 object-level activity.</strong> <code>GetObject</code>, <code>PutObject</code>, <code>DeleteObject</code>, <code>HeadObject</code> — individual object reads and writes.</li>\n<li><strong>Lambda function invocations.</strong> The <code>Invoke</code> call, recording every execution of a function.</li>\n<li><strong>DynamoDB item-level activity.</strong> <code>GetItem</code>, <code>PutItem</code>, <code>Query</code>, <code>Scan</code>, <code>DeleteItem</code>.</li>\n<li><strong>Many others.</strong> S3 Express, EBS direct APIs, SNS Publish, SQS message actions, Step Functions, CloudWatch RUM and more — the supported list keeps growing.</li>\n</ul>\n<p style=\"line-height: 1.75\">Three facts define data events, and they are the three facts interviewers test.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>They are NOT logged by default.</strong> Nothing you do by accident turns them on.</li>\n<li><strong>They must be explicitly enabled</strong> on a trail (or an Event Data Store in CloudTrail Lake), per resource type, with selectors saying which resources.</li>\n<li><strong>They cost extra</strong> — charged per event recorded, with no free tier, on top of S3 storage for the volume produced.</li>\n</ul>\n<p style=\"line-height: 1.75\">The reason is pure arithmetic. A busy application can generate millions of S3 GetObject calls per hour. Logging all of them means both a per-event charge and a large, continuously growing pile of log files in S3. AWS made the sensible default: off, and you opt in where it matters.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The classic interview scenario</h4>\n<p style=\"line-height: 1.75\">\"A confidential file was downloaded from an S3 bucket. How do you find out who downloaded it?\"</p>\n<p style=\"line-height: 1.75\">The correct answer has two halves, and only giving the first half is what separates a shaky answer from a strong one. <strong>First:</strong> you look for a CloudTrail <strong>data event</strong> with <code>eventName</code> of <code>GetObject</code> and the object key in <code>requestParameters</code>, and read <code>userIdentity</code> for the principal. <strong>Second, and more important:</strong> this only works if <strong>S3 data events were already enabled on that bucket before the download happened</strong>. Data events cannot be turned on retroactively — if they were off, that history simply does not exist and no amount of digging will produce it. The best remaining option is S3 server access logs, if those happened to be enabled.</p>\n<p style=\"line-height: 1.75\">The practical guidance follows directly: <strong>enable data events selectively</strong>, on the buckets, prefixes and functions that hold sensitive material — the PII bucket, the financial reports prefix, the credential-handling Lambda — rather than across every resource you own. Use <strong>advanced event selectors</strong> to scope by prefix so you capture the <code>confidential/</code> path and not the terabytes of thumbnails.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">CloudTrail Insights events</h4>\n<p style=\"line-height: 1.75\">The first two types record things that happened. <strong>Insights events</strong> are different: CloudTrail analyses your own history to learn what <em>normal</em> looks like, then generates an Insights event when current activity deviates sharply from that baseline.</p>\n<p style=\"line-height: 1.75\">It watches two signals. <strong>Unusual write API call volume</strong> — a sudden spike or collapse in the rate of write calls, such as <code>RunInstances</code> jumping from 5 per hour to 400. And <strong>unusual error rates</strong> — a spike in a particular error, most notably a flood of <code>AccessDenied</code>.</p>\n<p style=\"line-height: 1.75\">Why beginners should care: these are exactly the shapes of a real problem. A runaway script or a Terraform loop creating hundreds of resources shows up as a write-volume spike, and you would rather know at 3 a.m. than from the bill. An attacker with stolen credentials who does not know what they can access generates a wall of AccessDenied errors while probing. A deployment that broke a permission produces the same signature. Insights surfaces all three without you having to guess a threshold in advance.</p>\n<p style=\"line-height: 1.75\">Two practical notes: Insights is <strong>opt-in and separately charged</strong> (priced on the volume of events analysed), and it needs a <strong>baseline period</strong> — typically around a week of history — before it can judge what is unusual, so do not expect findings the moment you enable it. Insights events are delivered to a separate location from ordinary events, and can also be routed to EventBridge for alerting.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Network activity events (orientation)</h4>\n<p style=\"line-height: 1.75\"><strong>Network activity events</strong> are a newer, fourth category. They record AWS API activity that traverses a <strong>VPC endpoint</strong> — a private doorway that lets resources inside your VPC reach AWS services without going over the public internet.</p>\n<p style=\"line-height: 1.75\">They exist to close a visibility gap: they let you see attempts to reach services through your VPC endpoints, including calls from <em>outside</em> your organization that were denied by an endpoint policy — useful for detecting attempted data exfiltration through your own network path. Like data events, they are <strong>opt-in and separately charged</strong>, and configured with event selectors. As a beginner you need only know the category exists and what question it answers.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Narrowing what you capture: read/write filtering and advanced event selectors</h4>\n<p style=\"line-height: 1.75\">Because volume equals cost, CloudTrail lets you narrow what a trail records. An <strong>event selector</strong> is the configuration describing which events a trail should capture.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Read/write filtering.</strong> Every API call is either <strong>read-only</strong> (it looks at something and changes nothing — <code>DescribeInstances</code>, <code>GetObject</code>, <code>ListBuckets</code>) or <strong>write-only</strong> (it changes something — <code>RunInstances</code>, <code>PutObject</code>, <code>DeleteBucket</code>). You can set a trail to <code>ReadWriteType</code> of <code>WriteOnly</code>, <code>ReadOnly</code>, or <code>All</code>. Filtering to <strong>WriteOnly</strong> is a very effective cost lever, because read calls hugely outnumber writes and writes are what actually change your environment. The trade-off is real: you then cannot see who <em>read</em> something, which for a confidentiality investigation is the entire question. So: WriteOnly for broad coverage, All on genuinely sensitive resources.</li>\n<li><strong>Basic event selectors</strong> are the older, coarse mechanism — read/write type, whether to include management events, and data event resource types at bucket or function granularity.</li>\n<li><strong>Advanced event selectors</strong> are the modern, precise mechanism. They let you build conditions on fields including <code>eventCategory</code>, <code>resources.type</code>, <code>eventName</code>, and <code>resources.ARN</code>, using operators such as <code>equals</code>, <code>notEquals</code>, <code>startsWith</code>, <code>endsWith</code> and their \"not\" variants. That makes it possible to say \"log S3 data events only for ARNs starting with <code>arn:aws:s3:::finance-reports/confidential/</code>\" or \"log all object activity except <code>GetObject</code> on the public assets bucket\". This is how you get investigative coverage where it matters without paying for the noise.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Comparison table</h4>\n<div style=\"overflow-x: auto; font-size: 1.25rem; font-weight: 600\">Why \"log everything everywhere\" is a real budget decision</h4>\n<p style=\"line-height: 1.75\">Beginners often propose enabling every event type on every resource \"to be safe\". Here is the honest arithmetic. Management events on one trail are effectively free, so capture them broadly — there is no reason not to. Data events are charged <strong>per event</strong>, so an application making 50 million S3 requests a month generates 50 million billable records, plus the S3 storage to hold them, plus the query cost every time you search them, plus the egress or Athena scan cost of analysis.</p>\n<p style=\"line-height: 1.75\">The cost of logging can genuinely exceed the cost of the workload being logged. It is not unusual for an unscoped data-event configuration on a high-traffic bucket to add four figures a month. The engineering answer is not \"log nothing\" and not \"log everything\" — it is <strong>log management events everywhere, and scope data events with advanced event selectors to the resources whose access history you would actually need in an incident</strong>. Pair that with S3 lifecycle rules moving old log files to cheaper storage classes, and a retention policy that matches your compliance requirement rather than exceeding it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"CloudTrail logs every S3 object read by default.\"</strong> It does not. Object-level reads are <strong>data events</strong>, off by default. Only bucket-level management operations are captured automatically.</li>\n<li><strong>\"Data events are just more management events.\"</strong> They are a different category with different defaults, different pricing and separate configuration. They differ in <em>kind</em>: management events are about the box, data events are about what is inside it.</li>\n<li><strong>\"Insights is enabled automatically.\"</strong> It is opt-in, separately charged, and needs roughly a week of baseline history before it can flag anything as unusual.</li>\n<li><strong>\"Turning on data events everywhere is free.\"</strong> It is charged per event with no free tier, and on a busy account it can become one of your larger line items.</li>\n<li><strong>\"I can enable data events now and see last month's downloads.\"</strong> No. Logging is never retroactive.
