The software layer on that physical server that creates and manages virtual machines is called the <strong>hypervisor</strong>. AWS can measure your instance from the hypervisor's position, which is the view from <em>outside</em> the machine.</p>\n<p style=\"line-height: 1.75\">From outside, AWS can honestly see: how much CPU time your virtual machine consumed, how many bytes went in and out of its virtual network card, and how many read and write operations hit its virtual disk. All of those are things that pass <em>through</em> the hypervisor, so it can count them without ever looking inside.</p>\n<p style=\"line-height: 1.75\">What the hypervisor cannot see is what is happening <em>inside</em> your guest operating system — the Linux or Windows installation running on the instance. Memory is a good example. Your OS asks for a block of RAM once, then manages it internally: it allocates it to processes, frees it, caches files in it, and reuses it. None of that bookkeeping crosses the hypervisor boundary, so from outside, that RAM just looks \"assigned\". The same goes for disk space used: the hypervisor sees read and write operations going to the disk, but it does not understand your filesystem, so it has no idea whether the disk is 5% or 95% full.</p>\n<div style=\"overflow-x: auto; font-size: 1.25rem; font-weight: 600\">What an \"agent\" is, in plain words</h4>\n<p style=\"line-height: 1.75\">An <strong>agent</strong> is simply a small program that you install on a machine, which runs quietly in the background, collects information from inside that machine, and sends it somewhere. You will also see the word <strong>daemon</strong> — on Linux, that is the term for any long-running background program with no user interface, started automatically when the machine boots. An agent is a daemon whose job is collecting and reporting data.</p>\n<p style=\"line-height: 1.75\">Because the agent runs <em>inside</em> your operating system, it can read exactly the things the hypervisor cannot: <code>/proc/meminfo</code> for memory, the filesystem for disk usage, the process table, and any log file on disk. It then pushes that data up to CloudWatch over the network. The solution to \"I can't see memory\" is therefore always: install an agent.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">  <i class=k>WITHOUT</i> AGENT                        <i class=k>WITH</i> AGENT\n<i class=o>+</i><i class=c>---------------------+             +---------------------+</i>\n<i class=o>|</i>  Guest OS           <i class=o>|</i>             <i class=o>|</i>  Guest OS           <i class=o>|</i>\n<i class=o>|</i>   memory: ??? That is the one you should install; older blog posts referencing the \"CloudWatch Logs agent\" are describing a legacy tool.</p>\n<p style=\"line-height: 1.75\">There are four things to get right, and beginners usually stumble on the last one.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>1. Install the package.</strong> The agent is distributed as an RPM/DEB/MSI (the standard installer format for each OS). You can install it by hand, bake it into a machine image, or — easiest at scale — have Systems Manager do it (below).</li>\n<li><strong>2. Write a configuration file.</strong> The agent does nothing useful until you tell it what to collect. The config is a JSON file listing which system metrics you want and which log file paths to watch. On Linux it lives at <code>/opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json</code>.</li>\n<li><strong>3. Use the wizard if you are new.</strong> A <strong>wizard</strong> is an interactive question-and-answer program that writes the config file for you. Run <code>amazon-cloudwatch-agent-config-wizard</code>, answer questions like \"which log files?\", and it produces valid JSON so you do not have to memorize the schema.</li>\n<li><strong>4. Give the instance an IAM role that permits publishing.</strong> This is the step people forget. AWS denies every request that is not explicitly allowed, so the agent needs permission to call CloudWatch. An <strong>IAM role</strong> is a set of permissions the instance itself wears, so no passwords or keys are stored on disk. Attach the AWS-managed policy <code>CloudWatchAgentServerPolicy</code>. Without it, the agent installs and starts fine but silently fails to publish, and its own log file shows AccessDenied errors.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Deploying it at scale with Systems Manager</h4>\n<p style=\"line-height: 1.75\">Logging into fifty servers to install a package by hand is not a plan. <strong>AWS Systems Manager (SSM)</strong> is a management service that can run commands on your instances remotely, using its own small agent that comes preinstalled on modern Amazon Linux, Ubuntu and Windows AMIs.</p>\n<p style=\"line-height: 1.75\">Two Systems Manager features matter here. <strong>Run Command</strong> executes a one-off instruction across a group of instances — you pick the <code>AWS-ConfigureAWSPackage</code> document and it installs the CloudWatch agent everywhere at once. <strong>Parameter Store</strong> is a place to save configuration text centrally; you store your agent JSON there once under a name, and every instance pulls the same config, so you can update the config in one place and re-push it fleet-wide.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What the agent can collect</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>System metrics.</strong> Memory used and available, disk space used per mounted filesystem, swap usage (disk space the OS borrows when RAM runs short), per-process CPU and memory, network connection counts, and more.</li>\n<li><strong>Log files.</strong> You list file paths such as <code>/var/log/nginx/access.log</code> or <code>/var/app/current/app.log</code>, plus which log group they should land in, and the agent tails them (follows them as new lines are appended) into CloudWatch Logs. On Windows it can also collect Windows Event Log channels.</li>\n<li><strong>On-premises servers too.</strong> The agent is not EC2-only. Install it on a server in your own data centre or in another cloud, give it AWS credentials, and its metrics and logs flow into the same CloudWatch console — which is how teams build one dashboard across a hybrid environment.</li>\n<li><strong>StatsD.</strong> A very simple, long-established protocol where your application fires tiny UDP messages like \"counter signups went up by 1\". The agent can listen for these and turn them into CloudWatch custom metrics. Useful because StatsD client libraries exist for every language and are trivial to call.</li>\n<li><strong>collectd.</strong> An older, widely used open-source metric collection daemon with a large ecosystem of plugins (databases, web servers, hardware sensors). The agent can accept collectd's output, so if your Linux fleet already runs collectd you can forward that existing data into CloudWatch rather than re-instrumenting.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">A tour of the higher-level monitoring features</h4>\n<p style=\"line-height: 1.75\">Beyond raw metrics and logs, AWS offers packaged monitoring products. You do not need to master them as a beginner, but you should know each one exists and what problem it solves — interviewers ask exactly that.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Container Insights.</strong> Containers are short-lived and numerous, so per-instance metrics are not enough. Container Insights collects metrics and logs for ECS and EKS workloads and organizes them by cluster, node (the EC2 machine), pod (a group of containers scheduled together in Kubernetes) and individual container — so you can see which pod is eating memory, not just which server. It is <strong>opt-in</strong>, enabled per cluster.</li>\n<li><strong>Lambda Insights.</strong> Lambda already publishes Invocations, Duration, Errors and Throttles. Lambda Insights goes deeper with per-invocation data: CPU and memory actually used, network activity, and cold starts (the extra delay when AWS has to spin up a fresh execution environment). Enable it by adding a Lambda layer. It solves \"my function is slow and I need to know whether it is memory-starved or cold-starting.\"</li>\n<li><strong>CloudWatch Synthetics.</strong> A <strong>canary</strong> is a small script AWS runs on a schedule from outside your system — it loads your homepage, calls your API, or walks a checkout flow, and reports success, failure and latency. This is <em>proactive</em> monitoring: your servers can look perfectly healthy while DNS is broken or a certificate expired, and a canary catches that before a customer calls you. The name comes from the canary in a coal mine.</li>\n<li><strong>CloudWatch RUM (Real User Monitoring).</strong> A small JavaScript snippet in your web pages that reports what actual visitors experienced — page load times, JavaScript errors, browser and geography breakdowns. Where Synthetics is a robot in one location, RUM is the truth from real users on real devices and networks.</li>\n<li><strong>AWS X-Ray.</strong> <strong>Distributed tracing</strong>: following one single request as it hops across many services. If a user request goes API Gateway to Lambda to DynamoDB to another Lambda, X-Ray stitches those hops into one timeline showing where the 2 seconds went. This is a third data type, distinct from metrics (numbers over time) and logs (text lines): a <strong>trace</strong> is the story of one request across service boundaries.</li>\n<li><strong>Application Signals and ServiceLens.</strong> Two pieces of glue. ServiceLens joins traces, metrics and logs into one service map view. Application Signals is the newer capability that auto-instruments your application, discovers its services and dependencies, and lets you set service level objectives (targets like \"99.9% of requests succeed\") with dashboards tracking them.</li>\n<li><strong>CloudWatch Application Insights.</strong> Point it at an application's resources and it sets up sensible monitoring for common stacks (SQL Server, .NET, Java, web tiers) automatically — the relevant metrics, log patterns and alarms — instead of you hand-building them. It also groups related signals into \"problems\" with probable causes.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"EC2 memory metrics are built in.\"</strong> They are not, and never have been. X-Ray traces follow one request across services and show timing per hop. You want both: the trace tells you <em>where</em> time went, the log tells you <em>why</em>.</li>\n<li><strong>\"The agent only works on EC2.\"</strong> It works on on-premises and other-cloud servers too, given credentials.</li>\n<li><strong>\"Synthetics tells me about my real users.\"</strong> That is RUM.
