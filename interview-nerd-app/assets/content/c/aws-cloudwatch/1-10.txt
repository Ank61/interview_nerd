First, <strong>log retention defaults to Never Expire</strong>, so unless someone sets it, every log group accumulates storage cost permanently. Second, a <strong>custom metric is a unique combination of namespace, metric name and dimension values</strong> — adding one dimension with 10,000 distinct values to one metric creates 10,000 billable metrics. Custom metric pricing is tiered (cheaper per metric at high volume) but cardinality explosions outrun the tiering easily.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Diagnosis: Find the Dimension, Then the Owner</h4>\n<p style=\"line-height: 1.75\">Never start optimising before you know which dimension dominates; teams routinely spend a sprint tuning dashboards while log ingestion is 85% of the bill. The tool is <strong>Cost Explorer grouped by USAGE_TYPE</strong>, filtered to the AmazonCloudWatch service. Usage types are Region-prefixed and self-describing enough to map to the table above — data-processing usage types correspond to log ingestion, timed-storage usage types to log storage, data-scanned usage types to Logs Insights, and there are distinct usage types for metric monitoring, alarm monitoring, API requests, dashboards, canary runs, RUM events and Contributor Insights. Group by <strong>linked account</strong> next to find which team, then by <strong>tag</strong> if you have enforced tagging.</p>\n<p style=\"line-height: 1.75\">Cost Explorer stops at the service level, so the second step is finding the specific offenders inside CloudWatch:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Noisiest log groups by ingestion.</strong> The <code>IncomingBytes</code> metric in the <code>AWS/Logs</code> namespace is dimensioned by LogGroupName. Sum it over 30 days for every log group and sort descending — this is the single most valuable query in CloudWatch cost work, and it is usually brutally Pareto: three log groups account for most of the bill.</li>\n<li><strong>Storage and retention posture.</strong> <code>DescribeLogGroups</code> returns <code>storedBytes</code> and <code>retentionInDays</code>; a null retention means Never Expire. Listing log groups with no retention set, sorted by stored bytes, is your immediate-win list.</li>\n<li><strong>Metric cardinality.</strong> <code>ListMetrics</code> per namespace, counting results, exposes which custom namespace has exploded. Look at the dimension names — the culprit is nearly always an unbounded identifier.</li>\n<li><strong>API request sources.</strong> CloudTrail management events record <code>GetMetricData</code>, <code>GetMetricStatistics</code> and <code>ListMetrics</code> calls with the calling identity. Aggregating by principal names the polling integration precisely, which matters because the owner is often a third-party SaaS agent nobody remembers installing.</li>\n<li><strong>Per-run costs.</strong> Count canaries multiplied by runs per day, RUM event volume, and X-Ray traces recorded, and sanity-check each against the value it delivers.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Remediation Levers, in Priority Order</h4>\n<p style=\"line-height: 1.75\"><strong>1. Set retention on every log group.</strong> This is the highest ratio of savings to risk in the entire exercise. Most operational logs have a useful life of days to weeks; compliance logs need years but usually belong in S3, not in CloudWatch Logs. Enforce it with an AWS Config rule or an EventBridge rule on <code>CreateLogGroup</code> that applies a default retention automatically, and back it with a Service Control Policy or org-wide automation so new log groups never default to infinity again.</p>\n<p style=\"line-height: 1.75\"><strong>2. Reduce what you ingest.</strong> Ingestion is the biggest lever because you pay for it once at ingest and again for storage and again every time Insights scans it. Turn DEBUG off in production and make log level runtime-configurable so you can raise it temporarily during an incident instead of leaving it on permanently. Stop logging full request and response bodies. Collapse multi-line stack traces for expected, handled errors. <strong>Sample high-volume, low-information paths</strong> — log 1% of successful health checks and 100% of errors. Structured JSON logging helps here because it lets you drop fields rather than whole lines.</p>\n<p style=\"line-height: 1.75\"><strong>3. Filter at the collector, before ingestion.</strong> If you run the CloudWatch agent, Fluent Bit or the ADOT Collector, you can drop or sample records at the edge so they are never billed. This is strictly better than ingesting and then deleting, and it is where a filter/sample processor pays for itself immediately on access logs and Kubernetes chatter.</p>\n<p style=\"line-height: 1.75\"><strong>4. Choose the right storage tier and destination.</strong> The <strong>Infrequent Access log class</strong> offers materially lower ingestion pricing for logs you rarely query, at the cost of a reduced feature set — it does not support the full range of capabilities of the Standard class (Live Tail and metric-filter/EMF extraction among them), and the class is chosen at log group creation, so it fits new, high-volume, occasionally-queried groups rather than your primary alerting logs. For genuinely cold data, use a <strong>subscription filter to Firehose into S3</strong> (or export) and query with <strong>Athena</strong>: S3 storage is roughly an order of magnitude cheaper than CloudWatch Logs storage, Glacier tiers cheaper still, and Athena with Parquet and partitioning scans far less data than Logs Insights does over raw text. The trade-off is query latency and losing the integrated console experience, which is exactly right for audit and compliance data you touch twice a year.</p>\n<p style=\"line-height: 1.75\"><strong>5. Kill high-cardinality custom metrics.</strong> If a metric carries a dimension with unbounded values, you are paying metric prices for what is really log data. Move that detail into logs and use the <strong>Embedded Metric Format</strong>: EMF lets you emit one structured log event that both carries all the high-cardinality context <em>as log fields</em> and declares a small number of low-cardinality dimensions that CloudWatch extracts as metrics. You keep the ability to alarm on the aggregate and the ability to query the detail with Insights, while paying for a handful of metrics instead of thousands. Also delete or stop publishing metrics nobody graphs or alarms on — a custom metric with no alarm and no dashboard reference is a pure liability.</p>\n<p style=\"line-height: 1.75\"><strong>6. Replace polling with Metric Streams.</strong> Third-party observability platforms traditionally poll <code>GetMetricData</code> every minute across thousands of metrics, and the API-request line becomes shockingly large. <strong>CloudWatch Metric Streams</strong> pushes metric updates continuously through Kinesis Data Firehose to the destination instead, usually at lower total cost and with lower latency. Apply namespace include/exclude filters so you stream only what the destination actually uses. If you cannot move off polling, at least reduce frequency and the number of metrics requested.</p>\n<p style=\"line-height: 1.75\"><strong>7. Prune the long tail.</strong> Delete dashboards nobody has opened and alarms nobody acts on (an alarm in INSUFFICIENT_DATA for six months is both a cost and a lie). Disable Contributor Insights rules left running after an incident. Tune canary frequency to the value of the endpoint — one minute for checkout, fifteen for an internal admin tool — and put a lifecycle policy on the canary artifact bucket. Lower the RUM session sample rate. Tune <strong>X-Ray sampling</strong> down on high-volume low-value paths and audit any automation that retrieves traces in a loop, since retrieval and scanning are billable too.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Governance: Making the Savings Stick</h4>\n<p style=\"line-height: 1.75\">Every optimisation effort regresses within two quarters unless the incentives change. The mechanisms that work:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Attribution.</strong> Tag log groups, canaries and alarms with a team or cost-centre tag and activate those as cost allocation tags. Where tagging is impractical, a per-team account boundary attributes cost automatically — this is one of the strongest arguments for multi-account structure.</li>\n<li><strong>Showback or chargeback.</strong> A monthly report that names each team's observability spend changes behaviour faster than any policy document. Publish it as a dashboard, not an email nobody reads.</li>\n<li><strong>Budgets and anomaly detection on the observability bill itself.</strong> AWS Budgets with alerts scoped to the CloudWatch service per account, plus <strong>AWS Cost Anomaly Detection</strong> with a monitor on CloudWatch, catches the classic failure — a debug flag shipped on Friday afternoon that triples ingestion — within a day instead of at month end.</li>\n<li><strong>Guardrails at creation time.</strong> Default retention applied automatically to new log groups; a CI check that fails a pull request adding a metric dimension from a deny-list of known high-cardinality names; a quota on canaries per team.</li>\n<li><strong>Culture.</strong> State the principle explicitly in your observability standards: <em>the cost of a signal should be proportionate to the decision it enables</em>. The correct response to a large bill is not blanket austerity — cutting observability to the point where incidents take three hours longer to resolve is a false economy, and you should be able to argue that with the same numbers. Some signals justify enormous spend: 100% tracing on the payment path costs less than one undiagnosed checkout outage.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Production Scenario: Cutting a Very Large CloudWatch Bill</h4>\n<p style=\"line-height: 1.75\">The CloudWatch line has reached roughly &#36;180,000 a month across 40 accounts and leadership wants it halved without weakening incident response. A prioritised plan:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Week 1 — measure.</strong> Cost Explorer grouped by usage type and linked account. Suppose the split is ingestion 55%, storage 18%, custom metrics 12%, API requests 8%, Insights scanning 4%, everything else 3%. That immediately says: logs first, metrics second, and do not spend a day on dashboards.</li>\n<li><strong>Week 1 — the free win.</strong> Query <code>DescribeLogGroups</code> org-wide for groups with no retention. Typically a large share of stored bytes sits in Never Expire groups; applying a 30-day default (with documented exceptions) collapses most of the 18% storage line within a couple of weeks as old data ages out. Risk is low and the change is reversible going forward, though deleted data is gone — so snapshot anything needed for compliance to S3 first.</li>\n<li><strong>Week 2 — attack the top three log groups.</strong> Rank by <code>IncomingBytes</code>. The usual findings: an application left at DEBUG since a past incident, an ALB or ingress access log duplicating what is already in S3, and a Kubernetes sidecar logging a health check line per second per pod. Fixes: log level to INFO with a runtime override, drop the duplicate access logs or filter them at Fluent Bit, and sample the health-check lines at 1%. Realistically this removes 30-40% of ingestion by itself, which is roughly 20% of the total bill.</li>\n<li><strong>Week 3 — cardinality.</strong> <code>ListMetrics</code> per namespace finds a custom namespace with hundreds of thousands of metrics because someone added a customer ID dimension. Replace with <strong>EMF</strong>: dimension on service, operation and status class only, and keep customer ID as a log field so Insights can still answer per-customer questions. Removes the bulk of the 12% metrics line.</li>\n<li><strong>Week 3 — the surprise.</strong> CloudTrail aggregation of <code>GetMetricData</code> by principal reveals a third-party monitoring agent polling every metric in the account every minute. Switch it to a <strong>Metric Stream</strong> with a namespace filter. Removes most of the 8% API line.</li>\n<li><strong>Week 4 — cold data and the tail.</strong> Route audit and compliance logs to S3 via a Firehose subscription filter with Athena for querying, move a couple of new high-volume rarely-queried groups to the <strong>Infrequent Access</strong> class, delete abandoned dashboards and stale alarms, disable leftover Contributor Insights rules, reduce canary frequency on non-critical endpoints, and lower the RUM sample rate.</li>\n<li><strong>Week 5 — lock it in.</strong> EventBridge automation applying default retention on <code>CreateLogGroup</code>; cost allocation tags plus a monthly per-team showback dashboard; AWS Budgets and Cost Anomaly Detection scoped to CloudWatch; a documented standard stating retention defaults, allowed metric dimensions and sampling expectations.</li>\n</ul>\n<p style=\"line-height: 1.75\">Two discipline points make this credible in an interview. First, <strong>sequence by measured share, not by ease</strong> — the temptation is to start with dashboards because it is easy.
