None of it describes your <em>business</em>. AWS has no idea what an order is, cannot tell a successful checkout from a failed one, and does not know your cache exists. A <strong>custom metric</strong> — a number you measure and send to CloudWatch yourself — is how those facts get onto a graph. This topic covers the two ways to publish them, what they cost, and the far harder question of what is worth measuring at all.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why you need custom metrics at all</h4>\n<p style=\"line-height: 1.75\">Picture a deployment that quietly breaks the payment gateway integration. CPU is normal because the servers are doing less work. Lambda Invocations are normal because requests still arrive. Errors may even be normal if the code catches the failure and returns a polite \"please try again\" page. Every AWS metric is green while revenue is zero. The only signal that would have caught it is one only your code can produce: <code>OrdersCompleted</code> falling off a cliff.</p>\n<p style=\"line-height: 1.75\">That is the general shape of it. Typical custom metrics include orders placed, signups, checkout failures by reason, queue processing time, cache hit rate, background job duration, items in an internal work queue, and third-party API latency. These are the numbers that map to whether the product is actually working.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The PutMetricData API — the direct path</h4>\n<p style=\"line-height: 1.75\"><strong>PutMetricData</strong> is the CloudWatch API call that pushes data points in. Every data point you send carries a namespace (the container name you invent), a metric name, optional dimensions (name-value pairs identifying which thing this is about), a value, a unit, and optionally a timestamp. If you omit the timestamp, CloudWatch uses the time it received the call. You may send timestamps up to two weeks in the past and up to two hours in the future, which is how batch jobs backfill.</p>\n<p style=\"line-height: 1.75\">Practical limits worth knowing: a single call may carry up to 1,000 data points and a payload of about one megabyte, and the caller needs the <code>cloudwatch:PutMetricData</code> IAM permission — a missing permission is the most common reason a beginner's metric silently never appears.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Batching and statistic sets</h4>\n<p style=\"line-height: 1.75\">Calling PutMetricData once per event is the naive approach and it is a genuine problem: it costs money per request (roughly 0.01 USD per 1,000 API calls), it adds network latency to your request handler, and it burns API rate limit. There are two better patterns.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Multiple data points per call.</strong> Buffer values in memory and flush a batch periodically. You can also send a single MetricDatum with parallel <code>Values</code> and <code>Counts</code> arrays — \"the value 200 occurred 47 times, the value 350 occurred 3 times\" — which compresses repetitive data enormously.</li>\n<li><strong>Statistic sets.</strong> Instead of sending raw values at all, send a pre-aggregated summary: <strong>SampleCount, Sum, Minimum and Maximum</strong> for the interval. CloudWatch can then serve Average (Sum divided by SampleCount), Sum, Min and Max exactly as if you had sent every point. One tiny payload replaces thousands of values. The trade-off is that <strong>percentiles are impossible</strong> from a statistic set — p99 needs the distribution, and a four-number summary has thrown it away. If p99 matters, do not use statistic sets for that metric.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Units, and why they matter</h4>\n<p style=\"line-height: 1.75\">A <strong>unit</strong> declares what the number means: <code>Count</code>, <code>Seconds</code>, <code>Milliseconds</code>, <code>Microseconds</code>, <code>Bytes</code>, <code>Megabytes</code>, <code>Percent</code>, <code>Count/Second</code>, <code>None</code>. CloudWatch uses it to label axes and to scale sensibly — a Bytes metric is displayed as MB or GB when appropriate, and a Seconds metric shows time formatting.</p>\n<p style=\"line-height: 1.75\">Two rules. Be <strong>consistent</strong>: if you publish a metric as Milliseconds on Monday and Seconds on Tuesday, the graph mixes two incompatible scales and a value of 2 sits beside a value of 2000 meaning the same thing. And be <strong>honest</strong>: publishing milliseconds while declaring the unit Seconds produces a graph claiming your API takes 45 minutes. When querying or alarming, the unit must match what was published, or CloudWatch finds no data — a classic invisible failure.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cost — the warning that matters most</h4>\n<p style=\"line-height: 1.75\">Custom metrics are billed <strong>per metric per month</strong>, at roughly 0.30 USD each for the first 10,000, regardless of how many data points that metric contains. A well-worn starting framework is the <strong>four golden signals</strong>, in plain words:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Latency — how long things take.</strong> How long did the request take to serve? Measure successful and failed requests <em>separately</em>, because a fast error can otherwise flatter your average. Publish as a distribution so you can read p95 and p99, not just the mean.</li>\n<li><strong>Traffic — how much demand there is.</strong> Requests per minute, orders per minute, messages consumed. Without it you cannot tell a quiet night from an outage, and you cannot interpret an error count.</li>\n<li><strong>Errors — how often things fail.</strong> Failed requests, failed payments, exceptions thrown. Track as a rate against traffic, and split by cause (a 400 from a confused user and a 503 from a dead dependency mean different things).</li>\n<li><strong>Saturation — how full the system is.</strong> How close to a hard limit are you: memory used, disk full, queue depth, connection pool in use, thread pool utilisation. This is the leading indicator — saturation climbs before latency and errors do, which is what gives you time to act.</li>\n</ul>\n<p style=\"line-height: 1.75\">Start with those four for each user-facing service, add the handful of business metrics that would tell you revenue stopped, and resist the rest until an incident proves you needed it.
