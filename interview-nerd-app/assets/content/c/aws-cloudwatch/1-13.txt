{"title":"CloudTrail Lake — Event Data Stores, Federation, and Analysis","tags":["cloudtrail-lake","event-data-store","sql-analytics","compliance-retention"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">The classic way to analyse CloudTrail at volume is S3 plus Athena: a trail writes gzipped JSON into a bucket, you define an external table, you fight with partitions, and you write SQL that scans files. It works, and thousands of organizations run it. But you own the plumbing — the table definition, the partition strategy, the lifecycle policy, the Glue catalog, the query-results bucket. <strong>CloudTrail Lake</strong> is AWS's managed alternative: an <strong>event data store</strong> that ingests events directly, keeps them for years, and exposes SQL without you defining a single table. The senior question is not \"which is better\" but \"which cost and ownership model fits this requirement\", and that is what this topic builds toward.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Event data stores: what they are and what they hold</h4>\n<p style=\"line-height: 1.75\">An <strong>event data store</strong> is an immutable, append-only collection of events with its own retention period, its own encryption configuration, and its own SQL surface. It is created independently of trails — an event data store is <strong>not</strong> a consumer of a trail; it subscribes to the event stream itself, which means you can run Lake with no trail at all, or alongside one, and the selectors you configure on the store are separate from the selectors on any trail.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>CloudTrail management events.</strong> The control-plane record, filtered with the same advanced event selector fields you use on trails — <code>readOnly</code>, <code>eventName</code>, <code>eventSource</code>.</li>\n<li><strong>CloudTrail data events.</strong> Object-level and resource-level activity, scoped by <code>resources.type</code> and <code>resources.ARN</code> exactly as on a trail. The same economics apply: this is the volume that drives cost, so scope it.</li>\n<li><strong>CloudTrail Insights events.</strong> Anomalies in call rate and error rate, which can be stored and queried alongside the events that produced them.</li>\n<li><strong>AWS Config configuration items.</strong> This is the quietly powerful one. CloudTrail tells you what API call was made; Config tells you what the resulting <strong>resource state</strong> was. Putting both in one store lets a single SQL query join \"who called <code>AuthorizeSecurityGroupIngress</code>\" to \"what the security group's full rule set looked like afterwards\", which is otherwise a two-console investigation.</li>\n<li><strong>AWS Audit Manager evidence</strong>, for organizations already running formal control assessments.</li>\n<li><strong>Events from outside AWS.</strong> Through an <strong>integration</strong> and a channel, you can push your own activity events — from an on-premises system, a SaaS provider, a partner platform, or your own application's audit log — using the <code>PutAuditEvents</code> API, and they become queryable in the same SQL surface with the same retention guarantees. This is what turns Lake from \"a CloudTrail feature\" into \"an audit lake\".</li>\n</ul>\n<p style=\"line-height: 1.75\">Stores can be <strong>organization-wide</strong>, created from the management account or a registered delegated administrator, collecting every member account's events into one queryable surface — the same architectural pattern as an organization trail, and for the same reason: an investigator should ask one question once, not two hundred times.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Retention and the three-part cost model</h4>\n<p style=\"line-height: 1.75\">Lake bills in three distinct places, and conflating them is the most common costing mistake:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Ingestion</strong>, charged per GB of events written into the store. This is a one-time charge per event and is driven entirely by which events you select — so data events dominate here just as they do on trails.</li>\n<li><strong>Retention</strong>, charged for keeping the data. CloudTrail offers two pricing options chosen at store creation: a <strong>one-year extendable retention</strong> option, where roughly the first year is included in the ingestion price and additional retention up to a multi-year maximum is charged separately, and a <strong>seven-year retention</strong> option with a lower ingestion price and a fixed long retention. The choice is effectively \"cheap to ingest, pay to keep\" versus \"pay more up front, keep for years\" — and it is made when you create the store, so model your real retention obligation before creating it.</li>\n<li><strong>Query</strong>, charged per GB scanned, the same mental model as Athena. Time-bounded queries are cheap; unbounded <code>SELECT *</code> over a seven-year store is not.</li>\n</ul>\n<p style=\"line-height: 1.75\">The practical design consequence: <strong>ingest narrowly, retain deliberately, and always bound queries by <code>eventTime</code></strong>. A store whose selectors pull every S3 data event in the organization will be expensive in all three dimensions at once.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The SQL interface</h4>\n<p style=\"line-height: 1.75\">Queries are SQL against the event data store's ID as the table name, over a schema whose columns mirror the CloudTrail event record: <code>eventTime</code>, <code>eventName</code>, <code>eventSource</code>, <code>awsRegion</code>, <code>sourceIPAddress</code>, <code>userAgent</code>, <code>errorCode</code>, <code>errorMessage</code>, <code>recipientAccountId</code>, and the nested <code>userIdentity</code>, <code>requestParameters</code> and <code>responseElements</code> structures. You start a query with <code>StartQuery</code>, poll with <code>DescribeQuery</code>, and fetch with <code>GetQueryResults</code>; results can also be delivered to an S3 bucket for large outputs.</p>\n<p style=\"line-height: 1.75\">Two ergonomics notes that matter in practice. First, nested fields are addressed with dotted paths — <code>userIdentity.arn</code>, <code>userIdentity.sessionContext.sessionIssuer.userName</code> — which is considerably nicer than the JSON extraction gymnastics an Athena table over raw CloudTrail sometimes requires. Second, <strong>always filter on <code>eventTime</code> first</strong>: it is the dimension the store is organised by, and an unbounded query is the one way to make Lake expensive by accident.</p>\n<p style=\"line-height: 1.75\">Lake also provides <strong>dashboards</strong>: a set of curated views over your event data store covering things like top errors, most active principals and unusual activity, plus custom dashboards built from your own saved queries with a scheduled refresh. They are genuinely useful for the \"what does normal look like?\" question that precedes good detections, though they are not a substitute for a real BI or SIEM layer.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Lake federation: joining audit data with everything else</h4>\n<p style=\"line-height: 1.75\">By default a Lake store is queryable only through CloudTrail's own query interface, which is a hard boundary if your analysts live in Athena and your other datasets are in the Glue Data Catalog. <strong>Federation</strong> removes that boundary: enabling it on an event data store registers the store's metadata in the <strong>AWS Glue Data Catalog</strong> so it appears as a table queryable from <strong>Amazon Athena</strong> (and other Glue-aware engines), using a federation IAM role that CloudTrail assumes to expose the data.</p>\n<p style=\"line-height: 1.75\">What that unlocks is joins. Audit data becomes just another table, so you can join CloudTrail activity to your CMDB or resource-inventory table to attribute events to owning teams, to a Cost and Usage Report table to connect an API call to the spend it generated, to VPC flow logs to correlate a control-plane action with the network activity around it, or to an HR or identity-provider export to map a federated session to a person and their employment status. That last one is how you answer \"did any departed employee's access get used after their last day?\" in a single query. Federation queries are billed by the query engine you use — Athena's per-TB-scanned model — layered on top of Lake's own charges, so partition-style filtering on <code>eventTime</code> still matters.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Lake versus S3 plus Athena: the honest comparison</h4>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\">\n<th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Dimension</th>\n<th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">CloudTrail Lake</th>\n<th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">S3 + Athena</th>\n</tr></thead>\n<tbody>\n<tr>\n<td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Cost model</td>\n<td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Ingestion per GB + retention + per GB scanned. That is not indecision; it is matching each store to the access pattern it actually serves.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Importing years of existing S3 archives</h4>\n<p style=\"line-height: 1.75\">A new event data store starts empty and only captures events from its creation forward, which is exactly the wrong shape for an organization that has years of history in S3. The answer is the <strong>import</strong> capability: <code>aws cloudtrail start-import</code> copies existing trail logs from one or more S3 locations into an event data store, with an optional start and end time. You point it at the trail's S3 prefix, give CloudTrail a role that can read the bucket and the KMS key, and it backfills.</p>\n<p style=\"line-height: 1.75\">Three considerations for a senior answer. <strong>Cost</strong>: imported events are billed as ingestion, so importing seven years of an organization's full history — data events included — can be a genuinely large one-time charge, which is why you scope the import by time window and, where possible, by which prefixes you import. <strong>Time</strong>: large imports run for a long while and should be monitored with <code>list-import-failures</code>; failures on a subset of files are normal enough that you should check rather than assume. <strong>Judgement</strong>: usually you do not need all of it. Import the window that matches your active investigation needs — commonly one to two years — and leave the deeper archive in S3 where Athena can still reach it if a legal request ever demands it. Keeping the S3 archive regardless is the right default: it is the cheap, immutable copy, and Lake is a query convenience, not a replacement for the system of record.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Access control on audit data</h4>\n<p style=\"line-height: 1.75\">Audit data is sensitive: request parameters leak resource names, internal topology, bucket and table layouts, and sometimes the shape of your customer data. Query access should be a deliberate grant, not a side effect of being an administrator.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Separate reading from managing.</strong> <code>cloudtrail:StartQuery</code>, <code>cloudtrail:DescribeQuery</code> and <code>cloudtrail:GetQueryResults</code> on a specific event data store ARN form the analyst grant. <code>cloudtrail:UpdateEventDataStore</code>, <code>DeleteEventDataStore</code> and <code>StopIngestion</code> are administrative and belong to a much smaller group, protected by an SCP for everyone else.</li>\n<li><strong>Scope to the store, not to <code>*</code>.</strong> Resource-level permissions on event data store ARNs let you have, for example, an application-team store they can query and a security store they cannot.</li>\n<li><strong>Protect deletion.</strong> An event data store can be given <strong>termination protection</strong>, and deletion is a soft delete with a waiting period during which it can be restored — a meaningful safety net against both accident and malice, but do not rely on it alone; the SCP is the real control.</li>\n<li><strong>Encrypt with your own key.</strong> A customer managed KMS key on the store gives a second, independently revocable authorization checkpoint on the data.</li>\n<li><strong>Log the auditors.</strong> Queries against Lake are themselves CloudTrail management events. Alerting on who queries the audit store — particularly broad queries by unusual principals — is a control worth having, and it is the kind of detail that marks a security-mature answer.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario: Lake or Athena for a seven-year mandate?</h4>\n<p style=\"line-height: 1.75\"><strong>Constraints.</strong> A financial services organization must retain audit records for seven years and produce evidence on request within days. Roughly 4 TB of CloudTrail data accrues per year, mostly data events on a small number of regulated S3 buckets. The security team is three people. Investigations look back 90 days in almost every case; the seven-year requirement is regulatory, not operational.</p>\n<p style=\"line-height: 1.75\"><strong>Analysis.</strong> The two requirements have completely different access patterns and should not be served by the same store. The seven-year mandate is <strong>write-once, read-almost-never</strong>, and Lake's ingestion-plus-retention pricing charges you for durability you will rarely exercise; 28 TB in S3 with lifecycle tiering to Glacier is dramatically cheaper, and Object Lock in compliance mode gives an immutability story that stands up better in an audit than \"the service does not let us delete it\". The 90-day investigative pattern is the opposite: frequent, urgent, ad hoc, run by a three-person team who should not be maintaining partition projection and Parquet conversion pipelines.</p>\n<p style=\"line-height: 1.75\"><strong>Recommendation.</strong> S3 as the system of record for the full seven years — organization trail, Object Lock compliance mode with a seven-year default retention, lifecycle transition to Glacier after 90 days, log file validation on, and a documented, <strong>rehearsed</strong> procedure for restoring and querying archived data with Athena when a regulator asks. In parallel, a CloudTrail Lake event data store holding management events organization-wide plus data events for the regulated buckets only, with a shorter retention aligned to the investigative window, as the day-to-day surface. Enable federation so the store joins to the resource-ownership table for attribution. If the organization later needs history in Lake for a specific investigation, <code>start-import</code> can backfill that window on demand rather than paying to ingest seven years up front.
