{"title":"What Is AWS CloudTrail — The Audit Trail of Every API Call","tags":["cloudtrail","auditing","security","governance"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">It is Monday morning and the S3 bucket holding your production reports is gone. Not empty — gone. Nobody on the team admits to touching it. From what IP address? Was it a person, a CI/CD pipeline, or a compromised key?</p>\n<p style=\"line-height: 1.75\">Every metric and log you have is useless here. CloudWatch can show you that the bucket's request count dropped to zero, but it cannot tell you who deleted it. The service that answers \"who did what\" is <strong>AWS CloudTrail</strong>.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What CloudTrail is, in one sentence</h4>\n<p style=\"line-height: 1.75\"><strong>CloudTrail is a service that records the API calls made in your AWS account — essentially every action taken through the console, the CLI, an SDK, or by an AWS service acting on your behalf — and stores them as searchable event records.</strong></p>\n<p style=\"line-height: 1.75\">The term of art for this is an <strong>audit trail</strong>: a chronological, tamper-evident record of who did what and when, kept so that actions can be reconstructed and attributed after the fact. Banks keep audit trails of transactions; CloudTrail keeps one of your cloud.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why CloudTrail sees so much: almost everything is an API call</h4>\n<p style=\"line-height: 1.75\">An <strong>API call</strong> is a structured request one program makes to another asking it to do something — here, your request asking an AWS service to act. The essential insight for understanding CloudTrail is that <strong>almost everything in AWS is an API call, including clicking a button in the console</strong>.</p>\n<p style=\"line-height: 1.75\">The AWS Management Console is not a privileged inner interface. It is a web application that, when you click \"Launch instance\", constructs and sends the exact same <code>RunInstances</code> API call that the CLI or an SDK would send. The simplest case.</li>\n<li><strong>AssumedRole.</strong> The common case in well-run accounts. A <strong>role</strong> is a set of permissions anyone authorized can temporarily \"wear\" instead of holding permanent credentials. The identity looks like <code>AROAEXAMPLE:alice-session</code>. The part after the colon is the <strong>session name</strong> — the label chosen when the role was assumed, and often the only clue to the human behind it. Look inside <code>sessionContext.sessionIssuer</code> for the role's name, and check <code>mfaAuthenticated</code> to see whether multi-factor authentication was used.</li>\n<li><strong>AWSService.</strong> An AWS service acting on your behalf, shown as e.g. <code>autoscaling.amazonaws.com</code>. If Auto Scaling terminated your instance, this is how you know it was automation rather than a person.</li>\n<li><strong>Root.</strong> The account's original all-powerful login. Root activity should be extremely rare, and an alarm on it is a standard security baseline.</li>\n<li><strong>AWSAccount / FederatedUser.</strong> A principal from another account, or someone signed in through an external identity provider such as your corporate SSO.</li>\n</ul>\n<p style=\"line-height: 1.75\">This is why session naming conventions matter. If everyone assumes a role with the session name \"session\", CloudTrail can tell you the role but not the human. Make SSO or your role-assumption tooling put the username in the session name and every record becomes attributable.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What you get for free: Event history</h4>\n<p style=\"line-height: 1.75\">Good news for beginners: <strong>CloudTrail is already on</strong>. Every AWS account records recent management activity automatically, and you can view and search it in the console under <strong>Event history</strong> — the last <strong>90 days</strong>, at <strong>no charge</strong>, with no setup at all. If a bucket vanished last Tuesday, you can answer that question right now.</p>\n<p style=\"line-height: 1.75\">The limits matter though. Event history covers <strong>management events only</strong> (operations that manage resources), keeps just <strong>90 days</strong>, is <strong>per-region</strong>, and offers only simple attribute filters rather than rich querying. To keep events longer, deliver them to S3 for analysis, log data-plane activity, or aggregate across regions and accounts, you must create a <strong>trail</strong> — a configuration that continuously delivers CloudTrail events to a destination you own. Trails are their own topic; the key beginner takeaway is: the last 90 days are free and automatic, anything beyond that is a deliberate configuration.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; A denied call appears with <code>errorCode</code> of <code>AccessDenied</code> (or <code>UnauthorizedOperation</code> for EC2) plus an <code>errorMessage</code>.</p>\n<p style=\"line-height: 1.75\">This makes CloudTrail a first-class <strong>permissions debugging tool</strong>, not just a security one. On the security side, a burst of AccessDenied errors from one principal is a classic signature of credentials being probed by someone who does not know what they can do.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What beginners actually use it for</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"Who deleted this?\"</strong> Filter Event history by resource name or by event name such as <code>DeleteBucket</code>, then read <code>userIdentity</code>, <code>eventTime</code> and <code>sourceIPAddress</code>.</li>\n<li><strong>\"Why is this call denied?\"</strong> Find the failed event and read the exact action and principal instead of guessing at policies.</li>\n<li><strong>\"What did this role actually do?\"</strong> Filter by the role's user name to see its real behaviour — invaluable for tightening over-broad permissions toward least privilege.</li>\n<li><strong>\"When did this configuration change?\"</strong> Correlate a CloudWatch performance change with a CloudTrail configuration change at the same minute. This is the fastest root-cause technique there is.</li>\n<li><strong>Compliance evidence.</strong> Auditors for SOC 2, PCI DSS, HIPAA and ISO 27001 ask you to demonstrate that administrative actions are logged and attributable. CloudTrail is the standard answer.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"CloudTrail logs my application's requests.\"</strong> No. It logs calls to the <strong>AWS control plane</strong>. A user hitting <code>/api/checkout</code> on your web app is invisible to CloudTrail — that belongs in your own application logs or an ALB access log.</li>\n<li><strong>\"CloudTrail is real time.\"</strong> It is not. It is a record of actions, not of data.</li>\n<li><strong>\"I don't need a trail because Event history exists.\"</strong> Event history is 90 days, management events only, per-region, and not exportable for real analysis. Any serious security or compliance posture requires a trail.</li>\n<li><strong>\"userIdentity always names a person.\"</strong> With roles you often get a role ID and a session name. Attribution depends on good session-naming conventions.</li>\n<li><strong>\"CloudTrail prevents bad actions.\"</strong> It is <strong>detective</strong>, not preventive.
