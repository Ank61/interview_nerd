{"title":"Container and Kubernetes Observability — Container Insights, Fluent Bit, ADOT, and Prometheus","tags":["container-insights","eks","fluent-bit","adot-prometheus"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Container platforms break every assumption that host-based monitoring was built on. A host has a name, a lifetime measured in months, and a stable set of processes; a <strong>pod has a random name, may live for ninety seconds, and is one of forty replicas that are individually uninteresting</strong>. If you carry host thinking into Kubernetes you end up with dashboards keyed on instance ids that churn daily, alarms that fire because a node was replaced, and — the worst failure — logs that disappear along with the container that wrote them. The senior framing is that container observability requires three shifts: the <em>unit of interest</em> moves from host to workload (deployment, service, task definition), <em>collection must be external to the workload</em> because the workload is ephemeral, and <em>cardinality becomes the dominant cost and performance risk</em> because Kubernetes hands you unbounded labels by default.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why Naive Monitoring Fails on Containers</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Ephemerality.</strong> A container that crashes on startup may exist for two seconds. Anything that polls it, or that expects to read a file from it after the fact, gets nothing. Collection must be pull-from-outside or push-as-you-go, never after-the-fact.</li>\n<li><strong>The wrong unit.</strong> Nobody cares that pod <code>orders-7d9f8c-x2lq9</code> restarted; they care that the <code>orders</code> deployment's restart rate is non-zero. Aggregation must happen along stable workload identifiers, with pod identity available for drill-down but never as the primary key.</li>\n<li><strong>Shared hosts.</strong> Node-level CPU and memory tell you almost nothing about which tenant workload is responsible, and a node at 60% memory can still be evicting pods because of requests and limits rather than raw usage.</li>\n<li><strong>stdout is the contract.</strong> Container logs go to the runtime's stdout/stderr and are rotated and deleted by the node. Something must ship them before the container disappears, and that something has to survive the container's death.</li>\n<li><strong>Scheduling is a first-class failure mode.</strong> On a VM, \"the process is not running\" is one condition. On Kubernetes it splits into pending-because-unschedulable, image pull failure, CrashLoopBackOff, OOMKilled, evicted, and failing readiness — each with a different fix, and none visible from CPU graphs.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Container Insights for ECS and EKS</h4>\n<p style=\"line-height: 1.75\"><strong>Container Insights</strong> is CloudWatch's managed container monitoring layer. It collects and aggregates telemetry into a set of curated metrics in the <code>ContainerInsights</code> namespace and renders them as pre-built dashboards and maps, so you get useful views without building them. It is what makes Container Insights a genuine troubleshooting tool rather than a set of graphs, and it is billed on observations, so it costs materially more on a large cluster. <strong>Deployment</strong> differs by platform: on <strong>EKS</strong> the supported path is the <em>Amazon CloudWatch Observability EKS add-on</em>, which installs the CloudWatch agent (as a DaemonSet) and Fluent Bit and can also enable Application Signals; on <strong>ECS</strong> you enable it as an account setting or per cluster, with the agent running as part of the platform for Fargate tasks. The honest cost consideration: Container Insights metrics are <strong>custom metrics</strong>, and their volume scales with clusters times nodes times pods times metric count, so a large multi-tenant cluster can generate a surprising number of them. The usual mitigations are enabling enhanced observability selectively (production clusters, not every dev cluster), and accepting Container Insights for platform-level signals while application-level metrics come from EMF or Prometheus where you control cardinality directly.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Log Collection: awslogs, FireLens, and Fluent Bit</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>The awslogs driver (ECS).</strong> The simplest option: the Docker/containerd log driver writes container stdout directly to a CloudWatch log group, with a stream per task. It works everywhere and needs no sidecar. Its two important properties are that it does <em>no</em> filtering or transformation — you pay to ingest every byte the container prints — and that in its default <strong>blocking</strong> mode a slow or throttled CloudWatch Logs endpoint applies back-pressure to the container's writes, which can stall the application itself. Setting <code>mode=non-blocking</code> with a sized <code>max-buffer-size</code> converts that into dropped logs instead of a stalled service, which is almost always the correct trade for a request-serving workload.</li>\n<li><strong>FireLens with AWS for Fluent Bit (ECS).</strong> FireLens is the ECS integration that attaches a <em>log router</em> container to the task; the AWS-maintained <code>aws-for-fluent-bit</code> image is the usual implementation. This is where filtering, parsing, enrichment and multi-destination routing happen: drop health-check lines and framework noise <em>at the collector</em> so you never pay to ingest them, parse plain text into JSON before it lands, reassemble multi-line stack traces into single events, and route different streams to different destinations — errors to CloudWatch Logs, everything to S3 via Firehose, a security subset to a SIEM. The economic point is the important one in interviews: <strong>filtering at the collector is free; filtering at query time means you already paid for the data.</strong></li>\n<li><strong>Fluent Bit as a DaemonSet (EKS).</strong> One Fluent Bit pod per node tails <code>/var/log/containers</code>, uses the <em>kubernetes</em> filter to enrich each record with namespace, pod, container, labels and annotations from the API server, and outputs to CloudWatch Logs (or Firehose, S3, OpenSearch). The CloudWatch Observability add-on deploys this for you. Operational details that matter: resource limits on the collector itself so it cannot starve workloads, on-disk buffering so a CloudWatch Logs blip does not lose data, log group naming that groups by namespace or workload rather than by pod, and being deliberate about which namespaces are collected at all.</li>\n<li><strong>What to alarm on in the log path.</strong> Fluent Bit's own output metrics — retries, dropped records — plus a heartbeat from each workload, because a collector that silently stops looks exactly like a quiet service.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">AWS Distro for OpenTelemetry</h4>\n<p style=\"line-height: 1.75\"><strong>ADOT</strong> is AWS's supported distribution of the OpenTelemetry Collector and SDKs. The collector is configured as a <strong>pipeline</strong> with three stages, and understanding that model is the thing interviewers probe:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Receivers</strong> ingest telemetry: <code>otlp</code> for anything instrumented with OpenTelemetry, <code>prometheus</code> to scrape Prometheus endpoints, plus host and container receivers.</li>\n<li><strong>Processors</strong> transform in flight: <code>batch</code> for efficiency, <code>memory_limiter</code> to protect the collector, <code>resourcedetection</code> to attach cluster/node/account attributes, <code>k8sattributes</code> to enrich with pod metadata, <code>filter</code> and <code>attributes</code> to drop metrics or strip high-cardinality labels <em>before</em> they cost anything. This stage is where cardinality control lives.</li>\n<li><strong>Exporters</strong> emit: <code>awsemf</code> writes metrics to CloudWatch via Embedded Metric Format, <code>awsxray</code> sends traces to X-Ray, <code>prometheusremotewrite</code> ships to Amazon Managed Service for Prometheus, <code>awscloudwatchlogs</code> for logs, and any OTLP-speaking vendor backend.</li>\n</ul>\n<p style=\"line-height: 1.75\">It runs as a sidecar, a DaemonSet, a Deployment (gateway pattern) or via the ADOT Operator on EKS. The strategic argument for OpenTelemetry — the one to make in an interview — is <strong>vendor choice</strong>: instrumentation is the expensive, long-lived investment, and OTel decouples it from the backend. Your application emits OTLP; changing where telemetry lands becomes an exporter configuration change rather than a re-instrumentation project. That also enables dual-shipping during a migration and per-signal routing (traces to X-Ray, metrics to Prometheus, logs to CloudWatch) from one agent.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Prometheus, AMP and Managed Grafana in the AWS Context</h4>\n<p style=\"line-height: 1.75\">Kubernetes ecosystems are Prometheus-native: exporters, <code>ServiceMonitor</code> conventions, PromQL and community dashboards all assume it. <strong>Amazon Managed Service for Prometheus (AMP)</strong> provides the storage and query side as a managed, horizontally scaled service — you <em>remote-write</em> from an agent-mode Prometheus or from an ADOT collector, query with <strong>PromQL</strong>, and use its ruler for recording rules and alerting rules with Alertmanager-compatible routing. <strong>Amazon Managed Grafana</strong> provides visualization with managed identity integration and data sources for AMP, CloudWatch, X-Ray, OpenSearch and others in one workspace.</p>\n<p style=\"line-height: 1.75\">The realistic posture is <strong>combination, not exclusivity</strong>, and candidates who insist on picking one are usually wrong. CloudWatch is unavoidable and genuinely better for AWS service metrics — RDS, ALB, SQS, Lambda, quotas, and anything with an AWS-native alarm integration — and it is where alarms wire naturally into SNS, EventBridge and AWS incident tooling. Prometheus is better for application and Kubernetes-internal metrics: high-dimensional, cheap to emit, with PromQL's rate, histogram_quantile and label-manipulation functions that CloudWatch metric math cannot match. A common and defensible architecture is: Container Insights plus CloudWatch for platform and AWS-managed dependencies, AMP for application and Kubernetes metrics scraped by ADOT, Grafana as the single visualization layer over both, X-Ray or an OTLP backend for traces, and alerting split so page-worthy conditions land in one incident tool regardless of which system evaluated them.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Kubernetes Signals That Actually Matter</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Pod restarts and CrashLoopBackOff.</strong> A rising restart count is the single highest-value Kubernetes alarm. Distinguish <strong>OOMKilled</strong> (limit too low or a leak — check memory usage against limit) from application crash (check the <em>previous</em> container's logs, which is why shipping logs off-node matters) from failing liveness probes (probe too aggressive, or a genuinely wedged process).</li>\n<li><strong>Pending pods and scheduling failures.</strong> Pods stuck Pending mean the scheduler cannot place them: insufficient allocatable CPU/memory, node selectors or affinity that match nothing, taints without tolerations, unavailable persistent volumes in the right zone, or a cluster autoscaler that cannot scale (quota, subnet IP exhaustion). Alarm on pending duration, not pending count, and pair it with autoscaler logs.</li>\n<li><strong>Node pressure and conditions.</strong> <code>MemoryPressure</code>, <code>DiskPressure</code>, <code>PIDPressure</code> and <code>NotReady</code> precede evictions. Disk pressure on nodes is frequently caused by <em>log files</em>, which is a nice illustration that the observability system can cause the incident.</li>\n<li><strong>HPA behaviour.</strong> Watch current versus desired replicas, whether the HPA is pinned at max (under-provisioned) or flapping (metric too noisy or stabilization window too short), and whether it can read its metric at all — an HPA whose metrics API is broken silently stops scaling.</li>\n<li><strong>EKS control-plane logs.</strong> Optional log types — API server, audit, authenticator, controller manager, scheduler — delivered to CloudWatch Logs. The <strong>audit</strong> log answers \"who changed this\" and is the one security teams require; the <strong>scheduler</strong> log explains unschedulable pods; the <strong>authenticator</strong> log explains IAM-to-Kubernetes auth failures. They are off by default and are not free, so enable deliberately, with audit almost always on in production.</li>\n<li><strong>The golden signals still apply.</strong> Request rate, error rate, latency and saturation per service remain the alerting backbone; Kubernetes signals explain <em>why</em>, they are not a substitute for symptom-based alerts.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cardinality: The Kubernetes-Specific Trap</h4>\n<p style=\"line-height: 1.75\">Kubernetes generates unbounded identifiers as a matter of routine — pod names with random suffixes, pod UIDs, container ids, replica set names that change on every deploy, and node names in an autoscaled fleet. Attach any of these as a metric dimension or Prometheus label and you create a <strong>new time series per pod per deploy</strong>. In CloudWatch each unique dimension combination is a separately billed custom metric, and a deploy that rolls forty pods creates forty new metrics that will never receive another datapoint but are still charged and still clutter every metric search. In Prometheus and AMP the same mistake shows up as memory growth, slow queries and ingestion limits.</p>\n<p style=\"line-height: 1.75\">The discipline: <strong>aggregate along stable identifiers — namespace, deployment or service, container name, cluster — and keep pod identity in logs and traces rather than in metric dimensions.</strong> Enforce it in the collector, where it is cheap: use <code>metric_relabel_configs</code> in the Prometheus scrape config or the OpenTelemetry <code>attributes</code>/<code>filter</code> processors to drop <code>pod</code>, <code>pod_uid</code>, <code>instance</code> and <code>id</code> labels before export. The same rule applies to application labels: never label by customer id, request path with embedded ids, or full URL. Where you genuinely need per-pod detail for an investigation, it is available in Container Insights drill-down and in logs — which is the correct place for high-cardinality facts.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Production Scenario: Observability for a Multi-Tenant EKS Platform</h4>\n<p style=\"line-height: 1.75\">A platform team runs EKS clusters hosting dozens of internal teams' services, and must serve three audiences: the platform team (is the cluster healthy?), each tenant team (is my service healthy?), and finance (who is consuming what?). The design:</p>\n<p style=\"line-height: 1.75\"><strong>Collection.</strong> Deploy the CloudWatch Observability EKS add-on for Container Insights with enhanced observability on production clusters only, giving platform-level cluster/node/pod metrics plus Fluent Bit for logs. Alongside it, run an <strong>ADOT collector</strong> — DaemonSet for node-local scraping, plus a gateway Deployment for OTLP from applications — scraping tenant application metrics via Prometheus annotations and remote-writing to <strong>AMP</strong>, exporting traces to X-Ray, and applying <code>k8sattributes</code> for enrichment and <code>filter</code>/<code>attributes</code> processors to strip pod-level labels before export. <strong>Logs.</strong> Fluent Bit routes by namespace so each tenant's logs land in a log group named for their namespace — which gives per-tenant retention, per-tenant IAM scoping and per-tenant cost visibility in one decision. Health-check and known framework noise is dropped in the collector; verbose namespaces get a shorter retention and an Infrequent Access log group. <strong>Isolation.</strong> Tenants get IAM and Grafana permissions scoped to their own namespaces' log groups and metric labels, so nobody browses another team's data.</p>\n<p style=\"line-height: 1.75\"><strong>Alerting split by audience.</strong> Platform alarms on cluster capacity, node NotReady counts, pending-pod duration, control-plane error rates and collector health page the platform on-call. Tenant alarms on their own golden signals — error rate, p99 latency, saturation — plus pod restart rate and HPA pinned-at-max page the tenant team; these come from a shared module so severity and naming are consistent, and route through one incident tool. <strong>Visualization.</strong> Amazon Managed Grafana as the single pane, with CloudWatch and AMP data sources and a templated per-tenant dashboard so every team gets the same shape of view, plus a platform dashboard. <strong>Control plane.</strong> EKS audit and authenticator logs on in production, shipped to the security log archive account, with a metric filter alarming on authorization failure spikes. <strong>Cost.</strong> Per-namespace log groups plus tags make ingestion attributable per tenant and publishable back to them; enhanced observability is limited to production; and cardinality rules are enforced in the collector rather than by asking forty teams to behave. <strong>The failure mode to design against explicitly</strong> is the observability stack causing the incident: resource limits on Fluent Bit and the collector, disk-pressure alarms on nodes, and an alarm on collector dropped-record counts, because a platform that cannot see is worse than one that is merely slow.</p>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"Containers are ephemeral, so collection has to be external and continuous: Container Insights via the CloudWatch Observability add-on for cluster, node and pod metrics, and Fluent Bit or FireLens shipping stdout before the container disappears — filtering noise at the collector, because filtering at query time means you already paid to ingest it.
