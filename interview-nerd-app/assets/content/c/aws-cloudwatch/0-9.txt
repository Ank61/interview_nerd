{"title":"CloudWatch Events and Amazon EventBridge — Reacting to What Happens","tags":["eventbridge","cloudwatch-events","event-driven","scheduled-rules"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Metrics and logs tell you what happened <em>after</em> you go looking. But plenty of things in AWS deserve an immediate, automatic reaction: an EC2 instance terminated and you want to clean up its DNS record, a security group was changed and you want to be told within seconds, or midnight arrived and a nightly report needs generating. The AWS service for \"when X happens, automatically do Y\" is <strong>Amazon EventBridge</strong>.</p>\n<p style=\"line-height: 1.75\">One sentence of history, because it matters in interviews: the feature launched as <strong>CloudWatch Events</strong>, then grew into <strong>Amazon EventBridge</strong>. They are the same underlying capability — EventBridge is the current name and a strict superset, and old rules still show up under both consoles and APIs. If an interviewer or an old blog post says \"CloudWatch Events\", they mean EventBridge.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What an \"event\" actually is</h4>\n<p style=\"line-height: 1.75\">An <strong>event</strong> is a small JSON message announcing that something happened. It is not a command and it does not ask anyone to do anything — it is a factual notice, past tense: \"instance i-0abc123 changed state to terminated\", \"an object was created in bucket customer-uploads\", \"it is now 02:00 UTC\".</p>\n<p style=\"line-height: 1.75\">Every event has the same envelope of fields: <code>source</code> (which service emitted it, such as <code>aws.ec2</code>), <code>detail-type</code> (a short human-readable label like <code>EC2 Instance State-change Notification</code>), <code>time</code>, <code>region</code>, <code>account</code>, <code>resources</code> (the ARNs involved), and <code>detail</code> — a nested object with the service-specific payload. That predictable envelope is what makes filtering possible.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The three pieces: bus, rule, target</h4>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">AWS services  <i class=c>--+</i>\nYour own apps <i class=c>--+--&gt; [ EVENT BUS ] --&gt; [ RULE ] --&gt; [ TARGET(s) ]</i>\nPartner SaaS  <i class=c>--+     the channel      the filter    what runs</i>\nA schedule    <i class=c>--+                                     (Lambda, SNS,</i>\n                                                       SQS, ECS, ...)\n\n<i class=k>One</i> bus, many rules. <i class=k>One</i> rule, up <i class=k>to</i> <i class=n>5</i> targets.\nA rule that <i class=k>matches</i> nothing simply never fires <i class=o>-</i> silently.</code></pre></div>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Event bus — the channel events flow through.</strong> Think of it as a pipe that events are dropped into and that rules listen on. Every account gets a <strong>default event bus</strong> automatically, and all AWS service events land there at no charge. You can create <strong>custom event buses</strong> to carry your own application's events, which keeps your domain events separate from the noisy stream of AWS ones. <strong>Partner event buses</strong> receive events directly from third-party SaaS products such as Datadog, Zendesk or Shopify, so their webhooks become native AWS events.</li>\n<li><strong>Rule — the filter that decides what you care about.</strong> A bus carries an enormous amount of traffic; a rule is the standing instruction that says \"out of everything on this bus, I want these\". A rule works in one of two modes: it matches an <strong>event pattern</strong>, or it fires on a <strong>schedule</strong>. It cannot do both.</li>\n<li><strong>Target — what gets invoked when a rule matches.</strong> EventBridge delivers the matching event as JSON to the target. Common targets: <strong>Lambda</strong> functions (run code), <strong>SNS</strong> topics (fan out a notification to email, SMS or a webhook), <strong>SQS</strong> queues (buffer the event for a worker to pick up later), <strong>Step Functions</strong> state machines (start a multi-step workflow), <strong>ECS</strong> tasks (run a container), <strong>Systems Manager</strong> Automation documents (run remediation), Kinesis streams, API destinations (call any external HTTPS endpoint), and another event bus in a different account or region. A single rule can have up to five targets, all invoked in parallel.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Event patterns: filtering by content</h4>\n<p style=\"line-height: 1.75\">An <strong>event pattern</strong> is JSON shaped like the events you want to catch. The matching rule is simple: for every field you name in the pattern, the event's value must be in the list you provide; any field you do not mention is ignored entirely. So a pattern naming only <code>source</code> catches every event from that service, and adding more fields narrows it.</p>\n<p style=\"line-height: 1.75\">Note that pattern values are always <strong>arrays</strong>, even for a single value — <code>\"source\": [\"aws.ec2\"]</code>, not a bare string. Forgetting the brackets is the number one reason a beginner's rule never fires. Beyond plain equality, patterns support content filters such as <code>prefix</code>, <code>anything-but</code>, <code>exists</code>, and numeric comparisons.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Scheduled rules: the standard answer to \"run this every night\"</h4>\n<p style=\"line-height: 1.75\">Instead of an event pattern, a rule can carry a <strong>schedule expression</strong>. EventBridge then generates the trigger itself on a timer. This is the normal, expected answer to \"how do I run a Lambda function every night at 2 a.m.?\" — you do not need a server running cron, you create a scheduled rule.</p>\n<p style=\"line-height: 1.75\">There are two formats. A <strong>rate expression</strong> means \"every N units\" measured from when you created the rule: <code>rate(5 minutes)</code>, <code>rate(1 hour)</code>, <code>rate(7 days)</code>. Use the singular unit when the value is 1. A <strong>cron expression</strong> pins execution to specific clock times. \"cron\" comes from the classic Unix scheduler; it is six fields separated by spaces, each saying which values of that time unit are allowed.</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Expression</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">When it fires</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><code>rate(15 minutes)</code></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Every 15 minutes, forever</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><code>cron(0 2 * * ? *)</code></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">02:00 UTC every day</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><code>cron(30 18 ? * MON-FRI *)</code></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">18:30 UTC Monday to Friday</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><code>cron(0 0 1 * ? *)</code></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Midnight UTC on the 1st of every month</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><code>cron(0/10 8-17 ? * MON-FRI *)</code></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Every 10 min, 08:00-17:00 UTC, weekdays</td></tr>\n</tbody>\n</table>\n</div>\n<p style=\"line-height: 1.75\">The six cron fields are <strong>minutes, hours, day-of-month, month, day-of-week, year</strong>. For new scheduling work, prefer EventBridge Scheduler; know scheduled rules because they are everywhere in existing systems and in exam questions.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Concrete things beginners actually build</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Clean up after a terminated instance.</strong> Match <code>EC2 Instance State-change Notification</code> with state <code>terminated</code>, target a Lambda that removes the instance from a DNS record and a monitoring inventory.</li>\n<li><strong>Notify Slack when an alarm changes state.</strong> CloudWatch alarms emit <code>CloudWatch Alarm State Change</code> events. A rule on <code>aws.health</code> can page the on-call engineer automatically instead of relying on someone noticing an email.</li>\n<li><strong>Trigger a pipeline on a new file.</strong> S3 object-created events go to EventBridge, letting a rule fan the same upload out to several independent consumers.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The relationship with CloudTrail</h4>\n<p style=\"line-height: 1.75\">Some AWS services publish native events to EventBridge on their own. But a great many actions reach EventBridge only because <strong>CloudTrail</strong> — the service that records the API calls made in your account — sees them and feeds them through. These arrive with <code>detail-type</code> of <code>AWS API Call via CloudTrail</code>, and the <code>detail</code> field contains the CloudTrail record itself, including who made the call.</p>\n<p style=\"line-height: 1.75\">This is powerful because it means you can react to <em>any</em> recorded API call, not just the handful of native events. Someone widened a security group with <code>AuthorizeSecurityGroupIngress</code>, disabled a trail with <code>StopLogging</code>, or created an IAM user — a rule can match that within a couple of minutes and invoke a Lambda that alerts security or automatically reverts the change. The important caveat: only <strong>management events</strong> flow this way by default. CloudTrail <strong>data events</strong> (such as individual S3 object reads) must be explicitly enabled to reach EventBridge, and latency is typically a couple of minutes, so call this \"near real time\", never \"instant\".</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">When a target fails: retries and dead-letter queues</h4>\n<p style=\"line-height: 1.75\">If EventBridge cannot deliver an event — the Lambda threw an error, was throttled, or the target was temporarily unavailable — it retries automatically with <strong>exponential backoff</strong> (waiting progressively longer between attempts). You can configure the maximum retry attempts and the maximum event age; by default EventBridge keeps trying for up to 24 hours.</p>\n<p style=\"line-height: 1.75\">If every attempt fails, the event is <strong>discarded</strong> unless you configured a <strong>dead-letter queue (DLQ)</strong> — an SQS queue that catches events that could not be delivered. Without a DLQ, a failed delivery is gone with no record of what you lost. Configuring a DLQ on any rule that matters, and alarming on its message count, is standard practice.</p>\n<p style=\"line-height: 1.75\">Delivery is <strong>at-least-once</strong>: in rare cases a target may receive the same event twice. Your target code should therefore be <strong>idempotent</strong> — safe to run twice with the same result — for example by checking whether the work was already done before doing it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"CloudWatch Events and EventBridge are different services.\"</strong> Same capability, one grew into the other. Duplicates are possible; make targets idempotent.</li>\n<li><strong>\"Schedules are precise to the second.\"</strong> They are not. Scheduled rules have a best-effort granularity of about a minute and can fire a minute or so late. EventBridge is a router, not a store — an event is matched, delivered and gone.
