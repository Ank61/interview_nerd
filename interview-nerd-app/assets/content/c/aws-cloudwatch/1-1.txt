{"title":"CloudWatch Metric Streams and Third-Party Observability Integration","tags":["metric-streams","firehose","opentelemetry","vendor-integration"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Every organization that adopts a third-party observability vendor eventually hits the same wall: how do you get AWS-generated metrics — ELB, RDS, Lambda, DynamoDB, your own custom namespaces — into Datadog, New Relic, Splunk, Dynatrace or a self-hosted stack, continuously, for thousands of metrics, without melting the CloudWatch API? The historical answer was API polling, and it does not scale. <strong>CloudWatch Metric Streams</strong> is the push-based answer, and understanding when the crossover happens between polling and streaming is exactly the sort of quantitative trade-off question a senior interview is looking for.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why the Pull Model Breaks</h4>\n<p style=\"line-height: 1.75\">A vendor integration built on polling calls <code>GetMetricData</code> on a schedule for every metric it wants. Three things go wrong as the estate grows:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Throughput ceiling.</strong> GetMetricData accepts a bounded number of metric queries per request (on the order of 500) and the API has a transactions-per-second quota per account and Region. Ten thousand metrics polled every minute means many requests every minute, and once several integrations, dashboards and alarm evaluations share the same quota you start getting throttled. Throttling is the classic failure signature — the vendor's graphs develop gaps that look like an outage but are an API limit.</li>\n<li><strong>Discovery lag.</strong> A poller can only ask for metrics it knows about, so it must periodically call <code>ListMetrics</code> to discover new resources. An instance launched and terminated between discovery cycles may never be polled at all, which is fatal for autoscaling and serverless fleets.</li>\n<li><strong>Cost and latency.</strong> GetMetricData is billed per metric requested, so the polling bill scales with metrics x poll frequency. And you inherit two latencies stacked: the time for a metric to become available in CloudWatch, plus up to a full poll interval before anyone asks for it. Typical end-to-end freshness is several minutes, which is poor for a vendor you are paying for real-time alerting.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">How Metric Streams Work</h4>\n<p style=\"line-height: 1.75\">A metric stream is an account-and-Region-scoped resource that continuously pushes metric updates to <strong>Amazon Data Firehose</strong> (formerly Kinesis Data Firehose) as CloudWatch ingests them, with typical end-to-end latency in the low single-digit minutes rather than tens of minutes. Firehose then delivers to the destination: S3, an HTTP endpoint (which is how most SaaS vendors receive it), Amazon OpenSearch Service, Redshift, or a partner destination. You never manage a poller, and new resources appear in the stream automatically because the stream is defined by <em>filters</em>, not by an enumerated metric list.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">CloudWatch Metrics\n      <i class=o>|</i> (push, continuous)\n      v\n  Metric Stream  <i class=c>--(include/exclude filters, output format, statistics)</i>\n      <i class=o>|</i>\n      v\n  Amazon Data Firehose  <i class=c>--(buffer: size + interval, optional Lambda transform, GZIP)</i>\n      <i class=o>|</i>                              <i class=o>|</i>\n      <i class=o>|</i>                              <i class=o>+</i><i class=c>--&gt; S3 backup prefix (failed records)</i>\n      <i class=o>+</i><i class=c>--&gt; HTTP endpoint (Datadog / New Relic / Splunk / Dynatrace)</i>\n      <i class=o>+</i><i class=c>--&gt; S3 (Parquet via format conversion) --&gt; Glue/Athena</i>\n      <i class=o>+</i><i class=c>--&gt; OpenSearch / Redshift</i></code></pre></div>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Scoping the Stream: Filters and Statistics</h4>\n<p style=\"line-height: 1.75\">You choose either <strong>all metrics</strong> in the account and Region, or a filtered set defined by <strong>include filters</strong> (only these namespaces, optionally only these metric names within them) or <strong>exclude filters</strong> (everything except these). Namespace-level filtering is the coarse control; metric-name filtering within a namespace lets you take, say, only the four DynamoDB metrics you care about instead of the whole namespace. Since Metric Streams is billed per metric update streamed, filtering is the primary cost lever and the first thing to get right — \"all metrics\" on a large account is a common and expensive default.</p>\n<p style=\"line-height: 1.75\">By default each update carries the base statistics: <strong>min, max, sum and sample count</strong>. Average is derivable from sum and count, which is why it is not sent separately. Percentiles are not included by default; you configure <strong>additional statistics</strong> per metric (for example p95 and p99 on specific namespaces and metric names) when the destination needs them, and those extra statistics add to the streamed volume. This matters for vendor parity — a team that migrates dashboards and finds the p99 panels empty has usually forgotten to configure additional statistics.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Output Formats and Why OpenTelemetry Matters</h4>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Format</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Encoding</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Use when</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">JSON</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Newline-delimited JSON objects, human readable</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">S3 + Athena, custom consumers, quick debugging, Lambda transforms</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">OpenTelemetry</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Binary protobuf (OTLP ExportMetricsServiceRequest), length-delimited</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Vendor endpoints, any OTel-native collector, portability</td></tr>\n</tbody>\n</table>\n</div>\n<p style=\"line-height: 1.75\">The OpenTelemetry option is strategically important. It means the wire format leaving AWS is an open standard rather than an AWS-proprietary shape, so the same stream can feed any OTel-compatible backend, and switching vendors becomes a change of destination rather than a re-integration project. It is also more compact than JSON, which reduces Firehose and egress volume. The practical downside is that binary protobuf is harder to inspect — if you are writing to S3 for Athena analysis, JSON (ideally converted to Parquet by Firehose) is far easier to work with. A common pattern is two streams: OTel to the vendor, JSON to S3.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Firehose: Buffering, Transformation, and Error Handling</h4>\n<p style=\"line-height: 1.75\">Firehose is the delivery engine and its configuration determines your real latency and reliability characteristics.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Buffering hints.</strong> Firehose flushes when either a size threshold or a time interval is reached, whichever comes first. A small buffer interval lowers latency and raises request count and per-object overhead; a large one is cheaper and produces bigger, Athena-friendly S3 objects. For a vendor endpoint you tune toward low latency; for S3 archival you tune toward large objects, because thousands of tiny files is the classic way to make Athena slow and expensive.</li>\n<li><strong>Transformation.</strong> An optional Lambda transform can enrich, redact or reshape records in flight — adding account aliases or business unit tags, dropping namespaces that slipped through the filter, or converting to a vendor's bespoke shape. It adds cost, latency, and a new failure mode, so use it only when the destination genuinely cannot consume the native format.</li>\n<li><strong>Format conversion.</strong> For S3 destinations, Firehose can convert JSON records to <strong>Parquet or ORC</strong> using a Glue table schema. This is the single biggest lever on Athena cost, since columnar storage means a query touching two columns does not scan the whole record.</li>\n<li><strong>Error handling and backup.</strong> Configure an <strong>S3 backup prefix</strong> for failed records. If the HTTP destination returns errors or times out, Firehose retries for a configured duration and then writes the undeliverable records to that prefix rather than dropping them. This is what makes a vendor outage a recoverable backfill instead of a permanent data gap — and it is the detail most candidates omit.</li>\n<li><strong>Compression and encryption.</strong> GZIP compression on S3 destinations, and server-side encryption with a KMS key, are both configured on the Firehose stream, not on the metric stream.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Cost Crossover: Streaming vs. Polling</h4>\n<p style=\"line-height: 1.75\">Metric Streams is priced <strong>per metric update streamed</strong> (quoted per thousand updates), and you additionally pay for Firehose ingestion, plus the destination's own costs (S3 storage and requests, or nothing extra for a vendor HTTP endpoint beyond data transfer). Polling is priced per metric requested via GetMetricData.</p>\n<p style=\"line-height: 1.75\">The reasoning to articulate: with polling, cost is proportional to <em>metrics x poll frequency</em> and you pay even for metrics that did not change. With streaming, cost is proportional to <em>metric updates actually produced</em>, and you pay only when a datapoint exists. So streaming wins decisively when you have many metrics and want high freshness — the exact regime a vendor integration lives in — and polling can remain cheaper when you want a small, hand-picked set of metrics at a leisurely interval, or when you only need occasional ad-hoc reads. There is also a fixed operational cost to streaming (a Firehose stream, an IAM role, a backup bucket, monitoring of the pipeline) that makes it unattractive for a handful of metrics. A useful heuristic: below a few hundred metrics at five-minute freshness, polling; above a few thousand metrics at one-minute freshness, streaming, and the gap widens as either number grows. The other half of the argument is non-financial — polling throttling and discovery lag are correctness problems that no amount of money fixes.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common Architectures</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>SaaS vendor ingestion.</strong> Stream in OpenTelemetry format to a Firehose HTTP endpoint destination pointed at the vendor's intake URL, authenticated with the vendor's API key held in the Firehose configuration. One stream per account per Region, deployed by StackSets across the organization.</li>\n<li><strong>Cheap long-term retention.</strong> Stream in JSON to Firehose with Parquet conversion into a partitioned S3 prefix, cataloged in Glue, queried with Athena. This directly solves the CloudWatch roll-up problem: you keep one-minute fidelity for years at S3 pricing instead of losing it after about fifteen days.</li>\n<li><strong>Capacity planning data lake.</strong> The same S3 landing zone feeds a warehouse or notebook environment where utilization metrics are joined with cost and business data to model headroom, right-size instance families, and forecast reserved-capacity purchases — analysis that is impossible inside CloudWatch's query model.</li>\n<li><strong>Hybrid.</strong> Stream everything to S3 for durability and analysis, and stream a filtered, high-value subset to the vendor to control per-metric vendor pricing. Vendor contracts are often priced per custom metric ingested, so the filter on the vendor-facing stream is a direct lever on the vendor bill, not just the AWS one.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What Metric Streams Does Not Solve</h4>\n<p style=\"line-height: 1.75\">This is a <strong>metrics-only</strong> pipeline. It carries no logs, no traces, and no alarm state. Candidates who propose Metric Streams as \"the observability export solution\" get corrected. The complementary paths are:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Logs.</strong> CloudWatch Logs <strong>subscription filters</strong> to Firehose, Kinesis Data Streams, or a Lambda function, which is the streaming equivalent for log data. For bulk history, an export task to S3.</li>\n<li><strong>Traces.</strong> X-Ray, or more commonly the <strong>OpenTelemetry collector</strong> (ADOT) exporting OTLP directly to the vendor, bypassing AWS entirely for trace data.</li>\n<li><strong>Alarm state and events.</strong> EventBridge rules on CloudWatch alarm state-change events, routed to the vendor or to an incident tool.</li>\n<li><strong>Dashboards.</strong> Nothing exports them; dashboards are rebuilt in the vendor's own definition language, and that migration effort is usually underestimated.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cross-Account, Multi-Region, and Monitoring the Pipeline</h4>\n<p style=\"line-height: 1.75\">A metric stream is scoped to one account and one Region, so a 200-account, 4-Region organization needs 800 streams. You do not click those; you deploy them with <strong>CloudFormation StackSets</strong> or Terraform across the organization, with the Firehose in the same Region as the stream (metric streams deliver to a Firehose stream in the same Region). For centralization, the usual pattern is each Region's Firehose writing cross-account into a central S3 bucket in a telemetry account, with bucket policy and KMS key policy granting the delivery roles access — that is where cross-account setups typically fail, on a KMS key policy that omits the source account's delivery role. For a SaaS destination, each stream can ship directly to the vendor and the vendor does the aggregation, which is simpler. Note also that <strong>CloudWatch cross-account observability</strong> (monitoring accounts linked to source accounts) is a different feature that solves in-console cross-account viewing; it is not a substitute for a stream, though the two are often deployed together.</p>\n<p style=\"line-height: 1.75\">Finally, <strong>monitor the pipeline itself</strong>. The metric stream publishes metrics in the <code>AWS/CloudWatch/MetricStreams</code> namespace — notably a count of metric updates streamed — and Firehose publishes delivery metrics such as <code>DeliveryToHttpEndpoint.Success</code>, <code>DeliveryToS3.Success</code>, record age and throttled records in <code>AWS/Firehose</code>. Alarm on a drop in streamed updates (the stream silently stopped), on delivery success ratio falling below 1, on rising records-written-to-the-backup-prefix, and on increasing delivery latency. An unmonitored telemetry pipeline fails silently, and you discover it during the incident when the vendor's dashboard is empty.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario: Standardizing 180 Accounts on One Vendor</h4>\n<p style=\"line-height: 1.75\">An organization with 180 accounts across 3 Regions has bought a third-party observability platform. The vendor's default integration polls CloudWatch with a cross-account role; a pilot shows 6-8 minute data lag, intermittent gaps, and throttling errors in CloudTrail against GetMetricData. The design:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Replace polling with streams.</strong> One metric stream plus one Firehose per account per Region (540 total), deployed by a StackSet from the organization management account so new accounts get it automatically via the organizational-unit target.</li>\n<li><strong>Format.</strong> OpenTelemetry to the vendor endpoint, so a future vendor change is a destination swap. A second JSON stream in a small number of accounts writes to a central S3 lake in Parquet for capacity planning and for retention past CloudWatch's roll-up horizon.</li>\n<li><strong>Filters as the cost lever.</strong> Start with include filters for the ~20 namespaces the org actually uses plus its own custom namespaces, not \"all metrics\". Add p99 as an additional statistic only for the latency metrics the SLO dashboards need. This is negotiated with the vendor because their contract is priced per ingested metric.</li>\n<li><strong>Reliability.</strong> Firehose retry duration set generously, an S3 backup prefix in every account for undeliverable records, and a documented backfill runbook so a vendor outage is recoverable.</li>\n<li><strong>The rest of the telemetry.</strong> Logs go via CloudWatch Logs subscription filters into the same Firehose pattern; traces go from ADOT collectors straight to the vendor over OTLP; alarm state changes go through EventBridge. Metric Streams is explicitly scoped as the metrics leg only.</li>\n<li><strong>Observability of observability.</strong> A dedicated dashboard and alarms on streamed-update counts and Firehose delivery success per account, rolled up with a SEARCH expression so a single alarm covers the fleet.</li>\n</ul>\n<p style=\"line-height: 1.75\">The outcome to state: lag drops from minutes to near real time, gaps disappear because discovery is push-based, and the AWS-side cost becomes proportional to data actually produced rather than to poll frequency.</p>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"Polling GetMetricData for a large estate throttles, lags several minutes, misses short-lived resources, and costs per metric per poll.
