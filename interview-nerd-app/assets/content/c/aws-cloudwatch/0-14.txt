{"title":"CloudWatch vs CloudTrail vs Config vs X-Ray — Plus Pricing and Best Practices","tags":["aws","cloudwatch","cloudtrail","observability"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">This is one of the most frequently asked AWS interview questions, and candidates lose points not because they do not know the services but because they blur them together. The reliable way to keep them straight is to attach each one to a <em>question it answers</em>. Get the four one-line answers right and everything else follows.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Amazon CloudWatch</strong> answers <em>\"how is my system performing, and is it healthy?\"</em> — numbers over time (metrics), log lines, alarms, and dashboards.</li>\n<li><strong>AWS CloudTrail</strong> answers <em>\"who did what, when, and from where?\"</em> — an audit record of API activity in the account.</li>\n<li><strong>AWS Config</strong> answers <em>\"what did this resource's configuration look like at a point in time, and does it comply with my rules?\"</em> — configuration state, history, and compliance.</li>\n<li><strong>AWS X-Ray</strong> answers <em>\"where did the time go inside one request as it crossed my services?\"</em> — distributed tracing.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The four services, explored</h4>\n<p style=\"line-height: 1.75\"><strong>CloudWatch</strong> is the monitoring and observability service. A <strong>metric</strong> is a named number sampled over time, such as CPUUtilization or a custom OrdersPlaced counter. An <strong>alarm</strong> watches a metric and changes state when it crosses a threshold, optionally notifying you or taking an action such as scaling. <strong>CloudWatch Logs</strong> stores log lines in <strong>log groups</strong> and lets you query them with Logs Insights or match them with metric filters. Dashboards put it all on one screen. CloudWatch is about the <em>behaviour</em> of systems, not about people.</p>\n<p style=\"line-height: 1.75\"><strong>CloudTrail</strong> is about people and programs. It records API calls — who called, from which IP, with which credentials, what they asked for, and whether it succeeded. It says nothing about CPU or latency. If the question involves accountability, forensics, or compliance evidence, it is CloudTrail.</p>\n<p style=\"line-height: 1.75\"><strong>AWS Config</strong> sits in an interesting middle. Where CloudTrail records the <em>action</em> (\"Priya called ModifyDBInstance at 14:02\"), Config records the <em>resulting state</em> (\"at 14:02 this RDS instance went from single-AZ to multi-AZ, and here is the full before-and-after configuration\"). It keeps a timeline of every resource's configuration and lets you write <strong>Config rules</strong> — automated checks such as \"every S3 bucket must block public access\" or \"every EBS volume must be encrypted\" — that mark resources compliant or non-compliant and can trigger automatic remediation. The interview phrasing is: CloudTrail tells you <em>who changed it</em>; Config tells you <em>what it looked like before and after, and whether that is allowed</em>. They are complementary, not alternatives.</p>\n<p style=\"line-height: 1.75\"><strong>AWS X-Ray</strong> is distributed tracing. When a single user request passes through an API Gateway, a Lambda function, two microservices and a database, a metric tells you the total was slow but not which hop caused it. X-Ray propagates a <strong>trace ID</strong> through the call chain and records a <strong>segment</strong> for each service and <strong>subsegments</strong> for its internal work, then renders a service map and a waterfall showing exactly where the milliseconds went. Use it when latency is the problem and you need to attribute it.</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; The second is <strong>high-cardinality custom metrics</strong> — publishing a metric with a dimension of customer ID or request ID creates one billable metric per distinct value, so a thousand customers becomes a thousand metrics. Put high-cardinality identifiers in log fields, not metric dimensions; if you need both, use <strong>Embedded Metric Format</strong>, which lets you emit a structured log line from which CloudWatch extracts a small number of metrics.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Pricing in plain terms — CloudTrail</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Management events: the first copy is free.</strong> One trail recording management events (create, modify, delete operations on resources, plus logins) costs nothing per event. This is why \"just create a multi-Region trail\" is safe advice.</li>\n<li><strong>Additional copies cost.</strong> A second and subsequent trail recording the same management events is billed per 100,000 events. Two or three trails is usually a mistake, not a design.</li>\n<li><strong>Data events are billed per event and can be very expensive.</strong> Data events are the data-plane operations — S3 GetObject and PutObject, Lambda Invoke, DynamoDB item operations. They are off by default for good reason: an application doing a million S3 reads an hour generates a million events an hour. Enable them narrowly — one sensitive bucket or prefix, using advanced event selectors — never blanket \"all S3 buckets\" without doing the arithmetic.</li>\n<li><strong>CloudTrail Insights</strong> — the feature that automatically flags unusual API call-rate or error-rate patterns — is billed per events analysed, separately.</li>\n<li><strong>CloudTrail Lake</strong> charges to ingest events and to retain them for your chosen period; queries are included.</li>\n<li><strong>Plus S3.</strong> The delivered log files are ordinary S3 objects and you pay ordinary S3 storage and request charges for them — which is what lifecycle rules to Glacier classes are for.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Consolidated best-practices checklist</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Create a multi-Region organization trail.</strong> All Regions, all accounts, undisableable by members.</li>\n<li><strong>Deliver to a separate, locked-down log archive account.</strong> Versioning, Block Public Access, Object Lock, KMS encryption, lifecycle rules to Glacier. Whoever compromises the workload account must not be able to erase the evidence.</li>\n<li><strong>Enable log file integrity validation.</strong> It is free and it is what an auditor actually asks for.</li>\n<li><strong>Set retention on every log group.</strong> Default is never expire. Make it a rule enforced in your infrastructure-as-code and audited by a Config rule.</li>\n<li><strong>Alarm on user-visible symptoms, not internal noise.</strong> Error rate, latency, queue age, failed checkouts — not CPU at 71%. Every alarm should have an owner and a runbook, and an alarm nobody acts on should be deleted rather than muted.</li>\n<li><strong>Use structured JSON logging.</strong> One JSON object per line with consistent field names makes Logs Insights queries trivial and metric filters reliable. Free-form text does not.</li>\n<li><strong>Alert on critical security events.</strong> Root account usage, IAM policy and key changes, security group changes, MFA removal, CloudTrail StopLogging or DeleteTrail, bursts of AccessDenied. Route these to a channel humans genuinely watch.</li>\n<li><strong>Enable data events only where justified.</strong> Sensitive buckets and prefixes, with advanced event selectors to narrow further. Estimate the volume before turning them on.</li>\n<li><strong>Version-control dashboards and alarms.</strong> Dashboards are JSON and alarms are API objects — define them in CloudFormation, CDK or Terraform so they survive account rebuilds and are reviewed like code.</li>\n<li><strong>Never log secrets or personal data.</strong> Passwords, tokens, card numbers, full request bodies containing customer data. Logs get widely read, are hard to purge, and a leaked log is a breach. Redact at the source, and note that CloudTrail itself deliberately omits sensitive parameters such as passwords.</li>\n<li><strong>Centralise with cross-account dashboards or observability access manager</strong> so on-call sees one pane rather than logging into six accounts.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"CloudWatch and CloudTrail are basically the same thing.\"</strong> Performance versus accountability. CloudWatch watches the system; CloudTrail watches the people and programs acting on it.</li>\n<li><strong>\"CloudTrail replaces Config.\"</strong> CloudTrail gives you the action; Config gives you the resulting configuration state over time plus compliance rules. Use both.</li>\n<li><strong>\"CloudTrail is free.\"</strong> The first copy of management events is free. Additional trails, data events, Insights and Lake all cost, and the S3 storage is yours to pay for.</li>\n<li><strong>\"CloudWatch is cheap because metrics are cheap.\"</strong> Log ingestion and storage usually dominate the bill, and unbounded custom metric dimensions can dwarf both.</li>\n<li><strong>\"Enabling S3 data events everywhere is good security hygiene.\"</strong> It is a good way to generate a shocking bill. Scope them.</li>\n<li><strong>\"More alarms means better monitoring.\"</strong> Alarms nobody acts on train people to ignore alarms. Fewer, symptom-based, owned alarms beat hundreds of resource-level ones.</li>\n<li><strong>\"X-Ray is just fancier logging.\"</strong> It is per-request causal tracing across service boundaries — it answers a question logs structurally cannot.</li>\n<li><strong>\"Setting log retention deletes my audit trail.\"</strong> Log group retention governs CloudWatch Logs copies.
