CloudWatch then treats that metric exactly like any built-in one: you can graph it, alarm on it, and put it on a dashboard.\n</p>\n<p style=\"line-height: 1.75\">\nA metric filter has four parts you must supply: the <strong>filter pattern</strong> (what to match), the <strong>metric name and namespace</strong> (where to publish, the namespace being a folder that groups related metrics), the <strong>metric value</strong> (what number to emit per match), and the <strong>default value</strong> (what to emit when nothing matches in a period).\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Filter pattern syntax for plain text logs</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>A single term.</strong> <code>\"ERROR\"</code> matches any event whose text contains ERROR. Matching is case-sensitive, so <code>\"error\"</code> and <code>\"ERROR\"</code> are different patterns.</li>\n<li><strong>All of several terms (AND).</strong> <code>\"ERROR\" \"payment\"</code> — space-separated quoted terms must all appear in the same event.</li>\n<li><strong>Any of several terms (OR).</strong> <code>?ERROR ?FATAL</code> — the question mark marks each term as optional, so the event matches if it contains either.</li>\n<li><strong>Excluding a term (NOT).</strong> <code>\"ERROR\" -\"ExpectedTestError\"</code> — a leading minus excludes, which is how you stop a known-benign line from triggering pages.</li>\n<li><strong>Space-delimited positional patterns.</strong> For logs with fixed columns, brackets name each position and let you match on one: <code>[ip, id, user, timestamp, request, status_code = 5*, bytes]</code> matches only rows whose sixth field starts with 5.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Filter pattern syntax for JSON logs</h4>\n<p style=\"line-height: 1.75\">\nWhen your log events are JSON, you can match on a specific field rather than hoping a word appears somewhere. The pattern is wrapped in braces and refers to a field with a dollar-sign-dot prefix. To match events whose <code>level</code> field equals ERROR you write <code>{ &#36;.level = \"ERROR\" }</code>. Numeric comparisons work too: <code>{ &#36;.durationMs &gt; 2000 }</code>. Conditions combine with <code>&amp;&amp;</code> for AND and <code>||</code> for OR: <code>{ &#36;.level = \"ERROR\" &amp;&amp; &#36;.service = \"payments\" }</code>. Nested fields use dots, and array elements use index brackets.\n</p>\n<p style=\"line-height: 1.75\">\nThis is far more robust than text matching — the word ERROR appearing inside a customer's name or a URL will not falsely trigger a JSON field match. It is another strong argument for structured logging.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Metric value and the critical default value</h4>\n<p style=\"line-height: 1.75\">\nThe <strong>metric value</strong> is the number published per matching event. Usually it is simply <code>1</code>, so the metric becomes \"count of matches\". But it can also be a field from the log: with a JSON pattern you can set the metric value to <code>&#36;.durationMs</code> or <code>&#36;.bytesTransferred</code> and get a real measurement rather than a count.\n</p>\n<p style=\"line-height: 1.75\">\nThe <strong>default value</strong> is what gets published for a period when <em>no</em> event matched. Leave it unset and CloudWatch publishes nothing at all during quiet periods, which means the metric has <strong>gaps</strong> rather than zeros. That matters enormously for alarms: an alarm evaluating a metric with no data point does not evaluate to OK — it goes to the <strong>INSUFFICIENT_DATA</strong> state, and depending on how you configured missing-data treatment your alarm may sit in limbo or behave unpredictably. Setting the default value to <strong>0</strong> makes the metric a continuous line of zeros punctuated by real counts, so alarms evaluate cleanly every period and graphs are readable. Set it to 0 unless you have a specific reason not to.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Worked example: alert when ERROR appears more than 10 times in five minutes</h4>\n<ol style=\"margin-left: 1.5rem; list-style: decimal; line-height: 2\">\n<li>Create a metric filter on the log group <code>/app/checkout-api</code> with pattern <code>{ &#36;.level = \"ERROR\" }</code> (or <code>\"ERROR\"</code> for plain text logs).</li>\n<li>Publish it to namespace <code>CheckoutApp</code>, metric name <code>ApplicationErrorCount</code>, metric value <code>1</code>, default value <code>0</code>.</li>\n<li>Create an SNS topic and subscribe the on-call email or chat webhook to it. <strong>SNS</strong> is the AWS pub/sub notification service; alarms deliver their notifications through it.</li>\n<li>Create an alarm on <code>CheckoutApp/ApplicationErrorCount</code> with statistic <code>Sum</code>, period <code>300</code> seconds, threshold <code>GreaterThanThreshold 10</code>, evaluation periods <code>1</code>, and treat missing data as <code>notBreaching</code>.</li>\n<li>Point the alarm's alarm action at the SNS topic. It does not scan history. If you create an error-count filter today, the metric starts today — yesterday's errors are not in it, and no amount of waiting will backfill them. If you need to analyze past log data, that is what Logs Insights is for.
