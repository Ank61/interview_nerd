The HAR file is the underrated asset — when a canary fails, it tells you which specific third-party script hung or which asset 404ed, without needing to reproduce anything. Set a lifecycle policy on that bucket; screenshots and HARs accumulate quickly.</p>\n<p style=\"line-height: 1.75\">Canaries publish metrics to the <code>CloudWatchSynthetics</code> namespace, dimensioned by canary name: <strong>SuccessPercent</strong>, <strong>Failed</strong>, <strong>Duration</strong>, per-step durations and success, HTTP status-class counts, and <strong>VisualMonitoringSuccessPercent</strong> for visual checks. Those are ordinary metrics, so they alarm normally. Because canary schedules are discrete, alarm design matters: alarming on a single failed run of a one-minute canary will page you for transient network noise, so the standard pattern is <strong>M out of N</strong> datapoints (for example 3 of 5) on SuccessPercent below 100, with <code>TreatMissingData</code> set to <code>breaching</code> so a canary that stops running entirely also fires. Duration alarms catch the degradation case where the journey still works but has become unusably slow.</p>\n<p style=\"line-height: 1.75\"><strong>VPC canaries</strong> let you monitor internal endpoints that have no public address — an internal ALB, a private API Gateway, an admin console. You attach subnets and security groups, the underlying Lambda runs with those ENIs, and the security group on the target must allow the canary's. Remember that a VPC canary needs an outbound path to the CloudWatch, S3 and Synthetics endpoints: either a NAT gateway or, better, VPC endpoints. A VPC canary also tests only the internal path, so for a public service you want both an internal and an external canary to distinguish \"the app is broken\" from \"the internet cannot reach the app.\"</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Design Discipline: What a Canary Should Actually Do</h4>\n<p style=\"line-height: 1.75\">The single biggest determinant of canary value is <strong>what the script exercises</strong>. A canary that GETs <code>/health</code> tells you an HTTP listener is bound to a port. That endpoint typically returns 200 whether or not the database is reachable, the session store is up, the payment provider is reachable or the front-end bundle is valid. It is monitoring theatre.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Exercise the critical user journey.</strong> Log in, search for a product, add to cart, proceed to checkout, reach the payment step. Each of those becomes a named step so a failure tells you <em>where</em> the journey broke, and step durations give you a per-stage latency profile of the real experience.</li>\n<li><strong>Assert on content, not just status.</strong> Wait for a specific selector to appear and assert on its text. A page that renders 200 with an error banner must fail the canary.</li>\n<li><strong>Run from multiple Regions.</strong> Deploy the same canary in three or more Regions. If one Region's canary fails and the others pass, you have a regional or network problem; if all fail simultaneously, it is a global outage. Without that comparison, a single failing canary is ambiguous. A composite alarm over the per-Region canary alarms encodes this directly: page on \"two or more Regions failing\", raise a ticket on one.</li>\n<li><strong>Stop short of side effects, or make them safe.</strong> Do not place real orders, charge real cards or send real emails every minute. Use a dedicated test tenant and a test payment instrument, stop at the final confirmation step, or tag synthetic transactions so downstream systems (analytics, fulfilment, revenue reporting) can exclude them. Nothing destroys trust in observability data faster than canary traffic polluting business metrics.</li>\n<li><strong>Handle credentials safely.</strong> Never hardcode a password in the canary script; it is stored and readable. Fetch credentials from <strong>AWS Secrets Manager</strong> or SSM Parameter Store at run time using the canary's execution role, use a purpose-built low-privilege synthetic account, rotate it, and be careful that screenshots do not capture secrets — mask or skip screenshots on pages showing tokens.</li>\n<li><strong>Make canaries deterministic.</strong> Flaky canaries train people to ignore alarms. Use explicit waits on selectors rather than fixed sleeps, pin test data, and give the script sensible timeouts so a hang fails cleanly rather than at the Lambda limit.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">CloudWatch RUM: What Real Users Experienced</h4>\n<p style=\"line-height: 1.75\">Canaries are one scripted user on a clean network from an AWS Region. <strong>Real User Monitoring</strong> is the opposite sample: every real browser, on real devices and real networks, with real ad blockers and real corporate proxies. You create an <strong>app monitor</strong>, which gives you a JavaScript snippet (the CloudWatch RUM web client) to embed in your pages, backed by an Amazon Cognito identity pool for unauthenticated write access. From then on the browser reports:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Page load performance</strong> from the Navigation Timing and Resource Timing APIs — DNS, connect, TTFB, DOM content loaded, full load, and per-resource timings.</li>\n<li><strong>Core Web Vitals</strong> — Largest Contentful Paint, Cumulative Layout Shift and Interaction to Next Paint — the metrics that reflect perceived quality and feed search ranking.</li>\n<li><strong>JavaScript errors</strong> with message and stack, which is the one category of failure that leaves no trace whatsoever on the server.</li>\n<li><strong>HTTP request failures</strong> observed from the browser, including calls to third-party origins you do not operate.</li>\n<li><strong>Session and journey data</strong> — page views, navigation paths and where users dropped out.</li>\n</ul>\n<p style=\"line-height: 1.75\">Everything is segmentable by <strong>browser and version, device type, operating system, country/geography, and page</strong>. The web client has a <strong>session sample rate</strong> — sampling a fraction of sessions rather than all of them both reduces cost (RUM is billed per event ingested, and a busy site generates enormous event volume) and reduces data collected. Telemetry categories are opt-in individually: you can enable performance and errors but not the HTTP body capture, and you control whether the client sets a cookie to establish a session ID. With cookies disabled you lose session stitching but avoid consent complexity in jurisdictions where that matters; either way, coordinate with your consent-management platform so RUM initialises only after consent where the law requires it. Use page allow/deny lists to exclude pages whose <strong>URLs themselves contain sensitive identifiers</strong> — a URL like /account/12345/medical is PII the moment it is transmitted — and never attach raw user identifiers as custom attributes. Be aware that RUM data has a bounded retention window, so route events to CloudWatch Logs and archive if you need long-term analysis.</p>\n<p style=\"line-height: 1.75\">The most powerful configuration is <strong>correlating RUM with backend traces</strong>: enable X-Ray tracing on the app monitor and the web client adds trace context to outgoing XHR/fetch requests, so a slow page view in RUM links to the actual server-side trace for that request. That closes the last gap in the chain — a user complaint becomes a session, the session becomes a page view, the page view becomes an HTTP call, the call becomes a trace, and the trace names the slow hop. Add canaries on top and you have detection before impact, measurement of real impact, and root cause in one pivot path.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Production Scenario: Proactive Coverage for a Revenue-Critical Checkout</h4>\n<p style=\"line-height: 1.75\">You own a checkout flow generating significant revenue per hour.
