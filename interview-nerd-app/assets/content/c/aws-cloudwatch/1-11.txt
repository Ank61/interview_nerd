{"title":"Incident Response and Automated Remediation with CloudWatch and EventBridge","tags":["incident-response","eventbridge","ssm-automation","runbooks"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Detection is the easy half. The value of an observability investment is realised in the chain that runs from <em>a signal fires</em> to <em>the problem is resolved and cannot recur silently</em>. That chain has four links: routing the signal to something that can act (a human or a machine), acting correctly and safely, supporting the humans working the incident, and learning from it afterwards. Senior candidates are expected to reason about all four — especially about the judgement of <strong>when to automate and when to wake someone up</strong>, because automation applied to the wrong class of problem turns a small incident into a large one at machine speed.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Alarm to Human: Paging That Works</h4>\n<p style=\"line-height: 1.75\">CloudWatch alarm actions publish to <strong>SNS</strong>, and SNS is the fan-out point: an HTTPS subscription to <strong>PagerDuty</strong> or <strong>Opsgenie</strong> for paging and escalation policies, an email or ticketing subscription for low-severity work, and a chat subscription for awareness. EventBridge <strong>API destinations</strong> are the more flexible alternative when you need to call a paging vendor's API with a custom payload and managed credentials. Whichever transport, the paging tool — not CloudWatch — should own on-call schedules, escalation, acknowledgement and deduplication; CloudWatch is a poor rota manager.</p>\n<p style=\"line-height: 1.75\"><strong>AWS Chatbot, now Amazon Q Developer in chat applications</strong>, subscribes a Slack channel or Microsoft Teams channel to an SNS topic. Beyond pretty-printing alarms with graphs, it enables <strong>ChatOps</strong>: running read-only AWS CLI commands from the channel under a controlled IAM role, so a responder can check an Auto Scaling group or describe an alarm without leaving the conversation, and every command is visible to everyone in the channel — an audit trail and a training mechanism at once. Restrict it to read-only or narrowly-scoped actions; a chat channel is not a place for unbounded production write access.</p>\n<p style=\"line-height: 1.75\">The non-negotiable content requirements for anything that pages a human, at 03:00, on a phone:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>A runbook link in the alarm description.</strong> The description field is carried into the notification, so put the URL there. An alarm whose runbook is \"ask Priya\" is not production-ready.</li>\n<li><strong>Clear ownership.</strong> The alarm must name the owning team and route to that team's rota. Alarms with no owner become alarms nobody acts on.</li>\n<li><strong>Impact, not mechanism.</strong> \"Checkout success rate below 99% — customers cannot complete purchases\" beats \"ALB TargetResponseTime p99 &gt; 2\".</li>\n<li><strong>Actionability.</strong> If there is no action a human could take on receipt, it should not page. Every non-actionable page erodes the credibility of every future page — alert fatigue is a reliability risk, not a nuisance.</li>\n</ul>\n<p style=\"line-height: 1.75\">Use <strong>composite alarms</strong> to page on the meaningful condition rather than every contributing metric, and their <strong>alarm suppression</strong> capability (an actions-suppressor alarm) so that a known upstream problem does not generate twenty downstream pages for the same event.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">EventBridge as the Automation Fabric</h4>\n<p style=\"line-height: 1.75\">EventBridge is what turns alarms and AWS service events into actions. Two sources matter here. First, CloudWatch emits <strong>alarm state change events</strong> on the default bus with source <code>aws.cloudwatch</code> and detail-type <code>CloudWatch Alarm State Change</code>, carrying the alarm name, the previous and new state, the reason and the timestamp. You can match on a specific alarm, on any alarm whose name matches a prefix pattern, and on the transition direction so you act only on OK-to-ALARM. Second, AWS services emit <strong>operational events</strong> directly — EC2 instance state changes, EBS volume events, ECS task state changes, Auto Scaling lifecycle hooks, GuardDuty findings, Health events — which are often a better trigger than an alarm because they are precise and immediate.</p>\n<p style=\"line-height: 1.75\">Targets give you an escalating ladder of capability:</p>\n<div style=\"overflow-x: auto; <strong>expand a full EBS volume</strong> triggered by a disk-usage alarm from the CloudWatch agent, using a document that calls ModifyVolume and then grows the partition and filesystem through Run Command; <strong>isolate an unhealthy instance</strong> by deregistering it from its target group or putting it in Standby in the Auto Scaling group — which preserves it for forensics rather than terminating the evidence; <strong>revoke an over-permissive security group rule</strong> in response to a Config or GuardDuty finding, for which AWS ships remediation runbooks such as <code>AWS-DisablePublicAccessForSecurityGroup</code>; and rotating a leaked credential, clearing a poison-pill message to a DLQ, or forcing a cache flush.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Guardrails: Why Automation Is the Dangerous Part</h4>\n<p style=\"line-height: 1.75\">Automation executes your worst assumptions faster than you can notice them. Every remediation must ship with all of the following, and an interviewer will listen for them:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Idempotency.</strong> EventBridge delivery is at-least-once and alarms can flap, so the same event may arrive twice. Check current state before acting (\"is the volume already resized?\", \"is the instance already draining?\") and make repeated execution a no-op rather than a second restart.</li>\n<li><strong>Rate limiting and flap protection.</strong> Cap executions per resource and per time window — for example, at most two restarts per instance per hour and at most five remediations fleet-wide per hour — using a counter in DynamoDB or a Step Functions guard. Without this, an alarm that oscillates drives a restart loop that turns a degradation into an outage. When the cap is hit, the correct behaviour is to <strong>stop and page a human</strong>, not to keep trying.</li>\n<li><strong>An explicit kill switch.</strong> A single SSM Parameter or feature flag that disables all automated remediation instantly, checked at the top of every handler. During a major incident the first thing a commander may need is to stop the robots so humans can reason about a stable system.</li>\n<li><strong>Dry-run mode.</strong> Every remediation ships in log-only mode first, running in production for weeks and recording what it <em>would</em> have done. Reviewing that log is how you discover that your \"obviously safe\" action would have fired eleven times on benign conditions.</li>\n<li><strong>Blast-radius limits.</strong> Refuse to act on more than N resources in one execution; a bug that terminates one instance is an incident, one that terminates a fleet is a career event.</li>\n<li><strong>Full auditability.</strong> Log every automated action — trigger event, decision, parameters, result — to a dedicated log group, and emit a metric on remediation executions and failures with its own alarm. Publish a notification to chat so humans can see the robot working. CloudTrail records the API calls made by the automation role, which is how a postmortem answers \"did the automation cause this?\"</li>\n<li><strong>Least privilege.</strong> The automation role gets exactly the permissions for its one job, scoped by tag or resource where possible. An over-broad remediation role is a privileged, event-triggered path into production.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">When to Automate and When to Page</h4>\n<p style=\"line-height: 1.75\">The heuristic is a function of three variables: how well understood the failure is, how often it happens, and the blast radius if the action is wrong.</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Situation</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Decision</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Known, frequent, low-risk, reversible (disk fills weekly; a worker leaks memory and needs recycling)</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><strong>Automate fully</strong>, notify chat, do not page. Track the frequency so the underlying bug still gets fixed</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Known cause but high blast radius (failover a database, scale a fleet 10x, roll back a release)</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><strong>Automate with a human approval step</strong> — Step Functions or an SSM Automation approval — so a human authorises in one click</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Novel, ambiguous or correlated across services</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><strong>Page a human.</strong> Automation cannot diagnose something nobody has diagnosed yet</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Data-destructive or irreversible</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Never automate without explicit approval, and prefer isolate-and-preserve over delete</td></tr>\n</tbody>\n</table>\n</div>\n<p style=\"line-height: 1.75\">Two warnings. First, automated remediation <strong>hides the underlying defect</strong> — if a restart script silently fixes a memory leak twelve times a week, nobody fixes the leak. Always emit a metric on remediation frequency and alarm when it rises, so the automation surfaces the problem instead of burying it. Second, remediation is a <strong>treatment, not a diagnosis</strong>: restarting a service that is failing because a dependency is down does nothing except add churn and destroy the evidence.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Self-Healing You Already Have</h4>\n<p style=\"line-height: 1.75\">Before building bespoke automation, use the mechanisms AWS already provides. <strong>EC2 Auto Scaling</strong> with target-tracking or step-scaling policies driven by CloudWatch alarms handles capacity automatically; <strong>ELB health checks</strong> plus Auto Scaling health-check replacement remove and replace unhealthy instances without any custom code; <strong>EC2 auto-recovery</strong> (via a StatusCheckFailed_System alarm action or the built-in behaviour) recovers instances from underlying host failures; <strong>ECS and Kubernetes</strong> restart failed tasks and pods by their own reconciliation loops; Route 53 health checks with failover records shift traffic away from an unhealthy Region. Each of these is battle-tested and needs no guardrails of your own. Note the interaction risk though: custom automation that terminates an instance while Auto Scaling is also replacing it, or that scales a group that a target-tracking policy is simultaneously managing, produces oscillation — always check what is already acting on a resource before adding another actor.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Supporting the Humans: War Rooms, Correlation and AWS Health</h4>\n<p style=\"line-height: 1.75\">A <strong>war-room dashboard must exist before the incident</strong> — assembling one under pressure wastes the most valuable ten minutes. Build it per critical service with: the golden signals (traffic, errors, latency, saturation), the canary success rate per Region, dependency health, queue depths and DLQ counts, the deployment timeline, and a widget of recent CloudTrail write events. A <strong>CloudWatch automatic dashboard or custom dashboard with an annotation showing deploy markers</strong> makes the most common correlation visible instantly.</p>\n<p style=\"line-height: 1.75\">The correlation question in almost every incident is <em>what changed?</em>, and the answer is almost always a deployment or a configuration change. Cross-reference the alarm's state-change timestamp against deployment events (CodeDeploy/CodePipeline events on EventBridge) and against <strong>CloudTrail</strong> write events in the window — a security group modified, a parameter changed, a scaling policy edited, an IAM policy updated. CloudTrail Lake or an Athena table over the CloudTrail S3 bucket makes that a single query. For a spike with an unknown source, <strong>CloudWatch Contributor Insights</strong> answers \"who is the top contributor?\" — the IP, tenant, URL or key driving the traffic — directly from log fields, which is frequently the fastest path from symptom to cause.</p>\n<p style=\"line-height: 1.75\"><strong>AWS Health</strong> is the input that distinguishes your problem from an AWS problem. The Personal Health Dashboard (now the Health Dashboard) surfaces account-specific events — degraded service in an AZ, planned maintenance, a resource requiring action — and Health events are published to <strong>EventBridge with source <code>aws.health</code></strong>, so you can route them into the same incident channel automatically and even trigger pre-emptive action (drain an AZ on a degradation notice). The programmatic Health API requires a Business or Enterprise support plan. Checking Health early is a discipline: many incidents end in ten minutes when someone notices AWS has already declared the problem.</p>\n<p style=\"line-height: 1.75\">Capture the timeline <em>as it happens</em>. Alarm history (DescribeAlarmHistory), the chat transcript, automation execution records and deployment events together form the postmortem skeleton. A blameless postmortem needs detection time, engagement time, mitigation time and resolution time, plus a causal narrative and action items with owners and dates.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Measuring the Practice</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>MTTD (mean time to detect).</strong> From first customer impact to first alarm. The headline number that tells you whether your monitoring is any good.</li>\n<li><strong>MTTR (mean time to resolve/mitigate).</strong> Track mitigation and full resolution separately; mitigation is what customers feel.</li>\n<li><strong>Percentage of incidents with a preceding alarm.</strong> The single most diagnostic metric of monitoring coverage — if a third of incidents are first reported by customers, invest in detection before anything else.</li>\n<li><strong>Page volume and actionability.</strong> Pages per on-call shift, out-of-hours pages, and the fraction that required no action. Rising non-actionable pages predict a missed incident, because people stop reading.</li>\n<li><strong>Automation rate and its failure rate.</strong> Incidents resolved without human involvement, and how often remediation itself failed or had to be killed.</li>\n<li><strong>Action item completion.</strong> Postmortems whose action items are never delivered are theatre; track closure like any other backlog.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Worked Incident: First Alarm to Postmortem Action Items</h4>\n<p style=\"line-height: 1.75\"><strong>02:14</strong> — The composite alarm <code>checkout-critical</code> fires: the checkout canary is failing in two Regions and the API 5xx rate alarm is in ALARM. A CloudTrail query over the window confirms a <code>ModifyDBParameterGroup</code>... no — it shows only the deployment's normal ECS API calls, so the code is the suspect.</p>\n<p style=\"line-height: 1.75\"><strong>02:22</strong> — Contributor Insights on the orders-service log group shows errors concentrated on one operation, and Logs Insights on the error message shows connection-pool exhaustion. An X-Ray trace confirms the new code opens a connection per request without returning it to the pool.</p>\n<p style=\"line-height: 1.75\"><strong>02:26</strong> — <strong>Mitigate, do not debug.</strong> Roll back to the previous task definition.
