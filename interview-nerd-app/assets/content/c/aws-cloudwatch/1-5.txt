{"title":"Advanced Logs Insights and Structured Logging Strategy","tags":["logs-insights","structured-logging","emf","query-optimization"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Logs Insights is the difference between having logs and being able to answer questions. The gap that separates a mid-level engineer from a senior one here is not knowing the command names — it is knowing that <strong>query cost and query speed are both governed by bytes scanned</strong>, that the log data has to be <em>shaped</em> at write time for the interesting queries to be cheap at read time, and that during an incident the fastest path to an answer is usually <em>comparing</em> log shape between two time windows rather than reading individual lines. This topic covers the query engine properly, then the structured-logging contract that makes the query engine useful, then the incident workflow that ties them together.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Query Cost and Performance: Bytes Scanned Is the Only Number That Matters</h4>\n<p style=\"line-height: 1.75\">Logs Insights bills per GB of log data <strong>scanned</strong>, and scan volume is determined almost entirely by three choices made before the query language is even involved:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>The time range.</strong> Scan volume is linear in the window. Running the same query over 24 hours instead of 30 minutes costs roughly 48 times as much and takes proportionally longer. The habitual senior behaviour is to <em>start narrow and widen only if the answer is not there</em> — 15 minutes around the incident, then an hour, then a day. Junior engineers reflexively pick \"Last 1 week\" and then complain the console is slow.</li>\n<li><strong>The log groups selected.</strong> Selecting 20 log groups when the answer lives in one multiplies the scan by twenty. Selecting log groups by prefix is convenient during exploration and expensive as a habit.</li>\n<li><strong>What the engine can skip.</strong> This is where <strong>field index policies</strong> matter: indexing a small number of high-selectivity fields — a request id, a trace id, a tenant id — lets a query filtering on those fields skip large amounts of data rather than reading it. Indexes are most effective for needle-in-haystack lookups and do nothing for broad aggregations.</li>\n</ul>\n<p style=\"line-height: 1.75\">Within the query itself, ordering matters because commands execute as a pipeline. <strong>Put the most selective filter first</strong> so that expensive operations — <code>parse</code> with a regular expression, <code>stats</code> aggregation, <code>sort</code> — run over a small fraction of the events. A query that parses every line and then filters on the parsed field does far more work than one that filters on a raw substring first and then parses the survivors. A useful shape is: cheap raw filter, then parse, then refined filter, then stats. Also remember that <code>limit</code> caps returned rows, <em>not</em> data scanned — adding <code>limit 20</code> to a week-long query does not make it cheap; shrinking the window does.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Query Language Beyond the Basics</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>parse, glob form.</strong> <code>parse @message \"user=* action=* ms=*\" as user, action, ms</code> extracts fields from a predictable unstructured line using wildcards. Cheap, readable, and brittle if the format drifts — which is an argument for JSON, not for cleverer globs.</li>\n<li><strong>parse, regular-expression form.</strong> <code>parse @message /latency=(?&lt;latency&gt;\\d+)ms.*status=(?&lt;status&gt;\\d{3})/</code> uses named capture groups and handles variable formats, at meaningfully higher CPU cost per event. Filter before you parse.</li>\n<li><strong>filter.</strong> Supports comparison and boolean operators, membership (<code>filter level in [\"ERROR\", \"FATAL\"]</code>), substring tests (<code>filter @message like \"timeout\"</code>), and regular expressions (<code>filter @message like /Timeout|Deadline/</code>). Field-presence helpers such as <code>ispresent(field)</code> are how you separate \"field absent\" from \"field empty\", which matters when schemas evolve.</li>\n<li><strong>fields with computed expressions.</strong> <code>fields @timestamp, duration / 1000 as seconds, coalesce(tenantId, \"unknown\") as tenant</code> creates derived columns; arithmetic, string and date functions are available, and <code>coalesce</code> is the practical tool for fields that only some services emit.</li>\n<li><strong>stats with multiple aggregations and grouping.</strong> <code>stats count(*) as calls, avg(duration) as avg_ms, pct(duration, 99) as p99, count_distinct(userId) as users by service, statusCode</code> is the workhorse. Percentile via <code>pct()</code>, plus <code>sum</code>, <code>min</code>, <code>max</code>, <code>stddev</code>, <code>earliest</code> and <code>latest</code> cover most needs. Grouping by a high-cardinality field is the common way to make a query slow.</li>\n<li><strong>bin for time bucketing.</strong> <code>stats count(*) by bin(5m)</code> turns a query into a time series that can be graphed and placed on a dashboard. Combining a bin with a group-by — <code>by bin(5m), statusCode</code> — is how you see an error class emerging over time.</li>\n<li><strong>sort, limit, dedup.</strong> <code>sort @timestamp desc</code>, <code>limit 50</code>, and <code>dedup requestId</code> to collapse repeated events down to one row per key — <code>dedup</code> is excellent for turning a flood of retries into a list of distinct affected requests.</li>\n<li><strong>pattern.</strong> <code>pattern @message</code> automatically clusters similar log lines into templates, replacing variable tokens with placeholders, and reports the count and severity of each cluster. This is transformative during incidents: instead of scrolling a thousand lines you get a ranked list of the dozen distinct <em>shapes</em> of log line, and the unfamiliar one is usually the problem.</li>\n<li><strong>diff / compare.</strong> The comparison capability re-runs your query over an earlier equivalent window (the previous hour, day or week) and shows what changed — which patterns are new, which grew, which disappeared. During an incident, <strong>\"what log lines exist now that did not exist an hour ago\"</strong> is very often the single fastest route to root cause, and it is an answer no amount of reading individual lines produces quickly.</li>\n<li><strong>Alternative query languages.</strong> CloudWatch Logs Insights also supports OpenSearch PPL and SQL dialects alongside its native language, which lowers the barrier for teams arriving from other tooling. The native language remains the one with the fullest feature coverage.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cross-Log-Group and Cross-Account Queries</h4>\n<p style=\"line-height: 1.75\">A single query can target many log groups at once — by explicit list, or by prefix/pattern selection so that newly created groups matching the pattern are picked up automatically. There is a ceiling on how many log groups one query may span (on the order of tens), which pushes you toward sensible log group naming: a prefix per service family so that a query over an entire domain is one selection rather than a hand-maintained list. With <strong>CloudWatch cross-account observability</strong> configured, a query run in the monitoring account can span log groups in linked source accounts in the same statement, so a request that crossed an account boundary can be traced without logging into three consoles. The results carry the owning account, and the query charge lands where the query runs.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Structured Logging Strategy: The Contract That Makes It Work</h4>\n<p style=\"line-height: 1.75\">Everything above degrades to regex archaeology unless services agree on a schema. First, <strong>correlation identifiers must propagate across every service boundary</strong> — injected at the edge if absent, carried in an HTTP header, copied into message attributes for SQS/SNS/EventBridge hops, and restored into the logging context on the far side. The places this usually breaks are asynchronous boundaries and thread pools, and a single service that drops the header makes the whole trace unreconstructable. Second, <strong>the message text is for humans and the fields are for machines</strong>: never build queries around message wording, because someone will improve the wording. Keep the human string in <code>message</code> and the queryable identity in <code>event</code>.</p>\n<p style=\"line-height: 1.75\">The payoff is the <strong>pivot</strong>: a latency or error metric spikes on a dashboard, you click into the time window, run one Logs Insights query filtered to that window and that service, group by <code>event</code> or run <code>pattern</code> to see what changed, pull a handful of <code>requestId</code> values, and then query <em>all</em> services for those ids to see the full path. Without shared fields and propagated ids, none of those steps are one query.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Embedded Metric Format: One Emission, Two Products</h4>\n<p style=\"line-height: 1.75\">The <strong>Embedded Metric Format (EMF)</strong> lets a single structured log line carry both the rich context you want in logs and metric values that CloudWatch extracts automatically into real metrics. You emit JSON containing an <code>_aws</code> block declaring a namespace, dimension sets and metric names with units; CloudWatch ingests the line as a log event <em>and</em> materializes the named values as metrics you can alarm on and graph. On Lambda it is simply a line written to stdout; on EC2 and containers the CloudWatch agent exposes an EMF endpoint the application writes to.</p>\n<p style=\"line-height: 1.75\">The senior reasons to prefer EMF over <code>PutMetricData</code> are: it is <strong>asynchronous and off the request path</strong> (no synchronous API call to fail or add latency), it produces <strong>high-resolution, high-cardinality context in the log line while keeping the metric dimensions small</strong>, and the metric and its explanatory context are guaranteed to be the same event so you can always jump from a suspicious datapoint to the exact log line that produced it. The trap is the same as always: <strong>every distinct combination of dimension values is a separate custom metric with its own cost</strong>, so dimensions stay low-cardinality (service, operation, status class) while the interesting-but-unbounded values (customerId, requestId) stay as ordinary log properties, queryable but not dimensioned.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Saved Queries, Dashboards and Live Tail</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Saved queries</strong> turn tribal knowledge into shared assets. The set worth curating for every service: \"errors in the last 15 minutes grouped by event\", \"p99 latency by endpoint\", \"all log lines for a request id\", \"new log patterns versus an hour ago\". Put them in the runbook by name.</li>\n<li><strong>Dashboard query widgets</strong> render a Logs Insights query as a table or time series alongside metric widgets. This is how \"top five error messages right now\" sits next to the latency graph. Be deliberate: every dashboard load re-runs the query and re-incurs scan cost, so keep widget queries narrow and their default time ranges short.</li>\n<li><strong>Live Tail</strong> streams matching log events in near real time with filter expressions and highlight terms. It is the right tool while you are actively pushing traffic — verifying a fix, reproducing a bug, watching a canary — and it is billed per minute of session, so it is a tool you open and close, not one you leave running.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario: One Failed Customer Request Across Four Services</h4>\n<p style=\"line-height: 1.75\">A customer reports that a checkout failed at approximately 14:32 UTC, and gives you their account id.
