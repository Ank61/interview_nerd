{"title":"Distributed Tracing — X-Ray, OpenTelemetry, and ServiceLens","tags":["x-ray","opentelemetry","servicelens","tracing"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">In a monolith, a latency problem has one place to hide. In a microservice architecture, a single user request may traverse an edge proxy, an API gateway, an authentication service, a product service, three downstream data stores, a queue and two asynchronous workers. Metrics tell you the system is slow. Logs tell you what each component said about itself. Neither tells you which of the twelve hops on <em>this particular request</em> spent the time, because metrics are pre-aggregated (you lose the individual request) and logs are per-service (you lose the causal relationship between them). Distributed tracing is the third signal: it reconstructs one request's complete journey as a causally linked tree, so the answer to \"where did the 900 ms go?\" is a picture rather than an archaeology project.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why Metrics and Logs Are Structurally Insufficient</h4>\n<p style=\"line-height: 1.75\">Metrics are cheap because they throw away the request. A p99 latency of 2 seconds on the checkout API is a statement about a distribution, not about any request you can go and inspect. Worse, per-service metrics compose badly: every service in the chain can report a healthy p50 while the end-to-end p99 is terrible, because the slow requests are a small, correlated subset that each service's own aggregate hides. Logs preserve individual events but not causality — without a shared identifier you cannot join the auth service's log line to the payment service's log line for the same customer click, and even with a correlation ID you get a flat list of lines rather than a timeline with parent/child relationships and durations.</p>\n<p style=\"line-height: 1.75\">Tracing adds three things metrics and logs cannot: <strong>causal structure</strong> (this call happened inside that call), <strong>per-hop timing</strong> on a single request, and <strong>cross-service joins for free</strong> because every participant stamps the same trace identifier. The senior framing in an interview is that the three signals answer different questions — metrics answer \"is something wrong and how bad\", traces answer \"where in the system\", logs answer \"what exactly happened there\" — and a mature observability stack lets you pivot between them in one or two clicks.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Data Model: Traces, Segments, Subsegments, Annotations, Metadata</h4>\n<p style=\"line-height: 1.75\">AWS X-Ray models a request as a <strong>trace</strong> identified by a trace ID (format <code>1-&lt;8 hex digits of the epoch start time&gt;-&lt;24 hex random digits&gt;</code>). Each service that handles the request emits a <strong>segment</strong> — a document describing that service's work, with a start and end time, HTTP details, the service name, errors and faults. Inside a segment, the instrumentation records <strong>subsegments</strong> for downstream calls and interesting internal work: a DynamoDB query, an HTTP call to another service, a JSON deserialization loop you chose to time. Subsegments nest, giving you the tree. In OpenTelemetry vocabulary both are <strong>spans</strong> with a parent span ID; X-Ray's segment/subsegment split is largely a wire-format distinction, and the ADOT X-Ray exporter maps OTel spans onto it.</p>\n<p style=\"line-height: 1.75\">Attached data comes in two flavours and confusing them is a classic interview trap:</p>\n<div style=\"overflow-x: auto; Annotation keys are the dimension on which you slice traces, so treat them like metric dimensions — bounded cardinality of <em>keys</em>, arbitrary cardinality of <em>values</em> is fine (unlike custom metrics, where high-cardinality values are what bankrupts you). Never put secrets, tokens or PII into either field; trace documents are readable by anyone with X-Ray read permissions.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Trace Context Propagation — and the One Service That Breaks It</h4>\n<p style=\"line-height: 1.75\">Nothing in tracing works without <strong>context propagation</strong>: the trace ID, the current span ID (which becomes the child's parent) and the sampling decision must travel with the request over every hop. X-Ray uses the <code>X-Amzn-Trace-Id</code> header, carrying <code>Root</code>, <code>Parent</code> and <code>Sampled</code> fields. OpenTelemetry's standard is the W3C <code>traceparent</code> header; ADOT ships an X-Ray propagator so you can speak the AWS format while using OTel SDKs, and you configure propagators explicitly so that the whole fleet agrees.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">ALB <i class=c>---&gt; api-gateway ---&gt; auth-svc ---&gt; cart-svc ---&gt; pricing-svc ---&gt; DynamoDB</i>\n        (header ok)   (header ok)   (DROPS IT)   (starts <i class=k>NEW</i> trace)\n\n<i class=k>Result</i> <i class=k>in</i> the service map:\n  [client]<i class=c>--[api-gateway]--[auth-svc]--[cart-svc]        &lt;- trace A ends here</i>\n  [pricing<i class=o>-</i>svc]<i class=c>--[DynamoDB]                              &lt;- orphan trace B</i>\nSymptom: <i class=k>end</i><i class=o>-</i><i class=k>to</i><i class=o>-</i><i class=k>end</i> latency <i class=k>is</i> unattributable; pricing<i class=o>-</i>svc looks fast\n         because its own trace starts after the queueing delay.</code></pre></div>\n<p style=\"line-height: 1.75\">A single service that terminates the context — usually because it builds outbound requests with a raw HTTP client the SDK does not wrap, or copies only a whitelist of headers — severs the chain and produces two half-traces. This is the most common real-world tracing defect and the reason platform teams ship a shared, instrumented HTTP client rather than asking every team to remember.</p>\n<p style=\"line-height: 1.75\"><strong>Asynchronous boundaries need special handling</strong> because there is no HTTP header to ride on. For Amazon SQS, the trace header travels in the <code>AWSTraceHeader</code> system message attribute; Lambda's SQS integration reads it, and the SDK can be configured to propagate it so the consumer's work links to the producer's trace. Amazon SNS supports active tracing and passes trace context to SQS and Lambda subscribers. EventBridge propagates trace context on PutEvents where supported, and for anything else — Kinesis, Kafka, S3 event notifications, a database outbox — you must carry the context yourself as a message attribute or an envelope field and re-establish it on the consumer side. Be explicit about semantics too: the consumer span is usually a <em>link</em> rather than a strict child, because a batch of ten messages belongs to ten different traces, and modelling a batch handler as a child of one of them is wrong.</p>\n<h4 style=\"margin-top: 1.5rem; Instrumentation code lives in hundreds of services and outlives any vendor contract; if it speaks OTel, switching or adding a back end is a collector configuration change rather than a multi-quarter re-instrumentation project. The ADOT <strong>Collector</strong> makes that concrete: it receives OTLP from your services, applies processors (batch, memory limiter, tail sampling, attribute redaction, resource detection that stamps EC2/ECS/EKS identity), and exports simultaneously to the X-Ray exporter, a Prometheus remote-write endpoint, CloudWatch via EMF, and a third-party APM. Run it as a sidecar for per-pod isolation, as a DaemonSet for node-level efficiency, or as a gateway deployment when you need tail sampling across a whole trace. For Lambda, ADOT ships as a managed layer configured with <code>AWS_LAMBDA_EXEC_WRAPPER</code>; note the cold-start cost, which is why many teams use the Lambda-specific lightweight configuration.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Sampling: The Economics and the Correctness Rule</h4>\n<p style=\"line-height: 1.75\">Tracing every request at scale is prohibitively expensive — not mainly in dollars per trace, but in the network, storage and collector capacity to move full span trees for millions of requests per minute, plus the fact that the thousandth identical successful trace teaches you nothing. Sampling reduces volume while preserving statistical usefulness.</p>\n<p style=\"line-height: 1.75\">X-Ray sampling rules are centrally defined and pulled by the SDK or collector, so you can change sampling fleet-wide without a deploy. Each rule matches on service name, service type, host, HTTP method, URL path and resource ARN, and specifies two knobs: a <strong>reservoir</strong> (a fixed number of requests per second traced unconditionally, guaranteeing coverage on low-traffic endpoints) and a <strong>fixed rate</strong> (a percentage of requests beyond the reservoir). The default rule is a small reservoir of one request per second plus a low single-digit percentage. Rules have priorities; the lowest-numbered matching rule wins, so you layer specific high-value rules above a cheap catch-all.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>High-value paths.</strong> Give <code>/checkout</code> and <code>/payments</code> a 100% rate — a few hundred traces per second on the revenue path is cheap relative to the blast radius of an undiagnosed outage.</li>\n<li><strong>Noise reduction.</strong> Health checks, static assets and polling endpoints get a rule with a zero or near-zero rate; they dominate request counts and teach nothing.</li>\n<li><strong>Always trace errors.</strong> Head-based sampling decides before the outcome is known, so you cannot express \"sample all 5xx\" in an X-Ray sampling rule. The real answer is <strong>tail sampling in the collector</strong>: buffer complete traces and keep those with an error status, a latency above a threshold, or a rare attribute, plus a probabilistic slice of the boring ones. Tail sampling requires that all spans of a trace reach the same collector instance, which is why you deploy a gateway tier with trace-ID-aware load balancing.</li>\n<li><strong>Consistency is mandatory.</strong> The sampling decision is made once, at the entry point, and propagated in the <code>Sampled</code> flag or the W3C trace flags. Every downstream service must honour it. If services sample independently you get partial traces — the worst possible outcome, because they look complete and silently mislead you about where time went.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">ServiceLens, the Service Map, and Application Signals</h4>\n<p style=\"line-height: 1.75\"><strong>ServiceLens</strong> is the CloudWatch surface that stitches traces, metrics and logs together. Its centrepiece is the <strong>service map</strong>: an automatically derived topology in which each node is a service or downstream resource, sized and coloured by traffic, latency and fault rate. You do not draw it — it is inferred from the segments themselves, which makes it the fastest way to discover that a service you did not know about is on the critical path. Clicking a node gives the latency distribution and error/fault/throttle counts; clicking an edge gives the traces that crossed it; from a trace you jump to the exact CloudWatch Logs entries for that request, because the trace ID is injected into the log context by the instrumentation.</p>\n<p style=\"line-height: 1.75\"><strong>CloudWatch Application Signals</strong> builds an APM layer on this foundation. With OTel-based auto-instrumentation on EKS, ECS, EC2 or Lambda, it emits standardised application-level metrics (request volume, latency, availability/fault rate) per service and per operation without bespoke custom metrics, discovers services automatically, and lets you define <strong>SLOs</strong> with targets and error budgets that it tracks and burns down over time. The interview point is that this converts tracing from a debugging tool used during incidents into a continuous reliability practice: the same instrumentation drives the service map, the golden-signal dashboards and the SLO alerts.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cost, Quotas and Real Limits</h4>\n<p style=\"line-height: 1.75\">X-Ray charges along three axes: traces <strong>recorded</strong> (ingested), traces <strong>retrieved</strong> (via GetTraceSummaries and the console), and traces <strong>scanned</strong> by analytics-style queries; a monthly free tier covers small workloads. Because retrieval and scanning are billable, an automation that repeatedly polls trace summaries across a wide time range can cost more than the ingestion itself — the same polling-cost lesson as CloudWatch GetMetricData. Traces are retained for a bounded window (on the order of a month), which means X-Ray is an incident-and-recent-trend tool, not a long-term forensic archive; if you need year-scale retention, export spans from the collector to S3 as well.</p>\n<p style=\"line-height: 1.75\">Structural limits to know: a segment document has a maximum size, so oversized metadata is dropped or the segment rejected; there is a cap on indexed annotation keys per trace; the number of segments in one trace is bounded, so fan-out patterns that create thousands of subsegments will truncate; and the daemon or collector buffers in memory and <em>drops</em> spans under pressure rather than blocking your application — deliberately, since tracing must never become a source of latency. That last behaviour is why \"missing traces\" during an incident is often a symptom of the incident rather than a tracing bug.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Production Scenario: A p99 Regression Across a Five-Hop Chain</h4>\n<p style=\"line-height: 1.75\">The checkout API's p99 moved from 400 ms to 2.4 s after a release train; p50 is unchanged, every service's own dashboard is green, and error rates are flat.
