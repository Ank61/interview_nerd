Filtering to false instantly narrows an investigation to things that actually altered something.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Step one: Event history and lookup-events</h4>\n<p style=\"line-height: 1.75\">For a single question inside the last 90 days, the console's <strong>Event history</strong> page is the fastest tool in AWS. It lets you filter on one attribute at a time — user name, event name, resource type, resource name, event source, access key ID, or event ID — plus a time range. The same capability is available programmatically as the <strong>LookupEvents</strong> API, or <code>aws cloudtrail lookup-events</code> on the command line, which is far easier to script and to pipe into other tools.</p>\n<p style=\"line-height: 1.75\">Two limits to internalise. A moderately busy account produces millions of events a month. \"Show me every failed console login by IP address, grouped and counted, for the past year\" is not a thing you can click your way to. You also cannot see anything older than 90 days there — even though a trail has been faithfully writing those events to S3 the whole time. So for anything analytical you query the delivered files directly.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Querying S3 logs with Amazon Athena</h4>\n<p style=\"line-height: 1.75\"><strong>Amazon Athena</strong> is a service that runs ordinary SQL directly over files sitting in S3. There is no database to provision and nothing to load — you define a <em>table</em> that describes the shape of the files and where they live, and Athena reads them where they are, in parallel. You pay per query, based on the <strong>amount of data scanned</strong>.</p>\n<p style=\"line-height: 1.75\">You do not have to write the table definition by hand. In the CloudTrail console, the Event history page offers <strong>Create Athena table</strong>, which generates a CREATE TABLE statement matching the CloudTrail JSON schema and pointing at your trail's bucket and prefix. Run it once in Athena and you can start querying.</p>\n<p style=\"line-height: 1.75\"><strong>Partitioning</strong> is the single most important thing to get right. A partition is a way of telling Athena that the folder structure carries meaning — here, that <code>.../2026/09/16/</code> means a specific Region and date. Without partitions, a query for one day's failed logins reads <em>every file in the bucket</em>, which is slow and directly expensive because Athena bills on bytes scanned. With partitions and a WHERE clause on the partition columns, the same query reads one day of one Region. The difference is routinely a hundredfold in both time and cost. The modern approach is <strong>partition projection</strong>, where you declare the date and Region ranges in the table properties and Athena computes partitions automatically — no need to run a repair or add partitions as new days arrive.</p>\n<p style=\"line-height: 1.75\">Three queries that earn their keep: failed console logins (credential stuffing and lost-password noise both show here), everything a specific role did in a window, and every destructive action in a time range. All three appear in the examples below.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">AWS CloudTrail Lake — the managed alternative</h4>\n<p style=\"line-height: 1.75\"><strong>CloudTrail Lake</strong> removes the plumbing. Instead of delivering to S3 and wiring up Athena, you create an <strong>event data store</strong> — a managed, immutable collection of events with its own retention period, configurable up to ten years — and you run SQL against it directly from the CloudTrail console or CLI. There is no bucket policy, no table definition, no partitioning, no Glue catalog to maintain. To be told about something you did not think to look for, stream the trail into <strong>CloudWatch Logs</strong>. Two tools then apply. <strong>CloudWatch Logs Insights</strong> is an ad-hoc query language over recent logs — excellent for interactive triage during an incident. <strong>Metric filters</strong> are standing patterns that turn matching log lines into a numeric metric, which a <strong>CloudWatch alarm</strong> can then watch and notify on via SNS.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Root account usage.</strong> Pattern on userIdentity.type equal to Root. The root user should essentially never be used; any occurrence deserves a page.</li>\n<li><strong>IAM policy changes.</strong> Pattern on event names such as PutUserPolicy, AttachRolePolicy, CreatePolicyVersion, DeleteRolePolicy. Privilege escalation shows up here first.</li>\n<li><strong>Security group changes.</strong> AuthorizeSecurityGroupIngress, RevokeSecurityGroupIngress, and the equivalents — someone opening port 22 or 3389 to the world is a classic finding.</li>\n<li><strong>Unauthorized API calls.</strong> errorCode of AccessDenied or UnauthorizedOperation. A handful per day is normal; a sudden burst from one principal or IP usually means someone is probing the edges of a stolen credential.</li>\n<li><strong>CloudTrail configuration changes.</strong> StopLogging, DeleteTrail, UpdateTrail — an attacker turning off the recording is about as loud a signal as exists.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">An investigation playbook</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Who deleted this resource?</strong> Look up by ResourceName, or query for the Delete/Terminate event name with the resource ID in requestParameters. Take the userIdentity, and if it is an assumed role, find the AssumeRole event that created that session name to reach the human or pipeline behind it.</li>\n<li><strong>Why is this call being denied?</strong> Find the event with <strong>errorCode AccessDenied</strong> (or UnauthorizedOperation for EC2). Read the errorMessage — it often names the exact action and resource — then read userIdentity to learn which principal was actually used. Most \"my permissions are right\" problems turn out to be a different role than the engineer assumed, or a permissions boundary, SCP, or resource policy denying it.</li>\n<li><strong>What did this compromised role do?</strong> Query every event where the userIdentity ARN or the access key matches, ordered by time, from the moment of the first suspicious event. Filter readOnly to false to see the damage, then separately review the read events to understand what data was viewed.</li>\n<li><strong>What changed right before the outage?</strong> Take the alarm time, subtract sixty minutes, and list every non-read event in that window ordered by time. Configuration changes cluster tightly before most self-inflicted incidents.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"Athena queries are free.\"</strong> Athena bills per terabyte scanned. Always filter on partition columns and select only the columns you need.</li>\n<li><strong>\"I can investigate something from last year with default settings.\"</strong> Without a trail you have 90 days, full stop. With a trail you have whatever is still in S3 or still inside your Lake retention window.</li>\n<li><strong>\"CloudTrail tells me who read an S3 object.\"</strong> Not by default. Only management events (bucket creation, policy changes) are recorded out of the box.</li>\n<li><strong>\"lookup-events can filter on several attributes at once.\"</strong> It accepts exactly one lookup attribute. Combine conditions in Athena or Lake, not in lookup.</li>\n<li><strong>\"The role ARN in the event tells me who the person was.\"</strong> It tells you the role. You must follow the session back through AssumeRole to identify the actual principal.</li>\n<li><strong>\"CloudTrail is real-time.\"</strong> Expect minutes of delay.
