{"title":"Nest CLI","tags":["cli","schematics","monorepo","nest-cli-json"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">\nThe Nest CLI is the command-line tool that creates projects, generates files, and builds and runs your app. It does three jobs that are easy to mix up: <span style=\"font-weight: 600\">scaffolding</span> (writing new files for you), <span style=\"font-weight: 600\">building</span> (turning TypeScript into JavaScript), and <span style=\"font-weight: 600\">running</span> (starting the app in watch mode during development).\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">npm i -g @nestjs/cli      <i class=c># install globally</i>\nnest new my-api           <i class=c># create a project</i>\nnest g resource orders    <i class=c># generate a full CRUD feature</i>\nnest start --watch        <i class=c># run in development</i>\nnest build                <i class=c># compile for production</i></code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nYou can do all of this without the CLI. But the generated code follows the framework's conventions exactly, which matters a lot when several people work on the same codebase &mdash; everyone's modules look the same, so reviews are about the logic instead of the layout.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nCreating a Project\n</h4>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">nest new my-api                        <i class=c># asks which package manager</i>\nnest new my-api --package-manager pnpm\nnest new my-api --strict               <i class=c># turns on strict TypeScript</i>\nnest new my-api --skip-git</code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nUse <code>--strict</code> if you have the choice. The default project has several TypeScript safety checks turned off, and turning them on later means fixing dozens of errors at once. Turning them on at the start costs almost nothing.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nGenerating Files\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\n<code>nest generate</code> (short form <code>nest g</code>) creates files from templates. The templates are called <span style=\"font-weight: 600\">schematics</span>. The general shape is <code>nest g &lt;type&gt; &lt;name&gt;</code>.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">nest g module orders          <i class=c># a module</i>\nnest g controller orders      <i class=c># a controller + a spec file</i>\nnest g service orders         <i class=c># a service + a spec file</i>\nnest g class order.entity     <i class=c># a plain class</i>\nnest g interface order        <i class=c># an interface</i>\nnest g guard auth             <i class=c># a guard</i>\nnest g interceptor logging    <i class=c># an interceptor</i>\nnest g pipe validate          <i class=c># a pipe</i>\nnest g filter http-exception  <i class=c># an exception filter</i>\nnest g middleware logger      <i class=c># middleware</i>\nnest g decorator current-user <i class=c># a custom decorator</i>\nnest g gateway events         <i class=c># a WebSocket gateway</i>\nnest g resolver orders        <i class=c># a GraphQL resolver</i>\nnest g provider payment       <i class=c># a generic provider</i></code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nTwo things happen that people do not expect. First, the CLI puts the file in a folder named after what you generated &mdash; <code>nest g service orders</code> creates <code>src/orders/orders.service.ts</code>. Second, it <span style=\"font-weight: 600\">edits your module file for you</span>, adding the new class to the right array and adding the import at the top. That automatic edit is genuinely useful, because forgetting to register something is the most common beginner mistake.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nUseful flags:\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">nest g service orders --dry-run   <i class=c># show what WOULD happen, change nothing</i>\nnest g service orders --flat      <i class=c># do not create a folder</i>\nnest g service orders --no-spec   <i class=c># skip the test file</i>\nnest g controller orders/items    <i class=c># nest it inside an existing folder</i>\nnest g service shared/logger      <i class=c># path is relative to src/</i></code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\n<code>--dry-run</code> is worth knowing about. The CLI writes several files and edits your module, and if you got the path wrong you now have a mess to clean up. Running it first with <code>--dry-run</code> shows the exact list before anything changes.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nnest g resource: The Big One\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThis is the command that saves the most time. It generates a complete feature in one go:\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">nest g resource orders</code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nIt asks which transport you want &mdash; REST, GraphQL, a microservice or WebSockets &mdash; and whether to include CRUD boilerplate. Then it writes:\n</p>\n<ul style=\"margin-top: 1.0rem; margin-left: 1.5rem; list-style-type: disc\">\n<li style=\"margin-top: 0.4rem\">the module, controller and service</li>\n<li style=\"margin-top: 0.4rem\">a create DTO and an update DTO, with the update one already built using <code>PartialType</code></li>\n<li style=\"margin-top: 0.4rem\">an entity class</li>\n<li style=\"margin-top: 0.4rem\">spec files for the controller and service</li>\n<li style=\"margin-top: 0.4rem\">five wired-up route handlers: create, findAll, findOne, update, remove</li>\n<li style=\"margin-top: 0.4rem\">the module registered in <code>AppModule</code></li>\n</ul>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThe generated code is a starting point, not a finished feature. It uses <code>:id</code> parameters with no pipes, returns plain strings from the service, and has no validation decorators on the DTOs. Treat it as a skeleton you fill in, and add the pipes and validation immediately rather than later.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nRunning and Building\n</h4>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">nest start                 <i class=c># compile once and run</i>\nnest start --watch         <i class=c># restart when files change (development)</i>\nnest start --debug --watch <i class=c># same, with the Node inspector attached</i>\nnest build                 <i class=c># compile to dist/</i>\nnest build --watch         <i class=c># keep compiling on change, do not run</i></code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nIn production you do not use the CLI at all. You run <code>nest build</code> during the image build, then start the plain Node process with <code>node dist/main</code>. That keeps the CLI and its dependencies out of your runtime image.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nnest-cli.json\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThis file controls everything the CLI does. A default one looks like this:\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>json</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=x>{</i>\n  <i class=a>&quot;$schema&quot;</i><i class=x>:</i> <i class=s>&quot;https://json.schemastore.org/nest-cli&quot;</i><i class=x>,</i>\n  <i class=a>&quot;collection&quot;</i><i class=x>:</i> <i class=s>&quot;@nestjs/schematics&quot;</i><i class=x>,</i>\n  <i class=a>&quot;sourceRoot&quot;</i><i class=x>:</i> <i class=s>&quot;src&quot;</i><i class=x>,</i>\n  <i class=a>&quot;compilerOptions&quot;</i><i class=x>:</i> <i class=x>{</i>\n    <i class=a>&quot;deleteOutDir&quot;</i><i class=x>:</i> <i class=l><i class=k>true</i></i>\n  <i class=x>}</i>\n<i class=x>}</i></code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThe parts worth knowing:\n</p>\n<ul style=\"margin-top: 1.0rem; margin-left: 1.5rem; list-style-type: disc\">\n<li style=\"margin-top: 0.4rem\"><span style=\"font-weight: 600\">collection</span> &mdash; which set of templates to use. You can point this at your own schematics package.</li>\n<li style=\"margin-top: 0.4rem\"><span style=\"font-weight: 600\">sourceRoot</span> &mdash; where the CLI puts generated files.</li>\n<li style=\"margin-top: 0.4rem\"><span style=\"font-weight: 600\">deleteOutDir</span> &mdash; wipe <code>dist/</code> before building. Turn this on. Without it, deleted source files leave stale JavaScript behind that still gets loaded.</li>\n<li style=\"margin-top: 0.4rem\"><span style=\"font-weight: 600\">assets</span> &mdash; non-TypeScript files to copy into <code>dist/</code>, such as templates, email files or GraphQL schemas. If something works in development and disappears in production, this is usually why.</li>\n<li style=\"margin-top: 0.4rem\"><span style=\"font-weight: 600\">builder</span> &mdash; <code>tsc</code> (default), <code>swc</code> (much faster), or <code>webpack</code>.</li>\n<li style=\"margin-top: 0.4rem\"><span style=\"font-weight: 600\">plugins</span> &mdash; compile-time helpers, described below.</li>\n<li style=\"margin-top: 0.4rem\"><span style=\"font-weight: 600\">generateOptions</span> &mdash; defaults for <code>nest g</code>, for example <code>\"spec\": false</code> to stop generating test files.</li>\n</ul>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>json</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=x>{</i>\n  <i class=a>&quot;sourceRoot&quot;</i><i class=x>:</i> <i class=s>&quot;src&quot;</i><i class=x>,</i>\n  <i class=a>&quot;compilerOptions&quot;</i><i class=x>:</i> <i class=x>{</i>\n    <i class=a>&quot;deleteOutDir&quot;</i><i class=x>:</i> <i class=l><i class=k>true</i></i><i class=x>,</i>\n    <i class=a>&quot;builder&quot;</i><i class=x>:</i> <i class=s>&quot;swc&quot;</i><i class=x>,</i>\n    <i class=a>&quot;assets&quot;</i><i class=x>:</i> <i class=x>[</i>\n      <i class=x>{</i> <i class=a>&quot;include&quot;</i><i class=x>:</i> <i class=s>&quot;mail/templates/**/*.hbs&quot;</i><i class=x>,</i> <i class=a>&quot;outDir&quot;</i><i class=x>:</i> <i class=s>&quot;dist&quot;</i> <i class=x>}</i><i class=x>,</i>\n      <i class=s>&quot;**/*.graphql&quot;</i>\n    <i class=x>]</i><i class=x>,</i>\n    <i class=a>&quot;watchAssets&quot;</i><i class=x>:</i> <i class=l><i class=k>true</i></i><i class=x>,</i>\n    <i class=a>&quot;plugins&quot;</i><i class=x>:</i> <i class=x>[</i><i class=s>&quot;@nestjs/swagger&quot;</i><i class=x>]</i>\n  <i class=x>}</i><i class=x>,</i>\n  <i class=a>&quot;generateOptions&quot;</i><i class=x>:</i> <i class=x>{</i> <i class=a>&quot;spec&quot;</i><i class=x>:</i> <i class=l><i class=k>false</i></i> <i class=x>}</i>\n<i class=x>}</i></code></pre></div>\n</div>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nCLI Plugins\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nA plugin reads your source code while it compiles and adds things automatically. The Swagger plugin is the one nearly everyone uses. Without it, you decorate every DTO property by hand:\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>typescript</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=k>export</i> <i class=k>class</i> <i class=f>CreateOrderDto</i> {\n  <i class=m>@ApiProperty</i>({ <i class=a>description</i>: <i class=s>&#x27;Customer id&#x27;</i> })\n  <i class=m>@IsUUID</i>()\n  <i class=a>customerId</i>: <i class=b>string</i>;\n  <i class=m>@ApiProperty</i>({ <i class=a>required</i>: <i class=l>false</i>, <i class=a>type</i>: <i class=f>String</i> })\n  <i class=m>@IsOptional</i>() <i class=m>@IsString</i>()\n  <i class=a>note</i>?: <i class=b>string</i>;\n}</code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nWith the plugin turned on, you delete every <code>@ApiProperty</code>. The plugin reads the real TypeScript types before they are erased and adds the annotations for you &mdash; including whether a field is optional, whether it is an array, and what the enum values are. It can also pull your comments through as descriptions.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThis is worth understanding for interviews, because it explains something otherwise puzzling. Types are erased at compile time, so how can Swagger know that <code>note</code> is an optional string? The answer is that the plugin runs <span style=\"font-weight: 600\">before</span> erasure, at compile time, and writes the information into the output.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nThe SWC Builder\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nSWC is a compiler written in Rust that is many times faster than <code>tsc</code>. Switching to it can turn a twenty-second rebuild into a two-second one, which changes how development feels.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nBut there is a serious catch, and it is a favourite interview question. <span style=\"font-weight: 600\">SWC does not read your tsconfig settings for decorators.</span> It needs its own configuration:\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>json</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c>// .swcrc</i>\n<i class=x>{</i>\n  <i class=a>&quot;jsc&quot;</i><i class=x>:</i> <i class=x>{</i>\n    <i class=a>&quot;parser&quot;</i><i class=x>:</i> <i class=x>{</i> <i class=a>&quot;syntax&quot;</i><i class=x>:</i> <i class=s>&quot;typescript&quot;</i><i class=x>,</i> <i class=a>&quot;decorators&quot;</i><i class=x>:</i> <i class=l><i class=k>true</i></i> <i class=x>}</i><i class=x>,</i>\n    <i class=a>&quot;transform&quot;</i><i class=x>:</i> <i class=x>{</i> <i class=a>&quot;legacyDecorator&quot;</i><i class=x>:</i> <i class=l><i class=k>true</i></i><i class=x>,</i> <i class=a>&quot;decoratorMetadata&quot;</i><i class=x>:</i> <i class=l><i class=k>true</i></i> <i class=x>}</i><i class=x>,</i>\n    <i class=a>&quot;target&quot;</i><i class=x>:</i> <i class=s>&quot;es2021&quot;</i>\n  <i class=x>}</i>\n<i class=x>}</i></code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nMiss <code>decoratorMetadata</code> and the app still compiles, still starts, and every injected dependency is <code>undefined</code>. There is no compile error, because the missing piece is the metadata Nest reads at runtime to know what to inject.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nTwo more SWC differences. It does not type-check &mdash; it only strips types, so you need <code>tsc --noEmit</code> in CI to catch type errors. And it compiles one file at a time with no cross-file knowledge, which breaks <code>const enum</code>.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nStandalone Mode vs Monorepo Mode\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\n<span style=\"font-weight: 600\">Standalone mode</span> is the default: one app, one <code>src</code> folder, one <code>package.json</code>.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>code</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">my-api/\n  src/\n  test/\n  package.json\n  nest-cli.json</code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\n<span style=\"font-weight: 600\">Monorepo mode</span> holds several applications and shared libraries in one repository, with one <code>package.json</code> and one <code>node_modules</code>.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>code</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">my-platform/\n  apps/\n    api/          &lt;- deployable app\n    worker/       &lt;- deployable app\n    admin/        &lt;- deployable app\n  libs/\n    shared/       &lt;- shared code, not deployed on its own\n    database/\n  package.json\n  nest-cli.json</code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nYou switch by generating an app or a library, which converts the project automatically:\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">nest g app worker       <i class=c># converts to monorepo mode on first use</i>\nnest g library shared\nnest build api          <i class=c># build one app</i>\nnest start worker --watch\nnest g module orders --project api   <i class=c># generate into a specific app</i></code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nGenerating a library also adds a path alias to your tsconfig, so you import it by name rather than by a long relative path:\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>typescript</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=k>import</i> { <i class=f>OrderStatus</i> } <i class=k>from</i> <i class=s>&#x27;@app/shared&#x27;</i>;\n<i class=c>// instead of</i>\n<i class=k>import</i> { <i class=f>OrderStatus</i> } <i class=k>from</i> <i class=s>&#x27;../../../../libs/shared/src/order-status&#x27;</i>;</code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\n<span style=\"font-weight: 600\">The key difference between apps and libs:</span> an app is something you deploy and has its own <code>main.ts</code>. A library is code that apps import and is never run on its own.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\n<span style=\"font-weight: 600\">When monorepo mode is a good fit:</span> two or three services that share domain types and utilities, where you want one place to change a shared type and have every service pick it up.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\n<span style=\"font-weight: 600\">Where it stops being enough:</span> Nest's monorepo mode has no build caching, no way to work out which apps a change affects, and no enforcement of which library may import which. Past a handful of apps, teams usually move to Nx or Turborepo, which add exactly those things. The single <code>package.json</code> is also a real limitation &mdash; every app installs every dependency, so a package needed by one service ends up in all of their images.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nOther Commands\n</h4>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">nest info      <i class=c># versions of Node, npm and every Nest package - include in bug reports</i>\nnest add @nestjs/config   <i class=c># install a package AND run its setup schematic</i>\nnest --<i class=b>help</i>\nnest g --<i class=b>help</i></code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\n<code>nest add</code> is different from <code>npm install</code>. It installs the package and then runs a schematic that wires it in for you &mdash; editing modules, adding config files. Not every package supports it, but when it does, it saves a manual setup step.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nYour Own Schematics\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nIf your team has house conventions &mdash; every feature gets a repository, a port interface and a mapper &mdash; you can build your own templates and point <code>collection</code> at them:\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>json</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=x>{</i> <i class=a>&quot;collection&quot;</i><i class=x>:</i> <i class=s>&quot;@mycompany/nest-schematics&quot;</i> <i class=x>}</i></code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThis turns a written convention into something the tooling produces automatically, which is far more reliable than hoping people read the wiki.
