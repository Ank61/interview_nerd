Learn the order first, then learn why each step is where it is.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nThe Order, To Memorise\n</h4>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>code</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">Request arrives\n      |\n  1. They are the only stage that wraps around your code.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\n<span style=\"font-weight: 600\">The order reverses on the way out.</span> On the way in it is global, then controller, then route. On the way out it is route, then controller, then global. Interceptors nest like boxes inside boxes, so the outermost one starts first and finishes last.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nA short way to remember the sequence: <span style=\"font-weight: 600\">M-G-I-P-H-I-F</span>. Middleware, Guards, Interceptors, Pipes, Handler, Interceptors, Filters.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\n1. Middleware\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThe first thing to run. Middleware sits below Nest &mdash; it is Express or Fastify middleware that Nest happens to bind for you. It gets the raw request and response, plus a <code>next</code> function it must call to continue.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\n<span style=\"font-weight: 600\">Use it for:</span> correlation IDs, raw body capture, request rewriting, and adapting third-party Express middleware.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\n<span style=\"font-weight: 600\">The key limitation:</span> middleware has <span style=\"font-weight: 600\">no <code>ExecutionContext</code></span>. It cannot call <code>getHandler()</code> or <code>getClass()</code>, so it cannot read metadata written by decorators like <code>@Roles()</code>.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThat is not an oversight. Middleware is attached to <span style=\"font-weight: 600\">paths</span>, and at the moment it runs Express has not yet decided which controller method will handle the request. There is no handler to describe. So anything that depends on route metadata must be a guard or an interceptor instead.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nOne ordering detail: middleware registered with <code>app.use()</code> in <code>main.ts</code> always runs before middleware bound through a module's <code>configure()</code>, no matter how the code reads.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\n2. That is what makes <code>@Roles()</code> and <code>@Public()</code> possible.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>typescript</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=m>@Injectable</i>()\n<i class=k>export</i> <i class=k>class</i> <i class=f>RolesGuard</i> <i class=k>implements</i> <i class=f>CanActivate</i> {\n  <i class=f>constructor</i>(<i class=p><i class=k>private</i> <i class=a>reflector</i>: <i class=f>Reflector</i></i>) {}\n  <i class=f>canActivate</i>(<i class=a>ctx</i>: <i class=f>ExecutionContext</i>): <i class=b>boolean</i> {\n    <i class=k>const</i> required = <i class=v>this</i>.<i class=v>reflector</i>.<i class=v>getAllAndOverride</i>&lt;<i class=f>Role</i>[]&gt;(<i class=s>&#x27;roles&#x27;</i>, [\n      ctx.<i class=f>getHandler</i>(),   <i class=c>// method-level wins</i>\n      ctx.<i class=f>getClass</i>(),     <i class=c>// falls back to controller-level</i>\n    ]);\n    <i class=k>if</i> (!required) <i class=k>return</i> <i class=l>true</i>;\n    <i class=k>const</i> { user } = ctx.<i class=f>switchToHttp</i>().<i class=f>getRequest</i>();\n    <i class=k>return</i> required.<i class=f>some</i>(<i class=function>(<i class=p>r</i>) =&gt;</i> user?.<i class=v>roles</i>?.<i class=f>includes</i>(r));\n  }\n}</code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\n<span style=\"font-weight: 600\">The consequence people miss:</span> guards run <span style=\"font-weight: 600\">before pipes</span>, so the body a guard sees is raw and unvalidated. <code>ValidationPipe</code> has not run, nothing has been converted, and <code>whitelist</code> has not stripped unexpected fields.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nSo a guard reading <code>request.body.tenantId</code> is reading whatever the client sent &mdash; possibly an object, an array, or nothing. Basing an authorisation decision on that without checking it is a real security risk. Prefer deciding from something already trustworthy, such as a verified JWT claim or a route parameter.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nReturning <code>false</code> produces a generic 403. Throwing gives you a specific message, which is usually better.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\n3. Interceptors, First Half\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nAn interceptor wraps your handler. Everything before <code>next.handle()</code> runs on the way in; the RxJS operators after it run on the way out.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>typescript</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=m>@Injectable</i>()\n<i class=k>export</i> <i class=k>class</i> <i class=f>TimingInterceptor</i> <i class=k>implements</i> <i class=f>NestInterceptor</i> {\n  <i class=f>intercept</i>(<i class=p><i class=a>ctx</i>: <i class=f>ExecutionContext</i>, <i class=a>next</i>: <i class=f>CallHandler</i></i>) {\n    <i class=k>const</i> started = <i class=f>Date</i>.<i class=f>now</i>();                       <i class=c>// BEFORE the handler</i>\n    <i class=k>return</i> next.<i class=f>handle</i>().<i class=f>pipe</i>(                        <i class=c>// handler runs here</i>\n      <i class=f>map</i>(<i class=function>(<i class=p>data</i>) =&gt;</i> ({ data, <i class=a>ms</i>: <i class=f>Date</i>.<i class=f>now</i>() - started })),   <i class=c>// AFTER</i>\n      <i class=f>catchError</i>(<i class=function>(<i class=p>err</i>) =&gt;</i> { <i class=c>/* observe errors */</i> <i class=k>throw</i> err; }),\n    );\n  }\n}</code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nBecause they wrap, interceptors can do things no other stage can: measure total duration, transform the response, add a caching layer that skips the handler entirely, or apply a timeout.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nA caching interceptor is the clearest example of why they sit here. It can check the cache <em>before</em> the handler and return a value without ever calling it &mdash; something a pipe or a guard cannot do.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\n4. Pipes\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nPipes do two jobs: <span style=\"font-weight: 600\">transform</span> a value, and <span style=\"font-weight: 600\">validate</span> it. They run per parameter, right before your method is called.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>typescript</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=m>@Get</i>(<i class=s>&#x27;:id&#x27;</i>)\n<i class=f>findOne</i>(<i class=p>\n  <i class=m>@Param</i>(<i class=s>&#x27;id&#x27;</i>, ParseUUIDPipe) <i class=a>id</i>: <i class=b>string</i>,\n  <i class=m>@Query</i>(<i class=s>&#x27;page&#x27;</i>, <i class=k>new</i> DefaultValuePipe(<i class=n>1</i>), ParseIntPipe) <i class=a>page</i>: <i class=b>number</i>,\n</i>) {}</code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nOrder within one parameter is left to right, with each pipe receiving what the previous one returned. Across levels it is global, then controller, then route, then parameter.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nPipes come <span style=\"font-weight: 600\">after</span> guards deliberately. Validating a body is work, and there is no point doing it for a request that is about to be rejected as unauthorised. Checking permission first is cheaper and avoids leaking information about your validation rules to unauthenticated callers.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\n5 and 6. Handler and Services\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nYour controller method finally runs, with arguments that are already extracted, converted and validated. It calls a service, which does the real work.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nEverything the earlier stages did exists to make this method simple. By the time it runs, the caller is authenticated and authorised, the input is the right shape, and the values are the right types.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\n7. Interceptors, Second Half\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThe value your handler returned now travels back out through every interceptor, <span style=\"font-weight: 600\">in reverse order</span>.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>code</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">IN:   Global  -&gt;  Controller  -&gt;  Route  -&gt;  [ HANDLER ]\nOUT:                                         [ HANDLER ]  -&gt;  Route  -&gt;  Controller  -&gt;  Global</code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThink of them as nested boxes. The global interceptor is the outer box: it opens first and closes last. This is exactly how <code>ClassSerializerInterceptor</code> strips <code>@Exclude()</code> fields and how a response-wrapping interceptor adds an envelope.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nNest also handles async here: a returned Promise is awaited, and an Observable has its first emitted value taken.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\n8. Exception Filters\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nIf anything threw &mdash; in a guard, a pipe, an interceptor, the handler or a service &mdash; the normal flow stops and filters take over.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nFilters resolve in the <span style=\"font-weight: 600\">opposite</span> direction to everything else: <span style=\"font-weight: 600\">route, then controller, then global</span>. The most specific filter that matches the exception type wins.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThat direction makes sense once you see it as a fallback chain. A route-level filter handling one specific error is more specific than a global catch-all, so it gets first refusal.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>typescript</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=m>@Catch</i>(<i class=f>OrderNotFoundError</i>)          <i class=c>// very specific</i>\n<i class=k>export</i> <i class=k>class</i> <i class=f>OrderNotFoundFilter</i> <i class=k>implements</i> <i class=f>ExceptionFilter</i> { <i class=c>/* ... */</i> }\n<i class=m>@Catch</i>(<i class=f>HttpException</i>)               <i class=c>// less specific</i>\n<i class=k>export</i> <i class=k>class</i> <i class=f>HttpFilter</i> <i class=k>implements</i> <i class=f>ExceptionFilter</i> { <i class=c>/* ... */</i> }\n<i class=m>@Catch</i>()                            <i class=c>// catches everything - register globally</i>\n<i class=k>export</i> <i class=k>class</i> <i class=f>AllExceptionsFilter</i> <i class=k>implements</i> <i class=f>ExceptionFilter</i> { <i class=c>/* ... */</i> }</code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nOne important detail: <span style=\"font-weight: 600\">middleware errors do not reach Nest's filters</span>. If you need consistent error shapes, do not throw from middleware.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nGlobal, Controller and Route Levels\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nGuards, interceptors and pipes can all be attached at three levels, and they run <span style=\"font-weight: 600\">in that order regardless of how you stack the decorators</span>:\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>typescript</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c>// global - in CoreModule</i>\n{ <i class=a>provide</i>: <i class=v>APP_GUARD</i>, <i class=a>useClass</i>: <i class=f>JwtAuthGuard</i> }\n<i class=c>// controller level</i>\n<i class=m>@UseGuards</i>(<i class=f>RolesGuard</i>)\n<i class=m>@Controller</i>(<i class=s>&#x27;orders&#x27;</i>)\n<i class=k>export</i> <i class=k>class</i> <i class=f>OrdersController</i> {\n  <i class=c>// route level</i>\n  <i class=m>@UseGuards</i>(<i class=f>OwnershipGuard</i>)\n  <i class=m>@Get</i>(<i class=s>&#x27;:id&#x27;</i>)\n  <i class=f>findOne</i>(<i class=p></i>) {}\n}\n<i class=c>// Runs: JwtAuthGuard -&gt; RolesGuard -&gt; OwnershipGuard</i></code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nTwo things that follow from this.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\n<span style=\"font-weight: 600\">A method-level guard can never run before a global one.</span> Rearranging decorators changes nothing.
