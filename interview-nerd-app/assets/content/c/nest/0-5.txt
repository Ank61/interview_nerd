In Nest this principle is load-bearing because the container substitutes implementations for you &mdash; a consumer injecting <code>NotificationPort</code> has no idea whether it received the SES adapter, the SendGrid adapter or a test double, and it must not need to.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nViolations show up in recognisable ways:\n</p>\n<ol style=\"margin-top: 1.0rem; margin-left: 1.5rem; list-style-type: number\">\n<li style=\"margin-top: 0.5rem\"><span style=\"font-weight: 600\">Strengthened preconditions.</span> The base <code>send(to, body)</code> accepts any string; the SMS implementation throws if the body exceeds 160 characters. Callers written against the base now break when the implementation is swapped.</li>\n<li style=\"margin-top: 0.5rem\"><span style=\"font-weight: 600\">Weakened postconditions.</span> The base contract says <code>findById</code> returns the entity or <code>null</code>; one implementation throws instead. This is usually a signal that the interface is too fat &mdash; an ISP problem masquerading as an LSP one.</li>\n<li style=\"margin-top: 0.5rem\"><span style=\"font-weight: 600\">Changed error types.</span> One adapter throws <code>HttpException</code>, another throws a raw driver error. The consumer's error handling only works for one of them, which is why a well-designed port defines its <em>own</em> error taxonomy that every adapter must map onto.</li>\n</ol>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nA Nest-specific LSP hazard worth naming: <span style=\"font-weight: 600\">injection scope is part of the contract.</span> If a base provider is a singleton and you substitute a <code>REQUEST</code>-scoped implementation, every consumer up the injection chain silently becomes request-scoped too. Abstractions should not depend on details; details should depend on abstractions. <span style=\"font-weight: 600\">This is the principle Nest is built to serve</span>, and the IoC container is the machinery that serves it.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nTwo distinctions are worth stating precisely, because they are routinely conflated:\n</p>\n<ul style=\"margin-top: 1.0rem; margin-left: 1.5rem; list-style-type: disc\">\n<li style=\"margin-top: 0.4rem\"><span style=\"font-weight: 600\">Dependency Injection</span> is a technique: an object receives its collaborators rather than constructing them.</li>\n<li style=\"margin-top: 0.4rem\"><span style=\"font-weight: 600\">Inversion of Control</span> is the broader inversion: the framework calls you rather than you calling the framework.</li>\n<li style=\"margin-top: 0.4rem\"><span style=\"font-weight: 600\">Dependency Inversion</span> is the design principle about the <em>direction of source-code dependencies</em> pointing toward abstractions.</li>\n</ul>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nCrucially, using Nest's DI does not automatically achieve DIP.
