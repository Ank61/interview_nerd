None of these are answerable from the Nest documentation &mdash; they are answered by understanding the event loop, libuv, and how work is actually scheduled.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nThe Architecture\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nNode.js is composed of V8 (the JavaScript engine), libuv (the C library providing the event loop, the thread pool and cross-platform async I/O), and the Node bindings that glue JavaScript APIs to libuv primitives. The commonly repeated claim that \"Node is single-threaded\" is imprecise and interviewers listen for the correction: <span style=\"font-weight: 600\">JavaScript execution is single-threaded, but Node.js as a process is multi-threaded.</span> There is one main thread running your JavaScript, plus a libuv thread pool (four threads by default), plus V8's own threads for garbage collection and JIT compilation.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThe consequence that matters: only one piece of your JavaScript runs at any instant. If a request handler spends 300&nbsp;ms doing synchronous work, every other connection &mdash; including health checks &mdash; waits 300&nbsp;ms. Concurrency in Node comes from <span style=\"font-weight: 600\">not waiting</span>, not from parallelism.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nThe Event Loop Phases\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nEach iteration of the loop (a \"tick\") passes through six phases in a fixed order. Each phase has its own FIFO callback queue and is drained &mdash; subject to a system-dependent limit &mdash; before moving on.\n</p>\n<ol style=\"margin-top: 1.0rem; margin-left: 1.5rem; list-style-type: number\">\n<li style=\"margin-top: 0.5rem\">\n<span style=\"font-weight: 600; font-size: 1.05rem\">Timers</span> &mdash; executes callbacks scheduled by <code>setTimeout</code> and <code>setInterval</code> whose threshold has elapsed. It computes how long to block waiting for new I/O, then processes the I/O queue: incoming sockets, completed file reads, database responses. If the poll queue is empty and there are <code>setImmediate</code> callbacks pending, it ends immediately and moves to check; otherwise it may block here waiting for events.\n</li>\n<li style=\"margin-top: 0.5rem\">\n<span style=\"font-weight: 600; font-size: 1.05rem\">Check</span> &mdash; executes <code>setImmediate</code> callbacks. This phase exists specifically so you can schedule work to run <em>after</em> the current poll phase completes.\n</li>\n<li style=\"margin-top: 0.5rem\">\n<span style=\"font-weight: 600; font-size: 1.05rem\">Close callbacks</span> &mdash; <code>socket.on('close')</code> and similar teardown handlers.\n</li>\n</ol>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nMicrotasks: nextTick and Promises\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nMicrotasks are not a phase.
