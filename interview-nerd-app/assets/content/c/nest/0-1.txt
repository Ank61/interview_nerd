{"title":"Decorators","tags":["decorators","metadata","typescript","nestjs-internals"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">\nA decorator is a function that receives a declaration and can observe, modify or replace it. Every single line of idiomatic NestJS code is decorators: <code>@Module</code>, <code>@Controller</code>, <code>@Injectable</code>, <code>@Get</code>, <code>@Body</code>, <code>@UseGuards</code>. Understanding what they compile to &mdash; and in what order they run &mdash; is the difference between using Nest and being able to extend it. Interviewers reliably ask \"what does <code>@Injectable()</code> actually do?\", and the correct answer is short and specific: almost nothing except write a metadata key.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nTwo Competing Decorator Specifications\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThere are two incompatible decorator designs, and knowing which one Nest uses is a common differentiator.\n</p>\n<ol style=\"margin-top: 1.0rem; margin-left: 1.5rem; list-style-type: number\">\n<li style=\"margin-top: 0.5rem\">\n<span style=\"font-weight: 600; font-size: 1.05rem\">Legacy / experimental decorators</span> &mdash; the Stage 2 proposal, enabled by <code>\"experimentalDecorators\": true</code>. This is what NestJS, TypeORM, Angular and class-validator are all built on. It supports parameter decorators and integrates with <code>emitDecoratorMetadata</code>.\n</li>\n<li style=\"margin-top: 0.5rem\">\n<span style=\"font-weight: 600; font-size: 1.05rem\">Stage 3 / standard decorators</span> &mdash; shipped in TypeScript 5.0 and now in the ECMAScript pipeline. Decorators receive a <code>context</code> object with <code>kind</code>, <code>name</code>, <code>static</code>, <code>private</code>, <code>addInitializer</code> and metadata access. Crucially, <span style=\"font-weight: 600\">the standard has no parameter decorators</span>, which is precisely why NestJS cannot migrate to it without a redesign of <code>@Body()</code>, <code>@Param()</code> and constructor injection.\n</li>\n</ol>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nTurning on <code>experimentalDecorators</code> keeps the legacy behaviour. Leaving it off in TypeScript 5+ silently switches you to the standard semantics, and every Nest decorator breaks. That is a very common \"why did my app stop working\" interview scenario.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nThe Five Decorator Kinds and Their Signatures\n</h4>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>typescript</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c>// 1. That second effect is the real reason it is required; the container reads paramtypes to resolve the constructor.</li>\n<li style=\"margin-top: 0.4rem\"><code>@Controller('path')</code> &mdash; writes <code>PATH_METADATA</code> plus host/version options, and triggers paramtypes emission for the controller's constructor.</li>\n<li style=\"margin-top: 0.4rem\"><code>@Get()</code>, <code>@Post()</code> &mdash; method decorators writing <code>PATH_METADATA</code> and <code>METHOD_METADATA</code>. The <code>RoutesResolver</code> scans these at bootstrap to register Express/Fastify routes.</li>\n<li style=\"margin-top: 0.4rem\"><code>@Body()</code>, <code>@Param()</code>, <code>@Query()</code> &mdash; parameter decorators writing <code>ROUTE_ARGS_METADATA</code>, a map keyed by <code>paramtype:index</code> that describes how to extract each argument from the request.</li>\n<li style=\"margin-top: 0.4rem\"><code>@Inject(TOKEN)</code> &mdash; a parameter (or property) decorator writing <code>SELF_DECLARED_DEPS_METADATA</code>, which the injector consults <span style=\"font-weight: 600\">in preference to</span> the reflected paramtype. This is the escape hatch for interfaces, strings and symbols.</li>\n<li style=\"margin-top: 0.4rem\"><code>@UseGuards()</code>, <code>@UseInterceptors()</code> &mdash; dual-purpose decorators usable at class or method level; they write <code>GUARDS_METADATA</code> / <code>INTERCEPTORS_METADATA</code>, which <code>Reflector.getAllAndOverride</code> later reads with method-over-class precedence.</li>\n<li style=\"margin-top: 0.4rem\"><code>SetMetadata(key, value)</code> &mdash; the generic primitive underneath custom decorators such as <code>@Roles()</code> and <code>@Public()</code>.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nWriting Custom Decorators\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThere are three custom-decorator patterns you should be able to write from memory, because they come up in nearly every Nest interview.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>typescript</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c>// 1.
