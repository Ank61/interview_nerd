Two types are compatible if their shapes are compatible, regardless of their declared names or inheritance relationships. A class that happens to have a <code>save()</code> method returning a Promise satisfies an interface requiring <code>save()</code>, even if it never declares <code>implements</code>. This is why the <code>implements</code> keyword in TypeScript is purely a compile-time assertion &mdash; it produces no runtime artifact and disappears entirely after transpilation. The meaningful differences are:\n</p>\n<ol style=\"margin-top: 1.0rem; margin-left: 1.5rem; list-style-type: number\">\n<li style=\"margin-top: 0.5rem\">\n<span style=\"font-weight: 600; font-size: 1.05rem\">Declaration merging.</span> Interfaces with the same name in the same scope merge into a single interface. Type aliases throw a duplicate identifier error. This is not academic &mdash; it is exactly how you attach a <code>user</code> property to the Express <code>Request</code> object after your auth guard populates it.\n</li>\n<li style=\"margin-top: 0.5rem\">\n<span style=\"font-weight: 600; font-size: 1.05rem\">Expressiveness.</span> Type aliases can describe unions, tuples, primitives, mapped types, conditional types and template literal types. Interfaces can only describe object shapes and function/construct signatures. Anything involving <code>|</code> at the top level must be a type alias.\n</li>\n<li style=\"margin-top: 0.5rem\">\n<span style=\"font-weight: 600; font-size: 1.05rem\">Extension mechanics.</span> Interfaces use <code>extends</code>, which performs an eager compatibility check and reports conflicts at the declaration site. Type aliases use intersection (<code>&amp;</code>), which silently produces <code>never</code> for conflicting primitive members and only surfaces the error at the point of use. The interface error message is almost always more actionable.\n</li>\n<li style=\"margin-top: 0.5rem\">\n<span style=\"font-weight: 600; font-size: 1.05rem\">Compiler performance.</span> Interfaces are cached by name and resolved lazily. Deeply nested intersections of type aliases are recomputed and can noticeably slow down type checking in large codebases.\n</li>\n</ol>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThe practical rule used across most Nest codebases: use <code>interface</code> for object contracts that others may extend or augment (repository ports, module options, config shapes), and <code>type</code> for unions, function signatures and any computed type.\n</p>\n<div style=\"padding: 2px; This makes it the correct type for genuinely untrusted input &mdash; request bodies before validation, JSON.parse results, caught errors.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\n<code>never</code> is the empty set: no value has this type. Beyond the basics, three capabilities matter.
