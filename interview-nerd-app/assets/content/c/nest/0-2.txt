The magic comes from <code>emitDecoratorMetadata</code>, a TypeScript compiler flag that makes <code>tsc</code> automatically emit three well-known metadata keys derived from the type annotations it is about to erase:\n</p>\n<ol style=\"margin-top: 1.0rem; margin-left: 1.5rem; list-style-type: number\">\n<li style=\"margin-top: 0.5rem\">\n<span style=\"font-weight: 600; font-size: 1.05rem\">design:type</span> &mdash; the type of a property or the type <code>Function</code> for a method. The array becomes <code>[undefined]</code> and the error message shows <code>index [0]</code> with an empty dependency name. The fix is <code>forwardRef(() =&gt; Other)</code> on both sides &mdash; which works because the arrow defers evaluation until after both modules have finished loading &mdash; but the better fix is to break the cycle by extracting a shared module or inverting the dependency with an interface token.\n</li>\n<li style=\"margin-top: 0.5rem\">\n<span style=\"font-weight: 600; font-size: 1.05rem\">import type erases the binding.</span> <code>import type { UsersService } from './users.service'</code> guarantees the import is removed from the JavaScript output. The paramtype then references a non-existent binding. Use a value import for anything that participates in DI.\n</li>\n<li style=\"margin-top: 0.5rem\">\n<span style=\"font-weight: 600; font-size: 1.05rem\">Missing decorator means missing metadata.</span> A provider class with dependencies but no <code>@Injectable()</code> emits no <code>design:paramtypes</code> at all, so the injector sees zero dependencies and constructs it with no arguments &mdash; producing a mysterious \"cannot read property of undefined\" the first time a method is called, rather than a clear DI error.\n</li>\n<li style=\"margin-top: 0.5rem\">\n<span style=\"font-weight: 600; font-size: 1.05rem\">Barrel files (index.ts) amplify cycles.</span> Re-exporting through a barrel makes two files that do not directly reference each other participate in the same module cycle. This is the most common real-world cause of undefined paramtypes in large Nest codebases.\n</li>\n<li style=\"margin-top: 0.5rem\">\n<span style=\"font-weight: 600; font-size: 1.05rem\">Transpiler mismatch.</span> SWC and Babel need explicit configuration (<code>legacyDecorator</code> and <code>decoratorMetadata</code> for SWC; <code>@babel/plugin-proposal-decorators</code> with <code>legacy: true</code> plus <code>babel-plugin-transform-typescript-metadata</code> for Babel). Without them, the code compiles and the app starts, then every injection is <code>undefined</code>.\n</li>\n<li style=\"margin-top: 0.5rem\">\n<span style=\"font-weight: 600; font-size: 1.05rem\">Jest with a different transformer.</span> Tests can fail with DI errors that do not occur in production if <code>ts-jest</code> is not picking up the same tsconfig, or if <code>@swc/jest</code> lacks the metadata options.\n</li>\n</ol>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nOther Consumers of design:type\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nNest's DI is the headline user, but the same metadata powers several other libraries you use daily, and the shared limitation &mdash; that generic parameters are erased &mdash; explains their quirks:\n</p>\n<ul style=\"margin-top: 1.0rem; margin-left: 1.5rem; list-style-type: disc\">\n<li style=\"margin-top: 0.4rem\"><code>class-transformer</code> uses <code>design:type</code> to decide how to instantiate a nested object.
