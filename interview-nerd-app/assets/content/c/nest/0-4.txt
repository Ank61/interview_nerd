Each layer is either a middleware function or a route. When a request arrives:\n</p>\n<ol style=\"margin-top: 1.0rem; margin-left: 1.5rem; list-style-type: number\">\n<li style=\"margin-top: 0.4rem\">Node's <code>http</code> module parses the request line and headers (in C, via llhttp) and emits a <code>request</code> event carrying <code>IncomingMessage</code> and <code>ServerResponse</code>.</li>\n<li style=\"margin-top: 0.4rem\">Express's application handler receives them, decorates the objects with its own prototype methods (<code>res.json</code>, <code>res.status</code>, <code>req.get</code>), and enters the router.</li>\n<li style=\"margin-top: 0.4rem\">The router walks its stack in <span style=\"font-weight: 600\">registration order</span>. For each layer it tests the path against a regular expression compiled by <code>path-to-regexp</code>. Middleware registered with <code>app.use('/x')</code> matches by prefix; routes registered with <code>app.get('/x')</code> must match exactly.</li>\n<li style=\"margin-top: 0.4rem\">A matching layer is invoked with <code>(req, res, next)</code>. Control passes onward only when the layer calls <code>next()</code>. If it never calls <code>next()</code> and never writes a response, the request hangs until the client or server times out &mdash; there is no supervision.</li>\n<li style=\"margin-top: 0.4rem\">Calling <code>next(err)</code> with an argument skips all remaining normal layers and jumps to the first <span style=\"font-weight: 600\">error-handling</span> middleware, which is identified purely by having four parameters: <code>(err, req, res, next)</code>.</li>\n<li style=\"margin-top: 0.4rem\">If the stack is exhausted with no response, Express's default handler emits a 404.</li>\n</ol>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nEverything Nest does happens inside step 4. Nest registers exactly one Express route per controller handler, and the function it registers is a <span style=\"font-weight: 600\">proxy</span> generated at bootstrap that runs the entire Nest pipeline &mdash; guards, interceptors, pipes, the handler, response serialisation &mdash; before writing to <code>res</code>. From Express's point of view, your whole application is a handful of ordinary route callbacks.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nTwo Kinds of Middleware, and Why the Ordering Surprises People\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nNest gives you two distinct ways to install middleware, and they enter the Express stack at different times:\n</p>\n<ul style=\"margin-top: 1.0rem; margin-left: 1.5rem; list-style-type: disc\">\n<li style=\"margin-top: 0.4rem\">\n<span style=\"font-weight: 600\">Global middleware</span> via <code>app.use(...)</code> in <code>main.ts</code>. That class reads <code>PATH_METADATA</code> from the class decorator and <code>PATH_METADATA</code> plus <code>METHOD_METADATA</code> from each method, composes the full path (global prefix + controller prefix + method path + version), builds the handler proxy, and calls the adapter's corresponding method &mdash; <code>adapter.get(path, proxy)</code>, <code>adapter.post(...)</code> and so on.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nTwo important consequences follow. First, <span style=\"font-weight: 600\">route registration order is module resolution order</span>, then declaration order within a controller. On Express this determines matching precedence, so a wildcard route in an early-imported module can shadow a specific route in a later one. Second, all path matching semantics &mdash; parameter syntax, wildcards, optional segments &mdash; come from the underlying router, not from Nest. Nest simply passes the string through.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThe two routers behave differently in a way that matters:\n</p>\n<ul style=\"margin-top: 1.0rem; margin-left: 1.5rem; list-style-type: disc\">\n<li style=\"margin-top: 0.4rem\"><span style=\"font-weight: 600\">Express</span> uses <code>path-to-regexp</code> and a <span style=\"font-weight: 600\">linear scan</span> of the layer stack. First match wins, so declaration order is semantically significant. Performance degrades linearly with route count.</li>\n<li style=\"margin-top: 0.4rem\"><span style=\"font-weight: 600\">Fastify</span> uses <code>find-my-way</code>, a <span style=\"font-weight: 600\">radix tree</span>. Lookup is effectively constant-time regardless of route count, and static segments always take precedence over parametric ones automatically. It also <span style=\"font-weight: 600\">rejects duplicate routes at startup</span> rather than silently letting the first win &mdash; which turns a class of silent Express bugs into a boot-time error.</li>\n</ul>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nExpress 5, adopted by Nest 11, changed <code>path-to-regexp</code> to v8 and with it the wildcard syntax. The bare <code>'*'</code> is no longer valid as a named catch-all; you write <code>'*splat'</code> for a required catch-all or <code>'{*splat}'</code> for an optional one, and unnamed wildcards in <code>forRoutes</code> become <code>'{*splat}'</code>. Optional-parameter syntax also changed from <code>':id?'</code> to <code>'{:id}'</code>. Migrating a Nest 10 app to Nest 11 without updating these strings produces <code>PathError</code> at boot &mdash; a very likely interview scenario in 2025 and later.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\nResponse Handling: Standard Mode vs Library-Specific Mode\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThis is where the adapter abstraction is most visible, and where the most damaging mistakes are made.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nIn <span style=\"font-weight: 600\">standard mode</span> &mdash; when your handler simply <code>return</code>s a value &mdash; Nest takes ownership of the response. The returned value (or the resolved promise, or the first emission of an Observable) flows back out through the interceptor chain in reverse, gets serialised by <code>ClassSerializerInterceptor</code> if it is registered, and is finally written by <code>httpAdapter.reply()</code>. This is what makes interceptors, response mapping, serialisation groups and the exception filter's automatic formatting work at all.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThe moment you inject <code>@Res() res</code>, Nest switches that handler into <span style=\"font-weight: 600\">library-specific mode</span>. It assumes you will write the response yourself and stops managing it.
