{"title":"Step Functions Orchestration — Beyond the 15-Minute Limit","tags":["step-functions","orchestration","asl","workflows"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Lambda's 15-minute maximum timeout is not a limitation to work around — it is a design constraint telling you that <strong>a function is a unit of work, not a unit of process</strong>. When a workflow needs to run for forty minutes, or wait three days for a human approval, or fan out over a million records, the answer is not a longer timeout. It is to move the <strong>orchestration out of function code and into a state machine</strong>, where the workflow itself is durable, observable, and does not consume compute while it waits.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Anti-Pattern: Lambda Calling Lambda Synchronously</h4>\n<p style=\"line-height: 1.75\">The instinct when a process has three steps is to write three functions and have the first invoke the second with <code>InvocationType: RequestResponse</code>, then the second invoke the third the same way. This is one of the most consistently penalised designs in serverless review, for four independent reasons.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>You pay twice for the same wall-clock time — recursively.</strong> If A waits 10 seconds for B, you are billed 10 seconds of A's GB-seconds doing nothing but blocking on a socket, plus 10 seconds of B doing real work. With three levels of nesting you pay for the innermost work three times. This is sometimes called the \"double billing\" anti-pattern, and the multiplier is the nesting depth.</li>\n<li><strong>Concurrency multiplies.</strong> Each blocked caller holds a concurrency slot. A chain of depth three at 100 requests per second consumes three times the concurrency of the same work done asynchronously, and it is the <em>idle</em> slots that exhaust your account limit.</li>\n<li><strong>Failure modes compound.</strong> Now every hop needs its own retry logic, its own timeout budget (the caller's timeout must exceed the callee's, or you get a timeout that leaves the callee still running), and its own idempotency handling. A retry at the top of the chain re-executes everything below it. Available capacity, throttling, and partial failure become your code's problem.</li>\n<li><strong>The workflow is invisible.</strong> The sequence of steps exists only as scattered SDK calls inside handlers. There is no diagram, no execution history, no \"where is order 12345 right now\" query. Onboarding requires reading four codebases.</li>\n</ul>\n<p style=\"line-height: 1.75\">There are narrow exceptions — a genuinely synchronous request-response fan-out where you need a single aggregated answer within an API's latency budget, or calling into a shared library function you cannot import. But the default should be: <strong>if a Lambda's job is to decide what happens next, that decision belongs in a state machine.</strong></p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Step Functions and the Amazon States Language</h4>\n<p style=\"line-height: 1.75\"><strong>AWS Step Functions</strong> is a managed state machine service. You define a workflow in <strong>Amazon States Language (ASL)</strong>, a JSON (or, with ASL in YAML, YAML) DSL, and Step Functions durably executes it: it persists state between transitions, handles retries, and records every transition in an execution history. The workflow definition <em>is</em> the documentation, rendered as a visual graph in the console and in Workflow Studio.</p>\n<p style=\"line-height: 1.75\">The state types you should be able to name:</p>\n<div style=\"overflow-x: auto; A workflow that submits a job, waits five minutes, polls for completion, and loops back is a few lines of ASL and costs a handful of state transitions per hour. The same thing implemented as a Lambda sleeping in a loop is impossible past 15 minutes and expensive well before that.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Standard vs Express Workflows</h4>\n<div style=\"overflow-x: auto; Express also has no built-in history, so if a step fails you need CloudWatch Logs (set the logging level to ALL during development, and consider ERROR in production for cost) or you are blind. In exchange Express is dramatically cheaper for high-volume short workflows, because per-state-transition pricing on Standard becomes expensive when you run millions of executions.</p>\n<p style=\"line-height: 1.75\">The heuristic: <strong>Standard for business-critical, long-running, auditable processes</strong> — order fulfilment, loan approval, data pipelines, anything with a human in the loop. <strong>Express for high-volume, short, idempotent processing</strong> — per-event stream processing, a synchronous API orchestration behind API Gateway, IoT ingestion. A very effective pattern combines them: a Standard parent workflow that calls an Express child workflow as a nested Task for the high-volume inner loop, giving you durability and audit at the top and cost efficiency at the bottom.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Declarative Error Handling: Retry, Catch, and Fallback</h4>\n<p style=\"line-height: 1.75\">Hand-rolled retry code in Lambda is a recurring source of bugs: people forget jitter and cause thundering herds, they retry non-retryable errors like validation failures, they retry inside a function that is itself being retried by the platform, and they burn billed duration sleeping between attempts. ASL makes retry <strong>declarative</strong>.</p>\n<p style=\"line-height: 1.75\">A <code>Retry</code> array on a Task lists retriers, each matching <code>ErrorEquals</code> with an <code>IntervalSeconds</code>, <code>MaxAttempts</code>, <code>BackoffRate</code>, and optionally <code>MaxDelaySeconds</code> and <code>JitterStrategy: \"FULL\"</code>. Retriers are evaluated in order, so you put specific errors first and a general one last. Crucially, <strong>the wait between retries happens in Step Functions, not in your Lambda</strong> — you are not paying GB-seconds to sleep. Built-in error names matter: <code>States.TaskFailed</code>, <code>States.Timeout</code>, <code>States.Permissions</code>, <code>Lambda.ServiceException</code>, <code>Lambda.TooManyRequestsException</code> (throttling — always retry this one), and <code>States.ALL</code> as the catch-all. Custom errors thrown by your function (an exception class name in Python, or the <code>errorType</code> in Node) can be matched by name, which is how you distinguish \"retry the transient thing\" from \"do not retry the invalid input.\"</p>\n<p style=\"line-height: 1.75\">A <code>Catch</code> array routes a failing Task to a fallback state instead of failing the execution, with <code>ResultPath</code> letting you merge the error object into the state data so the handler downstream can see what went wrong. This is how you implement compensation: catch a failure in \"ChargeCard\" and route to \"ReleaseInventory\" then \"NotifyCustomer\". The combination of Retry then Catch is the pattern — retry transient failures a few times with backoff, and if they persist, catch and compensate.</p>\n<p style=\"line-height: 1.75\">Two related controls: <code>TimeoutSeconds</code> on a Task bounds how long Step Functions waits (essential for callback tasks, which otherwise wait up to a year), and <code>HeartbeatSeconds</code> lets a long-running worker prove it is still alive.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Map and Distributed Map</h4>\n<p style=\"line-height: 1.75\"><strong>Inline Map</strong> iterates a branch over each element of an array in the state input, with <code>MaxConcurrency</code> controlling parallelism (set it deliberately — unbounded Map fan-out is a classic way to overwhelm a downstream database). Inline Map is limited by the 256 KB state payload size and supports up to 40 concurrent iterations, so it suits tens or low hundreds of items.</p>\n<p style=\"line-height: 1.75\"><strong>Distributed Map</strong> (<code>ProcessorConfig.Mode: \"DISTRIBUTED\"</code>) is a different machine. It reads its items from an <strong>ItemReader</strong> — an S3 object list, a JSON array in S3, a CSV file in S3, or a manifest — so the item set is not bound by the payload limit. It runs <strong>up to 10,000 concurrent child executions</strong>, supports <code>ItemBatcher</code> to group items so each child processes a batch rather than one item (dramatically reducing cost when per-item work is small), supports a <code>ToleratedFailurePercentage</code> so a handful of bad records does not fail a million-item job, and writes results to S3 via <strong>ResultWriter</strong>. This turns Step Functions into a legitimate large-scale batch engine: processing 10 million S3 objects is a Distributed Map, not a fleet of chained Lambdas.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Callback Patterns and Direct SDK Integrations</h4>\n<p style=\"line-height: 1.75\">Service integrations come in three request patterns, expressed as an ARN suffix on the Task <code>Resource</code>:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Request Response</strong> (default, no suffix). Call the service and move on immediately.</li>\n<li><strong>Run a Job</strong> (<code>.sync</code>). Call the service and wait for the job to complete — available for Batch, Glue, EMR, ECS, SageMaker, and nested state machines. This is how you run a two-hour ECS task as a single Task state.</li>\n<li><strong>Wait for Callback</strong> (<code>.waitForTaskToken</code>). Step Functions injects a <strong>task token</strong> into the payload, then pauses — for up to a year — until something calls <code>SendTaskSuccess</code> or <code>SendTaskFailure</code> with that token.</li>\n</ul>\n<p style=\"line-height: 1.75\">The callback pattern is the clean solution to human-in-the-loop and external-system waits. Push a message to SQS containing the task token, email an approver a link that embeds the token, have an external partner's webhook return with the token — the workflow simply stops, consuming nothing, until the token comes back. Always set <code>TimeoutSeconds</code> on a callback task and <code>Catch</code> the <code>States.Timeout</code> so an unapproved request eventually escalates rather than hanging forever.</p>\n<p style=\"line-height: 1.75\"><strong>Direct SDK integrations</strong> (<code>arn:aws:states:::aws-sdk:service:apiAction</code>) let a Task call essentially any AWS API directly. This deletes a large category of glue-code Lambdas: putting an item in DynamoDB, publishing to SNS, sending to SQS, starting a Textract job, tagging an EC2 instance. Every glue Lambda you delete removes a deployment artifact, a cold start, an execution role, a log group, and a source of bugs. Combine with <strong>intrinsic functions</strong> (<code>States.Format</code>, <code>States.Array</code>, <code>States.JsonMerge</code>, <code>States.UUID</code>, <code>States.ArrayPartition</code>) and JSONata-based transformations to do payload reshaping without a Lambda at all. The rule of thumb: <strong>Lambda for business logic, Step Functions for everything else.</strong></p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Choreography vs Orchestration</h4>\n<p style=\"line-height: 1.75\">This is a genuine architectural fork, not a tooling preference. <strong>Orchestration</strong> (Step Functions) has a central coordinator that knows the whole process and tells each participant what to do. <strong>Choreography</strong> (EventBridge, SNS, queues) has no coordinator: each service emits events and reacts to events, and the process emerges from those reactions.</p>\n<div style=\"overflow-x: auto; The Orders domain emits <code>OrderPlaced</code> on an EventBridge bus; Fulfilment, Billing, and Analytics each subscribe without Orders knowing they exist. Inside Fulfilment, the multi-step \"reserve stock, pick, pack, book courier, handle failure\" process is a Step Functions state machine, because it is one team's process with a defined sequence and real compensation requirements. Reaching for choreography inside a tightly sequenced process produces a system nobody can reason about; reaching for orchestration across team boundaries produces a shared state machine that becomes a coordination bottleneck.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario: Redesigning a 40-Minute Batch Job</h4>\n<p style=\"line-height: 1.75\">The current system: a nightly job processes about 500,000 records from a vendor file in S3. Because it exceeds 15 minutes, someone \"solved\" it by having <code>batch-runner</code> process records until roughly 13 minutes have elapsed, then invoke <em>itself</em> asynchronously with an offset cursor, chaining perhaps four invocations. Failures are handled by a try/catch that writes an error to a log and continues. There is no way to know whether last night's run finished, and re-running means reprocessing from the start.</p>\n<p style=\"line-height: 1.75\"><strong>What is actually wrong.</strong> The self-invocation chain is a recursive loop with no supervisor — if invocation three dies from an OOM, nothing notices and the last 150,000 records are silently skipped. State lives in a cursor passed through an event payload, so there is no durable record of progress. Retrying means re-running everything, which is only safe if every record write is idempotent, and it almost certainly is not. There is no concurrency control, so if last night's run overruns it can overlap with tonight's. And Lambda's recursive-loop detection may itself terminate the chain, turning a fragile design into an outage.</p>\n<p style=\"line-height: 1.75\"><strong>The redesign.</strong> A <strong>Standard</strong> state machine, triggered by an EventBridge Scheduler rule (or by an S3 upload event via EventBridge, which is better — process when the file arrives rather than at a guessed
