{"title":"Invocation Types — Synchronous, Asynchronous, and Event Source Mapping","tags":["lambda","invocation","retries","error-handling"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Every Lambda invocation happens under exactly one of three models: <strong>synchronous</strong>, <strong>asynchronous</strong>, or <strong>event source mapping</strong> (poll-based). Which model is in play is not a property of your code — it is determined by <em>who invokes the function and how</em>. And it is the single most important thing to establish before you can answer the most common Lambda debugging question in existence: <strong>\"what happens when my function fails?\"</strong> The same thrown exception produces three completely different outcomes depending on the model, so a candidate who answers that question without first asking \"how is it invoked?\" has revealed that they do not really know Lambda.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Model 1: Synchronous (RequestResponse)</h4>\n<p style=\"line-height: 1.75\">The caller invokes the function and <strong>blocks until it returns</strong>, receiving the function's return value — or its error — in the HTTP response. This is the <code>RequestResponse</code> invocation type, and it is the default for the CLI and the SDKs.</p>\n<p style=\"line-height: 1.75\">Who invokes synchronously: <strong>API Gateway, Application Load Balancer, Lambda Function URLs, Amazon Cognito user pool triggers, Lex, CloudFront Lambda@Edge, Step Functions task states</strong> (by default), and any direct SDK or CLI invoke without <code>--invocation-type Event</code>.</p>\n<p style=\"line-height: 1.75\">The defining characteristic, and the one interviewers push on: <strong>Lambda does not retry synchronous invocations.</strong> If your function throws, the error is returned to the caller and Lambda's involvement ends. Retry is entirely the <em>caller's</em> responsibility. In practice that means the AWS SDK's built-in retry behaviour applies to <em>transport-level</em> errors and throttling (a <code>TooManyRequestsException</code> / HTTP 429), but a <strong>function error</strong> — your code raising an exception — is returned as a successful HTTP 200 from the Lambda API with a <code>FunctionError</code> header set to <code>Unhandled</code> and the error details in the payload. The SDK will not retry that, because from the API's point of view the call succeeded; it was your code that failed. This distinction between an <em>invocation error</em> and a <em>function error</em> is subtle and worth being able to articulate.</p>\n<p style=\"line-height: 1.75\">Practical limits: the request and response payloads are capped at <strong>6 MB</strong> each for synchronous invocation. Function URLs with response streaming can exceed this on the response side, up to 20 MB. And because the caller is waiting, synchronous invocation is where cold-start latency is felt most acutely — it is the model where provisioned concurrency earns its keep.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Model 2: Asynchronous (Event)</h4>\n<p style=\"line-height: 1.75\">The caller hands the event to Lambda and Lambda immediately returns <strong>HTTP 202 Accepted</strong> with an empty body. The event is placed on an <strong>internal queue owned and managed by the Lambda service</strong> (you cannot see or configure this queue), and Lambda invokes the function from that queue separately. The caller learns nothing about whether the function succeeded.</p>\n<p style=\"line-height: 1.75\">Who invokes asynchronously: <strong>S3 bucket notifications, SNS, EventBridge rules and schedules, CloudWatch Logs subscriptions, CodeCommit, SES, Config</strong>, and any direct invoke with <code>--invocation-type Event</code>.</p>\n<p style=\"line-height: 1.75\">Here <strong>Lambda itself owns the retry.</strong> On a function error, Lambda retries by default <strong>twice</strong> (three attempts in total), with delays between attempts — roughly a minute before the first retry and a couple of minutes before the second, though AWS does not guarantee exact timing. Two settings on the function's event invoke config control this:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>MaximumRetryAttempts.</strong> 0, 1, or 2. Default 2.</li>\n<li><strong>MaximumEventAge.</strong> 60 seconds to 6 hours, default 6 hours. Events older than this are discarded without further attempts — this is what protects you during a prolonged throttling event.</li>\n</ul>\n<p style=\"line-height: 1.75\">If all attempts fail, the event is discarded — <em>unless</em> you have configured somewhere for it to go. There are two mechanisms, and knowing that the newer one is preferred is a good signal:</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Mechanism</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Targets</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">What is delivered</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><strong>Dead-letter queue</strong> (older, <code>DeadLetterConfig</code>)</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">SQS queue or SNS topic</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">The original event payload only, with some metadata in message attributes. Note that the asynchronous payload limit is <strong>256 KB</strong>, much smaller than the synchronous 6 MB, and that the function's <strong>return value is thrown away</strong> — nobody is waiting for it. If you need the result, write it somewhere or use an on-success destination.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Model 3: Event Source Mapping (Poll-Based)</h4>\n<p style=\"line-height: 1.75\">For queue and stream sources, the Lambda service runs a <strong>poller fleet</strong> that reads records from the source and invokes your function with a <strong>batch</strong>. The mapping itself is a resource you create (<code>create-event-source-mapping</code>) with settings for batch size, batching window, starting position, and failure handling. Sources: <strong>SQS, Kinesis Data Streams, DynamoDB Streams, Amazon MQ, Amazon MSK and self-managed Kafka, and DocumentDB change streams.</strong></p>\n<p style=\"line-height: 1.75\">Failure behaviour here is <strong>source-specific</strong>, which is exactly why the model deserves to be treated as distinct rather than lumped in with async.</p>\n<p style=\"line-height: 1.75\"><strong>SQS.</strong> Lambda deletes messages from the queue only after the invocation succeeds. If the function throws, nothing is deleted; the messages' visibility timeout expires and they become visible again for another attempt. Retries are therefore governed by the <strong>queue's own redrive policy</strong> — after <code>maxReceiveCount</code> receives, SQS moves the message to the queue's dead-letter queue. Note the important default: a failure fails the <em>entire batch</em>, so nine good messages get reprocessed because of one bad one. The fix is <strong>partial batch response</strong>: set <code>FunctionResponseTypes</code> to <code>ReportBatchItemFailures</code> on the mapping and return a <code>batchItemFailures</code> array of just the failed <code>itemIdentifier</code> values.</p>\n<p style=\"line-height: 1.75\"><strong>Kinesis and DynamoDB Streams.</strong> These are <em>ordered</em> sources, so the default is far more aggressive: Lambda retries the failing batch <strong>until it succeeds or the records expire</strong> from the stream (up to 24 hours for DynamoDB Streams, up to the retention period for Kinesis). Meanwhile, that shard is <strong>blocked</strong> — nothing behind the poison-pill record is processed. This is the notorious \"poison pill blocks the shard\" failure mode. The mitigations, all configured on the event source mapping, are worth naming: <code>MaximumRetryAttempts</code>, <code>MaximumRecordAgeInSeconds</code>, <code>BisectBatchOnFunctionError</code> (split the batch in half to isolate the bad record), <code>OnFailure</code> destination (send failed batch metadata to SQS or SNS), and <code>ReportBatchItemFailures</code> to checkpoint past successful records.</p>\n<h4 style=\"margin-top: 1.5rem; If the function sits behind SNS or S3 — asynchronous — then Lambda's automatic retries are the prime suspect: the function timed out <em>after</em> calling the payment provider but <em>before</em> recording success, Lambda retried, and the charge happened again. If it is behind SQS, both the retry-on-throw behaviour and a visibility timeout shorter than the function timeout can cause concurrent duplicate processing.</p>\n<p style=\"line-height: 1.75\">The correct answer is not \"turn off retries\" — that trades duplicates for lost payments. It is <strong>idempotency</strong>. Derive a deterministic idempotency key (an order ID from the payload, or <code>context.awsRequestId</code> where the retry preserves it), record it conditionally in DynamoDB with a condition expression that fails if it already exists, and treat the conditional-write failure as \"already processed, return success.\" Pass the same key to the payment provider's idempotency header so the provider deduplicates too. Then, separately, tune the mechanics: raise the function timeout above the downstream call's worst case, set the SQS visibility timeout to at least six times the function timeout, and add an on-failure destination so genuinely-failed payments are visible rather than silently discarded. The headline sentence to say out loud: <strong>at-least-once delivery is a property of the platform, so idempotency is your responsibility, not Lambda's.</strong></p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common Beginner Misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"Lambda always retries failed invocations.\"</strong> Only for asynchronous and poll-based models. Synchronous invocations get exactly one attempt from Lambda; the caller must retry.</li>\n<li><strong>\"The invocation type is something I set in my function code.\"</strong> It is determined by the caller. The same function can be invoked synchronously by API Gateway and asynchronously by EventBridge on the same day.</li>\n<li><strong>\"A DLQ catches all failures.\"</strong> The <code>DeadLetterConfig</code> DLQ only applies to <strong>asynchronous</strong> invocations. It does nothing for synchronous calls, and for SQS event source mappings the relevant DLQ is the one on the <em>queue</em>, configured via its redrive policy — not on the function.</li>\n<li><strong>\"My async function's return value goes back to S3 / SNS.\"</strong> It goes nowhere. Asynchronous return values are discarded. Use an on-success destination if you need the result.</li>\n<li><strong>\"Retries are immediate.\"</strong> Asynchronous retries are delayed, roughly a minute then a couple of minutes, and the total lifetime is bounded by <code>MaximumEventAge</code> (up to 6 hours).</li>\n<li><strong>\"One bad record only fails that record.\"</strong> By default an exception fails the <em>entire batch</em> in an event source mapping.
