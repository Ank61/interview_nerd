{"title":"Error Handling, Retries, and Destinations — Designing Lambda Failure Paths","tags":["lambda","error-handling","retries","destinations"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Lambda does not have one retry policy. It has <strong>three completely different failure models</strong>, and which one applies depends entirely on <strong>how the function was invoked</strong>. Senior candidates who answer \"Lambda retries twice\" are describing only the asynchronous path. The synchronous path retries zero times inside Lambda, and the event source mapping path retries according to rules owned by the poller and the source service. Designing a failure path means deciding, for each invocation type, <strong>who retries</strong>, <strong>how many times</strong>, <strong>where a permanently failed event lands</strong>, and <strong>what evidence you keep</strong> so an operator can replay it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Model 1 — Synchronous invocation: the caller owns everything</h4>\n<p style=\"line-height: 1.75\">On a synchronous invoke (<code>InvocationType: RequestResponse</code>) Lambda runs the function, and if the handler throws, Lambda returns HTTP 200 from the Invoke API with an <code>X-Amz-Function-Error</code> header set to <code>Unhandled</code> or <code>Handled</code> and a JSON error payload containing <code>errorType</code>, <code>errorMessage</code> and <code>stackTrace</code>. This surprises people: the <strong>HTTP status is 200 because the invocation succeeded</strong>; the function failing is data in the response, not a transport error. Only genuine platform problems produce non-200s — 429 for throttling (<code>TooManyRequestsException</code>), 500 for <code>ServiceException</code>, 502 for a malformed runtime response.</p>\n<p style=\"line-height: 1.75\"><strong>Lambda performs no retry at all here.</strong> Whatever retry happens is the caller's. That caller may be:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>API Gateway.</strong> Does not retry your function. A function error surfaces as a 502 (bad integration response) or, for a proxy integration returning an error, whatever you mapped. The client decides whether to retry.</li>\n<li><strong>Application Load Balancer.</strong> Does not retry; returns 502 on a function error.</li>\n<li><strong>The AWS SDK.</strong> This is the dangerous one. The SDK retries <em>transport-level</em> failures and throttles on its own — the modern default is <strong>standard</strong> retry mode with a maximum of 3 total attempts. If your Invoke call times out at the socket level after Lambda already started executing, the SDK will happily invoke again, and your function runs twice with no error anywhere in your logs to explain it.</li>\n<li><strong>Step Functions.</strong> Explicit and excellent: <code>Retry</code> with <code>IntervalSeconds</code>, <code>MaxAttempts</code>, <code>BackoffRate</code> and <code>ErrorEquals</code>, plus <code>Catch</code> for routing. Because it is declarative, the retry policy is visible in the state machine definition rather than buried in a client config.</li>\n</ul>\n<p style=\"line-height: 1.75\">The classic silent-duplication bug: a function has a 30 second timeout, the calling SDK has a socket/read timeout of 10 seconds. The SDK gives up at 10s and retries — twice. Lambda never cancelled the first execution. You now have three concurrent executions doing the same work and the caller eventually reports one failure. <strong>Rule: the client read timeout must exceed the function timeout, or you must make the operation idempotent.</strong> For long synchronous work, set the SDK's read timeout above the function timeout and turn retries down to 1 attempt.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Model 2 — Asynchronous invocation: Lambda's internal queue</h4>\n<p style=\"line-height: 1.75\">On <code>InvocationType: Event</code>, the Invoke API returns <strong>202 Accepted</strong> immediately and places the event on an <strong>internal, Lambda-managed queue</strong> you cannot see, inspect, or drain. S3 notifications, SNS, EventBridge rules targeting Lambda, and CloudWatch Logs subscriptions all invoke asynchronously.</p>\n<p style=\"line-height: 1.75\">Lambda then reads from that queue and invokes your function. On a function error — or on a throttle, or a system error — Lambda retries. The default is <strong>two retries after the initial attempt (three attempts total)</strong>, with a delay of roughly one minute before the first retry and about two minutes before the second. Throttled events are handled more patiently: Lambda keeps re-queuing them with backoff for up to six hours.</p>\n<p style=\"line-height: 1.75\">Two knobs control this, set via <code>PutFunctionEventInvokeConfig</code> (SAM: <code>EventInvokeConfig</code>):</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>MaximumRetryAttempts.</strong> 0 to 2, default 2. Setting it to 0 means one attempt only — appropriate when the downstream is not idempotent and you would rather dead-letter immediately than risk duplicate side effects.</li>\n<li><strong>MaximumEventAge.</strong> 60 to 21600 seconds (1 minute to 6 hours), default 6 hours. This is the ceiling on how long an event may sit in the internal queue plus retry cycle. When the age is exceeded, the event is <strong>discarded</strong> — Lambda will not attempt it again even if retries remain.</li>\n</ul>\n<p style=\"line-height: 1.75\">Event age matters more than people expect during an incident. If your function is down for forty minutes and you set <code>MaximumEventAge</code> to 300 seconds because you wanted freshness, every event queued during that window silently ages out. Conversely, leaving it at six hours means that when you fix the bug, a six-hour backlog of events floods your function at once — a self-inflicted thundering herd against a downstream that is probably still fragile. Neither default is universally right; pick based on whether stale events are harmful and whether the downstream can absorb a replay burst.</p>\n<p style=\"line-height: 1.75\">When retries are exhausted <em>or</em> the event ages out, the event goes to whatever failure sink you configured. If you configured none, it is <strong>dropped silently</strong>. The only trace is the <code>Errors</code> metric and, if you look, the <code>AsyncEventsDropped</code> / <code>AsyncEventAge</code> metrics. An unconfigured async function is a data-loss machine.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Lambda Destinations — the modern failure sink</h4>\n<p style=\"line-height: 1.75\"><strong>Destinations</strong> attach to the asynchronous invocation path and route the <em>invocation record</em> to a target. The one legitimate reason to keep a DLQ is an existing operational tool that already consumes the bare-event format.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Model 3 — Event source mappings: source-dependent, poller-driven</h4>\n<p style=\"line-height: 1.75\">For poll-based sources, Lambda runs a managed <strong>event source mapping (ESM)</strong> poller that reads batches and invokes your function synchronously. Retries here follow the semantics of the source, not the async rules:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>SQS (standard).</strong> If the invocation throws, the poller does not delete the messages; they become visible again after the queue's visibility timeout and are redelivered. Retry count is governed by the <strong>queue's redrive policy</strong> (<code>maxReceiveCount</code>), and failed messages land in the queue's own DLQ. Set the queue visibility timeout to at least 6x the function timeout — AWS's documented guidance. Critically, a thrown error fails <strong>the whole batch</strong>, so nine good messages get reprocessed because of one poison message. The fix is <code>FunctionResponseTypes: [ReportBatchItemFailures]</code>, where the handler returns <code>batchItemFailures</code> listing only the message IDs to redeliver.</li>\n<li><strong>SQS FIFO.</strong> Same, but a failure blocks the message group — head-of-line blocking is the intended behavior since ordering is the point.</li>\n<li><strong>Kinesis and DynamoDB Streams.</strong> Ordered shard-based sources, so by default Lambda <strong>retries the batch until it succeeds or the records expire</strong> — a poison record stalls the shard indefinitely (up to 24 hours for DynamoDB Streams, up to the retention period for Kinesis). Tune with <code>MaximumRetryAttempts</code>, <code>MaximumRecordAgeInSeconds</code>, <code>BisectBatchOnFunctionError</code> (binary-search the batch to isolate the bad record), and <code>ReportBatchItemFailures</code>.</li>\n<li><strong>Kafka (MSK and self-managed).</strong> Offsets are committed only for successfully processed batches; behavior is partition-ordered like Kinesis.</li>\n</ul>\n<p style=\"line-height: 1.75\">For Kinesis, DynamoDB Streams and Kafka, the ESM supports an <strong>on-failure destination</strong> (<code>DestinationConfig.OnFailure</code>) that targets SQS, SNS, or — for stream sources — S3. The vital detail: <strong>this record contains batch metadata, not the data</strong>. You get the stream ARN, shard ID, starting and ending sequence numbers, approximate arrival timestamp and batch size. You must go back to the stream with those sequence numbers to recover the actual records, which only works inside the retention window. If the data matters and retention is short, write the failed records somewhere durable yourself.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The three models side by side</h4>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"></th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Synchronous</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Asynchronous</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Event source mapping</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><strong>Who retries</strong></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">The caller</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Lambda's internal queue</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">The managed poller</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><strong>How many</strong></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">0 by Lambda; caller-defined</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">2 retries (3 attempts) default</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">SQS: maxReceiveCount. Your code gives you fine, fast, cheap ones. The design question is where the boundary sits, and the answer comes from classifying errors:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Transient.</strong> A DynamoDB <code>ProvisionedThroughputExceededException</code>, an HTTP 503, a connection reset, an S3 <code>SlowDown</code>. The same request will probably succeed in 200ms. <strong>Retry in-process</strong> with exponential backoff and full jitter — but only within your remaining time budget.</li>\n<li><strong>Permanent.</strong> A schema validation failure, a 400 from a partner API, a missing required field, a business rule rejection. Retrying is pure waste and pollutes your error metrics. <strong>Do not retry; route it deliberately</strong> — catch it, write the poison record to a quarantine store or return a batch item failure, and let the invocation succeed so the platform does not retry either.</li>\n<li><strong>Ambiguous.</strong> A timeout on a write. You do not know whether it committed. This is exactly the case that forces idempotency; there is no retry policy that makes it safe on its own.</li>\n</ul>\n<p style=\"line-height: 1.75\">The essential Lambda-specific constraint: <strong>bound your in-process retries by <code>context.getRemainingTimeInMillis()</code></strong>. A retry loop that runs past the function timeout produces the worst possible outcome — the invocation is killed with no chance to log, no error object, no structured cleanup, and (on the async path) the platform retries the whole thing anyway. Always leave a safety margin, typically a second or two, and fail fast with a clear error rather than being reaped.</p>\n<p style=\"line-height: 1.75\"><strong>Circuit-breaker thinking.</strong> When a downstream is hard down, retrying makes things worse for everyone: you multiply load on a struggling service, burn concurrency that other functions need, and turn a partial outage into a total one. A Lambda-appropriate circuit breaker keeps the failure count in a shared store (a DynamoDB item, an ElastiCache key) rather than in module scope, because each execution environment has its own memory and would each have to learn the downstream is broken independently. When the breaker is open, fail fast with a distinct error type and let the failed events accumulate in the destination for a bulk replay once the downstream recovers.</p>\n<p style=\"line-height: 1.75\"><strong>Avoiding retry storms.</strong> Three compounding sources of amplification to check: layered retries (client retries 3x, Lambda async retries 3x, and your in-function loop retries 3x gives 27 calls to the downstream for one logical request); synchronized backoff (fixed delays cause every retry to arrive at the same instant — use full jitter); and replay bursts (a six-hour async backlog released at once). Reserved concurrency on the function is a blunt but effective circuit breaker of last resort: it caps how much damage the function can do to a shared downstream, at the cost of throttling.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario — the complete failure path for a payment-processing function</h4>\n<p style=\"line-height: 1.75\"><em>\"Design the end-to-end failure handling for a function that charges a customer's card when an order is placed. Nothing may be lost and nothing may be double-charged.\"</em></p>\n<p style=\"line-height: 1.75\"><strong>Step 1 — choose the invocation model.</strong> Do not invoke this synchronously from the API. The checkout API writes an order to DynamoDB and returns 202 immediately; the charge happens off the request path. Put an <strong>SQS queue</strong> between the order event and the charge function rather than relying on Lambda's invisible async queue — a real queue is inspectable, measurable (<code>ApproximateAgeOfOldestMessage</code>), pausable (disable the ESM to stop processing without losing anything) and has its own durable DLQ.</p>\n<p style=\"line-height: 1.75\"><strong>Step 2 — configure the mapping.</strong> <code>BatchSize: 1</code> so one bad charge cannot affect others and there is no partial-batch ambiguity around a money-moving operation. Queue <code>VisibilityTimeout</code> at 6x the function timeout. <code>maxReceiveCount: 3</code> on the redrive policy, DLQ retention 14 days. <code>MaximumConcurrency</code> on the ESM to cap pressure on the payment gateway to what our contract allows.</p>\n<p style=\"line-height: 1.75\"><strong>Step 3 — make the function idempotent.</strong> This is non-negotiable and it is what actually prevents double charges; retries are guaranteed somewhere in this chain. Conditionally write a claim item to a DynamoDB idempotency table keyed on the order ID before calling the gateway, and pass that same key to the gateway as its own idempotency key so the provider deduplicates too.</p>\n<p style=\"line-height: 1.75\"><strong>Step 4 — classify errors inside the handler.</strong> Gateway 5xx or network timeout: retry twice in-process with jittered backoff, bounded by remaining time; if still failing, throw so SQS redelivers. Card declined: that is a <em>business outcome</em>, not an error. Record it, emit an order-declined event, and <strong>return successfully</strong> — retrying a declined card three times is both pointless and a customer-visible problem. Malformed message: log, emit a metric, return successfully, and let the poison record go to a quarantine table rather than cycling to the DLQ.</p>\n<p style=\"line-height: 1.75\"><strong>Step 5 — instrument the sinks.</strong> CloudWatch alarm on DLQ <code>ApproximateNumberOfMessagesVisible</code> greater than 0 paging on-call, because a message in this DLQ means a customer's order is stuck. Alarm on <code>ApproximateAgeOfOldestMessage</code> on the main queue to catch a stalled poller. Alarm on the function's <code>Errors</code> and on a custom <code>GatewayCircuitOpen</code> metric.</p>\n<p style=\"line-height: 1.75\"><strong>Step 6 — build the replay path before you need it.</strong> A small operator function that reads a DLQ message, re-validates it, and re-sends it to the main queue. Because the charge function is idempotent, replay is safe: a message that actually did charge before failing on a later step will short-circuit on the idempotency record. <strong>Idempotency is what makes an aggressive retry policy safe; without it, every retry control becomes a risk control instead.</strong></p>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"Lambda has three failure models, not one.
