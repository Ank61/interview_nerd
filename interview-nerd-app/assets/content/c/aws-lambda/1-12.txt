{"title":"Versions, Aliases, and Safe Traffic Shifting","tags":["lambda","versions","aliases","codedeploy"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">A Lambda function is not one thing. It is a mutable draft called <strong>$LATEST</strong>, a set of <strong>immutable published versions</strong>, and a set of <strong>mutable aliases</strong> that point at those versions. Getting the relationship right is the foundation of every safe deployment strategy on Lambda: versions give you something stable to roll back <em>to</em>, aliases give you a stable name to roll back <em>with</em>, and weighted aliases plus CodeDeploy give you the machinery to shift traffic gradually and revert automatically when something goes wrong.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">$LATEST versus published versions</h4>\n<p style=\"line-height: 1.75\">Every function has <strong>$LATEST</strong>, the unqualified, always-mutable working copy. Calling <code>UpdateFunctionCode</code> or <code>UpdateFunctionConfiguration</code> changes $LATEST in place, immediately, for everyone pointed at it. There is no history and no rollback: the previous code is simply gone.</p>\n<p style=\"line-height: 1.75\"><code>PublishVersion</code> takes a snapshot of $LATEST and freezes it as a monotonically increasing integer — 1, 2, 3 — addressable as <code>arn:aws:lambda:region:account:function:name:3</code>. Versions are <strong>immutable</strong>; you cannot edit one, only delete it. That immutability is the whole point. It is what makes \"roll back to what was working\" a real operation rather than a hopeful redeploy.</p>\n<p style=\"line-height: 1.75\">The critical detail interviewers probe: <strong>a version snapshots code <em>and</em> configuration</strong>. Specifically it captures the deployment package or image digest, the handler, runtime, memory size, timeout, ephemeral storage, <strong>environment variables</strong>, the layer ARNs (pinned to their specific layer versions), VPC configuration, the execution role ARN, the dead letter config, and tracing config. Environment variables being versioned surprises people and is enormously useful: it means a config change is a deployable, rollbackable artifact just like a code change.</p>\n<p style=\"line-height: 1.75\">What a version does <strong>not</strong> capture — and this is the list that actually matters in an incident:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>The contents of the execution role's policies.</strong> The role <em>ARN</em> is snapshotted; the permissions attached to it are evaluated live. Rolling back a version does not roll back an IAM change that broke you.</li>\n<li><strong>Anything the code reads at runtime.</strong> SSM Parameter Store values, Secrets Manager secrets, AppConfig, feature flags, DynamoDB config tables. Rolling back the version does not roll back these.</li>\n<li><strong>Reserved concurrency.</strong> This is a function-level setting shared across all versions and aliases.</li>\n<li><strong>Provisioned concurrency.</strong> Allocated per version or alias, configured separately, not part of the snapshot.</li>\n<li><strong>Event source mappings, tags, and the function's alias set.</strong> These belong to the function, not the version.</li>\n<li><strong>Resource-based policy statements.</strong> These are attached per qualifier, so a new version does not inherit the permissions granted to a previous one — a very common cause of \"my new version cannot be invoked by S3.\"</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Aliases: the stable name</h4>\n<p style=\"line-height: 1.75\">An <strong>alias</strong> is a named, mutable pointer to exactly one version, with an ARN of its own: <code>arn:aws:lambda:us-east-1:111122223333:function:checkout:PROD</code>. Aliases solve the indirection problem. Without them, every caller, every event source mapping, every API Gateway integration and every EventBridge target would have to be reconfigured on each deploy.</p>\n<p style=\"line-height: 1.75\"><strong>Point everything at an alias, never at $LATEST and never at a bare version number.</strong> The reasoning:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Not $LATEST</strong>, because $LATEST changes under your feet. A caller on $LATEST gets whatever a developer pushed thirty seconds ago, and there is no way to shift traffic gradually to it or step back off it.</li>\n<li><strong>Not a bare version</strong>, because rolling back then means re-configuring every consumer.</li>\n<li><strong>An alias</strong>, because rollback becomes a single <code>UpdateAlias</code> call that repoints PROD from version 12 to version 11. It is atomic from the caller's point of view, takes effect in seconds, needs no redeployment or rebuild, and is the fastest mitigation available for a bad Lambda release.</li>\n</ul>\n<p style=\"line-height: 1.75\">Aliases also scope other things usefully: <strong>provisioned concurrency</strong>, <strong>function URLs</strong>, <strong>async invoke configuration</strong> (retries, destinations) and <strong>resource-based policies</strong> can all be attached to a specific alias, so the PROD alias can have provisioned concurrency and a strict destination configuration while a DEV alias has neither.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Weighted aliases — traffic shifting primitive</h4>\n<p style=\"line-height: 1.75\">An alias can carry a <strong>routing configuration</strong> (<code>RoutingConfig.AdditionalVersionWeights</code>) that splits invocations between the alias's primary version and <strong>one additional version</strong>, with the additional version's share expressed as a weight between 0.0 and 1.0. So PROD can send 95% of traffic to version 11 and 5% to version 12.</p>\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">         <i class=b>caller</i>  --&gt;  <i class=b>alias</i> <i class=s>&quot;PROD&quot;</i>  (arn ...:<i class=k>function</i>:checkout:PROD)\n                            |\n              RoutingConfig |  AdditionalVersionWeights: { <i class=s>&quot;12&quot;</i>: 0.05 }\n                            |\n            +---------------+---------------+\n            |                               |\n      version 11  (95%)               version 12  (5%)\n      the incumbent                   the canary\n\nrollback  = UpdateAlias --routing-config {}        (100% back to 11, seconds)\npromotion = UpdateAlias --function-version 12 --routing-config {}</code></pre></div>\n<p style=\"line-height: 1.75\">Constraints worth knowing precisely: the split is between <strong>exactly two versions</strong>, not N. Neither may be <strong>$LATEST</strong> — weighted routing requires published versions on both sides. Routing is applied <em>per invocation</em>, so a stateless function sees a clean percentage split, but nothing pins a given client to a given version; if your change is not backward compatible with in-flight state, a percentage split will expose that. And <code>context.invokedFunctionArn</code> plus the <code>executedVersion</code> field on the invoke response let you tell which version actually ran — essential for attributing errors during a shift.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">AWS CodeDeploy for Lambda: automating the shift</h4>\n<p style=\"line-height: 1.75\">Manually stepping a weight from 5% to 25% to 50% to 100% while watching dashboards is a job for a machine. <strong>CodeDeploy</strong> automates exactly that: it drives the alias's routing configuration on a schedule, runs your validation hooks, watches CloudWatch alarms, and rolls back automatically if anything trips. The deployment type is <code>Lambda</code> with platform <code>AWS::Lambda::Function</code>, and the AppSpec identifies the function, the alias, the <code>CurrentVersion</code> and the <code>TargetVersion</code>.</p>\n<p style=\"line-height: 1.75\">Three families of <strong>deployment configuration</strong>:</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Type</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Behaviour</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Built-in configurations</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Use when</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><strong>Canary</strong></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">A fixed small percentage for a bake period, then the remainder all at once</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><code>Canary10Percent5Minutes</code>, <code>Canary10Percent10Minutes</code>, <code>Canary10Percent15Minutes</code>, <code>Canary10Percent30Minutes</code></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Customer-facing production. A canary is only useful if the canary slice receives enough invocations during the bake window to produce a statistically meaningful error signal. A function invoked 12 times an hour will see roughly one invocation in a 10% / 10-minute canary — the alarm will never fire and you have added 10 minutes to every deploy for no safety. For low-traffic functions, invest in synthetic validation hooks instead of percentage-based baking.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Validation hooks and alarms</h4>\n<p style=\"line-height: 1.75\">CodeDeploy for Lambda exposes two lifecycle hooks, each implemented as its own Lambda function:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>BeforeAllowTraffic</strong> (SAM calls it <code>PreTraffic</code>). Runs <em>after</em> the new version is deployed but <em>before</em> any production traffic reaches it. This is where you invoke the new version directly by its version qualifier with synthetic test payloads and assert on the results. The new version is live and callable but has no real traffic, so this is a genuine smoke test in the production environment against production dependencies.</li>\n<li><strong>AfterAllowTraffic</strong> (SAM: <code>PostTraffic</code>). Runs after the shift completes. Used for end-to-end verification through the real front door, integration assertions, or notifying downstream systems.</li>\n</ul>\n<p style=\"line-height: 1.75\">Both hook functions must explicitly report their outcome by calling <strong><code>codedeploy.putLifecycleEventHookExecutionStatus</code></strong> with <code>Succeeded</code> or <code>Failed</code>, passing the <code>DeploymentId</code> and <code>LifecycleEventHookExecutionId</code> from the event. A hook that throws, or simply forgets to call this, causes the deployment to hang until it times out and then fail — a very common first-time mistake. The hook function's role needs <code>codedeploy:PutLifecycleEventHookExecutionStatus</code> plus permission to invoke the function under test.</p>\n<p style=\"line-height: 1.75\"><strong>CloudWatch alarms are the automatic rollback trigger</strong>, and they are the most important half of the setup. Attach alarms to the deployment group; if any enters <code>ALARM</code> state at any point during the deployment, CodeDeploy immediately reverts the alias to the previous version and marks the deployment failed. Alarms worth wiring: the new version's <code>Errors</code> metric (dimensioned on the function <em>and the version</em>, so the canary's errors are not diluted by the incumbent's healthy traffic), <code>Duration</code> p99, <code>Throttles</code>, and a business metric such as checkout failure rate. The version dimension is the detail that separates a working canary from a decorative one: at 10% traffic, a canary erroring 100% of the time raises the function-wide error rate by only 10%, which may not breach a function-level threshold at all.</p>\n<p style=\"line-height: 1.75\"><strong>SAM makes this about six lines.</strong> <code>AutoPublishAlias: live</code> tells SAM to publish a new version on every deploy and manage an alias named <code>live</code>; <code>DeploymentPreference</code> with a <code>Type</code>, <code>Alarms</code> and <code>Hooks</code> generates the CodeDeploy application, deployment group, IAM roles and AppSpec for you. That is the entire canary deployment pipeline.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Provisioned concurrency, versions, and deployments</h4>\n<p style=\"line-height: 1.75\"><strong>Provisioned concurrency cannot be allocated on $LATEST</strong> — only on a published version or an alias. That restriction exists for a good reason: pre-initialised execution environments are built from a specific immutable code snapshot, and $LATEST can change at any moment.</p>\n<p style=\"line-height: 1.75\">The operational consequence is that <strong>a new version starts with zero warm environments</strong>. Allocating provisioned concurrency is not instantaneous; the allocation moves through <code>IN_PROGRESS</code> to <code>READY</code> while Lambda initialises the environments, which takes on the order of a minute or more depending on the count and your init duration. If a deployment shifts traffic to a brand new version before its provisioned concurrency is <code>READY</code>, the canary slice hits cold starts — and you will see a latency spike that looks like a code regression but is purely a deployment artifact. Worse, if an alarm is watching p99 latency, the deployment rolls itself back for the wrong reason.</p>\n<p style=\"line-height: 1.75\">The correct sequence is: publish the version, allocate provisioned concurrency on the new version, wait for <code>READY</code>, then begin the traffic shift, and only release the old version's allocation after the deployment settles. When provisioned concurrency is attached to the <strong>alias</strong>, it follows the version the alias points at, which means you are paying for both old and new allocations during the overlap — budget for roughly double for the duration of the deployment. SAM handles the ordering when you put <code>ProvisionedConcurrencyConfig</code> on the function alongside <code>AutoPublishAlias</code> and <code>DeploymentPreference</code>, but it is worth understanding rather than trusting blindly, because a <code>BeforeAllowTraffic</code> hook that checks the allocation status before returning Succeeded is cheap insurance.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Environment promotion: aliases per stage versus accounts per stage</h4>\n<p style=\"line-height: 1.75\">A tempting pattern is one function with aliases named <code>dev</code>, <code>staging</code> and <code>prod</code> pointing at different versions. (2) An <strong>alias <code>live</code></strong> as the only thing API Gateway ever references — the integration URI is the alias ARN, so it never changes across deploys. (3) <strong><code>AutoPublishAlias: live</code></strong> in SAM, so every deploy publishes an immutable version and the alias is managed for us. (4) <strong><code>DeploymentPreference: Type: Canary10Percent10Minutes</code></strong>, giving a 10% slice and a 10-minute bake before the remaining 90% shifts. (5) <strong>Provisioned concurrency</strong> on the alias, so the new version is pre-warmed and the canary measures code, not cold starts. (6) A <strong>PreTraffic hook</strong> that invokes the new version directly by qualifier with a synthetic order, asserts on the response shape and on a write landing in the test partition, then calls <code>putLifecycleEventHookExecutionStatus</code> with Succeeded. (8) A <strong>PostTraffic hook</strong> running a short end-to-end test through API Gateway. (9) <code>AutoRollbackConfiguration</code> enabled on deployment failure and on alarm.</p>\n<p style=\"line-height: 1.75\"><strong>How failure plays out.</strong> Version 13 is published; provisioned concurrency initialises to READY; the PreTraffic hook smoke-tests it; CodeDeploy sets the alias routing config to 10% on version 13. Two minutes in, version 13 starts throwing on a null field that only exists in real traffic. The version-dimensioned <code>Errors</code> alarm breaches within a minute. CodeDeploy immediately clears the routing configuration, returning 100% of traffic to version 12, and marks the deployment failed. <strong>Total customer impact: roughly 10% of traffic for about three minutes, with no human involved.</strong> API Gateway was never reconfigured, so there is no propagation delay.
