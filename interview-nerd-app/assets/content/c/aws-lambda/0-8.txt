How do I find out why?\"</h4>\n<p style=\"line-height: 1.75\">Answer this as an ordered decision tree, not a list of tools. The order is the answer.</p>\n<p style=\"line-height: 1.75\"><strong>Step 1 — Was it invoked at all?</strong> Look at the <strong>Invocations</strong> metric for the time window. If it is <strong>zero</strong>, the function never ran, and nothing inside it can be the cause. Investigate the trigger instead: does the <strong>resource-based policy</strong> allow the source to invoke it (<code>aws lambda get-policy</code>)? Does the event source mapping exist and is it <code>Enabled</code>? For S3, does the notification config exist and do the prefix/suffix filters match? For EventBridge, does the rule pattern actually match the events being emitted — and does the rule show <strong>FailedInvocations</strong>? This step alone resolves a large share of \"my Lambda doesn't work\" tickets.</p>\n<p style=\"line-height: 1.75\"><strong>Step 2 — Was it throttled?</strong> Check the <strong>Throttles</strong> metric. Non-zero means requests were rejected before running because no concurrency was available — a reserved concurrency set to a low value, or the account's regional concurrency limit. The symptom looks like intermittent failure under load and nothing wrong in the code.</p>\n<p style=\"line-height: 1.75\"><strong>Step 3 — Did it error or time out?</strong> Check <strong>Errors</strong>, then go to the logs. In Logs Insights, filter for <code>@message like /ERROR/</code> or for the specific string <em>Task timed out</em>. A timeout and an exception look completely different: a timeout has <strong>Billed Duration equal to the configured timeout</strong> and an abrupt end with no stack trace; an exception has a stack trace and a normal duration. If the answer is timeout, the next question is <em>what</em> it was waiting on, which is an X-Ray question.</p>\n<p style=\"line-height: 1.75\"><strong>Step 4 — Is it a permissions problem?</strong> Look for <code>AccessDeniedException</code>, <code>User: arn:aws:sts::...:assumed-role/... is not authorized to perform:</code>, or a KMS-related denial in the logs. That message names the exact action and resource, so the fix is to add it to the <strong>execution role</strong>. Remember the special case: if you see <strong>no logs at all</strong> despite non-zero Invocations, the execution role is missing the CloudWatch Logs permissions and is suppressing its own evidence.</p>\n<p style=\"line-height: 1.75\"><strong>Step 5 — Is it slow rather than broken?</strong> Enable <strong>active tracing</strong> and read the X-Ray trace: is the time in Initialization (cold start), in a downstream call, or in your own compute? Check <strong>Max Memory Used</strong> in the REPORT line for right-sizing, and look for retries you did not know were happening.</p>\n<p style=\"line-height: 1.75\"><strong>Step 6 — Where did the failed events go?</strong> For asynchronous invocations, failures are retried twice and then sent to an <strong>on-failure destination</strong> or a <strong>dead-letter queue</strong> if configured — and discarded if not. For SQS, failed batches return to the queue and eventually land in the queue's DLQ. Checking the DLQ often recovers the exact payload that broke you, which is the fastest path to a local reproduction.</p>\n<p style=\"line-height: 1.75\">Two supporting tools to mention: <strong>CloudTrail</strong> for control-plane actions (who changed the function configuration at 3 a.m.), and <strong>AWS SAM CLI</strong> (<code>sam local invoke</code>, <code>sam logs</code>) plus the <strong>AWS Toolkit</strong> IDE integrations for local invocation and step-through debugging before you deploy.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"One log stream equals one invocation.\"</strong> No — one stream per <strong>execution environment</strong>, which may contain hundreds of invocations interleaved.
