{"title":"Lambda Pricing, Quotas, and Concurrency Basics","tags":["lambda","pricing","quotas","concurrency"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Lambda's commercial promise is that you <strong>pay only for what you use, and idle costs nothing</strong>. There is no hourly instance charge, no capacity you reserve and waste overnight. But \"what you use\" has a specific definition, and the <strong>quotas</strong> and <strong>concurrency</strong> model that surround it decide whether your architecture scales smoothly or falls over at the worst moment. This topic is the one where interviewers check whether you can reason about a bill and a limit, not just write a handler.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The two core charges: requests and GB-seconds</h4>\n<p style=\"line-height: 1.75\">Lambda bills on two dimensions:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Requests.</strong> A flat charge per invocation, regardless of how long it ran or how much memory it had. In most commercial Regions this has long been <strong>$0.20 per 1 million requests</strong> ($0.0000002 each).</li>\n<li><strong>Duration, measured in GB-seconds.</strong> <em>Memory allocated in GB</em> multiplied by <em>duration billed in seconds</em>, metered per <strong>millisecond</strong>. The commonly quoted x86 on-demand rate is about <strong>$0.0000166667 per GB-second</strong>; <strong>arm64/Graviton2 is cheaper per GB-second</strong>.</li>\n</ul>\n<p style=\"line-height: 1.75\">Two consequences follow immediately. First, <strong>you are billed on memory <em>allocated</em>, not memory used</strong> — the <em>Max Memory Used</em> figure in the REPORT line is diagnostic, not billing. Over-provisioning is real money. Second, <strong>idle time is free</strong>: a function invoked once an hour costs essentially nothing between invocations, which is exactly the opposite of an always-on EC2 instance. Note also that with the millisecond billing granularity, a 12 ms function is billed for 12 ms, not rounded up to 100 ms as it was in Lambda's early years — a detail that still appears in stale blog posts.</p>\n<p style=\"line-height: 1.75\">There is a <strong>free tier</strong> that AWS has historically offered as a perpetual monthly allowance (not just a 12-month trial): on the order of <strong>1 million free requests and 400,000 GB-seconds of compute per month</strong>. Many small side projects genuinely run at zero cost inside it. Treat the exact figures as something you check on the pricing page rather than recite as gospel, and say so in an interview — \"roughly a million requests and 400,000 GB-seconds a month, I'd confirm current numbers\" is a better answer than false precision.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">A worked cost calculation</h4>\n<p style=\"line-height: 1.75\">Make the numbers concrete. font-size: 1.25rem; font-weight: 600\">Concurrency, from first principles</h4>\n<p style=\"line-height: 1.75\"><strong>Concurrency is the number of invocations running at the same instant</strong> — not requests per second. Because one execution environment handles exactly one invocation at a time, concurrency equals the number of environments currently busy. The estimate every candidate should be able to produce on the spot is:</p>\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">concurrency  =  requests per second  x  average duration <i class=k>in</i> seconds\n\n100 req/s x 0.050 s  =    5 concurrent   (fast <i class=k>function</i>, trivial)\n100 req/s x 2.000 s  =  200 concurrent   (same traffic, 40x the concurrency)\n500 req/s x 3.000 s  = 1500 concurrent   -&gt; EXCEEDS the default 1,000 <i class=b>limit</i></code></pre></div>\n<p style=\"line-height: 1.75\">The lesson is that <strong>duration drives concurrency as hard as traffic does</strong>. A function that gets slower — a degraded dependency, a missing database index — quietly consumes more concurrency at unchanged traffic, and can throttle itself and every other function in the Region. That coupling is the most important operational idea in this topic.</p>\n<p style=\"line-height: 1.75\">On top of the <strong>1,000 per-Region account limit</strong>, Lambda gives a <strong>burst concurrency</strong> allowance: a function can scale up rapidly at the start of a spike, and beyond that scales in additional increments per minute. (AWS has since improved this to a faster per-function scaling rate.) The practical point is that Lambda scales fast but not infinitely instantaneously, so a true zero-to-huge spike can still throttle briefly.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Reserved concurrency: a floor and a ceiling</h4>\n<p style=\"line-height: 1.75\"><strong>Reserved concurrency</strong> is set per function and does two things at once, which is exactly why it is asked about:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>It guarantees</strong> that much concurrency for the function — that slice is carved out of the account pool and no other function can take it.</li>\n<li><strong>It caps</strong> the function at that number — the function can never exceed it, and excess invocations are throttled.</li>\n</ul>\n<p style=\"line-height: 1.75\">Use the <em>guarantee</em> side to protect a critical function from a noisy neighbour. Use the <em>cap</em> side to protect a fragile downstream: if a legacy database can only handle 20 connections, reserving 20 for the function that talks to it is the standard way to stop Lambda from stampeding it. Setting reserved concurrency to <strong>0</strong> throttles a function completely — the supported way to \"switch off\" a function during an incident without deleting it.</p>\n<p style=\"line-height: 1.75\">Two important interactions: reserved concurrency <strong>subtracts from the account pool available to everything else</strong>, and AWS keeps a minimum of unreserved concurrency available, so you cannot reserve the entire 1,000. And <strong>reserved concurrency is free</strong> — it is an allocation, not a purchase — whereas <strong>Provisioned Concurrency costs money</strong> because it actually keeps environments initialized. Mixing these two up is a classic stumble; the names are unhelpfully similar.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Throttling: what it looks like and how it behaves</h4>\n<p style=\"line-height: 1.75\">When there is no concurrency available, Lambda rejects the invocation with <strong>HTTP 429</strong> and the error <strong><code>TooManyRequestsException</code></strong> (reason <code>ConcurrentInvocationLimitExceeded</code>), and increments the <strong>Throttles</strong> metric — <em>not</em> the Errors metric. What happens next depends entirely on <strong>how the function was invoked</strong>, and this three-way split is a favourite exam question.</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Invocation type</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Examples</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Behaviour when throttled</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><strong>Synchronous</strong></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">API Gateway, Application Load Balancer, direct Invoke with RequestResponse</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">The <strong>429 is returned straight to the caller</strong>. Our function averages 1.5 seconds. Are we fine on the default limits?\" Compute it: 400 × 1.5 = <strong>600 concurrent executions</strong>. That fits under 1,000, but it consumes 60% of the <em>entire Region's</em> pool, leaving little for every other function in the account. So: request a <strong>Service Quotas increase</strong> ahead of the launch (these take time to approve — do it in advance, not during the incident), set <strong>reserved concurrency</strong> on this function to guarantee its share, alarm on <strong>ConcurrentExecutions</strong> approaching the cap and on any <strong>Throttles</strong>, and — the highest-leverage fix — <strong>reduce the 1.5-second duration</strong>, because halving duration halves concurrency at no traffic change. If the downstream database cannot take 600 concurrent connections, put <strong>RDS Proxy</strong> in front of it or cap the function with reserved concurrency and let an <strong>SQS queue</strong> absorb the difference.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">When Lambda is, and isn't, the right tool</h4>\n<p style=\"line-height: 1.75\">Lambda's economics are excellent for <strong>spiky, bursty, unpredictable or low-volume</strong> workloads, because you pay nothing between events and you never provision for a peak you rarely hit. Event-driven glue, scheduled jobs, API backends with variable traffic, stream processors and back-office automation are all natural fits, and the operational savings (no patching, no capacity planning, no autoscaling groups) are often worth more than the compute line item.</p>\n<p style=\"line-height: 1.75\">It fits badly when:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Load is steady, high and predictable.</strong> At constant saturation the per-request premium adds up, and the same work on <strong>Fargate</strong>, <strong>ECS/EKS on EC2</strong>, or reserved/Spot EC2 instances is frequently cheaper. The honest answer is \"run the numbers\": compare monthly GB-seconds against an equivalently sized always-on instance. This is the crossover argument interviewers want to hear you acknowledge rather than evangelise.</li>\n<li><strong>Work exceeds 15 minutes.</strong> Use Step Functions to decompose it, or Fargate/Batch for genuinely long jobs.</li>\n<li><strong>You need very low, very consistent latency.</strong> Cold starts put a floor under p99 unless you pay for Provisioned Concurrency — at which point you are paying for idle capacity anyway, which weakens the cost argument.</li>\n<li><strong>The workload needs large local state, GPUs, persistent connections (WebSocket servers), or specialised hardware.</strong></li>\n<li><strong>Payloads are large.</strong> The 6 MB sync / 256 KB async limits force S3-pointer designs that may not suit you.</li>\n<li><strong>Chatty request patterns with an expensive per-request tail</strong> — thousands of tiny invocations each paying a request charge plus minimum overhead can be less efficient than one long-lived process.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"I'm billed for the memory my function actually uses.\"</strong> No — for memory <strong>allocated</strong>. Max Memory Used is diagnostic only.</li>\n<li><strong>\"Concurrency is requests per second.\"</strong> It is simultaneous executions: roughly RPS × average duration in seconds.</li>\n<li><strong>\"Reserved concurrency and Provisioned Concurrency are the same thing.\"</strong> Reserved concurrency is a free allocation that both guarantees and caps; Provisioned Concurrency costs money and pre-initializes environments to remove cold starts.</li>\n<li><strong>\"The 1,000 limit is per function.\"</strong> It is per <strong>account per Region</strong>, shared by every function — which is why one runaway function can throttle your whole Region.</li>\n<li><strong>\"Throttles show up as Errors.\"</strong> They are a separate <strong>Throttles</strong> metric; a throttled request never ran.</li>\n<li><strong>\"A throttle always loses the request.\"</strong> Only for synchronous invocations. Asynchronous invocations are retried for hours, and poll-based sources back off and redrive.</li>\n<li><strong>\"Lambda is always cheaper than servers.\"</strong> False at steady high volume. Model it.</li>\n<li><strong>\"I can raise the 15-minute timeout by asking support.\"</strong> You cannot — it is a hard limit. Redesign with Step Functions or Fargate.</li>\n<li><strong>\"The Lambda bill is the serverless bill.\"</strong> CloudWatch Logs, NAT Gateway, API Gateway and DynamoDB frequently cost more than the functions.</li>\n</ul>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"You pay per request — about twenty cents per million — plus GB-seconds, which is memory allocated times duration billed per millisecond.
