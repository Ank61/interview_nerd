{"title":"Lambda Performance Tuning — Memory/CPU, Connection Reuse, and Package Optimization","tags":["performance","memory-tuning","connection-reuse","rds-proxy"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Lambda performance tuning is dominated by two facts that surprise people new to the platform. First, <strong>the memory setting is really a CPU setting</strong>, which means a CPU-bound function can become simultaneously faster <em>and</em> cheaper when you give it more memory. Second, <strong>execution environments are reused</strong>, which makes global-scope initialisation the highest-leverage code change available — and also makes concurrency multiply your downstream connection count in a way that quietly destroys relational databases.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Memory, vCPU, and Network Are One Dial</h4>\n<p style=\"line-height: 1.75\">You configure memory from <strong>128 MB to 10,240 MB in 1 MB increments</strong>. Lambda allocates <strong>CPU proportionally</strong>: you get approximately <strong>one full vCPU at 1,769 MB</strong>, and more vCPUs above that, up to about <strong>6 vCPUs at 10,240 MB</strong>. Network bandwidth and disk throughput to the execution environment scale on the same curve. There is no separate CPU knob — this single dial is the entire compute allocation API.</p>\n<p style=\"line-height: 1.75\">Two consequences follow immediately. <strong>Multithreading only helps above 1,769 MB.</strong> Below that you have a fraction of a core, so spawning threads (or Node worker threads, or a JVM parallel stream) adds context-switch overhead without adding throughput. Above it, a function doing image processing or compression can genuinely parallelise. And <strong>the cheapest memory setting is very often not the smallest</strong>, because billing is memory × duration, so if doubling memory more than halves duration, cost falls.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Cost Calculation That Proves It</h4>\n<p style=\"line-height: 1.75\">Take a CPU-bound image resizer, billed at the us-east-1 x86 rate of <strong>$0.0000166667 per GB-second</strong>, for <strong>10 million invocations per month</strong>. Beyond the knee at 1,769 MB the extra cores go unused and cost climbs 40 percent for a 17 percent latency gain. If this workload were <strong>IO-bound</strong> instead — waiting on DynamoDB — the duration column would barely move and every step up the table would be pure waste. That is why you measure rather than reason.</p>\n<p style=\"line-height: 1.75\"><strong>AWS Lambda Power Tuning</strong> is the standard empirical tool: an open-source <strong>Step Functions state machine</strong> (deployable from the Serverless Application Repository) that invokes your function at a list of memory settings with a real payload, discards cold starts, and returns a cost-versus-latency curve plus a recommended setting. You choose the optimisation strategy — <code>cost</code>, <code>speed</code>, or <code>balanced</code> with a weighting. Running it in CI on a representative payload is what separates a tuned fleet from folklore.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Connection Reuse — The Highest-Leverage Code Change</h4>\n<p style=\"line-height: 1.75\">Lambda <strong>freezes</strong> the execution environment after a response and <strong>thaws</strong> it for the next invocation. Everything in global scope — module-level variables, SDK clients, HTTP agents, database pools, caches — survives. The rule is therefore blunt: <strong>construct expensive, reusable objects outside the handler; keep only per-request state inside it.</strong></p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\"><li><strong>SDK clients.</strong> Creating a DynamoDB or S3 client costs credential resolution, region resolution, and middleware stack construction. Built once at init, it is amortised over thousands of warm invocations.</li><li><strong>HTTP keep-alive.</strong> Without it, every outbound call pays a TCP handshake plus a TLS handshake — easily 30–100 ms per call. The <strong>AWS SDK for JavaScript v3 enables keep-alive by default</strong>; with v2 you had to set <code>AWS_NODEJS_CONNECTION_REUSE_ENABLED=1</code>. For non-AWS HTTP calls, construct your own agent with <code>keepAlive: true</code> in global scope. In Python, a module-level <code>boto3</code> client or a <code>requests.Session</code> achieves the same.</li><li><strong>Database connections.</strong> A PostgreSQL or MySQL handshake plus authentication is tens of milliseconds and real server CPU. Establishing it per invocation is the single most common Lambda performance defect.</li></ul>\n<p style=\"line-height: 1.75\"><strong>The two pitfalls.</strong> First, <strong>connections go stale</strong>. The environment can be frozen for minutes, during which the database, a proxy, or a NAT Gateway (which has a 350-second idle timeout) may silently drop the TCP connection. The frozen process never sees the FIN, so the next invocation writes into a dead socket and gets <code>ECONNRESET</code> or a hang until timeout. Mitigate with connection validation before use, short socket timeouts, retry-on-stale-connection, and TCP keepalive tuning. Second — and this is the one that causes outages — <strong>concurrency multiplies connections</strong>. Each execution environment holds its own pool. At 400 concurrent environments with a pool of 5, you are asking for <strong>2,000 database connections</strong>. Relational databases price connections in memory and scheduler overhead, so <code>max_connections</code> is exhausted and the database fails for <em>every</em> client, not just Lambda. Pooling inside a Lambda is not pooling across a fleet.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">RDS Proxy — The Standard Answer</h4>\n<p style=\"line-height: 1.75\"><strong>Amazon RDS Proxy</strong> sits between Lambda and RDS or Aurora and maintains a warm pool of database connections that many client connections are <strong>multiplexed</strong> onto. Hundreds of concurrent execution environments share a small set of real database connections. It also holds client connections open across a <strong>failover</strong>, cutting failover-related downtime substantially, and supports <strong>IAM authentication</strong> with credentials stored in <strong>Secrets Manager</strong>, which removes database passwords from your function configuration entirely.</p>\n<p style=\"line-height: 1.75\">Caveats worth stating so the answer sounds lived-in: RDS Proxy is billed <strong>per vCPU of the database instance per hour</strong>, so it is not free; it requires the function to be <strong>VPC-attached</strong>; and <strong>session pinning</strong> can defeat multiplexing — if a session uses a temporary table, a session variable, a prepared statement outside the supported set, or an explicit lock, the proxy pins that client to a dedicated backend connection for the session's life, and heavy pinning collapses the pooling benefit. Monitor <code>DatabaseConnectionsCurrentlySessionPinned</code>. The complete defence-in-depth stack is: <strong>connection reuse in global scope</strong> → <strong>RDS Proxy for fleet-wide pooling</strong> → <strong>reserved concurrency as a hard backstop</strong>. And the strategic answer: if you are building greenfield, a serverless-native data store like <strong>DynamoDB</strong> — HTTP-based, connectionless, no pool to exhaust — removes the problem rather than managing it. <strong>Aurora DSQL</strong> and the <strong>Aurora Serverless Data API</strong> are HTTP-based alternatives when relational semantics are required.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Package Optimisation and Architecture</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\"><li><strong>Bundle and tree-shake.</strong> esbuild, Rollup, or webpack collapse a dependency tree into one minified file. This cuts both download time and module-resolution time, and the second effect is usually larger — thousands of small file reads are slow even when total bytes are modest.</li><li><strong>Layers versus bundling.</strong> Layers are good for sharing genuinely common, slow-moving binaries (native libraries, the Parameters and Secrets extension, a monitoring agent) and for separating deployment lifecycles. They are <strong>not</strong> a performance optimisation: layer content is merged into the same package and counts toward the <strong>250 MB unzipped limit</strong> (maximum 5 layers), it is not cached separately across functions, and layers defeat tree-shaking because they ship whole packages. Default to bundling; use layers deliberately.</li><li><strong>Container images.</strong> Up to <strong>10 GB</strong>, and Lambda caches and lazily loads image layers, so a large image does not cold start proportionally to its size the way a large zip does. Structure your Dockerfile so stable dependency layers sit below frequently changing application layers to maximise cache reuse.</li><li><strong>arm64 versus x86_64.</strong> Graviton2 offers roughly <strong>20 percent lower cost per GB-second</strong> and frequently better performance, giving up to 34 percent better price-performance. Migration is usually a one-line architecture change; the risk is <strong>native dependencies</strong> (sharp, numpy, grpc, any compiled extension) that need arm64 builds, so build on arm64 and test rather than assuming.</li><li><strong>Payload and serialisation.</strong> Synchronous invocation payloads are capped at <strong>6 MB</strong> request and response, asynchronous at <strong>256 KB</strong>; response streaming raises the response ceiling to <strong>20 MB</strong> with a soft limit and, more importantly, improves time-to-first-byte. Large JSON payloads cost real CPU in serialisation on both sides — use the <strong>claim-check pattern</strong> (put the payload in S3, pass the key) rather than pushing against the limits.</li></ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario: \"this function is slow\" — a diagnosis tree</h4>\n<p style=\"line-height: 1.75\">p99 is 3.5 seconds against a 500 ms budget.
