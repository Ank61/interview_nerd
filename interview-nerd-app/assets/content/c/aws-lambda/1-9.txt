{"title":"Lambda Function URLs and Application Load Balancer Integration","tags":["function-urls","response-streaming","alb","http-entrypoints"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">API Gateway is not the only way to put a Lambda function behind HTTP. There are three production-grade entry points — <strong>API Gateway</strong>, <strong>Lambda Function URLs</strong>, and an <strong>Application Load Balancer</strong> with a Lambda target group — and at senior level you are expected to choose deliberately rather than reflexively. They differ on cost model, auth model, feature surface, payload limits, and, critically, on which ones support <strong>response streaming</strong>. Getting this choice right is often worth more than any amount of function tuning: it decides your per-request cost curve, your security boundary, and whether you can deliver a first byte in 200 ms or 20 seconds.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Lambda Function URLs: what they are</h4>\n<p style=\"line-height: 1.75\">A <strong>function URL</strong> is a dedicated HTTPS endpoint attached directly to a function, of the form <code>https://&lt;url-id&gt;.lambda-url.&lt;region&gt;.on.aws/</code>. There is no separate service in the path — Lambda terminates TLS and invokes the function. You create one with <code>aws lambda create-function-url-config</code>, and you can attach it to <code>$LATEST</code> or to an <strong>alias</strong> (but not to a numbered version directly), which is how you get blue/green and weighted traffic shifting at the URL layer via alias routing configuration.</p>\n<p style=\"line-height: 1.75\">The request event uses <strong>payload format 2.0</strong> — the same envelope as an HTTP API — so <code>event.requestContext.http.method</code>, <code>event.rawPath</code>, <code>event.rawQueryString</code>, a <code>cookies</code> array, and comma-joined headers. <code>routeKey</code> and <code>stage</code> are always <code>$default</code>, because a function URL has <strong>no routing</strong>: every path and every method arrives at the same function and you route in code. The response contract is 2.0's lenient one — return an object with <code>statusCode</code>/<code>headers</code>/<code>body</code>, or return a bare JSON-serialisable value and Lambda wraps it as a 200 with a JSON content type.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">AuthType: the one security decision</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong><code>AWS_IAM</code>.</strong> Callers must sign requests with <strong>SigV4</strong> against the <code>lambda</code> service, and the caller's principal must be allowed <code>lambda:InvokeFunctionUrl</code> by IAM policy and by the function's resource policy. This is the right choice for service-to-service calls, internal tools, and anything invoked from another AWS account or from a signed client. It costs nothing extra and gives you IAM's full condition-key surface — including <code>lambda:FunctionUrlAuthType</code>, which you can use in an SCP to <em>forbid</em> anyone in the organisation from creating public function URLs.</li>\n<li><strong><code>NONE</code>.</strong> The endpoint is <strong>public to the entire internet</strong>. Creating it attaches a resource-based policy granting <code>lambda:InvokeFunctionUrl</code> to <code>Principal: \"*\"</code>. There is no network-level gate, no API key, no IP allow-list, and no WAF. Every request that reaches it costs you an invocation whether or not your code accepts it, so a scan or a scraper directly converts into billed duration and concurrency consumption. If you use <code>NONE</code>, <strong>all</strong> authentication and authorization must happen in your handler's first few lines, before any expensive work, and you must set <strong>reserved concurrency</strong> as your only blast-radius control.</li>\n</ul>\n<p style=\"line-height: 1.75\">The interview-grade nuance is that <code>AuthType: NONE</code> is not inherently wrong — it is exactly right for a public webhook receiver, a public health endpoint, or an origin behind CloudFront — but it must be a decision with compensating controls, not a default. The strongest pattern is <strong>CloudFront in front of the function URL with Origin Access Control</strong>: CloudFront signs requests to the origin with SigV4 so the function URL can stay on <code>AWS_IAM</code>, and you get a custom domain, edge caching, WAF, and request-level DDoS protection that the function URL alone cannot provide.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Built-in CORS</h4>\n<p style=\"line-height: 1.75\">Function URLs have a native <code>Cors</code> configuration — <code>AllowOrigins</code>, <code>AllowMethods</code>, <code>AllowHeaders</code>, <code>ExposeHeaders</code>, <code>AllowCredentials</code>, <code>MaxAge</code>. When configured, Lambda answers <code>OPTIONS</code> preflight requests itself <strong>without invoking your function</strong> (so preflights are free) and injects the CORS headers onto your responses. As with HTTP API CORS, you should <strong>not</strong> also emit <code>Access-Control-Allow-Origin</code> from your handler — duplicated headers cause browsers to reject the response. And note the usual trap: a 500 or a concurrency 429 returned before your code runs carries whatever CORS headers Lambda injects, but an unhandled failure can still surface in the browser as an opaque CORS error, so always check the raw status before believing the console message.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Response streaming — the feature that justifies function URLs</h4>\n<p style=\"line-height: 1.75\">By default, <code>InvokeMode</code> is <code>BUFFERED</code>: Lambda collects the entire response, caps it at the <strong>6 MB</strong> synchronous payload limit, and sends it at once. And the <strong>response size ceiling rises</strong> from 6 MB to a soft limit of <strong>20 MB</strong> (increasable on request), with the caveat that streamed responses get an initial burst allowance of the first 6 MB and are then bandwidth-capped, so streaming is about latency and size, not about raw throughput.</p>\n<p style=\"line-height: 1.75\">Mechanically, in the Node.js managed runtimes you wrap the handler in <code>awslambda.streamifyResponse</code> and receive a <code>responseStream</code> you write to; use <code>awslambda.HttpResponseStream.from(stream, { statusCode, headers })</code> to set status and headers before the first write, because <strong>once you have written a byte you can no longer change the status code</strong> — an error that occurs mid-stream cannot become a 500, so you must signal it in-band (an SSE <code>error</code> event, a trailing JSON error object) and design the client to handle a truncated stream. Other runtimes stream via the custom-runtime streaming API. The restriction that decides architectures: <strong>response streaming works only through function URLs and the <code>InvokeWithResponseStream</code> API — not through API Gateway and not through an ALB</strong>. If you need streaming and a rich gateway, the answer is CloudFront in front of a streaming function URL, not API Gateway.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What you give up versus API Gateway</h4>\n<p style=\"line-height: 1.75\">Precisely this list, and it is worth being able to recite it:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>No usage plans or API keys.</strong> No per-consumer quotas or metering of any kind.</li>\n<li><strong>No request validation or transformation.</strong> No JSON Schema models, no VTL mapping templates, no parameter mapping. Every malformed request costs a full invocation.</li>\n<li><strong>No custom authorizers, no JWT or Cognito authorizers.</strong> Your only built-in options are SigV4 (<code>AWS_IAM</code>) or nothing; any token validation runs inside your handler on your dime.</li>\n<li><strong>No WAF attachment.</strong> AWS WAF cannot be associated with a function URL; you must front it with CloudFront to get WAF, managed rule groups, or rate-based rules.</li>\n<li><strong>No built-in throttling.</strong> There is no requests-per-second control. Your only lever is <strong>reserved concurrency</strong>, and requests beyond it are rejected with a <code>429</code> carrying <code>x-amzn-errortype: TooManyRequestsException</code>.</li>\n<li><strong>No routing, no stages, no custom domain, no stage cache, no native X-Ray on the entry point.</strong> One URL, one function, one <code>$default</code> route; you implement routing in code and you bring CloudFront for a branded domain.</li>\n<li><strong>No WebSockets, no mTLS, no private/VPC-only endpoint.</strong></li>\n</ul>\n<p style=\"line-height: 1.75\">What you gain in exchange: <strong>zero per-request charge</strong> (you pay only Lambda), <strong>lower latency</strong> because there is one less service in the path, a simpler resource graph, and <strong>response streaming</strong>, which neither of the alternatives offers.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">ALB as a Lambda trigger</h4>\n<p style=\"line-height: 1.75\">An Application Load Balancer can route to a <strong>target group of type <code>lambda</code></strong>, which holds exactly one function. You must grant <code>lambda:InvokeFunction</code> to the <code>elasticloadbalancing.amazonaws.com</code> principal (the console and CloudFormation usually do this for you).</p>\n<p style=\"line-height: 1.75\">The event and response shapes are <strong>distinct from both API Gateway formats</strong>, which is the detail people get wrong when porting handlers:</p>\n<div class=\"code\"><div class=\"code-head\"><span>css</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">ALB request event                        ALB response (required shape)\n{                                        {\n  &quot;requestContext&quot;: {                      &quot;statusCode&quot;: <i class=n>200</i>,\n    <i class=s>&quot;elb&quot;</i>: { &quot;targetGroupArn&quot;: <i class=s>&quot;...&quot;</i> }     &quot;statusDescription&quot;: <i class=s>&quot;200 OK&quot;</i>,\n  },                                       &quot;headers&quot;: { &quot;<i class=a>Content</i>-Type&quot;: <i class=s>&quot;text/html&quot;</i> },\n  &quot;httpMethod&quot;: <i class=s>&quot;GET&quot;</i>,                     <i class=s>&quot;multiValueHeaders&quot;</i>: { &quot;Set-Cookie&quot;: [<i class=s>&quot;a=1&quot;</i>,<i class=s>&quot;b=2&quot;</i>] },\n  &quot;<i class=e>path</i>&quot;: <i class=s>&quot;/report&quot;</i>,                       <i class=s>&quot;body&quot;</i>: <i class=s>&quot;...&quot;</i>,\n  <i class=s>&quot;queryStringParameters&quot;</i>: { ... },        &quot;isBase64Encoded&quot;: false\n  <i class=s>&quot;headers&quot;</i>: { ... },                    }\n  &quot;<i class=e>body</i>&quot;: <i class=s>&quot;...&quot;</i>,\n  <i class=s>&quot;isBase64Encoded&quot;</i>: false                 Malformed =&gt; font-size: 1.25rem; font-weight: 600\">Interview scenario: choosing an entry point</h4>\n<p style=\"line-height: 1.75\">You must expose three surfaces for one product. Choose and justify each.</p>\n<p style=\"line-height: 1.75\"><strong>(a) A public customer-facing REST API.</strong> 20 million requests/month, OAuth2 tokens from an OIDC provider, per-customer rate limits on a free/pro/enterprise tiering, and payload validation. <strong>Choose API Gateway.</strong> An HTTP API with a native JWT authorizer covers the token validation with no Lambda in the auth path; per-route throttling covers the tiering coarsely, and if you need real per-customer quotas you go to a REST API for usage plans and API keys — at 20 M requests that is about 70 USD/month against 20 USD for an HTTP API, and the metering and request validation are worth the difference. Neither a function URL nor an ALB can enforce per-consumer quotas at all, and neither can reject malformed payloads before you pay for an invocation.</p>\n<p style=\"line-height: 1.75\"><strong>(b) A GitHub webhook receiver.</strong> Bursty, tens of thousands of deliveries per day, authentication is an HMAC signature in a header that only your code can verify, and you need the raw body to compute the digest. <strong>Choose a Function URL with <code>AuthType: NONE</code></strong>, plus compensating controls: verify the HMAC in the first lines of the handler using a constant-time comparison before any parsing or downstream call, set <strong>reserved concurrency</strong> (say 50) so a flood cannot consume the account pool, and put CloudFront with WAF in front if abuse becomes a problem. API Gateway would add per-request cost and a per-route configuration for an endpoint that has exactly one route and cannot use any of its authorizers; an ALB would add an hourly charge for a low-steady-volume endpoint.</p>\n<p style=\"line-height: 1.75\"><strong>(c) An LLM chat endpoint.</strong> Responses take 6–20 seconds to generate fully, users must see tokens immediately, and the browser is the client. <strong>Choose a Function URL with <code>InvokeMode: RESPONSE_STREAM</code>, fronted by CloudFront.</strong> This is the decisive case: API Gateway cannot stream at all and would both hold the client for the full generation time and risk a 504 at 30 seconds; an ALB cannot stream either and caps responses at 1 MB. Streaming takes TTFB from ~8 s to a few hundred milliseconds. Set the function URL's <code>AuthType</code> to <code>AWS_IAM</code> and use CloudFront Origin Access Control so CloudFront SigV4-signs to the origin — that gives you a custom domain, WAF, and no publicly-invocable endpoint. Handle errors in-band, since once the first byte is written the status code is fixed at 200.</p>\n<p style=\"line-height: 1.75\"><strong>Bonus — (d) the migration case.</strong> If the same product already has a monolith on ECS behind an ALB and you want to peel off <code>/reports</code> to Lambda, put a <strong>lambda target group behind the existing ALB</strong> with a path-based listener rule. You keep one hostname, one certificate, one WAF web ACL, and one set of access logs, and the cutover is a listener-rule change that you can weight and roll back instantly. That operational continuity usually outweighs anything API Gateway would give you for that particular route — but remember the 1 MB response cap and generate large reports to S3 with a pre-signed URL instead of returning bytes.</p>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"Function URLs give a function its own HTTPS endpoint with no per-request charge and the lowest latency, but you get only SigV4 or fully public auth — no usage plans, no request validation, no custom authorizers, no WAF, and no throttling beyond reserved concurrency.
