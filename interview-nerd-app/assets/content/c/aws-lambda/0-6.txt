font-size: 1.25rem; font-weight: 600\">The execution role in detail</h4>\n<p style=\"line-height: 1.75\">An execution role is an ordinary IAM role with two halves. The <strong>trust policy</strong> (assume-role policy) names <code>lambda.amazonaws.com</code> as a trusted service principal — this is what allows the Lambda service to assume the role at all. If the trust policy is wrong, function creation itself fails with an error about the role not being assumable. The <strong>permissions policies</strong> attached to the role list the AWS API actions your code may call.</p>\n<p style=\"line-height: 1.75\">When Lambda creates an execution environment for your function, it assumes that role and injects the resulting <strong>temporary credentials into the environment</strong> as the standard variables <code>AWS_ACCESS_KEY_ID</code>, <code>AWS_SECRET_ACCESS_KEY</code> and <code>AWS_SESSION_TOKEN</code>. The AWS SDKs pick these up automatically through the default credential provider chain. That is why a Lambda handler can simply construct a DynamoDB client with no credentials argument and it just works.</p>\n<p style=\"line-height: 1.75\">This design has an important security consequence you should say out loud in an interview: <strong>you never hard-code access keys in a Lambda function.</strong> Long-lived IAM user keys pasted into code or environment variables are a liability — they end up in git history, they do not rotate, and they survive after the function is deleted. The role's credentials are <strong>temporary, automatically rotated, and scoped to the function</strong>. If you catch yourself needing an access key inside Lambda, the answer is almost always \"put that permission on the execution role instead\", or for cross-account work, \"have the execution role assume a role in the other account\".</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">AWSLambdaBasicExecutionRole and the logging permissions</h4>\n<p style=\"line-height: 1.75\">Every Lambda function needs three CloudWatch Logs permissions to produce logs at all: <code>logs:CreateLogGroup</code>, <code>logs:CreateLogStream</code> and <code>logs:PutLogEvents</code>. AWS packages exactly these in the managed policy <strong>AWSLambdaBasicExecutionRole</strong>, and when you create a function in the console with a new role, the console attaches it for you. This is the minimum viable execution role.</p>\n<p style=\"line-height: 1.75\">Other AWS managed policies you should recognise by name:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>AWSLambdaBasicExecutionRole.</strong> CloudWatch Logs only. Every function needs this or an equivalent.</li>\n<li><strong>AWSLambdaVPCAccessExecutionRole.</strong> Adds the EC2 network-interface permissions (<code>ec2:CreateNetworkInterface</code>, <code>DescribeNetworkInterfaces</code>, <code>DeleteNetworkInterface</code>) that Lambda needs to attach your function to a VPC. Without it, a VPC-configured function fails to initialise.</li>\n<li><strong>AWSLambdaSQSQueueExecutionRole.</strong> For SQS event source mappings — <code>sqs:ReceiveMessage</code>, <code>DeleteMessage</code>, <code>GetQueueAttributes</code>.</li>\n<li><strong>AWSLambdaDynamoDBExecutionRole</strong> and <strong>AWSLambdaKinesisExecutionRole.</strong> For stream event source mappings, granting the read/iterator permissions on the stream.</li>\n</ul>\n<p style=\"line-height: 1.75\">Note the subtlety with poll-based sources: for SQS, DynamoDB Streams and Kinesis, the permission to read the source sits on the <strong>execution role</strong>, not in a resource-based policy — because Lambda <em>polls</em> those sources using your role rather than being pushed to. That asymmetry is a favourite interview follow-up.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Least privilege for execution roles</h4>\n<p style=\"line-height: 1.75\">Least privilege means granting only the actions the function actually performs, on only the resources it actually touches. In practice:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>One role per function.</strong> Sharing one fat role across twenty functions means every function inherits every permission, and a compromise of the least important one reaches the most important data.</li>\n<li><strong>Name specific actions, not wildcards.</strong> <code>dynamodb:PutItem</code> and <code>dynamodb:GetItem</code>, not <code>dynamodb:*</code>. Never <code>\"Action\": \"*\"</code> with <code>\"Resource\": \"*\"</code>.</li>\n<li><strong>Scope the Resource ARN.</strong> <code>arn:aws:s3:::uploads-bucket/incoming/*</code>, not <code>arn:aws:s3:::*</code>. Remember the S3 quirk: object actions target <code>bucket/*</code>, while bucket-level actions such as <code>s3:ListBucket</code> target the bucket ARN itself with no trailing wildcard.</li>\n<li><strong>Add condition keys where they fit.</strong> For example <code>dynamodb:LeadingKeys</code> to restrict access to a tenant's partition, or <code>aws:SourceArn</code> style conditions on KMS usage.</li>\n<li><strong>Do not forget KMS.</strong> If the S3 bucket, SQS queue or DynamoDB table is encrypted with a customer managed key, the execution role also needs <code>kms:Decrypt</code> (and <code>kms:GenerateDataKey</code> for writes) on that key — and the key policy must allow the role. A function that has perfect S3 permissions but no KMS permission fails with an access-denied that mentions KMS, and beginners spend an hour re-reading their S3 policy.</li>\n<li><strong>Start from generated policies.</strong> IAM Access Analyzer can generate a policy from CloudTrail activity, letting you deploy with a broad policy in a dev account, observe real calls, and tighten to exactly what was used.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The resource-based policy in detail</h4>\n<p style=\"line-height: 1.75\">The function policy is a JSON document attached directly to the function. Each statement grants a <strong>principal</strong> permission to perform <code>lambda:InvokeFunction</code> (or another Lambda action) on that function. You read it with <code>aws lambda get-policy</code> and you edit it with <code>aws lambda add-permission</code> and <code>aws lambda remove-permission</code> — you do not hand-edit a JSON blob the way you would an S3 bucket policy.</p>\n<p style=\"line-height: 1.75\">Two kinds of principal show up:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>AWS service principals.</strong> <code>s3.amazonaws.com</code>, <code>apigateway.amazonaws.com</code>, <code>events.amazonaws.com</code> (EventBridge), <code>sns.amazonaws.com</code>, <code>logs.amazonaws.com</code>. These are used by <em>push</em>-model event sources — the service calls Invoke on your function, so the service needs permission.</li>\n<li><strong>Accounts, IAM roles or users, and organizations.</strong> For cross-account invocation, for example letting account 111122223333 invoke your function, or letting an entire AWS Organization do so via the <code>aws:PrincipalOrgID</code> condition.</li>\n</ul>\n<p style=\"line-height: 1.75\">Two parameters on <code>add-permission</code> matter enormously for security. <strong><code>--source-arn</code></strong> restricts the grant to invocations originating from one specific resource — a particular bucket, a particular API, a particular EventBridge rule. Without it, you have told <em>every</em> S3 bucket in the world's service principal that it may invoke your function, which is the classic <strong>confused deputy</strong> problem: an attacker creates a bucket in their own account, points its notification at your function, and invokes it with data of their choosing. <strong><code>--source-account</code></strong> adds the account restriction, which matters for S3 because bucket ARNs do not contain the account ID. Always set these.</p>\n<p style=\"line-height: 1.75\">The convenience that hides all this: <strong>when you add a trigger in the Lambda or S3 console, or define one in SAM/CloudFormation, the resource-based policy statement is created for you automatically</strong>, correctly scoped. That is why beginners can go a long time without knowing function policies exist — and why the first time they wire something up with raw CLI or Terraform and nothing happens, they have no mental model for what is missing.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">How the two combine: the evaluation order</h4>\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">Caller (API Gateway / S3 / another account / a developer)\n      |\n      | 1. The function is running (Invocations metric is non-zero) but you cannot see anything. The cause is almost always that the <strong>execution role lacks CloudWatch Logs permissions</strong> — someone created a custom role with only DynamoDB access and forgot <code>logs:CreateLogStream</code> and <code>logs:PutLogEvents</code>. This creates a horrible debugging loop: the function may also be failing for another reason, but the evidence is being suppressed by the same missing role. The fix is to attach <strong>AWSLambdaBasicExecutionRole</strong> (or the three logs actions explicitly) and re-invoke. A second, subtler variant: the role is fine but a <strong>permissions boundary</strong> or an <strong>SCP</strong> denies <code>logs:*</code>, so the effective permission is still deny.</p>\n<p style=\"line-height: 1.75\"><strong>Failure 2 — \"I configured an S3 trigger and nothing happens.\"</strong> You upload an object, and the function's <strong>Invocations metric stays at zero</strong>. No errors, no logs, no throttles — total silence. That silence is the tell: if the function had run and failed you would see Errors and log output. Silence means it was never invoked, which points at the <strong>inbound</strong> direction. Run <code>aws lambda get-policy --function-name X</code>. If it returns <em>ResourceNotFoundException: The resource you requested does not exist</em>, the function has <strong>no resource-based policy</strong> and S3's invoke attempt is being rejected. The fix is <code>aws lambda add-permission</code> with principal <code>s3.amazonaws.com</code>, a <code>--source-arn</code> of the bucket and a <code>--source-account</code>. (Check the other candidate causes too: does the bucket notification configuration actually exist, and does the event type and prefix/suffix filter match the key you uploaded?)</p>\n<p style=\"line-height: 1.75\">The diagnostic principle that ties both together: <strong>\"error in the logs\" means the outbound direction (execution role); \"no invocation at all\" means the inbound direction (resource-based policy).</strong> Saying that sentence in an interview demonstrates you have actually debugged this.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"I gave the execution role s3:GetObject, so S3 can trigger my function.\"</strong> Backwards. That lets your function <em>read</em> S3. Letting S3 <em>invoke</em> you needs a resource-based policy.</li>\n<li><strong>\"I added a resource policy allowing invoke, so the function can now write to DynamoDB.\"</strong> Also backwards. Inbound permission grants nothing outbound.</li>\n<li><strong>\"SQS triggers need a resource-based policy on the function.\"</strong> No — SQS, DynamoDB Streams and Kinesis are <em>poll</em>-based. Lambda polls them using the <strong>execution role</strong>, so the read permissions go there. (The SQS queue's own policy may still need to allow the role.)</li>\n<li><strong>\"I'll put an access key in an environment variable so the function can call S3.\"</strong> Never. The execution role delivers temporary, rotating credentials automatically.</li>\n<li><strong>\"add-permission without --source-arn is fine, it's only S3.\"</strong> It is not fine; it grants the whole service principal, which anyone can use from their own account. Scope it.</li>\n<li><strong>\"The console wired up my trigger, so there's nothing else in play.\"</strong> The console silently created a resource-based policy statement for you. Know that it exists, because your IaC tooling will not create it for free.</li>\n<li><strong>\"AWSLambdaBasicExecutionRole is a role.\"</strong> It is an AWS <em>managed policy</em> that you attach to a role.
