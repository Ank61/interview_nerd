{"title":"Lambda with Kinesis and DynamoDB Streams — Shards, Ordering, and Iterator Age","tags":["kinesis","dynamodb-streams","iterator-age","parallelization-factor"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Stream sources are the one Lambda integration where <strong>concurrency is not elastic</strong>. With SQS, Lambda scales pollers to meet demand. With Kinesis Data Streams and DynamoDB Streams, the event source mapping assigns <strong>one concurrent invocation per shard</strong>, and that is the entire parallelism budget. If your throughput exceeds what one function instance can process per shard, no Lambda setting will save you — you must reshard, or multiply concurrency per shard with the <strong>parallelization factor</strong>. This single structural fact drives almost every design decision and every incident in stream-based serverless systems.</p>\n<p style=\"line-height: 1.75\">The second structural fact is <strong>ordering</strong>. Streams preserve order within a shard, which means the ESM must checkpoint monotonically, which means a record that cannot be processed <strong>blocks every record behind it on that shard</strong>. The whole error-handling toolkit for streams — bisect-on-error, maximum retry attempts, maximum record age, on-failure destinations — exists to put a bound on that blocking.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The shard model and parallelization factor</h4>\n<p style=\"line-height: 1.75\">A stream is partitioned into shards. Producers supply a <strong>partition key</strong> (for DynamoDB Streams, the item's partition key); the stream hashes it to pick a shard. Lambda's poller assigns each shard to a processor, reads records with <code>GetRecords</code>, and invokes your function with a batch. By default, <strong>maximum concurrency = number of shards</strong>.</p>\n<p style=\"line-height: 1.75\"><strong><code>ParallelizationFactor</code></strong> (1–10, default 1) raises that to <strong>shards × factor</strong>. Critically, it does <em>not</em> break ordering: Lambda groups records within the shard by partition key and guarantees that all records sharing a partition key go to the same concurrent processor, in order. So with a factor of 10 you get up to 10 concurrent invocations per shard, each handling a disjoint set of partition keys.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">ParallelizationFactor <i class=o>=</i> <i class=n>1</i>                 ParallelizationFactor <i class=o>=</i> <i class=n>4</i>\nShard <i class=n>0</i> <i class=o>-</i><i class=o>&gt;</i> [ invocation ]                 Shard <i class=n>0</i> <i class=o>-</i><i class=o>+</i><i class=o>-</i><i class=o>&gt;</i> [ inv A ]  keys hashing <i class=k>to</i> A\nShard <i class=n>1</i> <i class=o>-</i><i class=o>&gt;</i> [ invocation ]                          <i class=o>+</i><i class=o>-</i><i class=o>&gt;</i> [ inv B ]  keys hashing <i class=k>to</i> B\nShard <i class=n>2</i> <i class=o>-</i><i class=o>&gt;</i> [ invocation ]                          <i class=o>+</i><i class=o>-</i><i class=o>&gt;</i> [ inv C ]\n                                                   <i class=o>+</i><i class=o>-</i><i class=o>&gt;</i> [ inv D ]\nmax concurrency <i class=o>=</i> <i class=n>3</i>                       max concurrency <i class=o>=</i> <i class=n>3</i> x <i class=n>4</i> <i class=o>=</i> <i class=n>12</i>\n<i class=k>order</i> preserved <i class=k>per</i> shard                 <i class=k>order</i> preserved <i class=k>per</i> <i class=k>PARTITION</i> KEY</code></pre></div>\n<p style=\"line-height: 1.75\">When parallelization factor helps and when it does not: it helps when your bottleneck is <strong>function duration</strong> — e.g. each record costs 50 ms of downstream I/O and a single processor cannot keep up with the shard's arrival rate. It does <strong>not</strong> help when the bottleneck is <strong>shard read throughput</strong> (Kinesis gives 2 MB/s and 5 <code>GetRecords</code> calls per second per shard, shared across standard consumers) or when your partition keys are badly skewed — if 80% of traffic uses one partition key, all of it lands on one concurrent processor no matter what the factor is. Hot partition keys are the stream equivalent of a hot DynamoDB partition, and the fix is the same: change the key.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What ordering actually guarantees</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>There is no global ordering.</strong> Two records written a microsecond apart with different partition keys may be processed minutes apart, on different invocations, in either order. Any design that assumes \"the stream gives me the events in the order they happened\" is wrong the moment there is more than one shard.</li>\n<li><strong>Ordering is per shard</strong> with <code>ParallelizationFactor: 1</code>, and <strong>per partition key</strong> with a higher factor. DynamoDB Streams guarantees that all modifications to a <em>single item</em> appear in the correct order — that is the guarantee you can actually build on.</li>\n<li><strong>Resharding breaks naive assumptions.</strong> When a Kinesis shard splits or merges, the parent shard is drained fully before children are read, so per-key ordering survives — but the shard-to-key mapping changes, so anything caching state keyed by shard ID is now wrong.</li>\n<li><strong>Design implication.</strong> If a downstream projection must converge correctly, do not rely on arrival order alone. Carry a monotonic version or sequence number in the record and make writes conditional (<code>if incoming.version &gt; stored.version</code>), so out-of-order or replayed records are idempotently ignored. That turns an ordering requirement into a much weaker, much more achievable one.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">IteratorAge: the metric that matters most</h4>\n<p style=\"line-height: 1.75\"><strong><code>IteratorAge</code></strong> (namespace <code>AWS/Lambda</code>, milliseconds) is the age of the <em>last record in the batch Lambda just processed</em> — in other words, how far behind real time your consumer is. Kinesis publishes an equivalent, <code>GetRecords.IteratorAgeMilliseconds</code>, in <code>AWS/Kinesis</code>. For stream consumers this is the SLI: it directly answers \"how stale is my derived data\".</p>\n<p style=\"line-height: 1.75\">A healthy consumer shows iterator age in the low hundreds of milliseconds to a few seconds, roughly flat. Any <strong>sustained upward slope means you are consuming slower than you are producing</strong>, and because the slope compounds, a consumer that is 5% under-provisioned will eventually hit the retention wall and <strong>lose data permanently</strong> — 24 hours for DynamoDB Streams (not extendable), 24 hours by default for Kinesis (extendable to 7 days at standard rates, and up to 365 days with long-term retention). That data-loss cliff is what makes iterator age urgent rather than merely interesting.</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; Lambda's <code>IteratorAge</code> is emitted per function, but Kinesis emits <code>GetRecords.IteratorAgeMilliseconds</code> with a <code>ShardId</code> dimension when enhanced shard-level metrics are on. A uniform rise across shards is a capacity problem; a rise on exactly one shard is a poison record or a hot key. That one distinction cuts the diagnosis time in half.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The poison-pill problem and the stream error controls</h4>\n<p style=\"line-height: 1.75\">Default stream behaviour is brutal: if the invocation fails, the ESM does not checkpoint and <strong>retries the same batch until it succeeds or the records expire from the stream</strong>. With <code>MaximumRetryAttempts</code> at its default of <code>-1</code> (infinite), one unparseable record blocks its shard for up to 24 hours, during which iterator age climbs linearly and every downstream projection fed by that shard goes stale. This is the single most common stream incident.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong><code>BisectBatchOnFunctionError</code></strong> (default false). On failure, Lambda splits the batch in half and retries each half separately, recursing until it isolates the offending record down to a batch of one. Cost: up to <code>log2(BatchSize)</code> extra rounds of re-processing, so your handler <em>must</em> be idempotent. Benefit: the good records in a failing batch eventually get through instead of being blocked forever, and the retry budget is spent on the actual bad record.</li>\n<li><strong><code>MaximumRetryAttempts</code></strong> (<code>-1</code> = infinite, default; or 0–10000). Setting a finite value means Lambda gives up on the batch, emits to the on-failure destination if configured, and <strong>advances the checkpoint past it</strong>. This is the setting that converts \"shard blocked indefinitely\" into \"one batch skipped\".</li>\n<li><strong><code>MaximumRecordAgeInSeconds</code></strong> (<code>-1</code> = infinite, default; or 60–604800). Lambda discards records older than this bound rather than processing them. Use it when stale data is worse than missing data — real-time dashboards, fraud scoring, alerting. Note it also silently drops a backlog you were hoping to catch up on, so it is dangerous on pipelines that feed a system of record.</li>\n<li><strong><code>DestinationConfig.OnFailure</code></strong>. For Kinesis and DynamoDB Streams this can target SQS, SNS, or S3. The crucial caveat: for <strong>SQS and SNS targets the payload is metadata only</strong> — stream ARN, shard ID, starting and ending sequence numbers, approximate arrival timestamps, batch size, and the error. It does <em>not</em> contain the records. To recover them you re-read the stream at that sequence range, which only works inside the retention window. An <strong>S3 on-failure destination for Kinesis does capture the failed records themselves</strong>, which removes that race and is the better choice when you can use it.</li>\n<li><strong><code>ReportBatchItemFailures</code></strong>. On streams this checkpoints at the <strong>lowest failed sequence number</strong> and replays everything from there, so it salvages the successful <em>prefix</em> of a batch. It is a partial win, not per-record retry — combine it with bisect and a retry cap.</li>\n</ul>\n<p style=\"line-height: 1.75\">The defensible production baseline for a stream consumer is: <code>MaximumRetryAttempts</code> in the range 3–10, <code>MaximumRecordAgeInSeconds</code> set to something well under retention (say 3600 for real-time paths), <code>BisectBatchOnFunctionError: true</code>, an on-failure destination, <code>ReportBatchItemFailures</code> enabled, and an idempotent handler. Then alarm on the on-failure destination receiving anything — because with these settings, failures now become <em>data you must go look at</em> rather than a stalled pipeline.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Starting positions</h4>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">StartingPosition</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Behaviour</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Operational consequence</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">LATEST</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Start at the tip; only records written after the mapping is created</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Zero backfill, instant low iterator age — but any record written during a deploy gap is <strong>silently lost</strong></td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">TRIM_HORIZON</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Start at the oldest record still in retention</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Full replay of up to 24 hours (or more on Kinesis). list-style: disc; line-height: 2\">\n<li><strong><code>KEYS_ONLY</code>.</strong> Just the key attributes. Smallest records, so the largest effective batches, but your consumer must call <code>GetItem</code> to see the data — which reads the <em>current</em> value, not the value at the time of the change, and costs RCUs per record.</li>\n<li><strong><code>NEW_IMAGE</code>.</strong> The item as it exists after the change. The default choice for materializing a read model or search index.</li>\n<li><strong><code>OLD_IMAGE</code>.</strong> The item before the change. Useful for auditing deletes, since <code>NEW_IMAGE</code> is absent on a <code>REMOVE</code> event.</li>\n<li><strong><code>NEW_AND_OLD_IMAGES</code>.</strong> Both. The only view that lets you compute a true delta (\"which fields changed?\") and the right choice for CDC, audit trails, and conditional downstream updates. Costs the most payload, which matters because a 400 KB item doubled is 800 KB per record and you hit the 6 MB batch payload cap in eight records.</li>\n</ul>\n<p style=\"line-height: 1.75\">On <strong>enhanced fan-out</strong> for Kinesis: standard consumers share a shard's 2 MB/s read throughput and 5 <code>GetRecords</code> calls per second. Add a third consumer to a busy stream and all three start seeing <code>ReadProvisionedThroughputExceeded</code> and rising iterator age — each consumer degrades the others. Enhanced fan-out registers a consumer for a <strong>dedicated 2 MB/s per shard</strong> via an HTTP/2 push subscription, which also drops propagation latency from roughly 200 ms (polling) to around 70 ms. It costs extra per consumer-shard-hour plus per GB retrieved, so the rule is: one or two consumers, stay standard; three or more, or latency-sensitive, use enhanced fan-out. On the Lambda ESM you enable it by pointing the mapping at a registered consumer ARN rather than the stream ARN.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario: iterator age climbing steadily in production</h4>\n<p style=\"line-height: 1.75\">A Kinesis stream with <strong>8 shards</strong> feeds a Lambda that writes to OpenSearch. <code>IteratorAge</code> has risen from 2 seconds to <strong>45 minutes over 6 hours</strong> and is still climbing linearly. Retention is 24 hours, so you have roughly 18 hours before data loss. Walk the diagnosis.</p>\n<p style=\"line-height: 1.75\"><strong>Step 1 — is it one shard or all of them?</strong> Enable enhanced shard-level metrics and graph <code>GetRecords.IteratorAgeMilliseconds</code> by <code>ShardId</code>. If one shard is at 45 minutes and the rest are at 2 seconds, this is a poison record or a hot partition key — jump to step 4. Here, assume all 8 shards are climbing uniformly: it is a throughput problem.</p>\n<p style=\"line-height: 1.75\"><strong>Step 2 — do the arithmetic.</strong> Producer rate is 12,000 records/second. Concurrency is 8 shards × <code>ParallelizationFactor: 1</code> = <strong>8</strong>. <code>BatchSize</code> is 100 and <code>Duration</code> p50 is 900 ms. Each processor completes 100 records per 0.9 s ≈ 111 records/s, so total consumption is 8 × 111 ≈ <strong>890 records/second</strong> against 12,000 arriving. You are consuming at 7% of the required rate, which exactly matches a linearly climbing age. The numbers, not intuition, tell you this is a capacity problem of more than an order of magnitude.</p>\n<p style=\"line-height: 1.75\"><strong>Step 3 — confirm it is not throttling or errors.</strong> Check <code>Throttles</code> (if nonzero, the account pool is starving you and you need reserved concurrency of at least shards × factor). Check <code>Errors</code> (if nonzero and repeating on the same sequence numbers, you also have a poison record). Check the producer side for <code>WriteProvisionedThroughputExceeded</code> — if the producers are being throttled too, 8 shards is undersized for the write rate as well.</p>\n<p style=\"line-height: 1.75\"><strong>Step 4 — remediate, fastest lever first.</strong></p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Raise <code>ParallelizationFactor</code> to 10</strong> — takes effect in minutes, no resharding, concurrency goes 8 → 80, consumption goes ~890 → ~8,900 records/s. Requires the handler to be safe with per-partition-key rather than per-shard ordering, and requires 80+ available concurrency (reserve it).</li>\n<li><strong>Fix the 900 ms duration.</strong> OpenSearch writes should use the <code>_bulk</code> API once per batch instead of 100 individual requests. That alone typically takes duration from 900 ms to 80 ms — an 11× throughput gain with no infrastructure change, and it is the change that actually fixes the root cause.
