The handler's job is to parse the event, call a pure domain function, and map the result to a response. The domain function knows nothing about Lambda, nothing about the event shape, and nothing about AWS. Then the interesting logic is testable with ordinary function calls and no mocks at all.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">handler.ts          <i class=o>&lt;</i><i class=c>-- thin: parse event, call domain, map response</i>\n     <i class=o>|</i>                   tested <i class=k>with</i> a <i class=t>REAL</i> recorded event payload\n     v\ndomain<i class=o>/</i>pricing.ts   <i class=o>&lt;</i><i class=c>-- pure: no AWS, no I/O, no event shapes</i>\n     <i class=o>|</i>                   tested exhaustively <i class=k>with</i> plain unit tests\n     v\nadapters<i class=o>/</i>orders.ts  <i class=o>&lt;</i><i class=c>-- SDK calls behind an interface</i>\n                        injected; mocked <i class=k>in</i> unit tests,\n                        <i class=t>REAL</i> <i class=k>in</i> integration tests</code></pre></div>\n<p style=\"line-height: 1.75\"><strong>Dependency injection of SDK clients</strong> is what makes the adapter layer swappable. Construct the client at module scope for connection reuse (it must stay outside the handler so it survives across warm invocations), but let the handler accept an injected repository object with a default. In TypeScript that is a factory function returning the handler; in Python, a default argument or a module-level client the test patches.</p>\n<p style=\"line-height: 1.75\">For mocking the SDK itself, use purpose-built tools: <strong><code>aws-sdk-client-mock</code></strong> for the JavaScript v3 SDK (it intercepts at the client's <code>send</code> and lets you assert on command instances), <strong>moto</strong> for Python (which implements much of the service behaviour in-process rather than just returning canned responses), or <strong>botocore Stubber</strong> when you want strict request validation.</p>\n<p style=\"line-height: 1.75\"><strong>The mocking trap</strong> is worth stating plainly, because it is the most common way serverless test suites become worthless. Every mock encodes an assumption about how AWS behaves, and a test can only ever verify that your code matches <em>your belief</em> about AWS. A mocked <code>PutItem</code> that always succeeds will never tell you that a real <code>ConditionExpression</code> is malformed, that the item exceeds 400 KB, that the partition is throttling, or that the execution role lacks <code>dynamodb:PutItem</code>. A mocked SQS send will not reveal that the message exceeds 256 KB. A mocked Kinesis <code>PutRecords</code> will not surface partial failures in the response, which is the failure mode that actually breaks stream producers. The rule: <strong>mock at the boundary of code you own, and test the AWS boundary against real AWS.</strong> Heavy mocking produces a green suite and a broken deployment.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Integration testing: the ephemeral stack</h4>\n<p style=\"line-height: 1.75\">The highest-return investment in serverless testing is making it trivially cheap to deploy a <strong>complete, isolated copy of the stack</strong> — per developer, and per pull request — run tests against it, and tear it down. Serverless economics make this viable in a way it never was with servers: Lambda, DynamoDB on-demand, SQS and EventBridge cost essentially nothing when idle, so twenty ephemeral stacks cost less than one idle EC2 instance.</p>\n<p style=\"line-height: 1.75\">The mechanics: parameterise every resource name with a stack suffix, deploy with <code>sam deploy --stack-name orders-pr-1234</code> or <code>cdk deploy --context env=pr-1234</code>, read the real resource names from <strong>stack outputs</strong> rather than hardcoding them, run the test suite against those, and delete the stack in a CI job that runs even on failure. Add a scheduled reaper that deletes stacks older than a day, because pipelines get cancelled and orphaned stacks accumulate.</p>\n<p style=\"line-height: 1.75\">What this catches that nothing else can: <strong>IAM permission gaps</strong> (by far the most common serverless production failure, and structurally invisible to mocks); event source mapping misconfiguration; queue visibility timeouts that are too short; <strong>packaging errors</strong> such as a native binary built for the wrong platform, which by definition cannot be caught by any test that does not run the real artifact in the real runtime; environment variables that were never set; VPC and security group problems; resource policies; and real service semantics like DynamoDB's eventual consistency on GSI reads.</p>\n<p style=\"line-height: 1.75\">The trade-offs are honest ones. Integration tests are slower (minutes, not milliseconds), they can be flaky because distributed systems are eventually consistent, and they cost a little money. Manage flakiness with <strong>polling assertions rather than fixed sleeps</strong> — retry the assertion until it passes or a timeout expires — because a <code>sleep(5)</code> is simultaneously too slow for the happy path and too short for the tail.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Local emulation: useful, and precisely bounded</h4>\n<p style=\"line-height: 1.75\"><strong>SAM local</strong> runs your function in a Docker container built from the official Lambda runtime images. <code>sam local invoke MyFunction --event events/order.json</code> executes one invocation; <code>sam local start-api</code> stands up a local HTTP endpoint that emulates API Gateway's event shape; <code>sam local start-lambda</code> exposes a local Invoke endpoint you can point the SDK at. <strong>LocalStack</strong> goes further and emulates the services themselves — S3, SQS, DynamoDB, EventBridge and many more — so an entire local environment is possible.</p>\n<p style=\"line-height: 1.75\">Both are genuinely valuable for one thing: the <strong>fast inner loop</strong>. Change a line, invoke, see the result in two seconds instead of a two-minute deploy. That alone justifies them.</p>\n<p style=\"line-height: 1.75\">The fidelity gaps are what you must be able to enumerate in an interview:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>IAM is not enforced.</strong> Locally your code runs with your developer credentials or none at all. The single largest category of serverless production failure is invisible in local testing.</li>\n<li><strong>No throttling, quotas or backpressure.</strong> No DynamoDB <code>ProvisionedThroughputExceededException</code>, no Lambda concurrency limit, no API Gateway rate limit. Every retry path stays untested.</li>\n<li><strong>Ordering and eventual consistency are wrong.</strong> Emulators tend to be strongly consistent and locally ordered. Real DynamoDB GSIs lag; real S3 and real streams reorder.</li>\n<li><strong>Concurrency and lifecycle are wrong.</strong> <code>sam local invoke</code> starts a fresh container each time, so you can never observe warm-start behaviour, module-scope caching bugs, or state leaking across invocations — a genuinely common production bug class.</li>\n<li><strong>Performance numbers are meaningless.</strong> Local CPU is not Lambda CPU, and Lambda's CPU scales with memory. Never tune memory locally.</li>\n<li><strong>Emulator drift.</strong> LocalStack reimplements AWS; the reimplementation is always somewhat behind, and its bugs are not AWS's bugs. Time spent debugging an emulator discrepancy is pure waste.</li>\n</ul>\n<p style=\"line-height: 1.75\">The defensible position: <strong>use emulation for iteration speed, never as a gate.</strong> Nothing merges on the strength of a local test alone.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Testing event-driven paths</h4>\n<p style=\"line-height: 1.75\"><strong>Use real event shapes.</strong> Hand-written JSON that approximates an S3 event is a trap: you will invent <code>event.bucket</code> instead of <code>event.Records[0].s3.bucket.name</code>, your tests will pass against your invention, and production will throw a <code>KeyError</code>. Generate payloads with <strong><code>sam local generate-event</code></strong> (for example <code>sam local generate-event s3 put</code> or <code>sqs receive-message</code>), or better, <strong>capture a real event from CloudWatch Logs</strong> in a dev environment and commit it as a fixture. Typed event libraries help enormously: Powertools' data classes and parser (Pydantic models) in Python, or <code>@types/aws-lambda</code> in TypeScript, turn a wrong field name into a compile-time or validation error.</p>\n<p style=\"line-height: 1.75\"><strong>Assert on side effects, not return values.</strong> An asynchronously-invoked function's return value goes nowhere. The meaningful assertions are downstream: an item appeared in DynamoDB, a message landed on the next queue, an event was published to the bus, an object was written to S3. For EventBridge specifically, a neat technique is adding a test-only rule that forwards matching events to an SQS queue the test polls — giving you an observable tap on an otherwise fire-and-forget bus.</p>\n<p style=\"line-height: 1.75\"><strong>Test the failure paths, because those are the ones that break.</strong> Happy paths get exercised constantly in production; the retry and dead-letter paths run only during incidents, which is the worst time to discover they were misconfigured. Concretely, write tests that:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li>Send a message that deterministically fails, and assert it lands in the <strong>DLQ or OnFailure destination</strong> after the expected number of attempts. This validates <code>maxReceiveCount</code>, the destination ARN, and — critically — the execution role's permission to write to the destination, which fails silently in production.</li>\n<li>Send a batch where one record fails and assert, via <code>ReportBatchItemFailures</code>, that <strong>only that record is redelivered</strong> and the others are not reprocessed. This is the test that catches the batch-failure bug that double-charges customers.</li>\n<li>Force a timeout (a short <code>Timeout</code> in the test stack) and assert the system's behaviour is what you claimed.</li>\n<li>Assert the <strong>attempt count</strong>, not just eventual arrival — a test that passes because the event arrived after 30 retries when you configured 2 is a failing test that looks green.</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>Test idempotency explicitly by replaying duplicates.</strong> This deserves its own bullet because it is nearly always omitted. Invoke the handler twice with the identical event and assert that the downstream side effect happened <strong>exactly once</strong> and that both invocations returned the same response. Then do the harder version: invoke twice <em>concurrently</em> and assert the same, which is what actually exercises the conditional-write race rather than the sequential path. If your suite never replays a duplicate, you do not know whether you are idempotent — and since every event source is at-least-once, you will find out in production.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Contract testing and load testing</h4>\n<p style=\"line-height: 1.75\">In an event-driven system, services are coupled by <strong>event schemas</strong> rather than API calls, and that coupling is invisible to every test that exercises one service in isolation. A producer adding a field is safe; renaming or removing one silently breaks consumers, and the break appears asynchronously, in a different team's function, possibly days later. <strong>Contract testing</strong> makes the coupling explicit: consumers publish the shape they depend on, and the producer's pipeline fails if a change would violate it. Tools include Pact for consumer-driven contracts, and on AWS the <strong>EventBridge Schema Registry</strong> with schema discovery, which can infer schemas from live traffic and generate typed bindings — with the version number itself acting as a change signal.</p>\n<p style=\"line-height: 1.75\"><strong>Load testing</strong> targets behaviour that only appears under concurrency, and is therefore untestable at any lower layer: whether you hit the account concurrency limit (1,000 by default per region, raisable by request); whether scaling causes a cold start storm that breaches latency SLOs; whether a downstream RDS instance exhausts its connections because a thousand concurrent environments each opened one (the problem RDS Proxy exists to solve); whether reserved concurrency correctly protects a fragile dependency; and whether provisioned concurrency is sized correctly. Run it against a dedicated stack in a <strong>separate account</strong>, because the concurrency quota is per account per region and a load test in a shared account will throttle production. Artillery and k6 are common; assert on <code>ConcurrentExecutions</code>, <code>Throttles</code> and <code>Duration</code> p99, not just throughput.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario — test strategy for a three-function pipeline</h4>\n<p style=\"line-height: 1.75\"><em>\"You have an order pipeline: Function A is triggered by API Gateway and writes an order to DynamoDB; Function B consumes the DynamoDB stream, validates and charges a payment provider, and publishes an order-paid event to EventBridge; Function C consumes that event and sends a confirmation email via SES. Design a pragmatic test strategy.\"</em></p>\n<p style=\"line-height: 1.75\"><strong>Layer 1 — unit tests, fast and plentiful.</strong> Extract the domain logic from all three handlers: order validation and total calculation from A, the payment decision and error classification from B, the email template rendering from C. These are pure functions with no AWS in them; test them exhaustively, including boundary cases, in milliseconds. Then a thin handler test per function using a <strong>committed real event fixture</strong> — an API Gateway proxy event, a DynamoDB Streams record, an EventBridge event — captured from a dev environment rather than hand-written, with the SDK mocked via <code>aws-sdk-client-mock</code> or moto. These assert event parsing and error mapping only. Target: the whole layer runs in under ten seconds on every commit.</p>\n<p style=\"line-height: 1.75\"><strong>Layer 2 — integration in an ephemeral per-PR stack.</strong> This is where the budget goes. CI deploys <code>orders-pr-1234</code> with the payment provider pointed at its sandbox and SES in the mailbox simulator, reads resource names from stack outputs, and runs: (1) a happy path that POSTs an order to the real API Gateway URL and polls until a confirmation lands in the SES simulator, which validates the entire chain including every IAM policy, the stream event source mapping, the EventBridge rule pattern, and the packaging; (2) per-hop assertions so a failure localises to a function instead of just saying \"no email\"; (3) a <strong>duplicate replay test</strong> — invoke B twice with the identical stream record and assert the payment sandbox received exactly one charge and both invocations returned the same payment ID, plus a concurrent variant to exercise the conditional-write race; (4) a <strong>failure path test</strong> — an order that deterministically fails in B, asserting it reaches the OnFailure destination after exactly the configured number of attempts, which is the only way to prove the destination ARN and its IAM permission are right; (5) a <strong>partial batch test</strong> — a stream batch where record 3 fails, asserting records 1, 2, 4 and 5 are not reprocessed, because that bug is the one that double-charges customers.</p>\n<p style=\"line-height: 1.75\"><strong>Layer 3 — contract tests.</strong> The <code>order-paid</code> event is the interface between B and C, owned by two different teams. Register its schema in the EventBridge Schema Registry, generate typed bindings for C, and add a pipeline check that fails B's build on a breaking schema change. Without this, B renaming a field ships green and breaks C asynchronously and invisibly.</p>\n<p style=\"line-height: 1.75\"><strong>Layer 4 — load, run on a schedule rather than per commit.</strong> In a dedicated account, drive 500 orders per second at the API for ten minutes. Watch <code>ConcurrentExecutions</code> against the account limit, <code>Throttles</code> on all three functions, <code>IteratorAge</code> on the DynamoDB stream (the leading indicator that B cannot keep up and is about to lose records), and whether the payment sandbox's rate limit triggers retry storms. This is where you discover that B needs reserved concurrency to protect the payment provider.</p>\n<p style=\"line-height: 1.75\"><strong>Layer 5 — production verification.</strong> A CodeDeploy <code>PreTraffic</code> hook that invokes the new version with a synthetic order before any customer traffic reaches it, plus a CloudWatch Synthetics canary running the full path every five minutes against production. Testing does not stop at deployment; in an event-driven system, continuous synthetic verification is what tells you the pipeline is still connected.</p>\n<p style=\"line-height: 1.75\"><strong>What I would deliberately skip.</strong> LocalStack as a CI gate — it would emulate three services, none of them perfectly, and its failures would not be production's failures. Chasing 100% unit coverage on the handler wiring, which buys almost nothing given the integration layer covers it for real. And end-to-end tests for every business permutation; keep end-to-end for a small number of critical paths and push permutations down to the fast unit layer, or the suite becomes slow, flaky, and eventually ignored.</p>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"In serverless, most of the behaviour lives in the wiring — IAM, event source mappings, retry and destination config — not in my code, so the pyramid gets a much fatter integration layer.
