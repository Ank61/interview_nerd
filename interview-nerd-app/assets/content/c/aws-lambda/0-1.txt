For a synchronous invoke the caller receives it directly. For an asynchronous invoke nobody ever sees it — the return value is simply discarded — which surprises people constantly. For HTTP integrations the return value must match the shape the integration expects (for example an object with <code>statusCode</code> and <code>body</code> for API Gateway proxy integration and for ALB).</li>\n<li><strong>Throw an error (or reject the promise, or raise an exception).</strong> The runtime catches it and reports a <strong>function error</strong> to the Lambda service. The response body contains <code>errorType</code>, <code>errorMessage</code>, and a stack trace, the <code>Errors</code> CloudWatch metric increments, and — crucially — this is what triggers retry behaviour in asynchronous and poll-based models. Swallowing an exception and returning a cheerful 200 means Lambda believes the invocation succeeded and will never retry it.</li>\n</ul>\n<p style=\"line-height: 1.75\">That last point is the heart of many interview questions. <strong>Throwing is how you signal failure to the platform.</strong> If you catch everything and return normally, you have opted out of every retry and dead-letter mechanism Lambda offers. Conversely, if a message on an SQS batch is permanently unprocessable, throwing repeatedly will just retry it forever until the queue's redrive policy sends it to a DLQ — so error handling has to be deliberate, not reflexive.</p>\n<p style=\"line-height: 1.75\">Note also that a <strong>timeout is not an exception you can catch</strong>. When the configured timeout elapses, Lambda terminates the execution environment; your <code>finally</code> block does not run and no graceful shutdown occurs. This is why <code>getRemainingTimeInMillis()</code> exists: check it before starting a long operation and return early if there is not enough budget.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Async/Await vs the Legacy Callback Style in Node.js</h4>\n<p style=\"line-height: 1.75\">Node.js handlers come in two flavours. The <strong>modern style</strong> is an <code>async</code> function taking <code>(event, context)</code>; you return a value to succeed and throw to fail, and Lambda awaits the returned promise. The <strong>legacy style</strong> is a non-async function taking <code>(event, context, callback)</code>, where you call <code>callback(null, result)</code> on success and <code>callback(error)</code> on failure.</p>\n<p style=\"line-height: 1.75\">Use async/await for all new code. The most damaging beginner bug in this area is <strong>mixing the two</strong>: writing an <code>async</code> handler that also accepts and calls <code>callback</code>, or — far more common — writing an async handler that kicks off a promise without awaiting it. Lambda <strong>freezes the execution environment the moment the handler's promise settles</strong>. Any un-awaited work is suspended mid-flight; it may resume during a later invocation of the same environment, or may never complete at all. Symptoms are maddening: writes that sometimes land and sometimes do not, logs that appear attached to the wrong request. The rule is simple and worth stating in an interview: <strong>await every promise whose completion you care about before returning.</strong></p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Inside the Handler vs Outside the Handler — the Init Phase</h4>\n<p style=\"line-height: 1.75\">This distinction matters more than almost anything else in the Lambda programming model.
