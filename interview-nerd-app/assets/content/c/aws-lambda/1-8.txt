On REST APIs there are two types:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>TOKEN.</strong> Identity comes from a single header, conventionally <code>Authorization</code>. The event is minimal: <code>{ type: \"TOKEN\", authorizationToken, methodArn }</code>. The cache key is the token value.</li>\n<li><strong>REQUEST.</strong> Identity can come from any combination of headers, query strings, stage variables, and request context; the event looks much like a proxy integration event. The cache key is the concatenation of all configured identity sources. HTTP APIs support only this type.</li>\n</ul>\n<p style=\"line-height: 1.75\">A REST Lambda authorizer must return an <strong>IAM policy document</strong>:</p>\n<div class=\"code\"><div class=\"code-head\"><span>python</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">{\n  <i class=s>&quot;principalId&quot;</i>: <i class=s>&quot;user-12345&quot;</i>,\n  <i class=s>&quot;policyDocument&quot;</i>: {\n    <i class=s>&quot;Version&quot;</i>: <i class=s>&quot;2012-10-17&quot;</i>,\n    <i class=s>&quot;Statement&quot;</i>: [{\n      <i class=s>&quot;Action&quot;</i>: <i class=s>&quot;execute-api:Invoke&quot;</i>,\n      <i class=s>&quot;Effect&quot;</i>: <i class=s>&quot;Allow&quot;</i>,                     &lt;- <i class=k>or</i> <i class=s>&quot;Deny&quot;</i>\n      <i class=s>&quot;Resource&quot;</i>: <i class=s>&quot;arn:aws:execute-api:us-east-1:111122223333:abc123/prod/GET/orders/*&quot;</i>\n    }]\n  },\n  <i class=s>&quot;context&quot;</i>: { <i class=s>&quot;tenantId&quot;</i>: <i class=s>&quot;acme&quot;</i>, <i class=s>&quot;plan&quot;</i>: <i class=s>&quot;gold&quot;</i> },   &lt;- string/number/<i class=b>bool</i> ONLY, no objects\n  <i class=s>&quot;usageIdentifierKey&quot;</i>: <i class=s>&quot;apikey-for-usage-plan&quot;</i>        &lt;- optional, REST + usage plans\n}</code></pre></div>\n<p style=\"line-height: 1.75\">The <code>context</code> map is forwarded to your integration at <code>event.requestContext.authorizer</code> (REST/1.0) or <code>event.requestContext.authorizer.lambda</code> (HTTP/2.0) — that is how you pass tenant ID or scopes downstream without re-parsing the token. It must be flat: nested objects are dropped, so serialise with <code>JSON.stringify</code> if you need structure. Throwing the literal string <code>\"Unauthorized\"</code> produces a 401; returning an explicit <code>Deny</code> produces a 403. HTTP API authorizers can instead use <strong>simple responses</strong> (<code>enableSimpleResponses: true</code>) and return <code>{ isAuthorized: true, context: {...} }</code>, which is far easier to write correctly but gives up per-resource granularity.</p>\n<p style=\"line-height: 1.75\"><strong>Authorizer result caching and its security implications</strong> is the part interviewers push on. The TTL defaults to <strong>300 seconds</strong> and can be 0–3600. Caching is valuable — it removes an extra Lambda invocation (and cold start) from most requests — but it has sharp edges:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Revocation is delayed by up to the TTL.</strong> Disable a user, revoke a token, downgrade a role — the cached Allow keeps working for up to five minutes. If your security model requires immediate revocation, the TTL must be 0 or you need a fast denylist check that is not cached.</li>\n<li><strong>Over-broad <code>Resource</code> is a real privilege escalation.</strong> The policy is cached against the identity source, and API Gateway reuses it for <em>every</em> request matching that key. If your authorizer takes the shortcut of returning <code>Resource: \"arn:aws:execute-api:region:acct:apiId/stage/*/*\"</code>, then a token that legitimately unlocked <code>GET /orders</code> now unlocks <code>DELETE /admin/users</code> for the whole TTL. The safe patterns are either to return a correctly scoped wildcard that matches the caller's true entitlements, or to set TTL to 0 and return the exact <code>methodArn</code>. Returning the exact <code>methodArn</code> <em>with</em> caching enabled is the worst of both worlds: the first request's ARN gets cached and reused for different routes, producing baffling intermittent 403s.</li>\n<li><strong>The cache key must include everything that affects the decision.</strong> A REQUEST authorizer that reads a <code>X-Tenant-Id</code> header but does not list it as an identity source will serve one tenant's decision to another.</li>\n</ul>\n<p style=\"line-height: 1.75\">The managed alternatives avoid all of this where they fit. <strong>Cognito user pool authorizers</strong> (REST) and <strong>JWT authorizers</strong> (HTTP API) validate the token signature, issuer, audience and expiry natively — no Lambda, no cold start, no extra cost, and scope checks via <code>authorizationScopes</code>. Use them whenever your identity provider is OIDC-compliant; drop to a Lambda authorizer only for legacy tokens, opaque tokens needing introspection, mTLS-derived identity, or authorization logic that needs a database lookup. <strong>IAM authorization</strong> (<code>AWS_IAM</code>) requires callers to SigV4-sign requests and is the right choice for service-to-service and internal calls, because it reuses existing IAM roles and needs no token infrastructure at all.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Timeout math end to end</h4>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">client timeout (e.g. <i class=n>35</i>s)\n<i class=o>|</i><i class=c>----------------------------------------------------|</i>\n   API Gateway integration timeout (<i class=n>29</i>s REST <i class=o>/</i> <i class=n>30</i>s HTTP)\n   <i class=o>|</i><i class=c>-----------------------------------------|</i>\n      Lambda <i class=k>function</i> timeout  (<i class=k>set</i> <i class=k>to</i> <i class=n>25</i>s)\n      <i class=o>|</i><i class=c>-------------------------------|</i>\n         downstream SDK timeout <i class=o>+</i> retries (<i class=k>set</i> <i class=k>to</i> <i class=o>~</i><i class=n>8</i>s x <i class=n>2</i> attempts)\n         <i class=o>|</i><i class=c>------------|</i>\n\nRULE: <i class=k>each</i> <i class=k>inner</i> budget must be STRICTLY SMALLER than the <i class=k>one</i> containing it.</code></pre></div>\n<p style=\"line-height: 1.75\">Set the <strong>function timeout below the gateway timeout</strong>. If Lambda's timeout is 60 s and the gateway's is 29 s, the client gets a <strong>504 at 29 seconds while the function keeps running for another 31 seconds</strong> — still consuming a concurrency slot, still billing, and quite possibly still writing to the database, which means a client retry can now double-apply a side effect. Setting the function to 25 s means the function fails first, you get a real Lambda <code>Errors</code> data point and a log line with a stack trace, and the request stops consuming resources.</p>\n<p style=\"line-height: 1.75\">Push the same discipline one level down: your AWS SDK and HTTP client timeouts (plus retry count) must fit inside the function timeout, or a downstream stall consumes your whole budget in one attempt and you never get to your own error handling. And one level up: the client's timeout should exceed the gateway's, otherwise the client gives up and retries while the original request is still in flight. For work that genuinely cannot fit in 29 seconds, do not fight the limit — return <strong>202 Accepted</strong> with a job ID, do the work asynchronously (SQS, Step Functions), and let the client poll or receive a WebSocket/webhook notification. The REST API maximum integration timeout is an adjustable account quota, so you <em>can</em> raise it above 29 seconds, but holding an HTTP connection open for minutes is a bad architecture regardless of whether AWS permits it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Throttling, usage plans, CORS, and payload limits</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Gateway throttling protects Lambda concurrency.</strong> There is an account-level default of 10,000 requests per second with a 5,000 burst per region, and you can set stage-level and per-route (or per-method) throttles below that. This is your outermost defence: a request rejected at the gateway with a 429 costs no Lambda invocation, no concurrency, and no downstream load.
