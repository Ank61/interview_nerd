{"title":"Deployment and Infrastructure as Code — SAM, CDK, CloudFormation, and Containers","tags":["lambda","iac","sam","cdk"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">A Lambda function edited in the console is a production system with no source of truth. There is no diff, no review, no history beyond the code snapshot in $LATEST, no way to recreate it in another region or account, and no way to answer \"what changed?\" when it breaks at 3am. The console editor is a legitimate tool for <strong>experimentation and reading</strong>, and nothing else. Beyond that, <strong>everything about a function — code, memory, timeout, environment, IAM role, event sources, alarms — belongs in version-controlled infrastructure as code</strong>, deployed by a pipeline. This is not dogma; it is the only way the versioning, aliasing and canary machinery from the previous topic can function at all, since all of it presumes an artifact that was built somewhere reproducible.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The IaC options, honestly compared</h4>\n<p style=\"line-height: 1.75\"><strong>Raw CloudFormation.</strong> The substrate everything else compiles down to. You declare <code>AWS::Lambda::Function</code> with a <code>Code</code> property pointing at <code>S3Bucket</code> / <code>S3Key</code> / <code>S3ObjectVersion</code> (or <code>ImageUri</code> for a container), plus <code>AWS::Lambda::Permission</code>, <code>AWS::IAM::Role</code>, <code>AWS::Lambda::EventSourceMapping</code>, <code>AWS::Lambda::Version</code>, <code>AWS::Lambda::Alias</code> and a log group, by hand. It is verbose — a single function with an API trigger and sane defaults is comfortably 150 lines — and it cannot package your code; the artifact must already be in S3. Its virtues are that it is the lowest common denominator, has no extra toolchain, and is what you will be reading when you debug anything else.</p>\n<p style=\"line-height: 1.75\"><strong>AWS SAM.</strong> A CloudFormation <em>transform</em>: <code>Transform: AWS::Serverless-2016-10-31</code> at the top of the template tells CloudFormation to expand SAM's simplified resource types into standard resources at deploy time. <code>AWS::Serverless::Function</code> collapses that 150-line block into roughly 12, generating the role, the log group, the permissions, the versions and aliases, and the API Gateway plumbing. The CLI matters as much as the transform: <code>sam build</code> installs dependencies and stages the artifact (with <code>--use-container</code> to build inside the official Lambda build image), <code>sam deploy --guided</code> walks you through parameters and writes them to <code>samconfig.toml</code> so later deploys are one command, <code>sam local invoke</code> and <code>sam local start-api</code> run the function in Docker, and <code>sam logs</code> and <code>sam sync</code> shorten the iteration loop. SAM fits teams whose stack is predominantly serverless and who want declarative templates that a non-author can read.</p>\n<p style=\"line-height: 1.75\"><strong>AWS CDK.</strong> You write TypeScript, Python, Java, Go or C#; <code>cdk synth</code> produces a CloudFormation template; <code>cdk deploy</code> applies it. The unit of reuse is the <strong>construct</strong>, in three layers: <strong>L1</strong> (<code>CfnFunction</code>) is a mechanical one-to-one mapping of the CloudFormation resource; <strong>L2</strong> (<code>lambda.Function</code>) adds sane defaults and, crucially, <strong>automatic least-privilege IAM</strong> — <code>table.grantReadWriteData(fn)</code> generates exactly the policy needed, which is the single biggest practical advantage of CDK over hand-written templates; <strong>L3</strong> patterns compose several resources into one opinionated unit. CDK also has strong bundling: <code>NodejsFunction</code> runs <strong>esbuild</strong> to transpile and tree-shake your TypeScript, and <code>PythonFunction</code> installs dependencies in Docker. The cost is real: you now have a programming language in your infrastructure, which means abstractions that are hard to review, <code>cdk diff</code> output that can be surprising, and a deployment whose result depends on which version of the CDK library was installed.</p>\n<p style=\"line-height: 1.75\"><strong>Terraform.</strong> Genuinely the right answer when Lambda is a minority of your estate and the organisation already runs Terraform everywhere. HCL, a real state file, excellent multi-cloud and multi-provider support, and <code>terraform plan</code> is a better change-preview than <code>cdk diff</code> or a CloudFormation change set. The friction is that it has no native packaging story (you bring your own zip, usually via an archive data source or an external build), the serverless ecosystem's examples are mostly SAM or CDK, and you own the state backend.</p>\n<p style=\"line-height: 1.75\"><strong>Serverless Framework.</strong> Historically the fastest path to a deployed function and still very productive, with a large plugin ecosystem. It generates CloudFormation under the hood. The considerations now are licensing and commercial direction, and a plugin ecosystem of uneven maintenance quality.</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; A well-run Terraform pipeline beats a badly-run CDK one every time. Choose CDK when you have many similar services and want to encode standards as constructs; choose SAM when the estate is serverless and you value a template a reviewer can read at a glance; choose Terraform when Lambda is one resource type among many hundreds you already manage.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Packaging: where deployments actually break</h4>\n<p style=\"line-height: 1.75\">Lambda runs on <strong>Amazon Linux</strong> on either <strong>x86_64</strong> or <strong>arm64 (Graviton2)</strong>. Your deployment package must contain dependencies compiled for that exact combination. Pure-Python and pure-JavaScript packages do not care. Anything with a compiled extension — numpy, pandas, psycopg2, Pillow, cryptography, bcrypt, sharp, grpc, any node-gyp module — cares absolutely.</p>\n<p style=\"line-height: 1.75\"><strong>The classic failure.</strong> A developer runs <code>pip install -r requirements.txt -t ./package</code> on an Apple Silicon Mac. pip resolves wheels for macOS on arm64. The zip deploys cleanly, the function invokes, and Lambda reports <code>Unable to import module 'lambda_function': No module named 'pandas._libs...'</code> or, more diagnostically, <code>invalid ELF header</code> — because the <code>.so</code> file in the package is a Mach-O dylib, not a Linux ELF object. Nothing about the local test caught it, because locally the correct binary was present. The Node equivalent is <code>Error: Cannot find module</code> pointing at a <code>.node</code> native addon, or a sharp/bcrypt binary built for darwin-arm64.</p>\n<p style=\"line-height: 1.75\">The fixes, in order of robustness:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Build in a container that matches the runtime.</strong> <code>sam build --use-container</code> uses the official AWS build images; CDK's <code>PythonFunction</code> and <code>NodejsFunction</code> bundle in Docker by default. This is the default recommendation because it removes the class of problem rather than patching one instance.</li>\n<li><strong>Force the target platform explicitly.</strong> For Python: <code>pip install --platform manylinux2014_x86_64 --implementation cp --python-version 3.12 --only-binary=:all: --target ./package -r requirements.txt</code> (use <code>manylinux2014_aarch64</code> for arm64). <code>--only-binary=:all:</code> is the important flag — it makes pip <em>fail</em> rather than silently falling back to building from source against your local toolchain.</li>\n<li><strong>Match the architecture deliberately.</strong> The function's <code>Architectures</code> property must match what you built. arm64 is roughly 20% cheaper per GB-second and often faster, but every native dependency must have an aarch64 wheel or build.</li>\n<li><strong>Build in CI on Linux.</strong> A Linux CI runner eliminates the macOS mismatch for x86_64, though not the arm64/x86_64 mismatch.</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>Bundlers for Node.js</strong> solve a different problem: package size and cold start. <code>node_modules</code> with the full AWS SDK and transitive dependencies routinely reaches tens of megabytes; <strong>esbuild</strong> or <code>webpack</code> tree-shakes that to a few hundred kilobytes, and a smaller package means faster environment initialisation. Two Lambda-specific rules: mark the AWS SDK as <code>external</code> so you do not bundle a copy of what the runtime already provides (v3 modular clients are present in the Node.js 18+ managed runtimes), and <strong>enable source maps</strong> plus <code>NODE_OPTIONS=--enable-source-maps</code>, or every production stack trace will point at a single minified line and be useless.</p>\n<p style=\"line-height: 1.75\">Know the size quotas precisely: <strong>50 MB zipped</strong> for a direct upload through the API, <strong>250 MB unzipped</strong> for the function's code plus all attached layers, <strong>up to 5 layers</strong>, and <strong>10 GB</strong> for a container image. Deploying from S3 does not raise the 250 MB unzipped ceiling; it only raises the upload limit.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Container images and ECR: the tag trap</h4>\n<p style=\"line-height: 1.75\">Container image packaging suits large dependency trees (ML libraries), teams with existing Docker tooling, and anything that needs more than 250 MB. You build <code>FROM public.ecr.aws/lambda/python:3.12</code> (or use the <strong>Runtime Interface Client</strong> to make an arbitrary base image Lambda-compatible), push to <strong>ECR in the same region as the function</strong>, and set <code>ImageUri</code>.</p>\n<p style=\"line-height: 1.75\"><strong>The trap that catches nearly everyone:</strong> Lambda resolves an image tag to an immutable <strong>digest at the moment you call <code>UpdateFunctionCode</code></strong>, and pins to that digest. Pushing a new image to the <em>same tag</em> afterwards does <strong>nothing</strong> — the function keeps running the old digest, forever, with no error and no indication in the console that anything is stale. Teams lose hours to \"I deployed but my change isn't there.\" Two correct responses: reference images by <strong>digest</strong> (<code>repo@sha256:...</code>) rather than tag, which is also what makes CloudFormation detect a change and is required for reproducible promotion; or tag every build immutably with the commit SHA and never reuse a tag. Enabling <strong>ECR tag immutability</strong> on the repository enforces the latter at the registry.</p>\n<p style=\"line-height: 1.75\">Other container specifics: the image architecture must match the function's <code>Architectures</code> (build with <code>docker buildx --platform linux/arm64</code> for Graviton); cross-account pulls need an ECR repository policy allowing <code>lambda.amazonaws.com</code>; a deleted image in ECR breaks the function's ability to scale out, so apply lifecycle policies carefully; and cold starts are competitive with zip thanks to Lambda's layer caching and lazy loading, but a 9 GB image still initialises more slowly than a 5 MB zip.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; The immediate damage is invisible; the damage arrives at the next deploy, when CloudFormation silently reverts the console change and reintroduces the incident. Detect it with <code>aws cloudformation detect-stack-drift</code> and <code>describe-stack-resource-drifts</code>, run on a schedule and alarmed on.</p>\n<p style=\"line-height: 1.75\">The controls that actually work are preventative, not detective: deny console mutation in production through IAM or an SCP (allow <code>lambda:Get*</code> and <code>List*</code>, deny <code>lambda:UpdateFunctionConfiguration</code> and <code>UpdateFunctionCode</code> for human principals), require all changes through the pipeline, and — importantly — <strong>make the emergency path itself a code path</strong>. If the only way to raise a timeout at 3am is the console, people will use the console. Provide a parameterised fast-track pipeline instead. Where a console change is genuinely unavoidable, the follow-up work item is to reconcile it into the template the same day, not eventually.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario — \"it works locally but fails in Lambda\"</h4>\n<p style=\"line-height: 1.75\"><em>\"A Python function using pandas works perfectly on the developer's MacBook and in unit tests. Deployed to Lambda it fails immediately with <code>Runtime.ImportModuleError: Unable to import module 'handler': No module named 'pandas._libs.interval'</code>. Diagnose it.\"</em></p>\n<p style=\"line-height: 1.75\"><strong>Read the error precisely first.</strong> The module <em>is</em> in the package — this is not a missing-dependency error, it is a <strong>native extension</strong> error. <code>pandas._libs.interval</code> is a compiled C extension shipped as a <code>.so</code>. Python can see the parent package but cannot load the binary. A closely related variant of the same error is <code>invalid ELF header</code>, which states the cause outright.</p>\n<p style=\"line-height: 1.75\"><strong>Confirm it in thirty seconds.</strong> Unzip the deployment package and run <code>file</code> over the extension: if it reports <em>Mach-O 64-bit dynamically linked shared library arm64</em>, you have your answer — that is a macOS binary. Lambda needs <em>ELF 64-bit LSB shared object</em>. If it says ELF but <em>ARM aarch64</em> while the function is configured <code>x86_64</code>, the architecture is mismatched instead.</p>\n<p style=\"line-height: 1.75\"><strong>Root cause.</strong> <code>pip install -t ./package</code> resolves wheels for the <em>build machine's</em> platform. On Apple Silicon that is macosx arm64. The zip is structurally valid, uploads fine, and the failure only appears at import time inside the Lambda execution environment. Unit tests pass because they run against the developer's own correct binaries, never the package contents. <strong>The build is the bug; the code is fine.</strong></p>\n<p style=\"line-height: 1.75\"><strong>Fixes, and what I would actually do.</strong> Immediate: <code>sam build --use-container</code>, which builds inside the official <code>public.ecr.aws/sam/build-python3.12</code> image so the wheels match the runtime. Alternative when Docker is unavailable: force the target explicitly with <code>--platform manylinux2014_x86_64 --only-binary=:all:</code>, where <code>--only-binary</code> is essential because it makes pip fail loudly rather than quietly compiling from source with the local toolchain. For pandas and numpy specifically, the AWS-managed <strong>AWSSDKPandas</strong> layer is a maintained, correctly-built option that also keeps you under the 250 MB unzipped limit. If the dependency tree is genuinely large, switch to a <strong>container image</strong>, where the build environment is the runtime environment by construction and the ceiling is 10 GB.</p>\n<p style=\"line-height: 1.75\"><strong>Prevent the class, not the instance.</strong> Builds must never happen on developer laptops — do them in CI on Linux, or in the official build container. Pin <code>Architectures</code> explicitly in the template and build for that exact target. Add a CI step that runs <code>file</code> across every <code>.so</code> in the package and fails the build on anything that is not an ELF object of the expected architecture.
