It is a micro-VM (Firecracker) running the Lambda platform, a runtime, your function code, and — if you add them — <strong>extensions</strong>: additional processes that live inside the same environment, share its CPU, memory, and network namespace, and participate in its lifecycle. Extensions are the officially supported way to bolt cross-cutting concerns (secrets caching, telemetry shipping, configuration, security monitoring) onto a function without embedding them in your handler and without a sidecar container, which serverless does not offer.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What Extensions Are and How They Get There</h4>\n<p style=\"line-height: 1.75\">Extensions are delivered exactly two ways. For zip-packaged functions, an extension ships as a <strong>Lambda layer</strong>; Lambda unpacks layers into <code>/opt</code>, and any executable file in <code>/opt/extensions/</code> is started as an extension before the runtime initialises. For container-image functions there are no layers, so the extension binary is baked into the image at <code>/opt/extensions/</code> in the Dockerfile. Either way, an extension is just an executable — a Go binary, a Node or Python script with a shebang, a shell script — that speaks the <strong>Extensions API</strong> over HTTP to the endpoint given by the <code>AWS_LAMBDA_RUNTIME_API</code> environment variable.</p>\n<p style=\"line-height: 1.75\">The registration handshake is simple and worth knowing: the extension POSTs to <code>/2020-01-01/extension/register</code> with a <code>Lambda-Extension-Name</code> header matching its filename and a body listing the events it wants (<code>INVOKE</code>, <code>SHUTDOWN</code>). Lambda replies with a <code>Lambda-Extension-Identifier</code> header — a token used on every subsequent call. The extension then loops on <code>GET /2020-01-01/extension/event/next</code>, a long-poll that blocks until the next event arrives. That blocking GET is also the signal to Lambda that the extension has finished its current work, which is the detail people get wrong: <strong>calling event/next is how you say \"I am done\"</strong>, so an extension that does work after receiving an INVOKE event and before calling event/next again is extending the invocation.</p>\n<h4 style=\"margin-top: 1.5rem; A heavyweight extension that opens connections or fetches configuration during Init directly lengthens cold start, often by 50-300 ms. This is the single biggest cost of adopting one.</li>\n<li><strong>Extensions can add to billed duration.</strong> Because the invocation is not considered complete until all extensions have called <code>event/next</code>, an extension doing synchronous work after your handler returns is billed to you. Well-written telemetry extensions buffer and flush asynchronously or during Shutdown precisely to avoid this; poorly written ones ship on every invoke and add latency.</li>\n<li><strong>Shutdown is real but bounded.</strong> Extensions get a short, best-effort grace window. You cannot do meaningful network work with long timeouts there, and a SHUTDOWN with reason <code>timeout</code> or <code>failure</code> means the environment is already unhealthy. Note also that the runtime does <em>not</em> get a shutdown hook in the same way an external extension does — which is why \"flush my buffered logs at the end\" is an extension job, not a handler job.</li>\n</ul>\n<p style=\"line-height: 1.75\">One more subtlety: functions with external extensions registered get a longer function timeout grace and, importantly, you can attach a debugger or profiler that outlives a single invocation. Also, when any extension is registered, Lambda disables some fast-path optimisations, and <strong>an extension that crashes causes the whole execution environment to be recycled</strong> — including your function. That is the operational risk in one sentence.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Use Cases That Genuinely Justify an Extension</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Secrets and parameter caching.</strong> The <strong>AWS Parameters and Secrets Lambda Extension</strong> is the flagship example. It runs a local HTTP server on port 2773 (configurable via <code>PARAMETERS_SECRETS_EXTENSION_HTTP_PORT</code>). Your handler does a plain GET to <code>http://localhost:2773/secretsmanager/get?secretId=NAME</code> or <code>/systemsmanager/parameters/get?name=NAME&amp;withDecryption=true</code>, passing <code>X-Aws-Parameters-Secrets-Token: AWS_SESSION_TOKEN</code>. The extension handles the SigV4-signed AWS call, caches the result, and serves subsequent reads from memory with a TTL you set (<code>SECRETS_MANAGER_TTL</code>, <code>SSM_PARAMETER_STORE_TTL</code>). Value: no secrets API call on the hot path, bounded staleness so rotation is picked up, and one implementation shared across every runtime.</li>\n<li><strong>Observability agents.</strong> Datadog, New Relic, Dynatrace, Splunk, Sumo Logic, Lumigo and others ship extensions. They subscribe to the Telemetry API, buffer telemetry in the execution environment, and ship it directly to the vendor's API — bypassing CloudWatch Logs entirely, which both reduces CloudWatch ingestion cost and removes the latency of a log subscription pipeline. The <strong>ADOT (AWS Distro for OpenTelemetry) Lambda layer</strong> is the vendor-neutral version, running a Collector as an extension.</li>\n<li><strong>Configuration.</strong> The <strong>AWS AppConfig Lambda extension</strong> works like the secrets extension: a local endpoint (port 2772 by default) serving cached configuration and feature flags, polling AppConfig in the background. This is how you get feature flags in Lambda without a config fetch per invocation or a redeploy per toggle.</li>\n<li><strong>Security and runtime monitoring.</strong> Agents that watch process, file, and network activity inside the execution environment for anomalous behaviour, or enforce policy. This is a legitimate niche precisely because you cannot install a host agent on a serverless platform.</li>\n</ul>\n<p style=\"line-height: 1.75\">Note what is <em>not</em> on this list: business logic. An extension is infrastructure. If you find yourself writing application behaviour into one, you have chosen the wrong tool — that belongs in the handler or in a separate function.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Telemetry API</h4>\n<p style=\"line-height: 1.75\">Extensions get data out of the environment via the <strong>Lambda Telemetry API</strong>. An extension subscribes by PUTting to <code>/2022-07-01/telemetry</code> with its extension identifier, naming which <strong>streams</strong> it wants and where to deliver them. There are three streams:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>platform</strong> — lifecycle and performance events generated by Lambda itself: <code>platform.initStart</code> / <code>initRuntimeDone</code> / <code>initReport</code>, <code>platform.start</code>, <code>platform.runtimeDone</code>, <code>platform.report</code> (with billed duration, memory used, init duration), <code>platform.restoreStart</code> and <code>restoreReport</code> for SnapStart, plus <code>platform.telemetrySubscription</code> and <code>platform.extension</code>. These carry the structured equivalent of the REPORT line, which is far better than regex-parsing text.</li>\n<li><strong>function</strong> — everything your handler writes to stdout and stderr.</li>\n<li><strong>extension</strong> — output from extensions themselves.</li>\n</ul>\n<p style=\"line-height: 1.75\">Delivery is a push model: the extension runs a local HTTP listener and Lambda POSTs batches of events to it as JSON. You configure buffering with <code>maxItems</code>, <code>maxBytes</code>, and <code>timeoutMs</code> — larger buffers mean fewer deliveries and less overhead but more risk of loss if the environment is killed abruptly. Because delivery is a local loopback POST rather than a network call to CloudWatch, the extension sees telemetry with very low latency and can ship it onward on its own schedule.</p>\n<p style=\"line-height: 1.75\">The Telemetry API <strong>superseded the earlier Logs API</strong> (<code>/2020-08-15/logs</code>). The Logs API delivered only log lines — the <code>platform</code>, <code>function</code>, and <code>extension</code> log streams — as loosely structured records. The Telemetry API adds <strong>traces and richer structured platform events</strong>, gives every event a schema with a <code>type</code> and typed <code>record</code>, includes spans (such as <code>responseLatency</code> and <code>responseDuration</code>), and reports SnapStart restore phases. New development should target the Telemetry API; the Logs API still exists for compatibility but is not where the investment is.</p>\n<p style=\"line-height: 1.75\">One important caveat for anyone building a telemetry extension: the platform <code>report</code> event for invocation N arrives <em>after</em> the runtime has finished invocation N, and may be delivered during the next invocation or at shutdown. So an extension cannot assume it has complete telemetry for an invocation at the moment it calls <code>event/next</code>. That is precisely why the Shutdown flush window matters.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Costs, Risks, and When to Say No</h4>\n<p style=\"line-height: 1.75\">Extensions are not free, and a senior engineer should volunteer the downsides:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Cold start.</strong> Every extension is initialised before your runtime starts. Layered APM extensions commonly add 100-300 ms to Init; a minimal Go extension adds far less. On a latency-sensitive synchronous API this can be the deciding factor.</li>\n<li><strong>Memory.</strong> The extension shares the function's configured memory. A 200 MB agent inside a 512 MB function leaves you 300 MB, and the first symptom is an OOM kill that looks like a mysterious function crash. When you add an extension, re-measure <code>Max Memory Used</code> and resize.</li>\n<li><strong>CPU contention.</strong> CPU allocation scales with memory and is shared. An extension doing compression or serialization competes with your handler for the same vCPU slice, so at low memory settings an extension can measurably slow the function.</li>\n<li><strong>Billed duration.</strong> As above — the invocation is not done until every extension calls <code>event/next</code>.</li>\n<li><strong>Blast radius of a third-party binary.</strong> The extension runs with your execution role's credentials available in the environment, has full network access, and can read your function's telemetry including anything you logged. A compromised or buggy vendor layer is a serious incident. Pin layer versions explicitly (never track \"latest\"), review what network endpoints the extension contacts, and treat a layer version bump as a code change requiring a canary deploy.</li>\n<li><strong>Debuggability.</strong> When an extension crashes, the environment is recycled and your function fails in ways that do not point at the extension. Symptoms look like random elevated errors or init failures. The diagnostic move is to remove the layer and see if the symptom disappears.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario: Extension Cache vs In-Handler Cache</h4>\n<p style=\"line-height: 1.75\">You have a function that needs a database credential from Secrets Manager. Two options: the Parameters and Secrets extension, or twelve lines of your own caching code at module scope. Reason it through rather than defaulting to the AWS-branded option.</p>\n<p style=\"line-height: 1.75\"><strong>The in-handler cache.</strong> Fetch the secret once at module initialisation, store it in a module-level variable, reuse it for the life of the execution environment. Cost: one extra SDK call per cold start. Benefits: zero added init time from an extension, zero extra memory, no third-party code, trivially testable locally, no layer version to manage. Weakness: the cache has <strong>no TTL</strong> — it lives as long as the environment does, which can be many hours. When the secret rotates, warm environments keep using the stale credential until they recycle. You can mitigate that with your own TTL check (compare a stored fetch timestamp on each invocation and refetch when stale) and with a catch-on-auth-failure-and-refetch path, at which point you have reimplemented most of the extension.</p>\n<p style=\"line-height: 1.75\"><strong>The extension cache.</strong> Cost: added init time (the extension must register before the runtime starts), added memory footprint, a layer ARN to pin and update, and a local HTTP call per read instead of a variable read. Benefits: a real configurable TTL so rotation is picked up within a bounded window without any code; caching shared across the whole environment rather than per-module; one consistent mechanism across Node, Python, Java and Go functions, so platform teams can mandate it; and it handles SSM parameters and Secrets Manager with the same interface.</p>\n<p style=\"line-height: 1.75\"><strong>How to decide.</strong> Ask three questions. First, <strong>does the secret rotate?</strong> If it is a static third-party API key changed manually twice a year, the simple module cache is genuinely the better engineering choice and a TTL buys nothing. If it is an RDS credential under Secrets Manager managed rotation, you need bounded staleness and the extension earns its place. Second, <strong>how latency-sensitive is this function?</strong> For a synchronous user-facing API where p99 cold start is already a concern, the added Init cost is a real argument against, and a module cache plus an explicit refetch-on-auth-failure path may be the right compromise. For an asynchronous worker, the init cost is irrelevant. Third, <strong>how many functions and runtimes?</strong> One function: write the twelve lines. Eighty functions across four runtimes and three teams: standardise on the extension, because the consistency and the \"nobody has to get caching right again\" property outweigh the per-function overhead.</p>\n<p style=\"line-height: 1.75\">The answer that scores well names the third option too: <strong>Powertools' parameters utility</strong>, which gives you a configurable TTL in-process with no extension and no added Init from a separate binary — often the best of both for a single-runtime shop.
