Senior candidates who say \"use provisioned concurrency\" and stop have answered one third of the question. The useful framing is: <strong>decompose Init, measure which phase dominates, then choose the cheapest mitigation that actually targets that phase</strong> — and be willing to conclude that for many workloads the correct action is to do nothing at all.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What Actually Happens During Init</h4>\n<p style=\"line-height: 1.75\">The Lambda execution lifecycle is <strong>Init → Invoke → Shutdown</strong>. The Init phase decomposes into three sub-phases, and only some are yours to control:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\"><li><strong>Extension init and code download.</strong> Lambda fetches your deployment package (or pulls and unpacks container image layers) into the execution environment. Cost scales with <strong>package size</strong>. You influence this by shipping less.</li><li><strong>Runtime bootstrap.</strong> The microVM is created and the language runtime starts — the Node process, the Python interpreter, the JVM, the .NET CLR. This is where <strong>runtime choice</strong> dominates: an interpreted runtime bootstraps in tens of milliseconds; a JVM with classloading and JIT warm-up can take hundreds of milliseconds to seconds. You influence this only by changing runtime or by using SnapStart.</li><li><strong>Function init — your static/global scope.</strong> Everything outside the handler: module imports, SDK client construction, config parsing, secrets retrieval, database connection establishment, framework bootstrapping. This is the phase you control most directly and the one that most often dominates in practice.</li></ul>\n<p style=\"line-height: 1.75\">Two mechanical facts worth stating precisely. The <strong>Init phase has a 10-second limit</strong> for on-demand invocations — if your global scope exceeds it, Lambda aborts and restarts Init at the time of the first invocation, which produces a confusing double-init in the logs. And <strong>Init duration is reported separately</strong> in the REPORT line as <code>Init Duration</code>, which means you can measure the phase directly rather than guessing. Historically Init was not billed for managed runtimes; AWS changed this in <strong>August 2025</strong> so that INIT time is billed for on-demand invocations of managed runtimes as well — bringing them in line with container images and custom runtimes, where Init has always been billable. The JVM penalty is the reason SnapStart was built for Java first.</li><li><strong>Dependency bloat.</strong> This is usually worse than package size. Importing the entire AWS SDK v2 in Node costs hundreds of milliseconds of module resolution and parsing; importing a single v3 client costs a fraction of that. In Python, importing pandas or boto3-with-everything at module scope is the same mistake.</li><li><strong>Heavy global-scope work.</strong> Synchronously fetching secrets, warming caches, building ORM metadata, or reading large config files at init. These are not free just because they happen once.</li><li><strong>VPC attachment.</strong> Historically each execution environment created its own ENI, adding <strong>multiple seconds</strong> to cold starts and causing ENI exhaustion. ENI setup now happens at function create/update time, not per cold start; the residual per-cold-start cost is small.</li></ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Provisioned Concurrency in Depth</h4>\n<p style=\"line-height: 1.75\">Provisioned concurrency keeps N environments <strong>through Init and held ready</strong>, so an invocation routed to one of them skips code download, runtime bootstrap, and global scope entirely — the handler runs immediately. It is the only mitigation that works regardless of language, framework, or why Init is slow, which is what makes it the universal (and expensive) answer.</p>\n<p style=\"line-height: 1.75\">Mechanics that matter in an interview: it is configured on a <strong>published version or alias, never on $LATEST</strong>, which forces versioned deployments; allocation is <strong>not instantaneous</strong> (expect a minute or more before the config reports READY, longer for large allocations), so scheduled scaling must run <em>ahead</em> of the spike; and it is <strong>drawn from reserved concurrency if set, and always from the account quota</strong>. Critically, <strong>spillover beyond the provisioned count still cold starts</strong> — provisioned concurrency shaves the fast mode off the latency histogram but does not remove the cold-start tail, it just moves the threshold at which the tail appears.</p>\n<p style=\"line-height: 1.75\">Drive the allocation with <strong>Application Auto Scaling</strong>: target tracking on <code>LambdaProvisionedConcurrencyUtilization</code> for organically varying load, or <strong>scheduled scaling</strong> for predictable diurnal or event-driven peaks. The cost trade-off is a holding charge per GB-second for every provisioned environment whether or not it is invoked (about $0.0000041667 per GB-second in us-east-1) offset by a discounted duration rate (about $0.0000097222 versus $0.0000166667 per GB-second on-demand). At sustained utilisation above roughly 60 percent the discount can make provisioned concurrency <em>cheaper</em> than on-demand; below that it is a latency purchase you are paying for in cash.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">SnapStart — Snapshot and Restore</h4>\n<p style=\"line-height: 1.75\">SnapStart attacks Init from a completely different angle. When you <strong>publish a version</strong> of a SnapStart-enabled function, Lambda initialises the environment once, takes an <strong>encrypted Firecracker microVM snapshot</strong> of the fully initialised memory and disk state, and caches it. Subsequent cold starts <strong>restore from the snapshot</strong> instead of re-running Init — and the snapshot is loaded lazily, page by page, as the function touches memory. For a JVM function this can cut a two-second cold start to a couple of hundred milliseconds. It is available for <strong>Java 11 and later, Python 3.12 and later, and .NET 8 and later</strong>. SnapStart for Java carries no additional charge; for Python and .NET there are charges for snapshot caching and for restore.</p>\n<p style=\"line-height: 1.75\">Two operational constraints. <strong>SnapStart is incompatible with provisioned concurrency</strong> — you choose one or the other — and it does not work with EFS mounts or ephemeral storage above 512 MB. And snapshots for a <strong>version that has not been invoked for 14 days are deleted</strong>, so the next invocation of a dormant version pays a full Init; this catches teams with rarely exercised versions.</p>\n<p style=\"line-height: 1.75\"><strong>The correctness hazards are the real interview material.</strong> Anything captured in the snapshot is <em>replayed identically into every restored environment</em>:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\"><li><strong>Seeded randomness.</strong> A pseudo-random generator seeded at init will produce the <em>same sequence</em> in every restored environment. The Lambda Java runtime handles <code>java.security.SecureRandom</code> automatically, but a custom PRNG, a UUID generator seeded at init, or a library that caches entropy is a genuine security bug — duplicate tokens across environments.</li><li><strong>Unique identifiers generated at init.</strong> A container ID, a correlation prefix, or a lock token computed in global scope is no longer unique after restore; it is shared by every environment restored from that snapshot.</li><li><strong>Cached credentials and temporary tokens.</strong> IAM session credentials or a fetched Secrets Manager value captured at init can be <strong>expired by the time the snapshot is restored days later</strong>, producing sporadic authentication failures.</li><li><strong>Open network connections.</strong> Database connections, HTTP keep-alive sockets, and gRPC channels established at init are <strong>dead after restore</strong> — the peer closed them long ago. You get connection-reset errors on the first invocation of each restored environment.</li></ul>\n<p style=\"line-height: 1.75\">The mitigation is <strong>runtime hooks</strong>. Java uses the <strong>CRaC</strong> API — implement <code>Resource</code> with <code>beforeCheckpoint</code> and <code>afterRestore</code>. Python uses the <code>snapshot_restore_py</code> module with <code>register_before_snapshot</code> and <code>register_after_restore</code> decorators. .NET uses <code>Snapshot.RegisterBeforeSnapshot</code> and <code>Snapshot.RegisterAfterRestore</code>. The rule of thumb: <strong>close connections and drop credentials before the snapshot; re-seed randomness, re-generate identifiers, and re-establish connections after restore.</strong></p>\n<div style=\"overflow-x: auto;
