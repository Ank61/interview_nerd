That was catastrophic at two levels: it added roughly <strong>10 seconds</strong> to every cold start, and ENIs are a finite per-account and per-subnet resource, so scaling a VPC function produced <strong>ENI exhaustion</strong> and <code>EC2ThrottledException</code> errors.</p>\n<p style=\"line-height: 1.75\">AWS replaced it with <strong>Hyperplane ENIs</strong> — network interfaces managed by the same Hyperplane fabric behind NAT Gateway and NLB. Also attach when a compliance requirement demands that traffic traverse your own network controls and be inspectable.</p>\n<p style=\"line-height: 1.75\"><strong>Do not attach otherwise</strong>, and this deserves to be argued rather than assumed. A non-VPC function reaches DynamoDB, S3, SQS, SNS, Secrets Manager, and every other AWS API over the public AWS network path <strong>with IAM-signed requests over TLS</strong> — the requests are authenticated and encrypted, and \"not in a VPC\" is not the same as \"insecure\". Attaching unnecessarily buys you: ENI management, subnet IP consumption, a NAT Gateway bill, an extra failure domain, slower deployments, and a long tail of connectivity bugs. <strong>IAM is the security boundary for AWS API calls; the VPC is the security boundary for network-reachable resources.</strong> Attach for reachability, not for a vague sense of security.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Subnets, Availability, IP Exhaustion, and DNS</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\"><li><strong>Always configure at least two subnets in different Availability Zones</strong> — ideally three. A single-subnet VPC function loses availability when that AZ is impaired. Lambda spreads environments across the subnets you give it.</li><li><strong>Use private subnets.</strong> Public subnets provide no benefit and mislead future readers into thinking the function has internet access.</li><li><strong>IP address exhaustion.</strong> Hyperplane hugely reduced ENI count, but ENIs still consume subnet IPs, and interface endpoints consume one IP per AZ each, and RDS Proxy, NAT, and other VPC resources compete for the same space. A <code>/27</code> subnet has 27 usable addresses after AWS reserves 5 — far too tight. Use <code>/24</code> or larger for Lambda subnets, and remember the limiting factor is the <em>subnet</em>, not the VPC. Symptom of exhaustion: invocations failing with an ENI or <code>EC2ThrottledException</code>-style error, typically after a scaling event or a deployment.</li><li><strong>Security groups.</strong> The Lambda security group needs <strong>outbound</strong> rules to the destinations it calls (443 to interface endpoints, 5432 to the RDS security group, 6379 to ElastiCache). Because security groups are stateful, no inbound rule is needed on the Lambda SG — Lambda accepts no inbound connections. The <em>destination</em> security group must allow inbound <strong>from the Lambda security group ID</strong>, not from a CIDR; referencing the SG is both more precise and survives subnet changes. Standardise on a small number of Lambda SGs to limit ENI proliferation.</li><li><strong>DNS.</strong> The VPC must have <code>enableDnsSupport</code> and, for private hosted zones and endpoint private DNS, <code>enableDnsHostnames</code> enabled. Interface endpoints with <strong>private DNS enabled</strong> transparently resolve the public service hostname to the endpoint's private IP, which is what lets unmodified SDK code use the endpoint. If private DNS is off, or if a custom DHCP option set points at an on-premises DNS server that cannot resolve AWS names, calls fail with DNS resolution errors that look nothing like a networking problem. In hybrid setups, Route 53 Resolver inbound and outbound endpoints are the mechanism for making both directions resolve.</li></ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario: \"my Lambda times out calling an external API since I put it in a VPC\"</h4>\n<p style=\"line-height: 1.75\">The symptom is a <strong>timeout</strong>, not a connection-refused or DNS error, which is itself diagnostic: SYN packets are leaving and nothing is returning. Work the chain in order:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\"><li><strong>1. Confirm the cause.</strong> Did the function work before attachment? If yes, attachment replaced AWS-managed networking with yours and removed the default internet path. Do not start debugging the third-party API.</li><li><strong>2. Check the subnets.</strong> Look up the subnet IDs in the function's VPC config, then inspect each one's <strong>route table</strong>. If <code>0.0.0.0/0</code> points to an <strong>internet gateway</strong>, the function is in a public subnet and will never work — it has no public IP for the IGW to translate. If there is no <code>0.0.0.0/0</code> route at all, it is an isolated subnet.</li><li><strong>3. Check for a NAT Gateway.</strong> The correct configuration is <code>0.0.0.0/0</code> to a <strong>NAT Gateway</strong> that lives in a <em>different, public</em> subnet with an Elastic IP, and whose own subnet routes <code>0.0.0.0/0</code> to the IGW. Verify the NAT Gateway state is <code>available</code>. Verify every subnet the function uses has this route — a common bug is fixing the route table for subnet A and forgetting subnet B, which produces intermittent timeouts that correlate with nothing.</li><li><strong>4. Check security groups.</strong> The Lambda SG must allow <strong>outbound</strong> 443 to <code>0.0.0.0/0</code> (or the API's range). A restrictive SG with no egress rules blocks everything.</li><li><strong>5. Check NACLs.</strong> Network ACLs are <strong>stateless</strong>, so the subnet NACL must allow outbound 443 <em>and</em> inbound on the <strong>ephemeral port range 1024–65535</strong> for return traffic. A NACL that allows only inbound 443 breaks all outbound connections — and this is the failure people miss because security groups do not work that way.</li><li><strong>6. Check DNS.</strong> Confirm <code>enableDnsSupport</code> is on. If the VPC uses a custom DHCP option set pointing to on-premises DNS, that resolver must be reachable and able to resolve the API hostname. A DNS failure normally surfaces fast rather than as a timeout, which helps distinguish it.</li><li><strong>7. Check the destination.</strong> If the third-party service allow-lists source IPs, it must now allow the NAT Gateway's <strong>Elastic IP</strong> — the function's apparent source address changed. This produces a timeout or a 403 depending on how they drop traffic.</li><li><strong>8. Confirm with evidence.</strong> Enable <strong>VPC Flow Logs</strong> on the subnets and look for the ENI's outbound flows: <code>ACCEPT</code> on egress with no return flow points at NAT or the destination; <code>REJECT</code> points at a security group or NACL. Also raise the function timeout temporarily so you capture a full picture rather than a truncated one.</li><li><strong>9. Ask whether you needed the VPC at all.</strong> If the function was attached only so it could reach DynamoDB or S3, detach it and use IAM-signed calls — or if it genuinely needs RDS, keep it attached and add a NAT Gateway, sizing the bill deliberately.</li></ul>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"Attaching Lambda to a VPC replaces AWS-managed networking with yours, and the function gets no public IP — so it loses internet access, and a public subnet doesn't help because there's nothing for the internet gateway to translate.
