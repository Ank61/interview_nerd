{"title":"Idempotency and Exactly-Once Processing in Lambda","tags":["lambda","idempotency","exactly-once","dynamodb"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Every meaningful Lambda event source delivers <strong>at-least-once</strong>. Not \"usually once.\" At-least-once. Duplicates are a normal, expected, designed-in property of the platform, not a bug you can file. The consequence is blunt: <strong>exactly-once <em>processing</em> is something the consumer builds, never something the platform provides</strong>. Senior interviews probe this because it is the difference between an engineer who has run serverless systems in production and one who has read the marketing page.</p>\n<p style=\"line-height: 1.75\">The distinction that matters is <strong>exactly-once delivery</strong> versus <strong>exactly-once processing</strong>. Exactly-once delivery is impossible over an unreliable network — this is the Two Generals problem, and no amount of AWS engineering repeals it. Exactly-once <em>processing</em> is achievable and is what you actually want: the message may arrive five times, but the side effect happens once. You get there by making the operation <strong>idempotent</strong>, meaning f(f(x)) equals f(x) — applying it twice produces the same state as applying it once.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Where duplicates actually come from</h4>\n<p style=\"line-height: 1.75\">It helps to know the specific mechanism per source, because each produces a different <em>shape</em> of duplicate:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>SQS standard.</strong> Explicitly at-least-once by design. A message whose delete call fails, or whose consumer exceeds the visibility timeout, is redelivered. SQS also occasionally delivers a copy because of its distributed storage model, independent of anything you did.</li>\n<li><strong>Kinesis and DynamoDB Streams.</strong> Lambda retries a whole batch on failure. If record 7 of 10 fails, records 1-6 are reprocessed on the retry — <strong>guaranteed duplicates for the records that already succeeded</strong>. This is the most under-appreciated duplicate source, because the duplicate is caused by your own error handling. Shard resharding and checkpoint replay add more.</li>\n<li><strong>Asynchronous invocation.</strong> Lambda retries twice by default. A function that times out <em>after</em> completing its side effect will be retried, and the retry redoes the effect.</li>\n<li><strong>S3 event notifications.</strong> Documented as at-least-once. Multiple notifications can fire for one PUT, and notifications can arrive <strong>out of order</strong> — a delete notification can arrive before the create it followed.</li>\n<li><strong>EventBridge.</strong> At-least-once for rule targets. A rule with multiple targets, or overlapping rules, can produce what looks like duplication to your function.</li>\n<li><strong>Synchronous invocation.</strong> Client-side and SDK-level retries, as covered in the error-handling topic. The most invisible duplicates of all, since the first execution succeeded.</li>\n</ul>\n<p style=\"line-height: 1.75\">A useful mental frame: a duplicate is not always \"the same event twice.\" It is \"the same <em>business intent</em> processed twice.\" Two different message IDs carrying the same order can be a duplicate that no message-ID-based deduplication will catch. This is why <strong>key choice</strong> is the heart of the design.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Choosing the idempotency key</h4>\n<p style=\"line-height: 1.75\">Three families of key, each with a distinct failure mode:</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Key type</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Example</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Strength</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Pitfall</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><strong>Business / natural key</strong></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">orderId, paymentRequestId</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Catches the same intent arriving through different transports or message IDs</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Requires the producer to generate and carry it; too coarse a key blocks legitimate repeat operations</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><strong>Event / message ID</strong></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">SQS messageId, DynamoDB Streams eventID, EventBridge id</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Always present, no producer changes needed</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Only catches redelivery of the <em>same</em> message. Include a <code>publishedAt</code> timestamp in the hash and your deduplication silently stops working — every retry hashes differently. Exclude too much and two legitimate \"charge this customer 10 dollars\" requests one minute apart collapse into one, and you have silently swallowed a real transaction. The mitigation is to hash a <strong>deliberately selected subset</strong> of fields rather than the whole payload, and to document that choice.</p>\n<p style=\"line-height: 1.75\"><strong>The S3 case is the canonical interview trap.</strong> Using the object key alone as the idempotency key is wrong in two directions. First, an object can be legitimately overwritten — <code>uploads/report.csv</code> written on Monday and again on Tuesday are two real events, and keying on the object key makes you drop Tuesday's. Second, S3 notifications can arrive out of order, so a stale notification can overwrite fresher state. The record carries the fields that fix this: <code>s3.object.versionId</code> on a versioned bucket uniquely identifies the exact object generation, and <code>s3.object.sequencer</code> is a hexadecimal string whose <strong>lexicographic order (after left-padding to equal length) reflects the order of events for that key</strong>. AWS documents the sequencer explicitly for determining event sequence. The correct key is the bucket plus key plus versionId (or sequencer), and the correct out-of-order guard is a conditional write that only applies the change if the incoming sequencer is greater than the stored one.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The mechanics: conditional writes to atomically claim work</h4>\n<p style=\"line-height: 1.75\">The naive implementation is a read-then-write: check DynamoDB for the key, and if absent, do the work. <strong>This is broken</strong> — it is a textbook check-then-act race. Two concurrent invocations both read \"absent,\" both proceed, both charge the card. Under SQS with several messages in flight this happens routinely, not rarely.</p>\n<p style=\"line-height: 1.75\">The correct primitive is a <strong>conditional write</strong>: DynamoDB's <code>PutItem</code> with <code>ConditionExpression: attribute_not_exists(pk)</code>. This is a single atomic operation at the partition level — exactly one caller succeeds, every other caller receives <code>ConditionalCheckFailedException</code>. The claim and the check are the same operation, so there is no window between them.</p>\n<div class=\"code\"><div class=\"code-head\"><span>java</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">Invocation A                         <i class=t>Invocation</i> <i class=f>B</i> <i class=p>(duplicate)</i>\n    |                                     |\n    | PutItem(key, INPROGRESS)            | PutItem(key, INPROGRESS)\n    | cond: attribute_not_exists          | cond: attribute_not_exists\n    v                                     v\n  SUCCESS -- claim won              ConditionalCheckFailedException\n    |                                     |\n    | <i class=k>do</i> the side effect                  | GetItem(key) -&gt; read status\n    |  (charge the card)                  |    |\n    v                                     |    +-- COMPLETED -&gt; <i class=k>return</i> saved <i class=t>response</i>\n  <i class=f>UpdateItem</i><i class=p>(key,                         |    +-- INPROGRESS -&gt; throw / retry later\n     status=COMPLETED,                    |    +-- expired    -&gt; take over the claim\n     response={...}, ttl=now+<i class=n>86400</i>)</i>       v\n    |                                  no side effect performed\n    v\n  <i class=k>return</i> response</code></pre></div>\n<p style=\"line-height: 1.75\">Three states, and the middle one is where most homegrown implementations are wrong:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>INPROGRESS.</strong> Written before the side effect. A duplicate that sees INPROGRESS must <strong>not</strong> proceed and must <strong>not</strong> silently return success — it does not know the outcome yet. The right behaviour is to throw a distinct error so the platform retries later, by which point the original will have finished. Returning \"OK, already done\" here is a correctness bug: the original may be about to fail.</li>\n<li><strong>COMPLETED.</strong> Written after the side effect, along with the serialized response. Duplicates read this and return the <strong>original response</strong>.</li>\n<li><strong>The crash gap.</strong> If the function dies between claiming and completing, the record is stuck in INPROGRESS forever and the work is permanently blocked. The fix is an <strong>in-progress expiry timestamp</strong> — set it from <code>context.getRemainingTimeInMillis()</code> at claim time, so the claim expires shortly after the invocation could possibly still be alive. The condition then becomes \"no item exists <em>or</em> the existing item is an expired in-progress claim.\"</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>Caching and returning the original response</strong> is not a nicety; for synchronous APIs it is the requirement. A client that retries a payment must get back the same payment ID it would have gotten the first time, not an error and not a different ID. Store the serialized response on the COMPLETED record. Watch the 400 KB DynamoDB item limit — for large responses, store a pointer to S3 rather than the body.</p>\n<p style=\"line-height: 1.75\"><strong>TTL for cleanup.</strong> Set a <code>expiration</code> numeric attribute holding a Unix epoch seconds value and enable DynamoDB TTL on it. The critical operational caveat: <strong>TTL deletion is best-effort and typically happens within 48 hours of expiry, not at the instant of expiry</strong>. You therefore must not rely on TTL for correctness — always compare the stored expiry against the current time in your condition expression rather than assuming an expired item is gone. Choose the window from the business requirement: how long after a request would a retry still be considered the same request? For payments, 24 hours is typical; for a high-volume event pipeline, an hour may be enough and keeps the table small.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">AWS Lambda Powertools — the standard implementation</h4>\n<p style=\"line-height: 1.75\">Do not write this yourself. <strong>Powertools for AWS Lambda</strong> (Python, TypeScript, Java, .NET) ships an idempotency utility that implements exactly the state machine above, correctly, including the edge cases most hand-rolled versions miss. In Python it is the <code>@idempotent</code> / <code>@idempotent_function</code> decorator; in TypeScript, <code>makeIdempotent</code> and <code>makeHandlerIdempotent</code>.</p>\n<p style=\"line-height: 1.75\">Under the hood it does the following. It extracts the key from the event using a <strong>JMESPath expression</strong> you supply via <code>event_key_jmespath</code> — for example <code>powertools_json(body).orderId</code> to reach inside an API Gateway body, or <code>Records[0].messageId</code>. It hashes that value (MD5 by default, configurable) to form the partition key. It performs a conditional <code>PutItem</code> to claim the record with status INPROGRESS and an <code>in_progress_expiration</code> derived from the invocation's remaining time. It runs your function, then updates the record to COMPLETED with the serialized response and an <code>expiration</code> TTL attribute. On a duplicate it returns the stored response; if it encounters INPROGRESS it raises <code>IdempotencyAlreadyInProgressError</code> so the platform retries. It also stores a <strong>validation hash</strong> of a payload subset you nominate via <code>payload_validation_jmespath</code>, so if the same idempotency key arrives with a <em>different</em> body — a client bug — it raises <code>IdempotencyValidationError</code> rather than silently returning a response computed from different inputs. <code>DynamoDBPersistenceLayer</code> is the standard backend; Redis is also supported.</p>\n<p style=\"line-height: 1.75\">Two things to know for interviews. First, <strong>a decorator on the handler is the wrong granularity for batch sources</strong> — with SQS, the whole batch becomes one idempotency unit, so a redelivered batch containing one new message is treated as a duplicate and skipped entirely. For batches, apply <code>@idempotent_function</code> to the per-record function with <code>data_keyword_argument</code>, combined with batch item failure reporting. Second, it costs a read and one or two writes per invocation, plus latency; for very high-throughput, low-value events, that overhead can exceed the cost of the duplicate you are preventing.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Special cases and alternatives</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>SQS FIFO deduplication is not consumer idempotency.</strong> FIFO queues deduplicate on <code>MessageDeduplicationId</code> (or a SHA-256 content hash if content-based deduplication is enabled) within a <strong>5-minute deduplication interval</strong>. That window is fixed and not configurable. It is <em>producer-side</em> and <em>time-bounded</em>: it stops the same message being enqueued twice in five minutes. It does nothing about a consumer that processes a message, crashes before deleting it, and receives it again after the visibility timeout — which is the duplicate that actually charges your customer twice. FIFO also caps throughput (300 API calls/second per API action, or 3000 messages/second with batching, and up to 70,000 with high throughput mode enabled). Use FIFO for <em>ordering</em>; still build consumer idempotency.</li>\n<li><strong>S3 sequencer for ordering.</strong> As above: compare sequencers lexicographically after zero-padding to equal length, and reject an event whose sequencer is not greater than the last one stored for that key. This handles out-of-order notification delivery, which a pure deduplication check does not.</li>\n<li><strong>Conditional / optimistic-concurrency writes as the alternative.</strong> Sometimes you do not need a separate idempotency table at all, because the target write can itself be made idempotent. Writing the order record with <code>attribute_not_exists(orderId)</code> makes the write naturally once-only. An optimistic-concurrency <code>version</code> attribute with <code>ConditionExpression: version = :expected</code> plus <code>SET version = version + 1</code> makes an update safely repeatable. Better still, prefer <strong>naturally idempotent operations</strong>: a SET to an absolute value is idempotent, an ADD of a delta is not; use a <code>PUT</code>-style upsert on a deterministic key instead of an append. This is cheaper, has fewer moving parts, and fails closed. It only works when the operation touches a single item you control — cross-service side effects (charging a card, sending an email) still need the separate record.</li>\n<li><strong>Push idempotency to the downstream when it offers it.</strong> Stripe, most payment gateways, and many APIs accept an <code>Idempotency-Key</code> header. Pass <em>your</em> key through. Then even if your own guard fails, the provider deduplicates. Defence in depth.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario — customers are being charged twice</h4>\n<p style=\"line-height: 1.75\"><em>\"An order-processing Lambda triggered by SQS is occasionally charging customers twice. Diagnose it and redesign it.\"</em></p>\n<p style=\"line-height: 1.75\"><strong>Diagnosis.</strong> Do not start with the code; start with the invocation record. Query CloudWatch Logs Insights for <code>messageId</code> values appearing in more than one <code>requestId</code>. Two distinct patterns emerge and they have different causes. If the same <code>messageId</code> appears twice, SQS redelivered — which means the invocation did not delete the message, which means it either <strong>threw after the charge succeeded</strong> or <strong>ran past the visibility timeout</strong>. Check <code>Duration</code> against the queue's <code>VisibilityTimeout</code>; if duration ever approaches it, SQS handed the message to a second consumer while the first was still working. Also check whether a batch failure is at fault: with <code>BatchSize: 10</code> and no <code>ReportBatchItemFailures</code>, one bad message in a batch forces <strong>all ten to be redelivered</strong>, so nine customers who were charged correctly get charged again. That is by far the most common root cause and it is entirely a configuration bug. If instead two <em>different</em> messageIds carry the same orderId, the producer published twice — an upstream retry — and no message-level deduplication would ever have caught it.</p>\n<p style=\"line-height: 1.75\"><strong>Redesign, in order of importance.</strong> (1) <strong>Idempotency keyed on the business key</strong>, not the messageId — use <code>orderId</code> or a <code>paymentRequestId</code> the checkout service generates, because that is the only key that catches both duplicate classes. Claim it with a conditional <code>PutItem</code> on <code>attribute_not_exists(pk)</code> <em>before</em> calling the gateway, write INPROGRESS with an expiry derived from remaining invocation time, then UPDATE to COMPLETED with the stored charge ID and a 24-hour TTL. Use Powertools rather than writing it. (2) <strong>Pass the same key to the payment gateway</strong> as its <code>Idempotency-Key</code> header, so the provider is a second line of defence. (3) <strong>Fix the batch configuration</strong>: set <code>BatchSize: 1</code> for money-moving work, or enable <code>ReportBatchItemFailures</code> and return only the failed message IDs. (4) <strong>Fix the visibility timeout</strong> to at least 6x the function timeout. (5) <strong>Reorder the handler</strong> so the durable record of the charge is written before anything that could throw — never do the irreversible thing last, after three fallible operations that can fail the invocation and trigger a redelivery of work that already happened.</p>\n<p style=\"line-height: 1.75\"><strong>Verify it.</strong> The test that proves the fix is an integration test that deliberately invokes the handler twice with the identical event and asserts the gateway was called exactly once and both invocations returned the same charge ID. If your test suite does not replay duplicates, you do not know whether you are idempotent — you are only hoping.</p>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"Every Lambda event source is at-least-once, so exactly-once processing is the consumer's job, not the platform's.
