First, <strong>changing the function timeout is a queue change</strong>: bump the function from 30 s to 120 s without touching the queue and you have silently created a duplicate-processing bug. Put both in the same IaC template and derive one from the other. SQS itself moves a message to the DLQ once <code>ApproximateReceiveCount</code> exceeds <code>maxReceiveCount</code>. This is the one that applies to Lambda's SQS integration, and the DLQ receives the <strong>full original message body</strong>.</li>\n<li><strong>Lambda's own DLQ (<code>DeadLetterConfig</code>) and <code>OnFailure</code> destinations.</strong> These apply to <strong>asynchronous</strong> invocation only. SQS event source mappings invoke <em>synchronously</em>, so Lambda's DeadLetterConfig is never exercised by an SQS trigger. Configuring it and expecting SQS failures to land there is a real and frequently-shipped bug.</li>\n</ul>\n<p style=\"line-height: 1.75\">Tuning <code>maxReceiveCount</code>: AWS guidance is at least 5. Too low (1–2) and any transient blip — a downstream 500, a brief throttle, a cold-start timeout — dead-letters real work. Too high (50) and a genuinely poisonous message spends a very long time consuming concurrency and polluting your error rate. Five is a sensible default when you use MaximumConcurrency rather than reserved concurrency for backpressure; if you are still using reserved concurrency, bias higher because throttles consume receive counts. Always set the DLQ's retention to the maximum of 14 days so you have time to investigate, alarm on <code>ApproximateNumberOfMessagesVisible &gt; 0</code> on the DLQ, and use SQS's <strong>DLQ redrive</strong> feature to replay messages back to the source queue once the bug is fixed.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Partial batch failures in the SQS context</h4>\n<p style=\"line-height: 1.75\">Because Lambda deletes messages only when the whole invocation succeeds, default behaviour is all-or-nothing: throw once and all ten (or one hundred) messages return to the queue, their receive counts all incremented. Every already-processed message gets re-processed, and the good messages march toward the DLQ alongside the bad one. Enabling <code>FunctionResponseTypes: [\"ReportBatchItemFailures\"]</code> and returning <code>{ batchItemFailures: [{ itemIdentifier: messageId }] }</code> makes Lambda <strong>delete the successes and leave only the listed failures</strong>. With standard queues this gives true per-message granularity, since there is no ordering constraint to preserve.</p>\n<p style=\"line-height: 1.75\">Deleting successfully-processed messages is not merely an optimization — it is what makes <code>maxReceiveCount</code> meaningful. Without it, receive count measures \"how many times the <em>batch</em> failed\", not \"how many times <em>this message</em> failed\", so the DLQ stops being a signal about bad messages and becomes a signal about bad batches. It also does not remove the need for <strong>idempotency</strong>: SQS is at-least-once, a visibility timeout can still expire mid-flight, and partial batch reporting narrows the duplicate window without closing it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">FIFO queues with Lambda</h4>\n<p style=\"line-height: 1.75\">FIFO queues change three things at once: ordering, deduplication, and parallelism.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Ordering is per message group ID, not per queue.</strong> Messages sharing a <code>MessageGroupId</code> are delivered in order and are processed <strong>one batch at a time</strong> — Lambda will not have two in-flight invocations for the same group. Different groups proceed independently and in parallel.</li>\n<li><strong>Message group ID is therefore your parallelism dial.</strong> Effective concurrency is bounded by the number of <em>active</em> message groups. Using <code>MessageGroupId: \"orders\"</code> for everything gives you a strictly serial consumer with a maximum concurrency of one, no matter what you configure. Using the customer ID (or order ID, or tenant ID) as the group gives you ordering where it matters and concurrency proportional to your number of distinct entities. This is the single most important FIFO design decision.</li>\n<li><strong>Batch size for FIFO is capped at 10</strong>, and a batch never spans message groups in a way that breaks ordering.</li>\n<li><strong>Head-of-line blocking is real.</strong> If a message in group G fails and is retried, every later message in G waits. With standard queues a poison message only blocks itself; with FIFO it blocks its entire group until the message is dead-lettered.</li>\n<li><strong>Partial batch failures on FIFO</strong> must respect order: Lambda stops at the first reported failure in the group and returns that message and everything after it in the group to the queue.</li>\n</ul>\n<p style=\"line-height: 1.75\">On <strong>exactly-once processing</strong>: FIFO queues offer exactly-once <em>delivery</em> semantics using a 5-minute deduplication window keyed on <code>MessageDeduplicationId</code> (or a content-based hash). That prevents the <em>producer</em> from enqueuing the same logical message twice within five minutes. It says nothing about your consumer. If your function times out after committing a side effect, the message becomes visible again and is delivered again — the deduplication window governs enqueue, not redelivery. So even on FIFO, <strong>your handler must be idempotent</strong>. Interviewers ask this specifically to see whether you understand that queue-level guarantees do not compose into application-level guarantees.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Backpressure design</h4>\n<p style=\"line-height: 1.75\">The whole point of putting a queue in front of Lambda is to absorb bursts that a downstream system cannot. But Lambda's default behaviour is to scale <em>toward</em> the burst, so without a cap the queue does not protect anything — it just delivers the burst faster. Backpressure is an explicit configuration decision.</p>\n<p style=\"line-height: 1.75\">Suppose the downstream is an RDS instance that safely supports 40 concurrent connections. Set <code>ScalingConfig.MaximumConcurrency: 40</code> (or lower, if each invocation opens multiple connections, or use RDS Proxy). What happens next is exactly what you want: during a spike, the queue depth grows, <code>ApproximateAgeOfOldestMessage</code> rises, and the database stays healthy. The queue converts a <em>capacity</em> problem into a <em>latency</em> problem, which is nearly always the better failure mode. You then reason about it numerically: if the cap sustains 200 messages/second and a burst delivers 500/second for 10 minutes, you accumulate 180,000 messages and take about 15 minutes to drain after the burst ends — so message retention (max 14 days) is fine, but your freshness SLA is not, and either the cap or the downstream needs to change.</p>\n<p style=\"line-height: 1.75\">Two related patterns: <strong>reserved concurrency of 0</strong> is the emergency stop — it instantly halts consumption without deleting the mapping or losing messages, which is the right first move during an incident where the consumer is corrupting data. And for multi-tenant fairness, <strong>separate queues with separate mappings and separate caps</strong> beat one queue with a shared cap, because a single noisy tenant otherwise consumes the whole allowance.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Monitoring: three metrics read together</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong><code>ApproximateAgeOfOldestMessage</code> (AWS/SQS).</strong> The real SLI. It answers \"how stale is the worst thing in the system\", which is what users feel. Alarm on it, not on depth.</li>\n<li><strong><code>ApproximateNumberOfMessagesVisible</code>.</strong> Depth. Useful for capacity reasoning and for spotting a stuck consumer, but a high-throughput queue can have high depth and low age, which is fine.</li>\n<li><strong><code>ApproximateNumberOfMessagesNotVisible</code>.</strong> In-flight. If this is high and steady while depth grows, work is being received but not completed — a timeout or hang.</li>\n<li><strong>Lambda <code>Throttles</code>.</strong> Read alongside the above. Rising age + rising throttles = concurrency starvation and, if you are using reserved concurrency, imminent false dead-lettering.</li>\n</ul>\n<p style=\"line-height: 1.75\">The diagnostic matrix: <em>age up, invocations up, throttles zero</em> means you are simply undersized — raise the cap or the batch size. <em>Age up, invocations up, throttles up</em> means the concurrency cap is binding. <em>Age up, invocations flat or zero</em> means the mapping is broken or disabled. <em>Age flat but DLQ filling</em> means a poison-message problem, not a capacity problem.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario: \"messages are being processed multiple times\"</h4>\n<p style=\"line-height: 1.75\">Support reports that customers are receiving duplicate order-confirmation emails. Diagnose systematically, cheapest checks first.</p>\n<p style=\"line-height: 1.75\"><strong>1. Confirm it is redelivery, not double-publish.</strong> Log <code>record.messageId</code> and <code>record.attributes.ApproximateReceiveCount</code> on every record. If duplicates share a <code>messageId</code> and receive count is &gt; 1, SQS redelivered. If they have different message IDs, the <em>producer</em> sent twice and the queue is innocent — check the upstream retry logic.</p>\n<p style=\"line-height: 1.75\"><strong>2. Check visibility timeout against function timeout.</strong> Queue visibility timeout 30 s, function timeout 60 s, observed p99 duration 42 s. That is the bug: messages reappear at t=30 while the first invocation is still running. Fix: visibility timeout to 360 s (6 × 60). Verify with <code>aws sqs get-queue-attributes --attribute-names VisibilityTimeout</code> against <code>aws lambda get-function-configuration --query Timeout</code>.</p>\n<p style=\"line-height: 1.75\"><strong>3. Check for batch-level replays.</strong> If receive counts are 2–3 across <em>whole batches</em> rather than individual messages, one poison record is failing the batch and dragging its neighbours. Look for <code>ReportBatchItemFailures</code> in the mapping; if absent, that is a second, independent cause of duplicates. Enable it.</p>\n<p style=\"line-height: 1.75\"><strong>4. Check for throttle-induced redelivery.</strong> Correlate the Lambda <code>Throttles</code> metric with the duplicate timestamps. Reserved concurrency of 10 against a burst produces throttled receives, which increment receive count and return messages immediately. Replace reserved concurrency with <code>ScalingConfig.MaximumConcurrency</code>.</p>\n<p style=\"line-height: 1.75\"><strong>5. Accept at-least-once and make it safe.</strong> Even after fixing all of the above, SQS standard guarantees at-least-once; a host failure mid-invocation will redeliver.
