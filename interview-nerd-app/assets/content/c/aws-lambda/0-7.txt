{"title":"Cold Starts and the Execution Environment Lifecycle","tags":["lambda","cold-start","performance","provisioned-concurrency"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Your Lambda code does not run in a vacuum — it runs inside an <strong>execution environment</strong>, a secure, isolated micro-VM that Lambda creates, keeps around for a while, and eventually destroys. Understanding that environment's lifecycle explains nearly every \"why is Lambda behaving like that?\" question a beginner has: why the first request is slow, why a global variable sometimes still holds last request's value, why /tmp is not empty, and why the fix for latency is sometimes code and sometimes money.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The three phases</h4>\n<p style=\"line-height: 1.75\">Every execution environment moves through <strong>Init</strong>, then one or many <strong>Invoke</strong> phases, then <strong>Shutdown</strong>.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Init.</strong> Lambda provisions the micro-VM, <strong>downloads your code</strong> (the zip from S3-backed storage, or pulls and unpacks your container image), <strong>starts the runtime</strong> (the Node.js, Python, Java or custom runtime process), and then <strong>runs your initialization code</strong> — everything at module/global scope outside the handler: imports, requires, SDK client construction, connection pool creation, reading a config file, loading a machine-learning model. Init has its own time limit of <strong>10 seconds</strong> for the standard path; if your global-scope code exceeds it, Lambda restarts the init and may charge you for the retry. Init duration is reported separately in the logs as <code>Init Duration</code>.</li>\n<li><strong>Invoke.</strong> Lambda passes the event to your handler function and waits for it to return. This is the only phase you are usually thinking about. The same environment can serve <strong>many sequential invocations</strong>, one at a time — never two concurrently.</li>\n<li><strong>Shutdown.</strong> When Lambda decides the environment is no longer needed, it stops the runtime and destroys the micro-VM. Lambda sends a shutdown signal to any registered <strong>extensions</strong>, giving them a brief window (typically up to 2 seconds) to flush telemetry. Your handler code does <em>not</em> get a reliable shutdown hook, which is why you should never buffer important data in memory hoping to flush it \"later\".</li>\n</ul>\n<p style=\"line-height: 1.75\">How long does an idle environment survive? AWS deliberately does not publish a guarantee. Empirically it is often on the order of minutes, but it depends on load, capacity, and Lambda's own scheduling. <strong>Never write code that depends on an environment being alive.</strong></p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cold start vs warm start, precisely</h4>\n<p style=\"line-height: 1.75\">A <strong>cold start</strong> is an invocation that could not be routed to an existing idle environment, so Lambda had to <strong>create a new execution environment</strong> and run the full Init phase before the handler could run. The user-visible latency of that request is therefore <em>Init Duration + handler Duration</em>. Lambda also recycles environments periodically for its own operational reasons.</p>\n<p style=\"line-height: 1.75\">Proportionally, cold starts are <strong>rare at steady load</strong>. A function receiving continuous traffic serves the overwhelming majority of requests warm; a typical production API might see cold starts on well under 1% of invocations. They hurt most for <strong>low-traffic functions</strong> (every request may be cold) and for <strong>spiky traffic</strong> (a burst creates many environments at once, so a slice of users all see the slow path simultaneously).</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What actually influences cold-start duration</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Deployment package size.</strong> Lambda must fetch and unpack your code. A 3 MB zip initialises faster than a 200 MB one. Bundle only what you ship: tree-shake, exclude dev dependencies, exclude tests and docs, and do not bundle the AWS SDK if the runtime already provides it. Container images behave a little differently — Lambda caches and lazily loads image layers, so a large image is not as catastrophic as the equivalent zip, but a lean image still starts faster.</li>\n<li><strong>Runtime choice.</strong> Interpreted, lightweight runtimes initialise fastest. <strong>Node.js and Python</strong> are typically in the low hundreds of milliseconds; <strong>Go and Rust</strong> (compiled, provided runtime) are often the fastest of all; <strong>Java and .NET</strong> historically have the heaviest Init because of JVM/CLR startup plus class loading and framework wiring, and can reach seconds for a large Spring application. This is precisely the gap SnapStart was built to close.</li>\n<li><strong>Initialization work in global scope.</strong> Anything expensive you do at module scope is paid on every cold start: loading a 300 MB model file, parsing a huge config, opening a database connection, fetching a secret, building a dependency-injection container. There is a genuine trade-off here, discussed below.</li>\n<li><strong>VPC configuration.</strong> This one has a history you should know. Historically, attaching a function to a VPC meant creating an <strong>elastic network interface</strong> per environment during Init, which added <em>many seconds</em> to cold starts and made VPC-attached Lambda a serious latency problem. AWS re-architected this: Lambda now uses <strong>Hyperplane ENIs</strong> — shared, pre-created network interfaces, created once per unique subnet-plus-security-group combination and reused across environments. The result is that <strong>the old multi-second VPC cold-start penalty is essentially gone</strong>; the residual cost is small. Saying this accurately — that it <em>used to be</em> a big deal and no longer is — is a strong signal of current knowledge, because a lot of blog content on the internet is still stuck in the pre-2019 world.</li>\n<li><strong>Memory setting.</strong> Since CPU scales with memory, more memory means faster Init as well as faster handler execution. A Java function at 256 MB may spend seconds in Init that largely disappears at 1,769 MB.</li>\n<li><strong>Extensions and layers.</strong> Each Lambda extension runs its own init and adds to the total. Layers must also be downloaded and mounted.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Mitigation 1: global scope as an amortization tool</h4>\n<p style=\"line-height: 1.75\">The standard optimisation is to move expensive, reusable setup <strong>outside the handler</strong>, into module/global scope. Construct your DynamoDB client, your HTTP agent with keep-alive, your database connection, your cached secret, your compiled regex, once at Init. Every subsequent <strong>warm</strong> invocation reuses them for free. Doing that work <em>inside</em> the handler means paying it on every single invocation, warm or cold — usually far worse in aggregate.</p>\n<p style=\"line-height: 1.75\">The nuance an interviewer likes: this <strong>shifts cost into Init</strong>, so it makes cold starts slower while making warm starts faster. For a high-traffic function that is a clear win. For a function invoked once an hour, where nearly every invocation is cold, aggressive global-scope initialisation can make things worse. And you should only initialise what <em>every</em> invocation needs — lazily initialise a client that only one rare code path uses.</p>\n<p style=\"line-height: 1.75\">Two related practices: enable <strong>HTTP keep-alive</strong> in the AWS SDK so connections are reused across invocations (this is the default in AWS SDK for JavaScript v3 and can be set via <code>AWS_NODEJS_CONNECTION_REUSE_ENABLED=1</code> for v2), and be careful with <strong>relational database connections</strong> in global scope — each environment holds its own connection, so 500 concurrent environments means 500 connections, which can exhaust a small RDS instance. That is what <strong>Amazon RDS Proxy</strong> exists to solve.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Mitigation 2: Provisioned Concurrency</h4>\n<p style=\"line-height: 1.75\"><strong>Provisioned Concurrency</strong> tells Lambda to create and keep warm a specified number of execution environments, fully <strong>initialized in advance</strong> — code downloaded, runtime started, global scope already executed — and held ready. Requests routed to those environments have <strong>no cold start</strong>; they go straight to the handler. You configure it on a <strong>version or alias</strong>, never on the unqualified <code>$LATEST</code>.</p>\n<p style=\"line-height: 1.75\">The trade-off is simple and financial: <strong>you pay for provisioned environments for as long as they are provisioned, whether or not any request uses them.</strong> Pricing has a per-GB-hour charge for keeping them warm, plus a (lower) duration charge for the requests they serve. If traffic exceeds your provisioned count, the overflow spills over into regular on-demand concurrency — and those spillover invocations <em>do</em> cold start. You can pair Provisioned Concurrency with <strong>Application Auto Scaling</strong> to scale the provisioned count on a schedule (for a predictable daily peak) or on a utilisation target.</p>\n<p style=\"line-height: 1.75\">Use it when cold starts genuinely hurt: a user-facing, latency-sensitive API with a strict p99 SLA, a heavy Java or .NET function, or a predictable traffic spike (a marketing launch, market open). Do not use it as a reflex — for most background and asynchronous workloads it is money spent for no user benefit.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Mitigation 3: SnapStart</h4>\n<p style=\"line-height: 1.75\"><strong>Lambda SnapStart</strong> attacks the same problem differently and, for supported runtimes, at <strong>no additional charge for the snapshot itself</strong>. When you publish a function version with SnapStart enabled, Lambda runs Init <strong>once</strong>, takes an encrypted <strong>Firecracker microVM snapshot</strong> of the fully initialized memory and disk state, caches it, and then <strong>restores from that snapshot</strong> instead of re-running Init for each new environment. It launched for <strong>Java</strong> (where the JVM warm-up cost made it most valuable, often cutting cold starts by an order of magnitude) and has since been extended to additional runtimes including <strong>Python and .NET</strong>. It requires publishing a <strong>version</strong> — SnapStart applies to published versions, not <code>$LATEST</code>.</p>\n<p style=\"line-height: 1.75\">The correctness caveat is the interesting part: because many environments are restored from <em>the same</em> snapshot, anything captured during Init is <strong>duplicated across environments</strong>. Second, <strong>network connections and credentials</strong> captured in the snapshot may be stale or expired on restore.
