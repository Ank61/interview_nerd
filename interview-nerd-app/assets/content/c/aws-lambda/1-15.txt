{"title":"Lambda Security Deep Dive — Least Privilege, Secrets, Code Signing, and the Confused Deputy","tags":["security","iam","secrets","code-signing"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Serverless does not remove security work, it <strong>relocates</strong> it. You no longer patch kernels or rotate SSH keys, but you now own a much larger number of <strong>identity boundaries</strong>. Every Lambda function is its own principal with its own execution role, its own resource-based policy, its own environment variables, and its own dependency tree. A 200-function estate is 200 identities to scope. The single highest-value security control in serverless is <strong>genuinely least-privilege IAM</strong>, and the most common real-world finding is that nobody actually does it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Execution Roles: One Role Per Function, Always</h4>\n<p style=\"line-height: 1.75\">The execution role is the identity Lambda assumes on your behalf before invoking your handler. The runtime injects temporary credentials for that role into the environment (<code>AWS_ACCESS_KEY_ID</code>, <code>AWS_SECRET_ACCESS_KEY</code>, <code>AWS_SESSION_TOKEN</code>), and the SDK picks them up automatically. Anything your code can do, that role can do — and anything an attacker who achieves code execution inside your function can do, that role can do too.</p>\n<p style=\"line-height: 1.75\">The anti-pattern is a shared role, typically named something like <code>lambda-execution-role</code>, attached to dozens of functions and accumulating permissions over time because every new function needed \"just one more\" action. This is a real security finding, not a style preference. The reason is <strong>blast radius</strong>: if a shared role grants <code>dynamodb:*</code> on the orders table, the S3 thumbnail resizer — which has no business touching orders — can read, write, and delete them. A remote code execution bug in an image parsing library in the thumbnailer now becomes a data breach in the orders system. With per-function roles, that same RCE gets the attacker exactly one bucket prefix.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>One role per function.</strong> IAM roles are free and have no runtime cost. There is no operational excuse for sharing. Infrastructure-as-code frameworks (SAM, CDK, Serverless Framework) create per-function roles by default — sharing is usually a deliberate regression someone introduced to \"reduce clutter.\"</li>\n<li><strong>Scope resources, not just actions.</strong> <code>\"Action\": \"dynamodb:GetItem\", \"Resource\": \"*\"</code> is barely better than a wildcard action. Name the exact table ARN, and the index ARN if you query an index (index ARNs are a separate resource: <code>table/Orders/index/status-index</code>).</li>\n<li><strong>Scope down to the item level where it matters.</strong> DynamoDB supports <code>dynamodb:LeadingKeys</code> in a condition, which restricts a principal to items whose partition key matches a value — the foundation of multi-tenant row isolation.</li>\n<li><strong>Avoid managed policies that are broader than they look.</strong> <code>AWSLambdaBasicExecutionRole</code> is fine (CloudWatch Logs only). <code>AmazonDynamoDBFullAccess</code> or <code>AmazonS3FullAccess</code> on a Lambda role is an automatic finding.</li>\n<li><strong>Use permissions boundaries in larger orgs.</strong> A boundary caps the maximum permissions any role a developer creates can have, so a self-service deployment pipeline cannot mint an admin role.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Tightening Policies Empirically</h4>\n<p style=\"line-height: 1.75\">Writing least privilege by hand is guesswork; you either over-grant defensively or under-grant and cause an outage. The mature approach is <strong>empirical</strong>: start slightly broad in a non-production account, observe what the function actually calls, then generate a tight policy from evidence.</p>\n<p style=\"line-height: 1.75\"><strong>IAM Access Analyzer policy generation</strong> reads CloudTrail history for a role over a chosen window and emits a candidate policy containing only the actions actually used. <strong>IAM Access Analyzer unused access findings</strong> flag roles with permissions that have not been exercised in N days, which is how you find the accumulated cruft on an old shared role. <strong>Access Analyzer external access findings</strong> flag resource policies (including Lambda resource-based policies) that grant access outside your account or organization — this is how you catch a function accidentally made invokable by <code>\"Principal\": \"*\"</code>. Also check <strong>Last Accessed</strong> data in the IAM console, which shows service-level usage per role and is the fastest way to spot \"this role has S3 permissions it has never used.\"</p>\n<p style=\"line-height: 1.75\">The workflow that works in practice: deploy with a generous-but-not-wildcard policy to a dev account, run the full integration test suite plus a representative production traffic replay, run policy generation over that window, diff the generated policy against what you had, and promote the tightened version. Repeat on a cadence, because dependencies drift.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Secrets: Why Plaintext Environment Variables Fail</h4>\n<p style=\"line-height: 1.75\">Environment variables are the tempting place to put a database password. They are also the wrong place, and the reason is precise: <strong>anyone with <code>lambda:GetFunctionConfiguration</code> can read them in plaintext</strong>. That permission is included in read-only roles, is frequently granted to support engineers, auditors, CI systems, and cost-analysis tools, and shows up in the console without any extra click. Environment variables also land in CloudFormation templates, in Terraform state files, in Git history, and in CloudTrail if someone passes them on an update call. A password in an environment variable has effectively been shared with everyone who has read access to your account.</p>\n<p style=\"line-height: 1.75\">There are three escalating levels of correctness:</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Approach</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">How it works</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Weakness</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Plaintext env var</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Encrypted at rest with an AWS managed key, decrypted automatically before the handler sees it</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Readable by anyone with GetFunctionConfiguration; no rotation; leaks into IaC and state files</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Env var with customer managed KMS key + encryption helpers</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Ciphertext is stored in the variable; the function calls <code>kms:Decrypt</code> at init. When you supply your own KMS key, Lambda stores the ciphertext and does <strong>not</strong> transparently decrypt on read — the console shows encrypted values, and your handler must explicitly call <code>kms:Decrypt</code>. Now reading the secret requires two permissions: <code>lambda:GetFunctionConfiguration</code> <em>and</em> <code>kms:Decrypt</code> on that specific key. You control the second through the key policy, which is a separate, auditable authorization boundary. Do the decrypt once at module init, not per invocation.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Secrets Manager, Parameter Store, and the Caching Extension</h4>\n<p style=\"line-height: 1.75\">The strongest pattern is <strong>AWS Secrets Manager</strong> (for credentials that rotate, especially RDS credentials with managed rotation) or <strong>SSM Parameter Store SecureString</strong> (cheaper, fine for configuration-grade secrets). The secret never touches the function's configuration. Access is governed by its own resource policy and IAM policy, every retrieval is logged to CloudTrail, and rotation is a first-class operation.</p>\n<p style=\"line-height: 1.75\">The naive implementation calls <code>GetSecretValue</code> at the top of every invocation. That is a mistake on three axes: it adds 20-80 ms of latency to every request, it costs money per API call at scale, and it will eventually hit the Secrets Manager request rate quota during a traffic spike, turning a secrets service into your availability bottleneck. The fix is caching:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Module-level cache.</strong> Fetch once outside the handler, reuse for the life of the execution environment. Simple, zero dependencies. The downside is that a rotated secret is not picked up until the environment recycles, which can be hours.</li>\n<li><strong>AWS Parameters and Secrets Lambda Extension.</strong> A Lambda layer that runs a local HTTP cache on <code>localhost:2773</code>. Your code makes a plain HTTP GET to <code>http://localhost:2773/secretsmanager/get?secretId=NAME</code> with the header <code>X-Aws-Parameters-Secrets-Token</code> set to <code>AWS_SESSION_TOKEN</code>. The extension handles the AWS API call, caching, and TTL. Configure with <code>SECRETS_MANAGER_TTL</code> and <code>SSM_PARAMETER_STORE_TTL</code> (seconds), and <code>PARAMETERS_SECRETS_EXTENSION_CACHE_SIZE</code>. This gives you a bounded staleness window that you choose, which is the right answer when secrets rotate.</li>\n<li><strong>Powertools parameters utility.</strong> The AWS Lambda Powertools libraries ship a parameters module with configurable TTL, which achieves the same thing in-process without an extension layer.</li>\n</ul>\n<p style=\"line-height: 1.75\">Whichever you pick, the rule is: a secret fetch must not be on the per-invocation hot path, and a rotated secret must be picked up within a bounded time without a deployment. Also handle the rotation race: if a database call fails with an auth error, invalidate the cache and retry once before giving up.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Resource-Based Policies and the Confused Deputy</h4>\n<p style=\"line-height: 1.75\">Execution roles answer \"what can this function do.\" <strong>Resource-based policies</strong> answer the opposite question: \"who can invoke this function.\" When you add an S3 trigger or an API Gateway integration, AWS adds a statement to the function's resource policy granting the relevant service principal <code>lambda:InvokeFunction</code>.</p>\n<p style=\"line-height: 1.75\">The <strong>confused deputy</strong> problem arises when that grant is written to a bare service principal:</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">Principal: s3.amazonaws.com      <i class=o>&lt;</i><i class=c>-- ANY S3 bucket, in ANY AWS account</i>\nAction:    lambda:InvokeFunction\nResource:  my<i class=o>-</i><i class=k>order</i><i class=o>-</i>processor\n\nAttacker <i class=k>in</i> account <i class=n>999999999999</i>:\n  creates bucket &quot;evil-bucket&quot;\n  configures notification <i class=o>-</i><i class=o>&gt;</i> your <i class=k>function</i> ARN\n  uploads crafted object\n     <i class=o>|</i>\n     v\nS3 (the trusted deputy) invokes YOUR <i class=k>function</i> <i class=k>with</i> THEIR event</code></pre></div>\n<p style=\"line-height: 1.75\">S3 is the \"confused deputy\": a trusted service tricked into using its authority on an attacker's behalf. Your function now processes attacker-controlled events, possibly writing attacker data into your database, or at minimum burning your concurrency. The fix is <strong>condition keys that pin the grant to a specific source</strong>:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>aws:SourceArn.</strong> Restricts to a specific bucket, rule, topic, or API. This is the strongest scoping and should be the default.</li>\n<li><strong>aws:SourceAccount.</strong> Restricts to resources in a given account. Necessary for S3 because bucket ARNs do not contain an account ID — an attacker cannot forge your account ID, so pair both conditions for S3.</li>\n<li><strong>Least-privilege actions.</strong> Grant <code>lambda:InvokeFunction</code>, never <code>lambda:*</code>. Pin to a specific alias or version ARN when you use aliases.</li>\n</ul>\n<p style=\"line-height: 1.75\">On the CLI this is <code>aws lambda add-permission</code> with <code>--source-arn</code> and <code>--source-account</code>. The same pattern applies to cross-account <code>sts:AssumeRole</code> trust policies, where the equivalent control is <code>sts:ExternalId</code>. Audit existing functions with <code>aws lambda get-policy</code> and look for any statement missing a Condition block — every one of those is a finding.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Code Signing and Supply Chain</h4>\n<p style=\"line-height: 1.75\"><strong>Code signing for Lambda</strong> enforces that only artifacts signed by a trusted publisher can be deployed. You create an <strong>AWS Signer</strong> signing profile, sign your deployment package (Signer produces a signed zip with an embedded signature), create a <strong>code signing configuration</strong> listing the allowed signing profile version ARNs, and attach it to the function. Lambda then validates on every <code>UpdateFunctionCode</code>: it checks that the signature is present and valid, that the signing profile is trusted, that the signature has not expired, and that the code has not been altered since signing.</p>\n<p style=\"line-height: 1.75\">The configuration has two enforcement policies for untrusted artifacts — <code>Warn</code> (logs to CloudTrail, allows the deploy) and <code>Enforce</code> (rejects the deploy). Use <code>Warn</code> to roll it out without breaking pipelines, then flip to <code>Enforce</code>. The control this gives you is real: an attacker who steals CI credentials with <code>lambda:UpdateFunctionCode</code> still cannot ship code unless they also control a trusted signing profile. Note that code signing applies to zip-packaged functions; container images use a different chain (ECR image scanning, and signing via tools such as Notation/Sigstore in the pipeline).</p>\n<p style=\"line-height: 1.75\"><strong>Dependency supply chain</strong> is the other half. A Lambda deployment package is usually mostly third-party code. Practices that matter: lockfiles committed and enforced (<code>npm ci</code>, <code>pip install --require-hashes</code>), automated vulnerability scanning (<strong>Amazon Inspector</strong> scans Lambda functions and layers for known CVEs in dependencies, and scans container images in ECR), pinning transitive versions, minimizing the dependency surface (bundlers and tree-shaking cut both cold start and attack surface), and reviewing <strong>layers you did not build</strong> — a third-party layer is arbitrary code running with your execution role.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Network Controls, Log Hygiene, and Tenant Isolation</h4>\n<p style=\"line-height: 1.75\"><strong>VPC attachment as defense in depth.</strong> A VPC-attached function with no NAT gateway has no outbound internet access, which meaningfully limits exfiltration and command-and-control if the function is compromised. Combine with <strong>VPC endpoints</strong> (interface endpoints for Secrets Manager, KMS, and the Lambda API; gateway endpoints for S3 and DynamoDB) so AWS API calls never traverse the internet, and attach <strong>endpoint policies</strong> restricting which buckets or secrets are reachable through the endpoint. Security groups on the function's ENIs control egress; lock egress down to the specific ports and destinations required rather than the default allow-all.</p>\n<p style=\"line-height: 1.75\"><strong>Log sanitization.</strong> CloudWatch Logs is broadly readable inside an account and is frequently shipped onward to a third-party SIEM. Logging a whole event object is the standard way secrets and PII escape: API Gateway events carry <code>headers.Authorization</code> and cookies; webhook events carry signing secrets; order events carry names, addresses, and sometimes card fragments. Enforce a redaction layer — never log raw event or raw request bodies, keep an explicit denylist of header and field names, and use Powertools Logger, which supports declaring keys to mask. Note also that <strong>unhandled exceptions log the stack trace</strong>, and some drivers put connection strings including passwords in exception messages. CloudWatch Logs data protection policies can detect and mask sensitive data patterns as a backstop, but treat that as a net, not the primary control.</p>\n<p style=\"line-height: 1.75\"><strong>Multi-tenant isolation.</strong> The weak pattern is one function with a broad role that reads a tenant ID from the event and trusts its own code to filter. One bug — a missing WHERE clause, a path traversal in a key prefix — is a cross-tenant breach, and IAM never saw the tenant boundary at all. Stronger options, in increasing order of isolation:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Dynamically scoped credentials.</strong> The function's own role can do very little. At invocation it calls <code>sts:AssumeRole</code> into a tenant-scoped role, or calls <code>AssumeRole</code> with an inline <code>Policy</code> parameter that narrows permissions to that tenant's key prefix or partition key. Downstream calls use the scoped credentials, so IAM — not your code — enforces the boundary.</li>\n<li><strong>Session tagging (ABAC).</strong> Call <code>AssumeRole</code> with <code>--tags Key=tenant,Value=acme</code>, and write the target resource policy with a condition comparing <code>aws:PrincipalTag/tenant</code> against a resource tag or a DynamoDB leading key. One role definition scales to thousands of tenants without policy sprawl.</li>\n<li><strong>Silo model.</strong> A separate function (or separate account) per tenant. Maximum isolation and the cleanest audit story; highest operational cost. Usually reserved for premium or regulated tenants.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario: Security Review of an Existing Function</h4>\n<p style=\"line-height: 1.75\">You are handed <code>process-payments</code>, a production function, and asked to review it. It has: the shared <code>lambda-execution-role</code> (which includes <code>dynamodb:*</code> on <code>*</code>, <code>s3:*</code> on <code>*</code>, and <code>secretsmanager:GetSecretValue</code> on <code>*</code>); a plaintext env var <code>STRIPE_SECRET_KEY</code>; a resource policy granting <code>apigateway.amazonaws.com</code> invoke with no conditions; <code>console.log(JSON.stringify(event))</code> on the first line; 47 npm dependencies, last updated 14 months ago; no VPC; no code signing. Prioritize by <strong>exploitability times impact</strong>, not by checklist order:</p>\n<ol style=\"margin-left: 1.5rem; line-height: 2\">\n<li><strong>P0 — Plaintext payment provider secret.</strong> Anyone with account read access can retrieve a live key that moves money. Immediate action: rotate the key at the provider (assume it is compromised), move it to Secrets Manager, fetch via the Parameters and Secrets extension with a TTL, remove the env var, and scrub it from IaC and Git history.</li>\n<li><strong>P0 — Logging the full event.</strong> An API Gateway event contains the Authorization header and the request body, so card-adjacent data and bearer tokens are sitting in CloudWatch Logs, likely with infinite retention, likely replicated to the SIEM. Immediate action: remove the log line, set retention, and treat the historical logs as a potential incident requiring scoping.</li>\n<li><strong>P1 — Unconditioned resource policy.</strong> <code>apigateway.amazonaws.com</code> with no <code>SourceArn</code> means any API Gateway in any account can invoke a payment function. Fix: <code>add-permission</code> with <code>--source-arn</code> pinned to your API's ARN and stage, and remove the old statement. Verify with <code>get-policy</code>.</li>\n<li><strong>P1 — Shared over-broad execution role.</strong> <code>dynamodb:*</code> and <code>s3:*</code> on <code>*</code> means any code execution here is full data-plane access to the account. Fix: dedicated role, explicit resource ARNs, driven by Access Analyzer policy generation over a CloudTrail window rather than guesswork. Then audit every other function on that shared role.</li>\n<li><strong>P2 — Stale dependency tree.</strong> 14 months of unpatched transitive dependencies. Fix: run Amazon Inspector against the function, patch criticals, and add automated dependency updates plus scanning as a pipeline gate.</li>\n<li><strong>P2 — No deployment integrity control.</strong> Anyone with <code>UpdateFunctionCode</code> can ship arbitrary code to a payments function. Fix: Signer profile plus a code signing configuration in <code>Warn</code>, then <code>Enforce</code>.</li>\n<li><strong>P3 — Network egress unrestricted.</strong> Not itself a breach, but it is what turns a dependency compromise into exfiltration. Consider VPC attachment with restricted egress plus VPC endpoints, accepting the added complexity.</li>\n</ol>\n<p style=\"line-height: 1.75\">The framing that scores points in an interview is the ordering rationale: live credentials and already-leaked data first, then things that let an outsider reach the function, then blast radius reduction, then integrity and hardening. Saying \"I would fix the IAM role first\" is defensible but weaker than \"a rotating payment key is already exposed to every read-only principal and every log reader, so that is P0.\"</p>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"Lambda security is mostly identity design.
