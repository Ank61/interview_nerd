{"title":"Triggers and Event Sources — What Actually Invokes a Function","tags":["lambda","triggers","event-sources","integration"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">A Lambda function on its own does nothing. It needs a <strong>trigger</strong> — something that causes Lambda's <code>Invoke</code> API to be called with an event payload. Understanding triggers is really understanding two things: <em>which</em> AWS services and entry points can invoke a function, and <em>how</em> the invocation is wired, because there are two fundamentally different mechanisms — <strong>push</strong> and <strong>poll</strong> — and they differ in who initiates the call, what permissions are required, and where you configure the integration.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Two Mechanisms: Push vs Poll</h4>\n<p style=\"line-height: 1.75\">This is the architectural distinction that separates people who have actually built on Lambda from people who have only read about it.</p>\n<p style=\"line-height: 1.75\"><strong>Push (the service calls Lambda).</strong> An AWS service such as S3, SNS, EventBridge, API Gateway, or an Application Load Balancer calls Lambda's <code>Invoke</code> API directly when something happens. The configuration usually lives <em>on the source service</em> (an S3 bucket notification configuration, an SNS subscription, an EventBridge rule target). For this to work, the source service must be <strong>allowed to invoke your function</strong>, which is expressed as a <strong>resource-based policy</strong> attached to the Lambda function — also called the function policy.</p>\n<p style=\"line-height: 1.75\"><strong>Poll (Lambda reads from the source).</strong> For stream and queue sources — <strong>SQS, Kinesis Data Streams, DynamoDB Streams, Amazon MQ, and managed Kafka</strong> — the source has no notion of pushing to Lambda. Instead, the Lambda service runs a fleet of <strong>pollers</strong> on your behalf that continuously read from the source and then invoke your function with a <em>batch</em> of records. The configuration lives <em>on the Lambda side</em> as an <strong>event source mapping (ESM)</strong>, a first-class AWS resource with its own ARN. Because Lambda's poller is reading the source using your function's identity, the permission required is the opposite direction: your <strong>execution role must have read permissions on the source</strong> (for example <code>sqs:ReceiveMessage</code>, <code>sqs:DeleteMessage</code>, and <code>sqs:GetQueueAttributes</code>).</p>\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">PUSH MODEL\n  S3 / SNS / EventBridge / API GW  --Invoke--&gt;  Lambda <i class=k>function</i>\n  config lives on the SOURCE                    needs RESOURCE POLICY on the <i class=k>function</i>\n  (bucket notification, rule target)            allowing that service principal\n\nPOLL MODEL\n  Lambda poller fleet  --Read--&gt;  SQS / Kinesis / DynamoDB Streams\n         |                        config lives on the LAMBDA side (event <i class=b>source</i> mapping)\n         +--Invoke (batch)--&gt;  Lambda <i class=k>function</i>\n                                 needs EXECUTION ROLE permissions to <i class=b>read</i> the <i class=b>source</i></code></pre></div>\n<p style=\"line-height: 1.75\">A useful mnemonic: <strong>if the source can talk, it pushes and needs a resource policy; if the source can only be read, Lambda polls and needs execution-role permissions.</strong></p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Category 1: AWS Service Events</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Amazon S3 (push, asynchronous).</strong> Bucket notifications fire on events like <code>s3:ObjectCreated:*</code> or <code>s3:ObjectRemoved:*</code>, optionally filtered by key prefix and suffix. Classic uses: thumbnail generation, virus scanning, ingesting uploaded CSVs. Configured on the bucket.</li>\n<li><strong>Amazon SNS (push, asynchronous).</strong> A Lambda function subscribes to a topic; every published message fans out to every subscriber. Good for one-to-many notification fan-out.</li>\n<li><strong>Amazon EventBridge (push, asynchronous).</strong> Two distinct uses. <em>Rules</em> match event patterns on the default bus (AWS service events like an EC2 state change) or a custom bus (your own application events). <em>Scheduled rules</em> — including EventBridge Scheduler — replace cron: run a function every five minutes, or at 02:00 UTC daily. This is the standard answer for \"how do I run a Lambda on a schedule?\"</li>\n<li><strong>Amazon SQS (poll).</strong> An event source mapping polls the queue and delivers batches of up to 10 messages by default. The workhorse pattern for decoupling and for absorbing bursts. Standard and FIFO queues are both supported.</li>\n<li><strong>Amazon Kinesis Data Streams (poll).</strong> Lambda reads records per shard in order, invoking with batches. Used for real-time analytics and clickstream processing. Ordering is preserved per shard.</li>\n<li><strong>Amazon DynamoDB Streams (poll).</strong> Every item-level change in a table becomes a stream record with old and new images. The canonical way to build change-data-capture, audit trails, materialized views, or cross-table denormalization.</li>\n<li><strong>Others worth naming.</strong> CloudWatch Logs subscription filters, Amazon Cognito user pool triggers, AWS Config rules, CloudFormation custom resources, IoT rules, Step Functions task states, Amazon MSK and self-managed Kafka, and Amazon MQ.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Category 2: HTTP-Facing Entry Points</h4>\n<p style=\"line-height: 1.75\">Three ways to put a function behind an HTTP endpoint, all <strong>push and synchronous</strong>:</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Entry point</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">What it adds</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Choose it when</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><strong>API Gateway</strong> (REST or HTTP API)</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Routing, request validation, authorizers (JWT, IAM, Lambda authorizers), throttling, usage plans and API keys, WAF, custom domains, stages</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">You are building a real API with multiple routes, auth, and rate limiting. The console hides this — clicking \"Add trigger\" silently creates the policy statement for you — but on the CLI or in infrastructure-as-code you must do it explicitly with <code>aws lambda add-permission</code>. Always scope the statement with <code>--source-arn</code> (the specific bucket or topic) and, for S3, <code>--source-account</code>, otherwise <em>any</em> bucket in <em>any</em> account could invoke your function. This is the classic <strong>confused deputy</strong> problem and interviewers like to probe it.</p>\n<p style=\"line-height: 1.75\">For <strong>poll</strong> sources the flow is: create the function with an execution role that can read the source, then create an <strong>event source mapping</strong> with <code>aws lambda create-event-source-mapping</code>. No resource policy is needed, because nothing external is calling <code>Invoke</code> — the Lambda service is. AWS provides managed policies for the common cases, such as <code>AWSLambdaSQSQueueExecutionRole</code>, <code>AWSLambdaKinesisExecutionRole</code>, and <code>AWSLambdaDynamoDBExecutionRole</code>, each of which bundles the required read permissions plus basic CloudWatch Logs access.</p>\n<p style=\"line-height: 1.75\">A frequently-missed detail for SQS: your function's execution role needs <code>sqs:DeleteMessage</code>, not just <code>sqs:ReceiveMessage</code>. Lambda deletes messages from the queue after a successful invocation; without delete permission, messages are processed and then reappear after the visibility timeout, producing an infinite reprocessing loop that looks baffling until you check the role.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario: \"Uploads to S3 should be processed, but processing is slow and bursty\"</h4>\n<p style=\"line-height: 1.75\">A naive design wires S3 directly to the function. That works, and S3 invokes asynchronously so Lambda will retry twice on failure — but there are weaknesses. S3 notifications give you no batching, no control over concurrency, limited retry configuration, and if the function is throttled during a large bulk upload you are relying on Lambda's internal async queue. The stronger answer is to insert a queue: <strong>S3 notification to SQS, then an event source mapping from SQS to Lambda.</strong></p>\n<p style=\"line-height: 1.75\">What this buys you: the queue is a durable buffer that absorbs the burst; batching reduces invocation count; <strong>reserved concurrency</strong> on the function lets you protect a fragile downstream database from being hammered by 500 parallel invocations; failed messages become visible again after the visibility timeout and, after the configured <code>maxReceiveCount</code>, land in a dead-letter queue you can inspect and replay. Note the permission model changes with the design: the first version needs a resource policy allowing <code>s3.amazonaws.com</code> to invoke; the second needs an S3 bucket notification targeting SQS (with an SQS queue policy allowing S3 to send), plus SQS read permissions on the Lambda execution role. Being able to trace where the permission lives in each design is exactly the depth the question is probing.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common Beginner Misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"SQS pushes messages to Lambda.\"</strong> It does not. Lambda's own poller fleet reads from the queue and then invokes your function. That is why the configuration lives on the Lambda side as an event source mapping and why permissions go on the execution role.</li>\n<li><strong>\"I need a resource policy for every trigger.\"</strong> Only for push sources. Poll-based sources need execution-role permissions instead, and adding a resource policy for SQS does nothing useful.</li>\n<li><strong>\"The execution role controls who can invoke my function.\"</strong> Backwards. The <strong>execution role</strong> says what your function may do to other services. The <strong>resource policy</strong> plus the caller's identity policy say who may invoke your function.</li>\n<li><strong>\"One event equals one record.\"</strong> S3 and SNS events arrive wrapped in a <code>Records</code> array, and poll-based sources deliver genuine batches of many records. Always iterate.</li>\n<li><strong>\"The same handler code works behind any trigger.\"</strong> Only if you keep trigger-specific parsing in a thin adapter layer. The raw event shapes are structurally unrelated.</li>\n<li><strong>\"Function URLs are just cheap API Gateway.\"</strong> They are far more limited: no request validation, no usage plans, no API keys, no WAF integration directly, and only <code>NONE</code> or <code>AWS_IAM</code> auth.
