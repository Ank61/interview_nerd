{"title":"Runtimes and Deployment Packages — Zip Archives, Container Images, and Layers","tags":["lambda","runtimes","deployment","layers"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Before Lambda can run your code it needs two things: a <strong>runtime</strong> — the language environment and the bootstrap process that talks to the Lambda service — and a <strong>deployment package</strong>, the artifact containing your code and its dependencies. Lambda offers managed runtimes for the major languages, a custom runtime escape hatch for everything else, two packaging formats with very different size limits, and <strong>layers</strong> as a way to share dependencies across functions. Getting these choices right determines your cold-start latency, your build pipeline, and how much ongoing maintenance you sign up for.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Managed Runtimes</h4>\n<p style=\"line-height: 1.75\">A <strong>managed runtime</strong> is a language environment that AWS builds, hosts, and patches. You select one by identifier when you create the function — for example <code>nodejs22.x</code>, <code>python3.13</code>, <code>java21</code>, <code>dotnet8</code>, or <code>ruby3.3</code>. AWS maintains the underlying Amazon Linux image, applies security patches to the OS and to the language runtime, and rolls those updates out to your function without any action from you.</p>\n<p style=\"line-height: 1.75\">Go is the notable special case. The old <code>go1.x</code> runtime is gone; modern Go functions compile to a static binary and run on the <strong><code>provided.al2023</code></strong> OS-only runtime, using the <code>aws-lambda-go</code> library to handle the runtime protocol. Rust, C++, and anything else compiled follow the same pattern. This is why you will hear <code>provided.al2023</code> described both as \"the custom runtime\" and as \"the Go runtime\" — it is the same thing.</p>\n<p style=\"line-height: 1.75\">Every runtime also sets standard <strong>environment variables</strong> your code can read: <code>AWS_REGION</code>, <code>AWS_LAMBDA_FUNCTION_NAME</code>, <code>AWS_LAMBDA_FUNCTION_MEMORY_SIZE</code>, <code>AWS_LAMBDA_LOG_GROUP_NAME</code>, the credentials of the execution role, and <code>LAMBDA_TASK_ROOT</code> (where your code is unpacked, <code>/var/task</code>). Managed runtimes for Node.js and Python also bundle an AWS SDK, though relying on the bundled version is a mild anti-pattern — its version can change underneath you, so pinning the SDK in your own package is safer for reproducibility.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Runtime Deprecation Is Your Ongoing Responsibility</h4>\n<p style=\"line-height: 1.75\">This is the part beginners routinely miss, and it maps directly onto the shared responsibility model. AWS patches the runtime; AWS does <strong>not</strong> migrate you across major versions. When a language version reaches community end-of-life, AWS announces a deprecation schedule for the corresponding runtime, typically in two phases:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Phase 1 — end of support.</strong> The runtime stops receiving security patches and bug fixes. Existing functions keep running and can still be invoked, but you are now running unpatched software.</li>\n<li><strong>Phase 2 — block function create, then block function update.</strong> You can no longer create new functions on the runtime, and eventually you can no longer update the code or configuration of existing ones.</li>\n</ul>\n<p style=\"line-height: 1.75\">Practically, this means <strong>runtime upgrades are a recurring maintenance task you must plan for</strong>, roughly annually per function. AWS emails account contacts and surfaces warnings in the console and in AWS Health, and you can audit your fleet with a simple CLI query. Being able to say \"we track runtime deprecation notices and have a scheduled upgrade cadence\" is a genuinely strong interview answer, because it demonstrates you have operated Lambda rather than just deployed to it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Custom Runtimes and the Lambda Runtime API</h4>\n<p style=\"line-height: 1.75\">If your language is not on the managed list, you can bring your own. The <strong><code>provided.al2023</code></strong> runtime (and the older <code>provided.al2</code>) gives you a bare Amazon Linux environment and expects your package to contain an executable file named <strong><code>bootstrap</code></strong> at the root. That executable implements the <strong>Lambda Runtime API</strong>, a simple HTTP protocol served on the address in the <code>AWS_LAMBDA_RUNTIME_API</code> environment variable:</p>\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">bootstrap process loop:\n\n  GET  http://<i class=v>$AWS_LAMBDA_RUNTIME_API</i>/2018-06-01/runtime/invocation/next\n       -&gt; blocks <i class=k>until</i> an event arrives\n       -&gt; response body = the event JSON\n       -&gt; Lambda-Runtime-Aws-Request-Id header = the request ID\n\n  ... run the handler ...\n\n  POST .../2018-06-01/runtime/invocation/&lt;requestId&gt;/response   (success)\n  POST .../2018-06-01/runtime/invocation/&lt;requestId&gt;/error      (failure)\n\n  loop back to /next</code></pre></div>\n<p style=\"line-height: 1.75\">That is the whole contract. Understanding it demystifies Lambda considerably — and it explains why a <em>container image</em> can run on Lambda at all: the image simply has to contain something that speaks this protocol.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Packaging Option 1: The .zip Deployment Package</h4>\n<p style=\"line-height: 1.75\">The classic format. A zip archive containing your handler file at the root plus all dependencies — <code>node_modules/</code> for Node.js, the installed packages for Python. Lambda extracts it to <code>/var/task</code> in the execution environment.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>50 MB</strong> maximum for a direct upload via the API or CLI (<code>--zip-file</code>).</li>\n<li><strong>250 MB</strong> maximum <em>unzipped</em>, and this quota includes the contents of all attached layers. This is the limit people actually hit.</li>\n<li>Larger zips (above 50 MB compressed) must be uploaded to <strong>S3 first</strong> and referenced with <code>--code S3Bucket=...,S3Key=...</code>.</li>\n<li>If the package is small enough — roughly <strong>3 MB</strong> — the console shows the built-in code editor and you can edit the function inline. Above that, the console shows the code as read-only and you must deploy from a file or S3. This is a handy diagnostic: if the inline editor disappeared, your package grew.</li>\n</ul>\n<p style=\"line-height: 1.75\">The two classic zip mistakes are worth memorizing. First, <strong>zipping the folder rather than its contents</strong>, producing <code>myapp/index.js</code> when Lambda wants <code>index.js</code> at the root — this yields <code>Unable to import module</code>. Second, <strong>building native dependencies on the wrong platform</strong>: a Python package with C extensions compiled on macOS will not load on Amazon Linux, and an x86 build will not run on an <code>arm64</code> (Graviton) function. Build inside a matching container or use a build tool that handles this.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Packaging Option 2: Container Images</h4>\n<p style=\"line-height: 1.75\">Since 2020 Lambda can run OCI container images up to <strong>10 GB</strong>, pushed to <strong>Amazon ECR</strong> in the same Region as the function. Reach for a <strong>container image</strong> when your dependencies genuinely exceed 250 MB (large ML libraries such as PyTorch or SciPy are the canonical case), when you need OS-level packages or binaries like <code>ffmpeg</code> that are painful to vendor into a zip, when your organization has standardized on container tooling and you want one build pipeline for Lambda and ECS alike, or when you need a runtime AWS does not manage.</p>\n<p style=\"line-height: 1.75\">The trade-off that is easy to miss: a container image shifts patching responsibility onto you. There is no managed runtime underneath, so when the base image receives a security update you must rebuild and redeploy. You gain control and pay for it in maintenance. Note also that Lambda optimizes and caches container images on first use, so a very large image adds cold-start cost on the first pull even though subsequent cold starts benefit from caching.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Lambda Layers</h4>\n<p style=\"line-height: 1.75\">A <strong>layer</strong> is a .zip archive of libraries, dependencies, or other content that Lambda extracts into <strong><code>/opt</code></strong> in the execution environment before your handler runs. list-style: disc; line-height: 2\">\n<li><strong>Up to 5 layers</strong> per function.</li>\n<li><strong>Layers count toward the 250 MB unzipped limit.</strong> This is the most important and most misunderstood fact about layers — they do <em>not</em> give you more space. Moving a 200 MB dependency from your package into a layer changes nothing about the total.</li>\n<li><strong>Versioned and immutable.</strong> Publishing creates a new numbered version; you attach a specific version ARN ending in a number. An existing version can never be modified, which makes deployments reproducible. To update a dependency you publish a new version and update each function to point at it — there is no auto-upgrade.</li>\n<li><strong>Extracted read-only to /opt</strong> before the handler runs, and merged in the order the layers are attached, so later layers can overwrite earlier ones.</li>\n<li><strong>Shareable</strong> across functions, across accounts via a layer permission, or publicly. AWS publishes useful ones, such as the AWS Parameters and Secrets Lambda Extension and the Lambda Insights extension.</li>\n<li><strong>Not supported for container-image functions</strong> — use Docker image layers there instead.</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>What layers are not:</strong> they are <em>not a package manager</em>. There is no dependency resolution, no version constraint solving, no transitive dependency handling. A layer is a bag of files dropped into <code>/opt</code>. If two layers both contain a different version of the same library, the later one silently wins. And because layers are separate from your function's build, they are easy to drift out of sync with the versions your code was tested against. For this reason many teams now favour bundling dependencies directly into the package (with a bundler like esbuild, which often produces a smaller artifact than the layer would have been) and reserve layers for genuinely cross-cutting concerns: shared internal utility libraries used by dozens of functions, large binaries, and Lambda extensions.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario: \"Our ML inference function won't deploy — the package is 400 MB\"</h4>\n<p style=\"line-height: 1.75\">Establish the limit being hit: 400 MB unzipped exceeds the <strong>250 MB unzipped quota</strong>, which includes layers, so the first thing to say is that <em>moving the dependency into a layer will not help</em>. Then work through the options in order. First, <strong>trim</strong>: strip tests, docs, and <code>.pyc</code> files from the vendored packages, drop unused optional dependencies, and check whether a slimmer distribution exists — a CPU-only build of a deep-learning framework is often a fraction of the size of the default wheel. Second, <strong>externalize the model</strong>: model weights frequently dominate the package, and they can live in S3 and be downloaded to <code>/tmp</code> during INIT, or be mounted from EFS. Since ephemeral storage is configurable up to 10 GB, this is very workable and has the bonus that you can update the model without redeploying. Third, if the <em>libraries themselves</em> are genuinely too large after trimming, switch to a <strong>container image</strong>, which raises the ceiling to 10 GB and makes installing system-level dependencies straightforward. Finally, sanity-check whether Lambda is still the right service at all: if a single inference takes minutes and traffic is steady, Fargate or SageMaker endpoints may fit better than a function with a 15-minute cap. Naming the limit correctly, and explicitly rejecting the layer red herring, is what distinguishes a strong answer here.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common Beginner Misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"Layers let me get around the size limit.\"</strong> They do not. Their purpose is sharing and deduplication, not extra capacity.</li>\n<li><strong>\"Layers are a package manager.\"</strong> No resolution, no version constraints, no transitive dependencies — just files copied into <code>/opt</code>. Conflicting layers silently overwrite each other in attachment order.</li>\n<li><strong>\"I can update a layer in place.\"</strong> Layer versions are immutable. Publishing produces a new version number, and every function must be updated to the new version ARN explicitly.</li>\n<li><strong>\"AWS will upgrade my runtime automatically.\"</strong> AWS patches within a runtime version but never migrates you across major versions. Moving off a deprecated runtime is your job, and eventually you will be blocked from updating the function at all.</li>\n<li><strong>\"Container images are always slower to cold start.\"</strong> Not necessarily. Lambda optimizes and caches images, and a well-built image can cold start comparably to a zip. Use Docker image layers instead.</li>\n<li><strong>\"My package works locally so it'll work on Lambda.\"</strong> Native extensions must be built for <strong>Amazon Linux</strong> and for the right <strong>architecture</strong> — x86_64 or arm64.
