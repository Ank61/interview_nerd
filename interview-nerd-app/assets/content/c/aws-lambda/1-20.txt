With JSON log format enabled, or via the Telemetry API, these arrive as structured fields rather than requiring regex parsing.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 1: The Function Times Out</h4>\n<p style=\"line-height: 1.75\">The log ends with <code>Task timed out after N.NN seconds</code> and there is no stack trace, because <strong>a timeout is not an exception</strong> — the execution environment is killed and your <code>catch</code> and <code>finally</code> blocks never run. That is why you cannot log \"what I was doing when I died\" unless you instrumented before the fact.</p>\n<p style=\"line-height: 1.75\"><strong>Discriminate three causes.</strong> Query the Duration distribution: <code>filter @type = \"REPORT\" | stats count(*) by bin(5m), (@duration &gt; 29000)</code> or compare percentiles.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Bimodal distribution</strong> — most invocations are fast, a few pin exactly at the timeout. This is a <strong>downstream hang</strong>: a specific request hits a slow or unresponsive dependency. Check X-Ray subsegment durations for that trace, or the downstream's own latency metrics for the same window. The fix is almost always a <strong>client-side timeout shorter than the Lambda timeout</strong> — an SDK or HTTP client with no configured timeout will happily wait longer than the function can live. Set <code>connectTimeout</code> and <code>requestTimeout</code> on AWS SDK clients, and a socket timeout on HTTP clients.</li>\n<li><strong>Uniformly slow and scaling with input size</strong> — this is <strong>CPU starvation</strong>. Lambda allocates CPU proportionally to configured memory, so a 128 MB function gets a fraction of a vCPU. Run a memory sweep (AWS Lambda Power Tuning): if doubling memory roughly halves Duration, you are CPU-bound, and the larger size may be <em>cheaper</em> because you pay GB-seconds. Confirm with CloudWatch Lambda Insights CPU metrics, or by comparing total X-Ray subsegment time against total Duration — a large unexplained gap is your own compute.</li>\n<li><strong>Only VPC-attached functions affected, and only for internet destinations</strong> — this is a <strong>missing egress path</strong>. A Lambda in a VPC has no public IP; it needs a NAT gateway in a public subnet with a route, or a VPC endpoint. A common and confusing variant: the function is in a <em>public</em> subnet, which does <strong>not</strong> work, because without a public IP the internet gateway is useless. The symptom is a connection that hangs until the function times out rather than failing fast. Verify the route table for the function's subnets, and test reachability from an EC2 instance in the same subnet.</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>Commands and fields:</strong> <code>aws lambda get-function-configuration --function-name F --query '[Timeout,MemorySize,VpcConfig]'</code>; CloudWatch <code>Duration</code> p50/p99 versus the configured timeout; X-Ray subsegments; the <code>context.getRemainingTimeInMillis()</code> value logged before each downstream call, which is the cheapest way to make future timeouts self-explanatory.</p>\n<h4 style=\"margin-top: 1.5rem; Correlate the error onset timestamp against those events. If a deployment lines up, roll back first (shift the alias back to the previous version) and diagnose afterwards.</p>\n<p style=\"line-height: 1.75\">Then classify the errors rather than reading them one at a time: <code>filter level = \"ERROR\" | stats count(*) by errorType</code> in Logs Insights. A single dominant error type is a code or dependency bug; a broad spread across types usually means an environmental problem (a downstream outage, a credential expiry, a network change). Also check whether the spike is in <strong>rate</strong> or just in <strong>volume</strong> — a raw Errors count rises with traffic, so always divide by <code>Invocations</code>. And for asynchronous invocations, remember the platform retries twice, so one bad event produces three Errors datapoints.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 3: Throttles</h4>\n<p style=\"line-height: 1.75\">The <code>Throttles</code> metric is non-zero, and callers see <code>TooManyRequestsException</code> / HTTP 429 with <code>Rate Exceeded</code>. Three distinct causes, distinguished by what else is true:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Account concurrency exhaustion.</strong> <code>ConcurrentExecutions</code> across the account is at the regional quota (1,000 by default, often raised). Check the account-level <code>ConcurrentExecutions</code> metric with no function dimension, and <code>aws service-quotas get-service-quota --service-code lambda --quota-code L-B99A9384</code>. The tell is that <em>multiple unrelated functions</em> throttle at once. Fix: request a quota increase, and use <strong>reserved concurrency</strong> to partition the pool so a noisy function cannot starve critical ones.</li>\n<li><strong>Reserved concurrency cap on this function.</strong> Only this function throttles, and its <code>ConcurrentExecutions</code> flatlines exactly at a round number. <code>aws lambda get-function-concurrency</code> confirms. Note that setting reserved concurrency to <strong>0</strong> disables the function entirely — a legitimate emergency stop, and also a way someone accidentally takes a function offline.</li>\n<li><strong>Burst limit during a sharp ramp.</strong> Even with headroom, Lambda scales in defined increments; a step-function traffic spike can throttle briefly while capacity is added. The tell is throttles that appear only at the leading edge of a spike and clear within a minute or two. Fix: <strong>provisioned concurrency</strong> for predictable spikes, or a queue to absorb the burst.</li>\n<li><strong>Downstream-imposed limit.</strong> Not a Lambda throttle at all — the function's own calls get throttled (DynamoDB <code>ProvisionedThroughputExceededException</code>, Secrets Manager rate limits, a third-party API 429). These surface as function <em>errors</em>, not Lambda Throttles. Distinguish by checking whether <code>Throttles</code> is zero while <code>Errors</code> is high.</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>The consequences of a throttle differ by invocation type, and this is a favourite interview probe.</strong> <strong>Synchronous</strong> (API Gateway, direct invoke, Function URL): the caller immediately receives a 429 and the request is <em>lost</em> unless the caller retries — user-visible failure. <strong>Asynchronous</strong> (S3, SNS, EventBridge, async invoke): Lambda retries from its internal queue with backoff for up to six hours, so throttles are usually absorbed invisibly; only after the retry window expires does the event go to the DLQ or on-failure destination. <strong>Poll-based with a queue</strong> (SQS): the message simply returns to the queue after the visibility timeout and is retried — but watch <code>ApproximateAgeOfOldestMessage</code>, and be aware that persistent throttling plus a maxReceiveCount will eventually push messages to the DLQ. <strong>Poll-based with a stream</strong> (Kinesis, DynamoDB Streams): the shard blocks and retries the same batch, so throttling directly drives <code>IteratorAge</code> upward and risks record expiry.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 4: Memory Exhaustion / OOM Kill</h4>\n<p style=\"line-height: 1.75\">The signature is abrupt: the log shows <code>Runtime exited with error: signal: killed</code> or <code>Error: Runtime exited</code>, and the REPORT line shows <code>Max Memory Used</code> equal to (or essentially equal to) <code>Memory Size</code>. <strong>An OOM kill is not a catchable exception</strong> — the process is terminated by the kernel, so there is no stack trace, no <code>finally</code>, and no clean error message. That abruptness is itself diagnostic: an unexplained termination with no exception is almost always OOM or timeout, and the REPORT line tells you which.</p>\n<p style=\"line-height: 1.75\"><strong>Two distinct shapes.</strong> The first is <strong>genuinely under-provisioned</strong>: the function loads a large file or holds a big result set, and memory scales with input size. Fix by raising memory or, better, by streaming rather than buffering — process an S3 object as a stream rather than calling a \"read whole body\" helper, and paginate rather than collecting all results.</p>\n<p style=\"line-height: 1.75\">The second is a <strong>leak across warm invocations</strong>, and it is the more interesting one because it is specific to Lambda's execution model. Module-level state persists between invocations in the same environment, so anything that <em>appends</em> at module scope grows unboundedly: a cache with no eviction, an array of request metadata, event listeners registered inside the handler on a module-scope emitter, connection pools created per invocation instead of once, unresolved promises retained by a global, or files written to <code>/tmp</code> and never deleted (<code>/tmp</code> persists across invocations in the same environment and is bounded — 512 MB by default, configurable to 10 GB — so this produces <code>ENOSPC</code> rather than OOM, but the pattern is identical). The tell is <strong>Max Memory Used climbing with invocation count within a single environment</strong>, and errors that disappear after a deployment (which recycles all environments) then return hours later. Query it directly: <code>filter @type = \"REPORT\" | stats max(@maxMemoryUsed) by bin(30m)</code> and look for a sawtooth.</p>\n<p style=\"line-height: 1.75\"><strong>Commands and fields:</strong> <code>Max Memory Used</code> in REPORT (also available as a structured field via JSON logs and the Telemetry API); CloudWatch Lambda Insights <code>memory_utilization</code>; and remember that <strong>extensions share the function's memory</strong>, so adding an APM layer can push a previously fine function over the edge. Set memory with headroom — running at 95% of configured memory is not \"efficient\", it is one payload-size outlier away from an incident.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 5: No Logs At All</h4>\n<p style=\"line-height: 1.75\">The log group is empty, or has no recent streams. There are exactly two families of cause, and they are easy to separate by checking the <code>Invocations</code> metric.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Invocations &gt; 0 but no logs — a permissions problem.</strong> The execution role lacks <code>logs:CreateLogGroup</code>, <code>logs:CreateLogStream</code>, or <code>logs:PutLogEvents</code> (normally supplied by the <code>AWSLambdaBasicExecutionRole</code> managed policy). The function runs fine and you are simply blind. Variants: the role is scoped to a log group ARN that does not match the actual group; a <strong>permissions boundary</strong> or an SCP denies the logs actions; the function is configured with a <strong>custom log group</strong> and you are looking at the default one; or a KMS key used to encrypt the log group denies the role <code>kms:Decrypt</code>. Fix by checking the role's attached policies and, for a custom group, <code>aws lambda get-function-configuration --query LoggingConfig</code>.</li>\n<li><strong>Invocations = 0 — the function is never being invoked.</strong> The trigger is broken, not the logging. Check the <strong>resource-based policy</strong> (<code>aws lambda get-policy</code>) — if the service principal grant is missing, the caller gets AccessDenied and Lambda never sees the request. Check the <strong>event source mapping</strong> is present and <code>State: Enabled</code> (<code>aws lambda list-event-source-mappings</code>); a mapping can be auto-disabled after repeated failures. Check the S3 bucket notification configuration or the EventBridge rule actually matches (the rule's <code>MatchedEvents</code> metric being zero is conclusive — the events are being published but no rule matches, which is usually schema drift). Check you are looking at the right <strong>alias or version</strong>, since traffic may be going to <code>$LATEST</code> while you inspect an alias, or the reverse.</li>\n</ul>\n<p style=\"line-height: 1.75\">A third, subtler case: <code>Invocations &gt; 0</code>, logs exist, but your own log lines are missing while REPORT lines appear. That is a log-level filter — Lambda's <code>ApplicationLogLevel</code> is set above your log statements' level, filtering them before ingestion.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 6: Climbing IteratorAge</h4>\n<p style=\"line-height: 1.75\"><code>IteratorAge</code> (Kinesis and DynamoDB Streams) is the age of the last record processed — in effect, how far behind real time you are. A steadily climbing value means <strong>your consumer is slower than the producer</strong>, and it is urgent because stream records expire (DynamoDB Streams at 24 hours, Kinesis at 24 hours by default, extendable). Once age exceeds retention, <strong>data is permanently lost</strong>. This is a paging alarm, not a dashboard metric.</p>\n<p style=\"line-height: 1.75\">Diagnose by asking whether the problem is throughput or a stuck batch:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Insufficient parallelism.</strong> Lambda processes one batch per shard at a time, so your maximum concurrency equals the shard count — unless you raise <code>ParallelizationFactor</code> (up to 10 concurrent batches per shard, preserving per-partition-key order). If IteratorAge rises with producer volume and Duration is stable, you need more shards or a higher parallelization factor.</li>\n<li><strong>Slow processing.</strong> Duration per batch is high. Raise <code>BatchSize</code> only if per-record overhead dominates; otherwise optimise the handler or raise memory for CPU. Check whether the consumer is doing a synchronous call per record that should be batched.</li>\n<li><strong>A poison-pill batch.</strong> The classic and most damaging case: one record always fails, the batch is retried forever, and the shard makes <em>no progress at all</em> while the whole stream backs up behind it. The tell is IteratorAge rising linearly with a flat Invocations count and repeated identical errors. Fixes on the event source mapping: <code>BisectBatchOnFunctionError</code> (splits the batch to isolate the bad record), <code>MaximumRetryAttempts</code> and <code>MaximumRecordAgeInSeconds</code> (so a batch is eventually discarded rather than blocking forever), <code>FunctionResponseTypes: ReportBatchItemFailures</code> (return only the failed sequence numbers so successful records are checkpointed), and <code>DestinationConfig.OnFailure</code> to capture discarded batches for later analysis.</li>\n<li><strong>Throttling of the consumer.</strong> If the function is being throttled, the shard blocks. Check <code>Throttles</code> alongside IteratorAge.</li>\n</ul>\n<p style=\"line-height: 1.75\">The SQS equivalent is <code>ApproximateAgeOfOldestMessage</code> on the queue, with the same interpretation and largely the same fixes (batch size, <code>MaximumConcurrency</code> on the mapping, partial batch responses, a DLQ with a sensible <code>maxReceiveCount</code>).</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 7: Intermittent Networking Failures (VPC)</h4>\n<p style=\"line-height: 1.75\">Symptoms are erratic: connection timeouts that come and go, DNS resolution failures, failures correlated with traffic spikes. Because Lambda moved to shared <strong>Hyperplane ENIs</strong>, ENIs are created per unique combination of subnet and security group rather than per concurrent execution, which removed the old cold-start ENI penalty — but the underlying resources are still finite. Work through this order:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Subnet IP exhaustion.</strong> Every ENI consumes an IP from the subnet. A <code>/28</code> subnet has 11 usable addresses; add other workloads and you run out. The error is <code>EC2ThrottledException</code> or an ENI creation failure, and it appears as init failures under scaling. Check <code>AvailableIpAddressCount</code> with <code>aws ec2 describe-subnets</code>. Fix: larger subnets, and always attach the function to <strong>at least two or three subnets in different Availability Zones</strong> — both for IP capacity and because a single-AZ attachment means an AZ event takes the function down.</li>\n<li><strong>NAT gateway throughput or port exhaustion.</strong> A NAT gateway supports a bounded number of simultaneous connections to a single destination address and port (around 55,000). A high-concurrency function hammering one external API exhausts ports, producing <code>ErrorPortAllocation</code> on the NAT gateway metrics and intermittent connection failures. Check the NAT gateway's <code>ErrorPortAllocation</code> and <code>PacketsDropCount</code>. Fix: multiple NAT gateways (one per AZ, which you want anyway for resilience and to avoid cross-AZ data charges), connection reuse (<code>keep-alive</code>, and reusing SDK clients at module scope), and <strong>VPC endpoints</strong> for AWS services so that traffic never touches the NAT at all — this is usually the biggest single win.</li>\n<li><strong>DNS.</strong> Resolution failures at high concurrency can come from Route 53 Resolver limits (a per-ENI packets-per-second cap) or from a custom DHCP option set pointing at an on-premises DNS server that cannot take the load. Symptom: <code>EAI_AGAIN</code> or <code>getaddrinfo</code> failures. Mitigate with connection reuse and by caching DNS appropriately.</li>\n<li><strong>Security groups and NACLs.</strong> These fail deterministically rather than intermittently, so if the symptom is intermittent they are usually not the cause — but verify egress rules allow the destination port, that the destination's security group allows the Lambda security group as a source, and that NACLs permit the <strong>ephemeral port range on the return path</strong>, which is the classic NACL mistake.</li>\n<li><strong>Cross-AZ and endpoint policies.</strong> If a VPC interface endpoint exists in only one AZ but the function runs in three, calls from the other AZs fail or cross AZs. And an overly restrictive <strong>endpoint policy</strong> produces AccessDenied that looks like a networking problem.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 8: Duplicate Processing</h4>\n<p style=\"line-height: 1.75\">Customers are charged twice, emails are sent twice, counters are wrong. The root fact is that <strong>Lambda guarantees at-least-once delivery for asynchronous and poll-based sources</strong>; exactly-once is not on offer. Sources of duplication, in rough order of frequency:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Visibility timeout shorter than processing time (SQS).</strong> This is the number one cause and it is entirely self-inflicted. If processing takes 40 seconds and the visibility timeout is 30, the message becomes visible again and a second consumer picks it up while the first is still working — and it will happen <em>every time</em> under load. The rule: set the queue's visibility timeout to at least <strong>six times the function timeout</strong> (the AWS guidance), and always make the function timeout shorter than the visibility timeout. Verify with <code>aws sqs get-queue-attributes --attribute-names VisibilityTimeout</code> against <code>aws lambda get-function-configuration --query Timeout</code>.</li>\n<li><strong>Platform retries on async invocation.</strong> Lambda retries a failed async invocation twice by default. If your handler succeeded in its side effect and then threw during cleanup, the side effect is repeated.</li>\n<li><strong>Batch failure semantics.</strong> Without <code>ReportBatchItemFailures</code>, one failing record causes the <em>entire batch</em> to be retried, reprocessing every record that already succeeded. This is a very common source of large-scale duplication.</li>\n<li><strong>At-least-once by design.</strong> SQS standard can deliver a message more than once independent of anything you did; DynamoDB Streams and Kinesis can redeliver on resharding or failover; SNS can deliver twice.</li>\n</ul>\n<p style=\"line-height: 1.75\">The fix is not to eliminate duplicates but to make processing <strong>idempotent</strong>. Use a natural idempotency key (the SQS <code>MessageId</code> or <code>MessageDeduplicationId</code>, the stream <code>SequenceNumber</code>, or a business key such as the order ID plus operation), record it with a conditional write, and short-circuit on a repeat: in DynamoDB, <code>PutItem</code> with <code>ConditionExpression: attribute_not_exists(pk)</code>. Powertools Idempotency implements this properly, including the hard part — handling a concurrent in-flight duplicate (it stores an INPROGRESS marker) and caching the original response so a duplicate returns the same result rather than an error. Enable <strong>partial batch responses</strong> so successes are not replayed. Where the downstream supports it, pass an idempotency key to <em>them</em> (payment providers universally do). And consider <strong>SQS FIFO</strong> with content-based deduplication when a five-minute dedup window is sufficient, accepting the throughput and message-group ordering trade-offs.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Incident Playbook</h4>\n<p style=\"line-height: 1.75\">Under pressure, work this order. It is deliberately arranged so the cheapest and highest-yield checks come first.</p>\n<ol style=\"margin-left: 1.5rem; line-height: 2\">\n<li><strong>Scope the blast radius.</strong> One function or many? One region or all? One tenant or everyone? Multiple unrelated functions failing simultaneously points at an account-level cause (concurrency quota, an IAM or SCP change, a regional service event) rather than a code bug. Check the AWS Health Dashboard.</li>\n<li><strong>What changed?</strong> CloudTrail for <code>UpdateFunctionCode</code> / <code>UpdateFunctionConfiguration</code> / IAM and SCP changes, plus your deployment pipeline history, in a window starting 30 minutes before the symptom. Most incidents are changes. If a change correlates, <strong>roll back before diagnosing</strong> — shift the alias to the previous version.</li>\n<li><strong>Read the four metrics together, not individually.</strong> <code>Invocations</code>, <code>Errors</code>, <code>Throttles</code>, <code>Duration</code> on one graph for the affected function. Their <em>combination</em> is diagnostic: Invocations dropped to zero means a trigger problem; Throttles high means a concurrency problem; Duration pinned at the timeout means a dependency or CPU problem; Errors high with normal Duration means a code or permissions problem.</li>\n<li><strong>Read a REPORT line.</strong> <code>Max Memory Used</code> versus <code>Memory Size</code>, <code>Duration</code> versus timeout, presence of <code>Init Duration</code>.
