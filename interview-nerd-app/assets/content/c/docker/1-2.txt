The core principle is <strong>defense in depth</strong>: no single control is sufficient, and security must be embedded at every stage. Production incidents involving containers almost always trace back to one of a small set of root causes: containers running as root, outdated base images with known vulnerabilities (CVEs), secrets accidentally baked into images, overly permissive capabilities, or the absence of resource limits enabling denial-of-service attacks. Understanding the full security model — Linux kernel namespaces and cgroups, the container attack surface, capability dropping, seccomp and AppArmor profiles, image vulnerability scanning, and supply chain integrity — is essential for deploying containers in production and is a core topic in senior DevOps, Platform Engineering, and Security interviews.\n</p>\n<!-- ============================================================ -->\n<!-- SECTION 1: THE CONTAINER SECURITY MODEL -->\n<!-- ============================================================ -->\n<h4 style=\"margin-top: 2rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\n1. The Container Security Model: Namespaces, Cgroups, and the Shared Kernel\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1rem\">\nContainers are not virtual machines — they share the host kernel. Understanding what this means for security is foundational. Docker uses Linux <strong>namespaces</strong> to provide isolation: each container gets its own view of the filesystem (mount namespace), process tree (PID namespace), network interfaces (net namespace), users (user namespace), and inter-process communication (IPC namespace). A process running in a container cannot see or interact with processes in other containers or on the host — with one critical exception: the kernel is shared. A kernel vulnerability (like Dirty Pipe or Dirty COW) exploited from inside a container gives the attacker access to the host kernel, potentially breaking out of all namespace isolation. This is why <strong>kernel security updates are critical</strong>, and why defense-in-depth (dropping capabilities, seccomp, AppArmor) is necessary to limit what a compromised container can do.\n</p>\n<p style=\"line-height: 1.75; margin-top: 1rem\">\n<strong>Control groups (cgroups)</strong> provide the other half of the security model: resource limits. Without cgroup limits, a single container can exhaust all host memory or CPU, triggering the OOM killer on the host or causing a denial-of-service for all other containers. Resource limits are a security control as much as a performance control — they prevent a compromised container from starving other workloads.\n</p>\n<div style=\"margin-top: 1rem; border: 1px solid #e4e4e7; Image Security: Building Secure Images\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1rem\">\nThe security of a running container is determined almost entirely by the image it was built from. A poorly constructed image with a root user, outdated packages with known CVEs, and secrets baked into layers cannot be secured at runtime. Non-Root Users — The Most Critical Rule</h5>\n<p style=\"line-height: 1.75; margin-top: 0.5rem\">\nContainers run as root by default. If an attacker compromises a root-running container, they have root privileges within that container's namespace — they can install packages, modify system files, and crucially, if there's any kernel exploit or misconfiguration, they have a much easier path to host breakout. Running as a non-root user is the single most effective security control you can implement in a Dockerfile. The principle: <strong>the container should have the minimum privileges necessary to run the application</strong> — nothing more.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px; Runtime Security: Docker Run Flags\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1rem\">\nThe Dockerfile determines what's in the image, but runtime flags determine how the container is executed. Even a perfectly built image can be run insecurely if the runtime configuration is wrong. The key runtime security controls are: dropping Linux capabilities, setting resource limits, making filesystems read-only, and enabling security profiles (seccomp, AppArmor, SELinux).\n</p>\n<h5 style=\"margin-top: 1.25rem; font-size: 1.05rem; font-weight: 600\">3.1. Linux Capabilities — Dropping Privileges</h5>\n<p style=\"line-height: 1.75; margin-top: 0.5rem\">\nLinux capabilities break root privileges into small, granular units. Even if a container runs as root, you can drop all but the specific capabilities the application needs. The default Docker capability set is too permissive for most applications. The principle: <strong>drop all capabilities, then add back only what's required</strong>.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px; margin-top: 0.5rem\">\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c># ── CAPABILITY BASICS ─────────────────────────────────────────────</i>\n<i class=c># List capabilities granted to a running container</i>\ndocker run --<i class=b>rm</i> myapp capsh --<i class=b>print</i>\n<i class=c># Current: cap_chown,cap_dac_override,cap_fowner,cap_fsetid,cap_kill,cap_setgid,cap_setuid,cap_setpcap,cap_net_bind_service,cap_net_raw,cap_sys_chroot,cap_mknod,cap_audit_write,cap_setfcap</i>\n\n\n<i class=c># ── DROP ALL CAPABILITIES, ADD ONLY WHAT&#x27;S NEEDED ─────────────────</i>\n<i class=c># For a typical web app that only needs to bind to port 80/443 (&lt;1024)</i>\ndocker run   --cap-drop ALL   --cap-add NET_BIND_SERVICE   myapp\n\n<i class=c># For an app that needs to read timezone files but nothing else</i>\ndocker run   --cap-drop ALL   --cap-add SYS_TIME   myapp\n\n<i class=c># For an app that needs to change file ownership (e.g., copying files)</i>\ndocker run   --cap-drop ALL   --cap-add CHOWN   myapp\n\n\n<i class=c># ── COMMON CAPABILITIES REFERENCE ─────────────────────────────────</i>\n<i class=c># NET_BIND_SERVICE  → Bind to ports &lt;1024 (most web apps need this)</i>\n<i class=c># CHOWN             → Change file ownership</i>\n<i class=c># DAC_OVERRIDE      → Bypass file permissions (rarely needed)</i>\n<i class=c># KILL              → Send signals to processes (useful for graceful shutdown)</i>\n<i class=c># SYS_TIME          → Change system time (for timezone-aware apps)</i>\n<i class=c># SYS_ADMIN         → Most dangerous, mount filesystems, perform sysadmin tasks (AVOID if possible)</i>\n\n<i class=c># Check what capabilities your app actually needs:</i>\n<i class=c># Run with --cap-add ALL --security-opt=apparmor=unconfined, then use</i>\n<i class=c># strace or audit to see which syscalls fail, then reduce</i></code></pre></div>\n</div>\n<h5 style=\"margin-top: 1.5rem; font-size: 1.05rem; font-weight: 600\">3.2. Resource Limits — Preventing DoS</h5>\n<p style=\"line-height: 1.75; margin-top: 0.5rem\">\nWithout resource limits, a single container can consume all host memory (triggering OOM killer and killing other containers) or all CPU cores (starving other workloads). Setting memory and CPU limits is a critical security control to contain the blast radius of a compromised container or a bug causing resource exhaustion.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px; margin-top: 0.5rem\">\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c># ── MEMORY LIMITS ─────────────────────────────────────────────────</i>\n<i class=c># Hard limit (container cannot exceed this)</i>\ndocker run --memory=<i class=s>&quot;512m&quot;</i> myapp\n\n<i class=c># Memory + swap limit (swap is usually disabled in production)</i>\ndocker run --memory=<i class=s>&quot;512m&quot;</i> --memory-swap=<i class=s>&quot;512m&quot;</i> myapp\n\n<i class=c># Memory reservation (soft limit, used for scheduling)</i>\ndocker run --memory-reservation=<i class=s>&quot;256m&quot;</i> myapp\n\n<i class=c># OOM score adjustment (make container more/less likely to be killed)</i>\ndocker run --oom-score-adj=-500 myapp\n<i class=c># Negative values = less likely to be killed</i>\n\n\n<i class=c># ── CPU LIMITS ────────────────────────────────────────────────────</i>\n<i class=c># CPU shares (relative weight, not a hard limit)</i>\ndocker run --cpu-shares=512 myapp   <i class=c># default 1024, 512 = half the weight</i>\n\n<i class=c># CPU cores hard limit (e.g., use 0.5 cores)</i>\ndocker run --cpus=<i class=s>&quot;0.5&quot;</i> myapp\n\n<i class=c># CPU period/quota for fine-grained control</i>\ndocker run --cpu-period=100000 --cpu-quota=50000 myapp  <i class=c># 50% of one core</i>\n\n\n<i class=c># ── COMBINED RESOURCE LIMITS FOR PRODUCTION ──────────────────────</i>\ndocker run   --memory=<i class=s>&quot;512m&quot;</i>   --memory-swap=<i class=s>&quot;512m&quot;</i>   --cpus=<i class=s>&quot;0.5&quot;</i>   --pids-limit=100            <i class=c># Prevent fork bomb DoS</i>\n  --<i class=b>ulimit</i> nofile=65536:65536  <i class=c># Limit file descriptors</i>\n  myapp\n\n\n<i class=c># ── KUBERNETES RESOURCE LIMITS ───────────────────────────────────</i>\n<i class=c># apiVersion: v1</i>\n<i class=c># kind: Pod</i>\n<i class=c># spec:</i>\n<i class=c>#   containers:</i>\n<i class=c>#   - name: app</i>\n<i class=c>#     resources:</i>\n<i class=c>#       requests:</i>\n<i class=c>#         memory: &quot;256Mi&quot;</i>\n<i class=c>#         cpu: &quot;250m&quot;</i>\n<i class=c>#       limits:</i>\n<i class=c>#         memory: &quot;512Mi&quot;</i>\n<i class=c>#         cpu: &quot;500m&quot;</i></code></pre></div>\n</div>\n<h5 style=\"margin-top: 1.5rem; font-size: 1.05rem; font-weight: 600\">3.3. Read-Only Root Filesystem</h5>\n<p style=\"line-height: 1.75; margin-top: 0.5rem\">\nMaking the root filesystem read-only prevents attackers from writing malicious binaries or modifying system files. Any writes the application needs must go to a writable volume (like /tmp). This is a powerful security control: even if an attacker gains code execution, they cannot persist changes to the container's filesystem.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px; margin-top: 0.5rem\">\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c># ── READ-ONLY FILESYSTEM ─────────────────────────────────────────</i>\n<i class=c># Run with --read-only, provide a writable tmpfs for temporary files</i>\ndocker run   --read-only   --tmpfs /tmp:rw,noexec,nosuid,size=100m   myapp\n\n<i class=c># If your app writes logs, mount a volume for them</i>\ndocker run   --read-only   -v /var/log/myapp:/var/log:rw   myapp\n\n\n<i class=c># ── DOCKERFILE COMPATIBILITY FOR READ-ONLY ───────────────────────</i>\n<i class=c># The app must not write to the container&#x27;s root filesystem</i>\n<i class=c># All writes must go to:</i>\n<i class=c># - Volumes mounted with -v</i>\n<i class=c># - tmpfs mounts with --tmpfs</i>\n<i class=c># - /dev/shm (shared memory, rarely used)</i>\n\n<i class=c># Check your app for filesystem writes during development:</i>\n<i class=c># Run with --read-only and see which writes fail, then mount those paths</i></code></pre></div>\n</div>\n<h5 style=\"margin-top: 1.5rem; font-size: 1.05rem; font-weight: 600\">3.4. Seccomp & AppArmor — System Call Filtering</h5>\n<p style=\"line-height: 1.75; margin-top: 0.5rem\">\nSeccomp (secure computing mode) filters the system calls a container can make. A typical application only needs a small subset of Linux's ~400 system calls. By restricting syscalls, you prevent exploit techniques that rely on uncommon syscalls. Docker provides a default seccomp profile that blocks ~50 dangerous syscalls; you can create custom profiles for stricter filtering.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px; margin-top: 0.5rem\">\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c># ── DEFAULT SECCOMP PROFILE ──────────────────────────────────────</i>\n<i class=c># Docker&#x27;s default profile blocks ~50 syscalls:</i>\n<i class=c># - kernel module loading (init_module, finit_module)</i>\n<i class=c># - reboot, kexec (system shutdown/reboot)</i>\n<i class=c># - bpf (BPF program loading — eBPF exploits)</i>\n<i class=c># - perf_event_open (performance monitoring, used in side-channel attacks)</i>\n<i class=c># - process_vm_readv, process_vm_writev (cross-process memory access)</i>\n\ndocker run --security-opt seccomp=default.json myapp\n\n\n<i class=c># ── CUSTOM SECCOMP PROFILE (STRICT) ──────────────────────────────</i>\n<i class=c># Create a minimal seccomp profile that only allows syscalls your app needs</i>\n<i class=b>cat</i> &gt; seccomp-strict.json &lt;&lt; <i class=s>&#x27;EOF&#x27;</i>\n{\n  <i class=s>&quot;defaultAction&quot;</i>: <i class=s>&quot;SCMP_ACT_ERRNO&quot;</i>,\n  <i class=s>&quot;architectures&quot;</i>: [<i class=s>&quot;SCMP_ARCH_X86_64&quot;</i>],\n  <i class=s>&quot;syscalls&quot;</i>: [\n    {<i class=s>&quot;names&quot;</i>: [<i class=s>&quot;read&quot;</i>, <i class=s>&quot;write&quot;</i>, <i class=s>&quot;open&quot;</i>, <i class=s>&quot;close&quot;</i>, <i class=s>&quot;stat&quot;</i>, <i class=s>&quot;fstat&quot;</i>, <i class=s>&quot;lseek&quot;</i>, <i class=s>&quot;mmap&quot;</i>, <i class=s>&quot;munmap&quot;</i>, <i class=s>&quot;brk&quot;</i>, <i class=s>&quot;rt_sigaction&quot;</i>, <i class=s>&quot;rt_sigprocmask&quot;</i>, <i class=s>&quot;ioctl&quot;</i>, <i class=s>&quot;nanosleep&quot;</i>, <i class=s>&quot;exit&quot;</i>, <i class=s>&quot;exit_group&quot;</i>], <i class=s>&quot;action&quot;</i>: <i class=s>&quot;SCMP_ACT_ALLOW&quot;</i>}\n  ]\n}\nEOF\n\ndocker run --security-opt seccomp=seccomp-strict.json myapp\n\n\n<i class=c># ── APPARMOR (Ubuntu/Debian) ─────────────────────────────────────</i>\n<i class=c># AppArmor restricts file access, network access, and capabilities</i>\n<i class=c># Docker provides a default profile</i>\n\ndocker run --security-opt apparmor=docker-default myapp\n\n<i class=c># Disable AppArmor (NOT recommended in production)</i>\ndocker run --security-opt apparmor=unconfined myapp\n\n\n<i class=c># ── NO NEW PRIVILEGES ────────────────────────────────────────────</i>\n<i class=c># Prevents processes inside container from gaining new privileges</i>\n<i class=c># via setuid binaries (like sudo, su)</i>\n\ndocker run --security-opt no-new-privileges myapp</code></pre></div>\n</div>\n<div style=\"margin-top: 1rem; border-left: 4px solid #3b82f6; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\">\n<strong>🎯 Interview Answer:</strong> \"Runtime security is configured through Docker run flags. The baseline: <code>--cap-drop ALL --cap-add NET_BIND_SERVICE</code> to drop all Linux capabilities except what the app needs — usually just binding to ports below 1024. Set resource limits: <code>--memory=\"512m\" --cpus=\"0.5\" --pids-limit=100</code> to prevent DoS attacks. Use <code>--read-only --tmpfs /tmp</code> to make the root filesystem read-only, preventing attackers from writing binaries to the container. Enable <code>--security-opt no-new-privileges</code> to block privilege escalation via setuid binaries. For system call filtering, the default seccomp profile blocks ~50 dangerous syscalls, and you can create stricter profiles. In production, these flags should be part of your orchestrator's Pod spec (Kubernetes securityContext) rather than manual docker run commands.\"\n</div>\n<!-- ============================================================ -->\n<!-- SECTION 4: SECRETS MANAGEMENT -->\n<!-- ============================================================ -->\n<h4 style=\"margin-top: 2rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\n4. Secrets Management: Never Bake Secrets Into Images\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1rem\">\nSecrets (API keys, database passwords, TLS certificates, private keys) embedded in Docker images are one of the most common security failures. Once a secret is in a layer, it's there forever — even if you delete it in a later layer, it remains in the image history and is accessible to anyone who can pull the image. Secrets must be injected at runtime, never at build time.\n</p>\n<h5 style=\"margin-top: 1.25rem; font-size: 1.05rem; font-weight: 600\">4.1. Build-Time Secrets — BuildKit Mounts</h5>\n<p style=\"line-height: 1.75; margin-top: 0.5rem\">\nFor secrets needed during the build (private npm tokens, GitHub access tokens for go mod download), use BuildKit's <code>--mount=type=secret</code>. The secret is mounted as a file during a specific RUN instruction and is not stored in any layer.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px; margin-top: 0.5rem\">\n<div class=\"code\"><div class=\"code-head\"><span>dockerfile</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c># syntax=docker/dockerfile:1</i>\n\n<i class=k>FROM</i> node:<i class=n>20</i>-alpine AS builder\n<i class=k>WORKDIR</i><span class=\"language-bash\"> /app</i>\n\n<i class=c># Secret mounted only during this RUN — not in any layer</i>\n<i class=k>RUN</i><span class=\"language-bash\"> --mount=<i class=b>type</i>=secret,<i class=b>id</i>=npm_token     NPM_TOKEN=$(<i class=b>cat</i> /run/secrets/npm_token)     npm config <i class=b>set</i> //registry.npmjs.org/:_authToken <i class=v>$NPM_TOKEN</i></i>\n\n<i class=k>COPY</i><span class=\"language-bash\"> package*.json ./</i>\n<i class=k>RUN</i><span class=\"language-bash\"> npm ci</i>\n<i class=k>COPY</i><span class=\"language-bash\"> . .</i>\n<i class=k>RUN</i><span class=\"language-bash\"> npm run build</i>\n\n\n<i class=c># Build command:</i>\n<i class=c># docker build --secret id=npm_token,src=./.npmrc-token -t myapp .</i>\n\n<i class=c># Or read from environment variable:</i>\n<i class=c># docker build --secret id=npm_token,env=NPM_TOKEN -t myapp .</i>\n\n\n<i class=c># ── DANGEROUS: Never do this ──────────────────────────────────────</i>\n<i class=c># ARG NPM_TOKEN</i>\n<i class=c># RUN npm config set //registry.npmjs.org/:_authToken $NPM_TOKEN</i>\n<i class=c># The token is stored in the image&#x27;s metadata (docker history)</i></code></pre></div>\n</div>\n<h5 style=\"margin-top: 1.5rem; font-size: 1.05rem; font-weight: 600\">4.2. Runtime Secrets — Docker Secrets & Orchestrators</h5>\n<p style=\"line-height: 1.75; margin-top: 0.5rem\">\nFor runtime secrets, use Docker Swarm secrets, Kubernetes secrets, or HashiCorp Vault. Never pass secrets via environment variables (they're visible in <code>docker inspect</code>, logs, and /proc of child processes). Instead, mount secrets as files.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px; margin-top: 0.5rem\">\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c># ── DOCKER SWARM SECRETS ─────────────────────────────────────────</i>\n<i class=c># Create secret</i>\n<i class=b>echo</i> <i class=s>&quot;my-database-password&quot;</i> | docker secret create db_password -\n\n<i class=c># Use in service (mounted as /run/secrets/db_password)</i>\ndocker service create   --secret db_password   --name myapp   myapp:latest\n\n\n<i class=c># ── KUBERNETES SECRETS ───────────────────────────────────────────</i>\n<i class=c># Create secret (imperative)</i>\nkubectl create secret generic db-credentials   --from-literal=password=<i class=s>&#x27;my-database-password&#x27;</i>\n\n<i class=c># Use in Pod (mounted as file)</i>\napiVersion: v1\nkind: Pod\nspec:\n  containers:\n  - name: myapp\n    image: myapp:latest\n    volumeMounts:\n    - name: secrets\n      mountPath: /app/secrets\n      readOnly: <i class=l>true</i>\n  volumes:\n  - name: secrets\n    secret:\n      secretName: db-credentials\n\n\n<i class=c># ── NEVER USE ENVIRONMENT VARIABLES FOR SECRETS ──────────────────</i>\n<i class=c># Environment variables are visible in:</i>\n<i class=c># - docker inspect (anyone with image access)</i>\n<i class=c># - /proc/self/environ of running container (if process is compromised)</i>\n<i class=c># - Logs if the app prints env vars</i>\n<i class=c># - Cloud provider metadata services (if exposed)</i>\n\n<i class=c># Wrong:</i>\ndocker run -e DB_PASSWORD=secret myapp\n\n<i class=c># Correct:</i>\ndocker run -v /path/to/secrets:/secrets:ro myapp\n<i class=c># App reads /secrets/db_password</i></code></pre></div>\n</div>\n<div style=\"margin-top: 1rem; border-left: 4px solid #3b82f6; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\">\n<strong>🎯 Interview Answer:</strong> \"Secrets must never be baked into images — they remain in layers forever and anyone with image access can retrieve them. For build-time secrets (like npm tokens), use BuildKit's <code>--mount=type=secret</code> — the secret is mounted during a specific RUN instruction and leaves no trace in any layer. For runtime secrets, use Docker Swarm secrets, Kubernetes secrets, or HashiCorp Vault. Always mount secrets as files, never environment variables. Environment variables are visible in <code>docker inspect</code>, container logs, and can be read from /proc of a compromised container. The file mount approach ensures secrets are only in memory and on the filesystem of the container, and can be rotated without rebuilding the image.\"\n</div>\n<!-- ============================================================ -->\n<!-- SECTION 5: SUPPLY CHAIN SECURITY -->\n<!-- ============================================================ -->\n<h4 style=\"margin-top: 2rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\n5. Supply Chain Security: Image Signing & Provenance\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1rem\">\nSupply chain attacks — where an attacker compromises a base image, a dependency, or a build tool — are increasingly common. Defending the supply chain requires: pinning base images to digests (immutable references), signing images with Docker Content Trust (Notary), and verifying image provenance with attestations (SLSA, Cosign).\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px; margin-top: 0.5rem\">\n<div class=\"code\"><div class=\"code-head\"><span>dockerfile</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c># ── PINNING BASE IMAGES TO DIGESTS (IMMUTABLE) ───────────────────</i>\n<i class=c># Instead of:</i>\n<i class=k>FROM</i> node:<i class=n>20</i>-alpine\n\n<i class=c># Use digest (immutable, never changes)</i>\n<i class=k>FROM</i> node:<i class=n>20</i>-alpine@sha256:bf77dc26e48ea95fca9d1aceb5acfa69d2e546b765ec2abfb502975f1a2d4def\n\n<i class=c># Get the digest:</i>\ndocker pull node:<i class=n>20</i>-alpine\ndocker inspect node:<i class=n>20</i>-alpine --format=<i class=s>&#x27;{{index .RepoDigests 0}}&#x27;</i>\n\n\n<i class=c># ── DOCKER CONTENT TRUST (IMAGE SIGNING) ─────────────────────────</i>\n<i class=c># Enable Content Trust (requires Notary server)</i>\nexport DOCKER_CONTENT_TRUST=<i class=n>1</i>\n\n<i class=c># Push an image — automatically signed</i>\ndocker push myregistry.com/myapp:latest\n\n<i class=c># Pull with signature verification (only pulls if signature valid)</i>\ndocker pull myregistry.com/myapp:latest\n\n\n<i class=c># ── COSIGN (Sigstore) — Image Signing and Verification ──────────</i>\n<i class=c># Install cosign: https://docs.sigstore.dev/cosign/installation</i>\n\n<i class=c># Sign an image with a key</i>\ncosign sign --key cosign.key myregistry.com/myapp:latest\n\n<i class=c># Verify signature</i>\ncosign verify --key cosign.pub myregistry.com/myapp:latest\n\n\n<i class=c># ── SLSA PROVENANCE (Build Attestations) ────────────────────────</i>\n<i class=c># Generate provenance attestation (GitHub Actions + SLSA)</i>\n<i class=c># Verifies: where the image came from, how it was built, what source commit</i>\n<i class=c># Kubernetes admission controllers can reject images without attestation</i></code></pre></div>\n</div>\n<div style=\"margin-top: 1rem; border-left: 4px solid #3b82f6; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\">\n<strong>🎯 Interview Answer:</strong> \"Supply chain security ensures that the image you run is the one your CI built and not a tampered version. Pin base images to digests (node:20-alpine@sha256:...) so you always get the same immutable image, not a moving tag. Enable Docker Content Trust (DOCKER_CONTENT_TRUST=1) to require signatures when pulling images — ensures images come from trusted publishers. For production, use Cosign (Sigstore) to sign images with a private key and verify signatures in Kubernetes admission controllers. Generate SLSA provenance attestations to prove how the image was built — which source commit, which CI runner, which build command — so you can reject images that didn't come from your official CI pipeline.\"\n</div>\n<!-- ============================================================ -->\n<!-- SECTION 6: SECURITY AUDITING & MONITORING -->\n<!-- ============================================================ -->\n<h4 style=\"margin-top: 2rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\n6. Security Auditing & Monitoring\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1rem\">\nContinuous security monitoring is essential for production containers. Tools like Docker Bench Security (CIS benchmarks) check host and Docker daemon configuration against industry standards.
