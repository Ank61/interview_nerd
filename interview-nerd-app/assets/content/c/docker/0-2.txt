Think of it as a recipe or blueprint that defines exactly how your application's environment should be constructed — from the base operating system to the final runtime configuration. Mastering Dockerfile creation is fundamental to working with Docker effectively, and it's one of the most commonly tested topics in DevOps and backend engineering interviews.\n</p>\n<!-- ============================================================ -->\n<!-- SECTION 1: WHAT IS A DOCKERFILE -->\n<!-- ============================================================ -->\n<h4 style=\"margin-top: 2rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\n1. What is a Dockerfile?\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1rem\">\nA Dockerfile is a declarative script that automates the creation of Docker images. Instead of manually running commands inside a container to set it up, you write those commands once in a Dockerfile, and Docker executes them in sequence to build a reproducible image. This is the cornerstone of <strong>Infrastructure as Code (IaC)</strong> for containerization.\n</p>\n<h5 style=\"margin-top: 1.25rem; font-size: 1.05rem; font-weight: 600\">Key Characteristics</h5>\n<ol style=\"margin-top: 0.75rem; margin-left: 1.5rem; list-style-type: number\">\n<li style=\"margin-top: 0.5rem\">\n<span style=\"font-weight: 600\">Plain Text Format:</span> A Dockerfile is just a text file named exactly <code>Dockerfile</code> (no extension). Each line typically contains one instruction in UPPERCASE followed by arguments.\n</li>\n<li style=\"margin-top: 0.5rem\">\n<span style=\"font-weight: 600\">Sequential Execution:</span> Docker reads the Dockerfile from top to bottom, executing each instruction in order. Each instruction creates a new layer in the image.\n</li>\n<li style=\"margin-top: 0.5rem\">\n<span style=\"font-weight: 600\">Immutable and Reproducible:</span> The same Dockerfile will produce the same image every time (assuming base images and external dependencies don't change), making builds predictable and auditable.\n</li>\n<li style=\"margin-top: 0.5rem\">\n<span style=\"font-weight: 600\">Version Controlled:</span> Dockerfiles live in your source code repository alongside your application code, enabling full version history and collaborative development.\n</li>\n</ol>\n<h5 style=\"margin-top: 1.25rem; font-size: 1.05rem; font-weight: 600\">Basic Workflow</h5>\n<ol style=\"margin-top: 0.75rem; margin-left: 1.5rem; list-style-type: number\">\n<li style=\"margin-top: 0.5rem\">Write a <code>Dockerfile</code> defining your application environment</li>\n<li style=\"margin-top: 0.5rem\">Run <code>docker build</code> to execute the Dockerfile and create an image</li>\n<li style=\"margin-top: 0.5rem\">Run <code>docker run</code> to create and start a container from that image</li>\n<li style=\"margin-top: 0.5rem\">Push the image to a registry (Docker Hub, ECR, GCR) for sharing or deployment</li>\n</ol>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px; margin-top: 1.25rem\">\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c># Complete workflow from Dockerfile to running container</i>\n\n<i class=c># 1. Base Images — The FROM Instruction\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1rem\">\nEvery Dockerfile <strong>must</strong> start with a <code>FROM</code> instruction. This specifies the <strong>base image</strong> — the foundation upon which your application will be built. Think of it like inheritance in programming: you start with a pre-built image that already contains an operating system and possibly a runtime, then add your application on top.\n</p>\n<h5 style=\"margin-top: 1.25rem; font-size: 1.05rem; font-weight: 600\">FROM Syntax</h5>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px; margin-top: 0.75rem\">\n<div class=\"code\"><div class=\"code-head\"><span>dockerfile</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c># Basic syntax</i>\n<i class=k>FROM</i> image_name:tag\n\n<i class=c># Examples</i>\n<i class=k>FROM</i> ubuntu:<i class=n>22.04</i>           <i class=c># Ubuntu Linux 22.04</i>\n<i class=k>FROM</i> node:<i class=n>18</i>                <i class=c># Node.js 18 on Debian</i>\n<i class=k>FROM</i> node:<i class=n>18</i>-alpine         <i class=c># Node.js 18 on Alpine Linux (minimal)</i>\n<i class=k>FROM</i> python:<i class=n>3.11</i>-slim       <i class=c># Python 3.11 slim variant</i>\n<i class=k>FROM</i> nginx:latest           <i class=c># Nginx web server (latest version)</i>\n<i class=k>FROM</i> scratch                <i class=c># Empty base (for building minimal images)</i>\n\n<i class=c># Using a specific digest for guaranteed immutability</i>\n<i class=k>FROM</i> node:<i class=n>18</i>@sha256:a1b2c3d4e5f6...</code></pre></div>\n</div>\n<h5 style=\"margin-top: 1.25rem; font-size: 1.05rem; font-weight: 600\">Types of Base Images</h5>\n<ol style=\"margin-top: 0.75rem; margin-left: 1.5rem; list-style-type: number\">\n<li style=\"margin-top: 0.75rem\">\n<span style=\"font-weight: 600; font-size: 1.05rem\">Official Language Runtime Images</span>\n<p style=\"margin-top: 0.4rem; line-height: 1.75\">\nPre-built images maintained by Docker or the language's official team. They include the language runtime, package manager, and core dependencies already installed. Examples: <code>node:18</code> (Node.js), <code>python:3.11</code>, <code>golang:1.21</code>, <code>openjdk:17</code>, <code>ruby:3.2</code>. These are the most common starting point for application containers.\n</p>\n</li>\n<li style=\"margin-top: 0.75rem\">\n<span style=\"font-weight: 600; font-size: 1.05rem\">Operating System Base Images</span>\n<p style=\"margin-top: 0.4rem; line-height: 1.75\">\nMinimal Linux distributions without pre-installed runtimes. You install everything yourself. Examples: <code>ubuntu:22.04</code>, <code>debian:bullseye</code>, <code>alpine:3.18</code>, <code>centos:7</code>. Use these when you need full control over the environment or when official runtime images don't exist for your stack.\n</p>\n</li>\n<li style=\"margin-top: 0.75rem\">\n<span style=\"font-weight: 600; font-size: 1.05rem\">Alpine-based Images (Minimal)</span>\n<p style=\"margin-top: 0.4rem; line-height: 1.75\">\nAlpine Linux is a security-focused, ultra-lightweight distribution (~5MB base). Most official images offer an Alpine variant (e.g., <code>node:18-alpine</code>). <strong>Pros:</strong> Tiny image size, faster pulls, smaller attack surface. <strong>Cons:</strong> Uses <code>musl libc</code> instead of <code>glibc</code>, which can cause compatibility issues with some native dependencies. Missing common utilities like bash (uses <code>sh</code> instead).\n</p>\n</li>\n<li style=\"margin-top: 0.75rem\">\n<span style=\"font-weight: 600; font-size: 1.05rem\">Slim/Minimal Variants</span>\n<p style=\"margin-top: 0.4rem; line-height: 1.75\">\nStripped-down versions of standard images with fewer packages. Example: <code>python:3.11-slim</code> is Debian-based but removes development tools, documentation, and non-essential packages. Balances size reduction with compatibility better than Alpine.\n</p>\n</li>\n<li style=\"margin-top: 0.75rem\">\n<span style=\"font-weight: 600; font-size: 1.05rem\">Scratch (Empty Base)</span>\n<p style=\"margin-top: 0.4rem; line-height: 1.75\">\n<code>FROM scratch</code> starts with literally nothing — no OS, no shell, no utilities. Used for building minimal static binaries (e.g., a compiled Go binary with zero dependencies). Results in the smallest possible images but requires the application to be completely self-contained.\n</p>\n</li>\n</ol>\n<h5 style=\"margin-top: 1.25rem; font-size: 1.05rem; font-weight: 600\">Choosing the Right Base Image</h5>\n<div style=\"margin-top: 1.25rem; Essential Dockerfile Instructions\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1rem\">\nUnderstanding the core Dockerfile instructions and when to use each one is fundamental. These six instructions form the backbone of most Dockerfiles.\n</p>\n<h5 style=\"margin-top: 1.5rem; font-size: 1.1rem; font-weight: 600\">FROM — Set Base Image</h5>\n<p style=\"line-height: 1.75; margin-top: 0.5rem\">\n<strong>Purpose:</strong> Specifies the parent image to build upon. Creates the directory if it doesn't exist. This is like <code>cd /app</code> but persists across layers.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px; margin-top: 0.75rem\">\n<div class=\"code\"><div class=\"code-head\"><span>dockerfile</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c># Set working directory to /app</i>\n<i class=k>WORKDIR</i><span class=\"language-bash\"> /app</i>\n\n<i class=c># All subsequent commands now execute from /app</i>\n<i class=k>COPY</i><span class=\"language-bash\"> package.json .        <i class=c># copies to /app/package.json</i></i>\n<i class=k>RUN</i><span class=\"language-bash\"> npm install            <i class=c># runs in /app directory</i></i>\n<i class=k>COPY</i><span class=\"language-bash\"> . .                   <i class=c># copies to /app</i></i>\n\n<i class=c># Can use multiple WORKDIR commands to navigate</i>\n<i class=k>WORKDIR</i><span class=\"language-bash\"> /app/src</i>\n<i class=k>COPY</i><span class=\"language-bash\"> server.js .           <i class=c># copies to /app/src/server.js</i></i>\n\n<i class=c># ❌ BAD — Using RUN cd instead of WORKDIR</i>\n<i class=k>RUN</i><span class=\"language-bash\"> <i class=b>cd</i> /app</i>\n<i class=k>COPY</i><span class=\"language-bash\"> . .                   <i class=c># Still copies to root, not /app!</i></i>\n<i class=c># Problem: cd in RUN doesn&#x27;t persist to next layer</i>\n\n<i class=c># ✅ GOOD — Using WORKDIR</i>\n<i class=k>WORKDIR</i><span class=\"language-bash\"> /app</i>\n<i class=k>COPY</i><span class=\"language-bash\"> . .                   <i class=c># Correctly copies to /app</i></i></code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 0.75rem; font-size: 0.95rem\">\n<strong>Why use WORKDIR instead of RUN cd?</strong> Because each RUN instruction executes in a new shell, so <code>cd</code> doesn't persist. WORKDIR sets the working directory for the image itself, affecting all subsequent layers.\n</p>\n<h5 style=\"margin-top: 1.5rem; font-size: 1.1rem; font-weight: 600\">COPY — Copy Files from Host to Image</h5>\n<p style=\"line-height: 1.75; margin-top: 0.5rem\">\n<strong>Purpose:</strong> Copies files or directories from the build context (your local filesystem) into the image. This is how you add your application code to the image.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px; margin-top: 0.75rem\">\n<div class=\"code\"><div class=\"code-head\"><span>dockerfile</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c># Basic syntax: COPY &lt;source&gt; &lt;destination&gt;</i>\n<i class=c># Source is relative to build context (where you run docker build)</i>\n<i class=c># Destination is absolute or relative to WORKDIR</i>\n\n<i class=k>WORKDIR</i><span class=\"language-bash\"> /app</i>\n\n<i class=c># Copy single file</i>\n<i class=k>COPY</i><span class=\"language-bash\"> package.json .                    <i class=c># copies to /app/package.json</i></i>\n<i class=k>COPY</i><span class=\"language-bash\"> server.js /app/server.js          <i class=c># explicit destination</i></i>\n\n<i class=c># Copy multiple files</i>\n<i class=k>COPY</i><span class=\"language-bash\"> package.json package-lock.json ./</i>\n\n<i class=c># Copy with wildcards (glob patterns)</i>\n<i class=k>COPY</i><span class=\"language-bash\"> *.js ./                           <i class=c># all .js files</i></i>\n<i class=k>COPY</i><span class=\"language-bash\"> package*.json ./                  <i class=c># package.json and package-lock.json</i></i>\n\n<i class=c># Copy entire directory</i>\n<i class=k>COPY</i><span class=\"language-bash\"> src/ /app/src/                    <i class=c># copies src/ to /app/src/</i></i>\n<i class=k>COPY</i><span class=\"language-bash\"> . .                               <i class=c># copies everything (respects .dockerignore)</i></i>\n\n<i class=c># Copy and rename</i>\n<i class=k>COPY</i><span class=\"language-bash\"> config.dev.json config.json       <i class=c># copies and renames</i></i>\n\n<i class=c># Copy with specific ownership (advanced)</i>\n<i class=k>COPY</i><span class=\"language-bash\"> --<i class=b>chown</i>=node:node package.json .  <i class=c># set owner to &#x27;node&#x27; user</i></i></code></pre></div>\n</div>\n<div style=\"margin-top: 1rem; border-left: 4px solid #eab308; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\">\n<strong>⚠️ Build Context Gotcha:</strong> COPY sources are relative to the build context (the directory where you run <code>docker build</code>), NOT the directory where the Dockerfile is located. Used for installing packages, compiling code, creating directories, or any setup task. Each RUN creates a new layer.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px; margin-top: 0.75rem\">\n<div class=\"code\"><div class=\"code-head\"><span>dockerfile</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c># Shell form (runs in /bin/sh -c)</i>\n<i class=k>RUN</i><span class=\"language-bash\"> npm install</i>\n<i class=k>RUN</i><span class=\"language-bash\"> apt-get update &amp;&amp; apt-get install -y curl</i>\n\n<i class=c># Exec form (doesn&#x27;t invoke shell, preferred for non-shell commands)</i>\n<i class=k>RUN</i><span class=\"language-bash\"> [<i class=s>&quot;npm&quot;</i>, <i class=s>&quot;install&quot;</i>]</i>\n<i class=k>RUN</i><span class=\"language-bash\"> [<i class=s>&quot;/bin/bash&quot;</i>, <i class=s>&quot;-c&quot;</i>, <i class=s>&quot;echo hello&quot;</i>]</i>\n\n<i class=c># ❌ BAD — Multiple RUN commands (creates many layers)</i>\n<i class=k>RUN</i><span class=\"language-bash\"> apt-get update</i>\n<i class=k>RUN</i><span class=\"language-bash\"> apt-get install -y curl</i>\n<i class=k>RUN</i><span class=\"language-bash\"> apt-get install -y git</i>\n<i class=k>RUN</i><span class=\"language-bash\"> <i class=b>rm</i> -rf /var/lib/apt/lists/*</i>\n<i class=c># Creates 4 separate layers, bloats image</i>\n\n<i class=c># ✅ GOOD — Chain commands with &amp;&amp; (creates one layer)</i>\n<i class=k>RUN</i><span class=\"language-bash\"> apt-get update &amp;&amp; \\\n    apt-get install -y \\\n        curl \\\n        git \\\n        vim &amp;&amp; \\\n    <i class=b>rm</i> -rf /var/lib/apt/lists/*</i>\n<i class=c># Single layer, smaller image, better cache efficiency</i>\n\n<i class=c># ❌ BAD — Leaving temp files/cache in layer</i>\n<i class=k>RUN</i><span class=\"language-bash\"> apt-get update &amp;&amp; apt-get install -y python3</i>\n<i class=c># Problem: apt cache stays in this layer forever!</i>\n\n<i class=c># ✅ GOOD — Clean up in same layer</i>\n<i class=k>RUN</i><span class=\"language-bash\"> apt-get update &amp;&amp; \\\n    apt-get install -y python3 &amp;&amp; \\\n    <i class=b>rm</i> -rf /var/lib/apt/lists/*</i>\n<i class=c># Cache cleaned before layer is committed</i>\n\n<i class=c># Common patterns</i>\n\n<i class=c># Install Node.js dependencies</i>\n<i class=k>RUN</i><span class=\"language-bash\"> npm ci --only=production</i>\n\n<i class=c># Install Python dependencies</i>\n<i class=k>RUN</i><span class=\"language-bash\"> pip install --no-cache-dir -r requirements.txt</i>\n\n<i class=c># Create directories with correct permissions</i>\n<i class=k>RUN</i><span class=\"language-bash\"> <i class=b>mkdir</i> -p /app/logs &amp;&amp; <i class=b>chmod</i> 755 /app/logs</i>\n\n<i class=c># Download and extract</i>\n<i class=k>RUN</i><span class=\"language-bash\"> wget https://example.com/app.tar.gz &amp;&amp; \\\n    tar -xzf app.tar.gz &amp;&amp; \\\n    <i class=b>rm</i> app.tar.gz</i></code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 0.75rem; font-size: 0.95rem\">\n<strong>Performance Tip:</strong> Chain related commands with <code>&&</code> to reduce layers. Always clean up temporary files (caches, downloads, build artifacts) in the same RUN command that creates them — otherwise they're baked into that layer forever, bloating your image.\n</p>\n<h5 style=\"margin-top: 1.5rem; font-size: 1.1rem; font-weight: 600\">EXPOSE — Document Port Numbers</h5>\n<p style=\"line-height: 1.75; margin-top: 0.5rem\">\n<strong>Purpose:</strong> Documents which ports the containerized application listens on. This is <strong>metadata only</strong> — it does NOT actually publish or open the port. To publish ports, you must use <code>-p</code> or <code>-P</code> at runtime.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px; margin-top: 0.75rem\">\n<div class=\"code\"><div class=\"code-head\"><span>dockerfile</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c># Document that app listens on port 3000</i>\n<i class=k>EXPOSE</i> <i class=n>3000</i>\n\n<i class=c># Multiple ports</i>\n<i class=k>EXPOSE</i> <i class=n>3000</i> <i class=n>8080</i>\n\n<i class=c># Specify protocol (default is TCP)</i>\n<i class=k>EXPOSE</i> <i class=n>8080</i>/tcp\n<i class=k>EXPOSE</i> <i class=n>53</i>/udp\n\n<i class=c># EXPOSE does NOT publish the port!</i>\n<i class=c># You still need -p at runtime:</i>\n<i class=c># docker run -p 8080:3000 myapp</i>\n<i class=c>#             ↑     ↑</i>\n<i class=c>#             host  container</i></code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 0.75rem; font-size: 0.95rem\">\n<strong>Why use EXPOSE if it doesn't publish ports?</strong> (1) Documentation — tells users which port to map. (2) Docker Compose and orchestrators use it for automatic port configuration. (3) <code>docker run -P</code> (uppercase P) auto-maps all EXPOSED ports to random host ports.\n</p>\n<h5 style=\"margin-top: 1.5rem; font-size: 1.1rem; font-weight: 600\">CMD — Default Container Command</h5>\n<p style=\"line-height: 1.75; margin-top: 0.5rem\">\n<strong>Purpose:</strong> Specifies the default command to run when a container starts. Unlike RUN (which executes during build), CMD executes when the container runs. There can only be one CMD per Dockerfile (if multiple, only the last one takes effect).\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px; margin-top: 0.75rem\">\n<div class=\"code\"><div class=\"code-head\"><span>dockerfile</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c># Exec form (preferred — doesn&#x27;t invoke shell)</i>\n<i class=k>CMD</i><span class=\"language-bash\"> [<i class=s>&quot;node&quot;</i>, <i class=s>&quot;server.js&quot;</i>]</i>\n<i class=k>CMD</i><span class=\"language-bash\"> [<i class=s>&quot;python&quot;</i>, <i class=s>&quot;app.py&quot;</i>]</i>\n<i class=k>CMD</i><span class=\"language-bash\"> [<i class=s>&quot;npm&quot;</i>, <i class=s>&quot;start&quot;</i>]</i>\n\n<i Node.js</i>\n<i class=c># Container won&#x27;t stop gracefully</i>\n\n<i class=c># ✅ GOOD — Exec form receives signals correctly</i>\n<i class=k>CMD</i><span class=\"language-bash\"> [<i runtime</i>\n<i class=c># Dockerfile:</i>\n<i class=k>CMD</i><span class=\"language-bash\"> [<i class=s>&quot;node&quot;</i>, <i class=s>&quot;server.js&quot;</i>]</i>\n\n<i class=c># Override at runtime:</i>\ndocker <i class=k>run</i><span class=\"language-bash\"> myapp node debug.js</i>\n<i class=c># Runs debug.js instead of server.js</i>\n\n<i class=c># Common patterns</i>\n\n<i class=c># Node.js production</i>\n<i class=k>CMD</i><span class=\"language-bash\"> [<i class=s>&quot;node&quot;</i>, <i class=s>&quot;server.js&quot;</i>]</i>\n\n<i class=c># Python app</i>\n<i class=k>CMD</i><span class=\"language-bash\"> [<i class=s>&quot;python&quot;</i>, <i class=s>&quot;-u&quot;</i>, <i class=s>&quot;app.py&quot;</i>]</i>\n<i class=c># -u flag disables buffering for real-time logs</i>\n\n<i class=c># Start with shell script</i>\n<i class=k>CMD</i><span class=\"language-bash\"> [<i class=s>&quot;./entrypoint.sh&quot;</i>]</i>\n\n<i class=c># Run with specific user</i>\n<i class=k>CMD</i><span class=\"language-bash\"> [<i class=s>&quot;su-exec&quot;</i>, <i class=s>&quot;node&quot;</i>, <i class=s>&quot;node&quot;</i>, <i class=s>&quot;server.js&quot;</i>]</i></code></pre></div>\n</div>\n<div style=\"margin-top: 1rem; border-left: 4px solid #eab308; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\">\n<strong>⚠️ Signal Handling:</strong> Always use exec form (<code>CMD [\"node\", \"app.js\"]</code>) in production, not shell form (<code>CMD node app.js</code>). Shell form wraps your process in /bin/sh, which becomes PID 1 and doesn't forward signals like SIGTERM properly. This breaks graceful shutdown and causes containers to hang on <code>docker stop</code>.\n</div>\n<div style=\"margin-top: 1rem; border-left: 4px solid #3b82f6; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\">\n<strong>🎯 Interview Answer:</strong> \"The core Dockerfile instructions are: FROM (base image), WORKDIR (working directory — use instead of RUN cd), COPY (add files from host to image), RUN (execute commands during build — creates layers), EXPOSE (document ports — metadata only), and CMD (default runtime command — use exec form for signal handling). I always chain RUN commands with && to reduce layers and clean up temp files in the same layer to minimize image size.\"\n</div>\n<!-- ============================================================ -->\n<!-- SECTION 4: COMPLETE DOCKERFILE EXAMPLES -->\n<!-- ============================================================ -->\n<h4 style=\"margin-top: 2rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\n4. This gives you a full build environment without bloating your production image. The builder stage is discarded after build — only the final stage becomes your image.\n</div>\n<!-- ============================================================ -->\n<!-- SECTION 5: DOCKER BUILD PROCESS -->\n<!-- ============================================================ -->\n<h4 style=\"margin-top: 2rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">\n5. The Docker Build Process\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1rem\">\nUnderstanding exactly what happens during <code>docker build</code> helps you write better Dockerfiles and debug build issues.\n</p>\n<h5 style=\"margin-top: 1.25rem; font-size: 1.05rem; font-weight: 600\">Build Context</h5>\n<p style=\"line-height: 1.75; margin-top: 0.5rem\">\nWhen you run <code>docker build -t myapp .</code>, the <code>.</code> (dot) specifies the <strong>build context</strong> — the directory whose contents are sent to the Docker daemon for the build. All COPY/ADD source paths are relative to this directory.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px; margin-top: 0.75rem\">\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c># Basic build (context = current directory)</i>\ndocker build -t myapp:1.0 .\n\n<i class=c># Build with custom tag</i>\ndocker build -t myapp:latest .\ndocker build -t myregistry.com/myapp:v2.0 .\n\n<i class=c># Build with Dockerfile in different location</i>\ndocker build -f ./docker/Dockerfile.prod -t myapp:prod .\n<i class=c># -f specifies Dockerfile path</i>\n<i class=c># Context is still . (current directory)</i>\n\n<i class=c># Build with different context</i>\ndocker build -t myapp -f ./docker/Dockerfile ../\n<i class=c># Dockerfile is in ./docker/</i>\n<i class=c># Context is ../ (parent directory)</i>\n\n<i class=c># Build with build arguments</i>\ndocker build --build-arg NODE_VERSION=18 -t myapp .\n\n<i class=c># Build without cache (force full rebuild)</i>\ndocker build --no-cache -t myapp .\n\n<i class=c># Build and show all output (including intermediate layers)</i>\ndocker build --progress=plain -t myapp .\n\n<i class=c># Build for specific platform (useful for M1 Macs)</i>\ndocker build --platform linux/amd64 -t myapp .</code></pre></div>\n</div>\n<h5 style=\"margin-top: 1.25rem; border-radius: 8px; font-size: 14px; margin-top: 1rem\">\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c># Sample build output</i>\n$ docker build -t myapp:1.0 .\n\nSending build context to Docker daemon  15.2MB\nStep 1/8 : FROM node:18-alpine\n ---&gt; a1b2c3d4e5f6\nStep 2/8 : WORKDIR /app\n ---&gt; Using cache\n ---&gt; f6e5d4c3b2a1\nStep 3/8 : COPY package*.json ./\n ---&gt; Using cache\n ---&gt; 1a2b3c4d5e6f\nStep 4/8 : RUN npm ci --only=production\n ---&gt; This speeds up builds and reduces image size.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px; margin-top: 0.75rem\">\n<div class=\"code\"><div class=\"code-head\"><span>code</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"># .dockerignore file\n\n# Dependency directories (will be installed via package.json)\nnode_modules/\nbower_components/\n\n# Build outputs (rebuilt during docker build)\ndist/\nbuild/\n*.log\n\n# Development files\n.git/\n.gitignore\n.env\n.env.local\n*.md\nREADME.md\n\n# IDE and editor files\n.vscode/\n.idea/\n*.swp\n*.swo\n*~\n\n# Test files\n__tests__/\n*.test.js\n*.spec.js\ncoverage/\n\n# CI/CD files\n.github/\n.gitlab-ci.yml\nJenkinsfile\n\n# OS files\n.DS_Store\nThumbs.db</code></pre></div>\n</div>\n<div style=\"margin-top: 1rem; border-left: 4px solid #eab308; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\">\n<strong>⚠️ Common Mistake:</strong> Forgetting <code>.dockerignore</code> and including <code>node_modules/</code> in the build context. This sends your entire node_modules (100MB+) to Docker daemon, then you run <code>npm install</code> which downloads them again! Always exclude node_modules, .git, and other large or unnecessary directories.\n</div>\n<div style=\"margin-top: 1rem; border-left: 4px solid #3b82f6; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\">\n<strong>🎯 Interview Answer:</strong> \"When you run docker build, Docker sends the build context to the daemon, then executes Dockerfile instructions sequentially.
