Slow builds destroy developer productivity and lengthen CI pipelines. Runtime misconfigurations lead to resource starvation, noisy neighbors, and OOM kills. Optimization isn't just about best practices—it's about understanding Docker's layer model, the build cache, and the tradeoffs between image size and debuggability. Understanding Image Layers and the Build Cache\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1rem\">\nEvery instruction in a Dockerfile creates a layer. Build Performance Optimization\n</h4>\n<p style=\"line-height: 1.75; margin-top: 1rem\">\nFast builds are critical for developer productivity and CI/CD efficiency. Slow builds disrupt flow and increase CI costs. Build optimization focuses on maximizing cache reuse, parallelizing independent stages, and using advanced BuildKit features.\n</p>\n<h5 style=\"margin-top: 1.25rem; font-size: 1.05rem; font-weight: 600\">3.1. BuildKit — The Modern Build Engine</h5>\n<p style=\"line-height: 1.75; margin-top: 0.5rem\">\nBuildKit is Docker's next-generation build engine (enabled by default in Docker 23+). It provides parallel stage execution, cache mounts, and better cache management. Enable it with <code>DOCKER_BUILDKIT=1</code> or by default in newer versions.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px; margin-top: 0.5rem\">\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c># ── ENABLE BUILDKIT ──────────────────────────────────────────────</i>\n<i class=b>export</i> DOCKER_BUILDKIT=1\ndocker build -t myapp .\n\n<i class=c># Or in daemon config (/etc/docker/daemon.json):</i>\n{\n  <i class=s>&quot;features&quot;</i>: {\n    <i class=s>&quot;buildkit&quot;</i>: <i class=l>true</i>\n  }\n}\n\n\n<i class=c># ── PARALLEL STAGES (BuildKit automatically parallelizes) ────────</i>\n<i class=c># Dockerfile with independent stages:</i>\nFROM node:20-alpine AS frontend\nWORKDIR /frontend\nCOPY frontend/package*.json ./\nRUN npm ci\nCOPY frontend/ .\nRUN npm run build\n\nFROM /app/public\nCOPY --from=backend /backend/dist /app/server\n\n<i class=c># BuildKit runs frontend and backend stages in PARALLEL</i>\n<i class=c># Result: total build time = max(frontend time, backend package*.json ./\nRUN --mount=<i class=b>type</i>=cache,target=/root/.npm     npm ci\nCOPY . .\nRUN --mount=<i class=b>type</i>=cache,target=/root/.npm     npm run build\n\n<i class=c># Even when package.json changes (cache-busting the layer),</i>\n<i class=c># the mounted /root/.npm directory persists across builds</i>\n<i class=c># npm only downloads new packages, not everything from scratch</i>\n\n\n<i class=c># ── GO MODULE CACHE MOUNT ────────────────────────────────────────</i>\nFROM golang:1.22-alpine AS builder\nWORKDIR /app\nCOPY go.mod go.sum ./\nRUN --mount=<i First CI run: builds everything, pushes cache</i>\n<i class=c># Second CI run: pulls cache layers, only rebuilds changed layers</i></code></pre></div>\n</div>\n<h5 style=\"margin-top: 1.5rem; font-size: 1.05rem; font-weight: 600\">3.2. Build Context Optimization</h5>\n<p style=\"line-height: 1.75; margin-top: 0.5rem\">\nThe build context is sent to the Docker daemon before the build starts. Large contexts (e.g., including node_modules) slow down every build. Use .dockerignore and consider using <code>--context</code> for remote builds.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px; margin-top: 0.5rem\">\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=c># ── MEASURE BUILD CONTEXT SIZE ───────────────────────────────────</i>\n<i class=c># Check context size before building</i>\ntar -czf - . | <i class=b>wc</i> -c\n\n<i class=c># With .dockerignore properly set, context should be &lt;5MB for most apps</i>\n<i class=c># Without .dockerignore, node_modules alone can be 500MB+</i>\n\n\n<i class=c># ── DOCKER BUILD CONTEXT OPTIONS ─────────────────────────────────</i>\n<i class=c># Build from current directory (default)</i>\ndocker build -t myapp .\n\n<i class=c># Build from a specific directory (avoids sending entire repo)</i>\ndocker build -t myapp -f docker/Dockerfile .\n\n<i class=c># Build from a URL (tar archive)</i>\ndocker build -t myapp https://github.com/user/repo/archive/main.tar.gz\n\n<i class=c># Build with piped context (for CI, avoids temp files)</i>\ntar -czf - . | docker build -t myapp -\n\n\n<i class=c># ── ADVANCED: DOCKER BUILDX WITH DIFFERENT CONTEXTS ──────────────</i>\n<i class=c># Build from a local directory with specific includes</i>\ndocker buildx build   -f Dockerfile   --build-context app=./app   --build-context lib=./lib   -t myapp .</code></pre></div>\n</div>\n<div style=\"margin-top: 1rem; border-left: 4px solid #3b82f6; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\">\n<strong>🎯 Interview Answer:</strong> \"Build performance optimization starts with proper layer ordering—copy dependency manifests first to cache the install step. Enable BuildKit for parallel stage execution and cache mounts. Cache mounts persist across builds even when layers are invalidated, so npm install only downloads new packages, not everything. In CI, use remote cache with <code>--cache-from type=registry</code> so ephemeral runners pull cached layers from previous builds.
