{"title":"Troubleshooting Production RDS — A Symptom-Driven Playbook","tags":["troubleshooting","performance-insights","incident-response","debugging"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Production debugging is not a knowledge test, it is a <strong>discipline of narrowing</strong>. The engineer who does well in this interview does not recite metric names — they start from the symptom, name the <em>one</em> metric or query that splits the hypothesis space in half, and keep splitting until only one cause survives. Below is a playbook organised the way incidents actually arrive: by symptom. For each, the distinguishing signal is named explicitly, because \"check CloudWatch\" is not an answer.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">1. CPU pinned at 100%</h4>\n<p style=\"line-height: 1.75\">The decisive split is <strong>bad plan versus genuine capacity shortage</strong>, and the instrument is Performance Insights. Compare <strong>DBLoad (Average Active Sessions)</strong> against the instance's <strong>vCPU count</strong> — the vCPU line is drawn on the PI chart for exactly this purpose. If AAS is at or slightly above vCPU and the load is dominated by the <code>CPU</code> wait state spread across <em>many</em> distinct SQL digests, you are genuinely out of compute and the answer is right-sizing or offloading reads. If AAS is far above vCPU and <strong>one or two SQL digests</strong> account for most of the load, you have a query problem and scaling up only buys time at high cost.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Top SQL in PI, sliced by wait event.</strong> Sort by AAS, then look at calls per second versus average latency. A query whose <em>call rate</em> jumped is an application change; a query whose <em>per-call cost</em> jumped is a plan change.</li>\n<li><strong>Recent deploy?</strong> Correlate the CPU inflection against deployment timestamps and against <code>ANALYZE</code>/autovacuum activity. A plan flip after statistics refresh on a newly-grown table is the classic no-deploy cause.</li>\n<li><strong>Plan confirmation.</strong> PostgreSQL: <code>pg_stat_statements</code> for mean_exec_time drift, then <code>EXPLAIN (ANALYZE, BUFFERS)</code>. MySQL: <code>performance_schema.events_statements_summary_by_digest</code> and <code>EXPLAIN ANALYZE</code>. Look for a nested loop where a hash join used to be, or a sequential scan where an index scan used to be.</li>\n<li><strong>Burstable classes are a separate cause entirely.</strong> On <code>db.t3</code>/<code>db.t4g</code>, check <code>CPUCreditBalance</code> and <code>CPUCreditUsage</code>. When credits hit zero in <em>standard</em> mode the instance is throttled to its baseline (often 20 to 40 percent of a vCPU) and everything queues — the symptom is high CPU with low throughput. In <em>unlimited</em> mode you are not throttled, you are billed for surplus credits, so the symptom appears on the bill instead. A t-class instance should never host a sustained production workload.</li>\n<li><strong>Immediate mitigations.</strong> Kill the offending session (<code>pg_terminate_backend</code>, <code>CALL mysql.rds_kill(id)</code>), apply a statement timeout, disable the offending feature flag. Scaling the instance is a last resort because it costs a failover and hides the cause.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">2. Storage full — the most dangerous RDS failure</h4>\n<p style=\"line-height: 1.75\">When <code>FreeStorageSpace</code> reaches zero the instance enters the <code>storage-full</code> state and stops serving writes; in bad cases it becomes unavailable and recovery takes time you do not control. Treat any sustained downward slope on <code>FreeStorageSpace</code> as a page, not a ticket. The thing to internalise: <strong>storage usually fills for a reason unrelated to data growth</strong>.</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Consumer</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">How to confirm</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Fix</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Inactive replication slot (PostgreSQL)</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><code>pg_replication_slots</code> with <code>active = false</code> and large retained WAL</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Drop the slot; WAL is freed immediately. truncate or drop obviously disposable objects; turn off verbose logging and rotate; then <code>modify-db-instance --allocated-storage</code> to grow the volume — remembering the increase is asynchronous, performance is degraded during optimisation, there is a <strong>6-hour cooldown</strong> before another storage modification, and <strong>storage can never be shrunk</strong>. Prevention is <strong>storage autoscaling</strong> with a bounded <code>MaxAllocatedStorage</code> plus a <code>FreeStorageSpace</code> alarm at, say, 20 percent — autoscaling alone is not enough because it has its own cooldown and can be outrun by runaway WAL.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">3. Connection exhaustion</h4>\n<p style=\"line-height: 1.75\">Symptom: <code>FATAL: remaining connection slots are reserved</code> (PostgreSQL) or <code>ER_CON_COUNT_ERROR: Too many connections</code> (MySQL), with <code>DatabaseConnections</code> flat against a ceiling. The RDS defaults are formulas in the parameter group — PostgreSQL uses <code>LEAST({DBInstanceClassMemory/9531392}, 5000)</code> and MySQL <code>{DBInstanceClassMemory/12582880}</code> — so <strong>max_connections scales with instance memory</strong>, which is why scaling down silently reduces the ceiling and why raising it manually is dangerous: each PostgreSQL connection is a process with its own memory, so a higher limit converts a connection error into an out-of-memory kill.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Find the real state.</strong> <code>SELECT state, count(*) FROM pg_stat_activity GROUP BY 1;</code> A large <code>idle in transaction</code> count is the single most common cause — the application opened a transaction, made an external call, and never committed. Fix it with <code>idle_in_transaction_session_timeout</code> and by correcting the code, not by raising the limit.</li>\n<li><strong>Attribute by client.</strong> Group <code>pg_stat_activity</code> by <code>application_name</code>, <code>usename</code> and <code>client_addr</code> to find which service is leaking. Often a batch job or a BI tool with no pool limit.</li>\n<li><strong>Missing pooling.</strong> Serverless and container fleets multiply: 200 tasks with a pool of 20 is 4,000 connections. The remedy is <strong>RDS Proxy</strong> (or PgBouncer), which multiplexes many client connections onto a small warm pool, absorbs connection storms, and holds connections through a failover so the application sees a pause instead of a flood of errors.</li>\n<li><strong>Know the Proxy's limits.</strong> Session <strong>pinning</strong> — caused by session-level state such as temporary tables, prepared statements in some modes, <code>SET</code> variables, or advisory locks — defeats multiplexing. Check the <code>DatabaseConnectionsCurrentlySessionPinned</code> metric; heavy pinning means the Proxy is buying you little.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">4. Replica lag climbing</h4>\n<p style=\"line-height: 1.75\">Watch <code>ReplicaLag</code> for RDS read replicas and <code>AuroraReplicaLag</code> for Aurora (which is typically tens of milliseconds because replicas share storage rather than replaying a log, so sustained Aurora lag usually indicates an overloaded reader, not a replication backlog). The four causes and their signatures:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Write burst on the primary.</strong> Lag rises with <code>WriteIOPS</code>/<code>WriteThroughput</code> on the writer. Often a bulk load or a batch job. Throttle or chunk the writes.</li>\n<li><strong>Single-threaded apply.</strong> Classic MySQL replication replays the relay log with limited parallelism; a wide transaction serialises. Tune <code>replica_parallel_workers</code> and <code>binlog_transaction_dependency_tracking=WRITESET</code>, and make sure tables have primary keys — row-based replication without a primary key degenerates into full scans per row on the replica and is a notorious lag cause.</li>\n<li><strong>Long-running query on the replica blocking apply.</strong> In PostgreSQL, a read query conflicts with WAL replay; with <code>hot_standby_feedback = on</code> the replica pushes back and the <em>primary</em> accumulates bloat instead, and with it off, queries get cancelled with a conflict error. That is the trade-off to articulate: bloat on the primary versus query cancellation on the replica, tuned by <code>max_standby_streaming_delay</code>.</li>\n<li><strong>Replica under-provisioned.</strong> A replica smaller than the primary cannot keep up with the primary's write rate. Replicas should generally match the writer's class.</li>\n</ul>\n<p style=\"line-height: 1.75\">Remediation while lag is high: stop routing read traffic that requires freshness to the replica (a load balancer or application flag), pause the batch job, and consider whether the read workload belongs on a dedicated replica. If lag is unbounded and growing, recreating the replica is often faster than waiting for it to catch up.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">5. Blocking and lock contention</h4>\n<p style=\"line-height: 1.75\">Signature in Performance Insights: AAS dominated by <code>Lock:transactionid</code>, <code>Lock:tuple</code> or <code>Lock:relation</code> (PostgreSQL) or <code>synch/mutex</code> and row-lock waits (MySQL), while CPU stays <em>low</em>. Low CPU with high load is the tell that distinguishes contention from a capacity problem.</p>\n<p style=\"line-height: 1.75\">In PostgreSQL, <code>pg_blocking_pids()</code> joined to <code>pg_stat_activity</code> gives you the blocker directly — find the root blocker (the session blocked by nobody) and decide whether to terminate it. In MySQL, <code>SHOW ENGINE INNODB STATUS</code> and <code>performance_schema.data_lock_waits</code> joined to <code>threads</code> serve the same purpose. Common root causes: a transaction left open by an application that does not commit; <strong>DDL taking an exclusive lock</strong> — <code>ALTER TABLE</code> in PostgreSQL requires <code>ACCESS EXCLUSIVE</code> and, worse, <em>queues behind</em> existing readers while blocking every subsequent query, so a schema migration during traffic can stall the whole database; and deadlocks, which the engine resolves by killing a victim (check <code>deadlocks</code> in <code>pg_stat_database</code> or <code>SHOW ENGINE INNODB STATUS</code>). The durable fixes are a short <code>lock_timeout</code> on migrations so they fail rather than queue, <code>CREATE INDEX CONCURRENTLY</code>, consistent lock ordering in application code, and <code>idle_in_transaction_session_timeout</code>.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">6. Memory pressure and swapping</h4>\n<p style=\"line-height: 1.75\">Watch <code>FreeableMemory</code> trending down and <code>SwapUsage</code> trending up together — swap in use on a database means latency has already degraded, because the engine assumed its buffers were in RAM. The usual culprits: an oversized <code>work_mem</code> (it is allocated <em>per sort or hash node per connection</em>, so 64 MB times 400 connections times several nodes each is an unbounded multiplier), too many connections on a process-per-connection engine, an over-tuned <code>shared_buffers</code> or <code>innodb_buffer_pool_size</code> leaving nothing for the OS and per-connection needs, and parameter formulas that shifted when the instance class changed. If memory is exhausted, the Linux OOM killer can terminate the database process, which RDS then restarts — visible as a spontaneous restart in the events log with no failover. Fix by lowering the global <code>work_mem</code> and raising it per-session only for the few queries that need it, adding a connection pooler rather than more memory, and right-sizing to a memory-optimised class if the working set genuinely does not fit.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">7. An unexpected failover</h4>\n<p style=\"line-height: 1.75\">First, <strong>confirm it actually happened</strong>: <code>aws rds describe-events</code> for the instance or cluster over the window shows <code>Multi-AZ instance failover started</code> and <code>completed</code>, or for Aurora <code>A new writer was promoted</code>. CloudTrail shows whether a human called <code>FailoverDBCluster</code> or <code>RebootDBInstance --force-failover</code>. The engine log shows a recovery/startup banner at the same timestamp, and on Aurora the reader endpoint composition changes.</p>\n<p style=\"line-height: 1.75\">Then determine the cause: hardware or AZ impairment (AWS-initiated, you will see it in events and possibly Health Dashboard), an operation you requested (instance class change, OS or engine patching applied in a maintenance window, storage modification), or the instance becoming unhealthy — commonly an OOM restart or storage exhaustion. Finally, and most importantly for the interview, assess <strong>what the application should have absorbed</strong>. A Multi-AZ failover is typically 60 to 120 seconds; Aurora is usually under 30 seconds. During that time the endpoint's DNS record is repointed, so the application must use the <strong>endpoint name, never a cached IP</strong>, must honour a short DNS TTL (the JVM's <code>networkaddress.cache.ttl</code> defaulting to cache forever is a legendary cause of hour-long outages), must have <strong>connection validation in the pool</strong> so stale sockets are discarded, and must implement <strong>retry with exponential backoff and jitter</strong> for idempotent operations. RDS Proxy shortens the visible impact by holding client connections while it re-establishes its own.
