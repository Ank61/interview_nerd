One <strong>primary Region</strong> holds the writer; up to <strong>five secondary Regions</strong> hold read-only clusters that receive changes through the <strong>Aurora storage layer</strong>, not through the SQL engine. That single architectural fact — replication happens below the database, not inside it — explains the typical <strong>sub-second cross-Region lag</strong>, the negligible overhead on the primary's compute, and why this is a different product from a cross-Region read replica.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">How Storage-Level Replication Works</h4>\n<p style=\"line-height: 1.75\">In a conventional cross-Region replica (RDS for MySQL or PostgreSQL), the primary engine produces a logical or physical replication stream — binlog or WAL — ships it over the internet backbone, and the remote instance's engine <strong>replays it</strong>. The primary spends CPU generating and serving the stream, and the remote spends CPU applying it, often single-threaded, which is why such replicas lag by seconds to minutes and why lag grows non-linearly under write bursts.</p>\n<p style=\"line-height: 1.75\">Aurora Global Database instead has the <strong>primary Region's storage layer</strong> forward redo log records to <strong>dedicated replication infrastructure</strong> in each secondary Region, which writes them into that Region's Aurora storage volume. The primary's database instance is not involved beyond the write it was already doing. The secondary Region's instances read from their local volume exactly as any Aurora reader does. Consequences:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Typical replication lag is around one second</strong>, and it is relatively insensitive to the secondary's instance size because there is no engine-level replay backlog to work through.</li>\n<li><strong>Minimal overhead on the primary</strong> — you do not buy a bigger writer to support Global Database.</li>\n<li>Each secondary Region has its <strong>own six-way, three-AZ replicated volume</strong>, so a secondary is itself a fully durable, highly available Aurora cluster, not a single copy.</li>\n<li>Each secondary can host <strong>read-only instances</strong> (up to 16 readers per secondary cluster), serving local low-latency reads.</li>\n<li>A secondary Region can be created with <strong>no instances at all</strong> in some configurations (a headless secondary), keeping the storage volume current at minimal cost — a cheap warm-standby pattern, though it increases RTO because Be precise about which failover path produces which numbers, because this is where interviews get specific.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Managed planned failover.</strong> A single operation that switches the primary Region to a chosen secondary while the whole global cluster is <strong>healthy</strong>. Aurora first ensures the target secondary is fully caught up, then performs the role swap and reconfigures the remaining secondaries to replicate from the new primary. Because it waits for zero lag, it is <strong>RPO zero — no data loss</strong>. It is the right tool for planned Region migrations, DR drills, compliance-mandated rotation, and Region maintenance. It is <strong>not</strong> usable during a real outage, because it requires the current primary to be reachable.</li>\n<li><strong>Unplanned failover (detach and promote).</strong> When the primary Region is genuinely unavailable, you <strong>remove a secondary cluster from the global database</strong>, which promotes it to a standalone writable Aurora cluster. This is fast — the promoted cluster's storage is already current — but the RPO is whatever was in flight at the moment of failure, typically around a second of writes. Afterwards the old primary is no longer part of a coherent global cluster and the remaining secondaries must be re-established against the new primary. Newer capability: Aurora also supports a <strong>switchover/failover operation on an unhealthy global cluster</strong> for some engine versions, which automates part of the reconfiguration, but the non-zero RPO remains inherent.</li>\n</ul>\n<p style=\"line-height: 1.75\">The operational distinction to state crisply: <strong>planned failover trades availability of the operation for zero data loss; unplanned failover trades data loss for availability.</strong> You should have runbooks for both, and you should have executed the planned one recently enough that the team trusts it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Write Forwarding</h4>\n<p style=\"line-height: 1.75\">By default, secondary Regions are read-only, which forces the application to know which Region can accept writes. <strong>Write forwarding</strong> (available for Aurora MySQL and Aurora PostgreSQL on supported versions) lets an application connect to a secondary Region and issue writes: the secondary transparently <strong>forwards the statement to the primary Region's writer</strong>, which executes and commits it, and the change flows back through storage replication. The application sees a single logical endpoint.</p>\n<p style=\"line-height: 1.75\">The costs and semantics you must be able to articulate:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Latency.</strong> Every forwarded write pays a full cross-Region round trip — realistically 60–150 ms between, say, eu-west-1 and us-east-1, and more across the Pacific. Forwarding is excellent for a low-volume write path (a preference toggle, a comment) and terrible for a chatty transactional path. A loop of 100 forwarded inserts is 100 round trips.</li>\n<li><strong>Consistency modes.</strong> Aurora exposes a session-level setting controlling how a forwarding session sees data. <strong>Eventual</strong> is fastest: the read may not reflect your own just-forwarded write. <strong>Session</strong> gives read-your-writes within the session by waiting for the secondary to catch up past your write. <strong>Global</strong> waits for the secondary to be current with the primary as a whole, which is the strongest and slowest. On Aurora MySQL this is <code>aurora_replica_read_consistency</code>; the PostgreSQL equivalent is a corresponding session parameter. Choosing <strong>session</strong> is the usual default for application correctness.</li>\n<li><strong>Restrictions.</strong> Forwarded writes cannot participate in every construct — DDL, some transaction isolation combinations, temporary tables, and certain statement types are restricted, and long transactions spanning forwarded writes behave differently. Read the engine-specific limitation list before designing around it.</li>\n<li><strong>It is not multi-master.</strong> There is still exactly one writer globally. Write forwarding relocates the client, not the write.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Read Latency, and the Cost Model</h4>\n<p style=\"line-height: 1.75\">The non-DR reason to adopt Global Database is <strong>local read latency for globally distributed users</strong>. A user in Sydney reading from us-east-1 pays roughly 200 ms of round-trip per query; served from an ap-southeast-2 secondary, that becomes single-digit milliseconds. For a read-heavy application this transforms perceived performance in a way no amount of caching in front of a single-Region database can fully replicate.</p>\n<p style=\"line-height: 1.75\">The bill has three components people forget: (1) <strong>instance hours in every Region</strong> — you are running a real Aurora cluster in each secondary, and this usually dominates; (2) <strong>storage in every Region</strong>, since each Region has its own full volume; and (3) <strong>cross-Region replicated write I/O</strong>, charged per million replicated write I/Os, which scales with your write volume times the number of secondary Regions. Adding a fourth secondary Region roughly quadruples the replication I/O charge for the same workload. Two levers help: run secondaries as <strong>Aurora Serverless v2</strong> with a modest floor so idle DR capacity is cheap, and consider <strong>headless secondaries</strong> where RTO permits.</p>\n<h4 style=\"margin-top: 1.5rem;
