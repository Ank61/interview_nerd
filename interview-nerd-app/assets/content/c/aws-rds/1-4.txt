{"title":"Multi-AZ DB Clusters vs Multi-AZ DB Instances","tags":["rds","multi-az","high-availability","failover"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">AWS ships <strong>two different things both called \"Multi-AZ\"</strong> for the RDS engines, and conflating them is one of the most reliable ways to lose credibility in an interview. The classic <strong>Multi-AZ DB instance</strong> is a two-node, primary-plus-unreadable-standby, synchronous availability design that has existed for well over a decade. The newer <strong>Multi-AZ DB cluster</strong> is a three-node, one-writer-plus-two-readable-standbys, semi-synchronous design spanning three Availability Zones. They have different failover times, different cost, different read capability, and different engine support. Know which one someone means before you answer.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Multi-AZ DB Instance — the Classic Design</h4>\n<p style=\"line-height: 1.75\">One <strong>primary</strong> in one AZ, one <strong>standby</strong> in a different AZ in the same Region. Replication is <strong>synchronous</strong>: a transaction is not acknowledged to the client until the change is durable on the standby's storage as well as the primary's. This gives an <strong>RPO of zero</strong> for an AZ failure.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>The standby is not readable and not connectable.</strong> It exists purely for availability. This is the single most common misconception — people assume Multi-AZ gives them read scaling. It does not. If you want reads off the primary you add <strong>read replicas</strong>, which are a separate, asynchronous feature.</li>\n<li><strong>Failover is DNS-based.</strong> RDS repoints the instance's DNS CNAME from the primary to the standby. Because there is DNS propagation plus the standby finishing recovery and opening for connections, failover typically takes <strong>60 to 120 seconds</strong>. Client DNS caching can extend the observed outage well beyond that.</li>\n<li><strong>Latency cost.</strong> Every commit pays a cross-AZ synchronous round trip — typically low single-digit milliseconds, but on a write-heavy workload that is a real and measurable tax on commit latency compared with Single-AZ.</li>\n<li><strong>You are paying for idle compute.</strong> Roughly double the instance cost for a node that serves no traffic.</li>\n<li><strong>What triggers failover:</strong> AZ outage, primary instance failure, storage failure on the primary, network connectivity loss, and also <strong>planned maintenance</strong> — RDS patches the standby first, fails over, then patches the old primary, which is how you get patching with roughly one failover of downtime instead of a full outage.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Multi-AZ DB Cluster — the Newer Design</h4>\n<p style=\"line-height: 1.75\">One <strong>writer</strong> plus <strong>two readable standby instances</strong>, one in each of <strong>three different Availability Zones</strong>. Each instance has its own storage — this is <strong>not</strong> Aurora's shared volume, which is a distinction interviewers probe.</p>\n<p style=\"line-height: 1.75\">Replication is <strong>semi-synchronous</strong>: the writer acknowledges a commit once <strong>at least one of the two standbys</strong> confirms it has received and persisted the change to its transaction log — it does not wait for both. This is the key performance idea. In the two-node synchronous design, the single standby is unavoidably on the critical path, so if it is slow (noisy neighbor, storage hiccup, network blip) every commit is slow. With two standbys and a quorum of one, the <strong>slower standby is simply outrun</strong>, which removes a whole class of tail-latency events and is why AWS documents Multi-AZ DB clusters as having <strong>up to 2x the write throughput</strong> of a comparable Multi-AZ DB instance deployment.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>The standbys are readable.</strong> The cluster exposes a <strong>reader endpoint</strong> alongside the writer endpoint, so the two standby instances serve read traffic. You are no longer paying for idle hardware. Note the reads are served from instances that are <strong>very slightly behind</strong> the writer, so they are not read-your-writes consistent.</li>\n<li><strong>Failover is typically under 35 seconds</strong>, substantially faster than the classic design, plus whatever your client needs to reconnect and re-resolve DNS.</li>\n<li><strong>Endpoints.</strong> A cluster endpoint for writes and a reader endpoint for reads — structurally similar to Aurora, which helps if you later migrate.</li>\n<li><strong>Three instances of cost.</strong> This is the honest trade: 1.5x the instance spend of a Multi-AZ DB instance. You are getting read capacity for that money, so if you were going to run read replicas anyway, it can be cost-neutral or better.</li>\n<li><strong>Constrained support surface.</strong> This is the practical blocker. Multi-AZ DB clusters are available only for <strong>specific engines and versions</strong> — RDS for MySQL and RDS for PostgreSQL from certain minor versions onward (and MariaDB on recent versions) — and only on <strong>particular instance classes</strong>, historically the NVMe-backed classes such as db.m6gd/db.r6gd and db.m5d/db.r5d, with newer families added over time. Storage must be <strong>io1, io2 Block Express, or gp3</strong>. Always check the current support matrix rather than asserting from memory; the correct interview move is to name the constraint category and say you would verify the exact list.</li>\n<li><strong>Feature gaps.</strong> Historically Multi-AZ DB clusters did not support every RDS feature — cross-Region automated backups, some parameter and option behaviors, and certain replica topologies had restrictions, and converting an existing Multi-AZ DB instance into a cluster in place was not possible (you migrate via snapshot restore or logical replication). Support has broadened over time (read replicas from a Multi-AZ DB cluster and blue/green deployments were added), so state the shape of the limitation and note that you would confirm currency.</li>\n</ul>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">MULTI<i class=o>-</i>AZ DB font-weight: 600\">Why Read Replicas Are Not a Substitute</h4>\n<p style=\"line-height: 1.75\">A natural question is: why not just run a Multi-AZ DB instance plus two read replicas? That gives you three instances and read capacity too. The differences matter:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Read replicas are asynchronous.</strong> They can lag by seconds or minutes under write load, and lag is unbounded in principle. A Multi-AZ DB cluster's standbys are kept current semi-synchronously, so lag is far smaller and bounded by the acknowledgement protocol.</li>\n<li><strong>Read replicas are not automatic failover targets.</strong> Promoting an RDS read replica is a <strong>manual, one-way operation</strong> that severs it from the primary and takes minutes. It is a DR tool, not an HA mechanism. Multi-AZ standbys are promoted <strong>automatically</strong> in seconds.</li>\n<li><strong>Promotion of an async replica has a real RPO.</strong> Whatever had not replicated at the moment of failure is lost. Multi-AZ, in either flavor, is RPO zero for an in-Region failure.</li>\n<li><strong>You would still be paying for the idle standby</strong> in the Multi-AZ-instance-plus-replicas design: four instances (primary, idle standby, two replicas) versus three in a Multi-AZ DB cluster.</li>\n</ul>\n<p style=\"line-height: 1.75\">Where read replicas remain the right answer: <strong>cross-Region</strong> DR, offloading heavy analytics that you deliberately want isolated, scaling reads beyond two standbys, and engines or versions where Multi-AZ DB clusters are not supported.</p>\n<h4 style=\"margin-top: 1.5rem; HA protects against infrastructure failure; backups, point-in-time recovery, and (on Aurora MySQL) Backtrack protect against you.</li>\n<li><strong>Failover is never invisible.</strong> In all three designs, in-flight connections are dropped and uncommitted transactions roll back. The application needs reconnect-with-backoff and idempotent retry, plus a short client DNS TTL. <strong>RDS Proxy</strong> meaningfully reduces observed failover impact and works with RDS and Aurora.</li>\n<li><strong>Measure, do not assume, failover time.</strong> Use <code>reboot-db-instance --force-failover</code> for a Multi-AZ DB instance and <code>failover-db-cluster</code> for clusters, in staging, with realistic traffic. The number that matters is end-to-end application recovery, which includes DNS, pool re-establishment, and cache warm-up — usually considerably longer than the database's own number.</li>\n<li><strong>Cross-AZ data transfer</strong> for synchronous replication within a Region is not charged for Multi-AZ replication traffic, but your application's own cross-AZ traffic to the database is a separate consideration in cost and latency — co-locate where you can.</li>\n<li><strong>Migration path.</strong> You generally cannot convert a Multi-AZ DB instance into a Multi-AZ DB cluster in place; plan a snapshot-restore or a blue/green deployment and a cutover window.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario</h4>\n<p style=\"line-height: 1.75\">\"A fintech runs RDS for PostgreSQL 15, 800 GB, on a Multi-AZ DB instance. Writes are commit-latency sensitive. A compliance requirement just landed: failover must complete in under 60 seconds, and they also want to offload a growing reporting workload currently hammering the primary. They are reluctant to migrate to Aurora this quarter. What do you recommend?\"</p>\n<p style=\"line-height: 1.75\">Work the constraints. The 60-second failover requirement <strong>rules out the current Multi-AZ DB instance</strong>, whose typical 60–120 seconds does not reliably meet it. The reporting workload needs somewhere to go, and the current standby is unreadable, so today the only options are the primary (status quo, bad) or adding read replicas. Aurora is off the table this quarter for organizational reasons.</p>\n<p style=\"line-height: 1.75\">Recommend a <strong>Multi-AZ DB cluster</strong>. It addresses all three points at once: failover typically <strong>under 35 seconds</strong>, comfortably inside the requirement with margin for client reconnection; <strong>semi-synchronous replication with a quorum of one of two standbys</strong> lowers commit latency versus the current design, because a momentarily slow standby no longer gates every commit — this directly serves the write-latency sensitivity; and the <strong>two standbys are readable</strong>, so reporting moves to the reader endpoint with no additional instances beyond the third node. Cost goes from 2x to 3x instance spend, but compare against the honest alternative — Multi-AZ instance plus two read replicas is <strong>4x</strong> and still has the slow failover. So the cluster is both faster and cheaper than the alternative that meets the read requirement.</p>\n<p style=\"line-height: 1.75\">Then raise what a senior candidate raises. <strong>Verify support</strong>: PostgreSQL 15 is within the supported range, but confirm the exact minor version and check that the required instance class family and <strong>io1/io2 Block Express/gp3</strong> storage are acceptable — this may force an instance class change. <strong>Plan the migration</strong>: you cannot convert in place, so use a <strong>blue/green deployment</strong> or snapshot restore plus logical replication to minimize the cutover window, and schedule it. <strong>Set expectations on the reads</strong>: standbys are marginally behind the writer, so any report that must reflect a just-committed transaction still goes to the writer endpoint — and reporting queries that scan large tables should get a statement timeout so they cannot destabilize a standby that is also an HA component. <strong>Fix the client</strong>: short DNS TTL, connection pool with validation and max-lifetime, idempotent retry — otherwise a 35-second database failover is still a two-minute application outage and you will have missed the compliance target anyway. Finally, <strong>drill it</strong>: run <code>failover-db-cluster</code> in staging under load and measure end-to-end recovery, then repeat quarterly, because an unmeasured RTO is a guess. Note for completeness that if their read workload keeps growing past two standbys, or the dataset grows past comfortable EBS management, <strong>Aurora is the natural next step</strong> — and moving to a Multi-AZ DB cluster now is helpful preparation, since the writer/reader endpoint model is the same.</p>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"They are two different products.
