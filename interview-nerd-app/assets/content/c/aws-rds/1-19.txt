First, <strong>state the requirement that drove the choice</strong>, not the product's marketing: \"reads must be under 50 ms in Sydney and the writer is in Ireland, so storage-level cross-Region replication — Aurora Global Database\". Second, <strong>name what you are giving up</strong>. An answer with no trade-off sounds like a brochure.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">RDS versus Aurora, honestly</h4>\n<p style=\"line-height: 1.75\">Aurora reimplements the storage layer: instead of one volume per instance, the cluster writes to a <strong>distributed storage service that keeps six copies across three AZs</strong> and acknowledges a write on a four-of-six quorum. The engine ships redo log records rather than full pages, which is why write amplification drops and why replicas do not replay a log at all — they read the same volume. That single architectural difference produces most of Aurora's advantages:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Read scaling.</strong> Up to 15 replicas with typically single-digit to tens of milliseconds of lag, versus 5 replicas on RDS MySQL/PostgreSQL replaying a replication stream with lag that can reach minutes under load.</li>\n<li><strong>Failover.</strong> Typically under 30 seconds because a reader is promoted against the same storage; RDS Multi-AZ is usually 60 to 120 seconds.</li>\n<li><strong>Storage.</strong> Grows automatically in 10 GiB increments to 128 TiB with no provisioning decision, no gp2-versus-io1 debate, and no storage-full incident from under-provisioning.</li>\n<li><strong>Throughput.</strong> Substantially higher write throughput on the same instance class for many workloads, because of reduced write amplification.</li>\n<li><strong>Operational features.</strong> Fast database cloning (copy-on-write), Backtrack for Aurora MySQL, Global Database, zero-ETL to Redshift, and instant crash recovery without a redo replay phase.</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>The honest case against Aurora.</strong> It costs more: higher instance rates, higher storage rates, and on Standard configuration a per-I/O charge that can exceed the instance bill on I/O-heavy workloads. Its engines are <strong>Aurora-flavoured and lag community releases</strong> — a new PostgreSQL major version reaches RDS before Aurora, which matters if you depend on a specific new feature or extension, and extension availability is a curated list rather than anything you can compile. The minimum viable footprint is larger, so a small internal service is cheaper on a <code>db.t4g.medium</code> RDS instance than on an Aurora cluster. Aurora also cannot run Oracle or SQL Server. And crucially, <strong>Aurora does not fix a bad schema or a missing index</strong> — teams that migrate hoping for a performance miracle usually find the same slow query, now more expensive.</p>\n<p style=\"line-height: 1.75\">So: choose <strong>plain RDS</strong> for small to medium OLTP with predictable load, when cost sensitivity is high, when you need the newest community engine version or an unusual extension, or when the engine is Oracle or SQL Server. Choose <strong>Aurora</strong> when you need many readers, when failover time is a hard requirement, when write throughput exceeds what a single RDS writer sustains, when storage growth is unpredictable, or when you need cloning, Global Database or zero-ETL. A defensible middle answer that impresses: start on RDS PostgreSQL, because the migration path to Aurora PostgreSQL later is a snapshot restore or a replica promotion, and you keep optionality cheaply.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Managed versus self-managed on EC2, and RDS Custom</h4>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">          RDS <i class=o>/</i> Aurora            RDS Custom               Self<i class=o>-</i>managed <i class=k>on</i> EC2\nOS access      <i class=k>none</i>            sudo, but AWS<i class=o>-</i>aware        <i class=k>full</i> root\nDB superuser   bounded         yes                        yes\nPatching       AWS             you choose, AWS assists    entirely you\nBackups        automated       automated (<i class=k>with</i> caveats)   you build it\nHA             Multi<i class=o>-</i>AZ        Multi<i class=o>-</i>AZ                   you build it\nVersion        AWS catalog     <i class=k>any</i> supported <i class=k>by</i> Custom    anything <i class=k>at</i> <i class=k>all</i>\nSupport model  AWS owns it     shared responsibility      you own it\nUse <i class=k>when</i>       <i class=k>default</i>         vendor agent <i class=o>/</i> legacy      niche engine, <i class=k>full</i>\n                               <i class=t>binary</i> <i class=o>/</i> custom patch      control mandate</code></pre></div>\n<p style=\"line-height: 1.75\">Managed is the default and should be defended as such: AWS carries patching, backup, failover, monitoring and hardware replacement, which for most teams is several engineer-months a year they would rather spend elsewhere. Both scale; they make different things easy. Reason along five axes:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Access patterns.</strong> DynamoDB requires you to know your queries up front and design keys around them; it is superb when access is by a known identifier and dreadful when product managers keep inventing new filters. Relational engines let you ask questions you had not anticipated, which is a feature with real business value early in a product's life.</li>\n<li><strong>Transactional requirements.</strong> Multi-row, multi-table invariants — inventory decrements, double-entry ledgers, booking with constraints — are enormously easier with real ACID transactions, foreign keys and unique constraints. DynamoDB has transactions, but they are bounded in item count and cost double the capacity, so they are a tool, not a foundation.</li>\n<li><strong>Join needs.</strong> If the domain is genuinely relational — orders to line items to products to customers, queried in combination — a relational engine does in one query what NoSQL does with denormalisation and application-side assembly. Denormalisation then makes writes fan out and correctness harder.</li>\n<li><strong>Scale ceiling.</strong> Be numerate. A well-tuned Aurora writer handles a very large amount of OLTP; most systems that \"need NoSQL for scale\" have never measured. The genuine ceiling is <em>single-writer write throughput</em> and dataset sizes beyond tens of terabytes. If your peak is thousands of writes per second, relational is comfortable; if it is millions with unbounded growth and a simple key-based pattern, DynamoDB's horizontal model is the right shape.</li>\n<li><strong>Team familiarity.</strong> Underrated and legitimate. A team fluent in SQL and weak on single-table design will build a slow, expensive DynamoDB schema and a fine PostgreSQL one. Operational competence is part of the architecture.</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>Polyglot persistence</strong> is right when a workload has a genuinely different shape — a relational core for transactional truth, DynamoDB for a high-volume session or event store, ElastiCache for hot reads, S3 plus Athena or Redshift for analytics, OpenSearch for full-text. It is <strong>needless complexity</strong> when it is adopted per-service by default, because each store adds its own backup story, failure mode, access control, monitoring, on-call knowledge and, worst, <strong>consistency questions between stores</strong> that nobody owns. The rule I would state: add a second data store when you can name the specific query or scale property the first one cannot serve, and when you have an answer for how the two stay consistent.</p>\n<h4 <strong>one schema per tenant in shared clusters</strong> (good isolation, moderate operational cost, per-tenant restore is possible via logical dump); <strong>shared schema with a tenant_id column and row-level security</strong> (cheapest and simplest, but per-tenant PITR requires application-level export and a noisy tenant affects everyone). That single question usually settles relational versus NoSQL.</li>\n<li><strong>Estimate the numbers out loud.</strong> Writes per second, dataset size in two years, read/write ratio. Most \"we need NoSQL\" claims dissolve here.</li>\n<li><strong>State availability and durability targets</strong> as RTO and RPO, then pick Multi-AZ, Multi-AZ DB cluster, or Global Database accordingly — do not pick a topology first and rationalise the numbers afterwards.</li>\n<li><strong>Choose, then name the trade-off and the migration path</strong> if you are wrong. \"RDS PostgreSQL now; if write throughput becomes the ceiling, the path to Aurora is a replica promotion\" is a stronger answer than a confident absolute.</li>\n</ul>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"I start from access patterns, invariants and numbers, not from a product.
