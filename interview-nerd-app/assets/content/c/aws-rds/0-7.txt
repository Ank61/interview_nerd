Replication and Multi-AZ protect you when <em>hardware</em> fails, but they faithfully copy every mistake — a bad DELETE reaches every copy within milliseconds. Amazon RDS gives you two distinct mechanisms for going back in time: <strong>automated backups</strong> (which enable point-in-time recovery) and <strong>manual snapshots</strong> (which you take on demand and keep as long as you like).</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Automated backups: a daily copy plus a continuous log</h4>\n<p style=\"line-height: 1.75\">Automated backups are two things working together.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>A daily storage-level backup.</strong> Once every 24 hours, during a 30-minute <strong>backup window</strong> you choose (or that AWS picks for you), RDS captures a full copy of the database's storage. On a Single-AZ instance this can cause a brief pause in disk activity; on a Multi-AZ instance the backup is taken from the standby so the primary is unaffected.</li>\n<li><strong>Continuous transaction logs.</strong> A <strong>transaction log</strong> is the database's own running record of every change it makes, written before the change is finalised. RDS copies these logs to Amazon S3 continuously — typically every five minutes.</li>\n</ul>\n<p style=\"line-height: 1.75\">Together these give you something more powerful than a daily copy. Take yesterday's backup, then replay the logs forward up to any moment you choose, and you have the database exactly as it was at that moment. That is <strong>point-in-time recovery</strong>.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Retention period — and the dangerous value of zero</h4>\n<p style=\"line-height: 1.75\">The <strong>retention period</strong> is how many days of backups and logs RDS keeps. It can be set from 0 to 35 days. Anything older is deleted automatically, so retention directly determines how far back you can rewind.</p>\n<p style=\"line-height: 1.75\">The default depends on how you create the instance: creating it in the <strong>console</strong> gives you <strong>7 days</strong>, while creating it with the <strong>CLI or API</strong> defaults to just <strong>1 day</strong>. That inconsistency catches out a lot of people automating their infrastructure, so always set the value explicitly in your scripts and templates.</p>\n<p style=\"line-height: 1.75\">Setting retention to <strong>0 disables automated backups entirely</strong>. No daily backup, no log archiving, and — most importantly — <strong>no point-in-time recovery at all</strong>. In production this is almost always a serious mistake: a single bad migration becomes unrecoverable. The only defensible uses of 0 are throwaway test databases and the temporary speed-up sometimes used during a large bulk data load, after which you turn it straight back on. Note that toggling retention from 0 to a positive number causes a brief outage, because RDS must restart the instance to begin backups.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Point-in-time recovery in practice</h4>\n<p style=\"line-height: 1.75\">Suppose at 14:35 today an engineer runs <code>DELETE FROM orders</code> without a WHERE clause and removes every order. You know the last good moment was about 14:32. Point-in-time recovery lets you say to RDS: \"build me a database as it was at 14:32:00 today\". RDS restores the most recent daily backup and replays transaction logs up to exactly that second.</p>\n<p style=\"line-height: 1.75\">You can restore to any second within your retention period, up to the <strong>latest restorable time</strong> — which is normally around five minutes ago, because the logs are copied every few minutes. RDS reports this value as <code>LatestRestorableTime</code> on the instance.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Manual snapshots: a copy you control</h4>\n<p style=\"line-height: 1.75\">A <strong>manual snapshot</strong> (technically a DB snapshot) is a full copy of the database that <em>you</em> trigger, whenever you want. The defining difference from automated backups is <strong>lifetime</strong>: a manual snapshot lives until you explicitly delete it. It does not expire, and it is <em>not</em> removed when you delete the database instance it came from.</p>\n<p style=\"line-height: 1.75\">That makes manual snapshots the right tool for:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Before something risky.</strong> Take a snapshot before a schema migration, a major version upgrade, or a big deployment, so you have a known-good marker to fall back to.</li>\n<li><strong>Long-term retention.</strong> Keeping a quarterly copy for compliance, far beyond the 35-day automated limit.</li>\n<li><strong>Copying between Regions.</strong> Snapshots can be copied to another Region, which is the standard building block for disaster recovery.</li>\n<li><strong>Sharing between AWS accounts.</strong> You can share a snapshot with another account — for example to give a staging account a copy of production data (after masking sensitive fields).</li>\n<li><strong>Keeping data after deletion.</strong> A <strong>final snapshot</strong> taken when you delete an instance preserves the data even though everything else goes away.</li>\n</ul>\n<p style=\"line-height: 1.75\">Snapshots are <strong>incremental</strong> at the storage level: after the first one, each subsequent snapshot only stores the blocks that changed, so they are cheaper than their nominal size suggests.
