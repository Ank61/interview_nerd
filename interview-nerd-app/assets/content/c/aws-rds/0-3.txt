Two decisions: <strong>how much disk space</strong> you want, and <strong>how fast that disk should be</strong>. Getting the first wrong can take your database offline entirely; getting the second wrong makes every query slow in a way no amount of extra CPU will rescue.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Two Ways to Measure \"Fast Disk\": IOPS and Throughput</h4>\n<p style=\"line-height: 1.75\"><strong>IOPS</strong> stands for <em>input/output operations per second</em> — roughly, how many separate read or write requests the disk can service each second. <strong>Throughput</strong> is a different measure: how many megabytes per second the disk can move in total. They are not the same thing, and the difference matters.</p>\n<p style=\"line-height: 1.75\">An analogy: imagine a delivery service. <strong>IOPS is how many separate parcels it can deliver per second</strong>, no matter how small each one is. <strong>Throughput is how many total kilograms it can move per second.</strong> A service optimized for many tiny parcels and one optimized for a few heavy pallets are different services, even if both are \"fast\".</p>\n<p style=\"line-height: 1.75\">Databases care about both because they do two very different kinds of work:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Lots of small random operations — this is IOPS-bound.</strong> A typical web application does thousands of small reads and writes: fetch one user row by ID, update one order, insert one log entry. Each one is a tiny, separate trip to a random place on the disk. What limits you is the <em>number</em> of trips, not their size.</li>\n<li><strong>Large sequential scans and bulk work — this is throughput-bound.</strong> A nightly report reading an entire large table, restoring a backup, or building an index moves a lot of bytes in long continuous runs. What limits you is megabytes per second.</li>\n</ul>\n<p style=\"line-height: 1.75\">Most day-to-day application databases are IOPS-bound, which is why IOPS is the number people talk about. But a database that runs both a live application and heavy reporting can hit either ceiling, and diagnosing which one you hit determines what you should change.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">General Purpose SSD — gp2 and gp3</h4>\n<p style=\"line-height: 1.75\"><strong>General Purpose SSD</strong> is the sensible default for most RDS databases. It is solid-state storage with balanced price and performance. There are two generations, and the difference between them is genuinely important to understand.</p>\n<p style=\"line-height: 1.75\"><strong>gp2 (the older model) ties performance to volume size.</strong> You get a fixed number of IOPS per gigabyte provisioned — 3 IOPS per GiB — with a minimum floor. So a 100 GiB volume gets 300 IOPS, and a 1,000 GiB volume gets 3,000 IOPS. The only way to buy more speed is to buy more space, whether or not you need the space. gp2 also has a <strong>burst balance</strong>: smaller volumes accumulate credits while idle and can temporarily run at a much higher IOPS rate, but when that balance is exhausted they drop back to their baseline. This is the same credit trap as burstable instance classes, applied to disk — the database runs fine for a while and then slows down sharply.</p>\n<p style=\"line-height: 1.75\"><strong>gp3 (the newer model) decouples the two.</strong> You choose the size you need, and you separately choose the IOPS and throughput you want, within limits. A gp3 volume includes a baseline (3,000 IOPS and 125 MB/s) regardless of size, and you can provision more independently. This is simpler to reason about and usually cheaper for the same performance, because you are no longer forced to over-buy capacity to get speed.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">gp2:  size  <i class=c>-----&gt; performance        (3 IOPS per GiB, plus a burst balance)</i>\n      &quot;I need 3000 IOPS, so I must buy 1000 GiB even if I store 80 GiB.&quot;\n\ngp3:  size  ..X..  performance        (<i class=k>set</i> independently)\n      &quot;I need 3000 IOPS and 100 GiB.
