{"title":"Parameter Tuning Deep Dive — Memory, Concurrency, and Engine Internals","tags":["Parameter Groups","Autovacuum","InnoDB","Memory Tuning"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">RDS gives you a managed engine but not a tuned one. The default parameter group is a <strong>safe general-purpose configuration derived from instance memory</strong>, not an optimum for your workload. A small number of parameters account for nearly all of the achievable gain, and a smaller number account for nearly all of the self-inflicted outages. The senior skill is knowing which is which, understanding that RDS parameters are <strong>formulas</strong> rather than constants, and being able to reason about the instance's <em>total memory budget</em> before changing anything.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">How RDS Derives Defaults: The Formula Language</h4>\n<p style=\"line-height: 1.75\">Parameter values in an RDS parameter group can be expressions in braces referencing instance properties. The available variables are <strong>DBInstanceClassMemory</strong> (bytes of memory available to the database, which is the instance's RAM <em>minus</em> what RDS reserves for the OS and its management processes — so it is always somewhat less than the advertised instance memory), <strong>DBInstanceVCPU</strong>, <strong>AllocatedStorage</strong> (GiB) and <strong>EndPointPort</strong>. Supported operators are <code>+ - * /</code> with integer division, and the functions <code>GREATEST()</code>, <code>LEAST()</code>, <code>SUM()</code> and <code>LOG()</code>. The units of the result are whatever the parameter uses, which is the part people get wrong.</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Parameter</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">RDS default formula</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Unit and effective value</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">PostgreSQL <code>shared_buffers</code></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><code>{DBInstanceClassMemory/32768}</code></td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">8 kB pages. Dynamic.</td></tr>\n</tbody>\n</table>\n</div>\n<p style=\"line-height: 1.75\">Because these are formulas, they <strong>re-evaluate when you change instance class</strong>. That is usually a feature — scale up and your buffer pool grows automatically. It becomes a trap when you hard-code a value: setting <code>innodb_buffer_pool_size</code> to a literal 48 GB and then downsizing to a 32 GiB instance produces an instance that cannot start, or starts and immediately thrashes. Prefer formulas over literals whenever the value should track memory.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">PostgreSQL: Memory Parameters</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>shared_buffers.</strong> PostgreSQL's own page cache, sized at 25% by default. It is deliberately <em>not</em> 75% because PostgreSQL relies on the OS page cache as a second tier — pages evicted from shared_buffers are often still in the kernel's cache, so a read costs a memcpy rather than an EBS round trip. Raising it to 40% can help write-heavy workloads with high cache turnover, but going much beyond that gives back the double-buffering benefit and can hurt. It is a <strong>static</strong> parameter.</li>\n<li><strong>work_mem.</strong> The most dangerous parameter on the instance. It is the memory a <em>single sort, hash join, hash aggregate or bitmap heap scan node</em> may use before spilling to disk — and a query can have many such nodes, each of which gets its own allocation, multiplied again by parallel workers. The worst case is roughly <code>work_mem × nodes_per_query × parallel_workers × concurrent_queries</code>. The RDS default is a conservative 4 MB. Setting it to 256 MB \"because sorts were spilling\" on an instance with 500 connections is how people OOM a database. The correct technique is to <strong>leave the global low and raise it per-session or per-role</strong> for the specific reporting queries that need it.</li>\n<li><strong>maintenance_work_mem.</strong> Used by <code>VACUUM</code>, <code>CREATE INDEX</code>, <code>ALTER TABLE ... ADD FOREIGN KEY</code> and similar. Safe to set generously (1–2 GB) because concurrency is bounded by <code>autovacuum_max_workers</code> plus your manual DDL; a larger value directly reduces the number of index passes VACUUM must make over a big table. Note <code>autovacuum_work_mem</code> overrides it for autovacuum workers specifically.</li>\n<li><strong>effective_cache_size.</strong> Allocates nothing. It tells the planner how much data it can assume is cached between shared_buffers and the OS, which shifts the cost balance toward index scans. Under-setting it makes the planner pessimistic about indexes and biased toward sequential scans.</li>\n<li><strong>random_page_cost.</strong> Defaults to 4.0, a number that encodes the seek cost of a spinning disk. On EBS gp3 or io2, values around 1.1–1.5 are far more representative and often flip the planner toward correct index choices on large tables. This is one of the highest-value single-line changes on RDS PostgreSQL.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">PostgreSQL: Checkpoints and WAL</h4>\n<p style=\"line-height: 1.75\">PostgreSQL writes changes to WAL first and periodically checkpoints dirty buffers to the data files. If checkpoints are too frequent, the same page is written repeatedly and I/O spikes; if too rare, recovery takes longer and each checkpoint dumps a huge burst. The relevant knobs are <code>max_wal_size</code> (raise it — the default is often far too small for a write-heavy database and forces checkpoints by volume rather than by time), <code>checkpoint_timeout</code> (commonly raised from 5 to 15 minutes), and <code>checkpoint_completion_target</code> (0.9 in modern versions, which spreads the write over 90% of the interval to smooth the burst). Enable <code>log_checkpoints</code> and look for the phrase \"checkpoints are occurring too frequently\" in the log — it is PostgreSQL telling you <code>max_wal_size</code> is too low. Note that on RDS, <code>wal_level</code> is already set to support replication and backups, and <code>fsync</code> and <code>full_page_writes</code> must never be disabled.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Autovacuum: Why It Exists and Why It Is an Emergency</h4>\n<p style=\"line-height: 1.75\">PostgreSQL uses <strong>MVCC</strong>: an <code>UPDATE</code> does not modify a row in place, it writes a new row version and marks the old one dead; a <code>DELETE</code> only marks dead. Dead tuples remain in the heap until <strong>VACUUM</strong> reclaims their space for reuse. Without vacuum, a table that is updated heavily grows without bound even though its logical row count is constant — <strong>bloat</strong> — and every sequential scan must read the dead space, so query time degrades proportionally. VACUUM also maintains the <strong>visibility map</strong>, which is what allows index-only scans, and runs <code>ANALYZE</code> to keep planner statistics fresh.</p>\n<p style=\"line-height: 1.75\">The second job is the one that turns neglect into an outage. Every transaction gets a 32-bit <strong>transaction ID</strong>. Visibility is determined by comparing XIDs, and with only ~4 billion values the space is circular: PostgreSQL treats 2 billion XIDs ahead as \"future\" and 2 billion behind as \"past\". If a row's XID is never <strong>frozen</strong> (marked as unconditionally visible) and the counter advances more than about 2 billion transactions past it, that row would appear to be in the future and <em>disappear</em>. To prevent this, PostgreSQL escalates:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li>At table age <code>autovacuum_freeze_max_age</code> (default 200 million), an <strong>anti-wraparound autovacuum</strong> is launched on that table <em>even if autovacuum is disabled</em>, and it is not interruptible in the normal way.</li>\n<li>As the remaining margin shrinks (around 40 million transactions left), the server logs increasingly loud <code>WARNING</code>s to vacuum the database.</li>\n<li>With about 1 million transactions remaining, PostgreSQL <strong>refuses to accept new write transactions entirely</strong>: \"database is not accepting commands to avoid wraparound data loss\". The database is now down for writes, and the fix is a vacuum over the oldest tables, which on a multi-terabyte table can take many hours. There is no faster path — you cannot scale your way out of it.</li>\n</ul>\n<p style=\"line-height: 1.75\">The same mechanism applies to <strong>MultiXact IDs</strong> (used for multiple concurrent row lockers), governed by <code>autovacuum_multixact_freeze_max_age</code>, and it bites workloads with heavy <code>SELECT ... FOR SHARE</code> or foreign-key checking. Monitor with the CloudWatch metric <strong>MaximumUsedTransactionIDs</strong> and alarm well before 1 billion; query <code>age(datfrozenxid)</code> per database and <code>age(relfrozenxid)</code> per table.</p>\n<p style=\"line-height: 1.75\"><strong>Why autovacuum falls behind on a busy table.</strong> The defaults are scale-based: autovacuum triggers when dead tuples exceed <code>autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × reltuples</code>, with a scale factor of <strong>0.2</strong>. On a 500-million-row table that means waiting for <strong>100 million dead tuples</strong> before vacuum even starts — by which point the table is massively bloated and the vacuum itself is enormous. Then vacuum throttles itself: it accumulates a cost per page (<code>vacuum_cost_page_hit/miss/dirty</code>) and sleeps for <code>autovacuum_vacuum_cost_delay</code> whenever it exceeds <code>autovacuum_vacuum_cost_limit</code>. On instances with fast EBS these throttles are far too conservative. And only <code>autovacuum_max_workers</code> (default 3) tables can be vacuumed at once across the whole instance.</p>\n<p style=\"line-height: 1.75\">The fix for a hot table is to override settings <strong>per table</strong> rather than globally, so you do not make every small table vacuum aggressively: drop the scale factor to 0.01–0.02 with a modest absolute threshold, raise the cost limit and drop the cost delay so vacuum actually uses the available IOPS, and raise <code>autovacuum_max_workers</code> if many tables need attention. PostgreSQL 13+ adds <code>autovacuum_vacuum_insert_threshold</code> and <code>autovacuum_vacuum_insert_scale_factor</code>, which matter for append-only tables that previously were never vacuumed (no dead tuples) and therefore silently accumulated freeze debt. RDS also offers <code>rds.adaptive_autovacuum</code>, which automatically makes autovacuum more aggressive as the instance approaches wraparound — leave it on.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">MySQL/InnoDB: The Parameters That Matter</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>innodb_buffer_pool_size.</strong> Dominates everything. Unlike PostgreSQL, InnoDB does its own caching and uses <code>O_DIRECT</code>, bypassing the OS page cache — which is why 75% is the sensible default rather than 25%. The buffer pool caches both data and index pages, and it also absorbs writes (dirty pages flushed later), so a larger pool reduces both read and write I/O. The diagnostic is the buffer pool hit ratio from <code>SHOW ENGINE INNODB STATUS</code> or <code>Innodb_buffer_pool_reads</code> versus <code>Innodb_buffer_pool_read_requests</code>; below ~99% on an OLTP workload means the working set does not fit. In MySQL 5.7+ it is dynamically resizable in chunks of <code>innodb_buffer_pool_chunk_size × innodb_buffer_pool_instances</code>, though the resize itself is disruptive.</li>\n<li><strong>innodb_flush_log_at_trx_commit.</strong> The durability dial. <code>1</code> (default, ACID) writes and fsyncs the redo log at every commit — a transaction is safe the moment it returns. <code>2</code> writes to the OS at commit but fsyncs about once per second: you survive a MySQL process crash but can lose up to a second of transactions if the <em>host</em> dies. <code>0</code> writes and flushes once per second: you can lose a second of commits even on a clean MySQL crash. Setting 2 can multiply commit throughput for workloads that commit one small row at a time, and is a defensible trade-off for a non-critical, reconstructable workload. It is <em>not</em> defensible for financial data. Note the analogous <code>sync_binlog</code> (default 1) has the same shape and the two are usually changed together; also note that on a <strong>Multi-AZ</strong> RDS instance the standby replication is synchronous at the storage layer, which changes the risk calculus.</li>\n<li><strong>innodb_io_capacity / innodb_io_capacity_max.</strong> Tell InnoDB's page cleaner how many IOPS it may use for background flushing and change-buffer merging. The defaults (200/2000) are tuned for a single spinning disk. On gp3 with 12,000 provisioned IOPS, leaving 200 means InnoDB flushes dirty pages far too slowly, the dirty page ratio climbs toward <code>innodb_max_dirty_pages_pct</code>, and eventually InnoDB enters furious flushing and stalls all writes. Set <code>innodb_io_capacity</code> to a realistic fraction of provisioned IOPS and <code>innodb_io_capacity_max</code> to roughly your ceiling.</li>\n<li><strong>Redo log sizing.</strong> <code>innodb_log_file_size</code> (or <code>innodb_redo_log_capacity</code> in MySQL 8.0.30+) controls how much write activity can be buffered before a forced flush. Too small and you get constant checkpointing and write stalls under bursts; too large and crash recovery takes longer.</li>\n<li><strong>The query cache is gone.</strong> It was deprecated in MySQL 5.7 and <strong>removed in MySQL 8.0</strong>. It did not scale: every write to a table invalidated every cached query against that table, and the global mutex serialised access. If an interviewer raises it, the correct answer is that caching belongs in the application or in ElastiCache, not in a globally locked structure inside the engine.</li>\n<li><strong>Temporary tables and per-session buffers.</strong> <code>tmp_table_size</code> and <code>max_heap_table_size</code> bound in-memory internal temp tables — exceed them and MySQL spills to disk, which shows up as <code>Created_tmp_disk_tables</code> climbing and queries suddenly getting much slower. MySQL 8 uses the TempTable engine with <code>temptable_max_ram</code> (default 1 GB, shared across the server) before spilling. <code>sort_buffer_size</code>, <code>join_buffer_size</code> and <code>read_rnd_buffer_size</code> are <strong>per session</strong> — the same multiplication hazard as PostgreSQL's <code>work_mem</code>. Raising <code>sort_buffer_size</code> to 32 MB with 2,000 connections is a 64 GB liability.</li>\n<li><strong>max_connections.</strong> Dynamic in MySQL (unlike PostgreSQL), so it can be raised without a reboot — which makes it tempting, and just as wrong, because the per-session buffers scale with it.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Dynamic vs Static, and Safe Rollout</h4>\n<p style=\"line-height: 1.75\">Every RDS parameter has an <strong>ApplyType</strong> of either <code>dynamic</code> or <code>static</code>. Dynamic parameters take effect when you set <code>ApplyMethod=immediate</code>; static parameters require an instance <strong>reboot</strong>, and until that reboot the instance shows parameter status <code>pending-reboot</code>. Associating a <em>different</em> parameter group with an instance also requires a reboot before it takes effect. The high-value static parameters to know: PostgreSQL <code>shared_buffers</code>, <code>max_connections</code>, <code>shared_preload_libraries</code>, <code>wal_buffers</code>; MySQL <code>performance_schema</code>, <code>innodb_log_file_size</code> (historically), <code>log_bin</code>.</p>\n<p style=\"line-height: 1.75\">A dangerous property of dynamic parameters is that they apply <em>instantly across the fleet of instances sharing the parameter group</em>. Never point production and staging at the same custom parameter group. The safe rollout procedure is: clone the parameter group, change one parameter at a time, apply to a <strong>read replica</strong> or a restored point-in-time clone first, load-test, then apply to production during a low-traffic window, and record a rollback value. Use <code>describe-db-parameters</code> with the <code>user</code> source filter to see exactly which values you have overridden versus inherited — this is the fastest way to audit drift. For a static change, schedule the reboot explicitly; on Multi-AZ, <code>reboot-db-instance --force-failover</code> applies the change by failing over, which cuts downtime to the failover window.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario: A Memory Parameter Causes Swapping</h4>\n<p style=\"line-height: 1.75\"><em>\"An engineer raised work_mem from 4 MB to 512 MB on a db.r6g.2xlarge (64 GiB) PostgreSQL instance to stop a report from spilling. Two days later the instance restarted itself during peak traffic. Explain.\"</em></p>\n<p style=\"line-height: 1.75\"><strong>Build the memory budget.</strong> Total is 64 GiB, of which RDS reserves a few GiB for the OS and its agents — call it 60 GiB usable (this is what <code>DBInstanceClassMemory</code> approximates). Fixed allocations: <code>shared_buffers</code> at 25% is ~15 GiB, <code>maintenance_work_mem</code> × up to <code>autovacuum_max_workers</code> is another 1–6 GiB when vacuum is busy, plus WAL buffers and per-backend baseline of roughly 5–10 MB × connections. With 400 connections that baseline alone is 2–4 GiB. So before any query memory, you are near 20–25 GiB committed, leaving ~35 GiB.</p>\n<p style=\"line-height: 1.75\"><strong>Now apply work_mem.</strong> 512 MB is <em>per node, per query, per parallel worker</em>. A single analytical query with three hash joins and a sort has four such nodes — 2 GB for one query. If <code>max_parallel_workers_per_gather</code> is 2, that is potentially 6 GB. Thirty concurrent queries of that shape want <strong>180 GB</strong>. Even twenty ordinary OLTP queries that happen to include a sort and a hash aggregate want 20 GB. The 35 GiB of headroom disappears the moment concurrency rises — which is exactly what happens at peak.</p>\n<p style=\"line-height: 1.75\"><strong>What the symptoms look like.</strong> CloudWatch <strong>FreeableMemory</strong> falls toward zero, <strong>SwapUsage</strong> starts climbing, and latency degrades sharply because pages the database believes are in memory are actually on EBS. Then the Linux OOM killer terminates a PostgreSQL backend; because the postmaster treats a backend killed by a signal as a possible shared-memory corruption, it <strong>restarts the entire instance</strong> and all connections drop. That is the \"unexplained restart at peak\". Enhanced Monitoring's per-process view and the PostgreSQL log (\"server process was terminated by signal 9: Killed\") confirm it.</p>\n<p style=\"line-height: 1.75\"><strong>The correct remediation.</strong> Return the global <code>work_mem</code> to a modest value — a defensible starting formula is (usable memory − shared_buffers − OS reserve) ÷ (max_connections × expected nodes per query), which for this instance lands in the tens of megabytes, not hundreds. Then grant the report the memory it needs <em>narrowly</em>: <code>SET LOCAL work_mem = '512MB'</code> inside the reporting transaction, or <code>ALTER ROLE reporting_user SET work_mem = '512MB'</code> so only that role gets it, and route the report to a read replica so its memory pressure cannot take down the writer. Verify by checking <code>EXPLAIN (ANALYZE)</code> for <code>Sort Method: quicksort</code> (in memory) versus <code>external merge</code>, and by watching FreeableMemory and SwapUsage under load. Add a CloudWatch alarm on <code>FreeableMemory</code> below ~10% and on any non-zero <code>SwapUsage</code>. The general principle to state: <strong>per-connection memory settings must always be reasoned about as a product with concurrency, never as a single number.</strong> The identical argument applies to MySQL's <code>sort_buffer_size</code> and <code>join_buffer_size</code>.</p>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"RDS default parameters are formulas over DBInstanceClassMemory, so they track instance size — I avoid hard-coding literals that break when I resize.
