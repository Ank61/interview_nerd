{"title":"Migrating to RDS — AWS DMS, Schema Conversion, and Cutover Strategy","tags":["rds","dms","migration","schema conversion"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">A database migration is a project with phases, not a command you run. The phases are <strong>assess, convert, move data, validate, cut over, and decommission</strong>, and the difficulty is concentrated almost entirely in convert and cut over — moving bytes is the easy part. The first and most consequential decision is whether the migration is <strong>homogeneous</strong> (same engine: self-managed PostgreSQL to RDS PostgreSQL, MySQL to Aurora MySQL) or <strong>heterogeneous</strong> (different engines: Oracle to PostgreSQL, SQL Server to Aurora MySQL). That single distinction changes the tooling, the timeline, and the risk profile by an order of magnitude.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Homogeneous: prefer native tools</h4>\n<p style=\"line-height: 1.75\">When the engines match, the schema, stored procedures, data types, and SQL dialect all transfer unchanged. The honest senior answer here is often <strong>do not use DMS</strong> — native tooling is simpler, faster, and more faithful:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>PostgreSQL:</strong> <code>pg_dump</code>/<code>pg_restore</code> with <code>--jobs</code> for parallel restore handles an offline move well. For low downtime, use <strong>native logical replication</strong> (publication on the source, subscription on the RDS target) — RDS PostgreSQL supports being a logical replication subscriber, and the source can be any PostgreSQL 10+. For very large databases, <code>pg_dump --format=directory --jobs=N</code> plus restoring with indexes deferred is the standard speed trick.</li>\n<li><strong>MySQL:</strong> <code>mysqldump</code> or the much faster <code>mydumper</code>/<code>myloader</code> for the bulk load, then <strong>binlog replication</strong> from the source to the RDS instance using <code>mysql.rds_set_external_master</code> and <code>mysql.rds_start_replication</code> for the catch-up phase. Aurora MySQL can also ingest directly from an <strong>S3 backup of Percona XtraBackup</strong> output, which is by far the fastest path for multi-TB clusters.</li>\n<li><strong>Snapshot-based:</strong> if the source is already RDS, cross-Region or cross-account snapshot copies, or a read replica promoted in the target location, beat any external tool.</li>\n</ul>\n<p style=\"line-height: 1.75\">DMS earns its place in homogeneous migrations when you need selective migration (a subset of tables or schemas), continuous replication into a target that is also receiving other writes, or a source you cannot install anything on. Otherwise native replication has fewer moving parts and fewer surprises.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">AWS DMS: the architecture</h4>\n<p style=\"line-height: 1.75\">DMS has four objects. A <strong>replication instance</strong> — an EC2 instance DMS manages, living in your VPC, that does all the work; its size and storage matter, because it buffers changes and caches LOBs, and an undersized instance is the most common cause of a stalled migration. <strong>Source and target endpoints</strong>, each with connection details and engine-specific extra connection attributes. A <strong>replication task</strong> binding a source, a target, a migration type, and table mappings. And optional <strong>Serverless replications</strong>, where DMS provisions and scales capacity in DMS capacity units instead of you sizing an instance.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">SOURCE (<i class=k>on</i><i class=o>-</i>prem Oracle)            DMS REPLICATION INSTANCE          TARGET (RDS PostgreSQL)\n<i class=o>+</i><i class=c>------------------+               +-----------------------+         +--------------------+</i>\n<i class=o>|</i> tables <i class=o>+</i> redo    <i class=o>|</i><i class=c>--- full load -&gt;|  reads source,        |-- bulk -&gt;| tables (no 2ndary |</i>\n<i class=o>|</i> logs (CDC src)   <i class=o>|</i>                <i class=o>|</i>  transforms, applies  <i class=o>|</i>          <i class=o>|</i> indexes yet<i class=o>!</i>)      <i class=o>|</i>\n<i class=o>|</i>                  <i class=o>|</i><i class=c>--- CDC stream -&gt;|  buffers changes on  |-- DML --&gt;|                    |</i>\n<i class=o>|</i> STAYS LIVE       <i class=o>|</i>   (redo<i class=o>/</i>binlog<i class=o>/</i> <i class=o>|</i>  its own storage     <i class=o>|</i>          <i class=o>|</i> catch up, lag <i class=o>-</i><i class=o>&gt;</i> <i class=n>0</i> <i class=o>|</i>\n<i class=o>|</i> the whole <i class=t>time</i>   <i class=o>|</i>    WAL slot)    <i class=o>|</i>                      <i class=o>|</i>          <i class=o>|</i>                    <i class=o>|</i>\n<i class=o>+</i><i class=c>------------------+                +-----------------------+         +--------------------+</i>\n     <i class=o>|</i>                                                                          <i class=o>^</i>\n     <i class=o>+</i><i class=c>--- application keeps writing here until CUTOVER, then switches ----------+</i>\n\nSizing the replication instance <i class=o>=</i> the #<i class=n>1</i> operational failure. Requires the source to be quiesced or accepts that changes during the load are lost. Fine for a one-shot move with a long outage window.</li>\n<li><strong>Full load + CDC</strong> (<code>full-load-and-cdc</code>): the workhorse. DMS copies existing rows while simultaneously capturing changes from the source's change log, then applies the buffered changes once the load finishes and keeps applying them continuously. The source stays fully live and writable for days. This is what makes low-downtime migration possible.</li>\n<li><strong>CDC only</strong> (<code>cdc</code>): start replicating from a specified log position or timestamp. Used when you seeded the target another way — for example a native dump/restore or an Aurora snapshot ingest — and only need the delta. For huge databases this is often the right combination: fast native bulk load, DMS for the tail.</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>How CDC works</strong> depends on the source: Oracle redo logs via LogMiner or the much faster <strong>Binary Reader</strong>, MySQL binary logs in ROW format, PostgreSQL logical decoding through a <strong>replication slot</strong> (<code>pglogical</code> or <code>test_decoding</code>), SQL Server transaction logs with CDC or change tracking enabled. Each has prerequisites that must be arranged with the source DBA weeks in advance — enabling supplemental logging on Oracle, setting <code>binlog_format=ROW</code> and a sufficient <code>binlog_retention</code> on MySQL, setting <code>wal_level=logical</code> on PostgreSQL. A PostgreSQL replication slot that DMS stops consuming will <strong>pin WAL indefinitely and fill the source's disk</strong>, which is a genuine way to take down the system you are migrating away from — monitor it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What DMS does not do</h4>\n<p style=\"line-height: 1.75\">This is the part interviewers probe, because it is where projects fail. <strong>DMS migrates data, not database objects.</strong> By default it creates only enough target schema to land the rows: tables with columns and primary keys. It does <strong>not</strong> create secondary indexes, foreign keys, check constraints, defaults, sequences, triggers, views, stored procedures, functions, packages, or user-defined types. Believing otherwise and discovering it during cutover verification is a classic failure.</p>\n<p style=\"line-height: 1.75\">The correct practice is to <strong>pre-create the schema on the target</strong> (via SCT for heterogeneous, or native dump of schema-only for homogeneous), then deliberately <strong>drop or defer secondary indexes, foreign keys, and triggers before the full load</strong> and recreate them afterward. The reason is performance: every secondary index maintained during a bulk insert multiplies the write cost, and foreign keys force per-row lookups. On a multi-TB load this is not a marginal optimization — it routinely changes a 40-hour load into a 6-hour load plus a 3-hour parallel index build. Triggers are worse than slow: a trigger firing during a bulk load can corrupt the migrated data by applying business logic twice. DMS's target table preparation mode (<code>DO_NOTHING</code>, <code>DROP_AND_CREATE</code>, <code>TRUNCATE_BEFORE_LOAD</code>) should normally be <code>DO_NOTHING</code> or <code>TRUNCATE_BEFORE_LOAD</code> so your carefully built schema survives.</p>\n<p style=\"line-height: 1.75\"><strong>LOB handling</strong> is DMS's other well-known limitation and deserves a precise answer. Because DMS cannot know a LOB's size in advance, it offers three modes. <strong>Limited LOB mode</strong> is fastest: you declare a <code>MaxLOBSize</code>, DMS allocates that much memory per LOB and migrates them inline — but <strong>anything larger is silently truncated</strong>, which is data loss you will not notice without validation. <strong>Full LOB mode</strong> migrates LOBs of any size by fetching them in chunks in a separate pass, which is correct but dramatically slower and cannot be used with parallel-load optimizations. <strong>Inline LOB mode</strong> is the compromise: LOBs under a threshold go inline with the row, larger ones are fetched individually. Also note that full LOB mode requires the target table to have a primary key, and that some LOB types are unsupported for certain engine pairs. The practical approach is to query the source for <code>max(length(lob_column))</code> per table, set limited LOB mode with a size safely above that, and validate.</p>\n<p style=\"line-height: 1.75\">Other gaps worth naming: DMS does not migrate users, roles, grants, or passwords; it does not preserve <strong>sequence or auto-increment current values</strong>; and it does not guarantee ordering guarantees across tables beyond transactional consistency options you must enable.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Table mappings, transformations, and assessment</h4>\n<p style=\"line-height: 1.75\"><strong>Table mappings</strong> are JSON rules governing what moves. <code>selection</code> rules include or exclude schemas and tables by wildcard. <code>transformation</code> rules rename schemas, tables, and columns, change case (essential for Oracle-to-PostgreSQL, where Oracle's uppercase identifiers become awkward quoted identifiers in PostgreSQL unless lowercased), add or remove columns, and change data types. <code>table-settings</code> rules enable <strong>parallel load</strong>, which partitions a large table by ranges or by existing partitions and loads segments concurrently — the single most effective lever for shortening a full load of a very large table.</p>\n<p style=\"line-height: 1.75\"><strong>Premigration assessments</strong> run before the task and report engine-specific blockers: unsupported data types, tables without primary keys (which cannot do CDC updates or deletes correctly), LOB columns that will be affected by your LOB mode, and missing source prerequisites. Running the assessment and reading it is a five-minute step that prevents days of confusion. <strong>Data validation</strong> is a separate task feature that, after the load, compares source and target row by row and reports mismatches into <code>awsdms_validation_failures_v1</code> — it is not free (it adds load to both sides) but for a migration you intend to cut over to, it is not optional.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Heterogeneous migration and AWS SCT</h4>\n<p style=\"line-height: 1.75\">When the engines differ, data movement is the small half of the project. <strong>AWS Schema Conversion Tool</strong> (and its in-console successor, DMS Schema Conversion) connects to the source, analyzes the schema, and produces target-dialect DDL plus an <strong>assessment report</strong> that categorizes every object as automatically converted, convertible with minor effort, or requiring manual action, with estimated hours. That report is the input to your project plan and the honest basis for telling leadership how long this will take.</p>\n<p style=\"line-height: 1.75\">SCT converts tables, indexes, constraints, views, and simple procedural code well. What it converts poorly or not at all is exactly what enterprise databases are full of: <strong>Oracle PL/SQL packages</strong> (PostgreSQL has no package concept — these become schemas of functions, and package-level state has no equivalent), autonomous transactions, <code>DBMS_*</code> built-ins, hierarchical <code>CONNECT BY</code> queries, Oracle's treatment of empty string as NULL, <code>NUMBER</code> without precision mapping awkwardly to <code>numeric</code>, sequence and <code>ROWNUM</code> semantics, hints, and anything touching the Oracle-specific date/time model. SQL Server brings its own: T-SQL procedures, <code>MERGE</code> semantics, temp-table scoping, and CLR functions. Expect <strong>substantial manual rework</strong> and budget for it explicitly — a realistic heterogeneous migration is 60-80% application and stored-code effort, not data movement.</p>\n<p style=\"line-height: 1.75\">Two supporting facts worth knowing: SCT can also scan <strong>application source code</strong> for embedded SQL that will need changing, which is often the forgotten scope; and for very large or bandwidth-constrained sources, DMS can be combined with <strong>AWS Snowball Edge</strong> to ship the bulk data physically while CDC catches up over the network afterward.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cutover strategy</h4>\n<p style=\"line-height: 1.75\">Cutover is where a well-run migration is won or lost. There are two families.</p>\n<p style=\"line-height: 1.75\"><strong>Freeze and switch</strong> is the default and, done properly, is short. Stop writes (put the application into read-only mode or stop the writer fleet — do <em>not</em> rely on \"asking people not to use it\"), wait for CDC lag to reach zero and <strong>confirm it explicitly</strong> via <code>CDCLatencyTarget</code>, run verification, fix sequences, repoint the connection string, resume writes. With everything scripted and rehearsed this is commonly 5-15 minutes. The risk is concentrated: if verification fails you either roll back or extend the outage.</p>\n<p style=\"line-height: 1.75\"><strong>Dual-write</strong> means the application writes to both databases for a period, reading from one and gradually shifting reads. It sounds safer and is usually harder: you must handle partial failures (write succeeded on old, failed on new — now what?), ordering, and reconciliation, and you are running application code that nobody will ever run again. It is justified when the outage budget is genuinely zero and the team has the maturity to build reconciliation tooling. A middle path many teams prefer is <strong>freeze-and-switch with bidirectional CDC prepared</strong>: cut over quickly, but have a reverse DMS task ready from new back to old so a rollback hours later does not lose data.</p>\n<p style=\"line-height: 1.75\"><strong>Verification</strong> must be defined before the window, with pass/fail thresholds:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Row counts</strong> per table on both sides — cheap, catches gross failures, catches nothing subtle.</li>\n<li><strong>Checksums / aggregate comparisons</strong> — <code>sum()</code> of numeric columns, <code>md5</code> of concatenated key columns over ranges, or DMS data validation. This is what catches truncated LOBs, character-set mangling, and timezone shifts.</li>\n<li><strong>Targeted business queries</strong> — total order value for last month, count of active users — run on both and compared, because these are what stakeholders will check.</li>\n<li><strong>Constraint and index verification</strong> — confirm every expected index, foreign key, and trigger exists on the target, since DMS did not create them.</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>Sequences and auto-increment are the single most common cutover bug.</strong> DMS copies the rows but not the sequence state, so the target's sequence still sits at 1 and the first insert after cutover collides with an existing primary key. Every runbook must include: for PostgreSQL, <code>setval</code> on every sequence to <code>max(pk) + safety margin</code>; for MySQL, <code>ALTER TABLE ... AUTO_INCREMENT = N</code>. Add a comfortable margin, since a gap costs nothing and a collision costs an outage.</p>\n<p style=\"line-height: 1.75\"><strong>Connection cutover</strong> should never require a code deploy. Put the database host behind a <strong>Route 53 CNAME with a short TTL</strong> (30-60 seconds) or in <strong>Secrets Manager / Parameter Store</strong> that the application reads at startup or refreshes. Then cutover is a DNS or secret update plus a rolling restart, and rollback is the same operation in reverse. Lower the TTL days in advance, because a TTL change only takes effect after the old TTL expires.</p>\n<p style=\"line-height: 1.75\"><strong>Rollback plan:</strong> keep the source database running and untouched for an agreed period (a week is typical), define the decision deadline and who owns it, and be explicit about what rollback costs after writes have landed on the new system — which is why the reverse CDC task, if you can build it, converts an irreversible decision into a reversible one.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">DMS beyond migration</h4>\n<p style=\"line-height: 1.75\">A CDC task never has to end. The same machinery is widely used for ongoing replication: streaming changes into <strong>S3</strong> as Parquet for a data lake, into <strong>Kinesis Data Streams</strong> or <strong>Amazon MSK</strong> for event-driven consumers, into <strong>Redshift</strong> or <strong>OpenSearch</strong> for analytics and search, or into a second RDS instance to offload reporting. This gives you change data capture without instrumenting the application, and it is a legitimate architecture answer when asked \"how do we get operational data into the warehouse without dual-writing?\" The caveats are real: DMS adds load to the source's log reading, it is not a low-latency event bus (expect seconds, not milliseconds), schema evolution on the source needs handling, and for high-throughput permanent pipelines a purpose-built CDC tool or the engine's native logical replication may be a better long-term fit than a DMS task nobody owns.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario: 8 TB Oracle to Aurora PostgreSQL, 30-minute outage budget</h4>\n<p style=\"line-height: 1.75\"><em>Situation:</em> On-premises Oracle 19c, 8 TB, ~2,000 tables, 340 PL/SQL packages, 12 applications connecting, 10 Gbps Direct Connect. Business allows a single 30-minute write outage on a weekend. Target: Aurora PostgreSQL.</p>\n<p style=\"line-height: 1.75\"><strong>Phase 1 — Assess (weeks 1-3).</strong> Run SCT against the Oracle schema and read the assessment report honestly: expect tables, indexes, and views to convert largely automatically and expect the 340 packages to be the project. Categorize them — many will be dead code nobody has called in years, which you prove with Oracle's auditing or <code>DBA_HIST</code> data before deleting rather than porting. Run SCT's application code scanner against the 12 applications' repositories to find embedded Oracle-specific SQL. Produce a real estimate; if the report says 1,400 hours of manual conversion, say so. Also inventory: LOB columns and their maximum sizes, tables without primary keys (these break CDC updates and deletes and must be given a key or handled specially), data types with no clean mapping (<code>NUMBER</code> without precision, <code>DATE</code> carrying a time component, <code>RAW</code>), and identifier case.</p>\n<p style=\"line-height: 1.75\"><strong>Phase 2 — Convert and build (weeks 4-16).</strong> Apply SCT output to build the Aurora PostgreSQL schema, then do the manual work: rewrite packages as schemas of functions, replace <code>CONNECT BY</code> with recursive CTEs, handle the empty-string-is-NULL difference explicitly because it silently changes query results, and decide on identifier case via a DMS transformation rule that lowercases everything. Build a functional test suite that runs the same business operations against both databases and compares results — this is the artifact that makes cutover a decision rather than a leap of faith.</p>\n<p style=\"line-height: 1.75\"><strong>Phase 3 — Data movement (weeks 12-18, overlapping).</strong> Source prerequisites with the Oracle DBA: enable supplemental logging and archive logging, and use <strong>Binary Reader</strong> rather than LogMiner for CDC, because on a busy 8 TB system LogMiner will not keep up. Size the replication instance generously (a large memory-optimized class with ample storage) and put it in a private subnet with Direct Connect reachability. Strategy for speed: pre-create the schema but <strong>drop secondary indexes, foreign keys, and triggers</strong>; run <code>full-load-and-cdc</code> with <strong>parallel load</strong> table-settings on the twenty largest tables, partitioned by primary key ranges; set <strong>limited LOB mode</strong> with <code>MaxLOBSize</code> set above the measured maximum from the inventory, and explicitly validate LOB lengths afterward. When the full load completes, build indexes and constraints <strong>in parallel</strong> while CDC continues to apply changes — this overlap is where the schedule is won. Then let CDC run for weeks, monitoring <code>CDCLatencySource</code>, <code>CDCLatencyTarget</code>, and the replication instance's free storage.</p>\n<p style=\"line-height: 1.75\"><strong>Phase 4 — Rehearse (weeks 18-20).</strong> Rehearse the cutover at least twice against a clone of the target, with a stopwatch, using the actual runbook. Time each step. Lower the Route 53 TTL to 30 seconds a week in advance. Pre-write and test the sequence-fixing script, the verification queries with their pass/fail thresholds, and the rollback procedure. Build the <strong>reverse CDC task</strong> (Aurora back to Oracle) and confirm it works, so that a rollback two days later does not mean losing two days of orders.</p>\n<p style=\"line-height: 1.75\"><strong>Phase 5 — Cutover (30-minute window).</strong> Minute 0: put all 12 applications into read-only mode via a feature flag; confirm zero writes on Oracle by checking active sessions, not by trusting the flag. Minute 2: watch <code>CDCLatencyTarget</code> fall to zero and confirm DMS has applied everything. Minute 5: stop the DMS task cleanly. Minutes 5-15: run verification — row counts on all tables, checksums on the top 50, the agreed business queries, index and constraint existence checks, and LOB length spot-checks. Minute 15: run the sequence advance script for every sequence to <code>max(pk) + 1000</code>. Minute 18: update the Route 53 CNAME and the Secrets Manager entry; roll application instances. Minute 25: smoke tests, then lift read-only and watch error rates. If verification fails at minute 15, abort — lift read-only on Oracle, nothing was lost, and reschedule. That abort branch must be written down and rehearsed too.</p>\n<p style=\"line-height: 1.75\"><strong>Phase 6 — Aftermath.</strong> Start the reverse CDC task immediately so Oracle stays current as a rollback target. Keep Oracle running and licensed for an agreed period — a month is common for a system of this size — then decommission deliberately with a final export archived to S3. Watch Aurora Performance Insights closely for the first weeks: the most common post-migration surprise is not correctness but <strong>query plans</strong>, because PostgreSQL's planner makes different choices than Oracle's, and queries tuned for Oracle hints often need new indexes.
