A missing index that turns a 40-million-row sequential scan into an index lookup is often a <strong>1,000× reduction in work</strong>. No instance class upgrade gives you 1,000× — the largest RDS instances give you maybe 30× the smallest, at 30× the price, and the bad query will outgrow it again. Worse, scaling to hide a query removes the pressure that would have found it, so you arrive at the next crisis with a larger bill and the same defect.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Indexing.</strong> Use Performance Insights top SQL and <code>pg_stat_statements</code> / <code>sys.statement_analysis</code> to rank by total time. Prefer composite indexes ordered by selectivity and partial indexes over many single-column ones, and drop unused indexes to recover write throughput.</li>\n<li><strong>N+1 elimination.</strong> The most common application-level scaling defect: a loop issuing one query per row. 200 sub-millisecond queries is 200 network round trips. Fix with eager loading, a single <code>JOIN</code>, or an <code>IN</code> batch — often a 50× improvement in request latency with zero infrastructure change.</li>\n<li><strong>Batching writes.</strong> One transaction per row means one commit fsync per row. Batching 1,000 inserts into one transaction (or using <code>COPY</code> in PostgreSQL / multi-row <code>INSERT</code> in MySQL) can improve ingest throughput by an order of magnitude, because you pay one commit instead of a thousand.</li>\n<li><strong>Query rewrites.</strong> Replace <code>SELECT *</code> on wide tables, replace <code>OFFSET</code>-based pagination (which re-scans everything skipped) with keyset pagination, avoid functions on indexed columns, and push filtering into the database rather than into application loops.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Rung 2: Cache</h4>\n<p style=\"line-height: 1.75\">Most OLTP workloads are read-dominated and heavily skewed — a small set of rows serves a large fraction of requests. <strong>Amazon ElastiCache</strong> (Redis/Valkey or Memcached) in front of the database removes those reads entirely, at microsecond latency and a fraction of the cost of the database capacity they would consume. Memcached is simpler and multi-threaded; Redis/Valkey gives you data structures, persistence, replication and cluster mode, and is the default choice unless you want a pure LRU blob cache.</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Pattern</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">How it works</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Trade-off</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\"><strong>Cache-aside</strong> (lazy loading)</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">App reads cache; on miss reads DB and populates cache. Set TTLs by tolerance for staleness, not by convenience. Explicit invalidation on write gives freshness; TTL gives bounded incorrectness. Use both. Versioned or namespaced keys (<code>user:123:v7</code>) let you invalidate a whole family by bumping a version instead of enumerating keys.</p>\n<p style=\"line-height: 1.75\"><strong>Failure modes you must name in an interview.</strong> <em>Thundering herd / stampede</em>: a popular key expires and a thousand concurrent requests all miss and all hit the database simultaneously — mitigate with per-key locking (single-flight, so one request refreshes while others serve stale or wait), probabilistic early expiration, or background refresh. <em>Cold cache</em>: after a cache node restart or deployment, the entire read load lands on the database at once, which can be fatal if the database was sized assuming a 95% hit rate — mitigate by warming the cache, by using replicas so a single node loss does not empty the cache, and by ensuring the database can survive a full cache loss (or accept load shedding). <em>Stale reads</em>: the window between DB write and cache invalidate is a real correctness hazard for read-your-own-writes; a common fix is to write-through or delete-then-write with a short \"do not repopulate\" marker. <em>Hot key</em>: one key so popular it saturates a single Redis shard — mitigate with client-side caching or key splitting.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Rung 3: Scale Up</h4>\n<p style=\"line-height: 1.75\">Vertical scaling is the simplest lever: one <code>modify-db-instance --db-instance-class</code> call. Understand the cost. On a <strong>Single-AZ</strong> instance, the change requires a restart and the instance is unavailable for several minutes. On <strong>Multi-AZ</strong>, RDS modifies the standby first, fails over, then modifies the old primary — so downtime shrinks to the failover window (typically 60–120 seconds), which is a strong operational argument for Multi-AZ beyond durability. Either way the cache is cold afterwards, so expect a latency tail while shared_buffers or the buffer pool refills.</p>\n<p style=\"line-height: 1.75\">Vertical scaling ends for three reasons: there is a largest instance class and you will eventually reach it; cost grows linearly while benefit does not, because a workload bottlenecked on lock contention or commit fsync gains nothing from more vCPUs; and it does nothing for availability. Also remember that instance class changes re-evaluate the memory formulas in your parameter group, which is helpful if you used formulas and dangerous if you hard-coded literals. <strong>Aurora Serverless v2</strong> is the elastic form of this rung, scaling capacity in fine-grained ACU increments without a restart, which is attractive for spiky or unpredictable load.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Rung 4: Scale Reads</h4>\n<p style=\"line-height: 1.75\">Read replicas move read traffic off the writer. RDS supports up to 15 read replicas per source for MySQL, MariaDB and PostgreSQL, and Aurora supports up to 15 readers sharing the same storage volume. The replication mechanisms differ materially and you should say so: RDS MySQL uses <strong>asynchronous binlog replication</strong> with a single applier thread by default (parallel appliers are configurable), RDS PostgreSQL uses <strong>streaming WAL replication</strong> with a physical replica, and <strong>Aurora replicates at the storage layer</strong>, so readers see the same volume and lag is typically tens of milliseconds rather than seconds.</p>\n<p style=\"line-height: 1.75\"><strong>Routing.</strong> Either the application decides (an explicit read-only connection or session, chosen per query or per request) or a proxy decides. Aurora gives you a <strong>reader endpoint</strong> that DNS-round-robins across readers, and <strong>RDS Proxy</strong> supports read-only endpoints for Aurora. Application-level routing is more precise because only the application knows whether a given read tolerates staleness.</p>\n<p style=\"line-height: 1.75\"><strong>Replica lag and read-your-writes.</strong> This is the correctness problem that makes read replicas a design decision rather than a configuration change. If a user updates their profile and the next request reads from a lagging replica, they see the old value and file a bug. Strategies, in increasing sophistication: route the entire request to the writer for a short window after a write (sticky-to-primary, simple and effective); route only <em>that user's</em> reads to the writer using a session flag; or use an <strong>LSN/GTID token</strong> — capture the write position (<code>pg_current_wal_lsn()</code> in PostgreSQL, GTID in MySQL), pass it to the client, and have the read path either wait for the replica to catch up to that position or fall back to the writer. Aurora MySQL 3 also exposes session-level read consistency settings. Monitor <code>ReplicaLag</code> (RDS) or <code>AuroraReplicaLag</code> and alarm on it; a replica that falls behind is silently serving stale data.</p>\n<p style=\"line-height: 1.75\"><strong>The limit of read scaling.</strong> Every replica applies <em>every write</em>. Adding replicas multiplies read capacity but adds zero write capacity, and on RDS MySQL the single-threaded applier can become the bottleneck so that replicas fall further behind as writes grow. If your workload is 60% writes, read replicas solve very little. That is why the next rungs exist.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Rung 5: Partitioning Within One Database</h4>\n<p style=\"line-height: 1.75\">Partitioning splits one logical table into physical sub-tables inside the same database — a much lighter-weight step than sharding because there is no cross-node coordination, no application routing layer, and transactions still work normally. <strong>PostgreSQL declarative partitioning</strong> supports <code>RANGE</code>, <code>LIST</code> and <code>HASH</code>; the planner performs <strong>partition pruning</strong> so a query filtered on the partition key touches only the relevant partitions. The killer feature for time-series data is that dropping old data becomes <code>DROP TABLE</code> on a partition — instantaneous and generating no dead tuples — instead of a <code>DELETE</code> of 200 million rows that bloats the table and buries autovacuum. It also makes vacuum, index builds and statistics per-partition, so maintenance scales.</p>\n<p style=\"line-height: 1.75\">The constraints matter: in PostgreSQL, any <strong>unique or primary key constraint must include the partition key</strong>, which frequently forces a schema change; indexes are per-partition; and queries that do not filter on the partition key scan every partition. <code>pg_partman</code> automates partition creation and retention. <strong>MySQL partitioning</strong> (RANGE/LIST/HASH/KEY) has stricter limits — every unique key must contain all columns of the partitioning expression, and <strong>foreign keys are not supported</strong> on partitioned tables at all, which is often disqualifying.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Rung 6: Scale Writes and Offload</h4>\n<p style=\"line-height: 1.75\">Write scaling is the hard problem, because in a single-writer architecture there is exactly one place writes can go. The techniques, in order:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Reduce write amplification.</strong> Every index multiplies write cost; every trigger and foreign key adds work; in PostgreSQL, updating an indexed column defeats HOT updates and forces index writes plus vacuum debt. Auditing and dropping unused indexes is genuine write capacity recovered for free.</li>\n<li><strong>Batch and buffer.</strong> One commit per row is the most expensive possible pattern. Aggregate writes in the application or through a queue (SQS, Kinesis) and flush in batches; use <code>COPY</code> for bulk ingest. This is often a 10× gain.</li>\n<li><strong>Move high-volume append-only data out.</strong> Metrics, events, audit logs and IoT readings are usually the majority of write volume and almost never need relational semantics. Send time-series to <strong>Amazon Timestream</strong> or an event pipeline; put large blobs in <strong>S3</strong> and keep only a pointer plus metadata in the database. Removing a 100,000-writes-per-second telemetry table from an OLTP database often removes the entire scaling problem.</li>\n<li><strong>Move analytics off the OLTP database.</strong> Long-running aggregate scans compete for buffer cache and I/O with transactional traffic. Use <strong>Aurora zero-ETL integration with Amazon Redshift</strong>, an export to S3 queried through Athena, or at minimum a dedicated read replica so analytics cannot destabilise the writer.</li>\n<li><strong>Split by service.</strong> Before sharding, consider vertical decomposition: separate databases per bounded context. You lose cross-domain joins and transactions, which is a real cost, but it is far less invasive than sharding one table.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Rung 7: Sharding</h4>\n<p style=\"line-height: 1.75\">Sharding partitions data across independent database clusters by a <strong>shard key</strong>, and is the only approach that scales writes horizontally without bound. It is also the step teams delay as long as possible, and correctly so, because it changes the programming model permanently.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Shard key selection</strong> is the decision you cannot easily undo. It must produce even distribution (avoiding hot shards — a <code>tenant_id</code> key breaks when one tenant is 40% of your data), and it must align with your dominant access pattern so most queries hit exactly one shard. <code>tenant_id</code>, <code>user_id</code> and <code>region</code> are common; auto-increment IDs are a poor choice because they hot-spot the newest shard.</li>\n<li><strong>Cross-shard queries</strong> must be scatter-gather: query every shard and merge in the application. Aggregations, sorting and joins across shards become your problem, not the database's, and tail latency becomes the slowest shard's latency.</li>\n<li><strong>Cross-shard transactions</strong> are effectively gone. You either design so transactions never span shards, or adopt sagas with compensating actions and accept eventual consistency. Two-phase commit is possible and generally avoided for its availability cost.</li>\n<li><strong>Resharding</strong> is the operational nightmare: moving live data between shards while serving traffic, with dual writes and backfills and a cutover. Using <strong>consistent hashing</strong> or a directory/lookup service that maps logical shards to physical clusters, and starting with more logical shards than physical ones, makes resharding a rebalance rather than a rewrite.</li>\n<li><strong>Managed options.</strong> <strong>Aurora PostgreSQL Limitless Database</strong> provides AWS-managed horizontal sharding with a single endpoint; outside AWS-managed options, Vitess is the established MySQL sharding layer. Evaluate these before hand-rolling.</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>When the answer is a different data store.</strong> Sometimes the honest conclusion is that the workload is not relational. <strong>DynamoDB</strong> is the right answer for high-volume key-value or single-table access with predictable patterns and no ad-hoc querying — it scales writes essentially without limit, at the cost of giving up joins, flexible queries and multi-item transactions beyond limited support. <strong>OpenSearch</strong> is the right answer for full-text search and faceted filtering, which relational databases do badly. <strong>Redshift</strong> is the right answer for analytical scans over large history. The mature position is that these are complements, not replacements: keep the transactional core relational and move the workloads that do not fit.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario: A SaaS Database at the Limit</h4>\n<p style=\"line-height: 1.75\"><em>\"A multi-tenant SaaS on RDS PostgreSQL db.r6g.4xlarge is at 85% CPU during business hours. Traffic is 90% reads, 10% writes, and is projected to triple in a year. What do you do?\"</em></p>\n<p style=\"line-height: 1.75\"><strong>1. Measure before deciding.</strong> Open Performance Insights and check whether DB load exceeds the vCPU line, and what the wait composition is. Suppose top SQL shows the top three digests account for 60% of DB load, and waits are dominated by CPU and <code>IO:DataFileRead</code>. That immediately says: inefficient queries reading too much data, not lock contention and not a write ceiling.</p>\n<p style=\"line-height: 1.75\"><strong>2. Rung 1.</strong> <code>EXPLAIN (ANALYZE, BUFFERS)</code> the top three. If one is a tenant-scoped dashboard query doing a sequential scan because its index lacks <code>tenant_id</code> as the leading column, a composite index built with <code>CREATE INDEX CONCURRENTLY</code> may cut 40% of load in an afternoon at zero infrastructure cost. This is always the first move, and it buys time for everything else.</p>\n<p style=\"line-height: 1.75\"><strong>3. Rung 2.</strong> Identify read-heavy, staleness-tolerant data — tenant configuration, feature flags, plan limits, reference lookups. These are read on nearly every request and change rarely: perfect cache-aside candidates in ElastiCache with a 5-minute TTL plus explicit invalidation on write. Plan explicitly for the cold-cache scenario so a Redis failover does not take the database down.</p>\n<p style=\"line-height: 1.75\"><strong>4. Rung 4.</strong> With 90% reads, replicas are genuinely the right structural lever here. Add two read replicas, route reporting and dashboard reads to them, and handle read-your-writes by keeping a user's reads on the writer for a few seconds after any write by that user. Alarm on <code>ReplicaLag</code>.</p>\n<p style=\"line-height: 1.75\"><strong>5. Rung 3 as a bridge.</strong> If the projected 3× still does not fit, one instance-class step up on the writer is a legitimate stopgap while structural work proceeds — but call it explicitly a stopgap with an expiry date, not a solution.</p>\n<p style=\"line-height: 1.75\"><strong>6. Rungs 5 and 6.</strong> If a single events or audit table dominates size and write volume, convert it to <strong>declarative range partitioning</strong> by month so retention becomes <code>DROP TABLE</code>, and move analytics to a replica or to Redshift via zero-ETL so long scans stop competing with OLTP traffic.</p>\n<p style=\"line-height: 1.75\"><strong>7. Only then, rung 7.</strong> If growth continues past what one writer can absorb, multi-tenancy gives a natural shard key — <code>tenant_id</code> — and the schema is likely already tenant-scoped, which is the best possible starting position for sharding. Plan for tenant skew by allowing large tenants to occupy a dedicated shard.
