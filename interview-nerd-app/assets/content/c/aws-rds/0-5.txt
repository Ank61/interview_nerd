{"title":"Multi-AZ Deployments — High Availability and Automatic Failover","tags":["rds","multi-az","high-availability","failover"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">A <strong>Multi-AZ deployment</strong> means Amazon RDS keeps a second, continuously updated copy of your database running in a physically separate data centre, ready to take over automatically if the first one fails. It exists to keep your application <em>available</em> — it does not make your database faster, and the second copy does not answer any of your queries.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The problem: one server is one point of failure</h4>\n<p style=\"line-height: 1.75\">Imagine a small online shop whose database runs on a single RDS instance. Everything the shop does — showing products, taking orders, logging people in — goes through that one database. Now consider the things that can go wrong with a single machine: its disk can fail, its physical host can die, its operating system can need a reboot, its database engine can crash, or the entire data centre it sits in can lose power or network connectivity.</p>\n<p style=\"line-height: 1.75\">In every one of those cases the shop is simply <strong>down</strong>. Not slow — down. And it stays down until a human notices, decides what to do, and restores from a backup onto a new instance, which for a real database can take hours. That is the problem Multi-AZ solves.</p>\n<p style=\"line-height: 1.75\">Quick vocabulary before we go further. A <strong>Region</strong> is a geographic area where AWS operates, like Ireland. Within it, an <strong>Availability Zone</strong> (AZ) is one or more physically separate data centres with their own power, cooling and networking. Two AZs in the same Region are close enough that data can travel between them in a couple of milliseconds, but far enough apart that one flooding does not affect the other. <strong>Failover</strong> is the act of switching over so that a backup system takes the place of the failed one.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What a Multi-AZ deployment actually is</h4>\n<p style=\"line-height: 1.75\">When you enable Multi-AZ on an RDS instance, AWS provisions a second instance of the same size and configuration in a <em>different Availability Zone</em>. That second instance is called the <strong>standby</strong>. Every change written to the primary is also written to the standby. The standby sits there, fully up to date, doing nothing visible — waiting.</p>\n<p style=\"line-height: 1.75\">You do not manage the standby. You cannot connect to it. You do not get a second endpoint. From your application's point of view nothing changes at all: there is still one endpoint, one database, one set of credentials. font-size: 1.25rem; font-weight: 600\">Synchronous replication, explained plainly</h4>\n<p style=\"line-height: 1.75\"><strong>Replication</strong> just means copying changes from one database to another. The important question is <em>when</em> the copy happens relative to telling your application the write succeeded.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Synchronous.</strong> Your application sends a write. The primary records it, sends it to the standby, and waits for the standby to confirm it has recorded it too. Only <em>then</em> does the primary tell your application \"committed\". The consequence: the standby is never behind, so a failover cannot lose an acknowledged transaction.</li>\n<li><strong>Asynchronous.</strong> The primary records the write, immediately tells your application \"committed\", and sends the change to the copy afterwards. The copy is usually a fraction of a second behind, but if the primary dies in that gap, those last changes are gone.</li>\n</ul>\n<p style=\"line-height: 1.75\">Multi-AZ uses <strong>synchronous</strong> replication precisely because the whole point is not losing data during a failure. The trade-off is a small amount of extra write latency — every commit now includes a network round trip to another data centre. In practice that is a few milliseconds and most applications never notice, but a write-heavy, latency-sensitive workload should measure it. Reads are unaffected, because reads never touch the standby.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What happens during a failover, step by step</h4>\n<p style=\"line-height: 1.75\">RDS continuously health-checks the primary. When it decides the primary is unhealthy, this sequence runs automatically:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>1. Detection.</strong> RDS observes that the primary is not responding, or that its host, storage or Availability Zone has failed.</li>\n<li><strong>2. Promotion.</strong> The standby is promoted to be the new primary. Because replication was synchronous, it already has every committed transaction.</li>\n<li><strong>3. DNS update.</strong> RDS repoints the endpoint hostname — the same name your application has always used — at the new primary's address. <em>This is exactly why RDS gives you a DNS name instead of an IP address.</em></li>\n<li><strong>4. Reconnection.</strong> Existing connections are broken. Your application must open new ones. Once it does, it resolves the endpoint again, gets the new address, and carries on.</li>\n<li><strong>5. Rebuild.</strong> In the background, RDS builds a fresh standby in the other AZ so you are protected again. The roles have simply swapped.</li>\n</ul>\n<p style=\"line-height: 1.75\">Two details beginners must internalise. First, <strong>failover is not instantaneous</strong>. For the classic Multi-AZ instance deployment it typically takes about one to two minutes. During that window writes fail. If your business cannot tolerate that, Multi-AZ alone is not your answer.</p>\n<p style=\"line-height: 1.75\">Second, <strong>your application must be able to reconnect</strong>. Code that opens one connection at startup and assumes it lives forever will keep throwing errors long after the database is healthy again. Real-world applications need: a connection pool that detects and discards dead connections, retry logic with backoff around transient errors, sensible connection and socket timeouts, and short DNS caching (some JVM configurations cache DNS forever by default, which will keep an application pointed at the dead instance — set the TTL to around 5 to 10 seconds).</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The single most-tested fact: the standby serves no traffic</h4>\n<p style=\"line-height: 1.75\">If you remember one sentence from this topic, make it this one: <strong>in a classic Multi-AZ deployment, the standby does not serve read traffic.</strong> It has no endpoint you can connect to. You cannot run reports against it. You cannot send it your SELECT queries to take load off the primary.</p>\n<p style=\"line-height: 1.75\">Multi-AZ buys <strong>availability</strong>, not <strong>scale</strong>. If your database is struggling under read load, the tool for that is a <strong>read replica</strong>, which is a separate feature covered in the next topic: replicas are asynchronous, they <em>do</em> have their own endpoints, and they <em>do</em> serve reads — but they are not automatically promoted when the primary fails. Instead of one hidden standby it runs <em>two</em> standby instances in two other Availability Zones, and — unlike the classic deployment — those standbys <strong>are readable</strong>. The cluster gives you a reader endpoint alongside the writer endpoint, and failover is typically faster (usually under 35 seconds) because it uses a different replication mechanism that commits once a majority of instances confirm the write.</p>\n<p style=\"line-height: 1.75\">For a beginner, the thing to know is simply that it exists and that it changes the \"standby cannot be read\" rule for that specific deployment option. There is also a small charge for data transfer between Availability Zones for replication. Nothing about the pricing is surprising once you accept that the standby is a real, running machine.</p>\n<p style=\"line-height: 1.75\">Beyond surviving failures, Multi-AZ improves routine operations:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Backups have less impact.</strong> On a Single-AZ instance the daily automated backup can cause a brief I/O pause. With Multi-AZ, backups are taken from the standby, so the primary keeps serving normally.</li>\n<li><strong>Patching is less disruptive.</strong> RDS can patch the standby first, fail over to it, then patch the old primary — turning a long maintenance outage into a short failover.</li>\n<li><strong>Scaling the instance size is less disruptive</strong> for the same reason: the change is applied to the standby and then a failover switches you over.</li>\n<li><strong>You can test it.</strong> Rebooting with the failover option forces a real failover on demand, which is the only honest way to learn how your application behaves.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What Multi-AZ does not protect you against</h4>\n<p style=\"line-height: 1.75\">Because replication is faithful, it copies mistakes faithfully too. If someone runs <code>DELETE FROM orders</code> without a WHERE clause, that delete is applied to the standby within milliseconds. Multi-AZ protects against <em>infrastructure</em> failure. It does not protect against human error, application bugs, data corruption caused by your own code, accidental instance deletion, or the loss of an entire Region.
