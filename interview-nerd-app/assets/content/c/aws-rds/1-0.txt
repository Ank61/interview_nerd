{"title":"Amazon Aurora Architecture — The Distributed Storage Layer","tags":["aurora","storage","quorum","architecture"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Aurora is not <strong>RDS with a faster instance class</strong>. It is a re-implementation of the bottom half of a relational database. The MySQL or PostgreSQL SQL engine still parses, plans, and executes your queries, but everything below the transaction log — the buffer-pool flush path, the durability protocol, the file system, the replication of bytes — has been replaced by a <strong>purpose-built, distributed, multi-tenant, self-healing storage service</strong> that spans three Availability Zones. Every performance claim, every operational nicety, and every cost surprise about Aurora traces back to that one substitution. If you can explain the storage layer, you can derive the rest of Aurora from first principles in an interview.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Separation of Compute and Storage</h4>\n<p style=\"line-height: 1.75\">In RDS for MySQL or PostgreSQL, the database instance owns an EBS volume. The engine writes pages into that volume, the volume is replicated inside a single AZ by EBS, and Multi-AZ durability is achieved by a second instance with a second EBS volume receiving a synchronous block-level or log-level stream. Compute and storage are welded together: the instance is the only thing that can read or write its data, and losing the instance means promoting a standby that has its own complete copy.</p>\n<p style=\"line-height: 1.75\">Aurora breaks that coupling. The cluster has a <strong>shared storage volume</strong> that is a service, not a disk. The volume is carved into <strong>10 GB logical segments called protection groups</strong>. Each protection group is replicated <strong>six ways across three Availability Zones — two copies per AZ</strong> — and those six copies live on six different storage nodes drawn from a large fleet. A 40 TB Aurora volume is therefore thousands of segments scattered across hundreds or thousands of storage nodes, which is why Aurora's rebuild and repair operations are fast: repairing a failed node means re-replicating many small 10 GB segments in parallel from many different sources, not copying one enormous volume from one place.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Quorum: Why Four of Six and Three of Six</h4>\n<p style=\"line-height: 1.75\">Aurora uses a <strong>quorum protocol</strong> over those six copies. A write is considered durable when <strong>four of the six</strong> storage nodes acknowledge it. A read (in the rare cases Aurora must read from storage rather than serve from the buffer cache or from a known-latest node) requires <strong>three of six</strong>. The arithmetic matters: with V = 6, Vw = 4, Vr = 3, we have Vw + Vr &gt; V (7 &gt; 6), which guarantees any read quorum intersects any write quorum, and 2 × Vw &gt; V (8 &gt; 6), which prevents two conflicting writes from both committing.</p>\n<p style=\"line-height: 1.75\">The practical payoff is the fault tolerance envelope, and this is the sentence interviewers want:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Losing an entire AZ (two copies) plus one additional node</strong> — three copies total — still leaves three copies, which is enough to satisfy the read quorum. Reads and durability survive; Aurora rebuilds the lost copies from the survivors.</li>\n<li><strong>Losing an entire AZ (two copies)</strong> still leaves four copies, which satisfies the write quorum. <strong>Write availability survives a full AZ failure</strong> with no data loss and no reprovisioning of storage.</li>\n<li>A conventional three-copy, two-of-three system cannot do both. It loses write availability the moment it loses two copies, and an AZ failure plus a single unlucky disk is exactly that scenario.</li>\n</ul>\n<p style=\"line-height: 1.75\">Aurora also exploits the quorum for <strong>latency</strong>: because the writer only waits for the fourth acknowledgement, the two slowest storage nodes never appear on the critical path. Storage nodes doing garbage collection, hitting a slow disk, or experiencing a network hiccup are simply outrun. font-size: 1.25rem; font-weight: 600\">The Log Is the Database</h4>\n<p style=\"line-height: 1.75\">The single most important design decision is that <strong>Aurora ships only redo log records over the network, never data pages</strong>. In stock MySQL with InnoDB, committing and checkpointing a workload generates a remarkable amount of redundant I/O: the redo log write, the double-write buffer write (protecting against torn pages), the binary log write if enabled, the dirty page flush to the tablespace, and then the replica repeats much of that on its own storage after receiving the binlog. In a Multi-AZ RDS deployment those writes cross the network to a synchronous standby too. The same logical transaction can be written to durable media half a dozen times.</p>\n<p style=\"line-height: 1.75\">Aurora's writer sends the redo stream to the storage nodes and nothing else. There is <strong>no double-write buffer</strong> (the storage layer never produces a torn page, because pages are materialized from log on nodes that write them atomically), <strong>no full-page writes across the network</strong>, and no need to push whole 8 KB or 16 KB pages to replicas. The storage nodes are the ones that apply redo to produce page versions, and they do it <strong>asynchronously and in the background, on demand</strong>: a page is materialized when someone asks for it or when coalescing the log is convenient. The engine's job ends when the log is durable.</p>\n<p style=\"line-height: 1.75\">Two consequences follow. First, <strong>write amplification collapses</strong>, and because the network is usually the scarce resource in a distributed database, reducing bytes-on-the-wire per transaction is the dominant throughput lever. This is the honest technical explanation for Aurora's throughput advantage — not \"AWS made MySQL faster.\" Second, <strong>checkpointing largely disappears as a foreground concern</strong>. Traditional engines suffer periodic latency cliffs when a checkpoint forces a burst of dirty page flushes; Aurora's storage nodes coalesce log into pages continuously, so the sawtooth is smoothed out.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Crash Recovery, Backups, and Growth</h4>\n<p style=\"line-height: 1.75\"><strong>Crash recovery</strong> in a traditional engine is a single-threaded-ish, instance-bound replay: the recovering process reads the redo log from the last checkpoint forward and applies it before opening for connections. On a busy database with a large redo log that can take minutes. Aurora does not do this. Redo application is a <strong>continuous, parallel, distributed background activity performed by the storage nodes themselves</strong>. When an Aurora writer crashes and restarts (or a replica is promoted), it does not have to replay anything to make the volume consistent — the volume is already able to serve any page as of any recent log position. Recovery collapses to re-establishing the engine's in-memory state and resolving in-flight transactions, which is why Aurora instances typically come back in seconds rather than minutes.</p>\n<p style=\"line-height: 1.75\"><strong>Backups</strong> are continuous and incremental to Amazon S3, performed <strong>by the storage layer</strong>. This is the reason AWS can say backups have no performance impact: no instance is reading the volume to produce a backup, no snapshot freeze happens, no I/O is stolen from your workload. Point-in-time restore works off the same continuously captured log, with a backup retention window configurable from 1 to 35 days.</p>\n<p style=\"line-height: 1.75\"><strong>Storage grows automatically in 10 GB increments</strong> as data is written — you never provision a volume size and you never run an ALTER-and-resize maintenance window. Current Aurora MySQL and Aurora PostgreSQL clusters grow to a documented maximum of <strong>128 TiB</strong> (older engine versions were capped at 64 TiB, so verify for the specific version in an interview answer). Aurora also <strong>shrinks</strong> reclaimed space back on modern versions, which was historically a real operational complaint. Storage is billed on what you actually use, not on a provisioned high-water mark, unlike RDS gp3/io1 volumes which you pay for whether they are full or empty.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What Aurora Does Not Change</h4>\n<p style=\"line-height: 1.75\">This is where strong candidates separate themselves. Aurora runs <strong>the same SQL engines</strong>: Aurora MySQL is wire- and dialect-compatible with MySQL, Aurora PostgreSQL with PostgreSQL. Therefore:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Query planning and execution are unchanged.</strong> A missing index is still a table scan. A query with a bad join order is still slow. Aurora makes the I/O cheaper; it does not make a cross join clever.</li>\n<li><strong>Single-writer semantics remain.</strong> Aurora is not multi-master by default. All writes go through one instance, so write scaling is still vertical (bigger writer) or architectural (sharding, offloading, batching).</li>\n<li><strong>Lock contention is unchanged.</strong> Hot-row contention, long transactions holding locks, and PostgreSQL vacuum/bloat dynamics all behave as they do upstream.</li>\n<li><strong>Memory pressure is unchanged.</strong> Buffer cache hit ratio still dominates read latency. Aurora just makes the cache miss cheaper and more predictable.</li>\n<li><strong>Schema changes are still schema changes</strong> (Aurora MySQL has some fast DDL optimizations for adding nullable columns at the end of a table, but that is an engine feature, not magic).</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Cost Model and I/O-Optimized</h4>\n<p style=\"line-height: 1.75\">Aurora bills instance-hours plus storage-GB-months plus, on the default <strong>Aurora Standard</strong> configuration, a <strong>per-million-request charge for storage I/O</strong>. An Aurora I/O here is a storage-layer read or a batched write of log records — it is not one-to-one with a SQL statement, and a buffer-cache hit costs nothing. For a read-mostly workload with a good cache hit ratio, I/O charges are modest.
