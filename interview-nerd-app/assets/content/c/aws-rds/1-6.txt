{"title":"Performance Insights and Query Tuning on RDS","tags":["Performance Insights","Wait Events","EXPLAIN","Query Tuning"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">CloudWatch tells you <em>that</em> a database is unhappy; <strong>Amazon RDS Performance Insights</strong> tells you <em>why</em>, and which query is responsible. It does this by sampling active sessions once per second and attributing each one to a <strong>wait event</strong> — the specific thing the session is doing or waiting on. That turns \"CPU is 90%\" into \"62% of database time is <code>IO:DataFileRead</code> caused by one unindexed query from one host\". Pairing Performance Insights with engine-level tooling (<code>pg_stat_statements</code>, the MySQL slow query log, <code>EXPLAIN ANALYZE</code>) is the standard senior-engineer diagnostic loop on RDS.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">DB Load and Average Active Sessions</h4>\n<p style=\"line-height: 1.75\">The central metric is <strong>DB load</strong>, measured in <strong>average active sessions (AAS)</strong>. An \"active session\" is a connection currently executing a request — running on CPU or waiting on something. Performance Insights samples every second and averages over the display interval, so AAS = average number of sessions doing work at any instant. It is a <em>rate of concurrency</em>, not a count of connections: 500 idle connections contribute zero.</p>\n<p style=\"line-height: 1.75\">The interpretive rule that makes the metric actionable: <strong>compare AAS against the instance's vCPU count.</strong> Performance Insights draws this as a horizontal \"Max vCPU\" line on the DB load chart.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>AAS well below vCPU.</strong> The database has spare capacity. If the application is slow, the bottleneck is elsewhere — network, application code, connection acquisition, or single-query latency rather than concurrency.</li>\n<li><strong>AAS ≈ vCPU.</strong> Fully utilised. Fine as a steady state only if you have no headroom requirement; any spike now queues.</li>\n<li><strong>AAS &gt; vCPU.</strong> Saturated. Sessions are queuing. Crucially, the <em>composition</em> tells you what to fix: if the excess is <code>CPU</code>, you are compute-bound and need query efficiency or more vCPUs; if the excess is I/O waits, more vCPUs will not help and you need memory, faster storage or fewer reads; if the excess is <strong>lock waits</strong>, adding hardware makes it <em>worse</em> by admitting more contenders.</li>\n</ul>\n<p style=\"line-height: 1.75\">A useful mental conversion: AAS is the database-side equivalent of Little's Law. If AAS is 12 on an 8-vCPU instance and 4 of that is CPU wait, then roughly 8 sessions' worth of work is queued behind CPU at any moment — which is exactly the multiplier you will see in p99 latency.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Wait Events: The Diagnostic Vocabulary</h4>\n<p style=\"line-height: 1.75\">Every sampled session is tagged with what it is waiting on. Reading the top-waits stack is the fastest path from symptom to cause. If <code>performance_schema</code> is off, or if RDS cannot manage the instrumentation automatically, you lose per-wait-event detail and get a much coarser view. On PostgreSQL no extra setup is needed for wait events themselves, but per-SQL statistics are far richer with <code>pg_stat_statements</code> loaded.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Slicing the Load</h4>\n<p style=\"line-height: 1.75\">The DB load chart can be sliced by several dimensions, and switching between them is how you turn a wait into an owner:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Top SQL.</strong> Normalised statement digests with their share of DB load, calls, average latency and rows. This is the primary view — it directly names the query to fix. Performance Insights shows both the digest and sample full text.</li>\n<li><strong>Top waits.</strong> What the database is bottlenecked on overall. Start here to choose a class of fix.</li>\n<li><strong>Top hosts.</strong> Client IPs. Invaluable for finding a rogue batch job, an analytics tool, or one misbehaving service in a shared database.</li>\n<li><strong>Top users / top databases / top applications.</strong> Attribution by login role or <code>application_name</code>. If your services set a distinct <code>application_name</code>, this becomes free per-service accounting — a cheap practice worth adopting proactively.</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>Retention and cost.</strong> Performance Insights has a <strong>free tier with 7 days</strong> of rolling performance-history retention. Longer retention — up to <strong>24 months</strong> — is a paid option priced per vCPU per month, and is worth it when you need to compare this quarter's regression against last quarter's baseline, or to do capacity planning across seasonal peaks. Seven days is enough for incident response but not for trend analysis. Performance Insights data is also queryable programmatically via the <code>pi</code> API (<code>aws pi get-resource-metrics</code>), which is how you build custom dashboards or automate regression detection in CI.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Reading EXPLAIN Properly</h4>\n<p style=\"line-height: 1.75\">Once Performance Insights names the query, you need plan analysis. The distinction that matters: <code>EXPLAIN</code> shows the planner's <em>estimate</em>; <code>EXPLAIN ANALYZE</code> actually <em>runs</em> the query and shows real timings and row counts. In PostgreSQL always use <code>EXPLAIN (ANALYZE, BUFFERS)</code> — <code>BUFFERS</code> reports shared hits versus reads, which distinguishes \"slow because it read 2 GB from disk\" from \"slow because it burned CPU on a sort\". In MySQL 8.0.18+, <code>EXPLAIN ANALYZE</code> gives the same actual-vs-estimated treatment; before that you have <code>EXPLAIN FORMAT=JSON</code> with estimates only. Remember <code>EXPLAIN ANALYZE</code> executes DML for real — wrap it in a transaction you roll back.</p>\n<p style=\"line-height: 1.75\">What to look for, in priority order:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Estimated vs actual row divergence.</strong> If the planner expected 12 rows and got 1.2 million, every join method above that node is wrong. This is the single highest-signal thing in a plan, and it almost always means <strong>stale or insufficient statistics</strong>, a correlated predicate the planner cannot model, or a function the planner has no selectivity estimate for.</li>\n<li><strong>Sequential scan on a large table.</strong> Not always bad — a scan of a 10,000-row lookup table is correct, and a query returning 40% of a table is <em>better</em> served by a scan than by random index lookups. It is bad when a highly selective predicate exists and is not being used.</li>\n<li><strong>Unusable indexes.</strong> The index exists but the plan ignores it: a function or cast on the indexed column (<code>WHERE lower(email) = ...</code> without a matching expression index, or comparing a <code>varchar</code> column to an integer), a leading-wildcard <code>LIKE</code>, an <code>OR</code> across columns, or a composite index whose leading column is not in the predicate. Column collation or type mismatch across a join is a classic silent killer.</li>\n<li><strong>Selectivity.</strong> An index is only useful if it narrows the set substantially. An index on a boolean <code>is_active</code> where 98% of rows are true is close to worthless for finding active rows, though excellent for finding the 2% inactive ones — which is what a <strong>partial index</strong> (<code>WHERE is_active = false</code> in PostgreSQL) exists for.</li>\n<li><strong>Spills.</strong> PostgreSQL <code>Sort Method: external merge Disk: 84320kB</code> means <code>work_mem</code> was too small and the sort spilled; MySQL's equivalent is <code>Using temporary; Using filesort</code> with on-disk temp tables.</li>\n<li><strong>Nested loops over large outer sets.</strong> Fine for tens of rows, catastrophic for millions — usually a downstream symptom of the row-estimate error above.</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>The cost of over-indexing.</strong> Indexes are not free insurance. Every index must be maintained on every <code>INSERT</code>, <code>UPDATE</code> that touches its columns, and <code>DELETE</code>. Ten indexes on a hot table can mean an order of magnitude more write I/O than the table itself; in PostgreSQL they also defeat HOT updates (a non-HOT update must insert a new tuple into every index), which increases bloat and vacuum work. Indexes consume buffer cache that data pages would otherwise use. The discipline is to <em>remove</em> unused indexes as deliberately as you add them — <code>pg_stat_user_indexes.idx_scan = 0</code> and MySQL's <code>sys.schema_unused_indexes</code> identify candidates.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Plan Instability and Stale Statistics</h4>\n<p style=\"line-height: 1.75\">A query that was fast for six months and is suddenly slow, with no code change, is usually a <strong>plan flip</strong>. Causes:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Stale statistics.</strong> The planner's row estimates come from sampled statistics. After a bulk load, a large delete, or rapid growth, those estimates are wrong. In PostgreSQL, statistics are refreshed by <code>ANALYZE</code> (autovacuum runs it, but its thresholds may be too lax for a fast-growing table); <code>default_statistics_target</code> raises the sample size for skewed columns, and <code>CREATE STATISTICS</code> handles correlated columns the planner otherwise assumes independent. In MySQL/InnoDB, statistics are sampled by <code>innodb_stats_persistent_sample_pages</code> and refreshed with <code>ANALYZE TABLE</code>.</li>\n<li><strong>Generic vs custom plans (PostgreSQL).</strong> With server-side prepared statements, PostgreSQL builds custom plans for the first five executions, then compares and may switch to a parameter-independent <strong>generic plan</strong>. For skewed data — a tenant_id where one tenant holds 90% of rows — the generic plan can be far worse for the common case. <code>plan_cache_mode = force_custom_plan</code> is the escape hatch.</li>\n<li><strong>Data distribution drift.</strong> A status column that was 50/50 becomes 99/1 as a backlog clears, and the plan that was right is now wrong.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Engine Tooling and How to Enable It on RDS</h4>\n<p style=\"line-height: 1.75\"><strong>PostgreSQL.</strong> <code>pg_stat_statements</code> aggregates normalised statements with total and mean execution time, calls, rows, and shared-buffer hit/read counts — this is your cumulative, always-on query profile. It requires the library in <code>shared_preload_libraries</code> (a <strong>static</strong> parameter, so a reboot) and <code>CREATE EXTENSION pg_stat_statements;</code> in each database; on recent RDS PostgreSQL versions it is already in the default <code>shared_preload_libraries</code>. <code>auto_explain</code> logs the plan of any statement exceeding <code>auto_explain.log_min_duration</code> — priceless because it captures the plan that was actually used <em>at the moment of slowness</em>, which you often cannot reproduce later. Enable it the same way (static, reboot), and keep <code>auto_explain.log_analyze</code> off or narrowly scoped in production because it instruments every statement and adds real overhead. Also enable <code>log_min_duration_statement</code> and export <code>postgresql</code> logs to CloudWatch Logs.</p>\n<p style=\"line-height: 1.75\"><strong>MySQL.</strong> The <strong>slow query log</strong> is enabled with <code>slow_query_log = 1</code>, a threshold in <code>long_query_time</code> (start at 1 second, lower carefully), and <code>log_output = FILE</code> so the log can be exported to CloudWatch Logs — RDS also supports <code>TABLE</code>, which writes into <code>mysql.slow_log</code> and is convenient to query but adds write load to the instance itself. Add <code>log_queries_not_using_indexes</code> only briefly; on a busy system it floods. The <strong>Performance Schema</strong> plus the <code>sys</code> schema is the richer tool: <code>sys.statement_analysis</code>, <code>sys.schema_tables_with_full_table_scans</code>, and <code>sys.schema_unused_indexes</code> answer most tuning questions directly, and <code>performance_schema = 1</code> is what Performance Insights' per-wait-event detail relies on. All of these are set through <strong>parameter groups</strong>; <code>performance_schema</code> and <code>shared_preload_libraries</code> are static and require a reboot, while <code>long_query_time</code> and <code>slow_query_log</code> are dynamic.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario: p99 Doubled After a Deploy</h4>\n<p style=\"line-height: 1.75\"><em>\"p99 API latency went from 180 ms to 400 ms right after a deploy. No infrastructure changed. CPU is up moderately. Diagnose it.\"</em></p>\n<p style=\"line-height: 1.75\"><strong>1. Confirm the database is implicated.</strong> Open Performance Insights and set the window to straddle the deploy. If <strong>DB load</strong> steps up at the deploy timestamp, the database is involved; if AAS is flat, the regression is in application code and you should stop here. Note whether AAS crossed the Max vCPU line — that distinguishes \"the database is doing more work\" from \"the database is now saturated and queueing\", which have very different urgency.</p>\n<p style=\"line-height: 1.75\"><strong>2. Read the top waits.</strong> Compare the wait composition before and after. A jump in <code>IO:DataFileRead</code> (PostgreSQL) or InnoDB data-file reads means new queries are reading pages that are not cached — typically a new access path doing sequential scans. A jump in <code>CPU</code> with stable I/O suggests in-memory sorting or a much larger row count being processed. A jump in <code>Lock:transactionid</code> means the deploy introduced contention — a new update pattern on a hot row, or longer transactions.</p>\n<p style=\"line-height: 1.75\"><strong>3. Slice by top SQL.</strong> Sort by DB load contribution and diff against the pre-deploy window. Look for a query digest that is entirely new (a new feature or an ORM change), or an existing digest whose <em>calls per second</em> jumped by an order of magnitude — the signature of an <strong>N+1</strong>: the per-call latency is unchanged and tiny, but volume exploded. The two look completely different in Performance Insights, and distinguishing them determines the fix.</p>\n<p style=\"line-height: 1.75\"><strong>4. Cross-check cumulative stats.</strong> In PostgreSQL, <code>pg_stat_statements</code> ordered by <code>total_exec_time</code> confirms the ranking and gives <code>shared_blks_read</code> so you can see whether the query is I/O-heavy. If you snapshot and reset <code>pg_stat_statements</code> regularly you can diff two windows precisely. In MySQL, <code>sys.statement_analysis</code> or the slow log gives the equivalent.</p>\n<p style=\"line-height: 1.75\"><strong>5. Explain the suspect.</strong> Run <code>EXPLAIN (ANALYZE, BUFFERS)</code> with representative parameter values. Suppose it shows a sequential scan over a 40-million-row <code>orders</code> table with a filter on <code>tenant_id</code> and <code>created_at</code>, actual rows 1.1M against an estimate of 900, and <code>Rows Removed by Filter</code> in the tens of millions. Two findings: an index is missing or unusable, and the estimate is badly wrong.</p>\n<p style=\"line-height: 1.75\"><strong>6. Identify the precise cause.</strong> Inspect the predicate. If the deploy changed <code>WHERE created_at &gt;= $1</code> to <code>WHERE date_trunc('day', created_at) = $1</code>, the existing B-tree on <code>created_at</code> became unusable — the function on the column defeats it. That is a one-line application fix (rewrite as a half-open range) and is strictly better than adding an expression index, because it restores the existing index and adds no write cost.</p>\n<p style=\"line-height: 1.75\"><strong>7. Fix and verify.</strong> Ship the predicate rewrite; if a genuinely new access path is needed, create the composite index on <code>(tenant_id, created_at)</code> using <code>CREATE INDEX CONCURRENTLY</code> in PostgreSQL (non-blocking, but cannot run inside a transaction and can leave an invalid index if it fails) or an online <code>ALGORITHM=INPLACE, LOCK=NONE</code> add in MySQL 8. Run <code>ANALYZE</code> on the table to refresh statistics. Then verify in Performance Insights that DB load returns to the pre-deploy baseline and that the digest has dropped out of top SQL — verification in the same tool that found it closes the loop.</p>\n<p style=\"line-height: 1.75\"><strong>8. Prevent recurrence.</strong> Add an alarm on DB load exceeding vCPU count, capture <code>pg_stat_statements</code> snapshots in CI against a production-shaped dataset, and require <code>EXPLAIN</code> output in code review for any new query touching a large table.</p>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"Performance Insights measures DB load in average active sessions, and the key rule is to compare AAS against the instance's vCPU count — above that line the database is saturated and sessions are queueing.
