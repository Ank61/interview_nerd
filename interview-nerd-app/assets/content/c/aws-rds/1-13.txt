{"title":"Engine Version Upgrades — Minor, Major, and Deprecation Management","tags":["rds","upgrades","major version","extended support"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Engine upgrades are the operational task that senior engineers get asked about most and that teams defer the longest. The dynamic is predictable: upgrades carry real risk, so they get postponed; postponement accumulates versions, which increases the risk of the eventual jump; eventually AWS ends standard support, billing rises sharply, and the team is forced into the riskiest possible upgrade under time pressure. Managing this well is less about knowing a CLI flag and more about having a <strong>continuous, low-drama upgrade cadence</strong> backed by testing infrastructure.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Minor versus major: what actually differs</h4>\n<p style=\"line-height: 1.75\">A <strong>minor version upgrade</strong> (PostgreSQL 15.4 to 15.6, MySQL 8.0.35 to 8.0.39) is, by the upstream projects' own compatibility promises, backward compatible: no on-disk format change requiring a rewrite, no SQL semantics changes, mostly bug and security fixes. RDS applies it by patching binaries and restarting, which means <strong>downtime roughly equal to a reboot</strong> — seconds to a couple of minutes for a single-AZ instance. With <strong>Multi-AZ</strong>, RDS upgrades the standby first, fails over, then upgrades the former primary, so the visible impact is a single failover of 60-120 seconds rather than a full outage. Aurora minor upgrades use a similar rolling approach and benefit from <strong>zero-downtime patching (ZDP)</strong> on supported versions, which can preserve client connections entirely when conditions are right (no long-running transactions, no open temporary tables, no pending parameter changes, no in-flight DDL); if conditions are not met, Aurora falls back to a normal restart.</p>\n<p style=\"line-height: 1.75\"><strong>Auto minor version upgrade</strong> is an instance setting. When enabled, RDS applies designated minor versions during your <strong>maintenance window</strong>. Key nuances: it only applies to versions AWS marks as the <em>auto upgrade</em> target, not every minor release; it will not jump you across a major version; if you are on a custom parameter group it still applies (parameter groups are version-family scoped, so a minor upgrade inside the family is fine); and if the current version is deprecated, AWS may upgrade you regardless of the setting after due notice. Teams disable it after one bad experience — a restart during an unexpected moment, or a regression — and then <strong>fall behind by years</strong>, which converts many cheap minor upgrades into one terrifying major upgrade. The mature position is to <em>enable</em> auto minor upgrades in non-production continuously, and in production enable them with a carefully chosen maintenance window plus alerting on the pending-maintenance API, so you know what is coming.</p>\n<p style=\"line-height: 1.75\">A <strong>major version upgrade</strong> (PostgreSQL 14 to 16, MySQL 5.7 to 8.0, Aurora MySQL 2 to 3) is a different animal. It can change the on-disk catalog format, alter SQL behavior, remove deprecated features, change default settings, and change the query planner in ways that alter plans for your existing queries. It is <strong>never applied automatically by auto minor version upgrade</strong>; you must request it explicitly with <code>--engine-version</code> and <code>--allow-major-version-upgrade</code> — with the important exception that AWS will force major upgrades after the end of Extended Support, which is why deprecation deadlines are a planning issue rather than a nuisance.</p>\n<div style=\"overflow-x: auto; font-size: 1.25rem; font-weight: 600\">What actually breaks in a major upgrade</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Missing statistics (PostgreSQL).</strong> <code>pg_upgrade</code> does not transfer <code>pg_statistic</code>. The instance comes up with an empty statistics catalog, the planner assumes default selectivity, and <em>every</em> query gets a bad plan — sequential scans where index scans belong. Teams that skip <code>ANALYZE</code> experience what looks like a catastrophic performance regression ten minutes after cutover and often roll back unnecessarily. Run <code>ANALYZE</code> (or <code>vacuumdb --analyze-in-stages --jobs N</code>) as the <strong>first post-upgrade step, inside the maintenance window</strong>, before traffic returns.</li>\n<li><strong>Extension compatibility (PostgreSQL).</strong> Extensions are versioned independently. <code>pg_upgrade</code> refuses to proceed if an extension's shared library is unavailable in the target version. You must inventory extensions in advance, confirm the target version supports each, and run <code>ALTER EXTENSION ... UPDATE</code> after the upgrade. <code>PostGIS</code> is the classic pain point because it has its own upgrade sequence, and abandoned extensions may have no path at all, forcing a rewrite. RDS also removes or renames some extensions between versions.</li>\n<li><strong>Behavior and SQL changes.</strong> MySQL 5.7 to 8.0 changed the default character set to <code>utf8mb4</code> and the default collation, made many previously-reserved words reserved (<code>rank</code>, <code>groups</code>, <code>system</code>), removed the query cache entirely, and altered <code>GROUP BY</code> implicit sorting. PostgreSQL 10 to 11+ changed hash function behavior affecting hash partitioning; PostgreSQL 12 removed <code>recovery.conf</code> semantics; more recent versions have tightened implicit casts and changed <code>jsonb</code> subscripting. Any of these can break an application silently rather than loudly.</li>\n<li><strong>Query plan regressions.</strong> A new planner version can choose a different plan for a query that was fine for three years. This is the most common real-world upgrade incident, and it is why validating <code>EXPLAIN</code> output for your top queries on a clone of production data is the single highest-value pre-upgrade activity.</li>\n<li><strong>Replication topology.</strong> Logical replication slots, external replicas, and DMS tasks that consume the binlog or WAL typically do not survive; plan to rebuild them. Aurora MySQL 2 to 3 (MySQL 5.7 to 8.0 lineage) additionally requires checking for incompatible objects with tools like <code>mysqlcheck --check-upgrade</code> or the MySQL Shell upgrade checker.</li>\n<li><strong>Duration scales with catalog complexity, not data size.</strong> A 50 GB database with 400,000 tables and partitions upgrades far more slowly than a 5 TB database with 30 tables, because <code>pg_upgrade</code> works through the catalog. Simple, no extra infrastructure, and appropriate for non-production and for small, tolerant databases. Its defining weakness is rollback: <strong>there is no downgrade</strong>. If the upgraded database misbehaves, your only option is restoring the pre-upgrade snapshot, which discards every write since. On a busy system, that means the rollback decision must be made almost immediately or not at all — an uncomfortable position during an incident.</p>\n<p style=\"line-height: 1.75\"><strong>Blue/Green</strong> is now the default recommendation where supported. RDS builds a green environment at the target version replicating from blue, you validate for as long as you like, and you switch over in under a minute with guardrails (blue goes read-only, RDS waits for zero replication lag, aborts cleanly on timeout or unhealthy topology). Before switchover, abandoning costs nothing. After switchover, the old blue environment is retained under a renamed identifier, so a rollback is a second, deliberate cutover rather than a restore — though writes that landed on green after switchover would need reconciling. Costs are double for the duration and you must handle the resource-ID rename fallout (RDS Proxy targets, IaC state, alarms, cross-Region replicas).</p>\n<p style=\"line-height: 1.75\"><strong>Replica-promotion / logical replication</strong> is the lowest-downtime and highest-effort path, and it is the answer when blue/green does not support your engine (Oracle, SQL Server) or when you need a true bidirectional rollback. For PostgreSQL you build a new instance at the target version, establish <strong>logical replication</strong> from the old primary (publication on old, subscription on new), let it catch up, then cut over by stopping writes briefly, confirming zero lag, advancing sequences (logical replication does <em>not</em> replicate sequence values), and repointing the application. For MySQL the analogue is binlog replication to a new instance at the higher version. The effort is in the details logical replication does not cover — sequences, DDL, large objects, tables without primary keys — and it is exactly the same machinery DMS uses, which is why the two topics rhyme.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">RDS Extended Support: the budget deadline</h4>\n<p style=\"line-height: 1.75\">AWS publishes, per engine major version, a <strong>end of standard support</strong> date. After that date, if you have not upgraded, your instance is automatically enrolled in <strong>RDS Extended Support</strong> (unless you explicitly opt out, in which case AWS upgrades you). Extended Support keeps delivering critical security patches for up to three additional years — and bills an <strong>hourly per-vCPU surcharge on top of your instance cost</strong>, priced in two tiers that step up after the first two years. The surcharge is significant enough that for a large fleet it routinely exceeds the engineering cost of upgrading, and finance teams notice it as a sudden unexplained increase.</p>\n<p style=\"line-height: 1.75\">The practical consequences to state in an interview: the deadline is <strong>not negotiable</strong> and eventually results in a <strong>forced upgrade</strong> at AWS's timing rather than yours; the charge applies to Aurora clusters and RDS instances alike, including replicas, so a fleet on an old version multiplies quickly; and opting <em>out</em> of Extended Support is not a cost saving but a commitment to being upgraded automatically. The correct operational posture is a tracked inventory of every database's engine version against its end-of-standard-support date, a rolling program that keeps every production database within one major version of current, and budget visibility so that \"we will upgrade next quarter\" carries a visible price tag.
