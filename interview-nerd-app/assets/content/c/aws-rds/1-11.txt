They give you point-in-time recovery inside one Region, in one account, for at most 35 days, configured per instance by whoever created that instance. Everything that makes a backup program <em>trustworthy</em> at scale — central policy, guaranteed coverage of new databases, immutability against a malicious actor, long retention for compliance, and proof that restores actually work — has to be built on top. This topic is about that layer: <strong>AWS Backup</strong> as the policy engine, <strong>cross-account copies with vault lock</strong> as the blast-radius boundary, and the snapshot and Aurora-specific mechanics you need to estimate RTO honestly.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Where automated backups run out</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Retention caps at 35 days.</strong> Financial, healthcare, and many SOC 2 regimes want 1-7 years. PITR cannot express that.</li>\n<li><strong>Same Region, same account.</strong> A Region event or a compromised account takes them with it.</li>\n<li><strong>Deleting the instance deletes the automated backups</strong> unless you explicitly retain them. One <code>terraform destroy</code> against the wrong workspace can erase both the database and its recovery path.</li>\n<li><strong>Coverage is opt-in per resource.</strong> A new database created by a team that forgot to set <code>--backup-retention-period</code> has <em>zero</em> backups, and nothing tells you.</li>\n<li><strong>No central reporting.</strong> Answering \"are all 400 production databases backed up and did last night's jobs succeed?\" requires enumerating instances yourself.</li>\n<li><strong>No immutability.</strong> An administrator can set retention to 0 and delete every snapshot in minutes.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">AWS Backup: plans, rules, vaults, and selections</h4>\n<p style=\"line-height: 1.75\">AWS Backup is a policy-and-orchestration service that sits above the per-service snapshot APIs. The model has four pieces:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Backup plan.</strong> A named container of rules. You attach it to resources via selections.</li>\n<li><strong>Backup rule.</strong> A schedule (cron), a <strong>backup window</strong> and <code>CompletionWindowMinutes</code>, a target vault, a <strong>lifecycle</strong> (days to cold storage, days to delete), and optional <strong>copy actions</strong> to other vaults in other Regions and other accounts. One plan commonly carries several rules: hourly for 7 days, daily for 35, monthly for 7 years.</li>\n<li><strong>Backup vault.</strong> A logical container for recovery points with its own <strong>KMS key</strong> and its own <strong>resource policy</strong>. The vault is the security boundary, and vaults are where <strong>vault lock</strong> applies.</li>\n<li><strong>Resource selection.</strong> Either explicit ARNs or, far better, <strong>tag-based selection</strong> — for example every resource with <code>Backup=tier1</code>. Combined with an SCP or AWS Config rule that requires the tag at creation, this makes coverage automatic rather than remembered.</li>\n</ul>\n<p style=\"line-height: 1.75\">AWS Backup for RDS creates real RDS snapshots on your behalf. It can also enable <strong>continuous backup</strong> for supported RDS and Aurora engines, which gives PITR within AWS Backup's own model (up to 35 days) alongside the periodic snapshots. The important mental model is that AWS Backup does not invent a new storage format for RDS — it drives snapshots and copies, so restore semantics are the familiar ones.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Vault Lock: the control that actually defeats ransomware</h4>\n<p style=\"line-height: 1.75\"><strong>AWS Backup Vault Lock</strong> applies a WORM (write-once-read-many) policy to a vault. It has two modes. <strong>Governance mode</strong> can be removed by a principal holding specific <code>backup:DeleteBackupVaultLockConfiguration</code> permission — it is a guardrail against accident, not against a determined attacker. <strong>Compliance mode</strong> becomes immutable after a cooling-off period (a grace window you choose, minimum 3 days) and then <em>cannot be disabled or shortened by anyone, including the account root or AWS Support</em>, until the configured retention expires. Recovery points in a compliance-locked vault cannot be deleted early, and their retention cannot be reduced.</p>\n<p style=\"line-height: 1.75\">This is precisely the control that defeats the realistic ransomware and malicious-insider scenario. The modern attack against a cloud-hosted database is not encrypting your files — it is obtaining credentials, <strong>deleting your recovery options first</strong>, and then destroying or encrypting production. Every defense that lives in the same identity boundary as production falls to the same stolen credentials. Compliance-mode vault lock breaks that chain in two ways: the recovery points are in a <strong>different account</strong> the production credentials cannot reach, and even that account's own administrator cannot delete them early.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">PRODUCTION ACCOUNT (<i class=n>111122223333</i>)        BACKUP ACCOUNT (<i class=n>444455556666</i>)\n<i class=o>+</i><i class=c>---------------------------+            +-------------------------------+</i>\n<i class=o>|</i>  Aurora <i class=o>/</i> RDS clusters    <i class=o>|</i>            <i class=o>|</i>  Vault: prod<i class=o>-</i>immutable        <i class=o>|</i>\n<i class=o>|</i>  automated backups (<i class=n>35</i>d)  <i class=o>|</i>            <i class=o>|</i>  KMS CMK: backup<i class=o>-</i>cmk          <i class=o>|</i>\n<i class=o>|</i>  manual snapshots         <i class=o>|</i>  <i class=k>copy</i> <i class=c>--&gt; The backup account does not need credentials in production. Second, <strong>KMS</strong>: an encrypted RDS snapshot encrypted with the default <code>aws/rds</code> service key <em>cannot be shared or copied to another account</em>. You must use a <strong>customer managed key</strong> and grant the destination account key usage, or the copy job fails with an access-denied that reads confusingly.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Snapshot mechanics that matter for RTO</h4>\n<p style=\"line-height: 1.75\"><strong>Snapshots are incremental.</strong> The first snapshot of a volume copies all in-use blocks; subsequent snapshots store only changed blocks and reference the rest. This is why a daily snapshot of a 10 TB database with 2% daily churn costs far less than 10 TB per day, and why deleting an \"old\" snapshot often frees much less space than its nominal size — the blocks are still referenced by newer snapshots. It also means snapshot <em>creation</em> time is proportional to change, not to total size, while <strong>restore</strong> time is proportional to total size.</p>\n<p style=\"line-height: 1.75\"><strong>Lazy loading is the RTO trap.</strong> When you restore an RDS snapshot (or do a PITR), AWS provisions a new EBS volume backed by the snapshot in S3. The instance becomes <em>available</em> quickly, but blocks are <strong>hydrated from S3 on first access</strong>. Your first full table scan, your first index range that touches cold pages, your nightly report — all pay a one-time, first-touch latency penalty that can be an order of magnitude worse than steady state. Candidates who quote RTO from \"time until status=available\" are off by hours on a multi-TB database. Mitigations: run a deliberate pre-warm (a full scan of hot tables, or <code>pg_prewarm</code> on PostgreSQL) as a runbook step, size IOPS generously during hydration, or use Aurora, whose shared storage layer does not have the same per-block lazy-load penalty for cluster restores.</p>\n<p style=\"line-height: 1.75\"><strong>Cross-Region copy</strong> of an encrypted snapshot re-encrypts with a key in the destination Region — you must pre-create that key. Copies are also incremental <em>within</em> a Region for the same source but the first cross-Region copy is a full transfer, which for multi-TB databases takes real time and should be measured, not assumed.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Aurora Backtrack — rewinding in place</h4>\n<p style=\"line-height: 1.75\"><strong>Backtrack</strong> is an Aurora feature that rewinds the cluster to a prior point in time <em>without restoring</em>. It is an undo button with a short window, and it has a real cost: you pay per million change records retained, which scales with write volume, so a very write-heavy cluster with a 72-hour window can be expensive. It shines for two use cases — recovering from a bad migration within minutes, and <strong>iterating in a test cluster</strong> where you rewind to a fixed state between test runs.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Aurora clone — copy-on-write test environments</h4>\n<p style=\"line-height: 1.75\"><strong>Database cloning</strong> creates a new Aurora cluster that shares the source's storage using <strong>copy-on-write</strong>. The clone is available in minutes regardless of size and initially consumes almost no additional storage; pages diverge and are copied only as either side writes them. This is transformative for pre-production work: a 20 TB production cluster can be cloned for a migration rehearsal or a query-plan investigation at a fraction of the cost and time of a restore. Clones are also the right way to <strong>test a restore or an upgrade against production-like data</strong> without touching production. Caveats: clones live in the same Region and account as the source (cross-account cloning is possible via AWS RAM for Aurora), a clone's storage bill grows as it diverges, and a long-lived clone of a hot cluster eventually costs as much as a copy.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Retention, cost, and proving backups worked</h4>\n<p style=\"line-height: 1.75\">Design retention from requirements, not habit. A common tiered policy: <strong>continuous PITR for 14-35 days</strong> (operational recovery), <strong>daily snapshots for 35-90 days</strong> (slow-to-detect corruption), <strong>monthly snapshots for 12 months and yearly for 7 years</strong> in a locked vault (compliance). Push long-retention copies to <strong>cold storage</strong> via lifecycle — but note cold storage has a <strong>90-day minimum retention charge</strong> and restoring from cold takes hours, so never put your operational tier there.</p>\n<p style=\"line-height: 1.75\">Cost drivers: backup storage beyond the free allocation (for RDS, backup storage equal to the provisioned storage is generally included; Aurora includes storage equal to the cluster volume), cross-Region copy data transfer, KMS request charges at scale, and backtrack change records. The biggest real-world waste is <strong>orphaned manual snapshots</strong> from long-deleted instances — they persist forever and nobody owns them. Audit with <code>describe-db-snapshots --snapshot-type manual</code> and enforce tagging.</p>\n<p style=\"line-height: 1.75\">Monitoring is the part that turns a backup <em>configuration</em> into a backup <em>program</em>: <strong>AWS Backup Audit Manager</strong> frameworks assert controls such as \"every resource with tag Backup=tier1 has a recovery point in the last 24 hours\" and \"recovery points are encrypted and copied cross-Region\", producing compliance reports. Add EventBridge rules on AWS Backup job state changes to alert on <code>FAILED</code> or <code>EXPIRED</code>, a CloudWatch alarm on backup job failure count, and — most importantly — an <strong>automated monthly restore test</strong> that restores the latest recovery point in the backup account, runs row counts and checksums against an expected baseline, and pages if it fails. A backup that has never been restored is not a backup; it is a bill.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario: backup protection that survives a compromised account</h4>\n<p style=\"line-height: 1.75\"><em>Requirement:</em> 60 RDS and Aurora databases across four production accounts. Recovery must be possible even if every production account is unrecoverable.</p>\n<p style=\"line-height: 1.75\"><strong>Organization layout.</strong> Create a dedicated <strong>backup account</strong> in its own OU with no role that production can assume, no shared CI/CD pipeline, and its own break-glass credentials held under MFA by a different team. Attach an SCP to that OU denying <code>backup:DeleteBackupVault</code>, <code>backup:DeleteRecoveryPoint</code>, <code>backup:PutBackupVaultAccessPolicy</code>, and <code>kms:ScheduleKeyDeletion</code> for all principals except the break-glass role. Re-key existing databases off the default <code>aws/rds</code> key — this is a real migration (snapshot, copy with the new key, restore) and must be planned, because without a CMK the cross-account copy simply cannot work.</p>\n<p style=\"line-height: 1.75\"><strong>Plan.</strong> One organization-level backup policy applied to all four production accounts, with tag selection on <code>Backup</code> in {tier1, tier2, regulated}. Rules: continuous backup for PITR retained 35 days in the local vault; a daily snapshot at 03:00 UTC retained 35 days locally with a <strong>copy action</strong> into the backup account's vault in the same Region retained 90 days; a monthly rule on the 1st retained 2555 days copied into the backup account's vault in a <strong>second Region</strong>, transitioning to cold storage after 90 days. Add an AWS Config rule plus SCP requiring the <code>Backup</code> tag on <code>rds:CreateDBInstance</code>, so a new database cannot be created outside the program.</p>\n<p style=\"line-height: 1.75\"><strong>Immutability.</strong> Apply <strong>vault lock in compliance mode</strong> to the backup account's vaults: minimum retention 90 days for the operational vault, 2555 days for the compliance vault, with a 7-day changeable window during rollout so a misconfiguration can be corrected before it becomes permanent. After the window closes, nothing — not the root user, not AWS Support — can delete those recovery points early. This is the specific control that answers the threat model.</p>\n<p style=\"line-height: 1.75\"><strong>Proof.</strong> AWS Backup Audit Manager framework asserting daily coverage, encryption, and cross-Region copy for all tagged resources, with reports delivered to S3 in the audit account.
