Things here can potentially be reached from the internet.</li>\n<li><strong>Private subnet.</strong> No route to an internet gateway. This is where your database belongs.</li>\n</ul>\n<p style=\"line-height: 1.75\">When you create an RDS instance you give it a <strong>DB subnet group</strong> — a named list of subnets, in at least two <strong>Availability Zones</strong> (separate data centres in the same region), that RDS is allowed to place the database in. It does exactly one thing: it decides whether RDS assigns the instance a <strong>public IP address</strong> and whether its DNS name resolves to that public address from outside the VPC. Set to <em>No</em>, the endpoint resolves only to a private address that can only be reached from inside your VPC (or something connected to it, such as a VPN).</p>\n<p style=\"line-height: 1.75\">It should almost always be <em>No</em>. The reason is blunt: a publicly accessible database is one misconfigured firewall rule away from being scanned and brute-forced by bots within minutes. Real attackers run continuous internet-wide scans for open database ports. The safest database is one that simply cannot be addressed from the internet at all.</p>\n<p style=\"line-height: 1.75\">One important nuance: \"publicly accessible = yes\" alone does not let anyone in. Traffic still has to pass the security group. But relying on a single firewall rule as your only defence is exactly the \"one mistake away\" situation that layered security exists to prevent.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Security groups: the virtual firewall</h4>\n<p style=\"line-height: 1.75\">A <strong>security group</strong> is a virtual firewall attached to a resource. Use <strong>AWS Systems Manager Session Manager</strong> port forwarding or a small <strong>bastion host</strong> (a hardened jump server) and tunnel through it, so the database itself never becomes reachable.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Layer 2: Authentication — who may log in</h4>\n<p style=\"line-height: 1.75\">When you create an RDS instance you set a <strong>master username and password</strong>. This account is the database superuser-equivalent: it can create databases, create users, and grant privileges. It is the account you use to bootstrap things — and it should not be the account your application uses every day.</p>\n<p style=\"line-height: 1.75\">Why not? Because of <strong>least privilege</strong> — the principle that every identity should have exactly the permissions it needs and nothing more. If your web app only reads and writes rows in five tables, and it is compromised through some unrelated bug, the blast radius should be \"five tables\", not \"drop the entire database\".</p>\n<p style=\"line-height: 1.75\">The practical pattern is:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Use the master account once</strong>, to create the application database and its users.</li>\n<li><strong>Create a limited user per application</strong> with only <code>SELECT</code>, <code>INSERT</code>, <code>UPDATE</code>, <code>DELETE</code> on the tables it uses.</li>\n<li><strong>Create separate read-only users</strong> for analysts, dashboards, and reporting tools.</li>\n<li><strong>Store the master password somewhere safe</strong> and use it rarely.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Where credentials should live: AWS Secrets Manager</h4>\n<p style=\"line-height: 1.75\"><strong>AWS Secrets Manager</strong> is a service that stores sensitive strings (passwords, API keys) encrypted, controls which identities can read them, logs every read, and can <strong>rotate</strong> them — automatically generate a new password, update the database, and update the stored secret, on a schedule.</p>\n<p style=\"line-height: 1.75\">The problem it solves is real: a password hardcoded in source lands in Git history forever, gets copied into a Slack message, and is impossible to change without a code deploy. With Secrets Manager the application fetches the password at startup using its own AWS identity, so no secret ever appears in the repository.</p>\n<p style=\"line-height: 1.75\">RDS can create and manage the master password in Secrets Manager for you (the \"managed master user password\" option), which is a good default for new instances.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">IAM database authentication: logging in with a token instead of a password</h4>\n<p style=\"line-height: 1.75\"><strong>IAM</strong> (Identity and Access Management) is the AWS service that defines identities — users, roles — and what each one is allowed to do in AWS. A <strong>role</strong> is an identity a machine can assume, so an application server gets AWS permissions without anyone storing keys.</p>\n<p style=\"line-height: 1.75\"><strong>IAM database authentication</strong> lets an AWS identity log into the database with a <strong>short-lived authentication token</strong> instead of a long-lived password. Your app calls <code>generate-db-auth-token</code>, gets back a signed string valid for 15 minutes, and passes that string where the password would normally go. The database user is created with a special grant that says \"authenticate this user via IAM, not a stored password\".</p>\n<p style=\"line-height: 1.75\">The advantage: there is no password to leak, rotate, or accidentally commit, and you revoke access by editing an IAM policy rather than by running SQL. The constraints a beginner should know:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Tokens expire in 15 minutes.</strong> Long-lived connection pools must handle regenerating the token when they open new connections.</li>\n<li><strong>There is a connection rate limit.</strong> IAM authentication is throttled to a maximum number of new connections per second, so it suits applications with pooled, long-lived connections rather than ones that open a fresh connection per request.</li>\n<li><strong>TLS is required</strong> — the token travels with the connection, so the connection must be encrypted.</li>\n<li><strong>It is supported for MySQL, PostgreSQL, and MariaDB</strong> on RDS, not for every engine.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Layer 3: Encryption at rest</h4>\n<p style=\"line-height: 1.75\"><strong>Encryption at rest</strong> means the data physically written to disk is stored scrambled, so that a stolen or improperly decommissioned disk is useless without the key.
