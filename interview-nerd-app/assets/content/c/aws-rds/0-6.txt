You point the queries that only <em>read</em> data at the replicas, and leave the original database — the <strong>primary</strong> — to handle everything that <em>changes</em> data. The result is that one busy database becomes several, and read capacity stops being your bottleneck.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The problem: reads vastly outnumber writes</h4>\n<p style=\"line-height: 1.75\">Think about a blog. Someone publishes an article once. Then ten thousand people read it. Every page view runs several SELECT queries; the single INSERT that created the article happened once, hours ago. Online shops behave the same way: thousands of product-page views for every order placed.</p>\n<p style=\"line-height: 1.75\">A single database instance has finite CPU, memory and disk throughput. As traffic grows, all those reads start competing with each other and with the writes. Queries slow down, connections queue up, and eventually the site feels broken. Your first instinct is to make the instance bigger — <strong>vertical scaling</strong>, moving to a larger instance class. That works for a while, but there is always a largest instance, and each step up costs meaningfully more.</p>\n<p style=\"line-height: 1.75\">Read replicas give you <strong>horizontal scaling</strong> for reads instead: rather than one enormous machine, several ordinary ones, each handling a share of the read traffic.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">How a read replica works</h4>\n<p style=\"line-height: 1.75\">When you create a read replica, RDS takes a snapshot of the primary, builds a new instance from it, and then keeps that new instance updated by continuously streaming changes from the primary to it. The replica accepts connections and runs SELECT queries normally, but it <strong>rejects any attempt to write</strong> — an INSERT, UPDATE, DELETE or schema change sent to a replica fails with a read-only error.</p>\n<p style=\"line-height: 1.75\">Crucially, each replica gets <strong>its own endpoint</strong> — its own DNS hostname, separate from the primary's. There is no magic in front of them. RDS does not intercept your queries and decide where to send them. If you want your reads to go to the replica, <em>your application must be written to connect to the replica's endpoint for those queries</em>. <strong>asynchronous replication</strong>. In plain words: when your application writes to the primary, the primary records the change and immediately reports success. It then sends that change onwards to the replicas, which apply it shortly afterwards. The primary never waits for the replicas.</p>\n<p style=\"line-height: 1.75\">This design is deliberate. If replication were synchronous, every write on the primary would have to wait for every replica, so adding replicas would make writes slower and a single sick replica could stall the whole system. Asynchronous replication means replicas are cheap to add and cannot slow the primary down.</p>\n<p style=\"line-height: 1.75\">The price you pay is <strong>replica lag</strong>: the amount of time by which a replica is behind the primary. Typically it is well under a second, but it grows when the primary is taking a burst of writes, when the replica is a smaller instance class than the primary, when a long-running query on the replica blocks replication from being applied, or when a replica is in another Region and the changes must cross an ocean. RDS publishes this as the <code>ReplicaLag</code> metric in Amazon CloudWatch, and you should alarm on it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The consequence: reading your own writes</h4>\n<p style=\"line-height: 1.75\">Here is the scenario that bites every team the first time. A user opens their profile page and changes their display name from <em>Sam</em> to <em>Samantha</em>. Your application writes the change to the primary and redirects to the profile page. That page load reads the profile — from a replica. But the replica has not yet received the change, so the page renders <em>Sam</em>. The user thinks the save failed, clicks save again, and files a bug report.</p>\n<p style=\"line-height: 1.75\">This is the classic <strong>read-your-own-writes</strong> problem, and it is a direct consequence of asynchronous replication, not a defect. The standard fixes, roughly in order of preference:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Send critical reads to the primary.</strong> Any read that must reflect something the same user just changed goes to the primary endpoint. This is the simplest and most common fix.</li>\n<li><strong>Sticky-to-primary for a short window.</strong> After a user performs a write, route <em>all</em> of that user's reads to the primary for a few seconds.</li>\n<li><strong>Keep the write in the session.</strong> The application already knows the new name — display the value it just submitted rather than re-reading it.</li>\n<li><strong>Check the lag.</strong> Some applications compare a replication position marker against the write position and fall back to the primary if the replica is not caught up. This is the most precise approach and the most work.</li>\n</ul>\n<p style=\"line-height: 1.75\">A good mental rule: reads that are <em>analytical or browsing</em> (product listings, search, dashboards, reports, exports) are perfect for replicas. Reads that are <em>immediately after a write by the same user</em> should go to the primary.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What else read replicas can do</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Several at once.</strong> You can create multiple replicas of one primary (the exact maximum depends on the engine — for MySQL, MariaDB, PostgreSQL and Oracle it is up to 15 per source instance). Spread read traffic across them behind whatever routing your application or driver supports.</li>\n<li><strong>Cross-Region replicas.</strong> A replica can live in a different AWS Region. That puts data physically closer to users on another continent, cutting read latency dramatically, and it gives you a <strong>disaster-recovery foothold</strong>: if the primary Region becomes unavailable, you already have a current copy elsewhere.</li>\n<li><strong>Promotion to standalone.</strong> You can <strong>promote</strong> a read replica, which detaches it from the primary and turns it into an independent, fully writable database with its own lifecycle. Promotion is <em>manual and deliberate</em> — it does not happen automatically when the primary fails — and it is irreversible: a promoted replica cannot be reattached.</li>\n<li><strong>Offloading heavy work.</strong> Reporting queries, nightly exports and analytics scans are ideal replica workloads because they are read-only and their occasional slowness does not hurt customer-facing writes.</li>\n<li><strong>Independent configuration.</strong> A replica can have a different instance size, and for some engines additional indexes, so you can tune it for the reporting workload it serves.</li>\n<li><strong>Its own high availability.</strong> A replica can itself be Multi-AZ, and it can take its own backups.</li>\n</ul>\n<p style=\"line-height: 1.75\">A note on engines: MySQL, MariaDB, PostgreSQL and Oracle support read replicas straightforwardly.
