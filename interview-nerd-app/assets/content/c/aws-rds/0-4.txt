Everything that makes this confusing for beginners is not the database part — it is the <strong>networking</strong> part: the set of rules that decide whether your connection is even allowed to reach the database in the first place. This topic walks through that networking picture one piece at a time, assuming you have never seen any of it before.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The endpoint: the address of your database</h4>\n<p style=\"line-height: 1.75\">An <strong>endpoint</strong> is the DNS hostname that RDS gives your database — a human-readable name that the internet's naming system translates into an actual network address. It looks something like <code>shop-db.abc123xyz.eu-west-1.rds.amazonaws.com</code>. Your application puts that string in its database configuration instead of an IP address.</p>\n<p style=\"line-height: 1.75\">An <strong>IP address</strong> is the numeric address of a specific machine on a network, like 10.0.2.57. A <strong>DNS name</strong> is a label that points at an IP address and can be repointed at a different one later. That difference is the entire reason RDS gives you a name.</p>\n<p style=\"line-height: 1.75\">Here is why it matters. RDS is a managed service, which means AWS may replace the underlying server: during a version upgrade, during a hardware failure, or when it switches you over to a standby copy. When that happens the new machine has a <em>different IP address</em>. If your application had hardcoded the old IP, it would now be talking to nothing. Because you used the endpoint name, AWS simply updates what that name points to, and your application — after reconnecting — reaches the new machine without you changing a single line of configuration.</p>\n<p style=\"line-height: 1.75\"><strong>Practical rule:</strong> never put an RDS IP address in your application config, never cache the resolved IP for a long time in your application, and always store the endpoint in an environment variable or a secrets store so you can change it without a code change.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The port: which door on that address</h4>\n<p style=\"line-height: 1.75\">A single server can run many network services at once, so each service listens on a numbered <strong>port</strong> — think of the hostname as the building address and the port as which door you knock on. First, changing the port does not make your database secure — it is a trivial obstacle, not a defence. Second, whatever port you pick, the firewall rule you write later must name that <em>same</em> port, or the connection is silently dropped and you sit there watching a timeout.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The networking picture, built up from nothing</h4>\n<p style=\"line-height: 1.75\">Now the part that trips everyone up. Four concepts stack on top of each other, so take them in order.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Region.</strong> A geographic area where AWS has infrastructure — for example Ireland (<code>eu-west-1</code>) or Northern Virginia (<code>us-east-1</code>). You choose a Region mainly for latency to your users and for legal or data-residency reasons. Your database lives in exactly one Region.</li>\n<li><strong>Availability Zone (AZ).</strong> Inside a Region, AWS runs several physically separate data centres with independent power, cooling and networking. Each one is an Availability Zone, written like <code>eu-west-1a</code>. They are close enough for very fast connections between them, but far enough apart that a fire, flood or power failure in one is unlikely to affect another. This separation is what makes high availability possible.</li>\n<li><strong>VPC (Virtual Private Cloud).</strong> A private network inside AWS that only your own resources can reach. It has its own address range (for example 10.0.0.0/16) and nothing from the outside world gets in unless you explicitly build a door. Your RDS database always lives inside a VPC.</li>\n<li><strong>Subnet.</strong> A VPC is sliced into smaller address ranges called subnets — for example 10.0.1.0/24. Each subnet sits in exactly <em>one</em> Availability Zone. A subnet is <strong>public</strong> if its routing rules send internet-bound traffic to an internet gateway (so resources in it can be reachable from, and reach, the internet), and <strong>private</strong> if they do not. A private subnet is the normal, correct home for a database.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">DB subnet group: telling RDS where it may place the database</h4>\n<p style=\"line-height: 1.75\">RDS does not let you say \"put the database on this exact machine in this exact subnet\". Instead you give it a <strong>DB subnet group</strong>: a named list of subnets that RDS is allowed to choose from. RDS then picks one for the database and remembers the rest for later.</p>\n<p style=\"line-height: 1.75\">AWS requires a DB subnet group to contain subnets in <strong>at least two different Availability Zones</strong>. That requirement exists so that RDS always has somewhere else to go — if you later turn on a standby copy in another AZ, or if AWS has to move your instance after a failure, the subnet group already lists a valid destination. You cannot create an RDS instance without one; if you use the console's default settings, AWS quietly creates a default subnet group for you, which is why beginners often do not notice it exists.</p>\n<p style=\"line-height: 1.75\">Two practical consequences: all subnets in the group should be the same kind (all private for a private database), and the group should cover the same AZs your application servers run in, so traffic stays inside the Region and does not cross unnecessary boundaries.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Security group: the firewall that decides who may connect</h4>\n<p style=\"line-height: 1.75\">A <strong>security group</strong> is a virtual firewall attached to your database. It is a list of <em>allow</em> rules; anything not explicitly allowed is blocked. There is no \"deny\" rule to write — the default is already deny.</p>\n<p style=\"line-height: 1.75\">Each inbound rule says three things: the <strong>protocol</strong> (TCP for databases), the <strong>port</strong> (5432, 3306 and so on), and the <strong>source</strong> — who is allowed. The source can be an IP address range like <code>203.0.113.7/32</code> (one specific machine), or, much better, <em>another security group</em>.</p>\n<p style=\"line-height: 1.75\">That last option is the idiomatic AWS pattern and worth understanding properly. If your application servers are attached to a security group called <code>app-sg</code>, you write a rule on the database security group that says \"allow TCP 5432 from <code>app-sg</code>\". This means: any machine wearing the <code>app-sg</code> badge may connect. You never have to list IP addresses, and when you add or replace application servers the rule keeps working automatically because the new servers also wear the badge.</p>\n<p style=\"line-height: 1.75\">Security groups are also <strong>stateful</strong>: if an inbound connection is allowed, the reply traffic is automatically allowed back out. The failure mode is a useful clue: a connection that <em>hangs and eventually times out</em> is almost always a networking or firewall problem, while an <em>immediate, clear error message</em> usually means you reached the database and it refused you.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Is the database finished creating?</strong> Status must be <code>available</code>. While it says <code>creating</code>, <code>modifying</code> or <code>backing-up</code> during certain operations, connections may fail. Check with <code>aws rds describe-db-instances</code>.</li>\n<li><strong>Did you copy the endpoint exactly?</strong> The full hostname includes a random identifier and the Region. Copy it from the console or the CLI, never retype it. A typo shows up as a DNS resolution error such as <em>could not translate host name</em>.</li>\n<li><strong>Is the port right?</strong> 5432 for PostgreSQL, 3306 for MySQL — unless you chose a custom one at creation. Many clients silently default to their own engine's standard port.</li>\n<li><strong>Does the security group allow your source?</strong> This is the number one cause. If connecting from an EC2 instance, the rule's source should be that instance's security group. If connecting from a bastion, it should be the bastion's security group. Check the rule names the correct port too.</li>\n<li><strong>Are you outside the network entirely?</strong> If the database is in a private subnet and you are on your home broadband, there is no path at all — no firewall rule can fix that. You need a bastion, Session Manager or a VPN. This is the case that confuses beginners most, because the settings all \"look right\".</li>\n<li><strong>Is Public access set as you expect?</strong> If you deliberately want to reach it from outside, it must be <em>Yes</em> <em>and</em> the instance must be in a public subnet <em>and</em> the security group must allow your IP. All three, not one.</li>\n<li><strong>Are the credentials correct?</strong> A message like <em>password authentication failed for user</em> or <em>Access denied for user</em> means the network is fine and you have a username, password or database-name problem. Note the master username is set at creation and cannot be changed; the password can be reset with <code>modify-db-instance</code>.</li>\n<li><strong>Is TLS required?</strong> Some parameter groups enforce encrypted connections (<code>rds.force_ssl</code> on PostgreSQL, <code>require_secure_transport</code> on MySQL). If so, an unencrypted client is rejected. Download the AWS RDS certificate bundle and pass the right SSL mode.</li>\n<li><strong>Network ACLs.</strong> Rarely the culprit, but if someone has customised the subnet-level <strong>network ACL</strong> (a second, stateless firewall that applies to the whole subnet), it must allow the database port inbound and the ephemeral return ports outbound.</li>\n<li><strong>Connection limits.</strong> If everything worked yesterday and now fails under load, you may simply be out of connections. Check the <code>DatabaseConnections</code> metric in Amazon CloudWatch and consider RDS Proxy or a connection pool.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"Publicly accessible = insecure.\"</strong> Not by itself.
