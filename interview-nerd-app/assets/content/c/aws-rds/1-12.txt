{"title":"Blue/Green Deployments and Zero-Downtime Schema Changes","tags":["rds","blue-green","schema migration","zero downtime"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Changing a running production database is the riskiest routine operation most teams perform. There are two distinct disciplines involved, and strong candidates separate them. The first is <strong>changing the database environment</strong> — upgrading the engine, changing a static parameter, moving to a different instance class — which AWS addresses directly with <strong>RDS Blue/Green Deployments</strong>. The second is <strong>changing the schema while application code is mid-rollout</strong>, which no AWS feature solves for you and which is what interviewers are usually probing: the <strong>expand-and-contract</strong> pattern, DDL locking behavior, and online migration tooling.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">RDS Blue/Green Deployments: the managed mechanism</h4>\n<p style=\"line-height: 1.75\">Calling <code>create-blue-green-deployment</code> against a production instance or Aurora cluster (the <strong>blue</strong> environment) makes RDS build a full <strong>green</strong> copy — same topology, replicas included — and keep it synchronized from blue using <strong>logical replication</strong> (binlog-based for MySQL/MariaDB and Aurora MySQL, logical replication for PostgreSQL and Aurora PostgreSQL). You then make your changes on green: upgrade the major version, change a parameter group, add an index, run a schema migration. Blue keeps serving all production traffic the entire time, unaware.</p>\n<p style=\"line-height: 1.75\">When you are satisfied, you call <code>switchover</code>. RDS performs a guarded cutover, <strong>typically under a minute</strong>:</p>\n<div class=\"code\"><div class=\"code-head\"><span>bash</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">BEFORE                                  DURING SWITCHOVER            AFTER\napp --&gt; myapp.xxxx.rds  (BLUE  v13)     1. blue <i class=b>set</i> READ-ONLY        app --&gt; myapp.xxxx.rds (was GREEN, v16)\n              |  logical replication    2. <i class=b>wait</i> <i class=k>for</i> green to catch                |\n              v                            up to blue<i class=s>&#x27;s LSN/position             |\n           green-xxxx    (GREEN v16)    3. verify lag == 0            myapp-old1.xxxx.rds (was BLUE, v13)\n                                        4. Green takes over blue's DNS name, and the old blue instance is renamed with an <code>-oldN</code> suffix. Your application's connection string does not change. The old blue environment is <em>not deleted</em> — it stays, detached, so you can inspect it or use it as a manual rollback source. You pay for it until you delete it.</p>\n<p style=\"line-height: 1.75\">Before switchover you can <strong>abandon</strong>: delete the blue/green deployment, optionally deleting the green environment, and nothing has happened to production. That asymmetry — a long, low-pressure validation period followed by a short, reversible-until-committed cutover — is why blue/green is now the default recommendation for major version upgrades.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Constraints you must state honestly</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Engine and version support is limited.</strong> It covers RDS for MySQL and MariaDB, RDS for PostgreSQL, Aurora MySQL and Aurora PostgreSQL, each with minimum-version requirements. It does <strong>not</strong> support Oracle or SQL Server. Check the current support matrix rather than assuming.</li>\n<li><strong>Logical replication prerequisites.</strong> MySQL needs binary logging enabled with row-based format (set <code>binlog_format=ROW</code> in a custom parameter group, which for RDS MySQL requires backup retention greater than zero). PostgreSQL needs <code>rds.logical_replication=1</code>, which is a <strong>static</strong> parameter and therefore requires a reboot — so enabling blue/green on a PostgreSQL instance that never had it can itself cost a restart.</li>\n<li><strong>Logical replication's blind spots apply.</strong> For PostgreSQL, tables without a primary key or replica identity replicate poorly or not at all; large objects and certain DDL are not replicated. Sequences are <em>not</em> advanced by logical replication in older PostgreSQL versions, so sequence values must be reconciled at switchover.</li>\n<li><strong>Green is read-only by default.</strong> RDS keeps green read-only so replication stays consistent. You can permit writes on green (there is a setting in newer versions, and for PostgreSQL blue/green you can allow writes on green), but <strong>writes on green are not replicated back to blue</strong> and can break replication. Practically, this means you can validate query plans, EXPLAIN output, read performance, and application read paths against green, but you cannot run a full write-path load test there and then switch over with that data intact.</li>\n<li><strong>Switchover makes blue read-only for the duration.</strong> Even a 30-second switchover is 30 seconds of failed writes unless the application retries. Blue/green is <em>near</em>-zero downtime, not zero.</li>\n<li><strong>Cost doubles while both exist</strong>, and the detached old-blue keeps costing until deleted. Delete it deliberately, after a soak period.</li>\n<li><strong>It does not cover everything.</strong> Resources outside the database — RDS Proxy targets, IAM policies referencing the resource ID, DMS tasks, external replicas, Lambda event source mappings, monitoring dashboards keyed to the instance identifier — may need attention after the rename. Cross-Region read replicas of blue are not carried over.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The real interview topic: zero-downtime schema migration</h4>\n<p style=\"line-height: 1.75\">Blue/green solves environment changes. It does <strong>not</strong> solve the fundamental problem that during a rolling deploy, <strong>two versions of your application code run simultaneously against one schema</strong>. The schema must be compatible with the old code and the new code at the same time. That constraint, not the DDL mechanics, is what makes naive migrations break.</p>\n<p style=\"line-height: 1.75\">Consider the classic failure: a single deploy that renames <code>user_name</code> to <code>username</code>. The migration runs, then instances roll one at a time over ten minutes. Every old instance still issuing <code>SELECT user_name</code> errors immediately. The same applies to dropping a column, adding a <code>NOT NULL</code> column without a default, narrowing a type, or renaming a table. <strong>Any migration that removes or renames something is incompatible with a rolling deploy by construction.</strong></p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Expand and contract</h4>\n<p style=\"line-height: 1.75\">The pattern that resolves this splits every destructive change into a sequence of additive, individually-safe deploys. For renaming <code>user_name</code> to <code>username</code>:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Deploy 1 — Expand (schema only).</strong> <code>ALTER TABLE users ADD COLUMN username text</code>, nullable, no default that requires a rewrite. Nothing reads or writes it yet. Safe with all running code.</li>\n<li><strong>Deploy 2 — Dual write.</strong> Application writes both <code>user_name</code> and <code>username</code> on every insert and update; still reads <code>user_name</code>. Now new data is correct in both places while old code that writes only <code>user_name</code> is still running — so this deploy must also tolerate rows where <code>username</code> is null.</li>\n<li><strong>Step 3 — Backfill.</strong> A batched job copies <code>user_name</code> into <code>username</code> where null, in chunks of a few thousand rows with a commit and a short sleep between batches. Never one giant <code>UPDATE</code>.</li>\n<li><strong>Deploy 4 — Migrate reads.</strong> Application reads <code>username</code>, still dual-writes. Verify with metrics and a reconciliation query that the two columns never disagree. This deploy is the one you can roll back cheaply.</li>\n<li><strong>Deploy 5 — Stop writing the old column</strong>, and only after that has soaked, <strong>Deploy 6 — Contract</strong>: add the <code>NOT NULL</code> constraint (validated separately) and <code>ALTER TABLE users DROP COLUMN user_name</code>.</li>\n</ul>\n<p style=\"line-height: 1.75\">Six deploys to rename a column feels absurd until you have caused an outage with one. The discipline scales: adding a required field, changing a type, splitting a table, and moving a foreign key all decompose the same way. The invariant to state in an interview is simply: <strong>at every instant, the schema must be valid for both the code that is running and the code that is about to run, and every step must be independently reversible.</strong></p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">DDL locking: PostgreSQL versus MySQL</h4>\n<p style=\"line-height: 1.75\">The second half of the problem is that a DDL statement can be logically safe and still take the database down by holding a lock. The two engines fail differently.</p>\n<p style=\"line-height: 1.75\"><strong>PostgreSQL.</strong> Most <code>ALTER TABLE</code> forms take an <code>ACCESS EXCLUSIVE</code> lock, which blocks <em>everything</em> including <code>SELECT</code>. The saving grace is that many are <strong>metadata-only</strong> and complete in microseconds — adding a nullable column, and since PG 11, adding a column with a non-volatile default. The killers are operations that <strong>rewrite the table</strong>: changing a column type (with exceptions such as widening <code>varchar</code> length), adding a column with a volatile default, <code>SET NOT NULL</code> on a large table without a pre-validated check constraint. A rewrite of a 500 GB table holds ACCESS EXCLUSIVE for however long it takes.</p>\n<p style=\"line-height: 1.75\">The far more insidious PostgreSQL failure is the <strong>lock queue</strong>. A pending ACCESS EXCLUSIVE request queues behind any existing lock — including a long-running <code>SELECT</code> or an idle-in-transaction session — and <em>everything arriving after it queues behind the pending request</em>. A metadata-only ALTER that would have taken 200 microseconds waits 40 minutes on an analytics query, and during those 40 minutes every query on that table piles up. Total outage from a \"safe\" migration. The mitigations are non-negotiable: set a short <strong><code>lock_timeout</code></strong> (2-5 seconds) before DDL so the statement fails fast instead of queueing, retry in a loop, and never run migrations while long transactions are open. <code>CREATE INDEX CONCURRENTLY</code> and <code>DROP INDEX CONCURRENTLY</code> avoid the exclusive lock entirely at the cost of two table passes, no transaction wrapping, and the possibility of leaving an <code>INVALID</code> index behind that must be dropped and retried. Similarly, add a <code>CHECK (col IS NOT NULL) NOT VALID</code> constraint, <code>VALIDATE CONSTRAINT</code> (which takes only a SHARE UPDATE EXCLUSIVE lock), then <code>SET NOT NULL</code> cheaply.</p>\n<p style=\"line-height: 1.75\"><strong>MySQL/InnoDB.</strong> Since 5.6, many <code>ALTER TABLE</code> operations support <code>ALGORITHM=INPLACE</code> with <code>LOCK=NONE</code>, permitting concurrent DML. Adding a nullable column, adding a secondary index, and renaming a column are usually online. Since 8.0.12, <code>ALGORITHM=INSTANT</code> makes adding a column at the end of the row metadata-only. But several common operations still force <code>ALGORITHM=COPY</code>, which rebuilds the table and <strong>blocks writes</strong>: changing a column data type, adding or dropping a primary key, converting the character set, and some <code>OPTIMIZE TABLE</code> paths. The defensive practice is to always state the algorithm explicitly — <code>ALTER TABLE t ADD INDEX ix (c), ALGORITHM=INPLACE, LOCK=NONE</code> — so that if MySQL cannot honor it, the statement <strong>errors instead of silently taking a copy lock for four hours</strong>. Even online ALTERs need a brief exclusive metadata lock at start and end, and MySQL's metadata locks queue the same way PostgreSQL's do, so <code>lock_wait_timeout</code> matters too.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Online schema change tools</h4>\n<p style=\"line-height: 1.75\">For MySQL, when a change requires a rebuild, the standard answer is an external tool. <strong>pt-online-schema-change</strong> (Percona Toolkit) creates an empty shadow table with the new definition, installs <strong>triggers</strong> on the original to propagate ongoing changes, copies existing rows in throttled chunks, then does an atomic <code>RENAME</code>. <strong>gh-ost</strong> (GitHub) does the same job but reads the <strong>binlog</strong> instead of using triggers, which removes trigger overhead from the write path, makes the copy pausable and dynamically throttleable, and lets you test against a replica. Both work with RDS MySQL and Aurora MySQL; gh-ost typically runs in binlog-reading mode against the writer or a replica. The trade-offs to mention: both temporarily <strong>double the table's disk usage</strong>, both need a <strong>unique key</strong> on the table, both interact awkwardly with existing triggers and foreign keys, and both extend a five-minute blocking ALTER into a multi-hour throttled copy — which is the correct trade.</p>\n<p style=\"line-height: 1.75\">PostgreSQL's equivalents are narrower: <code>CREATE INDEX CONCURRENTLY</code> covers indexes, <code>pg_repack</code> covers table rewrites and bloat removal without a long exclusive lock, and for a type change the usual approach is expand-and-contract with a new column rather than an in-place <code>ALTER TYPE</code>.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Backfills, replica lag, and safety rails</h4>\n<p style=\"line-height: 1.75\">A backfill is where a careful migration still causes an incident. One <code>UPDATE</code> touching 200 million rows creates a single enormous transaction: it holds row locks for its duration, generates a mountain of WAL or binlog, bloats the table (PostgreSQL MVCC leaves a dead tuple per updated row), blocks <code>VACUUM</code> from cleaning anything older, and — critically — <strong>replicas cannot apply it faster than the writer produced it</strong>, so read replica lag spikes and your read-serving traffic sees stale or timing-out queries. On Aurora the storage layer absorbs some of this, but the replica-lag and long-transaction effects on MVCC remain.</p>\n<p style=\"line-height: 1.75\">Batched backfill practice: process by primary key range with a bounded chunk size (1,000-10,000 rows), commit each chunk, <strong>sleep between chunks</strong>, and make the loop <strong>adaptive</strong> — read <code>ReplicaLag</code> or <code>pg_stat_replication</code> lag and pause when it exceeds a threshold. Make the job <strong>idempotent and resumable</strong> by tracking the last processed key, so a failure at 3 a.m. resumes rather than restarting. Set <code>statement_timeout</code> so a pathological chunk cannot run away. Run it off-peak, monitor <code>WriteIOPS</code>, <code>DMLLatency</code>, and lag throughout, and be prepared to stop.</p>\n<p style=\"line-height: 1.75\">The safety rails, stated as a checklist you would put in a migration framework: <strong><code>lock_timeout</code></strong> (PostgreSQL) or <strong><code>lock_wait_timeout</code></strong> (MySQL) set low for all DDL, with automatic retry; <strong><code>statement_timeout</code></strong> to bound any single statement; <strong><code>idle_in_transaction_session_timeout</code></strong> to kill the abandoned psql session that will otherwise block your ALTER; explicit <code>ALGORITHM</code>/<code>LOCK</code> clauses on MySQL DDL; a rule that migrations and application deploys ship <em>separately</em>; and a pre-flight check that refuses to run DDL while a transaction older than N seconds exists.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario: change a column type on a 900 GB table with no downtime</h4>\n<p style=\"line-height: 1.75\"><em>Situation:</em> PostgreSQL 15 on RDS, table <code>events</code> with 3.1 billion rows and 900 GB. The <code>id</code> column is <code>integer</code> and will exhaust the 2.1 billion range in roughly seven weeks. It is the primary key and is referenced by two foreign keys. The service is 24/7 with a 99.95% SLO.</p>\n<p style=\"line-height: 1.75\"><strong>Why the obvious approach fails.</strong> <code>ALTER TABLE events ALTER COLUMN id TYPE bigint</code> rewrites the entire table and every dependent index while holding <code>ACCESS EXCLUSIVE</code>. On 900 GB that is hours of total unavailability, plus it needs 900 GB of free space, plus the foreign keys must be revalidated. Blue/green does not save you either: the DDL would run on green and be fine there, but the switchover requires replication to be caught up, and a multi-hour rewrite on green is fine — <em>however</em> logical replication of a table being rewritten on the subscriber side is not something to rely on. So: expand and contract.</p>\n<p style=\"line-height: 1.75\"><strong>Step 1 — Expand.</strong> <code>ALTER TABLE events ADD COLUMN id_big bigint;</code> Nullable, no default, metadata-only, microseconds — but run it with <code>SET lock_timeout = '3s'</code> and a retry loop, because the lock queue is the actual risk. Do the same on the two referencing tables: add <code>event_id_big bigint</code>.</p>\n<p style=\"line-height: 1.75\"><strong>Step 2 — Keep new rows correct.</strong> Add a <code>BEFORE INSERT OR UPDATE</code> trigger setting <code>NEW.id_big := NEW.id</code>, or dual-write from the application. The trigger is preferable here because it covers every writer including batch jobs and is a single change. Measure its cost on the write path — a trivial PL/pgSQL trigger on a high-insert table is not free, and this is worth a load test.</p>\n<p style=\"line-height: 1.75\"><strong>Step 3 — Backfill.</strong> Loop over <code>id</code> ranges of 5,000, <code>UPDATE events SET id_big = id WHERE id BETWEEN x AND x+4999 AND id_big IS NULL</code>, commit, sleep 50ms, and pause whenever replica lag exceeds 30 seconds or <code>WriteIOPS</code> exceeds a ceiling. Record progress in a control table. At 3.1 billion rows this runs for days; that is acceptable and expected. Watch bloat and ensure autovacuum keeps up — consider raising <code>autovacuum_vacuum_cost_limit</code> for this table during the backfill.</p>\n<p style=\"line-height: 1.75\"><strong>Step 4 — Build the new constraints without locks.</strong> <code>CREATE UNIQUE INDEX CONCURRENTLY events_pkey_big ON events (id_big);</code> then <code>ALTER TABLE events ADD CONSTRAINT events_id_big_not_null CHECK (id_big IS NOT NULL) NOT VALID;</code> followed by <code>VALIDATE CONSTRAINT</code>, which takes only a SHARE UPDATE EXCLUSIVE lock and can run for hours harmlessly. Build the new foreign keys as <code>NOT VALID</code> and validate them the same way.</p>\n<p style=\"line-height: 1.75\"><strong>Step 5 — The swap.</strong> In one short transaction with a 3-second <code>lock_timeout</code> and a retry loop: drop the old primary key constraint, rename <code>id</code> to <code>id_old</code>, rename <code>id_big</code> to <code>id</code>, attach the pre-built unique index as the primary key using <code>ALTER TABLE ... ADD CONSTRAINT events_pkey PRIMARY KEY USING INDEX events_pkey_big</code>, and re-point the sequence with <code>ALTER SEQUENCE events_id_seq AS bigint OWNED BY events.id</code> and <code>setval</code> above the current maximum. Because every expensive object was built beforehand, this transaction is metadata-only and completes in milliseconds — the whole design exists to make this one step cheap.</p>\n<p style=\"line-height: 1.75\"><strong>Step 6 — Contract.</strong> Soak for a week with monitoring and the ability to rename back. Then drop the trigger and <code>ALTER TABLE events DROP COLUMN id_old</code>, which in PostgreSQL is metadata-only and reclaims space lazily via vacuum. Rollback at every step before 5 is trivial; after step 5, rollback is a rename back, which is why the soak period matters more than the swap.</p>\n<p style=\"line-height: 1.75\"><strong>What to say about alternatives.</strong> If this were MySQL, <strong>gh-ost</strong> would do steps 1-5 as a single throttled, pausable, binlog-driven operation and would be the right call.
