Internalize that last clause, because almost every distinctive property of an Aurora topology — how fast you can add a replica, how small replica lag is, why replicas cost nothing in storage, and how failover can complete in seconds — is a direct consequence of there being a single copy of the data that all instances attach to. Candidates who mentally model Aurora replicas as \"read replicas, but better\" get every follow-up question slightly wrong.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Replicas Are Not Copies</h4>\n<p style=\"line-height: 1.75\">In RDS for MySQL or PostgreSQL, a read replica is a full second database: its own instance, its own EBS volume, its own copy of every byte, kept current by replaying a logical or physical replication stream. Creating one means copying the entire dataset, so provisioning time scales with data size. Keeping one current means the replica must perform the same write work the primary did, so under heavy write load replicas fall behind — lag measured in seconds or minutes is routine.</p>\n<p style=\"line-height: 1.75\">Aurora Replicas attach to the <strong>same storage volume</strong> in read-only mode. There is nothing to copy. Consequently:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Provisioning is fast and size-independent.</strong> Adding a replica to a 10 GB cluster and to a 40 TB cluster takes about the same time — typically a few minutes, dominated by instance launch, not data movement.</li>\n<li><strong>Replicas add no storage cost.</strong> You pay instance-hours only. This is frequently the dominant economic argument for Aurora in read-heavy architectures.</li>\n<li><strong>Lag is tiny — typically tens of milliseconds</strong>, often reported in the 10–20 ms range. The writer streams redo records to replicas so they can invalidate and update their in-memory buffer cache pages; the replica never has to redo work against storage. Lag is a cache-coherence delay, not a replay backlog.</li>\n<li><strong>Replicas are automatic failover targets.</strong> Because they already attach to the authoritative volume, promotion does not require attaching a volume or replaying a log.</li>\n</ul>\n<p style=\"line-height: 1.75\">The trade-off is the flip side of sharing: a replica <strong>cannot diverge</strong> from the writer, so you cannot use one as a writable staging copy, and a logical corruption written by the writer is instantly visible on every replica. Aurora replicas are an availability and read-scaling mechanism, not a data-protection mechanism. You still need backups and, for some use cases, a <strong>cloned</strong> cluster (Aurora fast database cloning is copy-on-write on the same storage and is the right tool for a writable test copy).</p>\n<h4 style=\"margin-top: 1.5rem; It follows failover automatically — this is the whole point. Applications must use it for all writes and for any read that must be read-your-writes consistent. The reader endpoint balances <strong>at DNS resolution</strong>, with a short TTL (on the order of five seconds). That produces good balance when connections are short-lived and frequently re-established. It produces <strong>terrible</strong> balance when:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li>You use a <strong>connection pool</strong> (HikariCP, pgbouncer, SQLAlchemy, Rails) that opens its connections once at startup and holds them for hours. Every pod that started at the same moment may resolve to the same replica and pin there permanently. After a deployment restarts every pod simultaneously, this is nearly guaranteed.</li>\n<li>Your runtime <strong>caches DNS indefinitely</strong>. The JVM historically caches successful lookups forever unless <code>networkaddress.cache.ttl</code> is set; setting it to something like 5 seconds is standard Aurora hygiene.</li>\n<li>You add a new replica and expect existing traffic to shift onto it — it will not. Only new connections can land there.</li>\n</ul>\n<p style=\"line-height: 1.75\">Mitigations, in increasing order of investment: set a short DNS TTL in the client runtime; <strong>recycle pooled connections on a max-lifetime</strong> (a 15–30 minute max lifetime forces periodic rebalancing); use a driver with native cluster awareness such as the <strong>AWS JDBC Driver for MySQL/PostgreSQL</strong>, which discovers the topology from the cluster metadata tables and can do its own load balancing and fast failover; or put <strong>RDS Proxy</strong> in front, which pools and multiplexes connections and dramatically improves both balance and failover behavior. Note explicitly for the interviewer: <strong>the reader endpoint never load balances individual queries inside one connection.</strong> Once a session is established it stays on that instance until it is closed.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Failover Mechanics and Promotion Tiers</h4>\n<p style=\"line-height: 1.75\">Every instance has a <strong>promotion tier from 0 to 15</strong> (default 1). On writer failure Aurora promotes a replica from the <strong>lowest-numbered tier</strong>; if multiple replicas share that tier, Aurora chooses the one with the <strong>largest instance size</strong>, and if those also tie, it picks arbitrarily among them. This gives you deliberate control: put your two production-sized readers in tier 0, and park a small reporting replica in tier 15 so it is never promoted into a role its instance class cannot handle. Setting a tier is an instance-level modification and takes effect immediately.</p>\n<p style=\"line-height: 1.75\">Timing: Aurora failover typically completes in <strong>under 30 seconds</strong> when the cluster has at least one replica, and the DNS record for the cluster endpoint is flipped to the promoted instance. If the cluster has <strong>no replicas</strong>, Aurora attempts to recreate the writer in the same or another AZ, which takes longer — often several minutes — and is the reason a single-instance Aurora cluster is not a highly available deployment despite the six-way storage replication. Storage durability and compute availability are different properties.</p>\n<p style=\"line-height: 1.75\">What happens to <strong>in-flight work</strong> is the part candidates skip: <strong>all existing connections to the old writer are terminated</strong>, uncommitted transactions are rolled back, and the client sees a dropped socket or a \"server closed the connection unexpectedly\" error. Committed transactions are never lost — the storage volume is authoritative. So the application contract is: <strong>you must implement reconnect-with-exponential-backoff and idempotent retry of the failed transaction.</strong> No amount of AWS-side speed removes this requirement. RDS Proxy softens it by holding the client connection open while re-establishing the backend connection, which can make a failover nearly invisible to well-behaved applications, and it also reduces observed failover time because the proxy detects topology change faster than DNS propagates.</p>\n<p style=\"line-height: 1.75\">You can and should <strong>test</strong> this. <code>aws rds failover-db-cluster</code> triggers a controlled failover, and Aurora supports <strong>fault injection queries</strong> (for example <code>ALTER SYSTEM CRASH INSTANCE</code> on Aurora PostgreSQL) to simulate crashes.
