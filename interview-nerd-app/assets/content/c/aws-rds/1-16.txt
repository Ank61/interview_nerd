{"title":"Auditing and Compliance — Database Activity Streams, Audit Logs, and CloudTrail","tags":["auditing","compliance","database-activity-streams","cloudtrail"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Database auditing on AWS is three <strong>separate, non-overlapping</strong> layers, and the single most common failure in interviews is collapsing them into one. <strong>CloudTrail</strong> sees the AWS control plane — who created, modified, snapshotted or deleted a database — and never sees a single SQL statement. <strong>Engine logs</strong> see inside the database but are written by the database, which means a sufficiently privileged DBA can turn them off or edit them downstream. <strong>Database Activity Streams</strong> see inside the database too, but are produced outside the DBA's reach and delivered to Kinesis encrypted with your own key, which is the separation-of-duties property that compliance regimes actually demand. Knowing which layer answers which question is the whole skill.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Layer 1 — CloudTrail: the control plane only</h4>\n<p style=\"line-height: 1.75\">CloudTrail records every RDS API call as a management event: <code>CreateDBInstance</code>, <code>ModifyDBInstance</code>, <code>DeleteDBInstance</code>, <code>CreateDBSnapshot</code>, <code>ModifyDBSnapshotAttribute</code> (snapshot sharing — a data-exfiltration path worth alarming on), <code>RestoreDBInstanceFromDBSnapshot</code>, <code>ModifyDBParameterGroup</code>, <code>AuthorizeDBSecurityGroupIngress</code> and the rest. Each event carries the identity, source IP, request parameters and the request id. This is your evidence for infrastructure change control and for questions like \"who opened this database to the internet last Thursday\" or \"who shared a production snapshot with an external account\".</p>\n<p style=\"line-height: 1.75\">What CloudTrail categorically <strong>cannot</strong> tell you is anything that happened over the database protocol. There are no CloudTrail <em>data events</em> for RDS the way there are for S3 objects or Lambda invocations. A query that reads every row of a customers table is invisible to CloudTrail. Candidates who answer \"use CloudTrail\" to \"who read the PII table\" are eliminated on the spot. CloudTrail also records the <em>surrounding</em> services: KMS <code>Decrypt</code> and <code>ScheduleKeyDeletion</code>, Secrets Manager <code>GetSecretValue</code> (which is how you see who retrieved a database credential), and STS <code>AssumeRole</code>, which is often the only way to attribute an action to a human behind a shared role.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Layer 2 — Engine logs and native audit plugins</h4>\n<p style=\"line-height: 1.75\">Every RDS engine writes logs locally on the instance, where they rotate and are lost. The step that makes them useful is <strong>publishing them to CloudWatch Logs</strong> with <code>--enable-cloudwatch-logs-exports</code>, which gives you retention policy, CloudWatch Logs Insights querying, metric filters and alarms, and export to S3. The available log types differ per engine:</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Engine</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Exportable log types</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Audit mechanism</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">MySQL / MariaDB / Aurora MySQL</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">audit, error, general, slowquery</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">MariaDB Audit Plugin via option group</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">PostgreSQL / Aurora PostgreSQL</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">postgresql, upgrade</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">pgaudit extension</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Oracle</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">alert, audit, trace, listener</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Unified Auditing / fine-grained audit</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">SQL Server</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">error, agent</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">SQLSERVER_AUDIT option to S3</td></tr>\n</tbody>\n</table>\n</div>\n<p style=\"line-height: 1.75\"><strong>pgaudit</strong> is the PostgreSQL answer. On RDS you add <code>pgaudit</code> to <code>shared_preload_libraries</code> (a static parameter, so a reboot is required), create the extension, and configure <code>pgaudit.log</code> with the classes you want: <code>ddl</code>, <code>role</code>, <code>write</code>, <code>read</code>, <code>function</code>, <code>misc</code>, or <code>all</code>. On RDS you also set <code>pgaudit.role = 'rds_pgaudit'</code> and create that role; object-level auditing then works by granting that role <code>SELECT</code> or <code>UPDATE</code> on precisely the sensitive tables, which is how you audit a handful of PII tables without paying to log every query in the database. Set <code>pgaudit.log_parameter</code> deliberately — it captures bind values, which is exactly what an investigator wants and exactly what a privacy reviewer objects to, since parameters frequently contain the PII you were trying to protect.</p>\n<p style=\"line-height: 1.75\"><strong>MySQL and MariaDB</strong> use the <code>MARIADB_AUDIT_PLUGIN</code> attached through an <strong>option group</strong> (not a parameter group — a classic trip-up). Its settings include <code>SERVER_AUDIT_EVENTS</code> (<code>CONNECT</code>, <code>QUERY</code>, <code>TABLE</code>, <code>QUERY_DDL</code>, <code>QUERY_DML</code>), <code>SERVER_AUDIT_INCL_USERS</code> and <code>SERVER_AUDIT_EXCL_USERS</code>. Aurora MySQL has its own higher-performance native implementation configured through <code>server_audit_logging</code> and related cluster parameters.</p>\n<p style=\"line-height: 1.75\"><strong>The performance cost is real and must be quantified, not hand-waved.</strong> The MySQL <em>general log</em> records every statement and is genuinely dangerous on a busy instance — it is a debugging tool, not an audit tool. A <em>slow query log</em> with <code>long_query_time</code> set too low degenerates into a general log. <code>pgaudit.log = 'all'</code> with <code>log_parameter</code> on a high-QPS OLTP database can add double-digit CPU overhead and produce log volume that dwarfs the data itself. The engineering answer is <strong>scope the audit to what the regime requires</strong>: DDL and role changes always, reads only on designated sensitive objects, and never blanket statement logging on the hot path. Also remember the local disk cost — verbose logs consume the same volume as your data and have caused <code>storage-full</code> incidents.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Layer 3 — Database Activity Streams</h4>\n<p style=\"line-height: 1.75\">Database Activity Streams (DAS) is the purpose-built compliance control. You start it on a cluster or instance and RDS creates an <strong>Amazon Kinesis Data Stream</strong> named <code>aws-rds-das-&lt;resource-id&gt;</code> in your account, into which it publishes a near-real-time record of database activity: connections and disconnections, the SQL text, the database user, the client application and host, the objects touched, and whether the statement succeeded. Each record's payload is encrypted with a data key protected by <strong>your customer managed KMS key</strong>, so consumers must hold both Kinesis read rights and KMS decrypt rights — two separable grants.</p>\n<p style=\"line-height: 1.75\">Support covers <strong>Aurora MySQL and Aurora PostgreSQL</strong> plus RDS for Oracle, RDS for SQL Server and RDS for PostgreSQL; it is not available for every engine, and that constraint has decided architectures. Two modes matter:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Synchronous mode.</strong> The database blocks until the activity event is durably recorded. You cannot lose an audit record, but a problem in the streaming path becomes a problem in your transaction latency. This is what a regulator means by a reliable audit trail.</li>\n<li><strong>Asynchronous mode.</strong> The database records the event and moves on. Performance is prioritised, and under extreme pressure events can be lost. Most teams start here and only move to synchronous where the control is mandatory.</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>The separation-of-duties property is the reason DAS exists.</strong> The stream is produced by the RDS service outside the database engine's privilege model, so a user with <code>rds_superuser</code> or DBA rights cannot quietly suppress it or edit the records. Stopping the stream is an <strong>RDS API call</strong> (<code>StopActivityStream</code>), which lands in CloudTrail and can be denied by IAM and alarmed on — so the act of disabling the audit trail is itself audited. Contrast that with engine logs, where the same DBA who performs a suspicious action can also set <code>pgaudit.log = 'none'</code> beforehand. When an interviewer asks why you would not just use pgaudit, this is the answer.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Building the downstream pipeline</h4>\n<div
