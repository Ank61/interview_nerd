{"title":"Monitoring an RDS Database and Understanding the Bill","tags":["cloudwatch","performance-insights","rds-cost","monitoring"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Two questions decide whether a database is genuinely under control: <strong>\"how do I know it is healthy?\"</strong> and <strong>\"why does it cost what it costs?\"</strong>. Engineers who can answer both are far more valuable than engineers who can only create an instance, and interviewers know it. This topic covers monitoring first, then the bill.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Part 1: Monitoring — what CloudWatch is</h4>\n<p style=\"line-height: 1.75\"><strong>Amazon CloudWatch</strong> is AWS's built-in monitoring service. It collects numeric <strong>metrics</strong> (a value measured over time, such as CPU usage), draws them as graphs, and lets you create <strong>alarms</strong> — rules that say \"if this metric crosses this threshold for this long, notify me\". RDS publishes metrics to CloudWatch automatically, at no extra charge, from the moment the instance starts. There is nothing to install.</p>\n<p style=\"line-height: 1.75\">Alarms typically send to an <strong>Amazon SNS topic</strong> (Simple Notification Service — a fan-out messaging service), which then emails you, pages you, or triggers something automatic.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The handful of metrics a beginner should actually watch</h4>\n<p style=\"line-height: 1.75\">RDS publishes dozens of metrics. font-size: 1.25rem; font-weight: 600\">Why FreeStorageSpace is the most important alarm</h4>\n<p style=\"line-height: 1.75\">Every other metric degrades performance. Running out of disk stops the database. When the storage volume fills, the engine can no longer write — the instance enters the <code>storage-full</code> state, writes fail, and the outage is total. Recovery means allocating more storage, which takes time you do not have during an incident.</p>\n<p style=\"line-height: 1.75\">Two things make this worse than beginners expect. First, storage is consumed not just by your table data but by logs, temporary files from big sorts, and transaction logs. Second, the fill can be sudden — one runaway query creating a huge temporary table can consume many gigabytes in minutes.</p>\n<p style=\"line-height: 1.75\">The defences: an alarm at roughly 20% free, and <strong>storage autoscaling</strong> (an RDS feature where you set a maximum, and RDS automatically grows the volume when free space stays low). Autoscaling is not a substitute for the alarm — it has cooldown periods and an upper bound you can still hit — but the two together make full-disk outages rare.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">DatabaseConnections and why \"too many connections\" is a classic outage</h4>\n<p style=\"line-height: 1.75\">Every database engine has a <strong>maximum number of simultaneous connections</strong> (<code>max_connections</code>). Each connection costs memory — in PostgreSQL it is a whole operating-system process. When the limit is reached, new connection attempts are <em>rejected</em>, so the application starts throwing errors even though the database itself is perfectly healthy.</p>\n<p style=\"line-height: 1.75\">This bites beginners because of how it escalates. A slow query makes requests take longer. Requests taking longer means connections are held open longer. More held-open connections means the app opens more. The limit is reached, and now everything fails, not just the slow thing.</p>\n<p style=\"line-height: 1.75\">The correct fix is almost never \"raise <code>max_connections</code>\" — more connections need more memory, and you simply trade connection errors for out-of-memory crashes. The normal fix is a <strong>connection pool</strong>: a component that keeps a small set of database connections open and lends them to requests as needed, so 500 concurrent web requests share, say, 20 connections. Every mainstream framework has one built in (HikariCP, pgbouncer, SQLAlchemy's pool). AWS also offers <strong>RDS Proxy</strong>, a managed pooler that sits between application and database and is especially valuable for serverless workloads like AWS Lambda, where thousands of short-lived function invocations would otherwise each open their own connection.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">IOPS and latency, explained simply</h4>\n<p style=\"line-height: 1.75\"><strong>IOPS</strong> means input/output operations per second — how many individual reads or writes the storage is performing. <strong>Latency</strong> is how long each one takes. Together they tell you whether the disk is the bottleneck.</p>\n<p style=\"line-height: 1.75\">The pattern to recognise: if <strong>IOPS is flat at a ceiling while latency climbs</strong>, you are saturating the storage volume. Requests are queueing. The fixes are, in order of preference: make the workload do less I/O (add an index so a query stops scanning a whole table), give the instance more memory so more data is cached in RAM, or provision faster storage.</p>\n<p style=\"line-height: 1.75\">A gp2-specific trap worth knowing: older general-purpose volumes earn <strong>burst credits</strong> that let small volumes temporarily exceed their baseline throughput. A database that was fast for weeks can suddenly turn slow when credits are exhausted, which looks mysterious until you know to look. The gp3 storage type gives a fixed baseline instead, which is one reason it is now the sensible default.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Enhanced Monitoring and Performance Insights</h4>\n<p style=\"line-height: 1.75\">Standard CloudWatch metrics come from the hypervisor — the layer outside the database instance — at one-minute granularity. Two optional features go deeper:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Enhanced Monitoring.</strong> Installs an agent on the instance to report true <em>operating-system</em> metrics — per-process CPU, memory breakdown, disk and filesystem usage — as often as every <strong>one second</strong>. Use it when a problem is too brief to show up in one-minute averages, or when you need to know which process is consuming resources. It carries a small extra cost because the data goes to CloudWatch Logs.</li>\n<li><strong>Performance Insights.</strong> A visual dashboard showing <strong>which SQL statements are consuming the most database time</strong>, broken down by what they are waiting on (CPU, disk I/O, locks). It is the fastest possible route from \"the app is slow\" to \"this specific query is the problem\", because it ranks queries by total load rather than making you read logs. It has a free tier retaining seven days of data, and it is the first tool a beginner should reach for during a slowdown.</li>\n</ul>\n<p style=\"line-height: 1.75\">The mental model: <strong>CloudWatch tells you the database is struggling. Enhanced Monitoring tells you which OS resource is exhausted. Performance Insights tells you which query is responsible.</strong></p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">\"My database feels slow\" — what to look at first</h4>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=n>1.</i> FreeStorageSpace     <i class=c>-- nearly full? Knowing them lets you predict costs and spot waste:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Instance hours.</strong> You pay per hour (billed per second, with a minimum) for the instance class while it exists and is running — <strong>whether it is busy or completely idle</strong>. This is usually the largest line, and idleness does not reduce it.</li>\n<li><strong>Storage.</strong> Charged per GB-month of storage you <strong>provisioned</strong>, not the amount you are actually using. Allocating 500 GB and storing 12 GB means paying for 500 GB. Note also that allocated storage can be increased but <strong>never decreased</strong>, so over-provisioning is a permanent cost.</li>\n<li><strong>Provisioned IOPS.</strong> If you choose the io1/io2 storage type, you pay separately for the IOPS you provision, on top of the per-GB storage charge. This can easily exceed the instance cost and should be a deliberate choice.</li>\n<li><strong>Backup storage.</strong> You get backup storage free up to <strong>100% of your provisioned database storage</strong>. Beyond that you pay per GB-month. Long retention periods and many manual snapshots push you past the free allowance.</li>\n<li><strong>Data transfer.</strong> Traffic within one Availability Zone is generally free; traffic <strong>across Availability Zones</strong> and out to the internet is charged. This is why a chatty application in one AZ talking to a database in another can generate a surprising line item.</li>\n<li><strong>Multi-AZ.</strong> Running a standby roughly <strong>doubles the instance and storage cost</strong>, because you are running a second copy. You are buying availability, and it is usually worth it in production.</li>\n<li><strong>Read replicas.</strong> Each replica is billed essentially like another instance — its own instance hours and its own storage. Three replicas means roughly four instances on the bill.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The billing gotchas that catch every beginner</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>A stopped instance still costs money.</strong> Stopping an RDS instance pauses the <em>instance hours</em>, but you continue paying for the <strong>provisioned storage</strong> and any <strong>backups</strong>. \"Stopped\" is not \"free\".</li>\n<li><strong>A stopped instance restarts itself after seven days.</strong> RDS allows a maximum of seven days stopped; after that AWS automatically starts it again so that pending maintenance can be applied. People stop a dev database on Friday, forget about it, and find it running and billing weeks later. If you genuinely do not need it, take a final snapshot and delete the instance.</li>\n<li><strong>Snapshots keep costing after the instance is deleted.</strong> Deleting an instance does not delete its manual snapshots, and a forgotten pile of them quietly accrues charges indefinitely. Audit them periodically.</li>\n<li><strong>Idle development databases are classic waste.</strong> A db.r5.xlarge left running for a proof of concept costs the same whether anyone queries it or not. Right-size non-production instances, or schedule them to stop overnight and at weekends with EventBridge Scheduler.</li>\n<li><strong>Over-provisioned storage is permanent.</strong> Because allocated storage cannot be reduced, the only way down is a snapshot-restore into a smaller instance. Start modestly and use storage autoscaling.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Reserved Instances and Savings Plans</h4>\n<p style=\"line-height: 1.75\">For a database that will run continuously for a year or more, <strong>Reserved Instances</strong> are the standard saving. You commit to a specific instance configuration for one or three years and receive a substantial discount off on-demand pricing — commonly in the range of 30% to 60% depending on term and payment option (no upfront, partial upfront, all upfront).</p>\n<p style=\"line-height: 1.75\">The trade-off is commitment: a reservation is a billing construct, not a resource, so it applies to matching usage rather than locking a particular instance, but if your usage disappears you still pay. The sensible sequence is: run on-demand, watch usage for a month or two, right-size the instance, and only then reserve the steady baseline. Reserving an oversized instance locks in the waste for a year.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">When RDS is and isn't the right choice</h4>\n<div style=\"overflow-x: auto;
