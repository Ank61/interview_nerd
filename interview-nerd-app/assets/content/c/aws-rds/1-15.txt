{"title":"RDS Security Deep Dive — IAM Authentication, Secrets Rotation, and KMS Key Strategy","tags":["security","iam-auth","secrets-manager","kms"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Securing a production RDS fleet is not one control, it is four independent planes that must all hold: <strong>who may call the RDS control plane</strong> (IAM), <strong>who may open a database session and how they prove it</strong> (IAM database authentication or Secrets Manager credentials), <strong>what protects the bytes at rest</strong> (KMS), and <strong>what protects the bytes on the wire</strong> (TLS plus certificate validation). Senior interviews probe the seams between these planes — the places where a control that looks enabled is actually bypassable, or where a key policy silently becomes the single point of failure for an entire database.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">IAM Database Authentication: mechanism, not magic</h4>\n<p style=\"line-height: 1.75\">IAM database authentication replaces a stored password with a <strong>short-lived, signed token</strong>. You enable it on the instance or cluster (<code>--enable-iam-database-authentication</code>), create a database user that delegates authentication to AWS, and then grant an IAM principal the <code>rds-db:connect</code> action on a resource ARN of the form <code>arn:aws:rds-db:region:account-id:dbuser:db-XYZRESOURCEID/db_user_name</code>. Note the resource id in that ARN is the <strong>DbiResourceId</strong>, not the instance identifier — it is immutable across renames and is the reason a policy keeps working when someone renames the instance.</p>\n<p style=\"line-height: 1.75\">The token itself is a <strong>SigV4-presigned request string</strong> generated entirely client-side — <code>aws rds generate-db-auth-token</code> or the SDK equivalent makes no network call to RDS. It is valid for <strong>15 minutes</strong>. The critical nuance interviewers look for: the 15 minutes bounds when you may <em>open</em> the connection, not how long the session may live. An established session persists until it is closed or the server terminates it, even hours later. That property is what makes IAM auth workable for long-lived pooled connections and completely unworkable as a per-request credential.</p>\n<p style=\"line-height: 1.75\">Engine support is <strong>MySQL, MariaDB and PostgreSQL</strong> on RDS, plus Aurora MySQL and Aurora PostgreSQL. It does not exist for Oracle, SQL Server or Db2. The user setup differs per engine: MySQL/MariaDB use <code>CREATE USER app_ro IDENTIFIED WITH AWSAuthenticationPlugin AS 'RDS';</code>, while PostgreSQL uses a normal role granted the built-in <code>rds_iam</code> role. Once <code>rds_iam</code> is granted to a PostgreSQL role, that role can <strong>only</strong> authenticate via IAM — password login is disabled for it, which is a nice hard guarantee but also a foot-gun during migration.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The connection-rate limitation</h4>\n<p style=\"line-height: 1.75\">Every IAM-authenticated connection performs a signature verification on the database host. AWS documents a practical ceiling of roughly <strong>200 new connections per second</strong> for RDS MySQL, and while PostgreSQL has no single published number, the same CPU cost applies and shows up as authentication latency and elevated CPU under churn. This is the single most important operational limit to state in an interview: IAM auth is not a drop-in replacement for a password in an application that opens a fresh connection per HTTP request. A PHP-style or Lambda-style workload with high connection churn will burn CPU on authentication and eventually see connection failures.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Where IAM auth genuinely shines.</strong> Human and CI access. Engineers and pipelines connect a handful of times per session, and you eliminate a stored password entirely — access is granted and revoked by editing an IAM policy, audited in CloudTrail (the STS calls) and expires automatically.</li>\n<li><strong>Where it shines for applications.</strong> Behind <strong>RDS Proxy</strong>. The application authenticates to the Proxy with IAM, the Proxy authenticates to the database with a Secrets Manager secret over a small, warm, multiplexed pool. Connection churn is absorbed by the Proxy, so the 200/second ceiling stops being a constraint and the application still stores no password.</li>\n<li><strong>Where it does not fit.</strong> Direct high-churn application connections, engines without support, and anything needing password-based tooling that cannot be taught to refresh a token.</li>\n<li><strong>Hard requirement.</strong> IAM-authenticated connections must use TLS. A driver configured with SSL disabled will fail, which is a feature, not a bug.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Secrets Manager rotation done properly</h4>\n<p style=\"line-height: 1.75\">Secrets Manager stores the credential and, more importantly, <strong>rotates</strong> it. Rotation is executed by a Lambda function that Secrets Manager invokes with four discrete steps against a staged version of the secret:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>createSecret.</strong> Generate a new password and store it as a new version labelled <code>AWSPENDING</code>.</li>\n<li><strong>setSecret.</strong> Apply the new password inside the database engine.</li>\n<li><strong>testSecret.</strong> Open a real connection with the pending credential and run a trivial query.</li>\n<li><strong>finishSecret.</strong> Move the <code>AWSCURRENT</code> label to the pending version; the previous version becomes <code>AWSPREVIOUS</code>.</li>\n</ul>\n<p style=\"line-height: 1.75\">The strategy choice is the interview question. <strong>Single-user rotation</strong> changes the password of the one user the application uses. Between <em>setSecret</em> and the moment every application instance has re-read the secret, any client still holding the old password will fail to open new connections. Existing connections survive, so short-lived outages hide behind a warm pool — until a scale-out event or a pool refresh lands in the window. <strong>Alternating-users rotation</strong> creates a clone user (typically <code>myapp</code> and <code>myapp_clone</code>) and alternates between them. At any instant, <strong>both the current and the previous credential are valid</strong>, so the window where an application holds a now-invalid password does not exist. The cost is that rotation needs superuser-equivalent credentials to manage two users and that you must keep grants identical on both users — a classic production bug is the clone missing a grant added later only to the primary user.</p>\n<p style=\"line-height: 1.75\"><strong>Caching is mandatory at scale.</strong> Calling <code>GetSecretValue</code> on every connection adds latency, costs money per 10,000 API calls, and will eventually hit the Secrets Manager request rate limit during a thundering-herd restart. Use the AWS Secrets Manager caching libraries (Java, Python, .NET, Go) or the Secrets Manager Lambda extension, with a refresh interval well under the rotation interval, and — critically — <strong>invalidate the cache and re-fetch on an authentication error</strong> rather than only on a timer. That retry-on-auth-failure path is what makes single-user rotation survivable at all.</p>\n<p style=\"line-height: 1.75\"><strong>Cross-account access</strong> requires two things people forget: a <strong>resource policy on the secret</strong> granting the external account <code>secretsmanager:GetSecretValue</code>, and encryption of the secret with a <strong>customer managed KMS key</strong> whose key policy also grants that account <code>kms:Decrypt</code>. The AWS managed key <code>aws/secretsmanager</code> cannot be shared cross-account, so a secret encrypted with it can never be read from another account, no matter how permissive the resource policy is.</p>\n<h4 style=\"margin-top: 1.5rem; The two decisive capabilities are cross-account snapshot sharing — a snapshot encrypted with the AWS managed key simply <strong>cannot be shared</strong>, and the only workaround is to copy the snapshot onto a CMK first — and revocability, because access to ciphertext is meaningless if the key is disabled.</p>\n<p style=\"line-height: 1.75\"><strong>Key policies versus IAM policies.</strong> A KMS key policy is the root of authority for that key: unlike S3 or most services, an IAM policy granting <code>kms:Decrypt</code> is ineffective unless the key policy delegates to IAM (the common <code>kms:CallerAccount</code>-style statement that allows the account root, thereby letting IAM policies take effect). Interviewers love asking why a user with <code>kms:*</code> in IAM still gets AccessDenied — the answer is a key policy that never delegated to the account.</p>\n<p style=\"line-height: 1.75\"><strong>The operational consequence of losing a key is severe.</strong> Disable the key or schedule its deletion, and RDS moves the instance to the <code>inaccessible-encryption-credentials</code> state. The database stops serving traffic; if the key remains unavailable the instance can progress to a terminal state from which the data is unrecoverable. Snapshots encrypted with that key are equally unrestorable. Practical controls: put deletion protection thinking around the key too — use a long <strong>pending deletion window</strong> (7 to 30 days), alarm on CloudTrail <code>DisableKey</code> and <code>ScheduleKeyDeletion</code> events, and never let a single key cover both production and its own backups if your threat model includes an insider.</p>\n<p style=\"line-height: 1.75\"><strong>Encryption at rest is immutable after creation.</strong> You cannot encrypt an existing unencrypted instance in place, and you cannot decrypt an encrypted one. The workaround is the snapshot-copy path: snapshot the unencrypted instance, <code>copy-db-snapshot</code> with <code>--kms-key-id</code>, restore from the encrypted copy, then cut over. That means a real migration window and a replication catch-up plan (for example DMS or logical replication) if you cannot afford the downtime of a plain snapshot restore. Re-keying to a different CMK uses the same snapshot-copy mechanism.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Enforcing TLS in transit</h4>\n<p style=\"line-height: 1.75\">RDS supports TLS by default, but supporting it is not requiring it. Enforcement is a parameter-group change, and it differs per engine:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>PostgreSQL.</strong> Set <code>rds.force_ssl = 1</code>. On PostgreSQL 15 and later this parameter is dynamic; on earlier versions it is static and requires a reboot.</li>\n<li><strong>MySQL and MariaDB.</strong> Set <code>require_secure_transport = ON</code> (dynamic). You can additionally pin per-user with <code>ALTER USER ... REQUIRE SSL</code> or <code>REQUIRE X509</code>.</li>\n<li><strong>SQL Server.</strong> Set <code>rds.force_ssl</code> in the parameter group; Oracle uses the <code>SSL</code> option in an option group with a dedicated encrypted port.</li>\n<li><strong>Aurora.</strong> Same parameters, but applied at the <em>cluster</em> parameter group level, not the instance level — a frequent cause of \"I set it and nothing happened\".</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>Certificate authority rotation is a recurring operational task that has caused real outages.</strong> The <code>rds-ca-2019</code> bundle expired in August 2024 and the industry-wide scramble to move clients onto <code>rds-ca-rsa2048-g1</code> (valid into 2061) broke applications that had pinned the old CA or had it baked into a container image. The lesson to state in an interview: the server-side change is one API call — <code>modify-db-instance --ca-certificate-identifier rds-ca-rsa2048-g1</code>, applied on reboot or in the maintenance window — but the <strong>client-side truststore update must land first</strong>. Use the <strong>global certificate bundle</strong> rather than a per-Region PEM so a Region-scoped rotation does not require a code change, and ship the bundle as a versioned artifact, not a file someone curled onto a host in 2019.</p>\n<p style=\"line-height: 1.75\"><strong>Validation matters more than encryption.</strong> A driver configured with <code>sslmode=require</code> (PostgreSQL) or <code>--ssl-mode=REQUIRED</code> (MySQL) encrypts the channel but does not verify the server, leaving you open to an in-path attacker. The correct settings are <code>sslmode=verify-full</code> with <code>sslrootcert</code> pointing at the RDS bundle, and <code>--ssl-mode=VERIFY_IDENTITY</code> with <code>--ssl-ca</code>. Applications that use RDS Proxy must validate against the same bundle — the Proxy presents an ACM-issued certificate for its own endpoint.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Least privilege inside the database</h4>\n<p style=\"line-height: 1.75\">Cloud IAM stops at the connection. Inside the database, the failure mode is a single application role that owns every object and can therefore drop every object. The pattern that survives review:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Separate the owner from the runtime user.</strong> A migration/DDL role owns the schema and is used only by the migration pipeline. The application role has <code>SELECT, INSERT, UPDATE, DELETE</code> and nothing else — no <code>CREATE</code>, no <code>DROP</code>, no ownership.</li>\n<li><strong>Separate read from write.</strong> A dedicated read-only role for reporting, BI tools and the replica endpoint. Reporting tools are the most commonly over-privileged clients in any estate.</li>\n<li><strong>Use default privileges, not one-time grants.</strong> In PostgreSQL, <code>ALTER DEFAULT PRIVILEGES FOR ROLE ddl_owner IN SCHEMA app GRANT SELECT ON TABLES TO app_ro;</code> so tomorrow's table is covered automatically. Also <code>REVOKE CREATE ON SCHEMA public FROM PUBLIC</code> on versions before 15, where it is not revoked by default.</li>\n<li><strong>Remember the RDS master user is not a superuser.</strong> It holds <code>rds_superuser</code> (PostgreSQL) or a broad but bounded grant set (MySQL). Do not design around true superuser behaviour, and do not use the master user as the application identity.</li>\n<li><strong>Row-level security</strong> in PostgreSQL for genuine multi-tenant isolation, understanding it is enforced per role and that a role with <code>BYPASSRLS</code> or table ownership sidesteps it.</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>Network controls are defense in depth, not the primary control.</strong> Private subnets with no route to an internet gateway, <code>PubliclyAccessible=false</code>, a security group whose source is the <em>application security group id</em> rather than a CIDR, and VPC endpoints so Secrets Manager and KMS traffic never leaves the VPC.
