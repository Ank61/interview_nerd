{"title":"RDS Database Engines — MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, and Aurora","tags":["aws","rds","database engines","aurora"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Amazon RDS is not a database. It is a <strong>service that runs databases for you</strong>, and it supports several different ones. The specific database software is called the <strong>engine</strong> — it is the program that actually stores your rows and executes your SQL. When you create an RDS database, one of the very first choices is which engine to use, and that single dropdown shapes your SQL dialect, your available features, your licensing bill, and how painful it will be to move later.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Engines RDS Offers</h4>\n<p style=\"line-height: 1.75\">There are six choices, and they fall into three natural groups: the two big open-source engines, the two commercial enterprise engines, and Amazon's own engine.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>MySQL.</strong> The classic open-source database of the web era. Enormously widely deployed, simple to learn, and supported by essentially every framework, ORM, hosting provider, and tutorial you will ever read. If you have ever installed WordPress, you have used MySQL.</li>\n<li><strong>MariaDB.</strong> A community-driven fork of MySQL, created after MySQL was acquired by Oracle. Very close to MySQL in behavior and largely drop-in compatible, with its own set of added features and storage engines. Teams choose it for governance reasons or for specific MariaDB features.</li>\n<li><strong>PostgreSQL.</strong> The other giant of open source, and the default choice for a great many new projects today. Known for strong standards compliance, a rich type system (native JSON, arrays, ranges), sophisticated indexing, and a deep <strong>extension</strong> ecosystem — extensions are optional add-on modules that teach PostgreSQL new tricks, such as <strong>PostGIS</strong> for storing and querying geographic data like map coordinates and shapes.</li>\n<li><strong>Oracle Database.</strong> A long-established commercial engine, very common inside large enterprises with decades-old systems built on it. Feature-dense, and carries commercial licensing costs.</li>\n<li><strong>Microsoft SQL Server.</strong> The other major commercial engine, especially common in organizations built on the Microsoft stack (.NET applications, Windows servers, Active Directory). Also commercially licensed, and sold in editions — Express, Web, Standard, Enterprise — with different capability and price levels.</li>\n<li><strong>Amazon Aurora.</strong> An engine AWS built itself, which speaks MySQL and PostgreSQL but is internally rearchitected. More on this below, because it deserves its own explanation.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Open Source vs Commercial: The Licensing Idea</h4>\n<p style=\"line-height: 1.75\">MySQL, MariaDB, and PostgreSQL are free software. You pay AWS for the server and storage, and nothing for the database software itself. Oracle and SQL Server are commercial products whose vendors charge for the right to run them, and that charge is often substantial — sometimes larger than the infrastructure cost.</p>\n<p style=\"line-height: 1.75\">RDS gives you two ways to handle that, and beginners should know both terms:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>License Included (LI).</strong> AWS has already bought the license and bundles its cost into your hourly RDS price. You do not talk to Oracle or Microsoft at all. This is the simple path: one bill, no procurement, and you can start in minutes.</li>\n<li><strong>Bring Your Own License (BYOL).</strong> You already own licenses — typically because your company negotiated an enterprise agreement years ago — and you apply them to your RDS instances. You pay AWS only for infrastructure, and you remain responsible for staying compliant with the vendor's licensing terms.</li>\n</ul>\n<p style=\"line-height: 1.75\">A plain-English rule of thumb: <strong>if you are starting something new and have no existing licenses, License Included is almost always the right answer for a commercial engine — and for most new projects, an open-source engine is a better answer still.</strong> Note that the specific BYOL and License Included options available differ by engine and edition (for example, SQL Server on RDS is License Included), so always check current AWS documentation rather than assuming.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Amazon Aurora — Related, But Its Own Thing</h4>\n<p style=\"line-height: 1.75\"><strong>Amazon Aurora</strong> is a database engine AWS designed and built. Its headline feature is <strong>compatibility</strong>: Aurora MySQL accepts MySQL clients and SQL, and Aurora PostgreSQL accepts PostgreSQL clients and SQL. Your application driver, your ORM, and most of your queries generally work unchanged.</p>\n<p style=\"line-height: 1.75\">What is different is underneath. A normal RDS instance writes to a disk volume attached to its own server, the way a database on your laptop writes to your laptop's drive. Aurora instead separates the database compute from a purpose-built <strong>distributed storage layer</strong> — a storage service spread across multiple physically separate data centers, which AWS calls <strong>Availability Zones</strong>, that keeps six copies of your data and is shared by all the database instances in your Aurora cluster. That design is what gives Aurora its performance characteristics, its fast replica creation, and its self-healing storage.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">Standard RDS (e.g. RDS PostgreSQL)      Amazon Aurora\n<i class=c>------------------------------------    ------------------------------------</i>\n[ DB instance ]                         [ writer ]  [ reader ]  [ reader ]\n      <i class=o>|</i>                                      \\         <i class=o>|</i>         <i class=o>/</i>\n [ its own EBS volume ]                    [ shared distributed storage ]\n                                           ( <i class=n>6</i> copies across <i class=n>3</i> AZs )</code></pre></div>\n<p style=\"line-height: 1.75\">For interview purposes at the beginner level, the thing to say is this: <strong>Aurora is offered through RDS and managed the same way, but it is a distinct engine with a different storage architecture, and the details are advanced material.</strong> You should know it exists, know it is MySQL- and PostgreSQL-compatible, and know that it is AWS-built and AWS-only — you cannot download Aurora and run it on your laptop, which is a genuine lock-in consideration. font-size: 1.25rem; font-weight: 600\">Why the Choice Matters More Than It Looks</h4>\n<p style=\"line-height: 1.75\">It is tempting to treat the engine dropdown as a preference. It is not — it is an architectural commitment, for four reasons:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>SQL dialect.</strong> \"SQL\" is a standard the way English is a language: everyone agrees on the core and disagrees on everything else. Auto-incrementing keys, string functions, date handling, upserts, and JSON operators all differ between engines. Real applications accumulate engine-specific SQL quickly.</li>\n<li><strong>Features and extensions.</strong> PostgreSQL's extension ecosystem, SQL Server's T-SQL stored procedures, and Oracle's PL/SQL packages are not portable. If you build on them, you have built on that engine.</li>\n<li><strong>Cost.</strong> A commercial engine can multiply your database bill. That difference compounds across every environment — production, staging, development, and every test copy.</li>\n<li><strong>Operational familiarity.</strong> Your team's ability to read an execution plan, tune a parameter, or debug a lock at 2am is engine-specific knowledge. It does not transfer for free.</li>\n</ul>\n<p style=\"line-height: 1.75\">Changing engines later is a <strong>migration project</strong>, not a setting change. You cannot flip an existing RDS MySQL instance to PostgreSQL. You provision a new database, convert the schema, rewrite the engine-specific SQL and stored procedures, move the data, test everything, and cut over — typically with a tool such as the <strong>AWS Schema Conversion Tool</strong> to translate schema and code and <strong>AWS Database Migration Service (DMS)</strong> to copy the data with minimal downtime.
