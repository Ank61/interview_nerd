{"title":"Troubleshooting Production SNS — A Symptom-Driven Playbook","tags":["troubleshooting","incident-response","debugging","runbook"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">SNS incidents have a distinctive character: the service itself is almost never the problem. In practice, essentially every SNS incident resolves to one of five root causes — <strong>a permission, a filter, a confirmation, a protocol semantic, or a consumer-side failure that SNS cannot see</strong>. Knowing that up front changes how you triage, because it means \"is SNS down\" is rarely the right first question and \"what changed about this subscription\" almost always is. This playbook is organized by symptom, because that is how incidents actually arrive: someone says \"we stopped getting events\" and you need a decision tree, not a feature tour. For each symptom, the goal is to name the <em>first thing to look at</em> — the single check that splits the hypothesis space fastest.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">General triage ordering</h4>\n<p style=\"line-height: 1.75\">Before diving into any specific symptom, run this sequence. It takes two minutes and eliminates most of the search space.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>1. Is the input healthy?</strong> <code>NumberOfMessagesPublished</code> on the topic. If it collapsed, stop — this is a publisher incident and nothing about subscriptions matters.</li>\n<li><strong>2. Is it one subscriber or all of them?</strong> Compute the fan-out ratio, delivered over published. One subscriber affected means configuration on that subscription; all subscribers affected means the topic, the publisher, or encryption.</li>\n<li><strong>3. Is SNS failing or not attempting?</strong> <code>NumberOfNotificationsFailed</code> non-zero means SNS tried and could not deliver (delivery-side: endpoint, permissions, TLS). Zero means SNS is not attempting at all (filtering, confirmation state, or the message never matched).</li>\n<li><strong>4. What changed?</strong> CloudTrail for <code>SetSubscriptionAttributes</code>, <code>SetTopicAttributes</code>, <code>Subscribe</code>, <code>Unsubscribe</code>, plus deployment history for the publisher and the consumer. The overwhelming majority of SNS incidents are change-induced, and the change is usually not in SNS.</li>\n<li><strong>5. Read the delivery status logs.</strong> If enabled, the failure log group answers most delivery questions outright via <code>providerResponse</code>. If not enabled, enable it now so the next occurrence is diagnosable — and note the gap: <strong>email and email-json have no delivery status logging</strong>.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 1 — A subscriber receives nothing, ever</h4>\n<p style=\"line-height: 1.75\"><strong>First thing to look at:</strong> the subscription ARN itself. Call <code>ListSubscriptionsByTopic</code>; if the <code>SubscriptionArn</code> reads literally <code>PendingConfirmation</code>, you are done — nothing was ever delivered and nothing ever will be. This is the number one cause of \"it never worked\", as distinct from \"it stopped working\".</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>PendingConfirmation.</strong> For HTTP/S and email, the endpoint must confirm. SNS sends a <code>SubscriptionConfirmation</code> message containing a <code>SubscribeURL</code> that must be visited (or the token passed to <code>ConfirmSubscription</code>) within the confirmation window. Common causes: the HTTP endpoint 200s the confirmation request but never acts on it because the handler only parses <code>Notification</code> type messages; the email went to spam; or the endpoint was not deployed when the subscription was created. SQS and Lambda subscriptions do not need confirmation and are active immediately, which is one reason they are more reliable.</li>\n<li><strong>Filter policy excluding everything.</strong> Read <code>FilterPolicy</code> and <code>FilterPolicyScope</code> from <code>GetSubscriptionAttributes</code>. Matching is <strong>exact and case-sensitive</strong>, types must match (a numeric matcher against a value published as a string will not match), and a policy with an attribute name the publisher never sets excludes everything. Confirm with <code>NumberOfNotificationsFilteredOut</code>.</li>\n<li><strong>Missing target resource policy.</strong> For SQS, the <em>queue policy</em> must allow <code>sqs:SendMessage</code> from <code>principal Service: sns.amazonaws.com</code> with a <code>aws:SourceArn</code> condition matching the topic. For Lambda, there must be a resource-based policy statement allowing <code>lambda:InvokeFunction</code> from <code>sns.amazonaws.com</code>. Console-created subscriptions add these automatically; hand-written IaC frequently forgets, and the symptom is silent non-delivery.</li>\n<li><strong>Wrong topic ARN.</strong> Right topic name, wrong Region or wrong account. Embarrassingly common in multi-Region deployments and instantly confirmed by comparing the ARN the publisher uses against the topic's actual ARN.</li>\n<li><strong>KMS permissions.</strong> If the <em>topic</em> uses a customer managed key, publishers need <code>kms:GenerateDataKey</code> and <code>kms:Decrypt</code>. If the <em>target queue</em> is encrypted with a CMK, the key policy must allow the SNS service principal to use it, or delivery fails. Encrypted-queue KMS policy is one of the most common causes of a subscription that is correctly configured in every visible way and still delivers nothing.</li>\n<li><strong>Endpoint rejecting confirmation.</strong> The endpoint returns non-2xx to the confirmation POST, is behind a WAF blocking the SNS user agent, or requires authentication SNS cannot provide.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 2 — Some messages arrive, others silently do not</h4>\n<p style=\"line-height: 1.75\"><strong>First thing to look at:</strong> the filtered-out metric family, split by variant. Partial delivery is nearly always filtering, because failures produce failure metrics and filtering produces silence.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Filter policy edge cases.</strong> String matching is exact and case-sensitive; <code>anything-but</code> and <code>exists</code> have subtle semantics; a key present in the policy but absent from the message does not match unless expressed with <code>exists: false</code>; numeric matchers require the attribute to be published with numeric type. Policies combine keys with AND and values within a key with OR, which people routinely invert in their heads.</li>\n<li><strong>A publisher stopped setting an attribute.</strong> Watch <code>NumberOfNotificationsFilteredOut-NoMessageAttributes</code>: a spike means a code path is publishing without attributes. <code>-InvalidAttributes</code> means attributes exist but are malformed or wrongly typed. For payload-scope policies, <code>-NoMessageBody</code> and <code>-InvalidMessageBody</code> mean the body was absent or not parseable JSON.</li>\n<li><strong>FIFO deduplication discarding a re-publish.</strong> On a FIFO topic, a message with the same <code>MessageDeduplicationId</code> (or the same content, under content-based deduplication) published within the <strong>5-minute deduplication window</strong> is accepted and acknowledged with a MessageId, then silently discarded. This produces the maddening pattern of a successful publish with no delivery, and it bites hardest on legitimate retries and on replaying identical events. The fix is an explicit deduplication id derived from a genuine business identity, not from content.</li>\n<li><strong>Throttling.</strong> Publish throttling surfaces as errors at the publisher, not as missing deliveries — but a publisher whose SDK swallows <code>Throttling</code> errors will look like intermittent message loss. Check publisher error logs and SDK retry configuration.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 3 — Duplicate messages</h4>\n<p style=\"line-height: 1.75\"><strong>First thing to look at:</strong> whether the duplicates share the same SNS <code>MessageId</code>. Same MessageId means redelivery; different MessageIds mean the publisher published twice, which is a completely different bug.</p>\n<p style=\"line-height: 1.75\">Standard SNS topics are <strong>at-least-once</strong> by design. Duplicates are not a malfunction and cannot be configured away. They arise when a delivery succeeds at the endpoint but the acknowledgement is lost, so SNS retries; when a slow endpoint exceeds the delivery timeout, processes the request anyway, and SNS retries; or when an SQS consumer's visibility timeout expires mid-processing so the same message is received again. FIFO topics offer deduplication, but only <strong>within a 5-minute window</strong> — they are not a substitute for idempotency across longer horizons. The only correct answer is <strong>consumer-side idempotency</strong>: a deterministic idempotency key from the event id in the envelope (never from a receive timestamp or an auto-generated id), a conditional write to a store keyed on it, and idempotent side effects. Payment and email side effects require particular care, since \"already processed\" must be distinguishable from \"in progress\".</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 4 — HTTP/S delivery failures</h4>\n<p style=\"line-height: 1.75\"><strong>First thing to look at:</strong> the delivery status <code>Failure</code> log group, filtered to <code>status = FAILURE</code>, reading <code>delivery.statusCode</code> and <code>delivery.providerResponse</code>. The endpoint's own words are usually the whole answer.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Non-2xx responses.</strong> SNS considers only 2xx a success. A 3xx redirect is a failure — SNS does not follow redirects. A 401 or 403 means the endpoint expects authentication. A 400 usually means the endpoint cannot parse the SNS envelope, often because the subscription has <code>RawMessageDelivery</code> set differently from what the handler expects.</li>\n<li><strong>Timeouts.</strong> SNS has a bounded delivery timeout; an endpoint that does synchronous work before responding will time out under load. The fix is to acknowledge immediately and process asynchronously — or better, put SQS in front.</li>\n<li><strong>TLS and certificate problems.</strong> Expired certificates, missing intermediate chain (works in a browser, fails from SNS), hostname mismatch, or an unsupported protocol version. <code>providerResponse</code> usually names it explicitly.</li>\n<li><strong>Delivery policy exhausted.</strong> The retry policy defines immediate, pre-backoff, backoff and post-backoff phases; once attempts are exhausted the message is dropped unless a redrive policy sends it to a DLQ. Check <code>delivery.attempts</code> in the logs to distinguish flaky from hard-down, and raise retries and total retry duration for endpoints with known maintenance windows.</li>\n<li><strong>Firewall or WAF.</strong> A WAF rule or IP allowlist blocking SNS. SNS publishes its IP ranges via the AWS IP address ranges document, but allowlisting is fragile — prefer verifying message signatures over IP-based trust.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 5 — Lambda subscriber \"loses\" events</h4>\n<p style=\"line-height: 1.75\"><strong>First thing to look at:</strong> Lambda's own <code>Errors</code> and <code>Throttles</code> metrics, not SNS metrics. This is the single most misunderstood interaction in SNS.</p>\n<p style=\"line-height: 1.75\">SNS invokes Lambda <strong>asynchronously</strong>. The moment Lambda accepts the invocation, SNS records the delivery as successful and its responsibility ends. Everything that happens afterwards — the function throwing, timing out, being throttled, running out of memory — is invisible to SNS. Consequently <code>NumberOfNotificationsFailed</code> stays at zero and any <strong>SNS subscription DLQ will never receive these messages</strong>, because from SNS's point of view nothing failed. Lambda applies its own async retry behaviour (by default two retries, with configurable maximum retry attempts and event age), and after that the event is discarded unless you configured somewhere for it to go.</p>\n<p style=\"line-height: 1.75\">The correct construct is a <strong>Lambda on-failure destination</strong> (or Lambda's own async DLQ) on the function's event invoke configuration, pointing at an SQS queue or another topic. That captures the failure with its context after Lambda's retries are exhausted. The interview-grade summary: <strong>an SNS DLQ protects against SNS failing to deliver; a Lambda on-failure destination protects against the function failing to process. They cover disjoint failure domains and a serious system has both.</strong> Also check <code>Throttles</code>: an unreserved-concurrency function competing with the rest of the account can be throttled, and Lambda will retry async invocations for a bounded period before giving up.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 6 — Ordering problems</h4>\n<p style=\"line-height: 1.75\"><strong>First thing to look at:</strong> whether the topic is actually FIFO, and then whether every hop in the chain preserves order.</p>\n<p style=\"line-height: 1.75\">Standard topics make <strong>no ordering guarantee whatsoever</strong> — none, not even usually. If a system depends on order and uses a standard topic, the design is wrong regardless of how often it appears to work. FIFO topics provide ordering within a <code>MessageGroupId</code>, but the guarantee is only as strong as the weakest link in the chain. It breaks if a FIFO topic delivers to a <strong>standard queue</strong> (a FIFO topic can only deliver to FIFO queues for ordered delivery); if multiple consumers process the same message group in parallel; if a consumer uses multiple threads per group; or if a failed message is retried while later messages in the group proceed. Note also that <strong>ordering is per group, not global</strong>: choosing a group id with too little cardinality serializes everything and destroys throughput, while too much cardinality means the things you needed ordered end up in different groups. The right group id is the entity whose state transitions must be sequential — typically an aggregate id like order id or account id.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Symptom 7 — SMS not delivered</h4>\n<p style=\"line-height: 1.75\"><strong>First thing to look at:</strong> <code>SMSMonthToDateSpentUSD</code> against the account spend limit. SNS <strong>automatically disables an endpoint</strong> when the push provider reports the token as invalid, and publishes to a disabled endpoint fail. This is normal lifecycle, not a bug — tokens rotate when apps are reinstalled or devices change — and your app must re-register and update the endpoint via <code>SetEndpointAttributes</code>, re-enabling it. Other causes: <strong>expired platform credentials</strong> on the platform application (APNs certificate expiry is the classic, since it fails for every device at once on a known date — set a calendar alarm); a <strong>malformed platform payload</strong>, since publishing to a platform endpoint requires a JSON message with <code>MessageStructure</code> set to <code>json</code> and a correctly shaped per-platform key such as <code>APNS</code>, <code>APNS_SANDBOX</code> or <code>GCM</code>; and <strong>using the sandbox platform against production tokens</strong> or vice versa, which fails uniformly.
