{"title":"Advanced Message Filtering — Policy Design at Scale","tags":["filter-policy","message-body-filtering","routing-contract","cost-optimization"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Filtering is usually taught as a convenience — \"so Lambda does not get messages it does not care about\". At scale it is an architectural control. A filter policy is evaluated inside SNS before any delivery happens, which means a non-matching message costs you no delivery, no downstream invocation, no queue traffic, and no compute. In a fan-out topic carrying every event in a domain, the filter policy <em>is</em> the routing layer, and the set of attributes it reads is a public contract between one publisher and many independently owned subscribers. Designing that contract badly produces the most insidious failure mode in SNS: everything reports healthy, publishes succeed, and one subscriber's traffic silently drops to zero.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Operator Set, Precisely</h4>\n<p style=\"line-height: 1.75\">A filter policy is a JSON object whose keys are attribute names and whose values are arrays of match conditions. Before it existed, \"deliver if the event is a refund <em>or</em> the amount exceeds ten thousand\" required two subscriptions because separate keys always AND. Now it is one policy. It composes with the normal rules: within each branch of the disjunction, the usual AND-across-attributes and OR-across-values semantics apply.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Filter Scope: MessageAttributes vs MessageBody</h4>\n<p style=\"line-height: 1.75\">Every subscription has a <code>FilterPolicyScope</code> attribute. The default is <code>MessageAttributes</code> — the policy is evaluated against the SNS message attribute map, which is metadata attached alongside the payload. Set it to <code>MessageBody</code> and the policy is evaluated against the JSON body of the message itself, with <strong>nested object matching</strong>: the policy mirrors the shape of the payload, so <code>{\"order\": {\"tenant\": {\"tier\": [\"enterprise\"]}}}</code> matches a body with that nested path. Arrays in the body match if any element matches.</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; My default for a widely shared platform topic is attributes for the routing contract, with body filtering reserved for one-off refinements a subscriber needs on data that genuinely should not be lifted into attributes.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Policy Design Patterns at Scale</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>A small, stable attribute set as the routing contract.</strong> Typically <code>eventType</code> (dotted namespace, e.g. <code>order.shipped</code>), plus one or two partitioning dimensions such as <code>tenantId</code>, <code>region</code>, <code>tier</code> or <code>env</code>. Publishers set these on every message, unconditionally. Everything else lives in the body.</li>\n<li><strong>Namespaced event types with prefix matching.</strong> A subscriber wanting all order events uses <code>{\"prefix\": \"order.\"}</code> and automatically receives new event types as they are added — the right default for a team that wants breadth. A subscriber that must opt in explicitly lists exact values. Offering both postures, and documenting which each subscription has chosen, is the point.</li>\n<li><strong>Versioning the contract.</strong> Add a <code>schemaVersion</code> attribute and treat attribute removals or renames as breaking changes. The safe migration is <strong>expand then contract</strong>: publish the new attribute alongside the old one, give subscribers a deprecation window to widen their policies (often with <code>&#36;or</code> or a list covering both values), verify per-subscription delivery metrics for every subscriber, and only then stop emitting the old attribute.</li>\n<li><strong>Documented, self-service contract.</strong> The allowed values of <code>eventType</code>, the meaning of each attribute, and the types (String vs Number) should live in a schema registry or a README next to the publisher, so a subscription owner can write and validate their own policy without asking the publishing team. Filtering only scales as an architectural tool if subscribers can self-serve.</li>\n<li><strong>Deny-style policies with anything-but.</strong> For a partner or public feed, an allow-list of event types is safer, but <code>{\"anything-but\": {\"prefix\": \"internal.\"}}</code> is a pragmatic guard that keeps internal events out of an external subscription even when new ones are added.</li>\n<li><strong>Avoid combinatorial explosions.</strong> Policies have documented limits on total size, nesting depth, number of attribute names, and the number of value <em>combinations</em> the policy expands to. A policy that cross-products five attributes with ten values each will hit the combination cap. Split into multiple subscriptions, or move a dimension into the topic structure.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Cost and Load Argument</h4>\n<p style=\"line-height: 1.75\">This is usually the strongest lever in a fan-out architecture and candidates routinely undersell it. Every subscription whose policy references it stops matching. Publishes succeed, no failure metric moves, no DLQ fills, no exception is thrown. The <em>only</em> signals are <code>NumberOfNotificationsDelivered</code> for that subscription falling to zero and <code>NumberOfNotificationsFilteredOut</code> rising. SNS also emits the more specific <code>NumberOfNotificationsFilteredOut-NoMessageAttributes</code> and <code>NumberOfNotificationsFilteredOut-InvalidAttributes</code> metrics, which distinguish \"the publisher sent nothing\" from \"the publisher sent something unusable\".</li>\n<li><strong>Case sensitivity.</strong> Plain string matching is exact and case-sensitive: <code>\"Acme\"</code> does not match <code>\"acme\"</code>. Either normalise at the publisher or use <code>equals-ignore-case</code>. Do not rely on convention.</li>\n<li><strong>Type mismatch.</strong> A numeric operator only matches an attribute published with <code>DataType: Number</code>. Publishing <code>149.95</code> as a String and filtering with a <code>numeric</code> condition matches nothing, forever, with no error. The mirror case bites too: a string policy will not match a Number attribute. This is the second most common silent-drop cause after the missing attribute.</li>\n<li><strong>Absent-attribute semantics.</strong> <code>anything-but</code> still requires the attribute to be present. If you want \"anything except X, including messages with no such attribute\", you need <code>&#36;or</code> combining the <code>anything-but</code> branch with an <code>{\"exists\": false}</code> branch.</li>\n<li><strong>Policy limits.</strong> Exceeding the documented caps on size, nesting depth, attribute count or total value combinations causes the <code>SetSubscriptionAttributes</code> call to be rejected — which is the good outcome, because it fails loudly at deploy time rather than silently at runtime.</li>\n<li><strong>Cutover is not instantaneous.</strong> Changing a filter policy takes effect for subsequent publishes; messages already accepted and in flight were evaluated under the old policy. During a migration, expect a brief overlap rather than a clean boundary.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Testing and Validating Policies Before Deployment</h4>\n<p style=\"line-height: 1.75\">Treat a filter policy as code, because it is a routing rule that can silently disable a production integration. A practical pipeline:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Unit-test the policy semantics.</strong> Keep a corpus of representative messages (attributes plus body) per event type in the repo and assert which subscriptions should match. An SNS filter policy is EventBridge-style pattern matching, so a small evaluator or a pattern-matching library gives you fast local tests without touching AWS.</li>\n<li><strong>Deploy to a staging topic first</strong> with a test subscription into a queue, replay the corpus through a real publish, and assert on what actually arrives. This catches type and casing mistakes that a local evaluator written from the same misunderstanding will happily reproduce.</li>\n<li><strong>Shadow deploy.</strong> For a risky policy change, add a second subscription with the new policy alongside the existing one, compare delivery counts for a day, then cut over. Cheap, and it makes \"did we lose traffic?\" an observation instead of an argument.</li>\n<li><strong>Alarm per subscription.</strong> A CloudWatch alarm on <code>NumberOfNotificationsDelivered</code> for a subscription dropping below an expected floor over a window, plus an alarm on <code>NumberOfNotificationsFilteredOut-NoMessageAttributes</code> rising above zero, converts a silent outage into a page.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario: Routing Contract for a Multi-Tenant Event Topic</h4>\n<p style=\"line-height: 1.75\">You own a platform topic carrying every event for a multi-tenant SaaS: roughly 40 event types, 3,000 tenants across three tiers, four Regions, and around 60 subscriber teams. Both are legitimate; document which you are.</li>\n<li><strong>Tenant scoping.</strong> A per-tenant integration subscribes with <code>{\"tenantId\": [\"acme\"]}</code>. Note this is a routing control, not a security control — IAM and topic policy decide who may subscribe at all, and a filter policy is editable by whoever can call <code>SetSubscriptionAttributes</code>.
