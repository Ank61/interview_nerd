It is a different service tier with a different throughput profile, a different set of supported subscription protocols, and a guarantee that only holds if the <em>entire chain</em> from publisher to consumer preserves it. The most common FIFO mistake in a design interview is not misunderstanding the guarantee — it is claiming the guarantee end to end when only one hop actually provides it. The second most common is reaching for FIFO when application-level convergence would be cheaper, simpler and more scalable.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Guarantee, Stated Precisely</h4>\n<p style=\"line-height: 1.75\">An SNS FIFO topic provides:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Strict ordering within a message group.</strong> Messages published with the same <code>MessageGroupId</code> are delivered to a given subscription in the order they were accepted. Across different groups there is no ordering relationship at all, and none is implied.</li>\n<li><strong>Deduplication within a 5-minute window.</strong> Two publishes with the same deduplication ID inside the window produce one delivered message. The second publish <em>succeeds</em> — it returns a MessageId — but is not delivered.</li>\n<li><strong>No cross-group guarantee, no global sequence number, no total order.</strong> There is no \"position in the topic\" you can read.</li>\n</ul>\n<p style=\"line-height: 1.75\">On <strong>subscription protocols</strong>: FIFO topics launched supporting only <strong>SQS FIFO queues</strong>, which remains the canonical and safest target because it is the only one that preserves order all the way to the consumer. AWS has since expanded the supported list (SQS standard queues among them, and further protocols have been added over time), so check the current documentation rather than trusting a memorised list. The architecturally important point is unchanged: <strong>subscribing a non-FIFO target to a FIFO topic throws the ordering guarantee away at that hop</strong>. An SQS standard queue subscribed to a FIFO topic gives you deduplication and multi-AZ delivery, but the queue itself does not preserve order and concurrent consumers will reorder regardless.</p>\n<h4 If two application threads publish \"balance debited\" and \"balance credited\" for the same account concurrently, SNS faithfully preserves whatever order it happened to accept them in, which is not the order your business logic intended. FIFO preserves an order; it does not create one. Establishing it means serialising at the source — a per-entity lock, a single-writer partition, or (best) deriving events from an ordered source such as a DynamoDB stream shard or a transactional outbox read in primary-key order.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Message Group Design: the Ordering/Parallelism Knob</h4>\n<p style=\"line-height: 1.75\">The <code>MessageGroupId</code> is the single most consequential design decision in a FIFO system, and the rule is the same as in SQS FIFO: <strong>choose the smallest entity whose events must be ordered relative to each other</strong>. That is usually a customer ID, an account ID, an order ID, a device ID, or an aggregate root ID. It is almost never a tenant (too coarse), and almost never a random UUID per message (which orders nothing).</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Group ID choice</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Ordering</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Parallelism</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Verdict</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">One constant, e.g. \"all\"</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Total order</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">One message at a time, globally</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Anti-pattern. With a per-account group, a poison message stalls that one account — an acceptable, bounded, debuggable blast radius. With a single constant group, it stalls the business. This is why group granularity is simultaneously a performance decision and a <strong>failure-isolation</strong> decision, and why it deserves explicit discussion. Mitigations are a redrive policy on the FIFO queue so a poison message moves to a DLQ after a bounded number of receives, and per-group backlog monitoring so a stuck entity is visible.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Deduplication and Its Sharp Edge</h4>\n<p style=\"line-height: 1.75\">FIFO topics deduplicate over a <strong>5-minute window</strong>, using one of two mechanisms:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Explicit <code>MessageDeduplicationId</code>.</strong> You supply the key. This is the right choice whenever you have a natural business identity for the event — an event ID, an outbox row ID, an idempotency key from the API request that caused it. It gives you control and makes the behaviour explainable.</li>\n<li><strong>Content-based deduplication</strong> (<code>ContentBasedDeduplication=true</code> on the topic). SNS hashes the message body and uses that as the dedup ID. Convenient, but it means two <em>semantically distinct</em> events with byte-identical bodies inside five minutes collapse into one. \"Heartbeat: OK\" twice, or \"retry attempt\" events with no distinguishing field, are the classic casualties. If your payload contains a timestamp or event ID it is usually safe; if it does not, it is a trap.</li>\n</ul>\n<p style=\"line-height: 1.75\">The operational sharp edge, and a genuinely good interview question: <strong>a duplicate publish inside the window returns success and is silently not delivered.</strong> There is no error, no distinct status code you will notice in normal logging, and no metric that screams \"suppressed\". Now consider where that bites:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>A retry storm.</strong> Your publisher's SDK retries a timed-out publish. The first publish actually succeeded, so the retry is deduplicated — correct behaviour, exactly what dedup is for.</li>\n<li><strong>A legitimate re-publish.</strong> An operator replays a batch of events after fixing a bug, within five minutes of the original attempt. Every event whose dedup ID is unchanged is accepted and dropped. The replay appears to have done nothing, and it looks exactly like message loss. This is the incident: someone \"replays\" and then spends an hour wondering why nothing arrived.</li>\n<li><strong>Deploy-time double-publish.</strong> Two instances of a job running briefly during a rolling deploy publish the same events; dedup saves you — which is fine until someone removes the dedup ID because \"we do not need it\".</li>\n</ul>\n<p style=\"line-height: 1.75\">The mitigation is to make dedup IDs <strong>intentional and replay-aware</strong>: derive them from the business event identity for normal operation, and include a replay or attempt token when you are deliberately re-emitting, so a replay is not mistaken for a retry. And document the five-minute window in the runbook, because the natural operator instinct — \"it did not arrive, publish it again immediately\" — is precisely the action the window defeats.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Throughput Characteristics</h4>\n<p style=\"line-height: 1.75\">FIFO throughput is materially lower than standard, because ordering requires coordination. SNS FIFO topics are documented at <strong>300 publishes per second per topic</strong> (or a corresponding data rate), with <code>PublishBatch</code> of up to 10 messages per call raising the effective message rate roughly tenfold. Standard topics, by contrast, sustain rates orders of magnitude higher in large Regions. Exact figures are documented per Region and some quotas are adjustable — quote the shape, not a half-remembered number.</p>\n<p style=\"line-height: 1.75\">What scales the system is the <strong>number of distinct message groups</strong>, because parallelism downstream is bounded by how many groups can be in flight simultaneously. A design with a million account-level groups can keep a large consumer fleet busy; a design with ten tenant-level groups cannot, no matter how many workers you run. When you model FIFO capacity, model it as \"groups times per-group serial rate\", not as a single aggregate number, and check that your <em>hottest</em> group's event rate is below what one consumer can process serially — because that, not the topic quota, is usually the real ceiling.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Fan-Out with FIFO, Filtering, and Archiving</h4>\n<p style=\"line-height: 1.75\">A FIFO topic can fan out to multiple SQS FIFO queues, and <strong>each queue independently preserves order within each group</strong>. This is the pattern for \"several consumers must each see this account's events in order\" — a ledger service, an audit writer, and a notification service each get their own ordered stream, with independent backlogs and independent DLQs, and a slow consumer on one queue does not affect the others.</p>\n<p style=\"line-height: 1.75\"><strong>Filter policies work on FIFO subscriptions</strong> and compose as expected, with one consequence worth stating: filtering removes messages from a subscription's stream, so that subscriber sees an ordered <em>subsequence</em> of its group's events. Order among the delivered messages is preserved, but the subscriber cannot infer \"nothing happened in between\" — gaps are invisible. If a consumer's logic depends on seeing every transition of a state machine, filtering it down is a correctness bug, not an optimisation. Carry a per-group sequence number in the payload if consumers need to detect gaps.</p>\n<p style=\"line-height: 1.75\">FIFO topics also support <strong>message archiving and replay</strong>: enable an archive policy with a retention period (up to a year) and a subscription can be replayed from a point in time. This is the only native replay in SNS and it is a strong reason to choose FIFO for a system-of-record event stream even when throughput is modest — it converts \"we cannot reconstruct what happened\" into a supported operation. Replay respects group ordering, and consumers must still be idempotent because replayed events will be re-processed.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Decision Framework: Do You Actually Need FIFO?</h4>\n<div style=\"overflow-x: auto; FIFO is the right answer when the semantics genuinely require serial application, or when you want the archive. Saying \"I would use FIFO only here, and here is the cheaper alternative and why it does not work in this case\" is a stronger answer than reaching for FIFO reflexively.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario: Ordered Per-Account Event Delivery</h4>\n<p style=\"line-height: 1.75\">A fintech needs account lifecycle events (opened, KYC verified, frozen, unfrozen, closed) delivered to three consumers — a ledger service, a compliance auditor, and a customer notification service. Freezing and unfreezing must never be applied out of order. Peak is roughly 200 events per second across 4 million accounts, bursting to 1,000 during batch KYC runs.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Establish order at the source.</strong> Events are emitted from a transactional outbox written in the same database transaction as the account state change, and a single-writer relay reads the outbox in primary-key order per account. Without this, FIFO would faithfully order the wrong sequence.</li>\n<li><strong>Group ID = accountId.</strong> Four million groups gives per-account serialisation with massive parallelism, and a poison message stalls exactly one account. Tenant-level or a constant group would be wrong on both counts.</li>\n<li><strong>Dedup ID = the outbox row ID</strong>, not content-based — two \"frozen\" events for an account in the same five minutes are semantically distinct and content hashing would collapse them. The replay tooling appends a replay token to the dedup ID so an intentional re-emission is not suppressed.</li>\n<li><strong>Fan-out to three SQS FIFO queues</strong>, each preserving per-account order, each with its own redrive policy and DLQ. The ledger queue's consumer processes one message per group at a time; the notification consumer may be more relaxed because notifications are commutative.</li>\n<li><strong>Filtering.</strong> The notification service subscribes with a filter for customer-visible event types only. Stated explicitly: it now sees an ordered subsequence and cannot detect gaps, which is fine for notifications but would be wrong for the auditor, so the auditor takes everything unfiltered.</li>\n<li><strong>Throughput check.</strong> 1,000 per second exceeds the documented 300-publishes-per-second-per-topic FIFO ceiling for single publishes, so the relay uses <code>PublishBatch</code> with up to 10 messages per call — and batches only messages the consumer can tolerate arriving together.
