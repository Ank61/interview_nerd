{"title":"Observability for SNS and Fan-Out Pipelines","tags":["observability","cloudwatch","delivery-status-logging","tracing"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">A queue is observable almost by accident. If something goes wrong with an SQS consumer the evidence sits in the queue: you can look at <code>ApproximateNumberOfMessagesVisible</code>, you can peek at a message, you can measure the age of the oldest item. A push-based fan-out gives you none of that. Amazon SNS hands a message to each subscriber and then, for standard topics, forgets it. There is no backlog to inspect, no message to re-read, no artifact left behind. If a subscriber silently stopped receiving events three days ago, nothing in the topic will tell you — the topic looks perfectly healthy because publishing succeeded every time. Observability for SNS therefore has to be <strong>designed in before the incident</strong>, not reconstructed during it. This topic covers the metric model, delivery status logging, the reconciliation technique that proves nothing was lost, correlation tracing across the fan-out boundary, alarm design, and SLOs for notification pipelines.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why push fan-out is harder to observe than a queue</h4>\n<p style=\"line-height: 1.75\">Three structural properties make SNS opaque. First, <strong>delivery is fire-and-forget from the publisher's perspective</strong>: <code>Publish</code> returns a <code>MessageId</code> as soon as the message is durably stored and accepted, long before any subscriber sees it, so a 200 from Publish tells you nothing about delivery. Second, <strong>failures are per-subscription but metrics are per-topic</strong>: a topic with twelve subscriptions reports one aggregate stream of counters, so a single broken HTTP endpoint is a small blip against eleven healthy ones. Third, <strong>the absence of a message is invisible</strong>: filter policies, by design, drop messages silently — a subscriber that receives nothing because someone tightened a filter looks identical to a subscriber for which no events occurred.</p>\n<p style=\"line-height: 1.75\">The senior framing in an interview is that SNS observability is a <strong>reconciliation problem</strong>, not a monitoring problem. You are trying to prove an equality: for each subscription, deliveries plus intentional filter drops plus known failures should equal publishes. Anything that does not reconcile is silent loss, and silent loss in a notification pipeline is the failure mode that destroys trust in the platform.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The SNS metric model and what each metric actually tells you</h4>\n<p style=\"line-height: 1.75\">SNS publishes to the <code>AWS/SNS</code> namespace, principally dimensioned by <code>TopicName</code> (with <code>Application</code>, <code>Platform</code>, <code>Country</code> and <code>SMSType</code> dimensions for mobile push and SMS). Understanding each one precisely is what separates a candidate who can name metrics from one who can debug with them.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>NumberOfMessagesPublished.</strong> Count of messages accepted by the topic. This is your <em>input</em> signal. A drop here is a publisher problem (deploy, IAM change, upstream outage), never a subscriber problem. Alarm on it going to zero for topics that should never be idle.</li>\n<li><strong>NumberOfNotificationsDelivered.</strong> Count of successful deliveries <em>summed across all subscriptions</em>. For a topic with N subscriptions and no filtering, this should be roughly N times the published count. That ratio is the single most useful derived number in SNS observability, and it is the basis of reconciliation.</li>\n<li><strong>NumberOfNotificationsFailed.</strong> Deliveries SNS could not complete after exhausting its delivery policy. For SQS and Lambda this is rare and usually means permissions or KMS; for HTTP/S it means the endpoint returned non-2xx or timed out through every retry. <strong>This metric should normally be zero, which makes it the best candidate for a static threshold alarm</strong> — a rare luxury in CloudWatch.</li>\n<li><strong>NumberOfNotificationsRedrivenToDlq.</strong> Messages that failed delivery and were successfully written to the subscription's dead-letter queue. Non-zero here means the safety net caught something; it is a demand for investigation, not an outage by itself.</li>\n<li><strong>NumberOfNotificationsFailedToRedriveToDlq.</strong> The alarm that matters most and that teams forget. This means SNS could not even write the failed message to the DLQ — usually a missing or wrong SQS queue policy, a deleted queue, or a KMS key the SNS service principal cannot use. <strong>Any non-zero value here is permanent data loss.</strong></li>\n<li><strong>NumberOfNotificationsFilteredOut.</strong> Messages deliberately not delivered because a subscription filter policy did not match. Healthy and expected — but a <em>step change</em> in this metric is one of the highest-signal early warnings you can have, because it usually means a publisher changed the shape of its messages.</li>\n<li><strong>NumberOfNotificationsFilteredOut-NoMessageAttributes.</strong> The subscription filters on message attributes but the message arrived with none. Almost always a publisher regression: a new code path calls Publish without setting attributes.</li>\n<li><strong>NumberOfNotificationsFilteredOut-InvalidAttributes.</strong> Attributes were present but malformed relative to the policy's expectations — for example a numeric matcher against a value published as a non-numeric string, or a badly typed attribute. This points at a type contract break rather than a missing field.</li>\n<li><strong>NumberOfNotificationsFilteredOut-NoMessageBody / -InvalidMessageBody.</strong> The equivalents for subscriptions using <code>MessageBody</code> filter scope. <code>InvalidMessageBody</code> in particular means the body was not parseable JSON, which is a red flag that a publisher is sending a raw string to a topic whose subscribers filter on payload.</li>\n<li><strong>PublishSize.</strong> A distribution metric of published message sizes. Watch the maximum and p99: SNS caps standard messages at 256 KB, so a rising p99 is an early warning that you are about to start getting <code>InvalidParameter</code> errors, and it is also a cost signal because publish requests are billed in 64 KB chunks.</li>\n<li><strong>SMS-specific metrics.</strong> <code>SMSMonthToDateSpentUSD</code> tracks spend against your account SMS limit — this is the one metric in all of SNS where the failure mode is financial and where a threshold alarm should page someone. <code>SMSSuccessRate</code> gives the fraction of SMS deliveries that succeeded; carrier-side failures show up here long before a customer complains. Both can be viewed with <code>Country</code> and <code>SMSType</code> dimensions where SNS emits them, which matters because a single country's carrier rules can tank an otherwise healthy global success rate.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The per-subscription blind spot — and how to close it</h4>\n<p style=\"line-height: 1.75\">Here is the detail that catches candidates out: <strong>the core SNS CloudWatch metrics are not dimensioned by subscription ARN</strong>. <code>NumberOfNotificationsFailed</code> for a topic is a single number across every subscriber. On a topic with eleven healthy SQS subscriptions and one broken HTTP endpoint, the failures are real but they are a rounding error against the delivered count, and a percentage-based alarm will never fire. You have to construct per-subscription visibility yourself, and there are three complementary ways:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Delivery status logs plus metric filters.</strong> The log records carry the destination endpoint and the delivery status, so a CloudWatch Logs metric filter on <code>status = FAILURE</code> grouped per destination gives you a genuine per-subscription failure metric that you can alarm on.</li>\n<li><strong>Downstream metrics as proxies.</strong> For SQS subscribers, <code>NumberOfMessagesSent</code> on each queue <em>is</em> the per-subscription delivered count. For Lambda subscribers, <code>Invocations</code> plus <code>Errors</code> on each function serves the same role. This is usually the cheapest per-subscription signal to build, and it has the advantage of being owned by the consuming team.</li>\n<li><strong>Per-subscription DLQs.</strong> Give every subscription its own redrive DLQ rather than sharing one. Then <code>ApproximateNumberOfMessagesVisible</code> on each DLQ is an unambiguous, per-subscriber health metric, and the DLQ contents tell you exactly which messages were affected.</li>\n</ul>\n<p style=\"line-height: 1.75\">Design rule: <strong>one DLQ per subscription, not one per topic.</strong> A shared DLQ forces you to parse messages to work out which subscriber failed, and it couples redrive operations across teams.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Delivery status logging — the primary diagnostic</h4>\n<p style=\"line-height: 1.75\">Delivery status logging is the closest thing SNS has to a per-message audit trail, and the single most important fact about it is that <strong>it is off by default</strong>. Teams discover this during an incident, enable it, and then wait for the problem to recur — which is why enabling it should be part of your topic provisioning module, not an incident response step.</p>\n<p style=\"line-height: 1.75\">The configuration is <strong>per topic and per protocol</strong>. Each protocol has its own pair of attributes: a feedback role ARN and a success sample rate. For example <code>HTTPSuccessFeedbackRoleArn</code> with <code>HTTPSuccessFeedbackSampleRate</code>, and the equivalents for <code>SQS</code>, <code>Lambda</code>, <code>Firehose</code> and <code>Application</code> (mobile push). The IAM role must be assumable by the SNS service principal and must allow <code>logs:CreateLogGroup</code>, <code>logs:CreateLogStream</code>, <code>logs:PutLogEvents</code> and <code>logs:PutRetentionPolicy</code>. Three operational details matter:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Sample rate applies to successes only.</strong> A sample rate of 0 still logs every failure. This is the right default for a high-volume topic: 0 percent success sampling plus failure logging gives you the diagnostic value at almost no cost. Raise the success rate temporarily (to 100) while debugging latency or verifying a new subscriber, then lower it again.</li>\n<li><strong>Log groups are created for you</strong>, in the shape <code>sns/&lt;region&gt;/&lt;account-id&gt;/&lt;TopicName&gt;</code> for successes and the same name with a <code>/Failure</code> suffix for failures. Set a retention policy explicitly; the default of never-expire on a busy topic is a real cost line.</li>\n<li><strong>Not every protocol is covered.</strong> Delivery status logging supports SQS, Lambda, HTTP/S, Firehose and mobile push applications. <strong>Email and email-json have no delivery status logging</strong>, and SMS delivery logging is configured separately through the account-level SMS preferences with its own delivery status role. This asymmetry is why the email walkthrough below is hard, and it is a great detail to volunteer in an interview.</li>\n</ul>\n<p style=\"line-height: 1.75\">Each record is a JSON document describing one delivery <em>attempt</em>, with a <code>notification</code> object (message id, topic ARN, timestamp), a <code>delivery</code> object and a top-level <code>status</code> of <code>SUCCESS</code> or <code>FAILURE</code>. Four carry most of the load in real incidents: failures grouped by destination and status code (which subscriber, failing how); p95 dwell time by destination (which subscriber is slow, feeding your latency SLO); a single-message trace by <code>notification.messageId</code> (did <em>this</em> business event reach every subscriber); and attempt-count distribution (distinguishing flaky from down). The examples section below gives these verbatim.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Reconciliation — proving nothing was silently lost</h4>\n<p style=\"line-height: 1.75\">Reconciliation is the technique that turns \"the dashboard looks fine\" into an actual guarantee. It has three layers, each catching what the previous one cannot.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Layer 1 — fan-out ratio.</strong> Compute <code>NumberOfNotificationsDelivered / NumberOfMessagesPublished</code> with CloudWatch metric math. On a topic with N unfiltered subscriptions this should sit at N. If it drifts to N minus 1, exactly one subscription stopped receiving. This one derived metric catches the most common silent failure in all of SNS, and it costs nothing to compute.</li>\n<li><strong>Layer 2 — conservation of messages.</strong> For each published message, every subscription should account for it exactly once as delivered, filtered out, failed, or redriven. So <code>Published &times; N</code> should equal <code>Delivered + FilteredOut + Failed</code> within a window, allowing for boundary effects. A persistent gap means messages are unaccounted for and deserves an investigation.</li>\n<li><strong>Layer 3 — downstream receipt.</strong> Compare SNS <code>NumberOfNotificationsDelivered</code> for a subscription against the target's own ingress metric: SQS <code>NumberOfMessagesSent</code> on the subscribed queue, or Lambda <code>Invocations</code> on the subscribed function. This is the layer that catches the case where SNS believes delivery succeeded but the consumer never processed the work — most importantly the <strong>Lambda async-invocation gap</strong>, where SNS records a successful delivery the moment Lambda accepts the invoke, and any failure inside the function is invisible to SNS entirely.</li>\n</ul>\n<p style=\"line-height: 1.75\">For high-value pipelines, add a <strong>business-level reconciliation</strong> on top: a scheduled job that counts source-of-truth records created in a window (orders placed, payments settled) and compares against the count of terminal records each consumer produced. Infrastructure reconciliation proves messages moved; business reconciliation proves the right ones moved.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Tracing across the fan-out boundary</h4>\n<p style=\"line-height: 1.75\">Distributed tracing degrades badly at a fan-out. A trace is a tree, and SNS turns one span into N independent branches running in different accounts, languages and teams. Two mechanisms keep it together:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Correlation identifier in message attributes.</strong> Put a <code>correlation_id</code> (and ideally a <code>causation_id</code> naming the event that caused this one) into the message attributes and into the envelope of the payload. Attributes are the right home because they survive raw message delivery and because subscribers can filter on them; the payload copy is insurance for consumers that read only the body. Every consumer then logs the correlation id on every log line, and a single Logs Insights query across all consumer log groups reconstructs the full fan-out for one business event. This is low-tech and it works across accounts and languages where a tracing SDK may not.</li>\n<li><strong>X-Ray active tracing.</strong> SNS supports X-Ray active tracing on topics: when the publisher is instrumented, SNS propagates the trace header and continues the trace into SQS and Lambda subscribers, so the fan-out appears as branches of one trace map. The caveats are worth knowing — it applies to supported target types, the subscriber must also be instrumented to continue the trace, and coverage across arbitrary HTTP subscribers in other accounts is not something you can assume. Treat X-Ray as the rich view where it works and the correlation id as the universal floor.</li>\n</ul>\n<p style=\"line-height: 1.75\">Without deliberate propagation, tracing simply breaks at the topic: the publisher's trace ends at Publish, and each consumer starts a fresh unrelated trace. In an interview, saying \"SNS is where traces go to die unless you propagate context explicitly\" and then explaining both mechanisms is a strong signal.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Alarm design — alarm on harm, not on activity</h4>\n<p style=\"line-height: 1.75\">Most SNS dashboards alarm on things that are merely interesting. The alarms that correspond to actual harm are:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>NumberOfNotificationsFailed &gt; 0</strong> sustained over two or three periods. Zero is the expected value, so this is a genuine static threshold.</li>\n<li><strong>NumberOfNotificationsFailedToRedriveToDlq &gt;= 1</strong>, treated as a page. This is data loss.</li>\n<li><strong>DLQ depth per subscription</strong> via <code>ApproximateNumberOfMessagesVisible</code>, plus <code>ApproximateAgeOfOldestMessage</code> so a slowly filling DLQ nobody drains still alerts.</li>\n<li><strong>Fan-out ratio deviation</strong> — metric math comparing delivered-per-published against the expected subscription count. This is the alarm that catches one dead subscriber among many.</li>\n<li><strong>Filtered-out step change</strong> using anomaly detection rather than a static threshold, because the healthy baseline is non-zero and workload-dependent. A spike in <code>NumberOfNotificationsFilteredOut-NoMessageAttributes</code> specifically is close to a direct signal of a publisher contract break and deserves its own alarm.</li>\n<li><strong>SMSMonthToDateSpentUSD</strong> at a fraction of your spend limit, so you learn about runaway SMS cost before deliveries start being suppressed.</li>\n<li><strong>Subscriber-side lag</strong> — queue <code>ApproximateAgeOfOldestMessage</code> and Lambda <code>IteratorAge</code>-equivalent signals, because SNS can be perfectly healthy while the consumers fall hours behind.</li>\n<li><strong>Publish volume floor</strong> for topics that should never be quiet, catching the silent publisher outage that no delivery metric can see.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">SLO thinking for notification pipelines</h4>\n<p style=\"line-height: 1.75\">Two SLIs describe a notification pipeline well. <strong>Delivery success rate</strong> is delivered divided by delivered plus failed, measured <em>per subscription</em>, with filtered-out excluded from the denominator because those drops are intentional. <strong>End-to-end delivery latency</strong> is the time from the business event occurring to the consumer finishing processing — not just the SNS dwell time. Measure it by stamping <code>event_time</code> into the envelope at publish and having each consumer emit a latency metric at the end of processing. The gap between SNS <code>dwellTimeMs</code> (typically low tens of milliseconds for SQS and Lambda) and your end-to-end latency tells you immediately whether a latency problem is SNS-side or consumer-side — and it is almost always consumer-side. Set the objective per subscriber class: an SQS-backed batch consumer might get a 5-minute objective while a paging integration gets 30 seconds, and different objectives justify different error budgets and different on-call expectations.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Investigation walkthrough: \"the email team says they stopped getting events\"</h4>\n<p style=\"line-height: 1.75\"><strong>Step 1 — establish the input.</strong> Look at <code>NumberOfMessagesPublished</code> on the topic over 14 days. If it fell off a cliff, this is not an email problem at all and you go upstream to the publisher. Assume here it is flat and healthy.</p>\n<p style=\"line-height: 1.75\"><strong>Step 2 — compute the fan-out ratio.</strong> Delivered over published. The topic has six subscriptions; the ratio used to sit at 6.0 and is now 5.0. That is decisive evidence that exactly one subscription stopped receiving, and it also tells you the failure is not intermittent.</p>\n<p style=\"line-height: 1.75\"><strong>Step 3 — check failures and filtering.</strong> <code>NumberOfNotificationsFailed</code> is flat at zero, so SNS is not attempting and failing — it is not attempting at all. <code>NumberOfNotificationsFilteredOut</code> has risen by exactly the missing volume, and the timestamp of the step change lines up with a deploy. This already points at filtering rather than delivery, which is important because <strong>email has no delivery status logs</strong>, so if the cause had been delivery-side you would have had to reason from metrics and bounce handling alone.</p>\n<p style=\"line-height: 1.75\"><strong>Step 4 — split the filtered-out variants.</strong> Graph <code>NumberOfNotificationsFilteredOut</code> against the <code>-NoMessageAttributes</code> and <code>-InvalidAttributes</code> variants. If the increase is in <code>-NoMessageAttributes</code>, a publisher code path is calling Publish without attributes. If it is in the plain metric, messages have attributes but the values no longer match — someone changed a value, or changed the policy.</p>\n<p style=\"line-height: 1.75\"><strong>Step 5 — compare the artifacts.</strong> Call <code>GetSubscriptionAttributes</code> on the email subscription and read the current <code>FilterPolicy</code> and <code>FilterPolicyScope</code>. Then capture a live message: temporarily subscribe a scratch SQS queue with no filter policy, or read a recent record from a sibling subscriber's delivery success log, and diff the actual attributes against what the policy expects. In this incident the publisher deploy renamed the attribute value from <code>order_shipped</code> to <code>OrderShipped</code> to match a new internal enum, while the email subscription's policy still matched the old lowercase value. Filtering is exact-match and case-sensitive, so every message was dropped silently.</p>\n<p style=\"line-height: 1.75\"><strong>Step 6 — confirm and remediate.</strong> Check CloudTrail for <code>SetSubscriptionAttributes</code> to rule out a policy change, confirming the publisher moved instead. Short-term, widen the policy to match both values so the team recovers immediately. Medium-term, ask what the messages that were dropped were worth — because unlike a delivery failure there is no DLQ and no replay for filtered-out messages on a standard topic, so if they mattered they must be regenerated from the source system. Long-term, the fixes are structural: add the fan-out-ratio alarm and the filtered-out anomaly alarm so this is detected in minutes rather than by a human noticing an empty inbox; treat message attribute values as a published contract with a versioned schema; and add a synthetic canary that publishes a known probe event each minute and asserts every subscriber observed it.</p>\n<p style=\"line-height: 1.75\">The last point is the durable lesson. In a system where the failure mode is <em>absence</em>, the only reliable detector is a continuous positive test.
