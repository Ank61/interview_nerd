{"title":"SNS to Lambda — Asynchronous Invocation Semantics in Depth","tags":["sns","lambda","async-invocation","dead-letter-queue"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">SNS to Lambda looks like the simplest integration in the AWS messaging toolbox: subscribe a function to a topic and messages arrive. The simplicity is deceptive. The entire failure model of this path is governed by one fact — <strong>SNS invokes Lambda asynchronously</strong> — and almost every production surprise on this path traces back to engineers reasoning about it as if it behaved like SQS-to-Lambda, which is a completely different mechanism (an event source mapping that polls). In an SDE-3 or SRE interview, the question \"where does a failed message go when SNS calls Lambda?\" separates people who have operated this from people who have only drawn it on a whiteboard.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The invocation mechanism and where responsibility transfers</h4>\n<p style=\"line-height: 1.75\">When a message is published to a topic with a Lambda subscription, SNS calls the Lambda <code>Invoke</code> API with an invocation type of <code>Event</code>. Lambda validates the request, checks the function's resource-based policy, checks concurrency headroom, and then places the event onto an internal asynchronous invocation queue that Lambda itself owns and manages. The moment Lambda returns a <code>202 Accepted</code>, SNS has done its job. From SNS's perspective the delivery <strong>succeeded</strong>. It will emit a <code>NumberOfNotificationsDelivered</code> data point and, if delivery status logging is enabled, a success record. Whether your handler subsequently throws, times out, runs out of memory, or silently swallows an exception is invisible to SNS.</p>\n<p style=\"line-height: 1.75\">This is the single most important sentence on this topic: <strong>the SNS subscription DLQ does not capture function errors.</strong> It captures only the case where SNS could not hand the event to Lambda at all — the function was deleted, the resource policy was removed, the function was throttled to the point that Lambda rejected the invoke after SNS exhausted its own delivery retries, or a persistent service-side failure occurred. Those are transport failures. Everything after the 202 belongs to Lambda.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">Publish <i class=c>--&gt; [ SNS Topic ] --&gt; Invoke(Event) --&gt; [ Lambda async queue ] --&gt; handler</i>\n                 <i class=o>|</i>                  <i class=o>|</i>                     <i class=o>|</i>                   <i class=o>|</i>\n                 <i class=o>|</i>                  <i class=o>|</i>  <i class=n>202</i> Accepted       <i class=o>|</i>  retries (<i class=n>2</i>x)     <i class=o>|</i>  throws\n                 <i class=o>|</i>                  v                     v                   v\n                 <i class=o>|</i>          SNS says DELIVERED      MaximumRetryAttempts   <i class=k>on</i><i class=o>-</i>failure\n                 <i class=o>|</i>                                  MaximumEventAge        destination\n                 v\n          SNS subscription DLQ\n          (<i class=k>ONLY</i> if the invoke itself never succeeded)</code></pre></div>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Lambda's own asynchronous retry behavior</h4>\n<p style=\"line-height: 1.75\">Once the event is in Lambda's internal queue, Lambda owns retries. By default an asynchronous invocation that fails is retried <strong>twice</strong> (three total attempts) with delays between them — roughly a minute before the first retry and a couple of minutes before the second, with jitter. Lambda also holds events in that internal queue for up to <strong>six hours</strong> by default, which matters when a function is fully throttled: the event is not lost immediately, Lambda keeps trying to place it as capacity frees up.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>MaximumRetryAttempts.</strong> Configurable from 0 to 2 via <code>PutFunctionEventInvokeConfig</code>. Set it to 0 when the work is not worth retrying in place (for example a poison payload) and you would rather get it to a failure destination immediately for human or automated triage.</li>\n<li><strong>MaximumEventAge.</strong> Configurable from 60 seconds to 21600 seconds (6 hours). This is an age-based discard: if the event has been sitting in Lambda's async queue longer than this, Lambda stops trying and sends it to the failure destination. For latency-sensitive work — a fraud signal that is meaningless after two minutes — set a short age so stale events are shed rather than processed late.</li>\n<li><strong>Both are per-function or per-version/alias</strong> configuration, not per-subscription. If one topic's traffic needs different retry semantics from another topic's, that is an argument for separate functions or for putting a queue in front.</li>\n<li><strong>Retries re-run the whole handler.</strong> There is no partial-batch semantics here because there is no batch — one message, one invocation, retried whole.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Destinations versus the legacy Lambda DLQ</h4>\n<p style=\"line-height: 1.75\">Lambda has two generations of failure capture for asynchronous invocations. The older one is the <strong>Lambda DLQ</strong> (<code>DeadLetterConfig</code>), which forwards the original event payload to an SQS queue or SNS topic after retries are exhausted. It works, but it gives you only the payload — no error message, no stack trace, no request ID correlation, and no success path.</p>\n<p style=\"line-height: 1.75\">The newer and strictly better mechanism is <strong>Lambda destinations</strong> (<code>PutFunctionEventInvokeConfig</code> with <code>DestinationConfig</code>). You configure an <strong>OnFailure</strong> destination and optionally an <strong>OnSuccess</strong> destination, each of which may be an SQS queue, an SNS topic, another Lambda function, or an EventBridge event bus. The record delivered to a destination is an envelope containing the original request payload, the <code>requestContext</code> (request ID, function ARN, condition such as <code>RetriesExhausted</code>, approximate invoke count) and the <code>responsePayload</code> with the actual error type and message. That error context is what turns a DLQ from a graveyard into a triage tool.</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Aspect</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Lambda DLQ (legacy)</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">On-failure destination</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Payload delivered</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Original event only</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Event plus error type, message, request ID, invoke count</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Targets</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">SQS, SNS</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">SQS, SNS, Lambda, EventBridge</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Success path</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">None</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">On-success destination available</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Recommendation</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Legacy, keep only for existing stacks</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Default choice for new work</td></tr>\n</tbody>\n</table>\n</div>\n<p style=\"line-height: 1.75\">If both are configured, the destination takes precedence for asynchronous invocations; do not configure both and expect two copies. Note also that a destination is <em>not</em> reached when the event is discarded for reasons outside the invocation, and that destination delivery itself is best-effort — it is an asynchronous hand-off, so alarm on the destination queue rather than assuming everything lands.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The two DLQs, side by side</h4>\n<p style=\"line-height: 1.75\">This is the interview question that reveals depth, so it is worth being crisp about it. There are two independently configured failure sinks on this path and they catch disjoint classes of failure.</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Sink</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Configured on</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Catches</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Does NOT catch</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">SNS subscription DLQ (RedrivePolicy)</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">The subscription</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Function deleted, permission removed, invoke rejected after SNS retries, sustained throttling at the invoke boundary</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Any handler error, timeout, OOM, or logic bug</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Lambda on-failure destination (or Lambda DLQ)</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">The function / alias</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Handler exceptions after retries exhausted, timeouts, OOM, events aged out past MaximumEventAge</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Messages SNS never managed to hand over</td></tr>\n</tbody>\n</table>\n</div>\n<p style=\"line-height: 1.75\">A production-grade SNS-to-Lambda subscription configures <strong>both</strong>, and alarms on both. Configuring only the subscription DLQ — which is what most teams do because it is the one the SNS console nudges you toward — produces a system where a function that is failing on every single message shows an empty DLQ and a green SNS delivery metric.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Event payload shape and parsing</h4>\n<p style=\"line-height: 1.75\">Lambda receives a <code>Records</code> array. In practice SNS delivers <strong>one record per invocation</strong> — the array shape exists for symmetry with other event sources, not because SNS batches. Each record has an <code>EventSource</code> of <code>aws:sns</code>, an <code>EventSubscriptionArn</code> identifying which subscription produced it, and an <code>Sns</code> object containing <code>MessageId</code>, <code>TopicArn</code>, <code>Subject</code>, <code>Timestamp</code>, <code>Message</code> and <code>MessageAttributes</code>. The <code>Message</code> field is always a <strong>string</strong>; if you published JSON you must parse it yourself. There is no raw message delivery option for Lambda subscriptions the way there is for SQS and HTTP endpoints, so the envelope is always present. Message attributes arrive as a map of name to an object with <code>Type</code> and <code>Value</code>, meaning a <code>Number</code> attribute still arrives as a string that you must coerce. Getting this wrong — iterating <code>Records</code> as if it could hold hundreds of entries, or treating <code>Message</code> as an object — is a common code-review finding.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Concurrency: the burst that eats your account</h4>\n<p style=\"line-height: 1.75\">Because there is no batching, the arithmetic is brutally direct: <strong>N messages published means N concurrent invocations</strong>, bounded only by how fast Lambda can scale. A fan-out topic that normally sees ten messages a second and suddenly receives a fifty-thousand-message backfill will attempt to scale that function toward fifty thousand concurrent executions. Two things then happen. First, the function's own downstream — a relational database, a third-party API with a rate limit — is hit with a concurrency it was never sized for. Second, and worse, the function consumes the <strong>account-level concurrency</strong> pool, which is shared across every function in that account and Region. Unrelated, business-critical functions begin throttling. This is the classic noisy-neighbour blast radius question.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Reserved concurrency.</strong> Setting reserved concurrency on the subscriber caps it and simultaneously guarantees that capacity to it. This is the minimum viable protection: it converts an account-wide outage into a localized throttle. Throttled async invocations are retried from Lambda's internal queue for up to the event age, so bursts are absorbed rather than dropped — but only within that window.</li>\n<li><strong>An SQS queue in between.</strong> Subscribing an SQS queue to the topic and using an event source mapping gives you batching (up to 10 000 records per batch depending on configuration), a real buffer with visible depth, and event-source-mapping level concurrency control including <code>MaximumConcurrency</code> on the mapping. The queue is the backpressure device: it grows instead of the downstream burning.</li>\n<li><strong>Provisioned concurrency</strong> solves cold-start latency, not burst protection — do not confuse the two in an interview.</li>\n<li><strong>Downstream-aware throttling.</strong> If the real constraint is a database with 200 connections, reserved concurrency below that number is the correct control, and it should be documented as such.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; Put a queue in the middle the moment the work touches a rate-limited downstream, needs replay, needs batching for cost, or has any chance of a large burst.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Permissions and idempotency</h4>\n<p style=\"line-height: 1.75\">SNS invokes Lambda using a <strong>resource-based policy</strong> on the function, not an execution role assumed by SNS. The statement grants <code>lambda:InvokeFunction</code> to principal <code>sns.amazonaws.com</code> and should be scoped with a <code>SourceArn</code> condition naming the exact topic, otherwise any topic in any account could invoke your function. Subscribing through the console adds this automatically; subscribing through raw API calls or a hand-written CloudFormation template frequently does not, which is the classic \"subscription exists but nothing ever runs\" bug. Deleting and recreating the function drops the policy and the subscription silently stops working while SNS begins filling the subscription DLQ.</p>\n<p style=\"line-height: 1.75\">On <strong>idempotency</strong>: SNS is at-least-once and Lambda async retries are at-least-once, so duplicates are a certainty at scale, not an edge case. Never key idempotency on the SNS <code>MessageId</code> — a Lambda retry of the same event reuses the same MessageId (so it deduplicates correctly) but an SNS-level redelivery generates the same MessageId too, while a genuine publisher retry produces a <em>different</em> MessageId for the same business event. The durable key is a business identifier the publisher puts in the payload (order ID plus state transition, for example), recorded in a DynamoDB table with a conditional write and a TTL.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Production scenario: the subscriber that silently drops work</h4>\n<p style=\"line-height: 1.75\">A payments team reports that roughly 4% of order events never produce a receipt. The receipt service is a Lambda subscribed directly to the <code>order-events</code> topic. The on-call engineer checks the topic: <code>NumberOfMessagesPublished</code> and <code>NumberOfNotificationsDelivered</code> match exactly, <code>NumberOfNotificationsFailed</code> is zero, and the subscription DLQ is empty. The conclusion drawn — wrongly — is that SNS is fine and the problem must be upstream.</p>\n<p style=\"line-height: 1.75\">The correct next move is to stop looking at SNS entirely, because SNS has already told you it handed off every message. Look at the function's <code>Errors</code> and <code>Throttles</code> metrics. Here <code>Errors</code> is non-zero and correlates with the 4%: the handler calls a downstream pricing API that intermittently returns 500, the handler catches the exception, logs it at <code>warn</code>, and <strong>returns normally</strong>. Because it returns successfully, Lambda considers the invocation a success — there are no retries and nothing reaches a failure destination, because from Lambda's point of view nothing failed. The bug is swallowed error handling, and it is invisible in every metric except a log line nobody alarms on.</p>\n<p style=\"line-height: 1.75\">The remediation has three parts. First, <strong>rethrow</strong>: an unrecoverable downstream error must propagate so Lambda's retry machinery engages. Second, configure an <strong>on-failure destination</strong> to an SQS queue with a CloudWatch alarm on <code>ApproximateNumberOfMessagesVisible</code>, so exhausted retries become a page rather than a silence. Third, for a function whose downstream is rate-limited and flaky, migrate to <strong>SNS to SQS to Lambda</strong> so that retries are queue-driven with a tunable visibility timeout, the backlog is measurable, and failed messages land in a queue DLQ that supports native redrive.
