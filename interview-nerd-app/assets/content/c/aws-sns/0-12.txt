Point your alarms at an alerts topic, then subscribe whatever should hear about it: an email address for the team list, an HTTPS endpoint for PagerDuty or Opsgenie, a Lambda that posts into chat, and an SQS queue that records every alert for later analysis. Filter policies let one alerts topic serve several severities — the paging subscription filters for critical only while the chat subscription takes everything.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Pattern 4: AWS service events into a topic</h4>\n<p style=\"line-height: 1.75\">Several AWS services publish directly to SNS. The canonical example is <strong>S3 event notifications</strong>: configure a bucket so that every object created under a prefix publishes to a topic, then fan out to a thumbnail generator, a virus scanner and an audit queue. Others include RDS events, Auto Scaling lifecycle events, and Config rule changes. Two gotchas worth knowing: the topic's access policy must allow the service principal with an <code>aws:SourceArn</code> condition naming the bucket, and the topic must be in the same region as the bucket.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Pattern 5: Mobile broadcast</h4>\n<p style=\"line-height: 1.75\">Subscribe many platform endpoints — each representing one phone — to a topic, and a single publish reaches every device. Use a topic per interest group so users only get what they opted into, and use the JSON message structure so iOS and Android each receive a correctly formatted payload from the same publish.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Pattern 6: Cross-account event distribution</h4>\n<p style=\"line-height: 1.75\">A topic in one AWS account can have subscribers in others — a common shape when platform teams publish events that product teams consume, each in their own account. Two policies must agree: the <strong>topic access policy</strong> in the publisher's account must allow the other account's principal to <code>sns:Subscribe</code>, and the subscriber's <strong>queue policy</strong> must allow the topic's ARN to <code>sqs:SendMessage</code>. A cross-account subscription also starts in a pending state until confirmed. Enable <strong>raw message delivery</strong> so consuming teams are not forced to unwrap the SNS envelope, and keep an eye on the fact that the message's origin account is visible in the ARN — useful for auditing.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Pattern 7: Archive everything with Firehose to S3</h4>\n<p style=\"line-height: 1.75\">SNS stores nothing, so \"what did we publish last Tuesday?\" is unanswerable unless you planned for it. The standard answer is to subscribe an <strong>Amazon Data Firehose</strong> delivery stream (formerly Kinesis Data Firehose) to the topic. Firehose buffers messages by size or time and writes them to S3 as batched, optionally compressed files. You now have a cheap, durable record you can query with Athena and re-read to reconstruct state after a bug — without changing a single publisher. Add this to a topic on day one; retrofitting it does not recover the past.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">                 <i class=o>+</i><i class=c>--&gt; [SQS billing-q]     --&gt; workers        (the live path)</i>\n(TOPIC) <i class=c>---------+--&gt; [SQS search-q]      --&gt; indexer</i>\n                 <i class=o>+</i><i class=c>--&gt; [Firehose stream]   --&gt; s3://events-archive/2026/09/17/...</i>\n                                                    <i class=o>^</i> durable history, queryable <i class=k>with</i> Athena</code></pre></div>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Pattern 8: Claim-check for large payloads</h4>\n<p style=\"line-height: 1.75\">SNS messages max out at 256 KB. When the thing you want to distribute is a 40 MB video or a large report, you use the <strong>claim-check</strong> pattern: the producer stores the big object in S3 and publishes only a small message containing the S3 bucket and key plus enough metadata for subscribers to decide whether they care. Each subscriber fetches the object itself if it needs it — a ticket for the coat check rather than the coat.</p>\n<p style=\"line-height: 1.75\">Two practical notes. Set an S3 lifecycle rule so claim-check objects expire once they can no longer be needed, and make sure every subscriber account has read permission on the object, or you will get mystifying downstream failures that look like SNS problems but are S3 permission problems.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Idempotency: the habit that makes all of this safe</h4>\n<p style=\"line-height: 1.75\"><strong>Idempotent</strong> means doing something twice has the same effect as doing it once. This matters because SNS standard topics guarantee <strong>at-least-once</strong> delivery: a subscriber can legitimately be invoked twice for a single publish — a retry after a timeout where the first attempt actually succeeded, a Lambda retry, an SQS message reappearing after a visibility timeout expired mid-processing. If your handler charges a card or sends an email, a duplicate is a real customer problem.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Do not use the SNS message id as your idempotency key.</strong> It is unique per publish, so a producer that retries its own <code>Publish</code> call produces two different message ids for the same business event — and your dedupe silently fails at exactly the moment it mattered.</li>\n<li><strong>Choose a key from the business meaning of the message.</strong> Something the producer already owns and would reuse on retry: <code>orderId</code> plus event type, a payment intent id, or a deterministic hash of the significant fields. \"Order A-991 was placed\" should carry the same key no matter how many times it is published.</li>\n<li><strong>Record processed keys somewhere with a conditional write.</strong> A DynamoDB table keyed by the idempotency key, written with a condition that the item does not already exist, is the standard approach: if the write fails the condition, you have seen this event, so acknowledge and stop. Give the table a TTL so it prunes itself.</li>\n<li><strong>Or make the effect naturally idempotent.</strong> An upsert keyed by order id, or a state transition guarded by \"only move to SHIPPED if currently PACKED,\" needs no separate bookkeeping at all. This is the cleanest option when the domain allows it.</li>\n<li><strong>Be careful where you record it.</strong> Recording the key before the work completes means a crash mid-way marks the event done and it is never processed; recording it after means a crash between the work and the record causes a duplicate. Doing both in one transaction with the business write is the robust answer.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The consolidated list of beginner mistakes, with fixes</h4>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Mistake</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">What you see</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Fix</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Forgetting the SQS queue policy</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Subscription exists, queue stays empty, no obvious error</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Add a queue policy allowing <code>sns.amazonaws.com</code> to <code>sqs:SendMessage</code>, with <code>aws:SourceArn</code> equal to the topic ARN.
