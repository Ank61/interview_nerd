They rotate, they are invalidated by uninstalls, they change on app reinstall and device restore, and the push providers tell you about it asynchronously and indirectly. A <strong>platform application</strong> holds the credentials for one app on one push provider in one Region — an APNs authentication key (the modern token-based <code>.p8</code> approach, preferred) or an APNs certificate, or FCM credentials for Android. Crucially, a platform application is scoped to a single provider and a single app build variant, so a typical product has at least four: iOS production, iOS sandbox, Android production, and often a separate one per white-label or staging build. Meanwhile the user may simply uninstall, in which case the token becomes permanently invalid but you do not learn this until you try to send to it. Push delivery is fundamentally <strong>asynchronous and out-of-band</strong> — <code>Publish</code> returns a MessageId immediately, and the provider reports invalidity later, at which point SNS sets the endpoint's <code>Enabled</code> attribute to <code>false</code>. A disabled endpoint is not deleted; it lingers, and every future publish to it fails.</p>\n<p style=\"line-height: 1.75\">The required hygiene loop has four parts, and skipping any one of them degrades the system:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Re-register on every app launch.</strong> The client should request its current token at each cold start and send it to your backend unconditionally. Do not optimise this away by caching \"we already registered\" — the whole point is that the token may have changed while the app was closed.</li>\n<li><strong>Reconcile on the server with a get-then-fix routine.</strong> The canonical algorithm: look up the stored endpoint ARN for this user and device; if none, call <code>CreatePlatformEndpoint</code>. If one exists, call <code>GetEndpointAttributes</code>. If that throws <code>NotFoundException</code> the endpoint was deleted, so create a new one. If it exists but the stored <code>Token</code> differs from the current token, or <code>Enabled</code> is <code>false</code>, call <code>SetEndpointAttributes</code> to write the new token and set <code>Enabled</code> back to <code>true</code>. This single routine handles token rotation, reinstall-after-uninstall, and revival of a previously disabled endpoint. Note that <code>CreatePlatformEndpoint</code> is idempotent for the same token and custom data, but returns an <code>InvalidParameterException</code> whose message contains the existing endpoint ARN when the same token exists with <em>different</em> custom data — production code must parse that ARN out and reuse it rather than failing.</li>\n<li><strong>Detect and clean up disabled endpoints.</strong> Run a periodic sweep using <code>ListEndpointsByPlatformApplication</code>, and delete endpoints that have been <code>Enabled=false</code> for longer than a grace period (30 to 90 days is typical — long enough that a user reinstalling revives it through the launch path, short enough to keep the population clean). Keep the deletion idempotent and rate-limited; the API is paginated and throttled.</li>\n<li><strong>Handle the same user on multiple devices.</strong> One user maps to many endpoints. Store the mapping in your own datastore keyed by user plus device identifier, and treat SNS as the delivery layer, not the system of record.</li>\n</ul>\n<p style=\"line-height: 1.75\">The consequence of skipping this loop is worth stating plainly, because it is the interview payoff. You accumulate a growing population of dead endpoints. Every broadcast wastes publishes against them. Your <strong>delivery metrics become misleading</strong> — a \"78% delivery rate\" that is really 95% among live devices and 0% among a 20% graveyard tells you nothing actionable, and worse, it moves when the graveyard grows rather than when real delivery degrades. Teams then chase phantom regressions. If you subscribed endpoints directly to topics, the dead endpoints also bloat the subscription list and slow every broadcast.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Event notifications for endpoint state changes</h4>\n<p style=\"line-height: 1.75\">Polling <code>ListEndpointsByPlatformApplication</code> across millions of endpoints is slow and expensive. SNS can instead emit <strong>application event notifications</strong> to a topic of your choosing when endpoint state changes. A platform application has event attributes including <code>EventEndpointCreated</code>, <code>EventEndpointDeleted</code>, <code>EventEndpointUpdated</code> and <code>EventDeliveryFailure</code>, each set to a topic ARN. Wire those to a topic feeding an SQS queue and a small reconciliation worker, and endpoint disablement becomes an <strong>event-driven</strong> signal you react to within seconds: mark the device inactive in your own store, stop targeting it, and record the reason. This turns the cleanup sweep from your primary mechanism into a safety net. Topics are elegant for broadcast because one <code>Publish</code> reaches every subscriber, but a topic accumulating millions of endpoint subscriptions runs into the per-topic subscription limit, makes subscription churn (every install and uninstall) a high-rate write workload against the SNS control plane, and offers no way to personalize content per recipient. Beyond roughly the low hundreds of thousands of subscribers, or as soon as the message body must differ per user, the better architecture is a <strong>fan-out job</strong>: read the target endpoint ARNs from your own database, shard them across an SQS queue, and have a bounded worker pool publish directly. That gives you personalization, precise rate control (important because you may want to smooth a ten-million-device send over an hour to avoid a thundering herd against your own API when everyone taps the notification), resumability, and per-recipient outcome tracking. The cost is that you have built and must operate it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Platform-specific payloads</h4>\n<p style=\"line-height: 1.75\">To send provider-specific payloads you publish with <code>MessageStructure</code> set to <code>json</code> and a message that is a JSON object whose keys are platform names. A <code>default</code> key is <strong>required</strong> and is used for any protocol without a specific entry. Each platform's value is itself a <strong>JSON-encoded string</strong>, not a nested object — a detail that trips up nearly everyone the first time, producing an <code>InvalidParameterException</code>.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>APNs.</strong> The payload contains an <code>aps</code> dictionary with <code>alert</code>, <code>badge</code>, <code>sound</code>, and optionally <code>content-available</code> for silent background delivery or <code>mutable-content</code> for notification service extensions. FCM's payload limit is 4 KB for most message types.</li>\n<li><strong>Silent/background notifications</strong> are the mechanism for waking an app to sync, but both platforms aggressively rate-limit and deprioritize them; treat them as best-effort hints, never as a reliable transport.</li>\n<li><strong>Collapse keys and TTL are the two most under-used features.</strong> A score-update or delivery-tracking notification should always set both: a short TTL so a device that was offline for six hours does not receive stale news, and a collapse key so the user sees one current notification instead of forty.</li>\n<li><strong>Size limits are enforced by the provider, not by SNS's 256 KB limit</strong> — exceeding 4 KB fails at the provider with an error surfaced only in delivery status logs.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Delivery quality and its honest limits</h4>\n<p style=\"line-height: 1.75\">Enable <strong>delivery status logging</strong> on the platform application by setting the success and failure IAM roles and a <code>SuccessFeedbackSampleRate</code>. SNS then writes per-message records to CloudWatch Logs containing the endpoint, the provider's response, and a status code or failure reason. Those reasons are the actionable data: invalid token or registration, mismatched sender or topic, payload too large, authentication failure, and provider throttling each imply a different fix. Pair this with the CloudWatch metrics <code>NumberOfNotificationsDelivered</code> and <code>NumberOfNotificationsFailed</code> dimensioned by <strong>Application</strong> — so you can see one platform degrade independently — and with your own event-notification feed for disablement rate.</p>\n<p style=\"line-height: 1.75\">Be honest in an interview about the ceiling of this telemetry. A \"delivered\" status means <strong>the push provider accepted the message</strong>. It does not mean the device received it, and it certainly does not mean the user saw it. The device may be offline (APNs and FCM store-and-forward with their own retention and collapse rules), the user may have notifications disabled at the OS level, the notification may be silently dropped by a background-activity limiter, or the user may swipe it away without reading. The only true measure of delivery is <strong>client-side acknowledgement</strong>: the app reports back on receipt and on open, and you compute the real funnel from published to provider-accepted to client-acked to opened. Teams that report \"push delivery rate\" using only SNS metrics are measuring the first hop and calling it the journey.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Credential rotation as a recurring outage cause</h4>\n<p style=\"line-height: 1.75\">APNs <strong>certificates expire annually</strong>, and the resulting outage is total, sudden and platform-wide: every publish to that platform application fails at once. It is one of the most reliably recurring self-inflicted outages in mobile engineering, because the expiry date is a year away when the certificate is installed and nobody owns the calendar entry. Mitigations, in order of value: migrate to <strong>token-based APNs authentication</strong> with a <code>.p8</code> key, which does not expire (though it can be revoked, and you should still track which key ID is in use); store credentials in <strong>Secrets Manager</strong> and update the platform application's attributes from there so rotation is a deployment rather than a console operation; run a <strong>synthetic canary</strong> that publishes to a test endpoint on every platform application every few minutes and alarms on failure, which catches expiry, revocation and misconfiguration equally; and alarm on a sharp rise in <code>NumberOfNotificationsFailed</code> per application. You give it an endpoint and a payload and it sends. It has no concept of a user profile, a segment, a campaign, a schedule, a journey, an A/B test, or an engagement funnel — you build all of that. That is exactly right for <strong>transactional</strong> notifications tightly coupled to a backend event: your order shipped, someone messaged you, a threshold alarm fired. Choose <strong>AWS End User Messaging push</strong> (the service that absorbed Amazon Pinpoint's messaging capability) when the requirement is marketing- or lifecycle-shaped: audience segmentation on user attributes and behaviour, scheduled and triggered campaigns, multi-step journeys, A/B testing of copy, per-channel opt-in management, and built-in open and engagement analytics. It also unifies push with SMS, email and in-app across one user profile, which SNS does not attempt. The usual mature architecture runs <strong>both</strong>: SNS for the transactional path where latency and simplicity matter, End User Messaging for the engagement path where segmentation and analytics matter, with a shared token-registration pipeline feeding endpoints to whichever is appropriate.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Production scenario: push delivery quietly degrading</h4>\n<p style=\"line-height: 1.75\">Over eight weeks, iOS push delivery rate has drifted from 94% to 71%.
