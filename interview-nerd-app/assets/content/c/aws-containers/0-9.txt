{"title":"What Is Amazon EKS — Managed Kubernetes on AWS","tags":["aws","eks","kubernetes","containers"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\"><strong>Amazon EKS</strong> (Elastic Kubernetes Service) is AWS running <strong>Kubernetes</strong> for you. To understand what that sentence means — and why EKS costs what it costs, and why people still complain about how much work it is — you first need to know what Kubernetes is and, crucially, which half of it AWS takes off your hands.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What Kubernetes is, in plain words</h4>\n<p style=\"line-height: 1.75\">A <strong>container</strong> is an application packaged with everything it needs to run, so it behaves the same on a laptop and on a server. Once you have more than a handful of containers across more than one machine, somebody has to decide which machine each container runs on, restart it when it dies, replace it when a machine fails, and route traffic to wherever it currently lives. Doing that by hand does not scale.</p>\n<p style=\"line-height: 1.75\"><strong>Kubernetes</strong> (often abbreviated <strong>K8s</strong> — eight letters between K and s) is an open-source system that does all of that automatically across a group of machines, called a <strong>cluster</strong>. It was born at Google, donated to the Cloud Native Computing Foundation, and became the industry standard. That last fact is the real reason people choose it: the same manifests, the same <code>kubectl</code> commands and the same Helm charts work on AWS, Google Cloud, Azure, a bare-metal rack in a data centre, or a laptop. Your skills and tooling <strong>transfer</strong>.</p>\n<p style=\"line-height: 1.75\">The price of that portability is complexity. Kubernetes is deliberately general and extensible, which means many more concepts than ECS: pods, deployments, services, ingresses, namespaces, controllers, custom resources, and an ecosystem of add-ons you must choose, install and keep current. ECS gives you a smaller vocabulary and native AWS integration; Kubernetes gives you a larger vocabulary and an enormous portable ecosystem.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The architecture split that explains everything</h4>\n<p style=\"line-height: 1.75\">Every Kubernetes cluster has two clearly separated halves. You submit it once, and <strong>controllers</strong> (background loops inside the control plane, each watching one kind of object) compare desired state to actual state forever and act on any difference. It never talks to your containers directly — it sends HTTPS requests to the <strong>API server</strong>, which records your intent, after which controllers and kubelets make it real. Its config lives in a file called the <strong>kubeconfig</strong>, normally at <code>~/.kube/config</code>, listing clusters, credentials and contexts.</p>\n<p style=\"line-height: 1.75\">EKS authentication has two distinct steps that beginners blur together:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Authentication — who are you?</strong> <code>aws eks update-kubeconfig</code> writes a kubeconfig entry that tells kubectl to run <code>aws eks get-token</code> before each request. That command uses your ordinary AWS credentials to mint a short-lived, signed token, which kubectl sends as a bearer token. The API server verifies it with AWS and learns your IAM identity.</li>\n<li><strong>Authorization — what may you do?</strong> Kubernetes does not understand IAM ARNs natively, so the IAM identity must be mapped to a Kubernetes user or group, which is then granted permissions through <strong>RBAC</strong> (role-based access control) objects.</li>\n</ul>\n<p style=\"line-height: 1.75\">There are two mechanisms for that mapping, and being accurate about both is worth marks in an interview:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>The aws-auth ConfigMap (older).</strong> A ConfigMap named <code>aws-auth</code> in the <code>kube-system</code> namespace lists IAM roles and users and the Kubernetes groups they map to. It is edited with kubectl, which creates a famous chicken-and-egg problem: a syntax error can lock everyone out, and you must already have cluster access to fix it.</li>\n<li><strong>EKS access entries (newer).</strong> You manage the mapping through the AWS API and console instead (<code>aws eks create-access-entry</code>), optionally attaching AWS-defined <strong>access policies</strong> such as cluster admin or view. Because it is an AWS control-plane API, it is auditable in CloudTrail, controllable with IAM, and survives a broken ConfigMap. A cluster's <strong>authentication mode</strong> can be the ConfigMap only, access entries only, or both.</li>\n</ul>\n<p style=\"line-height: 1.75\">One more accurate detail: whoever created the cluster gets administrative access automatically, which is why \"it works for me but my teammate gets Forbidden\" is such a common early experience.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Creating a cluster</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>eksctl.</strong> A community CLI, purpose-built for EKS.
