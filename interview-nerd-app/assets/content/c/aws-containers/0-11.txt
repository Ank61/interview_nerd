AWS runs, patches and backs up that brain for you across multiple data centres. What AWS does <em>not</em> automatically give you is the muscle: the actual compute capacity where your containers run. A brand-new EKS cluster with no compute attached is a perfectly healthy cluster that can run exactly zero applications.</p>\n<p style=\"line-height: 1.75\">A quick vocabulary check before we go further, because these three words appear in every sentence below. A <strong>container</strong> is your application plus its dependencies packaged into one runnable unit. A <strong>pod</strong> is Kubernetes' smallest deployable thing: one or more containers that always run together on the same machine and share a network address. A <strong>node</strong> is a machine (on AWS, an EC2 virtual server) that has joined the cluster and is willing to run pods.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">  AWS manages this            You provide this\n<i class=o>+</i><i class=c>---------------------+     +------------------------+</i>\n<i class=o>|</i>   EKS CONTROL PLANE <i class=o>|</i>     <i class=o>|</i>   COMPUTE CAPACITY     <i class=o>|</i>\n<i class=o>|</i>  API server         <i class=o>|</i> <i class=c>--&gt; |  Managed node group    |</i>\n<i class=o>|</i>  etcd (state store) <i class=o>|</i>     <i class=o>|</i>  Self<i class=o>-</i>managed nodes    <i class=o>|</i>\n<i class=o>|</i>  scheduler          <i class=o>|</i>     <i class=o>|</i>  Fargate (<i class=k>no</i> nodes)    <i class=o>|</i>\n<i class=o>+</i><i class=c>---------------------+     +------------------------+</i>\n       &quot;decides&quot;                    &quot;actually runs&quot;</code></pre></div>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Option 1: Managed node groups</h4>\n<p style=\"line-height: 1.75\">A <strong>managed node group</strong> is a set of EC2 instances that EKS creates and looks after on your behalf. Under the hood it builds an <strong>Auto Scaling group</strong> — an AWS feature that keeps a chosen number of identical EC2 instances running and replaces any that die. EKS wires that group up so every instance boots from an EKS-optimized <strong>AMI</strong> (an Amazon Machine Image: the disk template an EC2 instance starts from, here pre-loaded with the container runtime and the Kubernetes agent), automatically registers itself with your cluster, and appears as a ready node.</p>\n<p style=\"line-height: 1.75\">What you choose is the shape of the machines. The <strong>instance type</strong> is the hardware family and size — for example a general-purpose <code>m6i.large</code> with balanced CPU and memory, a compute-heavy <code>c6i</code>, or a memory-heavy <code>r6i</code>. Bigger instances pack more pods per machine and waste less on per-node overhead, but a single failure removes more capacity at once and very large pods may not fit neatly. A practical starting rule: pick a size where your typical pod uses roughly a tenth to a quarter of the node, so the scheduler has room to place things.</p>\n<p style=\"line-height: 1.75\">An <strong>Availability Zone</strong> (AZ) is an isolated group of data centres inside a Region. A single node group can span several AZs, and for stateless web apps that is fine and simple. But if your pods mount <strong>EBS volumes</strong> (network-attached disks that live in exactly one AZ), a pod that gets rescheduled into a different AZ cannot reattach its disk. The common pattern there is one node group per AZ, so the autoscaler can grow capacity in the specific zone where the disk lives.</p>\n<p style=\"line-height: 1.75\">Managed node groups also give you <strong>assisted upgrades</strong>. When a new Kubernetes version or AMI is available, you trigger the update and EKS performs a rolling replacement: it launches new nodes, then <strong>cordons</strong> each old node (marks it as \"no new pods here\") and <strong>drains</strong> it (politely evicts the running pods so they restart elsewhere) before terminating it. It respects a <strong>PodDisruptionBudget</strong> — a rule you write saying \"never take more than one replica of this app down at a time\".</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Still your job.</strong> Deciding <em>when</em> to upgrade; EKS never upgrades a node group on its own.</li>\n<li><strong>Still your job.</strong> Sizing, capacity headroom, and installing an autoscaler (nothing scales nodes by default).</li>\n<li><strong>Still your job.</strong> Node-level security posture: what you install on the node, and your container images.</li>\n<li><strong>Still your job.</strong> Writing PodDisruptionBudgets and graceful shutdown handling so drains do not cause user-visible errors.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Option 2: Self-managed nodes</h4>\n<p style=\"line-height: 1.75\">Here you create the EC2 instances yourself — your own launch template, your own Auto Scaling group — and run a <strong>bootstrap script</strong> (a start-up script that tells the node which cluster to join and passes settings to the Kubernetes agent). Nothing about the node's life cycle is handled for you.</p>\n<p style=\"line-height: 1.75\">People choose this when they genuinely need it: a custom or hardened AMI mandated by a security team, an operating system EKS does not offer a managed image for, unusual kernel tuning, licensed software baked into the image, or specialised hardware and boot-time configuration. The trade is real operational cost: you own AMI patching, the upgrade choreography, and the drain logic that managed groups give you for free. For most teams this is the option you should be able to <em>describe</em> in an interview and rarely need to pick.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Option 3: Fargate for EKS</h4>\n<p style=\"line-height: 1.75\"><strong>Fargate</strong> is <strong>serverless</strong> compute — \"serverless\" here does not mean there is no server, it means AWS owns, patches and scales the servers and you never see or log into them. With EKS on Fargate there are no nodes in your account at all. You ask for a pod; AWS quietly starts a right-sized, isolated micro-VM for exactly that pod and bills you for the CPU and memory it requested, for as long as it runs.</p>\n<p style=\"line-height: 1.75\">How does Kubernetes know a pod should go to Fargate instead of an EC2 node? Through a <strong>Fargate profile</strong>: a small piece of cluster configuration that lists one or more <strong>selectors</strong>, each of which is a <strong>namespace</strong> (a folder-like partition of the cluster) plus optional <strong>labels</strong> (key/value tags on a pod). Any pod whose namespace and labels match a selector is scheduled onto Fargate. A pod that matches no profile and has no node available simply stays <strong>Pending</strong> forever. Fargate profiles are therefore mandatory, not optional polish.</p>\n<div class=\"code\"><div class=\"code-head\"><span>java</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">Fargate profile <i class=s>&quot;web&quot;</i>\n  selector: namespace = production, labels = { compute: fargate }\n\n  pod <i class=t>A</i>  <i class=v>ns</i><i class=o>=</i><i class=t>production</i>  <i class=v>labels</i><i class=o>=</i>{compute: fargate}  --&gt; runs on Fargate\n  pod <i class=t>B</i>  <i class=v>ns</i><i class=o>=</i><i class=t>production</i>  <i class=v>labels</i><i class=o>=</i>{}                  --&gt; needs an EC2 node\n  pod <i class=t>C</i>  <i class=v>ns</i><i class=o>=</i>kube-<i class=t>system</i> <i class=v>labels</i><i class=o>=</i>{compute: fargate}  --&gt; needs an EC2 node</code></pre></div>\n<p style=\"line-height: 1.75\">Each Fargate pod gets its own <strong>elastic network interface</strong> (a virtual network card) with an IP address from your private subnets. That gives strong isolation and normal VPC security-group behaviour, but it also means a large fleet of Fargate pods consumes a lot of subnet IP addresses — plan subnet sizing accordingly. Fargate pods must run in private subnets and reach ECR and other AWS services through a NAT gateway or VPC endpoints.</p>\n<p style=\"line-height: 1.75\">Because there is no node you control, several Kubernetes features do not apply:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>No DaemonSets.</strong> A DaemonSet is \"run exactly one copy of this pod on every node\" — used for log collectors and monitoring agents. With no nodes, that idea has no meaning, so on Fargate you run those agents as <strong>sidecars</strong> instead: extra containers placed inside the same pod as your app.</li>\n<li><strong>No privileged containers.</strong> A privileged container has near-root access to the host kernel; Fargate never allows it, so tools that need it will not run.</li>\n<li><strong>No GPUs</strong> and no exotic instance families. ML training and GPU inference need EC2 nodes.</li>\n<li><strong>Per-pod resource ceilings.</strong> Fargate offers fixed CPU/memory combinations up to a defined maximum per pod; very large single pods do not fit, and your pod is billed at the next supported size up from what it requests, plus a small allowance for Kubernetes components.</li>\n<li><strong>Storage limits.</strong> Each pod gets a bounded amount of ephemeral (temporary, disappears when the pod stops) disk. EFS, a shared network file system, is supported for persistence; EBS volumes are not attachable to Fargate pods.</li>\n<li><strong>No node access.</strong> No SSH, no host-level agents, no hostPath volumes.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Two layers of scaling, and why both exist</h4>\n<p style=\"line-height: 1.75\">Beginners routinely blur these together. They solve different problems and you usually need both.</p>\n<p style=\"line-height: 1.75\"><strong>Pod-level scaling — the Horizontal Pod Autoscaler (HPA).</strong> The HPA watches a metric such as average CPU across your pods and changes the <em>number of pod copies</em>. Traffic doubles, CPU climbs, HPA goes from 4 replicas to 8. It needs the <strong>metrics-server</strong> add-on installed to read those numbers, and it needs your pods to declare CPU <strong>requests</strong> (the amount each pod reserves) — without requests there is no baseline to compute a percentage against.</p>\n<p style=\"line-height: 1.75\"><strong>Node-level scaling.</strong> The HPA can ask for 8 pods, but if the existing nodes are full those extra pods sit in <strong>Pending</strong> with a \"no nodes available\" event. Something must add machines:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Cluster Autoscaler.</strong> The classic tool. It watches for Pending pods and increases the desired count of an Auto Scaling group; when nodes sit underused it scales back down. It works within the instance types you predefined, so a pod needing an unusual shape may have nowhere good to go.</li>\n<li><strong>Karpenter.</strong> An AWS-built alternative that talks to EC2 directly. Instead of resizing predefined groups, it looks at the exact Pending pods and launches a right-sized instance just in time — often a better fit, faster, and it will consolidate workloads onto fewer nodes as demand drops. You define broad constraints (allowed families, architectures, zones, Spot or On-Demand) and it picks.</li>\n</ul>\n<div class=\"code\"><div class=\"code-head\"><span>yaml</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=s>traffic</i> <i class=s>up</i>\n   <i class=s>|\n   v\n</i>[ <i class=s>HPA</i> ]  <i class=n>4</i> <i class=s>pods</i> <i class=s>--&gt;</i> <i class=n>8</i> <i class=s>pods</i>\n   <i class=s>|\n   v  (4 pods Pending: no room)\n</i>[ <i class=s>Cluster</i> <i class=s>Autoscaler</i> <i class=s>/</i> <i class=s>Karpenter</i> ]  <i class=n>3</i> <i class=s>nodes</i> <i class=s>--&gt;</i> <i class=n>5</i> <i class=s>nodes</i>\n   <i class=s>|\n   v\n</i><i class=s>pods</i> <i class=s>scheduled,</i> <i class=s>traffic</i> <i class=s>served</i></code></pre></div>\n<p style=\"line-height: 1.75\">On Fargate you skip the node layer entirely: the HPA asks for more pods and AWS supplies capacity per pod. That simplicity is a large part of Fargate's appeal.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Spot instances and interruption handling</h4>\n<p style=\"line-height: 1.75\"><strong>Spot</strong> instances are spare EC2 capacity sold at a steep discount on the condition that AWS may reclaim them with about two minutes' notice. For fault-tolerant, stateless, replicated workloads this is one of the biggest cost levers available. Managed node groups support a Spot capacity type, and Karpenter can mix Spot and On-Demand.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Diversify instance types.</strong> Allow several families and sizes so a shortage in one pool does not empty your cluster.</li>\n<li><strong>Handle the notice.</strong> Managed node groups and Karpenter watch for the interruption warning and cordon and drain the node within that window; Karpenter also proactively replaces nodes with rebalance recommendations.</li>\n<li><strong>Design the app.</strong> Multiple replicas, PodDisruptionBudgets, spread across zones, and graceful shutdown on SIGTERM — the polite \"please stop\" signal.</li>\n<li><strong>Keep critical pieces On-Demand.</strong> Run cluster-critical add-ons and stateful singletons on On-Demand nodes.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cost: what you are actually billed for</h4>\n<p style=\"line-height: 1.75\">EKS charges a <strong>flat hourly fee per cluster</strong> for the managed control plane, regardless of how many pods you run — so ten tiny clusters cost ten times that fee, which is why teams consolidate environments into namespaces rather than spinning up a cluster per team. On top of that you pay for compute: EC2 instance-hours (whether or not the instances are busy) or Fargate's per-pod CPU and memory for the duration each pod runs, plus the usual storage, load balancer and data transfer charges.</p>\n<p style=\"line-height: 1.75\">The <strong>utilization argument</strong> is the heart of the EC2-versus-Fargate cost debate. EC2 per unit of CPU is cheaper, but you pay for the whole instance including the empty space. Fargate's per-unit rate is higher, but you only pay for what each pod asked for. If you bin-pack nodes well and keep them busy — say 70-80% utilized around the clock — EC2 wins clearly.
