Every container writes to two output streams: <strong>stdout</strong> (\"standard out\", normal messages) and <strong>stderr</strong> (\"standard error\", error messages). The <strong>awslogs</strong> driver captures both and forwards each line to <strong>CloudWatch Logs</strong>, AWS's managed log storage and search service. You enable it per container inside the <strong>task definition</strong> — the JSON blueprint describing how your containers run.</p>\n<p style=\"line-height: 1.75\">CloudWatch Logs organises data in two levels. A <strong>log group</strong> is a named bucket, usually one per application, where you set retention and permissions. First, permissions: the <strong>task execution role</strong> — the IAM role ECS itself assumes to set the task up, distinct from the <strong>task role</strong> your application code uses — must be allowed to create log streams and put log events. Second, the log group must exist, unless you set <code>awslogs-create-group</code> to true.</p>\n<p style=\"line-height: 1.75\">The classic beginner failure is a task that starts and immediately stops with a stopped reason mentioning a <strong>ResourceInitializationError</strong> and a logging configuration problem, and no logs anywhere to explain it. The container never ran: ECS could not set up logging, so it refused to start it. The usual causes are a missing or misspelled log group, a region mismatch, an execution role missing <code>logs:CreateLogStream</code> and <code>logs:PutLogEvents</code>, or a Fargate task in a private subnet with no route to the CloudWatch Logs endpoint — no NAT gateway and no VPC endpoint. That last one also breaks image pulls, so it often shows up as both symptoms at once.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">FireLens and Fluent Bit on ECS</h4>\n<p style=\"line-height: 1.75\">The awslogs driver is deliberately simple: every line goes to CloudWatch Logs, unchanged. When you need more — send to a third-party platform, split logs by severity, drop noisy health-check lines, or parse text into fields — you use <strong>FireLens</strong>. FireLens is not itself a log processor; it is an ECS feature that runs a log-router container alongside your app container in the same task and wires your app's output into it. That router is normally <strong>Fluent Bit</strong>, a lightweight open-source log processor. A container that runs beside your app in the same task purely to support it is called a <strong>sidecar</strong>.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Route anywhere.</strong> CloudWatch Logs, Amazon Kinesis Data Firehose, OpenSearch, S3, or vendors such as Datadog and Splunk.</li>\n<li><strong>Filter and enrich.</strong> Drop debug noise before it becomes billable, add fields like environment or version.</li>\n<li><strong>Fan out.</strong> Errors to a paging platform, everything to cheap S3 archive.</li>\n<li><strong>Cost.</strong> The sidecar consumes a little CPU and memory in every task, so keep it small.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">EKS logging: Fluent Bit DaemonSet and control plane logs</h4>\n<p style=\"line-height: 1.75\">Kubernetes has no built-in mechanism for shipping logs off the cluster. On an EC2 node, the container runtime writes each container's stdout and stderr to files under <code>/var/log</code> on the node, and <code>kubectl logs</code> reads them from there — which is why logs vanish when the node is replaced or the file is rotated. To keep them, you run <strong>Fluent Bit</strong> as a <strong>DaemonSet</strong>: a Kubernetes object that guarantees exactly one copy of a pod on every node. That one collector per node tails all the container log files, attaches Kubernetes metadata (namespace, pod name, labels) and ships everything to CloudWatch Logs or elsewhere. On Fargate, where there are no nodes, you instead enable the built-in Fargate log router by creating a ConfigMap in the <code>aws-observability</code> namespace.</p>\n<p style=\"line-height: 1.75\"><strong>Control plane logging</strong> is a completely separate thing and is off by default. It covers the Kubernetes components AWS runs for you — the API server, the audit log (who called what), the authenticator, the controller manager and the scheduler. You switch on the categories you want on the cluster, and they flow to a CloudWatch log group. The audit log is what answers \"who deleted that deployment\", so security-conscious teams turn it on despite the ingestion cost. It tells you nothing about your application, and your application logging tells you nothing about the control plane — you need both.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Log to stdout, as structured JSON</h4>\n<p style=\"line-height: 1.75\">The single most valuable habit: your application should write to <strong>stdout</strong>, not to a file inside the container, and each line should be a JSON object rather than free text. Files inside a container need extra machinery to collect, fill the container's disk, and vanish on crash. Stdout is picked up by every log driver and collector for free.</p>\n<p style=\"line-height: 1.75\"><strong>Structured logging</strong> means emitting <code>{\"level\":\"error\",\"msg\":\"payment failed\",\"order_id\":\"A-1029\",\"duration_ms\":812}</code> instead of a prose sentence. CloudWatch Logs Insights, the query language over your logs, can then filter and aggregate on those fields directly — average duration by endpoint, error counts by order, and so on. With free text you are reduced to substring matching. Two practical rules: never log secrets, card numbers or tokens, since logs are widely readable; and put multi-line stack traces into a single JSON field so they stay one log event instead of fragmenting into dozens.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Metrics: the basics and Container Insights</h4>\n<p style=\"line-height: 1.75\">A <strong>metric</strong> is a number sampled over time — CPU percentage, memory used, request count. Out of the box, ECS publishes a small free set to CloudWatch: <strong>CPUUtilization</strong> and <strong>MemoryUtilization</strong> at the <strong>service</strong> level (averaged across the running tasks of that service) and at the <strong>cluster</strong> level, plus counts of running and pending tasks.</p>\n<p style=\"line-height: 1.75\">Crucially, those two levels mean different things. At service level, utilization is measured against what your tasks <em>reserved</em> — so 90% means your tasks are working hard. At cluster level for EC2 capacity, it is measured against the total capacity of the container instances — so 20% means most of your fleet is idle. A cluster at 20% can contain a service at 95% that is falling over. Autoscale on the service metric; use the cluster metric for capacity planning.</p>\n<p style=\"line-height: 1.75\"><strong>Container Insights</strong> is the paid, deeper layer. Enabled per ECS cluster or installed as an agent on EKS, it collects per-task, per-pod and per-container CPU, memory, disk and network metrics, plus performance log events and automatic dashboards and maps. It answers questions the basic metrics cannot: which single container in a three-container task is eating the memory, which pod restarted eleven times last night. It is billed as custom metrics and ingested log data, and the cost scales with the number of tasks, pods and containers — which is why teams sometimes enable it in production only, or use the newer enhanced observability selectively.</p>\n<h4 style=\"margin-top: 1.5rem; Readiness failing is normal and temporary: the app is warming a cache or a downstream dependency is briefly slow, so stop sending requests and try again shortly. Liveness failing is a death sentence. Pointing a liveness probe at an endpoint that also checks your database means a database blip restarts every pod simultaneously, turning a small problem into a full outage. Keep liveness shallow (\"am I alive?\") and readiness meaningful (\"are my dependencies usable?\"). A <strong>startup probe</strong> exists for slow-booting apps so liveness does not kill them during a long start.</p>\n<p style=\"line-height: 1.75\">On ECS the same logic applies across two systems: the container health check restarts unhealthy tasks, the load balancer check decides what receives traffic. Open the stopped task in the console or run <code>aws ecs describe-tasks</code> and read two fields: the task-level <strong>stoppedReason</strong> and, for each container, the numeric <strong>exitCode</strong>. Between them they identify most failures:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>CannotPullContainerError.</strong> Wrong image name or tag, no ECR permission on the execution role, or no network path to ECR from a private subnet.</li>\n<li><strong>Exit code 137 — out-of-memory kill.</strong> The container exceeded its memory limit and the kernel killed it. Raise the limit or fix the leak; 137 means SIGKILL.</li>\n<li><strong>ResourceInitializationError on secrets.</strong> The execution role lacks <code>secretsmanager:GetSecretValue</code> or the KMS decrypt permission, so the task never starts.</li>\n<li><strong>Port mismatch.</strong> The app listens on 3000 but the container port or target group port says 8080; the load balancer health check fails and tasks churn endlessly.</li>\n<li><strong>Failing health check.</strong> Tasks start, get marked unhealthy, are replaced, forever — often because the health path needs auth or the grace period is too short.</li>\n<li><strong>Exit code 1.</strong> Your application itself crashed on startup — a missing environment variable, a bad config file, an unreachable database. Pod statuses translate directly:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Pending.</strong> Not scheduled anywhere. It is a symptom, never a cause: read the logs of the previous run.</li>\n<li><strong>OOMKilled in Last State.</strong> Memory limit exceeded — the Kubernetes twin of exit code 137.</li>\n<li><strong>Running but 0/1 Ready.</strong> The readiness probe is failing, so the process is alive but receives no traffic.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Getting a shell inside a running container</h4>\n<p style=\"line-height: 1.75\">Sometimes logs are not enough and you need to look around from the inside — check whether a config file rendered correctly, or test DNS resolution to a database. <strong>ECS Exec</strong> gives you an interactive shell in a running ECS container, including on Fargate, using AWS Systems Manager rather than SSH.
