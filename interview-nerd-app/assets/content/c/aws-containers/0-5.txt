Each one is then a <strong>container instance</strong>. Your responsibilities are real and ongoing:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>The AMI.</strong> An <em>AMI (Amazon Machine Image)</em> is the disk image an EC2 instance boots from. You normally use the <strong>ECS-optimized AMI</strong>, which already includes a container runtime and the <strong>ECS agent</strong> — a small program on each instance that registers it with the cluster, receives instructions from ECS, starts and stops containers, and reports status back.</li>\n<li><strong>An Auto Scaling group.</strong> This is the AWS feature that keeps a chosen number of EC2 instances alive, replacing failed ones and adding or removing instances as demand changes. You need one even for a fixed-size cluster, otherwise a failed instance is never replaced.</li>\n<li><strong>Instance type choice.</strong> How much CPU, memory, network bandwidth, whether you need GPUs, ARM (Graviton) or x86. Getting the shape wrong wastes money in one dimension while running out in another.</li>\n<li><strong>Patching and security of the OS.</strong> Kernel CVEs, agent upgrades, replacing instances to pick up new AMIs. AWS will not do this for you.</li>\n<li><strong>Capacity monitoring.</strong> If the cluster has no free CPU or memory, new tasks sit in PENDING. That is now your problem to detect and fix.</li>\n</ul>\n<p style=\"line-height: 1.75\">The billing model matters: you pay for each instance for every second it is running, regardless of whether tasks are using it. An instance at 15% utilization costs exactly the same as one at 90%.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Fargate launch type: you declare a size and stop thinking</h4>\n<p style=\"line-height: 1.75\">With Fargate you do not create instances at all. In the task definition you declare a CPU value and a compatible memory value — for example 1 vCPU and 2 GB — and ECS runs that task on AWS-managed infrastructure you never see, log into, size, or patch. There is no AMI to choose, no ECS agent to upgrade, no Auto Scaling group for capacity, no cluster to keep full.</p>\n<p style=\"line-height: 1.75\">Billing is per task: you pay for the vCPU and memory you <em>requested</em>, for the time the task runs, per second with a small minimum duration. That has a sharp consequence — <strong>over-requesting is pure waste</strong>. A task that asks for 4 vCPU and uses 0.3 costs the same as one that genuinely needs 4.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The honest comparison</h4>\n<div style=\"overflow-x: auto; ECS uses <strong>placement strategies</strong> to decide where a task goes — <code>binpack</code> fills instances as tightly as possible to minimise the number of instances needed, <code>spread</code> distributes tasks across Availability Zones or instances for resilience, and <code>random</code> does what it says. Most production clusters use spread across AZs first, then binpack on memory within an AZ.</p>\n<p style=\"line-height: 1.75\">Why it matters financially: on EC2 you pay for whole instances. Suppose you run 4 instances with 8 GB each (32 GB paid for) and 10 tasks needing 1 GB each (10 GB used). You are paying for 32 GB and using 10 — roughly 31% utilization, so your <em>effective</em> price per useful GB is over three times the sticker price. That single number is why \"EC2 is cheaper than Fargate\" is only sometimes true. A cluster at 75–85% utilization genuinely beats Fargate on cost; a cluster at 25% almost never does.</p>\n<p style=\"line-height: 1.75\">Two structural things stop you packing tightly: reserved headroom for deployments (your maximumPercent needs somewhere to put extra tasks) and awkward task shapes (a 5 GB task simply will not fit into the 3 GB left on each instance — this is called fragmentation).</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Capacity providers: the modern way to express the choice</h4>\n<p style=\"line-height: 1.75\">Setting <code>--launch-type FARGATE</code> or <code>--launch-type EC2</code> still works, but it is the older, blunter interface — it says \"use this one kind of capacity\". A <strong>capacity provider</strong> is a named source of compute attached to a cluster, and it lets you describe a mix.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>FARGATE.</strong> Built in on every cluster. Standard on-demand Fargate capacity.</li>\n<li><strong>FARGATE_SPOT.</strong> Built in too. Spare AWS capacity at a large discount, but AWS can reclaim a task with a warning (it sends a SIGTERM and a roughly two-minute grace period). Perfect for stateless workers, batch jobs and queue consumers; wrong for a task that cannot be interrupted mid-operation.</li>\n<li><strong>Auto Scaling group capacity providers.</strong> You create one by pointing at an EC2 Auto Scaling group. With <strong>managed scaling</strong> enabled, ECS itself measures how much capacity your pending tasks need and drives the ASG's size to meet it, aiming at a <em>target capacity</em> percentage (e.g. 100 means pack fully, 80 leaves 20% headroom for fast task placement). With <strong>managed termination protection</strong>, ECS prevents the ASG from terminating an instance that still has tasks on it, so scale-in does not kill running work.</li>\n</ul>\n<p style=\"line-height: 1.75\">A <strong>capacity provider strategy</strong> blends providers using two knobs:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>base.</strong> A fixed number of tasks that must run on this provider before anything else is considered. Only one provider in a strategy may have a non-zero base.</li>\n<li><strong>weight.</strong> The ratio for splitting all remaining tasks.</li>\n</ul>\n<div class=\"code\"><div class=\"code-head\"><span>java</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">Strategy: <i class=t>FARGATE</i>      <i class=v>base</i><i class=o>=</i><i class=n>2</i>  weight=<i class=n>1</i>\n          <i class=t>FARGATE_SPOT</i> <i class=v>base</i><i class=o>=</i><i class=n>0</i>  weight=<i class=n>4</i>\n\n<i class=t>desired</i> <i class=v>count</i> <i class=o>=</i> <i class=n>12</i>\n  step <i class=n>1</i>: base -&gt; font-size: 1.25rem; font-weight: 600\">Mixing both in one cluster</h4>\n<p style=\"line-height: 1.75\">A single ECS cluster can contain both EC2 container instances and Fargate tasks, and mature teams routinely exploit that:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Steady baseline on EC2, bursts on Fargate.</strong> Keep a well-packed reserved-instance or Savings-Plan-covered EC2 fleet for the traffic you always have, and let peak traffic overflow onto Fargate so you never buy hardware for the once-a-day spike.</li>\n<li><strong>Special workloads on EC2, everything else on Fargate.</strong> The GPU inference service and the per-host log collector daemon must be EC2; the twelve ordinary microservices are happier on Fargate.</li>\n<li><strong>Production on-demand, non-production on Spot.</strong> Dev and CI runners on FARGATE_SPOT or EC2 Spot, production on stable capacity.</li>\n<li><strong>Migration path.</strong> Teams often start on Fargate to ship quickly, then move the few genuinely high-utilization services onto EC2 once the bill justifies the operational work — not the other way around.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Choosing, in practice</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Pick Fargate when</strong> your team is small or has no dedicated ops capacity, traffic is spiky or unpredictable, you have relatively few tasks, you value task-level isolation, or you simply do not want to own patching.</li>\n<li><strong>Pick EC2 when</strong> you need GPUs or specific instance families, you run daemon workloads or privileged containers, you need task sizes beyond Fargate's menu, you have very high steady utilization you can genuinely bin-pack, or you have deep Savings Plan / Reserved Instance commitments to absorb.</li>\n<li><strong>Do not</strong> pick EC2 purely because the per-hour sticker price is lower. Multiply by your real utilization, and add the engineer-hours of patching, before you call it cheaper.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"Fargate is always more expensive.\"</strong> Per vCPU-hour, yes. In total, often no. EC2 only wins once you keep instances genuinely full — at 30% utilization your effective cost per useful vCPU triples, and Fargate wins comfortably. Add the unpriced engineering time spent on AMIs and scaling.</li>\n<li><strong>\"Fargate is a different service from ECS.\"</strong> No. Fargate is a compute engine <em>used by</em> ECS (and EKS). You still create ECS clusters, task definitions and services; only the placement target changes.</li>\n<li><strong>\"I can SSH into a Fargate task's host.\"</strong> There is no host you can reach — that is the deal. For debugging you use <strong>ECS Exec</strong>, which opens a shell <em>inside your running container</em>, not on the machine underneath.</li>\n<li><strong>\"EC2 launch type means I do not need an Auto Scaling group.\"</strong> You almost always do. Without one, a failed instance is never replaced and capacity never grows; you are back to hand-managed servers with extra steps.</li>\n<li><strong>\"Spot means unreliable, so avoid it.\"</strong> Spot is excellent for stateless, retryable, interruption-tolerant work. Services, deployments and logging are unchanged.</li>\n<li><strong>\"More tasks always means more instances.\"</strong> Not on Fargate — there are no instances of yours.
