{"title":"ECS Services — Keeping Containers Running and Deploying Changes","tags":["ecs","services","deployments","auto-scaling"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Imagine you have copied your app onto a server and started it by hand. It works — until the process crashes at 3am, or the server reboots, and nobody notices until customers complain. An <strong>ECS service</strong> is the thing that removes that 3am phone call. You tell it \"I always want 4 copies of this container running\", and it watches your cluster forever, replacing any copy that dies. That is genuinely the whole idea, and everything else in this topic is a detail hanging off it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">First, the vocabulary</h4>\n<p style=\"line-height: 1.75\">Three words come up constantly and they are easy to mix up. A <strong>task definition</strong> is the recipe — a JSON document saying which image to run, how much CPU and memory it gets, which ports it opens. A <strong>task</strong> is one running copy made from that recipe, like one running process. A <strong>service</strong> is the supervisor that keeps a chosen number of tasks alive.</p>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">TASK DEFINITION  <i class=o>-</i><i class=o>&gt;</i>  the recipe (image, CPU, memory, ports)   &quot;webapp:7&quot;\n       <i class=o>|</i>\n       <i class=o>|</i> service creates tasks <i class=k>from</i> it\n       v\nSERVICE          <i class=o>-</i><i class=o>&gt;</i>  the supervisor: &quot;keep 4 of these alive&quot;\n       <i class=o>|</i>\n   <i class=o>+</i><i class=c>---+---+---+---+</i>\n   v   v   v   v\n task task task task    <i class=o>&lt;</i><i class=o>-</i> actual <i class=k>running</i> containers</code></pre></div>\n<p style=\"line-height: 1.75\">The number you ask the service to maintain is called the <strong>desired count</strong>. It lives on the <em>service</em>, not on the task definition. If you set desired count to 4 and one task crashes, ECS notices that only 3 are running, compares that to the desired 4, and launches a brand new task to close the gap. Note the wording: a <em>brand new</em> task. ECS does not restart the broken container in place — it throws the dead one away and starts a fresh one from the same recipe.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Scheduler strategies: REPLICA and DAEMON</h4>\n<p style=\"line-height: 1.75\">The <strong>scheduler</strong> is the part of ECS that decides where and how many tasks to place. It has two strategies, and you pick one when you create the service.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>REPLICA.</strong> \"Run exactly N copies, spread across the cluster.\" This is the normal choice and what you will use for almost every web API, worker, or background job. You control N through the desired count. ECS tries to spread copies across Availability Zones (separate data centres in a region) so losing one zone does not take out every copy.</li>\n<li><strong>DAEMON.</strong> \"Run exactly one copy on every container instance in the cluster.\" A <em>container instance</em> is an EC2 virtual machine registered into your ECS cluster. You do not set a desired count for a daemon service — the count is simply \"however many instances there are\", and it goes up and down automatically as instances join or leave. This is for agents that must touch every host: a log shipper that tails files from the host, a metrics or monitoring collector, a security agent. DAEMON only applies to the EC2 launch type, because Fargate has no hosts of yours to place one copy on.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Putting a load balancer in front</h4>\n<p style=\"line-height: 1.75\">If your service is a web app, users need one stable address to hit, not four changing container IPs. That is a <strong>load balancer</strong> — usually an <strong>Application Load Balancer (ALB)</strong>, which understands HTTP and spreads incoming requests across your tasks.</p>\n<p style=\"line-height: 1.75\">A <strong>target group</strong> is simply the load balancer's list of destinations — the addresses it is currently willing to send traffic to. When ECS starts a new task, it <em>registers</em> that task into the target group; when it stops a task, it <em>deregisters</em> it. You never maintain that list by hand, which is the whole point.</p>\n<p style=\"line-height: 1.75\">The load balancer also runs a <strong>health check</strong>: it calls a URL on each target every few seconds (say <code>GET /health</code>) and only sends real traffic to targets that answer correctly. A target that fails several checks in a row is marked unhealthy, and ECS will stop that task and replace it.</p>\n<p style=\"line-height: 1.75\">Now the trap that catches nearly every beginner. Some apps take 60–90 seconds to boot — a JVM warming up, a framework running migrations, a big cache priming. During that time the health check fails, the load balancer says \"unhealthy\", and ECS dutifully kills the task and starts another one, which also takes 90 seconds, and also gets killed. Your service sits in an infinite restart loop and the logs look fine. The fix is the <strong>health check grace period</strong> — a number of seconds, set on the service, during which ECS ignores load balancer health check failures for a newly started task. Set it comfortably longer than your real cold start (e.g. 120 seconds for a 90-second boot) and the loop disappears.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">How a deployment actually happens</h4>\n<p style=\"line-height: 1.75\">You do not \"update the running container\". On EC2, extra tasks need spare room on your instances — if there is none, the deploy waits.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Connection draining and deregistration delay</h4>\n<p style=\"line-height: 1.75\">When ECS is ready to stop an old task, it first tells the load balancer to deregister it. The load balancer stops sending it <em>new</em> requests but lets requests already in flight finish. That waiting window is the <strong>deregistration delay</strong> (also called connection draining), set on the target group, defaulting to 300 seconds.</p>\n<p style=\"line-height: 1.75\">Without it, a user's half-finished upload or slow report would be cut off mid-response every single deploy. Tune it to slightly more than your slowest normal request: 30 seconds for a snappy JSON API, a few minutes for long downloads. Leaving it at 300 seconds for a fast API just makes every deploy needlessly slow. Separately, your container should handle <code>SIGTERM</code> (the polite \"please stop\" signal ECS sends) by finishing current work and exiting; if it ignores it, ECS waits out the stop timeout and then forcibly kills it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The deployment circuit breaker</h4>\n<p style=\"line-height: 1.75\">Suppose your new image has a typo in an environment variable and crashes on boot. ECS sees a task die, replaces it, that one dies too, forever. Without help, the service will sit there churning while you stare at the console.</p>\n<p style=\"line-height: 1.75\">The <strong>deployment circuit breaker</strong> watches how many new tasks have failed to reach a healthy state during a deployment. Past a threshold it declares the deployment FAILED and stops trying. If you also enable <strong>rollback</strong>, it goes one step further and automatically redeploys the last known-good task definition, so the service heals itself back to the previous version without a human. Turn both on for any service you care about — it converts a night-time outage into a failed pipeline step you read about in the morning.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Blue/green with CodeDeploy (orientation)</h4>\n<p style=\"line-height: 1.75\">Rolling updates mix old and new versions together for a few minutes. Sometimes you want a cleaner cut. With the <strong>CODE_DEPLOY</strong> deployment controller, AWS CodeDeploy stands up an entirely separate set of new tasks (the \"green\" set) alongside the current ones (\"blue\"), registered in a <em>second</em> target group. You can send test traffic to green through a separate test listener port, verify it, and then have the load balancer shift production traffic from blue to green — all at once, or gradually (for example 10% for 5 minutes, then the rest). Blue is kept running for a while, so rollback is a near-instant traffic switch back rather than a redeploy. The cost is complexity: two target groups, a CodeDeploy application and deployment group, and double capacity during the switch.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Two completely different kinds of scaling</h4>\n<p style=\"line-height: 1.75\">This distinction is asked in interviews constantly and confused by nearly everyone at first.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Service auto scaling</strong> changes the <em>desired count</em> — how many copies of your container run. It uses AWS Application Auto Scaling. The easiest form is <strong>target tracking</strong>: you name a metric and a target value (\"keep average CPU at 60%\") and AWS adds or removes tasks to hold it there, like a thermostat. Common metrics are <code>ECSServiceAverageCPUUtilization</code>, <code>ECSServiceAverageMemoryUtilization</code>, and <code>ALBRequestCountPerTarget</code> (requests per task per minute) — the last is often the best signal for web apps because it reacts to traffic directly rather than waiting for CPU to climb. There is also step scaling (CloudWatch alarm thresholds) and scheduled scaling (scale up at 08:00 on weekdays).</li>\n<li><strong>Cluster capacity scaling</strong> changes how many <em>EC2 instances</em> exist to host tasks. This is done by an Auto Scaling group, usually driven by an ECS <strong>capacity provider</strong> with managed scaling. It only exists for the EC2 launch type — on Fargate there is no cluster to scale.</li>\n</ul>\n<p style=\"line-height: 1.75\">They must be configured separately. A classic failure: someone sets service auto scaling to 30 tasks, traffic spikes, ECS tries to place 30 tasks on 3 small instances, runs out of CPU/memory, and the extra tasks sit in PENDING forever. Scaling the service did not scale the hardware.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Day-to-day operations</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Stopping a service temporarily.</strong> Set desired count to 0. The tasks stop, the service definition stays. Set it back later. (If service auto scaling is attached, note its minimum capacity can raise the count again.)</li>\n<li><strong>Deleting a service.</strong> Scale to 0 first, then <code>delete-service</code>. AWS also offers <code>--force</code> to delete a service still running tasks.</li>\n<li><strong>Changing settings.</strong> <code>update-service</code> edits desired count, task definition, deployment percentages, health check grace period, and more, in place.</li>\n<li><strong>--force-new-deployment.</strong> This tells ECS to replace all tasks even though nothing in the service definition changed. You need it when the <em>content behind an unchanged pointer</em> has changed — most commonly when you pushed a new image to the same tag (<code>myapp:latest</code>), so the task definition looks identical but the image is different. It is also the way to make tasks pick up a rotated secret, or to move tasks onto freshly added instances. Relying on <code>:latest</code> plus force-new-deployment is convenient but it destroys your ability to roll back precisely — prefer immutable image tags such as the Git commit SHA.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"A service restarts my container in place.\"</strong> It does not. A dead task is discarded and a brand new task is launched from the task definition. Anything written to that container's local disk is gone. Treat tasks as disposable.</li>\n<li><strong>\"Deploying means editing the running task.\"</strong> No. Task definitions are immutable; you register a new revision and point the service at it. Nothing is ever edited in flight.</li>\n<li><strong>\"Desired count is set in the task definition.\"</strong> No — the task definition is only the recipe. Desired count belongs to the service. The same task definition can back two services with different counts.</li>\n<li><strong>\"Scaling the service scales my EC2 instances.\"</strong> No. Service auto scaling changes task count only. Instance count is a separate Auto Scaling group / capacity provider concern, and forgetting that leaves tasks stuck in PENDING.</li>\n<li><strong>\"My deploy is stuck, ECS must be broken.\"</strong> Nearly always it is capacity or health: 100/100 percentages leaving no room, no spare CPU/memory on EC2 instances, or a slow-starting app being killed before the health check grace period would have saved it.</li>\n<li><strong>\"A DAEMON service needs a desired count.\"</strong> No. Its count is dictated by how many container instances exist, and it is EC2-only.</li>\n<li><strong>\"Health checks are all the same.\"</strong> There are three distinct ones: the container health check in the task definition, the ALB target group health check, and ECS's own view of whether the task is running.
