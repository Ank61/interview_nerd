{"title":"IAM for Containers — Task Role vs Task Execution Role","tags":["aws","ecs","iam","security"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">If you learn only one thing about running containers on AWS, make it this: there are <strong>two different identities</strong> involved in running a single ECS task, and they are used by two different actors at two different moments. Beginners mix them up constantly, and the resulting error messages look nothing like \"you mixed up your roles\". Interviewers know this, which is why \"what is the difference between the task role and the task execution role?\" is one of the most commonly asked ECS questions in existence.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">First, what is an IAM role, in plain words?</h4>\n<p style=\"line-height: 1.75\">AWS will not let anything call its APIs — \"list the objects in this S3 bucket\", \"write this log line\" — unless the caller proves who it is and has been granted permission. <strong>IAM</strong> stands for Identity and Access Management, and it is the AWS service that answers \"who are you, and are you allowed to do this?\"</p>\n<p style=\"line-height: 1.75\">An <strong>IAM role</strong> is a named bundle of permissions that an AWS resource can <em>temporarily borrow</em>, rather than a person's account. Borrowing is called <strong>assuming</strong> the role. When something assumes a role, AWS hands it a short-lived set of credentials that expire after a few hours and are automatically refreshed. Nothing is stored on disk, nothing is typed into a config file, and there is no password or long-lived access key to leak. That is the entire point of roles: <strong>identity without stored secrets</strong>.</p>\n<p style=\"line-height: 1.75\">Every role has two halves. The <strong>trust policy</strong> answers \"who is allowed to assume me?\" — for ECS roles the answer is the ECS service itself (<code>ecs-tasks.amazonaws.com</code>). The <strong>permissions policy</strong> answers \"once assumed, what can this role do?\" — for example \"read objects from the bucket named app-uploads\". The thing doing the assuming is called the <strong>principal</strong>, which is just the technical word for \"the identity making the request\".</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The two roles in an ECS task definition</h4>\n<p style=\"line-height: 1.75\">A <strong>task definition</strong> is the JSON blueprint that describes what to run: which image, how much CPU and memory, which ports, which environment variables. It has two separate role fields, and they are not interchangeable:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>executionRoleArn — the task execution role.</strong> Used by the <strong>ECS agent and the AWS-managed infrastructure</strong>, not by your code. This is AWS acting <em>on your behalf</em> to get your container started and wired up.</li>\n<li><strong>taskRoleArn — the task role.</strong> Assumed by <strong>your application code running inside the container</strong>. This is what your Python, Java or Node process uses when it calls the AWS SDK.</li>\n</ul>\n<p style=\"line-height: 1.75\">A useful mental image: the execution role is the <em>stagehand</em> who sets up the stage before the show, and the task role is the <em>actor</em> who performs once the curtain is up. That needs <code>ecr:GetAuthorizationToken</code>, <code>ecr:BatchCheckLayerAvailability</code>, <code>ecr:GetDownloadUrlForLayer</code> and <code>ecr:BatchGetImage</code>. A fully public image on Docker Hub needs no execution-role permission for the pull itself.</li>\n<li><strong>Sending logs.</strong> With the <code>awslogs</code> log driver, the agent — not your app — ships stdout and stderr to <strong>CloudWatch Logs</strong>. That needs <code>logs:CreateLogStream</code> and <code>logs:PutLogEvents</code>, plus <code>logs:CreateLogGroup</code> if you let ECS create the group.</li>\n<li><strong>Injecting secrets.</strong> When a container definition uses the <code>secrets</code> block instead of plain <code>environment</code>, ECS reads the value from <strong>AWS Secrets Manager</strong> or <strong>SSM Parameter Store</strong> at launch and places it into the container's environment. Because the reading happens before your process exists, the permission (<code>secretsmanager:GetSecretValue</code> or <code>ssm:GetParameters</code>, plus <code>kms:Decrypt</code> for a customer-managed key) belongs on the <strong>execution role</strong>. This trips up almost everyone.</li>\n<li><strong>Other infrastructure chores.</strong> On Fargate with an EFS file system, or with the FireLens log router, or with a private-registry credential stored in Secrets Manager, the extra permissions also land on the execution role.</li>\n</ul>\n<p style=\"line-height: 1.75\">AWS publishes a managed (AWS-maintained, ready-made) policy called <code>AmazonECSTaskExecutionRolePolicy</code> that covers the standard ECR-pull and CloudWatch-Logs permissions. It is the normal starting point. Note that it does <em>not</em> include secrets access — you attach that yourself, scoped to the specific secret ARNs.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The task role in detail</h4>\n<p style=\"line-height: 1.75\">The task role is the identity your business logic runs as. If your order service reads product images from <code>s3://catalog-images</code>, writes to the DynamoDB table <code>orders</code> and publishes to the SNS topic <code>order-events</code>, those three permissions — and nothing else — belong on the task role.</p>\n<p style=\"line-height: 1.75\">This is where <strong>least privilege</strong> lives: grant only the actions actually needed, only on the specific resources actually needed. Prefer <code>s3:GetObject</code> on <code>arn:aws:s3:::catalog-images/*</code> over <code>s3:*</code> on <code>*</code>. A service that only reads should not carry delete permissions, because the blast radius of a bug or a compromise is exactly the size of the role you attached.</p>\n<p style=\"line-height: 1.75\">Give <strong>one task role per service</strong>, not one shared role for the whole cluster. A shared role means the least trusted service in your account effectively has the permissions of the most privileged one, and it makes CloudTrail useless for answering \"which service did this?\" because every call looks identical. Per-service roles cost nothing and are the single highest-value habit here.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Side-by-side comparison</h4>\n<div style=\"overflow-x: auto; Because your process never ran, there is nothing in your application log group. Treat \"task stopped before it started, no app logs\" as an execution-role (or networking) problem.</p>\n<p style=\"line-height: 1.75\"><strong>Task-role failure = it starts and then misbehaves.</strong> The container is healthy, the health check passes, and then a request comes in and your log shows <code>AccessDenied: User: arn:aws:sts::123456789012:assumed-role/order-service-task-role/abc123 is not authorized to perform: dynamodb:PutItem</code>. Notice that the message names the assumed role — that string is your diagnostic gold, because it tells you exactly which role to fix.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">How the container actually gets credentials</h4>\n<p style=\"line-height: 1.75\">Your code never fetches the role explicitly. In Kubernetes the unit that runs containers is a <strong>pod</strong>, and every pod runs under a <strong>service account</strong>, a Kubernetes-internal identity object.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>IRSA (IAM Roles for Service Accounts).</strong> The older, widely used approach. You associate an IAM role with a Kubernetes service account by annotating the service account with the role ARN; EKS injects a signed token that the SDK exchanges for temporary credentials. It requires an OIDC identity provider per cluster.</li>\n<li><strong>EKS Pod Identity.</strong> The newer approach. You install an agent add-on and create an association mapping a service account to an IAM role through an AWS API call — no OIDC provider or role-annotation plumbing, and the role is reusable across clusters.</li>\n</ul>\n<p style=\"line-height: 1.75\">In both cases the role plays the part of the ECS <em>task</em> role. EKS has no separate \"execution role\" for image pulls, because on EKS the node (or Fargate profile) handles registry authentication through the node's own IAM role.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"One role is enough — I'll just put everything on the execution role.\"</strong> It can appear to work, because the execution role is also assumable, but your app does not use it. Your code reads the container credentials endpoint, which serves the <em>task</em> role. Pile S3 permissions onto the execution role and your app still gets AccessDenied.</li>\n<li><strong>\"The task role pulls the image.\"</strong> No. The image pull happens before any container exists, so the <em>execution</em> role does it. If you see CannotPullContainerError, do not go looking at the task role.</li>\n<li><strong>\"Secrets injection permissions go on the task role.\"</strong> No — injection is done by ECS at launch, so <code>secretsmanager:GetSecretValue</code> goes on the <strong>execution</strong> role. If your app instead calls Secrets Manager itself at runtime, <em>then</em> the permission belongs on the task role.</li>\n<li><strong>\"I should put access keys in environment variables.\"</strong> Never. They do not rotate, they leak through logs, task definitions and screenshots, and anyone with <code>ecs:DescribeTaskDefinition</code> can read them. Roles exist precisely to eliminate them.</li>\n<li><strong>\"Roles are only needed in production.\"</strong> Dev environments are where keys get committed to Git. Use roles everywhere; it is not extra work once set up.</li>\n<li><strong>\"The role is attached to the container image.\"</strong> Roles are attached to the task definition, not baked into the image. The same image can run under different roles in different environments — which is exactly what you want.</li>\n<li><strong>\"AccessDenied means my policy is wrong.\"</strong> Sometimes it means a resource policy (an S3 bucket policy or a KMS key policy) is denying you, or a permissions boundary or SCP is capping you.
