1.25rem; font-weight: 600\">Family, Revision and Container Basics</h4>\n<p style=\"line-height: 1.75\">The <strong>family</strong> is the name; each registration produces a new immutable <strong>revision</strong> number. Inside <code>containerDefinitions</code>, each container has a <strong>name</strong> (used by the load balancer configuration, by log stream names and by container overrides) and an <strong>image</strong>. Reference the image by digest (<code>@sha256:...</code>) or an immutable tag so the deployment is reproducible.</p>\n<p style=\"line-height: 1.75\"><strong>essential</strong> is quietly one of the most important fields. If a container marked <code>essential: true</code> exits for any reason, ECS <strong>stops the entire task</strong>, including its other containers. That is exactly what you want for your main application. It is exactly what you do not want for a short-lived helper: mark a one-shot init container <code>essential: false</code>, or your task will die the moment that helper finishes successfully. At least one container in a task must be essential.</p>\n<p style=\"line-height: 1.75\"><strong>command</strong> and <strong>entryPoint</strong> override what the image would run by default. In Docker terms, <code>entryPoint</code> corresponds to <code>ENTRYPOINT</code> (the executable) and <code>command</code> to <code>CMD</code> (its arguments or the whole command). Both are JSON arrays, not shell strings, so <code>[\"sh\",\"-c\",\"a &amp;&amp; b\"]</code> is how you run a shell pipeline. The common use is running one image in different modes — the same image as an API, as a worker, or as a migration job — instead of building three images.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; With <code>host</code>, port 8080 can only be used by one task per instance, so a second task fails placement. Memory is in MiB. Both can be set at the <strong>task level</strong> (the total envelope) and at the <strong>container level</strong> (how that envelope is divided).</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong><code>memory</code> is a hard limit.</strong> If the container's processes exceed it, the kernel's OOM killer terminates the container. In ECS you see exit code 137 and the stopped reason <em>\"OutOfMemoryError: Container killed due to memory usage\"</em>.</li>\n<li><strong><code>memoryReservation</code> is a soft limit.</strong> It is the amount ECS reserves for scheduling purposes; the container may temporarily use more, up to the hard limit or the host's capacity. It lets you pack more containers onto an EC2 host while allowing bursts.</li>\n<li><strong>Container <code>cpu</code> is a weight, not a cap.</strong> Under contention, containers get CPU roughly in proportion to their units; when the host is idle a container can use more than its share.</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>Fargate requires a valid CPU/memory combination</strong> chosen from a fixed table — you cannot ask for arbitrary values. Memory is the dangerous one, because exceeding it kills the container rather than merely slowing it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Environment Variables vs Secrets</h4>\n<p style=\"line-height: 1.75\"><strong>environment</strong> is a list of plain name/value pairs baked into the task definition — perfect for non-sensitive configuration such as <code>LOG_LEVEL</code>, a feature flag, a region, or a database <em>hostname</em>.</p>\n<p style=\"line-height: 1.75\"><strong>Never put a password, API key or token in <code>environment</code>.</strong> The value is stored in the task definition in plain text, so anyone with <code>ecs:DescribeTaskDefinition</code> — a permission often granted broadly for read-only access — can read it, it appears in the console, and it lands in your CloudTrail audit logs and in any Terraform or CloudFormation state file committed near your repo. Rotating it means registering a new revision and redeploying.</p>\n<p style=\"line-height: 1.75\">Instead use the <strong>secrets</strong> block. Each entry gives an environment variable <code>name</code> and a <code>valueFrom</code> ARN pointing at <strong>AWS Secrets Manager</strong> or <strong>SSM Parameter Store</strong> (a SecureString parameter). At task start, the ECS agent — using the <strong>execution role</strong>'s permissions — fetches the value and injects it into the container's environment. The task definition contains only the ARN, never the secret. For Secrets Manager you can select a single JSON key with the <code>:key::</code> suffix shown in the example above. Note the value is resolved at task start, so rotating a secret requires new tasks (<code>--force-new-deployment</code>) to pick it up.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Logging with the awslogs Driver</h4>\n<p style=\"line-height: 1.75\">A container writes to stdout and stderr; without configuration those bytes vanish when the task stops. On Fargate each task gets 20 GiB of ephemeral storage by default, configurable up to 200 GiB with <code>ephemeralStorage</code>.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Volumes and mountPoints.</strong> Declare a volume at task level in <code>volumes</code>, then mount it into a container with a <code>mountPoints</code> entry naming the <code>sourceVolume</code> and the <code>containerPath</code>. An empty volume declaration creates scratch space that <em>containers in the same task share</em> — handy for handing files from an app container to a sidecar.</li>\n<li><strong>Amazon EFS for persistence.</strong> Attach an <strong>EFS</strong> file system (a managed, network-attached, elastic NFS file system) with <code>efsVolumeConfiguration</code>.
