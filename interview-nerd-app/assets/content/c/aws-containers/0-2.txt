font-size: 1.25rem; font-weight: 600\">The Cluster</h4>\n<p style=\"line-height: 1.75\">A <strong>cluster</strong> is a logical grouping — a named boundary that your containers run inside. It is the unit you point deployments, permissions, metrics and Container Insights at. Teams typically create one cluster per environment (<code>dev-cluster</code>, <code>prod-cluster</code>) rather than one per application.</p>\n<p style=\"line-height: 1.75\">The thing that surprises beginners: with Fargate, <strong>a cluster contains no servers you manage</strong>. Creating a cluster provisions nothing and costs nothing by itself; it is closer to a folder or a namespace than to a machine. Only when you run tasks does capacity appear, and with Fargate that capacity is invisible AWS-managed infrastructure. If instead you use EC2 capacity, the cluster is where your registered EC2 instances live — each runs a small <strong>ECS container agent</strong>, a process that reports the instance's free CPU and memory to ECS and starts containers when told to.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Task Definition — a Blueprint</h4>\n<p style=\"line-height: 1.75\">A <strong>task definition</strong> is a JSON document describing <em>how to run</em> one or more containers together. Think of it as a recipe card, or as the ECS equivalent of a <code>docker run</code> command written down and version-controlled. It specifies:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Which image(s)</strong> to run, by ECR repository URI plus tag or digest.</li>\n<li><strong>How much CPU and memory</strong> the whole task gets, and optionally per container.</li>\n<li><strong>Which ports</strong> the containers listen on.</li>\n<li><strong>Environment variables</strong> and <strong>secrets</strong> references.</li>\n<li><strong>Where logs go</strong> — normally CloudWatch Logs.</li>\n<li><strong>Which IAM roles</strong> apply. An <strong>IAM role</strong> is a set of AWS permissions something can assume; an <strong>ARN (Amazon Resource Name)</strong> is the globally unique identifier of an AWS resource, like <code>arn:aws:iam::111122223333:role/myapp-task-role</code>.</li>\n</ul>\n<p style=\"line-height: 1.75\">The crucial point: <strong>a task definition is not running anything.</strong> Registering one starts no containers and costs nothing. It is pure description. Beginners routinely register a task definition, see nothing happen, and assume something is broken.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Revisions — Why Rollback Is Easy</h4>\n<p style=\"line-height: 1.75\">Task definitions are grouped by <strong>family</strong> (a name like <code>myapp</code>) and every registration creates a new immutable numbered <strong>revision</strong>: <code>myapp:1</code>, <code>myapp:2</code>, <code>myapp:3</code>. You never edit a revision in place — \"editing\" in the console simply registers the next one.</p>\n<p style=\"line-height: 1.75\">This design is what makes deployment and rollback straightforward. You do not deploy \"the task definition\"; you deploy a specific revision. Changing the image tag, the memory, or an environment variable all produce a new revision, so the complete configuration of every past deployment stays queryable. Rolling back is telling the service to use <code>myapp:6</code> again — one API call, and it includes every setting from that moment, not just the image.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Task — One Running Instance</h4>\n<p style=\"line-height: 1.75\">A <strong>task</strong> is one running instantiation of a task definition revision. If the revision describes two containers, the task is both of them, <strong>scheduled together on the same host and started and stopped as a unit</strong>. Containers in a task share networking, so with the <code>awsvpc</code> network mode they share one elastic network interface and one private IP, and can talk to each other over <code>localhost</code>. This is the closest ECS analogue to a Kubernetes <strong>pod</strong>.</p>\n<p style=\"line-height: 1.75\">Tasks are disposable. They get replaced on every deploy, killed during scale-in, and recreated after a failure — so never keep important state on a task's local disk.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Service — the Thing That Keeps Tasks Alive</h4>\n<p style=\"line-height: 1.75\">A <strong>service</strong> is the controller that maintains a specified number of copies of a task, forever. You declare a <strong>desiredCount</strong> — say 3 — and the service continuously works to make reality match. It is what you use for anything long-running: a web API, a background consumer, a gRPC backend.</p>\n<p style=\"line-height: 1.75\">A service does five jobs:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Maintains count.</strong> If a task exits or its host dies, the service launches a replacement.</li>\n<li><strong>Replaces unhealthy tasks.</strong> If the container health check or the load balancer health check fails, the task is stopped and replaced.</li>\n<li><strong>Deploys new revisions.</strong> The default <strong>rolling update</strong> uses <code>minimumHealthyPercent</code> and <code>maximumPercent</code> to control how many old tasks may be stopped and how many extra may run at once. ECS also supports blue/green deployments via AWS CodeDeploy.</li>\n<li><strong>Registers with load balancers.</strong> The service adds each new task's IP to an Application Load Balancer target group and removes it before stopping the task, with a configurable drain period so in-flight requests finish.</li>\n<li><strong>Scales.</strong> Service Auto Scaling adjusts <code>desiredCount</code> based on CloudWatch metrics such as average CPU or ALB requests per target.</li>\n</ul>\n<p style=\"line-height: 1.75\">Services also offer <strong>Service Connect</strong> (or the older Service Discovery via Cloud Map) so services can find each other by a friendly name instead of hard-coded IPs — necessary because task IPs change constantly.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Standalone Tasks — One-Off Work</h4>\n<p style=\"line-height: 1.75\">Not everything should run forever. A database migration, a nightly report, an ad-hoc data backfill — these should run once and exit. For those you use <code>aws ecs run-task</code>, which launches a task directly with no service wrapping it. Nothing restarts it when it exits; that is the point.</p>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\"><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Aspect</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Service</th><th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Standalone task (run-task)</th></tr></thead>\n<tbody>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Restarts on exit?</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Yes, always</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">No</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Load balancer integration</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Yes</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">No</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Autoscaling</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Yes</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">No</td></tr>\n<tr><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Typical use</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Web API, queue consumer</td><td style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Migration, batch job, cron via EventBridge Scheduler</td></tr>\n</tbody>\n</table>\n</div>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Where Does a Task Actually Run? Capacity and Placement</h4>\n<p style=\"line-height: 1.75\">A cluster's capacity comes from one of two sources, and this determines how much placement you think about.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Fargate.</strong> You state the task's CPU and memory; AWS finds or creates capacity. There is no host to choose, no bin-packing to reason about, and no instance to patch. Placement strategies do not apply — ECS spreads tasks across Availability Zones automatically based on the subnets you configure.</li>\n<li><strong>EC2.</strong> You register EC2 instances into the cluster (usually via an Auto Scaling group tied to an ECS <strong>capacity provider</strong>, which can also scale instances in and out for you). Best for availability: losing one AZ does not take out everything.</li>\n<li><strong>binpack</strong> — fill the most-utilized instance first to minimize the number of instances running. Best for cost.</li>\n<li><strong>random</strong> — pick arbitrarily. Rarely the right answer.</li>\n</ul>\n<p style=\"line-height: 1.75\">A common production choice is spread across AZ, then binpack on memory. The classic EC2 failure mode is a task stuck in <code>PROVISIONING</code> with the event <em>\"unable to place a task because no container instance met all of its requirements\"</em> — meaning no registered instance has enough free CPU, memory or the required port available.
