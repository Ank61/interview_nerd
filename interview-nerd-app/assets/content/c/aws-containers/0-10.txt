{"title":"Kubernetes Core Objects for Beginners — Pods, Deployments, Services and More","tags":["kubernetes","eks","pods","deployments"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Kubernetes is a vocabulary problem before it is a technology problem. Almost everything you do is creating, reading or updating <strong>objects</strong> — records stored in the cluster describing what you want — and then letting <strong>controllers</strong>, the background loops inside the control plane, make reality match. This topic walks the objects you will meet in your first month, in the order they build on each other, and finishes with an ECS-to-Kubernetes translation table.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Pod — the smallest deployable unit</h4>\n<p style=\"line-height: 1.75\">A <strong>Pod</strong> is one or more containers that are always scheduled together on the same node and share a network namespace and storage volumes. Sharing a network namespace means they share one IP address and can reach each other over <code>localhost</code>, exactly like two processes on one machine. If you know ECS, a pod is the close analogue of an <strong>ECS task</strong>.</p>\n<p style=\"line-height: 1.75\">Most pods contain a single container. Multiple containers in one pod are for helpers that must live and die with the main process — a log shipper reading a shared volume, a proxy, or an init container that prepares something before the app starts. That pattern is called a <strong>sidecar</strong>.</p>\n<p style=\"line-height: 1.75\">The crucial point: <strong>you almost never create pods directly</strong>. A bare pod is disposable and not self-healing — if its node dies, it is simply gone, with nothing to recreate it. Pods are cattle, not pets. You create a higher-level object that owns pods and keeps the right number alive.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">ReplicaSet and Deployment — keeping pods alive and updating them</h4>\n<p style=\"line-height: 1.75\">A <strong>ReplicaSet</strong> has exactly one job: keep N identical pods running. If one dies, it creates a replacement; if there are too many, it deletes some. It has no concept of updates or versions.</p>\n<p style=\"line-height: 1.75\">A <strong>Deployment</strong> is the object you actually write. They are connected by <strong>labels</strong>, which are simple key-value tags on an object, and <strong>selectors</strong>, which are queries over those labels. A Service does not list its pods; it says \"I route to anything labelled <code>app=web</code>\", and membership is computed continuously. A Deployment finds its pods the same way.</p>\n<p style=\"line-height: 1.75\">This is why labels are <strong>not documentation</strong> — they are functional. A single typo (<code>app: web</code> versus <code>app: Web</code>) yields a Service with zero endpoints and a perfectly healthy set of pods nobody can reach. This is one of the most common beginner outages, and <code>kubectl get endpoints</code> is the fastest way to detect it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Service — a stable address in front of changing pods</h4>\n<p style=\"line-height: 1.75\">Pods are ephemeral and their IP addresses change every time one is replaced. If your frontend hardcoded a backend pod IP, the first restart would break it. A <strong>Service</strong> solves this with a stable virtual IP and a stable DNS name that always resolve to the currently healthy matching pods. It is the same problem ECS solves with Service Connect or Service Discovery.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>ClusterIP (default).</strong> An internal-only virtual IP reachable from inside the cluster, plus a DNS name like <code>orders.prod.svc.cluster.local</code>. Use for service-to-service traffic.</li>\n<li><strong>NodePort.</strong> Opens the same fixed high port (30000-32767) on every node, so anything that can reach a node's IP can reach the service. Useful in labs; rarely used directly in production because you must manage node IPs and firewall rules yourself.</li>\n<li><strong>LoadBalancer.</strong> Everything NodePort does, plus the cloud provider provisions a real load balancer. On EKS with the AWS Load Balancer Controller this creates a <strong>Network Load Balancer</strong> and points it at your pods.</li>\n</ul>\n<p style=\"line-height: 1.75\">A Service is a layer-4 construct: it balances TCP connections, it does not understand URLs. Names must be unique within a namespace, not across the cluster, so <code>dev</code> and <code>staging</code> can each have a Deployment called <code>web</code>. Namespaces are where you attach per-team <strong>resource quotas</strong>, <strong>RBAC</strong> permission rules and network policies, which is why teams share one cluster with several namespaces rather than paying the per-cluster EKS fee many times.</p>\n<p style=\"line-height: 1.75\">Be precise in an interview: a namespace is <strong>not</strong> a security boundary by itself. Without network policies, pods in different namespaces can still reach each other over the network. For genuinely hostile tenants you use separate clusters.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">ConfigMaps and Secrets — configuration out of the image</h4>\n<p style=\"line-height: 1.75\">You want one image promoted unchanged from dev to prod, which means configuration must come from outside it. A <strong>ConfigMap</strong> holds non-sensitive key-value configuration — log level, feature flags, a config file — and can be exposed as environment variables or mounted as files. A <strong>Secret</strong> is the same shape, intended for sensitive values.</p>\n<p style=\"line-height: 1.75\">Here is the honest caveat that interviewers love: <strong>Kubernetes Secrets are only base64-encoded by default, not encrypted</strong>. Base64 is an encoding, trivially reversible with one command; it exists so binary data survives YAML, not to protect anything. Practical mitigations on EKS: enable <strong>envelope encryption of Secrets in etcd with a KMS key</strong>, lock down who can read Secrets with RBAC, and for real credentials keep the source of truth in <strong>AWS Secrets Manager</strong> or SSM Parameter Store, pulling values in with the Secrets Store CSI driver plus the AWS provider, or with an external-secrets operator, and granting the pod access via IRSA or EKS Pod Identity.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Resource requests and limits</h4>\n<p style=\"line-height: 1.75\">Every container should declare how much CPU and memory it needs. A <strong>request</strong> is the amount reserved for it: the <strong>scheduler</strong> uses requests to decide which node has room, so a pod whose request no node can satisfy stays <strong>Pending</strong>. A <strong>limit</strong> is the ceiling it may use.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>CPU is compressible.</strong> Exceeding the CPU limit causes <strong>throttling</strong> — the container runs slower but keeps running.</li>\n<li><strong>Memory is not compressible.</strong> Exceeding the memory limit gets the container <strong>killed, with status OOMKilled</strong>, and restarted. A pod repeatedly restarting with OOMKilled needs a higher limit or a memory-leak fix.</li>\n<li><strong>No requests at all</strong> means the scheduler is flying blind; it will happily overpack a node until a noisy neighbour destabilises everything on it. This is why requests and limits are a stability feature, not a cost-accounting nicety.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Liveness and readiness probes</h4>\n<p style=\"line-height: 1.75\">A <strong>probe</strong> is a health check the kubelet performs against your container.
