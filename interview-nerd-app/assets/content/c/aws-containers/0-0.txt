{"title":"Containers on AWS — Why Containers and What AWS Offers","tags":["containers","ecs","eks","fargate"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Imagine you have written a small web application — say a Node.js API or a Python Flask service. On your laptop it runs perfectly. You copy the files to a server, run the start command, and it crashes. The server has Node 16 instead of Node 20. Or a system library your image-processing package depends on is missing. Or the server sets a different timezone and your date handling breaks. This is the famous \"it works on my machine\" problem, and it is the single biggest reason containers exist.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Problem, Concretely</h4>\n<p style=\"line-height: 1.75\">Before containers, teams had three common answers to this problem, and each had real costs.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>A long setup document.</strong> A wiki page saying \"install Node 20, install libvips, set these five environment variables, create this directory.\" Humans skip steps, the page goes stale, and a new server is never quite identical to the old one. This is called <strong>configuration drift</strong> — two machines that should be the same slowly diverge.</li>\n<li><strong>A configuration-management tool.</strong> Tools like Ansible, Chef or Puppet turn that wiki page into a script that runs on every server. Much better, but the script still <em>mutates</em> an existing machine. If the starting state differs, the ending state differs. And the script takes minutes to run.</li>\n<li><strong>One whole virtual machine per application.</strong> A <strong>virtual machine (VM)</strong> is a simulated computer running its own complete operating system on top of a physical server. Bake an image of the whole machine and you truly get identical copies. But each VM carries a full operating system — gigabytes of disk, hundreds of megabytes of RAM, and a boot time measured in minutes. Running twenty small services means twenty operating systems doing nothing useful.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What a Container Actually Is</h4>\n<p style=\"line-height: 1.75\">A <strong>container</strong> is your application packaged together with everything it needs to run — the language runtime, the libraries, the configuration files, the directory layout — as one self-contained unit that runs the same way on your laptop, in your test environment, and in production. You do not ship \"the code and a list of requirements\"; you ship the whole working environment.</p>\n<p style=\"line-height: 1.75\">An <strong>image</strong> is the read-only template that describes that packaged unit. Think of the image as the recipe plus all the ingredients sealed in a box, and the container as the actual meal being cooked from it right now. One image can produce many containers. You build an image once, store it somewhere, and then start one, ten, or a hundred containers from it. Images are immutable — you never edit a running container and expect the change to persist; you build a new image.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Container vs Virtual Machine — The Key Difference</h4>\n<p style=\"line-height: 1.75\">This distinction gets asked in almost every interview. A VM virtualizes <em>hardware</em>: it includes an entire guest operating system with its own kernel (the core of the OS that talks to hardware), and it must boot that OS before your app starts. A container virtualizes the <em>process</em>: it shares the host machine's kernel and is isolated using kernel features (namespaces for \"what can I see\" and cgroups for \"how much CPU and memory can I use\"). Nothing has to boot. Containers are lighter than VMs, but they are not magic — they trade a little isolation for a lot of speed and density.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Docker and the OCI Standard</h4>\n<p style=\"line-height: 1.75\"><strong>Docker</strong> is the tooling most people use to build images and run containers: the <code>docker build</code> command that turns a <code>Dockerfile</code> (a text recipe) into an image, and <code>docker run</code> which starts a container from it. Docker made containers popular, but the format itself is now an open standard.</p>\n<p style=\"line-height: 1.75\">The <strong>OCI (Open Container Initiative)</strong> defines the image format and the runtime behavior so that an image built by Docker can be run by other tools. This matters practically: Amazon ECR stores OCI-compatible images, ECS and EKS run them, and you are never locked into one vendor's image format. On AWS Fargate and on Amazon EKS the actual runtime that starts your container is <strong>containerd</strong>, not the Docker daemon — the image you built with Docker still works, because both speak OCI.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why You Need Orchestration</h4>\n<p style=\"line-height: 1.75\">Running one container by hand with <code>docker run</code> is easy. Running a real system is not. <strong>Orchestration</strong> means having software that answers all the operational questions for you, continuously:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Placement.</strong> Which machine has enough free CPU and memory to run this container right now?</li>\n<li><strong>Self-healing.</strong> The container crashed at 3am — start a replacement without waking anyone up.</li>\n<li><strong>Deployment.</strong> Roll out version 2 gradually, keep version 1 serving traffic until the new one is healthy, and roll back automatically if it is not.</li>\n<li><strong>Scaling.</strong> Traffic tripled — run more copies; traffic dropped — run fewer, so you stop paying for idle capacity.</li>\n<li><strong>Networking and load balancing.</strong> Give each copy an address, register it with a load balancer (a component that spreads incoming requests across healthy copies), and deregister it when it goes away.</li>\n<li><strong>Health checking.</strong> Decide what \"healthy\" means and act when a container stops meeting it.</li>\n</ul>\n<p style=\"line-height: 1.75\">Doing this by hand across even three servers does not work. Someone SSHes in, restarts something, forgets to tell anyone, and now your servers are different again — you have reinvented configuration drift on top of containers. An orchestrator is the control loop that keeps reality matching your declared intent.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The AWS Container Landscape as a Map</h4>\n<p style=\"line-height: 1.75\">AWS gives you several container services, and the names blur together at first.
