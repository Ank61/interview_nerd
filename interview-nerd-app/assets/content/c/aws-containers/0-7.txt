The load balancer is the only thing exposed, so it is the only attack surface. Tasks sit in <strong>private subnets</strong> — subnets with no route to an internet gateway — so nothing on the internet can reach them directly even if a security group were misconfigured. That is defence in depth.</p>\n<p style=\"line-height: 1.75\">But tasks still need to reach <em>out</em>: to pull images from ECR, ship logs to CloudWatch, read secrets from Secrets Manager, call third-party APIs. A private subnet has no route out by itself. Two mechanisms fix that:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>NAT gateway.</strong> A managed device in a public subnet that lets private resources make outbound connections while remaining unreachable from the internet. It is the general-purpose answer, needed for any third-party API call. It costs an hourly charge per gateway plus a per-GB data processing charge, and you want one per AZ for resilience — which makes it one of the more expensive things in a small VPC.</li>\n<li><strong>VPC endpoints.</strong> Private doorways from your VPC directly into an AWS service, so that traffic never touches the internet at all. There are two kinds: <em>gateway endpoints</em> (S3 and DynamoDB, added as a route table entry, free) and <em>interface endpoints</em> (most other services, an ENI in your subnet, billed hourly plus per GB). For AWS service traffic these are better than NAT: more secure (traffic stays on the AWS network), often cheaper at volume, and they let you avoid NAT entirely if you truly have no third-party calls.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The single most common beginner failure</h4>\n<p style=\"line-height: 1.75\">You launch a Fargate service into private subnets. The task never starts. Pulling an image from ECR is a network call, and the task cannot make it. A Fargate task in a <em>public</em> subnet with ENABLED gets a routable public IP and can reach the internet without a NAT gateway. Beginners find this because it makes the image-pull failure disappear for free.</p>\n<p style=\"line-height: 1.75\">It is fine for a demo, a short batch job, or a dev environment where you are avoiding NAT costs. For production it is the wrong default because the task now has a public IP — your only protection is the security group, so a single over-permissive rule exposes the container directly to the internet, with no network-layer backstop behind it. It also gives every task a changing public IP, which makes egress IP allowlisting with partners impossible (a NAT gateway gives you a stable Elastic IP instead). The production answer is DISABLED, private subnets, and NAT or endpoints for egress.</p>\n<p style=\"line-height: 1.75\">One rule to memorise: a Fargate task in a <strong>public</strong> subnet with <code>assignPublicIp=DISABLED</code> has <em>no</em> internet access at all, because public subnets have no NAT. Your <code>orders</code> service needs to call your <code>inventory</code> service. In awsvpc mode, inventory's tasks have private IPs like <code>10.0.10.42</code>. But every deploy replaces those tasks with new ones on new IPs, and scaling adds and removes them constantly. Hardcoding an address guarantees an outage on the next deploy. You need a name that always resolves to whichever tasks are healthy right now.</p>\n<p style=\"line-height: 1.75\">Three answers, in increasing modernity:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>An internal load balancer.</strong> Put an internal ALB in front of inventory and call its stable DNS name. Your code calls <code>inventory.internal</code> and DNS returns the current task IPs. It is cheap and simple, but it is <em>DNS-based</em>, which brings DNS caching problems: clients that cache a record past its TTL keep trying dead IPs after a deploy, and plain DNS round-robin gives you no real load balancing or retries.</li>\n<li><strong>ECS Service Connect (the modern option).</strong> You give the service a short logical name in a namespace, and ECS injects a managed proxy sidecar into every task. Your code just calls <code>http://inventory</code>. The proxy knows the live endpoints without DNS caching, does client-side load balancing, retries failed requests, and emits per-service traffic metrics (request counts, errors, latency) into CloudWatch automatically. During a deploy it drains connections gracefully to the old tasks. You are near the limit, and the failure surfaces as tasks failing to launch with an insufficient-free-addresses error — typically <em>mid-deploy</em>, at the worst possible moment.</p><p>To plan properly: size container subnets at a <code>/22</code> (about 1019 usable) or <code>/21</code> per AZ, and <strong>budget for the deployment-time doubling rather than steady state</strong>. Keep tasks in separate subnets from databases and endpoints so one cannot starve the other, and alarm on the subnet's available-IP metric.
