First, an invalid pair (say 256 CPU with 8 GB memory) is simply rejected when you register the task definition — a very common first-day error. Second, because <strong>you are billed on what you request, not what you use</strong>, over-sizing is money burned every second the task runs. Right-sizing on Fargate is not a nice-to-have; it is the single biggest cost lever you have. Use CloudWatch Container Insights to look at real CPU and memory utilization per task and trim the request to fit with sensible headroom.</p>\n<p style=\"line-height: 1.75\">Individual containers inside a task can still be given <code>cpu</code>, <code>memory</code> (a hard cap — exceed it and the container is killed) and <code>memoryReservation</code> (a soft floor), which is how you divide the task's total between an app container and its sidecars.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Ephemeral storage: it is a scratch pad, not a disk</h4>\n<p style=\"line-height: 1.75\">Every Fargate task gets <strong>ephemeral storage</strong> — temporary local disk space, 20 GB by default, configurable up to 200 GB via <code>ephemeralStorage</code> in the task definition. It is shared by the containers in the task, and it is fast, which makes it good for image processing scratch files, build artifacts, temp files and caches.</p>\n<p style=\"line-height: 1.75\">The word to burn into memory is <em>ephemeral</em>. When the task stops — because it crashed, because you deployed, because scaling removed it — the storage is destroyed. There is no \"reattach the volume to the replacement task\" in Fargate. Anything that must outlive the task belongs in <strong>Amazon S3</strong> (objects and files), <strong>Amazon EFS</strong> (a shared network filesystem you can mount into a Fargate task and which does persist), or a database such as RDS or DynamoDB. A beginner who writes uploads to local disk will lose them on the very next deployment, and the bug will look mysterious because it only happens sometimes.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Networking: one network interface per task</h4>\n<p style=\"line-height: 1.75\">Fargate always uses <strong>awsvpc</strong> network mode. Each task is given its own <strong>elastic network interface (ENI)</strong> — a virtual network card — with its own private IP address inside your VPC (your private network in AWS). This has consequences worth internalising:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Security groups apply per task.</strong> A security group is a virtual firewall listing what traffic is allowed in and out. Because each task has its own interface, you can give the payments service a different firewall from the marketing site even though they share a cluster. On EC2 bridge mode you could not — everything on the instance shared the instance's rules.</li>\n<li><strong>Subnet IP capacity matters.</strong> Each task consumes one IP address from its subnet. A <code>/24</code> subnet has 256 addresses, of which AWS reserves 5 — so roughly 250 tasks, less anything else living there. Run a large service with 100/200 deployment percentages and the doubling during a deploy can exhaust it.</li>\n<li><strong>No port conflicts.</strong> Every task has its own IP, so ten copies of a service can all listen on port 8080.</li>\n<li><strong>Load balancer targets are IPs.</strong> The target group must be of type <code>ip</code>, not <code>instance</code>.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Platform versions</h4>\n<p style=\"line-height: 1.75\">The Fargate environment your task runs in is versioned — this is the <strong>platform version</strong>. It determines which underlying kernel, runtime and feature set you get (EFS support, larger ephemeral storage, and so on). The recommended setting is <code>LATEST</code>, which resolves to the current recommended version for your platform family (Linux or Windows). AWS patches the underlying environment for you; you never apply a kernel update or reboot a host. Practically, that means the \"patch our container hosts\" work item disappears from your backlog entirely — you only patch your own image.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What you give up</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>No host access.</strong> You cannot SSH to the machine, list its processes, read its files, or install an agent on it. For debugging, the supported route is <strong>ECS Exec</strong> — it uses AWS Systems Manager to open an interactive shell <em>inside your running container</em> (<code>aws ecs execute-command</code>). Note the distinction carefully: inside the container, never on the host. It requires the SSM permissions on the task role and <code>enableExecuteCommand</code> on the service or task.</li>\n<li><strong>No privileged containers.</strong> The <code>privileged</code> flag is not supported, so Docker-in-Docker style builds and anything needing broad kernel capabilities will not run.</li>\n<li><strong>No DAEMON scheduling.</strong> \"One copy per host\" is meaningless when you have no hosts. Per-node agents become per-task <strong>sidecar containers</strong> instead — a log router or observability agent added to each task definition.</li>\n<li><strong>Limited kernel-level features.</strong> No host bind mounts, no arbitrary kernel parameter tuning, a restricted set of Linux capabilities, and some tracing or profiling tools that need host privileges will not work.</li>\n<li><strong>No GPUs.</strong> Fargate has no GPU support at all. ML inference or training needing accelerators must use the EC2 launch type.</li>\n<li><strong>Fixed size menu and per-task caps.</strong> You cannot ask for an arbitrary shape, and a single task cannot exceed Fargate's maximum size.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Start-up latency and how to cut it</h4>\n<p style=\"line-height: 1.75\">A Fargate task start involves: provisioning the compute, creating and attaching the ENI, <strong>pulling the container image</strong>, then starting the container and waiting for health checks. Typically this lands in the tens of seconds. The image pull is usually the largest and most controllable part — a 1.5 GB image simply takes far longer to fetch than a 120 MB one.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Shrink the image.</strong> Multi-stage builds so compilers and build tools never ship; a slim or distroless base; remove package caches in the same layer that creates them.</li>\n<li><strong>Keep the registry close.</strong> Use ECR in the same region; cross-region pulls add latency and data transfer cost.</li>\n<li><strong>Use Seekable OCI (SOCI) lazy loading</strong> where supported, which lets a task start before the whole image has been downloaded — a large win for big images.</li>\n<li><strong>Scale before you need it.</strong> Target tracking with a sensible scale-out cooldown, or scheduled scaling ahead of a known traffic pattern, so start-up time is not on the critical path during a spike.</li>\n<li><strong>Warm up less.</strong> Long application boot sequences add to this; if you cannot shorten them, raise the health check grace period so ECS does not kill the task mid-boot.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Fargate Spot</h4>\n<p style=\"line-height: 1.75\"><strong>Fargate Spot</strong> runs your task on spare AWS capacity at a steep discount. The catch is honest and simple: AWS can take that capacity back. When it does, ECS sends your container a <code>SIGTERM</code> and a task state change event, and you get roughly a two-minute warning before the task is stopped.</p>\n<p style=\"line-height: 1.75\">That makes it excellent for work that can be interrupted and retried: queue consumers (the message returns to the queue if unacknowledged), batch processing, CI jobs, test environments, and stateless web tiers that keep an on-demand floor. It is a poor fit for long uninterruptible operations, stateful singletons, or anything where losing two minutes of work is expensive. The standard production pattern is a capacity provider strategy with an on-demand <code>base</code> and a Spot-heavy <code>weight</code>. Whatever you do, handle SIGTERM properly — finish or checkpoint current work and exit.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">A worked cost comparison</h4>\n<p style=\"line-height: 1.75\">Scenario: a web service that needs <strong>10 tasks of 1 vCPU / 2 GB</strong> running 24/7 for a 730-hour month. With <strong>Amazon EKS</strong> (managed Kubernetes) you can create a <strong>Fargate profile</strong> that says \"pods matching this namespace and these labels run on Fargate\". Each such pod gets its own isolated compute and its own ENI, exactly like an ECS Fargate task, and you skip managing node groups for those workloads. The same trade-offs apply: no DaemonSets on Fargate pods, no privileged pods, no GPUs, one pod per isolated environment. Knowing this is the difference between \"Fargate is an ECS feature\" and the correct answer, \"Fargate is a compute engine two orchestrators can use\".</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Security posture</h4>\n<p style=\"line-height: 1.75\">Fargate's isolation model is a real, quotable benefit. Each task runs in its own isolated compute environment — it does not share a kernel with another customer's workload, or even with your own other tasks. Compare that with EC2, where several of your containers share one kernel, so a container escape exposes everything else on that instance.</p>\n<p style=\"line-height: 1.75\">Combine that with per-task security groups, per-task IAM roles (the <strong>task role</strong> gives the application its AWS permissions, while the separate <strong>task execution role</strong> lets the ECS agent pull images and write logs), no SSH surface at all, and AWS patching the host, and you have a meaningfully smaller attack surface with much less effort. Your remaining job is your own image: scan it, keep base images current, run as a non-root user, and use a read-only root filesystem where you can.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Common beginner misconceptions</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>\"Fargate is an orchestrator.\"</strong> It is not. It runs containers on demand; ECS or EKS decides what to run, how many, and how to deploy. Fargate is the engine, not the driver.</li>\n<li><strong>\"There is no server at all.\"</strong> There absolutely is — AWS owns, patches and operates it. Serverless means \"not your server to manage\", not \"no server exists\".</li>\n<li><strong>\"I can run any container unchanged on Fargate.\"</strong> Not if it needs privileged mode, host bind mounts, GPUs, custom kernel parameters, or a size outside the supported CPU/memory pairs.</li>\n<li><strong>\"Fargate tasks keep their disk between runs.\"</strong> No. Ephemeral storage is destroyed when the task stops. Durable data goes to S3, EFS or a database.</li>\n<li><strong>\"I pay for what my container uses.\"</strong> No — you pay for what you <em>request</em>, per second. A task asking for 4 vCPU and using 0.3 is billed for 4.</li>\n<li><strong>\"I can SSH in to debug.\"</strong> There is no host to reach. ECS Exec gives you a shell inside the container, which is what you actually wanted anyway.</li>\n<li><strong>\"Fargate Spot is just cheaper Fargate.\"</strong> It is cheaper <em>and</em> interruptible with about two minutes of notice. Only use it where a task can be killed and retried.</li>\n<li><strong>\"Fargate always costs more.\"</strong> Only at high, genuinely well-packed EC2 utilization. Spiky or low-density workloads are usually cheaper on Fargate before you even count engineering time.</li>\n</ul>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"Fargate is a serverless compute engine for containers, used by ECS and EKS rather than instead of them.
