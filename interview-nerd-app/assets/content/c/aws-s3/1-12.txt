{"title":"S3 Server Access Logging vs CloudTrail","tags":["access-logging","cloudtrail","auditing","security-investigation"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">S3 offers two distinct logging mechanisms that are frequently confused because both produce \"logs about S3 activity,\" but they answer fundamentally different questions. <strong>S3 Server Access Logging</strong> records <strong>request-level detail about traffic hitting a specific bucket</strong> — who requested which object, when, and what the response was. <strong>AWS CloudTrail</strong> records <strong>API-level audit activity</strong> — which IAM identity called which AWS API, from where, and when, across all of AWS, not just S3. Knowing which one to reach for is a common interview probe because picking the wrong one in a real investigation wastes hours.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">S3 Server Access Logging</h4>\n<p style=\"line-height: 1.75\">When enabled on a bucket, Server Access Logging captures detailed records of requests made against that bucket — the requester (if identifiable), the bucket and key involved, the request time, the operation performed (REST.GET.OBJECT, REST.PUT.OBJECT, etc.), the HTTP status code, the bytes sent, total request time, referrer, user agent, and more. Logs are delivered as plain-text log files to a target S3 bucket (which can be the same bucket, though a separate bucket is recommended to avoid recursive logging and clutter). Delivery is <strong>best-effort</strong>: AWS does not guarantee that every single request is logged, nor does it guarantee delivery within a specific time window — logs can take hours to appear and, rarely, a request may not be logged at all. This makes access logging excellent for understanding traffic patterns, debugging unexpected 403s, or analyzing who is downloading what, but it is not a forensically complete, guaranteed audit trail.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">AWS CloudTrail for S3</h4>\n<p style=\"line-height: 1.75\">CloudTrail records <strong>API calls</strong> as structured, signed JSON events, capturing the calling principal's identity (IAM user, role, or federated identity), source IP, timestamp, request parameters, and response elements. For S3, CloudTrail distinguishes two event types:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Management events.</strong> Bucket-level, control-plane operations — CreateBucket, DeleteBucket, PutBucketPolicy, PutBucketAcl, PutBucketVersioning, and similar. These are captured by CloudTrail <strong>by default, at no extra charge</strong>, and are what populate CloudTrail Event history automatically.</li>\n<li><strong>Data events.</strong> Object-level, data-plane operations — GetObject, PutObject, DeleteObject. These are <strong>off by default</strong> and must be explicitly enabled on a trail, because at high request volumes they would generate enormous log volume; they also incur an additional per-event charge once enabled.</li>\n</ul>\n<p style=\"line-height: 1.75\">This distinction is the crux of many real design decisions: if you only need to know when someone changed a bucket policy or deleted a bucket, default management events already have you covered. If you need to know exactly who downloaded a specific confidential object, you must have proactively enabled S3 data events on a trail before the incident occurred.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario: \"Who deleted this bucket?\"</h4>\n<p style=\"line-height: 1.75\">This is a classic security-investigation question, and the correct answer is <strong>CloudTrail, not Server Access Logging</strong> — for a simple reason: once a bucket is deleted, its Server Access Logs (which were being written to a destination bucket) may still exist if that destination is a different, surviving bucket, but access logs never captured the DeleteBucket call in the first place, because DeleteBucket is a control-plane/management operation, not a data-plane request against objects. Access logging only ever logs object-level request traffic to the bucket being logged; it was never designed to capture bucket lifecycle management calls. CloudTrail, on the other hand, records DeleteBucket as a management event by default — captured automatically, with no extra configuration needed in advance.</p>\n<p style=\"line-height: 1.75\">The investigation path: open <strong>CloudTrail Event history</strong> in the console and filter by event name \"DeleteBucket\" (or \"DeleteObject\" if investigating a deleted object, which requires that data events were enabled beforehand) and by the resource name, within the relevant time window. Event history retains 90 days of management events searchable directly in the console with no setup. For a longer retention window, a deeper query, or correlating across many accounts, you'd instead query the CloudTrail logs that a configured <strong>trail</strong> has been continuously delivering to S3, using <strong>Amazon Athena</strong> over those JSON log files — for example, filtering eventSource = s3.amazonaws.com, eventName = DeleteBucket or DeleteObject, and inspecting the userIdentity block to identify the exact IAM principal, access key, and source IP responsible. That userIdentity field is the piece access logging simply does not reliably provide — it may show an anonymized or bucket-owner-relative identity rather than the precise calling principal's ARN.</p>\n<h4 style=\"margin-top: 1.5rem;
