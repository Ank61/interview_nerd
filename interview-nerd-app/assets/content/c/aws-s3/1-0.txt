{"title":"S3 Encryption — SSE-S3, SSE-KMS, SSE-C, and Client-Side Encryption","tags":["encryption","kms","sse-s3","security"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">S3 supports encrypting data <strong>at rest</strong> through several mechanisms that differ in who manages the key and who does the encrypting: <strong>SSE-S3</strong> (Amazon-managed keys), <strong>SSE-KMS</strong> (AWS KMS-managed keys with envelope encryption), <strong>SSE-C</strong> (customer-supplied keys, sent with every request), and <strong>client-side encryption</strong> (the application encrypts before the object ever reaches AWS). As of January 2023, AWS applies <strong>SSE-S3 encryption by default</strong> to every new object in every bucket, so \"unencrypted S3 data\" mostly no longer exists at rest — the real interview question is which of the stronger options to layer on top and why.</p>\n<h4 style=\"margin-top: 1.5rem; It requires zero configuration, has no additional cost, and is now the bucket default. The trade-off is that you have no control over the key and no per-key audit trail — you cannot prove in CloudTrail that a specific principal used a specific key to decrypt a specific object.</p>\n<p style=\"line-height: 1.75\"><strong>SSE-KMS</strong> uses <strong>envelope encryption</strong>: S3 asks KMS for a data key associated with a specific KMS key (CMK), KMS returns both a plaintext data key and an encrypted copy of it, S3 uses the plaintext data key to encrypt the object and then discards it, storing only the encrypted data key alongside the object. On read, S3 sends the encrypted data key back to KMS, which decrypts it (checking IAM and key-policy permissions in the process) and returns the plaintext key so S3 can decrypt the object. This indirection is why every SSE-KMS GET and PUT generates a <strong>GenerateDataKey</strong> or <strong>Decrypt</strong> CloudTrail event tied to the calling principal — a full audit trail SSE-S3 cannot give you.</p>\n<p style=\"line-height: 1.75\"><strong>SSE-C</strong> lets the customer supply their own 256-bit AES key with every PUT and GET, sent as request headers (<code>x-amz-server-side-encryption-customer-key</code> and its MD5). AWS uses it transiently to encrypt/decrypt and then discards it — S3 never stores the key. If you lose the key, the object is unrecoverable, since AWS has no copy anywhere. This requires HTTPS, since the key travels in headers on every call.</p>\n<p style=\"line-height: 1.75\"><strong>Client-side encryption</strong> moves encryption entirely out of AWS: the application encrypts the plaintext locally (often using the AWS Encryption SDK or the S3 Encryption Client) before calling PutObject, and decrypts locally after GetObject. S3 stores and serves ciphertext it can never read. This is the only option that satisfies a true \"AWS must never see plaintext\" requirement.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why Choose KMS Over SSE-S3</h4>\n<p style=\"line-height: 1.75\">Interviewers like this trade-off because it is not \"KMS is strictly better.\" SSE-KMS adds: (1) a CloudTrail record of every key use, tied to a caller identity — critical for compliance frameworks like PCI-DSS or HIPAA that require proof of who accessed encrypted data; (2) fine-grained access control via the <strong>KMS key policy</strong>, layered on top of S3 bucket policies and IAM, so you can require a specific role even if the S3 permissions would otherwise allow the read; (3) the ability to <strong>revoke access instantly</strong> by disabling or scheduling deletion of the KMS key, without touching S3 permissions at all; and (4) support for cross-account and cross-region key grants for controlled sharing. The costs are: a per-request charge for every KMS API call (GenerateDataKey/Decrypt), and the possibility of hitting <strong>KMS request quotas</strong> (region-specific requests-per-second limits) under very high-throughput workloads, which can throttle S3 operations with <code>ThrottlingException</code>. AWS mitigates this with S3 Bucket Keys, which cache a bucket-level data key inside S3 for a short time to drastically cut the number of calls to KMS.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">KMS Key Policy vs IAM Policy</h4>\n<p style=\"line-height: 1.75\">Accessing an SSE-KMS object requires passing <strong>two independent authorization checks</strong>: the caller's IAM policy must allow <code>s3:GetObject</code>/<code>s3:PutObject</code> on the bucket/object, <strong>and</strong> the KMS key policy (plus any IAM policy statements referencing the key) must allow <code>kms:Decrypt</code> or <code>kms:GenerateDataKey</code> for that principal. Unlike most AWS resources, a KMS key policy is the root of trust — even a fully permissive IAM policy is not enough by itself unless the key policy also allows the account/principal (directly or via an \"Enable IAM policies\" statement delegating to IAM). This dual-gate model is exactly what makes KMS useful for defense-in-depth: security teams can lock down who may ever decrypt data independently of who administers S3.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cross-Account KMS and Replication</h4>\n<p style=\"line-height: 1.75\">Using an SSE-KMS object across accounts requires the key policy to explicitly grant the other account's principal <code>kms:Decrypt</code> (and <code>kms:GenerateDataKey</code> for writes), since KMS keys are not implicitly shared even within an AWS Organization. <strong>Replicating</strong> SSE-KMS-encrypted objects (cross-region or same-region) requires additional, explicit setup: the replication rule must specify the destination KMS key, and the replication IAM role needs <code>kms:Decrypt</code> on the source key and <code>kms:Encrypt</code> on the destination key — this is not automatic even if the role otherwise has S3 replication permissions. Forgetting this is one of the most common real-world replication failures.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">If the KMS Key Is Disabled or Deleted</h4>\n<p style=\"line-height: 1.75\">If a KMS key used for SSE-KMS is <strong>disabled</strong>, all GET/PUT operations against objects encrypted with it immediately fail with <code>KMS.DisabledException</code> — objects are not corrupted, just inaccessible until the key is re-enabled. If the key is <strong>scheduled for deletion</strong> (KMS enforces a mandatory 7–30 day waiting window precisely to prevent accidental permanent loss) and deletion completes, the encrypted data keys stored with every object become permanently undecryptable — this is cryptographic, irreversible data loss with no AWS recovery path. This is why key deletion is one of the most dangerous single actions in an AWS account and should always require a documented approval process.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario: Choosing an Encryption Strategy</h4>\n<p style=\"line-height: 1.75\">A healthcare company stores PHI in S3 and must prove, for a HIPAA audit, exactly which employees accessed which records and when, and must be able to instantly cut off all access to a terminated employee without waiting for IAM policy propagation. The answer: use <strong>SSE-KMS with a customer-managed key</strong>, restrict the key policy to a small set of application roles, and rely on CloudTrail's per-key Decrypt/GenerateDataKey events as the audit log. To instantly revoke access, disable the KMS key or remove the principal from the key policy — this is faster and more centralized than untangling bucket policies across dozens of prefixes. SSE-S3 could not satisfy the audit requirement at all, since it produces no per-caller key-usage trail.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">When Client-Side Encryption Is Necessary</h4>\n<p style=\"line-height: 1.75\">Client-side encryption becomes necessary when the threat model includes AWS itself — for example, contractual or regulatory requirements stating that the cloud provider must never be able to view plaintext under any circumstances (including via a compelled legal order to AWS, or an AWS-side misconfiguration). Since SSE-S3, SSE-KMS, and even SSE-C all involve S3 performing the actual encrypt/decrypt operation (even SSE-C keys pass through S3's process in memory), only client-side encryption guarantees end-to-end confidentiality where S3 stores and serves nothing but ciphertext it cannot decode.</p>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"S3 gives you four encryption models.
