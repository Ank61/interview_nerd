Understanding how these layers interact — and where an explicit deny wins — is the single most tested security concept for S3 in AWS interviews, because misconfiguration here is the leading real-world cause of data breaches involving S3.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Identity Policies vs. Resource Policies</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>IAM (identity-based) policies</strong> are attached to a user, group, or role and define what that identity is allowed to do, typically across many resources and services. They answer: \"What can this principal do?\"</li>\n<li><strong>Bucket policies (resource-based)</strong> are attached directly to the bucket and define who can access it. They answer: \"Who can act on this bucket/object?\" and — critically — can grant access to principals in <strong>other AWS accounts</strong> without those accounts needing a matching IAM policy of their own, which is the basis of simple cross-account access.</li>\n</ul>\n<p style=\"line-height: 1.75\">For a request to succeed, at least one applicable policy (IAM or bucket policy, or both together for cross-account cases) must grant the action, and <strong>no</strong> applicable policy may explicitly deny it. AWS's evaluation logic is: gather all applicable policies (IAM policies, bucket policies, ACLs, SCPs, permission boundaries, session policies) → if any explicit <strong>Deny</strong> matches, the request is denied, full stop → otherwise, if any <strong>Allow</strong> matches, the request is permitted → otherwise it's denied by default (implicit deny). <strong>Explicit deny always wins</strong>, regardless of how many Allow statements exist elsewhere.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Request Flow Model</h4>\n<p style=\"line-height: 1.75\">A useful mental model for tracing an S3 request: <strong>User/Role → evaluated against their IAM Policy → request reaches the S3 Bucket → evaluated against the Bucket Policy (and Block Public Access, ACLs if present) → finally reaches the Object.</strong> Both the identity side and the resource side must agree the action is allowed (with the deny-wins rule applied across both) before the object is actually returned or modified. For same-account access, an IAM policy granting <code>s3:GetObject</code> alone is often sufficient without any bucket policy at all; bucket policies become necessary primarily for cross-account grants, public access, or bucket-wide conditions (like enforcing encryption or restricting to a VPC endpoint).</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Anatomy of a Bucket Policy</h4>\n<p style=\"line-height: 1.75\">A bucket policy is a JSON document with the standard IAM policy language elements, scoped to that bucket:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Effect.</strong> <code>Allow</code> or <code>Deny</code>.</li>\n<li><strong>Principal.</strong> Who the statement applies to — an account, IAM user/role ARN, or <code>*</code> for everyone (public). Required in bucket policies since, unlike IAM policies, they're attached to the resource, not the identity.</li>\n<li><strong>Action.</strong> The S3 API action(s), e.g. <code>s3:GetObject</code>, <code>s3:PutObject</code>.</li>\n<li><strong>Resource.</strong> The bucket or object ARN(s) the statement applies to.</li>\n<li><strong>Condition.</strong> Optional constraints, e.g. requiring TLS (<code>aws:SecureTransport</code>), restricting by source IP, or requiring a specific KMS key for encryption.</li>\n</ul>\n<p style=\"line-height: 1.75\">Example: enforcing HTTPS-only access and denying unencrypted uploads.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Block Public Access</h4>\n<p style=\"line-height: 1.75\"><strong>S3 Block Public Access (BPA)</strong> is a safety layer that overrides bucket policies and ACLs, not a replacement for them. It has four independent settings, settable at both the <strong>account level</strong> (applies to every bucket in the account) and the <strong>bucket level</strong> (applies to just that bucket):</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Block public access via new ACLs</strong> and <strong>Block public access via any ACLs</strong> — prevent granting public access through Access Control Lists.</li>\n<li><strong>Block public access via new bucket/access point policies</strong> and <strong>Block public and cross-account access via any bucket/access point policies</strong> — prevent bucket policies from granting public access, even if a policy statement technically allows <code>Principal: \"*\"</code>.</li>\n</ul>\n<p style=\"line-height: 1.75\">Since April 2023, all newly created S3 buckets have Block Public Access enabled by default, and AWS strongly recommends leaving it enabled at the account level unless a bucket genuinely needs to serve public content (e.g., static website hosting), in which case it should be disabled narrowly at the bucket level, ideally paired with tightly scoped bucket policy conditions rather than a blanket public grant. Public S3 buckets are dangerous because a single misconfigured policy or ACL can expose sensitive data (PII, credentials, backups) to the entire internet with no authentication required — a pattern behind numerous well-publicized breaches.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario: Preventing Accidental Public Buckets Organizationally</h4>\n<p style=\"line-height: 1.75\"><strong>Question: \"A developer accidentally makes an S3 bucket public. How do you prevent this organizationally?\"</strong> A strong answer layers preventive and detective controls rather than relying on any single guardrail:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>AWS Organizations + Service Control Policies (SCPs).</strong> At the organization or OU level, apply an SCP that denies actions which would disable Block Public Access or attach public bucket policies, so individual developers structurally cannot override the guardrail even with an otherwise-permissive IAM role.</li>\n<li><strong>Block Public Access enabled account-wide.</strong> Keep BPA on for every account by default, so even a mistakenly permissive bucket policy has no effect unless someone deliberately and explicitly disables BPA for that one bucket.</li>\n<li><strong>AWS Config rules.</strong> Use managed rules like <code>s3-bucket-public-read-prohibited</code> and <code>s3-bucket-public-write-prohibited</code> to continuously evaluate bucket configurations and flag or auto-remediate any bucket that becomes public.</li>\n<li><strong>AWS CloudTrail + monitoring/alerting.</strong> Log all S3 control-plane API calls (like <code>PutBucketPolicy</code>, <code>PutBucketAcl</code>, <code>PutPublicAccessBlock</code>) and alert via EventBridge/CloudWatch or a SIEM whenever one is invoked, so security teams get near-real-time notice of a risky change even if it isn't blocked outright.</li>\n<li><strong>Periodic access review.</strong> Tools like IAM Access Analyzer for S3 proactively flag buckets that are shared outside the account or publicly, independent of the change-time controls above.</li>\n</ul>\n<p style=\"line-height: 1.75\">The layered answer — prevent via SCPs and BPA, detect via Config and CloudTrail, review via Access Analyzer — is what distinguishes a mature answer from \"just turn on Block Public Access.\"</p>\n<div style=\"margin-top: 1rem;
