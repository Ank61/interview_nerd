{"title":"S3 and Microservices — Asynchronous Pipelines","tags":["s3","microservices","eventbridge","architecture"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">In microservice architectures, S3 is often more than storage — it becomes a <strong>durable handoff point</strong> between independent services that need to be decoupled in time, in deployment, and in failure domain. The canonical pipeline shape is: <strong>Upload Service → S3 → EventBridge → Image Processing Service → S3 → Notification Service</strong>. Understanding why this beats direct service-to-service calls, and how to design each stage, is core system-design knowledge for anyone working with S3 at scale.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Pipeline, Stage by Stage</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Upload Service.</strong> Accepts the incoming file from a user or upstream system and writes it to S3 (often via a presigned URL so the file goes directly to S3 rather than through the service's own compute). Its job ends the moment the object is durably stored.</li>\n<li><strong>S3 (raw uploads bucket).</strong> Durably persists the object and, on creation, emits an event.</li>\n<li><strong>EventBridge.</strong> Receives the S3 object-created event (S3 can send events directly to EventBridge when enabled on the bucket) and routes it to one or more interested consumers based on event pattern rules, without the Upload Service knowing or caring who those consumers are.</li>\n<li><strong>Image Processing Service.</strong> Triggered by the routed event, reads the original object from S3, performs its work (resizing, transcoding, thumbnail generation), and writes the result to a separate S3 location (a processed-images bucket or a distinct prefix).</li>\n<li><strong>S3 (processed bucket).</strong> Durably persists the processed output and emits its own creation event.</li>\n<li><strong>Notification Service.</strong> Triggered by that second event, notifies the end user or downstream system that processing is complete (email, push notification, webhook, or a status update visible via an API).</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why S3 + EventBridge Beats Direct Service-to-Service Calls</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Durability of the artifact.</strong> Once the Upload Service writes to S3, the file is durably persisted independent of whether any downstream service is up, healthy, or even deployed yet. A direct synchronous call from Upload Service to Image Processing Service would fail the entire upload if Image Processing were down; here, the upload succeeds regardless, and processing catches up whenever the consumer is ready.</li>\n<li><strong>Adding new consumers without touching the producer.</strong> Because EventBridge routes by event pattern rather than by a hardcoded list of receivers, a new downstream service (say, a virus-scanning service, or an analytics pipeline) can subscribe to the same S3 object-created event by adding a new EventBridge rule — with <strong>zero changes</strong> to the Upload Service or the Image Processing Service. This is the core decoupling win over direct HTTP calls, which would require the producer to know about and call every new consumer explicitly.</li>\n<li><strong>Natural retry and replay.</strong> Because the object persists in S3 independent of the event, a failed or lost event isn't a lost job — a service can be pointed at the bucket to reprocess any object that's missing its expected downstream output, and EventBridge itself supports retry policies and dead-letter queues for failed rule targets. Replaying a whole backlog is as simple as re-listing the source prefix and re-emitting synthetic events, something not possible with a purely synchronous call chain.</li>\n<li><strong>Failure isolation.</strong> If the Image Processing Service crashes mid-run or is being redeployed, the Upload Service is completely unaffected — it already finished its job by writing to S3. Failures in one stage don't cascade backward into upstream services the way a synchronous call chain would.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Designing Each Service to Be Independently Deployable, Scalable, and Isolated</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Independent deployability.</strong> Each service should own its own deployment pipeline and have no compile-time or runtime dependency on the internals of the others — only a shared contract on S3 object naming conventions and the event schema. The Image Processing Service can be redeployed, rolled back, or rewritten in a different language without the Upload Service changing at all.</li>\n<li><strong>Independent scalability.</strong> Because the hop between stages is asynchronous (an event, not a blocking call), each service scales based on its own load characteristics — the Upload Service can scale with incoming traffic while the Image Processing Service, likely more CPU-intensive, scales based on its own queue depth or concurrent Lambda invocations, entirely decoupled from upload volume in real time.</li>\n<li><strong>Failure isolation in practice.</strong> Route EventBridge targets through an <strong>SQS queue with a dead-letter queue</strong> in front of the Image Processing Service (rather than invoking it directly) so a burst of events queues up safely instead of overwhelming the consumer, and poison messages (events that repeatedly fail processing) land in the DLQ for inspection instead of blocking the whole pipeline.</li>\n<li><strong>Idempotency across the chain.</strong> Because EventBridge and S3 notifications are at-least-once, every stage (Image Processing, Notification) must be idempotent with respect to reprocessing the same object — consistent with the retry/idempotency principles used throughout S3-backed systems generally.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario: Justifying the Design Choice</h4>\n<p style=\"line-height: 1.75\">If asked \"why not just have the Upload Service call the Image Processing Service's API directly after the upload finishes?\", a strong answer highlights that a direct call couples the two services' <strong>availability</strong> (a processing outage now blocks uploads), <strong>deployment</strong> (schema or contract changes force coordinated releases), and <strong>scaling</strong> (a slow processing service applies backpressure directly onto uploads) — whereas S3 plus EventBridge removes all three couplings by turning the interaction into \"write an object, and let anyone interested react to it whenever they're ready.\"</p>\n<div style=\"margin-top: 1rem;
