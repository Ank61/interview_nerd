{"title":"S3 and CloudFront — Serving Private Content Securely","tags":["s3","cloudfront","signed-urls","oac"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">Pairing <strong>Amazon CloudFront</strong> with a <strong>private S3 bucket</strong> is the standard architecture for serving content — images, videos, downloads — to authenticated users at low latency, without ever exposing the bucket itself to the public internet. CloudFront acts as a caching, HTTPS-terminating CDN in front of S3, while access control decisions (who gets to see what) stay entirely in your application layer.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">CDN Caching Fundamentals</h4>\n<p style=\"line-height: 1.75\">CloudFront replicates content to <strong>edge locations</strong> around the world so that repeat requests for the same object are served from a location physically close to the viewer, instead of round-tripping to the S3 bucket's home region every time. The <strong>Origin</strong> is the source of truth — here, an S3 bucket — that CloudFront fetches from on a cache miss. Each object's caching behavior is governed by <strong>Cache-Control headers</strong> (set on the S3 object itself, or overridden by a CloudFront cache policy) and a <strong>TTL</strong> (time-to-live), which determines how long an edge location keeps serving a cached copy before re-checking the origin.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Origin Access Control (OAC)</h4>\n<p style=\"line-height: 1.75\"><strong>Origin Access Control (OAC)</strong> is the current, recommended mechanism for letting CloudFront — and only CloudFront — read from a private S3 bucket. You attach an OAC to the CloudFront distribution's S3 origin, and update the bucket policy to allow <code>s3:GetObject</code> only when the request's <code>AWS:SourceArn</code> matches that specific CloudFront distribution. The S3 bucket can then <strong>block all public access</strong> entirely; there is no public bucket policy, no public ACL, and direct <code>https://bucket.s3.amazonaws.com/...</code> requests are denied. OAC replaced the older <strong>Origin Access Identity (OAI)</strong>, which used a special CloudFront-managed IAM identity to sign requests to S3. OAC is preferred going forward because it supports SSE-KMS-encrypted objects natively, works with all S3 regions, and uses standard SigV4 signing rather than OAI's more limited mechanism — AWS recommends migrating existing OAI distributions to OAC.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Signed URLs vs Signed Cookies</h4>\n<p style=\"line-height: 1.75\">OAC/OAI locks the S3 origin so only CloudFront can reach it — but by default, anyone who knows a CloudFront URL can still request the object. To restrict access to specific authenticated users, CloudFront supports <strong>signed URLs</strong> and <strong>signed cookies</strong>, both generated by your application using a CloudFront key pair after your own authorization logic approves the request.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Signed URLs.</strong> Best for granting access to a <strong>single object</strong> (one video file, one PDF download link). The signature, expiration, and optional IP restriction are embedded directly in the query string of that one URL.</li>\n<li><strong>Signed cookies.</strong> Best for granting access to <strong>multiple resources or an entire session</strong> — for example, every asset in a video streaming session or every image on a private photo gallery page — without needing to sign every individual URL. The cookie is set once after login and CloudFront validates it on every subsequent request to matching paths.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario — Serving Private Images to Authenticated Users</h4>\n<p style=\"line-height: 1.75\">The canonical system-design walk-through: <strong>User → Application → Authorization check → CloudFront Signed URL generated → User's browser requests CloudFront → CloudFront validates signature → CloudFront fetches from private S3 origin via OAC → response cached at edge and returned</strong>. Step by step: (1) the user requests an image through your application; (2) your backend checks that this user is authorized to view it; (3) if authorized, the backend uses the AWS SDK and a CloudFront private key to generate a signed URL with a short expiration (for example, 5-15 minutes); (4) the browser is redirected to or given that signed URL; (5) CloudFront validates the signature and expiration itself, with no round-trip to your backend needed; (6) CloudFront retrieves the object from the private S3 bucket (allowed only because of OAC) and returns it, caching it at the edge for subsequent requests within the TTL. Critically, the S3 bucket itself never has to know anything about individual users — all authorization logic lives in your application and in the CloudFront signature.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cache Invalidation and HTTPS Enforcement</h4>\n<p style=\"line-height: 1.75\">Because CloudFront caches aggressively, updating or deleting an S3 object doesn't immediately change what edge locations serve — you either wait out the TTL or issue a <strong>cache invalidation</strong> to force edges to re-fetch from the origin (invalidations have a cost at high volume, so versioned object keys, for example including a hash in the filename, are often preferred over frequent invalidations).
