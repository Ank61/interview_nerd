A <strong>Multi-Region Access Point</strong> is a different, higher-level construct: it is attached to a <strong>set of buckets in different regions</strong> and exposes a single global hostname (something like <code>mfzwi23gnjvgw.mrap.accesspoint.s3-global.amazonaws.com</code>). A global user's request — say, from anywhere in the world — hits that one endpoint, and AWS's global network routes it, using <strong>AWS Global Accelerator</strong> technology under the hood, to whichever participating regional bucket currently offers the best latency and availability for that user, without the client needing to know which region that is.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Routing Behavior: Active-Active and Active-Passive</h4>\n<p style=\"line-height: 1.75\">MRAP supports two routing control patterns:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Active-active (latency-based routing).</strong> All participating regions are eligible to serve traffic simultaneously, and each request is routed to whichever region gives that specific client the lowest latency. This is the default behavior and is ideal for globally distributed user bases reading and writing the same logical dataset.</li>\n<li><strong>Active-passive (failover routing).</strong> You can explicitly designate one region as primary and another as a failover target, and use <strong>routing control</strong> (via Route 53 Application Recovery Controller integration) to redirect all traffic away from a failed or degraded region to the standby region, supporting a disaster-recovery pattern with a controlled, explicit cutover rather than pure latency-based routing.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Replication Dependency</h4>\n<p style=\"line-height: 1.75\">A Multi-Region Access Point does not itself copy or synchronize data — it is purely a <strong>routing layer</strong> in front of independent regional buckets. For an MRAP to be useful, the underlying buckets must be kept in sync with each other via <strong>S3 Cross-Region Replication (CRR)</strong>, typically configured bidirectionally so a write accepted in one region eventually propagates to the others. This has an important consequence: replication is <strong>asynchronous</strong>, so there is a replication lag window during which a global user routed to Region B might briefly not yet see an object that was just written by a user routed to Region A. Any system built on MRAP must accept this eventual-consistency characteristic, since MRAP inherits CRR's timing behavior rather than eliminating it.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem;
