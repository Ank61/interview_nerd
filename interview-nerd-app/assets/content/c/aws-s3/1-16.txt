Interviewers use these scenarios to see whether a candidate has actually operated S3 in production, because the fix is rarely \"check the IAM policy\" alone — real S3 issues usually require walking an ordered chain of possible causes until one is confirmed.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">1. 403 AccessDenied</h4>\n<p style=\"line-height: 1.75\">A 403 means S3 evaluated the request and explicitly denied it — the object may not even exist, but S3 won't tell you that until access is resolved. The debug chain, in order:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>IAM policy.</strong> Does the calling principal's identity-based policy actually grant <code>s3:GetObject</code> (or the relevant action) on that resource ARN, including the trailing <code>/*</code> for object-level actions?</li>\n<li><strong>Bucket policy.</strong> Is there an explicit <code>Deny</code> statement (these always win over any Allow) or a missing Allow for cross-account access?</li>\n<li><strong>Block Public Access.</strong> Both account-level and bucket-level BPA settings can silently override a bucket policy that looks correct — a bucket policy granting public read does nothing if BPA is still enabled.</li>\n<li><strong>Object Ownership / ACLs.</strong> If the bucket uses ACLs (Object Ownership not set to Bucket owner enforced) an object uploaded by another account may not be readable by the bucket owner without an explicit ACL grant.</li>\n<li><strong>KMS permissions.</strong> If the object is SSE-KMS encrypted, the caller needs <code>kms:Decrypt</code> (or <code>kms:GenerateDataKey</code> for writes) on the key's policy in addition to S3 permissions — a very common miss when the IAM policy looks fine.</li>\n<li><strong>VPC endpoint policy.</strong> If the request originates from inside a VPC through an S3 Gateway or Interface endpoint, the endpoint's own policy can restrict which buckets or actions are reachable, independent of IAM.</li>\n<li><strong>SCP (Service Control Policy).</strong> At the AWS Organizations level, an SCP can deny S3 actions account-wide regardless of what IAM and bucket policies allow.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">2. 404 NoSuchKey</h4>\n<p style=\"line-height: 1.75\">A 404 confirms permissions were fine but the object wasn't found under that exact key. Checklist: verify the <strong>exact key name and prefix</strong> (case-sensitive, no accidental leading/trailing slash); confirm the <strong>region</strong> the client is targeting matches the bucket's actual region; if versioning is enabled, check whether a specific <strong>version ID</strong> was requested that no longer exists, or whether the \"current\" version is actually a <strong>delete marker</strong> (a GET on a key whose latest version is a delete marker returns 404 by design); and check for <strong>URL encoding</strong> issues — keys containing spaces, plus signs, or other special characters can be double-encoded or under-encoded by the client, producing a key that doesn't match anything stored.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">3. Upload Is Slow</h4>\n<p style=\"line-height: 1.75\">Investigate in this order: <strong>network path</strong> — is the client geographically far from the bucket's region, adding round-trip latency per request? <strong>Multipart upload</strong> — is the upload using multipart with parallel part uploads, or sending one giant single PUT that can't use multiple TCP connections? <strong>Parallelism</strong> — for multipart uploads, is the client using a reasonable number of concurrent part uploads (the AWS CLI and SDK high-level uploaders default to several threads, but custom code often uploads parts serially)? <strong>Region distance</strong> — for globally distributed clients uploading to a single-region bucket, consider whether cross-region latency is the dominant factor. <strong>Transfer Acceleration</strong> — S3 Transfer Acceleration routes uploads through CloudFront edge locations over AWS's backbone network, often meaningfully improving throughput for distant clients, and is worth testing with the S3 Transfer Acceleration speed comparison tool. <strong>Object size</strong> — many small objects each pay full request overhead and TLS handshake cost; batching or increasing multipart part size can help.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">4. S3 Costs Increased</h4>\n<p style=\"line-height: 1.75\">This overlaps heavily with the dedicated cost-optimization playbook: check <strong>storage</strong> growth by class, <strong>noncurrent version</strong> accumulation on versioned buckets, active <strong>replication</strong> rules duplicating data and adding transfer cost, a spike in <strong>request count</strong> (often from a retry storm or inefficient polling/LIST pattern), unexpected <strong>retrieval</strong> charges from a batch job restoring Glacier objects, <strong>data transfer</strong> to the internet or across regions, and <strong>incomplete multipart uploads</strong> left behind by a failing upload client.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">5. Objects Disappeared</h4>\n<p style=\"line-height: 1.75\">Rarely does S3 lose data — \"disappeared\" almost always means something deleted or hid it. Check <strong>versioning</strong> status first: if enabled, the object may still exist under a prior version, hidden behind a <strong>delete marker</strong> — listing versions (<code>ListObjectVersions</code>) reveals this immediately, and removing the delete marker restores visibility. Check <strong>CloudTrail data events</strong> (if S3 data-event logging is enabled) to find exactly which principal issued the DeleteObject or DeleteObjects call and when. Check <strong>lifecycle configuration</strong> for an expiration rule that fired earlier than expected (a misconfigured date-based or age-based expiration is a classic cause). Check <strong>replication</strong> — if delete marker replication is enabled, a delete in the source region propagates to the destination automatically, which can look like data \"disappearing everywhere at once.\" Finally, check <strong>IAM</strong> for recent policy changes that might have allowed a process broader delete permissions than intended.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">6. Application Gets Intermittent S3 Errors</h4>\n<p style=\"line-height: 1.75\">Intermittent (not constant) errors point toward transient, load-related, or environmental causes rather than a hard misconfiguration. Check for <strong>503 SlowDown throttling</strong> — S3 automatically scales request rate per prefix, but a sudden burst can briefly exceed that scaling and return 503s. Check the client's <strong>retry strategy</strong> — is it retrying at all, and with exponential backoff and jitter, or failing immediately on the first 503/500? Review actual <strong>request rate</strong> against the prefix to see if load is genuinely spiking, which may call for spreading keys across more prefixes. Rule out <strong>network</strong> flakiness (packet loss, DNS resolution issues, connection pool exhaustion in the SDK). Check <strong>IAM</strong> for a policy or condition that intermittently fails (e.g., a time- or IP-based condition). Check <strong>KMS</strong> throttling — KMS has its own request-per-second limits, and high-volume SSE-KMS access can hit KMS throttling separately from S3 throttling. Confirm the client is targeting the correct <strong>region</strong> consistently (a load balancer or DNS misconfiguration alternating between regions produces intermittent failures).
