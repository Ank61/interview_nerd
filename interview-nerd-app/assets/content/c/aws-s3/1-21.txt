{"title":"S3 and SQS — Buffering and Worker-Based Processing","tags":["S3","SQS","Decoupling","Messaging"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\"> While <strong>S3 → Lambda</strong> is a natural fit for lightweight, fast, per-object processing, many real-world systems route S3 events through <strong>Amazon SQS</strong> instead, using a queue as a buffer in front of a fleet of workers. This pattern — <strong>S3 → SQS → Worker</strong> — trades some of Lambda's simplicity for explicit control over concurrency, retries, and processing duration, and it is the pattern interviewers expect you to reach for when asked how to handle bursty or heavyweight S3-triggered workloads at scale.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why Insert a Queue Instead of Calling Lambda Directly</h4>\n<p style=\"line-height: 1.75\">S3 can publish event notifications directly to an <strong>SQS queue</strong> instead of (or in addition to) Lambda, and workers — running on EC2, ECS, Fargate, or even Lambda functions that poll the queue — pull messages at their own pace. The motivations for this extra hop are concrete, not just architectural preference:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Backpressure.</strong> A queue naturally absorbs traffic bursts. If ten thousand objects land in S3 within a minute, direct S3 → Lambda invocation would spike concurrent Lambda executions dramatically, potentially hitting account concurrency limits and throttling other functions sharing that limit, or overwhelming a downstream database or API that the processing logic calls. With SQS in between, messages simply queue up and workers drain them at a sustainable, controlled rate.</li>\n<li><strong>Retry control.</strong> SQS gives you explicit, tunable retry semantics via <strong>visibility timeout</strong> — when a worker receives a message, it becomes invisible to other consumers for a set period; if the worker crashes or fails to delete it in time, the message reappears for another attempt. Combined with a <strong>redrive policy</strong> sending messages to a <strong>dead-letter queue</strong> after a configured number of failed receives, this is far more explicit and inspectable than Lambda's built-in asynchronous retry defaults (a fixed small number of automatic retries with less operator control per-message).</li>\n<li><strong>Buffering and pacing.</strong> Workers can process messages on their own schedule rather than reactively per-event. This decouples the rate of S3 writes from the rate of processing, which matters when downstream systems (databases, third-party APIs with rate limits) can't handle a 1:1 spike matching upload volume.</li>\n<li><strong>Long-running and batch workloads.</strong> Lambda functions are capped at a <strong>15-minute maximum execution duration</strong>. Workers running on EC2, ECS, or Fargate have no such ceiling — they can run video transcoding, large ML inference, or multi-hour ETL jobs that a Lambda function structurally cannot complete. Workers can also pull and process <strong>multiple SQS messages per batch</strong> (up to 10 per <code>ReceiveMessage</code> call), amortizing per-unit overhead across many objects rather than incurring a full cold start or connection setup per single S3 event.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">How the Pattern Is Wired</h4>\n<p style=\"line-height: 1.75\">S3 bucket notifications support SQS as a native destination type, just like Lambda: you configure a <strong>QueueConfiguration</strong> specifying the event type and optional prefix/suffix filter, and S3 needs an <strong>SQS queue access policy</strong> (not a Lambda-style resource policy) granting the <strong>s3.amazonaws.com</strong> principal <strong>sqs:SendMessage</strong> rights, scoped by <strong>SourceArn</strong> to the bucket. Workers then call <strong>ReceiveMessage</strong> in a polling loop (ideally using <strong>long polling</strong> with <code>WaitTimeSeconds</code> set to reduce empty responses and cost), process the referenced S3 object, and call <strong>DeleteMessage</strong> only after processing succeeds — this delete-on-success pattern is what gives you at-least-once, retry-safe processing.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario: Choosing Between Direct Lambda and SQS-Buffered Workers</h4>\n<p style=\"line-height: 1.75\">Suppose you're asked to design ingestion for a system where users upload video files to S3 that must be transcoded into multiple resolutions, and upload volume spikes heavily during business hours. Direct S3 → Lambda would immediately run into two walls: <strong>transcoding a large video can easily exceed Lambda's 15-minute limit</strong>, and a burst of uploads could spike concurrent invocations against your account's Lambda concurrency limit, causing throttling that cascades into other unrelated functions. The correct answer is <strong>S3 → SQS → Fargate/EC2 worker fleet</strong>: S3 publishes an event per upload to SQS, an auto-scaling worker fleet polls the queue and pulls jobs at a rate matched to available capacity, each worker can run a transcoding job for as long as it takes, and a visibility timeout tuned to something comfortably longer than expected job duration (with periodic <code>ChangeMessageVisibility</code> calls for very long jobs) ensures a crashed worker's job is retried rather than lost.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Related Pattern: Fan-Out with SNS</h4>\n<p style=\"line-height: 1.75\">A single S3 bucket notification can only target a limited set of destinations directly, and if <strong>multiple independent consumers</strong> each need their own copy of every event (e.g., one team wants to index metadata, another wants to run virus scanning, a third wants to trigger a downstream ETL), the standard approach is <strong>S3 → SNS → multiple SQS queues</strong> (fan-out). S3 publishes each event once to an SNS topic, and SNS delivers a copy of that message to every subscribed SQS queue. Each consumer team owns and scales its own queue and worker fleet independently, and a slow or backed-up consumer never affects the others because each has an isolated queue.</p>\n<div style=\"overflow-x: auto;
