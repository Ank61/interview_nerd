Some actions are <strong>bucket-level</strong> and target the bucket ARN itself; others are <strong>object-level</strong> and target the bucket ARN plus a wildcard for keys. Getting comfortable reasoning about exactly which ARN pattern each action needs is the single most useful IAM skill for debugging S3 access issues, and it's exactly what these three scenarios test.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Scenario 1: \"The user can list the bucket but cannot download any objects. Why?\"</h4>\n<p style=\"line-height: 1.75\">This is the single most common S3 IAM confusion. <strong>s3:ListBucket</strong> is a <strong>bucket-level</strong> action — it asks S3 \"what keys exist in this bucket,\" and its Resource element in a policy must be the bucket ARN itself, with no trailing <strong>/*</strong>: <strong>arn:aws:s3:::my-bucket</strong>. <strong>s3:GetObject</strong>, on the other hand, is an <strong>object-level</strong> action — it asks S3 \"give me the bytes of this specific key,\" and its Resource element must be the bucket ARN followed by a wildcard for the key: <strong>arn:aws:s3:::my-bucket/*</strong>. These are two structurally different ARNs pointing at two different resource types (the bucket resource vs. the objects within it), and IAM evaluates each action against its own Resource element independently. A policy that grants only <strong>s3:ListBucket</strong> on <strong>arn:aws:s3:::my-bucket</strong> will let a user see the list of keys (via ListObjectsV2) but will deny every GetObject call with an Access Denied, because no statement grants s3:GetObject on any object ARN. The fix is simply adding a second statement (or extending the Resource in the existing one, though best practice keeps them separate since the ARN shapes differ) granting s3:GetObject on arn:aws:s3:::my-bucket/*.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Scenario 2: \"The user can upload files but cannot delete them.\"</h4>\n<p style=\"line-height: 1.75\">This follows the same object-level pattern but is even more direct, since both actions target the same ARN shape. <strong>s3:PutObject</strong> and <strong>s3:DeleteObject</strong> are both object-level actions using Resource <strong>arn:aws:s3:::my-bucket/*</strong> — but they are still <strong>separate, independently-grantable actions</strong>. A policy granting only s3:PutObject (and perhaps s3:GetObject) on that Resource will let the user upload and read objects, but any DeleteObject call is denied because no statement authorizes it. This is frequently an intentional design, not a bug: many write-once/append-only or compliance-sensitive workflows (audit logs, financial records, content pipelines with a separate cleanup process) deliberately grant upload rights to application roles while withholding delete rights, sometimes reinforced further with S3 Object Lock or versioning plus a lifecycle policy so only a separate, tightly-controlled process can ever remove data.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Scenario 3: \"Cross-account access between Account A and Account B.\"</h4>\n<p style=\"line-height: 1.75\">Cross-account S3 access requires permission granted from <strong>both sides</strong> — a single IAM policy in one account is never sufficient by itself. The pattern:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Account A (the caller's side).</strong> An IAM role in Account A must have an identity-based policy allowing sts:AssumeRole against the role ARN in Account B (or, if directly calling S3 cross-account without assuming a role, the calling principal's own identity policy must allow the relevant s3:* actions on Account B's bucket ARN).</li>\n<li><strong>Account B (the resource owner's side).</strong> Because S3 buckets are resource-owner-controlled, Account B must attach a <strong>bucket policy</strong> to the bucket that explicitly names Account A's role (or user) as a <strong>Principal</strong> and grants it the needed actions (e.g., s3:GetObject, s3:PutObject) on the bucket/object ARNs. Without this bucket policy statement, Account A's role is denied even if its own IAM policy in Account A allows the action — IAM policies can only grant permissions on resources the account owns; they cannot unilaterally grant access into another account's resources.</li>\n</ul>\n<p style=\"line-height: 1.75\">This is the AWS cross-account trust model in miniature: <strong>the identity's home account must allow the action, and the resource's owning account must allow the identity</strong>. Only when both sides agree does the request succeed. A common variant uses an IAM role in Account B that Account A's role assumes via sts:AssumeRole (with Account B's role trust policy naming Account A as a trusted principal), after which the assumed role — now effectively \"in\" Account B — accesses the bucket using an ordinary same-account bucket policy or even no bucket policy at all if the role already has sufficient permissions in Account B.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario: debugging a three-layer denial</h4>\n<p style=\"line-height: 1.75\">A candidate is told: \"An engineer in Account A assumes a role and tries to GetObject from a bucket in Account B. Walk through your debugging process.\" The systematic answer: first check the assumed role's own identity policy in Account A — does it allow s3:GetObject on the target bucket ARN pattern (arn:aws:s3:::bucket-in-b/*)? Second, check Account B's bucket policy — does it have a statement with Principal referencing Account A's role ARN, allowing s3:GetObject on the same object ARN pattern? Third, check for any explicit Deny anywhere in the chain — SCPs at the AWS Organizations level, permission boundaries on the role, or a Deny statement in the bucket policy — since an explicit Deny anywhere always overrides an Allow.
