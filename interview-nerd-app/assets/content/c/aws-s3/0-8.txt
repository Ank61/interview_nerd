Anyone who possesses that URL can perform the specific operation it was signed for — typically a GET or a PUT — for a limited time window, <strong>without needing any AWS credentials of their own</strong>. If your backend's IAM role only has <code>s3:PutObject</code> on <code>uploads/*</code>, any presigned PUT URL it generates can only ever succeed for keys under that prefix — the URL cannot grant more access than the signer actually has. Conversely, if the signer has broad permissions, a bug that lets a URL be generated for the wrong key or bucket inherits that same broad scope, which is why presigning should always be done with a narrowly-scoped IAM role or session, not a set of admin credentials. Every presigned URL also carries an <strong>expiration</strong> (up to 7 days when signed with IAM user/role credentials via SigV4, or shorter when using temporary STS credentials, since the URL cannot outlive the STS session token itself) — after that timestamp, S3 rejects the request regardless of anything else.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Security Implications</h4>\n<p style=\"line-height: 1.75\">A presigned URL is a <strong>bearer credential</strong>: S3 does not check who is making the request, only whether the signature and expiration in the URL are valid. This means:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li>Anyone who obtains the URL — through a leaked log line, a browser history, a referrer header, or a forwarded link — can use it until it expires, with no additional login or authorization check.</li>\n<li>URLs should be treated like short-lived secrets: not logged in plaintext, not embedded in long-lived emails when the content is sensitive, and given the shortest expiration that is practical for the use case.</li>\n<li>For uploads, a presigned PUT alone does not restrict content-type, size, or other object metadata unless those constraints were included in the signature (via signed headers) or enforced separately with S3 Object Lambda, a bucket policy condition, or a follow-up validation step after upload.</li>\n<li>Presigned URLs do not bypass bucket-level Block Public Access settings for GET in the way a truly public object would, but they do bypass the need for the requester to have an IAM identity at all — the security boundary shifts entirely to \"who has the link.\"</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why the Backend Doesn't Need to Proxy the File</h4>\n<p style=\"line-height: 1.75\">Without presigned URLs, a naive architecture routes file bytes through the application server: <strong>Browser to Backend to S3</strong>. Every byte of every upload or download consumes the backend's own bandwidth, memory/connection slots, and compute time, even though the backend adds no value to that transfer beyond authorization. With presigned URLs, the backend's job shrinks to just the authorization decision: <strong>Frontend requests an upload URL to Backend</strong>, the <strong>Backend generates a presigned PUT URL</strong> (a cheap, local, sub-millisecond operation) and returns it, then <strong>Frontend PUTs the file bytes directly to S3</strong>.
