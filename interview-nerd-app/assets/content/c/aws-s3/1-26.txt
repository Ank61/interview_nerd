The client then <strong>PUTs directly to S3</strong>, which is why presigned URLs exist at all: S3 can absorb massive concurrent upload throughput that a typical application tier cannot.</p>\n<p style=\"line-height: 1.75\">The <strong>S3 event → SQS</strong> hop decouples \"the file landed\" from \"the file gets processed.\" If you removed SQS and had S3 invoke a worker synchronously (or had the client call the API again after upload to trigger processing), you'd lose retry semantics and backpressure handling — a burst of uploads would either overwhelm downstream processing or silently drop notifications if the direct call failed. SQS buffers that burst and lets the <strong>worker</strong> pull at its own pace, retrying failed messages instead of losing them.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: limit and can run into tens of gigabytes; multipart also lets the client parallelize parts and resume individual failed parts instead of restarting a multi-GB upload from zero. Removing it means large uploads fail outright or become extremely fragile on flaky connections.</p>\n<p style=\"line-height: 1.75\"><strong>EventBridge</strong> sits between the S3 event and SQS here (rather than S3 pushing to SQS directly) because a video platform typically needs to fan the same \"new video\" event out to <strong>multiple independent consumers</strong> — transcoding, content moderation scanning, metadata extraction, analytics — and EventBridge's rule-based routing does that fan-out far more flexibly than S3's native event notifications, which support a limited number of destinations per configuration. Remove EventBridge and adding a second consumer later means re-plumbing the bucket's notification config instead of adding a rule.</p>\n<p style=\"line-height: 1.75\">The <strong>processing fleet</strong> transcodes into multiple resolutions/bitrates so playback can adapt to each viewer's bandwidth (adaptive bitrate streaming); skip this and every viewer downloads the same file regardless of connection quality, causing buffering on weak connections and wasted bandwidth on strong ones. Using <strong>separate raw and processed buckets</strong> matters for two reasons: it lets you apply different lifecycle policies (raw originals might move to Infrequent Access or Glacier quickly since they're rarely re-read once processed, while processed images stay hot), and it avoids the event-notification recursion hazard of writing processed images back into the same bucket-prefix that triggers the event, which can cause infinite reprocessing loops if not carefully scoped by prefix/suffix filters.</p>\n<p style=\"line-height: 1.75\">If you removed <strong>SQS</strong> and had S3 invoke Lambda directly (S3 does support this natively for simple cases), you'd lose the queue's buffering during traffic spikes and its retry/dead-letter-queue semantics for images that fail to process — a burst of uploads could throttle concurrent Lambda invocations and silently drop notifications past retry limits without a DLQ to catch them.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Design 4 — Multi-Region S3</h4>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">         <i class=k>Global</i> Users\n              <i class=o>|</i>\n              v\n Multi<i class=o>-</i>Region Access Point (MRAP)\n        <i class=o>/</i>              \\\n       v                v\nUS S3 Bucket   <i class=o>&lt;</i><i class=c>-----&gt;  EU S3 Bucket</i>\n  (us<i class=o>-</i>east<i class=n>-1</i>)  bidirectional  (eu<i class=o>-</i>west<i class=n>-1</i>)\n                  replication</code></pre></div>\n<p style=\"line-height: 1.75\">The <strong>Multi-Region Access Point</strong> gives clients a single global endpoint and ARN; AWS's global network routes each request to whichever bucket is lowest-latency (or healthy) for that client, without the client needing region-aware logic. Remove the MRAP and you push that routing decision onto the client or a bespoke DNS/latency-based routing layer, which is more code to build and slower to fail over during a regional outage.</p>\n<p style=\"line-height: 1.75\"><strong>Bidirectional replication</strong> between the US and EU buckets is what keeps both regions' data consistent so that a write accepted in one region eventually shows up when read from the other — without it, the MRAP would be routing users to two buckets with diverging content, and a user who writes in the US and then gets routed to the EU bucket on their next request wouldn't see their own write. This design accepts <strong>eventual consistency</strong> across regions as the cost of active-active global availability; if the interviewer pushes on strong consistency, the honest answer is that MRAP with bidirectional CRR is an availability/latency-optimized pattern, not a strongly consistent one, and conflicting concurrent writes to the same key in both regions need an explicit resolution strategy (e.g., last-writer-wins via timestamps, or partitioning keys by region).</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Design 5 — Compliance Storage</h4>\n<div class=\"code\"><div class=\"code-head\"><span>sql</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\">Application\n     <i class=o>|</i>\n     v\n   S3 Bucket\n     <i class=o>|</i><i class=c>-- Versioning enabled</i>\n     <i class=o>|</i><i class=c>-- Object Lock (Compliance/Governance mode)</i>\n     <i class=o>|</i><i class=c>-- SSE-KMS encryption</i>\n     <i class=o>|</i>\n     v\n  CloudTrail (data events)\n     <i class=o>|</i>\n     v\n  Audit log <i class=o>/</i> SIEM</code></pre></div>\n<p style=\"line-height: 1.75\"><strong>Versioning</strong> is the prerequisite for Object Lock — Object Lock retention and legal holds are applied per version, so you cannot enable Object Lock without versioning, and without versioning an overwrite would simply destroy the prior state with no immutable trail. <strong>Object Lock</strong> (specifically Compliance mode for regulatory retention like SEC 17a-4 or Governance mode for internally-enforced holds) is what actually makes data immutable for a retention period — even an account administrator cannot delete or shorten retention on a Compliance-mode object before its retain-until date. Remove Object Lock and you have versioning (which protects against accidental overwrite/delete) but nothing stopping a malicious or compromised principal with delete permissions from purging the version history.</p>\n<p style=\"line-height: 1.75\"><strong>SSE-KMS</strong> adds customer-managed-key encryption with its own audit trail of key usage via CloudTrail, which regulated workloads often require over SSE-S3's AWS-managed keys, specifically because you can control and revoke key access independently of S3 bucket permissions, and rotate or disable the key entirely as an emergency kill-switch. Finally, <strong>CloudTrail</strong> data events log every S3 API call (GetObject, PutObject, DeleteObject, etc.) against the bucket, which is what lets an auditor answer \"who accessed this object and when\" — without it, Object Lock proves data wasn't tampered with, but you have no record of who read it, which is often an equally important compliance requirement (e.g., HIPAA access logging).</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario: defending a design under pushback</h4>\n<p style=\"line-height: 1.75\">A common interview pattern is to present one of these designs and then ask \"what if traffic spikes 100x\" or \"what if a region goes down.\" For Design 1, a 100x upload spike is absorbed because clients PUT directly to S3 (which scales far beyond any application tier) and SQS buffers the processing backlog so workers catch up without dropping events.
