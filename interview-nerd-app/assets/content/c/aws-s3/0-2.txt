{"title":"S3 Storage Classes — Choosing the Right Tier for Access Patterns","tags":["S3","storage-classes","lifecycle","cost-optimization"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">S3 <strong>storage classes</strong> let you attach a cost/performance profile to each object independently, so the same bucket can hold hot data next to archival data at a fraction of the cost. Choosing the right class — and automating transitions between classes with <strong>lifecycle rules</strong> — is one of the most commonly tested practical skills in AWS interviews, because it directly ties technical understanding to real cost savings.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Framework AWS Uses to Describe Classes</h4>\n<p style=\"line-height: 1.75\">Every storage class is defined along the same axes, and a strong answer walks through all of them rather than reciting a name:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Access frequency.</strong> How often you expect to read the data (frequent, infrequent, rarely/archival).</li>\n<li><strong>Latency.</strong> Milliseconds (Standard-tier and Instant Retrieval classes) vs. minutes-to-hours (Flexible Retrieval, Deep Archive).</li>\n<li><strong>Availability design.</strong> 99.99% for multi-AZ classes down to 99.5% for single-AZ classes.</li>\n<li><strong>Minimum storage duration.</strong> A minimum number of days you're billed for even if you delete or transition the object sooner (30 days for IA classes, 90 for Glacier Flexible Retrieval, 180 for Deep Archive).</li>\n<li><strong>Retrieval charges.</strong> Per-GB fees for reading data back, which apply to IA and Glacier classes but not Standard.</li>\n<li><strong>Storage cost per GB.</strong> Generally decreases as retrieval latency and minimum duration increase.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Frequently Accessed Tiers</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>S3 Standard.</strong> The default, general-purpose class for frequently accessed data. Millisecond first-byte latency, 99.99% availability, 11 nines durability across 3+ AZs, no minimum duration or retrieval fee. Best for active websites, content distribution, and data actively being processed.</li>\n<li><strong>S3 Express One Zone.</strong> A purpose-built, single-AZ, high-performance class offering the lowest latency in S3 (single-digit milliseconds, up to several times faster than Standard) for the most latency-sensitive and frequently accessed workloads, such as interactive analytics and ML training data staged close to compute. Data is stored in a special \"directory bucket\" construct rather than a general-purpose bucket. A dedicated topic covers this class in depth.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Automatically Optimized Tier</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>S3 Intelligent-Tiering.</strong> Monitors access patterns per object and automatically moves objects between a frequent-access tier and lower-cost tiers (including optional archive tiers) with no retrieval fees and no operational overhead. Ideal when access patterns are unknown or unpredictable, at the cost of a small monthly monitoring fee per object.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Infrequent Access Tiers</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>S3 Standard-IA.</strong> Same millisecond latency and multi-AZ 99.99% availability as Standard, but lower storage cost and a per-GB retrieval fee, plus a 30-day minimum storage duration. Good for backups and disaster-recovery data that's accessed rarely but needs to be available instantly when it is.</li>\n<li><strong>S3 One Zone-IA.</strong> Same as Standard-IA but stored in a single Availability Zone, giving a lower price and lower availability (99.5%). Suitable for easily-recreatable data (e.g., secondary backup copies, thumbnails you can regenerate) where losing an AZ is an acceptable risk.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Archive Tiers</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>S3 Glacier Instant Retrieval.</strong> Archive-priced storage with millisecond retrieval, aimed at data accessed roughly once a quarter but which still needs instant access when requested. 90-day minimum duration.</li>\n<li><strong>S3 Glacier Flexible Retrieval.</strong> Lower-cost archive storage with retrieval times ranging from minutes (Expedited) to 3–5 hours (Standard) to 5–12 hours (Bulk, cheapest). 90-day minimum duration. Good for backups and disaster recovery where occasional multi-hour retrieval is acceptable.</li>\n<li><strong>S3 Glacier Deep Archive.</strong> The lowest-cost S3 storage class, designed for data accessed once or twice a year, with standard retrieval of about 12 hours and bulk retrieval up to 48 hours. 180-day minimum duration. Used for long-term regulatory/compliance retention.</li>\n</ul>\n<div style=\"overflow-x: auto; margin-top: 0.75rem\">\n<table style=\"width: 100%; border-collapse: collapse; font-size: 0.92rem\">\n<thead><tr style=\"text-align: left\" data-box=\"1\">\n<th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Class</th>\n<th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Retrieval Latency</th>\n<th style=\"padding: 0.6rem; border: 1px solid #e2e8f0\" data-box=\"1\">Min. font-size: 1.25rem; font-weight: 600\">Interview Scenario: 100 TB of Logs, Hot for 7 Days</h4>\n<p style=\"line-height: 1.75\"><strong>Question: \"You have 100 TB of logs. Logs are heavily accessed for 7 days and almost never afterward. How would you design storage?\"</strong></p>\n<p style=\"line-height: 1.75\">Walk through the design as a pipeline rather than a single answer:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Day 0–7:</strong> Ingest logs into <strong>S3 Standard</strong>. Access is frequent and latency-sensitive during this window (dashboards, alerting, debugging), so paying Standard's per-GB rate for millisecond access is justified.</li>\n<li><strong>Day 7:</strong> Attach an <strong>S3 Lifecycle rule</strong> that transitions objects older than 7 days from Standard to <strong>S3 Standard-IA</strong> (or Intelligent-Tiering if the drop-off timing is variable per log stream). Access has dropped sharply but occasional urgent lookups (e.g., an incident investigation) still need millisecond retrieval.</li>\n<li><strong>Day ~30–90:</strong> A second lifecycle transition rule moves objects to <strong>S3 Glacier Flexible Retrieval</strong>, since by now logs are essentially never read except for rare audits, and a multi-hour retrieval time is acceptable.</li>\n<li><strong>Day ~180+ (compliance horizon):</strong> A final transition rule moves the oldest data into <strong>S3 Glacier Deep Archive</strong> for the cheapest possible long-term retention, satisfying regulatory retention requirements without paying for fast access nobody needs.</li>\n<li>Optionally add an <strong>expiration rule</strong> to delete logs entirely once the legally required retention window closes, since even Deep Archive isn't free.</li>\n</ul>\n<p style=\"line-height: 1.75\">This layered design — Standard → Lifecycle Rule → Standard-IA → Glacier → Deep Archive — mirrors exactly how AWS expects you to reason about cost: match the storage class's price and latency to how the data is actually accessed at each point in its life, and automate the transitions so nobody has to remember to do it manually.</p>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"I'd land the logs in S3 Standard while they're hot for the first week, since that's when they need millisecond access.
