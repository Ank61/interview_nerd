Understanding exactly how multipart upload works mechanically — not just that \"it exists for big files\" — is one of the most commonly probed areas of S3 knowledge in interviews, because it reveals whether a candidate understands reliability engineering, not just API names.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">PutObject: The Simple Path</h4>\n<p style=\"line-height: 1.75\">A single <code>PutObject</code> call uploads the entire object body in one HTTP request. It supports objects up to <strong>5 GB</strong> in size. Below that limit it is by far the simplest approach — one request, one response, done. Its major weakness is atomicity of failure: if the connection drops at 99% of a 4 GB upload, the entire request must be retried from byte zero, and there is no way to parallelize a single PUT across multiple connections to increase throughput.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Multipart Upload: Mechanics in Detail</h4>\n<p style=\"line-height: 1.75\">Multipart upload breaks one logical object into numbered <strong>parts</strong>, uploads them as separate requests (potentially in parallel, potentially from different machines), and then tells S3 to stitch them together into a single final object. It is required for objects larger than 5 GB and recommended by AWS for anything above roughly 100 MB. The full lifecycle involves three API calls plus one per part:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>CreateMultipartUpload.</strong> Initiates the upload against a key and returns an <code>UploadId</code> that ties together every subsequent call for this upload. No object is visible to GET/List yet — it exists only as an in-progress upload.</li>\n<li><strong>UploadPart.</strong> Sent once per chunk, each carrying the <code>UploadId</code>, a <strong>PartNumber</strong> (an integer from 1 to 10,000), and that chunk's bytes. Each successful UploadPart response returns an <strong>ETag</strong> for that part, which must be recorded by the client.</li>\n<li><strong>CompleteMultipartUpload.</strong> Sent once, after all parts succeed, listing every PartNumber and its ETag in order. S3 then concatenates the parts server-side into the final single object, which now becomes visible and gets its own final ETag (typically a hash-of-hashes plus a part count suffix, not a plain MD5, which is a well-known interview gotcha).</li>\n<li><strong>AbortMultipartUpload.</strong> Cancels an in-progress upload and deletes any parts already uploaded for it, freeing their storage. If this is never called (and no lifecycle rule cleans it up), abandoned parts remain in the bucket, fully billed, indefinitely.</li>\n</ul>\n<p style=\"line-height: 1.75\"><strong>Size constraints:</strong> each part must be at least 5 MB (except the last part, which can be smaller), and at most 5 GB; a single multipart upload supports up to 10,000 parts, and the assembled object can be as large as 5 TB total. Part numbers do not need to be uploaded in order, and they can be uploaded in parallel from multiple threads, processes, or even multiple machines, since each UploadPart call is independent and only needs the shared UploadId.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Reliability: Retry Parts, Not the Whole File</h4>\n<p style=\"line-height: 1.75\">The core reliability advantage of multipart upload is granular retry. If part 47 of 400 fails due to a transient network error, only part 47 needs to be re-sent — S3 will accept a re-uploaded PartNumber, which simply overwrites the previously stored data for that part number and returns a fresh ETag. This means the effective cost of a transient failure is proportional to one part's size, not the whole object, which is exactly why the AWS SDKs' high-level transfer managers (for example, the Java <code>TransferManager</code>, the Python <code>boto3</code> S3 Transfer Manager, or the CLI's <code>aws s3 cp</code>) automatically use multipart upload above a size threshold and handle this part-level retry internally.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cost and Cleanup of Abandoned Uploads</h4>\n<p style=\"line-height: 1.75\">An incomplete multipart upload — one where the client crashed, lost connectivity, or simply never called Complete or Abort — leaves its uploaded parts sitting in the bucket as normal billable storage, but the object never appears in <code>ListObjectsV2</code> since it was never completed. This creates a genuinely sneaky cost leak: storage keeps accruing with no corresponding object visible in the console's normal object browser. The standard mitigation is a lifecycle rule using the <strong>AbortIncompleteMultipartUpload</strong> action, which automatically aborts (and thus deletes the parts of) any multipart upload that has been open longer than a configured number of days. AWS explicitly recommends every bucket that accepts uploads have this rule configured, since it costs nothing when there is nothing to clean up.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Question: \"How Would You Upload a 20 GB File Reliably?\"</h4>\n<p style=\"line-height: 1.75\">The expected shape of the answer: split the file into parts using <strong>multipart upload</strong> rather than a single PutObject (which is capped at 5 GB anyway and offers no partial-failure recovery); upload the parts <strong>in parallel</strong> across multiple connections/threads to maximize throughput, since each part is an independent HTTP request that can use a different TCP connection; on any individual part failure, <strong>retry only that part</strong> instead of restarting the whole transfer; track progress (which PartNumbers have succeeded and their ETags) so the upload has a <strong>resume capability</strong> if the process itself is interrupted and restarted; and finally call <code>CompleteMultipartUpload</code> once every part has succeeded, with an <code>AbortIncompleteMultipartUpload</code> lifecycle rule as a safety net in case the client never gets that far.</p>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"For a 20 GB file I'd use multipart upload instead of a single PutObject, since PutObject caps out at 5 GB and offers no partial recovery.
