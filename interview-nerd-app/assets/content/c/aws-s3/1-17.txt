Building reliable software on top of it requires two complementary disciplines: <strong>retrying failed requests correctly</strong> (exponential backoff with jitter) and <strong>designing operations to be idempotent</strong> so that a retry — or a duplicate delivery — never causes incorrect behavior.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Exponential Backoff on Failed Requests</h4>\n<p style=\"line-height: 1.75\">The basic failure-handling loop is: <strong>Request → Failure (e.g., 503 SlowDown, 500 Internal Error, connection timeout) → Exponential Backoff → Retry</strong>. Exponential backoff doubles (or otherwise scales up) the wait time between successive retries, so the first retry might wait 100ms, the second 200ms, the third 400ms, and so on up to a capped maximum. The reasoning is that a transient failure is often caused by momentary overload — either on S3's side (a prefix briefly exceeding its automatically-scaling request rate) or on the client's network path — and a fixed, short retry interval means every failed client retries at roughly the same cadence, which can synchronize into repeated bursts that make the underlying overload worse, not better.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why Naive Immediate Retries Make Throttling Worse</h4>\n<p style=\"line-height: 1.75\">If a fleet of workers all retry immediately after a 503, the retries collectively regenerate the exact spike in request rate that caused the original throttling response, often synchronized closely enough in time to trigger another wave of throttling. This is sometimes called a <strong>retry storm</strong> or thundering herd. Backoff spaces retries out over time so the aggregate request rate decays rather than staying pinned at the overload threshold.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Jitter</h4>\n<p style=\"line-height: 1.75\">Pure exponential backoff without randomness still has every client in a fleet backing off on the same schedule if they all failed at the same moment, meaning they retry in near-lockstep even as intervals grow. <strong>Jitter</strong> adds randomness to each computed backoff interval so client retries desynchronize across the fleet. A common pattern is \"full jitter\" — pick a random delay uniformly between 0 and the computed exponential ceiling — which AWS's own SDKs and architecture guidance recommend as more effective at breaking synchronized retry waves than backoff alone.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Default SDK Retry Behavior</h4>\n<p style=\"line-height: 1.75\">AWS SDKs (v2 for JavaScript, Boto3 for Python, etc.) implement retry logic by default so most application code doesn't hand-roll it. Retryable conditions include throttling errors (503), certain 500-level server errors, and specific network-level failures (connection reset, timeout) — but not client errors like 403 or 404, which retrying can never fix. Modern SDKs default to a <strong>standard</strong> retry mode (a fixed retry budget with exponential backoff and jitter) and also offer an <strong>adaptive</strong> mode that dynamically adjusts the client's send rate based on observed throttling, which is preferable for high-throughput workloads that regularly brush up against service limits.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Idempotency for S3 Uploads</h4>\n<p style=\"line-height: 1.75\">A plain <code>PutObject</code> retry is naturally idempotent: S3 writes are whole-object overwrites keyed by object key, so retrying an identical PutObject after a timeout simply overwrites the same key with the same bytes — no duplication, no partial state. This is one of S3's underrated reliability properties compared to systems where a retried write could append or duplicate. <strong>Multipart uploads are the exception</strong>: they are a multi-step protocol (initiate, upload each part, complete), and a naive retry of the whole upload after a partial failure wastes bandwidth and can leave stray incomplete uploads behind, so multipart clients should retry only the specific failed part using its part number, not restart the entire object from scratch.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Idempotency for Event Processing</h4>\n<p style=\"line-height: 1.75\">S3 event notifications (to SQS, SNS, Lambda, or EventBridge) are delivered <strong>at-least-once, never exactly-once</strong>. Any consumer of these events — a Lambda function processing an S3 upload event, an SQS worker draining a queue fed by S3 notifications — must assume the same event can arrive twice (or more) and must be written so processing it twice produces the same end state as processing it once. Standard techniques include using the object's <strong>ETag</strong> or a content hash to detect and skip already-processed objects, writing processing results to a datastore with a deduplication key derived from the S3 object key plus version ID, and making downstream side effects (e.g., inserting a database row) use an upsert rather than a blind insert.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Multipart Upload Retry — Retry the Part, Not the Whole</h4>\n<p style=\"line-height: 1.75\">Each part of a multipart upload is uploaded independently via <code>UploadPart</code> and returns its own ETag. If part 7 of 20 fails, a well-built client retries only <code>UploadPart</code> for part 7 with backoff, keeping the other 19 parts' progress intact, then proceeds to <code>CompleteMultipartUpload</code> once all parts succeed.
