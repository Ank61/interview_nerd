{"title":"S3 Inventory","tags":["s3-inventory","reporting","cost-optimization","metadata"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\"><strong>S3 Inventory</strong> is a scheduled, fully managed report of the objects in a bucket (or a prefix within it) and their metadata, delivered as a flat file — CSV, Apache ORC, or Apache Parquet — to a destination bucket you specify. Instead of asking S3 in real time \"what objects do you have,\" you ask S3 to periodically write down the answer for you. Think of it as S3 doing a nightly (or weekly) inventory count of a warehouse and handing you a spreadsheet, rather than you walking every aisle yourself every time you need to know what's on the shelves.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why Inventory exists: the LIST problem at scale</h4>\n<p style=\"line-height: 1.75\">The S3 <strong>ListObjectsV2</strong> API returns at most 1,000 keys per call and is paginated. For a bucket with a few thousand objects this is trivial. For a bucket with hundreds of millions or billions of objects — common in data lakes, media archives, and log storage — a full LIST traversal means millions of paginated API calls, each incurring latency and a per-request cost (LIST requests are billed, and at billions of objects this adds up meaningfully). It can take hours to complete a single full listing, and if objects are being added or deleted concurrently, the listing can be inconsistent — you never get a clean, single point-in-time snapshot. S3 Inventory solves this by having AWS generate the report internally, against its own index, and simply drop a file (or set of files) in your destination bucket on a schedule. You then read that file with a single GetObject, or query it with Athena, instead of paginating through the live namespace.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What fields the report contains</h4>\n<p style=\"line-height: 1.75\">An Inventory configuration lets you choose which optional fields to include alongside the mandatory bucket name, key name, and version ID. Commonly selected fields include:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Size and last modified date.</strong> Object size in bytes and the last-modified timestamp.</li>\n<li><strong>Storage class.</strong> STANDARD, STANDARD_IA, GLACIER, GLACIER_DEEP_ARCHIVE, INTELLIGENT_TIERING, etc. — critical for auditing whether lifecycle policies are actually working as intended.</li>\n<li><strong>Encryption status.</strong> Whether the object is encrypted, and with what (SSE-S3, SSE-KMS) — useful for compliance audits that require proof every object is encrypted.</li>\n<li><strong>Replication status.</strong> Whether an object has been replicated (COMPLETED, PENDING, FAILED, REPLICA) under Cross-Region or Same-Region Replication — this is one of the only scalable ways to audit replication health across millions of objects.</li>\n<li><strong>Multipart upload flag.</strong> Whether the object was uploaded via multipart upload.</li>\n<li><strong>Object lock retention/legal hold fields.</strong> Retain-until date and legal hold status, for compliance reporting.</li>\n<li><strong>Version ID and is-latest flag.</strong> For versioned buckets, whether the listed row is the current version or a prior (noncurrent) one — helpful for estimating noncurrent version storage before writing a lifecycle rule.</li>\n<li><strong>Intelligent-Tiering access tier.</strong> Which access tier (Frequent, Infrequent, Archive Instant Access) an object currently sits in.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Delivery, frequency, and consistency</h4>\n<p style=\"line-height: 1.75\">Inventory reports can be generated <strong>daily</strong> or <strong>weekly</strong>. Each run produces a manifest file (manifest.json, plus a checksum manifest) listing the data files for that run, which is how downstream consumers (like an Athena table or a script) discover what to read. Delivery is <strong>best-effort</strong>: AWS does not guarantee an exact delivery time, and if a report generation fails for some internal reason, S3 will attempt it again on the next scheduled cycle rather than promising same-day delivery. The report reflects objects that existed as of a consistent point in time chosen internally by S3 for that run — it is not a live, continuously updated feed.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem;
