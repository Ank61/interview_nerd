S3 is an excellent, cheap, durable <strong>blob store</strong>, but it is not a transactional, queryable data store, and the standard, correct pattern is to split responsibilities: a relational (or other purpose-built) database owns structured metadata and relationships, while S3 owns the raw bytes. Understanding exactly <strong>why</strong> this split exists — not just that it's convention — is what separates a memorized answer from real architectural judgment.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why S3 Should Never Be Your Primary Transactional Database</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>No transactions.</strong> S3 has no concept of a multi-object atomic transaction. You cannot update three related objects and guarantee all-or-nothing semantics the way a database transaction with COMMIT/ROLLBACK provides. A partial failure mid-operation can leave objects in an inconsistent state relative to each other with no built-in mechanism to detect or roll it back.</li>\n<li><strong>No complex queries or joins.</strong> S3 has no query planner, no indexes beyond the key namespace, and no way to join data across objects. Finding \"all orders placed by customer X in the last 30 days\" against a bucket of JSON blobs means listing and downloading candidate objects and filtering client-side — an approach that doesn't scale.</li>\n<li><strong>No strong per-object schema.</strong> S3 stores opaque bytes with a small amount of key-value user metadata; it does not enforce or understand a schema, foreign keys, or data types the way a relational database does. Nothing prevents malformed or inconsistent data from being written.</li>\n<li><strong>Consistency and query limitations.</strong> S3 today offers strong read-after-write consistency for standard operations, which resolved historical eventual-consistency concerns, but it still has essentially <strong>no query language</strong> beyond S3 Select — a limited SQL-like filter over the contents of a single CSV/JSON/Parquet object, not a cross-object query engine. It cannot replace even basic relational query capability.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">The Standard Pattern: Database for Metadata, S3 for Bytes</h4>\n<p style=\"line-height: 1.75\">The conventional and correct architecture stores structured, queryable facts in a relational database (PostgreSQL, MySQL, etc.) and stores only a <strong>reference</strong> to the actual file — the S3 object key (and often bucket name and region) — as a column value. The large binary payload itself lives in S3, never in the database.</p>\n<p style=\"line-height: 1.75\">Concrete example: a <code>users</code> table has columns like <code>id</code>, <code>email</code>, <code>created_at</code>, and a <code>profile_image_key</code> column holding a string like <code>users/123/profile.jpg</code>. The application queries the database normally — \"find user by email,\" \"join users to their orders\" — and whenever it needs the actual image bytes, it uses the stored key to fetch (or generate a presigned URL for) the object directly from S3. A relational database is optimized for small, structured records with fast indexed lookups, joins, and transactional guarantees — exactly what \"find, filter, and relate metadata\" requires. S3 is optimized for storing an effectively unlimited volume of large, immutable-by-convention blobs durably (11 nines of durability) and cheaply, at a per-GB price a general-purpose database could never match, especially once you factor in database storage, backup, and replication costs for large binary columns. Storing large blobs directly in a relational database (as BLOB/BYTEA columns) also bloats table size, slows backups, degrades index performance, and increases replication lag — problems that simply don't exist when the blob lives in S3 and the database holds a lightweight string reference instead.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario: Designing a Document Upload Feature</h4>\n<p style=\"line-height: 1.75\">A candidate asked to design \"let users upload profile documents and search them by metadata\" should describe: an API that accepts the upload, writes the file to S3 under a key namespaced by user ID, and inserts a row into a <code>documents</code> table with columns like <code>user_id</code>, <code>filename</code>, <code>content_type</code>, <code>size_bytes</code>, <code>s3_key</code>, and <code>uploaded_at</code>. Searching \"all PDF documents uploaded by user X in March\" is a straightforward indexed SQL query against the database — never a full S3 bucket listing. Retrieving the actual file is a follow-up S3 GET (or a presigned URL handed to the client) using the <code>s3_key</code> from the matched row.
