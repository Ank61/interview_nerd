Once you enable versioning on a bucket, every object written from that point forward is assigned a unique <strong>version ID</strong>, and older versions are retained (and billed for) unless you explicitly delete them or expire them with a lifecycle rule. This turns S3 from a simple overwrite-in-place store into an append-only history of every object, which is the foundation for accidental-deletion recovery, compliance retention, and safe rollback.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Enabling, Suspending — Never Fully Disabling</h4>\n<p style=\"line-height: 1.75\">Versioning has three states at the bucket level: <strong>Unversioned</strong> (the default, no version IDs, objects have a version ID of <code>null</code>), <strong>Enabled</strong>, and <strong>Suspended</strong>. This is a one-way door in an important sense: once you move a bucket from Unversioned to Enabled, you can never get back to the Unversioned state. You can only <strong>Suspend</strong> versioning, which stops assigning new version IDs to future writes (new objects get a version ID of <code>null</code> again) but does not touch or delete any version IDs that already exist. This is a classic interview trap — candidates often say \"you can disable versioning,\" but the correct, precise answer is that it can only be suspended, and all historical versions created while it was enabled remain in the bucket, still accruing storage cost, until you explicitly delete them.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Version IDs and How Reads Behave</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Version ID.</strong> An opaque string (for example <code>3sL4kqtJlcpXroDTDmJ+rmSpXd3dIbrHY+MTRCxf3vjVBH40Nr8X8gdRQBpUMLUo</code>) that uniquely identifies one immutable copy of an object's bytes and metadata under a given key.</li>\n<li><strong>Default GET.</strong> A GET request without a <code>versionId</code> query parameter always returns the <strong>current</strong> version — the most recent one, or a delete marker if the object was \"deleted.\"</li>\n<li><strong>Explicit GET.</strong> Passing <code>?versionId=xxxx</code> retrieves that specific historical version regardless of what the current version is.</li>\n<li><strong>Listing versions.</strong> <code>ListObjectVersions</code> (distinct from the normal <code>ListObjectsV2</code>) returns every version and every delete marker for every key, each flagged with <code>IsLatest</code> to show which one is current.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario: \"What Happens When You Delete a Versioned S3 Object?\"</h4>\n<p style=\"line-height: 1.75\">This is one of the most commonly asked S3 questions, and the answer has two distinct branches depending on how the delete is issued.</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>DELETE without a version ID (the normal case).</strong> S3 does <em>not</em> remove any bytes. Instead it inserts a new, zero-byte <strong>delete marker</strong> as the new current version of that key. The underlying object data and all prior versions are untouched and still fully retrievable by version ID. From the perspective of a plain GET or a console listing, the object now \"appears deleted\" — a GET returns a 404 — but nothing has actually been destroyed.</li>\n<li><strong>DELETE with an explicit version ID (<code>DELETE /key?versionId=xxxx</code>).</strong> This is a <strong>permanent, unrecoverable</strong> delete of that exact version's bytes. There is no soft-delete step here — S3 does not create a delete marker for a versioned delete, it just removes that version. This is the only way to truly purge data from a versioned bucket (aside from lifecycle expiration of noncurrent versions).</li>\n</ul>\n<p style=\"line-height: 1.75\">The practical consequence is \"undelete\": to restore an object that was removed via a plain DELETE, you simply delete the <strong>delete marker itself</strong> (by issuing <code>DELETE /key?versionId=&lt;delete-marker-version-id&gt;</code>). Removing the delete marker exposes the previous version as current again, and the object becomes visible to normal GETs exactly as it was before — no data copy required. In a versioned bucket, lifecycle rules gain extra actions that only make sense in this context: <code>NoncurrentVersionTransition</code> (move old versions to cheaper storage classes after N days of being noncurrent) and <code>NoncurrentVersionExpiration</code> (permanently delete old versions after N days noncurrent, optionally keeping the most recent few via <code>NewerNoncurrentVersions</code>). There is also <code>ExpiredObjectDeleteMarker</code> cleanup, which removes a delete marker automatically once it is the only version left for a key (avoiding orphaned \"tombstone\" markers sitting forever). Without these rules, a versioned bucket with frequent overwrites will silently accumulate storage cost from every historical copy, which is a very common root cause of unexpected billing growth.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">MFA Delete — An Extra Layer</h4>\n<p style=\"line-height: 1.75\"><strong>MFA Delete</strong> is an optional, stricter protection you can enable on top of versioning.
