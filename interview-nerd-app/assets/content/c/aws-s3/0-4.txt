{"title":"ACL vs Bucket Policy vs IAM Policy, and S3 Object Ownership","tags":["S3","ACL","object-ownership","access-control"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">S3 offers three different mechanisms that can grant access — <strong>ACLs</strong>, <strong>bucket policies</strong>, and <strong>IAM policies</strong> — and understanding when each applies, plus how modern <strong>Object Ownership</strong> settings have largely retired ACLs, is a strong signal of practical S3 experience in an interview.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Three Mechanisms, Three Eras</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>S3 ACLs (Access Control Lists).</strong> The oldest access-control mechanism in S3, predating IAM. An ACL is attached to an individual <strong>bucket or object</strong> and grants coarse-grained permissions (READ, WRITE, FULL_CONTROL) to a fixed set of grantee types: a specific AWS account (by canonical ID), a predefined group like \"All Users\" (public) or \"Authenticated Users,\" or the log-delivery group. ACLs cannot express conditions, cannot reference IAM principals directly, and are managed outside the IAM policy language entirely — which is exactly why AWS now discourages them for nearly all new use cases.</li>\n<li><strong>Bucket Policy.</strong> A resource-based JSON policy attached to the bucket, using the full IAM policy language (Principal, Action, Resource, Condition). It can grant access to specific IAM users/roles, other AWS accounts, or the public, and supports fine-grained conditions.</li>\n<li><strong>IAM Policy.</strong> An identity-based JSON policy attached to a user, group, or role, defining what S3 (and other) actions that identity may perform, typically across many resources.</li>\n</ul>\n<p style=\"line-height: 1.75\">All applicable policies and ACLs are evaluated together for a given request; an explicit Deny anywhere wins, and otherwise at least one Allow (from IAM policy, bucket policy, or ACL) must exist for the request to succeed. In practice, well-designed modern S3 architectures use only IAM policies and bucket policies, and disable ACLs entirely via Object Ownership.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Why ACLs Are Discouraged: The Cross-Account Upload Problem</h4>\n<p style=\"line-height: 1.75\">The classic historical pain point that motivated moving away from ACLs: when Account B uploads an object into Account A's bucket (a common cross-account data-sharing pattern), by default the <strong>uploader (Account B) becomes the object's owner</strong>, not the bucket owner (Account A). Under the ACL model, Account A — despite owning the bucket — could not necessarily read, delete, or manage that object, because object-level ACLs controlled access and Account A's bucket policy alone didn't automatically give it rights over an object it didn't own. Workarounds required the uploader to explicitly grant an ACL such as <code>bucket-owner-full-control</code> on every single PUT, which was easy to forget and impossible to enforce centrally — a frequent source of \"I can see the object exists but I can't open it\" tickets.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">S3 Object Ownership</h4>\n<p style=\"line-height: 1.75\"><strong>Object Ownership</strong> is a bucket-level setting introduced specifically to eliminate the ACL cross-account ownership problem. It has three settings:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Bucket owner enforced.</strong> The recommended, modern default (and the default for all new buckets since April 2023). <strong>ACLs are entirely disabled</strong> — every object uploaded to the bucket is automatically owned by the bucket owner, regardless of who uploaded it. Access is controlled exclusively through IAM policies and bucket policies. This fully eliminates the cross-account ownership problem because ownership never transfers to the uploader in the first place.</li>\n<li><strong>Bucket owner preferred.</strong> ACLs remain enabled, but new objects uploaded by other accounts can be configured to automatically be owned by the bucket owner if the uploader includes the <code>bucket-owner-full-control</code> canned ACL on the PUT request. This is a transitional setting for buckets not yet ready to fully disable ACLs.</li>\n<li><strong>Object writer (legacy).</strong> The original behavior — whoever uploads an object owns it, and ACLs are fully in play. This is the source of the historical ownership problem.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario: Choosing an Access Model for a New Bucket</h4>\n<p style=\"line-height: 1.75\">If asked to design access control for a brand-new shared data bucket accepting uploads from multiple teams/accounts, a strong answer is: set <strong>Object Ownership to Bucket owner enforced</strong> immediately (this also disables ACLs, satisfying Block Public Access's ACL-related settings trivially since there are no ACLs to worry about), then grant cross-account write access via a <strong>bucket policy</strong> naming the specific uploading accounts/roles, and grant same-account application access via <strong>IAM policies</strong> on the roles that need it. This avoids ever needing to reason about ACL grants, keeps every permission auditable in one policy language, and guarantees the bucket owner always retains full control over everything landing in their bucket.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">When (If Ever) ACLs Still Matter</h4>\n<p style=\"line-height: 1.75\">A few legacy scenarios still involve ACLs: the <strong>log-delivery group ACL</strong> historically used for S3 server access logging (now largely superseded by bucket-policy-based log delivery), and buckets that predate Object Ownership and haven't been migrated. For any new design, however, AWS's guidance — and the interview-correct answer — is to disable ACLs via <strong>Bucket owner enforced</strong> and manage everything through IAM and bucket policies.</p>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"ACLs are the legacy, object-level access mechanism that predates IAM, and they're discouraged now because they caused real problems — most famously, when another account uploaded into your bucket, they'd own that object by default, and you as the bucket owner couldn't necessarily read or manage it unless they remembered to grant you a bucket-owner-full-control ACL on every upload.
