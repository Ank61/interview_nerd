{"title":"S3 Replication — Cross-Region and Same-Region","tags":["replication","crr","srr","disaster-recovery"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">S3 Replication automatically and asynchronously copies objects from a source bucket to one or more destination buckets. <strong>Same-Region Replication (SRR)</strong> copies within the same AWS Region (Bucket A → Bucket B, both in us-east-1) — commonly used for log aggregation across accounts, or maintaining a copy in a different storage class. <strong>Cross-Region Replication (CRR)</strong> copies across Regions (Bucket A in us-east-1 → Bucket B in eu-west-1) — commonly used for lower-latency reads closer to a distributed user base, regulatory data-residency copies, and disaster recovery.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Prerequisites</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Versioning must be enabled</strong> on both the source and destination buckets. This is non-negotiable — replication configuration cannot even be saved otherwise, because replication tracks and reproduces every version of an object, not just its current state.</li>\n<li><strong>An IAM replication role</strong> that S3 assumes to read from the source bucket (<code>s3:GetReplicationConfiguration</code>, <code>s3:GetObjectVersionForReplication</code>, etc.) and write to the destination (<code>s3:ReplicateObject</code>, <code>s3:ReplicateDelete</code>, <code>s3:ReplicateTags</code>).</li>\n<li><strong>A replication rule</strong> specifying source prefix/tag filters, destination bucket, storage class override (optional), and other options like delete-marker replication and RTC.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">What Does and Does Not Replicate</h4>\n<p style=\"line-height: 1.75\">By default, replication is <strong>not retroactive</strong>: enabling a replication rule only replicates <strong>new objects written after the rule takes effect</strong>. Objects that already existed in the bucket before replication was configured are not automatically copied. To backfill existing objects, you must run an explicit <strong>S3 Batch Replication</strong> job, which replicates a specified set of existing objects on demand (this is also how you'd re-replicate objects after fixing a previously broken rule). By default, <strong>delete marker replication</strong> is also <strong>opt-in</strong>: creating a delete marker in the source (deleting an object in a versioned bucket without specifying a version ID) does not replicate to the destination unless you explicitly enable \"Delete marker replication\" in the rule. Permanent deletions that specify an exact version ID are never replicated, regardless of settings, since replicating a permanent delete could destroy a version deliberately preserved on the destination.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Filtering and Rules</h4>\n<p style=\"line-height: 1.75\">Replication rules can filter by <strong>key prefix</strong>, <strong>object tags</strong>, or both, allowing selective replication (e.g., only <code>invoices/</code> objects, or only objects tagged <code>Compliance=required</code>). Multiple rules can target different destinations or apply different storage-class overrides on the same source bucket, as long as their filters don't overlap ambiguously.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cross-Account Replication and Ownership</h4>\n<p style=\"line-height: 1.75\">Replicating to a bucket owned by a <strong>different AWS account</strong> is fully supported and common in security architectures where a central \"vault\" account collects immutable copies of data from many producer accounts. By default, objects replicated cross-account remain owned by the <strong>source account</strong> unless you configure <strong>ownership override</strong> (<code>AccessControlTranslation</code> combined with granting the destination account <code>s3:ObjectOwnerOverrideToBucketOwner</code> permissions in the replication role), which reassigns replicated object ownership to the <strong>destination bucket owner</strong> — essential when the destination account needs full control (lifecycle rules, ACL management, deletion rights) over the received copies rather than depending on the source account.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Replicating KMS-Encrypted Objects</h4>\n<p style=\"line-height: 1.75\">Objects encrypted with SSE-KMS are <strong>not replicated by default</strong> unless you explicitly enable this in the rule and grant the replication role <code>kms:Decrypt</code> on the source CMK and <code>kms:Encrypt</code> on the destination CMK (which must be a Region-specific key valid in the destination Region, since KMS keys are regional). Forgetting this is one of the most common replication failure modes seen in production.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Monitoring and Common Failures</h4>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>Insufficient IAM role permissions</strong> — missing <code>s3:ReplicateObject</code> on the destination or <code>s3:GetObjectVersionForReplication</code> on the source.</li>\n<li><strong>Missing KMS grants</strong> for encrypted source objects, as above.</li>\n<li><strong>Destination bucket versioning disabled or suspended</strong> after the rule was created.</li>\n<li><strong>Object size or storage class exclusions</strong> — objects in S3 Glacier or Glacier Deep Archive storage classes are not replicated unless explicitly restored first.</li>\n<li>Replication status is exposed per-object via the <code>x-amz-replication-status</code> header (PENDING, COMPLETED, FAILED, REPLICA), and aggregate health can be monitored with <strong>S3 Replication metrics in CloudWatch</strong> (bytes pending, operations pending, replication latency) plus S3 Event Notifications for <code>s3:Replication:OperationFailedReplication</code>.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Replication Time Control (RTC)</h4>\n<p style=\"line-height: 1.75\"><strong>S3 Replication Time Control</strong> is an optional, paid enhancement that provides an <strong>SLA guaranteeing 99.99% of new objects replicate within 15 minutes</strong>, backed by S3 Replication metrics that report the actual replication time per object. RTC is the right answer whenever an interviewer asks about replication with a hard compliance or RPO deadline — standard replication is \"typically minutes\" but carries no guarantee, whereas RTC is contractually bounded.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario</h4>\n<p style=\"line-height: 1.75\">\"We enabled CRR on our production bucket last week. Why don't the millions of objects uploaded last year show up in the destination bucket?\" Because replication is not retroactive — it only applies going forward from when the rule was created.
