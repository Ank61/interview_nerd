font-size: 1.25rem; font-weight: 600\">Rule Anatomy: Transitions, Expiration, and Filters</h4>\n<p style=\"line-height: 1.75\">A lifecycle rule is scoped by a <strong>filter</strong> — a key prefix, one or more object tags, an object size range, or a combination — and then applies one or more actions once matched objects age past a threshold:</p>\n<ul style=\"margin-left: 1.5rem; font-size: 1.25rem; font-weight: 600\">Worked Timeline Example</h4>\n<p style=\"line-height: 1.75\">A typical cost-driven rule for log or report data looks like this: <strong>Day 0</strong> — object is written to S3 Standard. <strong>Day 30</strong> — transitions to Standard-IA, since access has become infrequent but retrieval must still be fast. <strong>Day 90</strong> — transitions to Glacier Flexible Retrieval, since the data is now effectively archival but might still be needed for audits within minutes-to-hours. <strong>Day 365</strong> — the object expires and is permanently deleted, because retention requirements only require one year. Each of these is a separate action inside a single rule, and S3 evaluates and applies them automatically without any application code being aware it is happening.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Minimum Storage Duration Constraints</h4>\n<p style=\"line-height: 1.75\">Several storage classes impose a <strong>minimum storage duration charge</strong>: Standard-IA and One Zone-IA charge for a minimum of 30 days even if you delete or transition the object sooner; Glacier Flexible Retrieval and Glacier Deep Archive impose 90-day and 180-day minimums respectively. This has a direct, often-missed economic consequence: transitioning small or short-lived objects too aggressively can actually <strong>increase</strong> cost. A 10 KB object that lives for 20 days and then gets transitioned to IA is still billed as if it sat in IA for 30 days, and S3 also charges a per-object transition request fee and, for IA/Glacier classes, a per-GB retrieval fee — so objects that are deleted or re-accessed quickly can end up costing more once \"optimized\" than if they had simply stayed in Standard. This is precisely why AWS recommends lifecycle transitions mainly for reasonably large objects with a predictable, cooling access pattern, and why S3 Intelligent-Tiering (which has no minimum duration for its frequent/infrequent tiers) is often a safer default when access patterns are unknown.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview Scenario: \"Your S3 Bill Increased by 40%. storage class distribution.</strong> Storage Lens and the console's Storage Class Analysis show whether data has quietly stayed in Standard when it should have transitioned, which inflates cost since Standard is the most expensive \"hot\" tier.</li>\n<li><strong>Look at object sizes and counts.</strong> A spike in a very large number of small objects raises per-request costs (PUT/GET/LIST charges) disproportionately versus a few large objects, since S3 request pricing is per-object-operation, not just per-byte.</li>\n<li><strong>Check for old/orphaned versions.</strong> On versioned buckets, a burst of overwrites without a lifecycle policy is one of the most common silent cost drivers — noncurrent versions accumulate invisibly to normal listings.</li>\n<li><strong>Check for incomplete multipart uploads.</strong> A failed or abandoned large upload leaves parts sitting in the bucket, fully billed, with no visible \"object\" in a normal listing — <code>ListMultipartUploads</code> or
