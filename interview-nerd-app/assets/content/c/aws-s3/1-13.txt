{"title":"S3 and VPC — Gateway Endpoints and Private Connectivity","tags":["vpc","gateway-endpoint","privatelink","networking"],"html":"<div>\n<p style=\"line-height: 1.75; margin-top: 1.5rem\">By default, traffic from an EC2 instance to S3 travels over the public AWS network, typically routed out through an <strong>Internet Gateway</strong> or a <strong>NAT Gateway</strong> even though it never actually leaves AWS's backbone. A <strong>VPC Endpoint</strong> lets you route that traffic privately within AWS's network instead, without traversing the public internet path, and S3 supports two distinct kinds of endpoint: the <strong>Gateway Endpoint</strong> and the <strong>Interface Endpoint (AWS PrivateLink)</strong>. Choosing between them — and understanding why they solve different problems — is one of the most common S3-networking interview topics.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">S3 Gateway Endpoint mechanics</h4>\n<p style=\"line-height: 1.75\">A <strong>Gateway Endpoint</strong> is implemented as a special target you add to one or more <strong>route tables</strong> in your VPC — it is not an ENI (elastic network interface) with an IP address inside your subnet. When you create the endpoint, you associate it with the route tables of the subnets that need private S3 access, and AWS automatically inserts a route (or you can scope it) that sends traffic destined for S3's IP prefix range to the Gateway Endpoint's special \"pl-\" prefix list target, rather than out through the Internet Gateway or NAT Gateway. Traffic flow becomes: <strong>EC2 instance → VPC route table → Gateway Endpoint → S3</strong>, entirely within the AWS network. Because this avoids NAT Gateway data processing charges and doesn't require a public IP, internet gateway, or NAT for S3 traffic specifically, it is both faster to set up and cheaper to run than the alternative.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Endpoint policies</h4>\n<p style=\"line-height: 1.75\">A Gateway Endpoint can have its own <strong>endpoint policy</strong> — a resource policy attached to the endpoint itself, separate from IAM policies and bucket policies — that restricts which S3 actions and which bucket ARNs are reachable through that endpoint. This lets you enforce, for example, \"traffic leaving this VPC via this endpoint may only reach our-company-data-bucket and only for GetObject/PutObject,\" even if the calling principal's IAM policy would otherwise allow broader S3 access. This is a common defense-in-depth control: it stops an instance in the VPC from exfiltrating data to an attacker-controlled bucket in another account, because the endpoint policy itself blocks any bucket not explicitly allowed, regardless of what IAM permits.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Route table configuration</h4>\n<p style=\"line-height: 1.75\">Concretely, setting up a Gateway Endpoint involves: creating the endpoint against the S3 service in the target VPC, selecting which route tables it should be associated with, and (optionally) attaching an endpoint policy. Once associated, each of those route tables gains an entry whose destination is the S3-managed prefix list and whose target is the endpoint ID (vpce-xxxxxxxx). Any subnet using one of those route tables now sends S3-bound traffic through the endpoint automatically — no changes are needed on the EC2 instance or application side, since the S3 API endpoint hostname and DNS resolution stay the same; only the routing path changes.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">When an Interface Endpoint / PrivateLink is needed instead</h4>\n<p style=\"line-height: 1.75\">A Gateway Endpoint only works for traffic that originates <strong>from within the VPC's own route tables</strong> — it has no IP address and cannot be reached from outside the VPC, such as from on-premises networks over Direct Connect or a Site-to-Site VPN, or from a different VPC without route propagation tricks. In those cases you need an <strong>Interface Endpoint</strong>, which provisions an ENI with a private IP address inside your subnet, backed by AWS PrivateLink. Because it has an actual private IP, it can be reached from on-premises via Direct Connect or VPN, or from peered VPCs, by simply routing to that private IP (typically via a private DNS name that resolves within the VPC). Typical reasons to reach for an Interface Endpoint over a Gateway Endpoint:</p>\n<ul style=\"margin-left: 1.5rem; list-style: disc; line-height: 2\">\n<li><strong>On-premises access.</strong> A data center connected via Direct Connect or VPN needs private access to S3 without traversing the public internet — only an Interface Endpoint has a private IP reachable from outside the VPC.</li>\n<li><strong>Centralized endpoint architectures.</strong> Sharing one endpoint across many VPCs via Transit Gateway or VPC sharing, where a routable private IP simplifies multi-VPC designs.</li>\n<li><strong>Security tooling that inspects traffic by IP.</strong> Some network security appliances need a fixed private IP target to apply inspection rules against, which a Gateway Endpoint's prefix-list-based routing doesn't provide.</li>\n</ul>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Cost difference</h4>\n<p style=\"line-height: 1.75\">This is a frequently tested distinction: <strong>Gateway Endpoints for S3 are free</strong> — there is no hourly charge and no data processing charge for traffic through them. <strong>Interface Endpoints incur an hourly charge per endpoint per Availability Zone, plus a per-GB data processing charge</strong> for all traffic that flows through them. Because of this, the general guidance is: use a Gateway Endpoint whenever VPC-only access is sufficient (which covers the overwhelming majority of EC2-to-S3 use cases), and reserve Interface Endpoints for the specific scenarios — on-premises connectivity, multi-VPC sharing, IP-based inspection — where a Gateway Endpoint's limitations actually block the design.</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600\">Interview scenario: locking down egress while keeping S3 private</h4>\n<p style=\"line-height: 1.75\">Suppose a security review flags that EC2 instances in a private subnet (no NAT Gateway, no Internet Gateway) need access to S3 for application data, but the security team insists no traffic should be able to reach any bucket outside the account. The solution: create a Gateway Endpoint for S3 in the VPC, associate it with the private subnets' route tables, and attach an endpoint policy restricting the Resource to only the specific bucket ARNs the application needs, with only the specific actions (e.g., s3:GetObject, s3:PutObject) required. This achieves fully private connectivity to S3 with zero data-transfer cost and an extra layer of control beyond IAM, entirely without provisioning any NAT Gateway, Internet Gateway, or Interface Endpoint.</p>\n<div style=\"margin-top: 1rem; border-left: 4px solid #f97316; padding: 1rem; border-radius: 4px; font-size: 0.9rem\" data-box=\"1\"><strong>🎯 Interview Answer:</strong> \"For EC2 in a VPC talking to S3, a Gateway Endpoint is almost always the right choice — you add it as a route table target, so traffic goes EC2 to VPC route table to the endpoint to S3, without needing an internet or NAT gateway, and it's free.
