An interface is a different kind of type: instead of describing data, it describes <span style=\"font-weight: 600\">behavior</span>. It says \"anything that can do these particular things counts as this interface,\" without caring at all what the underlying data actually is. This idea is one of the things that gives Go its flexibility, and once it clicks, you'll start seeing it used everywhere in the standard library and in real Go programs.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">What Is an Interface?</h4>\n<p style=\"line-height: 1.75\">\nAn interface is a type that lists a set of method names, along with the parameters and return types each method must have — but it never provides the actual code for those methods. Any type in your program — no matter what it looks like internally — automatically counts as a <code>Shape</code> as long as it has a method with exactly that name, exact same parameters, and exact same return type.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">Implicit Implementation: No \"implements\" Keyword</h4>\n<p style=\"line-height: 1.75\">\nThis is the single most important, and most surprising, thing about interfaces in Go compared to many other languages: you never write anything that says \"this struct implements this interface.\" There is no <code>implements</code> keyword at all. Imagine writing a function that saves data to a file. If you write it to only accept a specific struct like <code>*os.File</code>, then later, when you want to test your code without touching the real filesystem, or want to save to a network connection instead, you're stuck rewriting your function. But if your function instead accepts something like Go's built-in <code>io.Writer</code> interface (which just requires a <code>Write([]byte) (int, error)</code> method), it will happily work with a real file, an in-memory buffer, a network connection, or a fake test object — anything at all that has a matching <code>Write</code> method. The function becomes flexible without becoming complicated.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">Small Interfaces Are Idiomatic</h4>\n<p style=\"line-height: 1.75\">\nA well-known piece of Go wisdom is: \"the bigger the interface, the weaker the abstraction.\" In practice, this means Go developers strongly favor small interfaces — often with just one or two methods — over large ones with many required methods. font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">The nil Interface Gotcha</h4>\n<p style=\"line-height: 1.75\">\nHere's a subtle trap that catches even experienced Go developers off guard from time to time. Surprisingly, it doesn't — because an interface value is really made up of two hidden parts internally: the concrete type it's holding, and the actual value. An interface only equals <code>nil</code> when both of those parts are empty. If you store a <code>nil</code> pointer of a specific type into an interface, the \"type\" part is filled in (it knows it's a <code>*SomeStruct</code>), even though the \"value\" part is <code>nil</code> — and that combination does not count as the interface itself being <code>nil</code>.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>go</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=k>type</i> MyError <i class=k>struct</i>{}\n\n<i class=function><i class=k>func</i> <i class=p>(e *MyError)</i></i> Error() <i class=t>string</i> { <i class=k>return</i> <i class=s>&quot;something went wrong&quot;</i> }\n\n<i class=function><i class=k>func</i> <i class=f>doSomething</i><i class=p>()</i></i> <i class=t>error</i> {\n  <i class=k>var</i> err *MyError = <i class=l>nil</i>\n  <i class=k>return</i> err <i class=c>// returning a nil *MyError, but as an error interface</i>\n}\n\n<i class=function><i class=k>func</i> <i class=f>main</i><i class=p>()</i></i> {\n  err := doSomething()\n  fmt.Println(err == <i class=l>nil</i>) <i class=c>// false! — surprising, but explained above</i>\n}</code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThe practical takeaway from this trap is: when a function returns an interface type like <code>error</code>, and you want it to genuinely signal \"there's no error,\" return the literal <code>nil</code> directly, rather than a variable that happens to be a <code>nil</code> pointer of some concrete type. This small habit avoids one of the most notorious \"gotchas\" in the whole language.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">Combining Interfaces</h4>\n<p style=\"line-height: 1.75\">\nYou can build a bigger interface out of smaller ones by simply listing the smaller interfaces inside the bigger one, an idea called interface embedding (similar in spirit to struct embedding, covered earlier). But when deciding what type a function should return, lean toward a concrete struct (or a pointer to one) rather than an interface, since that gives the caller full, specific access to everything the struct offers, instead of artificially limiting them to only whatever a chosen interface happens to expose.\n</p>\n<div style=\"padding: 2px; This matters directly for interfaces too: if all of a type's methods use value receivers, both the plain value and a pointer to it satisfy any interface requiring those methods. But if even one required method uses a pointer receiver, only a pointer to that type satisfies the interface — a plain value does not, because it's missing that pointer-receiver method from its method set.\n</p>\n<div style=\"padding: 2px; border-radius: 8px; font-size: 14px\">\n<div class=\"code\"><div class=\"code-head\"><span>go</span><button class=\"copy\" type=\"button\">Copy</button></div><pre><code class=\"hljs\"><i class=k>type</i> Counter <i class=k>struct</i>{ count <i class=t>int</i> }\n\n<i class=function><i class=k>func</i> <i class=p>(c *Counter)</i></i> Increment() { c.count++ } <i class=c>// pointer receiver</i>\n\n<i class=k>type</i> Incrementer <i class=k>interface</i> {\n  Increment()\n}\n\n<i class=k>var</i> i Incrementer = &amp;Counter{} <i class=c>// works — *Counter satisfies Incrementer</i>\n<i class=c>// var j Incrementer = Counter{} // does NOT compile — Counter (value) doesn&#x27;t have Increment in its method set</i></code></pre></div>\n</div>\n<p style=\"line-height: 1.75; margin-top: 1.0rem\">\nThis is a common source of confusing compiler errors for newcomers, and it's a good reason to keep the earlier rule of thumb in mind: pick either all value receivers or all pointer receivers for a given type, and stay consistent, so you never have to puzzle over exactly which method set applies in a given situation.\n</p>\n<h4 style=\"margin-top: 1.5rem; font-size: 1.25rem; font-weight: 600; letter-spacing: -0.025em\">Interfaces as Parameters for Testing</h4>\n<p style=\"line-height: 1.75\">\nOne of the most practical, everyday benefits of interfaces shows up when writing tests.
